## Haskell strictness annotations（Haskell 严格性注解）

默认情况下，Haskell 会 abstracts away values 的 evaluation order，并且以 _lazily_ 的方式 evaluates，也就是说，只有当 values 需要被其他东西 computed 时，才会 evaluates 它们。这在许多情况下都很好，因为它让你能够 write elegant code，而不必担心 performing extraneous computations。另一方面，lazy evaluation 可能导致 memory-usage problems，因为它迫使你 store 一堆“thunks”——即 un-computed intermediate values——而不只是 final result。（例如，`sum [1, 1, 1, .... 1]` 将不得不 construct intermediate terms `1+1, (1+1)+1, ...`，并将它们 hold 在 memory 中，直到 final sum 被 requested。）

为了弥补这一点，Haskell 提供了一些相当简洁的方式来对 values 进行 [“forcing”（即 prematurely evaluating）](https://wiki.haskell.org/Performance/Strictness)，这些方式基于 `$!` infix operator、“BangPatterns” extension（它让你只需写下 `!x`，就能 force-evaluate `x`），以及 `seq` function。这用起来很好，因为你可以用它将 program 中任意少或任意多的部分 force 到 strict mode，而且使用起来非常容易（除了要在 file 顶部放上 `{# LANGUAGE BangPatterns #}`）。

唯一显而易见的潜在改进，是让 Haskell 将 compiler 的 strictness analysis 更 transparent 地呈现给 user。GHC 往往能够进行“strictness analysis”，以 determine thunks 最终是否会被 evaluated，并在它们导致 memory allocation 之前 force 它们。但很难判断 compiler 什么时候知道要 automatically force 一个 thunk，什么时候又必须被明确告知这样做。

## Julia JIT compiler（Julia 即时编译器）

在解决 transparency problem 方面做得很好的一种 language，是 Julia JIT compiler。这个 compiler 会在 compilation 期间执行各种精巧的 optimizations，但其中一些可能有点 fragile（例如，dependent on 是否存在 optional type annotations，由它们 creating 一个它知道如何 optimize 的特定 pattern）。幸运的是，为了这些目的，Julia exposes 了许多不同的 methods，用于 viewing 一个 method 的 generated code，[我的朋友 Leah 在这里介绍过它们](http://blog.leahhanson.us/julia-introspects.html)。你可以 view 从一个 function 的 abstract syntax tree，到它针对某一组 type arguments 的 specialization 所对应的 optimized machine code 的所有内容。对于 program 中少数需要更多 optimization 的部分，这让你能够脱离 dynamically-typed abstraction，实在是太棒了。

## Haskell strictness annotations

By default Haskell abstracts away the evaluation order of values and evaluates _lazily_, i.e., only evaluates values when they need to be computed by something else. This is great in many situations because it allows you to write elegant code without worrying about performing extraneous computations. On the other hand, lazy evaluation can cause memory-usage problems, because it forces you to store a bunch of “thunks”—un-computed intermediate values—not just the final result. (For instance, `sum [1, 1, 1, .... 1]` would have to construct the intermediate terms `1+1, (1+1)+1, ...` and hold them in memory until the final sum was requested.)

To compensate, Haskell has some quite concise ways of [“forcing” (i.e. prematurely evaluating)](https://wiki.haskell.org/Performance/Strictness) values, based on the `$!` infix operator, the “BangPatterns” extension (which lets you write just `!x` to force-evaluate `x`) and the `seq` function. This works great since you can use it to force as little or as much of your program into strict mode as you want and it’s very easy to use (modulo sticking `{# LANGUAGE BangPatterns #}` at the top of your file).

The only obvious potential improvement would be if Haskell made the compiler’s strictness analysis more transparent to the user. GHC can often do “strictness analysis” to determine that thunks will eventually be evaluated, and force them before they result in a memory allocation. But it’s hard to tell when the compiler knows to force a thunk automatically and when it must be told to.

## Julia JIT compiler

One language that solves the transparency problem well is the Julia JIT compiler. The compiler does all kinds of fancy optimizations during compilation, but some of them can be kind of fragile (e.g. dependent on the presence of optional type annotations creating a particular pattern that it knows how to optimize). Fortunately, for these purposes Julia exposes a bunch of different methods for viewing a method’s generated code, which [my friend Leah described here](http://blog.leahhanson.us/julia-introspects.html). You can view everything from the abstract syntax tree of a function, to the optimized machine code for its specialization to a certain set of type arguments. This is absolutely fantastic for dropping out of the dynamically-typed abstraction for the few parts of your program that require more optimization.
