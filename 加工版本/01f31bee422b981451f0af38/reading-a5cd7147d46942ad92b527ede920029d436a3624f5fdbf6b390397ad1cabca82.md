到现在，大家显然都已经看出，我停止了 BitC 的工作。关于_为什么_的解释，似乎早就该给出了。

一个答案是，我加入 Microsoft 时，Coyotos 的工作就停止了，而我_现在_专注的工作并不真正需要 BitC（似乎也无法从中受益）。众所周知，我们一生中能分配的时间终究有限。但仅凭这一点，还不足以让我彻底停下来。

第二个答案是，BitC 以目前的形式行不通。我碰到了几个问题，需要对 language 和 type system 进行彻底的 re-design，然后从头做一个新的 implementation。第一个 implementation 的经验表明，这会花上相当长的时间，而没有外部支持和资助，我实在无力承担这样的工作。Programming language 工作并不容易获得资助。

但第三个答案可能最令人感兴趣：从 language design 的角度看，我不再相信目前形式的 type classes 能够“work”。这是这里唯一重要的科学教训。

总体而言，目前的 design 有四个症结：

1.  compilation model 的问题。
2.  目前的 type system 在 by-reference 和 reference types 方面的 insufficiency。
3.  缺少某种形式的 inheritance。
4.  instance coherence problem 的问题。

在我看来，前两个问题是 solvable 的，尽管第二个需要对 compiler 进行近乎彻底的 re-implementation。最后一个（instance coherence）似乎不允许任何 general solution，而且它让我对使用 type classes 来实现 method overload 产生了 conceptual concerns。这个问题足够重要，因此我将在这里处理前三个主题，最后一个则另写一篇笔记讨论。

Inheritance 是 BitC 邮件列表上的人可能会激烈争论（有时也确实争论过）的话题。因此，先就这个话题简短说几句，或许有所帮助。

### 关于 Objects、Inheritance 和 Purity 的开场说明

BitC 最初被 designed 为一种 \[imperative\] functional language，因为我们关注的是 software verification。functional languages 的 typing 和 semantics 的 Specification，是一个有_很多_人在研究的领域。我们（作为一个研究领域）_算是_知道该怎么做，而我们在 Hopkins 的小组刚开始时，对这个领域了解并不多。Software verification 是一个 known-hard problem，在 imperative language 上做这件事已经是一项挑战，而对于一群初涉 language 研究的人来说，这似乎不是逆着领域当前潮流而行的好地方。看来，还是有所取舍为好。我们知道 inheritance 与 inference 之间存在 interactions_，_而通过巧妙的 compilation，type classes _似乎_能够达到许多相同的 operational results。因此，我很早就决定_不_在 language 中加入 inheritance。

对作为 programmer 的我来说，移除 inheritance 和 objects 是一个非常不情愿的决定，因为这牺牲了将大量现有 C++ code transcoding 到更 safe 的 language 的任何可能性。而事实证明，你无法真正从一个成功的 systems language 中移除底层的 semantic challenges。systems language _requires_ 某种用于 existential encapsulation 的 mechanism。体现这种 encapsulation 的 _mechanism_ 本身并不是真正的问题；一旦引入这种 encapsulation，就会牵涉到具有 subtyping 的 objects 所带来的大多数 verification 问题，而既然已经如此，你不妨也获得 objects 的好处。剩下的问题，本质上是 Self type 的 modeling；出于一系列原因，一旦引入 encapsulation，在 systems language 中拥有 Self type 就相当必要了。因此，_无论如何_，你最终都会在某个时候被推向 object type system。有了八年后的回望，我现在可以说，这完全是显而易见的！

我坚信，multiple inheritance 是一团糟。在我看来，关于 single inheritance 的赞成或反对之争，仍然主要是信仰问题。Inheritance 和 virtual methods 当然不是实现 encapsulation 的_唯一_方式，它们也未必是最好的 primitive mechanism。相比在 language design 的这一领域创新，我一直更感兴趣的是，把大量 software 带入一种 safe、high-performance 的 language。如果 transcoding 现有 code 算得上目标之一，我们就需要某种与 inheritance 非常相似的东西。

我们最初将 objects 排除在 BitC 之外的最后一个原因，是 purity。我想保留一种强大的 pure subset language——同样是为了让 verification 更容易。当时我所了解的 object languages 都是高度 stateful 的，我无法想象如何做出一种 non-imperative object-oriented language。事实上，对于 BitC 所关注的那些 applications，我_仍然_不确定自己是否知道如何切实做到这一点。但随着我们对 verification 价值的信心下降，我个人为了 verification 而继续受 purity 限制的意愿，也迅速减弱了。

支持 pure subset language 的_另一个_理由与推进 concurrency 有关，但当我真正开始深入研究 BitC 的 concurrency support 时，我越来越认为，这种处理 concurrency 的方式，并不适合人们实际试图解决的那类 concurrent problems；而在实践中，对 non-mutable state 的需求和使用，也远比 pure programming 方式所能应对的更加微妙复杂。Pure subprograms 显然发挥着重要作用，但它们还不够。

而且，我_仍然_不相信 monads。:-)

### Compilation Model（编译模型）

BitC 的目标之一，是在 conventional、static separate compilation scheme 下获得 acceptable performance。这也许是我目光短浅，但从 robustness 和 assurance 的角度看，run-time 时进行的 complex optimizations 让我非常不安。我知道，如今的 bytecode virtual machines 会进行非常 aggressive optimizations，而且取得了相当大的成功，但这也带来一些顾虑：

-   对于 robust language，我们希望 _minimize_ 那些免于 type checking 和\[最终的\] verification 的 code 的 size 和 complexity。Run-time code 就是以这种方式被豁免的。仅 garbage collector 本身就已经足够 large，足以引发 assurance 方面的顾虑。再往里面加上一个 large 且 complex 的 optimizer，会让 assurance 说辞的可信度大打折扣，其程度难以估量。
-   Run-time optimization 对 startup times 有非常不利的影响
-   尤其是在 transaction processing 的情境下。IBM（在 DB/2 中）和其他机构对此都有大量确凿数据。这也是“database 中的 Java”始终未能站稳脚跟的原因之一。随着 system 中 process 和 component instantiation 的 frequency 上升，startup delays 越来越令人担忧。Robust systems 不会 recycle subsystems。
-   Run-time optimization 会给 application 的 run-time environment 增加_巨量_的 space overhead。虽然 run-time compiler 的 _code_ 可以被 shared，但 run-time compiler 的 _state_ 不行，而且这种 state 相当多。
-   Run-time optimization——尤其是“on demand”进行时——会给 performance numbers 同时带来 variance 和 unpredictability。对于我所关注的某些 applications，我需要“steady state”performance。如果 code 正在被 optimized on the fly，即使它只提高了一个不大的 constant factor，real-time scheduling 也会开始成为一个非常令人困惑的挑战。
-   由 run-time optimizer _produced_ 的 Code 很难跨 address spaces 进行 share，不过，\*其他\* compilation approaches models 在这方面可能也解决得不太好。
-   如果存在 run-time optimization，applications 就会逐渐依赖它来获得 performance。也就是说：出于社会层面的原因，“optional”的 run-time optimization 往往很快就会变成必需的。

说清楚一点，我_并不_反对 continuous compilation。事实上，我认为这是个好主意，也认为有一些相当有说服力的 use-cases。我_确实_认为，run-time optimizer 应当用 strongly typed、safe 的 language 来 implemented。我_也_认为，hotspot technology 花了极其漫长的时间才 stabilize，而这需要被视为一个警示故事。我列举的许多问题和顾虑也很可能可以解决——但大概不会\*很快\*。对于对我最重要的 applications，assurance 方面的顾虑是首要的。因此，从 language design 的角度看，我很乐意利用 continuous compilation，但我不想 design 一种为了达到合理的 baseline performance 而 _requires_ continuous compilation 的 language。

当然，对于 conventional compilers，同样可以严肃地提出 optimizer complexity 的问题。你总要在_某个地方_进行 optimize。但我在 dynamic translation 方面的经验告诉我，一次只做一件事（并对其进行 reason about）要容易得多。一旦我们有了用 safe language 实现的 high-confidence optimizer，_到那时_，讨论将它 integrating 到 high-confidence system 的 run-time 中才可能有意义。在那之前，separation of concerns 应当是当下的准则。

现在，严格来说，应当指出，run-time compilation 对 BitC 或任何其他 bytecode language 而言，实际上并非必要。只有当你把 run-time loading 与 compiler-abstracted representations（见下文）结合起来，并允许具有 abstracted representation 的 types 出现在 run-time loaded libraries 的 signatures 中时，Run-time compilation 才变得必要。在那之前，仍然可以在 code generation 与 execution 之间维持适当的 phase separation。请继续读下去——我将在下面解释其中一些内容。

无论如何，我一开始就知道，strongly abstracted types 会在这个问题上引发顾虑，而我最初采取的是以下看法：

-   像 kernels 这样的东西可以被 whole-program compiled。这实际上消除了对 run-time optimizer 的要求。
-   像 critical system components 这样的东西，无论如何都希望被 statically linked，因此它们_也_可以作为 whole-program compilation 问题来处理。
-   至于其余的一切，我希望对 run-time compilation 采用某种“template expansion”方式。这不需要承担 optimizer 的全部 complexity；它只会 extend run-time linking 和 loading，以纳入 span 和 offset resolution。这仍然涉及大量 code，但并不是可怕地 _complex_ 的 code，而且这类东西适合进行 rigorous——甚至 formal——specification。

我花了好几年才意识到，template expansion 这个想法无法产生 acceptable baseline performance。问题在于 abstract types、operator overloading 和 inlining 之间的 interaction。

### Compiler-Abstracted Representations 与 Optimization 的对比

Types 具有 representations。这有时似乎让 PL community 中的某些成员有点不自在。仿佛是某种应该敬而远之的东西。非常像一个装满狗屎的密封袋（此处插入漫画）。从一个 systems 人士的角度来看，我很遗憾地告诉大家，bits 被 placed 在哪里、有多 big，以及它们的 assemblage，实际上_确实_很重要。如果你碰巧养狗，就会注意到，这里把“bits 比作狗屎”的比喻仍然很贴切。我们这些 systems 人士似乎命中注定要每天跋涉于 computational systems 的管道之中，所以这或许也不该让人意外。咳咳。

无论如何，PL community 将 representation 问题暂且搁置，以便先研究 type 问题。我不认为 pragmatics 被遗忘了，但我觉得可以公允地说，representation 问题并不是当前主流 PL research 的重点。甚至有一种观点把 representation 看成相当恶心的事情，认为应该在 compiler 中“像变魔术一样”处理它，而且 imperative operations 也应该如此处理。对于 systems code，这种办法行不通，因为我们需要处理的许多 representations 和 layouts 都是 hardware 强加给我们的。

无论如何，types _确实_具有 representations，而且即便是最简单的 compiler optimizations，也绝对离不开对这些 representations 的了解。因此，我们需要稍微小心一点，不要把 types 进行 abstract\* 得太 \* successfully_，_以免我们竟然破坏了 compilation model。

在 C 中，"+" operator 是 primitive，compiler 始终可以直接 select 适当的 opcode。其他“core” arithmetic operations 也类似。现在来试一个 thought experiment：假设我们把一个 program 中对这类 core operations 的每一次使用，都 replace 为一次对 runtime-implemented intrinsic 的 functionally equivalent procedure call。你只需要对 _user_ operations 这样做——compiler 为 perform address arithmetic 之类的事情而引入的 addition，始终是在 concrete types 上完成的，因此那些仍然可以被 generated efficiently。不过，即便只对 user operations 这样做，也显然会严重损害 program 的 performance。你_可以_用 run-time optimizer 来 recover 那些 performance，但这很 complicated。

在 C++ 中，"+" operator 可以被 overloaded。但 (1) primitive types 的 bindings 不能被 replaced，(2) 对于其他 types，我们 statically 知道其 bindings 和 representations _是_什么，以及 (3) 我们可以通过 inlining 来 control 那些 operations 中的哪些会在 run time 产生 procedure call。我并不是想说，我们希望被迫 manually control 这些。关键在于，compiler 对 operation 的 implementation 有足够的 visibility，因此可以在 static compile time 对 primitive operators（以及其他许多 operators）进行 inline。

为什么这在 C++ 中可行，在 BitC 中却不行？

在 C++ 中，abstract type（即 template）的 instantiation 发生于这样一个 environment：compiler 可以看到所涉及的 representations 的全部信息。那些 information 可能并非全都对 programmer 处于 in scope，但 compiler 可以跨越 scopes 去追踪，找到所有 pieces，将它们 assemble 在一起，并理解它们的 shapes。这就促成了 C++ 的“explicit instantiation” model。这也导致大量“internal” type declarations 和 implementation code 迁入 header files，往往会 constrain templates 的使用，并 increase 每个 compilation unit 所需 processed 的 header file lines 数量——我们曾在一个非常早期（早于 templates）的 C++ 产品上进行 measured，发现每一行“source”都需要 processed 超过 150 行 header lines。此后，这个 ratio 至少增长到了原来的十倍，而且（由于 templates）很可能是 20 倍。

这一切都相当烦人，但正是它使 static-compile-time template expansion 成为可能。从 _compiler_ 的角度来看，涉及的 types（更重要的是 representations）根本没有被 abstracted。在 BitC 中，这两者_都_在 static compile time 被 abstracted。直到 link time，所有 representations 才会全部就绪。

正如我上面所说，我们可以设想通过 extending linkage model 来处理这一点。提供所有那些 header file information，是为了处理 \* representation\* 问题，而不是 type checking。Representation 归根结底就是 sizes、alignments 和 offsets。即使我们不知道 concrete values，我们也_确实_知道它们全都是 compile-time constants，而且我们需要在 compile time 进行 compute 的 results，完全由这些 constants 的 sums 和 multiples 构成。我们可以设想，在 static compile time 将它们作为 _opaque_ constants 处理，并在 link time 填补空缺。这差不多就是我所说的 link-time template expansion 的意思。从概念上说：把所有 offsets 和 sizes 留作“空白”，依靠 linker 将它们填入，很像它处理 relocation 的方式。

这种办法的问题在于，它移除了 optimization 和 registerization 所需的关键信息，而且不 support inlining。在 BitC 中，我们可以_而且确实_将这类 instantiation 一直 extend 到 primitive operators！或许更重要的是，还 extend 到 primitive accessors 和 mutators。原因是，我们希望能够写出像“a + b”这样的 expressions，并说“只要存在对 +:('a,'a)->'a 的适当 resolution，那个 expression 就是 well-typed”。这是一种很好的对 operation 进行 _type_ 的方式，但它让 'a 的 representation 保持 fully abstracted。这意味着，我们无法看出它们何时是 primitive types。这又意味着，我们_恰好_（或者说，无论如何，太多时候）落到了不得不把_所有_ user-originated "+" operations 都 generating 为 procedure calls 的境地。令人意外的是，这其实还不是世界末日。我们可以设想发明某种“high-level assembler”，让我们的 static code generator 知道如何将它 translate 为 machine code。如果 static code generator 这样做，就可以让 run-time loader 负责 emitting procedure calls，并在适当位置 substitute intrinsic calls。这会使我们失去 code sharing，但在 non-embedded targets 上或许可以容忍。

不幸的是，这种 high-level assembler 对 optimization 有一些相当棘手的影响：首先，出于 optimization 的目的，我们不再知道 "+" operator 的 \* cost\* 是多少。我们不知道某一次对 + 的使用会耗费多少 cycles，但更重要的是，我们不知道它会 emit 多少 bytes 的 code。而没有那些 information，我们就无法再在 static compile time 作出一长串 optimization decisions。其次，在 static code generation time，我们不再有足够的 information 来 perform 一长串 _basic_ register 和 storage optimizations，因为我们不知道哪些 procedure calls 实际上会 use registers。

你听到的吱嘎声和呻吟声，就是 run-time code generator 在不断膨胀的同时变得臃肿、失去 reliability 的声音。虽然这种 mechanism 的影响实际上不会像我描绘的那么糟——因为许多 user types _并不是_ abstract——但这个 mechanism 的 _complexity_ 确实和我所说的一样糟糕。实际上，我们最终把 code generation 和 optimization 都 deferring 到了 link time。这个想法（至少）可以追溯到 David Wall 在 mid-1980s 关于 link time register optimization 的工作。此后，人们探索了它的许多 variants。这是个很有吸引力的想法，但有利也有弊。

这里的情况是，对于 static compilation 而言，BitC 中的 types 被 abstracted 得_过于_ successfully 了。结果就是一袋相当_大_的狗屎，所以也许 PL 那些人的想法确实有点道理。:-)

### 两种 Solutions

-   最显而易见的 solution——也是 C++ 采用的——是 redesign 这个 language，使 representation issues 不再对 compiler 隐藏。这确实是一个值得考虑的 solution。C++ 中的问题与其说是每个 source line 对应的 header file lines 数量，不如说是 C preprocessor 要求我们为每个 compilation unit 都 _重新_ process 这些 lines。BitC 中（有意地）没有任何与 C preprocessor 相当的东西。
-   另一种可能是转向一种可以称为“install time compilation”的方式。交付某种形式的 byte code，并在 install time 进行 static compilation。这能让你重新获得 classical compilation approach 理应带来的所有 code sharing 和 optimization；从 systems 的角度看，它提供了一些有趣的 design point 选项，而且（只要谨慎处理）还可以被 retrofitted 到 existing systems 中。如今有些 platforms（尤其是 cell phones）上，我们基本上已经在这样做了。

这里你不想跨越的 design point，是 loaded interface 携带着具有 abstracted representation 的 type 时的 dynamic _loading_。一旦到了那一步，你实际上就不得不采用 run-time code generation_，_不过我确实有一些缓解这一问题的想法。

### 关于 Compilation Model 的 Conclusion

**如果 static, separate compilation 是一项 requirement，那么每当使用 abstract type 时，compiler 就必须能够跨越 module boundaries 查看 source code。也就是说：任何具有 abstract type 的 procedure，都必须拥有 exposed source-level implementation。**

**切实可行的 alternative 是将 high-level intermediate form 与 install-time 或 run-time code generation 结合起来。这当然是可行的，但超出了我当时觉得自己能够承担的范围。**

这些都是可以处理、可以做到的。遗憾的是，这并不是我们原先走的路，所以基本上就意味着从头再来。

### Type System 的 Insufficiency

到某个阶段，BitC 已经有足够多的部分能够工作，让我们可以开始 building library code。我们在 library 中首先着手做的是 IO，这也许不会让你感到意外。我们发现，在这个 type system 中无法 handle typed input。为什么呢？

即使你准备在 IO library 中进行 dynamic allocation，也存在这样一个 level of abstraction：你需要 implement 一个相当于“inputStream.read(someObject: ByRef mutable 'a)”的 operation。对此有几种 variations，但关键是，你希望能够在某个时候把 incoming bytes move 到 previously allocated storage 中。到这里为止，一切都还好。

遗憾的是，为了限制 type system 中的 creeping featurism，我曾宣称（事实证明，这并不明智），我们唯一需要处理 ByRef types 的地方就是 parameters。Swaroop 对这句话的字面理解比我的本意更严格一些。他注意到，如果这 _确实_ 是唯一需要处理 ByRef 的地方，那么在内部就可以把“ByRef 'a”当作 'a，只需在 parameter 的 identifier record 上保留一个 marker，以表明在 code generation time 需要额外的 dereference。这实际上相当巧妙，只是它不能很好地 extend 到 type classes 与其 instances 之间的 signature matching。由于 _read_ 的 argument type 是 _ByRef 'a_，InputStream 就是这样一个 type class。

于是，我们现在面临着几个问题。首先，我们需要让 ByRef 'a 在 compiler 中成为 first-class type，以便能够对它进行 unify；其次，我们需要处理由此带来的 implicit coercion issues。也就是说：在 copy boundaries 处，在 ByRef 'a 与 'a 之间来回 conversion。coercion 这部分还不算太糟；ByRef 从来不会被 inferred，而与 ByRef 相关的 type coercions，发生的位置恰好与 const/mutable coercions 完全相同。我们在 type checker 中已经有一个 cleanly isolated 的位置来处理这一点。

但即使 ByRef 不会被 inferred，它仍然可以通过 unification 在 code 中 propagate。而 _这_ 会 causes safety violations！ByRef 被 syntactically restricted 为只能出现在 parameters 处，这就（有意地）确保了与 references into the stack 的 lifespan 相关的 safety restrictions 得到遵守——这正是我最初施加 ByRef 只能出现在 parameters 处这一 restriction 的原因。一旦 ByRef type 可以 unify，syntactic restriction 就不再 guarantees lifespan restriction 的 enforcement。要理解原因，请考虑以下情形中会发生什么：

```
  define byrefID(x:ByRef 'a) { return x; }
```

一个 _本应_ 是 downward-only reference 的东西，最终却被 returned up the stack。Swaroop 的 solution 之所以巧妙，部分原因在于它悄然 prevented 了这个 propagation problem。从某种意义上说，他的 implementation 并没有真正把 ByRef 当作 type，因此它不能 propagate。但 \*正因为 \*他没有把它当作 type，我们也就无法在 instances 与 type classes 之间进行必要的 matching check。

事实证明，能够这样做是 _useful_ 的。abstract mutable “property”（按 C# 中的含义）的 essential requirement，是我们能够在 language 中 construct 一个 function，让它 returns 待 mutated 之物的 _location_。这个 location 往往位于 stack 上，因此 returning 这个 location 与上面的例子 _完全_ 一样。“ByRef 仅限于 parameters”这一 restriction 实际上非常 conservative，而且我们知道，它阻止了我们最终想做的某些事情。我们曾有一个模糊的想法：以后再回来，通过 introducing region types 来 fix 这个问题。

结果，“以后”不得不变成“现在”，因为当 ByRef types 成为 first class 时，region types 才是 re-instate lifetime safety 的正确方式。但 _adding_ region types 带来了两个问题（这也正是我们原本希望推迟它们的原因）：

-   Adding region types 意味着 rewriting type checker，并 re-verifying inference algorithm 的 soundness 和 completeness，_而且_
-   这不只是一次 re-write。Regions 会 introduce subtyping。Subtyping 与 polymorphism 无法很好地相处，因此我们需要回头做大量研究。

带有 region subtyping 的 Region polymorphism 当然以前就已经有人做过，但我们在另一种情形中也遇到了 subtyping（见下文）。这正在把我们推向 kinding system 和一个不同的 type system。

因此，要 fix ByRef 问题，我们几乎需要从头 re-design type system 和 compiler 两者。考虑到 compiler 中积累的 cruft，无论如何这也许都是件好事，但 Swaroop 此时已在 Microsoft 全职工作，而我没有时间或资源独自处理这件事。

### 关于 Type System 的结论

**回过头来看，很难想象一种 strongly typed imperative language 不以 first-class 的方式对 locations 进行 type。如果这种 language 同时 supports explicit unboxing，它实际上就不得不处理 location lifespan 和 escape issues，这使得某种形式的 memory region typing 几乎不可避免。**

**即使没有其他原因，仅凭这一点，带有 unboxing 的 imperative language 的 type system 就必须 incorporate 某种形式的 subtyping。为了 ensure termination，这对 type inference 的使用施加了一些 constraints。好的一面是，一旦你 introduce subtyping，就能够在 language 中做许多有用的事情，而没有它，这些事情就很难做到。**

### Inheritance 与 Encapsulation

我们第一次遇到 inheritance 的麻烦，实际上是在 compiler 本身中。尽管我们尽了最大努力，BitC compiler 的 C++ implementation 仍未完全避免 inheritance，因此它无法直接 translation 成 BitC。而且，即使我们修改了 compiler 的 code，仍有大量 third-party libraries 是我们希望能够 transcode 的。其中很多依赖于 \[single\] inheritance。如果没有至少某种形式的 interface (type) inheritance，我们甚至无法真正做好与这些作为 foreign objects 的 libraries 的 interfacing。

撇开 compiler 不谈，我们还需要一种用于 encapsulation 的 mechanism。我一直在尝试 "capsules"，但很快就发现，capsules 实际上是 subclassing 的一种 degenerate form，而试图回避这个问题并不会让我取得任何进展。

我几乎可以想象，通过添加 "ThisType" 和 inherited _interfaces_ 来得到我所需要的东西。但这两个 features 的 combination 会 introduces subtyping。事实上，从 type system 的角度来看，这种 combination 与 single-inheritance subclassing 是 equivalent 的。

而且，我越是仔细审视 interfaces，就越开始问自己：为什么一个 interface 不就是一个 type class 呢？_这_让我从一个新的方向撞上了 instance coherence problem，而这个问题本来就已经让我头疼了。这也让我意识到，Interfaces 之所以能 work，部分原因在于它们总是 parameterized over a single type（即 ThisType）——一旦知道了这一个，所有其他的 bindings 就都由 type constructors 或 explicit specification 来 determined。

而 introducing SelfType 是比 introducing subtypes 更大的问题。这意味着完全离开 System F<:，进入 Cardelli _等人_的 object type system。这不只是 re-implementing type checker，以 support 我们已有的 type system 的某个 variant 的问题。这意味着完全 re-formalizing type system，并学习如何在一个不同的 model 中思考。

可以做到，但时间上无法在我们已经建立的 framework 或 compiler 内完成。到了这一步，我决定需要重新开始。我们从 BitC 工作的各个部分学到了很多，但有时必须先退一步，才能再向前迈出更多步。

### Instance Coherence 与 Operator Overloading

BitC 的 type classes 主要借鉴自 Haskell。Type classes 不只是 type qualifiers 的基础；它们提供了用于 \*ad hoc\*polymorphism 的 mechanism。无论 language purists 怎么说，真正的 languages 确实需要这一 feature。

问题在于，对于给定 type 上的给定 type class，可能存在多个 type class instances。因此，最终可能得到这样一个 function：

```
define f(x : 'x) {
  ...
  a:int32 + b  // typing fully resolved at static compile time
  return x + x  // typing not resolvable until instantiation
}
```

Problem：当 'x instantiates 为 _int32_ 时，我们不知道该 use "+" 的哪一个 instance。为了让 "+" 在 a+b 中是 meaningful 的，我们需要对 +:(int32, int32)->int32 进行 static-compile-time resolution。而我们从 Arith(int32) 得到它。到这里还好。但如果 'x 被 instantiated 为 _int32_，我们就会得到一个由 caller 提供的 type class instance。问题在于，没有办法保证这与我们先前见到的 Arith(int32) 的 instance 是 _same_ 的。

Haskell 中的 solution 是施加这样一条 _ad hoc_ rule：在给定 application 中，对于每个 unique type tuple，你只能 instantiate 一个 type class 一次。这与 C++ 中的做法是 similar 的：对于 particular type 上的给定 global operator，你只能有一个 overload。如果那个 type 上有不止一个 overload，就会出现 link-time failure。这种 restriction 在 C++ 中尚可容忍，主要是因为 operator overloading 非常 limited：

1.  overloadable operators 的 set 是 small 且 non-extensible 的。
2.  其中大多数都可以作为 methods 得到令人满意的处理，这使得它们的 resolution 是 unambiguous 的。
3.  那些_不能_作为 methods 处理的，大多数是 arithmetic operations，而人们希望 extend 它们到何种程度，在实践中是有限的。
4.  其余 highly overloaded global operators 都与 I/O 相关。在 suitably polymorphic language 中，它们_可以_是 methods。

在允许更丰富地使用 operator overloading 的 languages（如 BitC）中，这些 properties 似乎不太可能足够。

但在 Haskell 和 BitC 中，overloading 也被 extended 到了 _type properties_。例如，有一个 type class "Ord 'a"，它表明一个 type 'a 是否 admits 一个 ordering。Problem：大多数 admit ordering 的 types 都 admit 不止一个！知道某个 ordering _exists_，实际上并不足以告诉我们该 _use_ 哪个 ordering。而且，在 Haskell 或 BitC 中，我们无法为 'a introduce _两个_ orderings 而不 creating 一个 instance coherence problem。归根结底，instance coherence problem 之所以 exists，是因为 language design 以一种实质上 non-scoped 的方式 performs method resolution。

但至少，希望你能看出，BitC 和 Haskell 中对 overloading 更大量的使用，给 "single instance" rule 带来了高得多的压力。在我看来，这足以使那条 rule 无法成立。而且，由于我来自 capability 领域，我对那些带有 ambient authority 气味的东西极为反感。

现在，通过对一个 instance 可以在哪里（哪个 compilation unit）合法地被 defined 施加任意 restriction，我们可以在一定程度上绕过这个问题。但与 "excessively abstract types" 问题一样，我们似乎一直在 type class 问题上栽跟头。当 multi-variable type classes 也牵涉进来时，还会有其他问题。

归根结底，如果没有其他形式的支持，type classes 作为 overload resolution 的 mechanism，似乎就是不太行得通。

type classes 的第二个问题是，你无法在 static compile time 进行 resolve operators。而且，如果 instances 被 explicitly named，对 instances 的 references 就容易变成 first-class values。到了那一步，operator reference 就再也无法被 statically resolved，而我们实际上又重新发明了 operator methods！

### 关于 Type Classes 和 Overloading 的 Conclusion：

**type class notion（更准确地说：qualified types）很诱人，但如果没有合理的方法来处理 instance coherence 和 lexical resolution，它就无法为 operator overloading 提供令人满意的 basis。type class instances 与 object instances 之间存在一种令人不安的密切 relationship，需要 PL community 进一步探索。重要的 distinction 可能是 pragmatic 而非 conceptual 的：type class instances 是 compile-time constants，而 object instances 是 run-time values。这对 typing 没有重大影响，但会导致 naming、binding 和 \[human\] conceptualization 方面的显著 differences。**

**multi-parameter type classes 仍然存在 unresolved formal issues。其中许多似乎在 polymorphic object type system 中都有自然的 practical solutions，但 implementation 方面的顾虑促使我们在 boxed 和 unboxed types 之间作出 kinding distinctions，而这些 distinctions 相当令人不满意。**

### 收尾

目前的结果让人_极其_沮丧。虽然这里确实存在盲点，但 academic research community 的要求迫使我们花了近三年时间，寻找对 mutability 进行 complete inference 的方法。那是一项巨大的工作，也推迟了我们意识到自己所依托的 underlying type system 的种类完全错误的时间。虽然我仍然认为 mutability inference 有一定价值，但我觉得，原来的 inference mechanism 中一个相当微不足道的瑕疵，竟然因为实质上属于_政治_层面的原因而阻碍了整个项目取得更大规模的成功，实在令人遗憾。如果没有那件分散精力的事，我想我们很可能早已充分了解 I/O 和 instance coherency 问题，并在我们还有团队能够一起开展这项工作时，转向另一种 type system；这样，今天我们就会拥有一种能用且有用的 language。

撇开学术界那些分散精力的事情不谈，问问我们为什么没有构建小型的“concept test” programs，来对我们的 design 作 sanity check，是合理的。原因有好几个，但没有一个十分令人满意：

-   Research languages 可以对 primitive types（尤其是 integers）采用 simplifications，而 systems languages 不能。正是这一点最初把我们推向了 type classes；我们知道，针对 unboxed types 的 polymorphism 在 literature 中尚未受到太多关注，也知道 mutability inference 从未有人做过。我们人手有限，因此选择先专注于那些问题。
-   我们知道 parametric polymorphism 和 subtyping 无法很好地共存，因此想避免这种 combination。不幸的是，我们对 subtypes 回避得太彻底、太久了，而事实证明它们是不可避免的。
-   最初几年，我们非常关注 software verification，这_也_强烈地推动我们远离 object-based languages 和 subtyping。这蒙蔽了我们。
-   我们以“systems”人员的身份进入 language design 领域，又在一个缺乏 type systems 方面深厚专业知识和兴趣的系里工作，因此有大量的专业内容需要学习。我们失败的某些原因，对 PL community 的人来说是“显而易见的”，但另一些并非如此。我们对“systems” language 的追求，促使我们以不同于 PL community 通常采用的方式和优先次序来探索这一 space。

我认为我们确实作出了一些有意思的贡献。我们现在知道如何在实现显著 code sharing 的同时，对 unboxed types 进行 polymorphism（也就是说：如何 implement 它），也理解了如何处理 inferred mutability。这两点将来都会非常有用。我们还学到了大量关于 advanced type systems 的知识。

无论如何，BitC 目前的形态显然需要搁置并重新加工。我对如何着手_继续_这项工作已经有了相当清晰的想法，但这必须等到有人愿意为这一切付钱的时候。

## 原文

_This is an archive of the Jonathan Shapiro's "Retrospective Thoughts on BitC" that seems to have disappeared from the internet; at the time, BitC was aimed at the same niche as Rust_

```
Jonathan S. Shapiro shap at eros-os.org
Fri Mar 23 15:06:41 PDT 2012
```

By now it will be obvious to everyone that I have stopped work on BitC. An explanation of _why_ seems long overdue.

One answer is that work on Coyotos stopped when I joined Microsoft, and the work that I am focused on _now_ doesn't really require (or seem to benefit from) BitC. As we all know, there is only so much time to go around in our lives. But that alone wouldn't have stopped me entirely.

A second answer is that BitC isn't going to work in its current form. I had hit a short list of issues that required a complete re-design of the language and type system followed by a ground-up new implementation. Experience with the first implementation suggested that this would take quite a while, and it was simply more than I could afford to take on without external support and funding. Programming language work is not easy to fund.

But the third answer may of greatest interest, which is that I no longer believe that type classes "work" in their current form from the standpoint of language design. That's the only important science lesson here.

In the large, there were four sticking points for the current design:

1.  The compilation model.
2.  The insufficiency of the current type system w.r.t. by-reference and reference types.
3.  The absence of some form of inheritance.
4.  The instance coherence problem.

The first two issues are in my opinion solvable, thought the second requires a nearly complete re-implementation of the compiler. The last (instance coherence) does not appear to admit any general solution, and it raises conceptual concerns about the use of type classes for method overload in my mind. It's sufficiently important that I'm going to deal with the first three topics here and take up the last as a separate note.

Inheritance is something that people on the BitC list might (and sometimes have) argue about strongly. So a few brief words on the subject may be relevant.

### Prefacing Comments on Objects, Inheritance, and Purity

BitC was initially designed as an \[imperative\] functional language because of our focus on software verification. Specification of the typing and semantics of functional languages is an area that has a _lot_ of people working on it. We (as a field) _kind_ of know how to do it, and it was an area where our group at Hopkins didn't know very much when we started. Software verification is a known-hard problem, doing it over an imperative language was already a challenge, and this didn't seem like a good place for a group of novice language researchers to buck the current trends in the field. Better, it seemed, to choose our battles. We knew that there were interactions between inheritance and inference_,_ and it _appeared_ that type classes with clever compilation could achieve much of the same operational results. I therefore decided early _not_ to include inheritance in the language.

To me, as a programmer, the removal of inheritance and objects was a very reluctant decision, because it sacrificed any possibility of transcoding the large body of existing C++ code into a safer language. And as it turns out, you can't really remove the underlying semantic challenges from a successful systems language. A systems language _requires_ some mechanism for existential encapsulation. The _mechanism_ which embodies that encapsulation isn't really the issue; once you introduce that sort of encapsulation, you bring into play most of the verification issues that objects with subtyping bring into play, and once you do that, you might as well gain the benefit of objects. The remaining issue, in essence, is the modeling of the Self type, and for a range of reasons it's fairly essential to have a Self type in a systems language once you introduce encapsulation. So you end up pushed in to an object type system at some point in _any_ case. With the benefit of eight years of hindsight, I can now say that this is perfectly obvious!

I'm strongly of the opinion that multiple inheritance is a mess. The argument pro or con about single inheritance still seems to me to be largely a matter of religion. Inheritance and virtual methods certainly aren't the _only_ way to do encapsulation, and they may or may not be the best primitive mechanism. I have always been more interested in getting a large body of software into a safe, high-performance language than I am in innovating in this area of language design. If transcoding current code is any sort of goal, we need something very similar to inheritance.

The last reason we left objects out of BitC initially was purity. I wanted to preserve a powerful, pure subset language - again to ease verification. The object languages that I knew about at the time were heavily stateful, and I couldn't envision how to do a non-imperative object-oriented language. Actually, I'm _still_ not sure I can see how to do that practically for the kinds of applications that are of interest for BitC. But as our faith in the value of verification declined, my personal willingness to remain restricted by purity for the sake of verification decayed quickly.

The _other_ argument for a pure subset language has to do with advancing concurrency, but as I really started to dig in to concurrency support in BitC, I came increasingly to the view that this approach to concurrency isn't a good match for the type of concurrent problems that people are actually trying to solve, and that the needs and uses for non-mutable state in practice are a lot more nuanced than the pure programming approach can address. Pure subprograms clearly play an important role, but they aren't enough.

And I _still_ don't believe in monads. :-)

### Compilation Model

One of the objectives for BitC was to obtain acceptable performance under a conventional, static separate compilation scheme. It may be short-sighted on my part, but complex optimizations at run-time make me very nervous from the standpoint of robustness and assurance. I understand that bytecode virtual machines today do very aggressive optimizations with considerable success, but there are a number of concerns with this:

-   For a robust language, we want to _minimize_ the size and complexity of the code that is exempted from type checking and \[eventual\] verification. Run-time code is excepted in this fashion. The garbage collector taken alone is already large enough to justify assurance concerns. Adding a large and complex optimizer to the pile drags the credibility of the assurance story down immeasurably.
-   Run-time optimization has very negative consequences for startup times
-   especially in the context of transaction processing. Lots of hard data on this from IBM (in DB/2) and others. It is one of the reasons that "Java in the database" never took hold. As the frequency of process and component instantiation in a system rises, startup delays become more and more of a concern. Robust systems don't recycle subsystems.
-   Run-time optimization adds a _huge_ amount of space overhead to the run-time environment of the application. While the _code_ of the run-time compiler can be shared, the _state_ of the run-time compiler cannot, and there is quite a lot of that state.
-   Run-time optimization - especially when it is done "on demand" - introduces both variance and unpredictability into performance numbers. For some of the applications that are of interest to me, I need "steady state" performance. If the code is getting optimized on the fly such that it improves by even a modest constant factor, real-time scheduling starts to be a very puzzling challenge.
-   Code that is _produced_ by a run-time optimizer is difficult to share across address spaces, though this probably isn't solved very well by \* other\* compilation approaches models either.
-   If run-time optimization is present, applications will come to rely on it for performance. That is: for social reasons, "optional" run-time optimization tends to quickly become required.

To be clear, I'm _not_ opposed to continuous compilation. I actually think it's a good idea, and I think that there are some fairly compelling use-cases. I _do_ think that the run-time optimizer should be implemented in a strongly typed, safe language. I _also_ think that it took an awfully long time for the hotspot technology to stabilize, and that needs to be taken as a cautionary tale. It's also likely that many of the problems/concerns that I have enumerated can be solved - but probably not \* soon\*. For the applications that are most important to me, the concerns about assurance are primary. So from a language design standpoint, I'm delighted to exploit continuous compilation, but I don't want to design a language that _requires_ continuous compilation in order to achieve reasonable baseline performance.

The optimizer complexity issue, of course, can be raised just as seriously for conventional compilers. You are going to optimize _somewhere_. But my experience with dynamic translation tells me that it's a lot easier to do (and to reason about) one thing at a time. Once we have a high-confidence optimizer in a safe language, _then_ it may make sense to talk about integrating it into the run-time in a high-confidence system. Until then, separation of concerns should be the watch-word of the day.

Now strictly speaking, it should be said that run-time compilation actually isn't necessary for BitC, or for any other bytecode language. Run-time compilation doesn't become necessary until you combine run-time loading with compiler-abstracted representations (see below) and allow types having abstracted representation to appear in the signatures of run-time loaded libraries. Until then it is possible to maintain a proper phase separation between code generation and execution. Read on - I'll explain some of that below.

In any case, I knew going in that strongly abstracted types would raise concerns on this issue, and I initially adopted the following view:

-   Things like kernels can be whole-program compiled. This effectively eliminates the run-time optimizer requirement.
-   Things like critical system components want to be statically linked anyway, so they can _also_ be dealt with as whole-program compilation problems.
-   For everything else, I hoped to adopt a kind of "template expansion" approach to run-time compilation. This wouldn't undertake the full complexity of an optimizer; it would merely extend run-time linking and loading to incorporate span and offset resolution. It's still a lot of code, but it's not horribly _complex_ code, and it's the kind of thing that lends itself to rigorous - or even formal - specification.

It took several years for me to realize that the template expansion idea wasn't going to produce acceptable baseline performance. The problem lies in the interaction between abstract types, operator overloading, and inlining.

### Compiler-Abstracted Representations vs. Optimization

Types have representations. This sometimes seems to make certain members of the PL community a bit uncomfortable. A thing to be held at arms length. Very much like a zip-lock bag full of dog poo (insert cartoon here). From the perspective of a systems person, I regret to report that where the bits are placed, how big they are, and their assemblage actually _does_ matter. If you happen to be a dog owner, you'll note that the "bits as dog poo" analogy is holding up well here. It seems to be the lot of us systems people to wade daily through the plumbing of computational systems, so perhaps that shouldn't be a surprise. Ahem.

In any case, the PL community set representation issues aside in order to study type issues first. I don't think that pragmatics was forgotten, but I think it's fair to say that representation issues are not a focus in current, mainstream PL research. There is even a school of thought that views representation as a fairly yucky matter that should be handled in the compiler "by magic", and that imperative operations should be handled that way too. For systems code that approach doesn't work, because a lot of the representations and layouts we need to deal with are dictated to us by the hardware.

In any case, types _do_ have representations, and knowledge of those representations is utterly essential for even the simplest compiler optimizations. So we need to be a bit careful not to abstract types\* too \* successfully_,_ lest we manage to break the compilation model.

In C, the "+" operator is primitive, and the compiler can always select the appropriate opcode directly. Similarly for other "core" arithmetic operations. Now try a thought experiment: suppose we take every use of such core operations in a program and replace each one with a functionally equivalent procedure call to a runtime-implemented intrinsic. You only have to do this for _user_ operations - addition introduced by the compiler to perform things like address arithmetic is always done on concrete types, so those can still be generated efficiently. But even though it is only done for user operations, this would clearly harm the performance of the program quite a lot. You _can_ recover that performance with a run-time optimizer, but it's complicated.

In C++, the "+" operator can be overloaded. But (1) the bindings for primitive types cannot be replaced, (2) we know, statically, what the bindings and representations _are_ for the other types, and (3) we can control, by means of inlining, which of those operations entail a procedure call at run time. I'm not trying to suggest that we want to be forced to control that manually. The key point is that the compiler has enough visibility into the implementation of the operation that it is possible to inline the primitive operators (and many others) at static compile time.

Why is this possible in C++, but not in BitC?

In C++, the instantiation of an abstract type (a template) occurs in an environment where complete knowledge of the representations involved is visible to the compiler. That information may not all be in scope to the programmer, but the compiler can chase across the scopes, find all of the pieces, assemble them together, and understand their shapes. This is what induces the "explicit instantiation" model of C++. It also causes a lot of "internal" type declarations and implementation code to migrate into header files, which tends to constrain the use of templates and increase the number of header file lines processed for each compilation unit - we measured this at one point on a very early (pre templates) C++ product and found that we processed more than 150 header lines for each "source" line. The ratio has grown since then by at least a factor of ten, and (because of templates) quite likely 20.

It's all rather a pain in the ass, but it's what makes static-compile-time template expansion possible. From the _compiler_ perspective, the types involved (and more importantly, the representations) aren't abstracted at all. In BitC, _both_ of these things _are_ abstracted at static compile time. It isn't until link time that all of the representations are in hand.

Now as I said above, we can imagine extending the linkage model to deal with this. All of that header file information is supplied to deal with \* representation\* issues, not type checking. Representation, in the end, comes down to sizes, alignments, and offsets. Even if we don't know the concrete values, we _do_ know that all of those are compile-time constants, and that the results we need to compute at compile time are entirely formed by sums and multiples of these constants. We could imagine dealing with these as _opaque_ constants at static compile time, and filling in the blanks at link time. Which is more or less what I had in mind by link-time template expansion. Conceptually: leave all the offsets and sizes "blank", and rely on the linker to fill them in, much in the way that it handles relocation.

The problem with this approach is that it removes key information that is needed for optimization and registerization, and it doesn't support inlining. In BitC, we can _and do_ extend this kind of instantiation all the way down to the primitive operators! And perhaps more importantly, to primitive accessors and mutators. The reason is that we want to be able to write expressions like "a + b" and say "that expression is well-typed provided there is an appropriate resolution for +:('a,'a)->'a". Which is a fine way to _type_ the operation, but it leaves the representation of 'a fully abstracted. Which means that we cannot see when they are primitive types. Which means that we are _exactly_ (or all too often, in any case) left in the position of generating _all_ user-originated "+" operations as procedure calls. Now surprisingly, that's actually not the end of the world. We can imagine inventing some form of "high-level assembler" that our static code generator knows how to translate into machine code. If the static code generator does this, the run-time loader can be handed responsibility for emitting procedure calls, and can substitute intrinsic calls at appropriate points. Which would cause us to lose code sharing, but that might be tolerable on non-embedded targets.

Unfortunately, this kind of high-level assembler has some fairly nasty implications for optimization: First, we no longer have any idea what the \* cost\* of the "+" operator is for optimization purposes. We don't know how many cycles that particular use of + will take, but more importantly, we don't know how many bytes of code it will emit. And without that information there is a very long list of optimization decisions that we can no longer make at static compile time. Second, we no longer have enough information at static code generation time to perform a long list of _basic_ register and storage optimizations, because we don't know which procedure calls are actually going to use registers.

That creaking and groaning noise that you are hearing is the run-time code generator gaining weight and losing reliability as it grows. While the impact of this mechanism actually wouldn't be as bad as I am sketching - because a lot of user types _aren't_ abstract - the _complexity_ of the mechanism really is as bad as I am proposing. In effect we end up deferring code generation and optimization to link time. That's an idea that goes back (at least) to David Wall's work on link time register optimization in the mid-1980s. It's been explored in many variants since then. It's a compelling idea, but it has pros and cons.

What is going on here is that types in BitC are _too_ successfully abstracted for static compilation. The result is a rather _large_ bag of poo, so perhaps the PL people are on to something.:-)

### Two Solutions

-   The most obvious solution - adopted by C++ - is to redesign the language so that representation issues are not hidden from the compiler. That's actually a solution that is worth considering. The problem in C++ isn't so much the number of header file lines per source line as it is the fact that the C preprocessor requires us to process those lines _de novo_ for each compilation unit. BitC lacks (intentionally) anything comparable to the C preprocessor.
-   The other possibility is to shift to what might be labeled "install time compilation". Ship some form of byte code, and do a static compilation at install time. This gets you back all of the code sharing and optimization that you might reasonably have expected from the classical compilation approach, it opens up some interesting design point options from a systems perspective, and (with care) it can be retrofitted to existing systems. There are platforms today (notably cell phones) where we basically do this already.

The design point that you don't want to cross here is dynamic _loading_ where the loaded interface carries a type with an abstracted representation. At that point you are effectively committing yourself to run-time code generation_,_ though I do have some ideas on how to mitigate that.

### Conclusion Concerning Compilation Model

**If static, separate compilation is a requirement, it becomes necessary for the compiler to see into the source code across module boundaries whenever an abstract type is used. That is: any procedure having abstract type must have an exposed source-level implementation.**

**The practical alternative is a high-level intermediate form coupled with install-time or run-time code generation. That is certainly feasible, but it's more that I felt I could undertake.**

That's all manageable and doable. Unfortunately, it isn't the path we had taken on, so it basically meant starting over.

### Insufficiency of the Type System

At a certain point we had enough of BitC working to start building library code. It may not surprise you that the first thing we set out to do in the library was IO. We found that we couldn't handle typed input within the type system. Why not?

Even if you are prepared to do dynamic allocation within the IO library, there is a level of abstraction at which you need to implement an operation that amounts to "inputStream.read(someObject: ByRef mutable 'a)" There are a couple of variations on this, but the point is that you want the ability at some point to move the incoming bytes into previously allocated storage. So far so good.

Unfortunately, in an effort to limit creeping featurism in the type system, I had declared (unwisely, as it turned out) that the only place we needed to deal with ByRef types was at parameters. Swaroop took this statement a bit more literally than I intended. He noticed that if this is _really_ the only place where ByRef needs to be handled, then you can internally treat "ByRef 'a" as 'a, merely keeping a marker on the parameter's identifier record to indicate that an extra dereference is required at code generation time. Which is actually quite clever, except that it doesn't extend well to signature matching between type classes and their instances. Since the argument type for _read_ is _ByRef 'a_, InputStream is such a type class.

So now we were faced with a couple of issues. The first was that we needed to make ByRef 'a a first-class type within the compiler so that we could unify it, and the second was that we needed to deal with the implicit coercion issues that this would entail. That is: conversion back and forth between ByRef 'a and 'a at copy boundaries. The coercion part wasn't so bad; ByRef is never inferred, and the type coercions associated with ByRef happen in exactly the same places that const/mutable coercions happen. We already had a cleanly isolated place in the type checker to deal with that.

But even if ByRef isn't inferred, it can propagate through the code by unification. And _that_ causes safety violations! The fact that ByRef was syntactically restricted to appear only at parameters had the (intentional) consequence of ensuring that safety restrictions associated with the lifespan of references into the stack were honored - that was why I had originally imposed the restriction that ByRef could appear only at parameters. Once the ByRef type can unify, the syntactic restriction no longer guarantees the enforcement of the lifespan restriction. To see why, consider what happens in:

```
  define byrefID(x:ByRef 'a) { return x; }
```

Something that is _supposed_ to be a downward-only reference ends up getting returned up the stack. Swaroop's solution was clever, in part, because it silently prevented this propagation problem. In some sense, his implementation doesn't really treat ByRef as a type, so it can't propagate. But \*because \*he didn't treat it as a type, we also couldn't do the necessary matching check between instances and type classes.

It turns out that being able to do this is _useful_. The essential requirement of an abstract mutable "property" (in the C# sense) is that we have the ability within the language to construct a function that returns the _location_ of the thing to be mutated. That location will often be on the stack, so returning the location is _exactly_ like the example above. The "ByRef only at parameters" restriction is actually very conservative, and we knew that it was preventing certain kinds of things that we eventually wanted to do. We had a vague notion that we would come back and fix that at a later time by introducing region types.

As it turned out, "later" had to be "now", because region types are the right way to re-instate lifetime safety when ByRef types become first class. But _adding_ region types presented two problems (which is why we had hoped to defer them):

-   Adding region types meant rewriting the type checker and re-verifying the soundness and completeness of the inference algorithm, _and_
-   It wasn't just a re-write. Regions introduce subtyping. Subtyping and polymorphism don't get along, so we would need to go back and do a lot of study.

Region polymorphism with region subtyping had certainly been done before, but we were looking at subtyping in another case too (below). That was pushing us toward a kinding system and a different type system.

So to fix the ByRef problem, we very nearly needed to re-design both the type system and the compiler from scratch. Given the accumulation of cruft in the compiler, that might have been a good thing in any case, but Swaroop was now full-time at Microsoft, and I didn't have the time or the resources to tackle this by myself.

### Conclusion Concerning the Type System

**In retrospect, it's hard to imagine a strongly typed imperative language that doesn't type locations in a first-class way. If the language simultaneously supports explicit unboxing, it is effectively forced to deal with location lifespan and escape issues, which makes memory region typing of some form almost unavoidable.**

**For this reason alone, even if for no other, the type system of an imperative language with unboxing must incorporate some form of subtyping. To ensure termination, this places some constraints on the use of type inference. On the bright side, once you introduce subtyping you are able to do quite a number of useful things in the language that are hard to do without it.**

### Inheritance and Encapsulation

Our first run-in with inheritance actually showed up in the compiler itself. In spite of our best efforts, the C++ implementation of the BitC compiler had not entirely avoided inheritance, so it didn't have a direct translation into BitC. And even if we changed the code of the compiler, there are a large number of third-party libraries that we would like to be able to transcode. A good many of those rely on \[single\] inheritance. Without having at least some form of interface (type) inheritance, We can't really even do a good job interfacing to those libraries as foreign objects.

The compiler aside, we also needed a mechanism for encapsulation. I had been playing with "capsules", but it soon became clear that capsules were really a degenerate form of subclassing, and that trying to duck that issue wasn't going to get me anywhere.

I could nearly imagine getting what I needed by adding "ThisType" and inherited _interfaces_. But the combination of those two features introduces subtyping. In fact, the combination is equivalent (from a type system perspective) to single-inheritance subclassing.

And the more I stared at interfaces, the more I started to ask myself why an interface wasn't just a type class. _That_ brought me up against the instance coherence problem from a new direction, which was already making my head hurt. It also brought me to the realization that Interfaces work, in part, because they are always parameterized over a single type (the ThisType) - once you know that one, the bindings for all of the others are determined by type constructors or by explicit specification.

And introducing SelfType was an even bigger issue than introducing subtypes. It means moving out of System F<: entirely, and into the object type system of Cardelli _et al_. That wasn't just a matter of re-implementing the type checker to support a variant of the type system we already had. It meant re-formalizing the type system entirely, and learning how to think in a different model.

Doable, but time not within the framework or the compiler that we had built. At this point, I decided that I needed to start over. We had learned a lot from the various parts of the BitC effort, but sometimes you have to take a step back before you can take more steps forward.

### Instance Coherence and Operator Overloading

BitC largely borrows its type classes from Haskell. Type classes aren't just a basis for type qualifiers; they provide the mechanism for \*ad hoc\*polymorphism. A feature which, language purists notwithstanding, real languages actually do need.

The problem is that there can be multiple type class instances for a given type class at a given type. So it is possible to end up with a function like:

```
define f(x : 'x) {
  ...
  a:int32 + b  // typing fully resolved at static compile time
  return x + x  // typing not resolvable until instantiation
}
```

Problem: we don't know which instance of "+" to use when 'x instantiates to _int32_. In order for "+" to be meaningful in a+b, we need a static-compile-time resolution for +:(int32, int32)->int32. And we get that from Arith(int32). So far so good. But if 'x is instantiated to _int32_, we will get a type class instance supplied by the caller. The problem is that there is no way to guarantee that this is the _same_ instance of Arith(int32) that we saw before.

The solution in Haskell is to impose the _ad hoc_ rule that you can only instantiate a type class once for each unique type tuple in a given application. This is similar to what is done in C++: you can only have one overload of a given global operator at a particular type. If there is more than one overload at that type, you get a link-time failure. This restriction is tolerable in C++ largely because operator overloading is so limited:

1.  The set of overloadable operators is small and non-extensible.
2.  Most of them can be handled satisfactorily as methods, which makes their resolution unambiguous.
3.  Most of the ones that _can't_ be handled as methods are arithmetic operations, and there are practical limits to how much people want to extend those.
4.  The remaining highly overloaded global operators are associated with I/O. These _could_ be methods in a suitably polymorphic language.

In languages (like BitC) that enable richer use of operator overloading, it seems unlikely that these properties would suffice.

But in Haskell and BitC, overloading is extended to _type properties_ as well. For example, there is a type class "Ord 'a", which states whether a type 'a admits an ordering. Problem: most types that admit ordering admit more than one! The fact that we know an ordering _exists_ really isn't enough to tell us which ordering to _use_. And we can't introduce _two_ orderings for 'a in Haskell or BitC without creating an instance coherence problem. And in the end, the instance coherence problem exists because the language design performs method resolution in what amounts to a non-scoped way.

But if nothing else, you can hopefully see that the heavier use of overloading in BitC and Haskell places much higher pressure on the "single instance" rule. Enough so, in my opinion, to make that rule untenable. And coming from the capability world, I have a strong allergy to things that smell like ambient authority.

Now we can get past this issue, up to a point, by imposing an arbitrary restriction on where (which compilation unit) an instance can legally be defined. But as with the "excessively abstract types" issue, we seemed to keep tripping on type class issues. There are other problems as well when multi-variable type classes get into the picture.

At the end of the day, type classes just don't seem to work out very well as a mechanism for overload resolution without some other form of support.

A second problem with type classes is that you can't resolve operators at static compile time. And if instances are explicitly named, references to instances have a way of turning into first-class values. At that point the operator reference can no longer be statically resolved at all, and we have effectively re-invented operator methods!

### Conclusion about Type Classes and Overloading:

**The type class notion (more precisely: qualified types) is seductive, but absent a reasonable approach for instance coherence and lexical resolution it provides an unsatisfactory basis for operator overloading. There is a disturbingly close relationship between type class instances and object instances that needs further exploration by the PL community. The important distinction may be pragmatic rather than conceptual: type class instances are compile-time constants while object instances are run-time values. This has no major consequences for typing, but it leads to significant differences w.r.t. naming, binding, and \[human\] conceptualization.**

**There are unresolved formal issues that remain with multi-parameter type classes. Many of these appear to have natural practical solutions in a polymorphic object type system, but concerns of implementation motivate kinding distinctions between boxed and unboxed types that are fairly unsatisfactory.**

### Wrapping Up

The current outcome is _extremely_ frustrating. While the blind spots here were real, we were driven by the requirements of the academic research community to spend nearly three years finding a way to do complete inference over mutability. That was an enormous effort, and it delayed our recognition that we were sitting on the wrong kind of underlying type system entirely. While I continue to think that there is some value in mutability inference, I think it's a shame that a fairly insignificant wart in the original inference mechanism managed to prevent larger-scale success in the overall project for what amount to _political_ reasons. If not for that distraction, I think we would probably have learned enough about the I/O and the instance coherency issues to have moved to a different type system while we still had a group to do it with, and we would have a working and useful language today.

The distractions of academia aside, it is fair to ask why we weren't building small "concept test" programs as a sanity check of our design. There are a number answers, none very satisfactory:

-   Research languages can adopt simplifications on primitive types (notably integers) that systems languages cannot. That's what pushed us into type classes in the first place, we new that polymorphism over unboxed types hadn't seen a lot of attention in the literature, and we knew that mutability inference had never been done. We had limited manpower, so we chose to focus on those issues first.
-   We knew that parametric polymorphism and subtyping didn't get along, so we wanted to avoid that combination. Unfortunately, we avoided subtypes too well for too long, and they turned out to be something unavoidable.
-   For the first several years, we were very concerned with software verification, which _also_ drove us strongly away from object-based languages and subtyping. That blinded us.
-   Coming to language design as "systems" people, working in a department that lacked deep expertise and interest in type systems, there was an enormous amount of subject matter that we needed to learn. Some of the reasons for our failure are "obvious" to people in the PL community, but others are not. Our desire for a "systems" language drove us to explore the space in a different way and with different priorities than are common in the PL community.

I think we did make some interesting contributions. We now know how to do (that is: to implement) polymorphism over unboxed types with significant code sharing, and we understand how to deal with inferred mutability. Both of those are going to be very useful down the road. We have also learned a great deal about advanced type systems.

In any case, BitC in its current form clearly needs to be set aside and re-worked. I have a fairly clear notion about how I would approach _continuing_ this work, but that's going to have to wait until someone is willing to pay for all this.
