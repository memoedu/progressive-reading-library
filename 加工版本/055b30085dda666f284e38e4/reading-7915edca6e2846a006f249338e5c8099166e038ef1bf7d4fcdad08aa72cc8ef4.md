## 核心洞察

一、WSL 在开发场景下体验更佳：回答者认为 codex 在 Windows 桌面版中，WSL 环境才能获得最佳体验，且 opencode 也常出现类似问题。WSL 之前无法处理系统级操作，但若仅用于开发，WSL 提供完整体验，尤其当工具编译链在 Windows 上无解时，例如 expo 的部分 pnpm 包名过长、ink 框架的 cargo 依赖 C++ 编译工具。
[[#^pr-1243b2294424|正文跳转]]

二、WSL 交叉编译解决服务器部署性能问题：在将代码推送到服务器时，服务器直接进行 Rust 编译常因性能不足而缓慢，使用 WSL 交叉编译往往能更快完成上线。这体现了 WSL 在跨平台开发部署中的实际优势。
[[#^pr-772f3131c801|正文跳转]]

三、WSL 插件更新后支持浏览器使用：虽然默认配置下 WSL 与 PowerShell 的对比（如 5.6 sol）令人难以接受，但更新插件后 WSL 也能正常使用浏览器。回答者偏好默认配置，因为 codex 除开发外还承担代码审计、爬虫、服务器部署、Steam 修复、单机游戏文件修改等任务，不敢完全迁移到 WSL，部分原因是懒惰。
[[#^pr-b25bc968776b|正文跳转]]

四、推荐 WSL 而非 PowerShell 或 Bash：回答者明确推荐使用 WSL，认为 PowerShell 过于糟糕，而更简单的 Bash 功能又过于差劲。这一结论基于其个人使用经验，反映了 WSL 在功能与易用性之间的平衡。
[[#^pr-0adcb6d0f486|正文跳转]]

五、将 PowerShell 经验固化为 skills 降低试错：由于之前频繁使用 PowerShell，回答者让 AI 将相关经验写成 skills，以降低试错成本。这表明通过沉淀技能到 AI 工具中，可以提升后续操作的效率与稳定性。
[[#^pr-05de60fc55e0|正文跳转]]

六、Skills 在 opencode 中效果更明显：回答者感觉基于 codex 编写的 skills 在 opencode 中作用更明显，因为 codex 的 5.5、5.6 sol 模型叛逆心强，即使添加 skills 也可能试错，但通常只错一次就正常，相比没有 skills 时重试 4-5 次已有显著改善。

## 正文

基本上是这样的，而且不仅是 codex，实际上 opencode 也经常出现 deepseek v4 pro VS powershell

![](https://picx.zhimg.com/v2-f5e2a5ee0c0cab509aebd20587099194_r.jpg?source=2c26e567)

但 wsl 之前是有很多系统级操作搞不了，所以如果是只开发的话，wsl 确实是完全的体验，尤其是有的工具编译链经常在 windows 上就是无解的，比如 expo 的部分 pnpm 的包名太长，ink 框架 cargo 依赖的 C++ 编译工具。

而且推到服务器上的时候，服务器直接 rust 编译经常性能不够，用 wsl 交叉编译往往才能比较快的上线。

^pr-772f3131c801

但一般如果不改配置，5.6 sol VS powershell 多少有些难绷。不过现在更新了不少插件，所以使用 wsl 也能正常使用浏览器，只是我一般更喜欢用默认配置，因为 codex 除了基础的开发任务以外，还帮我进行代码审计、爬虫、服务器部署、steam 修复、单机游戏文件修改，事情干的确实是过于多了，还不敢完全丢到 wsl 上（其实单纯就是懒）

我还是推荐使用 wsl，powershell 确实太垃圾了，而更简单的 bash 功能又过于差劲

^pr-0adcb6d0f486

不过之前使用 powershell 的次数比较多，所以让 AI 自己写成了 skills，能降低试错
