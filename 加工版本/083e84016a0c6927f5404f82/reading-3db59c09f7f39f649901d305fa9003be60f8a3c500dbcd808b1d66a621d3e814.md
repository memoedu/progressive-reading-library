# 软件再也没有理由运行缓慢了｜There's no reason for software to be slow anymore

---

## 正文

前几天，我看到一条广为传播的推文，说那些议论 LLMs 如何导致 code 变得 slow、bloated 的人，等到他们用 super-optimized assembly 把一切 re-write 之后，就得认错了。[我们还没到想用 assembly 来 write 一切的地步](https://danluu.com/pl-tokens/)，不过，Nolan Lawson 关于 testing 所说的[你现在可以 choose 自己想要多少 bugs](https://nolanlawson.com/2026/08/16/you-can-just-choose-how-many-bugs-you-want-now/)——我也曾[在这里用不那么漂亮的措辞提过](https://danluu.com/ai-coding/)——某种类似的说法，对 performance 而言也越来越成立了。

我在上一篇文章中提到，[过去 specialized performance work 的 cost 已经 dropped 了许多个 orders of magnitude](https://danluu.com/benchpocalypse/)，而过去需要拥有一套罕见 skills 的个人或团队才能完成的 performance work，如今任何能打几句话的人都可以完成[1](https://danluu.com/no-slow/#fn:B)；这意味着，你可以做各种 optimizations，而这些 optimizations 过去太昂贵，除了 scale 最大或最赚钱的 projects 之外，都不值得做。对此，[Marc Brooker 回应道](https://x.com/MarcJBrooker/status/2089545628607255026)

> 完全同意你最后的观点。Dynamic custom software 针对某个特定 workload 而非某一 class 的 workloads 来 fitted，似乎是很有可能出现的结果。（这本身也伴随着各种有趣的 risks 和 opportunities）。这有点让我想起 [FFTW](https://www.fftw.org/faq/section4.html#whyfast)。还有许多古怪的老 demoscene techniques，它们追求的都是在某个非常特定的 problem（往往还有非常特定的 hardware）上做到 super fast 和 small。例如，我记得有个 demo 把自己的 code re-used 为 textures，以获得出色的 cache locality。

Michael Malis 也曾指出

> 最近一直流传着一种说法，认为 AI 没什么帮助，因为“code 从来就不是难的部分”。我认为，在某些 domains 中确实如此，但在另外一些 domains 中，writing 那些 code 绝对就是难的部分。JIT compilers 就是很好的例子。对于许多 software 来说，一个 JIT compiler 对 speeding up 其 code 会有很大帮助。JIT compilers 的罕见让我相信，过去 implementing 一个 JIT compiler 太过困难，以至于不值得做。LLMs 已经降低了入门门槛，让 write 一个 JIT compiler 容易得多。这就是 pgrust 背后的 thesis。Databases 过去是最难 build 的 software，也因此受到限制。如今，有了 AI，我们可以对自己 build 的 software 类型抱有更大的雄心。

### 针对某一 class 的 workload 进行 Optimizing

让我们用上一篇文章中 build 的 regex engine——[FRE](https://github.com/danluu/fre)——来试试。回顾一下，它是这样 created 的：让一个 agent 在能够访问 [rebar regex benchmark suite](https://github.com/BurntSushi/rebar) 的情况下，围绕 improving regex engine performance 进行了一个月的 loop。这导致 FRE 严重 overfit 于 rebar，直到我们提醒 agent，我们还有一个 holdout benchmark，agent 才对这些 optimizations 进行足够的 generalize，使其在我们的 holdout 上的 performance 还算过得去。一个在 holdout benchmarks 上无法 beat 经过 well-tested 的 regex engine 的“software factory”regex engine，并没有什么特别的使用理由，不过 FRE 有一点值得注意：它的 native AOT compiled version 在较长的 searches 上表现相当不错。我们当时指出，按理说，可以在 ripgrep 运行其 normal matcher 的同时，在另一个 thread 中 run 那个 native code compiler，然后在 compiling 完成时 cut over 到 native code，通常就能获得更好的 performance。当然，这通常会导致 short queries 的 performance 更差，因为我们得把一个 thread 用于 compilation，但比起 ripgrep 只运行几秒钟时要花多久，我更在意它运行许多秒甚至几分钟时要花多久，所以我可以接受这种 tradeoff。

既然我们能用几分钟的 human time 来 build 一个 regex engine，也同样可以用几分钟的 human time 来试试这个 experiment。我打了几句话，一个 agent 就去完成了使这件事成为可能的工作（对于人来说，这会是相当一部分 code surgery），还用来自我 codex history 的实际 ripgrep queries 跑了 benchmark。对于 longer queries，我们在其中几个非常 simple 的 queries 上看到了 2x-4x 的 performance improvement。但大多数 queries 更 complex，而当我们用 representative holdout queries 来 run 时，对于应该 enabled AOT 的 queries[2](https://danluu.com/no-slow/#fn:E)，我们获得了约 7% 的 speedup。这不是什么惊天动地的 result，但考虑到只花了几分钟给 codex 打字，这个结果也不差（而且它还在进行更多 optimization，想必还会进一步 speed things up）。

### 要 Build 一个 index 吗？

可以说，这么做有点傻，因为如果我们在 computer 上反复 searching text，显而易见的 speed up 方法并不是为 regex matching 写一个 native code compiler，而是 create 一个 index。但这里的重点只是，这种过去需要相当多时间和 expertise 的 technical work，如今可以轻而易举地完成。而如果我们想 build 一个 text index，恰好我曾参与过 [BitFunnel，也就是专为 constant/fast text ingestion 而 specialized 的 Bing search index](https://danluu.com/bitfunnel-sigir.pdf)，它获得过 SIGIR 的 Best Paper Award，所以，如果要为我们的整台 machine build 一个 fast local index，我能想到几个值得尝试的 experiments（我见过的 projects 似乎都是为了 index 你的 code directories，但真正拖垮我的 machine performance 的，是 codex 决定对包含大量 generated files 的庞大 temporary directories 运行 ripgrep，并在没有找到时把范围扩大到整台 machine，所以我想要的是整个 disk 的 index，而不只是某些 projects 的 code 的 index）。

如果我在一家 AI lab 工作，能够使用 running 在 Cerebras chips 上的 SOTA models，或其他能大幅 increase tok/s、从而 increase search 的 load/demand 的 accelerators，我或许真会调查现有的 indexers，看看它们是否足够 fast，还是说我想自己 build 一些 custom 的东西。虽然 BitFunnel 的 open source version “只”包含一个 bytecode interpreter 和一个 JIT，但 Bing version 包含多个 JIT compilers。做到这种程度的 optimization，过去是一项大工程，但如今，对于其中一些 projects 而言，“[我一个周末就能做出来](https://danluu.com/sounds-easy/)”已经真的成立了。以我这寒酸的 $200/mo account 来说，我觉得稍微 faster 一点的 ripgrep 加上任意现成的 index 就够用了，所以，也许这个 fast-ingesting whole-machine index project 可以留作一道“给读者的练习题（这位读者在 AI lab 工作）”。

### Optimizations 很便宜

optimizations 的 cost 大幅 reduction，早在 November 2025 使用 public models 时就已经如此，甚至可能更早一些（而我确信，AI labs 的人所能使用的东西，更早就已经能做到这一点）。举一个 GPT-5.1 或 5.2 那个时期的例子：我完全不了解 game AIs，却试着 building 一个 Azul AI。它最后成了这个 game 在全世界最 strongest 的 AI，而且领先幅度相当大。读过描述[第 2 strongest AI](https://www.youtube.com/watch?v=qkzpeXGwE-4) 的 thesis 后，我觉得我的 AI 在“AI”这一方面可能略好一些，但它主要赢在 optimization 上，尽管花费的时间看起来可能少了 two orders of magnitude（这是通过阅读 thesis、了解其中的过程并与我的过程比较而 estimated 的），而且我主要是在自己的 laptop 上工作，而不是有一个 cluster of machines 可用（这意味着用于 run experiments、做 parameter tuning 等的 bandwidth 要少得多）。例如，另一个 AI 是 single-threaded，而我的 AI 是 multi-threaded。由于我既有 native code version，也有[一个糟糕透顶的 shared wasm memory + javascript version](https://danluu.com/game/tile/)，还有用于两个不同 versions 的两种不同 search architectures，而它们“require”完全不同的 multi-threading algorithms（非常 small 且 fast 的 net 用 minimax，更大的 net 用 MCTS），如果手工完成，这原本会是一项相当大的工作。而且，在我自己花 30 minutes 阅读 game AIs 的 multi-threading algorithms 之前，我有几次让一个 LLM 根据它自己的（incorrect）reasoning 来 pick multi-threading algorithm，结果我多次 re-writing（让 codex re-write）这个 multi-threading algorithm。

要 debug 和 verify 这样的 multithreading algorithm，有不少 standard 的事情值得做，例如 implementing 从 debug logs 进行 replay，即使 algorithm 是 nondetermistic，也能 reproduce bugs。单是这件事，如果由我手工完成，可能就要花几天到一周，但它恰好是 agent 可以在 loop 中轻易完成的那类事情（只要让它尝试 replay logs，并在每次未能获得 perfect replay 时，为 non-determinism insert logging）。过去，为了让这样棘手的 optimization 能够 working 而不得不经历的许多繁琐工作，如今都消失了。

这也适用于许多其他棘手的 optimizations。我写过 CPU microcode，做过 CPU verification，也曾参与 optimizing 一个 search engine index 等等，因此经常会看着 optimizations 想：“嗯，这能 increase performance 2%，但要 verify 这个棘手的 optimization 确实 works，就得花 N person-days”，然后根据让这个 optimization working 是否值得花这些时间，决定要不要继续。如今，这个 N 已经下降了极大的 factor（具体幅度不一，但就 human time 而言，经常是 1000x / 10000x / 1000000x；如果把按 metered rates 计算的 token costs 与那位为 search index 编写所用 compilers 和 JITs 的 Bing engineer 相比较，那么在 dollar cost 上大概更接近 1000x），值得做的这类 optimizations 的数量也就大幅增加了。对于那些你不确定是否能奏效的 optimizations，也是如此。过去，我有时会看着某个不确定能否 speed things up 的 optimization，心想：“这得花 M hours 来 implement，才能达到有足够好的 measurement、可以估计 performance impact 的程度。”如今，这些 optimizations 中有更多值得尝试了。

回到 game AI 的例子，至少对我尝试的那个 AI 来说，似乎每次 speed doubling，大约就能增加 100 Elo（比 chess 中更多，我怀疑是因为 draws 非常少见）。在一台 large machine 上，仅仅 adding multithreading 就足以把其他方面 comparable 的 AI 打得落花流水。如果再叠加 10-20 个大多数人觉得手工完成太麻烦的 optimizations，strength 的 difference 就会极其巨大，试图用一个 hand-written AI 来跟上，实在不太合理[3](https://danluu.com/no-slow/#fn:A)。

game AI 的情况比大多数 software 稍微麻烦一些，因为你想做的许多 optimizations 实际上会 change the result，而且并没有一种 cheap、trivial 的方法，可以判断 speed increase + result 的 change 在实践中会带来更好还是更差的 actual result。而且，[正如我们之前提到的](https://danluu.com/ai-coding/)，当前 publicly available 的 SOTA models 在 experimental design 上相当差，所以我不得不搭建它们用于 determine 一个 optimization 是否 good 的 framework；但一旦搭好，它就和其他 optimization problem 一样了。我猜从事 LLM optimizations 的人也必须处理这类 problem，不过大多数 optimization problems 要 straightforward 得多。

再举一个例子，Jamie Brandon 为准备 performance interviews，尝试了 Anthropic [如今已经公开的 performance takehome](https://github.com/anthropics/original_performance_takehome/)。尝试之后，他让 Claude 接着自己停下的地方做，结果得到了好得多的 result。当他查看 Claude 做了哪些自己没做的事时，他说，许多 optimizations 他也想到过，只是还没来得及做，而“\[其\]他那些简直是疯狂的玩意儿，除非我在这上面花上几周，否则绝不会去试”[4](https://danluu.com/no-slow/#fn:C)。他是一位不错的 performance engineer，也拿到了自己想要的 performance 职位的 offer，但在一个 well-defined optimization problem 上，他面对一个 decent model 毫无胜算（我自己还没试过这个 problem，不过我怀疑，只要 time controls 大致 comparable，我也不会有任何胜算）。

### Workload-specific optimization（针对 workload 的 optimization）

回到 Marc Brooker 评论中的这一部分：

> Dynamic custom software，fitted 到某个特定 workload 而不是一类 workloads，似乎是一个非常可能的结果。

这似乎相当不可避免。在另一条对我文章的回复中，pgrust 的 Michael Malis 也说了类似的话：

> \[关于 pgrust optimizations 的 discussion\] ……我认为，create 这些 optimizations 已经足够容易，我们可以查看某个客户的 workload，再按需 add 它们

在没有任何 framework 或 setup 的情况下，就在开始写这篇文章之前，我让一个 agent 为我的 ripgrep queries 做 workload-specific optimization（不是 native code compiler 的切换，只是基于一组 benchmarks 对 general FRE engine 做 optimizations），我大约花了 2 minutes 就启动了这件事。这些 optimizations 在一组 queries 上 run，然后再用时间上较晚的一组 holdout queries 来 run。这仍在 running，不过 initial results 看起来很有希望。经过一轮 optimization，workload optimized version 在 holdout 上比 standard ripgrep 快了 2%，而且仍在变快。对于我本地的 ripgrep usage 来说，2% 算不上什么大事，但考虑到这只花了几分钟，而且这里的 optimizations 是在我开始敲下这一点时才启动的，如今仍在 improving，我愿意接受这里 2% 的 win（注意，这还没有与 native code compiler combined，如果 combined 得当，overall win 会更大）。还要记得，这里利用的是 [FRE](https://github.com/danluu/fre) regex engine[5](https://danluu.com/no-slow/#fn:F)，它在 holdout benchmarks 上曾比 Rust regex engine 慢得多，而且在 holdouts 上 improvement 缓慢，难以突破，因为我对 regex workloads 一无所知，而 SOTA LLMs 又不够擅长 experimental design，无法进行 unguided open-ended self-improving loops，所以我们没有什么好办法 improve 我们的 holdouts 上的 performance。但如果我关心的是自己 workloads 上的 performance，我就有大量 data，而且一直在 generating 更多。正如 Marc Brooker 在上面指出的，如果出现旧 data 中没有的 regime change 等情况，我们确实必须小心 overfitting，但我们仍然比以前处境更好。

在更 general 的情况下，如果你是 Amazon 的 Marc Brooker，或是在做 pgrust 的 Michael Malis 这样的人，合理的做法就不只是把这件事做一次，而是与客户合作，pilot 一个 program，利用他们的 data 为他们 optimize，然后再想办法将其 scale it out 到一般客户。我所在的公司并不是一个把时间花在这件事上最合适的地方[6](https://danluu.com/no-slow/#fn:T)，但能看到这正在向那些 scale 更大的大公司走来，实在令人惊叹；而且，考虑到为我个人的 workflows run 这些 experiments 只需要花我几分钟时间，在 personal projects 上折腾这类事情也相当合理。

### Appendix：software 已经没有理由再 slow 了

长期以来，我一直公开表示，[我强烈反对这样一种普遍看法：X 的 developers 很差劲，而且应该为此感到羞愧](https://mastodon.social/@danluu/111064964615090306)，仅仅因为他们 [writing slow code，因为 programming expertise 有许多不同的种类](https://mastodon.social/@danluu/110550198966171979)；而且，不仅并非大多数 programmers 都拥有 performance expertise，从 business 关心什么、employment market 是什么样子等角度来看，让他们去培养这种 expertise 甚至可能根本没有意义，所以，和 performance expert 能做到的相比，大多数 projects 的 performance 当然会非常 poor。我能理解，为什么 performance expert 看到[不断扩大的 gap](https://danluu.com/slow-device/)——也就是 [program 可以有多 fast，与 programs 实际有多 fast 之间的差距](https://danluu.com/input-lag/)——会觉得这很荒谬。我并不否认其中有荒谬之处，但如果我想想 UI 可以有多好，与我能（手工）做出的 UI 有多好之间的 gap，我不觉得这看起来就没那么荒谬；不过，我也不觉得花时间学习如何 build 一个出色的 UI，甚至只是一个像样的 UI，对我而言真的有意义，理由与大多数人没必要花时间学习如何做好 performance work 一样。

就上面的例子而言，Jamie Brandon 拿到了 Anthropic 的 offer，除非你是 OpenAI，否则你大概请不起他，但你负担得起一个能在 bounded optimization problem 上胜过他的 coding agent。这个 agent 没有他那样的判断力，在 open-ended problem 上会表现得更差（回想一下，[我们尝试 building 一个 optimized regex engine，只告诉它不要 overfit 时，它在我们的 holdout benchmarks 上比最好的 regex engines 差了不止一个 order of magnitude](https://danluu.com/benchpocalypse/)；不过也别忘了，告诉 agent 存在一个它表现不佳的 holdout 之后，它就把 regex engine performance 提升到了通常足以在 performance 方面匹敌 2nd tier regex engines 的程度，而与如今大多数 code 中 performance optimization 的普遍水平相比，这仍然极其出色），但这已经足以在各种 problems 上 achieve reasonable performance。本文主要讨论了 backend performance issues，不过，如果你想降低 LCP 和 CLS 这类一组 metrics，agents 在 front-end performance 方面似乎也不更差。事实上，在把我最近一直使用的 interactive plots 插入文章后，我发现自己的 client-side perf numbers 变差了，于是我让一个 LLM 花了我 weekly quota 的 1% 来 optimizing 它们，这些 numbers 就又恢复到了良好水平。这是一个非常 simple 的 site，不过，人们也在向数百万 users 发布的相当 complex 的 apps 上做这类 optimizations，而且在那里同样有效，只不过确实要多花一点 tookens。

我仍然不认为，一个人的 software 有 poor performance，就说明他很差劲，而且应该为此感到羞愧；但我确实认为，一个完全不懂 performance、但还算会使用 LLMs 的人（只是一般意义上会用，并非专门处理 performance problems），通常应该能够 create 具有 decent performance 的 software。如果你只是告诉一个 LLM 去 optimize，它常常会做出各种 incorrect 而且非常糟糕的事情，需要你发现；不过，这本来就是有效使用 LLM 时普遍存在的情况，因此，获得 decent performance 已不再是一种 specialized skill。

## 原文

The other day, I saw a viral tweet saying that people talking about how LLMs are causing slow, bloated, code are going to eat crow once they re-write everything in super-optimized assembly. [We're not quite at the point where we want to write everything in assembly](https://danluu.com/pl-tokens/), but some variant of what Nolan Lawson said about testing, [you can choose how many bugs you want now](https://nolanlawson.com/2026/08/16/you-can-just-choose-how-many-bugs-you-want-now/), which I [less eloquently noted here](https://danluu.com/ai-coding/), is becoming more true for performance.

In response to a comment in my last post that [the cost of formerly specialized performance work has dropped by many orders of magnitude](https://danluu.com/benchpocalypse/) and performance work that used to require a person or team that had a rare set of skills can be done by anyone who can type a few sentences[1](https://danluu.com/no-slow/#fn:B), which means that you can do all sorts of optimizations that used to be too expensive to be worthwhile for all but the largest scale or most lucrative projects, [Marc Brooker responded with](https://x.com/MarcJBrooker/status/2089545628607255026)

> Completely agree with your closing point. Dynamic custom software, fitted to a particular workload rather than a class of workloads, seems like a very likely outcome. (Which comes with all kinds of fun risks and opportunities of its own). Kind of reminds me of [FFTW](https://www.fftw.org/faq/section4.html#whyfast). And a ton of weird old demoscene techniques which were all about being super fast and small on a very particular problem (and often very particular hardware). For example, I remember a demo that re-used its code as textures to get great cache locality.

And Michael Malis has noted

> There’s been a meme circulating about how AI doesn’t help because “code was never the hard part.” I think that’s true in some domains, but in others, writing the code absolutely was the hard part. JIT compilers are a great example of that. For many pieces of software, a JIT compiler would help a lot with speeding up the code. The rarity of JIT compilers makes me believe that implementing a JIT compiler historically was too difficult for it to be worthwhile. LLMs have lowered the barrier to entry and made it much easier to write a JIT compiler. This is the thesis behind pgrust. Databases historically were the hardest piece of software to build and were limited because of that. Now, with AI, we can be more ambitious about the type of software we build.

### Optimizing for a class of workload

Let's try this out with [FRE](https://github.com/danluu/fre), the regex engine we built in the last post. Recall that it was created by having an agent loop for a month on improving regex engine performance with access to [the rebar regex benchmark suite](https://github.com/BurntSushi/rebar). This resulted in FRE being heavily overfit to rebar until we warned our agent that we had a holdout benchmark, which caused the agent to generalize the optimizations enough that performance was ok-ish on our holdout. There's no particular reason to use a "software factory" regex engine that doesn't beat a well-tested regex engine on holdout benchmarks, but one notable thing about FRE was that the native AOT compiled version did quite well at longer searches. We noted that, it stands to reason that one could run the native code compiler in another thread while ripgrep was running its normal matcher and then cut over to the native code when it finished compiling and generally get better performance. Of course this will generally result in worse performance for short queries as we lose a thread to compilation, but I care a lot more about how long ripgrep takes when it runs for many seconds or minutes than when it runs for a few seconds, so I'm ok with that tradeoff.

In the same way we could build a regex engine in a few minutes of human time, we can also just try this experiment in a few minutes of human time. I typed a few sentences and an agent went and did the work to allow this to happen (which would be a decent chunk of code surgery for a human) and it ran the benchmark on actual ripgrep queries that come from my codex history. For longer queries, we see a 2x-4x performance improvement here for a few very simple queries. But most queries are more complex, and when we run on representative holdout queries, for queries where AOT should be enabled[2](https://danluu.com/no-slow/#fn:E), we get about a 7% speedup. Not an earth shattering result, but also not a bad outcome for spending a few minutes typing to codex (and it's still doing more optimization and will presumably speed things up further).

### Build an index?

This is arguably a silly thing to do, since if we're repeatedly searching for text on a computer, the obvious thing to do to speed that up isn't to write a native code compiler for regex matching, it's to create an index. But the point here is just that this kind of technical work, which used to take a fair amount of time and expertise, can just be done trivially now. And if we wanted to build a text index, it just so happens that I worked on [BitFunnel, the Bing search index that was specialized for constant/fast text ingestion](https://danluu.com/bitfunnel-sigir.pdf) that won Best Paper Award at SIGIR, so I can think of a few experiments to try if we're going to build a fast local index of our entire machine (the projects I've seen seem to be intended to index your code directories, but what really kills my machine performance is when codex decides to run ripgrep against huge temporary directories with a ton of generated files and then expands to looking at my whole machine when it misses, so I'd want an index of my entire disk and not just of the code for some projects).

If I were working at an AI lab and had access to things like SOTA models running on Cerebras chips or other accelerators that greatly increase tok/s and therefore load/demand for search, I might actually survey the existing indexers to see if they're fast enough or if I'd want to build something custom myself. While the open source version of BitFunnel "only" contains a bytecode interpreter and one JIT, the Bing version contains multiple JIT compilers. A project that did that level of optimization used to be a major undertaking, but "[I could do that in a weekend](https://danluu.com/sounds-easy/)" is now actually true for some of these kinds of projects. With my lowly $200/mo account, I think a somewhat faster ripgrep plus any off-the-shelf index is fine, so maybe this fast-ingesting whole-machine index project can be left as an "exercise for the reader (who works at an AI lab)".

### Optimizations are cheap

The drastic reduction in the cost of optimizations has been true going back to November 2025 and maybe even somewhat before then with public models (and I'm sure before that still with what folks at AI labs had access to). For an example from the GPT-5.1 or 5.2 days, with no knowledge of game AIs, I tried building an Azul AI. This ended up being the strongest AI in the world for the game by a pretty large margin. From reading the thesis that describes [the 2nd strongest AI](https://www.youtube.com/watch?v=qkzpeXGwE-4), I think my AI is probably a bit better on the "AI" side of things, but the main place it wins is on optimization despite spending what looks like maybe two orders of magnitude less time (estimated by reading the thesis and seeing the process and comparison to my process) and also mostly working on my laptop vs. having a cluster of machines to use (which means much less bandwidth to run experiments with, do parameter tuning, etc.). For example, that other AI is single-threaded and my AI is multi-threaded. Since I have a native code version as well as [a heinous shared wasm memory + javascript version](https://danluu.com/game/tile/), and two different search architectures for two different versions, which "require" completely different multi-threading algorithms (minimax for a very small and fast net and MCTS for a larger net), this would've been a fairly large undertaking if done by hand. And, because I let an LLM pick the multi-threading algorithm based on its own (incorrect) reasoning a couple times before spending 30 minutes reading about multi-threading algorithms for game AIs myself, I ended up re-writing (having codex re-write) the multi-threading algorithm multiple times.

There's a bunch of standard stuff it makes sense to do to debug and verify a multithreading algorithm for something like this, like implementing replay from debug logs that can reproduce bugs despite the algorithm being nondetermistic. Doing that alone would've probably been days to a week of work had I done it by hand, but it's exactly the kind of thing an agent can trivially do in a loop (just have it try to replay logs and insert logging for non-determinism every time you don't get a perfect replay). A lot of the tedium it used to take to get a tricky optimization like this working is gone.

This also applies to a lot of other tricky optimizations. From having written CPU microcode, done CPU verification, worked on optimizing a search engine index, etc., I have a lot of experience looking at optimizations and thinking "hmm, this would increase performance by 2%, but it's going to take N person-days to verify that this tricky optimization works" and making a call to go ahead or not based on whether or not it's worth the time to get the optimization working. Now that this N has dropped by a tremendous factor (variable but, in terms of human time, frequently 1000x / 10000x / 1000000x, probably more like 1000x on dollar cost if you compare token costs at metered rates vs. the Bing engineer who wrote the compilers at JITs that the search index used), the number of these kinds of optimizations it makes sense to do goes way up. The same goes for optimizations that you aren't sure will work out. I used to sometimes look at an optimization that I wasn't sure would speed things up and think "this will take M hours to implement to the point where we have a good enough measurement to guess at the performance impact". Many more of those optimizations make sense to try out now.

Going back to the game AI case, at least for the AI I tried, it seems like you gain about 100 Elo for every doubling in speed (more than in chess, I suspect because draws are very rare). Just adding multithreading alone is enough to wipe the floor with an otherwise comparable AI on a large machine. If you stack in 10-20 more optimizations that seem too annoying for most people to do by hand, the difference in strength is tremendous and it's not really reasonable to try to keep up with a hand-written AI[3](https://danluu.com/no-slow/#fn:A).

The game AI case is a little more annoying than for most software because a lot of the optimizations you want to do actually change the result and there isn't a cheap, trivial, way to tell if the speed increase + the change in result gives a better or worse actual result in practice. And, [as we noted before](https://danluu.com/ai-coding/), current publicly available SOTA models are pretty bad at experimental design, so I had to set up the framework they used to determine if an optimization is good, but once that was in place, it's like any other optimization problem. I guess people working on LLM optimizations also have to deal with this class of problem but most optimization problems are a lot more straightforward.

To pick another example, as part of preparing for performance interviews, Jamie Brandon tried Anthropic's [now public performance takehome](https://github.com/anthropics/original_performance_takehome/). After trying it, he had Claude pick up where he left off and it got a much better result. When he looked at what Claude did that he didn't, he said a lot of the optimizations were things that occurred to him but he hadn't gotten to yet, and "\[o\]thers were just crazy shit that I would never try unless I was working on this for weeks"[4](https://danluu.com/no-slow/#fn:C). He's a reasonable performance engineer and he got an offer for the performance job he wanted, but on a well-defined optimization problem, he doesn't stand a chance against a decent model (I haven't tried the problem myself, but I suspect I also wouldn't stand a chance given remotely comparable time controls).

### Workload-specific optimization

Coming back to this part of Marc Brooker's comment:

> Dynamic custom software, fitted to a particular workload rather than a class of workloads, seems like a very likely outcome.

This seems pretty inevitable. In another response to my post, Michael Malis of pgrust said something similar:

> \[discussion of pgrust optimizations\] ... I think it's easy enough to create these optimizations that we could look at a customers workload and add them as needed

Without having any kind of framework or setup, right before I started writing this post, I had an agent do workload-specific optimization for my ripgrep queries (not the native code compiler switch, just the optimizations to the general FRE engine based on a set of benchmarks), which took about 2 minutes for me to launch. The optimizations run on a set of queries, and then there's a later holdout set of queries to run against. That's still running, but the initial results seem promising. After one pass of optimization, the workload optimized version is 2% faster than standard ripgrep on the holdout and it's still getting faster. 2% isn't a big deal for my local ripgrep usage, but considering that this took minutes of time and the optimizations done here got started when I started typing this point and are still improving, I'd take a 2% win here (note that this isn't combined with the native code compiler, which would give a larger overall win if combined properly). And recall that this is leveraging the [FRE](https://github.com/danluu/fre) regex engine[5](https://danluu.com/no-slow/#fn:F), which was substantially slower than the Rust regex engine on holdout benchmarks and was stuck with slow improvement on holdouts because with me knowing nothing about regex workloads and SOTA LLMs not being good enough at experimental design to do unguided open-ended self-improving loops, we didn't have a good way to improve performance on our holdouts. But if what I care about is performance on my own workloads, I have plenty of data and am generating more all the time. As Marc Brooker noted above, we do have to be careful about overfitting if there's a regime change that's not in the old data, etc., but we're still in a better situation than we were before.

In the more general case, if you're someone like Marc Brooker at Amazon or Michael Malis working on pgrust, it makes sense to not just do this as a one-off, but to work with customers to pilot a program that uses their data to optimize things for them and then figure out how to scale it out for customers in general. I'm not working at a company where that's the best use of my time[6](https://danluu.com/no-slow/#fn:T), but it's pretty wild that you can see that this is coming for larger companies with more scale, and given that it only takes minutes of my time to run these experiments for my personal workflows, it's pretty reasonable to mess with this kind of thing on personal projects.

### Appendix: There's no reason for software to be slow anymore

I've been on the record for a long time as [strongly disagreeing with the general sentiment that the developers of X are bad and should feel bad](https://mastodon.social/@danluu/111064964615090306) for [writing slow code because there are a lot of different kinds of programming expertise](https://mastodon.social/@danluu/110550198966171979) and not only is it not the case that most programmers don't have performance expertise, it probably doesn't even make sense for them to develop (from the standpoint of what the business cares about, what the employment market looks like, etc.), so of course most projects will have very poor performance compared to what a performance expert can do. I can see why a performance expert would look at [the growing gap](https://danluu.com/slow-device/) between [how fast a program can be and how fast programs actually are](https://danluu.com/input-lag/) and think that it's ridiculous. I don't disagree that there's an absurdity to it, but if I think about the gap between how good a UI can be and how a good a UI I can make (by hand) is, I don't think that looks any less absurd, but I also don't think it really makes sense for me to spend time learning how to build a great UI, or even a decent UI, for the same reasons it doesn't make sesne for most people to spend time learning how to decent performance work.

For the example above, Jamie Brandon got an offer from Anthropic and you probably can't afford him unless you're OpenAI, but you can afford to use a coding agent that can beat him on a bounded optimization problem. The agent doesn't have the judgement he has and will do worse on an open-ended problem (recall that [when we tried building an optimized regex engine and just told it to not overfit, it was more than an order of magnitude worse than the best regex engines on our holdout benchmarks](https://danluu.com/benchpocalypse/), but also recall that after telling the agent there was a holdout it was doing poorly on, it sped up regex engine performance enough to generally match 2nd tier regex engines in terms of performance, which is still extremely good compared to the general level of performance optimization in most code today), but that's plenty good to achieve reasonable performance on all sorts of problems. This post has generally discussed backend performance issues, but agents don't seem worse at front-end performance if you want to drive down a set of metrics like LCP and CLS. In fact, after inserting the interactive plots I've been using recently into posts, I found that my client-side perf numbers got worse, so I had an LLM spent 1% of my weekly quota optimizing those and the numbers are once again back to being good. This is a very simple site, but people do these kinds of optimizations on fairly complex apps that ship to many millions of users and it also works there, although it does cost a few more tookens.

I still don't think someone is bad and should feel bad if their software has poor performance, but I do think that someone who doesn't know anything about performance and is a reasonable user of LLMs (just in general, not on performance problems in particular) should generally be able to create software that has decent performance. If you just tell an LLM to optimize, it will often do all sorts of incorrect things that are really bad that you have to catch, but that's generally true of using the LLM effectively in the first place, so getting decent performance is no longer a specialized skill.

This is equivalent to `:(?:1[3-9]|[2-9][0-9])[0-9]{2}:` (which, if run through ripgrep on the original input, has approximately the same performance; the shorter regex is technically a bit faster on the real query data, but only by a very small amount). The entire pipeline for that was

```
cargo clippy … | rg 'crates/fre-aot-regex/src/module.rs:' | rg NUMBER_REGEX | head -250
```

which might be an odd thing for a human to do, but agents seem to do this kind of thing all the time.

On another topic, if we look at how long ripgrep queries took, there are quite a few slow queries, e.g., p99 is almost 1 minute! And p999 is almost 10 minutes! And the maximum query over this time period (around a month on one laptop; queries and distributions seem likely to be different on the AWS hosts I run agents on, etc., but I haven't checked) is approaching 2 hours!

In terms of command line options, we see the following. Perhaps unsurprisingly, codex often wants line numbers and, for whatever reason, it very occasionally uses PCRE2 regexes.

I won't add plots or tables for these, but another thing to note is that there's fairly low locality for what patterns are searched for (about 94% of patterns only occurred once), which makes some sense given how long a lot of the queries were. However, there's fairly high locality in what files get searched and a file that got searched is relatively likely to get searched again soon, indicating that (for small enough files), they're likely to be searched in memory.

Also, 99% of queries were regex queries (1% were non-regex string searches) and 99.9% of search queries were ASCII only, but in terms of files searched, approximately 45% were ASCII only and 55% contained Unicode, a higher percentage than I would've guessed for Unicode.

On a draft of the last post, Peter Geoghegan noted

> It's also possible for a regex implementation to be faster by supporting fewer features. Some implementations don't support back references, etc.

which is also true here. The workload-specific optimizations done here were fairly superficial because I just gave codex some short instructions and let it do whatever it wanted (which is, in general, not the most effective use of codex), but with a more detailed plan, more focused optimizations supporting the common use cases for my queries could be expected to yield larger gains.
