# 我一个周末就能搞定！｜I could do that in a weekend!

---

## 正文

我想不出有哪一家 large software company 不会经常招来这样的网上评论：“所有 employees 都在做什么？我自己就能 build 他们的 product。”[Benjamin Pollack](https://bitquabit.com/post/one-which-i-call-out-hacker-news/) 和 [Jeff Atwood](https://blog.codinghorror.com/code-its-trivial/) 曾公开批评过针对 Stack Overflow 这样说的人。但 [Stack Overflow 相当明显是 lean 的](http://nickcraver.com/blog/2016/03/29/stack-overflow-the-hardware-2016-edition/)，所以通常的回应大致是：“哦，当然，Stack Overflow 也许是 lean 的，但 FooCorp 肯定确实是 bloated 的。”而由于大多数人对 FooCorp 内部的了解相当有限，无论 FooCorp 具体是哪家公司，这听起来都像是可信的说法。毕竟，什么 product 可能需要数百、甚至数千名 engineers 呢？

几年前，在 rapgenius SEO 争议之后，不少人呼吁有人去 write 一个更好的 Google。Alex Clemmer 回应说，[也许 building 一个更好的 Google 是个 non-trivial problem](http://blog.nullspace.io/building-search-engines.html)。考虑到 Google 的 $500B market cap 中有多少来自 search，以及几十家（几百家？）competitors 为了获取其中一部分 value 已经花了多少钱，我觉得 search 并不是个 trivial problem，这一判断是可信的。但在 Alex 的文章评论中，多个人回应说，Lucene 基本上就在做 Google 所做的同样的事，而且 Lucene 即将在接下来的几年里 surpass Google 的 capabilities。距那时已经过了足够长的时间，我们可以回过头来说，Lucene 并没有 improved 到让 Google 面临一家组建了 Lucene cluster 的 startup 的威胁的程度。真要说有什么变化，那就是 creating 一个 viable 的 Google search competitor 的 cost 反而上升了。

要 making 一个 viable 的 Google competitor，我认为 ranking 是个比 indexing 更难的 problem，但即便我们只看 indexing，也存在单个 domains，其中 contain 的、我们可能想要 index 的 pages 达到了 on the order of one trillion（例如 Twitter），而且我猜我们能找到 on the order a trillion domains。如果你尝试 configure 任意一个 off-the-shelf search index，让它 hold 一个包含若干万亿 items 的 index，以 handle 比如 Google 的 load 的 1/100th 这样的 load，同时 latency budget 比如为 100ms（大部分 latency 应该用于 ranking，而不是 indexing），我想你会发现这并不 trivial。而且，如果你用 Google 来 search Twitter，你就能观察到，至少对于特定 users 或 tweets，Google indexes Twitter 的速度足够快，从 users 的角度看基本上是 real-time 的。任何尝试过在 high load 下用 Lucene 对 large corpus 进行 real-time indexing 的人，也都会发现这是 non-trivial 的。你可能会说，这并不完全公平，因为可以找到没有被 major search engines indexed 的 tweets；但如果你想决定哪些要 index、哪些不要，那么，这本身也是个在 general case 下 non trivial 的 problem。而我们这里还只是在谈 indexing，indexing 是 building 一个 search engine 时较容易的部分之一。

真正关心 turning a profit 的 Businesses 会花大量时间（因此也需要大量 engineers）来 optimizing systems，即使该 system 的 MVP 本可以在一个周末 built 出来。此外，已有大量 research 发现，对某些 businesses 而言，在相当宽的 latencies range 内，decreasing latency 都会对 revenue 产生 significant effect。Increasing performance 还有 reducing costs 的好处。Businesses 应当不断增加 engineers 来做 optimization，直到 adding an engineer 的 cost equals 在 margin 上的 revenue gain 加上 cost savings。这往往意味着需要的 engineers 比人们意识到的多得多。

而这还只是 performance。Features 也很重要：当我和任何公司里从事几乎任何 product 的 engineers 交谈时，他们往往会发现，有些看似 trivial 的 individual features 能给 revenue 增加 integer percentage points。就像 performance 一样，人们低估了在 engineers 不再能抵偿自身 cost 之前，你可以给一个 product 增加多少 engineers。

此外，features 往往比外人意识到的要 complex 得多。如果我们看 search，该如何确保不同 forms 的 dates 和 phone numbers 给出相同 results？internationalization 呢？每种 language 都有必须考虑到的 unique quirks。在 french 中，“l'foo” 通常应该 match “un foo”，反之亦然，但 90s 的 American search engines 实际上并没有正确地 handle 这一点。对 Chinese queries 进行 tokenizing 呢？其中 words 之间没有 spaces，sentences 也没有 unique tokenizations。Japanese 呢？其中 queries 很容易 contain 四种不同的 alphabets。handling Arabic 呢？它大多是 right-to-left 地 read，但其中一些部分却是 left-to-right 地 read。[而这甚至还不是 handling Arabic 最 complicated 的部分](https://r12a.github.io/scripts/tutorial/part3)！对于一个 weekend-project MVP，忽略这些没什么问题，但在真正的 business 中忽略它们，就意味着忽略大部分 market！其中有些已经由 open source projects handled 得还不错，但许多 problems 都涉及 open research problems。

还有 security！如果你不通过雇用 security 人员来让公司“bloat”，最终就会像 hotmail 或 yahoo 一样，你的 product 会因为经常被 hacked 而出名，而不是因为它的其他任何 features。

到目前为止，我们看过的所有东西都是 technical problem。与 organizational problems 相比，technical problems 算是 straightforward 的。Distributed systems 被认为很难，因为实际的 systems 可能会 drop 大约 0.1% 的 messages，corrupt 比这更小比例的 messages，并且出现处于 microsecond 到 millisecond range 内的 latencies。当我和上级交谈，并把他们以为自己在说的意思与同事认为他们在说的意思进行比较时，我发现 lost messages 的 rate 远高于 50%，每条 message 都会 gets corrupted，而 latency 可以长达数月甚至数年[1](https://danluu.com/sounds-easy/#fn:A)。当人们想象 build 某样东西应该花多长时间时，他们往往设想的是一个完美运作、把 100% 的时间都用于 coding 的 team。但那是不可能 scale up 的。问题不在于是否会有 inefficiencies，而在于会有多少 inefficiency。一家能够 eliminate organizational inefficiency 的公司，会是比以往任何 tech startup 都更大的 innovation。但在计算一家公司“应该”有多少 employees 时，人们通常会假定这家公司是个 efficient organization。

这篇文章碰巧用 search 作为 example，是因为我遇到一些人，声称 Lucene 随时就会 surpass Google 的 capabilities，但这篇文章所说的并没有什么是 search 独有的。如果你和几乎任何 field 中的人交谈，都会听到人们如何严重低估该 field 中 problems 的 complexity 的故事。这里的 point 并不是说，一个 small team 不可能 build 出比 Google search 更好的东西。完全有可能，有人会带来和 PageRank 一样了不起的 innovation，而一个 small team 可以把它变成一家 viable company。但一旦这家公司度过 VC-funded hyper growth phase，并希望 maximize 它的 profits，它最终就会拥有一个数千人的 platforms org，就像 Google 的一样，除非这家公司愿意因 hardware 和 software inefficiency 而每年白白放弃数亿或数十亿美元。而且，这家公司会想要 handle Thai、Arabic、Chinese 和 Japanese 等 languages，而其中每一种都是 non-trivial 的。而且，这家公司会想要拥有相对良好的 security。还有数以百计的小 features，users 甚至没有意识到它们的存在，但其中每一个都会带来明显的 revenue increase。公司应该 outsource 自己的 billing，这一点看似“显而易见”；但当你和自行 handle billing 的公司交谈时，它们能指出一些 individual features，这些 features 能让 conversion increase 个位数或两位数的百分比，而它们无法从 Stripe 或 Braintree 获得这些 features。超过一定 size 后，那个五十人的 billing team 完全值得。而且还有大多数 engineers 甚至都不会想到的 sales[2](https://danluu.com/sounds-easy/#fn:S)；适用于 optimization 的完全相同的 reasoning 也适用于 sales -- 只要再增加一名 salesperson 的 marginal benefit exceeds cost，你就应该预期公司会继续增加 salespeople，这往往会导致 sales force 比 engineering team 还大。此外还有 research，几乎按 definition 来说，它就涉及大量最终不会成功的 bets！

并不是说，不做上述所有事情就根本无法 run 一个 service；而是说，几乎每个 large service 如果不认真处理这些事情，就会白白放弃赚钱的机会。这让我想起我们在 unreliable systems 中见到的一种常见 fallacy：人们 build 出 happy path，认为 happy path 才是“真正的”工作，而 error handling 可以以后再补上。[对于 reliable systems，error handling 比 happy path 需要更多工作](https://danluu.com/postmortem-lessons/)。large services 也是如此 -- 所有这些人们不认为是“真正的”工作的事情，比 core service 需要更多工作[3](https://danluu.com/sounds-easy/#fn:W)。

### 更正

我经常做些小改动并补充新信息，而不特意说明，但这篇文章的原始版本有一个错误，移除这个错误所带来的改动足够大，我认为值得专门指出。我原先对用 Lucene 进行 indexing the web 的 cost 做过一个 back of the envelope calculation，但其中的 numbers 是根据一些 papers 中的 benchmarks results，以及从事 commercial search engine 工作的人所发表的评论得出的。当我尝试 reproduce 这些 papers 中的 results 时，我发现，[要获得比其中一篇 paper 所 reported 的好 orders of magnitude 的 performance 是 trivial 的](https://twitter.com/danluu/status/814167684954738688?lang=ro)；而当我尝试追查那些从事 commercial search engine 工作的人所发表的评论背后的来源时，我发现这些评论并没有 experimental evidence 作为依据，因此我移除了这个 example。

我正在尝试以意识流的方式写博客文章，不做太多编辑。这篇文章[和上一篇文章](https://danluu.com/bimodal-compensation/)都是这样写的。与我“平常”的文章相比，你觉得这些文章怎么样？[请告诉我你的想法](https://twitter.com/danluu)！

## 原文

I can't think of a single large software company that doesn't regularly draw internet comments of the form “What do all the employees do? I could build their product myself.” [Benjamin Pollack](https://bitquabit.com/post/one-which-i-call-out-hacker-news/) and [Jeff Atwood](https://blog.codinghorror.com/code-its-trivial/) called out people who do that with Stack Overflow. But [Stack Overflow is relatively obviously lean](http://nickcraver.com/blog/2016/03/29/stack-overflow-the-hardware-2016-edition/), so the general response is something like “oh, sure maybe Stack Overflow is lean, but FooCorp must really be bloated”. And since most people have relatively little visibility into FooCorp, for any given value of FooCorp, that sounds like a plausible statement. After all, what product could possible require hundreds, or even thousands of engineers?

A few years ago, in the wake of the rapgenius SEO controversy, a number of folks called for someone to write a better Google. Alex Clemmer responded that [maybe building a better Google is a non-trivial problem](http://blog.nullspace.io/building-search-engines.html). Considering how much of Google's $500B market cap comes from search, and how much money has been spent by tens (hundreds?) of competitors in an attempt to capture some of that value, it seems plausible to me that search isn't a trivial problem. But in the comments on Alex's posts, multiple people respond and say that Lucene basically does the same thing Google does and that Lucene is poised to surpass Google's capabilities in the next few years. It's been long enough since then that we can look back and say that Lucene hasn't improved so much that Google is in danger from a startup that puts together a Lucene cluster. If anything, the cost of creating a viable competitor to Google search has gone up.

For making a viable Google competitor, I believe that ranking is a harder problem than indexing, but even if we just look at indexing, there are individual domains that contain on the order of one trillion pages we might want to index (like Twitter) and I'd guess that we can find on the order a trillion domains. If you try to configure any off-the-shelf search index to hold an index of some number of trillions of items to handle a load of, say, 1/100th Google's load, with a latency budget of, say, 100ms (most of the latency should be for ranking, not indexing), I think you'll find that this isn't trivial. And if you use Google to search Twitter, you can observe that, at least for select users or tweets, Google indexes Twitter quickly enough that it's basically real-time from the standpoint of users. Anyone who's tried to do real-time indexing with Lucene on a large corpus under high load will also find this to be non-trivial. You might say that this isn't totally fair since it's possible to find tweets that aren't indexed by major search engines, but if you want to make a call on what to index or not, well, that's also a problem that's non trivial in the general case. And we're only talking about indexing here, indexing is one of the easier parts of building a search engine.

Businesses that actually care about turning a profit will spend a lot of time (hence, a lot of engineers) working on optimizing systems, even if an MVP for the system could have been built in a weekend. There's also a wide body of research that's found that decreasing latency has a significant effect on revenue over a pretty wide range of latencies for some businesses. Increasing performance also has the benefit of reducing costs. Businesses should keep adding engineers to work on optimization until the cost of adding an engineer equals the revenue gain plus the cost savings at the margin. This is often many more engineers than people realize.

And that's just performance. Features also matter: when I talk to engineers working on basically any product at any company, they'll often find that there are seemingly trivial individual features that can add integer percentage points to revenue. Just as with performance, people underestimate how many engineers you can add to a product before engineers stop paying for themselves.

Additionally, features are often much more complex than outsiders realize. If we look at search, how do we make sure that different forms of dates and phone numbers give the same results? How about internationalization? Each language has unique quirks that have to be accounted for. In french, “l'foo” should often match “un foo” and vice versa, but American search engines from the 90s didn't actually handle that correctly. How about tokenizing Chinese queries, where words don't have spaces between them, and sentences don't have unique tokenizations? How about Japanese, where queries can easily contain four different alphabets? How about handling Arabic, which is mostly read right-to-left, except for the bits that are read left-to-right? [And that's not even the most complicated part of handling Arabic](https://r12a.github.io/scripts/tutorial/part3)! It's fine to ignore this stuff for a weekend-project MVP, but ignoring it in a real business means ignoring the majority of the market! Some of these are handled ok by open source projects, but many of the problems involve open research problems.

There's also security! If you don't “bloat” your company by hiring security people, you'll end up like hotmail or yahoo, where your product is better known for how often it's hacked than for any of its other features.

Everything we've looked at so far is a technical problem. Compared to organizational problems, technical problems are straightforward. Distributed systems are considered hard because real systems might drop something like 0.1% of messages, corrupt an even smaller percentage of messages, and see latencies in the microsecond to millisecond range. When I talk to higher-ups and compare what they think they're saying to what my coworkers think they're saying, I find that the rate of lost messages is well over 50%, every message gets corrupted, and latency can be months or years[1](https://danluu.com/sounds-easy/#fn:A). When people imagine how long it should take to build something, they're often imagining a team that works perfectly and spends 100% of its time coding. But that's impossible to scale up. The question isn't whether or not there will inefficiencies, but how much inefficiency. A company that could eliminate organizational inefficiency would be a larger innovation than any tech startup, ever. But when doing the math on how many employees a company “should” have, people usually assume that the company is an efficient organization.

This post happens to use search as an example because I ran across some people who claimed that Lucene was going to surpass Google's capabilities any day now, but there's nothing about this post that's unique to search. If you talk to people in almost any field, you'll hear stories about how people wildly underestimate the complexity of the problems in the field. The point here isn't that it would be impossible for a small team to build something better than Google search. It's entirely plausible that someone will have an innovation as great as PageRank, and that a small team could turn that into a viable company. But once that company is past the VC-funded hyper growth phase and wants to maximize its profits, it will end up with a multi-thousand person platforms org, just like Google's, unless the company wants to leave hundreds of millions or billions of dollars a year on the table due to hardware and software inefficiency. And the company will want to handle languages like Thai, Arabic, Chinese, and Japanese, each of which is non-trivial. And the company will want to have relatively good security. And there are the hundreds of little features that users don't even realize that are there, each of which provides a noticeable increase in revenue. It's "obvious" that companies should outsource their billing, except that when you talk to companies that handle their own billing, they can point to individual features that increase conversion by single or double digit percentages that they can't get from Stripe or Braintree. That fifty person billing team is totally worth it, beyond a certain size. And then there's sales, which most engineers don't even think of[2](https://danluu.com/sounds-easy/#fn:S); the exact same line of reasoning that applies to optimization also applies to sales -- as long as marginal benefit of adding another salesperson exceeds the cost, you should expect the company to keep adding salespeople, which can often result in a sales force that's larger than the engineering team. There's also research which, almost by definition, involves a lot of bets that don't pan out!

It's not that all of those things are necessary to run a service at all; it's that almost every large service is leaving money on the table if they don't seriously address those things. This reminds me of a common fallacy we see in unreliable systems, where people build the happy path with the idea that the happy path is the “real” work, and that error handling can be tacked on later. [For reliable systems, error handling is more work than the happy path](https://danluu.com/postmortem-lessons/). The same thing is true for large services -- all of this stuff that people don't think of as “real” work is more work than the core service[3](https://danluu.com/sounds-easy/#fn:W).

### Correction

I often make minor tweaks and add new information without comment, but the original version of this post had an error and removing the error was a large enough change that I believe it's worth pointing out the change. I had a back of the envelope calculation on the cost of indexing the web with Lucene, but the numbers were based on benchmarks results from some papers and comments from people who work on a commercial search engine. When I tried to reproduce the results from the papers, I found that [it was trivial to get orders of magnitude better performance than reported in one paper](https://twitter.com/danluu/status/814167684954738688?lang=ro) and when I tried to track down the underlying source for the comments by people who work on a commercial search engine, I found that there was no experimental evidence underlying the comments, so I removed the example.

I'm experimenting with writing blog posts stream-of-consciousness, without much editing. Both this post [and my last post](https://danluu.com/bimodal-compensation/) were written that way. [Let me know what you think](https://twitter.com/danluu) of these posts relative to my “normal” posts!
