# 键盘延迟｜Keyboard latency

---

## 正文

如果你看看那些“gaming” keyboards，就会发现其中许多以它们很 fast 为卖点，售价达到 \$100 或更高。你会看到的广告文案包括：

尽管有这些说法，我却只能找到[一个公开 benchmarked keyboard latency 的人](http://forums.blurbusters.com/viewtopic.php?f=10&t=1836)，而且此人只 tested 了两个 keyboards。总的来说，我认为，如果有人在没有 benchmarks 的情况下提出 performance 方面的说法，那些说法很可能并不属实，就像没有经过 tested（或以其他方式 verified）的 code 应当被假定为 broken 一样。

一年前，如果你问我是否打算 build 一套 custom setup 来 measure keyboard latency，我会说这太傻了；然而现在，我却正在用一个 [logic analyzer](https://www.amazon.com/gp/product/B074TVSLN1/ref=as_li_qf_sp_asin_il_tl?ie=UTF8&tag=abroaview-20&camp=1789&creative=9325&linkCode=as2&creativeASIN=B074TVSLN1&linkId=9377ad585ac27e528ee655cc01b48cef) 来 measuring keyboard latency。

这一切的起因是，[我感觉某些老 computers 比现代 machines 要 responsive 得多](https://danluu.com/input-lag/)。例如，running macOS 9 的 iMac G4 和 Apple 2，感觉都比我的 [4.2 GHz Kaby Lake](https://www.amazon.com/gp/product/B01MXSI216/ref=as_li_qf_sp_asin_il_tl?ie=UTF8&tag=abroaview-20&camp=1789&creative=9325&linkCode=as2&creativeASIN=B01MXSI216&linkId=ce7b5129c29c9c012b53e5402ae33a18) system 更 quicker。我从不相信这样的感觉，因为几十年的研究表明，users 的感觉往往与现实截然相反，所以我弄来了一台 high-speed camera，开始 measuring 实际的 keypress-to-screen-update latency 以及 mouse-move-to-screen-update latency。结果发现，那些感觉 quick 的 machines 实际上确实 quick，比我的现代 computer 要 quicker 得多 -- 70 年代和 80 年代的 computers 在 out of the box 的情况下，keypress-to-screen-update latencies 通常在 30ms 到 50ms 的 range 内，而在现代 computers 上，当你在 terminal 中 press 一个 key 时，通常会落在 100ms 到 200ms 的 range 内。借助一套高档 gaming setup，在 well optimized games 中可以降到 50ms 的 range，而且有一种非同寻常的 consumer device 可以轻松降到 50ms 以下，但 default experience 要 slower 得多。现代 computers 的 [throughput 好得多，但它们的 latency](https://stackoverflow.com/a/39187441/334816) 就没那么出色了。

不管怎样，在我做这些 measurements 时，我的 4.2 GHz kaby lake 拥有当时能买到的所有 machine 中最快的 single-threaded performance，但 latency 却比一台来自 70 年代的 quick machine 更差（大约比 Apple 2 差 6x），这似乎有点奇怪。为了弄清 latency 来自哪里，我开始 measuring keyboard latency，因为它是 pipeline 的第一个部分。我的计划是考察 end-to-end pipeline，从起点入手，排除 keyboard latency 作为 latency 真正来源的可能性。但结果发现，keyboard latency 是 significant 的！我惊讶地发现，我 tested 的 median keyboard 所具有的 latency，竟然比 Apple 2 整个 end-to-end pipeline 的 latency 还要多。如果你没有立刻觉得这很荒谬，不妨想想：Apple 2 有 3500 个 running at 1MHz 的 transistors，而一名 Atmel 员工 estimates，如今许多 high-end keyboards 所用的 core 有 [80k transistors](https://www.embeddedrelated.com/showthread/comp.arch.embedded/14362-1.php)，running at 16MHz。这意味着 transistors 的数量是 20x，运行的 clock speed 是 16x -- keyboards 往往比 70 年代和 80 年代的整台 computers 还要 powerful！然而，如今的 median keyboard 所 adds 的 latency，却与一台来自 70 年代的 fast machine 的整个 end-to-end pipeline 一样多。

这些 latency measurements 是从 key 开始 moving 到[与该 key associated 的 USB packet](https://docs.mbed.com/docs/ble-hid/en/latest/api/md_doc_HID.html) 出现在 USB bus 上之间的时间。Numbers 被 rounded 到最近的 `5 ms`，以免给人一种虚假的 precision 感。`easterntimes i500` 也以 `tomoko MMC023` 的名称销售。

connection column 表示所用的 connection。`USB FS` 代表 `usb full speed` protocol，它允许高达 1000Hz polling，这是 high-end keyboards 经常宣传的一项 feature。`USB` 是 `usb low speed` protocol，也就是大多数 keyboards 使用的 protocol。‘gaming’ column 表示该 keyboard 是否以 gaming keyboard 的名义销售。`wireless` 表示某种 keyboard-specific dongle，而 `unifying` 是 logitech 的 wireless device standard。

我们可以看到，即使 tested 的 keyboards 集合有限，keyboards 之间的 latency difference 也可以高达 45ms。而且，一台 attached 了其中一种 slower keyboards 的现代 computer，不可能像一台来自 70 年代或 80 年代的 quick machine 那样 responsive，因为单是 keyboard 就比某些老 computers 的整个 response pipeline 还要 slower。

这确立了一个事实：现代 keyboards 对我们在过去四十年里看到的 latency bloat 有所贡献。问题的另一半是，现代 keyboard 所 added 的 latency，真的会对 users 产生影响吗？从表中我们可以看到，在 tested 的 keyboard 中，average latency 的 difference 可以高达 40ms。40ms 的 latency 是 noticeable 的吗？让我们先看看 keyboards 的一些 latency measurements，然后再看看有关 users 能 notice 多大 latency 的 empirical research。

这方面有相当多的 empirical evidence，我们可以看到，对于非常 simple tasks，[人们能 perceive 低至 2ms 甚至更低的 latencies](https://pdfs.semanticscholar.org/386a/15fd85c162b8e4ebb6023acdce9df2bd43ee.pdf)。而且，increasing latency 不仅对 users 来说是 noticeable 的，[它还会导致 users 在 execute simple tasks 时 less accurately](http://www.tactuallabs.com/papers/howMuchFasterIsFastEnoughCHI15.pdf)。如果你想通过 visual demonstration 看看 latency 是什么样的，而手边又没有一台 super-fast 的老 computer，[不妨看看这个关于 touchscreen latency 的 MSR demo](https://www.youtube.com/watch?v=vOvQCPLkPt4)。

### gaming keyboards 比其他 keyboards 更 faster 吗？

我确实希望先 test 更多 keyboards，再作出强有力的断言，不过从这里的 preliminary tests 看，gaming keyboards 似乎一般并不比 non-gaming keyboards 更 faster。

Gaming keyboards 经常声称具备能够 reduce latency 的 features，例如通过 USB FS 进行 connecting，以及使用 1000Hz polling。USB low speed spec 规定，packets 之间的 minimum time 是 `10ms`，即 100 Hz。然而，常见的情况是 USB devices 将它 round this down 到 nearest power of two，并以 `8ms`，即 125Hz 来 run。在采用 `8ms` polling 时，由于必须等到下一个 polling interval 而 added 的 average latency 是 `4ms`。在采用 `1ms` polling 时，USB polling 带来的 average latency 是 `0.5ms`，得到的 delta 为 `3.5ms`。虽然对于 Apple magic keyboard 这样的 quick keyboard 来说，这可能是 latency 的一项 significant contribution，但很明显，对于大多数 keyboards，是其他 factors 在 dominate keyboard latency，而这里 tested 的 gaming keyboards 如此 slow，以至于 shaving off `3.5ms` 也救不了它们。

关于 gaming keyboards，另一件值得注意的事是，它们经常宣传具备“n-key rollover”（即让 n 个 simulataneous keys 同时被 pressed 的能力——对于许多 key combinations，典型的 keyboards 往往只允许你同时 press 两个 keys，不包括 modifier keys）。虽然这里没有普遍对此进行 tested，但我试用了一款“Razer DeathStalker Expert Gaming Keyboard”，它宣传具备“最多支持 10 个 simultaneous key presses 的 Anti-ghosting capability”。这款 Razer gaming keyboard 并没有以有用的方式具备这种 capability，而且许多由三个 keys 组成的 combinations 都不能 work。我想，它们的广告宣称在技术上或许可以算是真的，因为 3 在某些情况下可以算是“up to 10”，但就像 gaming keyboards 声称由于采用 1000 Hz polling 而具有 lower latency 一样，这种说法即使往好里说，也极具误导性。

### 结论

大多数 keyboards 所 add 的 latency 足以让 user experience 明显变差，而宣传 speed 的 keyboards 不一定更 faster。我们 measured 的两款 gaming keyboards 并不比 non-gaming keyboards 更 faster，而 measured 的最快的 fastest keyboard 是 Apple 的一款 minimalist keyboard，它在营销时强调 design 多于 speed。

此前，我们已经看到，[terminals 能够 add significant latency；如果选择了“合适”的 terminal，在 mildly pessimistic conditions 下可达到 100ms](https://danluu.com/term-latency/)。在今后的一篇文章中，我们将考察整个 end-to-end pipeline，看看 latency 还悄悄进入了哪些地方，也会看看一些现代 devices 如何将 latency 控制在较低水平。

### 附录：latency 来自哪里？

latency 的一个主要来源是 key travel time。measured 的 quickest keyboard 同时也具有 shortest key travel distance，而且远短于其他 keyboards，这并非巧合。我用来 measure end-to-end latency 的 video setup 是一台 240 fps camera，这意味着 frames 之间相隔 4ms。在拍摄“正常的”keypresses 和 typing 时，一个 key 需要经过 4-8 frames 才会变得 fully depressed。大多数 switches 会在 key 达到 fully depressed 之前就开始 firing，但 key travel time 仍然 significant，而且很容易 add `10ms` 的 delay（或更多，具体取决于 switch mechanism）。与之相比，measured 的 Apple “magic” keyboard 的 key travel 如此 short，以至于无法用 240 fps camera 捕捉到，这表明 key travel time 是 < 4ms。

请注意，与我在网上找到的另一项 measurement 不同，这项 measurement 是从 keypress 的开始算起，而不是从 switch activation 算起。这是因为，作为人，你并不是在 activate switch，而是在 press key。从 switch activiation time 开始的 measurement 会漏掉 latency 的这一大块 component。例如，如果你正在玩 game，并在看到某件事发生时从 moving forward 切换到 moving backwards，你就必须付出 key movement 的 cost，而不同 keyboards 的这个 cost 并不相同。对此，一个常见的回应是，“真正的”gamers 会 preload keys，从而不必付出 key travel cost；但如果你带着 high speed camera 四处看看人们实际如何使用 keyboards，就会发现，即使观察的是 gamers，significantly preloaded 的 keypresses 所占的 fraction 也基本为 zero。如果观察 high-level competitive gamers，你或许会看到不同的情况，但即使如此，举个例子，使用 standard wasd 或 esdf layout 的人在从 back 转向 forward 时，通常也不会 preload 一个 key。另外，认为 keys 有一大段 useless travel 也没关系，因为可以在真正 pressing key 之前先 pre-depress key，这种想法简直荒谬。这就像说现代 computers 的 latency 没问题，因为有些人会 build gaming boxes，在运行 unusually well optimzed software 时能够获得 50ms response time。Normal、non-hardcore-gaming users 根本不会这样做。既然这些 users 占据了市场的绝大多数，那么即使所有“认真的”gamers 都这样做，那也仍然只是一个 round error。

latency 的其他主要来源是对 [keyboard matrix](http://blog.komar.be/how-to-make-a-keyboard-the-matrix/) 进行 scaning，以及 debouncing。这两种 delays 都不是 inherent 的——keyboards 使用必须被 scanned 的 matrix，而不是为每个 key 配备一根 wire，是因为这样能省几块钱；大多数 keyboards 以如此 slow rate 来 scan matrix，以至于会引起人能够察觉的 delays，也是因为这样能省几块钱。但只要 manufacturer 愿意在 manufacturing keyboard 上多花一点钱，就能使由此产生的 delay 远低于 human perception 的 threshold。关于 debouncing delay，请见下文。

虽然我们在这里没有讨论 throughput，但当我 measure 自己的 typing speed 时，我发现使用 [low-travel Apple keyboard](https://www.amazon.com/gp/product/B01NABDNPH/ref=as_li_tl?ie=UTF8&tag=abroaview-20&camp=1789&creative=9325&linkCode=as2&creativeASIN=B01NABDNPH&linkId=ccde207372bd2239204e1ebc3a36a9cd) 时能够比使用其他任何 keyboards 都 type faster。这件事无法进行 blinded experiment，但 Gary Bernhardt 等人也观察到了同样的现象。有些人声称 key travel 对 typing speed 并不重要，因为他们只使用必要的 minimum amount 的 travel，所以这不可能有影响；但与前面关于 keypresses 的说法一样，如果你带着 high speed camera 四处观察人们 type 时实际发生的情况，就会发现很难找到真正这样做的人。

### 2022 更新

我进行这些 experiments 时，似乎还没有人在多个 keyboards 上 testing latency。我觉得自己得到的 results 如此 unintuitive，于是试着寻找其他人的 keyboard latency measurements，而我能找到的只有一篇论坛帖子：有人试着 measure 自己的 keyboard（只有一个），得到的 results 也在同一 range 内，但他使用的 setup 不够 fast，无法真正妥当地 measure latency。我还用 high-speed camera 拍摄了自己的 test 以及非 test 的 keypresses，看看 depress keys 需要多长时间，而这些 results 与我现在得到的 results 并没有明显的 inconsistent 之处。

从我写完那篇文章的一两年后开始，我看到一些 gaming mouse 和 keyboard 制造商讨论如何制造 lower latency devices，而他们也开始推出确实具有 lower latency 的 devices，不再像他们以前的 devices 那样，基本上只是套着 gaming skins，而且往往还会发光。

如果你想要一个不是 Apple keyboard 的 low-latency keyboard（与我交谈过的不少人都说，长时间使用 Apple keyboard 后会感到 finger pain），[SteelSeries Apex Pro](https://amzn.to/3AYD7FG) 的 latency 相当 low；至于 mouse，[Corsair Sabre](https://amzn.to/3gPLoVl) 也相当 quick。

从那以后，另一个变化是，更多人明白了 debouncing 并不一定要 add noticeable latency。我写原文时，曾有多个 keyboard 制造商向我解释，说那篇文章是错的，debouncing 时不可能不 add latency。我觉得这很奇怪，因为我本来以为，一个大一的 EE 学生，甚至一个摆弄 electronics 的高中生，都应该明白为什么并非如此；但不知什么原因，多个以制造 keyboards 为生的人却不明白这一点。如今，如何在不 adding latency 的情况下 debounce 已经成为常识，而当我看到讨论中有人说 debouncing 必须 add 大量 latency 时，通常都会有人纠正他们。这一知识已经传播到大多数 keyboard 制造商那里，并 reduced 了一些新 keyboards 的 keyboard latency，不过我知道仍然至少有一家 keyboard 制造商不相信可以用 low latency 来 debounce，因此他们的新 keyboards 仍然 add 了相当多的 latency。

### 附录：针对 latency 无关紧要这一常见 arguments 的 counter-arguments

在写这篇文章之前，我阅读了自己能找到的关于 latency 的内容，很难找到哪篇面向非专业读者的文章或哪个评论区，没有出现下面列出的 arguments 中的至少一个：

#### Computers 和 devices 都很 fast

对于 latency 问题，最常见的回应是，input latency 基本上是 zero，或者如此 close to zero，以至于只是个 rounding error。例如，[这篇询问 keyboard latency 的 slashdot 帖子](https://hardware.slashdot.org/story/13/07/13/1331235/ask-slashdot-low-latency-ps2usb-gaming-keyboards)中，两条最热门的评论都说 keyboards 如此 fast，以至于 keyboard speed 并不重要。甚至有一个人说

> 没有任何一个现代 keyboard 具有 50ms latency。你们（humans）才有那种 latency。
> 
> 至于 response times，你只需要 increase USB stack 上的 poll time

正如我们已经看到的，一些 devices 确实具有处于 50ms range 内的 latencies。这段引文以及该讨论串中的其他评论说明了另一个常见的 fallacy -- 即 input devices 受到 USB polling 的 speed 的 limited。虽然这在技术上是可能的，但大多数 devices 远远没有 fast 到会受到 USB polling latency 的 limited 的程度。

遗憾的是，网上大多数关于 input latency 的解释都[假定 USB bus 是 limiting factor](https://byuu.org/articles/latency/)。

#### Humans 无法 notice 100ms 或 200ms latency

[这里有一位“研究 visual perception 和 cognition 的 cognitive neuroscientist”](https://stackoverflow.com/a/39985088/334816)，他提到 human reaction time 大约是 200ms 这一事实，接着又堆砌了一大堆科学术语的胡言乱语，声称没有人能够真正 notice 低于 100ms 的 latencies。这有点不同寻常，因为这位评论者声称自己具有某种特殊权威，并使用了大量 terminology；不过，人们经常声称，因为 human reaction time 是 200ms，所以你无法 notice 50ms 或 100ms 的 latency。这其实说不通，因为这些是 independent quantities。这种 argument 就像说，因为一次航班的飞行时间是六个小时，所以航班延误一个小时你也不会察觉。

这种 reasoning 的另一个问题是，从 keypress 到 screen update 的 full pipeline 相当长；如果你说这里 add 10ms、那里 add 10ms 总是没关系，那么整个 pipeline 最终就会积累多得多的 bloat。这也正是我们走到今天这一步的原因：你可以买到一个 system，配备能提供金钱所能买到的最快 single-threaded performance 的 CPU，却得到一台 70 年代 machine 的 6x latency。

#### 这无关紧要，因为 game loop 以 60 Hz runs

这从根本上说与上面的 fallacy 相同。如果你有一个 delay，其 duration 是一个 clock period 的 half，那么这个 delay 就有 50% chance 将 event 推到下一个 processing step。这比 100% chance 要好，但我不明白，为什么人们认为必须有一个与 clock period 一样长的 delay，这个 delay 才会产生影响。另外，作为参考，这里 measured 的最 slow 和最 fast 的 keyboard 之间的 `45ms` delta，在 60fps 下 corresponds to 2.7 frames。

#### 由于 [debouncing](http://www.eng.utah.edu/~cs5780/debouncing.pdf)，Keyboards 不可能以快于 5ms/10ms/20ms 的速度 response

即使不费尽周折去 optimize switch mechanism，只要你愿意在 system 中加入 hysteresis，就没有理由认为 keyboard 不能在看到 edge 的那一刻，就假定正在发生 keypress（或 release）。其他类型的 systems 通常就是这样做的，而且 AFAICT，没有理由认为 keyboards 不能做同样的事（也许有些已经这样做了）。debounce time 可能会 limit key 的 repeat rate，但没有任何 inherent reason 要求它必须 affect latency。而如果我们考虑 repeat rate，设想由于 introducing hysteresis，key state 的 rate of change 有一个 5ms limit。这让我们每 10ms 就能完成一个 full keypress cycle（press 和 release），或者说每个 key 每秒 100 keypresses，这远远超出了任何 human 的 capacity。你也许会 argue，这 introduces 了一种 imprecision，而这在某些 applications（music、rythym games）中可能很重要，但那是受到 switch mechanism 的 limited。使用带有 hysteresis 的 debouncing mechanism，并不会让我们的处境比以前更差。

debounce delay 的另一个问题是，大多数 keyboard 制造商似乎把 scan rate 和 debounce delay 混为一谈。具有处于 100 Hz 到 200 Hz range 内的 scan rates 的 keyboards 很常见。他们用诸如“scanning faster 没有意义，因为 debounce delay 是 5ms”这样的说法来为此辩护，而这 combines 了上面提到的两个 fallacies。如果你拿出 Apple 2e 的 schematics，就能看到 scan rate 大约是 50 kHz。它的 debounce time 大约是 6ms，这 corresponds to 167 Hz 的 frequency。为什么要如此 quickly 地 scan？fast scan 让 keyboard controller 几乎立即就能 start the clock 来计算 debounce time（最多在 20 microseconds 之后），而一个以 167 Hz scans 的现代 keyboard，可能要等到 6ms 后，才会 start the clock 来进行 debouncing，也就是要经过 300x 的时间。

抱歉没有在这里解释 terminology，但我认为，提出这一 objection 的任何人都应该理解这段 explanation :-)。

## 原文

If you look at “gaming" keyboards, a lot of them sell for $100 or more on the promise that they’re fast. Ad copy that you’ll see includes:

Despite all of these claims, I can only find [one person who’s publicly benchmarked keyboard latency](http://forums.blurbusters.com/viewtopic.php?f=10&t=1836) and they only tested two keyboards. In general, my belief is that if someone makes performance claims without benchmarks, the claims probably aren’t true, just like how code that isn’t tested (or otherwise verified) should be assumed broken.

A year ago, if you’d asked me if I was going to build a custom setup to measure keyboard latency, I would have said that’s silly, and yet here I am, measuring keyboard latency with a [logic analyzer](https://www.amazon.com/gp/product/B074TVSLN1/ref=as_li_qf_sp_asin_il_tl?ie=UTF8&tag=abroaview-20&camp=1789&creative=9325&linkCode=as2&creativeASIN=B074TVSLN1&linkId=9377ad585ac27e528ee655cc01b48cef).

It all started because [I had this feeling that some old computers feel much more responsive than modern machines](https://danluu.com/input-lag/). For example, an iMac G4 running macOS 9 or an Apple 2 both feel quicker than my [4.2 GHz Kaby Lake](https://www.amazon.com/gp/product/B01MXSI216/ref=as_li_qf_sp_asin_il_tl?ie=UTF8&tag=abroaview-20&camp=1789&creative=9325&linkCode=as2&creativeASIN=B01MXSI216&linkId=ce7b5129c29c9c012b53e5402ae33a18) system. I never trust feelings like this because there’s decades of research showing that users often have feelings that are the literal opposite of reality, so got a high-speed camera and started measuring actual keypress-to-screen-update latency as well as mouse-move-to-screen-update latency. It turns out the machines that feel quick are actually quick, much quicker than my modern computer -- computers from the 70s and 80s commonly have keypress-to-screen-update latencies in the 30ms to 50ms range out of the box, whereas modern computers are often in the 100ms to 200ms range when you press a key in a terminal. It’s possible to get down to the 50ms range in well optimized games with a fancy gaming setup, and there’s one extraordinary consumer device that can easily get below 50ms, but the default experience is much slower. Modern computers have much better [throughput, but their latency](https://stackoverflow.com/a/39187441/334816) isn’t so great.

Anyway, at the time I did these measurements, my 4.2 GHz kaby lake had the fastest single-threaded performance of any machine you could buy but had worse latency than a quick machine from the 70s (roughly 6x worse than an Apple 2), which seems a bit curious. To figure out where the latency comes from, I started measuring keyboard latency because that’s the first part of the pipeline. My plan was to look at the end-to-end pipeline and start at the beginning, ruling out keyboard latency as a real source of latency. But it turns out keyboard latency is significant! I was surprised to find that the median keyboard I tested has more latency than the entire end-to-end pipeline of the Apple 2. If this doesn’t immedately strike you as absurd, consider that an Apple 2 has 3500 transistors running at 1MHz and an Atmel employee estimates that the core used in a number of high-end keyboards today has [80k transistors](https://www.embeddedrelated.com/showthread/comp.arch.embedded/14362-1.php) running at 16MHz. That's 20x the transistors running at 16x the clock speed -- keyboards are often more powerful than entire computers from the 70s and 80s! And yet, the median keyboard today adds as much latency as the entire end-to-end pipeline as a fast machine from the 70s.

The latency measurements are the time from when the key starts moving to the time when the [USB packet associated with the key](https://docs.mbed.com/docs/ble-hid/en/latest/api/md_doc_HID.html) makes it out onto the USB bus. Numbers are rounded to the nearest `5 ms` in order to avoid giving a false sense of precision. The `easterntimes i500` is also sold as the `tomoko MMC023`.

The connection column indicates the connection used. `USB FS` stands for the `usb full speed` protocol, which allows up to 1000Hz polling, a feature commonly advertised by high-end keyboards. `USB` is the `usb low speed` protocol, which is the protocol most keyboards use. The ‘gaming’ column indicates whether or not the keyboard is branded as a gaming keyboard. `wireless` indicates some kind of keyboard-specific dongle and `unifying` is logitech's wireless device standard.

We can see that, even with the limited set of keyboards tested, there can be as much as a 45ms difference in latency between keyboards. Moreover, a modern computer with one of the slower keyboards attached can’t possibly be as responsive as a quick machine from the 70s or 80s because the keyboard alone is slower than the entire response pipeline of some older computers.

That establishes the fact that modern keyboards contribute to the latency bloat we’ve seen over the past forty years. The other half of the question is, does the latency added by a modern keyboard actually make a difference to users? From looking at the table, we can see that among the keyboard tested, we can get up to a 40ms difference in average latency. Is 40ms of latency noticeable? Let’s take a look at some latency measurements for keyboards and then look at the empirical research on how much latency users notice.

There’s a fair amount of empirical evidence on this and we can see that, for very simple tasks, [people can perceive latencies down to 2ms or less](https://pdfs.semanticscholar.org/386a/15fd85c162b8e4ebb6023acdce9df2bd43ee.pdf). Moreover, increasing latency is not only noticeable to users, [it causes users to execute simple tasks less accurately](http://www.tactuallabs.com/papers/howMuchFasterIsFastEnoughCHI15.pdf). If you want a visual demonstration of what latency looks like and you don’t have a super-fast old computer lying around, [check out this MSR demo on touchscreen latency](https://www.youtube.com/watch?v=vOvQCPLkPt4).

### Are gaming keyboards faster than other keyboards?

I’d really like to test more keyboards before making a strong claim, but from the preliminary tests here, it appears that gaming keyboards aren’t generally faster than non-gaming keyboards.

Gaming keyboards often claim to have features that reduce latency, like connecting over USB FS and using 1000Hz polling. The USB low speed spec states that the minimum time between packets is `10ms`, or 100 Hz. However, it’s common to see USB devices round this down to the nearest power of two and run at `8ms`, or 125Hz. With `8ms` polling, the average latency added from having to wait until the next polling interval is `4ms`. With `1ms` polling, the average latency from USB polling is `0.5ms`, giving us a `3.5ms` delta. While that might be a significant contribution to latency for a quick keyboard like the Apple magic keyboard, it’s clear that other factors dominate keyboard latency for most keyboards and that the gaming keyboards tested here are so slow that shaving off `3.5ms` won’t save them.

Another thing to note about gaming keyboards is that they often advertise "n-key rollover" (the ability to have n simulataneous keys pressed at once — for many key combinations, typical keyboards will often only let you press two keys at once, excluding modifier keys). Although not generally tested here, I tried a "Razer DeathStalker Expert Gaming Keyboard" that advertises "Anti-ghosting capability for up to 10 simultaneous key presses". The Razer gaming keyboard did not have this capability in a useful manner and many combinations of three keys didn't work. Their advertising claim could, I suppose, technically true in that 3 in some cases could be "up to 10", but like gaming keyboards claiming to have lower latency due to 1000 Hz polling, the claim is highly misleading at best.

### Conclusion

Most keyboards add enough latency to make the user experience noticeably worse, and keyboards that advertise speed aren’t necessarily faster. The two gaming keyboards we measured weren’t faster than non-gaming keyboards, and the fastest keyboard measured was a minimalist keyboard from Apple that’s marketed more on design than speed.

Previously, we've seen that [terminals can add significant latency, up 100ms in mildly pessimistic conditions if you choose the "right" terminal](https://danluu.com/term-latency/). In a future post, we'll look at the entire end-to-end pipeline to see other places latency has crept in and we'll also look at how some modern devices keep latency down.

### Appendix: where is the latency coming from?

A major source of latency is key travel time. It’s not a coincidence that the quickest keyboard measured also has the shortest key travel distance by a large margin. The video setup I’m using to measure end-to-end latency is a 240 fps camera, which means that frames are 4ms apart. When videoing “normal" keypresses and typing, it takes 4-8 frames for a key to become fully depressed. Most switches will start firing before the key is fully depressed, but the key travel time is still significant and can easily add `10ms` of delay (or more, depending on the switch mechanism). Contrast this to the Apple "magic" keyboard measured, where the key travel is so short that it can’t be captured with a 240 fps camera, indicating that the key travel time is < 4ms.

Note that, unlike the other measurement I was able to find online, this measurement was from the start of the keypress instead of the switch activation. This is because, as a human, you don't activate the switch, you press the key. A measurement that starts from switch activiation time misses this large component to latency. If, for example, you're playing a game and you switch from moving forward to moving backwards when you see something happen, you have pay the cost of the key movement, which is different for different keyboards. A common response to this is that "real" gamers will preload keys so that they don't have to pay the key travel cost, but if you go around with a high speed camera and look at how people actually use their keyboards, the fraction of keypresses that are significantly preloaded is basically zero even when you look at gamers. It's possible you'd see something different if you look at high-level competitive gamers, but even then, just for example, people who use a standard wasd or esdf layout will typically not preload a key when going from back to forward. Also, the idea that it's fine that keys have a bunch of useless travel because you can pre-depress the key before really pressing the key is just absurd. That's like saying latency on modern computers is fine because some people build gaming boxes that, when run with unusually well optimzed software, get 50ms response time. Normal, non-hardcore-gaming users simply aren't going to do this. Since that's the vast majority of the market, even if all "serious" gamers did this, that would stll be a round error.

The other large sources of latency are scaning the [keyboard matrix](http://blog.komar.be/how-to-make-a-keyboard-the-matrix/) and debouncing. Neither of these delays are inherent -- keyboards use a matrix that has to be scanned instead of having a wire per-key because it saves a few bucks, and most keyboards scan the matrix at such a slow rate that it induces human noticable delays because that saves a few bucks, but a manufacturer willing to spend a bit more on manufacturing a keyboard could make the delay from that far below the threshold of human perception. See below for debouncing delay.

Although we didn't discuss throughput in this, when I measure my typing speed, I find that I can type faster with the [low-travel Apple keyboard](https://www.amazon.com/gp/product/B01NABDNPH/ref=as_li_tl?ie=UTF8&tag=abroaview-20&camp=1789&creative=9325&linkCode=as2&creativeASIN=B01NABDNPH&linkId=ccde207372bd2239204e1ebc3a36a9cd) than with any of the other keyboards. There's no way to do a blinded experiment for this, but Gary Bernhardt and others have also observed the same thing. Some people claim that key travel doesn't matter for typing speed because they use the minimum amount of travel necessary and that this therefore can't matter, but as with the above claims on keypresses, if you walk around with a high speed camera and observe what actually happens when people type, it's very hard to find someone who actually does this.

### 2022 update

When I ran these experiments, it didn't seem that anyone was testing latency across multiple keyboards. I found the results I got so unintuitive that I tried to find anyone else's keyboard latency measurements and all I could find was a forum post from someone who tried to measure their keyboard (just one) and got results in the same range, but using a setup that wasn't fast enough to really measure the latency properly. I also video'd my test as well as non-test keypresses with a high-speed camera to see how much time it took to depress keys, and the results weren't obviously inconsistent with the results I got now.

Starting a year or two after I wrote the post, I witnessed some discussions from some gaming mouse and keyboard makers on how to make lower latency devices and they started releasing devices that actually have lower latency, as opposed to the devices they had, which basically had gaming skins and would often light up.

If you want a low-latency keyboard that isn't the Apple keyboard (quite a few people I've talked to report finger pain after using the Apple keyboard for an extended period of time), the [SteelSeries Apex Pro](https://amzn.to/3AYD7FG) is fairly low latency; for a mouse, the [Corsair Sabre](https://amzn.to/3gPLoVl) is also pretty quick.

Another change since then is that more people understand that debouncing doesn't have to add noticeable latency. When I wrote the original post, I had multiple keyboard makers explain to me that the post is wrong and it's impossible to not add latency when debouncing. I found that very odd since I'd expect a freshman EE or, for that matter, a high school kid who plays with electronics, to understand why that's not the case but, for whatever reason, multiple people who made keyboards for a living didn't understand this. Now, how to debounce without adding latency has become common knowledge and, when I see discussions where someone says debouncing must add a lot of latency, they usually get corrected. This knowledge has spread to most keyboard makers and reduced keyboard latency for some new keyboards, although I know there's still at least one keyboard maker that doesn't believe that you can debounce with low latency and they still add quite a bit of latency from their new keyboards as a result.

### Appendix: counter-arguments to common arguments that latency doesn’t matter

Before writing this up, I read what I could find about latency and it was hard to find non-specialist articles or comment sections that didn’t have at least one of the arguments listed below:

#### Computers and devices are fast

The most common response to questions about latency is that input latency is basically zero, or so close to zero that it’s a rounding error. For example, two of the top comments on [this slashdot post asking about keyboard latency](https://hardware.slashdot.org/story/13/07/13/1331235/ask-slashdot-low-latency-ps2usb-gaming-keyboards) are that keyboards are so fast that keyboard speed doesn’t matter. One person even says

> There is not a single modern keyboard that has 50ms latency. You (humans) have that sort of latency.
> 
> As far as response times, all you need to do is increase the poll time on the USB stack

As we’ve seen, some devices do have latencies in the 50ms range. This quote as well as other comments in the thread illustrate another common fallacy -- that input devices are limited by the speed of the USB polling. While that’s technically possible, most devices are nowhere near being fast enough to be limited by USB polling latency.

Unfortunately, most online explanations of input latency [assume that the USB bus is the limiting factor](https://byuu.org/articles/latency/).

#### Humans can’t notice 100ms or 200ms latency

[Here’s a “cognitive neuroscientist who studies visual perception and cognition"](https://stackoverflow.com/a/39985088/334816) who refers to the fact that human reaction time is roughly 200ms, and then throws in a bunch more scientific mumbo jumbo to say that no one could really notice latencies below 100ms. This is a little unusual in that the commenter claims some kind of special authority and uses a lot of terminology, but it’s common to hear people claim that you can’t notice 50ms or 100ms of latency because human reaction time is 200ms. This doesn’t actually make sense because there are independent quantities. This line of argument is like saying that you wouldn’t notice a flight being delayed by an hour because the duration of the flight is six hours.

Another problem with this line of reasoning is that the full pipeline from keypress to screen update is quite long and if you say that it’s always fine to add 10ms here and 10ms there, you end up with a much larger amount of bloat through the entire pipeline, which is how we got where we are today, where can buy a system with the CPU that gives you the fastest single-threaded performance money can buy and get 6x the latency of a machine from the 70s.

#### It doesn’t matter because the game loop runs at 60 Hz

This is fundamentally the same fallacy as above. If you have a delay that’s half the duration a clock period, there’s a 50% chance the delay will push the event into the next processing step. That’s better than a 100% chance, but it’s not clear to me why people think that you’d need a delay as long as the the clock period for the delay to matter. And for reference, the `45ms` delta between the slowest and fastest keyboard measured here corresponds to 2.7 frames at 60fps.

#### Keyboards can’t possibly response faster more quickly than 5ms/10ms/20ms due to [debouncing](http://www.eng.utah.edu/~cs5780/debouncing.pdf)

Even without going through contortions to optimize the switch mechanism, if you’re willing to put hysteresis into the system, there’s no reason that the keyboard can’t assume a keypress (or release) is happening the moment it sees an edge. This is commonly done for other types of systems and AFAICT there’s no reason keyboards couldn’t do the same thing (and perhaps some do). The debounce time might limit the repeat rate of the key, but there’s no inherent reason that it has to affect the latency. And if we're looking at the repeat rate, imagine we have a 5ms limit on the rate of change of the key state due to introducing hysteresis. That gives us one full keypress cycle (press and release) every 10ms, or 100 keypresses per second per key, which is well beyond the capacity of any human. You might argue that this introduces a kind of imprecision, which might matter in some applications (music, rythym games), but that's limited by the switch mechanism. Using a debouncing mechanism with hysteresis doesn't make us any worse off than we were before.

An additional problem with debounce delay is that most keyboard manufacturers seem to have confounded scan rate and debounce delay. It's common to see keyboards with scan rates in the 100 Hz to 200 Hz range. This is justified by statements like "there's no point in scanning faster because the debounce delay is 5ms", which combines two fallacies mentioned above. If you pull out the schematics for the Apple 2e, you can see that the scan rate is roughly 50 kHz. Its debounce time is roughly 6ms, which corresponds to a frequency of 167 Hz. Why scan so quickly? The fast scan allows the keyboard controller to start the clock on the debounce time almost immediately (after at most 20 microseconds), as opposed a modern keyboard that scans at 167 Hz, which might not start the clock on debouncing for 6ms, or after 300x as much time.

Apologies for not explaining terminology here, but I think that anyone making this objection should understand the explanation :-).

### Appendix: experimental setup

The USB measurement setup was a [USB cable](https://www.amazon.com/gp/product/B000E5CYW8/ref=as_li_qf_sp_asin_il_tl?ie=UTF8&tag=abroaview-20&camp=1789&creative=9325&linkCode=as2&creativeASIN=B000E5CYW8&linkId=4e14a96314e989f8166fe183a0a9b0ee0%20that%20was%20cut%20open%20to%20expose%20the%20wires,%20connected%20to%20a%20logic%20analyzer.%20The%20exact%20model%20of%20logic%20analzyer%20doesn%E2%80%99t%20really%20matter,%20but%20if%20you%E2%80%99re%20curious%20about%20the%20details,%20this%20set%20of%20experiments%20used%20a%20[salae%20pro]\(https://www.amazon.com/gp/product/B074TWM5WX/ref=as_li_tl?ie=UTF8&tag=abroaview-20&camp=1789&creative=9325&linkCode=as2&creativeASIN=B074TWM5WX&linkId=562b98ee01041c876c27311abdff418c\).%20While%20the%20exact%20model%20of%20USB%20cable%20doesn%27t%20matter,%20if%20you%20want%20to%20reproduce%20the%20experiment,%20I%20recommend%20using%20a%20[relatively%20short%20USB%20cable]\(https://www.amazon.com/gp/product/B000E5CYW8/ref=as_li_qf_sp_asin_il_tl?ie=UTF8&tag=abroaview-20&camp=1789&creative=9325&linkCode=as2&creativeASIN=B000E5CYW8&linkId=4e14a96314e989f8166fe183a0a9b0ee). Cutting open the cable damages the signal integrity and I found that, with a very long cable, some keyboards that weakly drive the data lines didn't drive them strongly enough to get a good signal with the cheap logic analyzer I used.

The start-of-input was measured by pressing two keys at once -- one key on the keyboard and a button that was also connected to the logic analyzer. This introduces some jitter as the two buttons won’t be pressed at exactly the same time. To calibrate the setup, we used two identical buttons connected to the logic analyzer. The median jitter was < 1ms and the 90%-ile jitter was roughly 5ms. This is enough that tail latency measurements for quick keyboards aren’t really possible with this setup, but average latency measurements like the ones done here seem like they should be ok. The input jitter could probably be reduced to a negligible level by building a device to both trigger the logic analyzer and press a key on the keyboard under test at the same time. Average latency measurements would also get better with such a setup (because it would be easier to run a large number of measurements).

If you want to know the exact setup, a [E-switch LL1105AF065Q](https://www.digikey.com/product-detail/en/e-switch/LL1105AF065Q/LL1105AF065Q-ND/3777946) switch was used. Power and ground were supplied by [an arduino board](https://www.amazon.com/gp/product/B008GRTSV6/ref=as_li_tl?ie=UTF8&tag=abroaview-20&camp=1789&creative=9325&linkCode=as2&creativeASIN=B008GRTSV6&linkId=51afaa1d76d1e6ef7c1e6bc0eeebdf9d). There’s no particular reason to use this setup. In fact, it’s a bit absurd to use an entire arduino to provide power, but this was done with spare parts that were lying around and this stuff just happened to be stuff that [RC](https://www.recurse.com/scout/click?t=b504af89e87b77920c9b60b2a1f6d5e8) had in their lab, with the exception of the switches. There weren’t two identical copies of any switch, so we bought a few switches so we could do calibration measurements with two identical switches. The exact type of switch isn’t important here; any low-resistance switch would do.

Tests were done by pressing the `z` key and then looking for byte 29 on the USB bus and then marking the end of the first packet containing the appropriate information. But, as above, any key would do.

I don't actually trust this setup and I'd like to build a completely automated setup before testing more keyboards. While the measurements are in line with the one other keyboard measurement I could find online, this setup has an inherent imprecision that's probably in the 1ms to 10ms range. While averaging across multiple measurements reduces that imprecision, since the measurements are done by a human, it's not guaranteed and perhaps not even likely that the errors are independent and will average out.
