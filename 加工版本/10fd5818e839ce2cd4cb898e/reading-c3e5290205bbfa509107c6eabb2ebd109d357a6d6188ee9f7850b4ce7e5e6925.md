# 为什么要急性子？

---

## 正文

2017 年 6 月：我和伴侣 Eve 被困在亚的斯亚贝巴博莱国际机场国内转机区的落地签柜台。其他转机乘客都是埃塞俄比亚人，他们轻快地从我们身边走过，在护照检查处排起一条长龙。我一拿到那枚宝贵的印章，就飞奔过去占住位置，免得更多乘客排到我们前面。

十分钟后，Eve 找到了我。坐了一夜红眼航班，她昏昏沉沉，又因独自应付埃塞俄比亚的签证柜台而不知所措。“你为什么非得那样跑掉？！”不知怎么，“这样我们就能在登机口等，而不是在护照检查的队伍里等”听起来实在算不上什么好理由。

就是在这一刻，我意识到，自己是个急躁得不讲道理的人。

（回想起来，我对任何耗时超过 15 秒的日常活动，都忍不住在脑子里做一遍 [critical path analysis](https://en.wikipedia.org/wiki/Critical_path_method)，这大概早该让我有所察觉。但我一直以为这很正常，直到开始和人约会，才注意到他们做事的顺序常常是 sub-optimal 的。）

* * *

既然已经坦白了自己急躁的毛病，接下来这篇文章的其余部分，我要试着说服你：这其实是件好事。

（好的一面，是经常问自己“怎样才能让这件事占用更少的 calendar time”这个习惯。我不建议以令人讨厌的方式表现出来，比如把伴侣丢在埃塞俄比亚的机场。）

急躁是让做事变得 faster 的最佳方式。而且，在数量多得令人惊讶的 domains 中，做事非常 fast 与 effective 之间都存在 correlates strongly 的关系。

显然，其中很多都是 non-causal correlations。不过，如此多不同的 datapoints 呈现出的 convergence，仍然令人惊讶：

### E-mail（电子邮件）

这看起来微不足道，但许多不同的人都注意到，对 emails 的 respond 很慢不是个好兆头；或者，那些你以为会忙得不可开交的名人，respond 却快得出奇。

[Sriram Krishnan](https://twitter.com/sriramk/status/1214278840358359040)：

> -   最有名、最有趣、最有影响力的人，都亲自 read 自己的 email
>     
> -   他们几乎无一例外都善于 quickly responding
>     
> -   他们总是非常、非常好奇。
>     
> -   他们的时间很少。任何有 friction 的事都会留到“以后”再做
>     

[Sam Altman](https://blog.samaltman.com/how-to-invest-in-startups)：

> 人们往往要么是 slow movers，要么是 fast movers，而这一点似乎更难改变。成为 fast mover 是件很重要的事；一个有些微不足道的例子是，我 investing 于那些不会对重要 emails 进行 respond quickly 的 founders，几乎从来没有赚到钱。

### Startups（初创企业）

quickly launching（以及 iterating）是 startups 能否 succeed 的一个 major factor，这已经成为普遍共识。

[还是 Sam Altman](https://startupclass.samaltman.com/courses/lec02/)：

> 你必须 decisive。Indecisiveness 是 startup 的杀手。Mediocre founders 花大量时间谈论宏伟计划，却从不 make a decision。他们说着，你知道，我可以做这件事，也可以做另一件事，就这样来回摇摆，始终不 act。而你真正需要的，是这种 bias towards action。
> 
> 最优秀的 founders 做的事情看起来很小，但他们 move really quickly。而且，他们 get things done really quickly。每次和最优秀的 founders 交谈，他们都已经完成了新的事情。事实上，我们发现，在 YC 中，这是最能 predicts founders 的 success 的一点。如果每次和一个 team 交谈，他们都已经完成了新的事情，那就是我们判断一家 company 将会 successful 的最佳 predictor。

这一点甚至 propagates 到你 deploy software changes 有多快的层面。[Nick Schrock](https://twitter.com/schrockn/status/1130569945891258369) 谈 Facebook / Instagram 的 moving fast and breaking things：

> Instagram 在 operationally 方面甚至比 Facebook 更 faster。他们有 continuous deployment。任何 engineer 都可以随时 deploy（他们会 run 一个名叫“Yolout”的 command，哈哈）。当时 Facebook 在 web 上采用 weekly deploys，在 mobile 上则慢得多。
> 
> IG 的故事无疑让 those-who-ship-faster-win 这一 argument 更有说服力
> 
> ……值得注意的是，Facebook 从中吸取了经验。随着 company 壮大，release cadence 变得更 faster。先是 daily，然后是 twice daily，现在已经是 continuous。这是 release engineering team 取得的一项了不起的成就。

不只是 Facebook；[_Accelerate_ 发现 deploy frequency 与 performance 之间存在 strong correlation](https://www.amazon.com/Accelerate-Software-Performing-Technology-Organizations-ebook/dp/B07B9F83WM/)：

> 概括来说，在 2017 年，我们发现，与 low performers 相比，high performers 的表现是：
> 
> -   code deployments 的频率是其 46 倍
>     
> -   lead time from commit to deploy 快 440 倍
>     

### Apps/tools（应用与工具）

“speed 非常重要”这一 principle，甚至也 applies 于已经非常 fast 的事物。Google 发现，[users 对 faster webpages 的偏好 _dramatically_ 更强](https://developers.google.com/web/fundamentals/performance/why-performance-matters)：

> -   BBC 发现，其 site 的 load 每多耗费一秒，就会额外流失 10% 的 users。
>     
> -   Google 旗下的 DoubleClick 发现，如果一个 page 的 load 耗时超过 3 秒，53% 的 mobile site visits 就会被 abandoned。
>     
> 
> …
> 
> -   当 AutoAnything 将 page load time reduced 到一半时，他们看到 sales 增长了 12-13%。

[James Somers](https://jsomers.net/blog/speed-matters)：

> Google 将 speed 作为一项 feature 来 prioritized，这一点广为人知。他们意识到，如果 search 是 fast 的，你就更有可能 search。原因在于，这会鼓励你尝试、获得 feedback，再次尝试。一个念头冒出来时，你知道 Google 已经在那里。念头与行动之间没有 delay，也没有机会让你失去探个究竟的冲动。googling 的 projected cost 是 nil。渐渐地，它给人的感觉就像自己头脑的延伸。

[Nelson Elhage 说得最好](https://blog.nelhage.com/post/reflections-on-performance/)：

> 也许不那么显而易见的是，_拥有 faster tools 会 changes users 如何 use 一个 tool 或 perform 一项 task。_ Users 几乎总有 multiple strategies 可用来 pursue 一个 goal——包括决定转而做完全不同的事情——而且他们会越来越频繁地选择 use faster tools。Fast tools 不只是让 users 能够更 faster 地 accomplish tasks；它们还让 users 能够以全新的 ways，accomplish 全新 types 的 tasks。在从事 Sorbet 和 Livegrep 的工作时，我都清楚地看到过这一现象……
> 
> Stripe 的许多 individual tests 都需要 10-20s，甚至更久……因为我们成功 building 了 Sorbet，让它能在那个 time window 内 typecheck 整个 codebase，它就成了许多 developers 为自己的 code 获得不错的 feedback、check 是否存在 basic typos、misused APIs 以及其他容易处理的 classes of errors 的 fastest way。由于这是他们的 fastest option，在我们的 development 和 rollout 还相当早的时候，我们就看到 users 已经把 Sorbet 当成 checking 自己 code 的 first line。即便 feedback 只是 mediocre，能 fast 地获得它以及一些 confidence，也远比任何需要几分钟的东西重要。
> 
> 在观察 users use livegrep 时，我也看到它的 performance 带来了一种相关的好处……因为 livegrep 如此 fast，users 会以 _interactively_ 的方式 use 它，而我很少见到人们以这种方式 interact 其他 search engines：他们 enter 一个 initial query，然后，如果得到的 results 太多或太少，就根据 result list 对它进行 edit，从而得到一组新的 results；接着，他们继续 refine 或 expand，直到找到自己寻求的 results。

### 个人 workflow

[Sam Altman](https://blog.samaltman.com/productivity)：

> 我也努力学习如何 type really fast，以及那些有助于我的 workflow 的 keyboard shortcuts。

[Steve Yegge，经 Jeff Atwood 转引](https://blog.codinghorror.com/we-are-typists-first-programmers-second/)：

> 我一直想弄清楚，对一个 CS student 来说，所能选修的最重要的 computer science course 究竟是哪门，最后意识到是 Typing 101。
> 
> 我认识的那些真正出色的 engineers，那些能 build 出色事物的人，都能 type。

这与我在 Wave 的经历一致：最优秀的 engineers 格外有可能做到 type quickly，熟悉自己的 keyboard shortcuts，并且投入了大量时间，让自己的常见 tasks 变得 efficient。

显然，这些并不是让他们成为优秀 engineers 的主要因素——但我认为，它们的帮助不只体现在那些显而易见的方面。

### Negotiations（谈判）

在 Wave，我们在 hiring 时注意到，让一个人更快地走完 hiring process，会使他们 accept 我们的 offer 的可能性大得_多_。如果我们很久才回复他们，或很久才 schedule 后续步骤，既会让他们有更多时间失去兴趣，也会让人觉得我们对他们并不热切。这可不是什么好印象！

这显然也是 sales 中的一句常见说法——[“时间会扼杀所有 deals”](https://www.fastcompany.com/1204077/time-kills-deals)。

Paul Graham 谈[Stripe 的 founders 如何让时间站到自己这一边](http://paulgraham.com/ds.html)：

> 在 YC，我们用“Collison installation”这个 term 来称呼他们发明的 technique。比较怯生生的 founders 会问：“你愿意试试我们的 beta 吗？”如果对方回答愿意，他们就会说：“太好了，我们会给你发送一个 link。”但 Collison 兄弟可不打算等。只要有人同意试试 Stripe，他们就会说：“那好，把你的 laptop 给我”，然后当场帮对方 set them up。

[Fred Wilson](https://avc.com/2018/08/strike-when-the-iron-is-hot/) 谈 networking 中的同一种 effect：

> 那天晚上回到家，我对 Gotham Gal 说：“我今天见到了 Danny Meyer，他给了我名片，说我什么时候需要订位都可以给他打电话。”她回答：“明天去那里吃午饭。”我对她说：“我明天没有午餐约会。”她说：“那就约一个。他明天还会记得你是谁，下个月就不会了。”

### Combat（作战）

John Boyd 是最有影响力的 military strategy 作家之一，他最为人所知的是“OODA loop”这一 idea：human action 是一个 iterated process，先 _observing_ 世界，在其中 _orienting_，再 _deciding_ 如何 respond，最后依据 decision 来 _acting_。Boyd 的主张是：_更快地 going through the OODA loop 是一种 decisive advantage_：

> 为了 win，我们应该以比我们的 adversaries 更快的 tempo 或 rhythm 来 operate——或者更好的是，get inside \[the\] adversary 的 Observation-Orientation-Decision-Action time cycle 或 loop……这样的 activity 会让我们显得 ambiguous（unpredictable），从而在我们的 adversaries 之中 generate confusion 和 disorder——因为我们的 adversaries 将无法 generate 出与他们所对抗的那些 menacing、而且更快的 transient rhythm 或 patterns 相符的 mental images 或 pictures。

举一个近期的例子，COVID epidemic 来袭时，许多州和国家[等得太久](https://www.benkuhn.net/macovid/)才 lock down，因为[这个 virus 已经 got inside 了它们的 OODA loop](https://www.ribbonfarm.com/2020/03/09/plot-economics/)：

> 眼下，各个层面的 perception of agency 都在 falling。Individuals、corporations、governments、heads of state、stock traders、UN，_所有人_都觉得自己正在失去对局面的把握，但他们也没看到其他任何人_找回_这种把握……据我们所知，一个 virus 已经 gotten inside 了 Homo sapiens 的 OODA loop，并且 seized the initiative，而我们还在费力琢磨到底该叫它什么。它 spreading 的速度，比我们最快的真相、谎言和胡扯还快。这是 narrative marketplace 中的一道 supersonic shock wave。

（他还维护着一份[他个人收集的快速事物清单](https://patrickcollison.com/fast)。）

> 一旦想清楚要做什么，就要势不可挡地迅速完成那寥寥几项 priorities。我还没遇到过一个行动迟缓却非常成功的人。

## 为什么要急性子？

行动更快的重要性，有一个显而易见的体现：如果你的 productive 程度高出 10%，你就会用少 10% 的时间完成工作，因此总共就能多做 10% 的工作。但我不认为这是 speed 重要的主要原因。

说到这里，值得指出的是，上面所有引文讲的都不只是埋头产出工作——它们讲的是更快地 _processing information_。你 process information 越快，就越能更快地把 result incorporate 到接下来要做的事情中。

换句话说，做事快的主要好处是，_你最终会去做不同的事情。_Nelson Elhage 的观点——“拥有更快的 tools，会 changes users 如何 use 一个 tool”——几乎适用于每一个 domain：

-   如果你迅速而不是慢吞吞地回复 emails，你就会获得更多新机会，最终会 prioritizing 这些机会，而不是去做原本可能做的事情。

-   如果你让 test 你的 code 的速度提高到 10x，你节省的不只是等待 tests 的时间——你可以开始做 [test-driven development](https://en.wikipedia.org/wiki/Test-driven_development)，更早地发现自己的 mistakes，并避免自己走上错误的道路。

-   如果你现在就 deploy 你的新 app，而不是等到下周，你就会提前一周知道 users 对新 features 的喜好，也就能把这些认识 feed back 到今后的 product decisions 中。

这意味着，行动迅速是一种会 compounds 的 advantage。速度达到两倍，不只是让你的 output double；它还会让你的 output 的 _growth rate_ doubles。随着时间推移，这会带来巨大的差异。

## 原文

June, 2017: my partner Eve and I are stuck at the visa-on-arrival desk in the domestic transfer wing of Bole International Airport, Addis Ababa. The rest of the transfer passengers, all Ethiopian, are waltzing past us to form a monster queue at passport control. As soon as I get my precious stamp, I sprint off to hold our place before more passengers sneak in front of us.

Ten minutes later, Eve finds me, groggy from our redeye and nonplussed about navigating the Ethiopian visa desk on her own. “Why did you have to run off like that?!” Somehow, “so that we could wait at the departure gate instead of in the passport control line” doesn’t seem like a very good reason.

It was at this moment that I realized I was an unreasonably impatient person.

(In retrospect, I probably should have been tipped off by my compulsion of doing a mental [critical path analysis](https://en.wikipedia.org/wiki/Critical_path_method) on any everyday activity taking more than 15 seconds, but I just thought that was normal until I started dating people and noticed they often did things in a sub-optimal order.)

* * *

Now that I’ve confessed to the sin of impatience, I’m going to spend the rest of this post trying to convince you that it’s actually a good thing.

(The good part is the habit of frequently asking yourself “how could this thing take less calendar time.” I don’t recommend manifesting it in annoying ways like ditching your partner in an Ethiopian airport.)

Being impatient is the best way to get faster at things. And across a surprising number of domains, being really fast correlates strongly with being effective.

Obviously, lots of these are non-causal correlations. Still, the sheer number of different datapoints is a surprising convergence:

### E-mail

It seems trivial, but lots of different people have observed that being slow to respond to emails is a bad sign, or that famous people whom you’d expect to be swamped respond surprisingly quickly.

[Sriram Krishnan](https://twitter.com/sriramk/status/1214278840358359040):

> -   the most famous, interesting, powerful people all read their own email
>     
> -   they’re almost universally good at responding to it quickly
>     
> -   they’re always very, very curious.
>     
> -   they have very little time. Anything with friction gets done “later”
>     

[Sam Altman](https://blog.samaltman.com/how-to-invest-in-startups):

> people tend to be either slow movers or fast movers and that seems harder to change. Being a fast mover is a big thing; a somewhat trivial example is that I have almost never made money investing in founders who do not respond quickly to important emails.

### Startups

It’s become common wisdom that launching (and iterating) quickly is a major factor behind whether startups succeed.

[Sam Altman again](https://startupclass.samaltman.com/courses/lec02/):

> \[Y\]ou have to be decisive. Indecisiveness is a startup killer. Mediocre founders spend a lot of time talking about grand plans, but they never make a decision. They’re talking about you know I could do this thing, or I could do that other thing, and they’re going back and forth and they never act. And what you actually need is this bias towards action.
> 
> The best founders work on things that seem small but they move really quickly. But they get things done really quickly. Every time you talk to the best founders they’ve gotten new things done. In fact, this is the one thing that we learned best predicts a success of founders in YC. If every time we talk to a team they’ve gotten new things done, that’s the best predictor we have that a company will be successful.

This propagates even down to the level of how quickly you deploy software changes. [Nick Schrock](https://twitter.com/schrockn/status/1130569945891258369) on Facebook / Instagram moving fast and breaking things:

> Instagram was even faster operationally than Facebook. They had continuous deployment. Any engineer could deploy at any time (they would run a command called “Yolout” lol). Facebook was on weekly deploys at the time on the web and way slower on mobile.
> 
> IG story definitely lends credibility to the those-who-ship-faster-win argument
> 
> …Worth noting that Facebook learned from this. As the company grew, the release cadence got faster. First daily, then twice daily, and it is now continuous. It’s a remarkable achievement by the release engineering team.

It’s not just Facebook; [_Accelerate_ found a strong correlation between deploy frequency and performance](https://www.amazon.com/Accelerate-Software-Performing-Technology-Organizations-ebook/dp/B07B9F83WM/):

> To summarize, in 2017 we found that, when compared to low performers, the high performers have:
> 
> -   46 times more frequent code deployments
>     
> -   440 times faster lead time from commit to deploy
>     

### Apps/tools

The “speed matters a lot” principle applies even to things that are already very fast. Google has found that [users _dramatically_ prefer faster webpages](https://developers.google.com/web/fundamentals/performance/why-performance-matters):

> -   The BBC found they lost an additional 10% of users for every additional second their site took to load.
>     
> -   DoubleClick by Google found 53% of mobile site visits were abandoned if a page took longer than 3 seconds to load.
>     
> 
> …
> 
> -   When AutoAnything reduced page load time by half, they saw a boost of 12-13% in sales.

[James Somers](https://jsomers.net/blog/speed-matters):

> Google famously prioritized speed as a feature. They realized that if search is fast, you’re more likely to search. The reason is that it encourages you to try stuff, get feedback, and try again. When a thought occurs to you, you know Google is already there. There is no delay between thought and action, no opportunity to lose the impulse to find something out. The projected cost of googling is nil. It comes to feel like an extension of your own mind.

[Nelson Elhage put it best](https://blog.nelhage.com/post/reflections-on-performance/):

> What is perhaps less apparent is that _having faster tools changes how users use a tool or perform a task._ Users almost always have multiple strategies available to pursue a goal — including deciding to work on something else entirely — and they will choose to use faster tools more and more frequently. Fast tools don’t just allow users to accomplish tasks faster; they allow users to accomplish entirely new types of tasks, in entirely new ways. I’ve seen this phenomenon clearly while working on both Sorbet and Livegrep…
> 
> Many individual tests at Stripe would take 10-20s or more…. Because we succeeded at building Sorbet so that it could typecheck the entire codebase in that time window, it became the fastest way many developers could get decent feedback on their code, to check for basic typos, misused APIs, and other low-hanging classes of errors. Since it was their fastest option, we saw users reaching for Sorbet as their first line of checking their code fairly early on in our development and rollout. Getting even mediocre feedback and some confidence fast was much more important than anything that would take minutes.
> 
> Watching users use livegrep, I’ve seen a related upside from its performance…. Because livegrep is so fast, users use it _interactively_ in a way I’ve rarely seen people interact with other search engines: they enter an initial query, and then, if they get too many or too few results, they edit it based on the result list, which gets a new set of results, which they continue to refine or expand until they hit on the results they are seeking.

### Personal workflow

[Sam Altman](https://blog.samaltman.com/productivity):

> I also made an effort to learn to type really fast and the keyboard shortcuts that help with my workflow.

[Steve Yegge via Jeff Atwood](https://blog.codinghorror.com/we-are-typists-first-programmers-second/):

> I was trying to figure out which is the most important computer science course a CS student could ever take, and eventually realized it’s Typing 101.
> 
> The really great engineers I know, the ones who build great things, they can type.

This matches my experience at Wave, where the best engineers are disproportionately likely to type quickly, know their keyboard shortcuts, and have invested a lot of time making their common tasks efficient.

Obviously, those aren’t the main things that make them good engineers—but I think they help in more than just the obvious ways.

### Negotiations

At Wave, when hiring, we’ve noticed that moving someone through the hiring process faster makes them _much_ more likely to accept our offer. If we take a long time to get back to them or schedule the next steps, it both gives them more time to lose interest, and makes it seem like we’re not excited about them. Not a good look!

This is apparently common trope in sales as well—[“time kills all deals”](https://www.fastcompany.com/1204077/time-kills-deals).

Paul Graham on [how the founders of Stripe got time on their side](http://paulgraham.com/ds.html):

> At YC we use the term “Collison installation” for the technique they invented. More diffident founders ask “Will you try our beta?” and if the answer is yes, they say “Great, we’ll send you a link.” But the Collison brothers weren’t going to wait. When anyone agreed to try Stripe they’d say “Right then, give me your laptop” and set them up on the spot.

[Fred Wilson](https://avc.com/2018/08/strike-when-the-iron-is-hot/) on the same effect in networking:

> That night when I got home I told the Gotham Gal “I met Danny Meyer today and he gave me his card and said I could call him whenever I need a table.” To which she replied “go there for lunch tomorrow.” And I told her “I don’t have a lunch tomorrow.” She said “Get one. He will remember who you are tomorrow but won’t next month.”

### Combat

One of the most influential military strategy writers, John Boyd, is most famous for the idea of the “OODA loop:” that human action is an iterated process of _observing_ the world, _orienting_ within it, _deciding_ how to respond and finally _acting_ on the decision. Boyd’s claim was that _going through the OODA loop faster was a decisive advantage_:

> In order to win, we should operate at a faster tempo or rhythm than our adversaries—or, better yet, get inside \[the\] adversary’s Observation-Orientation-Decision-Action time cycle or loop … Such activity will make us appear ambiguous (unpredictable) thereby generate confusion and disorder among our adversaries—since our adversaries will be unable to generate mental images or pictures that agree with the menacing, as well as faster transient rhythm or patterns, they are competing against.

As a recent example, for instance, many states and countries [waited far too long](https://www.benkuhn.net/macovid/) to lock down when the COVID epidemic hit because [the virus got inside their OODA loop](https://www.ribbonfarm.com/2020/03/09/plot-economics/):

> Right now, the perception of agency at all levels is falling. Individuals, corporations, governments, heads of state, stock traders, the UN, _everybody_ feels they’re losing the plot, but they don’t see anybody else _finding_ it…. As far as we can tell, a virus has gotten inside the OODA loop of Homo sapiens, and seized the initiative, while we’re struggling to figure out what to even call it. It is spreading faster than our fastest truths, lies, and bullshit. A supersonic shock wave in the narrative marketplace.

## Why impatience?

There’s an obvious way in which moving faster is important: if you’re 10% more productive, you will finish your work in 10% less time, so you can do 10% more work total. But I don’t think that’s the main reason that speed is important.

It’s worth pointing out at this point that all of the quotes above aren’t just about churning out work—they’re about _processing information_ more quickly. The faster you process information, the faster you can incorporate the result into what you do next.

In other words, the main benefit of being fast is that _you end up doing different things._ Nelson Elhage’s point—“having faster tools changes how users use a tool”—applies across nearly every domain:

-   If you respond to your emails quickly instead of slowly, you’ll get access to more new opportunities, and end up prioritizing them over whatever you would have done instead.

-   If you make it 10x faster to test your code, you don’t just save time waiting on tests—you can start doing [test-driven development](https://en.wikipedia.org/wiki/Test-driven_development), discover your mistakes earlier, and save yourself from going down bad paths.

-   If you deploy your new app now instead of next week, you’ll learn how users like the new features one week earlier, and you’ll be able to feed that knowledge back into future product decisions.

That means that moving quickly is an advantage that compounds. Being twice as fast doesn’t just double your output; it doubles the _growth rate_ of your output. Over time, that makes an enormous difference.
