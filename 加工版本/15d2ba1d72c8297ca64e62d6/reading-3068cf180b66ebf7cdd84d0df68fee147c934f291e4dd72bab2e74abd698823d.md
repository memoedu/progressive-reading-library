# 基准测试末日｜The benchmarkpocalypse

---

## 正文

关于 vulnpocalypse，已经有很多讨论了；我对此没有太多可补充的，因为我不是 security 人士，但我还没有看到多少关于与之密切相关的问题——benchmarkpocalypse——的讨论（公平地说，这个问题没那么严重）。

虽然实现显著的 performance gains 已经变得前所未有地容易，但对 benchmark 进行 reward hack、制造虚假的 performance gains，也变得前所未有地容易。前者大概正在许多不同的公司里悄悄发生，而后者如今我每周至少会看到一次。有人会声称自己 optimized 了 X，相比 existing software 获得了巨大的 performance improvement，但仔细一看，他们做的只是某种能 improves benchmark performance、却并没有真正 improving real-world performance 的 optimization。这往往是某种“我们用 Rust rewrote 了 X”[1](https://danluu.com/benchpocalypse/#fn:P) 的 project，或者是一家想要融资或卖点什么的新 startup，但其他种类的 projects 也会出现这种情况。

当然，人们一直都在吹嘘 unrepresentative microbenchmarks，以显示自己钟爱的 project 有多棒。伪造一个 unrepresentative microbenchmark 一直很容易，这一点永远不会改变。改变的是，以前要 game 一个 large benchmark suite，需要付出大量工夫，而现在一个 LLM 加上 loop 就能做到。在这件事还很困难的年代，就已经有不少 gaming large benchmark suites 的著名例子。例如，很久以前，人们还把 SPECint / SPECfp 当作 workstation performance 的 proxies 时，CPU vendors 会试图寻找能够 speed up benchmark 中 calculation 的 compiler “optimizations”，比如 Sun 找到了一种方法，能让 `179.art` [在 SPECfp2000 中 improve 12x](https://danluu.com/car-safety/)。熟练的 engineers 曾花大量时间寻找这样的 benchmark hacks。LLMs 不仅让这件事变得 trivial，而且默认就会这么做，使以前可信的 benchmarks 变得 meaningless，除非你 audit 了 result，或者信任做过 audit 的人。

与其指出别人不靠谱的说法，不如看看 [FRE，也就是我让一个 agent build 的这个 regex engine](https://github.com/danluu/fre/)。我完全可以声称它是世界上最快的 regex engine，因为它在相当 comprehensive 的 [rebar regex benchmark suite](https://github.com/BurntSushi/rebar) 上 beats Rust regex crate。但它的诞生过程，是把一个 agent 放在 loop 里跑了一个月，虽然指示它不要 overfit 到 benchmark，却没有真正的监督。大体上，让 LLM 给出一个不错的 benchmark score 相当容易，这次也不例外；它花了几周，便大致 match 了 Rust regex crate performance，又花了几周，就在 rebar 上达到了 1.4x faster[2](https://danluu.com/benchpocalypse/#fn:O)。但 agents 往往会 reward hack 和 overfit，除非你设置严格的 guardrails 来避免这种情况；作为实验，我这次没有这样做。

为了 check 是否存在 overfitting，我有些随意地[3](https://danluu.com/benchpocalypse/#fn:A)把 ripgrep benchmark corpus 用作 holdout benchmark；在那些没有因为 algorithmic blow-up 而让 benchmark 耗时没完没了的 cases 上，它是 10x slower，还有一些 cases 耗时太久，连等 benchmark complete 都不合理。所谓的 40% faster，也就这样了！

就 benchmaark suites 而言，Andrew Gallant（又名 BurntSushi）的 rebar benchmark suite 已经相当 comprehensive，但即使有这样一个相当 comprehensive 的 benchmark suite，agents 仍然可以轻松拿到 high score，同时以一种未必能带来良好 general performance 的方式 overfitting。

下一步是[使用我们之前谈过的一个技巧](https://danluu.com/pl-tokens/)：不只是告诉 LLM 不要 cheat，还要告诉它，有一个 holdout benchmark set 会用来评判它。之后，LLM 在一定程度上 generalized 了 performance，使它在 holdout 上整体约为 2.4x slower。考虑到我们是在把它与现存最快的 general purpose regex engine 作比较，这听起来已经相当不错了。但别忘了，这些 benchmarks 是由 coding agent 制作的。看看这些 benchmarks 究竟 measure 什么，就会发现，其中有些实在没有理由 include，至少不该赋予 equal weight。如果只看那些似乎真正重要的 benchmarks，[FRE](https://github.com/danluu/fre/) 在 holdout 上是 4x slower[0](https://danluu.com/benchpocalypse/#fn:and-actually-runs-all-tests-to-completion-so-the-speedup-was-much-more-than-just-10-4)，这比采用那个老办法——“告诉它们你有 holdout”——之前好多了，但距离 40% faster 仍然相当遥远。

这件事有几点让我觉得有意思：

1.  即使你指示 agents 不要为了赢得 benchmark 而 reward hack 或 overfit，以一种 meaningless 的方式“赢得”一个 non-trivial benchmark，仍然是 trivial 的
2.  再一次，告诉 LLM 存在 holdout set，比仅仅告诉 LLM 做 generalized work，或不要 overfit 或 cheat，更有效
3.  虽然 [FRE](https://github.com/danluu/fre/) 的 overall performance 并不那么好，但它在一些 use cases 中实际上 performs better；总体而言，过去针对某个 specific use case 编写 specialized code，需要人具备深厚的 engineering experience，如今这件事的 cost 已大幅下降

关于 (1)，难怪我会看到这么多虚假的说法。过去，要 build 一个像 [FRE](https://github.com/danluu/fre/) 这样的东西，把 performance 伪装得足以虚假地声称有 40% speedup，你需要相当多的专业知识。至少，你需要对 string matching algorithms、regex engines 有很好的理解，同时具备不错的 general code optimization 和 SIMD optimization 技能。[FRE](https://github.com/danluu/fre/) 还有一种 mode，会把 regex compiles 成 machine code，因此你还需要一些 compiler 专业知识。现在，只要打几分钟字，就能获得这种 benchmark cheating（不管你是否想要这种 cheating）。

关于 (2)，我很好奇这是否 generalizes，但还没有尝试足够多的 examples，无法判断。

关于 (3)，一个几乎没有投入人工、通过 vibe coded 得来的 regex library，如果比现有的 robust、well-tested 的 library 更慢，那就没有理由使用它，所以我觉得 [FRE](https://github.com/danluu/fre/) 这个 artifact 没什么意思。这里真正让我感兴趣的是，LLMs 能在多大程度上 substitute for 过去稀缺、specialized 且昂贵的知识。

过去，即使你具备这些知识，你大概也不会编写一个针对自己特定 workload 而 optimized 的 custom regex engine。在某些 large-scale use cases 中，人们确实会做到这种程度的 customization。例如，我参与[那个 Bing index](https://danluu.com/bitfunnel-sigir.pdf) 的工作时，code 中包含多个不同的 compilers，因为一位参与者希望榨出 maximal performance；在 search engine 中，你既关心 compile time，也关心 compiled performance，而不同地方的 trade-offs 又不一样，因此，为每个地方编写 custom compiler，可以获得更好的 performance；普通 project 在这些地方可能只会使用 interpreter，或者用“normal code”来 directly walk 某种 data structure。编写那些 compilers 的人，如果处理 regex-like code，可能也会编写多个 custom regex engines，但同时具备这种专业知识和意愿的人很少，更不用说还得有自由在工作中为这种 specialized code 投入如此多的时间。如果把那位 Bing engineer（当时是 Partner-level engineer，后来因在 search index 上的工作晋升为 Distinguished Engineer）的费用，与让一个 LLM 在 loop 中 running 的费用相比，就会发现，编写这类 specialized code 的 cost 已经下降了许多 orders of magnitude。

那些仍然认为 AI 是假的的人，读完本文前半部分，大概会想：“当然，AI produces 的都是假东西，所以它 produced 了一个假的 regex engine。”但看看 results：它在 holdout 上略低于世界上最快的 regex engine 一半的 speed，同时在许多 real workloads 上确实 faster（大部分 overfitting 并不是它对某个特定 benchmark pattern 做了 special cased，而是它对大致具有相同 shapes 的东西做了某种 optimization，却没有对其他大致 shapes 的东西这样做），这距离一个假的 regex engine 已经很远了。而且，事实上，它有一种 native code compiled mode，如果忽略 compile time，并且 running repeated searches 或一次很长的 search，它在 holdout 上实际上 beats Rust regex crate（对于许多实际的 use cases，这样做是合理的）。如果我做 [FRE](https://github.com/danluu/fre/) 的目标，是 produce 一个 fast regex engine，而不是看看只投入几分钟人工时间能 produce 出什么样的 regex engine，我猜它会在广泛的 holdout benchmarks 上相当有竞争力（不过仍会有些 gaps，只有人们在 diverse set 的 production workloads 上尝试后才会发现）；而且，即便是这个仓促粗糙的 version，在某些 real workloads 上也已经非常出色。

所以，即使 [FRE](https://github.com/danluu/fre/) regex engine 的 overall performance 不如 Rust regex crate，针对你的 workload 或 use case 进行 specializing 所能获得的 gains，也意味着，在某些 cases 中，在某个地方插入你自己的 specialized regex engine 可能是合理的；其他各种 low-level software 也是如此。你不必是 AI maximalist，也可以认为，再过若干年，我们有可能会看到类似的事情发生在更大的东西上，比如 databases。

### 附录：更多 FRE benchmark 细节

在写完上文、但尚未发表这篇文章时，我发现了一件事：LLM 关于 [FRE](https://github.com/danluu/fre/) 在 rebar 上比 Rust regex crate 快 40% 的说法也是错的。或者说，即便不算错，至少也具有误导性。它实际上并没有按照 rebar benchmarks 原本的运行方式来 running benchmarks。我花了一分钟检查 benchmark results，发现了两个问题，之后便检查了这一点。结果发现，尽管已经要求按照 [https://github.com/BurntSushi/rebar](https://github.com/BurntSushi/rebar) 中的运行方式来 run rebar benchmarks，LLM 还是改变了 interface，让 [FRE](https://github.com/danluu/fre/) 能够做一些 improve performance 的 optimizations。修复这一点后，[FRE](https://github.com/danluu/fre/) 在 rebar 上不再是比 Rust 快 1.4x，而是慢 1.5x（并且“仅仅”是 re2 的两倍快），因此原来的 result 在两重意义上都是假的。[FRE](https://github.com/danluu/fre/) 不仅对 rebar benchmarks 存在 highly overfit，results 还涉及 cheating。

不过，往好处看，这意味着 [FRE](https://github.com/danluu/fre/) 在 rebar 上（比 Rust 慢 1.5x）与在 holdout benchmarks 上（慢 2.4x）的 performance 差异，并没有之前看起来那么大，因此“告诉 LLM 你有一个 holdout”这一招，比之前看起来还要有效。

之后，我让一个 LLM 进行了几个小时的 hill climb，它声称 [FRE](https://github.com/danluu/fre/) 快了 1.28x。只花几个小时的 LLM 时间就有这样的 improvement，听起来相当不错，但随后我决定再花一分钟寻找 cheating，结果发现了多个问题，其中一个 case 是：对 `(?s)^(.*)$` 的 matches 的 count 进行 search 时，甚至没有查看 haystack（data），就 returned 了 count。另一个 cheating 的 case 是，在 benchmark 本应 line-by-line 进行的地方做了 multi-line grep。发现这些并不令人意外，因为把一个 agent 放在 loop 里运行一个月，又不 defining strict guardrails，就会发生这种事。这究竟加强了还是削弱了我在这里的观点，并不清楚，但又修复了一批这类问题后，[FRE](https://github.com/danluu/fre/) 又变成慢 1.4x 了。让一个 agent 跑了一整夜后，据称 [FRE](https://github.com/danluu/fre/) 又变成快 1.5x 了。

因为我原本的目标，是看看把当前的一个（公开的）SOTA agent（GPT-5.6 Sol）放在 loop 里，在没有多少监督、也没有任何实质监督的情况下，处理一个 non-trivial code optimization problem 会发生什么，所以我不会再花更多时间修修补补，让 benchmarks 更公平，而是就此打住，放几张 results 的 plots。

这里有一点值得注意：对于那些不把 compile time 纳入 benchmark、并且 repeatedly run searches 的 holdout benchmark cases，AOT [FRE](https://github.com/danluu/fre/) 在 benchmark 上能够 outperforms。对于许多 use cases，你不会想要一个需要好几秒才能 compile 的 regex，但也有很多 cases 完全可以接受这一点。例如，对于 ripgrep 或 Silver Searcher 这样的东西，它可以先用一个能够立即开始 matching 的 regex 来运行，然后在另一个 thread 中 compile，等 compiling 完成后再切换到更快的 matcher。考虑到我的 CPU 有那么多时间花在耗时很长的 ripgrep searches 上，这样的 strategy 似乎能够为我自己做的工作 improve performance。在 LLMs 出现之前，花力气写一个 optimizing regex compiler 大概并不划算，但现在只用一些 tokens 就能做到了。

这里另一个值得注意的地方是，这个 comparison 可以说并不公平，因为它是在一台带有 SVE/SVE2 的 ARM Graviton machine 上运行的，而 [FRE](https://github.com/danluu/fre/) 有 SVE/SVE2 optimizations。在 LLM 出现之前，为现有的每一种 SIMD instructions 的 combination 都准备 optimized 的 regexes，可能并不值得，但有了 LLMs，generate 还算过得去的 SIMD optimizations 已经相当容易。我认识一些人类专家，他们发现自己在这方面通常能够 outperform LLMs。例如，Jay Stelly 说，上一次他尝试让一个 LLM produce SIMD code 时，花了 20 多次 iterations，才让 code 达到他想要的水平。不过，另一方面，在任何给定的时间内，LLMs 都有能力尝试比人类所能尝试的更多的 optimizations，因此即使任何一个具体的 optimization 都不如人类专家做出来的好，它们总体上仍然可以 perform 得相当不错。

此外，还有本文讨论的 overfitting 问题。视 context 而定，这个问题可能非常容易 solve，也可能有点难 solve。我在这里刻意没有特别努力地 solve 这个问题，是想看看会发生什么；不过，在[开发这个 Azul AI 时](https://danluu.com/game/tile/)（仅举一例），我确实没有花费过多精力就成功 solve 了这个问题。但许多这类夸张的 benchmark 声称，都是在人们几乎不花、甚至完全不花力气来避免 overfitting 的情况下出现的，有时甚至是在做反向努力。在 LLM 出现之前，人们常常会挑选 highly unrepresentative microbenchmarks，炫耀自己钟爱的项目有多棒；至少在无意识层面上，这相当于在避免 overfitting 到某个 benchmark 这件事上做反向努力。鉴于人性如此，我不认为人们会停止作出误导性声称，而且现在作出误导性声称比以往任何时候都更容易，所以我们当然会看到更多这样的声称。

请注意，虽然本文讨论的是 non-AI software，但这里说的一切，对 AI software 而言都要加倍成立。例如，我看到很多人留言说 Kimi K3 达到了 Fable (5) 的水平。但我认识的每一个用过它的人，都发现它远不如 GPT-5.6 Sol 和 Fable。我并不是说它不是一项令人赞叹的 engineering achievement，但它在各种 real-world tasks 上的 performance，并没有达到它在 benchmarks 中的水平。这甚至适用于各种 eval-y problems，比如有个朋友在 ICFP 2026 contest problems 上尝试不同的 coding agents 时的情况。这也适用于 security issues，而我毫不怀疑 AI labs 会把这些放进自己的 evals。例如，我的一位同事尝试用 Kimi K3 在我们的 software 中 scan for vulns，发现它找到的 vulns 大约只有 GPT-5.6 Sol 找到的四分之一，没有找到任何 GPT-5.6 Sol 未找到的 vulns，而且除了 cost 之外，在任何 dimension 上都没有优势。我认识的那些用更便宜的 models 来寻找真正的 security issues 的人，用的是其他 models，例如 GLM-5.2；这些 models 在 benchmarks 上 perform 更差，但在实践中更好。

回到 FRE 的话题，还有一点要说明：这个 holdout benchmark 是 ripgrep benchmark setup 的一个 arbitrary subset，由一个 agent 出于未知原因选出。我让一个 agent 去 pull 整个 benchmark suite，但在这篇文章发表前还没完成，所以我不知道完成后 result 会是什么。

## 原文

There's been a lot of talk about the vulnpocalypse, to which I don't have much to add because I'm not a security person, but I haven't seen much discussion on the closely related (and to be fair, less serious, issue), the benchmarkpocalypse.

While it's become easier than ever to make serious performance gains, it's also become easier than ever to reward hack a benchmark and make fake performance gains. The former is probably happening quietly across many different companies, but the latter is something I see at least once a week nowadays. Someone will claim they optimized X and got some huge performance improvement over existing software, but, when you look at it, what they did was make some optimization that improves benchmark performance without actually improving real-world performance. This is often some kind of "we rewrote X in Rust"[1](https://danluu.com/benchpocalypse/#fn:P) project or a new startup that's looking to either fundraise or sell something, but it happens on other kinds of projects as well.

Of course, people have always trumpeted unrepresentative microbenchmarks to show that their pet project is great. It's always been easy to fake up an unrepresentative microbenchmark and that's never going to change. What's changed is that it used to take a lot of work to game a large benchmark suite, but an LLM and loop can just do it. There are quite a few famous examples of gaming large benchmark suites from back when this was hard. For example, way back when people cared about SPECint / SPECfp as proxies for workstation performance, CPU vendors would try to find compiler "optimizations" that would speed up the calculation in the benchmark, such as Sun finding a way to improve `179.art` [by 12x in SPECfp2000](https://danluu.com/car-safety/). Skilled engineers spent a lot of time trying to find benchmark hacks like that. LLMs not only make this trivial, they do it by default, making formerly trustworthy benchmarks meaningless unless you audit the result or trust someone who did.

Rather than point to someone's bad claim, I'll point to [FRE, this regex engine I had an agent build](https://github.com/danluu/fre/), which I could claim is the world's fastest regex engine because it beats the Rust regex crate at the fairly comprehensive [rebar regex benchmark suite](https://github.com/BurntSushi/rebar). But this was created by putting an agent in a loop for a month with instructions to not overfit to the benchmark but no real supervision. For the most part, getting an LLM to give you a good benchmark score is fairly easy, and this case was no different; it took a couple weeks to roughly match Rust regex crate performance and then another couple weeks to get to 1.4x faster[2](https://danluu.com/benchpocalypse/#fn:O) on rebar. But agents are wont to reward hack and overfit unless you put serious guardrails in place to avoid that, which I didn't do in this case as an experiment.

To check for overfitting, I somewhat arbitrarily[3](https://danluu.com/benchpocalypse/#fn:A) used the ripgrep benchmark corpus as a holdout benchmark it was 10x slower on cases where the benchmark didn't take forever due to an algorithmic blow-up, and there were cases where it took so long that it wasn't reasonable to even wait for the benchmark to complete. So much for being 40% faster!

Andrew Gallant (aka BurntSushi)'s rebar benchmark suite is fairly comprehensive as benchmaark suites go, but even with a fairly comprehensive benchmark suite, agents have no problem getting a high score while overfitting in a way that doesn't necessarily give good general performance.

The next step was [using a trick we talked about before](https://danluu.com/pl-tokens/) of not just telling the LLM not to cheat, but that there's a holdout benchmark set that it's judged against. After that, the LLM moderately generalized performance to the point where it's about 2.4x slower overall on the holdout. That sounds pretty good considering that we're comparing it to the fastest general purpose regex engine in existence. But, recall that these benchmarks were made by a coding agent. On looking at what the benchmarks measure, some of them really don't make sense to include, at least at equal weight. If we only look at the benchmarks that seem like they matter, [FRE](https://github.com/danluu/fre/) is 4x slower on the holdout[0](https://danluu.com/benchpocalypse/#fn:and-actually-runs-all-tests-to-completion-so-the-speedup-was-much-more-than-just-10-4), which is a lot better than before applying the good ole' "tell 'em you have a holdout trick", but still pretty far from being 40% faster.

There are a few things I thought were interesting about this:

1.  It's trivial to "win" a non-trivial benchmark in a meaningless way even when you instruct agents to not reward hack or overfit to win the benchmark
2.  Once again, telling the LLM there's a holdout set worked better than just telling the LLM to do generalized work or not overfit or cheat
3.  Although the overall performance of [FRE](https://github.com/danluu/fre/) isn't that good, it is actually performs better for some use cases; in general, the cost of writing specialized code that used to require people serious engineering experience for some specific use case has gone way down

On (1), no wonder I'm seeing so many bogus claims. In the past, to build something like [FRE](https://github.com/danluu/fre/) that fakes performance well enough to be able to bogusly claim a 40% speedup, you would need a fair amount of expertise. At a minimum, you'd need to have a pretty good understanding of string matching algorithms, regex engines, as well as decent general code optimization and SIMD optimization skills. [FRE](https://github.com/danluu/fre/) also has a mode where it compiles the regex to machine code, so you'd also need some compiler expertise. Now you can get that kind of benchmark cheating (whether or not you want the cheating) with a few minutes of typing.

On (2), I'm curious if this generalizes but haven't tried enough examples to be able to tell.

On (3), there's no reason to use a vibe coded regex library that was almost no human effort that's slower than a robust, existing, well-tested, library, so I find the [FRE](https://github.com/danluu/fre/) artifact uninteresting. The thing I find interesting here is how much LLMs can substitute for what used to be rare, specialized, and expensive, knowledge.

In the past, even if you had the knowledge, you probably wouldn't write a custom regex engine that's optimized for your particular workload. There are some large-scale use cases where people would do that level of customization, e.g., when I worked on [the Bing index](https://danluu.com/bitfunnel-sigir.pdf), the code contained multiple different compilers because someone who worked on it wanted to eke out maximal performance; since you care about both compile time and compiled performance in a search engine and the trade-offs are different in different places, you get better performance by writing a custom compiler for each place where a normal project might just use an interpreter or directly walk some data structure with "normal code". The person who wrote those compilers, working on regex-like code might also write multiple custom regex engines, but very few people have both the expertise and the inclination to do that, let alone the freedom to spend that kind of time on such specialized code for work. If you price out that Bing engineer (then a Partner-level engineer, promoted to Distinguished Engineer for their work on the search index) compared to the price of running an LLM in a loop, the cost of writing this kind of specialized code has gone down by many orders of magnitude.

People who still think AI is fake will probably read the first part of the post and think "of course, AI produces fake things, so it produced a fake regex engine". But if we look at the results, being a bit worse than half the speed of the world's fastest regex engine on a holdout while being genuinely faster on many real workloads (most of the overfitting isn't that it special cased a particular benchmark pattern, but that it has some kind of optimization for things of same rough shapes and not of other rough shapes) it's pretty far from a fake regex engine. And, in fact, there's a native code compiled mode that actually beats the Rust regex crate on the holdout if you ignore compile time and are running repeated searches or a very long search (which is a reasonable thing to do for many actual use cases). If my goal with [FRE](https://github.com/danluu/fre/) was to produce a fast regex engine instead of producing whatever regex engine one can produce in a few minutes of human time, I suspect it would be fairly competitive on a broad range of holdout benchmarks (with some gaps that would only be found when people tried it on a diverse set of production workloads), and, even this quick and dirty version is very good at some real workloads.

So, even though the overall [FRE](https://github.com/danluu/fre/) regex engine has worse performance than the Rust regex crate, the gains you can get for specializing to your workload or use case mean that, in some cases, it could be reasonable to insert your own specialized regex engine somewhere, and the same goes for various other kinds of low-level software. You don't have to be an AI maximalist to think that it's plausible that, within some number of years, we could see this kind of thing happening for larger things, like databases.

### Appendix: more FRE benchmark details

One thing I found after I wrote the above but before publishing the post, was that the LLM's claim that [FRE](https://github.com/danluu/fre/) is 40% faster than the Rust regex crate on rebar was also wrong. Or, if not wrong, at least misleading. It wasn't actually running benchmarks in the same way rebar benchmarks were run. I checked this after spending a minute checking benchmark results found two issues. It turns out that, despite instructions to run rebar benchmarks as they're run in [https://github.com/BurntSushi/rebar](https://github.com/BurntSushi/rebar), the LLM changed the interface to allow [FRE](https://github.com/danluu/fre/) to make some optimizations that improve performance. After fixing that, instead of [FRE](https://github.com/danluu/fre/) being 1.4x faster than Rust on rebar, it was 1.5x slower (and "only" twice as fast as re2), so the original result was doubly fake. Not only was [FRE](https://github.com/danluu/fre/) highly overfit to the rebar benchmarks, it the results also involved cheating.

But on the bright side, this means the difference in performance between [FRE](https://github.com/danluu/fre/) on rebar (1.5x slower than Rust) and on the holdout benchmarks (2.4x slower) isn't as big as it looked before, so the "tell the LLM you have a holdout" trick worked even better than it seemed to before.

After that, I let an LLM hill climb for a few hours and it claimed that [FRE](https://github.com/danluu/fre/) was 1.28x faster, which sounds like a great improvement for only a few hours of LLM time, but then I decided to spend another minute looking for cheating and found multiple issues, including one case where a search for the count of matches of `(?s)^(.*)$` returned the count without even looking at the haystack (data). Another case of cheating was doing a multi-line grep where the benchmark is supposed to be done line-by-line. Finding these isn't surprising because this is the kind of thing that happens when you leave an agent in a loop for a month without defining strict guardrails. Whether this makes my point here stronger or undermines it isn't clear, but after fixing another set of these issues, [FRE](https://github.com/danluu/fre/) was back to being 1.4x slower. After leaving an agent to run overnight, [FRE](https://github.com/danluu/fre/) was allegedly back to being 1.5x faster.

Since my original goal here was to see what happens when you run a current (public) SOTA agent in a loop (GPT-5.6 Sol) without much supervision on a non-trivial code optimization problem without any real supervision, rather than spend more time fixing things up to make the benchmarks fairer, I'll just stop here and put a few plots of the results.

Another thing to note here is that this comparison is arguably unfair because this was run on an ARM Graviton machine with SVE/SVE2 and [FRE](https://github.com/danluu/fre/) has SVE/SVE2 optimizations. Pre-LLM, it might not have been worth it to have regexes optimized for every combination of SIMD instructions out there, but with LLMs, it's fairly easy to generate ok-ish SIMD optimizations. I know human experts who find that they can generally outperform LLMs here, e.g., Jay Stelly said that the last time he tried getting an LLM to produce SIMD code, it took 20-some iterations to get the code as good as he wanted. But, on the flip side, LLMs have the capability to try more optimizations than a human could possibly try in any given amount of time, so they can still perform pretty well overall even if any specific optimization isn't as good as a human expert would produce.

There's also the problem discussed in this post of overfitting. Depending on the context, that problem is somewhere from very easy to solve to a bit difficult to solve. I deliberately didn't try very hard to solve the problem here to see what would happen, but I did manage to solve the problem without an outsized amount of effort when [working on this Azul AI](https://danluu.com/game/tile/) (just for example), but a lot of these big benchmark claims come when people spend little to no effort trying to avoid overfitting, or even negative effort. In the pre-LLM era, people would often pick highly unrepresentative microbenchmarks to show off how great their pet project is which, at least at a non-conscious level, involves negative effort to avoid overfitting to a benchmark. Due to how humans are, I don't think people are going to stop making misleading claims and it's become easier than ever to make misleading claims, so of course we see more of them.

Note that while this post has discussed non-AI software, everything said here goes double for AI software. For example, I've seen lots of people drop comments saying that Kimi K3 is Fable (5) level. But every single person I know who's used it has found it to be substantially worse than GPT-5.6 Sol and Fable. I'm not saying it's not an impressive engineering achievement, but the performance on a wide variety of real-world tasks isn't up to the level it is in benchmarks. This even applies to various eval-y problems, such as when a friend tried different coding agents on the ICFP 2026 contest problems. It also applies to security issues, which are something that I have no doubt AI labs are putting into their evals, e.g., a colleague of mine tried using Kimi K3 to scan for vulns in our software and found that it found approximately a quarter of the vulns GPT-5.6 Sol found, found no vulns that GPT-5.6 Sol didn't find, and didn't have any advantages in any dimension other than on cost. The people I know who are using cheaper models to find real security issues are using other models, such as GLM-5.2, which perform worse on benchmarks but better in practice.

I asked an agent to pull the entire benchmark suite, but that didn't finish in time for this post, so I don't know what the result will be once it's done.
