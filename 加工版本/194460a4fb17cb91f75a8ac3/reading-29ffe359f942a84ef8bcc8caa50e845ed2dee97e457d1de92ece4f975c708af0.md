## 核心洞察

一、数学证明与证伪的难度不对称：证明一个猜想需要完备工具与巨大搜索空间，而证伪只需找到一个反例。以池塘一万只青蛙为例，证明全部健康极难，发现一只三条腿即可完成证伪。这种不对称可能达到百倍到亿倍量级，使数学家用AI agent优先爆破low hanging fruits，把猜想一分为二或直接抹除，从而快速产出论文与推进版图。

二、黎曼猜想工具尚未造出：证明黎曼猜想可能不是简单增加算力或搜索，而是需要从头建立全新数学体系与完备工具，历史上可能需要数十人十年创立新分支。因此证明难度与证伪难度不在同一量级，搜索空间巨大且无法猜测，这解释了为何数学家更倾向先做证伪与边界推进。

三、用lemma DAG拆分证明：把数学证明随机拆成若干lemma并组成DAG，每个小agent证明一个小lemma，再组合成完整证明。这是今年四月提出的方向，与agent team方式并列，目标是从头构建严格formal proof的完备系统，而非半监督地由人类不断review和提示。

四、生成一万猜想再证伪九千九百九十九：在细分领域先生成一万个猜想，让AI agent自行爆破并证伪其中九千九百九十九个，最后剩下十个可能是AI无法证伪的猜想。若其中有价值，则发布出来。提出猜想本身也是数学贡献，可能为领域带来新方向与前进动力，这被视为真正创造新数学知识的方式。
[[#^pr-a6a6fc0d5405|正文跳转]]

五、网络安全攻防难度不对称：构建面面俱到、绝对安全的网络服务极难，而AI agent可批量自动化地找漏洞、溢出、注入，攻击难度相对为一。因此防御可能是一百，攻击是一。以攻击带防守成为可能：AI大量攻击自己的系统，成功一次即发现一个漏洞，相当于养更多自家白帽子，提升整体防御系数。
[[#^pr-6c37a4879048|正文跳转]]

六、攻击AI agent本身是灌水方向：针对AI agent的harness、behavior function、calling、memory进行污染或误导，目前不通用且依赖特定版本，属于学术界缝合式灌水。AI尚未被允许用于严肃production环境，本地环境相对可控，攻击意义不大，且下一个技术栈可能直接推翻该方向，因此不建议投入。
[[#^pr-0a18b97f00be|正文跳转]]

七、封闭完备问题易被AI接手：越封闭、有完备定义、明确specs、完备测试、人类定义架构与大方向的code base，越容易被AI完整接手。解锁方式包括test driven、spec driven、不断跑测试与优化、设定benchmark。越接近传统计算机理论的工作越容易被替代，越开放、贴近工程一线的工作越难。
[[#^pr-f88c00904e8d|正文跳转]]

八、招聘系统比操作系统更复杂：小型操作系统或编辑器有完备文档，方向会收敛到接近完整结果；而招聘系统涉及谁投简历、如何筛人、排序、筛选学历技能、打电话发邮件，是完全开放的问题。越与人类社会大面积接触，越需要human loop，越依赖程序员和产品经理做决策与判断。

九、multi agent的瓶颈在人的精力：同时管理六个到十二个agent需要不断监控状态并做正确决策，人的精力成为最大瓶颈，且容易脑子混乱、效果不佳。multi agent在测试、找bug、research、重写翻译等场景可能有效，但在完整开发流程中优势有限，需要挑选场景而非默认加速。

十一、项目膨胀导致失控与回滚困境：完全依赖Copilot、Claude Code、Codex而不读代码、不做review，项目会快速膨胀到开发者无法理解的地步。一旦出现bug，修一个引出三五个，回滚到早期版本再走仍可能再次崩溃。复杂度足够大时，出现bug的概率极高，最终无人能兜底，只能走向崩溃。

## 数学形式化与自动化工具
去解决数学里面的 formal proof 问题或者是证明问题、计算问题等很多很多，那著名的就是包括大量的 symbolic computing 的库，也包括大量的这种数学证明的工具。这些都是自动化的工具，它们和传统的 NLP 或者传统古典意义上的 AI 是有关系的。但是那个东西很原始。GPT 3.5 发布之后很长一段时间，人们在考虑用LLM去做 zero shot 一些数学证明的大爆破。

## 中学与本科数学题数据集
就是人们会拿一大批的中学范围内的数学或者是 IMO 级别的数学题，就是他们数学难度不是很高，复杂度的空和搜索空间也不是很大。但是他们很适合就是让LLM来测试一下我能不能理解这个数学题并且证明出来。所以说LLM时代呢，它还没有出现 agent。人们就尝试用 zero shot 一些的方式去直接爆破一些数学问题。然后那个时候产生大概有五六个很流行的 data set，就是按中学的数学题、IMO 的数学题、大学本科期间的数学题。

## 用 Lean 证明数学题与 LLM 的局限
可能有几百道题或者几千道题，然后让你用 Lean 去把它们证明出来。当时用很多纯粹的 vanilla 的方式去解决这些问题，结果不是特别好，有的是 20%、30%，解答成功率很低。人们开始意识到 LLM 可以解决数学问题，但人们发现，首先数学问题的复杂度和抽象程度要远远高于编程。所以在 GPT-4 的时代，人们不太能用 LLM 单纯用 LLM 和 agent 来解决大量的数学问题。

## Tony与Alessiah数学证明工具
Tony是UC Berkeley数学系的助理教授，也是我们这个年代数学上一位很天才的人物。今年应该是他在工业界的一年，他可以有一年的休假，正好在Google把这个工作完成了，这个工作叫Alessiah，是一个semi supervised的数学证明工具。

先讲一下什么是erdos problem和什么是first proof。erdos是上个世纪的一位数学家，这老头儿大概留下来可能一千多道题、将近两千道题，人们就说，那以后把这两千道题尽可能地解决掉吧。

## 证伪比证明更难与low hanging fruits的爆破
找一个反例、证伪一个问题，要比证明一个问题难得多。所以当今大量的数学家用头部的AI agent去爆破现有的数学问题，即low hanging fruits。比如说以前一个问题的边界，我把边界提升一下，就比如说黎曼猜想，还有大量大量的猜想——大量猜想可能是，比如说在我这个小领域里存在一百个可能，有三十个是差不多正确的，那我剩下七十个能不能找反例，把这个猜想证伪。然后数学家们就发现，我证伪一个猜想比证明一个猜想要难得多，要简单得多。

## 当前趋势：与其用 AI 构建完整证明，不如先做力所能及的工作
这是现在的一个大的趋势：与其用 AI 去构建一个非常完整的证明，不如首先做点自己能力所能及的手头的工作，先把一个问题证伪。

从一个猜想的角度来说，证明和证伪同等重要。但对于一个拥有 AI agent 的数学家来说，证明一个猜想要难得多，证伪一个猜想要简单得多。举一个很形象的例子，这个例子比较简单，可能有些不恰当的地方，但它比较容易让大家接受。

比如说，池塘里有一万只青蛙。任务一，要求一个一个去检查一万只青蛙全部健康，必须有一套非常完整、完备的方法和手段，来一个一个证明一万只青蛙全部健康。任务二，就是证伪，即证明一万只青蛙里面至少有一只是三条腿的。任务一的难度非常大：有一万只青蛙，必须从头到尾证明每一只青蛙在所有体征上都是完全健康的，这个事情非常难。

但是，只要发现青蛙里面有一只是三条腿的，就可以把任务二完成。所以，对于一个数学问题来说，从数学的学术价值来说，证明和证伪同样重要。但是数学家们发现，证伪这个东西，可能一天的时间就能证伪一个数学题；或者说，有的数学题、有的猜想可能已经出现了三四十年时间，没有人能证明。

## 证伪的成本与推进猜想
数学家说，现在有很多 AI agent，如果自己是政委，会发现这件事的成本可能就很低了，可能自己在家里面干，三天就可能构造出来一个数学题的证伪。像之前的 jacobian 就是这么一个例子：构建一个反例其实是非常简单的事情。哪怕只是构建一个猜想的弱化版本，至少它在某个领域上面，能构建出来它的一个反例，至少把这个猜想推进了一步，把猜想一分为二。

边界条件以及这边的这些定义，可能还需要未来的证明或者证伪，但这些条件以及这边的内容，基本上已经给它证伪了，那就把整个数学问题的猜想又推进了一大步。所以证伪比证明要简单太多了。
我的观点是，如果一个题目证明的证伪难度与证明难度相比，有可能是一百到一个亿。它不是说证伪的难度是证明难度的 1/10 或者是一半，而是说证明的难度可能是证伪难度的一百倍到一个亿倍，它的搜索空间巨大，而且甚至有的题目是……

证明黎曼猜想可能需要各种各样的更复杂的数学公式，或者数学体系、数学工具。目前大家对黎曼猜想虽然不知道它怎么证明，但一个基本认知是：人们用于证明黎曼猜想的工具都还没有造出来。

所有的涉险、构造全都做出来，当这些东西做好之后，我们才有可能证明黎曼猜想。所以证明的难度不是证伪难度的简单一倍、两倍或者十倍，它可能是一亿倍。

## 先构建反例、发论文挂 arXiv
我先不捞最大的，先捞两个再说。也就是说，先把一些简单的、能够证伪的猜想构建出几个反例，把论文发出来，挂到 arXiv 上面，让大家看一看，我确实挣出来了。

这样，你的工作产出就比那些试图去证明它的人要快得多。实际上你也是在灌水，但这个灌水灌得有意义，因为你确实把那些悬而未决的证明问题一个一个解决了。至少这些问题中，比如有 1/3 到 1/4 的猜想是不对的，我构造出反例，把它们从数学目前的版图上抹掉，这对数学来说也是巨大的贡献。

我不是说好与不好，只是跟你说，如果你是数学从业者，是数学 PhD 或者数学系教授，这个事情一定是目前大家最关注的问题。所以我说，数学领域里面，目前我能看到的是有两个方向。第一个方向是非常有价值的方向，但现在数学界没有人做，computer science 也没有人做，我再往前推动，但很多人推动的进度很慢。

很多人也在推动，Tony也在推动，陶哲轩也在推动。据我所知，OpenAI 也在推动，但这个东西很难，因为它的难度很高。就是说，我们能不能找一个方式，能够从头构建一个严格 formal proof 的完备系统。这个系统不是政委，不是去攻击，不是构造算力，而是完完全全从头开始构建一个证明的系统。

## 用 lemma DAG 拆分数学证明
用 lemma DAG，就是把一个数学证明的问题尝试去 randomly 拆分成几个 lemma，再把这些 lemma 组成一个 DAG 图的方式；然后每一个小 agent 去证明一个小的小的 lemma，再把这比如二十个或者一千个小的 lemma 组合起来，以此完成一个大的数学题的证明。

Copilot 去使用。众所周知，我是 GitHub 中国区非常非常靠前的用户，在 GitHub 上是“大 V”，在中国程序员里面我的排名非常靠前，所以我一直是 GitHub Copilot 忠实的荣誉、免费长期用户。

当时我就讲一个事情：如果你只用 GitHub Copilot 去开发，你就会很快发现一个巨大的问题——整个项目的发展会远远超出你的能力。如果完完全全超出你的能力，你不看代码，只是不断地 commit、不断地 push 你的代码，不断地修改，修改完之后直接 push。

你只用 Claude Code、只用 Codex 以及只用 GitHub Copilot 去开发，那么很多人就养成一个臭毛病：完全不读代码，不看细节，不做 code review，也不理解，就是把这个东西完完全全地算给它，让它去做这个东西，那么整个项目就会变成一个 toy project，就不好维护了。所以当你希望好好用这个项目的时候，你会发现。

## 项目膨胀与失控
这个项目就会逐渐地快速膨胀、变大，而且变大到你不能理解、也不可能理解的地步。也就是说，原来你还可以理解，只是没时间看；后来就复杂到巨大到你连看都看不懂的地步。当项目大或复杂到这个地步的时候，对你来说就失控了。而你是这个项目的唯一负责人，或者是少数几个负责人，那么整个开发者没有能力去管理代码，这个项目就彻底失控了。失控是什么意思呢？

他可能会出现一个 bug，然后一个 bug 后面出现三五个 bug，而且每次你修 bug 就会出现更多的 bug。因为你不懂整个的架构，你也不看代码，整个项目就会走向崩溃。这种东西很长很长存在，就是大量的人，他在公司里边就有很多文科生。为什么很多文科生他自己那么**啊，就是你看我之前直播间，我专门卖过一个人在银行里面的，他说我自己用 Codex，我写代码做了一个东西，在公司，公司公在银行里面内部的那个。

后台去写，大家偷偷去用。我说，如果这个项目足够大，大到足够复杂，复杂到你看不懂，甚至维护不了你的 Codex，你的 cloud code 也维护不了的地步，你该怎么办？

## 项目失控与回滚的困境
你的项目彻底失控了，彻底走向一连串的 bug、走向崩溃，用不了的时候你回滚，回滚之后你也解决不了。你回滚到一个非常非常早的版本，然后一步一步再做，然后你发现你还是——就是因为复杂度到这儿了，你一定有概率陷入一连串的 bug 里面去。你回滚到一个干净的版本，然后再往前走，然后又出现问题，再回滚、再往前走。

因为它足够复杂，复杂到足够巨大的地步的时候，它一定会出现。bug 的概率就非常非常高了，不出现 bug 的概率反而非常低。所以它一定会在可能在某一个阶段出现崩溃的问题，那么你无法维护，你要不要承担这个责任。所以今天 agent 的开发，一个最潜在的风险是管理上的风险，就是如果一个项目完全是 agent 去开发。

如果一个项目人们完全脱离了对代码的审查和观察，你有没有想过这个项目的复杂度或者巨大程度会到什么地步？如果到了你自己失控的地步，没有人接受这个东西。很多文科生说，我做了一个，我一下写了一个二十万行的项目，我说他妈谁看你这个**去。你说我好多好多企业里面就是这个德行，就是文科生产品经理，他自己会用 Codex，他写到二十行、写到五十行、写到二十万行、写到五十万行的时候非常复杂了，他把乱七八糟功能都往里加，加完删、删完加，他也不删，他也没有任何管理。

## 项目无人兜底时的崩溃风险
出现大问题了，他说这个时候不行了，我得找个程序员帮我去兜底，再给我擦屁股。没有人给你兜底，没有人给你擦屁股。没有人看见过这东西，你要雇一个人，要整个把你这个二十万行、五十万行的 code base 马上顺溜了，谁有这个功夫，谁有这个心气儿？不可能的事情。所以如果他这个项目走到这个地步，没有人给你维护，没有人给你兜底的时候，他就只能走向崩溃，就是这么简单。

所以这也是一个潜在的开——很多人低估，尤其是文科生，尤其是产品经理，他们非常低估这个钱的风险。我必须告诉你，这个东西我不是说 GPT 3.5 出来之后才警告你们，也不是说 LM agent 或者 cursor 出来之后才警告你们。

那个时候我就警告过你，你们这个东西一定会存在的。就是五六年前的时候我警告过你们，这个东西一定要听。这些东西文科生、产品经理不要觉得，我有 Codex，我不错了，我不用你们了，我自己干。

没有人给你擦屁股、兜底。你不知道，你不知道你不知道的事情，你连你未知的边界都不知道，这个东西是最可怕的。所以当项目做过复杂的时候，你整个对于项目的位置都是未知的；当整个项目的边界远远超出你认知的时候，你没有人给你擦屁股。就这么一个道理。好，还有一些设计上的一些想法，我跟大家之前讲过。

## proactive agent 与主动式交互
一个是 proactive agent，即主动的 agent。目前 agent 的大部分场景都是一个 SaaS，或者是一个本地的聊天对话框，需要你大量地去问，问完之后大量地打字或者语音。总而言之，就是你大量地输入一段内容，然后 agent 根据内容去执行。proactive agent 这个东西其实我提出得更早，但 Anthropic 大概在去年的十一月份提出来的，它这个名字起得好。

但我其实比他提得更早，因为我的 full self coding 就是这个逻辑：你不要输入任何问题，我直接发现问题，我直接把它解决掉。所以说就是不要等人喂，不要等人问，不要等人手动设置，不要让人写小作文儿。你要长时间定时地工作，自己去尝试发现和解决新问题，首先尝试发现问题，然后问一问我发现这个问题你要不要解决，你点 OK 确定，然后你就自己去解决，这叫 proactivation。这种产品设计现在来说比较少，因为这个场景比较少，你要自己找一个场景。我觉得更好的是桌面助手类的工作，或者是。

类似考核，或者公司内部有做得非常好的 CRM、ERP 系统，这类工作其实都可以做；研究调研，或者定期做预判这类事情也都可以做。总而言之，不要让 agent 只做一件事。

## 从被动工作转向主动工作
要让被动工作的 agent 变成主动工作的 agent。作为领导，我这里少写了一点，现在给你们加上。我之前跟大家讲过的一个基本的第一性原理。

这个思路就是：你要设身处地地为你的用户着想，或者为你产品潜在的用户着想。这是我自己从设计任何 agent 产品、或者探索场景时得出的几个想法。

这些是你设计任何 agent 产品、或者探索场景时都必须遵循的几个原则。第一，你要设想自己是老板，是一个至高无上的老板，是一个可以随便对员工又打又骂的老板，这时你要想你会怎么对待你的 agent。你是老板，你需要人伺候，而不是别人伺候你，也就是要把大量工作交给 agent 自动完成，而不是由你嘱咐 agent 来完成；是 agent 来伺候你，而不是你为 agent 去服务。第二，你喜欢带主动的员工，而不是天天需要手把手教的大**，也就是 agent 要自己去做。

## 让 agent 自主进化与实时汇报
要找到方法，让 agent 自己去进化、自己去思考，而不是天天教它。第三，你更愿意看到 agent 实时汇报工作，做好可视化，而不是 agent 一开始做，闷头做四天，这四天之间你任何东西都不知道，或者只给你一个简单的 log，告诉你我在做什么——那是不行的。要实时、定期地汇报。

## 让不同 agent 内部竞赛
第四，你愿意让不同的 agent 以不同的方式去竞争，搞内部竞赛，比如 AB test，或者 ABCDE 五个组赛马，谁做得最好就用谁，其他四个组不用——这是老板的思维。老板的思维在于用管理学的方式，尤其是 agent management、agent team management，是很有效的。

## 用户能力参照：像父母用电脑
第二，你要明白，你永远是你爸你妈，你爸你妈用电脑一定没有你熟练。所以你没有那么强的天天登 agent 的能力。如果你用潜在的用户里面，大部分可能更像你爸你妈，而不是更像你。

## 产品需要基本引导
用户对于你的产品，不知道你能做什么，也不知道你能力的边界是什么。所以你要像你爸你妈一样：我不知道的时候，你要给我做好基本的引导。你写不出大段大段的 prompt，这是能力问题，而且是全世界大部分人的能力问题；能写正确 prompt、能写正确的那个位进去文件和数据的是少数。

## Proactive Agent 的选择逻辑与长期工作方式
那么需要 agent 自己来选，自己来选择，甚至你连写作文、写命题作文的能力都不需要，你只需要做选择题：你告诉我你要做五件事情，哪一个 agent 自己来帮你完成。这是我跟你们讲的几个可以参考的原则。所以 proactive agent 的逻辑就是：你不要等着喂，也不要等着问，你自己要长期工作，要趴在上面，就像一个员工一样，24 小时工作的员工，7 乘 24 小时，他实时地去做研究、做报告、去做研判。

去搜索他可能感兴趣的问题，然后去研究，然后去调查，然后整理分析，然后给报告给你。所以 proactive agent 就是这么一个逻辑，这也包括 coding 的问题，也就是 coding 问题，他不断地去看你代码质量怎么样。

然后去尝试去帮你去改变、改善一些性能，或者修一些 bug，或者尝试去看一些你们有没有其他新的问题，或者从 community，或者从其他你的那些 teammate 里面看他们有什么意见或者建议。

这 proactive agent 的工作，它不是说我要把这个东西扔给你你再干，而是说它要常年趴在你的一个 system 或者趴在你的一个 environment 里面去。

## 主动式 Agent 对工作环境的改变
要让 Agent 主动来帮你干活，而不是你等着它、让它等着你喂给它工作去干。这是 proactive agent，它会改变很多的工作环境、办公环境、工作流程、自动化流程，它一定会这么改变。

第二，很多人对 Agent 的设计是：我的 Agent 可以做任何事情，可以写任何代码。理论上说，你接的那个 LLM、你接的那个模型很伟大，这么说可以；你的 Agent harness 问题再大，至少你的模型是好的，所以你说你可以做任何问题，可以。

但是用户就会打问号：你到底能做什么。你说你能做一切东西，那我就要打字问你，你到底能做什么、不能做什么。你说我这药可以治所有的病，我敢不敢吃这东西。我肯定不敢吃。我这病能不能治，你让我猜，我哪猜得着去。所以我认为正确的 Agent 设计、Agent 宣传，就是我在 ABC 三个领域，我的 Agent 可以做得更好。

其他领域，我可能也会帮你做一些研究，或者做一些什么东西，但我做得不好。ABC 三个领域里面，我们成功概率很高，而且我们是专业的，我们知道该把流程理顺，我的 agent team 或者我的 agent workflow 能做得更好。这是一个正确的逻辑或者思维。

## 心累的 agent 设计一定是错的
还有一个是心累的设计。我的第二个原理是：你要像你爸你妈一样。如果你让你爸你妈这么做——手动添加所有的文件、文档、数据、表格、环境图片，什么乱七八糟的 environment，什么 JSON body，一堆 private key、public key，然后一堆东西都喂进去，写一个一万字的小作文描述你的完整需求——这些东西一定是专业人士才能这么用。你爸你妈如果解决不了日常的办公问题，他一定干不了这么专业的事，所以这一定会让人心累。因此，心累的 agent 设计一定是错的。

## 舒适的 agent 设计
舒适的 agent 设计是：整个 tool calling、memory 已经就绪，准备好主动获取一些环境信息，准备了你就来做 ABC 的选择题，你做完选择题我给你执行。这是一个好的设计方式，好的设计原则。

## 用这个原则重新思考产品
很多人以这个原则再去思考你现在要做的产品或者要做的项目，它会给你一个巨大的改观：我可能原来想到的是错的，或者我想到一个场景不对，或者我设计产品的思路是有问题的。
