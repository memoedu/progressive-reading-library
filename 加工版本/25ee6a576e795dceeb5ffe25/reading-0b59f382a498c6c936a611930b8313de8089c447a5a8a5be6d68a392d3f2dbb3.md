# “我们应该在开发软件时更有雄心”｜“We should be more ambitious with the software we build”

---

## 正文

从今年年初开始，Michael Malis（[pgrust](https://github.com/malisper/pgrust) 的成员）就一直向我展示他做过的有趣东西，并说：

> 对于我们 build 的 software，我们应该更有雄心[1](https://danluu.com/ambitious/#fn:A)

人们对 pgrust 这样的 projects 有很多怀疑，这是可以理解的，因为现在有太多 low-quality AI-generated projects。如果我不认识 Malis，也没有深入了解，我只会认定 pgrust 又是一个永远不会 work 的 vibe slopped project。但我对 Malis 足够了解，不必深入了解就能信任他的工作；而如果你稍加了解，就会发现，他在 testing pgrust 时，testing 得足够 thoroughly，甚至 uncovering 了 Postgres 中真正的 bugs，例如[这个可能 cause valid SP-GiST operations fail 的 numerical bug](https://www.postgresql.org/message-id/19597-39c532e61d78dff6%40postgresql.org)、[这个可能 cause JSONPath 产生 incorrect results 的 format cache bug](https://www.postgresql.org/message-id/19594-5d9bdc019e3f7f6e%40postgresql.org)、[这个可能 cause 后续 operations fail 的 pgcrypto bug](https://www.postgresql.org/message-id/19600-e5fb479f50f5022d%40postgresql.org)、[dictionary loader 中的多个 memory safety bugs](https://www.postgresql.org/message-id/19595-7dc18b4e212c4757%40postgresql.org)[2](https://danluu.com/ambitious/#fn:D)、[这个 money overflow bug](https://www.postgresql.org/message-id/19586-bb603bf5ad9934dd%40postgresql.org)，等等。

这不是说 pgrust 是 bug free[3](https://danluu.com/ambitious/#fn:T)，但这确实表明有大量 testing 正在进行；即使 pgrust 本身永远没有成功，仅仅做出这次尝试，也会给 Postgres 带来持久的 improved。pgrust 的主要卖点其实是 performance，而真正有趣的工作正在这方面发生；如果 pgrust fails，他们已经展示的一些 optimizations 有可能进入 Postgres、Clickhouse 等，但这显然不如 filing 随后得到 fixed 的 Postgres bugs 那么直接。

话虽如此，每次我在 news aggregator 上看到关于 pgrust 的讨论，大多数人都把它当成 vibeslop 垃圾而不屑一顾，我觉得这可以理解，因为这些 rewrite projects 几乎全都是 slop。如果我不认识 Malis，也会做出同样的假定，因为谁有时间深入了解所有这些 projects 呢？正因为我认识 Malis，我才没有费心去看；我只是信任他（我之所以发现上面这些，只是因为我想在这篇文章里把 pgrust 用作 example 之前，先核实一下它的情况）。

作为 software 的 consumer，无论看向哪里，你都会看到[明明是 slow software，creator 却声称它是 fast](https://danluu.com/benchpocalypse/)，因为 creator 正在吹嘘某个 slop benchmark，例如，[这是我昨天看到的多个 examples 之一](https://x.com/anthonysheww/status/2108627889910669707)；当然，不能 work 的 low-quality software 也比以往任何时候都更常见。

但是，作为 software 的 builder，这些 projects 几乎全都是 [vibeslop，其他人正在大批铲出垃圾并把它称为黄金](https://danluu.com/brain-off/)，这并不重要。你可以 build 像 pgrust 这样的东西，或其他在过去规模太大、实际上无法 feasible 的 projects；只要在 testing 和 benchmarking 上做得合理，这些东西实际上就能达到足以使用的 good-enough quality。

如果由我来写，我会说“对于我们 build 的 software，我们可以更有雄心”，而不是“我们应该”，但 Malis 是在和我随意聊天时说这话的，所以也许他在正式文章中也会用同样的说法；不要过度解读这里“应该”和“可以”的区别。我感兴趣的是，capabilities 已经 advanced 到让我们能做更多事情的程度。

举个例子，听说 OpenAI 打算将 Cerebras 用于他们的 SOTA models，而不只是像 5.3-Codex-Spark 这样的 fast-but-low-quality models 后，我看了看：如果我使用一个 SOTA model，但它 faster 了 10x 到 100x，我的电脑上的时间会花在哪里；有些东西本来有时就已经是 bottleneck，在 model 更 fast 后只会变得更糟，包括：

1.  Ripgrep（文本搜索工具）
2.  对 Rust 进行 Compiling
3.  Syscall 和 filesystem overhead

就“对我够用”的 project 水平而言，这些东西都可以得到大幅 improved。我眼下没有多少空闲时间，但即便如此，我还是 built 了[这个 regex engine，可以对它进行 tweaked，使它在我关心的任意特定 workload 上都比其他 general-purpose regex libraries 更 faster](https://danluu.com/benchpocalypse/)、[这个 ripgrep fork，它 uses 了 regex engine 中的 native code compiler，并且对我的 codex ripgrep workloads 而言更 faster](https://danluu.com/no-slow/)（当然，text index 是更好的 solution，[但我已经做过 text indexing](https://danluu.com/bitfunnel-sigir.pdf)，而这只是一个“纯粹为了好玩”的 project，我并没有试图做 optimal 的事情），以及一个让我的 projects 的 builds 得到 sped up 的 Rust（对 cold builds 有 huge improvement，对 warm 则是 moderate；由于希望避免 forking Rust compiler front-end，改进受到了 limited）。对于 syscalls 和 filesystem overhead，仅仅把 development 从 Mac 切换到 Linux，就已经 improved 了很多；当然，这也是另一个可以大幅 sped up 的方面，尤其是在 agents 密集执行大量 small filesystem operations 时（我经常看到自己的机器在 waiting on filesystem ops，因为 standard OS filesystem interface 在 designed 时并没有考虑 modern disk performance）。有了 modern disks，就没有理由再 use \*nix filesystem API。过去，writing 一个 uses direct I/O 而非普通 filessytem operations 的 developer toolchain，或者 building 一个 custom OS，或者一个能 fakes out syscalls 的奇怪 layer，都会是荒唐的尝试，但现在完全做得到。

对于像我这样对 regexes、string matching algorithms、compilers、interpreters 等一无所知的人，这组 projects 原本需要一年甚至更久才能达到“对我够用”的 quality。实际上，它只占用了我不到几个小时、以低个位数计的时间。如果我想让其中任何一个达到“有用的 product 或 open source project”的 quality bar，就会需要多得多的工作[4](https://danluu.com/ambitious/#fn:O)（而且我认为，几年前所需时间与如今所需时间之间的 ratio 会更低），但这个 process 得到 sped up 的程度仍然相当惊人。

Malis 说“对于我们 build 的 software，我们应该更有雄心”时，我对他意思的理解是：人们甚至没有想到去做这些如今已经很容易的事情。有好几个星期，每次我登录 Twitter，都会看到有人抱怨 Rust compilation 是 slow，而且正在 limiting development velocity（我觉得，在我看到这些抱怨时，实际情况并非如此，因为那时 5.6 Sol 和 6 Astra 还没有在 Cerebras 上可用；如果 measured 时间实际上花在了哪里，就会发现 Rust compilation time 当时其实并不是那么大的 bottleneck）。没错，Rust compliation 是 slow。你完全可以 write 一个 Rust interpreter，也可以直接 speed up compilation。我每天都看到人们抱怨这类 problems，而如今不用投入多少时间或精力，就能 solvable。据我所知，这些 problems 之所以仍然是 problems，是因为人们心里隐含地沿用着 pre-agentic cost model。十年前，因为自己的 compiler 是 slow 就去 implemented 一个新 compiler 的人，也正是那种想做 indie game 时会先开始 programming 一个新 3d game engine 的人，也就是说，是那种从来不 ships 任何东西的人。我认识的大多数 productive programmers 仍然对这类事情抱有抵触，尽管如今 implement 这类东西实际上已经是合理的了[5](https://danluu.com/ambitious/#fn:S)。

我之前提到的另一个 project 是[这个在 matched time controls 下达到 superhuman 的 Azul AI](https://danluu.com/game/tile/)。我做它时（使用 GPT-5.1/5.2），对 AI 的了解为零，花了大约 5 小时自己的时间，就得到了一个 superhuman 的东西；花了大约 20 小时自己的时间，就让它成为当时看起来 strongest 的 AI，[包括在对抗 humans 时，比这个曾被用于在 Board Game Arena 上 cheat 的 AI 更 stronger](https://www.youtube.com/watch?v=qkzpeXGwE-4)。Gabriel Cangussu 最近 built 了一个能 demolishes 我的 AI 的 AI；据我所知，他花的时间比我做自己的 AI 时少得多。和他聊过之后，我了解到，一个关键区别是 Fable 5.1 和 Opus 5.5 对 board game AIs 的理解要好得多。我使用 GPT-5.1/5.2 时，它们给出的建议几乎全是错的，我必须做大量 steering，才能让结果勉强合理。如果我让 GPT read 一个 codebase 或一篇 paper，以 implement paper 中相关的 techniques，它就会 fail。如果我自己读 paper，并说出某个 technique 的名称，它会声称自己做了这个 technique，但通常只会做出某种表面上像那个 technique、实际上却不是那个 technique 的东西，直到我做出一些 corrections。当 model 离正确完成事情还差这么远时，如果你没有这个领域的背景，check model 是否做对就会相当耗时，因为你必须先充分了解它应该做什么，才能 check 它是否做到了自己声称完成的事情。

做那个 project 时，我对朋友说，我不认为 models 当时的状态会持续下去。它们似乎不可能不会很快进步到足以 read 一篇 paper 并 implement 其中 techniques 的程度，而且它们似乎也应该能自己挑选可供借鉴的 codebases 和 papers。根据我稍微试用 Fable 5 的经历，以及 Cangussu 使用 Fable 5.1 和 Opus 5.5 的经历，这似乎已经发生了；对于像我这样对 board game AIs 一无所知的人，这能节省大量时间（我现在懂了一点，但仍然比任何真正的 AI researcher 都少）[6](https://danluu.com/ambitious/#fn:B)。

对于任何特定 domain，比如 board game AIs，你都可以说：“谁在乎呢？Board game AIs 并不重要。”但我发现，capability 的这种 increase 在不少不同的 domains 中都存在。举个例子，[我做了这个关于 verification 和 test techniques 的 toy eval，让 GPT-5.6 Sol 在 medium 和 xhigh 下 implementing zstd](https://danluu.com/agentic-testing/)。我还没有时间把它写出来，但在发表那篇文章时，我也用 GPT-6 Astra 重新做了 evals。6 Astra 表现太好了，以至于我不得不寻找不同的 evals，因为 models 已经 advanced 得太多了。对于 zstd，在所有 conditions 下，6 Astra 都有超过 99% 的时候 succeeds at passing 全部 registered tests，即便那些会 significantly impair performance 的 conditions 也不例外，比如 using TDD（顺便说一句，它的花费也更低，implement zstd 大约只需 $1）。我最终用了 5.6 Sol 无法 effectively 完成的 IMAP RFC，以及 Pandoc；后者 implement 起来是件相当大的事，因为它需要能够 read 和 write 许多不同的 formats[7](https://danluu.com/ambitious/#fn:P)。

顺便说一句，有人说自己用了新的 model，一切就都能正常运行，software 的问题已经解决了，等等；我完全没有发现情况如此。较新的 model 确实能对更多事情 one-shot，让结果基本上直接可用，但这只意味着，我最终会去做更有雄心、models 仍然会遇到困难的事情[8](https://danluu.com/ambitious/#fn:E)。我[更 productive，而且可以工作得更 faster](https://danluu.com/productivity-velocity/)，但我发现，就自己在做的事情而言，每换一个更 capable 的 model，我反而离“直接就能用”更远，因为 model [无需大量手把手指导就能 verify effectively](https://danluu.com/agentic-testing/) 的事情，与 model 能够 implement 的事情之间的 gap 一直在 increasing[9](https://danluu.com/ambitious/#fn:F)。以上这一大段，只是在用一种冗长且不那么精练的方式说：对于我们 build 的 software，我们应该更有雄心。

### 附录：我们对自己 build 的 software 应该少一些雄心

下面是 Yossi Kreinin 的一则评论，在此引用（当然，已经得到许可）：

> 如果你发表这篇文章，我就会发表一篇回应，解释对大多数人而言，他们对自己用 AI build 的 software 应该少一些雄心，否则就会遭遇惨败。我认为，很多 problems 并不那么适合用 "agentic loops" 处理，因为你没有 clear pass/fail criteria；而即便有，大多数人也很难对 giant black boxes 进行 reasoning，他们可以对这些 black boxes impose constraints，却无法理解其内部机制。\[我也把自己算在其中。\] 我想这有点像 microservices：有些人既需要它，也非常善于使用它，但对大多数人而言，他们可能没那么需要它，而且根本用不好。当然，我有点羡慕那些对自己 build 的 software 应该、而且确实能够怀有如此雄心的人；并不是说你 _完全_ 不应该有更大的雄心，但我认为，对大多数人来说，节制这种雄心是应对当前局面的重要一环
> 
> 顺便说一句，我对“[software 没有理由是 slow](https://danluu.com/no-slow/)”也有类似想法；在很多情况下，如果你用 AI 来 speed up 某个 flow，就会添加一堆 messy code，它会对你 tested 的 use case 产生 overfit，而且既不能在 perf-wise 上 generalize 到所有你应该关心的 use cases，也无法在未来发生 changes 时保持 maintainable。如果你知道自己在做什么，理解 system 应该如何被 decomposed 成 parts，知道什么时候值得全力 optimizing 某个 part 或多个 parts 协同工作的 combination，以及如何 properly benchmark 它，等等，那当然很好。但如果，比如说，你有个 manager 认为 software 没有理由是 slow，并且催促大家用 AI 把 software 中随意一些 parts 变得 fast……赶紧找地方躲起来吧

我的感觉是，总体而言，这里的情况[有点 analogous 于这里的讨论：为什么我不喜欢人们说 AI 带来了 100x 或 1000x productivity increase](https://danluu.com/ai-coding/)。有些事情获得了极大 factor 的 sped up，轻轻松松就超过 1000000x。而有些事情目前根本没有获得 sped up。如果你做的事情与五年前会做的完全一样，只是用上了 AI，那么 speedup 就相当有限，[原因是 Amdahl's law](https://en.wikipedia.org/wiki/Amdahl%27s_law)。但在 general case 下，你可以选择要 speed up 什么；如果你在寻找值得做、能够产生成果的事情，这似乎往往涉及那些以前做起来代价太大的事情。

而且，我认为，即使大多数人不会这么做，你也往往可以 set up 具有某种 self-checking property 的 systems。[这篇关于 Guards of Atlantis 2 的 implementation 的讨论](https://danluu.com/pl-tokens/#appendix-guards-of-atlantis-2)就是一个例子。它并不适合作为 AI project，因为 official rules 是一堆 ambiguous、contradictory 的英文文字（这可能是我见过人类玩错比例最高的 game，而且 rules 混乱到，尽管 designer 一直坚称 rules 完全清楚，只要按原文阅读就能玩，他们自己却常常改变对自己所写 rules 含义的看法）。如果你试图用 naive 的方式 produce 一套 working rules，AI 对此并没有多大帮助（不过，一旦有了 clean spec，它就能 speed up implementation）。但在这件事上，我得以在所有对 game rules 的 inconsistent explanations 之间 set up 一套有点粗糙的 consistency checks，得到了一套相当接近 correct 的 rules（与另一个人投入更多人力、采用不那么 systematic 的 approach 所得到的结果大致同样接近），这就足以让我把它与另一个人的 implementation 进行 compare，并得到一套 working rules。这个 setup 确实比更 manual 的 approach 花费了多得多的 tokens。不过，它“只”花了使用 GPT-5.1/5.2 的 $200/mo OpenAI subscription 的一两个月费用，比我坐下来为这个 game 写一份 clean spec——也就是一份真正 consistent、correct 的 rules——所需的时间成本更低。

我感觉很多 problems 都属于类似的 class of problem：可以 set up 某种至少 partially self-checking 的 setup，而人只需在上面花少量时间。这也让我觉得 analogous 于整个 software testing 的情况：（在 coding agents 出现之前）我发现 fuzzing 和 property-based testing 是 highly effective 的。对于大多数 domains，人们都告诉过我某种理由，说这种 testing 行不通；但当我在所有那些被告知这些 techniques 行不通的 domains 中尝试这些 techniques 时，它们都能很好地发挥作用。apply 它们确实稍微费些工夫，但它们仍然是 applicable 的，而且 AFAICT，比 writing traditional unit tests 更 efficient、更 effective。

Yossi 那则评论的部分要旨是，人们并没有做这种事情。考虑到我如今看到的 bugs 比过去多了那么多，比如，上次我打开一家大型 AI lab 的 web chat，不到一分钟就遇到了两位数的 bugs，很难说 Yossi 错了。但就这一点而言，我仍然坚持原来的看法。别人正在大量生产 barely working slop，并不意味着你也非得这么做。

### 附录：几个“随意”的例子

我在正文中举出的那些我做过的事情，都是我原本绝不会去做的 tooling。类似的事情还有很多，因为 build 仅供我自己使用、达到“对我够用”质量的 tooling 实在太容易了。我确实认为，有可能做得过头，反而不再 productive，例如，[Steve Yegge 写了很多关于 Gas Town 及其有多 productive 的文章，但在 building 他的下一个 agentic framework 时，他提到，自己从未用 Gas Town 成功 build 过 Gas Town 以外的任何东西](https://x.com/danluu/status/2099800154639581353)，还有[这里有人在玩他用下一个 gen framework 创建的 game](https://youtu.be/NuktXEikxU8?si=Ylg6tCZa4ZYsn0Qe&t=1072)（评论者提到 $1B，是因为 Yegge 说他的 game 有望成为第一家由一个人经营的十亿美元公司），[人们曾有一阵子很热衷于 Ralph Loops，尽管我尝试 comparing 它们时，感觉它们还不如我当时所做的 naive 做法，也就是带有 context 的 normal loops：有时视情况 clear context，而不是默认在 single turn completed 这个完全任意的时间点这样做](https://x.com/danluu/status/2102405091634598313)，诸如此类，所以我一直尽量只做那些效果相当直接的事情。除了这种做法之所以有效的显而易见的原因之外，model 和 harness capability 随时间发生的剧烈变化，也意味着值得 build 的 tooling 变化得非常快，因此，花大量时间开发某个特定的 tool，而它三个月后充其量也只是 suboptimal，甚至很可能已经 obsolete，实在没有多大意义。

而且，对于我的许多个人 tools，我的假设是，某个 AI lab 很快就会让我的任何成果 obsolete。举一个很傻的例子，自 GPT-5.6 Sol 发布以来，我有一个一直很有用的 tool，它在发现 memory leak 时会 restarts codex。想必 OpenAI 迟早会 fix 这个问题，这个 tool 也就毫无价值了。再举一个稍微没那么傻的例子，就是我让某个 agent build 的 Rust interpreter。出于 token-budget 方面的原因，为实现一个非常 high-performance 的 interpreter 而应当做的许多事情，都还没有做。

例如，这个 interpreter 不会 modify 实际的 Rust front-end compiler，以便轻松接受 updates；如果我直接对 Rust front-end 做 changes，performance 会好得多，但我没有足够的 token budget 来 maintain Rust compiler 的 compatible fork，不过这对 OpenAI 应该不是问题。OpenAI 承诺投入 $10B+ 来获取 Cerebras 的使用权，同时阻止 Anthropic 获得使用权。

有趣的是，对于 coding，在许多 tasks 上，如果你实际使用他们的某个 SOTA models，并将其与 Anthropic 提供的东西 compare，实际的 speedup 并没有那么大，因为时间花在了 compiling Rust 之类的事情上。既然他们愿意为此投入 $10B+，那么按理说，他们最终会在 speeding up 相关 tools 方面做得比任何 AI lab 之外的人所能切实做到的都更好，所以在这方面投入过多精力并没有多大意义（如果预计 non-coding tasks 会在短期内完全主导 OpenAI 未来的收入，那么这个判断也许不成立；但即便如此，考虑到他们为 tokens 支付的费用与我支付的费用之间的差异，既然我在 lab 之外都能做到，让他们 speed up 其中许多事情似乎仍然是合理的；也许存在某种论点，比如，如果你能接触到他们的 usage data，就会发现还有太多更重要的 bottlenecks，以至于不值得 prioritize 这一个，但即使它排不进 Cerebras-enabled coding agents 的前 100 个 bottlenecks，在某个时候去做这件事，对他们而言似乎仍然应该是合理的）。

另一类事情，也许算不上有雄心，但能说明现在可以做到什么，就是我做过的 games。有些 games 我曾设想过，也想过要做，我觉得它们总体上没有好玩到值得面向真正的受众推出，但我自己一直想玩。例如，自从在 90 年代读过 David Gerrold 的 [Star Wolf](https://en.wikipedia.org/wiki/Star_Wolf_\(novel_series\)) 系列书籍后，我就一直想玩一款 implements 书中所描述的 combat 的 game，那有点像 submarine combat。至少在 realistic war games 中，这个 genre 极其小众，因为几乎人人都觉得 naval combat 很无聊，而 submarine combat 又是 naval combat games 中尤其无聊的 subgenre，所以把它做成一款赚钱的 game 并不怎么合理；但 implement games 实在太容易了，于是我让一个 agent implement 了这款 game，好让我玩上一两个小时。我绝不会为了玩一两个小时而花 10-20 小时 implementing 一款 game，但我愿意花 5 分钟。我之前也提到过 implementing [一款与 Scout 有着相同 rules 的 game](https://danluu.com/game/flip-taker/)、[Guards of Atlantis 2](https://danluu.com/pl-tokens/#appendix-guards-of-atlantis-2) 以及其他 board games。我原本绝不会花时间手动 implement 这些 games，仅仅是为了在无法与朋友线下相聚的时候能有一种一起玩的方式，但我很乐意让 LLM 把这些东西赶出来。当然，对于那些想面向更广泛受众制作 games 的人来说，coding agents 正在带来一场 game 复兴。如今，拥有 programming skills 以及投入时间运用这些技能，已不再是制作 games 的 bottleneck，随之出现的有趣而富有创意的 games 数量之多，令人惊叹。

Data analysis 是另一件 productivity multiplier 可以非常高的事情，我可以做各种原本绝不会去做的事。正如我在最近的多篇文章中提到的，这类 projects 实在太多了，即使我试着写得非常快、每半小时赶出一篇文章，也根本无法一一写出来。

在和人们聊他们的 one-off tooling 时，我发现大家做过许多有趣的东西。例如，下面是 Peter Geoghegan 一两个月前提到的一件事：

> 我让 Fable implement 了一个 custom Neovim Lua function，它会按照我非常具体的偏好来 formats code。这既是我不想亲自 maintain 的东西，本质上也是一个 Rube Goldberg device。理论上，我可以通过 patching clang-format，以一种有章法的方式达到同样的结果，但我的 requirements 太精确了，我觉得那种做法永远无法令人满意。
> 
> 我们使用一个叫 pgindent 的 tool，它是我们对 bsd\_indent 的 fork。你可以使用 clang-format 来 approximate 同样的 formatting rules，但那还不够好。如果我 commit 的东西没有完全按照 pgindent 进行 formatted/indented，就会遇到一个 CI failure，而我得迅速 fix 它——这是我实在很想避免的事情……
> 
> 实际来说，要得到利落的、clang-format-style formatting，同时避免收到抱怨 misindented code 的催促邮件，就必须搞出一团 architectural mess（我 _也_ 不想花时间开发一种有章法的做法，不过那其实是另一个问题）。这个 function 让我能够毫不费力地从 Neovim 中 format 给定的 block of code，类似于 clang-format LSP integration。当然，我在这里挑剔得有些不讲道理，但我发现 LLMs 让我可以对 tooling 如此苛求。
> 
> 这个 function 会 performs multiple passes：先是一个使用 clang-format/clangd 的 initial formatting pass，再是一个使用 pgindent 的 separate formatting pass。我需要它两者都做，因为 clang-format 能 handles 一些 pgindent 遗漏的 cases，而且处理得 correctly。这很 brittle，因为我只想 format 通过 block visual mode selected 的 range of lines 内的 code（我不想对并非由我的 patch added 的 code run clang-format）。这与 pgindent 的 design conflicts；它只能 format 整个 C files。
> 
> 要弄清 temp whole file buffer 中哪个相关 subset 需要被 copied back 到我的 working buffer，并不是一件简单的事。我最初 selected 的 line range 并不会 directly map to 受影响的 C AST elements。因此，这个 function 会 uses tree-sitter 来 intelligently delineate 那些需要被 copied back 的 temp indented C code 的 exact subset。对于我的 selection 横跨同一个 block of code 的 cases，这些 rules 需要以恰到好处的方式保持 fuzzy。这里有许多 edge cases。
> 
> 另一个让事情变复杂的因素是，pgindent 依赖一个用 objdump generated 的 typedef file 来 identify types；没有那个 file，formatting 看起来就很古怪。这个 formatting function 会针对那一个 file，从 clangd dynamically generates 任何额外的 typedefs，因此我不必担心 stale typedef file（我可能在 running formatting tool 的几秒钟前才 created 一个新的 struct，我不想每次都对整个 postgres binary run objdump，那会让 latency 暴涨）。
> 
> 这似乎运行得完美无缺。latency 完全可以接受。不过，我对这一切如何运作只有模糊的理解。我甚至不懂 Lua。这大概会继续正常工作，即使我们对 bsd\_indent 的 fork 进一步做 changes，多少 alter 了 code 被 formatted 的方式，而这种情况时有发生。
> 
> 我对 saaspocalypse 持怀疑态度。但我确实认为，LLMs 正在 writing 大量有用的 software，如果换成其他任何方式来 write，经济上都会极其不划算。有一小部分 software 很有意思：相对于它所创造的价值，让任何人来 maintain 都会繁琐到令人无法承受。

我觉得这类例子很有意思，也指向了这个 industry 在不远的将来会处于什么位置，但是，在依赖其他同样用 unlimited tokens 构建的 infrastructure 和 tooling 时，你用 unlimited tokens 能做什么，并不能充分说明你今天在没有无限资金的情况下能完成什么。像 pgrust 这样的 projects，以及我认识的人利用业余时间做的 projects（我提到的大概只有其中的 1%——这样的东西实在太多了，比如 David Turner 为 podcasts 创建了一个达到“对我够用”质量的 ad skipper，比他能找到的任何东西都好用，还有 [Dennis Snell 在这里提到的业余 projects](https://fluffyandflakey.blog/2026/10/19/radical-explorations/)，等等），更能代表你今天能做什么。

## 原文

Since early this year, Michael Malis (of [pgrust](https://github.com/malisper/pgrust)) has been showing me interesting things he's done and saying

> \[W\]e should be more ambitious[1](https://danluu.com/ambitious/#fn:A) with the software we build

There is, understandably, a lot of skepticism about projects like pgrust because there are so many low-quality AI-generated projects out there. If I didn't know Malis and didn't look into it, I would just assume that pgrust was another vibe slopped project that's never going to work. But I know Malis well enough to trust his work without looking into it, and if you look into it a bit, you'll see that in testing pgrust, he's testing thoroughly enough that he's even uncovering real bugs in Postgres, such as [this numerical bug that can cause valid SP-GiST operations to fail](https://www.postgresql.org/message-id/19597-39c532e61d78dff6%40postgresql.org), [this format cache bug that can cause incorrect results from JSONPath](https://www.postgresql.org/message-id/19594-5d9bdc019e3f7f6e%40postgresql.org), [this pgcrypto bug that can cause later operations to fail](https://www.postgresql.org/message-id/19600-e5fb479f50f5022d%40postgresql.org), [multiple memory safety bugs in the dictionary loader](https://www.postgresql.org/message-id/19595-7dc18b4e212c4757%40postgresql.org)[2](https://danluu.com/ambitious/#fn:D), [this money overflow bug](https://www.postgresql.org/message-id/19586-bb603bf5ad9934dd%40postgresql.org), etc.

This isn't to say that pgrust is bug free[3](https://danluu.com/ambitious/#fn:T), but it does indicate that there's a substantial amount of testing happening and, even if pgrust itself is never successful, just making the attempt will have improved Postgres in a durable way. The main pitch for pgrust is actually performance, and that's where the really interesting work is happening; if pgrust fails, it's possible that some of the optimizations they've demonstrated will make it into Postgres, Clickhouse, etc., but that's obviously less direct than filing Postgres bugs which get fixed.

That being said, I find it understandable that, every time I see pgrust discussed on a news aggregator, most people dismiss it as vibeslop garbage because almost all of these rewrite projects are slop. If I didn't know Malis, I would make the same assumption, because who has the time to look into all of these projects? Because I know Malis, I didn't bother to look at it; I just trusted him (I only found the above because I wanted to check on pgrust before using it as an example for this post).

As a consumer of software, everywhere you look, there's [slow software that the creator is claiming is fast](https://danluu.com/benchpocalypse/) because the creator is touting some slop benchmark, e.g., [here's one of multiple examples I saw yesterday](https://x.com/anthonysheww/status/2108627889910669707), and of course low-quality software that doesn't work is more common than ever.

But, as a builder of software, it doesn't matter that almost all of these projects are [vibeslop, that other people are out there shoveling out huge piles of crap and calling it gold](https://danluu.com/brain-off/). You can build things like pgrust or other projects that would've been too large to really be feasible in the past and, if you do a reasonable job with testing and benchmarking, that stuff can actually be good-enough quality to use.

If I were writing it, I would say "we can be more ambitious with the software we build" and not "we should", but Malis has been casually chatting with me when he's said this, so maybe he would say the same in an actual post; don't read too much into should vs. can here. What's interesting to me is how capabilities have advanced such that we can do a lot more.

Just for example, after hearing that OpenAI was going to use Cerebras for their SOTA models and not just fast-but-low-quality models like 5.3-Codex-Spark, I looked at where time on my computer would go if I was using a SOTA model, but 10x to 100x faster; some things that were already sometimes a bottleneck that would only get worse with a faster model were:

1.  Ripgrep
2.  Compiling Rust
3.  Syscall and filesystem overhead

At the level of a "works for me" project, these are all things that can seriously be improved. I don't have much spare time at the moment but, even so, I built [this regex engine that can be tweaked to be faster than other general-purpose regex libraries on any particular workload I care about](https://danluu.com/benchpocalypse/), [this ripgrep fork that uses the native code compiler from the regex engine and is faster for my codex ripgrep workloads](https://danluu.com/no-slow/) (of course a text index is the better solution, [but I've already worked on text indexing](https://danluu.com/bitfunnel-sigir.pdf) and this was a "just for fun" project where I wasn't trying to do the optimal thing), and a Rust that sped up builds for my projects (huge improvement for cold builds, moderate for warm, limited by wanting to avoid forking the Rust compiler front-end). For syscalls and filesystem overhead, just switching development from Mac to Linux improved this a lot, and of course this is another thing that can be sped up a lot as well, especially when agents are hammering lots of small filesystem operations (it's not uncommon to see my machine waiting on filesystem ops because the standard OS filesystem interface wasn't designed with modern disk performance in mind). With modern disks, there's no reason to use the \*nix filesystem API. In the past, writing a developer toolchain that uses direct I/O instead of normal filessytem operations or building a custom OS or a funny layer that fakes out syscalls would've been an absurd endevaor, but that's totally doable now.

For someone like me who doesn't know anything about regexes, string matching algorithms, compilers, interpreters, etc., this set of projects would've taken a year or more to get to "works for me" quality. Instead, this was a low single-digit number of hours of my time. If I wanted to make any of these things meet a "useful product or open source project" quality bar, that would be a lot more work[4](https://danluu.com/ambitious/#fn:O) (and I think the ratio between how long it would've taken a few years ago and how long it takes today would be lower), but it's still pretty incredible how much this process is sped up.

My read of Malis's meaning when he says “we should be more ambitious with the software we build”, is that it doesn't even occur to people to do these things that are now easy. For weeks, every time I logged into Twitter, I saw someone complain about how Rust compilation is slow and is limiting development velocity (I think this wasn't actually true when I saw the complaints, in that this was before 5.6 Sol and 6 Astra were available on Cerebras, and if you measured where the time actually went, Rust compilation time wasn't actually that much of a bottleneck at the time). Sure, Rust compliation is slow. You can just write a Rust interpreter as well as speed up compilation directly. There are problems like this which I see people complaining about daily that are solvable without a lot of time or effort now. As far as I can tell, these problems are problems because people are implicitly carrying around a pre-agentic cost model. Ten years ago, the kind of person who implemented a new compiler because their compiler was slow was the kind of person who started programming a new 3d game engine when they wanted to make an indie game, i.e., the kind of person who never ships anything. Most productive programmers I know still have an aversion to this kind of thing, even though it is now actually reasonable to implement this kind of thing now[5](https://danluu.com/ambitious/#fn:S).

Another project I previously mentioned was [this Azul AI which is superhuman at matched time controls](https://danluu.com/game/tile/). When I did that (with GPT-5.1/5.2), with zero AI knowledge, it took about 5 hours of my time to get something superhuman, and about 20 hours of my time to become what appeared to be the strongest AI at the time, [including being stronger against humans than this AI that was used to cheat on Board Game Arena](https://www.youtube.com/watch?v=qkzpeXGwE-4). Gabriel Cangussu recently built an AI that demolishes my AI, and AFAICT, it took him substantially less time than my AI took me. From talking to him about it, one key difference is that Fable 5.1 and Opus 5.5 have a much better understanding of board game AIs. When I used GPT-5.1/5.2, pretty much every suggestion they had was wrong and I had to do a lot of steering to get things to be remotely reasonable. If I had GPT read a codebase or a paper to implement relevant techniques from the paper, it would fail. If I read the paper myself and named a technique, it would say it did the technique, but it would generally do something that superficially looked like the technique but wasn't the actual technique until I issued some corrections. When the model is that far from being able to do the right thing, if you have no background in the area, it's fairly time consuming to check if the model did the right thing since you have to learn enough about what it's supposed to do to be able to check that it did what was claimed.

When I did that project, I said to friends that I didn't think the state models were in could last. It seemed impossible that they wouldn't get good enough to be able to read a paper and implement the techniques soon, and it seemed like they should also be able to pick out codebases and papers to crib from as well. From my experience messing around a bit with Fable 5 and Cangussu's experience with Fable 5.1 and Opus 5.5, that seems to have happened, which is a huge time saver for someone like me who doesn't know anything about board game AIs (I know a little bit now, but still less than any real AI researcher)[6](https://danluu.com/ambitious/#fn:B).

For any particular domain, like board game AIs, you can say, "who cares? Board game AIs don't matter", but I've found this increase in capability to be true in quite a few different domains. Just for example, [I did this toy eval of verification and test techniques with GPT-5.6 Sol implementing zstd on medium and xhigh](https://danluu.com/agentic-testing/). I haven't had time to write it up, but when I published that post, I also re-did the evals with GPT-6 Astra. 6 Astra was so good that I had to find different evals because models had advanced too much. For zstd, 6 Astra succeeds at passing all of the registered tests more than 99% of the time across all conditions, even the ones that significantly impair performance, like using TDD (and, BTW, it does it more cheaply as well, taking about $1 to implement zstd). I ended up using the IMAP RFC, which 5.6 Sol couldn't do effectively, and Pandoc, which is a pretty major thing to implement as it needs to be able to read and write many different formats[7](https://danluu.com/ambitious/#fn:P).

BTW, when people have said they used the new model and everything just works, software is solved, etc., I haven't found this to be true at all. It's true that there are a lot more things the newer model can one-shot, where things basically just work, but this just means that I end up working on more ambitious things where models still struggle[8](https://danluu.com/ambitious/#fn:E). I'm [more productive and can work faster](https://danluu.com/productivity-velocity/), but I find that, in terms of what I'm doing, I get farther from "it just works" with each more capable model because the gap between what the model [can verify effectively without significant handholding](https://danluu.com/agentic-testing/) and what the model can implement has been increasing[9](https://danluu.com/ambitious/#fn:F). All of that is a long-winded and less eloquent way of saying: we should be more ambitious with the software we build.

### Appendix: we should be less ambitious with the software we build

Here's a comment from Yossi Kreinin, quoted (with permission, of course):

> If you publish this I will publish a response explaining that for most people they should be less ambitious with the software they build with AI or they'll experience abject failure. I think a lot of the problems don't lend themselves that well to "agentic loops" since you don't have clear pass/fail criteria, and even when you do most people have trouble reasoning about giant black boxes which they can impose constraints on but can't understand the innards of \[I include myself in this set.\] This is a little bit like microservices I guess, where some people both need it and are very good at using it but likely for most people, they need it less and can't use it well at all. I sort of envy the ones who should and actually can be this ambitious about the software they build of course; not saying you shouldn't be more ambitious _at all_ but moderating said ambition is a big part of handling the current situation for most I think
> 
> I have a similar thought about "[there's no reason for software to be slow](https://danluu.com/no-slow/)" BTW; in many cases, if you use AI to speed up some flow, you will add a bunch of messy code that will be overfit for the use case you tested on and will neither generalize, perf-wise, for all the use cases you should care about, nor will be maintainable upon future changes. If you know what you're doing and you understand how the system should be decomposed into parts and when it makes sense to go all-in on optimizing some part or a combination of them working together and how to properly benchmark it, etc., then things are great, but if for instance you have a manager who thinks there's no reason for software to be slow and he pushes people to use AI to make random parts of the software fast... Run for cover

My feeling is that, overall, the situation here is [a bit analogous to the discussion here about why I don't like when people talk about how AI gives a 100x or 1000x productivity increase](https://danluu.com/ai-coding/). There are some things that are sped up by a very large factor, easily over 1000000x. And some things don't currently get sped up at all. If you do exactly what you would've done five years ago, but with AI, the speedup is fairly poor [because of Amdahl's law](https://en.wikipedia.org/wiki/Amdahl%27s_law). But, in the general case, you can choose what to speed up and if you're looking for things that are productive to do, this often seems to involve things that were previously too expensive to do.

And, I think that you can often set up systems that have some kind of self-checking property even when most people wouldn't. [This discussion of the implementation of Guards of Atlantis 2](https://danluu.com/pl-tokens/#appendix-guards-of-atlantis-2) is an example of that. It's a poor choice for an AI project because the official rules are a mess of ambiguous and contradictory English text (it's probably the game I've seen humans misplay at the highest rate, and the rules are confusing enough that the designer has often changed their mind about what their own rules mean despite continually maintaining that the rules are perfectly clear and one can play the game by simply reading the rules as written). If you try to produce a working set of rules in a naive way, AI won't really help with this (although it can speed up implementation once you have a clean spec), but for that, I was able to set up some kind of janky set of consistency checks between all of the inconsistent explanations of the game rules, which got fairly close to a correct set of rules (approximately as close as what someone else did with much more human effort and less of a systematic approach), which was enough to compare it to someone else's implementation and get a working set of rules. This setup did cost a lot more in tokens than a more manual approach. But it was "only" a month or two of the $200/mo OpenAI subscription with GPT-5.1/5.2, which is a lower cost than the cost in time of me sitting down and writing a clean spec for the game, i.e., a copy of the rules that is actually consistent and correct.

I feel like a lot of problems are in something like this class of problem, where it's possible to set up some kind of at least partially self-checking setup that a human can spend a small amount of time on. This also feels analogous to the situation about software testing at large, where (before coding agents) I found fuzzing and property-based testing to be highly effective. For most domains, people told me some kind of reason this kind of testing wouldn't work, but when I've tried these techniques with all of the domains people told me these techniques don't work for, they work fine. They're somewhat more work to apply, but they're still applicable and, AFAICT, more efficient and effective than writing traditional unit tests.

Part of the gist of Yossi's comment is that people aren't doing this kind of thing. Considering how many more bugs I see now than I used to, e.g., the last time I opened up the web chat for a big AI lab, I ran into a double-digit number of bugs within one minute, it's hard to say that Yossi is wrong. But, to that point, I still have my original opinion. Just because other people are pumping out vast quantities of barely working slop doesn't mean that you have to do the same thing.

### Appendix: a few "random" examples

The examples in the body of the post I gave for things I've done are tooling things I never would've done. There are a lot more things like that as well since it's so easy to build "works for me" quality tooling that's intended solely for me. I do think it's possible to go further than is productive, e.g., [Steve Yegge wrote a lot about Gas Town and how productive it was, but when he was building his next agentic framework, he noted that he never used Gas Town to successfully build anything other than Gas Town](https://x.com/danluu/status/2099800154639581353) and [here's someone playing his game that's been created with his next gen framework](https://youtu.be/NuktXEikxU8?si=Ylg6tCZa4ZYsn0Qe&t=1072) (the commenter's references to $1B are because Yegge says his game is in the running for being the first solo-run billion dollar company), [people were into Ralph Loops for a while even though, when I tried comparing them, they seemed worse than just doing the naive thing I was doing at the time, normal loops with context where you sometimes clear context as appropriate instead of doing it by default at the completely arbitrary point of when a single turn is completed](https://x.com/danluu/status/2102405091634598313), etc., so I've tried to stick to things where the impact is pretty direct. Besides the obvious reason this has been effective, the dramatic change in model and harness capability over time means that what tooling it makes sense to build changes very quickly, so spending a lot of time working on any particular tool that will be suboptimal at best and quite possibly obsolete in three months doesn't really make sense.

And, for a lot of my personal tools, my assumption is that an AI lab will obsolete anything I make in short order. For a very silly example of this, I have a tool that was useful since the release of GPT-5.6 Sol that restarts codex when it finds a memory leak. Presumably, OpenAI will fix this at some point and this tool will become worthless. For a slightly less silly example, take the Rust interpreter I had some agent build. For token-budget reasons, a lot of things that ought to be done for a very high-performance interpreter haven't been done.

For example, the interpreter doesn't modify the actual Rust front-end compiler to make it easy to take updates; performance would be much better if I just made changes to the Rust front-end, but I don't have the token budget to maintain a compatible fork of the Rust compiler, but this shouldn't be a problem for OpenAI. OpenAI committed $10B+ on getting access to Cerebras while also preventing Anthropic from having access.

Funnily enough, for coding, on many tasks, if you actually use one of their SOTA models and compare it to what you get from Anthropic, the actual speedup isn't all that large because of time spent on things like compiling Rust. Given that they were willing to commit $10B+ on this, it stands to reason that they'll eventually do a better job at speeding up the relevant tools than anyone could feasibly do outside an AI lab, so there's not much point in spending too much effort on this (this could arguably be untrue if non-coding tasks are expected to completely dominate future OpenAI revenue in the short term, but even then, given what they pay for tokens vs. what I pay, it still seems like it would make sense for them to speed a lot of these things up given that I could do it outside of a lab; perhaps there's some kind of argument like, if you have access to their usage data, there are so many more important bottlenecks that this one doesn't make sense to prioritize, but it still seems like it should make sense for them at some point even if it doesn't fall into the top 100 bottlenecks for Cerebras-enabled coding agents).

Another kind of thing that one might not call ambitious, but that speaks to the kind of thing that's possible, are games that I've made. There are games I've thought about and wanted to make that I don't think are generally enjoyable enough that they make sense for a real audience, but that I've wanted to play. For example, ever since reading David Gerrold's [Star Wolf](https://en.wikipedia.org/wiki/Star_Wolf_\(novel_series\)) books in the 90s, I've wanted to play a game that implements combat as described in the books, which is a sort of like submarine combat. At least among realistic war games, this genre is extremely niche because almost everybody finds naval combat boring, and submarine combat is a particularly boring subgenre of naval combat games, so this doesn't really make sense as a money-making game, but it's so easy to implement games that I had an agent implement the game so I could play it for an hour or two. I never would've spent 10-20 hours implementing a game so that I could play it for an hour or two, but I'd spend 5 minutes. I've also previously mentioned implementing [a game with the same rules as Scout](https://danluu.com/game/flip-taker/) and [Guards of Atlantis 2](https://danluu.com/pl-tokens/#appendix-guards-of-atlantis-2) and other board games. I was never going to take the time to implement these games by hand just so I have a way to play with my friends on the occasions where we can't get together in-person, but I'm happy to have an LLM bash these things out. And, of course, for people who want to make games with a wider audience, there's a game renaissance going on right now due to coding agents. It's amazing how many interesting and creative games are being made now that having programming skills and the time to put them to use is no longer a bottleneck for making games.

Data analysis is another thing where the productivity multiplier can be very high and I can do all sorts of things I never would've done. As I've mentioned in a number of my last posts, I have way too many of these projects to really be able to write them up, even when attempting to write very quickly and bash out posts in half an hour apiece.

When I've talked to people about their one-off tooling, there's a lot of fun stuff people have done. For example, here's something Peter Geoghegan mentioned a month or two back:

> I had Fable implement a custom Neovim Lua function that formats code according to my very specific preferences. This is both something I don't want to maintain myself and inherently a Rube Goldberg device. Theoretically I could accomplish the same outcome in a principled way by patching clang-format, but my requirements are so exact that I think that approach would never be satisfactory.
> 
> We use a tool call pgindent, which is our fork of bsd\_indent. You can approximate the same formatting rules using clang-format, but that isn't good enough. If I commit something that isn't perfectly formatted/indented according to pgindent, I get a CI failure that I'm expected to fix quickly -- something I'd really prefer to avoid ...
> 
> Practically speaking, getting slick, clang-format-style formatting that avoids nag emails about misindented code requires a total architectural mess (I _also_ don't want to spend the time developing a principled approach, but that's really a separate issue). The function allows me to effortlessly format a given block of code from Neovim, similar to the clang-format LSP integration. I'm being unreasonably fussy here, of course, but I find that LLMs allow me to be this exacting about tooling.
> 
> The function performs multiple passes: an initial formatting pass using clang-format/clangd, and a separate formatting pass using pgindent. I need it to do both because clang-format handles some cases correctly that pgindent misses. This is brittle because I only want to format the code within a range of lines selected via block visual mode (I don't want to run clang-format on code not added by my patch). This conflicts with pgindent's design; it can only format whole C files.
> 
> Figuring out which relevant subset of the temp whole file buffer needs to be copied back into my working buffer is nontrivial. The initial line range I selected doesn't directly map to the affected C AST elements. So the function uses tree-sitter to intelligently delineate the exact subset of the temp indented C code that needs to be copied back. The rules need to be fuzzy in exactly the right way for cases where my selection straddles the same block of code. There are a bunch of edge cases.
> 
> Another complicating factor is that pgindent relies on a typedef file generated with objdump to identify types; without that file, the formatting looks wonky. The formatting function dynamically generates any extra typedefs from clangd, for that one file, so I don't have to worry about a stale typedef file (I might have created a new struct seconds before running the formatting tool, I don't want to run objdump on the whole postgres binary each time, that'd blow up latency).
> 
> This appears to work perfectly. The latency is totally acceptable. I have only a vague understanding of how all this works, though. I don't even know Lua. This will probably continue to work, even as further changes are made to our fork of bsd\_indent that somewhat alter how code is formatted, which happens from time to time.
> 
> I'm skeptical of the saaspocalypse. But I do think that LLMs are writing a lot of useful software that would have been insanely uneconomical to write any other way. There's an interesting small subset of software that'd be impossibly tedious for any human to maintain, relative to the value that it creates.

I think these kinds of examples are interesting and they point to where the industry will be in the not-so-far future, but what you can do with unlimited tokens, while relying on other infrastructure and tooling built with unlimited tokens doesn't tell you much about what you can accomplish today without unlimited funds. Projects like pgrust as well as projects that people I know do in their spare time (of which I've probably mentioned something like 1%—there are just a lot of these, like David Turner creating an ad skipper for podcasts that's "works for me" quality that works better than anything he could find, [the spare-time projects Dennis Snell mentioned here](https://fluffyandflakey.blog/2026/10/19/radical-explorations/), etc.) are more representative of what you can do today.

Of course there are extreme examples like MongoDB, which disputed correctness issues for years despite Kyle Kingsbury repeatedly showing that the anecdotes people had about data corruption were real. For an example that's more typical, a friend of mine worked as an early employee for a database startup. Their webpage bragged about doing some huge number of QPS. On testing it, my friend found that the claim was off by multiple orders of magnitude and suggested that the webpage get changed. The founder disagreed because they were going to hit the performance numbers, so it was still a true claim. After multiple years of performance improvements, the company eventually reduced the claim by one order of magnitude and they can still only hit that number with a very contrived, unrealistic, workload. This is, unfortunately, pretty normal for a company peddling a product based on its performance. By contrast, when I look at the pgrust discord to see what Malis is saying about performance, here's his most recent message:

    > Right now, the best way to help is to find bugs and performance issues in 0.4-beta. The new query engine is very fast on some workloads, but it causes performance regressions on others, and it doesn't support some more complex queries. We're trying to track down everything that's either slower than Postgres or errors out. It's not an easy thing to do given the massive space of queries you can run
    > 
    > We want to fix these things before the general release of 0.4-beta. Off the top of my head, there was a big performance regression in very fast queries. This is because we primarily optimized the new query engine for large-scale OLAP-like workloads. I'm doing optimization work to fix the very slow queries. I don't think there's any fundamental reason why the new engine should be slower than the previous one for fast queries

    Even though he was a founder and exec of a successful startup prior to starting the pgrust project, he never really got into the mindset that most founders seem to, where they seem to be able to say anything and believe anything they say. You might say this is a low bar, and I'd agree, but I still think it's rare and it's why I trusted what he says about pgrust without looking into it and also why, when I looked into it, his claims seem to be borne out by reality.
