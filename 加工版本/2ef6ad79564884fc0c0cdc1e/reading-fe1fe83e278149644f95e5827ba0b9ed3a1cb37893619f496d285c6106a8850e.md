# PCA 并非万能药｜PCA is not a panacea

---

## 正文

今年早些时候，我去一家知名的 tech startup 面试；它是数百家声称自己的面试比 Google[1](https://danluu.com/linear-hammer/#fn:1) 更难、工作更有挑战性、员工更聪明的公司之一。第一位面试官 John 按惯例带我参观了一圈：摆满健康零食和糖果的迷你厨房；围在桌上足球台旁的二十多岁白人男性；采用可爱主题的明亮空间；用来玩电子游戏的巨型电视；还有洗手间。最后，他带我看了一间壁橱大小的会议室，我们开始谈正事。

走完惯常的 data structures 和 algorithms 那套过场后，我们进入了主要问题：你会如何为 foo[2](https://danluu.com/linear-hammer/#fn:2) design 一个 classification system？我们讨论了 design tradeoffs，但主要分歧在于 algorithm。我说，如果必须在面试中 code 出点什么，我会 use 一个 naive matrix factorization algorithm，但我不指望能得到很好的 results，因为并不是所有东西都能轻易被 decomposed。John 不同意——他坚称 PCA 是任何 classification problem 的 solution。

我们讨论了二十五分钟的 mathematical underpinnings——占面试所分配时间的一半——随后显然，我们谁也无法用 theory 说服对方。我换了个方向，尝试 empirical approach，提到了一个以前的 result，它比较了用 LSA（它只能 capture words 之间的 pairwise correlations）[3](https://danluu.com/linear-hammer/#fn:C) 与 deep learning[4](https://danluu.com/linear-hammer/#fn:B) 来 classifying text 的情况。下面是用 LSA 得到的结果：

![二维 LSA](https://danluu.com/images/linear-hammer/PCA.webp)

每种 color represents 一种不同的 text type，它们被 projected down 到 two dimensions；你或许不想把 dimensionality reduce 得那么多，但这是 visualize 当前情况的好办法。不同 categories 之间存在一定的 separation；green dots 往往位于 bottom right，black dots 在 diagram 的 top half 要 denser 得多，等等。但当 documents 是 similar、彼此的 differences 又很 nuanced 时，任何基于此的 classification 都根本不会很好。

下面是我们用 deep autoencoder 得到的结果：

![二维 deep autoencoder](https://danluu.com/images/linear-hammer/deep_autoencoder.webp)

它并不完美，但 results 好得多。

即便给出了这个 example，显然我仍无法与面试官达成一致，所以我问能否保留分歧，继续下一个话题。这没什么大不了的，毕竟只是一次面试。但在面试之外，我每月至少会看到一次对极其普通的 methods 的这种 misapplication，而且当事人通常坚信，无论遇到什么 problem，只需要 apply 这个 linear technique 就行。

当只有泛泛的 business knowledge 的 consultants 登门，以 $500/hr 收费，给出常识性的建议，却把细节搞得一团糟时，Engineers 总是最先抱怨的人。但 data science 足够新、足够热门，以至于人们只要自称 data scientists 而不是 technology consultants，就能蒙混过关。我并不是要贬低 data science（不管它是什么意思），甚至也不是要贬低 linear methods[5](https://danluu.com/linear-hammer/#fn:D)。它们很有用。但我总是看到有人试图把同样四种 linear methods apply 到眼前的每一个 problem 上。

事实上，就在我写这篇文章时，我女朋友正在另一个房间，接受一家大公司的 data science 团队的电话面试。他们正试图 use multivariate regression 来 predict 其 systems 的 performance，并根据 regression coefficient，把 resource utilization decomposing 到 application 和 query level，得到诸如 foobar 的 4000 QPS uses 18% 的 CPU 这样的 results。他们问她的问题，也是他们目前正在研究的问题，是如何 speed up 这个 regression，以便把他们的 test system 推到 web scale？

真正的问题是，你为什么要这么做？几乎每门研究生入门级的 computer architecture 课程都涉及 writing 或 modifying 一个 simulator，这是有原因的；真实的 system performance 充满了 non-linear cliffs，对于这类情况，你不能仅仅 apply 一个 queuing theory model，更不用说 linear regression model 了。但当你手里只有 linear 锤子时，non-linear 螺丝看起来也很像钉子。

_对此，John Myles White 提出了一个很好的观点：linear 与 non-linear 的对比其实并不是恰当的 framing，而且实际上也没有很好的 vocabulary 来谈论这类事情。抱歉，我对 terminology 的使用不够严谨。如果你想更 precise，可以把每一处提到的 "linear" 换成 "含含糊糊的 objective function"，或者也许换成 "simple"。_

## 原文

Earlier this year, I interviewed with a well-known tech startup, one of the hundreds of companies that claims to have harder interviews, more challenging work, and smarter employees than Google[1](https://danluu.com/linear-hammer/#fn:1). My first interviewer, John, gave me the standard tour: micro-kitchen stocked with a combination of healthy snacks and candy; white male 20-somethings gathered around a foosball table; bright spaces with cutesy themes; a giant TV set up for video games; and the restroom. Finally, he showed me a closet-sized conference room and we got down to business.

After the usual data structures and algorithms song and dance, we moved on to the main question: how would you design a classification system for foo[2](https://danluu.com/linear-hammer/#fn:2)? We had a discussion about design tradeoffs, but the key disagreement was about the algorithm. I said, if I had to code something up in an interview, I'd use a naive matrix factorization algorithm, but that I didn't expect that I would get great results because not everything can be decomposed easily. John disagreed – he was adamant that PCA was the solution for any classification problem.

We discussed the mathematical underpinnings for twenty-five minutes – half the time allocated for the interview – and it became clear that neither of us was going to convince the other with theory. I switched gears and tried the empirical approach, referring to an old result on classifying text with LSA (which can only capture pairwise correlations between words)[3](https://danluu.com/linear-hammer/#fn:C) vs. deep learning[4](https://danluu.com/linear-hammer/#fn:B). Here's what you get with LSA:

![2-d LSA](https://danluu.com/images/linear-hammer/PCA.webp)

Each color represents a different type of text, projected down to two dimensions; you might not want to reduce to the dimensionality that much, but it's a good way to visualize what's going on. There's some separation between the different categories; the green dots tend to be towards the bottom right, the black dots are a lot denser in the top half of the diagram, etc. But any classification based on that is simply not going to be very good when documents are similar and the differences between them are nuanced.

Here's what we get with a deep autoencoder:

![2-d deep autoencoder](https://danluu.com/images/linear-hammer/deep_autoencoder.webp)

It's not perfect, but the results are a lot better.

Even after the example, it was clear that I wasn't going to come to an agreement with my interviewer, so I asked if we could agree to disagree and move on to the next topic. No big deal, since it was just an interview. But I see this sort of misapplication of bog standard methods outside of interviews at least once a month, usually with the conviction that all you need to do is apply this linear technique for any problem you might see.

Engineers are the first to complain when consultants with generic business knowledge come in, charge $500/hr and dispense common sense advice while making a mess of the details. But data science is new and hot enough that people get a pass when they call themselves data scientists instead of technology consultants. I don't mean to knock data science (whatever that means), or even linear methods[5](https://danluu.com/linear-hammer/#fn:D). They're useful. But I keep seeing people try to apply the same four linear methods to every problem in sight.

In fact, as I was writing this, my girlfriend was in the other room taking a phone interview with the data science group of a big company, where they're attempting to use multivariate regression to predict the performance of their systems and decomposing resource utilization down to the application and query level from the regression coefficient, giving you results like 4000 QPS of foobar uses 18% of the CPU. The question they posed to her, which they're currently working on, was how do you speed up the regression so that you can push their test system to web scale?

The real question is, why would you want to? There's a reason pretty much every intro grad level computer architecture course involves either writing or modifying a simulator; real system performance is full of non-linear cliffs, the sort of thing where you can't just apply a queuing theory model, let alone a linear regression model. But when all you have are linear hammers, non-linear screws look a lot like nails.

_In response to this, John Myles White made the good point that linear vs. non-linear isn't really the right framing, and that there really isn't a good vocabulary for talking about this sort of thing. Sorry for being sloppy with terminology. If you want to be more precise, you can replace each mention of "linear" with "mumble mumble objective function" or maybe "simple"._
