# 构建多久会出一次故障？｜How often is the build broken?

---

## 正文

我注意到，open source projects 中 builds 出现 broken、tests 出现 fail 的频率，比“工作”中的 projects 高得多。我不确定这在多大程度上是我的感觉，又在多大程度上是实际情况，所以我获取了 GitHub 上几个热门 categories 的 Travis CI data[1](https://danluu.com/broken-builds/#fn:C)。

![build reliability 的 Graph。向 nu、oryx、caffe、catalyst 和 Scala 致敬。](https://danluu.com/images/broken-builds/reliability.webp)

作为参考，在我工作过的每个地方，build 的 reliability 如果是两个 9（99% uptime），都会被认为很糟糕。这意味着 build 每年有超过三天半的时间处于 failing 状态，或者每月七个小时。即使是三个 9（99.9% uptime），每月也有大约四十五分钟的 downtime。如果没有严格的 system 来 prevent 人们 checking in bad code，这还算过得去，但对于认真对待 working builds 的地方来说，这就相当糟糕了。

相比之下，对于我获取了 data 的那些 projects[2](https://danluu.com/broken-builds/#fn:B)，2 个 9 的 reliability 远高于 average -- 40 个 projects 中只有 8 个如此 reliable。几乎两倍数量的 projects -- 40 个中的 15 个 -- 甚至达不到一个 9 的 uptime。而且，我的 sample 严重 biased，偏向 reliable projects。其中的 projects 知名度已经高到足以被 GitHub 的人工精选列表列为“featured”。这本身就已经使 data 存在 biases。然后，我又只获取了那些足够重视 testing、因而 set up TravisCI 的 projects 的 data[3](https://danluu.com/broken-builds/#fn:1)，这引入了更强的 bias。

为了确保自己没有获取不好的 samples，我 removed 了最初所有成组出现的 failing tests（人们尝试 set up Travis 却将其 misconfigured 时，通常会有很多 fails），也 removed 了那些使用另一个 system 来 tracking builds、只是顺带使用 Travis 的 projects（例如 Rust）[4](https://danluu.com/broken-builds/#fn:T)。

为什么工作中的 build 不会总是 fail？Engineers 不喜欢等待别人来 unbreak build，而 managers 可以做一个 back of the envelope calculation：N 个 idle engineers \* X 小时的 build breakage = $Y 的金钱浪费。

但同样的 logic 也适用于 open source projects！只不过，浪费的不是钱，而是 contributor 的时间。

Web programmers 非常清楚，web page load 时额外 100ms 的 latency 会对 conversion rate 产生明显的 effect。那么，当你的 project 的一位潜在 contributor 花了 20 分钟 installing dependencies，又花了一个小时 building 你的 project，最后却发现 build 是 broken 时，这会对 conversion rate 产生什么 effect？

过去，我会深入排查这些 failures 来 find bug，通常会认为这一定是我的 machine 特有的某个 configuration issue。但在花了多年时间 debugging 我在 clean build 上使用 `make check` 时遇到的 failures 后，我发现，很多时候只不过是有人 checked in bad code。如今，如果我正考虑 contributing 给某个 project，或尝试 fix 一个 bug，而 build 无法 work，我就会转去另一个 project。

经常出现的 build failures 最糟糕的一点在于，它们很容易[5](https://danluu.com/broken-builds/#fn:E) prevent。Graydon Hoare 确实把 keeping a clean build 称为“[not rocket science rule](http://graydon2.dreamwidth.org/1597.html)”，还编写了一个任何人都能用来做这种不需要高深学问之事的 open source tool（bors）。然而，大多数 open source projects 仍然忍受着 broken 和 failed builds，以及由此造成的 developer 时间损失和 developer “conversions”损失。

请不要过度解读 graph 中个别的 data。我觉得很有意思的是，DevOps projects 往往比 languages 更 reliable，而 languages 又往往比 web frameworks 更 reliable；ML projects 则各种情况都有（不过大多数是 reliable 的）。但就个别 projects 而言，各种各样的事情都可能导致一个 project 的 numbers 不好看。

感谢 Kevin Lynagh、Leah Hanson、Michael Smith、Katerina Barone-Adesi 和 Alexey Romanov 提供意见。

另外，也向 Puppetlabs 的 Michael Smith 致谢：他友善地联系了我，并一起仔细检查 puppet 的 build data，以确保我的 scripts 中没有 bug。这是我遭受诟病最多的 blog posts 之一，因为没有人愿意相信，自己 project 的 build 比其他 projects 的 build 更经常出现 broken。但尽管通过本文中的 links，获取一个 project 的 data 并对其进行 sanity check 只需要大约一分钟，真正和我一起仔细检查 data 的却只有一个人；与此同时，一大群人连 data 都没有 checking 过，就告诉我它显然一定是 incorrect 的。

这并不是说我没有任何 bugs。这是一个匆忙完成的 hack，很可能有 bugs，而且我始终很乐意收到 bugreports！但有些被反复 reported 的 non-bugs 包括：获取的是所有 branches 的 data，而不是 main branch 的；获取的是所有 PRs 的 data，而不仅仅是实际上 checked in 到 main branch 的 code 的；以及使用的是 failed builds 的数量，而不是 build 处于 down 状态的时间长度。我相当确定，你只需要花上与提出这些 claims 差不多的时间，就能 check 其中任何一个 claim 是 false 的，但这并没有阻止人们继续提出这些 claim。

## 原文

I've noticed that builds are broken and tests fail a lot more often on open source projects than on “work” projects. I wasn't sure how much of that was my perception vs. reality, so I grabbed the Travis CI data for a few popular categories on GitHub[1](https://danluu.com/broken-builds/#fn:C).

![Graph of build reliability. Props to nu, oryx, caffe, catalyst, and Scala.](https://danluu.com/images/broken-builds/reliability.webp)

For reference, at every place I've worked, two 9s of reliability (99% uptime) on the build would be considered bad. That would mean that the build is failing for over three and a half days a year, or seven hours per month. Even three 9s (99.9% uptime) is about forty-five minutes of downtime a month. That's kinda ok if there isn't a hard system in place to prevent people from checking in bad code, but it's quite bad for a place that's serious about having working builds.

By contrast, 2 9s of reliability is way above average for the projects I pulled data for[2](https://danluu.com/broken-builds/#fn:B) -- only 8 of 40 projects are that reliable. Almost twice as many projects -- 15 of 40 -- don't even achieve one 9 of uptime. And my sample is heavily biased towards reliable projects. There are projects that were well-known enough to be “featured” in a hand curated list by GitHub. That's already biases the data right there. And then I only grabbed data from the projects that care enough about testing to set up TravisCI[3](https://danluu.com/broken-builds/#fn:1), which introduces an even stronger bias.

To make sure I wasn't grabbing bad samples, I removed any initial set of failing tests (there are often a lot of fails as people try to set up Travis and have it misconfigured) and projects that that use another system for tracking builds that only have Travis as an afterthought (like Rust)[4](https://danluu.com/broken-builds/#fn:T).

Why doesn't the build fail all the time at work? Engineers don't like waiting for someone else to unbreak the build and managers can do the back of the envelope calculation which says that N idle engineers \* X hours of build breakage = $Y of wasted money.

But that same logic applies to open source projects! Instead of wasting dollars, contributor's time is wasted.

Web programmers are hyper-aware of how 100ms of extra latency on a web page load has a noticeable effect on conversion rate. Well, what's the effect on conversion rate when a potential contributor to your project spends 20 minutes installing dependencies and an hour building your project only to find the build is broken?

I used to dig through these kinds of failures to find the bug, usually assuming that it must be some configuration issue specific to my machine. But having spent years debugging failures I run into with `make check` on a clean build, I've found that it's often just that someone checked in bad code. Nowadays, if I'm thinking about contributing to a project or trying to fix a bug and the build doesn't work, I move on to another project.

The worst thing about regular build failures is that they're easy[5](https://danluu.com/broken-builds/#fn:E) to prevent. Graydon Hoare literally calls keeping a clean build the “[not rocket science rule](http://graydon2.dreamwidth.org/1597.html)”, and wrote an open source tool (bors) anyone can use to do not-rocket-science. And yet, most open source projects still suffer through broken and failed builds, along with the associated cost of lost developer time and lost developer “conversions”.

Please don't read too much into the individual data in the graph. I find it interesting that DevOps projects tend to be more reliable than languages, which tend to be more reliable than web frameworks, and that ML projects are all over the place (but are mostly reliable). But when it comes to individual projects, all sorts of stuff can cause a project to have bad numbers.

Thanks to Kevin Lynagh, Leah Hanson, Michael Smith, Katerina Barone-Adesi, and Alexey Romanov for comments.

Also, props to Michael Smith of Puppetlabs for a friendly ping and working through the build data for puppet to make sure there wasn't a bug in my scripts. This is one of my most maligned blog posts because no one wants to believe the build for their project is broken more often than the build for other projects. But even though it only takes about a minute to pull down the data for a project and sanity check it using the links in this post, only one person actually looked through the data with me, while a bunch of people told me how it must quite obviously be incorrect without ever checking the data.

This isn't to say that I don't have any bugs. This is a quick hack that probably has bugs and I'm always happy to get bugreports! But some non-bugs that have been repeatedly reported are getting data from all branches instead of the main branch, getting data for all PRs and not just code that's actually checked in to the main branch, and using number of failed builds instead of the amount of time that the build is down. I'm pretty sure that you can check that any of those claims are false in about the same amount of time that it takes to make the claim, but that doesn't stop people from making the claim.
