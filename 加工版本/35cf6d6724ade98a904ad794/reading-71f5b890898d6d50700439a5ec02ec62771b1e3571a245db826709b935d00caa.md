# 一切都坏了｜Everything is broken

---

## 正文

如果非要我猜，我会说，平均一周里，我大概会 work around 数百个 bugs，糟糕的一周则有数千个。我在一周内遇到一百个此前没见过的 bugs，并不稀奇。但当我提到自己每天都会遇到多个（对我而言）新的 bugs，而且如果我们不改变 write tests 的方式，这就是不可避免的，往往会遭到怀疑。好吧，下面是一周的 bugs 记录，仅限于那一周我第一次遇到的 bugs。简要描述这些 bugs 之后，我会谈谈我们能做些什么来改善这种状况。显而易见的答案是在 testing 上投入更多精力，但大家早就知道应该这样做，却没人去做。不过，这并不意味着毫无希望。

### 一周的 bugs

#### Ubuntu（操作系统）

在 logging into 我的 machine 时，我看到一个 screen，上面说我 entered password 时出了错。经过五秒的 delay 后，它却还是把我 logged me in 了。这大概至少是两个 bugs，或许更多。

#### GitHub（代码托管平台）

GitHub 从 Pygments switched 到了他们给 Atom 用的某个东西，[使大多数 languages 的 syntax highlighting 出现 breaking](http://www.greghendershott.com/2014/11/github-dropped-pygments.html)。HN 上对此的 comments 表明，受影响的不只是 obscure languages；Java、PHP、C 和 C++ 都有明显的 breakage。

[在一个 GitHub issue 中](https://github.com/github/linguist/issues/1717)，一位 GitHub developer 说：

> 你当然可以自由地 fork 这个 Racket bundle，并按自己的想法改进它。恐怕 GitHub 没有人使用 Racket，所以我们无法判断 proper highlighting 应该是什么样。不过，凭借 O P E N S O U R C E 的魔力，我们当然会 pull 你的 changes。

另一位 GitHub 员工最近刚做过一场题为[“快速行动，什么也别弄坏”](http://zachholman.com/talk/move-fast-break-nothing/)的主题演讲，现在这样说，多少有些讽刺。更别提这办法多半行不通。上一次我向 linguist submitted 一个 PR，直到我写了[一篇 blog post，指出他们有 100s 个 open PRs，其中一些已经搁置了一年](https://danluu.com/discourage-oss/)，它才被 merged；那篇文章登上 reddit 后，他们才 merge 了一批 PRs。据我所见，“O P E N S O U R C E 的魔力”，其实是登上 reddit/HN 首页或拥有大批 twitter followers 的魔力的暗语。

另外，icons 也曾 broken 了一阵子。那是在刚过去的这一周吗？

#### LinkedIn（职业社交平台）

回复某人的“InMail”后，我过了几天又查看了一下，发现对方原来的 message 仍被 listed 为 unread（没有 reply）。它究竟有没有 send 我的 reply？我完全不知道，直到对方回复了我。

#### Inbox（收件应用）

Inbox app（不要和 Inbox App 混淆）会在真正 downloads 一条 message 之前，就 notifies 你有一条新 message。过多久 app 本身才能收到这条 message，完全没个准数，而且在 app 中 refreshing 也不会让这条 message download。

notifications 的另一个问题是，收到 message 时，它们有时并不出现。我收到 gmail app 的 notification 时，大约有一半的情况也会收到 Inbox app 的 notification。另一半情况下，notification 就被 dropped 了。

总的来说，收到 notification 后真能读到相应 message 的情况，大概只有 1/3。

#### Google Analytics（分析服务）

U.S. 附近的一些 locations（例如 Mexico City 和 Toronto），似乎不配拥有自己的 country。location map 把这些 cities 显示在 U.S. 外面的蓝色 ocean 中。

#### Octopress（博客系统）

如果你允许 main page 上显示 posts（而不是 index），并使用 syntax 把部分内容放在 below the fold，那么 Footnotes 在 main page 上就不会 work correctly。你得到的不是 linking 到 footnote 的链接，而是一个 reference，指向哪儿也去不了的 anchor text。这还不算我早就知道的另一个 footnote bug。

Tags 只在某些 contexts 中被 downcased，在其他 contexts 中却不会，这意味着任何带 capitalized letters 的 tags（有时）都不会 work correctly。我甚至不用 tags，但在别人的 blog 上注意到了这个问题。

我的 Atom feed [不能 work correctly](https://twitter.com/chmaynard/status/534540677078855680)。

如果你认为 performance bugs 也算问题，那么我在刚过去的一周里注意到的这类问题实在太多，以至于它们[单独占了一篇 blog post](https://danluu.com/octopress-speedup/)。

#### Running with Rifles（Game，游戏）

本该 stun 的 Weapons 反而会 injure 你。直到有人提到下一个 version 会把它 fixed，我才意识到这是个 bug。

你可以隔着 walls stab 别人。

如果 level changes 时你正 holding 一个 key，那么在下一个 level 中，你的 character 会一直连续执行那个 action，即使你已经 released 了这个 key。

你的 character 的 position 会 randomly 与 server get out of sync。发生这种情况时，我找到的唯一 reliable fix 就是 randomly shoot 一阵子。看来 shooting 会使 client 做出类似向 server send 一份你的 position 的 snapshot 这样的事？不明白为什么不直接定期这样做。

Vehicles 可能 randomly spawn 在你头顶，把你 killing。

你可能 randomly spawn 在一辆 vehicle 下面，把自己 killing。

AI teammates 在 throwing grenades 时不考虑 walls 或 buildings，因此经常导致它们 kill themselves。

Grenades 有时会 damage 你上一次乘坐的 vehicle，即使你离那辆 vehicle 很远。

AI vehicles 几乎能在任何 obstacle 上 get permanently stuck。

这是我大约 15 年来玩的第一个 video game。我通常觉得 games 相当 reliable，但这大概是因为 15 年前的 games 要简单得多。MS Paint 也没有多少 bugs。

更新：上面的 sync issue 是由 memory leaks caused 的。我最初以为，这个 game 只是 online play code 写得很糟糕，但后来发现，在 server restart 后的头 6 hours 左右，它其实还可以。有些 scripts 可以定期 restart 这些 servers，但它们有时也有 bugs，会导致它们 stop running。如果这种事发生在 official servers 上，这个 game 基本就变得 unplayable online 了。

#### Julia（编程语言）

Unicode sequence 会 causes match/ismatch 因 bounds error 而 blow up。

Unicode sequence 会 causes 把 string 用作 hash index 的操作因 bounds error 而 blow up。

Exception 会 randomly 不被 catch 所 caught。这很糟糕，因为把东西放进 try/catch 原本是上面两个 bugs 的 workaround。我以前见过它的其他 variants；这也许不该算一个新 bug，因为它可能和我见过的某个 bug 有相同的 root cause。

某个 Function（我忘了是哪个）在被给定 bad length arguments 时，会 returns 完全 wrong results。你甚至可以给它 wrong type 的 length arguments，它仍然会“work”，而不是 throwing an exception 或 returning an error。

如果 API design bugs 也算，那么对 iterables 进行 operation 的 methods，有时把这些东西 take 为 first argument，有时却不是。这类情况实在太多，没法逐一列出。举个例子，`match` 先 takes 一个 regex，再 takes 一个 string，而 `search` 先 takes 一个 string，再 takes 一个 regex。这一周，我在一个 numerical function 上被类似的问题坑了一次。

当然，我仍然在遇到那个[已经存在 1+ 个月、会 breaks convert 的 bug](https://github.com/JuliaLang/julia/issues/8631)，它的影响如此 pervasive，以至于任何触发它的事情都会 renders Julia unusable。

还有一个可能是 OS X bug？我写了些 bad code，导致某些 Julia code 中出现 infinite loop。那个 `while` loop 里实际上什么都没发生，所以它只会一直 run 下去。糟糕。这个 bug 在于，这不知怎么竟然导致我的 system run out of memory，并变得 unresponsive。Activity monitor 显示，kernel 占用的 memory 越来越多；我 killed 那个 Julia process 后，这些占用就消失了。

我就不列 packages 中的 bugs 了，因为太多。即便只说 core Julia，我遇到的 Julia bugs 也已经多到让我不再 file bugs。这实在太打断事情了。等有时间，我应该花一天把记得的所有 bugs 都 filing 一遍，但我觉得，为每一个 bug 写出一份像样的、reproducible 的 bug report，真的会花掉整整一天。

关于我为什么会遇到这么多 Julia bugs，更多内容请看[这篇文章](https://danluu.com/julialang/)。

### WAT（什么鬼）

> 我心情超级好。一切仍然是 broken 的，但现在这让我觉得好笑，而不是生气。
> 
> — Gary Bernhardt (@garybernhardt) [2013 年 1 月 28 日](https://twitter.com/garybernhardt/status/296033898822004738)

这到底是怎么回事？有些 software 实在太 buggy，列出其中所有 bugs 会让这篇文章的长度变成三倍，所以我没有列出；如果把这些 bugs 也算上，那就是一周大约 80 个 bugs。而这还只算我以前没见过的 bugs。为什么所有东西里都有这么多 bugs？

对于这种评论，一个常见回应是：这是 open source，你这个不知感恩的家伙，为什么不自己 fix 那些 bugs？我确实会 fix 一些 bugs，但一周的时间真的不够我去 debug 并 fix 遇到的每一个 bug。这里有一种 tragedy of the commons effect。如果只有少数几个 bugs，developers 很可能会 fix 自己遇到的 bugs。但如果 bugs 多到连取得一点进展都毫无希望，很多人就懒得费这个劲了。

我打算看看 Julia，因为我已经熟悉它，不过我估计它在 tested 方面，既不会比这里其他大多数 projects 更好，也不会更差（Chrome 除外，它是 relatively well tested）。粗略衡量投入了多少 test effort，可以看它有 18k 行 test code。但与之相对的是，`src` 加上 `Base` 中大约有 108k 行 code。

在我工作过的每个地方，一个 2k LOC 的 prototype，即使只是为了让你取得 preliminary performance numbers，或许再试用一下 API，也应该至少有同样数量的 tests；否则，你怎么知道它没有 broken 到让你的 performance estimates 偏差一个 order of magnitude 的地步？由于 complexity 并不会随 LOC 而 scale linearly，随着 prototype 变大，大家会期待多得多的 test code。

用 18k LOC 的 tests 对应 108k LOC 的 code，users 肯定会 find bugs。大量的 bugs。

按理说，写到这里，我应该呼吁大家更认真地对待 testing，并[真正为它投入精力](https://danluu.com/empirical-pl/#fn2)。但我们都知道，这不会奏效。需要 90k LOC 的 tests，才能让 Julia 达到一个 poorly tested prototype 那样的 tested 程度（这里还错误地假设了 complexity 与 size 呈 linear 关系）。那是 two person-years 的工作量，甚至还没算上 debug 和 fix bugs 的时间（算上之后，很可能更接近四五年）。谁会去做呢？没有人。Writing tests 就像 writing documentation。每个人都已经知道应该做。告诉人们应该做，并没有增加任何 information[1](https://danluu.com/everything-is-broken/#fn:D)。

既然人们不会在 testing 上投入什么精力，那么最好的办法是什么？

Property-based testing。Generative testing。Random testing。Concolic Testing（早在这个 term 被创造出来之前，就已经有人在做了）。Static analysis。[Fuzzing](https://danluu.com/everything-is-broken/)。[Statistical bug finding](https://danluu.com/bugalytics/)。有很多选择。其中有些实际上是同一回事，因为我们使用的 terminology 是 inconsistent 而且 buggy 的。我会随意挑一个来谈，但它们都值得研究。

不过，人们往往会被这些东西吓住。我听过很多介绍它们的演讲，而这些演讲常常让它们听起来特别难。[Csmith](http://embed.cs.utah.edu/csmith/) 有 40k LOC。[American Fuzzy Lop](https://code.google.com/p/american-fuzzy-lop/) 的 compile-time instrumentation 足够聪明，能够 [generate valid JPEGs](http://lcamtuf.blogspot.com/2014/11/pulling-jpegs-out-of-thin-air.html)。在 exploration 方面，[Sixth Sense](http://researcher.watson.ibm.com/researcher/view_group_subpage.php?id=2989) 拥有与 American Fuzzy Lop 同样的 intelligence，此外还 uses symbolic execution 来 exhaustively explore state space 的很大一部分；如果它能够充分 collapse state space，从而对其 exhaustively search，就会 formally verify 你的 asserts 确实 hold，否则它只会尝试通过 covering 不同的 paths 和 states，取得尽可能好的 test coverage。此外，它还会 use symbolic equivalence checking，来相互 check 你的 code 的不同 versions。

这些确实都很了不起，但做这些事情并不需要一个 formal methods PhD。你可以在一个小时内 write 一个能 shake out 很多 bugs 的 fuzzer[2](https://danluu.com/everything-is-broken/#fn:T)。真的。放上这个链接让我有点不好意思，不过[这个 fuzzer](https://github.com/danluu/Fuzz.jl) 大约只花了一个小时就写出来了，并 found 20-30 个 bugs[3](https://danluu.com/everything-is-broken/#fn:R)，包括 incorrect code generation，以及 multiplication 和 exponentiation 这类 basic operations 上的 crashes。我猜，再花 2-3 个小时，就能再 shake out 20-30 个 bugs（加入对更多 types 的 support）；再花一天，或许又能找到 20-30 个（加入对 random expressions 的 very basic support）。我提它，不是因为它好。它并不好。它简直糟透了。但这正是重点所在。你可以花一个小时拼凑出一个荒唐的 hack，结果它却相当有用。

与手工 writing unit tests 相比：即使我事先知道 bugs 是什么，也很难 code 得足够快，快到能在一个小时内 generate 30 个 bugs。一天 30 个 bugs？当然可以，但前提是我事先已经知道 bugs 是什么。这不是说 unit testing 没有价值，而是说，如果你打算花几个小时 writing tests，那么花几个小时 writing 一个 fuzzer，会比花几个小时 writing unit tests 更有效。你打字也许能达到每分钟 100 words，但你的 CPU 轻轻松松就能每分钟 execute 200 billion instructions。这根本没得比。

Write 一个 fuzzer 究竟需要什么？嗯，你需要为一个 program generate random inputs。在[这个例子](https://github.com/danluu/Fuzz.jl)中，我们是在某个 namespace 中 generating random function calls。很简单。之所以花了一个小时，只是因为我对 Julia 的 reflection capabilities 理解得还不够，没法轻松 generate random types，结果只能手工 writing 那些 type generation 的东西。

这适用于许多不同 types 的 programs。有 GUI？随意戳一戳 random UI elements 相当容易。会从 network 上 Read files 或其他东西？Generating（或 mutating）random data 很直接。这是谁都能做的事。

但这并不是万能药。漫不经心的 testing 意味着[你的 users 将会 find bugs](https://danluu.com/cpu-bugs/)。不过，即使 developers 花在 testing 上的时间远远不够，我们依然可以比现在做得好得多。

## 原文

If I had to guess, I'd say I probably work around hundreds of bugs in an average week, and thousands in a bad week. It's not unusual for me to run into a hundred new bugs in a single week. But I often get skepticism when I mention that I run into multiple new (to me) bugs per day, and that this is inevitable if we don't change how we write tests. Well, here's a log of one week of bugs, limited to bugs that were new to me that week. After a brief description of the bugs, I'll talk about what we can do to improve the situation. The obvious answer to spend more effort on testing, but everyone already knows we should do that and no one does it. That doesn't mean it's hopeless, though.

### One week of bugs

#### Ubuntu

When logging into my machine, I got a screen saying that I entered my password incorrectly. After a five second delay, it logged me in anyway. This is probably at least two bugs, perhaps more.

#### GitHub

GitHub switched from Pygments to whatever they use for Atom, [breaking syntax highlighting for most languages](http://www.greghendershott.com/2014/11/github-dropped-pygments.html). ### WAT

> I'm in a super good mood. Everything is still broken, but now it's funny instead of making me mad.
> 
> — Gary Bernhardt (@garybernhardt) [January 28, 2013](https://twitter.com/garybernhardt/status/296033898822004738)

What's going on here? If you include the bugs I'm not listing because the software is so buggy that listing all of the bugs would triple the length of this post, that's about 80 bugs in one week. And that's only counting bugs I hadn't seen before. How come there are so many bugs in everything?

A common response to this sort of comment is that it's open source, you ungrateful sod, why don't you fix the bugs yourself? I do fix some bugs, but there literally aren't enough hours in a week for me to debug and fix every bug I run into. There's a tragedy of the commons effect here. If there are only a few bugs, developers are likely to fix the bugs they run across. But if there are so many bugs that making a dent is hopeless, a lot of people won't bother.

I'm going to take a look at Julia because I'm already familiar with it, but I expect that it's no better or worse tested than most of these other projects (except for Chrome, which is relatively well tested). As a rough proxy for how much test effort has gone into it, it has 18k lines of test code. But that's compared to about 108k lines of code in `src` plus `Base`.

At every place I've worked, a 2k LOC prototype that exists just so you can get preliminary performance numbers and maybe play with the API is expected to have at least that much in tests because otherwise how do you know that it's not so broken that your performance estimates aren't off by an order of magnitude? Since complexity doesn't scale linearly in LOC, folks expect a lot more test code as the prototype gets bigger.

At 18k LOC in tests for 108k LOC of code, users are going to find bugs. A lot of bugs.

Here's where I'm supposed to write an appeal to take testing more seriously and [put real effort into it](https://danluu.com/empirical-pl/#fn2). But we all know that's not going to work. It would take 90k LOC of tests to get Julia to be as well tested as a poorly tested prototype (falsely assuming linear complexity in size). That's two person-years of work, not even including time to debug and fix bugs (which probably brings it closer to four of five years). Who's going to do that? No one. Writing tests is like writing documentation. Everyone already knows you should do it. Telling people they should do it adds zero information[1](https://danluu.com/everything-is-broken/#fn:D).

Given that people aren't going to put any effort into testing, what's the best way to do it?

Property-based testing. Generative testing. Random testing. Concolic Testing (which was done long before the term was coined). Static analysis. [Fuzzing](https://danluu.com/everything-is-broken/). [Statistical bug finding](https://danluu.com/bugalytics/). There are lots of options. Some of them are actually the same thing because the terminology we use is inconsistent and buggy. I'm going to arbitrarily pick one to talk about, but they're all worth looking into.

People are often intimidated by these, though. I've seen a lot of talks on these and they often make it sound like this stuff is really hard. [Csmith](http://embed.cs.utah.edu/csmith/) is 40k LOC. [American Fuzzy Lop](https://code.google.com/p/american-fuzzy-lop/)'s compile-time instrumentation is smart enough to [generate valid JPEGs](http://lcamtuf.blogspot.com/2014/11/pulling-jpegs-out-of-thin-air.html). [Sixth Sense](http://researcher.watson.ibm.com/researcher/view_group_subpage.php?id=2989) has the same kind of intelligence as American Fuzzy Lop in terms of exploration, and in addition, uses symbolic execution to exhaustively explore large portions of the state space; it will formally verify that your asserts hold if it's able to collapse the state space enough to exhaustively search it, otherwise it merely tries to get the best possible test coverage by covering different paths and states. In addition, it will use symbolic equivalence checking to check different versions of your code against each other.

That's all really impressive, but you don't need a formal methods PhD to do this stuff. You can write a fuzzer that will shake out a lot of bugs in an hour[2](https://danluu.com/everything-is-broken/#fn:T). Seriously. I'm a bit embarrassed to link to this, but [this fuzzer](https://github.com/danluu/Fuzz.jl) was written in about an hour and found 20-30 bugs[3](https://danluu.com/everything-is-broken/#fn:R), including incorrect code generation, and crashes on basic operations like multiplication and exponentiation. My guess is that it would take another 2-3 hours to shake out another 20-30 bugs (with support for more types), and maybe another day of work to get another 20-30 (with very basic support for random expressions). I don't mention this because it's good. It's not. It's totally heinous. But that's the point. You can throw together an absurd hack in an hour and it will turn out to be pretty useful.

Compared to writing unit tests by hand: even if I knew what the bugs were in advance, I'd be hard pressed to code fast enough to generate 30 bugs in an hour. 30 bugs in a day? Sure, but not if I don't already know what the bugs are in advance. This isn't to say that unit testing isn't valuable, but if you're going to spend a few hours writing tests, a few hours writing a fuzzer is going to go a longer way than a few hours writing unit tests. You might be able to hit 100 words a minute by typing, but your CPU can easily execute 200 billion instructions a minute. It's no contest.

What does it really take to write a fuzzer? Well, you need to generate random inputs for a program. In [this case](https://github.com/danluu/Fuzz.jl), we're generating random function calls in some namespace. Simple. The only reason it took an hour was because I don't really get Julia's reflection capabilities well enough to easily generate random types, which resulted in my writing the type generation stuff by hand.

This applies to a lot of different types of programs. Have a GUI? It's pretty easy to prod random UI elements. Read files or things off the network? Generating (or mutating) random data is straightforward. This is something anyone can do.

But this isn't a silver bullet. Lackadaisical testing means that [your users will find bugs](https://danluu.com/cpu-bugs/). However, even given that developers aren't going to spend nearly enough time on testing, we can do a lot better than we're doing right now.

1.  If I were really trying to convince you of this, I'd devote a post to the business case, diving into the data and trying to figure out the cost of bugs. The short version of that unwritten post is that response times are well studied and it's known that a 100ms of extra latency will cost you a noticeable amount of revenue. A 1s latency hit is a disaster. How do you think that compares to having your product not work at all?

    Compared to 100ms of latency, how bad is it when your page loads and then bugs out in a way that makes it totally unusable? What if it destroys user state and makes the user re-enter everything they wanted to buy into their cart? Removing one extra click is worth a huge amount of revenue, and now we're talking about adding 10 extra clicks or infinite latency to a random subset of users. And not a small subset, either. Want to stop lighting piles of money on fire? Write tests. If that's too much work, at least [use the data you already have to find bugs](https://danluu.com/bugalytics/).

    Of course it's sometimes worth it to light pile of money on fire. Maybe your rocket ship is powered by flaming piles of money. If you're a very rapidly growing startup, a 20% increase in revenue might not be worth that much. It could be better to focus on adding features that drive growth. The point isn't that you should definitely write more tests, it's that you should definitely do the math to see if you should write more tests.
