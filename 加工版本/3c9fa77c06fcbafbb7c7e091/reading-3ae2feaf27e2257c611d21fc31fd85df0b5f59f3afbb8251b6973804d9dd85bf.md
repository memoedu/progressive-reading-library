# 如何打击开源贡献的积极性｜How to discourage open source contributions

---

## 正文

当你在一个 open source project 中发现 bug 或看到缺少的 feature 时，你做的第一件事是什么？去看看 project page，然后 submit 一个 patch！

![请给我们 Send 一个 pull request！（116 个 open pull requests）](https://danluu.com/images/discourage-oss/send-us-116-pull-requests.webp)

哦。也许他们的留言实在太鼓舞人心，以至于他们每周都会收到数百个 pull requests，而 backlog 也没那么糟。

![好几个人询问为什么这个 bug fix 一直被忽视。没有回应。](https://danluu.com/images/discourage-oss/why-is-this-ignored.webp)

也许并不是这样。我这个大傻瓜，即使看到了这些，还是 submitted 了一个 pull request。综合来看，光是[竟然还能 submit pull requests](http://www.jwz.org/blog/2013/02/wow-remember-when-people-tracked-bugs-welcome-to-the-next-level/)，我就该觉得自己很幸运了。如果我真的足够幸运，也许他们总有一天会抽空[看一看它](http://www.jwz.org/doc/cadt.html)。

我并不是想专门挑这个 project 的毛病。我能理解这种情况是怎么发生的。你是一个能够 merge pull requests 的 dev，但你并不负责 triaging bugs 和 pull requests；你有一份日常工作，有自己负责的 projects，也有 coding 之外的生活。也许你偶尔会看看 repo，把好的 pull requests 给 merge in，并对那些还需要进一步完善的提出意见，但你不会查看全部 116 个 open pull requests；谁有那么多时间呢？

这种行为对任何个人而言都极其合理，却造成了 systemic failure，给新的 open source contributors 增添了额外负担。经常有人问我如何开始参与 open source。我很容易忘记，起步可能很难，因为我最早 contributed 的那些 projects，对于 issues 和 pull requests 的 response time 都是以小时计算的[1](https://danluu.com/discourage-oss/#fn:1)。但很多人的经历就没那么美好了。他们向几个 projects 各 contribute 了几个 patches，却都被忽视了，之后便不知道该何去何从。并不需要[个人有多么恶劣的行为](http://lostechies.com/derickbailey/2012/12/14/dear-open-source-project-leader-quit-being-a-jerk/)，就足以营造出一种充满敌意的环境。

这让我没有去为某些 projects 进行 contributing。在上一份工作中，我致力于让一个知名的 open source project 达到 production quality，在几个月里 fixing 了数百个 bugs。有空的时候，我研究过如何将这些 changes 给 pushing 回 open source community。但当我查看那个 project 的 mailing list 时，却看到一片荒地：许多不错的 patches 完全无人理会，submitter 会在 list 里 ping 几次，然后放弃。为了 submit 一组十有八九会被忽视的 patches，花上一周时间把我们的 IP 从 project 中剥离出来，看起来值得吗？不值得。

如果你对一个存在这种问题的 project 拥有 commit access，请为收到的 pull requests [承担起整个流程的责任](http://en.wikipedia.org/wiki/Diffusion_of_responsibility)（或者就别在你的 repo description 中征求 pull requests）。你不必永远负责下去；只要坚持到建立起一套制度为止[2](https://danluu.com/discourage-oss/#fn:2)。这样不仅会让你的 project 获得更多 contributors，也会帮助消除成为 open source contributor 的一道障碍。

![joewiz 回复了一条一个月前的 comment。几个月后请求 review。没有回复。](https://danluu.com/images/discourage-oss/plz-review.webp)

想了解本文提到的 repo 的后续情况，可以[看看这条针对一个 breaking change 的回应](https://danluu.com/everything-is-broken/#github)。

## 原文

What's the first thing you do when you find a bug or see a missing feature in an open source project? Check out the project page and submit a patch!

![Send us a pull request! (116 open pull requests)](https://danluu.com/images/discourage-oss/send-us-116-pull-requests.webp)

Oh. Maybe their message is so encouraging that they get hundreds of pull requests a week, and the backlog isn't that bad.

![Multiple people ask why this bug fix is being ignored. No response.](https://danluu.com/images/discourage-oss/why-is-this-ignored.webp)

Maybe not. Giant sucker than I am, I submitted a pull request even after seeing that. All things considered, I should consider myself lucky that it's possible to [submit pull requests at all](http://www.jwz.org/blog/2013/02/wow-remember-when-people-tracked-bugs-welcome-to-the-next-level/). If I'm really lucky, maybe they'll get around to [looking at it one day](http://www.jwz.org/doc/cadt.html).

I don't mean to pick on this particular project. I can understand how this happens. You're a dev who can merge pull requests, but you're not in charge of triaging bugs and pull requests; you have a day job, projects that you own, and a life outside of coding. Maybe you take a look at the repo every once in a while, merge in good pull requests, and make comments on the ones that need more work, but you don't look at all 116 open pull requests; who has that kind of time?

This behavior, eminently reasonable on the part of any individual, results in a systemic failure, a tax on new open source contributors. I often get asked how to get started with open source. It's easy for me to forget that getting started can be hard because the first projects I contributed to have a response time measured in hours for issues and pull requests[1](https://danluu.com/discourage-oss/#fn:1). But a lot of people have experiences which aren't so nice. They contribute a few patches to a couple projects that get ignored, and have no idea where to go from there. It doesn't take [egregious individual behavior](http://lostechies.com/derickbailey/2012/12/14/dear-open-source-project-leader-quit-being-a-jerk/) to create a hostile environment.

That's kept me from contributing to some projects. At my last job, I worked on making a well-known open source project production quality, fixing hundreds of bugs over the course of a couple months. When I had some time, I looked into pushing the changes back to the open source community. But when I looked at the mailing list for the project, I saw a wasteland of good patches that were completely ignored, where the submitter would ping the list a couple times and then give up. Did it seem worth spending a week to disentangle our IP from the project in order to submit a set of patches that would, in all likelihood, get ignored? No.

If you have commit access to a project that has this problem, please [own the process](http://en.wikipedia.org/wiki/Diffusion_of_responsibility) for incoming pull requests (or don't ask for pull requests in your repo description). It doesn't have to permanent; just until you have a system in place[2](https://danluu.com/discourage-oss/#fn:2). Not only will you get more contributors to your project, you'll help break down one barrier to becoming an open source contributor.
