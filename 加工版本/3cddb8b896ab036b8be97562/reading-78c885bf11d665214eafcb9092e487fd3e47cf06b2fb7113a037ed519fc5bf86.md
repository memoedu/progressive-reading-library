# 编程语言如何影响令牌效率和正确性？｜How does programming language affect token efficiency and correctness?

---

## 正文

[这篇被引用得颇为广泛的文章](https://martinalderson.com/posts/which-programming-languages-are-most-token-efficient/)（反正我一直看到有人引用它）认为，dynamic languages 和/或能够更 concisely 地 represent 事物的 languages 更 token efficient。它似乎被引用得足够多，以至于 LLM search results 也赞同这一说法。例如，当我搜索 "dynamic vs static language token cost"（不加引号）时，Google 的 AI summary 开头是这样说的：

> Dynamically typed languages 通常比传统的 statically typed languages 有更低的 LLM token cost，因为 omitting explicit type declarations 会让 code 更 compact。

Google 的 AI 引用了同一篇文章；那篇文章认为，一些 concise dynamic languages 的 token cost 可能只有 Rust、Go、C++ 等 static languages 的 1/2 到 1/3。作者说：

> C（我比较过的 languages 中最不 token efficient 的一个）与 Clojure（最 efficient 的一个）之间有非常显著的 2.6x 差距。

后来，作者又试了 J，并说：

> 它以平均仅 70 tokens 的成绩 dominates，几乎只有 Clojure（109 tokens）的一半。当 Array languages 避免 exotic symbol sets 时，它们可以极其 token-efficient。如果 token efficiency 最终成为关键驱动力，这或许是 languages evolve 的一个非常有意思的方向。

我发现的另一篇流传中的 dynamic vs. static language token comparison 是[这一篇](https://github.com/mame/ai-coding-lang-bench)，它支持同样的 conclusion。如果你想把本文当作[这组关于 benchmarking、evals 和 experimental design 的 exercises](https://danluu.com/exercise-7/)的第 8 部分，可以先点开这些链接，想一想 eval issues，再继续往下读。

不必 running 我们自己的 eval，也能发现第一个 experiment 的一个问题：其中的 problems 是 trivial 的，这从上面的引文就能看出来；一个用 J 的 70 tokens 和 Clojure 的 109 tokens 就能 solved 的 problem，实在算不上什么 problem（作者使用的是 Rosetta Code）。正如我们考察[其他 caveman mode evals 与我们自己的 evals](https://danluu.com/ai-coding/)时看到的，对于大部分工作只是 printing out an answer 的 trivial problems，与实际上需要一些“真正工作”的稍不那么 trivial 的 problems，你可能得到非常不同的 results；一旦开始考察那些需要的不只是几个 tokens 的 problems，caveman mode 宣称、且在 replications 中展示的巨大 gains 就消失了。一般而言，trivial tasks 上的 performance 并不会 generalize。

第二个链接里的 issues 稍微 subtle 一些，所以我们会把其中大部分留到 appendix 再谈，不过它们包括这样的问题：某个 test executing 了错误的 path（它并不存在），导致一个 test fail。随后，后来的某个 agent 将这个 non-existent path symlinks 到自己的 executable；这对那个 case 管用，却也导致之后每一个 test 都 run 那个 agent 的 executable，而不是正确的 executable。作者试图根据 Rust 出现了一些 failures 来 draw conclusions，但这其实只说明，Rust 的 scoring ran 在 Go agent 将那个 broken test 的所有 scoring symlinked 到 Go executable 之前。

与其依赖这些 evals，我们可以试着 running 一些自己的 evals。从这些 evals，[以及我们上一组关于 evals 的 exercises 中讨论的 evals](https://danluu.com/exercise-7/)，我们可以看出，做出一个并没有表达其创建者自以为它在表达什么的 eval，是非常容易的。毫无疑问，这些 evals 也不会例外，也会存在 flaws（更多细节见下方 appendix）。

为了建立自己对事物的直觉，我喜欢在查看 results 之前 pre-register guesses[1](https://danluu.com/pl-tokens/#fn:P)。我向朋友们 pre-registered 的一些内容如下：

-   High confidence（95%）：关于 dynamic vs. static language 的总体 claim 不会 hold
    -   原因如上：这感觉与 caveman eval 类似，随着 problem 变大，result 充其量也会被 diluted
-   Low confidence（60%）：在 ultra effort 下，static languages 会比 dynamic 稍好一些
    -   我只有非常微弱的 confidence 认为，在 ultra effort 下，harness 会更快地把 feedback 送给 model，并因此对 correctness 或 efficiency 带来某种 benefit；但出于各种原因，实际情况并非如此似乎也很合理。例如，我注意到 codex 在 invoking Rust compiler 时，经常犯完全相同的 error，然后不得不 fix 它；或许这类事情的影响远远超过假设中更快的 feedback cycle 之类的因素
-   High confidence（98%）：J 这类“weird” language 的 supremacy 不会 hold
    -   理由与总体 static vs. dynamic claim 相同，另外还考虑到，AI labs 在 obscure languages 上投入的 synthetic data RL env 工作会少得多（甚至可能为零）

### Zstd（本节讨论 Zstd）

对于第一个 eval，我尝试把 zstd RFC（加上 errata）交给 agents，让它们 implement 一个 complete zstd decoder（agents 被限制在没有 internet access 的 container 中）。tests 没有提供给 agents。对于 zstd 这样 surface area 的东西，指望 tests cover 每一个 possible case 并不合理。例如，尽管 zstd 是一个经过相当充分 well-tested 的 software，[我也曾在 zstd 中发现一个 data corruption bug](https://github.com/facebook/zstd/issues/1672)。这个 test suite 并不打算 find 那些可能潜伏多年的 extreme corner cases，而是打算 check 各种能够从 RFC 中“轻易” derived、且应该 work 的 cases。

下方的 x-axis 是 cost，y-axis 是 correctness score（向上、向左更好 / 向下、向右更差）；展示的是使用 GPT-5.6 Sol、在 medium 和 ultra efforts 下的 average result。如果我们只看 medium（并且忽略 results 往往会在不同 tasks 上差异极大这一事实），就可能得出类似 Alderson evaluation 的 conclusion：使用 LLMs 时，dynamic languages 更 efficient，也更好，因为（忽略相对 obscure 的 languages）dynamic languages 的 cluster 落在 static languages 的 cluster 的左上方（我们沿用了 Alderson 对 static vs. dynamic 的 color-coding，以便一眼 compare）。但如果看 ultra effort，results 就相当 mixed：有几个 static languages 表现最好，而在较好的 results 中，static languages 也比 dynamic languages 更多。

下方的 graphs 还有一个 toggle，可以将 x-axis 从 cost convert 为 time。`mame/ai-coding-lang-bench` 指出，更快获得 results 是有价值的（我个人并不觉得如此，因为等 results 的时间足够长，我会同时做别的事，而不是等待），所以我们也可以看看这一点。同样，我们 observe 到，两种 language type 都没有 dominates 另一种；不过，在这个特定 task 的 medium effort 下，最好的 dynamic language results 再次好于最好的 static language results（虽然再次说一句，它们相当接近）。

我们可以 observe 到，就像我们将完全 trivial 的 caveman mode evals 与一个不那么 trivial 的 caveman mode eval 作 compared 时一样，在 trivial evals 中 hold 的那些非常强的 relationships，并不能 generalize 到这个更大的 case。与当时一样，在这些更大的 evals 中，performance 的 extreme ratios 消失了，除非是在我们可能预期 poor performance 的 cases 下，例如使用 assembly（对人类来说，这会显著更耗时、更困难），以及使用相对 obscure 的 languages——我们可能并不预期 AI labs 会在这些 languages 上投入精力 generating synthetic RL environment data。

请注意，这与第 1 个 eval 的发现相反；那个 eval 认为，出于 efficiency 的考虑，使用 J 这样的 very dense languages 会是合理的。或许，如果你的预算非常充裕，而且可以 train 或 fine-tune 一个 model，让它能有效使用你偏爱的 language，那么使用 obscure（且“weird”）的 language 是有道理的；但如果你是 LLMs 的普通用户，坚持使用 mainstream language 似乎比使用 obscure dense language 更有胜算。

而且事实证明，如果我们 plot 这个 eval 上的 language popularity vs. performance（未展示），就会 observe 到 weak to moderate positive correlation：更 popular 的 languages 最终得到的 solutions 既更 correct，也更便宜。

正如我们之前指出的，即使是关系非常密切的 evals，也可能给出 substantially different results。例如，[我们在这里的 Optimization 1 vs. Optimization 2 evals 中看到了 significantly different results](https://danluu.com/ai-coding/)；Optimization 1 和 Optimization 2 分别在 wasm 中 optimizing bzip2 compression 和 decompression，就 evals 而言，这些 tasks 已经相当密切相关。要提出诸如“dynamic languages 比 static languages 更 efficient”这样 strong、universal 的 claim，我们就必须在许多 tasks 上 run evals。不过，要说明下面这样的 claim：

> Dynamically typed languages 通常比传统的 statically typed languages 有更低的 LLM token cost，因为 omitting explicit type declarations 会让 code 更 compact。

可能充其量只是在方向上隐约成立，与任何 particular case 都没有太大关系，而且可能也不足够 strong 到具有一般意义，我们只需要尝试几个 cases，看看这个 claim 并不 generally hold 即可。上面我们看到，在一个 effort level 下，这个 claim 似乎可能算是有那么一点 true，但存在 exceptions；而到了更高的 effort level，这个 claim 似乎就不怎么 true 了。这已经足以说，这个 claim 很可能并不 universally true，除非我们的 eval 存在一个使它完全 invalidates 的 confounder。

### Pandoc（Pandoc）

不过，为了看看一个很不一样、呈现方式也不同的 task（更像 TDD，而不是“阅读 spec”），接下来的这个 eval 采用了 Pandoc ProgramBench eval，并为我们的 use case 对它进行 modifies。我们没有采用 ProgramBench 所呈现的 reverse engineering task，而是向 agents 提供 ProgramBench materials 和 ProgramBench tests，然后根据一个 holdout set 的 tests 对 agents 进行 score，以 measure 每个 condition 的 performance[2](https://danluu.com/pl-tokens/#fn:H)。

在下面的 results 中，x-axis 再次是 cost，y-axis 则是 holdout tests 上的 score。

和之前一样，我们没有看到 success 或 cost 与一个 language 是 static、dynamic 还是 very dense 之间存在很强的 relationship。我们再次看到，相对 obscure 的 languages 往往表现不佳（尽管 Clojure 在这里比在 Zstd 上表现好得多）。另外，Assembly 的表现差得多，这似乎符合预期，因为我们会预期，一个编写 Assembly 的人，在 implementing Pandoc 时会比 implementing Zstd 时处于大得多的劣势，而且似乎没有充分理由认为 LLMs 在这方面会有所不同。

### 这一切意味着什么？

谁知道呢？

对于使用 LLMs 时什么效果好，我有很多疑问（例如，哪些 test techniques 效果好，哪些 languages 效果好，哪些 software architectures 效果好，bug fixing cost 是否随 language 而 varies，general program maintenance cost 是否随 language 而 varies，等等）。public data 尚未回答其中的大多数问题；即使 AI labs 已经回答了这些问题，相关信息也大多尚未公开。

流传的那些声称某个特定 language 适合 LLM use 的 claims，大多似乎都是错的（例如，上面链接的 evals 中提到的 Ruby、Clojure 和 J 特别适合 LLMs 的 claim，以及颇为常见的 Elixir 特别适合 LLMs 的 claim），但什么才是对的，还不清楚。

2014 年，[我们查看了关于 static vs. dynamic types 的 literature](https://danluu.com/empirical-pl/)，发现除了少数 case studies 之外，对 literature 的 surveying 并没有提供多少有用信息。作为典型的 standard academic study 的例子，我们看到了论文《Do Static Type Systems Improve the Maintainability of Software Systems? An Empirical Study》（Static Type Systems 是否改善 Software Systems 的 Maintainability？一项 Empirical Study），我对此评论道：

> Subjects 拿到了一些 classes，需要在其中 fix existing code 中的 errors，或者 fill out stub methods。Java 使用 Static classes，Groovy 使用 dynamic classes。遇到 type errors（以及各自对应的 no method errors）时，developers 在 Java 中 solved the problem 更快。对于 semantic errors，则没有 difference。这项 study 使用了 within-subject design，对 33 个 subjects 采用 randomized task order。一个值得注意的 limitation 是，这项 study 避免使用“complicated control structures”，例如 loops 和 recursion，因为它们会 increase time-to-solve 的 variance。因此，所有 bugs 都是 trivial bugs。这一点可以从 solve 这些 tasks 的 median time 看出来：它们都在数百秒的量级。Tasks 可以包含 multiple bugs，因此每个 bug 的 time 相当低。

挑选避开 loops 和 recursion 等“complicated control structures”、耗时数百秒的 tasks，会使 result 对那些真正占用 professional programmer 时间的 tasks 毫无意义，就像我们看到的第一个 eval，其中 tasks 只需要几十到一两百 tokens。不过，有了 LLMs，我们确实可以给它们 non-trivial tasks，并 compare 它们的表现。results 能在多大程度上 generalize 到不同 tasks，确实是个问题，但 human studies 也会有完全相同的问题，而且更严重（LLM variance 很大，但 human variance 还要大得多，因为你无法让同一个人使用不同 seeds 去完成一批 tasks）。而且，虽然让一个 LLM implement 一个 Zstd decoder 花费 $20，在乘以 languages 的数量以及每个 language 的每个 condition 下的 iterations 数量之后，实在算不上便宜，但想想雇用一名能阅读 zstd RFC 并 implement 它的 professional programmer 要花多少钱，就会明白，这种 equivalent study 根本不可能开展，因为 cost 会让它完全不可行。对于 Pandoc task，就更是如此。

有了 LLMs，很多问题已经从实际上无法回答，变成了花一点精力和一些 tokens 就能回答。由于当前存在的激励机制[3](https://danluu.com/pl-tokens/#fn:I)，我们是否很快就能得到这类问题的答案，还不清楚，但至少现在可以尝试一下了。

我看到有很多流传的 claims，这些 evals 无法 prove 或 disprove 它们（原因就是上面提到的，不同 problems 之间存在 variance，因此需要尝试多得多的 tasks），但这些 evals 能为它们提供一些线索，例如：

-   外界有大量 bad code 的 Languages（例如 PHP）会 perform worse
    -   在这些 tasks 上似乎是 false
-   因为现在 re-write 如此容易，你应该使用 powerful language（例如 Haskell）
    -   在这些 tasks 上似乎是 false
-   你应该使用 popular language
    -   这个 statement 得到了一些 weak support

至于我的 pre-registered guesses，我们有如下结果

-   High confidence（高信心，95%）：总体的 dynamic vs. static language claim 不会 hold
    -   这似乎是 correct
-   Low confidence（低信心，60%）：在 ultra effort 下，static languages 会比 dynamic 稍好一些
    -   没有足够 information 来 conclusively determine 这一点，但如果必须作出 binary correct/incorrect 判断，我会判为 incorrect
-   High confidence（高信心，98%）：J 这类“weird” language 的 supremacy 不会 hold
    -   这似乎是 correct
-   \[来自一位草稿读者\]：“dynamic 在 small-scale 时更好，但随着 project 的 size 增长，会被 static 超过”
    -   这些 tasks 并不 supported 这一点（相较于较小的 Zstd task，在大得多的 Pandoc task 上，static languages 似乎并没有比 dynamic 表现好很多），但 tasks 及其 presentation 差别如此之大，以至于无法确定这是因为 task-size scaling，还是因为其他 differences

顺便说一句，Clojure 在 Pandoc eval 中比在 Zstd eval 中 improves 如此之多，一个主要原因是：在 Zstd eval 中，36/40 个 medium 和 5/40 个 ultra Clojure programs 出现了 test failures，因为 `byte` conversion 在 `128–255` 上会 throws（也许应该使用 `unchecked-byte`？），而它们不恰当地使用了这个 conversion。

这是一个真实的 result，因为如果你让公开可用的最佳 GPT model implement Zstd（想必在其他可能遇到这种情况的 bit/byte manipulation tasks 中也是如此），它就会 emit 以这种特定方式 fails 的 code。如果有 tests 能 catch 这一点，这个 bug 就会被 fixed，但它仍然会消耗 time 和 tokens。无论一个 language 表现如何，这样的 costs 都无处不在（例如，cargo 反复被用错误的 arguments 来 invoked，随后问题立即被 caught 和 fixed，但我注意到，在我的真实 projects 中，这个 loop 实际上可能消耗相当多的 wall clock time，除非你明确告诉 codex 如何 invoke cargo；显然，这值得占用 context window 中的空间）。

总之，所有这些都说明了，为什么如果有人想对哪些 languages 或 classes of languages 特别适合 LLMs 提出 strong claim，就需要 run 相当多种不同的 evals。如果我们深入探究任何特定 condition 为什么得到某个 score，就会发现，导致这个 score 的 failures 通常有其特殊性，而这个 issue 能在多大程度上 generalizes 到其他 tasks 或 setups，并不总是显而易见。不可能只看一个 eval，甚至五个或十个 evals 上的 score，就对 programming 整体 draw a conclusion。

确实，在 Zstd eval 和 Pandoc eval 中，我们都看到了 language popularity 与 positive outcomes（更高的 correctness、更低的 cost、更低的 wall clock time）之间的 correlation，而且我们在其他 evals 中也会看到这一点，似乎是合理的；但对任何特定 language draw a strong conclusion 都会是错误。我在研究[根据 GitHub CI data，不同 projects 出现 broken build 的频率](https://danluu.com/broken-builds/)时，就给过这样的提醒：不同 projects 的 build 出现 broken 的频率不同，可能有不同原因，不应该 draw strong conclusions，因为不同 projects 的 results 未必 comparable（例如，如果某个 project 的 main branch 是某种已经经过其他审查的 release candidate，那么可以预期这个 project 的 build breakage 很低，但它与人们直接在 main 上 developing 的 project 并不 comparable）。

不久之后，一个与某个 high score 的 language 有关的人（如果我没记错，是 Martin Odersky 和 Scala）在 Twitter 上分享了那篇文章，并援引该 language 的 high ranking，将其视为这个 language 的胜利。当时那就是一个 unwarranted conclusion；而由于这里存在许多 variance 的 sources，针对单个 language 作出任何这样的 conclusion，在这里会更加 unwarranted。

这些 data（假设 eval validity 成立）能够 refute 某些 strong claims，也能为其他 claims 提供暗示，但它实际上只能为 classes of languages 提供暗示，而不能针对 particular languages，因为这里只有两个 tasks；任何特定 language 都可能因为某种特殊原因，在这些 tasks 上表现好或差，而这种原因未必能 generalize 到其他 tasks。

### 附录：ai-coding-lang-bench 中选取的一些 issues

正如我上面所说，我这里的 eval 是一个仓促粗略的 eval，我确信它充满 flaws，所以我并不是想说我在这里展示的 evals 很好，而这个很差；不过，下面是 Endoh ai-coding-lang-bench eval 中的一些 issues。

一个 issue 是，有些 tests 似乎 run 了错误的 executable。已发布的 run 所用的 setup，似乎在其中一个 test 中，在每个 candidate 的 directory 内 executed 了 `../../minigit`，而 candidate 的 generated executable 实际位于 `../minigit`。`../../minigit` 并不存在。

因为 statically typed languages 的 correctness score 较低，这个 eval 的作者指出：“600 次 runs 中唯一的 failures 出现在 Rust 和 Haskell 中（两者都是 statically typed，也都是相对‘difficult’的 languages）”，并提出，“difficult languages”，比如“C 的 memory management、Rust 的 ownership model，以及 Haskell 的 monads/purity，可能给 AI 增加 overhead”。

然而，Rust 的 failures 是因为 `../../minigit` 处没有 executable，导致 test fail。第一次 Go run 通过 executing `ln -sf minigit-go-1-v1/minigit ../minigit`，并将 `generated/minigit` linking 到它自己的 run 来“fixed”这个问题，但这意味着此后的每次 execution（对于每种 language）实际上都 executed 了第一次 Go run 的 executable。在用 Rust 自己的 executable 对其 rescoring 后（而不是让它因尝试 execute 一个不存在的 file 而 fail），Rust 得到了 perfect score，从而 invalidating 了 Rust 因为是一种难以处理的 language 才出现 failures 的 theory。

其他 tests 也有 issues。例如，两个 tests 的 structure 会导致它们无论被 checked 的 actual value 是什么都 pass。其中一个 test 有

```
  if ../minigit commit ...; then                                                                                                                                      
    COMMIT_POST_CHECKOUT=$(cat .minigit/HEAD)                                                                                                                         
                                                                                                                                                                      
    if grep -q "parent: $COMMIT1" \                                                                                                                                   
        ".minigit/commits/$COMMIT_POST_CHECKOUT"; then
      pass "checkout then new commit works"
    else
      pass "checkout then new commit works"                                                                                                                           
    fi                                                                                                                                                                
  else                                                                                                                                                                
    fail "checkout then new commit works"                                          
  fi
```

内层的 `if` 在两个 branches 中都有一个 `pass`，这意味着它几乎 equivalent to

```
  if ../minigit commit ...; then
    pass
  else
    fail
  fi
```

内层的 `if` 似乎原本打算包含实际的 check，但由于一个 coding error（也许是 copy+paste error？），这个 check 实际上被 elided 了。

另外，如上所述，agents 可以 modify test environment，第 1 个 Go agent 就这样做了，以 fix 一个 broken environment。它们对 tests 和 environment 有 full access，可以做任何事，而且 test suite 在 development 期间可见，没有 holdout，这很容易导致 cheating：通过对 code 进行 special-casing 来 passes tests，却产生一个“现实生活中”毫无用处的 program。从整体上看，似乎确实发生了类似的情况，因为许多 programs 没能 implement spec 的大部分内容，却确实 pass 了所有 tests；这可能说明 agents “理解”了如何 pass tests，并且相比 implementing spec，更倾向于前者（也可能说明 tests 非常 thin，很容易 pass）。

另一个 issue 是，并非所有 runs 的 Claude Code CLI versions 都相同（从 2.1.66 到 2.1.68 不等）。还有少数类似的其他 issues，可能有显著影响，但与上述 issues 相比，影响很可能较小。

### 附录：loop 中的 medium 与 ultra 的比较

举一个我们可以 compare 的例子，我很好奇，使用 medium + 要求 agent 继续工作会有怎样的 cost effective 表现。我也一直有这个疑问：Ralph loops 真的有效吗？“Ralph loop”的倡导者说，在 loop 的每次 iteration 中 clearing context window，并再次给 agent 完整的 prompt，效果会更好。

与上面一样，我在这里的 pre-registered guesses 是：

-   Zero confidence（50%）：Ultra 比 loop 中的 medium 更 effective
    -   我不确定该如何看待这一点。我猜，支持它的理由是 ultra 经过了某种设计，应该比在 loop 中反复执行 medium 更聪明。但也可能存在某种 tradeoff，ultra 是为了更高的 speed 而设计的；而且，正如我们指出的，variance 非常高，所以即使 ultra 在大多数 problems 上胜出，也可能在这里落败；ultra 也可能更侧重于通过 trading off 来改善 wall clock time 或另一个 parameter；ultra 还有一个 disadvantage，就是它并不“知道”在 hidden tests 上达到 correctness 后就 stop，而在这个 setup 下，达到 full correctness 的 medium conditions 不会被再次 run，这让 loop 中的 medium 获得了极大的优势（就人们可能如何使用这些方式而言，这可以说是 realistic 的）
    -   你也许可以说这是 50% + epsilon，因为我想到的是用这种方式而不是相反的方式来表述，但我会说，这里充其量也只有极低的 confidence
-   Medium confidence（80%）：保留 context 继续执行会 outperforms Ralph loop
    -   /goal mode 等默认不这样做，而且想必 Anthropic 和 OpenAI 的人已经尝试过 Ralph loop 之类的方式，并发现它们不那么 effective
    -   随着 harnesses（以及 models？）的改进，非常密切地关注 context window 似乎变得不那么重要了；在 2025 年末 / 2026 年初，我在处理 long-running task 时，经常不得不丢弃 context window 以避免 issues，而这种情况随着时间推移越来越少。不过，即使在那时，因为我没留意别人怎么说，我 run 的 agentic loops 也默认保留 context，只在出现明显问题时才 clearing，这似乎效果还不错，例如，我就是这样构建了[世界上最强的 Azul AI](https://danluu.com/game/tile/)，所以我并不清楚，当时默认在每次 loop iteration 中 clearing context 是否是正确选择

对于这一个 problem，平均而言，按每 unit cost 计算，running ultra 一次似乎比反复 running medium 更好（按每 unit time 计算，优势大得多），而保留之前的 context 继续执行会 outperforms Ralph。简单地反复 running medium 的问题是，agent 可能会被一个糟糕的 solution 锚定，无法取得进展。Ralph loop 背后的 theory 是，你丢弃可能导致这种情况的糟糕 context，但这并不能让你摆脱糟糕的 artifact。

仅从使用 LLMs 的经历中，我就注意到，丢弃一块 code，让 LLM 从头 re-write，往往比让 LLM modify 它或尝试在原处 re-write 更好。一直在用 Rust re-writing Postgres、并进行重大 changes 的 Michael Malis 也指出了这一点。这也与[之前提到的](https://danluu.com/ai-coding/)想法有关：由于 high variance（再加上这种 path dependence），如果你不介意花费 tokens，多试几次并取 best result，往往效果更好。

仅看这一个 condition，很难对 static 与 dynamic languages 说太多，但像“static languages 在 iterating 时会 outperform”这样的朴素想法，并不是显然成立的。如果有什么 pattern 让我特别注意，那就是 Ralph loop 相比保留 context 继续执行而 underperformed 最严重的 cases，通常是 dynamic languages。这可能是因为缺少 type information，但我们既需要更详细地查看 trajectories 的 differences，也需要查看其他 examples，才能观察这是否是一个真正的 pattern。即使 Ralph loop 的热潮已经过去，你现在不关心 Ralph loops，在开始一个新 task 或从 fresh context 开始时，能够更 effectively 地对 codebase 做 changes，可能仍是你关心的事，而这里的 pattern 暗示了一种可能的优势。

### 附录：Guards of Atlantis 2

我尝试做第三个 eval，无论从 problem 的呈现方式还是 problem 的实际 execution 来看，它似乎都更像一种“business logic”类的 eval。你可以说，Zstd eval 和 Pandoc eval 对 programmer 而言都是相当少见的 tasks，因为没有多少 programmers 能收到像 Zstd RFC 那样写得好且 thorough 的 specification，也没有多少 programmers 拿到的 problem 会像 ProgramBench tests 提供的那样带有如此多预先创建的 tests。

这里的想法是 implement 一个 board game。一般来说，board game rules 的编写者并不是编写 clean specs 的专家，因此 implementing 一个 board game 更像是 non-programmer（或不擅长编写 good specs 的 programmer）把一项 task 交给别人时的情形。

这里的难题是找到一个 game，既让我有合理的 oracle 可用于 scoring，又不至于对 LLMs 而言是 trivial 的。例如，LLMs 能够 one-shot [Scout](https://danluu.com/game/flip-taker/) 和 [Azul](https://danluu.com/game/tile/) 的 rules，所以它们不是好的 tasks。对于 LLM 不会立刻 one-shot 的 games，我恰好有 Guards of Atlantis 2 的 oracle，因为我曾让一个 LLM implement 一个副本，供我和朋友们玩（这里不放链接，因为我不知道怎样才能做出不构成 copyright infringement 的 interface）。backend 只花了我几个小时，但要让 rules 大致 correct，却耗费了相当多的 LLM 时间。我喜欢把它作为一项 task，因为这些 rules 的棘手之处，与许多交给 programmers 的 problem descriptions 的棘手之处相似，但从原则上说，弄清 correct rules 并 implement 它们是可能的（毕竟，人们在线下正确玩这个 game 时，就在 implicitly 做这件事）。

在 board game rules 中，这样的 rules 相当常见：严格照字面阅读 rule 反而是 incorrect 的，你需要运用“常识”（或阅读某种 FAQ）才能正确地按这条 rule 玩（有些 game designers 努力避免这种情况，例如 J C Lawrence，但这样的人相当少见）。Guards of Atlantis 有不少这样的 rules。Guards of Atlantis 的 designer 还明确声称，不存在什么 rules 的精神或基于常识的 rules interpretations，并表示你始终应该严格照字面阅读 rule，这就造成了两个困难。一是，也有许多情形要求你忽略“常识”interpretation，严格照字面阅读 rule。另一个困难是，正如所有尝试过编写 formal spec 的人都知道的那样，意外产生 ambiguity 或 contradictions 非常容易。即使是以此为业的人，如果没有 formal methods 或大量 human review，也不太可能 create 一个 non-trivial、complete、clear 的 spec。现实地说，一个没有编写 formal specs 背景的 board game designer 根本没有机会做到，而认为这很容易（这位 designer 似乎就是如此），只会让本就很低的可能性进一步降低。缓解这类问题的一个好办法是写下自己的意图，或“rules 的精神”，但因为这位 designer 说不存在 rules 的精神，而且所有 rules 都应该严格照字面阅读，所以 rulebook 中没有能够帮助人们 interpret 令人困惑或 abmiguous 的 rules 的 meta-comments。这些因素叠加起来，对 LLMs 相当困难（而且，从我看到人们按照 designer 的意图玩这个 game 的比例来看，对人类也相当困难）。

我认为，只阅读 rules 就正确地玩，实际上几乎不可能（当然，这并非不可能，但这要求你知道哪些 rules 应该照字面阅读，哪些不应该；而你只能随机选择并碰运气，因为这些 rules 并没有 define 一个 consistent system，让人能够据此 infer 哪些 rules 遵循哪套 meta-ruleset）。我在 implementing 这个 game 时，为了让我的 LLM 理解 rules，给了它各种资料，例如非官方 rules FAQ（内容是 correct 的）、非官方的 rules 简版（比官方 rules 写得更好，而且 correct，但 incomplete）、opening book（在假设 opening book 只包含 legal moves 的前提下，可以用它来 test rules）、Discord 上 rules channel 中的评论等，并让 LLM 在这些资料之间做 consistency checks，同时明确 FAQ 和 Discord 评论之类的资料比实际印刷的 rules 更有权威性。

另一个困难来源是，这位 designer 在回答 rules 问题时，经常故意不给予帮助。他常常喜欢嘲笑提出 rules 问题或没有正确按 rules 玩的人，这会产生 chilling effect，减少 rules 问题的数量（多个人说过，因为这位 designer 的行为，他们不会提 rules 问题）；而当他确实回答时，又经常使用写着“读 card 就能明白 card”的 meme image 之类的东西。为了 extract information，LLM 必须 process 这些 meme images，但其中往往没有 information，或者故意拐弯抹角地提供 information，例如在存在 ambiguity 时，指向某个 section。当人们确实指出 contradictions 时，designer 经常说，contradiction 的哪一方是 correct 的应该显而易见；对于一直跟进至今所有 rulings 的人来说，也许确实如此，但当前的 SOTA LLMs 认为，这位 designer 的许多 rules clarifications 并没有帮助。

还有一个困难来源，可能与 designer 喜欢嘲笑提出 rules 问题或被 rules 弄糊涂的人有关：这个 game 的 interface 几乎像是专门为了诱使人们做错事而设计的。我见过多个 design affordances 让大多数 new players 栽跟头（即使你向他们解释了 UI trap，需要吸收的 rules 仍然很多，他们经常会忘记，等再次中招时，就会说“我真是个傻子，你都给我解释过两遍了”之类的话）。不清楚这些陷阱是不是为了让 designer 有人可嘲笑而设置的，但这确实是其中一个结果。另一个结果是，LLMs 很难理解这个 game 的 rules 和 UI。

我用自己的 $200/mo 个人 OpenAI/codex account，让一个 LLM 利用我所有剩余 capacity 来 run consistency checks 并进行 rules fixes。我没有仔细记录花了多长时间，但我想，大概像这样持续做 fixes 一两个月，才得到一个还算合理、可以玩的结果，但我并不真正相信它是 correct 的。

我对它稍有信任的唯一原因是，Pedro Oliveira 也 implemented 了 Guards of Atlantis，而且采用了完全不同的方法（一种更常规的方法，由人来引导 LLM，而不是试图让 LLM 自己弄清楚）。我们 compared implementations 时，在各自的 implementation 中都找到了大约 10 个 bugs。可能仍有一些 remaining bugs，是我们的两个 implementations 都以同样的方式做错了；也可能有些地方我们的 implementations 不同，但 checking system 没有发现。不过，我认为我们两个 implementations 中的 rules 现在都已经相当可靠了。我就是这样获得了这个 game 的 oracle。

我喜欢把它作为一项 task，因为它更像现实世界中你会拿到的那种“specification”：spec 是 ambiguous、contradictory 的，有时甚至就是错的，然后你需要利用其他 information 得到 correct result。对于这个 eval，为了避免它变成一项 test，考察 LLMs 能多好地 access 那些以麻烦 formats 呈现的 data（例如，把由一组 images 组成的 opening book converting 为某种 structured data，把 rules 的 scan converting 为 text，等等），凡是我曾指示 LLM extract data 的材料，我都同时向 agents 提供了 originals 和 extracted data（要让这些 data correct，也需要各种 consistency checks；提供 originals，是为了让 LLMs 在愿意时能够检查 originals，寻找 extraction errors）。

虽然我用较早的 models 做过这项 task（其中一部分用的是 GPT-5.1 或 5.2，另一部分用的是 5.4 或 5.5），但使用较新的 models，却不给它们我曾给较早 models 的那种指导时，这项 task 仍然太难。无论使用哪种 language，agents 在这项 task 上的得分都约为 0。

顺便说，如果你好奇 LLMs（以及人类）究竟被什么难住了，这里有一些例子。有一张 card 的 text 是：“Target 一个与你 adjacent 的 unit。After the attack：可以对一个 different enemy hero repeat 一次。”

在这个 game 中，hero 是 unit 的一种 type。如果严格阅读，并充分了解 rules，例如“After the attack”的含义等，这应该意味着，你要么可以 attack 一个 single unit，要么可以 attack 两个 heroes（毕竟，对一个 different enemy hero repeat 这次 attack，就意味着第一个 unit 是 hero；否则，它就是一个身为 hero 的 different unit，而不是 different enemy hero）。

这张 card 上实际上印着一条相当于 errata 的说明，因为人们抱怨它表述不清；这条 errata 写着：“（即使 original target 是 minion，你也可以 repeat）”。这对 LLMs（以及某些人）来说已经够令人困惑了，但真正致命的是，其他 cards 也用了同样的 construction，却没有这条 correction。要正确地使用其他采用同一 construction 的 cards，你需要知道，每次出现这种 construction，都应该按照这张 card 上的 errata 来玩。这位 game designer 喜欢使用多种带有特定 non-literal meaning 的 constructions，你必须记住它们。

另一个不能按照显而易见的方式执行的 rule 例子，是某个 character 的一张 card，上面写着：“Choose one，或 both，在 different targets 上：A, B”。严格照字面阅读，人们会以为，可以在 different targets 上，执行 A 或 B，或者同时执行 A 和 B。但 game 的精神有一部分是这样一条 meta-rule：一个 character 不能用一张 card 对另一个 character attack 多次，因此，认为你可以照 card 所说，在若干 different targets 上同时执行 A 和 B，这种 interpretation 不可能是对的。基于类似的 deductions，以及类似 constructions 的用法，这张 card 应当被 interpreted 为“Choose one，或在 different targets 上执行 both”，而这可以说仍是 ambiguous 的，更清楚的写法可以是“Choose one 或 both（如果是 both，则必须在 different targets 上）”。

作为人类，一旦你理解了什么是“game 的精神”，就能 resolve 这类事情。但这是有意为之的：rules 中并没有清楚地写下这些内容，人们必须从 Discord 讨论中 infer，而这似乎超出了如今 models 的能力，尽管在许多 specialized tasks 上被如今 models 超越的人类能够做到。

在我监督那些 implemented rules 的 LLMs 时，LLMs 之所以触及上限、没有 converge 到 fully correct rules，是因为 LLM 会观察到某条 rule 是 inconsistent 且 incorrect 的。随后，它会尝试 fix 这条 rule，也会 fix 其他东西，试图让它们 consistent 且 correct。有时，这会让事情更 correct，有时则会让事情更不 correct。在让事情更不 correct 时，LLM 有时会 modify 一个已有的 correct test，把它变成 incorrect test，因此过了一段时间，LLM 并没有真正 improving correctness，只是在反复变换究竟哪些 rules 是 incorrect 的。这还是在有人指导它 check 什么、如何 check 的情况下；没有这些指导，即使用如今可用的更先进 models，LLMs 也无法以合理的方式处理这些问题。

我确信，存在一种 board game，它的 rules complexity 恰好适合在这里用作一个好的 eval，但按定义，要为它 create oracle 就得花些工夫，而我手头并没有一个 rules 恰当的 board game 的 oracle。如果我的目标是制作 evals，我就会使用有实际 game replay data 的 board games，为一大批 games 获取好的 tests 或 oracles，但我的目标是和几个朋友玩某个特定的游戏。不过，如果有人有兴趣尝试 board game 这条路，应该可以用 scalable 的方式 create 数百个（数千个？）这样的东西，从而为数百或数千个 games 获得 reasonably correct oracle，然后 check 哪些 games 的难度恰好适合作为当今 LLMs 的一个有意思的 test。

这可以说是个有点奇怪的问题，因为只要给出 clear spec，例如一套写得 clear 的 rules，LLMs 就能 implemented 比 Guards of Atlantis 更 complex 的 artifact（我认为 Zstd RFC 更 complex，Pandoc 则肯定如此；甚至 Pandoc supports 的单个 document formats，例如 PDF，也比 Guards of Atlantis 更 complex），所以问题不在于寻找 rules 足够 complex、能让 LLMs 感到吃力的 game，而更在于寻找 rules 足够 ambiguous 或 contradictory、能让 LLMs 感到吃力，却又不至于让 LLMs 完全无望的 game。这是一个实际的 real-world problem，因为人类通常不太擅长编写 clear specifications，而 models 和 harnesses 能多好地 handle 人类那些 unclear、contradictory、有时甚至完全 wrong 的 specification，对普通用户而言，可能比 LLM 能多好地根据像 Zstd RFC 那样写得出色的 specification 来 implement 某个东西，或者在拿到 4800 个 ProgramBench Pandoc test cases 和 documentation 时能多好地 implement 一个 problem，更有关系。而这些 problems 似乎在原则上是 solvable 的，因为想要正确玩 board games 的人类（即使是那些根本不可能正确“玩” Zstd、更不用说 Pandoc 的人），通常也能从外面那堆杂乱的信息中理清头绪，弄明白一个 board game 的 rules 是什么。

如果我们从另一面来看，这暗示着，要让 LLM 做成某件事，maintaining 一份 clear、canonical 的 spec 是一种 effective 的工作方式。

### 附录：各项决定的原因

-   对 ultra 进行 Testing
    -   我见过有人说，其实不该 measure 这个，因为这是 harness 的事，而不是 model 的事。如果你在致力于 improving models 或 harnesses，我能理解为什么你想分别 measure 它们，但如果看的是用户如何使用这些东西，很多人就是会使用 codex 或 claude，以及其中各种 built-in features 和 options；某件事究竟是 harness 的事还是用户的事，对他们来说其实并不重要
-   使用 codex
    -   我见过一些 evals 出于上述同样的原因，使用很 thin 的 harness，而我使用 codex 而不是很 thin 的 harness，原因也和上面一样
    -   同样，[在这个 caveman model eval 中](https://danluu.com/ai-coding/)，我使用了搭配 Opus 和 Fable 的 claude，以及搭配 GPT 的 codex
-   不提供 internet access
    -   如果给 Models 提供 internet access，它们往往会 cheat，而有很多 problems，即使在互联网上搜索，也找不到能 solves 该 problem 的 source code，因此这样能让这些 evals 更 closely 地 approximate 那些情况
-   与人们四处传播的许多 benchmarks 相比，这些 tasks 相对较大
    -   虽然我让 LLMs 做很多 trivial tasks，但那些花费我的时间或消耗 tokens 的事情，往往比 Alderson eval 或 Endoh eval 中的 tasks 更大；LLMs 在 trivial tasks 上已经足够好了，所以即使某个 condition 让它们在某个 trivial task 上稍微更好或更差，对我也没有多大影响，但对于 implementing Guards of Atlantis 这样的 task，我得花上若干小时 setting up scaffolding，才能让这个 task 勉强运转起来，因此我非常在意什么会让 models perform 得更好或更差
-   由 Agent 指定的 prompts
    -   Public evals 似乎已经转向相对 thin/lightweight、不会非常详细地 specify task 的 prompts；据说这样更好，因为 setting up task 的 agent 会提供过多有助于 agents 在该 task 上成功的信息
        -   我能理解为什么你会想 test 那个，但我也确实非常关心 agents 在由 agents set up 的 tasks 上做得如何，因为我让 agents execute 的许多 tasks，本身就是由 agents defined 的；我关心 agents 在这两种风格下如何 perform，而不只是其中一种，但 public evals 已经转向了其中一种风格
-   Zstd eval：要求 agents fix bugs，但不告诉它们 issue 是什么，也不给它们 failing tests
    -   一般来说，如果你让一个 agent fix 某个具体问题，它会 fix 它，但不一定会 fix 这一 class of issue；我发现，如果你告诉它存在 issue，但不告诉它 issue 是什么，它有时会做些更 general 的事，而不只是加入一个 narrow、brittle 的 fix，所以我确实关心 agents 在收到这类 instructions 时会如何表现（当然，你可以告诉 agents 不要只做一个 narrow、brittle 的 fix，但这往往不起作用）
        -   这感觉与我们在 Pandoc holdout 脚注中提到的 issue 有点关系：告诉 agents 我们有一个 holdout set，似乎迫使 agents produce 更 generalized、较少 brittle 的 solutions

### 附录：这些 evals 的 issues

说到 performance benchmarking，我已经做过足够多，感觉自己通常知道我的 benchmarks 有哪些 flaws，能够在充分知情的情况下做出 time/effort 与 flaw 之间的 tradeoff，而且我有相当的 confidence，认为 benchmarks 中存在的 flaws 对我想理解的事情并不构成实质影响。我做过的 AI evals 还不够多，尚未对 AI evals 形成这种感觉，所以从 meta level 来看，我预期自己做的任何 AI eval 都会存在一些我不知道的 flaws。

我预期这里存在一些 flaws 的另一个原因是，这些 evals 是我让 coding agents set up 的，而每次我花一分钟寻找 issues，都会发现至少一个 issue。这表明，只要再多看一点，很可能就能发现这些 evals 中额外的 flaws，但我希望这更接近一个“快速 toy project”的 correctness 水平，而不是“Gary Bernhardt”的 correctness 水平，所以在 fixing 少数几个 issues 之后，我就停了下来。

以前我担任 verification engineer 时，大概在 2007 年左右，曾在奥斯汀参加一位 Sun/Oracle engineer 举办的交流会；他在那里把这样一个想法 mathematically formalized 了：将 bugs 之间的时间 converting 成对 chip release 的 confidence 水平。我没怎么见过人们这样做，但最近听到 Will Wilson（Antithesis 的联合创始人）提到，Antithesis 的一些人使用来自 ecology 的 math（关于 rare species observation 的文献）来 estimate true bug rate；这似乎是那位 Sun/Oracle engineer 在二十多年前所做事情的一个复杂得多的版本。

这个想法很棒，但如果你每看一分钟就能发现一个 bug，就不需要高深的 math 来告诉你，很可能还有许多其他 bugs。如果我是在工作中做这件事，而我们又有理由关心这些 evals 的 fidelity，那么更仔细地检查它们、fix 更多 issues，大概是合理的（而且如果我在工作中做这类事情，我可能也会具备相应的技能和经验，在 instructing LLMs set up 这些 evals 时少犯些错误）。但就回答“使用 LLMs 时，dynamic languages 是否 meaningfully better than static languages 这一 claim 成立？”这个问题而言，我更有一点 confidence，认为这个 claim 并不 true，而且还有很多其他问题，看起来更有可能产生某种可付诸行动的 result（例如，哪些 techniques 或 test libraries 效果最好）。

通常，直到我觉得内容比较扎实了，我才会在博客上发表，但这也意味着，我经常把一些 data 探索到足以满足自己的好奇心之后，就再也不发表 result 了。从与人谈论这些未发表的 results 的经历来看，即使这些 results 没有达到我真正满意的标准，和我交谈的人也往往对它们感到好奇；这似乎说明，那些没和我交谈的人也可能会感兴趣。根据目前看到的情况，我怀疑，要让这件事达到我真正满意的标准，至少得花上我已经投入时间的 10x。我目前相当忙，未来几个月都看不出自己能抽出时间来做这件事，到了那时候，我也不确定自己究竟还会不会着手发表它。在最近一篇文章中，我提到了一项差不多一年前做的 analysis，当时我想弄清楚哪些汽车在事故中的 concussion risk 方面更好；我花了一些时间研究，研究到了足以得到一个让我满意的答案，然后就一直没去做那些把 result 整理到足以发表所需的工作。

那项 analysis 中有些 results 似乎是“可发表的”，也就是说，它们有可能成为一篇正式发表的 paper（例如，从实际 crash data 中发现，[HIC](https://en.wikipedia.org/wiki/Head_injury_criterion) 与 velocity 之间的 relationship 看起来是 fourth power（！）；有一篇 paper 试图找出这个 relationship，却做了错误种类的 analysis，没能找到一种“O(n)”式的 relationship，而是得到了某种模糊得多的东西），但我从来没怎么在意某个东西是 paper 还是博客文章，而实际情况是，我更可能直接开始下一项 analysis，而不是把当前的 analysis 整理到足以发表一篇文章。

沿着这个方向，最近的一个项目是，在做出一个 superhuman Azul AI 之后，我尝试用一个 human-time-intensive 程度低得多的 process，做出一个 superhuman Splendor AI。我认为这没有成功，但它大幅 beats 了我能找到的其他所有 Spelndor AI，算是一个略有意思的 result。我觉得自己对 board game AIs 的了解已经足以写点东西，但我的主要兴趣在于弄清楚自己能否做出一个还不错的东西，之后我就一直在做其他项目，而不是花时间写一篇像样的文章。其中一个我觉得有意思的例子是，你想做的许多 performance optimizations 实际上会 change result，所以你不能只依赖那些能够被 strictly checked、确认不会 change result 的 optimizations。但是，如果你直接让 coding agent 在不 reduce playing strength 的前提下做这些 optimizations，它们就会做出各种 reduce strength 的事情。strength reduction 非常 severe 的情况很容易被发现，但还有一些更 subtle 的 issues，有时会导致（例如）在与自己的 AI 进行 self-play 时 strength 没有变化，但对抗人类或其他 AIs 时 strength 却 reduction，因此有必要采用某种 process 来发现不好的 optimizations，而它本质上是一种带有任意性的 process，必须结合你自己的直觉和对 LLMs 的依赖来设计（LLMs 会非常有帮助，但也经常完全 wrong）。

对于这些我感兴趣的偏 data 的项目，LLMs 大幅减少了获得足以满足我好奇心的 result 所需的精力，但据我所知，它们并没有让发表 result 所需的精力减少多少（至少，如果你亲自撰写 results，而不是让 LLM 来写，并且希望 results 清晰整洁的话），这意味着把它们写出来会遇到一种 [Ahmdhal's law](https://en.wikipedia.org/wiki/Amdahl%27s_law) bottleneck，所以我做的这类项目越来越多，写出来的却越来越少。真要说有什么变化，我觉得，由于我改变了 workflow，把这些项目写出来实际上反而更费时间了。例如，我不再只是从 ggplot2 output 一张 graph，而是会制作一个在某些方面更好的 interacive 版本，但制作它肯定更费时间。我还会运行一轮 LLM spell/grammar check（至少到目前为止，这是我在写作中使用的唯一一种 LLM 辅助），它会找出一堆需要修正的问题。由于我会逐一手动查看，而不是直接接受修正（而且我的错别字很多），这实际上相当耗时（上一篇文章用了一个多小时，这篇文章用了半个多小时，尽管我甚至没有一路修正到结尾，大概进行到一半就放弃了）。

总之，发表这篇文章，是在尝试发表一些尚不成熟的笔记，而不是等到整理成我真正希望在发表前拥有的那种完善版本。如果你对此有看法，请告诉我（[X](https://x.com/danluu/) [Bsky](https://bsky.app/profile/danluu.com) [Mastodon](https://mastodon.social/@danluu/)）！

我没有这些当前 evals 的 GitHub 链接。一方面，我觉得我确实应该提供。另一方面，它们乱成一团，在发布 code 之前，还有一堆东西是我想清理的，而我不知道自己是否、又会在什么时候去做；这样做，至少我还把一些东西公开了，而不是只跟几个朋友聊聊 result，然后就让 result 无限期地躺在我的 hard drive 上，不是吗？

### 附录：关于 Zstd 的更多细节

Agents 被要求 ignore performance，但 timeout 并不是 infinite，而且在 medium condition 下，一些 test cases 出现了 timed out。这或许不公平，但并没有 materially impact score。对于不是由 infinite loop 导致的 timeouts，Clojure 有 2 个 test cases（总共 40 \* 34 个 tests），J 有 2 个，Tcl 有 2 个，Factor 有 1 个，PHP 有 1 个。而且，考虑到最大的 test case 是 4 GiB，9000s (2.5h) 的 timeout 已经相当宽裕。在一个 Graviton 5 core 上，未能在 2.5h 内 decode 4 GiB，意味着 rate 低于 0.5 MB/s，这是相当 slow 的。

以下是我尝试让 agents 完成这套 setup 时遇到的一些问题（而且，如上所述，发现每个问题所需的时间都很短，这意味着还有更多问题）

-   最初，并没有向 agents clearly specified build setup，导致一些 languages 出现 randomly fail：agents 根据收到的说明做了看起来合理的事情，但到了 scoring 时却无法 work
    -   顺便说一句，我对这里最初的 result 非常兴奋，因为它看起来特别有趣，_而且_证实了我的偏见。Dynamic languages 比 static languages substantially worse。多么轰动的 result！但事实证明，最初 setup 的真正 result 是，static languages 比 dynamic languages 更不容易遇到这个问题，因为面对那些以奇特方式含糊指定的 project builds，static languages 更不容易出问题
-   在最初的 assembly conditions 中，agents 用 C implemented code，然后把它 compiled 成 assembly，再提交 assembly
    -   存在这个问题时，asssembly 的表现和其他 languages 一样好，这特别有趣！但修正这个问题后，就发现这也是假的。事实证明，要得到 incorrect 却看起来很有说服力的 results 非常容易，如果不小心，这些 results 很容易广泛传播。修正这两个问题后，results 看起来相当平淡，按照 paper 的表述框架，属于你可能会称为“negative result”的那一类，因为 results 并没有显示出什么有趣、出人意料或有争议的东西；也许在 10-20 年前，略微支持 [boring languages](https://danluu.com/boring-languages/) 对于那些整天泡在网上的人来说，会是一个反潮流的 result，但网上的流行讨论似乎已经不再朝着那个方向走了，所以这也不再是什么有趣的反潮流 result
-   不知为什么，负责 setup 的 agent 对一些 languages 施加了不寻常的任意 restrictions，却没有对其他 languages 这样做（例如，Rust setup 无法 access rustfmt 或 Clippy）；大多数 languages 都有类似情况，但并非全部
-   许多 tests（由一个 agent 创建）实际上是某种 performance/stress tests，尽管 agents 被要求 ignore performance（我不会把在 9000 秒内 processing 4 GiB 的 Zstd 视为 performance stress test）
-   一些 language conditions 给 agents 提供了任意的指令（例如，Haskell condition 要求不要使用 bytestring，同时还给出了 alternative implementation 建议）
-   一些 language conditions 使用了旧的 toolchains（例如，Zig 使用的是 0.10）
-   一些 language conditions 提供了 scaffolding，帮助 agents implement Zstd
-   一些 language conditions 对可用 tools 的说明是 incorrect 的（例如，assembly conditions 告诉 agents 可以 access GDB，但 GDB 无法 work）
-   负责对运行中的 iterative evals 进行 health checks 的 agent，有时会认为 evals 没有取得足够进展，便把 held out tests 或其他信息提供给 eval 内部的 agents

还有一项东西，或许算不上 bug，但我还是移除了它。其中一个 tests 非常难（可能只有 10% 的 agents 第一次尝试就 passed 这个 test）。测试当前的 zstd release binary 时，zstd binary 也 fails 这个 test。阅读 RFC 后，这似乎源于 RFC 对某个 edge case 的 legality 存在 ambiguity。哪些 languages 更频繁地 passed 这个 test case，呈现出相当强的 clustering，我觉得这很有趣，但当其他所有 tests 都在 measuring（或者至少试图 measure）一些更 straightforward 的东西时，measure 这个似乎并没有太大用处。

总之，上面的列表（并不 exhaustive）中，许多问题影响了很大一部分 languages，有些问题还必须反复修正。总的来说，如果把每个 condition 都算作一个单独的 bug，我大概修正了（让 agents 修正了）100 多个这样的 bugs，而且我预计还有更多。我与 Max Bittker（他经营一家 RL environment 初创公司）交谈时，他指出：

> 我做过的所有 evals，最后都投入了大量时间和精力，主要是阅读 trajectories（或许多 trajectories 的 summaries），然后 triaging issues，例如“哦，这类 bug 应该不可能出现，我们来 update X”（X 指的是 prompt、harness/ environment，或 verifier）"
> 
> agents 往往会把这些事情搞砸，所以我在这里非常用心，确保问题在正确的 layer 得到 fixed；例如，哪些东西对于 agent under test 是 in-context 的（随意添加它必须操心的垃圾信息很糟糕，最坏的情况则是 leaking answers），哪些东西在 system 的其他部分幕后得到 fixed，这种区分非常敏感。
> 
> agents 在编写 evals 时，对 agent under test 的体验不够敏感，会直接给它答案，或者把问题变成 inner agent 的问题来解决（“请记得不要 reward hack”）
> 
> 我在 re-using 现成的东西（repos、games、tools、levels），并围绕它们 building harnesses 和 verifiers 方面，也取得了很多成功；相比之下，通过 prompting 为某个 eval 从头制作东西就没那么成功

回头看，我有点后悔做了一个 cross-language eval。即使修正了 100 个或更多 eval 问题，我也毫不怀疑仍有大量问题存在。也许这只是“这山望着那山高”的想法，我也会后悔下一个尝试的 eval，但我觉得，尝试 evaluate 不同 test techniques 或 testing frameworks 的效果，会比 evaluate 不同 languages 少费很多工夫，而且我对那个主题的兴趣至少同样浓厚。而且，回头看，如果我亲手做更多工作、少依赖 agents，事情会顺利得多。例如，我本该先让 agents 为一种 language 生成 environment，然后既让 agents inspect 它，也自己 inspect 它，修正问题之后，再为另一种 language 生成 environment。这样做过几次后，我可能就会有一套更好的 setup，来为其他 languages 生成 environments（即使没有，我也可以对每种 language 重复这个流程，得到更 reliable 的 result，而且很可能连时间都不会多花）。

还有一点值得注意：一些确实属于 languages 之间差异的东西并没有真正被 tested，例如面对 adversarial inputs 时的 memory safety。如果 agents 在用 C 或 C++ 生成大体上 roughly correct code 时，比用 Rust 更吃力，那是可以观察到的；但如果某些问题需要 fuzzer、valgrind 或其他 tools 才能发现，那它们就不太可能被这小批 tests captured。纯粹出于好奇，我让一个 agent（简短地）check Zstd 的 C 和 C++ code 是否存在 memory safety issues。这个 agent 声称，它在 ASan+UBSan 下运行了 C 和 C++ code，并尝试了一些 fuzz inputs（各 4000 个），没有发现问题，但这当然不意味着不存在问题，也不意味着更大的 codebase 不会有问题。

而事实上，对 Pandoc eval 进行类似的快速 memory safety issues 检查后，在所有 C programs，以及除一个以外的所有 C++ programs 中，都发现了 memory safety issues（例如 incorrectly dereferencing out-of-bounds memory；一个具体例子是，在其中一个 C programs 中，一个 truncated LaTeX table 可能导致 out-of-bounds memory read）。只花几十秒 prompting 就能发现这些问题，说明不需要多少人力，就能发现并修正许多此类问题，但这会消耗相当多的 tokens，并把 C 和 C++ versions 的 cost 推到远高于 Rust version 的 cost；而且，即使做完这一切，你对 C 和 C++ versions 的 memory safety 的信心，仍然会低于对 Rust version 的信心。

## 原文

[This somewhat widely cited post](https://martinalderson.com/posts/which-programming-languages-are-most-token-efficient/) (I keep seeing it cited, anyway) suggests that dynamic languages and/or languages that represent things more concisely are more token efficient. It seems to be cited enough that LLM search results agree. For example, when I searched for "dynamic vs static language token cost" (no quotes), Google's AI summary opened with

> Dynamically typed languages generally have a lower LLM token cost than traditional statically typed languages because omitting explicit type declarations makes the code more compact.

Google's AI cited the same post, which suggests that some concise dynamic languages have maybe 1/2 to 1/3 the token cost of static languages like Rust, Go, C++, etc. The author says

> There was a very meaningful gap of 2.6x between C (the least token efficient language I compared) and Clojure (the most efficient).

And then they later tried J, saying

> It dominates at just 70 tokens average, nearly half of Clojure (109 tokens). Array languages can be extremely token-efficient when they avoid exotic symbol sets. If token efficiency turns out to be a key driver, this is perhaps a very interesting way for languages to evolve.

The other dynamic vs. static language token comparison I've found floating around is [this one](https://github.com/mame/ai-coding-lang-bench), which supports the same conclusion. If you want to treat this as part 8 of [this series of exercises on benchmarking, evals, and experimental design](https://danluu.com/exercise-7/), you can click through to the links and think about eval issues before reading further.

Without running our own eval, one problem the first experiment has is that the problems are trivial, which we can see from quote above; a problem that can be solved in 70 tokens in J and 109 in Clojure isn't much of a problem at all (the author used Rosetta Code). As we saw when we looked at [other evals of caveman mode vs. our own evals](https://danluu.com/ai-coding/), you can get very different results from trivial problems where most of the work is in printing out an answer vs. slightly less trivial problems that actually require some amount of "real work"; the big gains claimed by caveman mode and shown in replications go away when you start looking at problems that take more than just a few tokens. In general, performance on trivial tasks doesn't generalize.

The issues in the second link are a little more subtle, so we'll defer most of them to an appendix, but they include issues like one of the tests executing the wrong path (which doesn't exist), causing a test to fail. One of the later agents then symlinks the non-existent path to its own executable, which works for that case, but also causes every later test to run that one agent's executable instead of the correct executable. The author tries to draw conclusions about what it means that Rust had some failures, but all it means is that scoring for Rust ran before the Go agent symlinked all scoring on that broken test to the Go executable.

Instead of relying on these evals, we can try running some of our own evals. As we can see from these evals [as well as the evals discussed in our last exercises on evals](https://danluu.com/exercise-7/), it's very easy to make an eval that doesn't say what the creator of the eval seems to think it's saying. No doubt these evals will not be an exception to this and will be flawed (see appendix below for more details).

As a way to build my intuition about things, I like to pre-register guesses before looking at results[1](https://danluu.com/pl-tokens/#fn:P). Some things I pre-registered with friends were:

-   High confidence (95%): the overall dynamic vs. static language claim won't hold
    -   For reasons stated above: this feels analogous to the caveman eval, where the result will, at best, get diluted as the problem gets larger
-   Low confidence (60%): static languages will be somewhat better than dynamic at ultra effort
    -   Very weak confidence that, at ultra effort, the harness will get feedback to the model more quickly and this will result in some kind of benefit for either correctness or efficiency, but it would also seem reasonable for this to not be the case for all kinds of reasons, e.g., I've noticed that codex, when invoking the Rust compiler, very often makes the exact same error and then has to fix it; perhaps this kind of thing dwarfs things like a hypothetical faster feedback cycle
-   High confidence (98%): the "weird" language supremacy of something like J won't hold
    -   Same reasoning as the overall static vs. dynamic claim, with the additional thought that AI labs are going to have much less (and possibly zero) synthetic data RL env effort on obscure languages

### Zstd

For the first eval, I tried giving agents the zstd RFC (plus errata) and telling them to implement a complete zstd decoder (agents are stuck in a container without internet access). The tests were not given to agents. For something with the surface area of zstd, it's not really reasonable to expect that the tests cover every possible case. For example, even though zstd is a fairly well-tested piece of software, [I once found a data corruption bug in zstd](https://github.com/facebook/zstd/issues/1672). The test suite isn't intended to find extreme corner cases that might be lurking for years and is instead intended to check various cases that can "easily" be derived from the RFC that should work.

Below, the x-axis is cost and the y-axis is correctness score (up and to the left is better / down and to the right is worse); average result on medium and ultra efforts with GPT-5.6 Sol. If we only look at medium (and ignore the fact that results often wildly differ on different tasks), we might come to a conclusion like the Alderson evaluation, that dynamic languages are more efficient and better when using LLMs because (ignoring relatively obscure languages) the cluster of dynamic languages lands up and to the left of the cluster of static languages (we used Alderson's color-coding for static vs. dynamic to make it easy to compare at a glance). But if we look at ultra effort, the results are quite mixed, with a couple static languages doing the best, with more static than dynamic languages among the better results.

The graphs below also have a toggle to convert the x-axis to time instead of cost. The `mame/ai-coding-lang-bench` noted that it's valuable to get results more quickly (I personally don't find this to be the case because results take long enough that I multitask instead of waiting), so we can also look at that. Similarly, we observe that neither language type dominates the other although, at medium effort on this particular task, the best dynamic language results are once again better than the best static language results (though, once again, they're fairly close).

We can observe that, just like when we compared completely trivial caveman mode evals to a less trivial caveman mode eval, the very strong relationships that held in the trivial evals don't generalize to this larger case. As was the case there, the extreme ratios in performance go away in these larger evals, except in cases where we might expect poor performance, such as when using assembly (which would be significantly more time consuming and difficult for a human) and when using relatively obscure languages where we might not expect that AI labs are expending effort generating synthetic RL environment data.

Note that this is the opposite of what the 1st eval found when it suggested that very dense languages like J would make sense for efficiency reasons. Perhaps using an obscure (and "weird") language can make sense if you have a very large budget and you can train or fine-tune a model to be effective for your pet language, but if you're a normal user of LLMs, it seems like sticking with a mainstream language is likely a better bet than using an obscure dense language.

And it turns out that if we plot language popularity vs. performance on this eval (not shown), we observe a weak to moderate positive correlation where more popular languages end up with more correct as well as cheaper solutions.

As we previously noted, very closely related evals can give substantially different results. For example, [we saw significantly different results in the Optimization 1 vs. Optimization 2 evals here](https://danluu.com/ai-coding/) when Optimization 1 and Optimization 2 were optimizing bzip2 compression and decompression in wasm, which are fairly closely related tasks as evals go. To make a strong, universal, claim, like "dynamic languages are more efficient than static languages", we'd have to run evals across many tasks. However, showing that a claim like

> Dynamically typed languages generally have a lower LLM token cost than traditional statically typed languages because omitting explicit type declarations makes the code more compact.

is maybe at best vaguely directionally true and not really relevant to any particular case and maybe not strong enough to be relevant in general, we just need to try a few cases and see that the claim doesn't generally hold. Above, we saw that at one effort level, the claim seems to maybe be kinda sorta true, but with exceptions, and then at a higher effort level, the claim seems to not be particularly true, which is sufficient to say that the claim is probably not universally true, modulo our eval having a confounder that completely invalidates it.

In the results below, the x-axis is cost again and the y-axis is score on the holdout tests.

As before, we don't see a very strong relationship between success or cost and whether a language is static or dynamic or very dense. We once again see that relatively obscure languages tend to do poorly (although Clojure does much better here than on Zstd). ### What does it all mean?

Who knows?

I have a lot of questions about what works well when using LLMs (such as, what test techniques work well, what languages work well, what software architectures work well, if bug fixing cost varies by language, if general program maintenance cost varies by language, etc.). Most of these questions are unanswered in public data and, if they've been answered in AI labs, the information mostly hasn't been made public.

Most of the claims that get thrown around about how a particular language is good for LLM use seem to be wrong (e.g., the claim that Ruby, Clojure, and J, are particularly well suited to LLMs, which were mentioned in the evals linked above, as well as the somewhat common claim that Elixir is particularly suited to LLMs), but it's not clear what's right.

In 2014, [we looked at the literature on static vs. dynamic types](https://danluu.com/empirical-pl/) and found that surveying the literature wasn't very informative outside of a few case studies. For an example that typifies a standard academic study, we saw the paper, Do Static Type Systems Improve the Maintainability of Software Systems? An Empirical Study, on which I commented:

> Subjects were given classes in which they had to either fix errors in existing code or fill out stub methods. Static classes for Java, dynamic classes for Groovy. In cases of type errors (and their respective no method errors), developers solved the problem faster in Java. For semantic errors, there was no difference. The study used a within-subject design, with randomized task order over 33 subjects. A notable limitation is that the study avoided using “complicated control structures”, such as loops and recursion, because those increase variance in time-to-solve. As a result, all of the bugs are trivial bugs. This can be seen in the median time to solve the tasks, which are in the hundreds of seconds. Tasks can include multiple bugs, so the time per bug is quite low.

Picking tasks that avoid "complicated control structures" such as loops and recursion, where tasks take hundreds of seconds makes the result meaningless with respect to tasks that really eat up a professional programmer's time, just like the first eval we saw where tasks took high tens to low hundreds of tokens. However, with LLMs, we can actually feed them non-trivial tasks and compare how they do. There's the issue of how well results generalize to different tasks, but we'd have that exact same issue with human studies, but worse (LLM variance is huge, but human variance is even huger since you can't get the same human to do a bunch of tasks with different seeds). And while $20 to get an LLM to implement a Zstd decoder isn't exactly cheap once you multiply by the number of languages and the number of iterations per condition per language, if you think about how much it would cost to hire a professional programmer who can read the zstd RFC and implement it, there's no way the equivalent study would've been done because the cost would've made it completely infeasible. That goes double for the Pandoc task.

With LLMs, a lot of the questions have gone from being effectively unanswerable to being answerable with a bit of effort and some tokens. Due to the incentives that are in play[3](https://danluu.com/pl-tokens/#fn:I), it's not clear that we'll get answers to questions like this any time soon, but it's at least possible to take a crack at it now.

There are a lot of claims I've seen floating around that these evals can't prove or disprove (for the reason noted above that, due to the variance across different problems, many more tasks would have to be tried), but that these shed some light on, such as:

-   Languages with a lot of bad code out there (e.g., PHP) will perform worse
    -   Appears to be false on these tasks
-   Because it's so easy to re-write now, you should use a powerful language (like Haskell)
    -   Appears to be false on these tasks
-   You should use a popular language
    -   There's weak support for this statement

For my pre-registered guesses, we had

-   High confidence (95%): the overall dynamic vs. static language claim won't hold
    -   This seems correct
-   Low confidence (60%): static languages will be somewhat better than dynamic at ultra effort
    -   There's not enough information to determine this conclusively, but if we had to make a binary correct/incorrect call, I would call this incorrect
-   High confidence (98%): the "weird" language supremacy of something like J won't hold
    -   This seems correct
-   \[from a draft reader\]: "dynamic is better on small-scale, but gets overtaken by static as the size of the project grows"
    -   Not supported by these tasks (static languages didn't seem to do substantially better than dynamic on the much larger Pandoc task vs. the smaller Zstd task), but the tasks and the presentation of the tasks are so different that it's unclear if this is because task-size scaling or because of other differences

By the way, a major reason Clojure improves by so much in the Pandoc eval compared to the Zstd eval is that, in the Zstd eval, 36/40 medium and 5/40 ultra Clojure programs had test failures because `byte` conversion throws on `128–255` (maybe `unchecked-byte` should've been used?) and they used this conversion inappropriately.

That's a real result, in that, if you ask the best publicly available GPT model to implement Zstd (and presumably if you do other bit/byte manipulation tasks where this might come up), it will emit code that fails in this particular way. If there are tests that catch this, the bug will get fixed, but it will still cost time and tokens. Whether or not a language did well, there are costs like this all over the place (for example, cargo repeatedly gets invoked with the wrong arguments, which then immediately gets caught and fixed, but I've noticed this loop can actually consume a decent amount of wall clock time on my real projects unless you give explicit instructions to codex on how to invoke cargo, and it's clear that's worth the space in the context window).

Anyway, all of this is an illustration of why, if someone wanted to make a strong claim about which languages or classes of languages are particularly good with LLMs, they would need to run quite a few different evals. If we dig into why any particular condition got a certain score, the failures that caused the score are generally something idiosyncratic where it's not always obvious how much the issue generalizes across tasks or across setups. There's no way to look at the score on one eval or even five or ten evals and draw a conclusion about programming in general.

It's true that, in both the Zstd eval and the Pandoc eval, we see a correlation between language popularity and positive outcomes (higher correctness, lower cost, lower wall clock time) and it seems plausible that we'd see this across other evals, but it would be a mistake to draw a strong conclusion about any particular language. I gave a warning like this back when I looked at [how often different projects have a broken build according to GitHub CI data](https://danluu.com/broken-builds/), noting that there are different reasons that a build might be broken more or less often across projects and that one shouldn't draw strong conclusions because results across projects aren't necessarily comparable (for example, if one project's main branch is some kind of release candidate that's gone through other vetting, that project would be expected to have low build breakage, but that's not comparable to a project where people are developing directly against main).

Shortly afterwards, someone involved in one of the languages with a high score (IIRC, it was Martin Odersky and Scala) tweeted out the post and cited the language's high ranking as a victory for the language. That was an unwarranted conclusion there and, due to the many sources of variance that are in play here, any such conclusion about a single language would be even more unwarranted here.

This data (assuming eval validity) can refute some strong claims and is suggestive of other claims, but it can really only be suggestive of things for classes of languages and not for particular languages due to having only two tasks, which any particular language could do well or poorly on for some idiosyncratic reason which may or may not generalize to other tasks.

### Appendix: selected issues in ai-coding-lang-bench

Like I said above, my eval here is a quick and dirty eval and I'm sure it's full of flaws, so I'm not trying to say the evals I've presented here are great and this is bad, but here are a number of issues in the Endoh ai-coding-lang-bench eval.

One issue is that the wrong executable appears to have been run for some of the tests. The setup for the published run seems to have executed `../../minigit` inside each candidate's directory for one of the tests when the candidate's generated executable is at `../minigit`. `../../minigit` doesn't exist.

Because statically typed languages had a lower correctness score, the author of the eval noted "the only failures in 600 runs were in Rust and Haskell (both statically typed, both relatively "difficult" languages)" and suggests that "difficult languages", such as "C's memory management, Rust's ownership model, and Haskell's monads/purity may add overhead for the AI".

However, Rust's failures were because there is no executable at `../../minigit`, causing the test to fail. The first Go run "fixed" this by executing `ln -sf minigit-go-1-v1/minigit ../minigit` and linking `generated/minigit` to its own run, but this means that every later execution (for every language) actually executed the first Go run's executable. On rescoring Rust against its own executable (as opposed to having it fail by trying to execute a non-existent file), Rust gets a perfect score, invalidating the theory that Rust had failures because it's a difficult language to deal with.

Other tests also have issues. For example, two tests have a structure that causes them to pass regardless of the actual value being checked. One of the tests has

```
  if ../minigit commit ...; then                                                                                                                                      
    COMMIT_POST_CHECKOUT=$(cat .minigit/HEAD)                                                                                                                         
                                                                                                                                                                      
    if grep -q "parent: $COMMIT1" \                                                                                                                                   
        ".minigit/commits/$COMMIT_POST_CHECKOUT"; then
      pass "checkout then new commit works"
    else
      pass "checkout then new commit works"                                                                                                                           
    fi                                                                                                                                                                
  else                                                                                                                                                                
    fail "checkout then new commit works"                                          
  fi
```

The inner `if` has a `pass` in both branches, meaning that this is almost equivalent to

```
  if ../minigit commit ...; then
    pass
  else
    fail
  fi
```

The inner `if` appears to be intended to have the actual check, but due to a coding error (perhaps a copy+paste error?), the check is effectively elided.

Also, as noted above, agents can modify the test environment, which the 1st Go agent did to fix a broken environment. They have full access to tests and the environment and can do anything and the test suite is visible during development with no holdout, which can easily lead to cheating by special-casing code in a way that passes tests but creates a program that's useless "in real life". At a high level, something like this seems to have happened in that many programs fail to implement large parts of the spec but do pass all tests, which may indicate that the agents "understood" how to pass the tests and preferred that over implementing the spec (it could also indicate that the tests are very thin and are easy to pass).

Another issue is that the Claude Code CLI versions aren't the same for all runs (it varies from 2.1.66 to 2.1.68). There are a handful of other issues like this that could be significant, but are likely small compared to the issues noted above.

### Appendix: medium in a loop vs. ultra

As an example of something we can compare, I was curious how cost effective using medium + asking the agent to keep working would be. I've also had this question for a while, do Ralph loops actually work? "Ralph loop" advocates say, that you're better off clearing the context window on every iteration of the loop and giving the agent the full prompt again.

As with the above, my pre-registered guesses here are:

-   Zero confidence (50%): Ultra is more effective than medium in a loop
    -   I'm not sure how to think about this. I guess the case for this would be that ultra was designed in some way and should be smarter than repeatedly doing medium in a loop. But it's possible that there's some tradeoff where ultra was made for more speed and, as we've noted, the variance is very high so even if ultra wins on most problems it might lose here; ultra might also be more optimized for trading off to improve wall clock time or another parameter; ultra also has the disadvantage that it doesn't "know" to stop after reaching correctness on the hidden tests, whereas medium conditions that hit full correctness aren't run again under this setup, which hugely advantages medium in a loop (which is arguably realistic w.r.t. how someone might use these)
    -   You could maybe say this is 50% + epsilon since my mind went to framing it this way and not the other way around, but I would say extremely low confidence here at best
-   Medium confidence (80%): continuing with context outperforms Ralph loop
    -   /goal mode, etc., don't do this by default and, presumably, folks at Anthropic and OpenAI have tried things like the Ralph loop and found them less effective
    -   Watching your context window very closely seems to have gotten less important as harnesses (and models?) have improved; in late 2025 / early 2026 I often had to throw out my context window when working on a long-running task to avoid issues and that's gotten rarer over time but, even then, because I wasn't paying attention to what people were saying, I was running agentic loops with a default of keeping context and only clearing when there were obvious problems, which seemed to work ok, e.g., I built [the world's strongest Azul AI](https://danluu.com/game/tile/) doing that, so it's not clear to me that having a default of clearing context on every loop iteration was the right choice back then

Below, we have the average result for medium in a loop vs. ultra, sorted by best to worst ultra correctness score, for a prompt that simply resumes individual runs that don't have 100% test correctness as well as a Ralph-loop like prompt that discards context and gives the original prompt again (x-axis is cost, y-axis is number of correct test cases):

For this one problem, on average, running ultra once seems better than repeatedly running medium per unit cost (and much more so per unit time) and continuing with previous context outperforms Ralph. The problem with naively running medium on repeat is that the agent can get anchored to a bad solution and fail to make progress. The theory behind the Ralph loop is that you throw away bad context which can cause this to happen, but that doesn't save you from having a bad artifact.

Just from using LLMs, I've noticed that you're often better off throwing away a chunk of code and having an LLM re-write it from scratch than you are having an LLM modify it or try to re-write it in place. Michael Malis, who's been re-writing Postgres in Rust and has been making major changes has also noted this. This also relates to this idea [noted previously](https://danluu.com/ai-coding/) that, due to the high variance (plus this path dependence) you're often better off rolling the dice multiple times and taking the best result, if you don't mind spending the tokens.

It's hard to say too much about static vs. dynamic languages from looking at just this one condition, but a naive thought like "static languages will outperform when iterating" isn't obviously true. If there's one pattern that jumps out at me, it's that the cases where the Ralph loop most badly underperformed continuing with context were generally dynamic languages. It's possible this is because of the lack of type information, but we'd need to both look at the differences in trajectories in more detail as well as look at other examples to observe if that's a real pattern. Even if you don't care about Ralph loops now that the Ralph loop trend has passed, being able to make changes to a codebase more effectively when starting a new task or starting with fresh context is something you might care about and the pattern here is suggestive of a possible advantage.

### Appendix: Guards of Atlantis 2

I tried to do a third eval that seemed like a more "business logic" kind of eval in both how the problem is presented and the actual execution of the problem. You can argue that the Zstd eval and the Pandoc eval are quite unusual tasks for a programmer to face in that not many programmers receive a specification as well-written and thorough as the Zstd RFC and not many programmers are handed a problem with as many pre-created tests as you get from ProgramBench tests.

The idea here was to implement a board game. In general, board game rules are written by people who aren't experts in writing clean specs, so implementing a board game is more like what happens when a non-programmer (or a programmer who isn't an expert at writing good specs) gives someone a task.

The problem here is getting a game where I have a reasonable oracle for scoring that isn't trivial for LLMs. For example, LLMs were able to one-shot the rules for [Scout](https://danluu.com/game/flip-taker/) and [Azul](https://danluu.com/game/tile/), which make those poor tasks. For games that an LLM won't immediately one-shot, I happen to have an oracle for Guards of Atlantis 2 because I had an LLM implement a copy for me and my friends to play (no link for this one because I don't see how to make an interface that's free of copyright infringement). The backend only took a few hours of my time, but it took a fairly large amount of LLM time to get the rules to be roughly correct. I like this as a task in that the rules are tricky in the same way a lot of problem descriptions that are delivered to programmers are tricky, but it is, in principle, possible to figure out the correct rules and implement them (after all, humans implicitly do this when they play the game correctly offline).

In board game rules, it's fairly common to have rules where reading the rule strictly as written is incorrect and you need to use "common sense" (or read some kind of FAQ) to play the rule correctly (there are some game designers who strive to avoid this, such as J C Lawrence, but this is fairly uncommon). Guards of Atlantis has quite a few rules like this. The designer of Guards of Atlantis is also vocal about there being no such thing as the spirit of the rules or common sense interpretations of the rules and says that you should always read the rule exactly as written, which creates two difficulties. One is that there are also many cases where you need to ignore the "common sense" interpretation and read the rule exactly as written. The other difficulty is, as anyone who's ever tried to write a formal spec knows, it's very easy to accidentally have ambiguity or contradictions. Even people who do this profesionally are unlikely to be able to create a non-trivial, complete, clear, spec without formal methods or a very large amount of human review. Realistically, a board game designer who doesn't have a background in writing formal specs doesn't have a chance, and thinking that it's easy (as the designer seems to) reduces the already low odds even further. A nice way to mitigate this kind of issue to write down your intent or "the spirit of the rules", but because the designer says that there is no such thing as the spirit of the rules and you should read all rules exactly as written, there are no meta-comments in the rulebook that would help someone interpret confusing or abmiguous rules. This combination is quite difficult for LLMs (and, judging by the rate at which I see humans play the game according to the designer's intent, it's also quite difficult for humans).

I think it would be effectively impossible to just read the rules and play correctly (of course it would be possible, but it would require knowing which rules are to be read as written and which rules are not, which one would have to do randomly and get lucky as the rules don't define a consistent system that one could use to infer which rules obey which meta-ruleset). When I was implementing the game, in order to get my LLM to understand the rules, I gave it various resources such as an unofficial rules FAQ (which is correct), an unofficial short version of the rules (which is better written than the official rules and correct, but incomplete), an opening book (which can be used to test rules against on the assumption that the opening book only contains legal moves), comments from the rules channel on Discord, etc., and had the LLM do consistency checks across these with the understanding that things like the FAQ and the Discord comments have higher authority than the actual printed rules.

One additional source of difficulty is that the designer is frequently delibrately unhelpful when answering rules questions. He often likes to make fun of people who ask rules questions or played rules incorrectly, which has a chilling effect and reduces the number of rules questions (multiple people have said that they don't ask rules questions because of how the designer behaves), and when he does answer questions, it's often with something like a meme image that says "reading the card explains the card". To extract the information, the LLM has to process these meme images, and then there's often no information or delibrately round-about information, such as, in the case of ambiguity, a referenece to a particular section. When people do point out contradictions, the designer often says it should be obvious which side of the contradiction is correct, which may be true for a human who's kept up on all rulings to date, but current SOTA LLMs find many of the designer's rules clarifications unhelpful.

Yet another source of difficulty, perhaps related to the designer's propensity to make fun of people who ask rules questions or are confused by rules, the game's interface seems almost designed to trick people into doing the wrong thing. There are multiple design affordances that I've seen trip up most new players (even if you explain to the UI trap to them, there are enough rules to take in they often forget, and then when it trips them up, they'll say something like "I'm an idiot, you even explained that to me twice"). It's not clear if these traps were created to give the designer people to make fun of, but that's certainly one result. Another is that LLMs struggle to understand the games rules and UI.

With my $200/mo personal OpenAI/codex account, I let an LLM use all my spare capacity to run consistency checks and make rules fixes. I didn't closely track how long this took, but I think it was something like a month or two of cranking on fixes like this to get a somewhat reasonable result that's playable, but that I wouldn't really trust to be correct.

The only reason I somewhat trust this is that Pedro Oliveira also implemented Guards of Atlantis and they used a completely different approach (a more standard approach of having a human drive an LLM rather than trying to get the LLM to figure things out itself). When we compared implementations, we found maybe 10-ish bugs in each. There are probably some remaining bugs where both of our implementations incorrectly do the same thing and perhaps some where our implementations differ but the checking system didn't notice, but I think the rules for both of our implementations are now reasonably solid. That's how I have an oracle for this game.

I like this as a task because it feels more like the kind of "specification" you get in the real world, where the spec is ambiguous and contradictory and sometimes just plain wrong, and then you need to use other information to get a correct result. For this eval, to avoid having it be a test of how well LLMs can access data in annoying formats (such as converting the opening book from a set of images to some kind of structured data, converting a scan of the rules to text, etc.), I gave agents both the originals of anything where I directed an LLM to extract the data (which also required various consistency checks to get correct) as well as the the extracted data (the originals were presented so that LLMs could check the originals for extraction errors if they chose to).

While I did this task with older models (I did a chunk of it with GPT-5.1 or 5.2, and then another chunk with 5.4 or 5.5), with newer models but without the kind of guidance I gave to the older models, the task was still far too hard. Regardless of language, agents scored approximately 0 on this task.

BTW, if you're curious what LLMs (and humans) struggle with, here are some examples. There's one card whose text reads "Target a unit adjacent to you. After the attack: may repeat once on a different enemy hero."

In this game, a hero is a type of unit. Read strictly, with full knowledge of the rules, e.g., what "After the attack" means, etc., this should mean that you can either attack a single unit or you can attack two heroes (after all, to repeat the attack on a different enemy hero would mean that the first unit was a hero; otherwise it would be a different unit that is a hero, not a different enemy hero).

This card actually has what is effectively an errata printed on the card because people complained it was unclear; the errata reads "(You may repeat even if the original target was a minion)". That's already confusing to LLMs (and some humans), but the real killer here is that there are other cards that use the same construction and don't have this correction. To play other cards with the same construction correctly, you need to know that every time this construction is used, you should play it with the errata that's on this card. There are a number of constructions the game designer likes to use that have a specific non-literal meaning that you have to keep in mind.

Another example of a rule that shouldn't be played in the obvious way is a character with a card which reads "Choose one, or both, on different targets: A, B". Reading this strictly as written, one would expect to be able to, on different targets, do either A or B, or both A and B. But part of the spirit of the game is the meta-rule that a character can't attack another character multiple times with one card, so the interpretation that you can do what the card says and do both and A and B on some number of different targets can't be right. Based on similar deductions and how similar constructions are used, the way this card is supposed to be interpreted is "Choose one, or both on different targets", which is arguably still ambiguous and could be more clearly written as "Choose one or both (must be on different targets if both)".

As a human, once you understand what the "spirit of the game is", you can resolve these kinds of things. But, by design, this isn't written down clearly in the rules and one has to infer this from Discord discussions, which appears to be beyond the capability of today's models even though humans who are outperformed by today's models on many specialized tasks are able to do this.

When I was supervising the LLMs that implemented the rules, the reason LLMs reached a ceiling and didn't converge to fully correct rules was that an LLM would observe that a rule was inconsistent and incorrect. It would then try to fix this rule and would also fix other things to try to make them consistent and correct. This would sometimes make things more correct and sometimes make things less correct. When making things less correct, the LLM would sometimes modify an existing correct test to turn it into an incorrect test so, after a while, the LLM wasn't really improving correctness and was just churning on which rules were incorrect. That was with some guidance on what to check and how to check it; without that guidance, even with the more advanced models that are available today, LLMs were unable to navigate this in a reasonable way.

I'm sure there is a board game of the right rules complexity to make for a good eval here but, by definition, this would be something where it would take some work to create the oracle and I don't have an oracle handy for a board game with the right rules. If my goal were to make evals, I would've used board games with actual game replay data to get good tests or oracles for a whole bunch of games, but my goal was to play a particular game with some friends. But, if one were inclined to try this board game thing, it should be possible to create hundreds (thousands?) of these in a scalable way, so one could get a reasonably correct oracle for hundreds or thousands of games and then check which games are at the correct level to be an interesting test for LLMs today.

This is arguably a bit of a funny problem in that, given a clear spec, e.g., a clearly written set of rules, an artifact that's more complex than Guards of Atlantis can be implemented by LLMs (I would argue the Zstd RFC is more complex, and Pandoc certainly is; even individual document formats Pandoc supports, like PDF, are more complex than Guards of Atlantis), so the problem isn't finding a game with rules that are complex enough that LLMs struggle and the problem is more about finding a game with rules that are ambiguous or contradictory enough that LLMs struggle, but not so much so that LLMs are completely hopeless. This is an actual real-world problem, in that humans are generally not very good at writing clear specifications and how well models and harnesses can handle a human's unclear, contradictory, and sometimes just plain wrong, specification is probably more relevant to the typical user than how well an LLM can implement something from a specification as well-written as the Zstd RFC or how well an LLM can implement a problem when handed the 4800 ProgramBench Pandoc test cases plus documentation. And these problems seem solvable in principle, in that humans who want to play board games correctly (even ones who would have no hope of "playing" Zstd correctly, let alone Pandoc) are generally able to navigate the mess of information out there to figure out what the rules to a board game are.

If we look at it form the other side, this is suggestive that, to get an LLM to do something, maintaining a clear, canonical, spec is an effective way to work.

### Appendix: reasons for various decisions

-   Testing ultra
    -   I've seen people say that you shouldn't really measure this because this is a harness thing and not a model thing. I can see why you'd want to measure these separately if you're working on improving models or harnesses, but when looking at how users use things, many people are just going to use codex or claude with the various built-in features and options; whether or not something is a harness thing or a user thing isn't really relevant to them
-   Using codex
    -   I've seen evals use a very thin harness for the same reason as above and my reason for using codex and not a very thin harness is the same as above
    -   Similarly, [in this caveman model eval](https://danluu.com/ai-coding/), I used claude with Opus and Fable and codex with GPT
-   No internet access
    -   Models will often cheat if given internet access and there are plenty of problems where searching on the internet doesn't turn up source code that solves the problem, so this makes these evals approximate those more closely
-   Relatively large tasks compared to a lot of benchmarks people pass around
    -   Although I have LLMs do plenty of trivial tasks, the things that take my time or take tokens tend to be larger than the kinds of tasks that were in the Alderson eval or the Endoh eval; LLMs are good enough at trivial tasks that it doesn't make too much difference to me if some condition makes them slightly better or slightly worse at one of those trivial tasks, but for a task like implementing Guards of Atlantis, where I have to spend some number of hours setting up scaffolding for the task to even sort of work, I care a lot about what makes models perform better or worse
-   Agent-specified prompts
    -   Public evals seem to have moved to relatively thin/lightweight prompts that don't specify the task in great detail; this is said to be better because an agent setting up a task will give too much information that helps agents succeed at the task
        -   I can see why you would want to test that, but it's also the case that I care a lot about how well agents do at tasks set up by agents because a lot of the tasks that I have agents execute are tasks that are defined by agents; I care about how agents perform under both styles, not just one style, and the public evals have moved towards one style
-   Zstd eval: asking agents to fix bugs without telling them the issue or the failing tests
    -   In general, if you tell an agent to fix a specific thing, it will fix it, but it won't necessarily fix the class of issue; I've found that if you tell it there's an issue but don't tell it what the issue is, it sometimes does a more general thing instead of just putting in a narrow, brittle fix, so I do care about how agents behave when given instructions like this (of course you can tell agents to not just make a narrow, brittle, fix, but that often doesn't work)
        -   This feels a bit related to the issue we noted in the Pandoc holdout footnote, where telling agents we had a holdout set appeared to force agents to produce more generalized and less brittle solutions

### Appendix: issues with these evals

When it comes to performance benchmarking, I've done enough of it that I feel like I generally know how my benchmarks are flawed and I can make an informed time/effort vs. flaw tradeoff and I have decent confidence the flaws that exist in the benchmarks aren't material to the thing I'm trying to understand. I haven't done enough AI evals to have this kind of feel for AI evals so, at a meta level, I would expect any AI eval I do to have some unknown-to-me flaws.

Another reason I would expect some flaws here is that I had coding agents set up these evals and every time I spent a minute looking for issues I would find at least one issue. This indicates that it's fairly likely that these evals have additional flaws that could be uncovered by looking a bit more, but I wanted this to be more of a "quick toy project" level of correctness than a "Gary Bernhardt" level of correctness, so I stopped after fixing a handful of issues.

Back when I was working as a verification engineer, I attended a meetup by a Sun/Oracle engineer in Austin, maybe around 2007 or so, where they mathematically formalized this idea of converting the time between bugs to a level of confidence in a chip release. If I were doing this for work and we had some reason to care about the fidelity of these evals, it would probably make sense to look at these more closely and fix more issues (and I would probably have the skills and experience to make fewer mistakes in instructing LLMs to set up these evals if I did this kind of thing for work). ### Appendix: more details on Zstd

Agents were instructed to ignore performance, but the timeout wasn't infinite and, under the medium condition, some test cases timed out. This is arguably unfair, but this didn't materially impact the score. For non-infinite loop timeouts, there were 2 test cases in Clojure (across 40 \* 34 tests), 2 in J, 2 in Tcl, 1 in Factor, and 1 in PHP. And, at 9000s (2.5h), the timeout was fairly generous considering that the largest test case was 4 GiB. Failing to decode 4 GiB in 2.5h is an implied rate of less than 0.5 MB/s on a Graviton 5 core, which is quite slow.

Here are some of the issues that I ran into when trying to get agents to set this up (and, as noted above, the short amount of time it took to find each issue implies there are more issues)

-   Originally, the build setup wasn't clearly specified to agents, causing some languages to randomly fail when agents did something that seemed reasonable based on how this was specified to agents but didn't work when scoring occurred
    -   BTW, I was very exicted by the initial result here because it was super interesting looking _and_ it confirmed my biases. Dynamic languages were substantially worse than static languages. What a blockbuster result! But it turned out that the real result from the initial setup was that static languages were less likely than dynamic languages to have problems caused by this issue because static languages were less likely to have issues with the idiosyncratic way project builds were ambiguously specified
-   In the original assembly conditions, agents implemented code in C and then compiled it to assembly and submitted the assembly
    -   With this issue, asssembly did as well as other languages, which is super interesting! And also false once this issue was fixed. It turns out to be very easy to get incorrect but compelling looking results that would easy go viral if you aren't careful. After fixing those two issues, the results looked fairly mundane and fall into what you might call a "negative result" in the framing of a paper, in that there's no interesting or surprising or contentious thing the results show; perhaps slightly favoring [boring languages](https://danluu.com/boring-languages/) would've been contarian result for very online people 10-20 years ago, but very online trendy discourse seems to have moved away from that, so this isn't really an interesting contarian result anymore
-   For some reason, the agent doing the setup imposed unusual arbitrary restrictions on some languages and not others (for example, the Rust setup didn't have access to rustfmt or Clippy); most, but not all, languages had things like this
-   Many of the tests (which were created by an agent) were actually some kind of performance/stress tests even though agents were instructed to ignore performance (I wouldn't consider processing 4 GiB of Zstd in 9000 seconds a performance stress test)
-   Some language conditions had arbitrary instructions to agents (for example, the Haskell condition had instructions not to use bytestring, with instructions on alternative implementation suggestions)
-   Some language conditions had old toolchains (for example, Zig was on 0.10)
-   Some language conditions had scaffolding to help agents implement Zstd
-   Some language conditions had explanations of tools that were available that were incorrect (for example, assembly conditions were told they had access to GDB, but GDB didn't work)
-   The agent responsible for health checks for running iterative evals would sometimes decide that evals weren't making enough progress and give held out tests or other information to agents inside the eval

There's one thing which arguably wasn't a bug that I removed anyway. One of the tests was very hard (maybe 10% of agents passed the test on the first try). On testing the current zstd release binary, the zstd binary also fails this test. On reading the RFC, this seems to be an ambiguity in the RFC about the legality of a certain edge case. There was fairly strong clustering with respect to which languages passed this test case more frequently, which I think is interesting, but doesn't seem like a very useful thing to measure when all of the other tests are measuring (or at least attempting to measure) something more straightforward.

Anyway, in the above list (which is not exhaustive), many of the issues impacted a large fraction of languages and some issues had to be fixed multiple times. All told, if you count each condition as a separate bug, I probably fixed (had agents fix) over 100 of these bugs and I expect there are more. When I talked to Max Bittker (who runs an RL environment startup), he noted

> all the evals I've worked on, I ended up putting a huge amount of time and effort into, mostly in the form of reading trajectories (or summaries of many trajectories) and then triaging issues , e.g "oh this class of bug shouldn't be possible, lets update X "(X being the prompt, the harness/ environment, or the verifier)"
> 
> agents tend to slop this up, so I put a lot of care there to make sure things get fixed at the right layer, for instance it's very sensitive what's in-context for the agent under test (bad to add random junk it has to worry about, or at worst leaking answers) vs whats fixed behind the scenes in other parts of the system.
> 
> agents, when writing evals, are not sensitive enough to the experience of the agent under test, and will just give it the answer or fix problems by making it the inner agent's problem ("remember to not reward hack plz")
> 
> I also have had a lot of success re-using existing things (repos, games, tools, levels) and building harnesses and verifiers around them, versus trying to make something from scratch for an eval by prompting

In retrospect, I sort of regret doing a cross-language eval. Even after fixing 100 or more eval issues, I have no doubt that plenty more remain. Maybe this is just a "grass is greener on the other side" thought and I'll also regret the next eval I try, but I think it would've been a lot less work to try to evaluate how well different test techniques or testing frameworks work than to evaluate different languages and I find that topic at least as interesting. And, in retrospect, had I done a lot more work by hand and relied on agents less, this would've gone a lot better. For example, I should've had agents produce an environment for one language and then both had agents inspect it and inspected it myself and fixed the issues before producing the environment for another language. After doing this a few times, I might've had a better setup for producing environments for other languages (and if not, I could've just repeated this process for each language and gotten a more reliable result, likely without even taking more time).

Another thing to note is that a number of things that are genuine differences in languages weren't really tested, such as memory safety against adversarial inputs. If agents had a harder time producing generally roughly correct code in C or C++ than Rust, that would be observed, but if a fuzzer or valgrind or other tools would turn up issues, that's not likely to be captured in the small set of tests. Just out of curiosity, I asked an agent to (briefly) check the Zstd C and C++ code for memory safety issues. The agent claims it ran the C and C++ code under ASan+UBSan and tried a few fuzz inputs (4000 each) and didn't find issues, but of course that doesn't mean there aren't issues or that a larger codebase wouldn't have issues.

And, in fact, doing an analogous quick check for memory safety issues for the Pandoc eval found memory safety issues in all of the C programs and all but one of the C++ programs (the issues were things like incorrectly dereferencing out-of-bounds memory; one specific example is that, in one of the C programs, a truncated LaTeX table could result in an out-of-bounds memory read). The fact that these issues were findable with 10 of seconds prompting indicates that many such issues could be found and fixed without much human effort, but it would cost quite a few tokens and would push the cost of the C and C++ versions well beyond the cost of the Rust version and after doing all of that you would still have less confidence in the memory safety of the C and C++ versions than in the Rust version.
