# 为简单架构辩护｜In defense of simple architectures

---

## 正文

Wave 是一家 $1.7B 的 company，拥有 70 名 engineers[1](https://danluu.com/simple-architectures/#fn:R)，其 product 是一个对 numbers 进行 adds 和 subtracts 的 CRUD app。与此相应，我们的 architecture 是 standard CRUD app architecture，即一个位于 Postgres 之上的 Python monolith。[从 simple architecture 开始，并以 simple ways 来 solving problems](https://twitter.com/danluu/status/1462607028585525249)，在可能的情况下这样做，让我们得以 scale 到这一规模，同时 engineers 大多专注于为 users delivers value 的工作。

Stackoverflow 对一个 monolith 进行了 scaled up，效果很好（[2013 architecture](https://nickcraver.com/blog/2013/11/22/what-it-takes-to-run-stack-overflow/) / [2016 architecture](https://nickcraver.com/blog/2016/02/17/stack-overflow-the-architecture-2016-edition/)），最终以 $1.8B 被 acquired。如果我们看的是 traffic 而不是 market cap，Stackoverflow 在 internet 上属于 traffic 最高的前 100 个 sites（关于建立在 monoliths 之上的其他许多有价值的 companies 的 examples，[请看这条 Twitter thread 的回复](https://twitter.com/danluu/status/1498678300163588096)。我们的 web traffic 不多，因为我们是一个 mobile app，但 Alexa 仍将我们的 website 排在前 75k，尽管我们的 website 基本上只是供人们找到 app 的一种途径，而且大多数人甚至不是通过我们的 website 找到 app 的）。

有些 applications 的 demands 会使一个位于 boring database 之上的 simple monolith 根本不可行，但对于大多数 applications，即使 traffic 达到 top-100 site 的水平，computers 也足够 fast，能让 high-traffic apps 通过 simple architectures 来 served，而这些 architectures 通常比 complex architectures 更便宜、更容易 created。

尽管 simple architectures 的 effectiveness 好得惊人，大多数报道却都聚焦于 complex architectures。例如，在最近一次综合性的 tech conference 上，有六场 talks 讨论如何 build complex、microservice-based 的 architectures，或如何处理它们的 side effects，却没有任何一场讨论如何 build out 一个 simple monolith。关于 quantum computing 的 talks（有一场）甚至比关于 monoliths 的 talks（零场）还多。规模更大的 conferences 也类似；最近在 SF 举行的一次面向 enterprise 的 conference 上，有两位数的 talks 讨论如何应对 sophisticated architecture 的 complexity，却没有任何一场讨论如何 build 一个 simple monolith。上次参加那个 conference 时，让我惊讶的是，有那么多 attendees 所在的 enterprises 拥有原本可以用 simple architectures 来 built 的 low-scale applications，却照搬了 conference 圈子和 HN 上流行的最新、最受推崇的 sophisticated techniques。

我们的 architecture 非常 simple，我甚至不打算费心画 architectural diagram。相反，我会谈谈我们做的几件 boring 的事情，它们帮助我们让一切保持 boring。

我们目前使用的是 boring、synchronous 的 Python，这意味着我们的 server processes 在等待 I/O（例如 network requests）时会 block。我们以前尝试过 Eventlet，这是一个 async framework，理论上可以让我们从 Python 获得更高的 efficiency，但遇到的 bugs 实在太多，以至于我们认定：与其承受处理 Eventlet issues 所带来的 operational pain，不如承担等待 events 的 CPU 和 latency cost。还有其他[知名的 Python async frameworks](https://twitter.com/mcfunley/status/1194713713330122752)，但那些 frameworks 的 users 在大规模使用时，也经常报告[大规模使用这些 frameworks 所造成的严重后果](https://twitter.com/mcfunley/status/1194715290841432064)。使用 synchronous Python 是昂贵的，因为我们花钱购买的 CPU 在 network requests 期间除了等待之外什么也不做；但由于我们每月只 handling 数十亿次 requests（目前如此），即使使用 Python 这样的 slow language，并支付 retail public cloud prices，这方面的 cost 也很低。我们的 engineering team 的 cost 完全 dominates 我们所 operate 的 systems 的 cost[2](https://danluu.com/simple-architectures/#fn:B)。

我们没有承担把 monolith 变成 async 的 complexity，而是将 long-running tasks（我们不希望 responses 在这些 tasks 上 block）交给一个 queue。

有一个地方我们无法像希望的那样保持 boring，那就是我们的 on-prem datacenters。过去只在 Senegal 和 Côte d'Ivoire 经营时，我们完全在 cloud 中 operate，但随着我们 expand 到 Uganda（以及未来更多的国家），我们不得不 split 我们的 backend，并 deploy on-prem，以遵守当地的 data residency laws and regulations。这算不上 simple operation，但任何用 complex service-oriented architecture 做过同样事情的人都知道，比起我们采用 complex service-oriented architecture 时的情况，这个 operation 要 simple 得多。

另一个方面是我们不得不自行 build（而不是 buy）的 software。刚起步时，相比 building software，我们强烈倾向于 buying software，因为一个只有几名 engineers 的 team 无法承担 building 一切所需的 time cost。那在当时是正确的选择，尽管[“buy” 选项通常给你的是不能 work 的 tools](https://danluu.com/nothing-works/)。当我们无法说服 vendors 去 fix 那些对我们构成 critical blockers 的 showstopping bugs 时，[build 更多我们自己的 tools，并在更多领域 maintain in-house expertise，确实是有道理的](https://danluu.com/in-house/)，这与 company 只应在其 core competency 领域选择 “build” 的 standard advice 相矛盾。其中许多 complexity 是我们不愿承担的，但在一些 product categories 中，即使经过相当广泛的研究，我们仍找不到任何似乎有望提供适合我们的 product 的 vendor。公平地说，我们的 vendors 为了给我们 deliver 一个 working solution 而需要 solve 的 problem，比我们自己需要 solve 的 problem 要 complex 得多，因为我们的 vendors 承担的是为每个 customer solving a problem 的 complexity，而我们只需要为一个 customer，也就是我们自己，solve 这个 problem。

我们在最初几个月的 operation 中犯过一个至今仍带来一些 cost 的错误，就是没有仔细 delimiting database transactions 的 boundaries。在 Wave 的 codebase 中，SQLAlchemy database session 是一个 request-global variable；每当一个 DB object 的 attribute 被 accessed 时，它都会 implicitly begins 一个新的 database transaction，而 Wave 的 codebase 中的任何 function 都可以对这个 session 执行 call commit，从而使它 commit 所有 pending updates。这让我们难以 control database updates 发生的时间，增加了 subtle data-integrity bugs 的发生率，也让我们更难借助 database 来 build 诸如 [idempotency keys](https://brandur.org/idempotency-keys) 或 [transactionally-staged job drain](https://brandur.org/job-drain) 这样的东西。这也增加了我们意外 holding open long-running database transactions 的 risk，而这可能[使 schema migrations 在 operationally 方面变得 difficult](https://gocardless.com/blog/zero-downtime-postgres-migrations-the-hard-parts/)。

有些选择我们并不确定是否妥当（也就是说，我们正在考虑改变这些选择，或者会建议其他从头开始的 teams 考虑不同的做法），包括使用 RabbitMQ（对于我们的用途，Redis 作为 task queue 大概同样能 work 得很好，而仅使用 Redis 就能 reduce operational burden）、使用 Celery（对于我们的 use case，它是 overcomplicated 的，而且牵涉数次 outages，例如 version upgrades 期间的 backwards compatibility issues 所导致的 outages）、使用 SQLAlchemy（它使 developers 很难理解他们的 code 将会 emit 哪些 database queries，导致各种难以 debug、并带来不必要 operational pain 的情况，尤其是与上文提到的 database transaction boundaries 有关的情况），以及使用 Python（由于我们创始 CTO 的 technical background，它是最初的正确选择，但它的 concurrency support、performance 和 extensive dynamism 让我们怀疑，它是否适合 large-scale backend codebase）。这些都算不上重大错误，而且对于其中一些选择（例如 Python），其不利之处足够小，以至于对我们来说，继续承担增加的 maintenance burden，比投入资源 migrating 到理论上更好的东西更便宜；但如果我们今天从头开始一个类似的 codebase，我们会认真考虑它们是否是正确的选择。

在一些方面，我们对自己的选择感到满意，尽管它们听起来可能不是最 simple 的 feasible solution：我们的 API 使用 GraphQL，我们的 transport protocols 曾有一段时间采用 custom protocol，而我们的 host management 使用 Kubernetes。在 transport protocols 方面，我们曾使用一个 runs on top of UDP 的 custom protocol，并以 SMS 和 USSD 作为 fallback，[原因是这场 talk 中所述的 performance 考量](https://www.youtube.com/watch?v=EAxnA9L5rS8)。随着 HTTP/3 的 rollout，我们已经能够用 HTTP/3 来 replace 我们的 custom protocol，而且通常只在最近 Mali 的 internet shutdowns 这类 events 中才需要 USSD。

至于使用 GraphQL，我们认为对我们而言，pros 大于 cons：

Pros（优点）：

-   对 exact return type 的 Self-documentation
-   针对 exact return type 的 Code generation 会 leads to 更 safer 的 clients
-   GraphiQL interactive explorer 带来了 productivity 上的提升
-   我们的各种 apps（user app、support app、Wave agent app 等）大多可以 share 一个 API，从而 reducing complexity
-   Composable query language 使 clients 能够在一次 single packet roundtrip 中 fetch exactly 它们需要的 data，而不必 build 大量 special-purpose endpoints
-   对于什么才算 RESTful API，不再需要 bikeshedding；这正是其 Eliminates 的争论

Cons（缺点）：

-   在我们 adopted GraphQL 时，GraphQL libraries 并不出色（base Python library 是 Javascript 那个 library 的 port，因此并不 Pythonic；Graphene required 大量 boilerplate；而 Apollo-Android produced 的 code 则是 very poorly optimized 的）
-   Default GQL encoding 是 redundant 的，而我们非常在意 limiting size，因为我们的许多 customers 都有 low bandwidth

至于 Kubernetes，我们之所以使用 Kubernetes，是因为当时知道，如果业务取得成功（事实的确如此），而且我们继续扩张，我们最终会进入要求我们在境内 operate services 的国家。具体 regulations 因国家而异，但我们已经在进入一个重要的 African market，那里要求我们在该国境内 operate 我们的 “primary datacenter”；还有其他国家的 regulations 会提出例如这样的要求：我们必须能够 fail over 到该国境内的 datacenter。

对我们而言，telecom integrations 是一个存在不可避免的 complexity 的领域。理论上，我们会为所有事情使用一个 SaaS SMS provider，但[主要的 SaaS SMS provider 并非在 Africa 的所有地方都 operate](https://youtu.be/6tb8ALAvodM?t=196)，而且在所有地方都使用它们的 cost 将是 prohibitive 的[3](https://danluu.com/simple-architectures/#fn:C)。如果我们所有的 SMS needs 都使用 SaaS SMS provider，前面关于 engineers 的 compensation cost 会 dominates 我们的 systems 的 cost 的说法就不成立了；提供 telecom integrations 的 team 所节省的费用，足以多次抵偿其自身 cost。

通过让我们的 application architecture 尽可能保持 simple，我们可以将 complexity（以及 headcount）budget 用在那些承担 complexity 能让业务受益的地方。除非有充分理由增加 complexity，否则就尽可能 simple 地做事——遵循这一想法，让我们能够用并不算多的 engineers 建立起相当大的业务，尽管我们经营的是通常被认为很难进入的 African finance business。我们将在未来的一篇文章中讨论这一点（我们最早、最有帮助的 advisers 之一，曾提供对 Wave 的成功至关重要的建议，但他最初认为 Wave 是个糟糕的 business idea，并建议 founders 换一个，因为他预见到了太多潜在困难）。

## 原文

Wave is a $1.7B company with 70 engineers[1](https://danluu.com/simple-architectures/#fn:R) whose product is a CRUD app that adds and subtracts numbers. In keeping with this, our architecture is a standard CRUD app architecture, a Python monolith on top of Postgres. [Starting with a simple architecture and solving problems in simple ways](https://twitter.com/danluu/status/1462607028585525249) where possible has allowed us to scale to this size while engineers mostly focus on work that delivers value to users.

Stackoverflow scaled up a monolith to good effect ([2013 architecture](https://nickcraver.com/blog/2013/11/22/what-it-takes-to-run-stack-overflow/) / [2016 architecture](https://nickcraver.com/blog/2016/02/17/stack-overflow-the-architecture-2016-edition/)), eventually getting acquired for $1.8B. If we look at traffic instead of market cap, Stackoverflow is among the top 100 highest traffic sites on the internet (for many other examples of valuable companies that were built on top of monoliths, [see the replies to this Twitter thread](https://twitter.com/danluu/status/1498678300163588096). We don’t have a lot of web traffic because we’re a mobile app, but Alexa still puts our website in the top 75k even though our website is basically just a way for people to find the app and most people don’t even find the app through our website).

There are some kinds of applications that have demands that would make a simple monolith on top of a boring database a non-starter but, for most kinds of applications, even at top-100 site levels of traffic, computers are fast enough that high-traffic apps can be served with simple architectures, which can generally be created more cheaply and easily than complex architectures.

Despite the unreasonable effectiveness of simple architectures, most press goes to complex architectures. For example, at a recent generalist tech conference, there were six talks on how to build or deal with side effects of complex, microservice-based, architectures and zero on how one might build out a simple monolith. There were more talks on quantum computing (one) than talks on monoliths (zero). Larger conferences are similar; a recent enterprise-oriented conference in SF had a double-digit number of talks on dealing with the complexity of a sophisticated architecture and zero on how to build a simple monolith. Something that was striking to me the last time I attended that conference is how many attendees who worked at enterprises with low-scale applications that could’ve been built with simple architectures had copied the latest and greatest sophisticated techniques that are popular on the conference circuit and HN.

Our architecture is so simple I’m not even going to bother with an architectural diagram. Instead, I’ll discuss a few boring things we do that help us keep things boring.

We’re currently using boring, synchronous, Python, which means that our server processes block while waiting for I/O, like network requests. We previously tried Eventlet, an async framework that would, in theory, let us get more efficiency out of Python, but ran into so many bugs that we decided the CPU and latency cost of waiting for events wasn’t worth the operational pain we had to take on to deal with Eventlet issues. The are other [well-known async frameworks for Python](https://twitter.com/mcfunley/status/1194713713330122752), but users of those at scale often also report [significant fallout from using those frameworks at scale](https://twitter.com/mcfunley/status/1194715290841432064). Using synchronous Python is expensive, in the sense that we pay for CPU that does nothing but wait during network requests, but since we’re only handling billions of requests a month (for now), the cost of this is low even when using a slow language, like Python, and paying retail public cloud prices. The cost of our engineering team completely dominates the cost of the systems we operate[2](https://danluu.com/simple-architectures/#fn:B).

Rather than take on the complexity of making our monolith async we farm out long-running tasks (that we don’t want responses to block on) to a queue.

A place where we can’t be as boring as we’d like is with our on-prem datacenters. When we were operating solely in Senegal and Côte d'Ivoire, we operated fully in the cloud, but as we expand into Uganda (and more countries in the future), we’re having to split our backend and deploy on-prem to comply with local data residency laws and regulations. That's not exactly a simple operation, but as anyone who's done the same thing with a complex service-oriented architecture knows, this operation is much simpler than it would've been if we had a complex service-oriented architecture.

Another area is with software we’ve had to build (instead of buy). When we started out, we strongly preferred buying software over building it because a team of only a few engineers can’t afford the time cost of building everything. That was the right choice at the time even though [the “buy” option generally gives you tools that don’t work](https://danluu.com/nothing-works/). In cases where vendors can’t be convinced to fix showstopping bugs that are critical blockers for us, [it does make sense to build more of our own tools and maintain in-house expertise in more areas](https://danluu.com/in-house/), in contradiction to the standard advice that a company should only choose to “build” in its core competency. Much of that complexity is complexity that we don’t want to take on, but in some product categories, even after fairly extensive research we haven’t found any vendor that seems likely to provide a product that works for us. To be fair to our vendors, the problem they’d need to solve to deliver a working solution to us is much more complex than the problem we need to solve since our vendors are taking on the complexity of solving a problem for every customer, whereas we only need to solve the problem for one customer, ourselves.

A mistake we made in the first few months of operation that has some cost today was not carefully delimiting the boundaries of database transactions. In Wave’s codebase, the SQLAlchemy database session is a request-global variable; it implicitly begins a new database transaction any time a DB object’s attribute is accessed, and any function in Wave’s codebase can call commit on the session, causing it to commit all pending updates. This makes it difficult to control the time at which database updates occur, which increases our rate of subtle data-integrity bugs, as well as making it harder to lean on the database to build things like [idempotency keys](https://brandur.org/idempotency-keys) or a [transactionally-staged job drain](https://brandur.org/job-drain). It also increases our risk of accidentally holding open long-running database transactions, which can [make schema migrations operationally difficult](https://gocardless.com/blog/zero-downtime-postgres-migrations-the-hard-parts/).

Some choices that we’re unsure about (in that these are things we’re either thinking about changing, or would recommend to other teams starting from scratch to consider a different approach) were using RabbitMQ (for our purposes, Redis would probably work equally well as a task queue and just using Redis would reduce operational burden), using Celery (which is overcomplicated for our use case and has been implicated in several outages e.g. due to backwards compatibility issues during version upgrades), using SQLAlchemy (which makes it hard for developers to understand what database queries their code is going to emit, leading to various situations that are hard to debug and involve unnecessary operational pain, especially related to the above point about database transaction boundaries), and using Python (which was the right initial choice because of our founding CTO’s technical background, but its concurrency support, performance, and extensive dynamism make us question whether it’s the right choice for a large-scale backend codebase). None of these was a major mistake, and for some (e.g. Python) the downsides are minimal enough that it’s cheaper for us to continue to pay the increased maintenance burden than to invest in migrating to something theoretically better, but if we were starting a similar codebase from scratch today we’d think hard about whether they were the right choice.

Some areas where we’re happy with our choices even though they may not sound like the simplest feasible solution is with our API, where we use GraphQL, with our transport protocols, where we had a custom protocol for a while, and our host management, where we use Kubernetes. For our transport protocols, we used to use a custom protocol that runs on top of UDP, with an SMS and USSD fallback, [for the performance reasons described in this talk](https://www.youtube.com/watch?v=EAxnA9L5rS8). With the rollout of HTTP/3, we’ve been able to replace our custom protocol with HTTP/3 and we generally only need USSD for events like the recent internet shutdowns in Mali.

As for using GraphQL, we believe the pros outweigh the cons for us:

Pros:

-   Self-documentation of exact return type
-   Code generation of exact return type leads to safer clients
-   GraphiQL interactive explorer is a productivity win
-   Our various apps (user app, support app, Wave agent app, etc.) can mostly share one API, reducing complexity
-   Composable query language allows clients to fetch exactly the data they need in a single packet roundtrip without needing to build a large number of special-purpose endpoints
-   Eliminates bikeshedding over what counts as a RESTful API

Cons:

-   GraphQL libraries weren’t great when we adopted GraphQL (the base Python library was a port of the Javascript one so not Pythonic, Graphene required a lot of boilerplate, and Apollo-Android produced very poorly optimized code)
-   Default GQL encoding is redundant and we care a lot about limiting size because many of our customers have low bandwidth

As for Kubernetes, we use Kubernetes because knew that, if the business was successful (which it has been) and we kept expanding, we’d eventually expand to countries that require us to operate our services in country. The exact regulations vary by country, but we’re already expanding into one major African market that requires we operate our “primary datacenter” in the country and there are others with regulations that, e.g., require us to be able to fail over to a datacenter in the country.

An area where there’s unavoidable complexity for us is with telecom integrations. In theory, we would use a SaaS SMS provider for everything, but [the major SaaS SMS provider doesn’t operate everywhere in Africa](https://youtu.be/6tb8ALAvodM?t=196) and the cost of using them everywhere would be prohibitive[3](https://danluu.com/simple-architectures/#fn:C). The earlier comment on how the compensation cost of engineers dominates the cost of our systems wouldn’t be true if we used a SaaS SMS provider for all of our SMS needs; the team that provides telecom integrations pays for itself many times over.

By keeping our application architecture as simple as possible, we can spend our complexity (and headcount) budget in places where there’s complexity that it benefits our business to take on. Taking the idea of doing things as simply as possible unless there’s a strong reason to add complexity has allowed us to build a fairly large business with not all that many engineers despite running an African finance business, which is generally believed to be a tough business to get into, which we’ll discuss in a future post (one of our earliest and most helpful advisers, who gave us advice that was critical in Wave’s success, initially suggested that Wave was a bad business idea and the founders should pick another one because he foresaw so many potential difficulties).
