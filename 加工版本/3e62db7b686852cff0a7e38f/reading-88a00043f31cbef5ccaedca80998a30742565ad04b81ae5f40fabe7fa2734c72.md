# 汇编与内在函数｜Assembly v. intrinsics

---

## 正文

每隔一段时间，我就会听说 intrinsics 已经改进到足以放心用于 high performance code 的程度。要真是这样就好了。intrinsics 的承诺是，你可以通过 calling out 到与特定 assembly instructions 相对应的 functions（intrinsics），来编写 optimized code。由于 intrinsics 的行为如同 normal functions，它们可以是 cross platform 的。而且，由于你的 compiler 能利用比你的大脑更多的 computational power，以及每种 CPU 的 detailed model，compiler 理应能够更好地完成 micro-optimizations。尽管早在十年前就有人声称 intrinsics 能让你轻松一些，实际情况似乎从来都不如人意。

我上一次尝试 intrinsics 是在 2007 年左右；关于它们当时为什么毫无希望，可以进一步阅读（[参见 VirtualDub 作者的这篇探讨](http://virtualdub.org/blog/pivot/entry.php?id=162)）。最近我又试了一次，虽然它们有所改进，但仍然不值得费这个力气。问题在于，intrinsics 实在太 unreliable，以至于你必须在预期 code 会运行的每个 platform 和每个 compiler 上 manually check result，然后 tweak intrinsics，直到得到合理的 result。这比直接手写 assembly 还费事。如果你不手动 check results，就很容易得到糟糕的 results。

例如，截至本文撰写时，Google 对 `popcnt benchmark` 的前两个搜索结果（以及 bing 前 3 个搜索结果中的 2 个）都声称，Intel 的 hardware `popcnt` instruction 比一种 software implementation 更 slow；后者通过使用 [SSSE3](https://en.wikipedia.org/wiki/SSSE3) `pshufb` instruction 的 table lookup，来 counts buffer 中 bits set 的 number。事实证明这并不属实，但这一点显然不容易看出来，否则这种说法也不会如此经久不衰。让我们看看，为什么有人在使用 intrinsics 编写 solution 后，可能会得出 `popcnt` instruction 很 slow 的结论。

排名靠前的一个搜索结果同时提供了 native `popcnt` 和使用 `pshufb` 的 software version 的 sample code 与 benchmarks。[他们的 code](http://www.strchr.com/media/crc32_popcnt.zip) 需要 MSVC，而我没法使用它，不过他们的第一个 `popcnt` implementation 只是在 loop 中 calls `popcnt` intrinsic，很容易将其 reproduce 成 gcc 和 clang 都能接受的形式。对它进行 Timing 也相当简单，因为我们只是在 timing 一个 function（它恰好会 count 某个 fixed sized buffer 中 bits set 的 number）。

```
uint32_t builtin_popcnt(const uint64_t* buf, int len) {
  int cnt = 0;
  for (int i = 0; i < len; ++i) {
    cnt += __builtin_popcountll(buf[i]);
  }
  return cnt;
}
```

这与我上面链接的 code 略有不同，因为他们使用的是 `popcnt` 的 dword（32-bit）version，而我们使用的是 qword（64-bit）version。由于我们的 version 在每次 loop iteration 中完成的工作是其两倍，我预计我们的 version 会比他们的 version 更 faster。

嗯，这倒有意思。Clang 似乎在 manually calculating，而不是使用 `popcnt`。它似乎使用了[这里描述的 approach](http://graphics.stanford.edu/~seander/bithacks.html#CountBitsSetParallel)，大致如下

```
x = x - ((x >> 0x1) & 0x5555555555555555);
x = (x & 0x3333333333333333) + ((x >> 0x2) & 0x3333333333333333);
x = (x + (x >> 0x4)) & 0xF0F0F0F0F0F0F0F;
ans = (x * 0x101010101010101) >> 0x38;
```

对于一个不依赖任何 specialized hardware 的 simple implementation 来说，这还不错，但它所需的时间会比单条 `popcnt` instruction 长得多。

我用的 clang version（3.0）相当老，所以让我在 upgrading 到 3.4 后再试一次，看看他们是否“最近”添加了 hardware `popcnt` support。

这就好多了！我们得到了 hardware `popcnt`！让我们将它与 SSSE3 `pshufb` implementation 相 compare，后者在[这里](http://www.strchr.com/crc32_popcnt)被介绍为执行 popcnt 的最快方法。我们会使用与链接中类似的 table 来展示 speed，不过展示的是 rate，而不是 raw cycle count，这样不同 sizes 之间的 relative speed 就会很清楚。rate 的单位是 GB/s，也就是我们每秒能 process 多少 gigs 的 buffer。我们以 chunks 向 function 提供 data（从 1kb 到 16Mb 不等）；每个 column 都是不同 chunk-size 对应的 rate。如果我们看看每种 algorithm 在不同 buffer sizes 下有多 fast，就会得到以下结果。

| Algorithm | 1k | 4k | 16k | 65k | 256k | 1M | 4M | 16M |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| Intrinsic | 6.9 | 7.3 | 7.4 | 7.5 | 7.5 | 7.5 | 7.5 | 7.5 |
| PSHUFB | 11.5 | 13.0 | 13.3 | 13.4 | 13.1 | 13.4 | 13.0 | 12.6 |

这就不太理想了。相较于上面链接中的 benchmark，我们的表现更好，因为我们使用的是 64-bit `popcnt`，而不是 32-bit `popcnt`，但 PSHUFB version 仍然几乎是它的两倍 fast[1](https://danluu.com/assembly-intrinsics/#fn:B)。

一个奇怪之处是 `cnt` 被 accumulated 的方式。`cnt` 被 stored 在 `ecx` 中。但是，clang 没有将 `popcnt` 的 result adding 到 `ecx`，而是决定将 `ecx` add 到 `popcnt` 的 result。为了解决这个问题，clang 随后还必须在每次 loop iteration 结束时，将该 sum move 到 `ecx` 中。

另一个明显的问题是，loop 的每次 iteration 中只有一个 `popcnt`，这意味着 loop 没有被 unrolled，我们为每个 `popcnt` 都付出了完整的 loop overhead cost。Unrolling loop 还可以让 CPU 从 code 中 extract 更多 instruction level parallelism，不过这有点超出这篇博客文章的讨论范围。

使用 clang 时，即使有 `-O3 -funroll-loops`，也会出现这种情况。使用 gcc 时，我们能得到 properly unrolled loop，但 gcc 还有其他问题，后面就会看到。现在，让我们试着在 loop 的每次 iteration 中多次 calling `__builtin_popcountll`，自己来 unrolling loop。为简单起见，让我们试着在每次 iteration 中执行四个 `popcnt` operations。我并不是说这是 optimal 的，但它应该会有所改进。

```
uint32_t builtin_popcnt_unrolled(const uint64_t* buf, int len) {
  assert(len % 4 == 0);
  int cnt = 0;
  for (int i = 0; i < len; i+=4) {
    cnt += __builtin_popcountll(buf[i]);
    cnt += __builtin_popcountll(buf[i+1]);
    cnt += __builtin_popcountll(buf[i+2]);
    cnt += __builtin_popcountll(buf[i+3]);
  }
  return cnt;
}
```

我们的 loop 的 core 现在包含

```

0000000100001398        popcntq 0x8(%rdi,%rcx,8), %rax

00000001000013a8        addl    %eax, %edx
```

| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| Intrinsic | 6.9 | 7.3 | 7.4 | 7.5 | 7.5 | 7.5 | 7.5 | 7.5 |

通过使用 64-bit `popcnt` 和 unrolling loop，我们已经击败了据称更 faster 的 `pshufb` code！不过两者仍然足够接近，换一个 compiler 或其他 chip，可能就会得到不同的 results。让我们看看能否做得更好。

那么，最近备受关注的这个 [popcnt false dependency bug](http://stackoverflow.com/questions/25078285/replacing-a-32-bit-loop-count-variable-with-64-bit-introduces-crazy-performance) 究竟是怎么回事？原来，`popcnt` 对其 destination register 存在 false dependency，这意味着即使 `popcnt` 的 result 并不 depend on 它的 destination register，CPU 仍然认为存在这种关系，并且会等到 destination register ready 后才 starting `popcnt` instruction。

x86 通常具有 two operand operations，例如，`addl %eax, %edx` 会 adds `eax` 和 `edx`，然后将 result places 到 `edx` 中，因此 operation 对其 output register 存在 dependency 很常见。在这个例子中，不应该存在 dependency，因为 result 并不 depend on output register 的 contents，但这种 bug 很容易 introduce，却很难 catch[2](https://danluu.com/assembly-intrinsics/#fn:D)。

在这个具体例子中，`popcnt` 具有 3 cycle latency，但它是 pipelined 的，因此每个 cycle 都可以 execute 一个 `popcnt` operation。如果忽略其他 overhead，这意味着，只要 operations 是 independent 的，单个 `popcnt` 就需要 3 cycles，2 个需要 4 cycles，3 个需要 5 cycles，n 个需要 n+2 cycles。但是，如果 CPU 错误地认为它们之间存在 dependency，我们实际上就失去了 pipeline instructions 的能力，而那个 n+2 就变成了 3n。

我们可以通过购买 AMD 或 VIA 的 CPU 来 work around 这个问题，也可以将 `popcnt` results 放进不同的 registers。让我们建立一个 destinations 的 array，这样就可以将每个 `popcnt` 的 result 放到不同的位置。

```
uint32_t builtin_popcnt_unrolled_errata(const uint64_t* buf, int len) {
  assert(len % 4 == 0);
  int cnt[4];
  for (int i = 0; i < 4; ++i) {
    cnt[i] = 0;
  }

  for (int i = 0; i < len; i+=4) {
    cnt[0] += __builtin_popcountll(buf[i]);
    cnt[1] += __builtin_popcountll(buf[i+1]);
    cnt[2] += __builtin_popcountll(buf[i+2]);
    cnt[3] += __builtin_popcountll(buf[i+3]);
  }
  return cnt[0] + cnt[1] + cnt[2] + cnt[3];
}
```

现在我们得到

```
0000000100001420        popcntq (%rdi,%r9,8), %r8
0000000100001426        addl    %ebx, %r8d
0000000100001429        popcntq 0x8(%rdi,%r9,8), %rax
0000000100001430        addl    %r14d, %eax
0000000100001433        popcntq 0x10(%rdi,%r9,8), %rdx
000000010000143a        addl    %r11d, %edx
000000010000143d        popcntq 0x18(%rdi,%r9,8), %rcx
```

这就好多了——可以看到，第一个 popcnt outputs 到 `r8`，第二个到 `rax`，第三个到 `rdx`，第四个到 `rcx`。不过，这里执行的 accumulation 与原来一样奇怪：它没有将 `popcnt` 的 result adding 到 `cnt[i]`，而是反过来操作，因此之后必须将 results moving 回 `cnt[i]`。

```

0000000100001341        movl    %edx, %r11d

0000000100001347        movl    %r8d, %ebx
```

嗯，至少在 clang（3.4）中是这样。Gcc（4.8.2）太聪明了，不会上这种 separate destination 做法的当，而是把 code “optimizes”回类似我们原始 version 的样子。

| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| Intrinsic | 6.9 | 7.3 | 7.4 | 7.5 | 7.5 | 7.5 | 7.5 | 7.5 |

为了得到一个既能用于 gcc、又能用于 clang，而且没有这些额外 `mov`s 的 version，我们必须手写 assembly[3](https://danluu.com/assembly-intrinsics/#fn:A)：

```
uint32_t builtin_popcnt_unrolled_errata_manual(const uint64_t* buf, int len) {
  assert(len % 4 == 0);
  uint64_t cnt[4];
  for (int i = 0; i < 4; ++i) {
    cnt[i] = 0;
  }

  for (int i = 0; i < len; i+=4) {
    __asm__(
        "popcnt %4, %4  \n\
        "add %4, %0     \n\t"
        "popcnt %5, %5  \n\t"
        "add %5, %1     \n\t"
        "popcnt %6, %6  \n\t"
        "add %6, %2     \n\t"
        "popcnt %7, %7  \n\t"
        "add %7, %3     \n\t" // +r means input/output, r means intput
        : "+r" (cnt[0]), "+r" (cnt[1]), "+r" (cnt[2]), "+r" (cnt[3])
        : "r"  (buf[i]), "r"  (buf[i+1]), "r"  (buf[i+2]), "r"  (buf[i+3]));
  }
  return cnt[0] + cnt[1] + cnt[2] + cnt[3];
}

```

这会将 assembly 直接 translates 到 loop 中：

```
00000001000013c3        popcntq %r10, %r10
00000001000013c8        addq    %r10, %rcx
00000001000013cb        popcntq %r11, %r11
00000001000013d0        addq    %r11, %r9
00000001000013d3        popcntq %r14, %r14
00000001000013d8        addq    %r14, %r8
00000001000013db        popcntq %rbx, %rbx
```

太好了！`add`s 现在的方向正确了，因为我们确切指定了它们应该做什么。

| Algorithm | 1k | 4k | 16k | 65k | 256k | 1M | 4M | 16M |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| Intrinsic | 6.9 | 7.3 | 7.4 | 7.5 | 7.5 | 7.5 | 7.5 | 7.5 |
| PSHUFB | 11.5 | 13.0 | 13.3 | 13.4 | 13.1 | 13.4 | 13.0 | 12.6 |
| Unrolled | 12.5 | 14.4 | 15.0 | 15.1 | 15.2 | 15.2 | 15.2 | 15.2 |
| Unrolled 2 | 14.3 | 16.3 | 17.0 | 17.2 | 17.2 | 17.0 | 16.8 | 16.7 |
| Assembly | 17.5 | 23.7 | 25.3 | 25.3 | 26.3 | 26.3 | 25.3 | 24.3 |

终于！一个远远胜过 `PSHUFB` implementation 的 version。我们怎么知道这应该就是最终的 version？从 [Agner 的 instruction tables](http://www.agner.org/optimize/instruction_tables.pdf) 可以看出，我们每个 cycle 最多只能 execute 一个 `popcnt`。我恰好是在一颗 3.4Ghz Sandy Bridge 上运行它，因此得到的 upper bound 是 `8 bytes / cycle * 3.4 G cycles / sec = 27.2 GB/s`。这与我们实际得到的 `26.3 GB/s` 相当接近，说明我们已经无法让它再快很多了[4](https://danluu.com/assembly-intrinsics/#fn:S)。

在这个例子中，hand coded assembly version 比原始 intrinsic loop 大约快 3x（不算那个没有 emit `popcnt` 的 clang version 所产生的 version）。对于我们使用的 compiler，使用 `popcnt` intrinsic 的 unrolled loop 恰好比 `pshufb` version 稍快一些，但我用 `gcc` 尝试时，两个 unrolled versions 中有一个并非如此。

不难理解，为什么有人可能对同样的 code 进行 benchmarked 后，就认定 `popcnt` 并不很 fast。也不难理解，为什么在 performance critical code 中使用 intrinsics 会耗费大量时间[5](https://danluu.com/assembly-intrinsics/#fn:1)。

## 原文

Every once in a while, I hear how intrinsics have improved enough that it's safe to use them for high performance code. That would be nice. The promise of intrinsics is that you can write optimized code by calling out to functions (intrinsics) that correspond to particular assembly instructions. Since intrinsics act like normal functions, they can be cross platform. And since your compiler has access to more computational power than your brain, as well as a detailed model of every CPU, the compiler should be able to do a better job of micro-optimizations. Despite decade old claims that intrinsics can make your life easier, it never seems to work out.

The last time I tried intrinsics was around 2007; for more on why they were hopeless then ([see this exploration by the author of VirtualDub](http://virtualdub.org/blog/pivot/entry.php?id=162)). I gave them another shot recently, and while they've improved, they're still not worth the effort. The problem is that intrinsics are so unreliable that you have to manually check the result on every platform and every compiler you expect your code to be run on, and then tweak the intrinsics until you get a reasonable result. That's more work than just writing the assembly by hand. If you don't check the results by hand, it's easy to get bad results.

For example, as of this writing, the first two Google hits for `popcnt benchmark` (and 2 out of the top 3 bing hits) claim that Intel's hardware `popcnt` instruction is slower than a software implementation that counts the number of bits set in a buffer, via a table lookup using the [SSSE3](https://en.wikipedia.org/wiki/SSSE3) `pshufb` instruction. This turns out to be untrue, but it must not be obvious, or this claim wouldn't be so persistent. Let's see why someone might have come to the conclusion that the `popcnt` instruction is slow if they coded up a solution using intrinsics.

One of the top search hits has sample code and benchmarks for both native `popcnt` as well as the software version using `pshufb`. [Their code](http://www.strchr.com/media/crc32_popcnt.zip) requires MSVC, which I don't have access to, but their first `popcnt` implementation just calls the `popcnt` intrinsic in a loop, which is fairly easy to reproduce in a form that gcc and clang will accept. Timing it is also pretty simple, since we're just timing a function (that happens to count the number of bits set in some fixed sized buffer).

```
uint32_t builtin_popcnt(const uint64_t* buf, int len) {
  int cnt = 0;
  for (int i = 0; i < len; ++i) {
    cnt += __builtin_popcountll(buf[i]);
  }
  return cnt;
}
```

This is slightly different from the code I linked to above, since they use the dword (32-bit) version of `popcnt`, and we're using the qword (64-bit) version. Since our version gets twice as much done per loop iteration, I'd expect our version to be faster than their version.

Running `clang -O3 -mpopcnt -funroll-loops` produces a binary that we can examine. On macs, we can use `otool -tv` to get the disassembly. On linux, there's `objdump -d`.

That's not so great. Relative to the the benchmark linked above, we're doing better because we're using 64-bit `popcnt` instead of 32-bit `popcnt`, but the PSHUFB version is still almost twice as fast[1](https://danluu.com/assembly-intrinsics/#fn:B).

One odd thing is the way `cnt` gets accumulated. `cnt` is stored in `ecx`. But, instead of adding the result of the `popcnt` to `ecx`, clang has decided to add `ecx` to the result of the `popcnt`. To fix that, clang then has to move that sum into `ecx` at the end of each loop iteration.

The other noticeable problem is that we only get one `popcnt` per iteration of the loop, which means the loop isn't getting unrolled, and we're paying the entire cost of the loop overhead for each `popcnt`. Unrolling the loop can also let the CPU extract more instruction level parallelism from the code, although that's a bit beyond the scope of this blog post.

Using clang, that happens even with `-O3 -funroll-loops`. Using gcc, we get a properly unrolled loop, but gcc has other problems, as we'll see later. For now, let's try unrolling the loop ourselves by calling `__builtin_popcountll` multiple times during each iteration of the loop. For simplicity, let's try doing four `popcnt` operations on each iteration. I don't claim that's optimal, but it should be an improvement.

```
uint32_t builtin_popcnt_unrolled(const uint64_t* buf, int len) {
  assert(len % 4 == 0);
  int cnt = 0;
  for (int i = 0; i < len; i+=4) {
    cnt += __builtin_popcountll(buf[i]);
    cnt += __builtin_popcountll(buf[i+1]);
    cnt += __builtin_popcountll(buf[i+2]);
    cnt += __builtin_popcountll(buf[i+3]);
  }
  return cnt;
}
```

The core of our loop now has

Between using 64-bit `popcnt` and unrolling the loop, we've already beaten the allegedly faster `pshufb` code! But it's close enough that we might get different results with another compiler or some other chip. Let's see if we can do better.

So, what's the deal with this [popcnt false dependency bug](http://stackoverflow.com/questions/25078285/replacing-a-32-bit-loop-count-variable-with-64-bit-introduces-crazy-performance) that's been getting a lot of publicity lately? Turns out, `popcnt` has a false dependency on its destination register, which means that even though the result of `popcnt` doesn't depend on its destination register, the CPU thinks that it does and will wait until the destination register is ready before starting the `popcnt` instruction.

x86 typically has two operand operations, e.g., `addl %eax, %edx` adds `eax` and `edx`, and then places the result in `edx`, so it's common for an operation to have a dependency on its output register. In this case, there shouldn't be a dependency, since the result doesn't depend on the contents of the output register, but that's an easy bug to introduce, and a hard one to catch[2](https://danluu.com/assembly-intrinsics/#fn:D).

In this particular case, `popcnt` has a 3 cycle latency, but it's pipelined such that a `popcnt` operation can execute each cycle. If we ignore other overhead, that means that a single `popcnt` will take 3 cycles, 2 will take 4 cycles, 3 will take 5 cycles, and n will take n+2 cycles, as long as the operations are independent. But, if the CPU incorrectly thinks there's a dependency between them, we effectively lose the ability to pipeline the instructions, and that n+2 turns into 3n.

We can work around this by buying a CPU from AMD or VIA, or by putting the `popcnt` results in different registers. Let's making an array of destinations, which will let us put the result from each `popcnt` into a different place.

```
uint32_t builtin_popcnt_unrolled_errata(const uint64_t* buf, int len) {
  assert(len % 4 == 0);
  int cnt[4];
  for (int i = 0; i < 4; ++i) {
    cnt[i] = 0;
  }

  for (int i = 0; i < len; i+=4) {
    cnt[0] += __builtin_popcountll(buf[i]);
    cnt[1] += __builtin_popcountll(buf[i+1]);
    cnt[2] += __builtin_popcountll(buf[i+2]);
    cnt[3] += __builtin_popcountll(buf[i+3]);
  }
  return cnt[0] + cnt[1] + cnt[2] + cnt[3];
}
```

And now we get

```
0000000100001420        popcntq (%rdi,%r9,8), %r8
0000000100001426        addl    %ebx, %r8d
0000000100001429        popcntq 0x8(%rdi,%r9,8), %rax
0000000100001430        addl    %r14d, %eax
0000000100001433        popcntq 0x10(%rdi,%r9,8), %rdx
000000010000143a        addl    %r11d, %edx
000000010000143d        popcntq 0x18(%rdi,%r9,8), %rcx
```

That's better -- we can see that the first popcnt outputs into `r8`, the second into `rax`, the third into `rdx`, and the fourth into `rcx`. However, this does the same odd accumulation as the original, where instead of adding the result of the `popcnt` to `cnt[i]`, it does the opposite, which necessitates moving the results back to `cnt[i]` afterwards.

```
000000010000133e        movl    %ecx, %r10d
0000000100001341        movl    %edx, %r11d
0000000100001344        movl    %eax, %r14d
0000000100001347        movl    %r8d, %ebx
```

Well, at least in clang (3.4). Gcc (4.8.2) is too smart to fall for this separate destination thing and “optimizes” the code back to something like our original version.

To get a version that works with both gcc and clang, and doesn't have these extra `mov`s, we'll have to write the assembly by hand[3](https://danluu.com/assembly-intrinsics/#fn:A):

```
uint32_t builtin_popcnt_unrolled_errata_manual(const uint64_t* buf, int len) {
  assert(len % 4 == 0);
  uint64_t cnt[4];
  for (int i = 0; i < 4; ++i) {
    cnt[i] = 0;
  }

  for (int i = 0; i < len; i+=4) {
    __asm__(
        "popcnt %4, %4  \n\
        "add %4, %0     \n\t"
        "popcnt %5, %5  \n\t"
        "add %5, %1     \n\t"
        "popcnt %6, %6  \n\t"
        "add %6, %2     \n\t"
        "popcnt %7, %7  \n\t"
        "add %7, %3     \n\t" // +r means input/output, r means intput
        : "+r" (cnt[0]), "+r" (cnt[1]), "+r" (cnt[2]), "+r" (cnt[3])
        : "r"  (buf[i]), "r"  (buf[i+1]), "r"  (buf[i+2]), "r"  (buf[i+3]));
  }
  return cnt[0] + cnt[1] + cnt[2] + cnt[3];
}

```

This directly translates the assembly into the loop:

```
00000001000013c3        popcntq %r10, %r10
00000001000013c8        addq    %r10, %rcx
00000001000013cb        popcntq %r11, %r11
00000001000013d0        addq    %r11, %r9
00000001000013d3        popcntq %r14, %r14
00000001000013d8        addq    %r14, %r8
00000001000013db        popcntq %rbx, %rbx
```

Great! The `add`s are now going the right direction, because we specified exactly what they should do.

| Algorithm | 1k | 4k | 16k | 65k | 256k | 1M | 4M | 16M |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| Intrinsic | 6.9 | 7.3 | 7.4 | 7.5 | 7.5 | 7.5 | 7.5 | 7.5 |
| PSHUFB | 11.5 | 13.0 | 13.3 | 13.4 | 13.1 | 13.4 | 13.0 | 12.6 |
| Unrolled | 12.5 | 14.4 | 15.0 | 15.1 | 15.2 | 15.2 | 15.2 | 15.2 |
| Unrolled 2 | 14.3 | 16.3 | 17.0 | 17.2 | 17.2 | 17.0 | 16.8 | 16.7 |
| Assembly | 17.5 | 23.7 | 25.3 | 25.3 | 26.3 | 26.3 | 25.3 | 24.3 |

Finally! A version that blows away the `PSHUFB` implementation. How do we know this should be the final version? We can see from [Agner's instruction tables](http://www.agner.org/optimize/instruction_tables.pdf) that we can execute, at most, one `popcnt` per cycle. I happen to have run this on a 3.4Ghz Sandy Bridge, so we've got an upper bound of `8 bytes / cycle * 3.4 G cycles / sec = 27.2 GB/s`. That's pretty close to the `26.3 GB/s` we're actually getting, which is a sign that we can't make this much faster[4](https://danluu.com/assembly-intrinsics/#fn:S).

In this case, the hand coded assembly version is about 3x faster than the original intrinsic loop (not counting the version from a version of clang that didn't emit a `popcnt`). It happens that, for the compiler we used, the unrolled loop using the `popcnt` intrinsic is a bit faster than the `pshufb` version, but that wasn't true of one of the two unrolled versions when I tried this with `gcc`.

It's easy to see why someone might have benchmarked the same code and decided that `popcnt` isn't very fast. It's also easy to see why using intrinsics for performance critical code can be a huge time sink[5](https://danluu.com/assembly-intrinsics/#fn:1).
