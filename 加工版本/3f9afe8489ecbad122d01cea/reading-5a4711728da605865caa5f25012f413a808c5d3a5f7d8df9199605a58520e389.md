# 为什么使用 ECC？｜Why use ECC?

---

## 正文

Jeff Atwood 或许是读者最多的 programming blogger，他有一篇文章，[主张反对使用 ECC memory](http://blog.codinghorror.com/to-ecc-or-not-to-ecc/)。在我看来，他的主要观点是：

1.  Google 在 1999 年 built 他们的 servers 时没有使用 ECC
2.  大多数 RAM errors 是 hard errors，而不是 soft errors
3.  RAM errors 很 rare，因为 hardware 已经 improved
4.  如果 ECC 真的重要，那么它就会到处使用，而不只是用于 servers。为这种可选的东西付钱，实在是“太有企业那一套的味道了”

让我们逐一看看这些 arguments：

## 1\. Google 在 1999 年没有使用 ECC

Google 将这些 non-ECC machines put into production 后没过多久，就意识到这是一个严重的错误，省下的成本并不值得。如果你仅仅因为那是 Google，就觉得 cargo culting Google 的做法是个好主意，那么你或许会做下面这些事：

#### A. 把你的 servers 放进 shipping containers。

直到今天，仍有文章称赞这是多么好的主意，尽管 Google 的这项 experiment 已被判定为失败。事实证明，即便是 Google 的 experiments 也不是总能成功。实际上，他们早年对“登月式冒险”的偏爱，意味着他们失败的 experiments 比大多数公司还多。照搬他们失败的 experiments，并不是什么特别好的策略。

#### B. 在你自己的 datacenters 里引发火灾

那篇文章有一部分在谈这些 servers 有多么了不起：

> 有些人看着 Google 早期的这些 servers，可能会觉得这是业余得很的火灾隐患。我不这么看。我看到的是一种先见之明：他们明白 inexpensive commodity hardware 将如何塑造今天的 internet。看到这台 server 时，我觉得十分亲切；在同样的情况下，我也一定会这样做

最后那部分说得没错。但前面那部分也有几分道理。Google 开始 designing 自己的 boards 时，其中一代出现了 regrowth[1](https://danluu.com/why-ecc/#fn:R) 问题，引发了 non-zero 次火灾。

顺便说一句，如果你点进 Jeff 的文章，看看引文所指的照片，就会发现那些 boards 有很大的 flex。这造成了一些问题，下一代便对此进行了 fixed。你还可以看到，cabling 相当凌乱，这也造成了问题，下一代也对此进行了 fixed。此外还有其他问题。Jeff 在这里的 argument 似乎是，如果他当时在那里，他也会看到 Google 早期的 enigneers 所看到的完全相同的机会；而且，既然 Google 这么做了，那就一定是对的，即便看起来不像如此。但是，有好些让这件事看起来不对的因素，实际上也确实让它成了错误的做法。

#### C. 制造会伤害你员工的 servers

Google 有一代 servers 的 sharp edges 臭名昭著，因此落下了由“剃刀刀片和仇恨”制成的名声。

#### D. 在你的 datacenters 里制造天气

和许多大型科技公司的人聊过之后，似乎其中大多数都出现过 climate control 问题，导致 datacenters 里出现云或雾。你或许会说，这是 Google 为了挖走 MS 员工而重现西雅图天气的巧妙计划。又或者，这是一个制造字面意义上的 cloud computing 的计划。当然，也可能不是。

请注意，这些都是 Google 尝试过、随后又改变了的做法。犯错后再修正，在每个成功的 engineering organization 中都很常见。如果你非要 cargo cult 某种 engineering practice，至少也该 cargo cult 现在的 engineering practices，而不是[1999 年的做法](https://danluu.com/butler-lampson-1999/)。

1999 年，Google 使用没有 ECC 的 servers 时，发现了许多最终被证实由 memory corruption 引起的 symptoms，其中包括一个对 queries returned 的 results 实际上是 random 的 search index。这里实际发生的 failure mode 很有启发性。我经常听人说，这些 machines 可以忽略 ECC，因为 individual results 中出现 errors 是可以接受的。但是，即便你能 tolerate 偶尔出现的 errors，ignoring errors 也意味着你正让自己面临 total corruption，除非你已经做过非常仔细的 analysis，确保 single error 只能 contaminate single result。针对 filesystems 的 research 已反复表明，尽管人们竭尽全力尝试 creating 能够 robust against a single error 的 systems，做到这一点仍然极其困难，而且基本上每一种经过 heavily tested 的 filesystem 都可能因为 single error 而发生 massive failure（[如果你对此感兴趣，可以看看 Wisconsin 的 Andrea 和 Remzi 的 research group 的成果](https://danluu.com/file-consistency/)）。我并不是在贬低 filesystem developers。他们做这种 analysis 的本领比 99.9% 的 programmers 都强。只不过，这个问题已经被反复证明难到了人类无法对其 effectively reason 的程度，而用于这类 analysis 的 automated tooling 距离一键完成也还很远。Google 在他们关于 [warehouse scale computing](http://www.morganclaypool.com/doi/abs/10.2200/S00516ED2V01Y201306CAC024) 的书中讨论了 error correction 和 detection，并把 ECC 列为一个毫无争议的例子，用以说明什么时候显然应该使用 hardware error correction[2](https://danluu.com/why-ecc/#fn:P)。

Google 有出色的 infrastructure。根据我听说的其他大型科技公司的 infra 的情况，Google 的似乎是世界上最好的。但这并不意味着你应该照搬他们所做的一切。即便只看他们的好主意，对大多数公司而言，照搬也没有道理。他们[为 Linux 的 work stealing scheduler created 了一个 replacement，同时使用 hardware run-time information 和 static traces，从而利用 Intel 的 server processors 中允许你在 cores 之间 dynamically partition caches 的新 hardware](https://danluu.com/intel-cat/)。如果用于他们的整个 fleet，那么只用一周，就很容易为 Google 省下比 stackexchange 自成立以来花在 machines 上的全部费用还多的钱。这是否意味着你应该照搬 Google？不，除非你已经拿到了所有唾手可得的收益，其中包括确保你的 core infrastructure 是用 highly optimized C++ written 的，而不是 Java，或是（老天保佑，千万别是）Ruby。问题在于，对绝大多数公司而言，用一种带来 20x performance penalty 的 language 来 writing，是完全合理的决定。

## 2\. 大多数 RAM errors 是 hard errors

反对 ECC 的论述引用了[一项关于 DRAM errors 的 study 中的这一部分](http://selse.org//images/selse_2012/Papers/selse2012_submission_4.pdf)（粗体是 Jeff 加的）：

> 我们的 study 有几项主要 findings。首先，我们发现，**大约 70% 的 DRAM faults 是 recurring（例如 permanent）faults，而只有 30% 是 transient faults。**其次，我们发现，large multi-bit faults，例如 affects 整个 row、column 或 bank 的 faults，constitute 了全部 DRAM faults 的 40% 以上。第三，我们发现，将近 5% 的 DRAM failures 会 affect board-level circuitry，例如 data (DQ) 或 strobe (DQS) wires。最后，我们发现，chipkill functionality 将 DRAM faults 所致的 system failure rate reduced 了 36x。

这似乎暴露出对这项 study 的 implications 缺乏理解，因为这段引文听起来不像是反对 ECC 的 argument；它听起来倒像是支持“chipkill”的 argument，而后者是 ECC 的一个特定 class。先不谈这一点，Jeff 的文章指出，hard errors 的常见程度是 soft errors 的两倍，然后提到他们拿到 machines 时会在上面 run memtest。首先，2:1 的 ratio 并没有大到可以直接 ignore soft errors 的程度。其次，这篇文章暗示 Jeff 相信 hard errors 基本上是 immutable，不会在过了一段时间之后才 surface，这是 incorrect 的。你可以把 electronics 的 wearing out 想成与 mechanical devices 的 wear out 一样。其 mechanisms 是 different 的，但 effects 是 similar 的。事实上，如果你 compare chips 的 reliability analysis 与其他种类的 reliability analysis，你会发现它们往往使用相同的 families of distributions 来 model failures。而且，如果 hard errors 是 immutable，它们通常会在 manufacturer 的 testing 中被 catch；manufacturer 比 consumers 更容易 catch errors，因为他们有接入 circuits 的 hooks，能够以远高于你在 server 或 home computer 上所能做到的效率来 test memory。第三，Jeff 的 line of reasoning 暗示 ECC 无法帮助进行 hard errors 的 detection 或 correction，这不仅是 incorrect 的，而且还被引文直接 contradicted。

那么，你打算多频繁地在自己的 machines 上 run memtest，尝试 catch 这些 hard errors，又愿意忍受多少 data corruption？ECC 的一个关键用途不是 correct errors，而是 signal errors，以便在 silent corruption occurs 之前 replaced hardware。没有人会同意每天 shutting down 一台 machine 上的一切来 run memtest（那会比直接购买 ECC memory 更昂贵），即使你能说服大家这么做，它也不会像 ECC 那样 catch 那么多 errors。

我曾在一家拥有大约 1000 台 machines 的公司工作，我们注意到出现了一些奇怪的 consistency check failures，大概过了半年才意识到，这些 failures 在某些 machines 上比在其他 machines 上更容易发生。这些 failures 相当 rare，平均也许每周几次，因此 accumulate data 花了很长时间，而有人意识到究竟发生了什么又花了更多时间。在不知道原因的情况下，analyzing logs，弄清这些 errors 是由 single bit flips caused 的（具有 high probability），也并非 trivial。幸运的是，作为我们所用 process 的一个 side effect，checksums 是在 separate process 中、在另一台 machine 上、在另一个时间 calculated 的，因此一个 error 无法 corrupt result，再把这种 corruption propagate 到 checksum 中。如果你只是试图用 in-memory checksums 保护自己，那么你很可能会对已经 corrupted 的 data 执行 checksum operation，并 compute 出 bad data 的 valid checksum，除非你正在使用一些非常精巧的办法，让 calculations 自带 checksums（而如果你对 error correction 如此认真，那么无论如何你大概已经在用 ECC 了）。总之，完成 analysis 后，我们发现 memtest 无法 detect 任何问题，但 replacing 那些有问题的 machines 上的 RAM，使 error rate 出现了 one to two order of magnitude reduction。大多数 services 并没有我们这种 checksumming；那些 services 只会 silently write corrupt data 到 persistent storage，直到有 customer 抱怨才会注意到问题。

## 3\. 由于 hardware manufacturing 的进步，errors 已经非常 rare

Jeff 说

> 我确实认真怀疑，ECC 是否真如我们被引导相信的那样 operationally critical \[对于 servers\]，而且我认为 data 表明，现代的 non-ECC RAM 已经 extremely reliable……来自信誉良好的 vendors 的现代 commodity computer parts 是 amazingly reliable 的。而且，它们的 trends 表明，自 2012 起，essential PC parts 变得更 reliable，而不是更不 reliable。（我也可以为 SSD reliability 的改善作证，因为在 3 years 内，我们配有 24+ drives 的 12 台 servers 没有出现任何 server SSD failures……

并引用了一项 study。

这篇文章中的 data 并不足以 support 这一 assertion。请注意，由于 RAM usage 一直在 increasing，而且继续以很快的 exponential rate increase，RAM failures 必须以更大的 exponential rate decrease，才能真正 reduce data corruption 的 incidence。此外，随着 chips 继续 shrink，features 变得更小，使“2”中讨论的那类 wearout issues 更加 common。例如，在 20nm 时，一个 DRAM capacitor 可能只能 hold 大约 50 个 electrons，而到了下一代 DRAM，随着继续 shrink，这个数量还会更小。

[Atwood 引用的 2012 年 study](http://selse.org//images/selse_2012/Papers/selse2012_submission_4.pdf) 中有下面这张 graph，展示了十个 randomly selected failing nodes 上的 corrected errors（全部 errors 的一个 subset）（6% 的 nodes 至少出现过一次 failure）：

![](https://danluu.com/images/why-ecc/one_month_ecc_errors.webp)

我们说的是，一个出现 failure 的 typical node 有 10 到 10k 个 errors，而且这还是一篇主张你不需要 ECC 的文章 cherry-picked 出来的 study。请注意，这里的 nodes 只有 16GB 的 RAM，比现代 servers 通常拥有的 RAM 少了一个 order of magnitude，而且它使用的是较早的 process node，相比我们现在的情况，对 noise 的 vulnerable 程度更低。对于习惯处理 reliability issues、只想知道 FIT rate 的人来说，这项 study 得到的 FIT rate 是每 Mbit 介于 0.057 和 0.071 faults 之间（与 Atwood 的 assertion 相反，这并不是一个低得惊人的数值）。如果你采用最乐观的 FIT rate，即 .057，并为一台 RAM 不多的 server 做 calculation（这里我使用 128GB，因为我如今见到的 servers 通常拥有 128GB 到 1.5TB 的 RAM）。那么得到的 expected value 就是每台 server 每年 .057 \* 1000 \* 1000 \* 8760 / 1000000000 = .5 faults。请注意，这说的是 faults，而不是 errors。从上面的 graph 可以看到，一个 fault 很容易每月 cause 数百乃至数千个 errors。另一个值得注意的地方是，有多个 nodes 在 study 开始时并没有 errors，却在之后 develop errors。因此，事实上，Jeff 链接的这项 cherry-picked study contradicted 了 Jeff 关于 reliability 的 claim。

Sun/Oracle 在几十年前就曾遭遇过这个问题，广为人知。当时 Transistors 和 DRAM capacitors 正在变小，与现在非常相似，而 memory usage 和 caches 正在增长，也与现在非常相似。一方面，更小的 transistors 对 transient upset 的 resilient 程度更低，也更难 manufacture；另一方面，on-chip cache 越来越多，因此绝大多数 server vendors 决定为 caches 添加 ECC。Sun 决定省下几美元，跳过 ECC。直接结果就是，许多 Sun customers 报告了 sporadic data corruption。Sun 花了多年时间才 spin 出具有 ECC cache 的新 architecture，而且要求 customers 签署 NDA 才能拿到 replacement chips。当然，这种事情不可能永远掩盖下去；事情曝光后，Sun 因生产 reliable servers 而享有的声誉受到了永久损害，就像他们曾试图[通过在 terms of services 中加入 disallowing benchmarking 的条款来掩盖 poor performance results](https://danluu.com/anon-benchmark/)时一样。

这里另一个值得注意的地方是，当你为 ECC 付费时，你不只是在为 ECC 付费，也是在为经过更彻底 qual'd 的 parts（CPUs、boards）付费。从 disk failure rates 很容易看出这一点，我也见过很多人在自己的 private datasets 中 observe 到这一点。至于 public data，我记得 Andrea 和 Remzi 的研究组几年前有一篇 SIGMETRICS paper，其中表明，SATA drives 出现 disk read failures 的可能性是 SCSI drives 的 4x，出现 silent data corruption 的可能性则是 10x。即使 drives 来自同一家 manufacturer，这种 relationship 也 held true。没有什么特别的理由认为 SCSI interface 应该比 SATA interface 更 reliable，但关键不在 interface，而在于购买的是 high-reliability server part 还是 consumer part。也许你并不特别在意 disk reliability，因为你对一切都进行 checksum，可以轻易 detect disk corruption，但有些种类的 corruption 更难 detect。

\[2024 年更新，距原文已近十年\]：回过头来看，我们可以发现，Jeff 关于 commodity parts 是 reliable 的 assertion——“来自信誉良好的 vendors 的现代 commodity computer parts 是 amazingly reliable 的”——依然不成立。根据 Firefox 的 real-world user data，[Gabriele Svelto estimated，全部 Firefox crashes 中大约有 10% 到 20% 是由 memory corruption 所致](https://fosstodon.org/@gabrielesvelto/112401643131904845)。多家 track 这类事情的 game companies 也报告，相当一部分 user crashes 似乎是由 data corruption 所致，不过我手头没有这些公司的 estimate。一个更直接的 argument 是，如果你与那些运行大量 ECC memory 的大公司员工交流，并查看 ECC errors 的 rate，就会发现，尽管 ECC memory 通常比随意挑选的 non-ECC memory 有更低的 error rate，ECC memory 仍然 detected 了相当多的 errors。这类 argument 经常有人提出（在这里，十年前就已在上文详细说明；不久前我在 Twitter 工作时也看过这个问题，而 memory technology 并没有发生什么革命，使 ECC 的必要性相较十年前 papers 中讨论的 rates 有所降低），但它往往无法打动那些会说“好吧，反正那些 bits 大概也不重要”“大多数 memory 最后根本不会被 read”之类话的人。查看 real-world crashes，并注意到 silent data corruption 的数量应当远高于 crashes 的 rate，似乎更能打动那些对查看 datacenters 中原始 FIT rates 不感兴趣的人。

## 4\. 如果 ECC 确实重要，它就会到处被使用，而不只是在 servers 中。

[一种改述方式，是把它说成某种鸡尾酒会版的 efficient markets hypothesis。这不可能重要，因为如果重要，我们早就有了](https://danluu.com/cocktail-ideas/)。当然，这并不正确，而且有许多对 consumers 有益的东西，我们并没有，比如[被 designed 为 safe、而不是只求在 crash tests 中获得 maximum score 的 cars](https://danluu.com/car-safety/)。从 server 和 consumer markets 的角度来看，这个 argument 可以改述为：“如果这个 feature 对 servers 确实重要，它就会被用于 non-servers”，这并不正确。决定 servers 与 non-servers 中分别有哪些东西的一个主要 driver，是可以加入哪些让 servers 的买家愿意花大价钱购买的东西，从而允许在 server 和 non-server parts 之间实行 price discrimination。这实际上是 large cloud vendors 面临的较为恼人的问题之一——hardware vendors 能够抬高带有 server features 的 parts 的价格，因为这些 features 在 server applications 中比在 desktop applications 中有价值得多。大多数 home users 并不介意，这就给了 hardware vendors 一种 mechanism，让它们既能从购买 servers 的人那里赚取更多钱，又能继续为 consumers 提供便宜的 parts。

Cloud vendors 往往有足够的 negotiating leverage，能够以 cost 获得 parts，但这只在存在不止一家 viable vendor 的地方才行得通。少数没有任何 viable competitors 的领域中，就包括 CPUs 和 GPUs。CPU vendors 已经多次尝试进入 server market，但迄今为止，每一次尝试都有 fatally flawed 的地方，以至于从早期阶段就能明显看出，这次尝试注定会失败（而这些往往是历时 5 年的项目，所以这意味着把大量时间花在注定会失败的项目上）。Qualcomm 的尝试一直受到大量炒作，但当我和我认识的 Qualcomm 员工交谈时，他们都告诉我，目前的 chip 基本上是用来练手的，因为 Qualcomm 需要向那些从 IBM 挖来的人学习如何 build 一个 server chip，而下一款 chip 才是第一款有望 competitive 的 chip。我对 Qualcomm，以及一项 build 优秀 server parts 的 ARM 尝试，都寄予厚望，但这些努力距离取得成果还需要一段时间。

就 performance per TCO dollar 而言，目前的 ARM（和 POWER）options（不包括 Apple's 那款令人印象深刻的 ARM chip 的 hypothetical variants）对于大多数 server workloads 几乎完全 unsuitability，这有些离题，所以我会留到另一篇文章再说；但关键在于，Intel 拥有让人们为 server features 额外付费的 market power，而且它确实这样做了。此外，某些 features 对 servers 确实比对 mobile devices 更重要，后者只有几个 GB 的 RAM、几 watts 的 power budget，而且反正大家也预期它们会时不时地 randomly crash 和 reboot。

## Conclusion（结论）

你应该购买 ECC RAM 吗？这要视情况而定。对于 servers，考虑到 cost，这大概是个不错的选择，尽管很难真正进行 cost/benefit analysis，因为实在很难算清 silent data corruption 的 cost，也很难算清承担这样一种风险的 cost：耗费半年的 developer 时间去 tracking down intermittent failures，最后却发现它们是由使用 non-ECC memory caused 的。

对于普通的 desktop use，我是 pro-ECC 的，但如果你还没有设置好 [regular backups](https://www.reddit.com/r/programming/comments/adoux/coding_horror_and_blogsstackoverflowcom/)，那么进行 backups 的 ROI 大概比 ECC 更好。不过，一旦你把最基本的事情做好了，就有相当充分的理由为 consumer machines 使用 ECC。例如，如果你有 backups 却没有 ECC，你很容易把 corrupt data 进行 write 到 primary store 中，再把那些 corrupt data 进行 replicate 到 backup 中。但更一般地说，运行 datacenters 的大公司大概比 consumers 更有条件 detect data corruption，也更有可能在 higher levels 上拥有 error correction，从而使它们能够从 data corruption 中 recover，因此可以说，对 consumers 使用 ECC 的理由比对 servers 还要充分，而对 servers 的理由已经充分到通常被认为是不言而喻的了。consumers 通常不使用 ECC 的一个主要原因，并不是它对他们不值得，而是当 crashes 和 data corruption 发生时，他们根本不知道该如何 attribute。一旦你像 Google 和其他大公司那样开始做这件事，就会立刻清楚地看到，即使你在 higher levels 上运行着 multiple levels 的 error correction，ECC 也值得付出这个 cost。这与[我们在 files 上看到的情况](https://danluu.com/deconstruct-files/)类似：为自己的 datacenters 编写 software 的大型科技公司，在处理 data corruption 方面，比编写 consumer software 的大型科技公司做得好得多（而且这在同一家公司内部也往往成立）。对于 user 来说，自己的 web app 对 data 进行 corrupt 所带来的 cost，与自己的 desktop app 对 data 进行 corrupt 时并没有那么大的区别；区别在于，当 web app 对 data 进行 corrupt 时，责任更明显在公司身上，这改变了公司的 incentives。

### 附录：security

如果你允许任何形式的 code execution，即使是 sandboxed execution，也存在[像 rowhammer 这样的](https://en.wikipedia.org/wiki/Row_hammer) attacks，能够让 users 引发 data corruption，而且已经有过由此实现 privilege escalation 的实例。ECC 并不能完全 mitigate 这种 attack，但它会让这种 attack 困难得多。

## 原文

Jeff Atwood, perhaps the most widely read programming blogger, has a post that makes [a case against using ECC memory](http://blog.codinghorror.com/to-ecc-or-not-to-ecc/). My read is that his major points are:

1.  Google didn't use ECC when they built their servers in 1999
2.  Most RAM errors are hard errors and not soft errors
3.  RAM errors are rare because hardware has improved
4.  If ECC were actually important, it would be used everywhere and not just servers. Paying for optional stuff like this is "awfully enterprisey"

Let's take a look at these arguments one by one:

## 1\. Google didn't use ECC in 1999

Not too long after Google put these non-ECC machines into production, they realized this was a serious error and not worth the cost savings. If you think cargo culting what Google does is a good idea because it's Google, here are some things you might do:

#### A. Put your servers into shipping containers.

Articles are still written today about what a great idea this is, even though this was an experiment at Google that was deemed unsuccessful. Turns out, even Google's experiments don't always succeed. In fact, their propensity for “moonshots” in the early days meannt that they had more failed experiments that most companies. Copying their failed experiments isn't a particularly good strategy.

#### B. Cause fires in your own datacenters

Part of the post talks about how awesome these servers are:

> Some people might look at these early Google servers and see an amateurish fire hazard. Not me. I see a prescient understanding of how inexpensive commodity hardware would shape today's internet. I felt right at home when I saw this server; it's exactly what I would have done in the same circumstances

The last part of that is true. But the first part has a grain of truth, too. When Google started designing their own boards, one generation had a regrowth[1](https://danluu.com/why-ecc/#fn:R) issue that caused a non-zero number of fires.

BTW, if you click through to Jeff's post and look at the photo that the quote refers to, you'll see that the boards have a lot of flex in them. That caused problems and was fixed in the next generation. You can also observe that the cabling is quite messy, which also caused problems, and was also fixed in the next generation. There were other problems as well. Jeff's argument here appears to be that, if he were there at the time, he would've seen the exact same opportunities that early Google enigneers did, and since Google did this, it must've been the right thing even if it doesn't look like it. But, a number of things that make it look like not the right thing actually made it not the right thing.

#### C. Make servers that injure your employees

One generation of Google servers had infamously sharp edges, giving them the reputation of being made of “razor blades and hate”.

#### D. Create weather in your datacenters

From talking to folks at a lot of large tech companies, it seems that most of them have had a climate control issue resulting in clouds or fog in their datacenters. You might call this a clever plan by Google to reproduce Seattle weather so they can poach MS employees. Alternately, it might be a plan to create literal cloud computing. Or maybe not.

Note that these are all things Google tried and then changed. Making mistakes and then fixing them is common in every successful engineering organization. If you're going to cargo cult an engineering practice, you should at least cargo cult current engineering practices, not [something that was done in 1999](https://danluu.com/butler-lampson-1999/).

When Google used servers without ECC back in 1999, they found a number of symptoms that were ultimately due to memory corruption, including a search index that returned effectively random results to queries. The actual failure mode here is instructive. I often hear that it's ok to ignore ECC on these machines because it's ok to have errors in individual results. But even when you can tolerate occasional errors, ignoring errors means that you're exposing yourself to total corruption, unless you've done a very careful analysis to make sure that a single error can only contaminate a single result. In research that's been done on filesystems, it's been repeatedly shown that despite making valiant attempts at creating systems that are robust against a single error, it's extremely hard to do so and basically every heavily tested filesystem can have a massive failure from a single error ([see the output of Andrea and Remzi's research group at Wisconsin if you're curious about this](https://danluu.com/file-consistency/)). I'm not knocking filesystem developers here. They're better at that kind of analysis than 99.9% of programmers. It's just that this problem has been repeatedly shown to be hard enough that humans cannot effectively reason about it, and automated tooling for this kind of analysis is still far from a push-button process. In their book on [warehouse scale computing](http://www.morganclaypool.com/doi/abs/10.2200/S00516ED2V01Y201306CAC024), Google discusses error correction and detection and ECC is cited as their slam dunk case for when it's obvious that you should use hardware error correction[2](https://danluu.com/why-ecc/#fn:P).

Google has great infrastructure. From what I've heard of the infra at other large tech companies, Google's sounds like the best in the world. But that doesn't mean that you should copy everything they do. Even if you look at their good ideas, it doesn't make sense for most companies to copy them. They [created a replacement for Linux's work stealing scheduler that uses both hardware run-time information and static traces to allow them to take advantage of new hardware in Intel's server processors that lets you dynamically partition caches between cores](https://danluu.com/intel-cat/). If used across their entire fleet, that could easily save Google more money in a week than stackexchange has spent on machines in their entire history. Does that mean you should copy Google? No, not unless you've already captured all the lower hanging fruit, which includes things like making sure that your core infrastructure is written in highly optimized C++, not Java or (god forbid) Ruby. And the thing is, for the vast majority of companies, writing in a language that imposes a 20x performance penalty is a totally reasonable decision.

## 2\. Most RAM errors are hard errors

The case against ECC quotes [this section of a study on DRAM errors](http://selse.org//images/selse_2012/Papers/selse2012_submission_4.pdf) (the bolding is Jeff's):

> Our study has several main findings. First, we find that approximately **70% of DRAM faults are recurring (e.g., permanent) faults, while only 30% are transient faults.** Second, we find that large multi-bit faults, such as faults that affects an entire row, column, or bank, constitute over 40% of all DRAM faults. Third, we find that almost 5% of DRAM failures affect board-level circuitry such as data (DQ) or strobe (DQS) wires. Finally, we find that chipkill functionality reduced the system failure rate from DRAM faults by 36x.

This seems to betray a lack of understanding of the implications of this study, as this quote doesn't sound like an argument against ECC; it sounds like an argument for "chipkill", a particular class of ECC. Putting that aside, Jeff's post points out that hard errors are twice as common as soft errors, and then mentions that they run memtest on their machines when they get them. First, a 2:1 ratio isn't so large that you can just ignore soft errors. Second the post implies that Jeff believes that hard errors are basically immutable and can't surface after some time, which is incorrect. You can think of electronics as wearing out just the same way mechanical devices wear out. The mechanisms are different, but the effects are similar. In fact, if you compare reliability analysis of chips vs. other kinds of reliability analysis, you'll find they often use the same families of distributions to model failures. And, if hard errors were immutable, they would generally get caught in testing by the manufacturer, who can catch errors much more easily than consumers can because they have hooks into circuits that let them test memory much more efficiently than you can do in your server or home computer. Third, Jeff's line of reasoning implies that ECC can't help with detection or correction of hard errors, which is not only incorrect but directly contradicted by the quote.

So, how often are you going to run memtest on your machines to try to catch these hard errors, and how much data corruption are you willing to live with? One of the key uses of ECC is not to correct errors, but to signal errors so that hardware can be replaced before silent corruption occurs. No one's going to consent to shutting down everything on a machine every day to run memtest (that would be more expensive than just buying ECC memory), and even if you could convince people to do that, it won't catch as many errors as ECC will.

When I worked at a company that owned about 1000 machines, we noticed that we were getting strange consistency check failures, and after maybe half a year we realized that the failures were more likely to happen on some machines than others. The failures were quite rare, maybe a couple times a week on average, so it took a substantial amount of time to accumulate the data, and more time for someone to realize what was going on. Without knowing the cause, analyzing the logs to figure out that the errors were caused by single bit flips (with high probability) was also non-trivial. We were lucky that, as a side effect of the process we used, the checksums were calculated in a separate process, on a different machine, at a different time, so that an error couldn't corrupt the result and propagate that corruption into the checksum. If you merely try to protect yourself with in-memory checksums, there's a good chance you'll perform a checksum operation on the already corrupted data and compute a valid checksum of bad data unless you're doing some really fancy stuff with calculations that carry their own checksums (and if you're that serious about error correction, you're probably using ECC regardless). Anyway, after completing the analysis, we found that memtest couldn't detect any problems, but that replacing the RAM on the bad machines caused a one to two order of magnitude reduction in error rate. Most services don't have this kind of checksumming we had; those services will simply silently write corrupt data to persistent storage and never notice problems until a customer complains.

## 3\. Due to advances in hardware manufacturing, errors are very rare

Jeff says

> I do seriously question whether ECC is as operationally critical as we have been led to believe \[for servers\], and I think the data shows modern, non-ECC RAM is already extremely reliable ... Modern commodity computer parts from reputable vendors are amazingly reliable. And their trends show from 2012 onward essential PC parts have gotten more reliable, not less. (I can also vouch for the improvement in SSD reliability as we have had zero server SSD failures in 3 years across our 12 servers with 24+ drives ...

and quotes a study.

The data in the post isn't sufficient to support this assertion. Note that since RAM usage has been increasing and continues to increase at a fast exponential rate, RAM failures would have to decrease at a greater exponential rate to actually reduce the incidence of data corruption. Furthermore, as chips continue shrink, features get smaller, making the kind of wearout issues discussed in “2” more common. For example, at 20nm, a DRAM capacitor might hold something like 50 electrons, and that number will get smaller for next generation DRAM and things continue to shrink.

The [2012 study that Atwood quoted](http://selse.org//images/selse_2012/Papers/selse2012_submission_4.pdf) has this graph on corrected errors (a subset of all errors) on ten randomly selected failing nodes (6% of nodes had at least one failure):

![](https://danluu.com/images/why-ecc/one_month_ecc_errors.webp)

We're talking between 10 and 10k errors for a typical node that has a failure, and that's a cherry-picked study from a post that's arguing that you don't need ECC. Note that the nodes here only have 16GB of RAM, which is an order of magnitude less than modern servers often have, and that this was on an older process node that was less vulnerable to noise than we are now. For anyone who's used to dealing with reliability issues and just wants to know the FIT rate, the study finds a FIT rate of between 0.057 and 0.071 faults per Mbit (which, contra Atwood's assertion, is not a shockingly low number). If you take the most optimistic FIT rate, .057, and do the calculation for a server without much RAM (here, I'm using 128GB, since the servers I see nowadays typically have between 128GB and 1.5TB of RAM)., you get an expected value of .057 \* 1000 \* 1000 \* 8760 / 1000000000 = .5 faults per year per server. Note that this is for faults, not errors. From the graph above, we can see that a fault can easily cause hundreds or thousands of errors per month. Another thing to note is that there are multiple nodes that don't have errors at the start of the study but develop errors later on. So, in fact, the cherry-picked study that Jeff links contradicts Jeff's claim about reliability.

Sun/Oracle famously ran into this a number of decades ago. Transistors and DRAM capacitors were getting smaller, much as they are now, and memory usage and caches were growing, much as they are now. Between having smaller transistors that were less resilient to transient upset as well as more difficult to manufacture, and having more on-chip cache, the vast majority of server vendors decided to add ECC to their caches. Sun decided to save a few dollars and skip the ECC. The direct result was that a number of Sun customers reported sporadic data corruption. It took Sun multiple years to spin a new architecture with ECC cache, and Sun made customers sign an NDA to get replacement chips. Of course there's no way to cover up this sort of thing forever, and when it came up, Sun's reputation for producing reliable servers took a permanent hit, much like the time they tried to [cover up poor performance results by introducing a clause into their terms of services disallowing benchmarking](https://danluu.com/anon-benchmark/).

Another thing to note here is that when you're paying for ECC, you're not just paying for ECC, you're paying for parts (CPUs, boards) that have been qual'd more thoroughly. You can easily see this with disk failure rates, and I've seen many people observe this in their own private datasets. In terms of public data, I believe Andrea and Remzi's group had a SIGMETRICS paper a few years back that showed that SATA drives were 4x more likely than SCSI drives to have disk read failures, and 10x more likely to have silent data corruption. This relationship held true even with drives from the same manufacturer. There's no particular reason to think that the SCSI interface should be more reliable than the SATA interface, but it's not about the interface. It's about buying a high-reliability server part vs. a consumer part. Maybe you don't care about disk reliability in particular because you checksum everything and can easily detect disk corruption, but there are some kinds of corruption that are harder to detect.

\[2024 update, almost a decade later\]: looking at this retrospectively, we can see that Jeff's assertion that commodity parts are reliable, "modern commodity computer parts from reputable vendors are amazingly reliable" is still not true. Looking at real-world user data from Firefox, [Gabriele Svelto estimated that approximately 10% to 20% of all Firefox crashes were due to memory corruption](https://fosstodon.org/@gabrielesvelto/112401643131904845). Various game companies that track this kind of thing also report a significant fraction of user crashes appear to be due to data corruption, although I don't have an estimate from any of those companies handy. A more direct argument is that if you talk to folks at big companies that run a lot of ECC memory and look at the rate of ECC errors, there are quite a few errors detected by ECC memory despite ECC memory typically having a lower error rate than random non-ECC memory. This kind of argument is frequently made (here, it was detailed above a decade ago, and when I looked at this when I worked at Twitter fairly recently and there has not been a revolution in memory technology that has reduced the need for ECC over the rates discussed in papers a decade ago), but it often doesn't resontate with folks who say things like "well, those bits probably didn't matter anyway", "most memory ends up not getting read", etc. Looking at real-world crashes and noting that the amount of silent data corruption should be expected to be much higher than the rate of crashes seems to resonate with people who aren't excited by looking at raw FIT rates in datacenters.

## 4\. If ECC were actually important, it would be used everywhere and not just servers.

[One way to rephrase this is as a kind of cocktail party efficient markets hypothesis. This can't be important, because if it was, we would have it](https://danluu.com/cocktail-ideas/). Of course this is incorrect and there are many things that would be beneficial to consumers that we don't have, such as [cars that are designed to safe instead of just getting the maximum score in crash tests](https://danluu.com/car-safety/). Looking at this with respect to the server and consumer markets, this argument can be rephrased as “If this feature were actually important for servers, it would be used in non-servers”, which is incorrect. A primary driver of what's available in servers vs. non-servers is what can be added that buyers of servers will pay a lot for, to allow for price discrimination between server and non-server parts. This is actually one of the more obnoxious problems facing large cloud vendors — hardware vendors are able to jack up the price on parts that have server features because the features are much more valuable in server applications than in desktop applications. Most home users don't mind, giving hardware vendors a mechanism to extract more money out of people who buy servers while still providing cheap parts for consumers.

Cloud vendors often have enough negotiating leverage to get parts at cost, but that only works where there's more than one viable vendor. Some of the few areas where there aren't any viable competitors include CPUs and GPUs. There have been a number of attempts by CPU vendors to get into the server market, but each attempt so far has been fatally flawed in a way that made it obvious from an early stage that the attempt was doomed (and these are often 5 year projects, so that's a lot of time to spend on a doomed project). The Qualcomm effort has been getting a lot of hype, but when I talk to folks I know at Qualcomm they all tell me that the current chip is basically for practice, since Qualcomm needed to learn how to build a server chip from all the folks they poached from IBM, and that the next chip is the first chip that has any hope of being competitive. I have high hopes for Qualcomm as well an ARM effort to build good server parts, but those efforts are still a ways away from bearing fruit.

The near total unsuitability of current ARM (and POWER) options (not including hypothetical variants of Apple's impressive ARM chip) for most server workloads in terms of performance per TCO dollar is a bit of a tangent, so I'll leave that for another post, but the point is that Intel has the market power to make people pay extra for server features, and they do so. Additionally, some features are genuinely more important for servers than for mobile devices with a few GB of RAM and a power budget of a few watts that are expected to randomly crash and reboot periodically anyway.

## Conclusion

Should you buy ECC RAM? That depends. For servers, it's probably a good bet considering the cost, although it's hard to really do a cost/benefit analysis because it's really hard to figure out the cost of silent data corruption, or the cost of having some risk of burning half a year of developer time tracking down intermittent failures only to find that the were caused by using non-ECC memory.

For normal desktop use, I'm pro-ECC, but if you don't have [regular backups](https://www.reddit.com/r/programming/comments/adoux/coding_horror_and_blogsstackoverflowcom/) set up, doing backups probably has a better ROI than ECC. But once you have the absolute basics set up, there's a fairly strong case for ECC for consumer machines. For example, if you have backups without ECC, you can easily write corrupt data into your primary store and replicate that corrupt data into backup. But speaking more generally, big companies running datacenters are probably better set up to detect data corruption and more likely to have error correction at higher levels that allow them to recover from data corruption than consumers, so the case for consumers is arguably stronger than it is for servers, where the case is strong enough that's generally considered a no brainer. A major reason consumers don't generally use ECC isn't that it isn't worth it for them, it's that they just have no idea how to attribute crashes and data corruption when they happen. Once you start doing this, as Google and other large companies do, it's immediately obvious that ECC is worth the cost even when you have multiple levels of error correction operating at higher levels. This is analogous to [what we see with files](https://danluu.com/deconstruct-files/), where big tech companies write software for their datacenters that's much better at dealing with data corruption than big tech companies that write consumer software (and this is often true within the same company). To the user, the cost of having their web app corrupt their data isn't all that different from when their desktop app corrupts their data, the difference is that when their web app corrupts data, it's clearer that it's the company's fault, which changes the incentives for companies.

### Appendix: security

If you allow any sort of code execution, even sandboxed execution, there are attacks [like rowhammer](https://en.wikipedia.org/wiki/Row_hammer) which can allow users to cause data corruption and there have been instances where this has allowed for privilege escalation. ECC doesn't completely mitigate the attack, but it makes it much harder.

1.  One of the funnier examples I can think of this, at least to me, is the magical self-healing fuse. Although there are many implementations, you can think of a fuse on a chip as basically a resistor. If you run some current through it, you should get a connection. If you run a lot of current through it, you'll heat up the resistor and eventually destroy it. This is commonly used to fuse off features on chips, or to do things like set the clock rate, with the idea being that once a fuse is blown, there's no way to unblow the fuse.

    Once upon a time, there was a semiconductor manufacturer that rushed their manufacturing process a bit and cut the tolerances a bit too fine in one particular process generation. After a few months (or years), the connection between the two ends of the fuse could regrow and cause the fuse to unblow. If you're lucky, the fuse will be something like the high-order bit of the clock multiplier, which will basically brick the chip if changed. If you're not lucky, it will be something that results in silent data corruption.

    I heard about problems in that particular process generation from that manufacturer from multiple people at different companies, so this wasn't an isolated thing. When I say this is funny, I mean that it's funny when you hear this story at a bar. It's maybe less funny when you discover, after a year of testing, that some of your chips are failing because their fuse settings are nonsensical, and you have to respin your chip and delay the release for 3 months. BTW, this fuse regrowth thing is another example of a class of error that can be mitigated with ECC.

    This is not the issue that Google had; I only mention this because a lot of people I talk to are surprised by the ways in which hardware can fail.

2.  In case you don't want to dig through the whole book, most of the relevant passage is:

    In a system that can tolerate a number of failures at the software level, the minimum requirement made to the hardware layer is that its faults are always detected and reported to software in a timely enough manner as to allow the software infrastructure to contain it and take appropriate recovery actions. It is not necessarily required that hardware transparently corrects all faults. This does not mean that hardware for such systems should be designed without error correction capabilities. Whenever error correction functionality can be offered within a reasonable cost or complexity, it often pays to support it. It means that if hardware error correction would be exceedingly expensive, the system would have the option of using a less expensive version that provided detection capabilities only. Modern DRAM systems are a good example of a case in which powerful error correction can be provided at a very low additional cost. Relaxing the requirement that hardware errors be detected, however, would be much more difficult because it means that every software component would be burdened with the need to check its own correct execution. At one early point in its history, Google had to deal with servers that had DRAM lacking even parity checking. Producing a Web search index consists essentially of a very large shuffle/merge sort operation, using several machines over a long period. After some investigation a pattern was found in the new index files that corresponded to a bit being stuck at zero at a consistent place in the data structures; a bad side effect of streaming a lot of data through a faulty DRAM chip. Consistency checks were added to the index data structures to minimize the likelihood of this problem recurring, and no further problems of this nature were reported. Note, however, that this workaround did not guarantee 100% error detection in the indexing pass because not all memory positions were being checked—instructions, for example, were not. It worked because index data structures were so much larger than all other data involved in the computation, that having those self-checking data structures made it very likely that machines with defective DRAM would be identified and excluded from the cluster. The following machine generation at Google did include memory parity detection, and once the price of memory with ECC dropped to competitive levels, all subsequent generations have used ECC DRAM.
