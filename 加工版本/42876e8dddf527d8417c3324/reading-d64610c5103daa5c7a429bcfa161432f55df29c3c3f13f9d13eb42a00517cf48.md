## 核心洞察

一、grill-me 减少会话 fork 与自我反馈强化：常规 LLM 交互中，回答信息量常超出用户掌控，一段内容前中后均需追问，导致会话频繁 fork；且 LLM 会在两三轮后把用户未回应的输出当作事实记录，形成自我反馈强化。grill-me 通过主动提问机制显著缓解了这两个问题，使交互更可控。
[[#^pr-74b8415631e2|正文跳转]]

二、grill-me 有效提问的三类场景：与 grill-me 交互时，以下问题显著有帮助：一是对要不要做、技术选型等影响后续较大的细节判断；二是关键细节问题；三是人类已知而 LLM 假设有误的情况。这些场景能发挥 grill-me 的追问优势，帮助用户澄清决策和纠正模型错误。
[[#^pr-47a20ac00d61|正文跳转]]

三、grill-me 的挫败感来源：重复与低信息量问题：grill-me 会提出信息量较低或重复的问题，例如刚说过细节 C 又紧接着问“把 C 作为本项目假设可以吗”，这种重复提问打断思路，带来挫败感。
[[#^pr-3a373298ed7a|正文跳转]]

四、脱离 scope 的问题导致模块混淆：grill-me 可能提出超出本次对话限定范围的问题，如在模块 A 设计中问模块 B 的环节设计，且用户可能几轮后才察觉。若不通过 harness 强行锁定其他模块实现，LLM 会把 B 模块当作自己该实现的部分，造成范围蔓延。
[[#^pr-dbfb8781098f|正文跳转]]

五、LLM 无法先天区分细节感知度：用户常觉得 grill-me 过于追求细节，给出差异不大或无法感知差别的选项。但 LLM 并不先天知道哪些细节低感知、哪些高决定性，因此这类问题必然存在；正是这种状态才可能产生“关键性细节”的提问。
[[#^pr-2666f65d48ca|正文跳转]]

六、grill-me 缺乏主动结束机制：与 grill-me 沟通可能持续上百轮，但 AI 反馈状态与第一轮无明显区别，不会主动告知何时结束。用户需在大量问答后主动提出“还有多久”或“先做这些”，否则对话可能无休止。
[[#^pr-c415ec39737a|正文跳转]]

七、用户认知错误可通过实践与版本控制缓解：用户自身认知错误（如张冠李戴、对模块认识不清）会导致沟通偏差。可通过“先做一下”查看效果或花时间查询解决；也可用 git 维护版本，生成错误时回退到上一步，这是常见的 harness 问题。
[[#^pr-b4088fd1d7d1|正文跳转]]

八、单次生成过多且关键细节覆盖不足：与 grill-me 沟通后，单次工作生成内容过多，但仍有关键细节未被覆盖，导致细节效果不令人满意，这是体验中的一个明显短板。
[[#^pr-c8d139fc3fcc|正文跳转]]

九、串行交互范式效率受限：grill-me 的设计范式效率未拉满：每次沟通必经“阅读生成内容-思考并回答-等待下一轮生成”，即使能沉浸聊 30-50 轮，等待生成的时间对快问快答仍不短。
[[#^pr-c23af5b32308|正文跳转]]

十、批量提问可降等待但易生无意义问题：借鉴 Grill-me 模式，让 AI 一次输出多个问题可降低生成时间占比，但容易生成无意义的问题，需要在效率与问题质量间权衡。
[[#^pr-0fef988e5d7a|正文跳转]]

## 正文

grill-me 本身的介绍 [@吴浩亮](https://www.zhihu.com/people/cabd61eff8b9fb95c072826ec3e10523) 写得很好了，我讲下我的个人体验和踩过的坑。

常规和 LLM 交互时，单纯回答中 LLM 会输出超过常人能掌控的信息量（特别是 GPT-5.5），一段内容中可能前 1/3、中间 1/3、最后 1/3 分别都是需要你追问的，这导致了会话的频繁 fork，而 grill-me 没有这个问题。

^pr-74b8415631e2

另外，人和 LLM 交互的过程中，LLM 会“自我反馈强化”，在两三轮之后就会把他输出的内容（但用户没回应）当作事实记录下来，grill-me 的这个情形轻得多。

和 grill-me 交互过程中，有一些提出的问题显著能够帮到人：1. 对于要不要做、技术选型等会对之后影响较大细节的判断；2. 关键的细节问题；3. 人类已经知道，而 LLM 的假设有错误的情况。

^pr-47a20ac00d61

但 grill-me 在这些情况下会给人挫败感：

1. 信息量较低、重复的问题，比如“前面已经说过细节 C，紧接着的问题再次提问‘我们就把 C 作为本项目假设、可以吗’”。

^pr-3a373298ed7a

2. 脱离 scope 的问题，试图去问本次对话限定范围以外的问题，比如在模块 A 的设计中提问“（模块 B 的）某个环节这么设计可以吗”，这个提问甚至可能过上几轮你才会发现他们没在这个模块的 scope 中，那么要不然靠 harness 把对其他模块的实现强行锁住，要不然 LLM 就会把 B 模块当作自己模块该实现的一部分。

^pr-dbfb8781098f

3. 给出用户觉得差异不大的情况，或者用户没有能力对几个选项感知到差别（这就是很多人说的过于追求细节），但是需要知道，对于 LLM 来说，他并不先天知道哪些细节是低感知的、哪些细节是高决定性的，因而必然会有这类问题出现。如果没有这个状态，就不会出现所谓“给出关键性细节”的事情。

^pr-2666f65d48ca

4. 没有尽头，兴冲冲和 AI 沟通了甚至一百轮左右，人类感知上和第一轮 AI 的反馈状态没什么区别，他并不会告诉你到哪一轮可以结束，或者说是没有主动结束一说的，需要人（在进行了大量的提问-回答之后）主动提出“还有多久”或者“让我们先做这些”。

^pr-c415ec39737a

5. 人的认知本身就是错误的，比方说张冠李戴把名词 A 理解成名词 B，人自己对模块认识不清等等。这些可以通过“先做一下”查看效果，或者花费更多的时间查询来解决。这是老生常谈的 harness 问题，或者用 git 维护版本解决一下就好，生成错了就回到上一步。

^pr-b4088fd1d7d1

6. 和他沟通后，单次工作生成的东西太多，并且仍然有关键细节没有被覆盖，导致这一部分的细节效果是不令人满意的。

^pr-c8d139fc3fcc

另外，这个 skill 的设计范式也是效率没拉满的，固然你能比较沉浸地和他聊 30 轮、50 轮，但每次沟通必然经过“阅读生成内容-思考并回答-等待下一轮生成”，对于快问快答来说，“等待下一轮生成”是个不短的时间。

^pr-c23af5b32308

借鉴 Grill-me 的模式，让他一次输出多些问题，可以降低“生成”的时间占比，但是就容易生成没意义的问题。

^pr-0fef988e5d7a
