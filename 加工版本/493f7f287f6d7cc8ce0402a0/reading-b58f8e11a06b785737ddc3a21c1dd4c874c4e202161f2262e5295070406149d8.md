# Why object-relational mapping makes me sad

---

## 正文

最近我花了不少时间与 SQLAlchemy 打交道，它是用于 Python 的 _object-relational mapper_。正如你可能从这篇文章的标题猜到的那样，它让我有些难过。

SA 的职责是充当 database 之上的 abstraction layer，让你能把 queries 写成 Python functions，并以 Python objects 的形式取回 results。SQLAlchemy abstraction barrier 在某些方面确实起到了 barrier 的作用：

-   你根本不知道自己的 code 可能在 generating 什么 queries。

-   而且，如果你看到一条 raw query（例如，因为它被 flagged 为 running slowly），你根本不知道是什么 code generated 了它。

-   Generated queries 是 massive 的，而且难以阅读。

-   SA 根本不知道你的 database 是否真的 conforms to 它的 schema。它只是试着猜测，如果哪里出了问题，就会 throws hard-to-debug errors。

-   如果你正在 traversing relationships，你根本不知道 queries 是在_什么时候_被 emitted 的，也不知道有多少条。

-   你无法轻易地把 database processes 与正在 running 它们的 code 联系起来。

另一方面，它对另外一些事情却完全撒手不管：

-   每次 query 时，你都需要 explicitly declare 每个 relationship 是如何被 loaded 的。

-   你仍然受制于 SQL 的 inexpressiveness——例如，让一个 column default to being equal to 那个 primary key，竟然会莫名其妙地困难重重。

-   Cache invalidation 完全交给你自己处理。

-   它也尝试 handling 像 polymorphism 这样的 complex object relationships，但它的工作方式在很大程度上取决于所选择的 underlying relational representation（“joined”、“single-table” 或 “multi-table” inheritance）。

我并不是说 ORMs 总体上一定不好。使用 SQLAlchemy 几乎肯定比直接 writing raw SQL 更能提高我们的工作效率。但我还是忍不住觉得，一定有更好的东西。

## 原文

I’ve spent a lot of time lately dealing with SQLAlchemy, which is an _object-relational mapper_ for Python. As you might guess from the title of this post, it makes me kind of sad.

SA’s job is to be an abstraction layer over the database, so that you can write queries as Python functions and get back your results as Python objects. The SQLAlchemy abstraction barrier does act as a barrier in some ways:

-   You have no idea what queries your code might be generating.

-   And if you see a raw query (e.g. because it’s flagged as running slowly), you have no idea what code generated it.

-   Generated queries are massive and hard to read.

-   SA has no idea if your database actually conforms to its schema. It just tries to guess and throws hard-to-debug errors if something’s wrong.

-   You have no idea _when_ queries are emitted, or how many of them, if you’re traversing relationships.

-   You can’t easily connect database processes to the code that’s running them.

On the other hand, it totally punts on some other things:

-   You need to explicitly declare how every relationship is loaded, every time you query.

-   You’re still a slave to the inexpressiveness of SQL—for instance, having one column default to being equal to the primary key is randomly really hard.

-   Cache invalidation is left entirely up to you.

-   There’s some attempt at handling complex object relationships like polymorphism, but the way it works depends a lot on a choice of underlying relational representation (“joined” vs “single-table” vs “multi-table” inheritance).

I’m not claiming that ORMs are necessarily bad on net. We’re almost certainly more productive using SQLAlchemy than if we were writing raw SQL. But I can’t help but feel like there must be something better.
