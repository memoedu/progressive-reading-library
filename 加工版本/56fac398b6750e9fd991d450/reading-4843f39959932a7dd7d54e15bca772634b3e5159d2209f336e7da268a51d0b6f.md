# Julia 语言综述｜A review of the Julia language

---

## 正文

这里有一种 language，它能提供 near-C performance，用起来却像 Python 或 Ruby，带有 optional type annotations（你可以把它们交给[两个工具之一](https://github.com/tonyhffong/Lint.jl)，也就是这些 [static analysis tools](https://github.com/astrieanna/TypeCheck.jl)），对 macros 有良好的 support，对 FP 也有还算不错的 support，此外还有许多东西。这有什么不让人喜欢的呢？不过，我基本上不打算谈 Julia 有多棒，因为网上到处都能找到大量这样写的博文。

上一次使用 Julia 时（大约在 Oct. 2014），我遇到了两个此前没见过的 bugs，都涉及 processing Unicode strings 时出现 bogus exceptions。为了 work around 这些问题，我用了 try/catch，但这当然又碰上了我之前发现的一个与 try/catch 有关的 non-deterministic bug。我还碰到了一个 bug：如果给某个 function passed 一个 wrong type 的 argument，它就会 returned 一个完全 wrong result，而不是 throwing 一个 "no method" error。我花了半小时写一个用完即弃的 script，结果在 core language 中遇到了四个 bugs。

倒数第二次使用 Julia 时，我遇到的 bugs 多得列不完；其中最糟糕的一个使 generating plots 每个 plot 都要花 30 seconds，迫使我改用 R/ggplot2 来 plotting。首先是这个 [plotting dates 不起作用](https://github.com/dcjones/Gadfly.jl/issues/462)的 bug。我 work around 它之后，又遇到了一个 regression，导致 plotting 会 [break core language 的很大一部分](https://github.com/JuliaLang/julia/issues/8631)，所以 data manipulation 必须在 plotting 之前完成。如果我确切知道自己想要什么，这倒也没关系，但在做 exploratory data analysis 时，我希望先 plot 一些 data，对这些 data 做点事情，然后再 plot 一次。要这样做，每做一个新的 plot 就得 restarting REPL。这本来也可以接受，只是在我的 1.7GHz Haswell 上 load Gadfly 要花 22 seconds（用 `time` 对一个只 loads Gadfly、不做任何工作的 file 计时），再加上 load 我使用的其他 packages 还要花大约 10 seconds，于是我的 plotting workflow 就变成了：restart REPL，等待 30 seconds，做个改动，做一个 plot，看一眼 plot，然后重复。

使用一种年轻的 language 时遇到 bugs 并不稀奇，但以 Julia 的成熟程度来说，它的 bugs 未免太多了。如果你看看它的 test process，就会发现这基本上是不可避免的。

据我所知，在类似现代 test framework 的东西中，FactCheck 是最常用的，而它几乎没人用。直到不久之前，它还处于 unmaintained 和 broken 的状态，但即使现在，绝大多数 tests 仍然是用 `@test` 写的，而它基本上就是一个 assert。从理论上说，在一个 file 里写满 test code 和 asserts，也可能写出好的 tests。但实际上，凡是这样做的人都没有认真对待 testing，也不会写出好的 tests。

不仅现有的 tests 不太好，大多数东西根本就没有经过 tested。你可能会指出，很多 packages 的 coverage stats 并没有那么糟，但上次我查看时，coverage tool 中有一个 bug，导致它只对具有 non-zero coverage 的 functions 进行 aggregate coverage statistics。也就是说，untested functions 中的 code 不计入 coverage stats！再加上所采用的 test coverage 概念很弱（line coverage[1](https://danluu.com/julialang/#fn:L)），这些 coverage stats 对于判断 packages 是否经过充分 tested 并没有帮助。

缺乏 testing 不仅意味着你会遇到 regression bugs。Features 也会无缘无故地消失。REPL 被 rewritten 时，许多已有的 shortcut keys 和其他 features 都停止工作了。据我所知，这并不是因为有人希望它以不同的方式工作，而是因为，对没有经过 tested 的东西进行 re-write，不可能不丢失 functionality。

与大多数 Julia packages（以及 language 本身）的 testing 水平相伴而来的，是缺乏一套良好的 error handling 方案。虽然你可以轻松地在 Julia 中使用 `Nullable`（它是 Julia 中与 `Some/None` 对应的东西）或 error codes，但最常见的 idiom 是使用 exceptions。而且，如果你使用 `Base` 中的东西，比如 arrays 或 `/`，就只能接受 exceptions。我[并不喜欢这种方式](https://web.archive.org/web/20140213012902/http://blogs.msdn.com/b/oldnewthing/archive/2005/01/14/352949.aspx)，但这也没关系——许多 reliable software 都使用 exceptions 来做 error handling。

问题在于，Julia 所处的小众领域并不在乎[2](https://danluu.com/julialang/#fn:R) error handling，因此，要写出一个 robust Julia program 极其困难。写较小的 scripts 时，你往往希望它能“fail-fast”，让 debugging 更容易，但对于某些 programs，你希望 program 能采取合理的行动，keep running，也许还要 log error。即使采用这里对 robust 的宽松 definition，写出 robust program 也很难。问题存在于多个层面。篇幅所限，我只列两个。

如果我正在写一个希望它能 robust 的东西，我真的希望 function documentation 能包含这个 function 可能 throw 的所有 exceptions。Julia docs 不仅没有这些内容，而且经常会出现这样的情况：call 某个 function，得到一个莫名其妙的 exception，它与某个 implementation detail 有关，却与 API interface 毫无关系。我写过的所有真正必须 reliable 的东西都是 exception free 的，所以，也许在人们使用 exceptions 时，这就是正常现象？不过，在我看来这相当奇怪。

另一个问题是，catching exceptions 不起作用（有时会无缘无故地这样）。我遇到过一个 bug，使用 exceptions 会导致 code 被 incorrectly optimized out。你可能会说，这样讲不公平，因为它是[通过 fuzzer 发现的](https://github.com/danluu/Fuzz.jl)，而 fuzzers 本来就是用来 find bugs 的，但那个 fuzzer 并没有在 fuzzing exceptions，甚至也没有在 fuzzing expressions。那个 fuzzer 的 implementation 只是碰巧涉及在一个 loop 中 eval'ing function calls，并用一个 `try/catch` 来 handle exceptions。结果发现，如果你这样做，function 可能根本不会被 called。这不是用 fuzzer 来 generate 数十亿个 tests、其中一个 failed 的情况，而是只试了一件事，这一件就 failed 了。那个 bug 现在已经 fixed，但仍然有一个讨厌的 bug，会导致 exceptions 有时无法被 `catch` caught。如果你把某些东西放进 `try/catch` block，正是因为不希望 exception 一路传到 top level 并 kill 你的 program，那么这可是个相当糟糕的消息。

我在 `Base` 中 grepped，想找出真正 catching an exception 并根据那个具体 exception 做些事情的实例，结果只找到一个。当然，这是我自己在 less 中浏览 grep output，所以可能漏掉了一些实例，但这种做法并不常见；在常见 packages 中 grepping，也能发现 error handling code 与其他 code 的比例差不多。Julia 的人不在乎 error handling，所以它既 buggy 又 incomplete。我曾问过这件事，得到的答复是 exceptions 不起作用并不重要，因为你本来就不该使用 exceptions——你应该使用 Erlang style error handling，在出现 error 时 kill 整个 process，并 build transactionally robust systems，让它们能够承受随机 processes 被 killed。先不谈在一种没有 Erlang 那类 support 的 language 中这样做有多困难，在 Erlang 中，你可以轻松地 spin up 一百万个 processes。而在 Julia 中，只要你 load 一两个常用 packages，启动一个新的 Julia instance 就很容易花上半分钟或一分钟。要 spin up 一百万个 independent instances，每个花 30 seconds，总共大约需要两年。

既然我们已经大致谈到了 APIs，那么，error conditions 并不是 `Base` API 唯一不尽如人意的地方。从 function naming 到 arguments 的 order，Conventions 在许多方面都 inconsistent。有些作用于 collections 的 methods 会把 collection 作为 first argument，有些则不会（例如，replace 先接受 string，再接受 regex，而 match 先接受 regex，再接受 string）。

更普遍地说，`Base` APIs 在 Julia 所针对的小众领域之外，往往并不合理。例子多得无法一一列出，但请看这个：UDP interface 遇到 partial packet 时会 throws 一个 exception。这确实很奇怪，而且也没有帮助。[多个人都在这个 issue 中指出了这一点](https://github.com/JuliaLang/julia/pull/5697)，但 devs 还是决定 throw 那个 exception。Julia implementers 在 linear algebra 和其他熟悉的领域有极好的直觉。但他们终究也是人，在不熟悉的领域，直觉就没那么好了。问题是，即使有人评论说那可能不是最好的主意，他们仍然照着自己的直觉行事。

对我来说，另一个问题是，我并不属于 package manager 设计时面向的受众。它以一种巧妙的方式由 git 支撑，让人们能做各种我从来不会做的事情。这一切的结果是，它需要对每个 package 执行 `git status`，发生在我 run `Pkg.status()` 时，这让它慢得可怕；我关心的大多数其他 `Pkg` operations 也因为类似的原因而很慢。

如果它有我最想要的 feature，这也许还能接受：能够 specify packages 的 exact versions，并且让 packages 的多个、互相 conflicting 的 versions 同时 installed[3](https://danluu.com/julialang/#fn:T)。由于 core language libraries 和 packages 中存在各种 regressions，我经常需要使用某个 package 的 old version，才能让某个 function 真正工作，而这又可能要求使用其 dependencies 的 old versions。没有什么不靠 hack 的办法能做到这一点。

既然说到了那些我远比 core devs 更在乎的问题，那还有 benchmarking。网站上展示了一些相较于其他 languages、听起来很惊人的 speedup numbers。但那些 benchmarks 都与 real workloads 相去甚远。即使你在 workload characterization 和 systems architecture（是 computer architecture，不是 software architecture）方面有深厚背景，也很难从 microbenchmark numbers 推广出任何近似 real workload 的 performance results。据我所知，Julia 的 performance optimization 是基于一个更大的、由类似 benchmarks 构成的集合来进行的，而出于所有同样的原因，这也存在问题。Julia 实际上相当 fast，但这种 ad hoc benchmarking 基本上保证了仍有 performance 没有发挥出来。此外，这些 benchmarks 的写法还刻意让其他 languages 处于不利地位。来自其他 language communities 的人提交 PRs，想用各自 languages 的 idiomatic 方式 rewrite benchmarks 时，常常遭到拒绝。Julia 网站声称，“所有 benchmarks 都是为了 test specific algorithms 的 performance 而写的，并以合理的 idiom 来表达”，而针对特定 languages 作出 idiomatic 的调整会不公平。然而，如果你看看 Julia code，就会注意到，它们的写法避开了好些会让 performance 暴跌的做法。如果你关注 mailing list，就会看到，有不少直觉上很自然的 Julia code 写法会有非常糟糕的 performance。Julia benchmarks 避开了这些陷阱，但其他 languages 的 code 在编写时远没有得到这样的用心对待；事实上，情况恰恰相反。

我刚刚列举了 Julia 的一堆问题。我想，面对对 open source project 的抱怨，标准回应就是：你怎么不自己 fix 那些 bugs，你这个自以为理应得到照顾的小混蛋？好吧，我试过。一方面，[bugs 实在太多，我经常连 file bugs 都不做，更别说 fix 它们了，因为这样太打断手头的事](https://danluu.com/everything-is-broken/#julia)。但更大的问题是新 contributors 面临的门槛。我花了几个 person-days 来 fixing bugs（主要是在 debugging，而不是 writing code），这就几乎足以让我进入 GitHub 的 contributors 名单前 40 名。我的意思不是我 contributed 了很多，而是我并没有，但这仍然让我排在了前 40 名的紧后面。

有很多阻力让人无法为 Julia contributing。build 经常是 broken，或者有 failing tests。当我为 GitHub 上的 languages [polled Travis CI stats](https://danluu.com/broken-builds/) 时，Julia 的 uptime 基本上并列倒数第一。这不只是一个统计上的趣闻：我第一次尝试 fix 一些东西时，build 有将近一周都处于 non-deterministically broken 的状态，因为有人没有经过 review，就把 bad code 直接 checked 进了 master。我大概花了一周 fixing 一些东西，然后休息了一阵。下次我回来想 fix 一些东西时，又一次 bad check-in 导致 tests 整整一天都在 failing，于是我放弃了 fixing bugs 的念头。考虑到 test coverage 很差，tests 如此频繁地 fail，比听起来还糟。即便 build 是“working”的，它也使用 [recursive makefiles](http://aegis.sourceforge.net/auug97.pdf)，而且经常 fails，并给出一条 message，告诉你需要 run `make clean`，然后重新 build，这要花半小时。照做之后，它又经常 fails，并给出一条 message，告诉你需要 `make clean all`，然后重新 build，这要花一小时。接着还有一定可能再次 fail，你就得 manually clean out `deps`，再重新 build，这花的时间更长。而这还是好的情况！糟糕的情况是 build fails non-deterministically。这些都是使用 recursive make 时会出现的公认问题，早在 1997 年左右的 [Recursive Make Considered Harmful（认为 Recursive Make 有害）](http://aegis.sourceforge.net/auug97.pdf) 中就有描述。

而这甚至还不是向 core Julia contributing 的最大门槛。最大的门槛是，绝大多数 core code 在 written 时都没有任何 markers of intent（comments、meaningful variable names、asserts、meaningful function names、对 short variable 或 function names 的解释、design docs 等）。这一切都给 core Julia 深处的 debugging 和 fixing bugs 增添了额外负担。我恰好认识一位 Julia core contributors（目前在 GitHub 的 ranking 中列为 #2 contributor），当我问他一些我正在钻研的、比较晦涩的 functions 时，他也弄不明白。他建议我去问 mailing list，但对于 core codebase 中那些真正晦涩的 code，可能只有一到三个人真正理解；如果他们忙得没空回复，你也就没辙了。

我不介意花业余时间，免费帮别人 fix bugs。事实上，这种事我做得相当多，而且发现自己经常乐在其中。但我年纪大了，脾气也倔了，不想把闲暇时间花在 deciphering code 上，尤其是那些过于晦涩、连 core developers 都弄不明白的 code。

这些都不是说 Julia 不好，只是 core team 关心的事与我关心的事很不一样。在一篇抱怨性质的博客文章写到这里时，按理说应该提出一个替代方案，或者呼吁大家采取行动，但我不知道在这里这两者是否有意义。纯粹的 technical problems，比如 slow load times 或 package manager，正在被 fixed，或者将会被 fixed，所以没什么可说的。至于 process problems，比如不 writing tests、不 writing internal documentation，以及把 unreviewed、有时还是 breaking changes 的改动直接 checking 进 master，嗯，通过增加一个 code review process，强制大家为 code write tests 和 documentation，就能很“容易”[4](https://danluu.com/julialang/#fn:E)地 fix，但这并不是没有代价的。

一个由[才华横溢的](http://lwn.net/2000/0824/a/esr-sharing.php3) developers 组成的小团队，基本上能靠集体记忆把所有 code 装在脑子里；他们可以避开一切不是单纯 coding 的事情，取得很大进展，代价则是让其他人更难 contribute。这值得吗？很难说。如果必须让 [Jeff](https://github.com/JeffBezanson)、[Keno](https://github.com/Keno) 和其他效率极高的 core contributors 放慢脚步，结果只换来几个像我这样的废柴，那大概不值得。如果换来一千个像我这样的人，那大概就值得。现实处在中间那个模糊地带，可能值得，也可能不值得。大部分收益要到长期才会出现，而成本却不成比例地集中在短期支付，这让权衡变得复杂。我以前有位 [engineering professor](http://morrow.ece.wisc.edu/)，他说每个 engineering question 的答案都是“视情况而定”。Julia 应该怎么做？视情况而定。

### 2022 更新

这篇文章原本提到 Julia community 很友善，但我删掉了那部分，因为从收到的回应来看，这似乎并不准确。很多人非常支持，比如这位 Julia core developer：

![](https://danluu.com/images/julialang/julia_community.webp)

不过，也有不少人的回应相当恶劣。我认为，如果回应虽然大多积极，却有相当一部分恶劣的回应，那么说一个 community 友善并不准确，因为不需要太多恶意，就足以让一个群体显得不友善。另外，随着时间推移，对这篇文章的态度变得更加负面，因为 [communities 往往会跟随高层的方向](https://yosefk.com/blog/people-can-read-their-managers-mind.html)，而 Julia 的几位 co-creators 对这篇文章一直相当负面。

现在来谈谈这些问题究竟在多大程度上得到了 fixed。co-founders 最初的回应是，这些问题其实并不存在，而且这篇文章错得离谱。随着时间推移，一些问题得到了一些处理，回应又变成了这篇文章已经过时，问题都已 fixed，例如，[这是 Julia 的一位 co-creators 在 2016 年的回应](https://news.ycombinator.com/item?id=11073642)：

> Dan 的文章中，主要的合理抱怨是：
> 
> 1.  testing 和 coverage 不足。base Julia 的 Code coverage 已从他写这篇文章时的约 50% 上升到现在的 84%。虽然 tests 总可以更多一些（而且确实在增加），但我当然不认为这在目前还是一个主要的抱怨点。
>     
> 2.  Package 问题。Julia 现在有了 package precompilation，因此 package loading 相当 fast。Package manager 本身已经被 rewritten，改为使用 libgit2，这让它快了很多，尤其是在 shelling out 慢得令人痛苦的 Windows 上。
>     
> 3.  Travis uptime。这已经好得多了。Dan 写那篇文章时，确实存在一个特定的神秘问题。那个问题已经被 fixed。现在我们还在 AppVeyor 上做 Windows CI。
>     
> 4.  Julia internals 的 Documentation。考虑到现在已有相当全面的 developer docs，很难认为这个问题还没有得到处理：[http://julia.readthedocs.org/en/latest/devdocs/julia/](http://julia.readthedocs.org/en/latest/devdocs/julia/)
>     
> 
> 所以，那篇博客文章中提出的正当问题都已 fixed。

对此排名最靠前的回应是：

> > 主要的_合理_抱怨 $$...$$ 所提出的_正当_问题 $$...$$
> 
> 这种措辞实在是阴阳怪气、滑头。我建议重新考虑在公开讨论的回应中使用这种语气。
> 
> 与其暗示其他抱怨是不合理或不正当的，你完全可以干脆不提，或者至少在把它们搁置一旁时用更友善的措辞。比如，“……主要的_可采取行动的_抱怨……”或者“主要的 _technical_ 抱怨……”

先不谈语气问题，我认为文章中的主要问题，也就是 core team 对 correctness 的态度，既是一个正当问题，也是一个尚未 fixed 的问题。等我们看看那些被说成已 fixed 的具体问题实际上也仍未 fixed 时，就会看到这一点。

就 correctness 而言，如果 correctness 问题已经 fixed，我们就不会继续在 Julia 中看到 showstopping bugs。但我有几位朋友继续使用 Julia 好几年，直到受够了 correctness 问题，并发给我不少他们亲自遇到的严重 bugs；这些都发生在 2016 年那条声称 correctness 已经 fixed 的评论很久之后，例如，[从 distribution 进行 sampling 时 getting 一个 incorrect result](https://github.com/JuliaStats/Distributions.jl/issues/1241)、[从 array 进行 sampling 会 produces incorrect results](https://github.com/JuliaStats/StatsBase.jl/issues/642)、[product function，也就是 multiplication，会 produces incorrect results](https://github.com/JuliaLang/julia/issues/39183)、[quantile 会 produces incorrect results](https://github.com/JuliaStats/Statistics.jl/issues/119)、[mean 会 produces incorrect results](https://github.com/JuliaStats/Statistics.jl/issues/22)、[incorrect array indexing](https://github.com/JuliaLang/julia/issues/39379)、[divide 会 produces incorrect results](https://github.com/JuliaLang/julia/issues/49422)、[converting from float to int 会 produces incorrect results](https://github.com/JuliaLang/julia/issues/49422)、[quantile 会 produces incorrect results（又一次）](https://github.com/JuliaStats/Statistics.jl/issues/144)、[mean 会 produces incorrect results（又一次）](https://github.com/JuliaStats/Statistics.jl/issues/140)，等等。

Julia 一直不断出现非常严重的 bugs，还有许多其他人提到自己遇到了 serious bugs，例如[这里](https://kidger.site/thoughts/jax-vs-julia/)：

> 我至今还极其不愉快地记得，有一次我的一个 Julia models 一直 failing to train。我断断续续花了好几个月，想让它正常 working，尝试了所有能想到的办法。
> 
> 终于——终于！——我找到了 error：**Julia/Flux/Zygote 在 returning incorrect gradients**。在花了那么多精力应付上面的第 1 和第 2 点之后，到这一步我干脆放弃了。两小时的 development work 后，我让这个 model 成功 training 了……用的是 PyTorch。

还有[这里](https://discourse.julialang.org/t/state-of-machine-learning-in-julia/74385/13)

> 我被 Zygote/ReverseDiff.jl 中的 incorrect gradient bugs 坑过。这耗费了我好几周的生命，也彻底动摇了我对整个 Julia AD landscape 的信心。$$...$$ 我使用 PyTorch/TF/JAX 这么多年，从未遇到过一次 incorrect gradient bug。

还有[这里](https://discourse.julialang.org/t/state-of-machine-learning-in-julia/74385/21)

> 自从开始使用 Julia，我遇到了两个 Zygote 的 bugs，让我的工作耽搁了好几个月。往好的方面说，这迫使我深入 code，对自己使用的 libraries 了解了很多。但我发现事情已经有些难以承受，我需要花大量时间 debugging code，而不是做 climate research。

尽管 bugs 持续不断地出现，Julia 的 co-creators 和一些 core community members 的公开回应通常仍然声称，这些问题很快就会被 fixed，就像他们对这篇文章所做的回应一样（例如，参见[一些 core devs 在最近一篇文章下的评论，说所有问题都正在处理，很快就会被 fixed](https://news.ycombinator.com/item?id=31263516)，或者这条 [2020 年的评论，说 2016 年确实存在严重的 correctness 问题，但现在已经很好了](https://news.ycombinator.com/item?id=22138071)，等等）。

这些 developers 并没有认真对待 correctness issues 或其他问题，而是发表了诸如[以下这位 Julia co-creator 的言论；这些话是我的一位朋友转给我的，当时他又遇到了一个 showstopping bug](https://danluu.com/images/julialang/julia-testing-seriously.jpg)：

> 那些说 Julia 不认真对待 testing 的看法……我不明白。我们花了那么多时间和精力，对所有东西进行拼了命的 testing。我真的不知道还有哪个 open source project 能做到如此 thoroughly end-to-end tested。

总的说法是，Julia 不仅已经 fixed 了它的 correctness issues，而且在 correctness 方面已经好得不能再好了。

关于 package issues，当时的说法是 package load times 到 2016 年就已经 fixed 了。但这仍然是我认识的 Julia 使用者的一大抱怨，例如，Jamie Brandon 在 2022 年放弃了 Julia，因为他的 CSV parsing pipeline 要花两分钟才能 run，其中大部分时间都花在 package loading 上。另一个例子是，2020 年，[Julia developers 在一个 benchmark 中吹嘘，相比 R，Julia 在反复 loading 同一个 CSV 这种奇怪的 workload 上非常 fast（是在 loop 中，而不是反复 running 一个 script）](https://news.ycombinator.com/item?id=24746057)，有人指出，由于 Julia 的 package load times 非常长，这并不 realistic，说打开 CSV package 需要 2 seconds，之后 load 一个 plotting library 又需要 104 seconds。2022 年，面对 package loading 慢得令人痛苦的评论，一位 Julia developer 逐一回应这些问题，说每个问题都会被 fixed；关于 package loading，他们说：

> 我们离实现 native code caching，以及更多东西，已经很近了：[https://discourse.julialang.org/t/precompile-why/78770/8](https://discourse.julialang.org/t/precompile-why/78770/8)。你也会读到，困难来自 Julia 在 composability 和 aggressive specialization 上做出的重要 tradeoffs……但这并不是 fundamental 的，而且是可以克服的。是的，这一路有过一些痛苦，但希望最终我们能得到接近两全其美的东西。

一位 Julia co-creator 在 2016 年声称 package load time 的问题已经 fixed，然而这些问题在 2020 年和 2022 年竟然还能存在，实在令人好奇。但这就是我们所看到的 Julia PR 的总体模式。面对任何一项具体批评，对它的归类总是以下之一：不正当、很快就会 fixed，或者，如果这项批评已经超过一年，就是早已 fixed。但纵观不同时期的回应，我们能看到，那些“早已 fixed”或“很快就会 fixed”的问题，实际上在声称已经 fixed 的许多年后仍然没有 fixed。这些问题确实有进展，但如果在 Julia 中 load 一个 CSV，并使用一个 standard plotting library（相当于 ggplot2）来 generate 一个 plot，仍然需要将近两分钟，那么说 package load time 问题已经 fixed、说“package loading 相当 fast”，实在不太公允。correctness issues 也是如此：core libraries、Julia 本身，以及那些被称作让 Julia 如此出色的神奇之处的 libraries 中，仍然不断出现问题（例如，[谈论 features 时，autodiff 经常被称为 Julia 的一大优势](https://news.ycombinator.com/item?id=29684214)，但随后[一谈到 bugs，那些 bugs 就不算数了，因为它们不在 Julia 本身之中](https://news.ycombinator.com/item?id=31268796)（当然，最后那条评论下面，也有一位 Julia developer 评论说，所有问题很快都会得到处理）。

这里有一种偷换手法：一些 Julia co-creators 和 core developers 的条件反射式回应，是用一句话打发掉任何具体问题，而[不认识用过 Julia 的人的读者](https://twitter.com/danluu/status/1524949021252411392)如果在 HN 或 Twitter 上读到这句话，会觉得听起来很有道理。这能带来很好的 PR 效果，因为对于 Julia 这样的新兴 language，大多数潜在 users 在现实中并不认识认真使用过它的人，而如果不深入了解，那些条件反射式评论听起来也颇为可信。

我在这里用“条件反射式”这个词，是因为有些 Julia co-creators 似乎会对任何批评进行反驳，例如[这里](https://twitter.com/danluu/status/1526256307736412160)，一位 core developer 回应一篇关于 showstopping bugs 的文章时，说有 bugs 其实是好事；还有[这里](https://twitter.com/Viral_B_Shah/status/1315425480548462592)，我指出，有些人评论说，他们已经厌倦了 Julia developers 那些误导性的 benchmarking practices，一位 Julia co-creator 就跑来说：“我想在此郑重声明，我不同意你在这个 thread 中关于 Julia 的言论。”但我在那个 thread 中所说的，仅仅是存在像 [https://news.ycombinator.com/item?id=24748582](https://news.ycombinator.com/item?id=24748582) 这样的评论。郑重声明自己不同意这类评论存在，实在荒谬，因为它们显然确实存在。

条件反射式回应的另一个例子是[这个 2022 年的 thread](https://news.ycombinator.com/item?id=31401814)：有人尝试过 Julia，但在接连遇到需要花数周才能 debug 的 bugs 后，不再用它做严肃工作；他提出，Julia ecosystem 需要一次 rewrite，因为 community 的态度和文化导致了大量 correctness issues。一位 Julia core developer 对这条评论的“反驳”是，东西一直都在被 re-written，并举出了一些因 performance 原因而被 re-written 的例子。众所周知，Performance re-writes 是 introduce bugs 的好办法，这让那段“反驳”实际上成了某种反向反驳。但正如许多 Julia core developers 的典型做法，这个人看到有人提出一个问题（re-writes 不够），就条件反射式地否认，说 re-writes 已经够多了。

只要花一点时间读读这些条件反射式回应，再看看历史背景，就很容易看出它们站不住脚；但这种“否认、否认、再否认”的回应通常有极好的 PR 效果，对 Julia 也一直有效，所以他们这样做倒也可以理解。例如，[这条 2020 年的评论与 2016 年那条声称 correctness 已经 fixed 的评论相矛盾，它说 2016 年确实有严重问题，但到了 2020 年，“现在”已经好了](https://news.ycombinator.com/item?id=22138071)，有人回复说：“谢谢，这真让人振奋。”因为这让他们不再担心问题仍然存在。当然，在 2022 年的讨论中，你基本上还能看到同样的讨论，但在 2022 年读到讨论的人，通常不会回头查看同样的讨论是否也发生在 2020 年、2016 年、2013 年等时候。

关于 build uptime，对方声称，造成 uptime 问题的那个问题已经 fixed，但我当时评论的，是长期用“在我的 machine 上 works”来打发这个问题的态度。正如我们从上述例子中看到的，打发问题这一 meta-issue 仍在继续。

关于最后一个被称为正当、同时也被称为已经 fixed 的问题，也就是 documentation，它仍然是 community 中常见的抱怨，例如[2018 年的这里](https://news.ycombinator.com/item?id=17730094)，距离 2016 年声称 documentation 已经 fixed 过去了 2 年，还有[2019 年的这里](https://news.ycombinator.com/item?id=20589167)、[2022 年的这里](https://news.ycombinator.com/item?id=31398705)，等等。在一段长得多的抱怨中，有人指出：

> 最大的问题，也是他们似乎不愿意真正处理的问题，是实际使用 type system 做任何出色的事情，都要求你完全依赖可能存在、也可能不存在（或者并非最新）的 documentation。

另一个人也表达了相同的感受：

> 这确实是一个重要问题。

当然，像往常一样，[有人回应说，这很快就会被 fixed](https://news.ycombinator.com/item?id=17741797)。然而，你仍然能看到有人抱怨 documentation。

如果你回头阅读关于 Julia correctness issues 的讨论，还会看到三种常见辩护：所有东西都有 bugs，bugs 会很快被 fixed，以及 testing 其实很棒，因为 X 是 well tested 的。你可以在[2014 年的这里](https://groups.google.com/g/julia-users/c/GyH8nhExY9I/m/0BznqtD5VJgJ)和[2022 年的这里](https://news.ycombinator.com/item?id=31397499)看到“所有东西都有 bugs”的例子（当然，中间那些年也有），仿佛所有 non-zero bug rates 都是 the same，尽管许多 developers 已经指出，他们不再使用 Julia 工作，转而使用其他 ecosystems，因为虽然所有东西都有 bugs，但所有 non-zero numbers 当然并不是 the same。Bugs 会很快被 fixed，有时并不属实（例如，本文链接的许多 bugs 已经 open 了相当长一段时间，而且至今仍然 open），而且这也是[一种经典辩护，用来转移人们对那些 practices 的注意，而这些 practices 会直接导致数量异常庞大的新 bugs 的产生](https://twitter.com/danluu/status/1270987200545435648)。如上面多个链接中所指出的，debug correctness issues 可能需要数周或数月，因为许多 correctness issues 的形式是“silently return incorrect results”；而且，如前所述，我遇到过一个 bug，其中 exceptions 会 non-deterministically incorrectly 地没有被 caught。某些情况下，这类 bugs 在被发现后可能确实会很快被 fixed，但这些问题仍然会让 users 花费大量时间去 track down。我们在[上面](https://news.ycombinator.com/item?id=31401814)已经见过一个“testing 其实很棒，因为 X 是 well tested 的”的例子。如果你想看一个更新的例子，[这里有一个 2022 年的例子](https://news.ycombinator.com/item?id=31397499)：有人说，自己在 Julia 中遇到的 correctness bugs，比自己在数十年 programming 生涯中使用过的任何其他 ecosystem 都多，一位 Julia core dev 的回应却是，Julia 中许多东西都是 very well tested 的，例如 libuv，仿佛把某些 components 的 testing 做好，就成了可以抵御其他 components 中 bugs 的护身符。这显然荒谬，就像说一栋门敞开着的建筑不可能不安全，因为它还有非常坚固的墙壁，但这是 Julia core developers 常用的辩护。当然，针对撰文谈论 Julia 这件事，也存在直截了当的 FUD。例如，2022 年，在 Yuri Vishnevsky 关于 Julia bugs 的文章下面，一位 Julia co-creator 说：[“Yuri 的批评并不是 Julia 作为一种 language 存在 correctness bugs，而是某些 libraries 在与 common operations composed 时存在 bugs（其中许多现在已经得到处理）。”](https://news.ycombinator.com/item?id=31881164)。这当然完全不属实。在与 Yuri 的交谈中，他告诉我，他特意纳入了 core language 和 core library bugs 的例子，因为这些 bugs 出现得太频繁了；Julia 的 core 人员假装它们不存在，而他们的 FUD 似乎还奏效了，因为人们经常回应得仿佛他们的评论并非不实，这令他感到沮丧。如上所述，这种对简单事实的断然否认非常有效，所以人们采用这种手法也可以理解，但就我个人而言，我并不喜欢。

说清楚一点，我本身并不反对 software 是 buggy 的。正如我提到过的，[我认为 move fast and break things 可以是一种好的价值观](https://twitter.com/danluu/status/1487232684363370496)，因为它明确表明，比起 correctness，更看重 velocity。Julia 的 creators 和 core developers 的言论宣扬的却是，Julia 不仅 highly reliable 而且 correct，实际上还是世界一流的（“我们花了那么多时间和精力，对所有东西进行拼了命的 testing。我真的不知道还有哪个 open source project 能做到如此 thoroughly end-to-end tested。”等等）。但从 revealed preference 来看，我们能看出 Julia 的价值观是“move fast and break things”。

## 原文

Here's a language that gives near-C performance that feels like Python or Ruby with optional type annotations (that you can feed to [one of two](https://github.com/tonyhffong/Lint.jl) [static analysis tools](https://github.com/astrieanna/TypeCheck.jl)) that has good support for macros plus decent-ish support for FP, plus a lot more. What's not to like? I'm mostly not going to talk about how great Julia is, though, because you can find plenty of blog posts that do that all over the internet.

The last time I used Julia (around Oct. 2014), I ran into two new (to me) bugs involving bogus exceptions when processing Unicode strings. To work around those, I used a try/catch, but of course that runs into a non-deterministic bug I've found with try/catch. I also hit a bug where a function returned a completely wrong result if you passed it an argument of the wrong type instead of throwing a "no method" error. I spent half an hour writing a throwaway script and ran into four bugs in the core language.

The second to last time I used Julia, I ran into too many bugs to list; the worst of them caused generating plots to take 30 seconds per plot, which caused me to switch to R/ggplot2 for plotting. First there was this bug with [plotting dates didn't work](https://github.com/dcjones/Gadfly.jl/issues/462). When I worked around that I ran into a regression that caused plotting to [break large parts of the core language](https://github.com/JuliaLang/julia/issues/8631), so that data manipulation had to be done before plotting. That would have been fine if I knew exactly what I wanted, but for exploratory data analysis I want to plot some data, do something with the data, and then plot it again. Doing that required restarting the REPL for each new plot. That would have been fine, except that it takes 22 seconds to load Gadfly on my 1.7GHz Haswell (timed by using `time` on a file that loads Gadfly and does no work), plus another 10-ish seconds to load the other packages I was using, turning my plotting workflow into: restart REPL, wait 30 seconds, make a change, make a plot, look at a plot, repeat.

It's not unusual to run into bugs when using a young language, but Julia has more than its share of bugs for something at its level of maturity. If you look at the test process, that's basically inevitable.

As far as I can tell, FactCheck is the most commonly used thing resembling a modern test framework, and it's barely used. Until quite recently, it was unmaintained and broken, but even now the vast majority of tests are written using `@test`, which is basically an assert. It's theoretically possible to write good tests by having a file full of test code and asserts. But in practice, anyone who's doing that isn't serious about testing and isn't going to write good tests.

Not only are existing tests not very good, most things aren't tested at all. You might point out that the coverage stats for a lot of packages aren't so bad, but last time I looked, there was a bug in the coverage tool that caused it to only aggregate coverage statistics for functions with non-zero coverage. That is to say, code in untested functions doesn't count towards the coverage stats! That, plus the weak notion of test coverage that's used (line coverage[1](https://danluu.com/julialang/#fn:L)) make the coverage stats unhelpful for determining if packages are well tested.

The lack of testing doesn't just mean that you run into regression bugs. Features just disappear at random, too. When the REPL got rewritten a lot of existing shortcut keys and other features stopped working. As far as I can tell, that wasn't because anyone wanted it to work differently. It was because there's no way to re-write something that isn't tested without losing functionality.

Something that goes hand-in-hand with the level of testing on most Julia packages (and the language itself) is the lack of a good story for error handling. Although you can easily use `Nullable` (the Julia equivalent of `Some/None`) or error codes in Julia, the most common idiom is to use exceptions. And if you use things in `Base`, like arrays or `/`, you're stuck with exceptions. I'm [not a fan](https://web.archive.org/web/20140213012902/http://blogs.msdn.com/b/oldnewthing/archive/2005/01/14/352949.aspx), but that's fine -- plenty of reliable software uses exceptions for error handling.

The problem is that because the niche Julia occupies doesn't care[2](https://danluu.com/julialang/#fn:R) about error handling, it's extremely difficult to write a robust Julia program. When you're writing smaller scripts, you often want to “fail-fast” to make debugging easier, but for some programs, you want the program to do something reasonable, keep running, and maybe log the error. It's hard to write a robust program, even for this weak definition of robust. There are problems at multiple levels. For the sake of space, I'll just list two.

If I'm writing something I'd like to be robust, I really want function documentation to include all exceptions the function might throw. Not only do the Julia docs not have that, it's common to call some function and get a random exception that has to do with an implementation detail and nothing to do with the API interface. Everything I've written that actually has to be reliable has been exception free, so maybe that's normal when people use exceptions? Seems pretty weird to me, though.

Another problem is that catching exceptions doesn't work (sometimes, at random). I ran into one bug where using exceptions caused code to be incorrectly optimized out. You might say that's not fair because it was [caught using a fuzzer](https://github.com/danluu/Fuzz.jl), and fuzzers are supposed to find bugs, but the fuzzer wasn't fuzzing exceptions or even expressions. The implementation of the fuzzer just happens to involve eval'ing function calls, in a loop, with a `try/catch` to handle exceptions. Turns out, if you do that, the function might not get called. This isn't a case of using a fuzzer to generate billions of tests, one of which failed. This was a case of trying one thing, one of which failed. That bug is now fixed, but there's still a nasty bug that causes exceptions to sometimes fail to be caught by `catch`, which is pretty bad news if you're putting something in a `try/catch` block because you don't want an exception to trickle up to the top level and kill your program.

When I grepped through `Base` to find instances of actually catching an exception and doing something based on the particular exception, I could only find a single one. Now, it's me scanning grep output in less, so I might have missed some instances, but it isn't common, and grepping through common packages finds a similar ratio of error handling code to other code. Julia folks don't care about error handling, so it's buggy and incomplete. I once asked about this and was told that it didn't matter that exceptions didn't work because you shouldn't use exceptions anyway -- you should use Erlang style error handling where you kill the entire process on an error and build transactionally robust systems that can survive having random processes killed. Putting aside the difficulty of that in a language that doesn't have Erlang's support for that kind of thing, you can easily spin up a million processes in Erlang. In Julia, if you load just one or two commonly used packages, firing up a single new instance of Julia can easily take half a minute or a minute. To spin up a million independent instances would at 30 seconds a piece would take approximately two years.

Since we're broadly on the topic of APIs, error conditions aren't the only place where the `Base` API leaves something to be desired. Conventions are inconsistent in many ways, from function naming to the order of arguments. Some methods on collections take the collection as the first argument and some don't (e.g., replace takes the string first and the regex second, whereas match takes the regex first and the string second).

More generally, `Base` APIs outside of the niche Julia targets often don't make sense. There are too many examples to list them all, but consider this one: the UDP interface throws an exception on a partial packet. This is really strange and also unhelpful. [Multiple people stated that on this issue](https://github.com/JuliaLang/julia/pull/5697) but the devs decided to throw the exception anyway. The Julia implementers have great intuition when it comes to linear algebra and other areas they're familiar with. But they're only human and their intuition isn't so great in areas they're not familiar with. The problem is that they go with their intuition anyway, even in the face of comments about how that might not be the best idea.

Another thing that's an issue for me is that I'm not in the audience the package manager was designed for. It's backed by git in a clever way that lets people do all sorts of things I never do. The result of all that is that it needs to do `git status` on each package when I run `Pkg.status()`, which makes it horribly slow; most other `Pkg` operations I care about are also slow for a similar reason.

That might be ok if it had the feature I most wanted, which is the ability to specify exact versions of packages and have multiple, conflicting, versions of packages installed[3](https://danluu.com/julialang/#fn:T). Because of all the regressions in the core language libraries and in packages, I often need to use an old version of some package to make some function actually work, which can require old versions of its dependencies. There's no non-hacky way to do this.

Since I'm talking about issues where I care a lot more than the core devs, there's also benchmarking. The website shows off some impressive sounding speedup numbers over other languages. But they're all benchmarks that are pretty far from real workloads. Even if you have a strong background in workload characterization and systems architecture (computer architecture, not software architecture), it's difficult to generalize performance results on anything resembling real workload from microbenchmark numbers. From what I've heard, performance optimization of Julia is done from a larger set of similar benchmarks, which has problems for all of the same reasons. Julia is actually pretty fast, but this sort of ad hoc benchmarking basically guarantees that performance is being left on the table. Moreover, the benchmarks are written in a way that stacks the deck against other languages. People from other language communities often get rebuffed when they submit PRs to rewrite the benchmarks in their languages idiomatically. The Julia website claims that "all of the benchmarks are written to test the performance of specific algorithms, expressed in a reasonable idiom", and that making adjustments that are idiomatic for specific languages would be unfair. However, if you look at the Julia code, you'll notice that they're written in a way to avoid doing one of a number of things that would crater performance. If you follow the mailing list, you'll see that there are quite a few intuitive ways to write Julia code that has very bad performance. The Julia benchmarks avoid those pitfalls, but the code for other languages isn't written with anywhere near that care; in fact, it's just the opposite.

I've just listed a bunch of issues with Julia. I believe the canonical response for complaints about an open source project is, why don't you fix the bugs yourself, you entitled brat? Well, I tried that. For one thing, [there are so many bugs that I often don't file bugs, let alone fix them, because it's too much of an interruption](https://danluu.com/everything-is-broken/#julia). But the bigger issue are the barriers to new contributors. I spent a few person-days fixing bugs (mostly debugging, not writing code) and that was almost enough to get me into the top 40 on GitHub's list of contributors. My point isn't that I contributed a lot. It's that I didn't, and that still put me right below the top 40.

There's lots of friction that keeps people from contributing to Julia. The build is often broken or has failing tests. When I [polled Travis CI stats](https://danluu.com/broken-builds/) for languages on GitHub, Julia was basically tied for last in uptime. This isn't just a statistical curiosity: the first time I tried to fix something, the build was non-deterministically broken for the better part of a week because someone checked bad code directly into master without review. I spent maybe a week fixing a few things and then took a break. The next time I came back to fix something, tests were failing for a day because of another bad check-in and I gave up on the idea of fixing bugs. That tests fail so often is even worse than it sounds when you take into account the poor test coverage. And even when the build is "working", it uses [recursive makefiles](http://aegis.sourceforge.net/auug97.pdf), and often fails with a message telling you that you need to run `make clean` and build again, which takes half an hour. When you do so, it often fails with a message telling you that you need to `make clean all` and build again, with takes an hour. And then there's some chance that will fail and you'll have to manually clean out `deps` and build again, which takes even longer. And that's the good case! The bad case is when the build fails non-deterministically. These are well-known problems that occur when using recursive make, described in [Recursive Make Considered Harmful](http://aegis.sourceforge.net/auug97.pdf) circa 1997.

And that's not even the biggest barrier to contributing to core Julia. The biggest barrier is that the vast majority of the core code is written with no markers of intent (comments, meaningful variable names, asserts, meaningful function names, explanations of short variable or function names, design docs, etc.). There's a tax on debugging and fixing bugs deep in core Julia because of all this. I happen to know one of the Julia core contributors (presently listed as the #2 contributor by GitHub's ranking), and when I asked him about some of the more obtuse functions I was digging around in, he couldn't figure it out either. His suggestion was to ask the mailing list, but for the really obscure code in the core codebase, there's perhaps one to three people who actually understand the code, and if they're too busy to respond, you're out of luck.

I don't mind spending my spare time working for free to fix other people's bugs. In fact, I do quite a bit of that and it turns out I often enjoy it. But I'm too old and crotchety to spend my leisure time deciphering code that even the core developers can't figure out because it's too obscure.

None of this is to say that Julia is bad, but the concerns of the core team are pretty different from my concerns. This is the point in a complain-y blog post where you're supposed to suggest an alternative or make a call to action, but I don't know that either makes sense here. The purely technical problems, like slow load times or the package manager, are being fixed or will be fixed, so there's not much to say there. As for process problems, like not writing tests, not writing internal documentation, and checking unreviewed and sometimes breaking changes directly into master, well, that's “easy”[4](https://danluu.com/julialang/#fn:E) to fix by adding a code review process that forces people to write tests and documentation for code, but that's not free.

A small team of [highly talented](http://lwn.net/2000/0824/a/esr-sharing.php3) developers who can basically hold all of the code in their collective heads can make great progress while eschewing anything that isn't just straight coding at the cost of making it more difficult for other people to contribute. Is that worth it? It's hard to say. If you have to slow down [Jeff](https://github.com/JeffBezanson), [Keno](https://github.com/Keno), and the other super productive core contributors and all you get out of it is a couple of bums like me, that's probably not worth it. If you get a thousand people like me, that's probably worth it. The reality is in the ambiguous region in the middle, where it might or might not be worth it. The calculation is complicated by the fact that most of the benefit comes in the long run, whereas the costs are disproportionately paid in the short run. I once had [an engineering professor](http://morrow.ece.wisc.edu/) who claimed that the answer to every engineering question is "it depends". What should Julia do? It depends.

### 2022 Update

This post originally mentioned how friendly the Julia community is, but I removed that since it didn't seem accurate in light of the responses. Many people were highly supportive, such as this Julia core developer:

![](https://danluu.com/images/julialang/julia_community.webp)

However, a number of people had some pretty nasty responses and I don't think it's accurate to say that a community is friendly when the response is mostly positive, but with a significant fraction of nasty responses, since it doesn't really take a lot of nastiness to make a group seem unfriendly. Also, sentiment about this post has gotten more negative over time as [communities tend to take their direction from the top](https://yosefk.com/blog/people-can-read-their-managers-mind.html) and a couple of the Julia co-creators have consistently been quite negative about this post.

Now, onto the extent to which these issues have been fixed. The initial response from the co-founders was that the issues aren't really real and the post is badly mistaken. Over time, as some of the issues had some work done on them, the response changed to being that this post is out of date and the issues were all fixed, e.g., [here's a response from one of the co-creators of Julia in 2016](https://news.ycombinator.com/item?id=11073642):

> The main valid complaints in Dan's post were:
> 
> 1.  Insufficient testing & coverage. Code coverage is now at 84% of base Julia, from somewhere around 50% at the time he wrote this post. While you can always have more tests (and that is happening), I certainly don't think that this is a major complaint at this point.
>     
> 2.  Package issues. Julia now has package precompilation so package loading is pretty fast. The package manager itself was rewritten to use libgit2, which has made it much faster, especially on Windows where shelling out is painfully slow.
>     
> 3.  Travis uptime. This is much better. There was a specific mystery issue going on when Dan wrote that post. That issue has been fixed. We also do Windows CI on AppVeyor these days.
>     
> 4.  Documentation of Julia internals. Given the quite comprehensive developer docs that now exist, it's hard to consider this unaddressed: [http://julia.readthedocs.org/en/latest/devdocs/julia/](http://julia.readthedocs.org/en/latest/devdocs/julia/)
>     
> 
> So the legitimate issues raised in that blog post are fixed.

The top response to that is:

> > The main _valid_ complaints \[...\] the _legitimate_ issues raised \[...\]
> 
> This is a really passive-aggressive weaselly phrasing. I’d recommend reconsidering this type of tone in public discussion responses.
> 
> Instead of suggesting that the other complaints were invalid or illegitimate, you could just not mention them at all, or at least use nicer language in brushing them aside. E.g. “... the main _actionable_ complaints...” or “the main _technical_ complaints ...”

Putting aside issues of tone, I would say that the main issue from the post, the core team's attitude towards correctness, is both a legitimate issue and one that's unfixed, as we'll see when we look at how the specific issues mentioned as fixed are also unfixed.

On correctness, if the correctness issues were fixed, we wouldn't continue to see showstopping bugs in Julia, but I have a couple of friends who continued to use Julia for years until they got fed up with correctness issues and sent me quite a few bugs that they personally ran into that were serious well after the 2016 comment about correctness being fixed, such as [getting an incorrect result when sampling from a distribution](https://github.com/JuliaStats/Distributions.jl/issues/1241), [sampling from an array produces incorrect results](https://github.com/JuliaStats/StatsBase.jl/issues/642), [the product function, i.e., multiplication, produces incorrect results](https://github.com/JuliaLang/julia/issues/39183), [quantile produces incorrect results](https://github.com/JuliaStats/Statistics.jl/issues/119), [mean produces incorrect results](https://github.com/JuliaStats/Statistics.jl/issues/22), [incorrect array indexing](https://github.com/JuliaLang/julia/issues/39379), [divide produces incorrect results](https://github.com/JuliaLang/julia/issues/49422), [converting from float to int produces incorrect results](https://github.com/JuliaLang/julia/issues/49422), [quantile produces incorrect results (again)](https://github.com/JuliaStats/Statistics.jl/issues/144), [mean produces incorrect results (again)](https://github.com/JuliaStats/Statistics.jl/issues/140), etc.

There has been a continued flow of very serious bugs from Julia and numerous other people noting that they've run into serious bugs, such as [here](https://kidger.site/thoughts/jax-vs-julia/):

> I remember all too un-fondly a time in which one of my Julia models was failing to train. I spent multiple months on-and-off trying to get it working, trying every trick I could think of.
> 
> Eventually – eventually! – I found the error: **Julia/Flux/Zygote was returning incorrect gradients**. After having spent so much energy wrestling with points 1 and 2 above, this was the point where I simply gave up. Two hours of development work later, I had the model successfully training… in PyTorch.

And [here](https://discourse.julialang.org/t/state-of-machine-learning-in-julia/74385/13)

> I have been bit by incorrect gradient bugs in Zygote/ReverseDiff.jl. This cost me weeks of my life and has thoroughly shaken my confidence in the entire Julia AD landscape. \[...\] In all my years of working with PyTorch/TF/JAX I have not once encountered an incorrect gradient bug.

And [here](https://discourse.julialang.org/t/state-of-machine-learning-in-julia/74385/21)

> Since I started working with Julia, I’ve had two bugs with Zygote which have slowed my work by several months. On a positive note, this has forced me to plunge into the code and learn a lot about the libraries I’m using. But I’m finding myself in a situation where this is becoming too much, and I need to spend a lot of time debugging code instead of doing climate research.

Despite this continued flow of bugs, public responses from the co-creators of Julia as well as a number of core community members generally claim, as they did for this post, that the issues will be fixed very soon (e.g., see [the comments here by some core devs on a recent post, saying that all of the issues are being addressed and will be fixed soon](https://news.ycombinator.com/item?id=31263516), or this [2020 comment about how the there were serious correctness issues in 2016 but things are now good](https://news.ycombinator.com/item?id=22138071), etc.).

Instead of taking the correctness issues or other issues seriously, the developers make statements like [the following comments from a co-creator of Julia, passed to me by a friend of mine as my friend ran into yet another showstopping bug](https://danluu.com/images/julialang/julia-testing-seriously.jpg):

> takes that Julia doesn't take testing seriously... I don't get it. the amount of time and energy we spend on testing the bejeezus out of everything. I literally don't know any other open source project as thoroughly end-to-end tested.

The general claim is that, not only has Julia fixed its correctness issues, it's as good as it gets for correctness.

On the package issues, the claim was that package load times were fixed by 2016. But this continues to be a major complaint of the people I know who use Julia, e.g., Jamie Brandon switched away from using Julia in 2022 because it took two minutes for his CSV parsing pipeline to run, where most of the time was package loading. Another example is that, in 2020, [on a benchmark where the Julia developers bragged that Julia is very fast at the curious workload of repeatedly loading the same CSV over and over again (in a loop, not by running a script repeatedly) compared to R](https://news.ycombinator.com/item?id=24746057), some people noted that this was unrealistic due to Julia's very long package load times, saying that it takes 2 seconds to open the CSV package and then 104 seconds to load a plotting library. In 2022, in response to comments that package loading is painfully slow, a Julia developer responds to each issue saying each one will be fixed; on package loading, they say

> We're getting close to native code caching, and more: [https://discourse.julialang.org/t/precompile-why/78770/8](https://discourse.julialang.org/t/precompile-why/78770/8). As you'll also read, the difficulty is due to important tradeoffs Julia made with composability and aggressive specialization...but it's not fundamental and can be surmounted. Yes there's been some pain, but in the end hopefully we'll have something approximating the best of both worlds.

It's curious that these problems could exist in 2020 and 2022 after a co-creator of Julia claimed, in 2016, that the package load time problems were fixed. But this is the general pattern of Julia PR that we see. On any particular criticism, the criticism is one of: illegitimate, fixed soon or, when the criticism is more than a year old, already fixed. But we can see by looking at responses over time that the issues that are "already fixed" or "will be fixed soon" are, in fact, not fixed many years after claims that they were fixed. It's true that there is progress on the issues, but it wasn't really fair to say that package load time issues were fixed and "package loading is pretty fast" when it takes nearly two minutes to load a CSV and use a standard plotting library (an equivalent to ggplot2) to generate a plot in Julia. And likewise for correctness issues when there's still a steady stream of issues in core libraries, Julia itself, and libraries that are named as part of the magic that makes Julia great (e.g., [autodiff is frequently named as a huge advantage of Julia when it comes to features](https://news.ycombinator.com/item?id=29684214), but then [when it comes to bugs, those bugs don't count because they're not in Julia itself](https://news.ycombinator.com/item?id=31268796) (that last comment, of course, has a comment from a Julia developer noting that all of the issues will be addressed soon).

There's a sleight of hand here where the reflexive response from a number of the co-creators as well as core developers of Julia is to brush off any particular issue with a comment that sounds plausible if read on HN or Twitter by [someone who doesn't know people who've used Julia](https://twitter.com/danluu/status/1524949021252411392). This makes for good PR since, with an emerging language like Julia, most potential users won't have real connections who've used it seriously and the reflexive comments sound plausible if you don't look into them.

I use the word reflexive here because it seems that some co-creators of Julia respond to any criticism with a rebuttal, such as [here](https://twitter.com/danluu/status/1526256307736412160), where a core developer responds to a post about showstopping bugs by saying that having bugs is actually good, and [here](https://twitter.com/Viral_B_Shah/status/1315425480548462592), where in response to my noting that some people had commented that they were tired of misleading benchmarking practices by Julia developers, a co-creator of Julia drops in to say "I would like to let it be known for the record that I do not agree with your statements about Julia in this thread." But my statements in the thread were merely that there existed comments like [https://news.ycombinator.com/item?id=24748582](https://news.ycombinator.com/item?id=24748582). It's quite nonsensical to state, for the record, a disagreement that those kinds of comments exist because they clearly do exist.

Another example of a reflexive response is [this 2022 thread](https://news.ycombinator.com/item?id=31401814), where someone who tried Julia but stopped using it for serious work after running into one too many bugs that took weeks to debug suggests that the Julia ecosystem needs a rewrite because the attitude and culture in the community results in a large number of correctness issues. A core Julia developer "rebuts" the comment by saying that things are re-written all the time and gives examples of things that were re-written for performance reasons. Performance re-writes are, famously, a great way to introduce bugs, making the "rebuttal" actually a kind of anti-rebuttal. But, as is typical for many core Julia developers, the person saw that there was an issue (not enough re-writes) and reflexively responded with a denial, that there are enough re-writes.

These reflexive responses are pretty obviously bogus if you spend a bit of time reading them and looking at the historical context but this kind of "deny deny deny" response is generally highly effective PR and has been effective for Julia, so it's understandable that it's done. For example, [on this 2020 comment that belies the 2016 comment about correctness being fixed that says that there were serious issues in 2016 but things are "now" good in 2020](https://news.ycombinator.com/item?id=22138071), someone responds "Thank you, this is very heartening." since it relieves them of their concern that there are still issues. Of course, you can see basically the same discussion on discussions in 2022, but people reading the discussion in 2022 generally won't go back to see that this same discussion happened in 2020, 2016, 2013, etc.

On the build uptime, the claim is that the issue causing uptime issues was fixed, but my comment there was on the attitude of brushing off the issue for an extended period of time with "works on my machine". As we can see from the examples above, the meta-issue of brushing off issues continued.

On the last issue that was claimed to legitimate, which was also claimed to be fixed, documentation, this is still a common complaint from the community, e.g., [here in 2018](https://news.ycombinator.com/item?id=17730094), 2 years after it was claimed that documentation was fixed in 2016, [here in 2019](https://news.ycombinator.com/item?id=20589167), [here in 2022](https://news.ycombinator.com/item?id=31398705), etc. In a much lengthier complaint, one person notes

> The biggest issue, and one they seem unwilling to really address, is that actually using the type system to do anything cool requires you to rely entirely on documentation which may or may not exist (or be up-to-date).

And another echoes this sentiment with

> This is truly an important issue.

Of course, [there's a response saying this will be fixed soon](https://news.ycombinator.com/item?id=17741797), as is generally the case. And yet, you can still find people complaining about the documentation.

If you go back and read discussions on Julia correctness issues, three more common defenses are that everything has bugs, bugs are quickly fixed, and testing is actually great because X is well tested. You can see examples of "everything has bugs" [here in 2014](https://groups.google.com/g/julia-users/c/GyH8nhExY9I/m/0BznqtD5VJgJ) as well as [here in 2022](https://news.ycombinator.com/item?id=31397499) (and in between as well, of course), as if all non-zero bug rates are the same, even though a number of developers have noted that they stopped using Julia for work and switched to other ecosystems because, while everything has bugs, all non-zero numbers are, of course, not the same. Bugs getting fixed quickly is sometimes not true (e.g., many of the bugs linked in this post have been open for quite a while and are still open) and is also [a classic defense that's used to distract from the issue of practices that directly lead to the creation of an unusually large number of new bugs](https://twitter.com/danluu/status/1270987200545435648). As noted in a number of links, above, it can take weeks or months to debug correctness issues since many of the correctness issues are of the form "silently return incorrect results" and, as noted above, I ran into a bug where exceptions were non-deterministically incorrectly not caught. It may be true that, in some cases, these sorts of bugs are quickly fixed when found, but those issues still cost users a lot of time to track down. We saw an example of "testing is actually great because X is well tested" [above](https://news.ycombinator.com/item?id=31401814). If you'd like a more recent example, [here's one from 2022](https://news.ycombinator.com/item?id=31397499) where, in response to someone saying that ran into more correctness bugs in Julia than than in any other ecosystem they've used in their decades of programming, a core Julia dev responds by saying that a number of things are very well tested in Julia, such as libuv, as if testing some components well is a talisman that can be wielded against bugs in other components. This is obviously absurd, in that it's like saying that a building with an open door can't be insecure because it also has very sturdy walls, but it's a common defense used by core Julia developers. And, of course, there's also just straight-up FUD about writing about Julia. For example, in 2022, on Yuri Vishnevsky's post on Julia bugs, a co-creator of Julia said ["Yuri's criticism was not that Julia has correctness bugs as a language, but that certain libraries when composed with common operations had bugs (many of which are now addressed)."](https://news.ycombinator.com/item?id=31881164). This is, of course, completely untrue. In conversations with Yuri, he noted to me that he specifically included examples of core language and core library bugs because those happened so frequently, and it was frustrating that core Julia people pretended those didn't exist and that their FUD seemed to work since people would often respond as if their comments weren't untrue. As mentioned above, this kind of flat denial of simple matters of fact is highly effective, so it's understandable that people employ it but, personally, it's not to my taste.

To be clear, I don't inherently have a problem with software being buggy. As I've mentioned, [I think move fast and break things can be a good value](https://twitter.com/danluu/status/1487232684363370496) because it clearly states that velocity is more valued than correctness. Comments from the creators of Julia as well as core developers broadcast that Julia is not just highly reliable and correct, but actually world class ("the amount of time and energy we spend on testing the bejeezus out of everything. I literally don't know any other open source project as thoroughly end-to-end tested.", etc.). But, by revealed preference, we can see that Julia's values are "move fast and break things".
