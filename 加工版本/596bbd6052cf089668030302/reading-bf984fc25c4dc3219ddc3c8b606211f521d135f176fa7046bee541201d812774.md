### 第 1 章：Introduction（引言）

_本章所有内容都会在后文得到详细得多的介绍。_

招聘人员来 manage system stability 的两种 approaches：

#### 传统的 approach：sysadmins

-   将现有的 components 进行 Assemble，再 deploy，以 produce 一个 service
-   在 events 和 updates 发生时对其 Respond
-   随着 service grows，让 team Grow，以消化增加的工作
-   优点
    -   容易 implement，因为这是 standard 做法
    -   可供招聘的 talent pool 很大
    -   有大量可用的 software
-   缺点
    -   change management 和 event handling 所需的 Manual intervention，会导致 team 的 size 随 system 的 load 而 scale
    -   Ops 与 dev 存在根本冲突，这可能导致对 changes 的病态抵制，继而引发 devs 同样病态的回应：他们会将“launches” reclassify 为“incremental updates”、“flag flips”等。

#### Google 的 approach：SREs

-   让 software engineers 来做 operations
-   Candidates 应当能够达到或接近通常的 dev hiring bar，也可能具备一些在 devs 中较为少见的额外 skills（例如 L1 - L3 networking 或 UNIX system internals）。
-   Career progress 与 dev career track 相当
-   结果
    -   SREs 会因手工做 tasks 而感到无聊
    -   具备 automate tasks 所需的 skillset
    -   做与 operations team 相同的工作，但依靠 automation，而不是 manual labor
-   为了避免 manual labor trap 导致 team size 随 service load 而 scale，Google 为 SREs 的“ops”工作量设置了 50% 的 cap
    -   这是 Upper bound。实际的 ops 工作量预计会低得多
-   优点
    -   进行 scale 的成本更低
    -   能够 Circumvents devs/ops split
-   缺点
    -   难以招聘合适的人
    -   某些做法可能不合常规，需要 management support（例如，因为 error budget 已经 depleted，而决定在本季度停止 releases，product team 可能会反对这一决定）

_我不太明白，这怎么就成了 circumventing dev/ops split 的例子。我能理解，在某种意义上确实如此，但因为 error budget 已经 got hit 而 stopping 所有 releases 的例子，似乎与“sysadmin”例子中 teams 反对 launches 的情况没有根本区别。看起来，SREs 拥有更多可动用的政治资本，而且在给出的具体例子里，SREs 可能更通情达理，但没有理由认为 sysadmins 就不能通情达理。_

#### SRE 的 Tenets

-   SRE team 负责 latency、performance、efficiency、change management、monitoring、emergency response 和 capacity planning

#### 确保持续专注于 engineering

-   50% 的 ops cap 意味着，超额的额外 ops 工作会被 redirected 给 product teams
-   既为 product teams 提供 feedback mechanism，也能 keeps load down
-   目标是每个 8-12 hour 的 on-call shift 最多有 2 个 events
-   所有 serious incidents 都要做 Postmortems，即使它们没有 trigger a page
-   Blameless postmortems（不追责的事后复盘）

_每个 shift 有 2 个 events 是 max，那么 average 是多少？预计每周会有多少 on-call events 从 SRE team 转交给 dev team？_

_如何从 blameful postmortem culture 转变为 blameless postmortem culture？既然现在人人都知道应该做 blameless postmortems，[每个人都会声称自己在这样做。这有点像声称自己拥有良好的 testing 和 deployment practices](https://danluu.com/wat/)。我很幸运，所在的 on call rotation 从未被 paged，但当我与最近加入并参与 on call 的人交谈时，他们讲述的却是一些不太愉快的经历：相互指责、出言不逊、推卸责任。人人都知道自己应该做到 blameless，这似乎反而让指出 blamefulness 变得更难，而不是更容易。_

#### 在不 breaking SLO 的前提下 Move fast

-   Error budget。对几乎所有事物而言，100% 都是错误的 reliability target
-   从 5 9s 提升到 100% reliability，大多数 users 都无法察觉，却需要付出巨大的努力
-   设定一个承认 trade-off 并留下 error budget 的 goal
-   Error budget 可以 spent 在任何事情上：launching features，等等
-   Error budget 使大家能够讨论，如何通过 phased rollouts 和 1% experiments 来 maintain 可容忍 levels 的 errors
-   SRE team 的 Goal 不是“zero outages”——SRE 与 product devs 是 incentive aligned 的，都会希望 spend error budget，以获得 maximum feature velocity

_虽然没有明确说出来，但对于需要“move fast”的 teams，如果持续远低于 error budget，可能意味着 team 在 reliability 上投入了过多精力。_

_我很喜欢这个想法，但当我与 Jessica Kerr 讨论时，她提出了异议：也许你低于 error budget 仅仅是因为运气好，而单个非常糟糕的 event 就可能 wipe out 你未来十年的 error budget。后续问题是：你如何才能对自己的 risk model 有足够信心，从而有意 consume error budget 来 move faster，而不担心 downstream（时间上靠后）的 bad event 会让你 overbudget？Nat Welch（一位前 Google SRE）对此回应说，可以通过 simulated disasters 和其他 testing 来建立信心。_

#### Monitoring（监控）

-   Monitoring 绝不应要求人来 interpret alerting domain 的任何部分
-   monitoring output 有三种 valid 类型
    -   Alerts：人需要立即 take action
    -   Tickets：人最终需要 take action
    -   Logging：不需要 action
    -   请注意，例如，graphs 是一种 log

#### Emergency Response（应急响应）

-   Reliability 是 MTTF (mean-time-to-failure) 和 MTTR (mean-time-to-recovery) 的 function
-   在 evaluating responses 时，我们关心的是 MTTR
-   人会 add latency
-   不需要人来 respond 的 Systems 会因 lower MTTR 而有 higher availability
-   有了“playbook”，就能产生 3x lower MTTR
    -   有能 respond 一切的 hero generalists 是管用的，但有 playbooks 更管用

_我个人赞同，但天哪，我们可真喜欢自己的 on call heros。我想知道，我们怎样才能培养 documentation 的文化。_

#### Change management（变更管理）

-   70% 的 outages 源于 live system 中的 changes。Mitigation：
    -   进行 Implement progressive rollouts
    -   Monitoring（监控）
    -   Rollback（回滚）
-   将人 Remove 出 loop，避免人在 repetitive tasks 上常见的问题

#### Demand forecasting 与 [capacity planning](http://www.amazon.com/gp/product/0596518579/ref=as_li_tl?ie=UTF8&camp=1789&creative=9325&creativeASIN=0596518579&linkCode=as2&tag=abroaview-20&linkId=EK2PBWYSHYK26GIV)

-   这很直接，但不这样做的 teams/services 多得令人惊讶

#### Provisioning（资源配置）

-   Adding capacity 比 load shifting 更 riskier，因为它往往涉及 spinning up 新的 instances/locations，对现有 systems 作出重大的 changes（config files、load balancers 等）
-   它的成本高到应当仅在必要时才做；而且必须迅速完成
    -   如果你不知道自己实际需要什么，并且 overprovision，那就会花冤枉钱

#### Efficiency 与 performance

-   Load 会 slows down systems
-   SREs 通过 provision 来 meet capacity target，同时满足特定的 response time goal
-   Efficiency == money（效率就是金钱）

### 第 3 章：Embracing risk

-   例如：如果一名 user 使用的是 reliability 为 99% 的 smartphone，那么他就无法分辨 99.99% 与 99.999% reliability 的差别

#### Managing risk（管理风险）

-   Reliability 与 cost 并不是 linear 的关系。为了再获得一个 increment 的 reliability，很容易就要多花 100x 的 cost
    -   与 redundant equipment 相关的 Cost
    -   为 reliability 而非“normal” features 构建 features 的 Cost
    -   Goal：让 systems 足够 reliable，但不要过于 reliable！

#### Measuring service risk（衡量服务风险）

-   Standard practice：identify 一个 metric，来 represent 要 optimize 的 system property
-   可用的 metric = uptime / (uptime + downtime)
    -   对于 globally distributed service，这存在问题。uptime 究竟意味着什么？
-   Aggregate availability = successful requests / total requests（总体可用性等于成功请求数除以请求总数）
    -   显然，并非所有 requests 都是 equal，但 aggregate availability 是一个尚可的 first order approximation
-   通常 set 每季度的 targets

#### services 的 Risk tolerance

-   通常并非客观上显而易见
-   SREs 与 product owners 合作，将 business objectives 转化为 explicit objectives

##### Target availability（目标可用性）

-   贯穿本节的例子：Bigtable

### 第 4 章：Service level objectives

_注：跳过 terminology 一节的笔记。_

-   例如：Chubby 的 planned outages
    -   Google 发现，Chubby 一直高于其 SLO，而且 global Chubby outages 会在 Google 引发异常严重的 outages
    -   Chubby 实在太 reliable，以至于 teams 错误地假定它永远不会 down，也未能 design 能 account for Chubby 中 failures 的 systems
    -   Solution：当 Chubby 在一个季度里远高于其 SLO 时，在全球范围内 take Chubby down，以向 teams“展示”Chubby 也可能 go down

#### 你和你的 users 关心什么？

-   indicators 太多：难以关注
-   indicators 太少：可能忽略重要的 behavior
-   不同 classes 的 services 应有不同的 indicators
    -   User-facing：availability、latency、throughput
    -   Storage：latency、availability、durability
    -   Big data：throughput、end-to-end latency
-   所有 systems 都关心 correctness

#### Collecting indicators（收集指标）

-   往往可以很自然地从 server 完成，但有时需要 client-side metrics。

#### Aggregation（聚合）

-   使用 distributions，而不要使用 averages
-   User studies 表明，人们通常更喜欢 slower average、但 tail latency 更好的情况
-   采用共同的 defs 来 Standardize，例如，针对 1 minute 的 average、针对 cluster 中 tasks 的 average，等等
    -   可以有 exceptions，但有合理的 defaults 会让事情更容易

#### Choosing targets（选择目标）

-   不要根据当前的 performance 来 pick target
    -   当前的 performance 可能需要拼尽全力才能维持
-   保持 simple
-   避免 absolutes
    -   谈论“infinite” scale 或“始终”available 并不合理
-   对 SLOs 的数量进行 Minimize
-   Perfection 可以等等
    -   随时间推移，随时都可以 redefine SLOs
-   SLOs 会 set expectations
    -   保留 safety margin（internal SLOs 可以比 external SLOs 更宽松地 defined）
-   不要 overachieve
    -   参见上面的 Chubby 例子
    -   另一个例子是确保 system 在 light loads 下不会太 fast

### 第 8 章：Release engineering

-   这是 Google 的一个特定 job function

#### Release engineer 的职责

-   Release engineers 与 SWEs 和 SREs 一起 define software 如何 released
    -   使 dev teams 能专注于 dev work
-   Define best practices
    -   Compiler flags、build ID tags 的 formats，等等
-   Releases 是 automated 的
-   不同 teams 的 Models 各不相同
    -   可以是“push on green”，并 deploy 每一个 build
    -   也可以每小时进行 builds 和 deploys
    -   等等。
-   Hermetic builds
    -   Building 相同的 rev number 应该总是给出 identical results
    -   Self-contained -- 这包括对所有东西进行 versioning，一直到所使用的 compiler
    -   可以针对旧的 rev 进行 cherry-pick fixes，以 fix production software
-   几乎所有 changes 都需要 code review
-   Branching
    -   所有 code 都在 main branch 中
    -   Releases 会被 branched off
    -   Fixes 可以从 master 进入 branch
    -   Branches 从不 merged back
-   Testing
    -   CI
    -   Release process 会 creates 一个 audit trail，它 runs tests 并 shows tests 已 passed
-   Config management
    -   看似 simple，[可能 cause instability](https://danluu.com/postmortem-lessons/)
-   有许多可能的 schemes（都涉及将 config storing 在 source control 中，并进行 strict config review）
-   对 config 使用 mainline -- config 在 head 处 maintained，并立即 applied
    -   最初用于 Borg（以及 pre-Borg systems）
    -   Binary releases 与 config changes 是 decoupled 的！
-   将 config files 和 binaries Include 在同一个 package 中
    -   是 Simple 的
    -   对 binary 和 config 进行 Tightly couples -- 适用于 config files 很少，或很少有 configs change 的 projects
-   把 config Package 成“configuration packages”
    -   与 code 采用相同的 hermetic principle
-   Release engineering 不应该是事后才考虑的事情！
    -   在 dev cycle 开始时 Budget resources

### 第 10 章：根据 time-series data 进行 Altering

#### Borgmon 系统

-   与 [Prometheus](https://prometheus.io/) 有些 Similar-ish
-   用于 logging 的 Common data format
-   Data 同时用于 dashboards 和 alerts
-   对一种 legacy data format“varz”进行了 Formalized，它允许通过 HTTP 来 viewed metrics
    -   要手动 view metrics，请前往 [http://foo:80/varz](http://foo/varz)
-   Adding 一个 metric 只需要在 code 中有一个 declaration
    -   add 新 metric 的 user-cost 很 low
-   Borgmon 定期从每个 target fetches /varz
    -   还 includes synthetic data，例如 health check、name 是否已 resolved，等等，
-   Time series arena
    -   Data 以 in-memory 方式 stored，并 checkpointing 到 disk
    -   Fixed sized allocation
    -   在 full 时，GC 会 expires 最旧的 entries
    -   conceptually 是一个 2-d array，其中一个 axis 是 time，另一个 axis 是 items
    -   一个 data point 为 24 bytes -> 1M 条 unique time series，持续 12 hours，采用 1-minute intervals = 17 GB
-   Borgmon rules
    -   Algebraic expressions
    -   从其他 time-series 中 Compute time-series
    -   Rules 在 threadpool 上 evaluated in parallel
-   Counters 与 gauges 的对比
    -   Def：counters 是 non-decreasing 的
    -   Def：可以 take any value
    -   相比 gauges 更 preferred Counters，因为 gauges 可能会因 sampling interval 而 lose information
-   进行 Altering
    -   Borgmon rules 可以 trigger alerts
    -   设有 minimum duration，以 prevent“flapping”
    -   通常 set 为两个 duration cycles，使 missed collections 不会 trigger 一个 alert
-   Scaling
    -   Borgmon 可以从其他 Borgmon 获取 time-series data（使用 binary streaming protocol，而不是 text-based varz protocol）
    -   可以有多个 tiers 的 filters
-   Prober
    -   对 user 所见内容进行 monitors 的 Black-box monitoring
    -   可以通过 varz 被 queried，或者直接向 Altertmanager send alerts
-   Configuration
    -   将 rules 的 definition 与正在 monitored 的 targets 进行 Separation

### 第 11 章：担任 on-call

-   典型的 response time
    -   对于 user-facing 或其他 time-critical tasks，为 5 min
    -   对于不那么 time-sensitive 的事务，为 30 min
-   Response times 与 SLOs 相关联
    -   例如：一个季度的 99.99% 意味着 13 minutes 的 downtime；显然 response time 不能超过 13 minutes
    -   SLOs 较为 looser 的 Services 可以有数十分钟的 response times（或者更久？）
-   Primary 与 secondary on-call 的比较
    -   Work distribution 随 team 而异
    -   在有些 team 中，secondary 可以作为 primary 的 backup
    -   在另一些 team 中，secondary handles non-urgent / non-paging events，primary handles pages
-   保持 Balanced 的 on-call
    -   定义：quantity：处于 on-call 的时间百分比
    -   定义：quality：在 on call 期间发生的 incidents 的数量

_这很好。我们应该这样做。人们有时会连续几次碰上非常难熬的 on-call rotations，而考虑到 on-call rotations 并不频繁，没有理由指望这一切会在一两年内 randomly balance out。_

-   在 quantity 上保持 Balance
    -   \>= 50% 的 SRE 时间用于 engineering
    -   在剩余时间中，用于 on-call 的不超过 25%
-   优先选择 multi-site teams
    -   夜班有害健康，multi-site teams 可以消除夜班
-   在 quality 上保持 Balance
    -   On average，处理一个 incident（包括 root-cause analysis、remediation、writing postmortem、fixing bug 等）需要 6 hours。

### 第 20 章：datacenter 中的 Load balancing

-   Flow control
-   需要 avoid unhealthy tasks
-   针对 unhealthy tasks 的 Naive flow control
    -   Track 发往某个 backend 的 requests 的 number
    -   当 threshold 被 reached 时，将 backend Treat 为 unhealthy
    -   Cons：总体上很糟糕
-   Health-based flow control
    -   Backend task 可以处于 three states 中的一个：{healthy, refusing connections, lame duck}
    -   Lame duck state 仍可以 take connections，但会向所有 clients sends backpressure request
    -   Lame duck state 会 simplifies clean shutdown
-   Def：subsetting：limiting 一个 client task 可以 interact 的 backend tasks 的 pool
    -   RPC system 中的 Clients 会 maintain 通向 backends 的 connections 的 pool
    -   与需要时才进行 setup/teardown 相比，Using pool 会 reduces latency
    -   Inactive connections 相对 cheap，但并非 free，即使处于 “inactive” mode 也是如此（reduced health checks、用 UDP 代替 TCP 等）
-   Choosing correct subset
    -   Typ：20-100，根据 workload 进行 choose
-   Subset selection：random
    -   Bad utilization
-   Subset selection：round robin
    -   Order 是 permuted 的；每个 round 都有自己的 permutation
-   Load balancing
    -   Subset selection 用于 connection balancing，但我们仍需要 balance load
-   Load balancing：round robin
    -   实践中，在 most loaded 与 least load 之间 observe 到 2x difference
    -   实践中，most expensive request 可以比 cheapest request 更 expensive，达到 1000x
    -   此外，requests 中还存在 random unpredictable variation
-   Load balancing：least-loaded round robin
    -   正如其名：在 least loaded backends 之间进行 round-robin
    -   Load 似乎是根据 connection count 来 measured 的；这未必总是最佳 metric
    -   这是 per client 的，而非 globally，因此可能会向一个已经有许多来自其他 clients 的 requests 的 backend send requests
    -   实践中，对于 larg services，会发现 most-loaded task 使用的 CPU 是 least-loaded 的两倍；与 normal round robin 类似
-   Load balancing：weighted round robin
    -   与上述相同，但用其他 factors 来 weight
    -   实践中，load distribution 比 least-loaded round robin 好得多

### 第 21 章：Handling overload

-   即使有“良好”的 load balancing，systems 仍会变得 overloaded
-   Typical strategy 是 serve degraded responses，但在 very high load 下，这可能无法做到
-   将 capacity Modeling 为 QPS 或 requests 的 function（例如，requests read 多少 keys）是 failure prone 的
    -   这些通常 change slowly，但也可能 change rapidly（例如，因为一次 checkin）
-   更好的 solution：直接 measure available resources
-   CPU utilization _通常_是 provisioning 的一个良好 signal
    -   有 GC 时，memory pressure 会 turns into CPU utilization
    -   对于其他 systems，可以 provision 其他 resources，使 CPU 很可能成为 limiting factor
    -   如果 over-provisioning CPU 过于 expensive，就要将其他 resources 考虑在内

_通常像这样 over-provision CPU，要花多少钱？_

-   Client-side throttling
    -   当 customer hits quota 时，Backends 开始 rejecting requests
    -   Requests 即使被 rejected，仍会 use resources -- 没有 throttling，backends 可能会将大部分 resources 花在 rejecting requests 上
-   Criticality
    -   似乎就是 priority，只是换了个名字？
    -   RPC system 中的 First-class notion
    -   Client-side throttling 为 criticality 的每个 level keeps separate stats
    -   默认情况下，criticality 会通过后续 RPCs 被 propagated
-   Handling overloaded errors
    -   如果 DC 是 overloaded，就向其他 DCs 进行 Shed load
    -   如果 DC 没问题，但某些 backends 是 overloaded，就向其他 backends 进行 Shed load
-   Clients 收到 overloaded response 时会 retry
    -   Per-request retry budget (3)
    -   Per-client retry budget (10%)
    -   来自 client 的 Failed retries 会 cause 向 upstream returned “overloaded；不要 retry” response

_提供“不要 retry”的 response 是“显而易见”的，但在实践中相对少见。许多实际 systems 都存在 failed retries 导致 stack 上层出现更多 retries 的问题。crossing hardware/software boundary 时尤其如此（例如，filesystem read 导致 DVD/SSD/spinning disk 上发生多次 retries，随后 fails，然后又在 filesystem level 被 retried），但在 pure software 中似乎通常也是如此。_

### 第 22 章：Addressing cascading failures

-   Typical failure scenarios 有哪些？
-   Server overload
-   Ex：有 two servers
    -   其中一个变得 overloaded，随后 failing
    -   另一个此时收到所有 traffic，也 fails
-   Resource exhaustion
    -   CPU/memory/threads/file descriptors/等
-   Ex：resources 之间的 dependencies
    -   1) Java frontend 的 GC params 是 poorly tuned 的
    -   2) Frontend 因 GC 而 runs out of CPU
    -   3) CPU exhaustion 会 slows down requests
    -   4) Increased queue depth 会 uses 更多 RAM
    -   5) 整个 frontend 的 Fixed memory allocation 意味着可用于 caching 的 memory 更少
    -   6) Lower hit rate
    -   7) 更多 requests 进入 backend
    -   8) Backend 会 runs out of CPU 或 threads
    -   9) Health checks 会 fail，从而 starting cascading failure
    -   在 outage 期间很难 determine cause
-   注意：avoid 那些 serve errors 的 servers 的 policies 可能让情况更糟
    -   available 的 backends 更少，它们收到过多 requests，随后又变得 unavailable
-   Preventing server overload
    -   进行 Load test！必须有 realistic environment
    -   提供 Serve degraded results
    -   在 overloaded 时进行 Fail cheaply and early
    -   让 higher-level systems 进行 reject requests（在 reverse proxy、load balancer 以及 task level）
    -   进行 Perform capacity planning
-   Queue management
    -   Queues 在 steady state 中什么也不做
    -   Queued reqs 会 consume memory 并 increase latency
    -   如果 traffic 是 steady-ish，最好保持 small queue size（比如，thread pool size 的 50% 或更少）
    -   Ex：Gmail 使用 queueless servers，在 threads 满时进行 failover
    -   对于 bursty workloads，queue size 应当是 #threads、time per req、bursts 的 size/freq 的 function
    -   另见 [adaptive LIFO 和 CoDel](http://queue.acm.org/detail.cfm?id=2839461)
-   Graceful degradation
    -   注意，test graceful degradation path 很重要，或许可以定期让一小组 servers 在接近 overload 的状态下 running，因为这条 path 在 normal circumstances 下很少被 exercised
    -   最好保持 simple 且易于理解
-   Retries
    -   始终使用 randomized exponential backoff
    -   参见上一章关于仅在 single level 进行 retrying 的内容
    -   考虑设置 server-wide retry budget
-   Deadlines
    -   不要对 deadline 已被 missed 的情况 do work（这是 cascading failure 的常见主题）
    -   在每个 stage，都要 check deadline 尚未被 hit
    -   Deadlines 应当被 propagated（例如，即使通过 RPCs 也如此）
-   Bimodal latency
    -   Ex：long deadline 的问题
    -   假设 frontend 有 10 servers，每个有 100 threads（total cap 为 1k threads）
    -   Normal operation：1k QPS，reqs 耗时 100ms => 100 worker threads 被 occupied (1k QPS \* .1s)
    -   假设 5% 的 operations 不会 complete，并且有一个 100s deadline
    -   这会 consumes 5k threads (50 QPS \* 100s)
    -   Frontend 的 oversubscribed 程度为 5x。Success rate = 1k / (5k + 95) = 19.6% => 80.4% error rate

_用 deadlines 代替 timeouts 很好。我们确实应该更 systematic 地对待这件事。_

_通过设置 reasonable deadlines，不让 systems 被无意义的 zombie requests 填满，这是“显而易见”的，但许多实际 systems 似乎都在使用 arbitrary timeouts，取一些对人而言整齐的数字（30s、60s、100s 等），而非考虑 load/cascading failures 来 assigned 的 deadlines。_

-   尽量 avoid intra-layer communication
    -   这样更 Simpler，并且 avoids 可能的 cascading failure paths
-   针对 cascading failures 进行 Testing
    -   对 components 进行 Load test！
    -   Load testing 既会 reveals breaking，也会 point ferrets out 那些在 load 下会彻底 fall over 的 components
    -   确保分别 test 每个 component
    -   对 non-critical backends 进行 Test（例如，确保 search 的 spelling suggestions 不会 impede critical path）
-   立即 address cascading failures 的 steps
    -   进行 Increase resources
    -   暂时 stop health check failures/deaths
    -   进行 Restart servers（仅在这样有帮助时 -- 例如，处于 GC death spiral 或 deadlock 时）
    -   进行 Drop traffic -- 很激烈，是最后手段
    -   进行 Enter degraded mode -- 需要此前已将其 built 到 service 中
    -   进行 Eliminate batch load
    -   进行 Eliminate bad traffic

_这让我想起了我最喜欢的一篇 distributed database postmortems。这个 database 被 configured 成一个 ring，其中每个 node 都会与由 5 个 servers 组成的一个“neighborhood”进行 talks to，并向其中 replicates data。如果 neighborhood 中的一些 machines 出现 go down，其他 servers 就会 join 这个 neighborhood，而 data 也会被 appropriately replicated。_

_听起来不错，但如果一个 server 出现 goes bad，并认定不存在任何 data，而且它的所有 neighbors 都是 bad，那么它就能比任何一个 neighbors 更快地 return results，同时还会告诉它的 neighbors，它们全都是 bad。由于这个 bad server 没有 data，它非常 fast，能够比它的 neighbors report 它是 bad 更快地 report 它的 neighbors 是 bad。糟糕！_

#### [Paxos](http://research.microsoft.com/en-us/um/people/lamport/pubs/paxos-simple.pdf)（Paxos 算法）

-   一系列 proposals，它们可能被 processes 的 majority 所 accepted，也可能不被 accepted
    -   未被 accepted => fails
    -   每个 proposal 都有 Sequence number，必须在整个 system 中 unique
-   Proposal（提案）
    -   Proposer 向 acceptors 进行 sends seq number
    -   如果 Acceptor 尚未 seen 更高的 seq number，它就会 agrees
    -   Proposers 可以用更高的 seq number 再试一次
    -   如果 proposer 从 majority 处 recvs agreement，它就会通过 sending 带有 value 的 commit message 来 commits
    -   Acceptors 在 accept 时必须 journal 到 persistent storage

#### Patterns（模式）

-   Distributed consensus algorithms 是一种 low-level primitive
-   Reliable replicated state machines（可靠的复制状态机）
    -   用于 data config/storage、locking、leader election 等的 Fundamental building block
    -   参见这些 papers：[Schnieder](https://www.cs.cornell.edu/fbs/publications/SMSurvey.pdf)、[Aguilera](http://citeseerx.ist.psu.edu/viewdoc/download?doi=10.1.1.174.8238&rep=rep1&type=pdf)、[Amir & Kirsch](http://www.cnds.jhu.edu/pub/papers/psb_ladis_08.pdf)
-   Reliable repliacted data 和 config stores（可靠的复制数据与配置存储）
    -   非 distributed-consensus-based 的 systems 经常 use timestamps：这存在问题，因为 clock synchrony 无法被 gauranteed
    -   关于使用 distributed consensus 的例子，参见 [Spanner paper](http://research.google.com/archive/spanner.html)
-   Leader election（领导者选举）
    -   与 distributed consensus 是 Equivalent 的
    -   当 leader 的 work 可以由一个 process 来 performed performed，或可以被 sharded 时，leader election pattern 允许像编写一个 simple program 那样 writing distributed system
    -   例如，GFS 和 Colussus 都会 Used 它
-   Distributed coordination 和 locking services（分布式协调与锁服务）
    -   例如，Barrier 在 MapReduce 中被 used，以确保 Map 已经 finished 后，Reduce 才 proceeds
-   Distributed queues 和 messaging（分布式队列与消息传递）
    -   Queues：可以 tolerate 来自 worker nodes 的 failures，但 system 需要 ensure claimed tasks 被 processed
    -   可以 use leases，而不是从 queue 中 removal
    -   使用 RSM 意味着，即使 queue 出现 goes down，system 仍然可以 continue processing
-   Performance（性能）
    -   认为 consensus algorithms 不能被 used 于 high-throughput low-latency systems 的传统看法是 false 的
    -   Distributed consensus 位于许多 Google systems 的 core
    -   由于 Scale，这对 Google 来说比对大多数其他公司更棘手，但它仍然有效
-   Multi-Paxos（多轮 Paxos）
    -   Strong leader process：除非尚未 elected 出一个 leader，或发生 failure，否则只需要一个 round trip 就能 reach consensus
    -   注意，group 中的另一个 process 可以随时 propose
    -   可能会来回 ping pong，并出现 pseudo-livelock
    -   这并非 multi-paxos 所 unqique，
    -   Standard solutions 是 elect 一个 proposer process，或 use rotating proposer
-   对 read-heavy workloads 进行 Scaling
    -   例如：Photon 允许从任意 replica 进行 reads
    -   从 stale replica 进行 Read 会 requres 额外 work，但不会 produce bad incorrect results
    -   要 gaurantee reads 是 up to date 的，需执行以下操作之一：
    -   1) Perform 一个 read-only consensus operation
    -   2) 从 guaranteed 为 most-up-to-date 的 replica 中 Read data（stable leader 可以提供这个 guarantee）
    -   3) Use quorum leases
-   [Quorum leases](http://www.pdl.cmu.edu/PDL-FTP/associated/CMU-PDL-14-105_abs.shtml)（法定人数租约）
    -   Replicas 可以被 granted 一个覆盖 system 中部分（或全部）data 的 lease
-   Fast Paxos（快速 Paxos）
    -   其 Designed 目的是在 WAN 上更 faster
    -   每个 client 都可以直接向一组 acceptors 中的每个 member 进行 send `Propose`，而不是通过一个 leader
    -   [不一定比 classic Paxos 更 faster](http://www.sysnet.ucsd.edu/sysnet/miscpapers/hotdep07.pdf) -- 如果到 acceptors 的 RTT 很 long，我们就是用 N 条跨越 slow link 的 message，替代了一条跨越 slow link 的 message 加上 N 条以 in parallel 方式跨越 fast link 的 message
-   Stable leaders（稳定领导者）
    -   “几乎所有在 designed 时考虑了 performance 的 distributed consensus systems，都会 use single stable leader pattern 或一个采用 rotating leadership 的 system”

    -   可能混合存在 transactional 和 non-transactional 的 backup 和 restore
    -   business logic 的不同 versions 可能同时处于 live 状态
    -   如果 services 是 independently versioned 的，那么可能存在许多 versions 的 combinations
    -   Replicas 并不 sufficient -- replicas 可能 sync corruption
-   对 Google 的 19 次 data recovery 工作进行的 Study
    -   最常见的 user-visible data loss，是由 software bugs 导致的 deletion 或 referential integrity 的 loss 所造成的
    -   最棘手的 cases 是几周到几个月后才被发现的 low-grade corruption

#### Defense in depth（纵深防御）

-   第一 layer：soft deletion
    -   Users 应该能够 delete 他们的 data
    -   但这意味着 users 也能够意外地 delete 他们的 data
    -   此外还有 account hijacking 等
    -   意外的 deletion 也可能由 bugs 导致
    -   Soft deletion 会将实际的 deletion delays 一段时间
-   第二 layer：backups
    -   需要弄清楚在 recovery 期间可以接受 lose 多少 data、recovery 可以花多长时间，以及 backups 需要追溯到多久以前
    -   希望 backups 能永远向前追溯，因为 corruption 可能几个月（甚至更久）都未被察觉
    -   但对 code 和 schema 的 changes 可能使较早 backups 的 recovery 变得 expensive
    -   Google 通常有一个 30 到 90 day 的 window，具体取决于 service
-   第三 layer：early detection
    -   Out-of-band integrity checks（带外完整性检查）
    -   很难把这件事做好！
    -   Correct changes 可能导致 checkers fail
    -   但 loosening checks 又可能导致 failures 被漏掉

Two approaches to hiring people to manage system stability:

#### Traditional approach: sysadmins

-   Assemble existing components and deploy to produce a service
-   Respond to events and updates as they occur
-   Grow team to absorb increased work as service grows
-   Pros
    -   Easy to implement because it’s standard
    -   Large talent pool to hire from
    -   Lots of available software
-   Cons
    -   Manual intervention for change management and event handling causes size of team to scale with load on system
    -   Ops is fundamentally at odds with dev, which can cause pathological resistance to changes, which causes similarly pathological response from devs, which reclassify “launches” as “incremental updates”, “flag flips”, etc.

#### Google’s approach: SREs

-   Have software engineers do operations
-   Candidates should be able to pass or nearly pass normal dev hiring bar, and may have some additional skills that are rare among devs (e.g., L1 - L3 networking or UNIX system internals).
-   Career progress comparable to dev career track
-   Results
    -   SREs would be bored by doing tasks by hand
    -   Have the skillset necessary to automate tasks
    -   Do the same work as an operations team, but with automation instead of manual labor
-   To avoid manual labor trap that causes team size to scale with service load, Google places a 50% cap on the amount of “ops” work for SREs
    -   Upper bound. Actual amount of ops work is expected to be much lower
-   Pros
    -   Cheaper to scale
    -   Circumvents devs/ops split
-   Cons
    -   Hard to hire for
    -   May be unorthodox in ways that require management support (e.g., product team may push back against decision to stop releases for the quarter because the error budget is depleted)

### Chapter 10: Altering from time-series data

#### Borgmon

-   Similar-ish to [Prometheus](https://prometheus.io/)
-   Common data format for logging
-   Data used for both dashboards and alerts
-   Formalized a legacy data format, “varz”, which allowed metrics to be viewed via HTTP
    -   To view metrics manually, go to [http://foo:80/varz](http://foo/varz)
-   Adding a metric only requires a single declaration in code
    -   low user-cost to add new metric
-   Borgmon fetches /varz from each target periodically
    -   Also includes synthetic data like health check, if name was resolved, etc.,
-   Time series arena
    -   Data stored in-memory, with checkpointing to disk
    -   Fixed sized allocation
    -   GC expires oldest entries when full
    -   conceptually a 2-d array with time on one axis and items on the other axis
    -   24 bytes for a data point -> 1M unique time series for 12 hours at 1-minute intervals = 17 GB
-   Borgmon rules
    -   Algebraic expressions
    -   Compute time-series from other time-series
    -   Rules evaluated in parallel on a threadpool
-   Counters vs. gauges
    -   Def: counters are non-decreasing
    -   Def: can take any value
    -   Counters preferred to gauges because gauges can lose information depending on sampling interval
-   Altering
    -   Borgmon rules can trigger alerts
    -   Have minimum duration to prevent “flapping”
    -   Usually set to two duration cycles so that missed collections don’t trigger an alert
-   Scaling
    -   Borgmon can take time-series data from other Borgmon (uses binary streaming protocol instead of the text-based varz protocol)
    -   Can have multiple tiers of filters
-   Prober
    -   Black-box monitoring that monitors what the user sees
    -   Can be queried with varz or directly send alerts to Altertmanager
-   Configuration
    -   Separation between definition of rules and targets being monitored

    -   Many things can affect plan: increase in efficiency, increase in adoption rate, cluster delivery date slips, etc.
    -   Even small changes require rechecking allocation plan
    -   Large changes may require total rewrite of plan
    -   Labor intensive and error prone
-   Google solution: intent-based capacity planning
    -   Specify requirements, not implementation
    -   Encode requirements and autogenerate a capacity plan
    -   In addition to saving labor, solvers can do better than human generated solutions => cost savings
-   Ladder of examples of increasingly intent based planning
    -   1) Want 50 cores in clusters X, Y, and Z -- why those resources in those clusters?
    -   2) Want 50-core footprint in any 3 clusters in region -- why that many resources and why 3?
    -   3) Want to meet demand with N+2 redundancy -- why N+2?
    -   4) Want 5 9s of reliability. Could find, for example, that N+2 isn’t sufficient
-   Found that greatest gains are from going to (3)
    -   Some sophisticated services may go for (4)
-   Putting constraints into tools allows tradeoffs to be consistent across fleet
    -   As opposed to making individual ad hoc decisions
-   Auxon inputs
    -   Requirements (e.g., “service must be N+2 per continent”, “frontend servers no more than 50ms away from backend servers”
    -   Dependencies
    -   Budget priorities
    -   Performance data (how a service scales)
    -   Demand forecast data (note that services like Colossus have derived forecasts from dependent services)
    -   Resource supply & pricing
-   Inputs go into solver (mixed-integer or linear programming solver)

### Chapter 20: Load balancing in the datacenter

-   Flow control
-   Need to avoid unhealthy tasks
-   Naive flow control for unhealthy tasks
    -   Track number of requests to a backend
    -   Treat backend as unhealthy when threshold is reached
    -   Cons: generally terrible
-   Health-based flow control
    -   Backend task can be in one of three states: {healthy, refusing connections, lame duck}
    -   Lame duck state can still take connections, but sends backpressure request to all clients
    -   Lame duck state simplifies clean shutdown
-   Def: subsetting: limiting pool of backend tasks that a client task can interact with
    -   Clients in RPC system maintain pool of connections to backends
    -   Using pool reduces latency compared to doing setup/teardown when needed
    -   Inactive connections are relatively cheap, but not free, even in “inactive” mode (reduced health checks, UDP instead of TCP, etc.)
-   Choosing the correct subset
    -   Typ: 20-100, choose base on workload
-   Subset selection: random
    -   Bad utilization
-   Subset selection: round robin
    -   Order is permuted; each round has its own permutation
-   Load balancing
    -   Subset selection is for connection balancing, but we still need to balance load
-   Load balancing: round robin
    -   In practice, observe 2x difference between most loaded and least load
    -   In practice, most expensive request can be 1000x more expensive than cheapest request
    -   In addition, there’s random unpredictable variation in requests
-   Load balancing: least-loaded round robin
    -   Exactly what it sounds like: round-robin among least loaded backends
    -   Load appears to be measured in terms of connection count; may not always be the best metric
    -   This is per client, not globally, so it’s possible to send requests to a backend with many requests from other clients
    -   In practice, for larg services, find that most-loaded task uses twice as much CPU as least-loaded; similar to normal round robin
-   Load balancing: weighted round robin
    -   Same as above, but weight with other factors
    -   In practice, much better load distribution than least-loaded round robin

### Chapter 21: Handling overload

-   Even with “good” load balancing, systems will become overloaded
-   Typical strategy is to serve degraded responses, but under very high load that may not be possible
-   Modeling capacity as QPS or as a function of requests (e.g., how many keys the requests read) is failure prone
    -   These generally change slowly, but can change rapidly (e.g., because of a single checkin)
-   Better solution: measure directly available resources
-   CPU utilization is _usually_ a good signal for provisioning
    -   With GC, memory pressure turns into CPU utilization
    -   With other systems, can provision other resources such that CPU is likely to be limiting factor
    -   In cases where over-provisioning CPU is too expensive, take other resources into account

_How much does it cost to generally over-provision CPU like that?_

-   Client-side throttling
    -   Backends start rejecting requests when customer hits quota
    -   Requests still use resources, even when rejected -- without throttling, backends can spend most of their resources on rejecting requests
-   Criticality
    -   Seems to be priority but with a different name?
    -   First-class notion in RPC system
    -   Client-side throttling keeps separate stats for each level of criticality
    -   By default, criticality is propagated through subsequent RPCs
-   Handling overloaded errors
    -   Shed load to other DCs if DC is overloaded
    -   Shed load to other backends if DC is ok but some backends are overloaded
-   Clients retry when they get an overloaded response
    -   Per-request retry budget (3)
    -   Per-client retry budget (10%)
    -   Failed retries from client cause “overloaded; don’t retry” response to be returned upstream

_Having a “don’t retry” response is “obvious”, but relatively rare in practice. A lot of real systems have a problem with failed retries causing more retries up the stack. This is especially true when crossing a hardware/software boundary (e.g., filesystem read causes many retries on DVD/SSD/spinning disk, fails, and then gets retried at the filesystem level), but seems to be generally true in pure software too._

### Chapter 22: Addressing cascading failures

-   Typical failure scenarios?
-   Server overload
-   Ex: have two servers
    -   One gets overloaded, failing
    -   Other one now gets all traffic and also fails
-   Resource exhaustion
    -   CPU/memory/threads/file descriptors/etc.
-   Ex: dependencies among resources
    -   1) Java frontend has poorly tuned GC params
    -   2) Frontend runs out of CPU due to GC
    -   3) CPU exhaustion slows down requests
    -   4) Increased queue depth uses more RAM
    -   5) Fixed memory allocation for entire frontend means that less memory is available for caching
    -   6) Lower hit rate
    -   7) More requests into backend
    -   8) Backend runs out of CPU or threads
    -   9) Health checks fail, starting cascading failure
    -   Difficult to determine cause during outage
-   Note: policies that avoid servers that serve errors can make things worse
    -   fewer backends available, which get too many requests, which then become unavailable
-   Preventing server overload
    -   Load test! Must have realistic environment
    -   Serve degraded results
    -   Fail cheaply and early when overloaded
    -   Have higher-level systems reject requests (at reverse proxy, load balancer, and on task level)
    -   Perform capacity planning
-   Queue management
    -   Queues do nothing in steady state
    -   Queued reqs consume memory and increase latency
    -   If traffic is steady-ish, better to keep small queue size (say, 50% or less of thread pool size)
    -   Ex: Gmail uses queueless servers with failover when threads are full
    -   For bursty workloads, queue size should be function of #threads, time per req, size/freq of bursts
    -   See also, [adaptive LIFO and CoDel](http://queue.acm.org/detail.cfm?id=2839461)
-   Graceful degradation
    -   Note that it’s important to test graceful degradation path, maybe by running a small set of servers near overload regularly, since this path is rarely exercised under normal circumstances
    -   Best to keep simple and easy to understand
-   Retries
    -   Always use randomized exponential backoff
    -   See previous chapter on only retrying at a single level
    -   Consider having a server-wide retry budget
-   Deadlines
    -   Don’t do work where deadline has been missed (common theme for cascading failure)
    -   At each stage, check that deadline hasn’t been hit
    -   Deadlines should be propagated (e.g., even through RPCs)
-   Bimodal latency
    -   Ex: problem with long deadline
    -   Say frontend has 10 servers, 100 threads each (1k threads of total cap)
    -   Normal operation: 1k QPS, reqs take 100ms => 100 worker threads occupied (1k QPS \* .1s)
    -   Say 5% of operations don’t complete and there’s a 100s deadline
    -   That consumes 5k threads (50 QPS \* 100s)
    -   Frontend oversubscribed by 5x. Success rate = 1k / (5k + 95) = 19.6% => 80.4% error rate

_Using deadlines instead of timeouts is great. We should really be more systematic about this._

_Not allowing systems to fill up with pointless zombie requests by setting reasonable deadlines is “obvious”, but a lot of real systems seem to have arbitrary timeouts at nice round human numbers (30s, 60s, 100s, etc.) instead of deadlines that are assigned with load/cascading failures in mind._

-   Try to avoid intra-layer communication
    -   Simpler, avoids possible cascading failure paths
-   Testing for cascading failures
    -   Load test components!
    -   Load testing both reveals breaking and point ferrets out components that will totally fall over under load
    -   Make sure to test each component separately
    -   Test non-critical backends (e.g., make sure that spelling suggestions for search don’t impede the critical path)
-   Immediate steps to address cascading failures
    -   Increase resources
    -   Temporarily stop health check failures/deaths
    -   Restart servers (only if that would help -- e.g., in GC death spiral or deadlock)
    -   Drop traffic -- drastic, last resort
    -   Enter degraded mode -- requires having built this into service previously
    -   Eliminate batch load
    -   Eliminate bad traffic

### Chapter 23: Distributed consensus for reliability

-   How do we agree on questions like…
    -   Which process is the leader of a group of processes?
    -   What is the set of processes in a group?
    -   Has a message been successfully committed to a distributed queue?
    -   Does a process hold a particular lease?
    -   What’s the value in a datastore for a particular key?
-   Ex1: split-brain
    -   Service has replicated file servers in different racks
    -   Must avoid writing simultaneously to both file servers in a set to avoid data corruption
    -   Each pair of file servers has one leader & one follower
    -   Servers monitor each other via heartbeats
    -   If one server can’t contact the other, it sends a STONITH (shoot the other node in the head)
    -   But what happens if the network is slow or packets get dropped?
    -   What happens if both servers issue STONITH?

_This reminds me of one of my favorite distributed database postmortems. The database is configured as a ring, where each node talks to and replicates data into a “neighborhood” of 5 servers. If some machines in the neighborhood go down, other servers join the neighborhood and data gets replicated appropriately._

_Sounds good, but in the case where a server goes bad and decides that no data exists and all of its neighbors are bad, it can return results faster than any of its neighbors, as well as tell its neighbors that they’re all bad. Because the bad server has no data it’s very fast and can report that its neighbors are bad faster than its neighbors can report that it’s bad. Whoops!_

-   Ex2: failover requires human intervention
    -   A highly sharded DB has a primary for each shard, which replicates to a secondary in another DC
    -   External health checks decide if the primary should failover to its secondary
    -   If the primary can’t see the secondary, it makes itself unavailable to avoid the problems from “Ex1”
    -   This increases operational load
    -   Problems are correlated and this is relatively likely to run into problems when people are busy with other issues
    -   If there’s a network issues, there’s no reason to think that a human will have a better view into the state of the world than machines in the system
-   Ex3: faulty group-membership algorithms
    -   _What it sounds like. No notes on this part_
-   Impossibility results
    -   [CAP](https://en.wikipedia.org/wiki/CAP_theorem): P is impossible in real networks, so choose C or A
    -   [FLP](http://the-paper-trail.org/blog/a-brief-tour-of-flp-impossibility/): async distributed consensus can’t gaurantee progress with unreliable network

#### [Paxos](http://research.microsoft.com/en-us/um/people/lamport/pubs/paxos-simple.pdf)

-   Sequence of proposals, which may or may not be accepted by the majority of processes
    -   Not accepted => fails
    -   Sequence number per proposal, must be unique across system
-   Proposal
    -   Proposer sends seq number to acceptors
    -   Acceptor agrees if it hasn’t seen a higher seq number
    -   Proposers can try again with higher seq number
    -   If proposer recvs agreement from majority, it commits by sending commit message with value
    -   Acceptors must journal to persistent storage when they accept

#### Patterns

-   Distributed consensus algorithms are a low-level primitive
-   Reliable replicated state machines
    -   Fundamental building block for data config/storage, locking, leader election, etc.
    -   See these papers: [Schnieder](https://www.cs.cornell.edu/fbs/publications/SMSurvey.pdf), [Aguilera](http://citeseerx.ist.psu.edu/viewdoc/download?doi=10.1.1.174.8238&rep=rep1&type=pdf), [Amir & Kirsch](http://www.cnds.jhu.edu/pub/papers/psb_ladis_08.pdf)
-   Reliable repliacted data and config stores
    -   Non distributed-consensus-based systems often use timestamps: problematic because clock synchrony can't be gauranteed
    -   See [Spanner paper](http://research.google.com/archive/spanner.html) for an example of using distributed consensus
-   Leader election
    -   Equivalent to distributed consensus
    -   Where work of the leader can performed performed by one process or sharded, leader election pattern allows writing distributed system as if it were a simple program
    -   Used by, for example, GFS and Colussus
-   Distributed coordination and locking services
    -   Barrier used, for example, in MapReduce to make sure that Map is finished before Reduce proceeds
-   Distributed queues and messaging
    -   Queues: can tolerate failures from worker nodes, but system needs to ensure that claimed tasks are processed
    -   Can use leases instead of removal from queue
    -   Using RSM means that system can continue processing even when queue goes down
-   Performance
    -   Conventional wisdom that consensus algorithms can't be used for high-throughput low-latency systems is false
    -   Distributed consensus at the core of many Google systems
    -   Scale makes this worse for Google than most other companies, but it still works
-   Multi-Paxos
    -   Strong leader process: unless a leader has not yet been elected or a failure occurs, only one round trip required to reach consensus
    -   Note that another process in the group can propose at any time
    -   Can ping pong back and forth and pseudo-livelock
    -   Not unqique to multi-paxos,
    -   Standard solutions are to elect a proposer process or use rotating proposer
-   Scaling read-heavy workloads
    -   Ex: Photon allows reads from any replica
    -   Read from stale replica requres extra work, but doesn't produce bad incorrect results
    -   To gaurantee reads are up to date, do one of the following:
    -   1) Perform a read-only consensus operation
    -   2) Read data from replica that's guaranteed to be most-up-to-date (stable leader can provide this guarantee)
    -   3) Use quorum leases
-   [Quorum leases](http://www.pdl.cmu.edu/PDL-FTP/associated/CMU-PDL-14-105_abs.shtml)
    -   Replicas can be granted lease over some (or all) data in the system
-   Fast Paxos
    -   Designed to be faster over WAN
    -   Each client can send `Propose` to each member of a group of acceptors directly, instead of through a leader
    -   [Not necessarily faster than classic Paxos](http://www.sysnet.ucsd.edu/sysnet/miscpapers/hotdep07.pdf) -- if RTT to acceptors is long, we've traded one message across slow link plus N in parallel across fast link for N across slow link
-   Stable leaders
    -   "Almost all distributed consensus systems that have been designed with performance in mind use either the single stable leader pattern or a system of rotating leadership"

### Chapter 26: Data integrity

-   Definition not necessarily obvious
    -   If an interface bug causes Gmail to fail to display messages, that’s the same as the data being gone from the user’s standpoint
    -   99.99% uptime means 1 hour of downtime per year. Probably ok for most apps
    -   99.99% good bytes in a 2GB file means 200K corrupt. Probably not ok for most apps
-   Backup is non-trivial
    -   May have mixture of transactional and non-transactional backup and restore
    -   Different versions of business logic might be live at once
    -   If services are independently versioned, maybe have many combinations of versions
    -   Replicas aren’t sufficient -- replicas may sync corruption
-   Study of 19 data recovery efforts at Google
    -   Most common user-visible data loss caused by deletion or loss of referential integrity due to software bugs
    -   Hardest cases were low-grade corruption discovered weeks to months later

#### Defense in depth

-   First layer: soft deletion
    -   Users should be able to delete their data
    -   But that means that users will be able to accidentally delete their data
    -   Also, account hijacking, etc.
    -   Accidentally deletion can also happen due to bugs
    -   Soft deletion delays actual deletion for some period of time
-   Second layer: backups
    -   Need to figure out how much data it’s ok to lose during recovery, how long recovery can take, and how far back backups need to go
    -   Want backups to go back forever, since corruption can go unnoticed for months (or longer)
    -   But changes to code and schema can make recovery of older backups expensive
    -   Google usually has 30 to 90 day window, depending on the service
-   Third layer: early detection
    -   Out-of-band integrity checks
    -   Hard to do this right!
    -   Correct changes can cause checkers to fail
    -   But loosening checks can cause failures to get missed
