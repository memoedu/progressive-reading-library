## 核心洞察

一、大模型不可分割，团队扩张导致局部优化冲突：大模型是单一连续的高维参数张量，通过全局梯度下降更新，无法像传统软件那样物理拆分。当团队从 10 人扩张到上千人，只能拆分训练流程和工具链，形成数据清洗、Pre-train、SFT、RLHF、Infra 等团队，各部门为自身 KPI 局部优化，但这些指标在数学上相互冲突，导致模型权重更新实际沿部门博弈妥协的缝隙下降，最终智能水平不会超过各部门扯皮后的平均值。
[[#^pr-b33209d9ab25|正文跳转]]

二、传统软件工程人力可并行，大模型研发不行：传统软件工程中，复杂系统如操作系统、电商平台、即时通讯软件，可通过架构设计拆分为几十个子模块，由成百上千程序员并行编写，代码可物理分割，增加人力能加快进度。但大模型违反这一范式，其本质是不可分割的数学实体，无法像微服务那样拆分，因此人力扩张无法直接转化为研发效率，反而带来组织协调问题。
[[#^pr-eb46269a9b75|正文跳转]]

三、小团队认知对齐，大团队认知壁垒导致局部最优：小规模极客团队中，少数人协同解决问题，因为他们大脑中的认知高度对齐。团队规模扩大后，部门间沟通和妥协导致认知无法对齐，积累研发壁垒，跨部门优化被分隔，各部门陷入局部最优解。这解释了为何大团队研发大模型容易陷入低效。
[[#^pr-3be80ef04523|正文跳转]]

四、求助他人如同缓存未命中，破坏认知上下文：在研发流程中，求助于人相当于 Cache Miss。CPU 读取 L1 Cache 只需几个时钟周期，而读取内存需上百周期，磁盘 I/O 更慢。将任务拆分交给他人，会作废自己大脑中已建立的高速上下文，需要写文档、画架构图、反复沟通来投射认知，且返回结果概率性正确，与 LLM 输出无异，效率低下。
[[#^pr-e4e97c139734|正文跳转]]

五、大模型抹平技术鸿沟，个人可独立完成全栈工作：古法时代，个人无法同时精通 C++ 底层通信、CUDA 算子开发、PyTorch 调试、Rust 数据清洗和 Vue 前端等所有领域。但大语言模型作为通用认知中介，已抹平不同技术领域间的信息鸿沟，自己一个人就能搞定优化部署一条龙。大模型内部记忆了公开知识，但需要专家知识激活对应区域，使用专有名词能改变激活模式，提升输出质量。
[[#^pr-ca8f3e18cb93|正文跳转]]

六、人与大模型存在同步率，文档化决策可提升协作：人和大模型之间存在同步率概念，类似人与人之间的同步，但人与人因心之壁同步率极低，即使知己也常无法完全理解。而有足够上下文的大模型可以做到，只需将所有决策文档化，让 AI 自行阅读。作者因此不再需要人与人同步，转而与所有 Agent 同步，形成'我即是虫群'的工作模式，并认为传统招聘无意义，因为招人反而降低群体同步率。

## 正文

没考你反转二叉树就不错了，什么年代了还 Coding 面试，就应该当场回怼 HR：我正在用 DeepSeek Vibe Coding，看他怎么说。

HR 明明招满了人，但还会有面试场次/面试到场率的 KPI，于是就会疯狂挑刺过人，这种面试第一眼就该关掉了。

在一片看好之声中，我应该是之前唯一对 DeepSeek 开放招聘唱反调的人：

[](https://www.zhihu.com/question/2053625552725079594/answer/2054032755080671682)

我还是之前的观点：

> 科层制能开发出天网，能开发出终产者，但绝对开发不出 AGI。  
> DeepSeek 现在扩招，还在招真人 PM、真人 HR、真人算法开发，那就还是在给仿生机械鸟堆砌血肉，期待它有一天能像真正的鸟类一样翱翔于天际。  
> 那 Sorry，你已经和 AGI 说拜拜了

* * *

很多读者还是没看懂我之前的想法，觉得我小题大做，那就让我们来凝视真正的深渊。

在传统的软件工程里，我们有一套非常成熟的人力规模放大逻辑。

即便把复杂度打到夯级，比方说我们想写一个全新操作系统，或是想写一个淘宝那么复杂的电商平台，QQ/微信那样的即时通讯软件，这一切都是有迹可循的。

^pr-eb46269a9b75

我们会很自然地进行架构设计，把项目拆分成几十个子模块，然后招募成百上千的程序员去写代码，或者说填充代码。

传统软件的边界是清晰的、模块化的。

A 团队负责用户系统，B 团队负责支付网关，C 团队负责前端渲染，彼此之间通过定义好的 API 进行同步通信，本质上就这么简单。

在这样的系统里，增加人力的确能够加快开发进度，因为代码是可以被物理分割并并行编写的。

* * *

然而，大模型和深度学习违反了这一范式。

大模型的本质是一个单一连续的高维参数张量，这些张量在训练过程中通过全局梯度下降来更新自身的权重。

^pr-b33209d9ab25

这是一个统一且不可分割的数学实体，你无法像拆分微服务那样，对大模型进行物理拆分。

你不可以把一个 MoE 架构的模型里 Expert 的作用区分出来，他不是逻辑能力、架构能力这种非常具体可分的东西，甚至不具备可解释性。

一个大模型研发团队从最初的 10 人核心小组迅速膨胀到几百上千人的庞大组织，灾难就开始了。

由于模型无法在物理上被分割开发，庞大的人力不得不去拆分模型的训练流程和配套工具链。

于是，组织开始划分出，或者说，涌现出新的边界：

也就是所谓的数据清洗，Pre-train，SFT，RLHF，Infra，还有杂七杂八的模型评估与测试团队。

这种划分看似极其符合现代工业化流水线协作方式，但是对于 AGI 而言，其实是有问题的。

* * *

在这样一个庞大的组织里，每一个团队都在为了自己部门的指标进行局部优化，可这些指标在数学上往往是相互冲突的。

在小规模的极客团队里，同一个人或极少数几个人协同就能解决问题，协作成立的条件是，他们大脑里的认知本身就是高度对齐的。

^pr-3be80ef04523

一旦团队规模扩大，由于部门与部门之间的沟通和妥协，认知完全不可能对齐，潜移默化中就积累了一种研发壁垒，使得跨部门优化被分隔，各部门陷入了各自的局部最优解。

等价地说，超大模型的权重更新，其实并不是沿着字面上纯粹的数学损失函数下降的，而是沿着公司内部各部门 KPI 之间的博弈与妥协间的缝隙下降的。

最后产出的模型，其智能水平不会超越这个组织中各个部门互相扯皮后的平均值。

* * *

为了避免这种智力越多，智力越少的怪圈，我现在就在刻意培养自己的思维模式。

我不再把活交给别人去干，我觉得，如果我需要找人帮忙，那一定是我的问题。

我有厌蠢症，现在的沟通协作能力已经不再是一种美德。

CPU 读取 L1 Cache 只需要几个时钟周期，但读取内存需要上百个时钟周期。

一旦发生磁盘 I/O 那就更别提了，纯空耗。

同理，在研发流程中，求助于人就是一种 Cache Miss。

^pr-e4e97c139734

一旦你将一个任务拆分并交给了另一个人，你就主动作废了自己大脑中已经建立起来的高速上下文。

你必须写文档、画架构图、反复沟通，试图把你的认知投射到对方的大脑里。

反复确认没理解错需求，然后 await 这种外部调用，最后得到返回一个结果。

这个结果是概率性正确的，我靠，那和 LLM 也没差别啊？！

* * *

在没有大模型辅助的古法时代，一个人的精力和知识面是有限的，一个人无法同时精通 C++ 底层通信、CUDA 算子开发、PyTorch 模型框架调试、Rust 数据清洗流水线设计，以及 Vue 前端展示界面的编写。

但是现在，我不知道别人怎么样，至少我就这么干活，我一个人就可以搞定优化部署一条龙。

大语言模型作为一种通用的认知中介，已经彻底抹平了不同技术领域之间的信息鸿沟。

^pr-ca8f3e18cb93

你觉得没有，是因为你没有专家知识，没法激活大模型中对应的区域。

人类的语料根本不够大模型吃的，前沿的大模型实际都是饥渴的欠拟合状态，内部本身就记忆了一切公开的知识。

只是，你用专有名词，和不用专有名词，大模型的激活模式是完全不一样的，就好似能随着你的水平提升而提升。

* * *

在不久的将来，以大多数人的水平之低，压根达不到谈大模型智商的条件，包括我。

所以说人和大模型之间也是有一个同步率的概念的。

^pr-295e15fbe3fb

当然，人和人之间也有，但是由于心之壁的存在，这个同步率是极低的。

即便是所谓的知己也是，并不能每次都 get 到你的意思。

但是有足够上下文的大模型可以，你要做的只是把所有的决策文档化，让 AI 自己去看。

* * *

我即是虫群，我即是军团。

我不再需要人与人之间的同步，所有的 Agent 和我同步就行了。

当你沉迷于这种工作模式，你会发现，传统的招聘一点意思也没有。

为什么要招一个废物来降低我们这个大群意识之间的同步率呢？
