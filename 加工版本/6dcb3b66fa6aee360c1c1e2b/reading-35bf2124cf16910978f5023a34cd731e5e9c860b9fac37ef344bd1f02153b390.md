### 29\. Napkin math numbers（粗略估算数值）

#### Random memory access latency（随机内存访问延迟）

让我朋友（Jamie）立刻觉得奇怪的是，random memory R/W 被列为 20ns，因为这里的 random memory R/W 暗指真正的 DRAM read（而不是 cache hit），他觉得，作为 order of magnitude estimate，这应该在 100ns 左右。

我们聊到这里时，他指出，README 对一些实际上并不是 latencies 的东西使用了“latency”这个术语。随后，他打开 random memory read latency 的 code，发现了下面的内容（如果你还想做一道 exercise，可以在阅读下面的解释之前，想想下面的 code 有什么问题）：

```
  while test.i < test.vec.len() {                                                       
      let random_index = test.order[test.i];                                            
      black_box(test.vec[random_index]);                                                                                                                                         
      test.i += 1;                                                                                                                                                               
  }     
```

Jamie 指出，loop iterations 之间没有 data dependency，所以这里的 memory reads 是 in parallel 发生的。由于所谓的 latency 数值是通过求一次 access 的 average time 来 determined 的，这并不正确，因为 CPU 可以同时有 multiple loads in flight。如果想用这种方式 measure latency，就必须在 loads 之间 introduce 一个 dependence，以 prevent overlapping accesses（我们在[本系列第 4 篇涵盖的 exercise 19](https://www.patreon.com/posts/127627543) 中讨论过一个相关话题）。

#### Random SSD read（随机 SSD 读取）

我同意 Jamie 的所有意见，不过我自己并没有特别指出 latency 这个术语的用法，因为它也许在某些情况下是 latency 的简称，而在另一些情况下指某种有点 latency-like 的东西（例如 reciprocal throughput），这样可以让 table 更简单。

除了 memory latency 数值之外，最先引起我注意的是其他一些数值。例如，random SSD read 被列为 100 us / 70 MB/s。你可以买到快得多（也慢得多）的 SSDs。例如，如果你有一个 fast（但并不 exotic，例如非 Optane）的 device，你可能会看到低于 40us 的 latencies，例如 Kioxia CD9P-R [在这里 measured 的结果约为 ~30 us](https://www.storagereview.com/review/kioxia-cd9p-r-review-read-intensive-gen5-up-to-61-44tb)。除了一些 trivial scripts，我从没做过什么需要关心 disk performance 的工作，所以我对人们应该记住哪些数值没有直觉[1](https://danluu.com/exercise-7/#fn:P)，但我也在想，给 random read latency 和 throughput 各记一个数值，是否不如对 DRAM accesses 这样做有用。每当我看 disk benchmarks 时，results 似乎都会随着 read size、queue depth 和 number of jobs 而在很大的 range 内变化（例如，参见[前面关于 Kioxia CD9P-R 的链接](https://www.storagereview.com/review/kioxia-cd9p-r-review-read-intensive-gen5-up-to-61-44tb)）。当然，也有类似的因素会影响 DRAM latency 和 bandwidth，但在思考 memory accesses 时，你似乎更常处于这样一种 regime：知道一两个数值就很有帮助。由于我对 disk performance 一无所知，我请教了做过 Postgres disk performance 工作的 Peter Geoghegan；他赞同我的看法，还在[下面](https://danluu.com/exercise-7/#appendix-more-on-disk-performance) 对 disk performance 的 complexity 写了一些补充意见。

如果看看这个 SSD random read 数值对应的 code，我会觉得不太对劲，就像 Jamie 觉得 random memory read 的 code 不太对劲一样。它用下面的方式 generates offsets：

```
for i in 0..(buffer.len() / page_size) {
    pages.push((i * page_size + 1) as u64);
}
```

然后进行 8 KiB reads（offsets 会被 shuffled，以 create random reads）。其中让我觉得不太对劲的地方包括：

1.  这个 +1 让每次 read 都是 unaligned。在 page size 为 4KiB 时，这会让一次 read touch 3 个 pages
2.  不同的 offsets 可能 overlap 同样的 pages，导致从 page cache 进行看起来并非有意的 reads
3.  取决于 page size，reads 可能 extend past file 的末尾，并 cause 一个 panic

“buffer.len() / page\_size”这种 construction 似乎是为了让 accesses 保持 in bounds，但它与 access length 是 independent 的。如果我们想偷个懒，不去考虑确切的 offsets，不妨想想某个很大的 access length，比如 4 GiB（buffer size 是 8 GiB）。那肯定会 overflow。如果想更 precise，overflow case 更像是 4KiB page 搭配 8KiB access length，但同样的思路仍然适用。

最后一个 offset 将是 SIZE - 4096 + 1。这给了我们可以 access 的 4095 bytes，但我们却尝试 access 8192 bytes。由于 benchmark 只 runs 5 seconds，它实际上可能会，也可能不会尝试 read past EOF 并 fail，但无论它在某次 run 中是否 randomly fails，这里都存在一个 bug。

#### Sequential SSD read（顺序 SSD 读取）

光看 code，我就觉得其中很多地方不太对劲。例如，看看用于 generate sequential 8 KiB SSD read 的 code，据说它具有 1us latency 和 8 GiB/s throughput。正如我前面说的，我从没做过任何 disk performance 很重要的问题，所以我对这样的数值是否 plausible 没有直觉，但这段 code 让我觉得不对劲。code 取一个 1 GiB file，对它进行 flushing，然后反复 re-reading，因此我们会得到一次 uncached read，后面跟着 cached reads。这里的意图似乎是 measure uncached reads，但如果意图是 measure cached reads，这段 code 同样也没做到（其他一些数值似乎也存在这个问题，例如 3 GiB/s 的 fsync'd reads）。你可以说，一次 uncached read 后跟着 cached reads 是 realistic 的，但如果一个人使用的是 1 次 uncached read 后跟 N 次 cached reads 的 aggregate number，而他的 workload 并不完全相同，那么他应该如何使用这个数值就不清楚了；N 也没有以明显的方式写出来，所以他甚至无法知道自己的 workload 是否相同。

由于我完全不知道这里的数值应该是多少，也许我们可以查一些数值。据说，这个 measurement 是在一个 `c4-standard-48-lssd` 上完成的。Google 关于这个 instance 的 docs 声称，全部 8 个 attached disks 的 maximum throughput 为 5000 MiB/s（从 Google 的 table 来看，这会随 attached disks 的数量而 scales，每个 disk 是 625 MiB/s）。根据我对 disk benchmarks 极其有限的了解，peak throughput 数值通常似乎是在使用较大的 reads 时得到的，因此 8 GiB/s 看起来过高，而看 code 时那种不对劲的感觉似乎是对的。而且，如果看看其他数值，似乎也能支持一个更广泛的观点：用几个针对特定 read sizes 的单一数值，并不能 representative 地反映总体的 disk performance。

#### Representativeness（代表性）

但这类「napkin math」背后的想法通常并不是了解某个 cloud instance 究竟如何 performs；而是获得一些 basic numbers，用于以各种方式 estimate performance。如果我们回头看 Kioxia CD9P benchmarks，会发现有很多采用各种 parameters 的 read benchmarks，其 bandwidth 比那个更高（也有很多采用各种 parameters、bandwidth 更低的）。至于 latency，即使是采用 minimize latency 的 settings 的 sequential reads，latency 也更高（benchmark 中的其他 disks 也是如此），这进一步表明 `sirupsen` benchmark 正在无意中 reading from cache；但即使这些 numbers 是 correct，也不清楚你能拿它们做什么。

看起来，`sirupsen` code 尝试 prevent caching 和 prefetching。如果它 detects 这个 test 正在 Linux 上 run，就会 sets 一个 advisory `POSIX_FADV_RANDOM`，并且在 test 开始前 sets 一个 advisory `POSIX_FADV_DONTNEED`，但这两者都不会在 OS level prevent 这个 benchmark 中的 caching，也不应指望它们 prevent lower-level caching（例如 SSD 内部的 caching）。在 Mac 上，benchmark 会事先 calls `Command::new("sudo").arg("purge").output().expect("failed to flush page cache")`，但没有 `POSIX_FADV_RANDOM` 的 equivalent，而且似乎也没有针对其他 OSes（例如 BSD 或 Windows）做任何处理。

code 的其他部分还有其他问题，但与其深入纠缠每一个具体问题和所呈现的大多数 values，不如回到这个想法：对于有些事情，我们想了解的是不同 regimes 下 numbers 的 range，而这样的情况似乎还相当多。再举一个例子，README 将「Decompression」列为 1 GiB/s，将「Compression」列为 500 MiB/s。当然，任何 napkin math 都不会是 precise，但只要试试不同的 `zstd` compression options，compression speeds 就会出现超过 two orders of magnitude 的 difference，而且还有更专门针对 high speed compression 的 algorithms，使 range 变得更大（当然，你也可以多花些功夫，以获得 lower speed 和 denser compression）。

回到 disk 的例子，我们之前提到，disk numbers 来自一个带有 8 disks 的 VM configuration。这些 numbers 看起来是 incorrect，但即使它们是 correct，如果使用这个 VM 的 single-disk version，read bandwidth 之类的 numbers 当然也会不同。如果 read benchmarks 并不是在 reading from the page cache，你应该预期其 read bandwidth 大约只有 1/8th。不清楚为什么把 GCP 上某个特定 8-disk configuration 的 read bandwidth number 作为 napkin math figure 记下来会特别有用。

#### 学些什么才有用？

总的来说，我确实觉得知道一些这类 numbers 很有用，但不确定自己是否一定想通过查看 table 来了解这些 numbers（也许为了准备面试除外：如果我有充分理由相信面试中会被问到这些，我会为此准备，但也预期自己在面试后立刻忘掉）。一般来说，如果你所做的事情确实需要知道这些 numbers，那么只要使用它们，你自然就会记住。例如，我至今仍记得 standard single-mode fiber 中的 dispersion 是 17 ps / nm \* km，因为二十年前我做过一些 optics / photonics 方面的工作。它在 back-of-the-envelope calculations 中出现得足够频繁，只要使用得足够多，你迟早就会记住。各种 powers of 2（例如 2^8 = 256、2^16 = 65536 等）也是如此；我并没有试图背下它们，而是自然而然记住的，因为如果你做了足够多会接触这些 numbers 的 coding，最终就会记住那些经常派得上用场的 numbers。

链接中的 napkin math repo 指出，「numbers \[是\] rounded，以便记忆」，暗示把这些记下来是有意义的。除了上面提到的内容，许多这样的 numbers 都是 derivable，而且在我看来，如果你在工作中使用它们，即使已经记住了一个 ballpark number，了解其 derivation 通常仍然有意义。例如，[我们在第 4 部分根据一些 basic parameters，derived 了 Sandy Bridge processor 的 single-core memory bandwidth number](https://www.patreon.com/posts/127627543)。如果你只是想知道一段 code 将 run 得多快，通常不必从 first principles 出发 rederive 所有东西。但如果你想了解改变某些东西的 implications，知道有哪些 mechanisms 在起作用、它们将如何 interact 会很有帮助，而仅仅记住几个 numbers 并不能让你获得这些认识。

回到这个问题的背景，也就是我那位正在准备面试的朋友，他最后提到的担忧是：这个 repo 非常受欢迎，因此面试官可能会使用它，却不知道其中列出的大多数 numbers 都是 wrong。

#### 690ns？

我们还看到了一些来自 90 年代、极高的 outlier results。不花太多时间查看这些 results，并不能明显看出这些 results 是 incorrect 的。在 Intel 这边，那个大的 outlier 是一颗 83 MHz Intel Pentium Overdrive。其他较早的 Intel results 都来自 non-Overdrive Pentiums。

Overdrive Pentiums 是可以直接装进为上一代 CPU 准备的 motherboard 的 chips。看起来，这个 test 是在一块 Gigabyte GA-5486AL motherboard 上 run 的，它使用 ALi M1489/M1487 chipset，bus speed 被设为 33 MHz。根据 ALi M1489/M1487 datasheet，有四种可能的 DRAM read timings。如果它被 configured 为 "normal" setting，一次 read page miss 就是 `CP+8`，read timing 为 `4-4-4`。我对 486 bus timing 的了解甚至比对 disk performance 还少，所以我就此问了一个 LLM，它告诉我这是 correct 的，而且这里一次 memory access 应当需要 21、22 或 23 cycles。这感觉不太对，因为在追问 LLM 这些 numbers 到底是什么意思之后，原来它们指的是 first word 以及随后的每个 additional word，所以这个 cycles 数对应的是一次 full cache line fill。那么，一次 word access 的实际 load-to-use latency 应当是第一部分，也就是 11 bus cycles；不过，如果你想知道整个 cache line 所需的时间，那么这个 number 看起来或许确实属于相应的 benchmark。

查看那个 outlier AMD K5 PR166 result 时，会发现它有点奇怪，不过，对于一个关于 modern computer performance 的问题来说，我们已经在细枝末节上走得太远了，所以也许可以把它留作本系列后面的另一个问题。

### 30\. DeepSWE / Senior SWE-Bench：这两个基准测试

#### 整体可信性：General plausibility

先不看这些 benchmarks 的 methodology，只看 results，无论 DeepSWE 还是 Senior SWE-Bench，作为 coding agents 整体工作表现的 summaries，都让人觉得不太 plausible。粗看 DeepSWE homepage，会觉得 OpenAI 的上一代 model（GPT-5.5）与 Anthropic 的这一代 model（Fable 5）一样好；粗看 Senior SWE-Bench，则会觉得 Anthropic 的上一代 model（Opus 4.8）比 OpenAI 的这一代 model（GPT 5.6）更好。一般来说，大多数人得到的就是这种表面印象，而我通常看到的也是这种用法（例如在工作 slack 中，或别人直接把这些发给我时，等等）。

#### 方法问题：Methodlogy issues

如果看看这些东西到底是怎么做出来的，就会发现，在公开可用的 benchmarks 中，很少有看起来值得依赖、能帮助我们大致了解 coding agents 有多好的东西。从 methodology 来看，就获得 generalizable result 所需要 measure 的内容而言，这些 benchmarks 实在说不通。正如我对 disk performance 一无所知一样，我对 AI 也一无所知，所以我请了一位曾在 Anthropic 管理过一段时间 evals team 的人（Aaron Levin）来 review 这里的 reasoning 和 conclusion，他赞同总体想法和 reasoning。和请教 disk-performance expert 时一样，这里并不是说，因为 expert 同意，你就应该同意；而是说，在这些情况下，你不需要任何该领域的 specialized knowledge，也能得出与 expert 相同的 conclusion。你只需要运用你在 evaluate 任何 benchmarking 或 experimental design problem 时会使用的那种 generic reasoning。

#### 汇总得分的代表性：Summary score representativeness

在[上一篇文章](https://danluu.com/ai-coding/)中，我们讨论过这样一个 high-level idea：单个 summary score 几乎可以说明任何事情，因为当我们查看 subbenchmark results 时，会有很多 results favor model X over model Y；而一般来说，并没有特别好的办法对现有 tasks 的 distribution 进行 sample，从而声称 benchmark A 比 benchmark B 更好，因为它更 representative。

如果进一步查看这些 benchmarks 的 details，DeepSWE 有 113 个 tasks（反正 codex 是这么告诉我的），每个都 run 四次，采用的通常看起来是 pass/fail score（models 在每个 task 上的 score 似乎是 0%、25%、50%、75% 或 100%）。从 graph 上可以看到，GPT-5.5 比 Opus 4.8 好得多；GPT-5.5 与 Opus 4.8 之间的 difference，差不多和 Opus 4.8 与 Gemini-3.5 Flash 之间的 difference 一样大。正如上面提到的，如果你用过这些 models，就会发现，这与我或任何我信任其判断的人的整体体验并不相符（当然，在某些 specific tasks 或 sub-benchmarks 上，这确实成立）。

如果看看为什么据说会这样，GPT-5.5 xhigh 据称比 Opus 4.8 xhigh 稍微 cheaper 一些，而且好得多（scoring 67% vs. 54%）。在这 113 个 tasks 中，两个 models 在 34 个 tasks 上 tie，GPT-5.5 xhigh 在 57 个 tasks 上 wins，而 Opus 4.8 在 22 个 tasks 上 wins。对我或另一位 programmer 来说，如果这些 tasks 对我们所做的 tasks 是 representative 的，那么这或许是 meaningful 的。113 个 tasks（甚至只是那 79 个 differing tasks）已经超过本文打算详细查看的数量，不过，从 tasks 的名字来看，其中几乎没有哪个与我所做的 tasks 有关。再看 language，在那些存在差别的 tasks 中，有 4 个 tasks 使用的是我经常借助 coding agents 处理的 language（Rust），其余 tasks 使用的 languages，要么是我不会借助 coding agents 处理的，要么是我只会让它们处理 trivial problems、任何 model 都足够应付的[2](https://danluu.com/exercise-7/#fn:L)。

results 存在差别的四个 Rust tasks 是：

Boa 中的 Hierarchical evaluation cancellation（[](https://deepswe.datacurve.ai/data/v1.1/tasks/boa-hierarchical-evaluation-cancellation)[https://deepswe.datacurve.ai/data/v1.1/tasks/boa-hierarchical-evaluation-cancellation](https://deepswe.datacurve.ai/data/v1.1/tasks/boa-hierarchical-evaluation-cancellation)）、fd 中的 Deterministic multi-key sorting（[](https://deepswe.datacurve.ai/data/v1.1/tasks/fd-deterministic-multi-key-sorting)[https://deepswe.datacurve.ai/data/v1.1/tasks/fd-deterministic-multi-key-sorting](https://deepswe.datacurve.ai/data/v1.1/tasks/fd-deterministic-multi-key-sorting)）、在 oxvg 中 Preserve stylesheet-selector structure（[](https://deepswe.datacurve.ai/data/v1.1/tasks/oxvg-structural-selector-preservation)[https://deepswe.datacurve.ai/data/v1.1/tasks/oxvg-structural-selector-preservation](https://deepswe.datacurve.ai/data/v1.1/tasks/oxvg-structural-selector-preservation)），以及 wasmi 中的 Trap coredump generation（[](https://deepswe.datacurve.ai/data/v1.1/tasks/wasmi-trap-coredumps)[https://deepswe.datacurve.ai/data/v1.1/tasks/wasmi-trap-coredumps](https://deepswe.datacurve.ai/data/v1.1/tasks/wasmi-trap-coredumps)）。这些似乎都与我使用 coding agents 做的事情没多大关系，所以这对我毫无价值。

其中一个似乎隐约像是我过去一年做过的事情，另外三个则不像。通过查看 individual benchmarks，我们知道，不同 benchmarks 的 results 之间存在 significant variance（例如，在[上一篇文章](https://danluu.com/ai-coding/)的 Optimization 1 benchmark 中，我们得到的 model ranking 隐约有点像 DeepSWE，而在 GameAI 中，我们得到的 ranking 则像 Senior SWE-Bench；不过，正如我们在那篇文章里也观察到的，一个 benchmark 即使名义上看起来类似于我们关心的某个 task，也可能给出与我们在实际 task 上看到的情况相反的 result，这同样是因为 variance 非常高）。113 个 tasks 中只有 1 个多少类似于我做过的 task，这意味着 DeepSWE benchmark score 对我个人而言是 meaningless 的。

#### Senior SWE-Bench（Senior SWE-Bench 基准）

再来看另一个 benchmark，Senior SWE-Bench 存在上述所有问题，而且它以更具误导性的方式呈现 results，还存在对 results 进行更 subjective grading 的额外问题。我不想做那种极长的逐点剖析，不过可以看看其中的一个问题：要 qualify 为一个 "tasteful solve"，一个 solution 必须 meet 多项 criteria，包括在某个 rubric 上 scoring 高于某个 score，以及其 result 的 length 不能是 reference result 的 >= 2x。

#### Arbitrary 且 subjective 的 scoring function

甚至不必更深入地看，我们就已经能看出，这是一个典型的 [https://danluu.com/discontinuities/](https://danluu.com/discontinuities/) 情形。这个 benchmark 有这些 continuous scores，然后又通过要求一个 strict cutoff 来 introduces threshold effects。根据我的观察，人们经常这样做，是因为这样更简单，但如果你认为 underlying criteria 很重要，那么一般而言，你往往不会想说，X 的 score 就是 pass，而 X-epsilon 的 score 就是 failure。相反，这些 scores 应当以某种 non-discontinuous 方式被 aggregated。我想，人们往往不愿这样做，是因为一旦试着为它写下一个 formula，就常常会明显看出 weights 是 arbitrary 的，而且 score 是 meaningless 的。我们大概知道，如果 reference 是 R LOC，我们并不想给一个 1 LOC solution 多达 N 的 extra score，所以我们需要某个 function 来 cap 那里的 value。也许我们可以通过类似 `(2R)/(R+N)` 的做法，把 bonus cap 在 2。也许这还不足以 penalize large functions，所以我们应该改用 `(2R^2)/(R^2+N^2)`。如果把它写成 `1+tanh(ln(R/N))`，可能更容易看出它的 behavior，所以如果你愿意，可以在脑中 substitute 成这种形式。然后我们需要把它与其他 scores combine，所以我们需要在 M 个 formulas 中 add 至少 M-1 个，从而为它们设置某种 relative weighting。

这显然会是一个难以 justify 的 arbitrary formula。但实际使用的、带有这些 discontinuities 的 formula，是另一个完全 arbitrary function，而且其 properies 更差，使它甚至更难 justify！只不过，写下它的人不必把它当作一个 formula 来思考，因此可以避免思考它究竟有多 arbitrary。

#### Threshold effects（阈值效应）

如果我们具体看看 Senior SWE-Bench 所 defined 的 LOC measure，当然会看到 threshold effects。例如，在 [](https://senior-swe-bench.snorkel.ai/tasks/paperless-ngx-perf-workflow-queries)[https://senior-swe-bench.snorkel.ai/tasks/paperless-ngx-perf-workflow-queries](https://senior-swe-bench.snorkel.ai/tasks/paperless-ngx-perf-workflow-queries) 上，GLM-5.2 在 121 LOC 时被 scores 为 tasteful，而 reference 是 61。如果再多仅仅一个 LOC，就会变成 122，也就是 double，这会使 GLM-5.2 fail 而不是 pass。我们还可以从链接中看到，这个 benchmark 在每个 condition 下只 run 了一次。正如任何用过 LLMs 的人都知道的，也正如我们[在上一篇文章中](https://danluu.com/exercise-7/danluu.com/ai-coding/)看到的那样，不同 runs 之间存在巨大的 variance（相当经常地，不同 runs 之间的 variance 会超过不同 models 和 effort levels 之间的 variance，我们在上一篇文章中观察到了这一点），因此，即使用某种合理的 continuous score 进行 scored，single run 也已经不太有意义。当这类 noisy metrics 又因为这些 threshold effects 而被 removed information 时，result 就变得更加没有意义。

就 LOC score 而言，这甚至还不算一个问题特别严重的 benchmark。[plausible-fix-top-pages-comparison](https://senior-swe-bench.snorkel.ai/tasks/plausible-fix-top-pages-comparison) 更糟，因为 reference solution 是 1 LOC（由于 addition 和 deletion 各 count 为 1 LOC，这被 scored 为 2 LOC）。这使 tasteful solve 的 maximum size 只有 3 LOC；如果 additions 和 deletions 都发生，那就必须是 1 LOC deleted、2 added，或者反过来。

#### Grader variance（评分器方差）

LLM variance 也适用于 grading 本身。当然，如果我们把 single run 的 results 多次 feed 给一个 LLM grader，就一定会得到不同的 scores，原因与我们多次请 LLM solve 同一个 problem 时，常常得到大相径庭的 results 一样。我试着让身边那位亲切的 coding agent，对 GPT-5.6 Sol 和 Opus 4.8 接受 tested 的每个 condition 都 re-run grading 10 次（codex 告诉我 grading 是用 Sonnet 4.6 run 的，所以它也用那个 re-ran）。在使用相同 model 和 effort level 时，expected LLM-graded tastefulness result 有 23% 的时候会相对于 official result 发生 flips（就 sub-results 而言，relative taste 在 32% 的 cases 中 flips，practice alignment 在 5% 的 cases 中 flips，task rubric 在 3% 的 cases 中 flips）。如果改为查看 official result 不同于 typical/median result 的时间比例，overall 有 21% 的 difference（relative taste 为 27%，practice alignment 为 3%，task rubric 为 2%）。overall flip rate 低于 individual flip rate，是因为在某些 cases 中，当 overall score 已经是 untasteful 时，某个 sub-score 中的 result 才从 tasteful flipped 为 untasteful。

说清楚一点，这不是 run-to-run variance。这是在 single run 上使用 LLM grading 所产生的 variance；在公开可用的 GPT-5.6 Sol 和 Opus 4.8 benchmarks 中，它似乎约有 20% 的时候会给出 incorrect result（前提是我们 assume，被 measured 的东西本来就是 correct 且值得 measure 的，而且 most likely Sonnet score 就是 correct score）。

当然，如果用不同的 models 来 grade，我们也会得到不同的 results。如果我们用 GPT-5.6 Sol 而不是 Sonnet 4.6 来 re-grade，那么对两个 models 来说，被 judged 为 tasteful 的 solutions 的 number 都会减少一半以上。这样是更 accurate，还是更不 accurate？谁知道呢？

### Taste oracle：品味判定者

即使 LLMs 已经足够好，通常能够对 code quality 作出 judgement call，上述问题也仍然是问题。Senior SWE-Bench 不仅是 structurally flawed，它还有一个缺陷：如今试图用 SOTA LLMs 来 judge code quality 是毫无意义的，更不用说 Sonnet 4.6 了。[正如我们之前指出的，当我们面对一个没有好的 numerical angle 的问题时，避免编造 fake number 往往比赋予它一个 meaningless number 更好](https://danluu.com/empirical-pl/)，而如今让 LLM 尝试 judge code quality，得到的就是这样的数字。

#### Overall validity：整体有效性

有时候，你可以看着一个 benchmark 说，虽然某些 individual results 是 wrong，但 in aggregate，noise cancels out，overall results 还是说得通的。我不认为这里是这种情况。我见过许多人到处转发 Senior SWE-Bench，似乎是因为它声称自己提供了 realistic problems，并以合理的方式对它们 score。我们已经指出，prima facie，这些 results 似乎并不 plausible；而查看 methodology，也支持了那个 prima facie 的想法，即这个 result 并没有 meaningful 的意义[3](https://danluu.com/exercise-7/#fn:M)。

results 的 presentation 也有不尽如人意之处。在我加入的一个 Slack 中，有人发来了它的链接，其中显示的 preview snippet 如下：

-   Claude Fable 5: 29.1%
-   Claude Opus 4.8: 25.0%
-   GPT-5.6 Sol: 24.4%

那人给出了赞许的评论，说这比其他 benchmarks 更 realistic（指的是许多把 GPT-5.5 排在 Opus 4.8 前面的 benchmarks 中的一个）。如果你真的查看 results，就会清楚地看到，25.0% 与 24.4% 之间的 difference 几乎是 meaningless，但这些 results 的 presentation 却仿佛这些 differences 是 meaningful 的。虽然页面清楚说明，根据 measured 的结果，GPT-5.6 Sol 比 Opus 4.8 便宜得多，但我见过的大多数提到 Senior SWE-Bench 的讨论都略去了这一点，只提 headline result。另一个奇怪之处在于，headline result 对 Fable、Opus 和 Sonnet 使用 `max`，却对 GPT-5.6、GPT-5.5 和 GPT-5.4 使用 `xhigh`。

### 31\. Cold weather tire performance：寒冷天气下的轮胎性能

虽然人们常说 all-season tires 在 7C / 45F 时会变得如此 hard（不知为何，常见的说法是它们会变得像“冰球”一样硬），以至于变得 unsafe，但根本没有 benchmark！这是本系列反复出现的一个主题：人们一再重复某个 claim，而它[显然没有 measurement 依据](https://danluu.com/why-benchmark/)[4](https://danluu.com/exercise-7/#fn:C)。

幸运的是，正如我们[在这篇关于 platforms 和 monetization 的文章中讨论过的](https://danluu.com/why-video/)，Jonathan Benson 已经能够将对 tires 的深入探索 monetize，从而让公开的 tire benchmarks 达到了前所未见的细致程度。他[tested 了不同种类的 tires 在不同 temperatures 和不同 conditions 下 perform 得如何](https://www.youtube.com/watch?v=bKtnczk8Mxk)。我相信 tire manufacturers 有各种各样这样的 tests，但据我所知，此前还没有人以全面的方式公开做过这件事（嗯，这似乎与 coding agents 的公开 benchmarks 没那么不同）。

在 Benson 的 testing 中，他发现，在 dry conditions 下，即使低至 0C / 32 F，summer tires 仍具有最好的 grip（他没有 test 更冷的 conditions），其次是 all-seasons，而 winter 比 summer tires 和 all-seasons 都差了相当大的一截。在 wet conditions 下，他只 tested 到 2C，因为到了 0C，就会出现 icy conditions，而不只是 wet conditions。ranking 有些不同，因为在 2C 的 wet conditions 下，all-season tires 大幅 outperformed summer tires，但 summer tires 仍然 outperformed winter tires。

请注意，在视频中，Benson 所说的 winter tire 是 UHP winter tire，我很少见到美国或加拿大有人使用它（不过，我自己用的 winter tire 就是这种，因为它适合我居住地的 local conditions）。作为一个会留意别人用什么 tires 的怪人，除了我自己的车以外，我在当地只见过那些拥有 high-performance care、而 OEM recommended option 是 UHP winter tire 的人使用 UHP winter tires（即便如此，他们装 winter tire 时，大多数时候也不会用 UHP winter tire）。

他所说的“nordic” tire，才是大多数人用作 winter tire 的类型，即便在我现在住的地方以及以前住过的所有地方也是如此；在这些地方，这种 tire 其实都不太合理，除非你经常开车进山（即便如此，对我住过的那些地方的大多数人来说，它可能仍然不是正确选择），或者你经常在 ice 上驾驶，因为它在 dry 和 wet codnitions 下的 performance 比 UHP winter tire 差得多；在我居住的当地，市区里极少出现 ice（超过半个十年的时间里，我以 street speeds 行驶时从未遇到过），而主要在市区开车的人，大部分时间是在 dry 和 wet conditions 下行驶，偶尔遇到 snow；在这种情况下，除了 track tire 或 all-terrain tire 之类的 specialist tire，“nordic”（standard）winter tire 就是你能用的最差的 tire。再看看 UHP winter tire 与 all-seasons 相比的 results，在 0C 以上的 dry 或 wet conditions 下，all-seasons 仍然更好，只是 difference 的 magnitude 远小于与美国大多数人使用的“nordic” winter tires 相比时的差距（我想，他用的 terminology 可能在欧洲更常见？）。

当然，不同 tires 会 perform 得不同，换用不同 tires，我们会看到 results 出现一些 variation；当然，也有许多 conditions 下，使用 winter tires 比 all-season tires 或 summer tires 更好。但在经常被引用的 temperatures 下，all-season tires 会变得 too hard to grip、仅仅因为 cold 就必须使用 winter tires 的说法，显然是 false 的。

#### 谁会在意 tires？

顺便说一句，如果你想知道为什么要在意 tires，那么 on average，[motor vehicle accidents 是相当主要的 cause of death](https://upload.wikimedia.org/wikipedia/commons/a/a5/Causes_of_death_by_age_group_%28percent%29.png)，而如果你看看 velocity 对 accident severity 的 impact，就会发现它相当 significant。因此，使用能够让你 brake more rapidly、或 corner 得稍好一些，从而也许能够 avoid accident 或稍微 deflect accident 的 tires，按理说应该会对 accident severity 产生 substantial impact；这样想是合理的。我不认为这类事情有非常好的 data（要开展 randomized trial 会非常困难，而 observational data 通常会是 highly confounded 的）。

不过，作为我去年所做的一项 analysis 的一部分，我曾试图从实际的 crash test data 中找出 [HIC](https://en.wikipedia.org/wiki/Head_injury_criterion) 与 velocity 之间的 relationship。让我意外的是，我找不到做过这件事的 paper（不过，我倒是找到了一些可以用作本系列 exercises 的 papers），但一项 straightforward analysis 表明，这个 relationship 大致是 to the fourth power。我真应该把它写成一篇[类似于这篇关于 crash testing 的文章](https://danluu.com/car-safety/)的文章，不过专门讨论各种 vehicles 的 HIC 和 concussion risk！总之，我尽量驾驶装有适合当地的 tires 的车，因为这似乎很可能是我为自身 safety 所能采取的、按每一美元和／或投入的精力计算具有较高 impact 的 interventions 之一。但我从来没有接近过那种我非常好的 tires 真正发挥作用的情境，而且，一个会出于 safety 原因努力寻找合适 tires 的人，原本就可能更不容易遭遇 accident，所以这也许只是一个完全无关紧要的傻爱好。

    多年前，我读 McElreath 的 Statistical Rethinking 开头部分时，希望能学到某种通向 rigorous statistical analysis 的 process，却看到一个隐约相关的观点：实际上并不存在这样的 process，最终你还是必须运用自己的判断，来决定某件事是否合理。

    既然如此，我想一系列 exercises 或许行得通，于是就有了把大约 50 或 100 个 exercises 写进一篇文章的想法。对于小型 exercises 来说，这似乎相当可行，但从观察人们学习各种事物的过程来看，很明显，给人们一堆小型 exercises，然后指望他们把 techniques generalize 到更大、更 complex 的 exercises 上，通常效果并不好。一旦开始加入更大、更 complex 的 exercises，篇幅很快就会超出一篇长文的长度，即便按照这个博客的标准也是如此——这里可是有一篇[关于 FTC 在 2011-2012 年对 Google 的 investigation 中弄错了什么的 32k 词文章](https://danluu.com/ftc-google-antitrust/)（作为参考，一部普通小说通常被认为有 80k-100k 词）。

    总体而言，我一直避免在博客上发表分成多篇的文章，因为作为读者，我更希望内容全都放在一篇文章里，而不是散落在某个长长的系列中。我理解作者往往更喜欢分成多篇发表，因为这样通常能带来更多 traffic，让文章在 social media 上 going viral 的机会更大，等等；但我一直以来对这个博客的 optimized 方向，都是让它更接近我自己想读的东西，而不是 maximize page views。在这个例子里，单篇版本似乎很容易就能长到一部厚得可以当门挡的奇幻小说那么长（作为参考，据说 Brandon Sanderson 的 Stormlight Archive 系列每本约有 450k 词），而这篇文章只有 3 个 exercises，大约 7k 词。我想，照这个速度，我需要写 64 篇，而我现在才写到第 7 篇；不过，能写成 64 篇文章的 problems 肯定是足够的，剩下的只是抽出时间来写。

### 29\. Napkin math numbers

#### Random memory access latency

The thing that immediately jumped out to my friend (Jamie) as odd was random memory R/W listed as 20ns, since random memory R/W is implied to be a real DRAM read (as opposed to a cache hit), which he felt this should be around 100ns for an order of magnitude estimate.

As we were chatting about this, he noted that the README uses the term "latency" for some things that aren't really latencies. Then, when he pulled up the code for random memory read latency, he found the following (if you want another exercise, consider what's wrong with the following code before reading the explanation below):

```
  while test.i < test.vec.len() {                                                       
      let random_index = test.order[test.i];                                            
      black_box(test.vec[random_index]);                                                                                                                                         
      test.i += 1;                                                                                                                                                               
  }     
```

Jamie noted that there's no data dependency between the loop iterations, so the memory reads here happen in parallel. Since the alleged latency number is determined by finding the average time for an access, this is incorrect because the CPU can have multiple loads in flight at once. If you wanted to measure latency this way, you'd have to introduce a dependence between loads, to prevent overlapping accesses (we discussed a related topic in [exercise 19, covered in part 4 of this series](https://www.patreon.com/posts/127627543)).

#### Random SSD read

I agree with all of Jamie's comments, although I didn't really flag the use of the term latency myself because maybe it's shorthand for latency in some cases and something a bit latency-like in other cases (such as reciprocal throughput), which makes the table simpler.

What first jumped out to me, besides the memory latency number, was some of the other numbers. For example, random SSD read is listed as 100 us / 70 MB/s. You can get much faster (as well as much slower) SSDs. For example, if you have a fast (but non-exotic, e.g., non Optane) device, you might see latencies below 40us, e.g., the Kioxia CD9P-R [was measured at ~30 us here](https://www.storagereview.com/review/kioxia-cd9p-r-review-read-intensive-gen5-up-to-61-44tb). Other than for some trivial scripts, I haven't worked on anything where I care about disk performance, so I don't have an intuition for what numbers someone would want to have in mind[1](https://danluu.com/exercise-7/#fn:P), but I also wonder if having a single number for random read latency and throughput is less useful than it is for DRAM accesses. Whenever I've looked at disk benchmarks, it seems like there's a huge range of results based on read size, queue depth, and number of jobs (e.g., see [the previous link on the Kioxia CD9P-R](https://www.storagereview.com/review/kioxia-cd9p-r-review-read-intensive-gen5-up-to-61-44tb)). Of course, there are analogous factors that influence DRAM latency and bandwidth, but it seems like you're much more often in a regime where knowing one or two numbers is helpful when thinking about memory accesses. Since I don't know anything about disk performance, I asked Peter Geoghegan, who's done work on Postgres disk performance; he concurred and also wrote some additional comments on the complexity of disk performance [below](https://danluu.com/exercise-7/#appendix-more-on-disk-performance)

If we look at the code for this SSD random read number, it feels off to me in the same way that the random memory read code felt off to Jamie. It generates offsets with

```
for i in 0..(buffer.len() / page_size) {
    pages.push((i * page_size + 1) as u64);
}
```

and then does 8 KiB reads (offsets are shuffled to create random reads). Some things that don't feel right about this are:

1.  The +1 makes every read unaligned. With a 4KiB page size, this makes one read touch 3 pages
2.  Different offsets can overlap the same pages, causing seemingly unintended reads from page cache
3.  Depending on the page size, reads can extend past the end of the file and cause a panic

The "buffer.len() / page\_size" construction seems to be intended to keep accesses in bounds, but this is independent of the access length. If we want to be lazy and not think about exact offsets, consider some huge access length like 4 GiB (the buffer size is 8 GiB). That will surely overflow. If we want to be more precise, the overflow case will be more like a 4KiB page with 8KiB access length, but the same idea applies.

The very last offset is going to be SIZE - 4096 + 1. This gives us 4095 bytes we can access, but we try to access 8192 bytes. Because the benchmark only runs for 5 seconds, it may or may not actually try to read past EOF and fail, but there's a bug here regardless of whether or not it randomly fails on any given run.

#### Sequential SSD read

Just looking at the code, a lot of it doesn't feel quite right to me. For example, consider the code that's used to generate the sequential 8 KiB SSD read, which is said to have 1us latency and 8 GiB/s throughput. Like I said, I haven't worked on any problems where disk performance matters, so I don't have an intuition on whether or not numbers like this are plausible, but the code feels off to me. The code takes a 1 GiB file, flushing it, and then re-reading it repeatedly, so we'll have one uncached read followed by cached reads. It seems like the intent is to measure uncached reads here, but if the intent is to measure cached reads, the code isn't doing that either (this appears to be an issue for some of the other numbers as well, such as 3 GiB/s of fsync'd reads). One could argue that it's realistic to have an uncached read followed by cached reads, but it's not clear what someone who's using the aggregate number of 1 uncached read followed by N cached reads should do with the number when they don't have the exact same workload; N isn't stated in an obvious way, so they wouldn't even know if they have the same workload.

Since I have no idea what the numbers should be here, maybe we can look up some numbers. The measurement was said to be done on a `c4-standard-48-lssd`. Google's docs for that instance claim that the maximum throughput for all 8 attached disks is 5000 MiB/s (from Google's table, this scales per number of attached disks and is 625 MiB/s per disk). From the very little I know of disk benchmarks, it seems like peak throughput numbers are generally done when using larger reads, so 8 GiB/s seems excessive and the feeling that something is off from the code seems to be right. And if we look at other numbers, it seems like the broader point that having a few single numbers for specific read sizes isn't representative of disk performance in general.

#### Representativeness

But the idea behind this kind of "napkin math" generally isn't to know how exactly one cloud instance performs; it's to get some basic numbers that can be used to estimate performance in various ways. If we look back to the Kioxia CD9P benchmarks, there are plenty of read benchmarks with higher bandwidth than that, with various parameters (and also plenty with lower bandwidth, with various parameters). For latency, the latency is higher even for sequential reads at settings that minimize latency (including for the other disks in the benchmark), which is another sign that the `sirupsen` benchmark is inadvertently reading from cache, but even if the numbers were correct, it's not clear what you'd do with the numbers.

It seems like the `sirupsen` code has an attempt to prevent caching and prefetching. If it detects the test is being run on Linux, it sets an advisory `POSIX_FADV_RANDOM` and, before the test starts, it sets an advisory `POSIX_FADV_DONTNEED`, but neither of these will prevent caching on this benchmark at the OS level, nor should these be expected to prevent lower-level caching (such as inside the SSD). On Mac, the benchmark calls `Command::new("sudo").arg("purge").output().expect("failed to flush page cache")` beforehand, but there's no equivalent of `POSIX_FADV_RANDOM` and there doesn't seem to be anything done on other OSes (such as BSD or Windows).

There are other issues in other parts of the code, but rather than get into the weeds on every specific issue and most of the presented values, if we come back to this idea that there are things where we want to get an idea of a range of numbers in different regimes, there are quite a few places where that seems to be the case. To pick another example, the README cites "Decompression" at 1 GiB/s and "Compression" at 500 MiB/s. Of course, any kind of napkin math isn't going to be precise, but just playing with different `zstd` compression options, we get more than two orders of magnitude difference in compression speeds and there are algorithms that are more specialized for high speed compression, giving an even larger range (and of course you can spend more effort to get lower speed and denser compression).

Going back to the disk example, we noted that the disk numbers come from a VM configuration with 8 disks. The numbers appear to be incorrect but, if the numbers were correct, of course you'd get different numbers for something like read bandwidth if you used a single-disk version of the VM. You'd expect roughly 1/8th the read bandwidth for the read benchmarks if it wasn't reading from the page cache. It's not clear why it's particularly useful to have a read bandwidth number for one particular 8-disk configuration on GCP memorized as a napkin math figure.

#### What's useful to learn?

Overall, I do find knowing some of these kinds of numbers useful, but I don't know that I'd necessarily want to look at a table to see the numbers (except maybe as interview prep that I'd expect to forget immediately after the interview if I had good reason to believe I'd be asked about them in an interview). In general, if you're doing things where it makes sense to know these numbers, you'll pick them up just by using them. For example, I still remember that dispersion in standard single-mode fiber is 17 ps / nm \* km because I did some optics / photonics work twenty years ago. This comes up often enough in back-of-the-envelope calculations that you'll just remember this at some point if you use it enough. Likewise for various powers of 2 (e.g., 2^8 = 256, 2^16 = 65536, etc.), which I didn't try to memorize but picked up because, if you do enough coding where you touch these numbers, you end up remembering the numbers that often come in handy.

The linked napkin math repo notes that "numbers \[are\] rounded for memorization", implying that it makes sense to memorize these. In addition to what's mentioned above, a lot of these numbers are derivable and, in my opinion, if you're using these for work, it often makes sense to understand the derivation even if you have a ballpark number memorized. For example, [we derived the single-core memory bandwidth number for a Sandy Bridge processor from some basic parameters in part 4](https://www.patreon.com/posts/127627543). If you just want to know how fast a piece of code is going to run, you generally don't to rederive everything from first principles. But, if you're trying to understand the implications of changing something, it's helpful to know the what mechanisms are in play and how they'll interact, which is something you don't get from having a handful of numbers memorized.

Going back to the context for this question, my friend who was doing interview prep, the last concern he mentioned was that this repo is very popular, so the interviewer might be use it without knowing that most of the numbers that are listed are wrong.

#### General plausibility

Before looking at the methodology of these benchmarks and just looking at the results, neither DeepSWE nor Senior SWE-Bench feel plausible as summaries for how well coding agents work overall. A surface-level reading of the DeepSWE homepage has OpenAI's last-generation model (GPT-5.5) being as good as Anthropic's current-generation model (Fable 5) and a surface-level reading of the Senior SWE-Bench has Anthropic's last-generation model (Opus 4.8) as being better than OpenAI's current generation model (GPT 5.6). #### Methodlogy issues

If we look at how the sausage is made, very few of the publicly available benchmarks seem like reasonable things to rely on for getting a general idea of how good coding agents are. In terms of methodology, the benchmarks don't really make sense with respect to what you'd need to measure to get a generalizable result. Just like I don't know anything about disk performance, I don't know anything about AI, so I asked someone who ran an evals team at Anthropic for a while (Aaron Levin) to review the reasoning and conclusion and he concurred with the general idea and the reasoning. You just need to apply the same kind of generic reasoning you'd use to evaluate any benchmarking or experimental design problem.

#### Summary score representativeness

In [the last post](https://danluu.com/ai-coding/), we discussed the high-level idea that a single summary score can say pretty much anything because, when we look at subbenchmark results, there will be plenty that favor model X over model Y and there isn't a particularly good way to, in general, sample the distribution of tasks out there to say that benchmark A is better than benchmark B because it's more representative.

If we look more at the details of these benchmarks, for DeepSWE, there are 113 tasks (or that's what codex told me, anyway), each one of which is run four times, with what generally appears to be a pass/fail score (models appear to score 0%, 25%, 50%, 75%, or 100% on each task). #### Senior SWE-Bench

Moving on to the other benchmark, Senior SWE-Bench has all of the problems noted above, and it also presents the results in a more misleading way and has the additional issue of doing more subjective grading of results. I don't want to do one of these super long point-by-point teardowns, but to look at one issue with it, to qualify as a "tasteful solve", a solution has to meet multiple criteria, including scoring better than a certain score on a rubric and having a result that isn't >= 2x the length of a reference result.

#### Arbitrary and subjective scoring function

Without even looking at it more deeply, we already see this is a classic [https://danluu.com/discontinuities/](https://danluu.com/discontinuities/) situation. The benchmark has these continuous scores and then it introduces threshold effects by requiring a strict cutoff. From what I've seen, this kind of thing is often done because it makes things simpler, but if you believe the underlying criteria are important, in general, you often don't want to say that a score of X is a pass and a score of X-epsilon is a failure. Instead, the scores should be aggregated in some non-discontinuous way. I think there's often a hesitancy to do this because trying to write down a formula for this often makes it obvious that the weights are arbitrary and the score is meaningless. We probably know we don't want to give up to N extra score for a 1 LOC solution if the reference is R LOC, so we need some function that will cap the value there. Maybe we can cap the bonus at 2 by doing something like `(2R)/(R+N)`. Maybe this doesn't penalize large functions enough, so we should switch to `(2R^2)/(R^2+N^2)`. It might be easier to see the behavior of this if we write it as `1+tanh(ln(R/N))`, so you can mentally substitute that if you prefer. We then need to combine this with the other scores, so we need to add at least M-1 of the M formulas so we have some relative weighting for them.

This would clearly be an arbitrary formula that's hard to justify. But the actual formula used has these discontinuities is another completely arbitrary function, but with worse properies that make it even harder to justify! It's just that whoever's writing it down doesn't have to think of it as a formula so they can avoid thinking about how arbitrary it is.

#### Threshold effects

If we look specifically at the LOC measure as defined by Senior SWE-Bench, of course we see threshold effects. For example, on [](https://senior-swe-bench.snorkel.ai/tasks/paperless-ngx-perf-workflow-queries)[https://senior-swe-bench.snorkel.ai/tasks/paperless-ngx-perf-workflow-queries](https://senior-swe-bench.snorkel.ai/tasks/paperless-ngx-perf-workflow-queries), GLM-5.2 scores tasteful at 121 LOC vs. 61 for the reference. If there was one single LOC more, it would be 122, or double, which would cause GLM-5.2 to fail instead of pass. We can also see from the link that the benchmark was run once per condition. As anyone who's used LLMs knows and as we saw [in the last post](https://danluu.com/exercise-7/danluu.com/ai-coding/), there's tremendous variance between runs (quite often, there is commonly variance between runs than across different models and effort levels, which we observed in the last post), which already makes a single run not very meaningful when scored with some kind of reasonable continuous score. When noisy metrics like this then have information removed with these threshold effects, the result becomes even less meaningful.

That isn't even a particularly problematic benchmark with respect to the LOC score. [plausible-fix-top-pages-comparison](https://senior-swe-bench.snorkel.ai/tasks/plausible-fix-top-pages-comparison) is worse because the reference solution is 1 LOC (since addition and deletion each count as 1 LOC, this is scored as 2 LOC). This makes the maximum size of a tasteful solve 3 LOC; if additions and deletions both happen, this would have to be 1 LOC deleted and 2 added or vice versa.

#### Grader variance

LLM variance also applies to the grading itself. Of course it must be the case that if we feed the results of one single run to an LLM grader multiple times, we'll get different scores for the same reason we often get wildly different results when we ask an LLM to solve the same problem multiple times. I tried having my friendly neighborhood coding agent re-run grading 10 times for each condition that GPT-5.6 Sol and Opus 4.8 were tested under (codex tells me grading was run using Sonnet 4.6, so it re-ran with that). The expected LLM-graded tastefulness result flips from the official result 23% of the time when using the same model and effort level (in terms of sub-results, relative taste flips in 32% of cases, practice alignment flips in 5% of cases, and task rubric flips in 3% of cases). If we instead look at the fraction of the time the official result differed from the typical/median result, there's a 21% difference overall (27% for relative taste, 3% for practice alignment, and 2% for task rubric). The overall flip rate is lower than the individual flip rate because, in some cases, a result flipped from tasteful to untasteful in a sub-score when the overall score was already untasteful.

Just to be clear, this is not run-to-run variance. This is the variance from using LLM grading on a single run, which, across the publicly available GPT-5.6 Sol and Opus 4.8 benchmarks, appears to give an incorrect result about 20% of the time (if we assume what's being measured is correct and reasonable to measure in the first place and tha the most likely Sonnet score is the correct score).

Of course we get different results if we grade with different models as well. If we re-grade with GPT-5.6 Sol instead of Sonnet 4.6, the number of solutions that are judged to be tasteful is cut by more than half for both models. Is that more or less accurate? Who knows?

### Taste oracle

The issues described above would be a problem even if LLMs were good enough to, in general, make a judgement call on code quality. In addition to Senior SWE-Bench being structurally flawed, it's also flawed because it's pointless to attempt to judge code quality with SOTA LLMs today, let alone Sonnet 4.6. [As we previously noted, when we have a problem we don't have a good numerical angle on, it's often better to avoid making up a fake number than to assign a meaningless number](https://danluu.com/empirical-pl/), which is what we get today if we have an LLM try to judge code quality.

#### Overall validity

Sometimes, you can look at a benchmark and say that, while some individual results are wrong, in aggregate, the noise cancels out and the overall results make sense. I don't think that's the case here. I've seen a lot of people passing Senior SWE-Bench around, seemingly because it purports to give realistic problems and score them in a reasonable way. We already noted that, prima facie, the results don't seem plausible, and, that looking at the methodology supports the prima facie thought that the result is not meaningful[3](https://danluu.com/exercise-7/#fn:M).

The presentation of results also leaves something to be desired. On a Slack I'm on, someone linked to this, which shows a preview snippet with the following:

-   Claude Fable 5: 29.1%
-   Claude Opus 4.8: 25.0%
-   GPT-5.6 Sol: 24.4%

They gave an approving comment, saying this was more realistic than other benchmarks (referring to one of the many benchmarks that put GPT-5.5 ahead of Opus 4.8). If you actually look at the results, it's clear that the difference between 25.0% and 24.4% is pretty much meaningless, but the results are presented as if these are meaningful differences. Although the page makes it clear that GPT-5.6 Sol is, as measured, much cheaper than Opus 4.8, most discussions I've seen that refer to Senior SWE-Bench elide this and mention only the headline result. It also seems odd that the headline result uses `max` for Fable, Opus, and Sonnet, but `xhigh` for GPT-5.6, GPT-5.5, and GPT-5.4.

### 31\. Cold weather tire performance

Although people commonly say that all-season tires become so hard (for some reason, the phrasing that they become as hard as "hockey pucks" is common) at 7C / 45F that they're unsafe, there's no benchmark! This has been a common theme in this series: people repeating a claim that has [no apparent basis in a measurement](https://danluu.com/why-benchmark/)[4](https://danluu.com/exercise-7/#fn:C).

Luckily, as we [discussed in this post on platforms and monetization](https://danluu.com/why-video/), Jonathan Benson has been able to monetize in-depth explorations on tires, resulting in a never-before seen level of detail in public tire benchmarks. He [tested how well different kinds of tires perform at different temperatures and in different conditions](https://www.youtube.com/watch?v=bKtnczk8Mxk). I'm sure tire manufacturers have all sorts of tests like this but, AFAIK, this hadn't been done publicly in a comprehensive way before (hmm, this doesn't seem so different from public benchmarks of coding agents).

In Benson's testing, he finds that, in dry conditions, summer tires have the best grip down to 0C / 32 F (he didn't test colder conditions), followed by all-seasons, with winter being worse than both summer tires and all-seasons by a fairly large margin. In wet conditions, he only tested down to 2C since, at 0C, you have icy conditions and not just wet conditions. The ranking is a bit different since all-season tires wildly outperformed summer tires at 2C in the wet, but summer tires still outperformed winter tires.

Note that, in the video, what Benson calls a winter tire is a UHP winter tire, which I very rarely see people using in the US or Canada (although it's what I use for a winter tire since that makes sense for the local conditions where I live). As weirdo who looks at what tires people are running, except on my car, I've only seen people running UHP winter tires locally when they have a high-performance care where the OEM recommended option is a UHP winter tire (and even then, they won't be running a UHP winter tire most of the time when they have a winter tire).

What he calls a "nordic" tire is what most people use for a winter tire even locally here and everywhere else I've lived, all of which are locations where that kind of tire doesn't really make sense unless you're spending a lot of time driving into the mountains (and even then, it's probably still not the right choice for most people where I've lived) or you spend a lot of time driving on ice because performance in dry and wet codnitions is dramatically worse than a UHP winter tire; locally, where I live, ice is extremely rare in the city (I've never encountered it at street speeds in more than half a decade) and someone who who mostly drives in the city is mostly driving in dry and wet conditions with occasional snow, where a "nordic" (standard) winter tire is the worst tire you could run other than a specialist tire like a track tire or an all-terrain tire. And if you look at the UHP winter tire results compared to all-seasons, it's still true that all-seasons are better in dry or wet conditions above 0C, although the magnitude of the difference is much smaller than it is relative to the "nordic" winter tires that most people in the US use (I think the terminology he's using might be more common in Europe?).

Of course different tires will perform differently and we'd see some variation in results with different tires, and of course there are many conditions where it's better to have winter tires than all-season tires or summer tires, but the idea that all-season tires become too hard to grip and you have to have winter tires for cold alone is clearly false at commonly cited temperatures.

#### Who cares about tires?

BTW, if you're wondering why you should care about tires at all, on average, [motor vehicle accidents are a fairly major cause of death](https://upload.wikimedia.org/wikipedia/commons/a/a5/Causes_of_death_by_age_group_%28percent%29.png) and, if you look at the impact of velocity on accident severity, it's pretty significant, so it stands to reason that having tires that let you brake more rapidly or corner a little better and maybe avoid or deflect the accident a bit, it's reasonable to think this would have a substantial impact on accident severity. I don't think this is the kind of thing there's really good data for (it would be very hard to run the randomized trial and observational data is going to be highly confounded, in general).

But, as part of an analysis I did last year, I tried to find the relationship between [HIC](https://en.wikipedia.org/wiki/Head_injury_criterion) and velocity in actual crash test data. Surprisingly to me, I couldn't find a paper that had done this (I did find some papers that could serve as exercises for this series, though), but a straightforward analysis put the relationship as roughly to the fourth power. I should really write that up into a post that's [like this other post on crash testing](https://danluu.com/car-safety/), but specifically about the HIC and concussion risk of various vehicles! Anyway, I try to drive a car with the right tires for the locale because it seems like that's plausibly one of the higher impact interventions I could do for my own safety per dollar and/or effort. But I've never gotten close to a situation where my really good tires have made a difference and someone who's going to try to find the right tires for safety reasons may be less likely to get into an accident in the first place, so this may just be a silly hobby that doesn't matter at all.
