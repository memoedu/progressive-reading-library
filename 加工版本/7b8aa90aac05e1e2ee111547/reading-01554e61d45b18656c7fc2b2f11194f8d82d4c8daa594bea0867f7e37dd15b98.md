# 将这个网站的速度提升至原来的 50 倍｜Speeding up this site by 50x

---

## 正文

我看过不少这样的 studies，表明 page load time 的 100ms improvement 会对 page views、conversion rate 等产生 significant effect，但我从未真正尝试过 optimize 我的网站。这个博客是一个 static Octopress site，hosted 在 GitHub Pages 上。Static sites 应该是 fast 的，而 GitHub Pages uses Fastly，后者也应该是 fast 的，所以一切都应该是 fast 的，对吧？

因为以前没做过这件事，我不知道该怎么办。不过，在一场精彩的、讲解 internet 如何 works 的演讲中，[Dan Espeset](https://twitter.com/danielespeset) 建议试试 [webpagetest](http://www.webpagetest.org/)；那就试试看吧。

下面是它对我这个几乎保持 stock 状态的 Octopress setup[1](https://danluu.com/octopress-speedup/#fn:S) 给出的结果。我做过的 changes 只有 enabling Google Analytics、文章底部的 social media buttons，以及为 tables adding CSS styling（它们 by default 是 unstyled 而且难以阅读的）。

![开始 rendering 的时间：9.7s](https://danluu.com/images/octopress-speedup/octo_initial.webp) ![达到 visual completion 的时间：10.9s](https://danluu.com/images/octopress-speedup/octo_initial_detail.webp)

到第一次 page view 竟然要 12 秒！发生了什么？我以为 static sites 应该是 fast 的。first byte 不到半秒就到了，但 page 直到 9 秒后才开始 rendering。

![大量的 js、CSS 和 fonts](https://danluu.com/images/octopress-speedup/octo_initial_waterfall.webp)

看起来，最先发生的事就是我们 load 了一大堆 `js` 和 `CSS`。看看 source，我们有这么多 `js`，都在 `source/_includes/head.html` 里。

```
<script src="{{ root_url }}/javascripts/modernizr-2.0.js"></script>
<script src="//ajax.googleapis.com/ajax/libs/jquery/1.9.1/jquery.min.js"></script>
<script>!window.jQuery && document.write(unescape('%3Cscript src="./javascripts/lib/jquery.min.js"%3E%3C/script%3E'))</script>
<script src="{{ root_url }}/javascripts/octopress.js" type="text/javascript"></script>
{% include google_analytics.html %}
```

我对 web page optimization 一无所知，但 Espeset 提到，`js` 会 stall page loading 和 rendering。如果我们把 scripts move 到 `source/_includes/custom/after_footer.html` 呢？

![开始 rendering 的时间：4.9s](https://danluu.com/images/octopress-speedup/octo_js_after_footer.webp)

这可好多了！我们刚刚在 load time 和开始 rendering 的时间上各省了大约 4 秒。

那些 script tags 会 load modernizer、jquery、octopress.js，以及一些 google analytics 的东西。这个 `octopress.js` 里到底有什么？主要是用于 support embedding flash videos、delicious integration 和 github repo integration 这类东西的 code。其中确实有几样东西被我的网站用到，但大部分 code 都是累赘。

还有，为什么会有多个 `js` files？Espeset 还提到，connections 是 finite resources，如果有一大堆不同的 files，我们就会耗尽 simultaneous open connections。让我们 strip out 所有那些 unused `js`，再把剩下的 `js` combine 成一个 file。

![开始 rendering 的时间：1.4s](https://danluu.com/images/octopress-speedup/octo_one_js_file.webp)

好多了！不过，等一下。我需要 `js` 做什么？据我所知，我的网站仍然 using octopress 的 `js`，唯一的用途就是让你能通过 clicking 右侧的 sidebar 来把它来回推动，而 jquery 和 modernizer 也只是 octopress 中使用的 js 所必需的。我从不用那个功能，而且根据 in-page analytics，其他人也都不用。把它去掉吧。

![开始 rendering 的时间：.7s](https://danluu.com/images/octopress-speedup/octo_no_js.webp) ![达到 visual completion 的时间：1.2s](https://danluu.com/images/octopress-speedup/octo_no_js_detail.webp)

这并没有让 total load time 改变多少，但 browser 更早开始了 rendering。现在，网站在 1.2s 后就能 visually complete，而最初需要 9.6s——这是 8x improvement。

还剩什么？每篇文章底部的 twitter 和 fb widgets 仍然有一些 js，但它们都是在内容 rendered 之后才 loaded 的，所以并不会真正影响用户的 experience，尽管它们会让“Load Time”这个数字显得很难看。

![这些 fonts 可真多！](https://danluu.com/images/octopress-speedup/octo_no_js_pie.webp)

这是一张 pie chart，展示我的 page 中有多少 bytes 用于每一种 file。显然，payload 中占比最大的是 fonts。尽管我用作 reference 的文章是一篇 image 异常多的博客文章，fonts 仍然占了 43.8%，而 images 的 percentage 小到 webpagetest 甚至没有列出数字。我的 browser 不是已经有一些 default fonts 了吗？我们直接用那些不行吗？

![开始 rendering 的时间：.6s](https://danluu.com/images/octopress-speedup/octo_no_fonts.webp) ![达到 visual completion 的时间：.9s](https://danluu.com/images/octopress-speedup/octo_no_fonts_detail.webp)

事实证明，可以。webpage 现在能在 0.9s 内 visually complete——这是 12x improvement。对于“Repeat View”[2](https://danluu.com/octopress-speedup/#fn:R)，improvement 没有那么显著——那里只有 8.6x improvement——但仍然相当不错。

剩下的一个“明显”问题是，header 会 loads 两个 css files，其中一个没有 minified。这会 uses up 两个 connections，并 sends 超出必要数量的 data。对另一个 css file 进行 Minifying，再 combining 它们，还能进一步 speeds 这个过程 up。

![开始 rendering 的时间：.6s](https://danluu.com/images/octopress-speedup/octo_one_css.webp) ![达到 visual completion 的时间：.7s](https://danluu.com/images/octopress-speedup/octo_one_css_detail.webp)

达到 visually complete 的时间现在是 0.7s——这是 15.6x improvement[3](https://danluu.com/octopress-speedup/#fn:1)。而且，这还是在一个对我的网站而言 image 异常多的 page 上。

![主要是 image load time](https://danluu.com/images/octopress-speedup/octo_one_css_waterfall.webp)

到了这一步，page 开始 displaying 之前发生的事情就只有：，loading HTML、loading 那一个 `css` file，以及 loading 那张巨大的 image（reliability.png）。

我们已经 minified 了 css，所以剩下的主要事情就是让那张巨大的 image 变得更好。我已经对所有 images 运行过 `optipng -o7 -zm1-9`，但 ImageOptim 仍然能够再削减这张 image 的 4%，带来一点 improvement。对于我所有文章中的全部 images，ImageOptim 能在 optipng 的基础上额外 reduce images 20%，但在这个例子里帮助不大。

我还尝试过 specifying image 的 size，看看这是否能让 page 在 image 完成 downloading 之前就 render，但这并没有带来多大区别。

之后，我想不出还有什么可以尝试的了，不过 webpagetest 给出了一些有用的建议。

![哎呀，github pages](https://danluu.com/images/octopress-speedup/octo_suggestions.webp)

显然，我所在的 server 很 slow（在 initial request 后 sending first byte 这一项上，它得了 D）。它还建议 caching static content，但当我查看各条具体建议时，发现大多针对的是并不由我 host/control 的 widgets。我应该使用 CDN，但对于 bare domains，Github Pages 不会把 content 放到 CDN 上，除非你使用 DNS alias record，而我的 DNS provider 不 support alias records。这就有了两个停止通过 Github Pages servering 的理由（或者说，一个离开 Github Pages 的理由，以及一个更换 DNS provider 的理由），所以我改用了 Cloudflare，它把 time to first byte 缩短了超过 100ms。

注意，如果你为 static site 使用 Cloudflare，你会需要 create 一个 "Page Rule"，并 enable "Cache Everything"。By default，Cloudflare 不 cache HTML，而对于一个主要由 HTML 构成的 static blog 来说，这就有点没意义了。如果你已经做了这里的 optimizations，你也会想避开他们那个 "Rocket Loader"，它试图通过 loading blocking javascript 来 load js asynchronously。"Rocket Loader" 和 AMP 一样，可以 speed up 大型、bloated 的 websites，但它本身又足够庞大，以至于会 slows down moderately optimized websites。

下面是我最初 enabled Cloudflare、却还没意识到需要 create 一个 "Page Rule" 时发生的情况。

![Cloudflare 在 1GB 中 saves 了 80MB](https://danluu.com/images/octopress-speedup/octo_cloudflare_wat.webp)

这大约是 2013 年一天的 traffic。最初，Cloudflare 在 serving 我的 CSS，并为 HTML redirecting 到 Github Pages。后来我 inlined 了 CSS，Cloudflare 就真的什么也没做了。总体来说，在 1GB 的 traffic 中，Cloudflare served 了 80MB，因为它只在 caching images，而这个博客的 images 相对较少。

我还没有谈到 inlining CSS，但这很容易，而且能为首次 visit 带来巨大的 speedup，因为这意味着 display page 只需要一个 connection，而不是两个 sequentialy connections。对于之后的 visits，这反而是不利的，因为这意味着每个 page 都必须重新 re-downloaded CSS；但由于我的 traffic 大多来自偶然看到某一篇博客文章、不会 click through 到其他内容的人，所以总体上还是划算的。在 `_includes/head.html` 中

```
<link href="{{ root_url }}/stylesheets/all.css" media="screen, projection" rel="stylesheet" type="text/css">
```

应该改为

```
{\% include all.css %}
```

此外，css 里还有很多无用的 cruft。Removing 那些连我这样不懂 CSS 的人都能看出毫无意义的东西（比如对 delicious 的 support、对 Firefox 3.5 及更早版本的 support，以及被 firefox flags 为有 syntax errors 的 lines，例如把 `no-wrap` 写在了本应是 `nowrap` 的地方），就能把剩余的 CSS 削减大约一半。剩下的内容仍然有很多 duplication，我预计 CSS 还能再 reduced 到四分之一，但那就需要真正懂 CSS 了。仅仅做了这些事情，我们就把网页达到 visually complete 之前的时间降到了 .4s。

![对 css 进行 Inlining](https://danluu.com/images/octopress-speedup/octo_inline_css.webp)

这就是 `10.9/.4 = 27.5` 倍的 speedup。在 mobile 上的 effect 要显著得多；在那里，更接近 50x。

我不确定该怎么看待这一切。一方面，我很高兴能让自己的网站获得 25x-50x speedup。另一方面，我通常会把这种量级的 speedups 与这些事情联系起来：把 plain Ruby code porting 到 optimized C++，把 optimized C++ porting 到 GPU，或者把 GPU porting 到 quick-and-dirty exploratory ASIC。一个对 web development 零了解的人，怎么可能只看了一场演讲，再折腾 25 分钟，就获得这样的 speedup？我原本希望也许能找出 100ms 的 slack，结果发现，一个 Octopress setup 里不只是有 100ms，甚至不只是 1000ms，而是有 10000ms 的 slack。根据我看过的一项 study，从 1000ms 变成 3000ms，会让你损失 20% 的读者和 50% 的 click-throughs。我没见过考察从 400ms 变成 10900ms 的 study，因为一个 website 竟然会那么 slow，这个想法荒谬到人们甚至不会去探究这种可能性。但很多 websites 就是那么 slow！[4](https://danluu.com/octopress-speedup/#fn:D)

### 更新

我发现，要折腾着 trimming down Octopress 自带的庞大 CSS file 实在太难了，所以我 removed 了所有 CSS，然后 added 了几行，以支持一个 nav bar。这在上面的 desktop benchmark 中几乎没有区别，但对于 slow connections 而言，这是一个明显的 improvement。[对于 56k connections 以及具有 high packetloss 的 connections，这种区别相当显著](https://danluu.com/web-bloat/)。

从我做出这项 change 的那天起，我的 analytics data 就显示，engagement 和 traffic 有了明显的 improvement。这里有太多因素 confounded 在一起，无法判断是什么 caused 了这项 change（performance increase、完全没有 styling 等），但其中有几点让我觉得有意思。首先，这似乎很可能表明，认为保持 line lengths 为 short 非常重要的建议是不正确的，因为如果这件事的影响非常大，就会盖过其他 changes，导致 reduced engagement，而不是 increased engagement。其次，尽管 Octopress design 被广泛使用并备受赞誉（在我开始写 blog 时，它似乎是 programmers 最广泛使用的 blog theme），它似乎却会让一个 blog（或者至少是这个 blog）获得比完全没有任何 styling 更少的 readership。没有 styling 肯定不是 optimal，但没有 styling 竟然胜过了当时最广泛使用的 programmer blog styling，这多少有些好笑；这意味着，它很可能也胜过了 wordpress、[svtble](https://danluu.com/writing-non-advice/#svbtle)、blogspot、medium 等，因为它们具有与 Octopress 大体相同的组成部分。

## 原文

I've seen all these studies that show how a 100ms improvement in page load time has a significant effect on page views, conversion rate, etc., but I'd never actually tried to optimize my site. This blog is a static Octopress site, hosted on GitHub Pages. Static sites are supposed to be fast, and GitHub Pages uses Fastly, which is supposed to be fast, so everything should be fast, right?

Not having done this before, I didn't know what to do. But in a great talk on how the internet works, [Dan Espeset](https://twitter.com/danielespeset) suggested trying [webpagetest](http://www.webpagetest.org/); let's give it a shot.

Here's what it shows with my nearly stock Octopress setup[1](https://danluu.com/octopress-speedup/#fn:S). The only changes I'd made were enabling Google Analytics, the social media buttons at the bottom of posts, and adding CSS styling for tables (which are, by default, unstyled and unreadable).

![time to start rendering: 9.7s](https://danluu.com/images/octopress-speedup/octo_initial.webp) ![time to visual completion: 10.9s](https://danluu.com/images/octopress-speedup/octo_initial_detail.webp)

12 seconds to the first page view! What happened? I thought static sites were supposed to be fast. The first byte gets there in less than half a second, but the page doesn't start rendering until 9 seconds later.

![Lots of js, CSS, and fonts](https://danluu.com/images/octopress-speedup/octo_initial_waterfall.webp)

Looks like the first thing that happens is that we load a bunch of `js` and `CSS`. Looking at the source, we have all this `js` in `source/_includes/head.html`.

```
<script src="{{ root_url }}/javascripts/modernizr-2.0.js"></script>
<script src="//ajax.googleapis.com/ajax/libs/jquery/1.9.1/jquery.min.js"></script>
<script>!window.jQuery && document.write(unescape('%3Cscript src="./javascripts/lib/jquery.min.js"%3E%3C/script%3E'))</script>
<script src="{{ root_url }}/javascripts/octopress.js" type="text/javascript"></script>
{% include google_analytics.html %}
```

I don't know anything about web page optimization, but Espeset mentioned that `js` will stall page loading and rendering. What if we move the scripts to `source/_includes/custom/after_footer.html`?

![time to start rendering: 4.9s](https://danluu.com/images/octopress-speedup/octo_js_after_footer.webp)

That's a lot better! We've just saved about 4 seconds on load time and on time to start rendering.

Those script tags load modernizer, jquery, octopress.js, and some google analytics stuff. What is in this `octopress.js` anyway? It's mostly code to support stuff like embedding flash videos, delicious integration, and github repo integration. There are a few things that do get used for my site, but most of that code is dead weight.

Also, why are there multiple `js` files? Espeset also mentioned that connections are finite resources, and that we'll run out of simultaneous open connections if we have a bunch of different files. Let's strip out all of that unused `js` and combine the remaining `js` into a single file.

![time to start rendering: 1.4s](https://danluu.com/images/octopress-speedup/octo_one_js_file.webp)

Much better! But wait a sec. What do I need `js` for? As far as I can tell, the only thing my site is still using octopress's `js` for is so that you can push the right sidebar back and forth by clicking on it, and jquery and modernizer are only necessary for the js used in octopress. I never use that, and according to in-page analytics no one else does either. Let's get rid of it.

![time to start rendering: .7s](https://danluu.com/images/octopress-speedup/octo_no_js.webp) ![time to visual completion: 1.2s](https://danluu.com/images/octopress-speedup/octo_no_js_detail.webp)

That didn't change total load time much, but the browser started rendering sooner. We're down to having the site visually complete after 1.2s, compared to 9.6s initially -- an 8x improvement.

What's left? There's still some js for the twitter and fb widgets at the bottom of each post, but those all get loaded after things are rendered, so they don't really affect the user's experience, even though they make the “Load Time” number look bad.

![That's a lot of fonts!](https://danluu.com/images/octopress-speedup/octo_no_js_pie.webp)

This is a pie chart of how many bytes of my page are devoted to each type of file. Apparently, the plurality of the payload is spent on fonts. Despite my reference post being an unusually image heavy blog post, fonts are 43.8% and images are such a small percentage that webpagetest doesn't even list the number. Doesn't my browser already have some default fonts? Can we just use those?

![time to start rendering: .6s](https://danluu.com/images/octopress-speedup/octo_no_fonts.webp) ![time to visual completion: .9s](https://danluu.com/images/octopress-speedup/octo_no_fonts_detail.webp)

Turns out, we can. The webpage is now visually complete in 0.9s -- a 12x improvement. The improvement isn't quite as dramatic for “Repeat View”[2](https://danluu.com/octopress-speedup/#fn:R) -- it's only an 8.6x improvement there -- but that's still pretty good.

The one remaining “obvious” issue is that the header loads two css files, one of which isn't minified. This uses up two connections and sends more data than necessary. Minifying the other css file and combining them speeds this up even further.

![time to start rendering: .6s](https://danluu.com/images/octopress-speedup/octo_one_css.webp) ![time to visual completion: .7s](https://danluu.com/images/octopress-speedup/octo_one_css_detail.webp)

Time to visually complete is now 0.7s -- a 15.6x improvement[3](https://danluu.com/octopress-speedup/#fn:1). And that's on a page that's unusually image heavy for my site.

![Mostly image load time](https://danluu.com/images/octopress-speedup/octo_one_css_waterfall.webp)

At this point the only things that happen before the page starts displaying are:, loading the HTML, loading the one `css` file, and loading the giant image (reliability.png).

We've already minified the css, so the main thing left to do is to make giant image better. I already ran `optipng -o7 -zm1-9` on all my images, but ImageOptim was able to shave off another 4% of the image, giving a slight improvement. Across all the images in all my posts, ImageOptim was able to reduce images by an additional 20% over optipng, but it didn't help much in this case.

I also tried specifying the size of the image to see if that would let the page render before the image was finished downloading, but it didn't result in much of a difference.

After that, I couldn't think of anything else to try, but webpagetest had some helpful suggestions.

![Blargh github pages](https://danluu.com/images/octopress-speedup/octo_suggestions.webp)

Apparently, the server I'm on is slow (it gets a D in sending the first byte after the initial request). It also recommends caching static content, but when I look at the individual suggestions, they're mostly for widgets I don't host/control. I should use a CDN, but Github Pages doesn't put content on a CDN for bare domains unless you use a DNS alias record, and my DNS provider doesn't support alias records. That's two reasons to stop servering from Github Pages (or perhaps one reason to move off Github Pages and one reason to get another DNS provider), so I switched to Cloudflare, which shaved over 100ms off the time to first byte.

Note that if you use Cloudflare for a static site, you'll want to create a "Page Rule" and enable "Cache Everything". By default, Cloudflare doesn't cache HTML, which is sort of pointless on a static blog that's mostly HTML. If you've done the optimizations here, you'll also want to avoid their "Rocket Loader" thing which attempts to load js asynchronously by loading blocking javascript. "Rocket Loader" is like AMP, in that it can speed up large, bloated, websites, but is big enough that it slows down moderately optimized websites.

Here's what happened after I initally enabled Cloudflare without realizing that I needed to create a "Page Rule".

![Cloudflare saves 80MB out of 1GB](https://danluu.com/images/octopress-speedup/octo_cloudflare_wat.webp)

That's about a day's worth of traffic in 2013. Initially, Cloudflare was serving my CSS and redirecting to Github Pages for the HTML. Then I inlined my CSS and Cloudflare literally did nothing. Overall, Cloudflare served 80MB out of 1GB of traffic because it was only caching images and this blog is relatively light on images.

I haven't talked about inlining CSS, but it's easy and gives a huge speedup on the first visit since it means only one connection is required to display the page, instead of two sequentialy connections. It's a disadvantage on future visits since it means that the CSS has to be re-downloaded for each page, but since most of my traffic is from people running across a single blog post, who don't click through to anything else, it's a net win. In `_includes/head.html`

```
<link href="{{ root_url }}/stylesheets/all.css" media="screen, projection" rel="stylesheet" type="text/css">
```

should change to

```
{\% include all.css %}
```

In addition, there's a lot of pointless cruft in the css. Removing the stuff that, as someone who doesn't know CSS can spot as pointless (like support for delicious, support for Firefox 3.5 and below, lines that firefox flags as having syntax errors such as `no-wrap` instead of `nowrap`) cuts down the remaining CSS by about half. There's a lot of duplication remaining and I expect that the CSS could be reduced by another factor of 4, but that would require actually knowing CSS. Just doing those things, we get down to .4s before the webpage is visually complete.

![Inlining css](https://danluu.com/images/octopress-speedup/octo_inline_css.webp)

That's a `10.9/.4 = 27.5` fold speedup. The effect on mobile is a lot more dramatic; there, it's closer to 50x.

I'm not sure what to think about all this. On the one hand, I'm happy that I was able to get a 25x-50x speedup on my site. On the other hand, I associate speedups of that magnitude with porting plain Ruby code to optimized C++, optimized C++ to a GPU, or GPU to quick-and-dirty exploratory ASIC. How is it possible that someone with zero knowledge of web development can get that kind of speedup by watching one presentation and then futzing around for 25 minutes? I was hoping to maybe find 100ms of slack, but it turns out there's not just 100ms, or even 1000ms, but 10000ms of slack in a Octopress setup. According to a study I've seen, going from 1000ms to 3000ms costs you 20% of your readers and 50% of your click-throughs. I haven't seen a study that looks at going from 400ms to 10900ms because the idea that a website would be that slow is so absurd that people don't even look into the possibility. But many websites are that slow![4](https://danluu.com/octopress-speedup/#fn:D)

### Update

I found it too hard to futz around with trimming down the massive CSS file that comes with Octopress, so I removed all of the CSS and then added a few lines to allow for a nav bar. This makes almost no difference on the desktop benchmark above, but it's a noticable improvement for slow connections. [The difference is quite dramatic for 56k connections as well as connections with high packetloss](https://danluu.com/web-bloat/).

Starting the day I made this change, my analytics data shows a noticeable improvement in engagement and traffic. There are too many things confounded here to say what caused this change (performance increase, total lack of styling, etc.), but there are a couple of things find interesting about this. First, it seems to likely show that the advice that it's very important to keep line lengths short is incorrect since, if that had a very large impact, it would've overwhelmed the other changes and resulted in reduced engagement and not increased engagement. Second, despite the Octopress design being widely used and lauded (it appears to have been the most widely used blog theme for programmers when I started my blog), it appears to cause a blog (or at least this blog) to get less readership than literally having no styling at all. Having no styling is surely not optimal, but there's something a bit funny about no styling beating the at-the-time most widely used programmer blog styling, which means it likely also beat wordpress, [svtble](https://danluu.com/writing-non-advice/#svbtle), blogspot, medium, etc., since those have most oof the same ingredients as Octopress.
