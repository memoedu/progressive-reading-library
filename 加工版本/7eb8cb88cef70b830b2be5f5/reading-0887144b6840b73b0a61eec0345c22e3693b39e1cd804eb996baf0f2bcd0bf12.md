# 算法面试：理论与实践｜Algorithms interviews: theory vs. practice

---

## 正文

当我问那些时髦的 big tech companies 的人，为什么 algorithms quizzes 是强制性的时，最常得到的回答大致是：“我们的 scale 这么大，可承受不起有人不小心写出一个 `O(n^2)` algorithm，把 site 弄到 down 的地步”[1](https://danluu.com/algorithms-interviews/#fn:A)。这件事让我觉得好笑的一点是，尽管我为公司创造的 value 中，有相当一部分来自在工作中 solving phone-screen level algorithms problems，我却没法 pass algorithms interviews！我这么说时，人们往往以为我的意思是，我有一半 interviews 会 fail，或是差不多这样。其实不止一半。

我曾写过一篇讲述自己 interview 经历的博客草稿，读过草稿的人批评它太无聊、太重复，因为我 fail 的 interviews 实在太多。他们说，我应该用一个 table 来 summarize 这些失败，因为没人会想读一篇长达 10k 词、只是接连讲述失败经历的博客文章（这是个好建议；我正在写一个带 table 的版本）。我大概参加过 40 来场“真正的” software interviews，其中可能只 passed 了一两场（也可以说是零场）[2](https://danluu.com/algorithms-interviews/#fn:S)。

我们来看几个 examples，说明我上面说的“phone-screen level algorithms problem”究竟是什么意思。

在我工作过的一家大公司，一个 team 为自己的用途 wrote 了一个 core library，其中 implemented 了一个 resizable array。每次 resize 导致 array 的 backing store overflowed 时，这个 implementation 都会 added 一个 constant number 的 elements，然后将旧 array copied 到一个刚刚 allocated、稍微 larger 的 array。这是一个经典的反面 example，说明不该如何 [implement a resizable array](https://en.wikipedia.org/wiki/Dynamic_array)，因为它会导致 linear time resizing，而不是 [amortized constant time](https://en.wikipedia.org/wiki/Amortized_analysis) resizing。这个 example 实在太经典，以至于在 demonstrating amortized analysis 时，它经常被用作 canonical example。

对于不熟悉 big tech company phone screens 的人来说，我遇到的典型 phone screens 属于以下几种之一：

-   一道“easy”的 coding/algorithms question，前面可能还有一道“very easy”的 warm-up question。
-   一系列“very easy”的 coding/algorithms questions，
-   一堆 trivia（在 generalist roles 中很少见，但在 low-level 或 performance-related roles 中并不少见）

这个 array implementation problem 被认为如此 easy，以至于它被归入“very easy”这一类，要么作为“真正的” phone screen question 之前的 warm-up，要么与一堆同样 easy 的 questions 放在一起。然而，这个 resizable array 却造成了公司所有 JVM code 中约 1% 的 GC pressure（它是全部 code 中第二大的 allocations 来源），还消耗了相当一部分 CPU。幸运的是，这个 resizable array implementation 并没有被当作 generic resizable array 使用，而只由一个 semi-special-purpose wrapper 来 instantiated，这才让它“仅仅”造成公司全部 GC pressure 的 1%。如果把它作为一道 interview question，这个 team 的大多数成员极有可能在 interview 中 correctly implemented 它。我对它的 fixing，每年为雇主多赚的钱，比我一辈子赚到的钱还多。

那是第二大的 allocations 来源，排在第一位的来源，则是同一个 core library 中将一对 `long` values converting 为 byte arrays。看来之所以这样做，是因为有人 wrote 或 copy pasted 了一个以 byte array 作为 input 的 hash function，然后通过接收两个 byte arrays、依次对它们 operating，将其 modified 为接收两个 inputs，结果 hash function interface 就成了 `(byte[], byte[])`。为了对两个 longs call 这个 function，他们使用了一个广泛使用的 utility library 中方便的 `long` 到 `byte[]` 的 conversion function。那个 function 除了 allocating 一个 `byte[]` 并将一个 `long` stuffing 进去，还会 reverses 这个 long 的 endianness（这个 function 看起来原本是为了将 `long` values convert 为 network byte order）。

不幸的是，switching 到更合适的 hash function 会是一次 major change，因此我的 fix 是将 hash function interface change 为接收一对 longs，而不是一对 byte arrays，并让 hash function 来做 endianness reversal，而不是把它作为 separate step 来做（由于 hash function 本来就在 shuffling bytes，这并没有带来额外工作）。Removing 这些 unnecessary allocations，每年为雇主多赚的钱，比我一辈子赚到的钱还多。

严格来说，Finding 一个 constant factor speedup 不算 algorithms question，但它也是 algorithms interviews 中会出现的内容。作为 algorithms question 的 follow-up，我经常被问：“你能让它 faster 吗？”这些问题的答案，往往涉及做一个 simple optimization，从而得到 constant factor improvement。

有一个具体的 example，我在 interviews 中被问过两次：你正在将 IDs storing 为 ints，但 question 中已经给出了一些 context，让你知道这些 IDs 是 densely packed，因此你可以改为将它们 store 为 bitfield。这个 bitfield interview question 与现实中那个 superfluous array 的区别在于，现实中的 existing solution 与 expected answer 相去甚远，以至于对方可能根本不会再让你 find 一个 constant factor speedup。更有可能的是，到那一步时，你就已经 failed 那场 interview 了。

再举一个其他公司的 example：[BitFunnel](https://danluu.com/bitfunnel-sigir.pdf) 是 Bing 使用的一个 search index，它的 configuration 也是一个 interview-level algorithms question 的 example[3](https://danluu.com/algorithms-interviews/#fn:P)。

要 describe 这个 solution 所需的完整 context，对这篇博客文章来说有点太多了，不过基本上，就是有一组 bloom filters 需要 configured。一种做法（据说当时就是这么做的）是 write 一个 black-box optimization function，利用 gradient descent 尝试 find 一个 optimal solution。据说这总会导致一些奇怪的 properties，而 output configuration 总会带来一些 non-idealities；为绕过这些问题，他们让 backing bloom filters 变得 less dense，也就是向这个 problem 投入更多 resources（因而也就是更多钱）。

为了 create 一个更 optimized 的 solution，你可以 observe 到，BitFunnel 中的 fundamental operation 是 equivalent to 将 probabilities multiplying 在一起，因此，对于任何特定 configuration，你只需将一些 probabilities multiply 在一起，就能 determine 一个 configuration 会如何 perform。由于 configuration space 并没有那么大，你随后可以将它放进几个 for loops 中，iterate over possible configurations 的 space，再挑出 best set 的 configurations。这并不完全正确，因为 multiplying probabilities assumes 了一种在现实中并不 hold 的 independence，但它似乎运作得还可以，原因与 [naive Bayesian spam filtering](https://en.wikipedia.org/wiki/Naive_Bayes_spam_filtering) 刚问世时效果相当不错是一样的，尽管后者 incorrectly assumes 任意两个 words 在一封 email 中 appearing 的 probability 是 independent。而如果你想要完整的 solution，也可以推导出 non-independent 的细节，不过那大概已经超出一场 interview 的 scope 了。

这些只是我随手想到的三个 examples。我经常遇到这类事情，不假思索就能举出几十个 examples；如果坐下来，试着列出我处理过的每一个 example，可能会超过一百个；如果列出我知道的、由其他人处理过（或者没人处理过）的 examples，那肯定超过一百个。无论是这篇文章里的 examples，还是我没有写进来的那些，都有以下 properties：

-   这个 example 可以被表述为一道 interview question
-   如果被表述为一道 interview question，你会预期相关 team 的大多数人（很可能是所有人）都能在一场 interview 的时间内给出 right answer
-   fixing 这个 example 带来的年度 cost savings，比我迄今为止一生的收入还多
-   这个 example 已经存在了足够长的时间，因此可以合理 assume，如果没有这样的介入，它就不会被 discovered

在本文开头，我们提到，big tech companies 的人经常声称，他们必须进行 algorithms interviews，因为在 scale 很大的情况下，inefficiencies 的代价太高。我的经验却是，在我工作过的每一家进行 algorithms interviews 的公司，这类 examples 都数不胜数。试图通过在 interviews 中问 algorithms questions，让人们在工作中 solve algorithms problems，这种做法并不奏效。

一个原因是，尽管大公司努力确保他们雇用的人能 solve algorithms puzzles，他们同时也在 incentivize 许多、甚至大多数 developers，促使他们避免运用这种 reasoning 来赚钱。

上述 examples 的三个 solutions 中，有两个已经在 production 中，一个没有。如果我拿着一个 diff 去找一个随便选的 team，而且不持续跟进，通常就是这样的 hit rate（相比之下，另一种情况是我有理由相信这个 team 愿意接受，或这个 team 主动求助，或我一直缠着一个 team，直到 fix 被采纳）。

如果你非常愤世嫉俗，你可能会说，success rate 居然这么高，已经令人惊讶了。如果我随便找一个 team，efficiency 极有可能既不在这个 team 的 objectives 里，也不在其 org 的 objectives 里。公司很可能花了不少精力来 incentivizing teams 达成他们的 objectives——不然设立 objectives 有什么意义？Accepting 我的 diff，就要求他们 test、integrate、deploy 这个 change，而且会产生 risk（因为所有 deployments 都有 non-zero risk）。基本上，我是在要求 teams 做一些工作、承担一些 risk，去做一件对他们毫无价值的事。尽管 incentives 如此，人们通常还是会接受 diff，但他们不大可能花很多自己的业余时间去尝试 find efficiency improvements（而他们正常的工作时间，则会用于那些与 team 的 objectives 是 aligned 的事情）[4](https://danluu.com/algorithms-interviews/#fn:E)。

假设一家公司并不努力确保其 developers 能 pass algorithms quizzes，却确实 incentivize developers 使用 relatively efficient algorithms。我认为，上面那三个 examples 中，任何一个都不可能在多年间一直未被 discovered，也不可能一直没有被 fixed。设想在一家人们会 profile 自己 code 的公司工作的某个 developer，很可能会查看公司里 computationally intensive 程度最高的 library 的 profile 中那些 hottest items。前两个 examples 的“诀窍”不是什么 algorithms 魔法，而是至少去看一眼，而这正是 incentives 可以解决的问题。第三个 example 则没那么必然，因为没有一个 standard tool 会告诉你去看这个 problem。要把那个 result 包装成某种魔法也很容易——那个 example 构成了一篇 paper 的核心部分，这篇 paper 在其领域（IR）的顶级 conference 上获得了“best paper award”，但事实上，所谓“诀窍”只是 applying high school math，也就是说，真正的诀窍是有足够的时间去查看 high school math 可能 applicable 的地方，从中找到一处。

我确实曾在一家公司工作过，它采用的策略是：“不要在 interviews 中问 algorithms questions，但要 incentivize 那些从全局来看对公司有益的事情”。在那里的时候，我只找到过一个几乎符合上述 examples 的 criteria 的 fix（如果那家公司的 scale 更大，它就会符合全部 criteria，但由于公司的 size，efficiency 的 increases 所带来的价值远低于大公司——比我当时赚的钱多得多，但 annual return 仍少于我迄今为止一生的总收入）。

我认为，我只找到一个近似例子的主要原因是，有足够多的人把让公司变得更好视为自己的工作，因此 straightforward high-value fixes 往往并不存在，因为 systems 通常在 designed 时就已经使其从一开始便没有什么容易发现的 improvements。在少数并非如此的情况下，也有足够多的人努力做对公司有益的事（而不是被迫服从那些与公司整体利益相去甚远的 local incentives），因此，在我遇到问题之前，其他人很可能就已经去 fix 这个 issue 了。

那家公司的 interview 中，algorithms/coding 部分（initial screen 加上 onsite 合计）比大型科技公司的 phone screen 更容易，而且我们基本上不做 system design interview。

有一段时间，我们尝试过一道 algorithmic onsite interview question，它偏难，但仍处于你可能在 BigCo phone screen 中遇到的正常范围内（不过仍比你预期会在 onsite interview 中遇到的题目容易）。我们后来不再问这道题，因为我们 interview 过的每一个 new grad 都没能答出来（我们不会给 experienced candidates 这类题）。我们的声望实在不足以吸引那些能轻松回答这些问题的 candidates，因此不可能使用[其他所有人都在用的那些时髦 hiring filters](https://danluu.com/programmer-moneyball/) 来 hire。在如今关于 interviews 的讨论中，我们的做法常被称为“降低门槛”，但我不明白，如果一个人受雇从事的工作很少涉及跳过横杆（有些情况下甚至完全不涉及），我们为什么要在意他能跳过多高的横杆。而且，即使在确实需要他们跳过横杆的情况下，那些横杆可能也只有 2" 高，轻轻迈步就能跨过去。

如果用实际的 productivity 来 measured，那是我工作过的公司中最 productive 的一家。我相信，其原因在于文化，而且过于复杂，无法在这篇文章中充分探讨，不过我认为，有一点起到了帮助：我们没有用 algorithms quizzes 来 filter out 完全合格的 candidates，而且我们相信，只要我们的文化是大家普遍做正确的事，而不是专注于 local objectives，人们就能够在工作中学会那些东西。

如果其他公司希望人们在工作中 solve interview-level algorithms problems，也许可以试着 incentivizing 人们去 solve algorithms problems（在相关的情况下）。这既可以作为 filtering 那些能够 whiteboard algorithms problems 的人的补充，甚至也可以取而代之。

### 附录：我们是怎么走到这一步的？

很久以前，interviews 经常涉及“trivia” questions。它们如今的版本可能如下：

-   MSI 是什么？MESI 呢？MOESI 呢？MESIF 呢？MESIF 相较于 MOESI 有什么 advantage？
-   在 destructor 中 throw 时会发生什么？如果是 C++11 呢？如果一个由 top-level destructor 正在 called 的 sub-object 的 destructor throws，其他哪些 sub-object destructors 会 execute？如果在 stack unwinding 期间 throw 呢？在什么情况下，这不会导致 `std::terminate` 被 called？

我还在上学时就听说过这种做法，甚至也在一些“老派”公司见过。当时，Microsoft 是业内最大的公司，想要模仿成功公司的人很可能会模仿 Microsoft。当时读者最多的 programming 博主（Joel Spolsky）告诉大家，他们需要采用 software practice X，因为 Microsoft 正在这样做，不采用同样的 practices 就无法与之竞争。例如，在那个时代最具影响力的 programming 博文之一中，Joel Spolsky 提倡他所谓的 Joel test，其中一个理由就是，你必须做这些事，才能跟上 Microsoft 这样的公司：

> score 为 12 是 perfect，11 是 tolerable，但如果是 10 或更低，你就有严重的问题了。事实是，大多数 software organizations 都在 score 为 2 或 3 的情况下运转，它们需要 _极大的_ 帮助，因为 Microsoft 这样的公司始终以 12 的水平运转。

当时，广为流传的说法是，Microsoft 会问人们下面这样的问题（而在 2001 年前后我参加 Microsoft 的 interview 时，他们确实问了我其中一道 brainteasers，此外，algorithms 或 coding questions 的数量恰好为零）：

-   如果你只有半英寸高，你会如何从搅拌机里逃出来？
-   为什么井盖是圆的？
-   一间没有窗户的房间里有 3 盏灯，每盏灯都由房间外的一个开关控制。你在房间外。你只能进入房间一次。你如何确定哪个开关控制哪个灯泡？

由于我参加 interviews 时恰逢这种变化发生的年代，我被问过大量 trivia questions，也被问过大量 brainteasers（包括上面所有的 brainteasers）。当时流行的另外一些问题，严格来说并不属于 brainteasers，而是 [Fermi problems](https://en.wikipedia.org/wiki/Fermi_problem)。当时的另一种潮流是 behavioral interviews，我参加过 interviews 的好几家公司采用的是 100% behavioral interviews，technical interviews 则为零。

总之，当时人们需要一个理由，来合理化自己照搬 Microsoft-style interviews 的做法。当我问人们为什么觉得 brainteasers 或 Fermi questions 好时，他们给我的现成理由通常是：这些问题能告诉你一个 candidate 是否真的会思考，不像那些愚蠢的 trivia questions，只能告诉你人们是否记住了一些 trivia。我们真正需要 hire 的，是那些真正会思考的 candidates！

回过头看，人们现在意识到，这并不 effective，而且对 Microsoft 的每一个决定都进行 cargo culting，并不会让你像 Microsoft 一样成功，因为 Microsoft 的成功归根结底来自几个关键因素，加上 network effects，因此照搬他们的 interview 方式不可能把你变成 Microsoft。相反，它只会把你变成一家 interview 方式像 Microsoft、却不具备利用 Microsoft 所能利用的那些 network effects 的条件的公司。

对 interviewees 而言，当时围绕 brainteasers 的流程，基本上和如今围绕 algorithms questions 的流程一样，只不过你会在 interviews 前复习 [How Would You Move Mount Fuji](https://www.amazon.com/gp/product/0316778494/ref=as_li_tl?ie=UTF8&camp=1789&creative=9325&creativeASIN=0316778494&linkCode=as2&tag=abroaview-20&linkId=bcc3345d4905164e75b79f2cd2a0f5fb)，而不是 [Cracking the Coding Interview](https://www.amazon.com/gp/product/0984782850/ref=as_li_tl?ie=UTF8&camp=1789&creative=9325&creativeASIN=0984782850&linkCode=as2&tag=abroaview-20&linkId=381539624231e0e40b66f2695c925536)，以学会一堆永远不会在工作中用到的 brainteaser knowledge，而不是永远不会在工作中用到的 algorithms knowledge。

当时，interviewers 会专门从“How Would You Move Mount Fuji?”这样的 interview prep 书籍中学习问题，然后把这些问题拿去问那些从“How Would You Move Mount Fuji?”这类书籍中学会答案的 candidates。当我和比我小十岁的人谈起这些事时，他们觉得这很荒唐——那些问题显然与工作毫无关系，而且，能否很好地回答这些问题，与是否做过一些 interview prep 的 correlated 程度，远远强于与能否胜任工作的 correlated 程度。Hillel Wayne 讨论过如今人们是如何想出 interview questions 的（我自己也在几家不同公司亲眼见过），而除了那些 testing 被认为属于 specialized 的 knowledge 的团队之外，如今的情况似乎也没有那么不同。

到现在，我们已经经历了几十年的 programming interview 潮流，其中每一种事后看来都很荒唐。要么，我们终于找到了 effectively interviewing 的真正秘诀，并且通过推理跨越了那些曾导致过去所有人采用明显不靠谱的时髦 interview techniques 的障碍；要么，我们正身处另一股潮流之中，十年或二十年后的人们回头看时，也会觉得它同样荒唐。

即使完全不了解 interviews 的 effectiveness，从 meta 层面来看，既然人们获取 interview techniques 的方式没有变（从周围声望最高的公司抄来 high-level technique），我认为，如果这不是一股潮流，反而会相当令人惊讶。如果人们正在进行或参考 empirical research，或者曾 independently discovered 哪些做法有效，那么，发现如今的 techniques 并非一股潮流，就不会让我那么惊讶。

受到 [Wesley Aptekar-Cassels 的一条评论](https://twitter.com/danluu/status/925728187375595521)的启发，上一次找工作时，我问过一些人，他们如何检查其 interview process 的 effectiveness，又如何尝试 reduce 流程中的 bias。我得到的回答如下（相似的回答归在一起，按出现频率从高到低排列）：

-   啊？我们不做这个，而且／或者，我们为什么要做这个？
-   我们其实不知道我们的 process 是否 effective
-   我／我们就是知道它管用
-   我／我们并不 biased
-   如果存在 bias，我／我们会注意到的，而它并不存在
-   有人调查过，而且／或者做过一项 study，但告诉我这些的人，从来没有谁能具体说清楚究竟是如何调查的，或者那项 study 的 methodology 是什么

### 附录：training

与大多数 real world problems 一样，当我们试图弄清为什么每年造成七位、八位、甚至九位数损失的 interview-level algorithms bugs 就在那里等着被 fixed 时，并没有一个可以指认的单一“root cause”。相反，这里存在一种由 misaligned incentives 构成的 [hedgehog defense](https://en.wikipedia.org/wiki/Hedgehog_defence)。这其中的另一个方面是，[training 受到的重视严重不足](https://danluu.com/programmer-moneyball/#training-mentorship)。

我们已经讨论过，在我工作过的公司中，除了一家之外，都存在一些 incentive systems，让 developers 觉得自己不该花时间寻找 efficiency gains，即使简单的 calculation 就能表明，有数千万乃至数亿美元的 waste 可以轻易被 fixed。然后，因为这件事并未受到 incentivized，developers 往往缺乏做这类事情的经验，因而觉得陌生，也就觉得它比实际更难。所以，即使一天的工作就能带来 $1m/yr 的 savings 或 profit（根据我的经验，这在大公司相当常见），人们也意识不到这只需要一天，而且只需对 velocity 作出很小的妥协就能完成。解决后一个问题的一种办法是 training，但与那些不在你的 objectives 之内的 efficiency gains 相比，这甚至更难获得认可！

举个例子，我曾写过一篇篇幅适中的 tutorial（4500 words，按 word count 算比本文短，不过如果算上图片，可能更长），介绍如何 find 各种 inefficiencies（如何使用 allocation 或 CPU time profiler，如何为我们使用的 GCs 做 service-specific GC tuning，如何使用我构建的一些 tooling 来 automatically find 你的 JVM 或 container configs 中的 inefficiencies，等等；基本上都是一些 simple 而且往往 high impact、很容易为其编写 runbook 的事情；如果你在 Twitter，可以在 [http://go/easy-perf](http://go/easy-perf) 阅读）。有几位以前遇到 issue 会来找我帮忙的人告诉我，他们已经能够独自 debug 和 fix 一个 issue；我还间接听说，另外几位我不认识的人也能够自己去 increase 他们的 service 的 efficiency。如果我听说的案例竟然达到了这篇 tutorial 帮助过的所有案例的 10%，我都会感到意外，所以我猜它已经帮助了几十位 engineers，而且可能还要多得多。

如果我把一周时间花在做“真正的”工作上，而不是编写 tutorial，我就会有一些具体的、具有 quantifiable value 的成果，可以轻松放进 promo packet 或 performance review。而现在，我得到的却是这么一种模糊的东西，充其量只能算一点“额外加分”。我并不是在特别抱怨这件事——这正是我预期的结果。不过，平均而言，公司得到的就是它们所 incentivize 的东西。如果它们指望 training 来自 developers（而不是雇人制作 training materials，后者获得的经费与 engineering 相比往往少得可怜），却不像重视 dev work 那样重视它，那么 training 就会供给不足。

我相信，在 public educational materials 中，你也能看到 training 处于 under-incentivized 的状态，因为 education 和 training 相对难以 monetizing。如果你想将讲解事物 monetize，有几种 techniques 似乎很有效。如果讲解的内容具有直接而明显的价值，出售定价“很高”的 video course（一门 short course 收费数百乃至数千美元）似乎行得通。做 corporate training 也相当有效：公司出机票请你过去，给一屋子 30 人讲课，而你按每人 $3k 收费。

如果你想触达（并且可能帮助）很多人，把文字放到 internet 上免费提供，效果相当不错，但这样做的 monetization 效果很差。对于 technical topics，我不确定 non-ad-blocking audience 的规模是否真的足够大，能让你通过 ads 来 monetize（而不是通过 pay wall）。

举个例子，Julia Evans 能靠她的 [zine income](https://jvns.ca/blog/2019/10/01/zine-revenue-2019/) 养活自己；她说过，过去两年，这项收入大约为 $100k/yr。corporate training 做得非常好的人，靠一门一两天的 training course 就能赚到这个数目；而根据我听说的 corporate speaking rates，一些收入很高的 tech speakers 只需两次演讲就能赚到这么多。这些 rates 显著高于平均水平，尤其是演讲的收费，不过，既然我们是在与 Julia Evans 作比较，我认为采用高于平均水平的 rate 并不算不公平。

### 附录：misaligned incentive hedgehog defense，第 3 部分

在上面的三个例子中，一个是我在某个团队发现的，在那里，做任何对公司真正有价值的事情，对我个人而言显然都没有任何价值；另外两个是在另一个团队发现的，在那里，做对公司有益的事情，对我个人也有价值，不管具体做的是什么。根据我的经验，这对于大公司的团队来说非常少见，但即使在那个团队，incentive alignment 仍然相当差。有一次，在获得 promotion 和 raise 之后，我 computed 了我的 changes 为公司赚到的钱与我的 raise 之间的 ratio，发现我的 raise 只是我为公司赚到的钱的 0.03%，而这还只计算了容易 quantifiable 且完全无可争议的、对 bottom line 的 impact。我的绝大多数工作都与 tooling 有关，其 value 难以 quantify，而我怀疑它实际比那些 quantifiable impact 的 value 更大，所以，我获得的可能远远不到自己所创造的 marginal value 的 0.01%。而且，这其实还高估了我受到多少 incentivized 才去做这些工作——在 at the margin 的意义上，我强烈怀疑，我做的任何事情对我个人而言都没有价值。在最初的 $10m/yr or maybe $20m/yr 之后，在 performance reviews、promotions、raises 等方面基本上就没有区别了。因为做工作没有 upside，却有一些 downside（可能陷入政治斗争，可能 bring the site down，等等），所以，做超过“足够”程度的工作，对我个人的 marginal return 很可能是 negative。

有些公司经常给员工发放非常丰厚的 out-of-band bonuses，但我做这些工作的那家公司并不常这么做，所以，一旦某人已经做了“足够”的工作，能在 performance review 中拿到最好的 rating，公司就没有什么办法表明它重视额外的工作。从 [mechanism design](https://en.wikipedia.org/wiki/Mechanism_design) 的角度来看，公司基本上是在要求员工：一旦完成了当年“足够”的工作，就停止工作。

所以，即使在这个相较于大多数团队、与公司成功的 aligned 程度较高的团队中，公司的 compensation system 仍然给团队所能达到的 aligned 程度设置了一个很低的 ceiling。

这也以另一种方式发生了。与许多公司的常见做法一样，managers 会获得一笔覆盖整个团队的 raises budget，它主要是 headcount 的 function，然后以 zero-sum 的方式分配给 team members。对每位 team member 来说，不幸的是（至少在 compensation 方面），这个团队几乎全是 productive engineers，这意味着没有人能在这场 zero-sum raise game 中获得特别好的结果。团队的 turnover 很低，因为人们喜欢与优秀的同事共事，但公司却在动用自己手中最大的杠杆之一——compensation——试图让人们离开这个团队，加入那些较不 effective 的团队。

因为这种安排非常普遍，我听说过多家公司的 managers 试图 retain 那些无害却 ineffective 的人，以绕过这个问题。如果你抽象地问某个人，公司是否想 hire 和 retain 那些 ineffective 的人，我猜他们会回答不想。但如果可以说公司想要什么，那么，它想要的就是它所 incentivizes 的东西。

## 原文

When I ask people at trendy big tech companies why algorithms quizzes are mandatory, the most common answer I get is something like "we have so much scale, we can't afford to have someone accidentally write an `O(n^2)` algorithm and bring the site down"[1](https://danluu.com/algorithms-interviews/#fn:A). One thing I find funny about this is, even though a decent fraction of the value I've provided for companies has been solving phone-screen level algorithms problems on the job, I can't pass algorithms interviews! When I say that, people often think I mean that I fail half my interviews or something. It's more than half.

When I wrote a draft blog post of my interview experiences, draft readers panned it as too boring and repetitive because I'd failed too many interviews. I should summarize my failures as a table because no one's going to want to read a 10k word blog post that's just a series of failures, they said (which is good advice; I'm working on a version with a table). I’ve done maybe 40-ish "real" software interviews and passed maybe one or two of them (arguably zero)[2](https://danluu.com/algorithms-interviews/#fn:S).

Let's look at a few examples to make it clear what I mean by "phone-screen level algorithms problem", above.

At one big company I worked for, a team wrote a core library that implemented a resizable array for its own purposes. On each resize that overflowed the array's backing store, the implementation added a constant number of elements and then copied the old array to the newly allocated, slightly larger, array. This is a classic example of how not to [implement a resizable array](https://en.wikipedia.org/wiki/Dynamic_array) since it results in linear time resizing instead of [amortized constant time](https://en.wikipedia.org/wiki/Amortized_analysis) resizing. It's such a classic example that it's often used as the canonical example when demonstrating amortized analysis.

For people who aren't used to big tech company phone screens, typical phone screens that I've received are one of:

-   an "easy" coding/algorithms question, maybe with a "very easy" warm-up question in front.
-   a series of "very easy" coding/algorithms questions,
-   a bunch of trivia (rare for generalist roles, but not uncommon for low-level or performance-related roles)

This array implementation problem is considered to be so easy that it falls into the "very easy" category and is either a warm-up for the "real" phone screen question or is bundled up with a bunch of similarly easy questions. And yet, this resizable array was responsible for roughly 1% of all GC pressure across all JVM code at the company (it was the second largest source of allocations across all code) as well as a significant fraction of CPU. Luckily, the resizable array implementation wasn't used as a generic resizable array and it was only instantiated by a semi-special-purpose wrapper, which is what allowed this to "only" be responsible for 1% of all GC pressure at the company. If asked as an interview question, it's overwhelmingly likely that most members of the team would've implemented this correctly in an interview. My fixing this made my employer more money annually than I've made in my life.

That was the second largest source of allocations, the number one largest source was converting a pair of `long` values to byte arrays in the same core library. It appears that this was done because someone wrote or copy pasted a hash function that took a byte array as input, then modified it to take two inputs by taking two byte arrays and operating on them in sequence, which left the hash function interface as `(byte[], byte[])`. In order to call this function on two longs, they used a handy `long` to `byte[]` conversion function in a widely used utility library. That function, in addition to allocating a `byte[]` and stuffing a `long` into it, also reverses the endianness of the long (the function appears to have been intended to convert `long` values to network byte order).

Unfortunately, switching to a more appropriate hash function would've been a major change, so my fix for this was to change the hash function interface to take a pair of longs instead of a pair of byte arrays and have the hash function do the endianness reversal instead of doing it as a separate step (since the hash function was already shuffling bytes around, this didn't create additional work). Removing these unnecessary allocations made my employer more money annually than I've made in my life.

Finding a constant factor speedup isn't technically an algorithms question, but it's also something you see in algorithms interviews. As a follow-up to an algorithms question, I commonly get asked "can you make this faster?" The answer is to these often involves doing a simple optimization that will result in a constant factor improvement.

A concrete example that I've been asked twice in interviews is: you're storing IDs as ints, but you already have some context in the question that lets you know that the IDs are densely packed, so you can store them as a bitfield instead. The difference between the bitfield interview question and the real-world superfluous array is that the real-world existing solution is so far afield from the expected answer that you probably wouldn’t be asked to find a constant factor speedup. More likely, you would've failed the interview at that point.

To pick an example from another company, the configuration for [BitFunnel](https://danluu.com/bitfunnel-sigir.pdf), a search index used in Bing, is another example of an interview-level algorithms question[3](https://danluu.com/algorithms-interviews/#fn:P).

The full context necessary to describe the solution is a bit much for this blog post, but basically, there's a set of bloom filters that needs to be configured. One way to do this (which I'm told was being done) is to write a black-box optimization function that uses gradient descent to try to find an optimal solution. I'm told this always resulted in some strange properties and the output configuration always resulted in non-idealities which were worked around by making the backing bloom filters less dense, i.e. throwing more resources (and therefore money) at the problem.

To create a more optimized solution, you can observe that the fundamental operation in BitFunnel is equivalent to multiplying probabilities together, so, for any particular configuration, you can just multiply some probabilities together to determine how a configuration will perform. Since the configuration space isn't all that large, you can then put this inside a few for loops and iterate over the space of possible configurations and then pick out the best set of configurations. This isn't quite right because multiplying probabilities assumes a kind of independence that doesn't hold in reality, but that seems to work ok for the same reason that [naive Bayesian spam filtering](https://en.wikipedia.org/wiki/Naive_Bayes_spam_filtering) worked pretty well when it was introduced even though it incorrectly assumes the probability of any two words appearing in an email are independent. And if you want the full solution, you can work out the non-independent details, although that's probably beyond the scope of an interview.

Those are just three examples that came to mind, I run into this kind of thing all the time and could come up with tens of examples off the top of my head, perhaps more than a hundred if I sat down and tried to list every example I've worked on, certainly more than a hundred if I list examples I know of that someone else (or no one) has worked on. Both the examples in this post as well as the ones I haven’t included have these properties:

-   The example could be phrased as an interview question
-   If phrased as an interview question, you'd expect most (and probably) all people on the relevant team to get the right answer in the timeframe of an interview
-   The cost savings from fixing the example is worth more annually than my lifetime earnings to date
-   The example persisted for long enough that it's reasonable to assume that it wouldn't have been discovered otherwise

At the start of this post, we noted that people at big tech companies commonly claim that they have to do algorithms interviews since it's so costly to have inefficiencies at scale. My experience is that these examples are legion at every company I've worked for that does algorithms interviews. Trying to get people to solve algorithms problems on the job by asking algorithms questions in interviews doesn't work.

One reason is that even though big companies try to make sure that the people they hire can solve algorithms puzzles they also incentivize many or most developers to avoid deploying that kind of reasoning to make money.

Of the three solutions for the examples above, two are in production and one isn't. That's about my normal hit rate if I go to a random team with a diff and don't persistently follow up (as opposed to a team that I have reason to believe will be receptive, or a team that's asked for help, or if I keep pestering a team until the fix gets taken).

If you're very cynical, you could argue that it's surprising the success rate is that high. If I go to a random team, it's overwhelmingly likely that efficiency is in neither the team's objectives or their org's objectives. The company is likely to have spent a decent amount of effort incentivizing teams to hit their objectives -- what's the point of having objectives otherwise? Accepting my diff will require them to test, integrate, deploy the change and will create risk (because all deployments have non-zero risk). Basically, I'm asking teams to do some work and take on some risk to do something that's worthless to them. Despite incentives, people will usually take the diff, but they're not very likely to spend a lot of their own spare time trying to find efficiency improvements(and their normal work time will be spent on things that are aligned with the team's objectives)[4](https://danluu.com/algorithms-interviews/#fn:E).

Hypothetically, let's say a company didn't try to ensure that its developers could pass algorithms quizzes but did incentivize developers to use relatively efficient algorithms. I don't think any of the three examples above could have survived, undiscovered, for years nor could they have remained unfixed. Some hypothetical developer working at a company where people profile their code would likely have looked at the hottest items in the profile for the most computationally intensive library at the company. The "trick" for both isn't any kind of algorithms wizardry, it's just looking at all, which is something incentives can fix. The third example is less inevitable since there isn't a standard tool that will tell you to look at the problem. It would also be easy to try to spin the result as some kind of wizardry -- that example formed the core part of a paper that won "best paper award" at the top conference in its field (IR), but the reality is that the "trick" was applying high school math, which means the real trick was having enough time to look at places where high school math might be applicable to find one.

I actually worked at a company that used the strategy of "don't ask algorithms questions in interviews, but do incentivize things that are globally good for the company". During my time there, I only found one single fix that nearly meets the criteria for the examples above (if the company had more scale, it would've met all of the criteria, but due to the company's size, increases in efficiency were worth much less than at big companies -- much more than I was making at the time, but the annual return was still less than my total lifetime earnings to date).

I think the main reason that I only found one near-example is that enough people viewed making the company better as their job, so straightforward high-value fixes tended not exist because systems were usually designed such that they didn't really have easy to spot improvements in the first place. In the rare instances where that wasn't the case, there were enough people who were trying to do the right thing for the company (instead of being forced into obeying local incentives that are quite different from what's globally beneficial to the company) that someone else was probably going to fix the issue before I ever ran into it.

The algorithms/coding part of that company's interview (initial screen plus onsite combined) was easier than the phone screen at major tech companies and we basically didn't do a system design interview.

For a while, we tried an algorithmic onsite interview question that was on the hard side but in the normal range of what you might see in a BigCo phone screen (but still easier than you'd expect to see at an onsite interview). We stopped asking the question because every new grad we interviewed failed the question (we didn't give experienced candidates that kind of question). We simply weren't prestigious enough to get candidates who can easily answer those questions, so it was impossible to hire using [the same trendy hiring filters that everybody else had](https://danluu.com/programmer-moneyball/). In contemporary discussions on interviews, what we did is often called "lowering the bar", but it's unclear to me why we should care how high of a bar someone can jump over when little (and in some cases none) of the job they're being hired to do involves jumping over bars. And, in the cases where you do want them to jump over bars, they're maybe 2" high and can easily be walked over.

When measured on actual productivity, that was the most productive company I've worked for. I believe the reasons for that are cultural and too complex to fully explore in this post, but I think it helped that we didn't filter out perfectly good candidates with algorithms quizzes and assumed people could pick that stuff up on the job if we had a culture of people generally doing the right thing instead of focusing on local objectives.

If other companies want people to solve interview-level algorithms problems on the job perhaps they could try incentivizing people to solve algorithms problems (when relevant). That could be done in addition to or even instead of filtering for people who can whiteboard algorithms problems.

### Appendix: how did we get here?

Way back in the day, interviews often involved "trivia" questions. Modern versions of these might look like the following:

-   What's MSI? MESI? MOESI? MESIF? What's the advantage of MESIF over MOESI?
-   What happens when you throw in a destructor? What if it's C++11? What if a sub-object's destructor that's being called by a top-level destructor throws, which other sub-object destructors will execute? What if you throw during stack unwinding? Under what circumstances would that not cause `std::terminate` to get called?

I heard about this practice back when I was in school and even saw it with some "old school" companies. This was back when Microsoft was the biggest game in town and people who wanted to copy a successful company were likely to copy Microsoft. The most widely read programming blogger at the time (Joel Spolsky) was telling people they need to adopt software practice X because Microsoft was doing it and they couldn't compete without adopting the same practices. For example, in one of the most influential programming blog posts of the era, Joel Spolsky advocates for what he called the Joel test in part by saying that you have to do these things to keep up with companies like Microsoft:

> A score of 12 is perfect, 11 is tolerable, but 10 or lower and you’ve got serious problems. The truth is that most software organizations are running with a score of 2 or 3, and they need _serious_ help, because companies like Microsoft run at 12 full-time.

At the time, popular lore was that Microsoft asked people questions like the following (and I was actually asked one of these brainteasers during my on interview with Microsoft around 2001, along with precisely zero algorithms or coding questions):

-   how would you escape from a blender if you were half an inch tall?
-   why are manhole covers round?
-   a windowless room has 3 lights, each of which is controlled by a switch outside of the room. You are outside the room. You can only enter the room once. How can you determine which switch controls which lightbulb?

Since I was interviewing during the era when this change was happening, I got asked plenty of trivia questions as well plenty of brainteasers (including all of the above brainteasers). Some other questions that aren't technically brainteasers that were popular at the time were [Fermi problems](https://en.wikipedia.org/wiki/Fermi_problem). Another trend at the time was for behavioral interviews and a number of companies I interviewed with had 100% behavioral interviews with zero technical interviews.

Anyway, back then, people needed a rationalization for copying Microsoft-style interviews. When I asked people why they thought brainteasers or Fermi questions were good, the convenient rationalization people told me was usually that they tell you if a candidate can really think, unlike those silly trivia questions, which only tell if you people have memorized some trivia. What we really need to hire are candidates who can really think!

Looking back, people now realize that this wasn't effective and cargo culting Microsoft's every decision won't make you as successful as Microsoft because Microsoft's success came down to a few key things plus network effects, so copying how they interview can't possibly turn you into Microsoft. Instead, it's going to turn you into a company that interviews like Microsoft but isn't in a position to take advantage of the network effects that Microsoft was able to take advantage of.

For interviewees, the process with brainteasers was basically as it is now with algorithms questions, except that you'd review [How Would You Move Mount Fuji](https://www.amazon.com/gp/product/0316778494/ref=as_li_tl?ie=UTF8&camp=1789&creative=9325&creativeASIN=0316778494&linkCode=as2&tag=abroaview-20&linkId=bcc3345d4905164e75b79f2cd2a0f5fb) before interviews instead of [Cracking the Coding Interview](https://www.amazon.com/gp/product/0984782850/ref=as_li_tl?ie=UTF8&camp=1789&creative=9325&creativeASIN=0984782850&linkCode=as2&tag=abroaview-20&linkId=381539624231e0e40b66f2695c925536) to pick up a bunch of brainteaser knowledge that you'll never use on the job instead of algorithms knowledge you'll never use on the job.

Back then, interviewers would learn about questions specifically from interview prep books like "How Would You Move Mount Fuji?" and then ask them to candidates who learned the answers from books like "How Would You Move Mount Fuji?". When I talk to people who are ten years younger than me, they think this is ridiculous -- those questions obviously have nothing to do the job and being able to answer them well is much more strongly correlated with having done some interview prep than being competent at the job. Hillel Wayne has discussed how people come up with interview questions today (and I've also seen it firsthand at a few different companies) and, outside of groups that are testing for knowledge that's considered specialized, it doesn't seem all that different today.

At this point, we've gone through a few decades of programming interview fads, each one of which looks ridiculous in retrospect. Either we've finally found the real secret to interviewing effectively and have reasoned our way past whatever roadblocks were causing everybody in the past to use obviously bogus fad interview techniques, or we're in the middle of another fad, one which will seem equally ridiculous to people looking back a decade or two from now.

Without knowing anything about the effectiveness of interviews, at a meta level, since the way people get interview techniques is the same (crib the high-level technique from the most prestigious company around), I think it would be pretty surprising if this wasn't a fad. I would be less surprised to discover that current techniques were not a fad if people were doing or referring to empirical research or had independently discovered what works.

Inspired by [a comment by Wesley Aptekar-Cassels](https://twitter.com/danluu/status/925728187375595521), the last time I was looking for work, I asked some people how they checked the effectiveness of their interview process and how they tried to reduce bias in their process. The answers I got (grouped together when similar, in decreasing order of frequency were):

-   Huh? We don't do that and/or why would we do that?
-   We don't really know if our process is effective
-   I/we just know that it works
-   I/we aren't biased
-   I/we would notice bias if it existed, which it doesn't
-   Someone looked into it and/or did a study, but no one who tells me this can ever tell me anything concrete about how it was looked into or what the study's methodology was

### Appendix: training

As with most real world problems, when trying to figure out why seven, eight, or even nine figure per year interview-level algorithms bugs are lying around waiting to be fixed, there isn't a single "root cause" you can point to. Instead, there's a kind of [hedgehog defense](https://en.wikipedia.org/wiki/Hedgehog_defence) of misaligned incentives. Another part of this is that [training is woefully underappreciated](https://danluu.com/programmer-moneyball/#training-mentorship).

We've discussed that, at all but one company I've worked for, there are incentive systems in place that cause developers to feel like they shouldn't spend time looking at efficiency gains even when a simple calculation shows that there are tens or hundreds of millions of dollars in waste that could easily be fixed. And then because this isn't incentivized, developers tend to not have experience doing this kind of thing, making it unfamiliar, which makes it feel harder than it is. So even when a day of work could return $1m/yr in savings or profit (quite common at large companies, in my experience), people don't realize that it's only a day of work and could be done with only a small compromise to velocity. One way to solve this latter problem is with training, but that's even harder to get credit for than efficiency gains that aren't in your objectives!

Just for example, I once wrote a moderate length tutorial (4500 words, shorter than this post by word count, though probably longer if you add images) on how to find various inefficiencies (how to use an allocation or CPU time profiler, how to do service-specific GC tuning for the GCs we use, how to use some tooling I built that will automatically find inefficiencies in your JVM or container configs, etc., basically things that are simple and often high impact that it's easy to write a runbook for; if you're at Twitter, you can read this at [http://go/easy-perf](http://go/easy-perf)). I've had a couple people who would've previously come to me for help with an issue tell me that they were able to debug and fix an issue on their own and, secondhand, I heard that a couple other people who I don't know were able to go off and increase the efficiency of their service. I'd be surprised if I’ve heard about even 10% of cases where this tutorial helped someone, so I'd guess that this has helped tens of engineers, and possibly quite a few more.

If I'd spent a week doing "real" work instead of writing a tutorial, I'd have something concrete, with quantifiable value, that I could easily put into a promo packet or performance review. Instead, I have this nebulous thing that, at best, counts as a bit of "extra credit". I'm not complaining about this in particular -- this is exactly the outcome I expected. But, on average, companies get what they incentivize. If they expect training to come from developers (as opposed to hiring people to produce training materials, which tends to be very poorly funded compared to engineering) but don't value it as much as they value dev work, then there's going to be a shortage of training.

I believe you can also see training under-incentivized in public educational materials due to the relative difficulty of monetizing education and training. If you want to monetize explaining things, there are a few techniques that seem to work very well. If it's something that's directly obviously valuable, selling a video course that's priced "very high" (hundreds or thousands of dollars for a short course) seems to work. Doing corporate training, where companies fly you in to talk to a room of 30 people and you charge $3k per head also works pretty well.

If you want to reach (and potentially help) a lot of people, putting text on the internet and giving it away works pretty well, but monetization for that works poorly. For technical topics, I'm not sure the non-ad-blocking audience is really large enough to monetize via ads (as opposed to a pay wall).

Just for example, Julia Evans can support herself from her [zine income](https://jvns.ca/blog/2019/10/01/zine-revenue-2019/), which she's said has brought in roughly $100k/yr for the past two years. Someone who does very well in corporate training can pull that in with a one or two day training course and, from what I've heard of corporate speaking rates, some highly paid tech speakers can pull that in with two engagements. Those are significantly above average rates, especially for speaking engagements, but since we're comparing to Julia Evans, I don't think it's unfair to use an above average rate.

### Appendix: misaligned incentive hedgehog defense, part 3

Of the three examples above, I found one on a team where it was clearly worth zero to me to do anything that was actually valuable to the company and the other two on a team where it valuable to me to do things that were good for the company, regardless of what they were. In my experience, that's very unusual for a team at a big company, but even on that team, incentive alignment was still quite poor. At one point, after getting a promotion and a raise, I computed the ratio of the amount of money my changes made the company vs. my raise and found that my raise was 0.03% of the money that I made the company, only counting easily quantifiable and totally indisputable impact to the bottom line. The vast majority of my work was related to tooling that had a difficult to quantify value that I suspect was actually larger than the value of the quantifiable impact, so I probably received well under 0.01% of the marginal value I was producing. And that's really an overestimate of how much I was incentivized I was to do the work -- at the margin, I strongly suspect that anything I did was worth zero to me. After the first $10m/yr or maybe $20m/yr, there's basically no difference in terms of performance reviews, promotions, raises, etc. Because there was no upside to doing work and there's some downside (could get into a political fight, could bring the site down, etc.), the marginal return to me of doing more than "enough" work was probably negative.

Some companies will give very large out-of-band bonuses to people regularly, but that work wasn't for a company that does a lot of that, so there's nothing the company could do to indicate that it valued additional work once someone did "enough" work to get the best possible rating on a performance review. From a [mechanism design](https://en.wikipedia.org/wiki/Mechanism_design) point of view, the company was basically asking employees to stop working once they did "enough" work for the year.

So even on this team, which was relatively well aligned with the company's success compared to most teams, the company's compensation system imposed a low ceiling on how well the team could be aligned.

This also happened in another way. As is common at a lot of companies, managers were given a team-wide budget for raises that was mainly a function of headcount, that was then doled out to team members in a zero-sum way. Unfortunately for each team member (at least in terms of compensation), the team pretty much only had productive engineers, meaning that no one was going to do particularly well in the zero-sum raise game. The team had very low turnover because people like working with good co-workers, but the company was applying one the biggest levers it has, compensation, to try to get people to leave the team and join less effective teams.

Because this is such a common setup, I've heard of managers at multiple companies who try to retain people who are harmless but ineffective to try to work around this problem. If you were to ask someone, abstractly, if the company wants to hire and retain people who are ineffective, I suspect they'd tell you no. But insofar as a company can be said to want anything, it wants what it incentivizes.
