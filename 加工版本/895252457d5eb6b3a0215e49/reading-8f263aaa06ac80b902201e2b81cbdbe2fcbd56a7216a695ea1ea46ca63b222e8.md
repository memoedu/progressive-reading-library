# 任何时候，停止思考都行不通｜There's no point at which turning your brain off will work

---

## 正文

2025 年初，我开始看到一些人在使用 LLMs 时不再动脑。他们会让一个 LLM 执行某个 action（summarize text、write 一些 code 等），然后直接假定它 worked[1](https://danluu.com/brain-off/#fn:N)[2](https://danluu.com/brain-off/#fn:L)。2025 年初，这样做通常并不 work，结果也往往相当可笑。

随着 LLMs 变得更好，我看到这种情况越来越多。有时，人们会试着让 LLM 为他们 write 一些 code，然后基本上就直接假定它 works[3](https://danluu.com/brain-off/#fn:H)。有时会有一个 human in the loop，而如果那东西不 work，他们就会让 LLM 找出 problem 并 solve 它。Niklas Gruhn [把这种做法的一些变体称为充当 meat proxy](https://gruhn.me/blog/2026-08-03/)。[4](https://danluu.com/brain-off/#fn:G)

充当 for loop meat proxy 比 2025 年初更管用了，我试过的、以这种方式 developed 的 software，有时居然还算 works。虽然还没有好到让我想用，也算不上 successful，但在 2026 年 9 月，充当 meat proxy 居然如此 effective，还是让我印象深刻。可以想象，LLMs 会进步到足以让不动脑的 meat-proxy development 在可预见的未来 produces [average](https://danluu.com/everything-is-broken/) [quality](https://danluu.com/nothing-works/) 的 [software](https://danluu.com/bug-blind/)，甚至 LLMs 会进步到不需要 human in the loop 也能 produce 出色的 software。

假设这真的发生了。company 还有什么理由 employ 这个 meat proxy？company 完全可以直接让 LLM 在 loop 中 run，然后 lay off 那名 employee。这种 methodology 在任何阶段都不会对 employee 有利[5](https://danluu.com/brain-off/#fn:F)。

_感谢 Max Bittker、Yossi Kreinin、Luke Burton、Thomas Dullien、Dennis Snell、Milosz Danczak、Peter Geoghegan 和 Jamie Brandon 提供意见、纠正与讨论。_

2.  Luke Burton 留下了这段评论：

    我认为，能够这样做，说明正在做的 work 属于什么 type，其意义比人们想的更大。只有当 task 的 value 相当 low、能够承受 fail 时，我才会把这样的 work 放着不管。

    对于 high value tasks，LLM 对它们 one-shotting 的 probability 要低得多。我必须承担 QA、engineering manager 和 architect 的 role。这个 while loop 常常让人感觉像在赶工。我总有一种挥之不去的疑虑，觉得自己漏掉了什么，而且一个 badly specified prompt 可能导致一个需要被 undone 的 architectural choice。

    另一个观察是，high throughput 让我提高了自己对所 ship 内容的标准。以前我可能会 shipped 一个 MVP，然后 iterated；现在我会让 agents 进行 polish 并 explore edge cases，远远超出我平时的程度，而除非得到 prompted，否则它们总是做不到这些。

    这也许会让一些人产生不舒服的想法，但如果 agents 这么轻松就能搞定，那么我想问那些 meat proxies：1) 有没有可能，你们本来就已经有点在混日子了？2) 为什么不 pushing agents 去做远远超出它们能轻松 tackle 的 tasks？

    我们一直在做一件你可能会以为极其适合“hands off” automation 的事，也就是 converting \[已隐去\]，使其用 Bazel 来 build。即使用了 agents，这也花了我们好几个月。这个 task 中埋着许多 intangible、hard-to-specify requirements，让 agents 把握好分寸意味着要持续 supervision。给它们一个类似“把这个 convert 为 Bazel”的 prompt，然后就放手不管，至少还要再过好几个月才可能做到，也许要几年，也许永远也做不到？这里涉及的 decision points 太多，unknown unknowns 也太多。

    比如，这种情景有多常见：你遇到一些 code，不清楚它为什么这样 functions，但知道原因会实质性地改变你应该采取的 course of action。也许它会改变 dev experience，也许你不知道是否已有某个 customer 开始使用它，诸如此类。面对这种情况，你究竟要怎样靠 meat proxy 混过去？

    反过来，你和某位 stakeholder 一起 review 你做过的东西，对方却说：“哦，那个？那部分并不需要，我们甚至早就不用它了。”围绕某个 element 需要被 preserved 这一 false assumption，究竟作出了哪些 decisions？

    \[Luke 的评论结束，下面是我的评论\]。当 agent 遇到 out of distribution 的东西时，你需要作出 decisions 这一点会更加明显。一个程度较轻的例子[是我们比较 agents 使用不同 programming languages 的表现时](https://danluu.com/pl-tokens/)，agents 在 obscure languages 上的表现差得多，虽然它们也在这些 languages 上经过 trained，只是没有在 mainstream languages 上那么多。一个更加 out of distirbution 的例子是尝试玩 board game（尤其是现代 game，而不是 chess 或 go 之类的 classical games）。一般而言，对于 Lost Cities 或 Dominion 这样的 game，SOTA model 和 harness 的表现不如一个 board games 水平尚可、但从未玩过这款 game 的人。如果你向 agent 询问这款 game，它知道许多有关这款 game 的信息，也能说出一些话，在不懂这款 game 的人听来似乎有道理，但任何懂这款 game 的人都能看出明显不对。我最近和一位新 player 玩了几局 Dominion，对方以为用 ChatGPT 帮助理解这款 game，会有助于学习和玩这款 game。我对此相当怀疑，并提出这很可能让对方玩得更差（AFAICT，确实如此）。玩了几局之后，我看了看 ChatGPT 告诉对方的内容，大概一半对、一半错，但错误的那一半，反而把对方引向了比一个通常很会玩 games、会运用 general game playing heurisitics 的人更糟的境地。BTW，公开信息已经足够多，所以我认为，一个从来没玩过的人，如果决定花上比如五个小时，阅读有关这款 game 的资料、看看有哪些信息，只要做一些预先阅读，就很容易达到这款 game 的 [99%-ile or above](https://danluu.com/p95-skill/)（如果允许边玩边查阅参考资料，也许只要 30 分钟）。我觉得那样会失去乐趣，也不建议任何人这么做，但考虑到 agents 可以进行 searches、query APIs 等，这就说明了今天的人与 agent 在面对 out of distribution problem 时的差距。说不定下一次重大 model release 就会扭转这一局面，但今天的差距仍然相当大。

    总之，我在这里想说的是，即使在做 coding tasks 时，你也经常会碰到 out of distribution questions，而 agent 在这些问题上的表现远逊于一个正常的人。如果你今天想得到好的 overall result，就需要留意这些情况，并加以处理。

3.  如果有人直接假定事情会 work，可能出什么岔子，可以看[这个案例](https://danluu.com/pl-tokens/#fn:H)，其中 agents（有时）会 heavily overfit to tests；或者看[这个案例](https://danluu.com/benchpocalypse/)，其中 agents 会 heavily overfit to a metric。我听过一种 theory，认为 agents 在 eval-shaped problems 上会更多地 cheating。我不确定这是否属实，但即便假定它属实，也假定我在工作和 personal projects 中，即使不 running evals，也倾向于比大多数人 create 更多 eval-shaped instructions，我仍然见过其他人并没有 create 很 eval-shaped 的东西，却在 write 一些 instructions、让 agents 在没有 supervision 的情况下放任发挥时，遇到同样的 problem（我觉得实际上还更严重）。（我曾在 minimal supervision 下这样做并取得一些成功，但前提是对 agents 作了相当多的限制，这使得事情比大多数人似乎在做的更加 eval-shaped。）

    当我试用那些把思考 outsourced 给 LLM 的人做出的 software 时，software 都存在严重 issues。有人告诉我这种做法 works，但那些 software 往往[处于这样一种水平：按照这里讨论的 standard，我会说它并不 work](https://danluu.com/bug-blind/)。

    举个可笑的例子，我看到一位 programming 领域的意见领袖在 Twitter 上宣称，programming 已经 solved，因为他们尝试了各种（programming）fields 的 projects，而 Claude 能像 expert 一样 solve 所有 problems。我真的去看了他们的 GitHub，我看过的所有 examples（数量 non-zero）要么不 work，要么 worked 得很糟糕。其实，我是在制作 board game AIs、寻找能与我的 AIs 对战的现成 AIs 时偶然碰到这件事的。他们的 AI 是一个 AlphaZero-style bot，其实力甚至不如这样得到的结果：用 prompt 让 LLM write 一个 simple minimax heuristic bot，然后让 LLM 在 loop 中 run 一会儿，tweak 那个 heuristic scoring（对于这款 game，这种 bot 本应被一个 mediocre AlphaZero-style bot 打得落花流水）。

    再举一个可笑的例子，沿着 standard flow（某个真正 commercial product 的流程）操作，会让你进入一个 infinite loop，虽然 technically 可以 escape（大多数 programmers 大概能想出如何 escape），但 typical user（这个 software 并不是面向 programmers 的）大概无法 escape，也就无法真正使用 software 的 main functionality。

    BTW，我也为自己制作了大量“对我够用”这种 quality 的 software；如果它们是真正的 product，我会评价为“基本上不 work”，所以我不认为 software 基本上不 work 就天然不好（例如，我让 agent build 的、用来 speed up 我电脑上 ripgrep searches 的[这里讨论的 regex engine](https://danluu.com/no-slow/)，或者我让 agent build 的、用来 speed up 某些 projects 上 agent iteration loop 的[这个 Rust interpreter](https://github.com/danluu/rust-interpreter)，这两个你都不应该使用）。[我在这里也提到过](https://danluu.com/ai-coding/)，让 agent 在 loop 中 run 来做 data analysis，producing 完全 incorrect results，再由我指导它 fix up，我觉得这相当有价值。但是，为自己制作能满足狭窄 use case 的 software，明知只要“用法不对”它就不 work，或者 producing 自己知道 incorrect、然后会 fix up 的成果，与 write 一堆不 work 的 software 后就宣称 programming 已经 solved，或者同样把这种 quality 的东西放进 commercial product，是有区别的。

    Thomas Dullien（又名 Halvarflake）读过这篇文章的草稿后，我问这组简短的想法是否值得发表，他说：“好文章！对，发出来，因为每当我说‘LLMs 并不能 solve 所有 programming problems’时，人们看我的眼神都像在看疯子，而我看他们也一样。”巧的是，在我完成这份草稿后，我看到 Gary Bernhardt 发推说：“把实际的 agent output 和我在这里看到的人们对它们的说法放在一起对比，真是太超现实了。在日常 changes 中，我的 reviews 经常把 diff 削减到 original size 的 25%。一大堆 useless tests；疑神疑鬼；inverted logic。然后我看 Twitter，上面说‘coding 已经 solved’。”随后又说：“自从我发那条推文以来的一个小时里就有个例子：我让它 fix 一些 DATABASE\_URL management。它直接在 NPM scripts 里面 added 了 `if`s，还在 CI 中 added 了一次 conditional node invocation，running 一个 inline JS script。diff 里大约有 20 个 hunks。在我 corrected 它之后：+0 lines，+1 word。”

    我想，任何对 software 抱有 Thomas 或 Gary 那种态度的人，都已经有这种感受一段时间了。有一阵子，我曾怀疑，那些对 LLM productivity 做出最夸张宣称的人中，是不是有很多人通过某种方式从 LLMs 中获得了远超我所认识的任何人的价值，但[正如我们在这里讨论过的](https://danluu.com/bug-blind/)，随着更多证据出现，我越来越确信，这只是人们在自欺欺人。我喜欢那个 board game example 的一点在于，你可以直接 measure 最终的 AI 到底有多好。在极端情况下，你可能会遇到某种 rock-paper-scissors 情形，观察到 `A > B > C > A`，但如果某个东西只是 AI 胡言乱语，那么从 objective 的角度来看，这一点就相当明显。commercial software 也是如此，你可以与公司里的人交谈，或者亲自查看 data，从而发现 conversion rate 很差、churn 非常高、user satisfaction surveys 显示 dissatisfaction 的程度非常高，等等。

    如果你还想看一个荒唐、但没那么侧重 software 的例子：最近有篇文章，有人发给我一份 ChatGPT fact check，还居高临下地评论了我的错误，但我当然早就已经用 ChatGPT 对那篇文章做过 fact checked，并修正了真正的错误，所以剩下的全是 ChatGPT 的错误。总的来说，我发现，对于这类事情（针对任何人的内容，而不只是我的），false positive rate（precision）很差，而 false negative rate（recall）也很一般。如果你稍微动动脑子，我认为做这些 fact checks 仍然值得，因为我扫一遍包含大量 false positives 的列表，仍然比再请一个人阅读文章草稿省事得多。

    再举一个荒唐的例子，[tpatcek 最近提到过一个话题](https://sockpuppet.org/blog/2026/09/17/how-to-write-with-an-llm/)：你不应该因为 LLM 的奉承，就觉得自己做的某项工作很好（他特别指的是写作，但其他种类的工作也一样）。如果你抱有上面提到的 Gary 或 Halvarflake 的态度，这自然不言而喻，但有些人不愿意知道这一点（我觉得，你得真的刻意回避，才会没注意到这一点），因为我看到有人拿 LLM 对自己工作的某种吹捧，来证明它有多么出色。也许有一天，LLM 说你的作品是天才之作，或者说你的 reasoning thoroughly demolishes 了与你争论的那个人的 reasoning，会是有意义的；但今天我们离那种程度还差得很远（就 accuracy 而言；这并不是在预测时间上还要多久），以至于有人拿 LLM 对自己作品或 reasoning 的吹捧文章来证明其优秀，主要说明他停止了思考，也相当强烈地表明，那项作品或 reasoning 很差。

    也许还有另一种 argument，大意是：“由于 inertia，在 LLMs 已经好到足以 replace programmers 之后，还会有一段时间，你可以当 meat proxy 而蒙混过关。”现实地看，考虑到公司裁员的热情，这似乎也恰好与事实相反，因为如果你的目标是尽可能少干活，那么这么做的最佳时机是在过去。如果你跟大公司的人聊过这类事情，就会听到各种故事：有人真的完全不来上班（也没有远程工作），而公司要花几个月甚至几年才把他们解雇。过去这几年，我没再听到那么多这样的故事，但我以前所在的一个团队就有人这么干过，而且，如果我没记错的话（我以前知道确切数字，但现在不确定自己是否记对了），从他决定退休、觉得只要不再来上班就能多领几次工资开始，公司花了六个月才把他解雇（这是疫情之前，发生在一家不实行远程办公的公司）。我有个朋友在另一家公司，也遇到有人这么做，那里花了两年才把人解雇。很长一段时间里，甚至没人启动解雇程序，之后又经历了缓慢逐级加重警告的过程，最后才终于把人开掉。我的朋友说，经理说过，如果那个人想钻制度的空子，只要开始来公司，稍微装作工作一下，就会重新开始计时，解雇他还得花更长时间。按当时的情况，如果他是个有本事的摸鱼者，就能无限期地保住工作。我不确定公司为什么曾经会处于这种状态，但公司似乎正在以 AI 为借口摆脱这种状态，这使得现在和很可能即将到来的未来，成为很长时间以来最不适合既不付出任何努力、也不提供任何价值，却还想保住工作的时期。毫无疑问，有些公司仍会让你这样蒙混过关，但如果你想什么也不干就领工资，你早就可以在比近期未来更容易做到这一点的环境里，持续这样做很长时间了（也许别做得那么彻底，真的一次班也不去上）。

## 原文

In early 2025, I started seeing people turn off their brain as they use LLMs[1](https://danluu.com/brain-off/#fn:N). They would have an LLM take an action (summarize text, write some code, etc.), and just assume that it worked[2](https://danluu.com/brain-off/#fn:L). This generally didn't work in early 2025 and the result was often quite silly.

As LLMs have gotten better, I've seen more of this. Sometimes, people will try to get the LLM to write some code for them and basically just assume that it works[3](https://danluu.com/brain-off/#fn:H). Sometimes there's a human in the loop and, if the thing doesn't work, they'll ask the LLM to figure out the problem and solve it. Niklas Gruhn [calls some variants of doing this being a meat proxy](https://gruhn.me/blog/2026-08-03/).[4](https://danluu.com/brain-off/#fn:G)

Being a for loop meat proxy works better than it did in early 2025 and the software I've tried that's developed like this sometimes actually sort of works. Not well enough that I'd want to use it or that it's successful, but I'm impressed at how effective being a meat proxy is in September 2026. You could imagine LLMs improving enough that brain-off meat-proxy development produces [average](https://danluu.com/everything-is-broken/) [quality](https://danluu.com/nothing-works/) [software](https://danluu.com/bug-blind/) in the foreseeable future, or even that LLMs improve enough that they produce great software without a human in the loop.

Let's say that happens. What reason is there for the company to employ the meat proxy? The company can just run the LLM in a loop and lay off the employee. There's no point at which this methodology will work for the employee[5](https://danluu.com/brain-off/#fn:F).

1.  I've been having this thought for about a year and a half now. I have it more frequently now as LLMs get better and I see people spend more time turning their brain off when interacting with LLMs. [\[return\]](https://danluu.com/brain-off/#fnref:N)
2.  Luke Burton had this comment:

    I think being able to do this says more about the type of work being done than people think. I will only walk away from work like this if the task is quite low value, if it can afford to fail.

    For high value tasks, the probability of an LLM one-shotting them is much lower. I have to assume the role of QA, engineering manager, and architect. The while loop often feels like a crunch time. I feel the nagging suspicion I've missed something and that a badly specified prompt could result in an architectural choice that needs to be undone.

    Another observation is that the high throughput causes me to raise my own bar for what I ship. Whereas before I might have shipped an MVP and iterated, now I have agents polish and explore edge cases well beyond my norm, which they invariably fail to do unless prompted.

    Maybe it raises some uncomfortable thoughts for people, but my question for the meat proxies out there if the agents are nailing it so easily: 1) is it possible you've been coasting a bit already? 2) why aren't you pushing agents well beyond tasks they can tackle so easily?

    We've been doing something you'd think is extremely amenable to "hands off" automation, which is converting \[redacted\] to build with Bazel. It has taken us months even with agents. There's a lot of intangible, hard-to-specify requirements buried inside this task and having agents walk that line means constant supervision. Giving them a prompt like "convert this to Bazel" and walking away is at minimum many months in the future, maybe years, and maybe not ever? There are too many decision points, and too many unknown unknowns involved.

    Like how often does this scenario come up: you encounter some code and it's not clear why it functions this way, but knowing that materially changes what course of action you should take. Maybe it changes the dev experience, maybe you don't know if some customer has started using it, so on and so forth. How exactly do you meat proxy your way through that?

    Conversely you review what you've done with some stakeholder and they say "oh that? that part of it wasn't needed, we aren't even using that any more". What kind of decisions got made around the false assumption that a certain element needed to be preserved?

    \[End of Luke's comment, comment from me\]. A place where it's more obvious you need to make decisions is when the agent runs into something that's out of distribution. A minor version of this [was when we compared how well agents use different programming languages](https://danluu.com/pl-tokens/) and agents were much worse at obscure languages, which they're trained on, just not as much as with mainstream languages. A more out of distirbution example is if you try to play a board game (especially a modern game and not one of the classical games like chess or go). In general, for a game like Lost Cities or Dominion, a SOTA model and harness is worse than a human who's reasonable at board games but has never played the game before. If you ask the agent about the game, it knows a lot about the game and can say things that sound like they make sense to someone who doesn't understand the game, but are obviously wrong to anyone who does understand the game. I recently played some Dominion with a new player who thought that using ChatGPT to help them understand the game would help them learn and play the game. I was quite skeptical of this and suggested that it will probably make them worse (which, AFAICT, it did). After playing a few games, I looked at what ChatGPT was telling them, and it was maybe half right and half wrong, but the half wrong parts were steering them to a worse place than someone who generally plays games well and uses general game playing heurisitics would do. BTW, there's enough public information out there that I think that someone who'd never played before, but decided to spend, say, five hours reading about the game and seeing what information is out there, could easily be [99%-ile or above](https://danluu.com/p95-skill/) at the game if they did some pre-reading (maybe 30 minutes if using references while playing is allowed). I think that would be un-fun and I wouldn't recommend that anyone do it, but given that agents can do searches, query APIs, etc., it shows you the gap between a human and an agent today when approaching an out of distribution problem. For all I know, the next big model release will flip this around, but the gap is still fairly large today.

    Anyway, my point here is that, even when doing coding tasks, you often run into out of distribution questions where the agent behaves very poorly compared to a reasonable human being. If you want a good overall result today, you need to notice these cases and deal with them.

Some examples of what goes wrong when someone just assumes things will work are [this case](https://danluu.com/pl-tokens/#fn:H), where agents (sometimes) heavily overfit to tests or [this case](https://danluu.com/benchpocalypse/) where agents heavily overfit to a metric. I've heard a theory that agents do more cheating on eval-shaped problems. I'm not sure that's true, but even assuming it's true and that, in my work and personal projects, I tend to create more eval-shaped instructions than most people even when not running evals, I've seen other people who don't create very eval-shaped things run into the same problem (I think actually more severely) when they write some instructions and let agents go wild without supervision (I've had luck doing that with minimal supervision, but only by fencing the agents in quite a bit, which makes the thing more eval-shaped than what most people seem to do).

    When I try software from people who've outsourced thinking to the LLM, the software has serious issues. I've had people tell me this kind of thing works, but the software is often [at a level where I would say that it doesn't work according to the standard discussed here](https://danluu.com/bug-blind/).

    To pick a silly example, I saw that a programming thought leader declared on Twitter that programming is solved because they tried projects in all sorts of (programming) fields and Claude was able to solve all the problems as well as an expert. I went and actually looked at their GitHub and all of the examples I looked at (a non-zero number) either didn't work or worked very badly. I actually ran across this when I was making board game AIs and was looking for existing AIs for my AIs to play against. Their AI was an AlphaZero-style bot that was weaker than what you get if you prompt an LLM to write a simple minimax heuristic bot and then have the LLM run in a loop for a bit to tweak the heuristic scoring (which, for this game, should get demolished by a mediocre AlphaZero-style bot).

    To pick another silly example, following the standard flow (of a real commercial product) put you into an infinite loop where it was technically possible to escape (most programmers could probably figure out how to escape) but a typical user (for this software that wasn't aimed at programmers) was probably not going to be able to escape and actually use the main functionality of the software.

    BTW, I make plenty of software for myself that's "works for me" quality software that I would rate as "basically doesn't work" if it was an actual product, so I don't think it's inherently bad when software basically doesn't work (for example, the [regex engine discussed here](https://danluu.com/no-slow/) I had an agent build to speed up ripgrep searches on my computer or [this Rust interpreter](https://github.com/danluu/rust-interpreter) I had an agent build to speed up the agent iteration loop on some projects, both of which you shouldn't use). [I also mentioned here](https://danluu.com/ai-coding/) that I find it quite valuable to have an agent run in a loop for data analysis, producing completely incorrect results that I then direct it to fix up. But there's a difference between making software for yourself that works for your narrow use case that you know doesn't work if you "hold it wrong" or producing work that you know is incorrect that you fix up, and declaring that programming is solved after writing a bunch of software that doesn't work, or likewise putting something of that quality into a commercial product.

    On reading a draft of this post, when I asked if this short set of thoughts was worth publishing, Thomas Dullien (a.k.a. Halvarflake) said, "Good post! Yes, publish it, because whenever I say "LLMs don't solve all programming problems" ppl look at me like I'm crazy, and I look at them like they are". And, coincidentally, after I finished this draft, I saw that Gary Bernhardt tweeted, "It's so surreal to contrast actual agent output with the things that I see people say about them here. In everyday changes, my reviews often cut the diff to 25% of its original size. Tons of useless tests; paranoia; inverted logic. Then I read Twitter and 'coding is solved'", and then "An example in the hour since I tweeted that: I told it to fix some DATABASE\_URL management. It added `if`s directly inside NPM scripts, and a conditional node invocation in CI running an inline JS script. About 20 hunks in the diff. After I corrected it: +0 lines, +1 word."

    I think anyone with Thomas's attitude or Gary's attitude towards software will have felt this way for some time. For a while, I wondered if a lot of the folks making the biggest claims about LLM productivity were somehow getting much more value out of LLMs than I've seen from anyone I know, but [as we discussed here](https://danluu.com/bug-blind/), as more evidence has come in, I've gotten more sure that it's just that people are fooling themselves. One thing I like about the board game example is that you can just measure how good the resultant AI is. At the limit, you can have some kind of rock-paper-scissors situation where you observe `A > B > C > A` but, if something is just AI nonsense, this is pretty obvious in an objective way. And likewise for commercial software, where you can talk to people at the company or look at the data yourself and find out that conversion rate is poor, churn is very high, user satisfaction surveys report very high levels of dissatisfaction, etc.

    If you want another silly but less software-focused example, on a recent post, someone sent me a ChatGPT fact check with a condescending comment about my errors, but of course I'd already fact checked the post with ChatGPT and fixed the actual errors, so all that was left was ChatGPT's errors. In general, I've found that, for this kind of thing (for anyone's content, not just mine), the false positive rate (precision) is poor, and the false negative rate (recall) is mediocre. If you use your brain a bit, I think it's still worth it run these fact checks because my skilling a list with a bunch of false positives is still much cheaper than asking an additional human to read a draft post.

    For yet another silly example, [there's a topic tpatcek recently mentioned](https://sockpuppet.org/blog/2026/09/17/how-to-write-with-an-llm/), that you shouldn't let yourself be flattered by an LLM into thinking that some piece of work you did was good (he was referring to writing in particular, but this goes for other kinds of work as well). If you have Gary's attitude or Halvarflake's attitude mentioned above, this goes without saying, but some people don't want to know this (I think you'd have to really be trying to avoid noticing this to not know this) as I see people use some kind of LLM puffing up of their own work to justify how great it is. There may come a day when an LLM saying that your work is genius or your reasoning thoroughly demolishes the reasoning of the person you're arguing against is meaningful, but we're far enough from that today (in terms of accuracy; this is not a prediction on how far away it is in terms of time) that someone using an LLM's puff piece about their own work or reasoning to justify its goodness is mostly a sign that they turned their brain off and a fairly strong signal that the work or reasoning is poor.

Maybe this works for founders, large shareholders, etc., but when I've personally seen people do this so far, it's been employees at work or people working on personal projects who are making a statement about how well this works, software is solved, etc., implying something about how software is a solved problem for employed software engineers.

    Another argument might be something like "we're all going to be obsolete now, so why not just give up?", but this argument seems backwards to me unless it's guaranteed that human obsolescence is very close. If you're financially ready to retire, you can just turn your brain off, but you could always do that and there's always been plenty of people who've mailed it in and not done much of anything. If you're not ready to retire, you can do something that will make you more money, which will probably not involve turning your brain off. In the non-obsolescence future, there's no particular need to rush to make money, but if you think obsolescence is coming soon and you need to make money, then now's the time to rush to make money and do the opposite of turning your brain off. There's a line of reasoning that's something like "why bother working hard or doing the right thing, you don't get paid more anyway", which seems quite wrong to me, in that I've gotten raises, gotten bonuses, etc. from going and finding a problems and fixing them and this is also the experience of my friends, unless they're in a very dysfunctional place that doesn't reward doing good work at all, in which case they leave and go somewhere else.

    Maybe there's another argument that's something like "due to inertia, there will be a window where you can get away with being a meat proxy after LLMs are good enough to replace programmers". Realistically, with how excited companies are to lay people, this also seems to be the opposite of correct, in that if your goal is to do as little work as possible, the best time to do this was in the past. If you've talked to people at big companies about this kind of thing, there are all sorts of stories about people literally not showing up to work at all (and also not working remotely) and it taking months to years to fire them. I haven't heard as many of these stories for the last couple years, but someone on a team I was on did this and, IIRC (I used to know the number, but I'm not I'm not sure I'm remembering it correctly now) it took six months to fire them after they decided to retire and figured they could collect a few more paychecks if they just stop showing up (this was pre-pandemic at a non-remote company). A friend of mine at a different company had someone do this where it took two years. No one even started the process of firing them for quite some time, and then there was some slow process of escalating warnings before they were finally fried. My friend said that the manager said that, had they wanted to game the system and just started coming in and pretending to work a bit, this would've started a new clock and it would've taken even longer to fire them. If they were a competent slacker, they could've kept the job indefinitely as conditions were at the time. I'm not sure why companies were ever in this state, but companies seem be using AI as an excuse to move away from this state, making now and the likely near future the worst time in a very long time to try to hold down a job while not putting any effort and not providing any value. No doubt there will be some companies where you can get away with this, but if you wanted to do nothing and collect a pay check, you could've been doing that for a long time (maybe don't go full monty and literally never show up to work at all) in an environment where it's easier than it will be in the near future.
