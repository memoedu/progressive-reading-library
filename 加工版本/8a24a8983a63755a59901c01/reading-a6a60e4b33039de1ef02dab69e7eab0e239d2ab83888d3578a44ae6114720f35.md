## 核心洞察

一、传统行业仍在追问如何起步：过去两年已有 AI agent、Multi-agent、软件工程 agent 等话题的分享，许多传统行业朋友仍在问：普通人如何用 AI 在自己的行业里发挥作用？如果想用 AI 改造传统行业，应该从哪些思路入手？

三、聊天工具好用且当时免费：ChatGPT 及其他由大语言模型包装成的 chatbot 都是很好的工具，在视频所述的当时都是免费的。

四、清楚提问与提供上下文缺一不可：用好聊天工具首先要学会提问：用正确、条理清晰的 prompt 描述问题，同时提供与问题相关的 context，也就是上下文。两个要素缺一不可。
[[#^pr-0b6ac5cf8044|正文跳转]]

五、不能指望模型凭空回答：无论使用哪种模型，都要通过实际使用摸清能力边界，不能把它当成全知全能的人。模型能回答的问题也受到人类知识和信息来源的限制；不说明人物身份、关系和年龄，就问两人相差几岁，是缺少信息的错误提问。预测下周彩票号码、地球或太阳系何时爆炸、太阳何时被黑洞吸走等问题，违反因果律或超出模型乃至人类的能力范围；模型可能给出模糊或错误的回答，也可能明确表示无法回答。
[[#^pr-fe082dc2d326|正文跳转]]

六、比较数字应按方法而非猜测：数值比较体现了直接猜答案与按方法计算的区别：只把两个数字念一遍，普通人也可能记不住、只能猜，模型也不应该靠猜。正常比较应先看整数部分位数，再从高位逐位比较；当前位相同就继续，不同就据此判断大小，整数部分无法区分时再比较小数部分。例子中的 116854.153 和 16421.27，与随后口述的“两者都是五位数”“第三位分别是 8 和 4”并不一致。
[[#^pr-200067d1699e|正文跳转]]

七、数值比较错误曾被反复讨论：过去几年，人们经常讨论模型比较“8.9 和 8:11 哪个大”时容易答错的问题，这是数值比较中“直接猜答案”与“按方法计算”之别的一个引例。
[[#^pr-200067d1699e|正文跳转]]

八、直接比较数字也可能高概率出错：比较 116854.153 和 16421.27 时，我认为模型直接回答也有很大概率出错。
[[#^pr-200067d1699e|正文跳转]]

九、可编程解决的问题交给程序：对数值、计算、分析等能够用编程可靠解决的问题，要让模型使用程序，采用 agentic 方法。提供问题、编程要求和可用工具后，让模型编写 Python 程序，通过 Terminal 运行，读取输出，再根据运行结果回答。例如比较 a 与 b，可以让程序在 a 大于 b 时输出 true，否则输出 false，模型读取 true 后判断 a 更大。
[[#^pr-5d78241fbe03|正文跳转]]

十、让模型计算，不要让它猜：模型可以通过程序或 reasoning 计算，不应要求它蒙结果。比较数字时，读取 Terminal 输出的 true 后再判断 a 更大，是在能力范围内借助工具完成任务，而不是直接猜测。摸不清能力边界、直接索要答案，会带来很大的危害。
[[#^pr-0f93e22a5ab6|正文跳转]]

十一、正确使用需要问题、上下文与工具：正确解决问题需要正确的问题、充分的上下文和适用的工具；缺少必要工具时，有些问题无法解决。普通人拿到文章后若被要求不经过处理就立即给出结果，也可能出错，不能把使用方式的问题一概归咎于大语言模型。应在日常使用中理解能力边界，再进一步构建能解决实际问题的工具。
[[#^pr-713bf6c2b818|正文跳转]]

十二、推理加搜索对大部分人已够用：进一步启用 reasoning 和 search：搜索工具根据问题生成关键词，搜索并汇集相关网页，交给模型阅读、推理和回答。用最好的模型结合全球网页搜索，对大部分人已经够用，可以获得接近专家的帮助；对普通日常问题及行业分析中较浅层的数据、研究问题，这类工具已经能做到七八十分，减少逐条搜索 Google、小红书的需要。
[[#^pr-414610a779e2|正文跳转]]

十三、付费是否划算取决于效率提升：不要舍不得为好模型和好工具付费。如果付费能够把效率提高 10 倍或 50 倍，就比自己逐篇阅读、反复折腾更划算。
[[#^pr-414610a779e2|正文跳转]]

十四、搜索工具原理相近，速度有别：ChatGPT 可以启用 Web 与 reasoning；我比较常用 Perplexity。“SPY search”的主要优势是快，像更快的 Perplexity。这些工具的基本原理相近，都是推理模型加网页搜索。
[[#^pr-414610a779e2|正文跳转]]

十五、RAG 的全称与此前介绍：RAG 即 retrieval augmented generation，是我两年前反复讲过的技术。
[[#^pr-a0bf5018da51|正文跳转]]

十六、RAG 以切块检索应对上下文上限：RAG 首先针对模型单次能够接收内容的上限：一两篇文章通常可以输入，几百篇则可能因过长而无法处理。面对几千篇文章、幻灯片或表格，可以切成小块，经 embedding 后存入向量数据库；切块长度示例为 512、256 或 1,024，未说明单位，切割后可能形成几十万个 chunk。提出 query 后，检索相似、可能有用的片段，再生成带上下文、相对精确的回答。
[[#^pr-da1ad86af0b0|正文跳转]]

十七、RAG 适合大量资料的宽泛搜索：RAG 不必对几千个文档逐篇检索或逐篇交给模型处理，适合对大量资料进行较宽泛的搜索。预先切块并存入向量数据库再查询，可以节省时间和费用；其作用被描述为“理论上来说……context window是无限大”，但它不是万金油，存在很大的技术问题、不确定性和缺陷。
[[#^pr-76e67508cc3c|正文跳转]]

十八、RAG 仍可满足资料库的基本需求：RAG 已经很老、存在不少弊端，但传统行业从业者仍可能用得上。它仍适合企业内部资料库，以及小说、文学、哲学、历史、手册、合同、法律相关文档等场景；两年前就有很多企业用它搭建内部 chatbot，检索文件、合同和说明书。对企业资料库、文史哲、合同或法律相关从业者，它仍能满足六七十分的基本需求，在大量文档中提供相对不错的解答。如果因费用较高而没有能力采用口述中所称的“翻译听力”方式，可以考虑用 RAG 满足基本需求。新文档可随时切块、进行 embedding 并存入向量数据库，随后即可检索使用。
[[#^pr-3571a9012f35|正文跳转]]

十九、内部 RAG 可借助成熟方案搭建：文本切割、向量数据库部署等已有成熟方案，不懂编程的传统行业从业者可以找外包，不必自行搭建。一套包含向量数据库、大语言模型、文档切块组件、后端和前端的系统，估计可能只需人民币几千块钱。这类方案搭建和原理都简单，适合企业内部咨询、搜索，以及文史哲、党政机关和其他传统行业的资料检索场景。
[[#^pr-294c09e29603|正文跳转]]

二十、聊天界面背后接入领域资料：RAG 的界面仍可以是类似 ChatGPT 或 Perplexity 的 chatbot 和搜索框，区别在于背后有领域知识、文件内容及向量数据库中的文档块作为上下文。相比把几千个文档逐个交给 ChatGPT 提问，这样更便宜、更快，是初级阶段接近理想的解决方案；关于其能力和限制已有很多讨论与 benchmark，仍应实际尝试，形成自己的结论。

二十一、固定流程承载模型决策与批处理：Workflow 可以理解为非常简单、原始的 agent，也可以认为它不是 agent：工作流程固定，中间的决策和处理由大语言模型完成。可以选用 OpenAI GPT、Claude、Google Gemini、DeepSeek 等模型；框架搭好后，就能接收大量输入，按固定流程逐项处理并输出结果，用于固定条件下的批量任务。

二十二、批量文本可转为后续可用的字段：Workflow 的一个用法是输入一批文字，输出 JSON 格式或一批字符串，再提取某个属性供后续使用。有编程背景的人可以使用 LangChain、LlamaIndex，或者自行搭建。

二十三、不会编程也能拖拽搭建工作流：不会编程的人也可以使用 Dify、n8n、扣子等可视化 Workflow 工具。三者功能大体相近，都提供无需编程、通过可视化拖拽搭建工作流的框架，用哪个都可以；不过，这三个工具也都有问题，个人使用感受是都不太好用。

25、简历筛选明确条件与输出：示例将 1,000 份 Word、TXT 或 PDF 简历按四项条件同时筛选：人在北京而非其他地方、学历必须是“985以上”、计算机等相关专业背景、至少获得一项编程比赛或电子设计大赛三等奖以上奖项。全部符合才输出姓名、电话、邮件和文件名，否则跳过、不输出。传统方式可能依赖 LinkedIn、现成筛选平台或外包 Java 系统；没有大模型的传统方案可能比较模糊、不精确，而且搭建昂贵、繁琐。
[[#^pr-12dd9f82fb74|正文跳转]]

26、无编程背景仍需技术理解：简历筛选 Workflow 先设置 start 接收字符串或文件，接入大语言模型，把四项筛选条件、符合时的输出要求及不符合时不输出写入 prompt，再批量提交 1,000 份简历。这不需要编程背景，但仍需理解如何输出 JSON，以及如何触发下一动作或进入下一步骤。
[[#^pr-a323e4a04937|正文跳转]]

27、简化搭建并比较运行费用：如果了解一点编程、JSON 和大语言模型特性，搭建并不难；这类工具大幅简化固定条件工作流的构建，支持单次和批量运行。主要费用是模型和平台费用：Dify、n8n、扣子的托管平台好像都需要花点钱，Dify 和 n8n 本地运行应该不怎么花钱，主要支付模型费用。相比之下，外包开发可能需要几千上万元，还要额外支付模型费用。

28、小票识别接入报销审批分支：具有视觉能力的模型可以读取小票上的金额、名字和条目，再按预设审批条件处理。示例包括：老板的小票全部报销；某类小票交给会计张三批准；金额超过某个数值且满足另一项条件时直接拒绝报销；满足某些条件时直接批准。具体票据类别、金额阈值及其他条件未展开。搭建时先梳理条件、写出草稿，再拖拽搭建流程并设置输出。

29、测试通过后上线并尝试接入系统：先测试并查看结果，如果测试结果都不错，再部署到生产环境。后续可能连接邮件、Salesforce 等 CRM 的 API，或尝试连接金蝶、SAP 等 ERP；连接能力只是“可能都可以连”，CRM、ERP 等连接可能性需按具体系统确认。

30、先验证工作流，也可用于生产：可以先手动搭建流程，验证 AI 能否完成当前重复工作中的某个工作流。这些工具不要求很多编程或项目搭建经验，能较快捷、智能地处理一些传统平台难以处理的事情。也可以先搭出输入、模型、输出和中间模块作为原型；觉得好用后，如果不信赖 Dify 或 n8n，再投入金钱或时间自行搭建。这些工具直接用于生产工作也没有太大问题，并非只是玩具，已有很多企业用它们搭建内部大型工具和工作流。它们有不少文档和案例，扣子好像还有很多中文文档。

31、多数批量任务可止于工作流：对大部分希望用大模型完成批量、自动化、智能化任务的人，Workflow 已经可以作为终点。使用到这一步，可能显著提高工作效率，甚至替代公司的一部分模块或部门人员。

32、Agent 自行决定工具调用步骤：给定问题和 prompt，提供工具、工具参数及最近的 observation、notes 等信息，模型便可以思考先用什么工具、再做什么，逐步解决问题并给出结果。普通人利用邮件、手机、会议、搜索引擎和浏览器解决问题，也可以理解为 agent：例如回答法国首都，知道就直接回答巴黎，不知道则搜索、阅读结果、推理确认后回答。
[[#^pr-5be56088ea42|正文跳转]]

33、工具让搜索与程序分析串联：Agent 可以使用浏览器、天气和股票等外部 API、操作电脑的 API、Terminal、文本编辑器及专用搜索工具；MCP 中的大量工具可以像插件一样接入，不希望自行编写工具时可以了解这些现成接口。稍复杂的任务可以先搜索、读取并总结网页，在 Terminal 中写入文件，再编写 Python 程序对网页数据排序、做回归分析，最后再次排序、总结并反馈给用户。Agent 成本通常比前面介绍的方法更高，因为一个任务可能多次调用模型，较大的项目可能调用十几次或几十次。
[[#^pr-5be56088ea42|正文跳转]]

34、多角色协作不保证效果更好：Multi-agent 由多个各有职位、角色、工具、功能和工作内容的 AI agent 组成，彼此可以沟通，也可以存在上下级或先后顺序。管理者拆分任务，交给不同职位和技能的 agent，在某一步汇总成果，可以理解成三四人、十几人甚至更多人的小团队。细分角色可能让具体问题解决得更好，也可能更差，不能一概而论。
[[#^pr-0cad4e375d36|正文跳转]]

35、合理并行可加快网页研究：传统网页研究由一个 agent 逐个搜索网页、分析结果；Manus 的案例则由 manager 将问题拆成几十个或上百个小问题，让几十个或几百个 agent 同时搜索、分析各自领域，最后汇总结论。单个具备 reasoning 的 agent 一次推理可能需要 30 秒或一分钟；案例中的口述估计是，顺序执行“100个一分钟”要“60分钟或者是一个小时两个小时”，并行则可能两三分钟，随后汇总给 manager 回答，该场景的效率提升被描述为“100倍”。Multi-agent 并非 Manus 最先提出，李国豪的 CAMEL AI、CrewAI 等也很早就在做。
[[#^pr-0cad4e375d36|正文跳转]]

36、软件工程是 Agent 最佳例子：软件工程 Agent 是目前最成功的一类 Agent 落地，也是 AI agent 最好的例子。2024、2025 年关于 AI 替代程序员的讨论，基本都围绕 SWE-agent 这套思路展开。

38、编程 Agent 使用程序员式接口：软件工程 Agent 拥有 Terminal 命令终端，可读取、搜索、编辑文件的文件系统，以及可切换分支、修改和提交的 Git 与代码仓库版本管理接口，能够在仓库里反复查看、运行程序、修改代码。

39、工具与反馈构成程序员工作闭环：如果相信模型能力会不断 scale up，那么当模型足够强、又拥有程序员式操作接口时，就能够利用工具完成程序员任务。Agent 可以通过 Terminal、文件系统和 Git 执行操作，再从环境反馈判断文件修改、程序运行、编译、debug、Makefile 运行及 Git push 是否成功，用于后续操作。

# 传统行业如何用 AI 改造工作流：从聊天工具到 Agent 与 Multi-agent

- 分享背景与面向对象 ^pr-19b35a2f83d9
  - 过去两年，我分享过 AI agent、Multi-agent、软件工程 agent 等热门话题，但很多传统行业的朋友仍然会问：普通人如何用 AI 在自己的行业里发挥作用？如果想用 AI 改造传统行业，应该从哪些思路入手？
  - 这期视频主要面向没有计算机或 AI 背景、或者只懂一点编程的朋友，讨论如何在建筑、船舶、材料、商业分析、咨询等行业使用 AI 工具、设计 agent 或让相关工具落地。
  - 我希望尽量不设技术壁垒，把内容讲得简单、容易理解，让大家知道如何迈出改变工作流或行业实践的第一步。

- 第一步：用好 ChatGPT，理解大语言模型的能力边界 ^pr-f27367172c14

  - 我最原始的建议是先用好 ChatGPT。ChatGPT 以及其他由大语言模型包装成的 chatbot，都是很好的工具；我在视频中也提到，它们现在都是免费的。 ^pr-114ffabaf8f4

  - 用好这些工具，首先要学会提问，两个要素缺一不可： ^pr-0b6ac5cf8044
    - 用正确、条理清晰的 prompt 描述问题。
    - 提供与问题相关的 context，也就是上下文。

  - ```mermaid
    flowchart TD
    A["用好聊天模型"] --> B["正确、条理清晰地描述问题"]
    A --> C["提供问题相关的上下文"]
    B --> D["两点缺一不可"]
    C --> D
    ```

  - 无论使用 GPT、Claude、Google Gemini 还是 DeepSeek，都要通过实际使用摸清能力边界，不能把模型当成黑箱、神、先知、占卜师或全知全能的人。 ^pr-fe082dc2d326
    - 我的理解是，模型能够回答的问题也受到人类知识和信息来源的限制：如果人都无法回答，或者人类没有相关信息来源，不能指望 ChatGPT 凭空回答。
    - 错误提问的例子是直接问“老张比小张大几岁”，却不说明老张、小张是谁、是什么关系，也不提供年龄信息。
    - 另一些例子是问下周彩票的中奖号码，或者要求预测地球、太阳系什么时候爆炸、太阳什么时候被黑洞吸走。我认为这些问题违反因果律或超出模型乃至人类的能力范围。
    - 对这类问题，模型可能给出模糊或错误的回答，也可能明确表示无法回答。
    - ```mermaid
      flowchart TD
      A["预测彩票号码等超出能力范围的问题"] --> B["可能给出模糊或错误的回答"]
      A --> C["也可能告知无法回答"]
      ```

  - 数值比较说明了“直接猜答案”和“按方法计算”的区别。 ^pr-200067d1699e
    - 过去几年，大家经常讨论模型比较“8.9 和 8:11 哪个大”时容易答错的问题。
    - 再如比较 116854.153 和 16421.27，我认为模型直接回答也有很大概率出错。
    - 如果只把两个数字念一遍，普通人也可能记不住、只能猜。正常比较需要先看整数部分位数，再逐位比较；整数部分无法区分时，再比较小数部分。
    - ```mermaid
      flowchart TD
      A["先比较位数"] --> B["从小数点前的高位逐位比较"]
      B --> C{"当前比较位是否不同"}
      C -->|"相同"| D["继续比较下一位"]
      D --> C
      C -->|"不同"| E["按这一位判断大小，停止比较"]
      B -->|"小数点前比较完"| F["再比较小数点后"]
      ```
    - 我在口述中又将这个比较过程描述为“你是五位数……你也是五位数”，并举了“第三位……这是8，这是4”的例子；这里的数字描述与前面给出的数字并不一致。
    - 人比较数字是在按方法比较、计算，而不是听完就猜。模型也不应该靠猜。

  - 对数值、计算、分析等能够用编程可靠解决的问题，要让模型使用程序，采用 agentic 方法。 ^pr-5d78241fbe03
    - 可以提出这样的要求：使用 Python 写一段程序，可以生成一个文件，并把运行结果输出到 Terminal，同时提供它可以使用的工具。
    - 以 GPT-4o、o1、o3-mini 等模型为例，我描述的流程是：模型编写 Python 程序，通过 Terminal 运行，读取结果，再据此回答。
    - ```mermaid
      flowchart TD
      A["提供问题、编程要求和可用工具"] --> B["模型编写 Python 程序"]
      B --> C["在 Terminal 中运行"]
      C --> D["读取 Terminal 输出"]
      D --> E["根据运行结果回答"]
      ```
    - 比较数字时，可以将第一个数设为 a、第二个数设为 b：如果 a 大于 b，就输出 true，否则输出 false。
    - ```mermaid
      flowchart TD
      A["数字 a 与数字 b"] --> B{"a 是否大于 b"}
      B -->|"是"| C["输出 true"]
      B -->|"否"| D["输出 false"]
      C --> E["读取 true，判断 a 更大"]
      ```

  - 模型读到 Terminal 输出 true 后，再判断 a 更大。这是在其能力范围内使用工具完成任务，而不是直接猜测。 ^pr-0f93e22a5ab6

  - 模型可以通过程序或 reasoning 进行计算，但不要要求它蒙一个结果。我认为，摸不清能力边界、直接索要答案，会带来很大的危害。 ^pr-713bf6c2b818
    - 正确解决问题需要正确的问题、充分的上下文，以及适用的工具；没有必要的工具，有些问题就无法解决。
    - 如果给普通人一篇文章，要求不经过处理就立即给出结果，人也可能做错。不能把使用方式的问题一概归咎于 ChatGPT 或其他大语言模型。
    - 日常多用这些工具，理解边界，再进一步构建能够解决实际问题的工具。

- 第二步：结合推理模型与网页搜索 ^pr-414610a779e2
  - 使用大语言模型时，进一步启用 reasoning 和 search。
    - 我提到的推理模型包括 o3-mini、o4-mini、Gemini 2.5 Pro、DeepSeek R1。
    - 搜索工具会根据问题生成关键词，搜索网页，把相关内容交给模型阅读，再进行推理和回答。
    - ```mermaid
      flowchart TD
      A["用户问题"] --> B["提出搜索关键词"]
      B --> C["在 Google 上搜索"]
      C --> D["汇集相关网页"]
      D --> E["模型阅读网页内容"]
      E --> F["进行推理"]
      F --> G["给出回答"]
      ```

  - 我认为，大部分人使用到这一步就已经够用：用最好的模型结合全球网页搜索，获得接近专家的帮助。
    - ChatGPT 可以启用 Web 与 reasoning。
    - 我比较常用 Perplexity。
    - 我还提到了“SPY search”，认为它主要优势是快，像更快的 Perplexity。
    - 这些工具的基本原理相近，都是推理模型加网页搜索。
  - 对普通日常问题，以及行业分析中较浅层的数据、研究问题，我认为这类工具已经能做到七八十分。
    - 可以少依赖逐条搜索 Google、小红书等方式，用这些工具更快地整理出较好的回答。
    - 不要舍不得为好模型和好工具付费。如果花钱能够把效率提高 10 倍或 50 倍，比自己逐篇阅读、反复折腾更划算。

- 第三步：用 RAG 检索大量内部资料

  - RAG，即 retrieval augmented generation，是我两年前反复讲过的技术。我认为它已经很老、存在不少弊端，但传统行业从业者今天仍可能用得上。 ^pr-a0bf5018da51

  - 它首先针对的是 context window，也就是模型单次能够接收的内容上限。 ^pr-da1ad86af0b0
    - 输入一两篇文章通常可以，但一次输入几百篇，可能因为内容太长而无法处理。
    - 面对几千篇文章、PPT slides、spreadsheet 或 Excel 表格，可以把内容切成小块。口述给出的长度是“512或者256或者1,024”，没有说明单位。
    - 文档切割后可能形成几十万个 chunk，经过 embedding，存入 Vector Database，也就是向量数据库。
    - ![RAG 的文档切块与向量数据库](_assets/video-z7i4rviqXCo/images/shot_00_11_37.png)
    - ```mermaid
      flowchart TD
      A["文章、幻灯片或表格等文档"] --> B["切成小块"]
      B --> C["切块长度示例：512、256 或 1024"]
      C --> D["经过 embedding"]
      D --> E["存入向量数据库"]
      ```
    - 提出 query 后，在向量数据库中检索相关内容，找到相似、可能有用的片段，再生成有上下文的 response。
    - ```mermaid
      flowchart TD
      A["提出问题 query"] --> B["搜索向量数据库"]
      B --> C["比较文档块是否有用、是否相似"]
      C -->|"如果比较相似"| D["给出带上下文、相对精确的回答"]
      ```

  - RAG 的价值与限制 ^pr-76e67508cc3c
    - 不必面对几千个文档逐篇检索或逐篇交给模型处理，适合对大量资料进行较宽泛的搜索。

  - 将内容预先切块、存入向量数据库再查询，可以节省时间和费用。我在口述中将其描述为“理论上来说……context window是无限大”。 ^pr-3571a9012f35
    - 但 RAG 不是万金油，存在很大的技术问题、不确定性和缺陷。
    - 我认为它仍适合企业内部资料库，以及小说、文学、哲学、历史、手册、合同、法律相关文档等场景。
    - 两年前就有很多企业用它搭建内部 chatbot，检索文件、合同、说明书等资料。
    - 如果没有能力进行我口述中所称的“翻译听力”，因为那种方式比较贵，可以考虑用 RAG 满足基本需求。
    - RAG 比较灵活：可以随时加入新文档，切成 chunk，进行 embedding，再存入向量数据库，随后就能使用。
    - ```mermaid
      flowchart TD
      A["加入新文档"] --> B["切成小块 chunk"]
      B --> C["处理后存入向量数据库"]
      C --> D["随后可检索使用"]
      ```
    - 对企业资料库、文史哲、合同或法律相关从业者，我认为它仍能满足六七十分的基本需求，在大量文档中提供相对不错的解答。

  - 搭建与使用方式 ^pr-294c09e29603
    - 文本切割、向量数据库部署等已有成熟方案。不懂编程的传统行业从业者，不必自己搭建，可以找外包。
    - 我估计，一套包含向量数据库、大语言模型、切块组件、后端和前端的系统，可能只需人民币几千块钱。
    - ![企业内部 RAG 工具的组成](_assets/video-z7i4rviqXCo/images/shot_00_15_04.png)
    - ```mermaid
      flowchart TD
      A["企业内部 RAG 工具"] --> B["向量数据库"]
      A --> C["大语言模型"]
      A --> D["文档切块处理"]
      A --> E["后端"]
      A --> F["前端"]
      ```
    - 这类方案搭建简单、原理也简单，适合企业内部咨询、搜索，以及文史哲、党政机关和其他传统行业的资料检索场景。

  - 最终界面仍可以像 ChatGPT 或 Perplexity：一个 chatbot、一个搜索框。 ^pr-88ab5bf561bc
    - 区别在于后面有领域知识、文件内容和向量数据库中的 chunk 作为上下文。
    - 相比把几千个文档逐个交给 ChatGPT 提问，这样更便宜、更快。我认为它是初级阶段一个接近理想的解决方案。
    - 关于它能做什么、不能做什么，已有很多讨论和 benchmark；希望大家实际尝试，形成自己的结论。

- 第四步：用 Workflow 完成固定条件下的批量任务

  - Workflow 可以理解为非常简单、原始的 agent，也可以认为它不是 agent。 ^pr-08005e4cc546
    - 它的工作流程固定，但中间的决策和处理由大语言模型完成。
    - 可以使用 OpenAI GPT、Claude、Google Gemini、DeepSeek 等不同模型。
    - 框架搭好后，可以接收大量输入，按固定流程逐项处理并输出结果。

  - ```mermaid
    flowchart TD
    A["批量输入"] --> B["固定工作流框架"]
    B --> C["中间决策与处理使用大语言模型"]
    C --> D["逐个自动完成流程"]
    D --> E["批量输出"]
    ```

  - 有编程背景，可以使用 LangChain、LlamaIndex，或者自己搭建。

  - 例如，输入一批文字，输出 JSON 格式或一批 string，再提取某个 attribute 供后续使用。 ^pr-db29ca0b242f

  - 不会编程，也可以使用可视化 Workflow 工具。 ^pr-521ca0f9400a
    - 我举了 Dify、n8n、扣子三个例子，并在口述中介绍 Dify 是中国团队的开源工具、n8n 是美国团队的工具、扣子是字节跳动的工具。
    - ![可视化 Workflow 工具介绍](_assets/video-z7i4rviqXCo/images/shot_00_17_58.png)
    - 我认为它们功能大体相近，都提供不需要编程、可视化拖拽搭建 Workflow 的框架，用哪个都可以。

  - 这些介绍不是广告，也没有收广告费。 ^pr-e016a092d546
    - 没提到其他好工具，可能只是做 PPT 时没想起来，可以在评论区补充。
    - 提到的工具也有问题；我个人觉得这三个都不太好用，如果有更好用的，也希望大家提示。

  - HR 批量筛选简历的例子 ^pr-12dd9f82fb74
    - 有 1,000 份 Word、TXT 或 PDF 简历，老板要求同时满足以下条件：
      - 人在北京，不能在其他地方。
      - 学历“必须是985以上”。
      - 专业为计算机等相关背景。
      - 至少获得一个编程比赛或电子设计大赛的小奖，三等奖以上。
    - 符合条件，输出名字、电话、邮件和文件名；不符合条件，就过掉，不输出结果。
    - ```mermaid
      flowchart TD
      A["1000 份简历"] --> B{"是否同时满足四项条件"}
      C["人在北京"] --> B
      D["学历要求：985 以上"] --> B
      E["计算机相关专业背景"] --> B
      F["至少一项编程比赛或电子设计大赛三等奖以上奖项"] --> B
      B -->|"是"| G["输出姓名、电话、邮件及文件名"]
      B -->|"否"| H["跳过该简历"]
      ```
    - 传统方式可能依赖 LinkedIn、现成筛选平台，或者外包开发一套 Java 系统。我认为，没有大模型的传统方案可能比较模糊、不精确，而且搭建昂贵、繁琐。

  - Workflow 的搭建过程 ^pr-a323e4a04937
    - 设置 start，接收字符串或文件输入。
    - 中间接入一个大语言模型，将四个筛选条件写入 prompt，规定符合条件时输出什么、不符合时不输出。
    - 将 1,000 份简历批量交给 Workflow 处理。
    - ```mermaid
      flowchart TD
      A["字符串或简历文件输入"] --> B["大语言模型读取文件与筛选 prompt"]
      B --> C{"是否符合条件一至四"}
      C -->|"符合"| D["输出规定结果"]
      C -->|"不符合"| E["不输出该简历结果"]
      F["批量提交 1000 份简历"] --> A
      ```
    - 不需要编程背景，但并非完全不需要技术理解：仍需了解如何输出 JSON、如何触发 next action 或进入 next step。

  - ![简历筛选 Workflow 的输入、模型与输出](_assets/video-z7i4rviqXCo/images/shot_00_20_08.png)

  - 如果了解一点编程、JSON 和大语言模型特性，搭建并不难。它大幅简化了固定条件工作流的构建，既能单次运行，也能批量运行。 ^pr-c17ee0271aab
    - 主要费用是模型和平台费用。
    - Dify、n8n、扣子的托管平台“好像……都需要花点钱”；Dify 和 n8n 自己本地运行，“应该是不怎么花钱的”，主要支付模型费用。
    - 相比之下，找外包开发可能需要几千上万元，还要额外支付模型费用。

  - 会计处理小票和报销的例子 ^pr-9a5ef3a9c459
    - 具有视觉能力的模型可以读取小票上的金额、名字、条目等信息。
    - 可以把不同审批条件写入流程：
      - 老板的小票全部报销。
      - 某类小票交给会计张三批准。
      - 金额超过某个数值，并且满足另一项条件时，直接拒绝报销。
      - 满足某些条件时，直接批准。
    - ```mermaid
      flowchart TD
      A["视觉模型读取小票金额、名称与条目"] --> B["按预先设置的条件筛选"]
      B -->|"老板的小票示例"| C["直接报销"]
      B -->|"某类小票，具体条件未说明"| D["交会计张三批准"]
      B -->|"超过设定金额且满足其他设定条件"| E["拒绝报销"]
      B -->|"满足直接批准条件，具体条件未说明"| F["直接批准"]
      ```
    - 先梳理条件、写出草稿，再拖拽搭建流程并设置输出。

  - 测试与生产使用 ^pr-84d970aaf374
    - 先测试结果；如果测试结果都不错，再部署到 production。
    - 后面可以连接邮件、Salesforce 等 CRM 的 API，或尝试连接金蝶、SAP 等 ERP；我在口述中对这些连接能力使用的是“可能都可以连”的表述。

  - ```mermaid
    flowchart TD
    A["梳理条件，写出草稿"] --> B["拖拽搭建工作流"]
    B --> C["配置输出"]
    C --> D["测试并查看结果"]
    D -->|"如果测试结果不错"| E["部署到生产环境"]
    E --> F["可连接邮件或内部系统 API"]
    F --> G["CRM、ERP 等连接可能性需按具体系统确认"]
    ```

  - 可以先手动搭建一个流程，验证 AI 能否完成当前重复工作中的某个工作流。 ^pr-baed5139dd12
    - 它能够较快捷、智能地完成一些传统平台难以处理的事情，不要求很多 coding 或项目搭建经验。
    - 也可以把它当成原型工具：先搭出输入、模型、输出及中间模块，觉得好用后，如果不信赖 Dify 或 n8n，再花钱或花时间自行搭建。
    - 我认为，这些工具直接用于生产工作也没有太大问题，不只是玩具，已有很多企业用它们搭建内部大型工具和工作流。
    - 它们有不少文档和案例，扣子好像还有很多中文文档，可以进一步了解。

  - 对大部分希望用大模型完成批量、自动化、智能化任务的人，我认为 Workflow 已经可以作为终点。 ^pr-7e6caf21ed77
    - 使用到这一步，可能显著提高工作效率，甚至替代公司的一部分模块或部门人员。

- AI Agent：给模型工具，让它逐步解决问题 ^pr-5be56088ea42
  - 过去一年多，我反复介绍 AI agent 和 Multi-agent。我认为，除了姚顺宇本人等人以外，自己可能是华语世界较早、较多讨论这些问题的人之一，但不敢说自己是最早或最多的。
  - Agent 的基本构成
    - 给定一个问题和 prompt。
    - 提供工具、工具参数，以及最近的 observation、notes 等信息。
    - 模型像一个人一样思考先用什么工具、再做什么，逐步解决问题，最后给出结果。
  - 可以把普通人也理解为 agent：人有邮件、手机、会议、搜索引擎、浏览器等工具，接到问题后利用这些工具解决。
    - 例如问法国首都是哪里，知道就直接回答巴黎；不知道，就打开浏览器，在 Google 搜索，阅读结果、推理确认，再回答。
    - ```mermaid
      flowchart TD
      A["问题：法国的首都是哪里"] --> B{"是否知道答案"}
      B -->|"知道"| C["直接回答巴黎"]
      B -->|"不知道"| D["调用浏览器，打开 Google 搜索"]
      D --> E["读取搜索结果"]
      E --> F["推理并确认结果"]
      F --> C
      ```

  - Agent 可以使用的工具包括：
    - 浏览器。
    - 天气、股票等外部 API。
    - 操作电脑的 API、Terminal、文本编辑器。
    - 专门为 agent 提供的搜索工具。
    - MCP 中的大量工具，可以像插件一样接入；如果不希望自己编写工具，可以了解这些现成接口。
  - 一个稍复杂的任务流程可以是：
    - 搜索网页。
    - 读取搜索结果。
    - 总结搜索结果。
    - 在 Terminal 中写入文件。
    - 写一段 Python 程序，对网页中的数据排序、进行 regression 回归等分析。
    - 再排序、总结，把结果反馈给用户。
  - ```mermaid
    flowchart TD
    A["搜索"] --> B["读入搜索结果"]
    B --> C["总结搜索结果"]
    C --> D["在 Terminal 中写文件或 Python 小程序"]
    D --> E["对网页数据排列，或进行回归分析"]
    E --> F["排序"]
    F --> G["总结并反馈给用户"]
    ```

  - Agent 成本通常比前面的方法更高，因为一个任务可能调用多次模型；较大的项目可能调用十几次或几十次。

- Multi-agent：让多个角色分工协作 ^pr-0cad4e375d36
  - Multi-agent 由多个 AI agent 组成，各自有职位、角色、工具、功能和工作内容。
    - 它们之间可以沟通，也可以存在上下级或先后顺序。
    - supervisor、manager 或“老板”拆分任务，交给不同职位、技能的 agent 处理，再在某一步汇总成果。
    - ![Multi-agent 的角色分工与汇总](_assets/video-z7i4rviqXCo/images/shot_00_28_30.png)
    - 可以把它理解成一个三四人、十几人，甚至更多人的小团队。

  - 细分角色可能让具体问题解决得更好，也可能更差，不能一概而论。
  - ```mermaid
    flowchart TD
    A["管理者拆分任务"] --> B["分配给不同职位、工作和技能的 Agent"]
    B --> C["各自解决具体问题"]
    C --> D["汇总工作"]
    C --> E["细分问题可能解决得更好"]
    C --> F["也可能解决得更差"]
    ```
  - 合理设计并行，可以提高速度。
    - 我以口述中称为“Manus”的工具为例。它的一些想法与我此前在 Twitter Space 中讨论过的想法相近；我原先不确定实现后能有多少 benefit，而它做出来的效果还不错。

  - 并行网页研究的例子
    - 传统做法由一个 agent 逐个搜索网页、逐个分析结果。
    - 我描述的 Manus 做法是：manager 将问题拆成几十个或上百个小问题，让几十个或几百个 agent 同时搜索、分析各自领域，最后汇总结论。
    - ```mermaid
      flowchart TD
      A["Manager 将问题拆成多个小问题"] --> B["分配给多个 Agent"]
      B --> C["多个 Agent 同时搜索网页"]
      C --> D["各自进行领域分析"]
      D --> E["汇总结果与结论"]
      E --> F["向用户回答"]
      ```
    - 单个具备 reasoning 的 agent，一次 inference 可能需要 30 秒或一分钟。

  - 关于顺序与并行耗时，我口述的估计是：“100个一分钟，那就是60分钟或者是一个小时两个小时”；并行时则“可能就是两三分钟”，随后再汇总给 manager，由 manager 回答。
  - ```mermaid
    flowchart TD
    A["多个搜索或推理任务"] --> B["顺序逐个执行"]
    A --> C["合理设计后并行执行"]
    B --> D["单次推理可能需 30 秒或一分钟，逐次等待累积"]
    C --> E["案例中可能两三分钟完成多个任务"]
    E --> F["再汇总并交给 Manager 回答"]
    ```

  - 我将这个场景的效率提升描述为“100倍”，认为它是一个很好的实现。
    - Multi-agent 并不是 Manus 最先提出的，李国豪的 CAMEL AI、CrewAI 等也很早就在做。

- 软件工程 Agent：目前最成功的一类落地

  - SWE-agent 的思路 ^pr-c709ff07146e
    - 我认为，软件工程 agent 是 AI agent 最好的例子。
    - 姚顺宇等人较早把这个概念写成了论文；我认为自己在 2023 年的 Twitter Space 和置顶帖子中提得更早，只是他们先完成了论文。我的 Twitter timeline 可以作为我这一说法的依据。
    - 2024、2025 年关于 AI 替代程序员的讨论，基本都围绕这套思路展开。

  - 它拥有类似程序员的操作接口： ^pr-b650a64552c7
    - Terminal，即命令终端或命令行终端。
    - 文件系统，可以读取、搜索、编辑文件。
    - Git 和代码仓库版本管理，可以切换 branch、修改、commit。
    - 可以在仓库里反复查看、运行程序、修改代码。

  - ![程序员 Agent 的工具接口](_assets/video-z7i4rviqXCo/images/shot_00_31_35.png)

  - 我的判断是，如果相信模型能力会不断 scale up，那么当模型足够强、又拥有这些接口时，就能够利用工具完成程序员任务。 ^pr-5e316df9ea63
    - 它可以从 environment 和 Terminal 获取 feedback，判断文件是否修改成功、程序是否运行成功、编译是否成功、debug 是否成功、Makefile 是否运行成功、Git push 是否成功。
    - ```mermaid
      flowchart TD
      A["程序员 Agent"] --> B["Terminal：执行命令、运行程序"]
      A --> C["文件系统：查看、搜索、修改文件"]
      A --> D["Git 与仓库版本管理"]
      B --> E["环境反馈：运行或编译是否成功"]
      C --> F["环境反馈：文件修改是否成功"]
      D --> G["环境反馈：推送是否成功"]
      E --> A
      F --> A
      G --> A
      ```

  - 我认为，这构成了一个完整的程序员式工作框架。 ^pr-d54cbd1d0fdb
    - v0、口述中的“BOSN da NIO”或“bought new”、Lovable、Cursor、Windsurf 等，使用的都是类似思路：把操作抽象成 function calling 或 tool calling，交给 agent 使用。
    - 理论上，这类工具可以完成很广泛的编程任务，但产品通常聚焦特定场景。

- MetaGPT：按软件团队组织 Multi-agent 的早期案例 ^pr-b8184abd3bae
  - 团队与产品创新
    - MetaGPT 不是硅谷团队，也不是北上广深团队；我在口述中认为，它应该是厦门的 DeepWisdom 团队做的。
    - 我认为它是非常优秀的团队，成员虽有良好学术背景，但也是一群非常年轻的人，并不是靠院士、教授等头衔做出的产品。
    - 我的看法是，在 AI、尤其 agent 时代，从 ACM Fellow、中科院院士到高中生，都可能在同一起跑线上。想象力比头衔更重要。
    - 好工作不一定由最有名、职位最高的人做出来，普通人、年轻人和爱用 AI 的人，也能凭灵感做出好产品。
  - 五个角色完成软件项目
    - Product Manager：产品经理，编写需求文档。
    - Architect：架构师，编写 system design。
    - Project Manager：项目经理，拆分 task。
    - Engineer：程序员，编写代码。
    - QA Engineer：测试人员，编写测试，再根据结果继续迭代。
    - 例如提出写一个 2048、Flappy Bird 或愤怒的小鸟类游戏的任务，由上述五个 agent 依次协作，中间没有人参与。
  - ![MetaGPT 的软件项目角色交接](_assets/video-z7i4rviqXCo/images/shot_00_40_08.png)
  - ```mermaid
    flowchart TD
    A["用户提出游戏等软件项目需求"] --> B["产品经理：编写需求文档"]
    B --> C["架构师：编写系统设计"]
    C --> D["项目经理：编写任务"]
    D --> E["程序员：编写代码"]
    E --> F["QA：编写测试"]
    F --> G["再逐步反馈回去，具体回流路径未展开"]
    ```

  - 我认为，这种方式在保证可读性、合理性、工程性和流程完整性的前提下，能够交付可运行的游戏。
    - 几个 LLM 分别扮演角色，像人类团队一样分工，利用软件工程中的管理经验逐步完成任务。
  - 成本与速度
    - 一次完整运行可能有几百次或上千次 iteration、模型调用，比单次调用贵，但我认为仍没有人力贵。
    - 因为按 sequential 方式一步步执行，所以比较慢。
  - ```mermaid
    flowchart TD
    A["可能有几百次或上千次模型调用"] --> B["相对单次调用更贵"]
    C["按顺序一步一步执行"] --> D["流程较慢"]
    E["借用人类管理和工程经验"] --> F["组织多个角色完成任务"]
    ```

  - 设计上的讨论空间
    - 是否 over-design、是否过度设计？
    - 是否存在更优的组织方式？
    - 某些环节是否可以不这样设计？
    - feedback 是否正确？
    - 这些问题都有很大讨论空间。
  - 我选择它，不是因为它最好，而是因为它是该领域非常早、很经典的目的性实现。
    - 它借用人类管理、工程和社会经验，把任务拆分给不同角色，最后交付成果。
    - 更早的斯坦福小镇是在小镇中模拟模型角色聊天、工作等活动，我认为那种方式没有明确目的；MetaGPT 则把角色组织起来完成一个具体工作。
    - CrewAI、CAMEL AI 等也有类似思路，可以探索把客服、商业分析、管理文档、会计、人事等问题拆分处理。
    - 这是我过去一两年反复讨论和验证的方向，我认为确实有可能性。

- Multi-agent 落地的门槛与不稳定性

  - 首先需要真正理解 Multi-agent，设计过 agent 或 Multi-agent 框架。 ^pr-29efe1199f83

  - 每个任务和拆分后的子任务都必须有边界。 ^pr-5c5f00ae8935
    - 如果让它处理 unbounded problem，也就是没有边界、没有结束条件的问题，它很可能跑飞。
    - 一个任务跑飞，可能导致整个 Multi-agent 框架跑飞或跑废。

  - 需要监督、feedback、review 等机制，也需要可靠、稳定的 agent 通信协议。 ^pr-a230d91aa9e5
    - 我提到微软 AutoGen 的工作就在讨论这类问题。

  - ```mermaid
    flowchart TD
    A["任务没有边界或结束条件"] -->|"很可能"| B["子任务跑飞"]
    B --> C["整个 Multi-agent 框架跑飞或跑废"]
    D["为任务和子任务设置边界"] --> E["设计运行约束"]
    F["监督、反馈或审核机制"] --> G["检查 Agent 能否跑通"]
    H["可靠稳定的 Agent 间通信协议"] --> E
    ```

  - 传统行业专家即使很懂本行业，也可能缺乏调教、调试 Multi-agent 系统的经验，这是难以推广的原因之一。 ^pr-abc1d7e73b4a

  - ```mermaid
    flowchart TD
    A["从业者很懂自己的行业"] --> B["但可能缺乏 Multi-agent 系统调试经验"]
    B --> C["成为难以推广落地的原因之一"]
    ```

  - 软件开发比依赖外部沟通的工作更容易落地。 ^pr-6987cb7859a9
    - 一段代码可以在本地或其他受控环境运行，通过读写代码、编译器、测试等方式获得反馈。

  - 本地开发可以逐步修改、检查、拆任务、重写模块、扩展 API。可能等半小时或一个小时，流程就能跑完，不必持续依赖外界沟通。 ^pr-4cec18e62737
    - 客服、销售等岗位却不可避免地与外界互动：给张客户打电话、发邮件或短信，给李客户发 Slack 或 Discord，与上游供应商打电话或开会。
    - 外部条件不可知，缺失的信息或意外情况可能堵住某一步。
    - 例如客户突然说“哎呀咱喝个酒吧”，agent 该怎么回应、怎么处理？这类问题常常超出它的处理能力。

  - 相比之下，在本地处理几十个或几千个文件、跑 benchmark、找 bug、优化和版本管理，有明显优势。 ^pr-20241135975d

  - ```mermaid

    A["本地程序开发"] --> B["可读写代码、使用编译器并获得反馈"]
    B --> C["任务较可控，不必与外界沟通"]
    C --> D["Agent 落地具有优势"]
    E["客服、销售等岗位"] --> F["需要联系客户或供应商"]
    F --> G["存在未知的外界条件或信息"]
    G -->|"很有可能"| H["某一步被堵住，落地困难"]

  - 在自己的行业设计 Multi-agent，需要明确： ^pr-f6d062303392
    - 每个任务的边界。
    - stop criteria，即停止条件。
    - 任务本身的条件。
    - review requirements，即审核要求。
    - 如何顺利结束并成功交付。
    - 如果失败怎么办，反复几次失败又怎么办。

  - ```mermaid
    flowchart TD
    A["每个任务的设计"] --> B["任务边界"]
    A --> C["停止条件 stop criteria"]
    A --> D["任务自身的条件"]
    A --> E["审核要求 review requirements"]
    A --> F["失败或反复失败时怎么办"]

    D --> G
    E --> G
    F --> G
