# CLWB 和 PCOMMIT｜CLWB and PCOMMIT

---

## 正文

最新版 Intel 手册中有几条[用于 non-volatile storage（例如 SSDs）的新 instructions](https://software.intel.com/sites/default/files/managed/0d/53/319433-022.pdf)。这是怎么回事？

在详细了解这些 instructions 之前，我们先来看看超快 NVRAM 存在的问题。一个问题是，下一代 storage technologies（PCM、3d XPoint 等）会足够 fast，以至于 syscall 和其他 OS overhead 可能比 disk access 的实际 cost 还要 expensive[1](https://danluu.com/clwb-pcommit/#fn:1)。另一个问题是 x86 memory hierarchy 与 persistent memory 之间的 impedance mismatch。这两种情况基本上都是 [Amdahl's law](https://en.wikipedia.org/wiki/Amdahl%27s_law) 问题：一个 component 已经 improved 了这么多，其他 components 就必须 improve 才能跟上。

关于第一个问题，有一篇 [Todor Mollov、Louis Eisner、Arup De、Joel Coburn 和 Steven Swanson 撰写的好 paper](http://research.microsoft.com/pubs/198366/Asplos2012_MonetaD.pdf)；下面我将展示他们的一张 graphs。

![NVRAM operations 的 OS 及其他 overhead](https://danluu.com/images/clwb-pcommit/Moneta_overhead.webp)

所有地方都写着“Moneta”，因为那是他们的 system 名称（顺便说一句，这个 system 相当酷；我推荐阅读这篇 paper，看看他们是怎么做到的）。他们的“baseline” case 显著好于你在 stock system 上能得到的结果。他们做了许多 optimizations（例如，bypassing Linux 的 IO scheduler，并在可能的情况下 removing context switches），这使 latency 相比普通 linux reduces 了 62%。即便如此，transaction 的 hardware + DMA cost（bar 的白色部分）在 overhead 面前仍然显得微不足道。注意，他们把 DMA 的 cost 视为 hardware overhead 的一部分。

他们能够完全 bypass OS，并 reduce 大量 overhead，但 write 的大部分 cost 依然是 overhead。

![NVRAM operations 的 OS bypass speedup](https://danluu.com/images/clwb-pcommit/Moneta_speedup.webp)

尽管无法消除所有 overhead，他们在小型 microbenchmarks 和实际 code 上都获得了相当显著的 speedups。所以，这是其中一个问题。当你的 I/O device 非常 fast 时，OS 会给 I/O 加上一笔相当沉重的负担。

也许你只需把 NVRAM device mapping 到一个 memory 的 region，并按需向其中 committing 内容，就能 bypass 这个问题的很大一部分。但这会碰到另一个问题，也就是：如果你想要类似 transactional semantics 的东西，caches 与 NVRAM region 的 interact 方式就存在 impedance mismatch。

[Kumud Bhandari、Dhruva R. Chakrabarti 和 Hans-J. Boehm 的这份 report 对此有更详细的描述](http://www.hpl.hp.com/techreports/2012/HPL-2012-236.pdf)。我也会借用他们的几张 figures。

![粗略的 memory hierarchy diagram](https://danluu.com/images/clwb-pcommit/HP_hierarchy.webp)

我们有这样一个 safe 且 persistent 的 NVRAM region，但 CPU 在能够访问它之前，必须经过多个具有不同 ordering guarantees 的 layers。他们给出了下面的 example：

> 例如，考虑一种常见的 programming idiom：一个 persistent memory location N 被 allocated、initialized，并通过将 allocated address assigning 给一个 global persistent pointer p 而被 published。如果对 global pointer 的 assignment 在 initialization 之前就于 NVRAM 中 becomes visible（推测是因为后者被 cached，尚未到达 NVRAM），而 program 恰在此时 crashes，那么 restart 后对 persistent pointer 的 dereference 就会 read uninitialized data。假设采用 writeback (WB) caching mode，可以在对 global persistent pointer p 进行 assignment 之前，为刚刚 allocated 的 persistent locations N inserting cache-line flushes，从而避免这个问题。

到处 Inserting `CLFLUSH` instructions 是可行的，但会带来多少 overhead 呢？

![reads 和 writes 的 Persistence overhead](https://danluu.com/images/clwb-pcommit/HP_synthetic.webp)

他们研究的四种 memory types（也是 x86 supports 的四种）分别是 writeback (WB)、writethrough (WT)、write combine (WC) 和 uncacheable (UC)。正常情况下，你接触的就是 WB。Memory 可以被 cached，并在被强制要求时 written back。WT 允许 memory 被 cached，但 writes 必须被 written straight through 到 memory，也就是说，memory 会与 cache 保持同步。UC 则根本不能被 cached。WC 类似 UC，只是 writes 在被 sent out 到 memory 之前可以被 coalesced。

R、W 和 RW benchmarks 只是针对 reading 和 writing memory 的 benchmarks。WB 显然遥遥领先（越 lower 越好）。如果你想直观感受 WB 比其他 policies 好多少，可以尝试用任何非 WB 的 memory 来 booting 一个 OS。

我偶尔不得不这么做，因为我以前在一家 chip 公司工作，而我们最初拿到 chip 时，往往不知道必须 disable 哪些 bits 才能绕过 bugs。取得进展的最简单办法通常就是完全 disable caches。这样确实“管用”，但没有 WB memory 时，就连 DOS 这样 minimal 的 OSes，boot 起来也明显 slow。我记得 Win 3.1 要花将近一个小时，而 Win 95 则要花好几个小时。

\_b benchmarks 会 force writes 对 memory 为 visible。对于 WB case，这需要先执行一个 `MFENCE`，再执行一个 `CLFLUSH`。带有 visibility constraints 的 WB 显著 slower 于其他 alternatives。与 writes 不必被 ordered 和 flushed 的 WB 相比，这是多个 order of magnitude 的 slowdown。

他们还对一些实际 data structures run benchmarks，并施加了 data 必须 persistently visible 的 constraint。

![data structure operations 的 Persistence overhead](https://danluu.com/images/clwb-pcommit/HP_data_structures.webp)

普通 WB memory 的 performance 可能 slow 得惊人：与不使用 caches 运行时的 performance 相差不到一个 factor of 2。而这还仅仅是离开 cache hierarchy 所产生的 overhead——即使你的 persistent storage 是 infinitely fast，这一点也依然成立。

现在，我们来看看 Intel 决定如何解决这个问题。有两条新 instructions，`CLWB` 和 `PCOMMIT`。

`CLWB` 的作用类似 `CLFLUSH`，因为它会 forces data 被 written out 到 memory。不过，它不会 force cache 丢弃 data，这使得之后的 reads 和 writes 要 faster 得多。此外，`CLFLUSH` 仅相对于 `MFENCE` 为 ordered，但 `CLWB` 也相对于 `SFENCE` 为 ordered。下面是他们对 `CLWB` 的描述：

> 从 cache coherence domain 内 cache hierarchy 的任意 level，将包含由 memory operand 指定的 linear address 的 cache line（如果是 dirty）Writes back 到 memory。该 line 可以以 non-modified state 被 retained 在 cache hierarchy 中。将 line Retaining 在 cache hierarchy 中是一种 performance optimization（被 hardware 当作 hint），用于 reduce 后续 access 发生 cache miss 的可能性。Hardware 可以选择将 line retain 在 cache hierarchy 的任意 levels 中，并且在某些情况下，可以从 cache hierarchy 中 invalidate 该 line。source operand 是一个 byte memory location。
> 
> 应当注意，processors 可以自由地从那些被 assigned 了允许 speculative reads 的 memory-type 的 system memory regions 中 speculatively fetch 和 cache data（例如 WB、WC 和 WT memory types）。由于这种 speculative fetching 可以随时发生，并且不与 instruction execution 绑定，CLWB instruction 相对于 PREFETCHh instructions 或任何 speculative fetching mechanisms 都不是 ordered（也就是说，在 references 该 cache line 的 CLWB instruction 的 execution 紧接之前、期间或之后，data 都可能被 speculatively loaded 到 cache line 中）。
> 
> CLWB instruction 只由 store-fencing operations 进行 ordered。例如，software 可以使用 SFENCE、MFENCE、XCHG 或 LOCK-prefixed instructions，以确保之前的 stores 被 included 在 write-back 中。CLWB instruction 不必由另一条 CLWB 或 CLFLUSHOPT instruction 进行 ordered。CLWB 会与 logical processor 对 same address executed 的 older stores 隐式地 ordered。
> 
> CLWB 的 Executions 与 PCOMMIT 的 executions 会 interact。PCOMMIT instruction 会 operates on 某些已经 accepted to memory 的 store-to-memory operations。针对与某个 older store 相同的 cache line executed 的 CLWB，会在 CLWB execution becomes globally visible 时，使该 store 变为 accepted to memory。

`PCOMMIT` 被 applied 到整个 memory ranges，并 ensures 该 memory range 中的所有内容都被 committed 到 persistent storage。下面是他们对 `PCOMMIT` 的描述：

> PCOMMIT instruction 会使针对 persistent memory ranges 的某些 store-to-memory operations 变为 persistent（power failure protected）。1 具体而言，PCOMMIT applies to 那些已经 accepted to memory 的 stores。
> 
> 虽然所有 store-to-memory operations 最终都会 accepted to memory，但下面各项说明了 software 可以采取哪些 actions，以确保它们被 accepted：
> 
> 针对 write-back (WB) memory 的 Non-temporal stores，以及针对 uncacheable (UC)、write-combining (WC) 和 write-through (WT) memory 的所有 stores，一旦 globally visible，就会 accepted to memory。如果在针对 write-back (WB) memory 的一次普通 store becomes globally visible 之后，对与该 store 相同的 cache line executed 了 CLFLUSH、CLFLUSHOPT 或 CLWB，那么当 CLFLUSH、CLFLUSHOPT 或 CLWB execution 本身 becomes globally visible 时，该 store 就会 accepted to memory。
> 
> 如果 PCOMMIT 是在针对某个 persistent memory range 的 store 被 accepted to memory 之后 executed 的，那么该 store 会在 PCOMMIT becomes globally visible 时变为 persistent。这意味着，如果在后来的一次针对 persistent memory 的 store 被 executed 时，某次 PCOMMIT 的 execution 已经 globally visible，那么该 store 就不能先于 PCOMMIT applies 的那些 stores 变为 persistent。
> 
> 下面各项详细说明了 PCOMMIT 与其他 operations 之间的 ordering：
> 
> logical processor 不会 ensure 在开始 PCOMMIT 的一次 execution 之前，之前的 stores 和（由该 logical processor 进行的）CLFLUSHOPT 与 CLWB 的 executions 已经 globally visible。这意味着，software 在 executing PCOMMIT 之前，必须使用适当的 fencing instruction（例如 SFENCE），以确保之前针对 persistent memory ranges 的 stores-to-memory operations 以及 CLFLUSHOPT 和 CLWB executions 已经 globally visible（从而使它们 accepted to memory）。
> 
> logical processor 不会 ensure 在开始后续 stores 之前，PCOMMIT 的某次 execution 已经 globally visible。如果 software 要求这些 stores 不得先于 PCOMMIT 而 become globally visible（例如，因为 younger stores 不得先于由 PCOMMIT committed 的那些 stores 变为 persistent），就可以在 PCOMMIT 与后来的 stores 之间使用适当的 fencing instruction（例如 SFENCE）来确保这一点。
> 
> PCOMMIT 的一次 execution 相对于 SFENCE、MFENCE、XCHG 或 LOCK-prefixed instructions 的 executions，以及 serializing instructions（例如 CPUID），是 ordered 的。
> 
> PCOMMIT 的 Executions 相对于 load operations 并不是 ordered。Software 可以使用 MFENCE 来将 loads 与 PCOMMIT 进行 order。
> 
> PCOMMIT 的 Executions 不会 serialize instruction stream。

`CLWB` 和 `PCOMMIT` 实际能 improve 多少 performance，将取决于它们的 implementations。对它们进行 benchmark 并看看表现如何，会很有意思。无论如何，这是解决 WB/NVRAM impedance mismatch 问题的一次尝试。它并没有直接解决 OS overhead 问题，但后者在很大程度上可以在不增加 hardware 的情况下绕过。

## 原文

The latest version of the Intel manual has a couple of [new instructions for non-volatile storage, like SSDs](https://software.intel.com/sites/default/files/managed/0d/53/319433-022.pdf). What's that about?

Before we look at the instructions in detail, let's take a look at the issues that exist with super fast NVRAM. One problem is that next generation storage technologies (PCM, 3d XPoint, etc.), will be fast enough that syscall and other OS overhead can be more expensive than the actual cost of the disk access[1](https://danluu.com/clwb-pcommit/#fn:1). Another is the impedance mismatch between the x86 memory hierarchy and persistent memory. In both cases, it's basically an [Amdahl's law](https://en.wikipedia.org/wiki/Amdahl%27s_law) problem, where one component has improved so much that other components have to improve to keep up.

There's a [good paper by Todor Mollov, Louis Eisner, Arup De, Joel Coburn, and Steven Swanson](http://research.microsoft.com/pubs/198366/Asplos2012_MonetaD.pdf) on the first issue; I'm going to present one of their graphs below.

![OS and other overhead for NVRAM operations](https://danluu.com/images/clwb-pcommit/Moneta_overhead.webp)

Everything says “Moneta” because that's the name of their system (which is pretty cool, BTW; I recommend reading the paper to see how they did it). Their “baseline” case is significantly better than you'll get out of a stock system. They did a number of optimizations (e.g., bypassing Linux's IO scheduler and removing context switches where possible), which reduces latency by 62% over plain old linux. Despite that, the hardware + DMA cost of the transaction (the white part of the bar) is dwarfed by the overhead. Note that they consider the cost of the DMA to be part of the hardware overhead.

They're able to bypass the OS entirely and reduce a lot of the overhead, but it's still true that the majority of the cost of a write is overhead.

![OS bypass speedup for NVRAM operations](https://danluu.com/images/clwb-pcommit/Moneta_speedup.webp)

Despite not being able to get rid of all of the overhead, they get pretty significant speedups, both on small microbenchmarks and real code. So that's one problem. The OS imposes a pretty large tax on I/O when your I/O device is really fast.

Maybe you can bypass large parts of that problem by just mapping your NVRAM device to a region of memory and committing things to it as necessary. But that runs into another problem. which is the impedance mismatch between how caches interact with the NVRAM region if you want something like transactional semantics.

This is described [in more detail in this report by Kumud Bhandari, Dhruva R. Chakrabarti, and Hans-J. Boehm](http://www.hpl.hp.com/techreports/2012/HPL-2012-236.pdf). I'm going to borrow a couple of their figures, too.

![Rough memory hierarchy diagram](https://danluu.com/images/clwb-pcommit/HP_hierarchy.webp)

We've got this NVRAM region which is safe and persistent, but before the CPU can get to it, it has to go through multiple layers with varying ordering guarantees. They give the following example:

> Consider, for example, a common programming idiom where a persistent memory location N is allocated, initialized, and published by assigning the allocated address to a global persistent pointer p. If the assignment to the global pointer becomes visible in NVRAM before the initialization (presumably because the latter is cached and has not made its way to NVRAM) and the program crashes at that very point, a post-restart dereference of the persistent pointer will read uninitialized data. Assuming writeback (WB) caching mode, this can be avoided by inserting cache-line flushes for the freshly allocated persistent locations N before the assignment to the global persistent pointer p.

Inserting `CLFLUSH` instructions all over the place works, but how much overhead is that?

![Persistence overhead on reads and writes](https://danluu.com/images/clwb-pcommit/HP_synthetic.webp)

The four memory types they look at (and the four that x86 supports) are writeback (WB), writethrough (WT), write combine (WC), and uncacheable (UC). WB is what you deal with under normal circumstances. Memory can be cached and it's written back whenever it's forced to be. WT allows memory to be cached, but writes have to be written straight through to memory, i.e., memory is kept up to date with the cache. UC simply can't be cached. WC is like UC, except that writes can be coalesced before being sent out to memory.

The R, W, and RW benchmarks are just benchmarks of reading and writing memory. WB is clearly the best, by far (lower is better). If you want to get an intuitive feel for how much better WB is than the other policies, try booting an OS with anything but WB memory.

I've had to do that on occasion because I use to work for a chip company, and when we first got the chip back, we often didn't know which bits we had to disable to work around bugs. The simplest way to make progress is often to disable caches entirely. That “works”, but even minimal OSes like DOS are noticeably slow to boot without WB memory. My recollection is that Win 3.1 takes the better part of an hour, and that Win 95 is a multiple hour process.

The \_b benchmarks force writes to be visible to memory. For the WB case, that involves an `MFENCE` followed by a `CLFLUSH`. WB with visibility constraints is significantly slower than the other alternatives. It's a multiple order of magnitude slowdown over WB when writes don't have to be ordered and flushed.

They also run benchmarks on some real data structures, with the constraint that data should be persistently visible.

![Persistence overhead on data structure operations](https://danluu.com/images/clwb-pcommit/HP_data_structures.webp)

The performance of regular WB memory can be terribly slow: within a factor of 2 of the performance of running without caches. And that's just the overhead around getting out of the cache hierarchy -- that's true even if your persistent storage is infinitely fast.

Now, let's look how Intel decided to address this. There are two new instructions, `CLWB` and `PCOMMIT`.

`CLWB` acts like `CLFLUSH`, in that it forces the data to get written out to memory. However, it doesn't force the cache to throw away the data, which makes future reads and writes a lot faster. Also, `CLFLUSH` is only ordered with respect to `MFENCE`, but `CLWB` is also ordered with respect to `SFENCE`. Here's their description of `CLWB`:

> Writes back to memory the cache line (if dirty) that contains the linear address specified with the memory operand from any level of the cache hierarchy in the cache coherence domain. The line may be retained in the cache hierarchy in non-modified state. Retaining the line in the cache hierarchy is a performance optimization (treated as a hint by hardware) to reduce the possibility of cache miss on a subsequent access. Hardware may choose to retain the line at any of the levels in the cache hierarchy, and in some cases, may invalidate the line from the cache hierarchy. The source operand is a byte memory location.
> 
> It should be noted that processors are free to speculatively fetch and cache data from system memory regions that are assigned a memory-type allowing for speculative reads (such as, the WB, WC, and WT memory types). Because this speculative fetching can occur at any time and is not tied to instruction execution, the CLWB instruction is not ordered with respect to PREFETCHh instructions or any of the speculative fetching mechanisms (that is, data can be speculatively loaded into a cache line just before, during, or after the execution of a CLWB instruction that references the cache line).
> 
> CLWB instruction is ordered only by store-fencing operations. For example, software can use an SFENCE, MFENCE, XCHG, or LOCK-prefixed instructions to ensure that previous stores are included in the write-back. CLWB instruction need not be ordered by another CLWB or CLFLUSHOPT instruction. CLWB is implicitly ordered with older stores executed by the logical processor to the same address.
> 
> Executions of CLWB interact with executions of PCOMMIT. The PCOMMIT instruction operates on certain store-to-memory operations that have been accepted to memory. CLWB executed for the same cache line as an older store causes the store to become accepted to memory when the CLWB execution becomes globally visible.

`PCOMMIT` is applied to entire memory ranges and ensures that everything in the memory range is committed to persistent storage. Here's their description of `PCOMMIT`:

> The PCOMMIT instruction causes certain store-to-memory operations to persistent memory ranges to become persistent (power failure protected).1 Specifically, PCOMMIT applies to those stores that have been accepted to memory.
> 
> While all store-to-memory operations are eventually accepted to memory, the following items specify the actions software can take to ensure that they are accepted:
> 
> Non-temporal stores to write-back (WB) memory and all stores to uncacheable (UC), write-combining (WC), and write-through (WT) memory are accepted to memory as soon as they are globally visible. If, after an ordinary store to write-back (WB) memory becomes globally visible, CLFLUSH, CLFLUSHOPT, or CLWB is executed for the same cache line as the store, the store is accepted to memory when the CLFLUSH, CLFLUSHOPT or CLWB execution itself becomes globally visible.
> 
> If PCOMMIT is executed after a store to a persistent memory range is accepted to memory, the store becomes persistent when the PCOMMIT becomes globally visible. This implies that, if an execution of PCOMMIT is globally visible when a later store to persistent memory is executed, that store cannot become persistent before the stores to which the PCOMMIT applies.
> 
> The following items detail the ordering between PCOMMIT and other operations:
> 
> A logical processor does not ensure previous stores and executions of CLFLUSHOPT and CLWB (by that logical processor) are globally visible before commencing an execution of PCOMMIT. This implies that software must use appropriate fencing instruction (e.g., SFENCE) to ensure the previous stores-to-memory operations and CLFLUSHOPT and CLWB executions to persistent memory ranges are globally visible (so that they are accepted to memory), before executing PCOMMIT.
> 
> A logical processor does not ensure that an execution of PCOMMIT is globally visible before commencing subsequent stores. Software that requires that such stores not become globally visible before PCOMMIT (e.g., because the younger stores must not become persistent before those committed by PCOMMIT) can ensure by using an appropriate fencing instruction (e.g., SFENCE) between PCOMMIT and the later stores.
> 
> An execution of PCOMMIT is ordered with respect to executions of SFENCE, MFENCE, XCHG or LOCK-prefixed instructions, and serializing instructions (e.g., CPUID).
> 
> Executions of PCOMMIT are not ordered with respect to load operations. Software can use MFENCE to order loads with PCOMMIT.
> 
> Executions of PCOMMIT do not serialize the instruction stream.

How much `CLWB` and `PCOMMIT` actually improve performance will be up to their implementations. It will be interesting to benchmark these and see how they do. In any case, this is an attempt to solve the WB/NVRAM impedance mismatch issue. It doesn't directly address the OS overhead issue, but that can, to a large extent, be worked around without extra hardware.
