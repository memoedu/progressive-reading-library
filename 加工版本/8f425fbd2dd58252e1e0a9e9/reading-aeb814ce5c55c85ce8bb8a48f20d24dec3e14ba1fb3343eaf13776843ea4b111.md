# 无限圆盘｜Infinite disk

---

## 正文

Hardware performance “显然”会 affects software performance，也会 affects software 如何被 optimized。例如，caches 比 RAM 快多个 orders of magnitude，这意味着 [blocked array accesses](http://suif.stanford.edu/papers/lam-asplos91.pdf) 比反复 striding through an array 能提供更好的 performance。

有一点偶尔会被忽略：hardware performance 对 system design 和 architecture 也有深远影响。[让我们看看这张自 2012 年以来一直流传的 latencies 表](https://gist.github.com/jboner/2841832)：

```
Operation                                Latency (ns)     (ms)
L1 cache reference                            0.5 ns
Branch mispredict                             5   ns
L2 cache reference                            7   ns
Mutex lock/unlock                            25   ns
Main memory reference                       100   ns
Compress 1K bytes with Zippy              3,000   ns
Send 1K bytes over 1 Gbps network        10,000   ns    0.01 ms
Read 4K randomly from SSD               150,000   ns    0.15 ms
Read 1 MB sequentially from memory      250,000   ns    0.25 ms
Round trip within same datacenter       500,000   ns    0.5  ms
Read 1 MB sequentially from SSD       1,000,000   ns    1    ms
Disk seek                            10,000,000   ns   10    ms
Read 1 MB sequentially from disk     20,000,000   ns   20    ms
Send packet CA->Netherlands->CA     150,000,000   ns  150    ms
```

考虑一下 disk seek 的 latency (10ms)，再对比同一个 datacenter 内 round-trip 的 latency (.5ms)。round-trip latency 比 disk 的 seek time 低得多，因此我们可以 dis-aggregate storage，并将其 distribute 到 datacenter 内的任何位置，而不会出现明显的 performance degradation，从而让 applications 仿佛拥有 infinite disk space，同时 performance 没有任何明显变化。这一事实促成了过去二十年里 datacenter 内 GFS 等 distributed filesystems 的兴起，以及更早以前各种 networked attached storage schemes 的出现。

然而，在配有 SSDs 的 2012 年代 commodity network 上做同样的事并不可行。在 SSD 上 read 一个 page 所需的时间是 150us，而 network 上的 round-trip time 是 500us。与 spinning metal disk 相比，这仍然带来了明显的 performance improvement，但比 local SSD 慢了超过 4x。

但现在已经是 2015 年了。情况已经改变。Disks 已经快了许多。Enterprise NVRAM drives 可以在大约 15us 内完成一次 4k random read，比 2012 年的 SSDs 快一个 order of magnitude。Networks 的改善幅度更大。如今，采用 low-latency user-mode networking stack 已经比较常见，它能将一次 4k transfer 的 round-trip latencies 降至 10s of microseconds。这已经足够快，可以 disaggregate SSD，并让 applications access infinite SSD。要 disaggregate high-end NVRAM，这还不够快，但 [RDMA](https://en.wikipedia.org/wiki/RDMA_over_Converged_Ethernet) 可以做到。

![](https://danluu.com/images/infinite-disk/rdma_vs_tcp.webp)

RDMA 将 latencies 又降低了一个 order of magnitude，使 network latencies 比 NVRAM access latencies 低得足够多，因此我们可以 disaggregate NVRAM。请注意，这些 numbers 对应的是没有 congestion 的 unloaded network -- 在 load 下，这些 numbers 会大幅恶化，但它们展示了可能达到的水平。这并不是什么新 technology：HPC 领域的人多年来一直在使用 RDMA over InfiniBand，但 InfiniBand networks 的价格很高，因此在 datacenters 中并未得到广泛采用。过去几年出现的新能力，是在 Ethernet 上 run RDMA。事实证明，这并不简单；[Microsoft](http://conferences.sigcomm.org/sigcomm/2015/pdf/papers/p523.pdf) 和 [Google](http://conferences.sigcomm.org/sigcomm/2015/pdf/papers/p537.pdf) 在今年的 SIGCOMM 上都有 papers，探讨如何做到这一点，同时避免在尝试将其 scale 到不止几个 nodes 时出现的诸多问题。不过，这是可能的，而且我们正在接近这样一个阶段：即使不是规模大得惊人的公司，也将能够 deploy 这项 technology at scale[1](https://danluu.com/infinite-disk/#fn:R)。

然而，虽然很容易说，因为 network latency 与 disk latency 的 ratio 已经改变，所以我们应该使用 disaggregated disk，但事情并不像随便拿一个旧 system 放到 fast network 上那么简单。如果我们拿一个 2005 年代的 distributed filesystem 或 distributed database，将其放到 fast network 上，它并不会真正利用这个 network。那个 2005 年的 system 会有这样的 assumptions：一个 operation 花费 500ns 没什么问题，毕竟 500ns 能有多大影响？但当你的 round-trip network latency 仅仅是它的几倍时，这就影响很大了，而在 higher-latency 时代编写的 applications 往往充斥着“粗心”的 operations，每次都会消耗数百 nanoseconds。更糟的是，在 higher latencies 下 optimal 的 designs，会随着 latency 的 decreases 而产生 overhead。例如，在 latency 为 1ms 时，添加 local caching 会带来巨大收益，而 2005 年代的 high-performance distributed applications 往往会非常依赖 local caching。但当 latency 降到 1us 以下时，2005 年曾带来巨大收益的 caching 往往不仅毫无意义，实际上还会成为适得其反的 overhead。

Latency 不只是在 datacenter 内降低了。如今，我连接 YouTube 的 latency 大约是 2ms 到 3ms。YouTube、Netflix 和许多其他 services 将大量 boxes 放在靠近 consumers 的地方，以提供 high-bandwidth low-latency connections。这带来的一个附带结果是，任何拥有这类 services 之一的公司，都有能力向 consumers 提供只比 normal disk 稍慢的 infinite disk。这件事至今尚未发生，有各种各样的原因，但它最终发生基本上是不可避免的。如果你看看主要 cloud providers 为 storage 支付的费用，就会发现，它们提供 safely replicated storage 的 [COGS](https://en.wikipedia.org/wiki/Cost_of_goods_sold) 已经或将会低于我为家用 machine 上 un-backed-up unreplicated local disk 支付的 retail cost。

cloud storage 可以比 local storage 更便宜，这可能看起来很奇怪，但大型 cloud vendors 有很强的议价能力。对于它们购买的、既不是 Intel CPU 也不是 Nvidia GPU 的 median component，其价格与 retail price 相比低得惊人。此外，还有这样一个事实：大多数人在大多数时候都不会 access 他们绝大多数的 files。如果你看看如今大型 HDs 的 throughput，就会发现，甚至不可能做到这一点。一个 [typical consumer 3TB HD](http://hdd.userbenchmark.com/Toshiba-DT01ACA300-3TB/Rating/2735) 的 average throughput 为 155MB/s，因此 read 整个 drive 所需的时间为 3e12 / 155e6 seconds = 1.9e4 seconds = 5 hours and 22 minutes。而且，人们在大多数时候根本就不会 access 自己的 disks！即使他们这样做，其 access patterns 所产生的 throughput 也远低于 linearly reading 整个 disk 时能达到的 throughput。这意味着，绝大多数 disaggregated storage 都可以放在便宜的 cold storage 中。一个很巧妙的例子是，[Balakrishnan et al. 的 Pelican OSDI 2014 paper](https://www.usenix.org/system/files/conference/osdi14/osdi14-paper-balakrishnan.pdf) 展示了：如果你 build out cold storage racks，使得任意时刻只有 8% 的 disk 可以被 accessed，就能获得可观的 cost savings。只有极小一部分 storage 必须放在 edge，其原因与只有极小一部分 YouTube videos 会被 cached 在 edge 相同。从某种意义上说，其 economics 比 YouTube 更差，因为任何特定的 chunk of data 都很可能被 shared，但按照 edge compute/storage 的 scaling up 速度，十年后这不太可能成为一个有力的反对理由。

无论在 datacenter 内部还是外部，针对 disaggregated disk 最常见的 counter argument 都是 bandwidth costs。但 bandwidth costs 几十年来一直在 declining exponentially，而且仍将如此。自 1995 年以来，我们看到 datacenter NIC speeds 从 10Mb 增至 40Gb，而 50Gb 和 100Gb 也即将到来。这种增长如此迅速，以至于除了大型公司之外，几乎没有人对其 applications 进行 re-architected，以充分利用可用的 bandwidth。大多数 applications 无法 saturate 一个 10Gb NIC，更不用说 40Gb NIC 了。bandwidth 确实已经多到人们不知道该如何利用。datacenter 之外的情况变化没有这么快，但即便如此，我也只需为 100Mb 支付 $60/month；如果过去二十年的趋势继续下去，那么未来十年里，我们应该会看到 bandwidth per dollar 再增加 50x。现在还不清楚，目前的 cost structure 是否使面向 consumers、由 cloud 提供的 disaggregated disk 具有可行性，但当前 bandwidth cost 持续下降的趋势意味着，这在未来五年内将不可避免地成为现实。

有一点需要小心：[仅仅因为我们能够 disaggregate 某样东西，并不意味着我们就应该这么做](http://www.researchgate.net/profile/David_Rogers2/publication/265543548_Aggregation_and_disaggregation_techniques_and_methodology_in_optimization/links/54357d8e0cf2643ab986792e.pdf)。[Lim et. al 在 HPCA 2012 上有一篇关于 disaggregated RAM 的精彩 paper](http://web.eecs.umich.edu/~twenisch/papers/hpca12-disagg.pdf)，他们通过 backplane connecting RAM，来 build out disaggregated RAM。虽然我们具备这样做的 technology，而且它有双重优势：既能让我们以更低的 per-unit cost 来 provision RAM，又能让 provisioned RAM 获得更好的 utilization，但至少到目前为止，这似乎并不能在可接受的 performance 水平下带来 performance per dollar savings[2](https://danluu.com/infinite-disk/#fn:S)。

不同 components 的 relative performance 发生变化，会使 applications 应该如何被 designed 发生根本变化。仅仅 profile 我们的 applications 并 eliminate hot spots 是不够的。为了获得良好的 performance（或良好的 performance per dollar），我们有时必须退后一步，重新审视我们的 assumptions，并 rewrite 我们的 systems。关于 hardware improvements 正在放缓的讨论很多，而这通常指的是 CPU performance 的 improvements。这确实如此，但还有许多其他领域正在经历快速变化，这就要求关注 performance 或 cost efficiency 的 applications 必须改变。GPUs、hardware accelerators、storage 和 networking 都在以前所未有的速度演进。

#### 更新

Microsoft 在这件事上似乎并不赞同我。OneDrive 一直在朝相反的方向走。他们取消了 infinite disk，降低了 non-infinite storage tiers 的 quotas，还在改变其 sync model，使这种做法变得不那么自然。我写这篇文章可能花了一个小时。他们大概有一个 Harvard MBA 团队，花了 100x 于此的时间来讨论放弃 infinite disk。我不知道自己遗漏了什么。Average utilization 是每个 user 5GB，这几乎不花钱。少数 users 有大量 data，但如果有人 uploads 比如说 100TB，你可以把其中的大部分放在 tape 上。tape 的 Access times 慢得惊人——arm 取出 cartridge 并把它放到正确位置需要数秒，而 seek 到 tape 上的正确位置则需要数十秒。但 uploads 100TB 的人基本上本来就是把它用作 archival storage，而对于最常见的 use cases（uploading 电影或其他 media 的 libraries），你可以 mask 其中大部分 latency。如果 file 的开头部分不在 tape 上，而 user 开始 playing 一部存放在 tape 上的电影，那么在 tape access 被 queued up 的同时，这部电影完全可以先从 warmer storage 播放几分钟。你可能会说，不值得花时间 build 这样的 system（也许需要两名 engineers 工作六个月），但你本来就会需要一个能够为 large files mask 通往 disk-based cold storage 的 latency 的 system。在此基础上 Adding 另一个 tier，并不会增加多少工作。

## 原文

Hardware performance “obviously” affects software performance and affects how software is optimized. For example, the fact that caches are multiple orders of magnitude faster than RAM means that [blocked array accesses](http://suif.stanford.edu/papers/lam-asplos91.pdf) give better performance than repeatedly striding through an array.

Something that's occasionally overlooked is that hardware performance also has profound implications for system design and architecture. [Let's look at this table of latencies that's been passed around since 2012](https://gist.github.com/jboner/2841832):

```
Operation                                Latency (ns)     (ms)
L1 cache reference                            0.5 ns
Branch mispredict                             5   ns
L2 cache reference                            7   ns
Mutex lock/unlock                            25   ns
Main memory reference                       100   ns
Compress 1K bytes with Zippy              3,000   ns
Send 1K bytes over 1 Gbps network        10,000   ns    0.01 ms
Read 4K randomly from SSD               150,000   ns    0.15 ms
Read 1 MB sequentially from memory      250,000   ns    0.25 ms
Round trip within same datacenter       500,000   ns    0.5  ms
Read 1 MB sequentially from SSD       1,000,000   ns    1    ms
Disk seek                            10,000,000   ns   10    ms
Read 1 MB sequentially from disk     20,000,000   ns   20    ms
Send packet CA->Netherlands->CA     150,000,000   ns  150    ms
```

Consider the latency of a disk seek (10ms) vs. the latency of a round-trip within the same datacenter (.5ms). The round-trip latency is so much lower than the seek time of a disk that we can dis-aggregate storage and distribute it anywhere in the datacenter without noticeable performance degradation, giving applications the appearance of having infinite disk space without any appreciable change in performance. This fact was behind the rise of distributed filesystems like GFS within the datacenter over the past two decades, and various networked attached storage schemes long before.

However, doing the same thing on a 2012-era commodity network with SSDs doesn't work. The time to read a page on an SSD is 150us, vs. a 500us round-trip time on the network. That's still a noticeable performance improvement over spinning metal disk, but it's over 4x slower than local SSD.

But here we are in 2015. Things have changed. Disks have gotten substantially faster. Enterprise NVRAM drives can do a 4k random read in around 15us, an order of magnitude faster than 2012 SSDs. Networks have improved even more. It's now relatively common to employ a low-latency user-mode networking stack, which drives round-trip latencies for a 4k transfer down to 10s of microseconds. That's fast enough to disaggregate SSD and give applications access to infinite SSD. It's not quite fast enough to disaggregate high-end NVRAM, but [RDMA](https://en.wikipedia.org/wiki/RDMA_over_Converged_Ethernet) can handle that.

![](https://danluu.com/images/infinite-disk/rdma_vs_tcp.webp)

RDMA drives latencies down another order of magnitude, putting network latencies below NVRAM access latencies by enough that we can disaggregate NVRAM. Note that these numbers are for an unloaded network with no congestion -- these numbers will get substantially worse under load, but they're illustrative of what's possible. This isn't exactly new technology: HPC folks have been using RDMA over InfiniBand for years, but InfiniBand networks are expensive enough that they haven't seen a lot of uptake in datacenters. Something that's new in the past few years is the ability to run RDMA over Ethernet. This turns out to be non-trivial; both [Microsoft](http://conferences.sigcomm.org/sigcomm/2015/pdf/papers/p523.pdf) and [Google](http://conferences.sigcomm.org/sigcomm/2015/pdf/papers/p537.pdf) have papers in this year's SIGCOMM on how to do this without running into the numerous problems that occur when trying to scale this beyond a couple nodes. But it's possible, and we're approaching the point where companies that aren't ridiculously large are going to be able to deploy this technology at scale[1](https://danluu.com/infinite-disk/#fn:R).

However, while it's easy to say that we should use disaggregated disk because the ratio of network latency to disk latency has changed, it's not as easy as just taking any old system and throwing it on a fast network. If we take a 2005-era distributed filesystem or distributed database and throw it on top of a fast network, it won't really take advantage of the network. That 2005 system is going to have assumptions like the idea that it's fine for an operation to take 500ns, because how much can 500ns matter? But it matters a lot when your round-trip network latency is only few times more than that and applications written in a higher-latency era are often full of "careless" operations that burn hundreds of nanoseconds at a time. Worse yet, designs that are optimal at higher latencies create overhead as latency decreases. For example, with 1ms latency, adding local caching is a huge win and 2005-era high-performance distributed applications will often rely heavily on local caching. But when latency drops below 1us, the caching that was a huge win in 2005 is often not just pointless, but actually counter-productive overhead.

Latency hasn't just gone down in the datacenter. Today, I get about 2ms to 3ms latency to YouTube. YouTube, Netflix, and a lot of other services put a very large number of boxes close to consumers to provide high-bandwidth low-latency connections. A side effect of this is that any company that owns one of these services has the capability of providing consumers with infinite disk that's only slightly slower than normal disk. There are a variety of reasons this hasn't happened yet, but it's basically inevitable that this will eventually happen. If you look at what major cloud providers are paying for storage, their [COGS](https://en.wikipedia.org/wiki/Cost_of_goods_sold) of providing safely replicated storage is or will become lower than the retail cost to me of un-backed-up unreplicated local disk on my home machine.

It might seem odd that cloud storage can be cheaper than local storage, but large cloud vendors have a lot of leverage. The price for the median component they buy that isn't an Intel CPU or an Nvidia GPU is staggeringly low compared to the retail price. Furthermore, the fact that most people don't access the vast majority of their files most of the time. If you look at the throughput of large HDs nowadays, it's not even possible to do so. A [typical consumer 3TB HD](http://hdd.userbenchmark.com/Toshiba-DT01ACA300-3TB/Rating/2735) has an average throughput of 155MB/s, making the time to read the entire drive 3e12 / 155e6 seconds = 1.9e4 seconds = 5 hours and 22 minutes. And people don't even access their disks at all most of the time! And when they do, their access patterns result in much lower throughput than you get when reading the entire disk linearly. This means that the vast majority of disaggregated storage can live in cheap cold storage. For a neat example of this, [the Balakrishnan et al. Pelican OSDI 2014 paper](https://www.usenix.org/system/files/conference/osdi14/osdi14-paper-balakrishnan.pdf) demonstrates that if you build out cold storage racks such that only 8% of the disk can be accessed at any given time, you can get a substantial cost savings. A tiny fraction of storage will have to live at the edge, for the same reason that a tiny fraction of YouTube videos are cached at the edge. In some sense, the economics are worse than for YouTube, since any particular chunk of data is very likely to be shared, but at the rate that edge compute/storage is scaling up, that's unlikely to be a serious objection in a decade.

The most common counter argument to disaggregated disk, both inside and outside of the datacenter, is bandwidth costs. But bandwidth costs have been declining exponentially for decades and continue to do so. Since 1995, we've seen an increase in datacenter NIC speeds go from 10Mb to 40Gb, with 50Gb and 100Gb just around the corner. This increase has been so rapid that, outside of huge companies, almost no one has re-architected their applications to properly take advantage of the available bandwidth. Most applications can't saturate a 10Gb NIC, let alone a 40Gb NIC. There's literally more bandwidth than people know what to do with. The situation outside the datacenter hasn't evolved quite as quickly, but even so, I'm paying $60/month for 100Mb, and if the trend of the last two decades continues, we should see another 50x increase in bandwidth per dollar over the next decade. It's not clear if the cost structure makes cloud-provided disaggregated disk for consumers viable today, but the current trends of implacably decreasing bandwidth cost mean that it's inevitable within the next five years.

One thing to be careful about is that [just because we can disaggregate something, it doesn't mean that we should](http://www.researchgate.net/profile/David_Rogers2/publication/265543548_Aggregation_and_disaggregation_techniques_and_methodology_in_optimization/links/54357d8e0cf2643ab986792e.pdf). There was a [fascinating paper by Lim et. al at HPCA 2012 on disaggregated RAM](http://web.eecs.umich.edu/~twenisch/papers/hpca12-disagg.pdf) where they build out disaggregated RAM by connecting RAM through the backplane. While we have the technology to do this, which has the dual advantages of allowing us to provision RAM at a lower per-unit cost and also getting better utilization out of provisioned RAM, this doesn't seem to provide a performance per dollar savings at an acceptable level of performance, at least so far[2](https://danluu.com/infinite-disk/#fn:S).

The change in relative performance of different components causes fundamental changes in how applications should be designed. It's not sufficient to just profile our applications and eliminate the hot spots. To get good performance (or good performance per dollar), we sometimes have to step back, re-examine our assumptions, and rewrite our systems. There's a lot of talk about how hardware improvements are slowing down, which usually refers to improvements in CPU performance. That's true, but there are plenty of other areas that are undergoing rapid change, which requires that applications that care about either performance or cost efficiency need to change. GPUs, hardware accelerators, storage, and networking are all evolving more rapidly than ever.

#### Update

Microsoft seems to disagree with me on this one. OneDrive has been moving in the opposite direction. They got rid of infinite disk, lowered quotas for non-infinite storage tiers, and changing their sync model in a way that makes this less natural. I spent maybe an hour writing this post. They probably have a team of Harvard MBAs who've spent 100x that much time discussing the move away from infinite disk. I wonder what I'm missing here. Average utilization was 5GB per user, which is practically free. A few users had a lot of data, but if someone uploads, say, 100TB, you can put most of that on tape. Access times on tape are glacial -- seconds for the arm to get the cartridge and put it in the right place, and tens of seconds to seek to the right place on the tape. But someone who uploads 100TB is basically using it as archival storage anyway, and you can mask most of that latency for the most common use cases (uploading libraries of movies or other media). If the first part of the file doesn't live on tape, and the user starts playing a movie that lives on tape, the movie can easily play for a couple minutes off of warmer storage while the tape access gets queued up. You might say that it's not worth it to spend the time it would take to build a system like that (perhaps two engineers working for six months), but you're already going to want a system that can mask the latency to disk-based cold storage for large files. Adding another tier on top of that isn't much additional work.

#### Update 2

It's happening. In April 2016, Dropbox announced that they're offering "Dropbox Infinite", which lets you access your entire Dropbox regardless of the amount of local disk you have available. The inevitable trend happened, although I'm a bit surprised that it wasn't Google that did it first since they have better edge infrastructure and almost certainly pay less for storage. In retrospect, maybe that's not surprising, though -- Google, Microsoft, and Amazon all treat providing user-friendly storage as a second class citizen, while Dropbox is all-in on user friendliness.

If your goal is to get better utilization, the poor man's solution today is to give applications access to unused RAM via RDMA on a best effort basis, in a way that's vaguely kinda sorta analogous to [Google's Heracles work](https://danluu.com/intel-cat/). You might say, wait a second: you could make that same argument for disk, but in fact the cheapest way to build out disk is to build out very dense storage blades full of disks, not to just use RDMA to access the normal disks attached to standard server blades; why shouldn't that be true for RAM? For an example of what it looks like when disks, I/O, and RAM are underprovisioned compared to CPUs, [see this article where a Mozilla employee claims that it's fine to have 6% CPU utilization because those machines are busy doing I/O](http://www.wired.com/2012/10/data-center-servers/). Sure, it's fine, if you don't mind paying for CPUs you're not using instead of building out blades that have the correct ratio of disk to storage, but those idle CPUs aren't free.

    If the ratio of RAM to CPU we needed were analogous to the ratio of disk to CPU that we need, it might be cheaper to disaggregate RAM. But, while [the need for RAM is growing faster than the need for compute](http://web.eecs.umich.edu/~twenisch/papers/isca09-disaggregate.pdf), we're still not yet at the point where datacenters have a large number of cores sitting idle due to lack of RAM, the same way we would have cores sitting idle due to lack of disk if we used standard server blades for storage. A Xeon-EX can handle 1.5TB of RAM per socket. It's common to put two sockets in a 1/2U blade nowadays, and for the vast majority of workloads, it would be pretty unusual to try to cram more than 6TB of RAM into the 4 sockets you can comfortably fit into 1U.

    That being said, the issue of disaggregated RAM is still an open question, and [some folks](https://www.usenix.org/conference/srecon15europe/program/presentation/hoffman) are a lot more confident about its near-term viability [than others](http://arxiv.org/abs/1503.01416).
