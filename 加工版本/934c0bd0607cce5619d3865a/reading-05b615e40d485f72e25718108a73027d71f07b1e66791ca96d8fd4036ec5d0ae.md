# 慢锁｜Slowlock

---

## 正文

偶尔，你会听到这样的故事：“曾经有一台 machine 上的 1-Gbps NIC card 突然只以 1 Kbps 进行 transmitting，随后在 upstream 引发了 chain reaction，导致整个 100-node cluster 的全部 workload 的 performance 慢得像蜗牛爬一样，实际上使这个 system 在任何实际用途上都变得 unavailable。”这些故事很有意思，postmortems 读起来也很有趣，但 systems 对这种 failure 究竟有多 vulnerable，以及这些 failures 有多 prevalent，其实并不清楚。

这种情况让我想起 [Jepsen](https://aphyr.com/tags/jepsen) 出现以前的 distributed systems failures。有很多道听途说的可怕故事，但人们对此常见的回应是“我用着没问题”，即使谈论的是如今已知 broken 得极其严重的 systems，也依然如此。少数真正重视 correctness 的公司有良好的 tests 和 metrics，但它们大多不会公开谈论这些，而普通人也没有简单的办法判断自己正在 running 的 systems 是否 sound。

Thanh Do 等人尝试 systematically 考察这个问题——[被 crippled 却没有被 killed 的 hardware 会产生什么 effect](http://ucare.cs.uchicago.edu/pdf/socc13-limplock.pdf)，以及[这种情况在实践中多久发生一次](http://ucare.cs.uchicago.edu/pdf/socc14-cbs.pdf)？结果发现，许多常用的 systems 面对“limping” hardware 时并不 robust，但这类 failures 的 incidence 很低（至少在 scale 大到不合理之前是如此）。

单个 slow node 的 effect 可能[相当 dramatic](http://pages.cs.wisc.edu/~thanhdo/pdf/talk-socc-limplock.pdf)：

![单个 slow NIC 对整个 cluster 的 effect](https://danluu.com/images/limpware/fb_slow_nic.webp)

job completion rate 从每小时 172 jobs 降至每小时 1 job，实际上 killing 了整个 cluster。Facebook 有应对 dead machines 的 mechanisms，但当时它们显然没有任何办法应对 slow machines。

当 Do 等人考察广泛使用的 open source software（HDFS、Hadoop、ZooKeeper、Cassandra 和 HBase）时，他们发现了类似的问题。

![](https://danluu.com/images/limpware/limpware.webp)

每个 subgraph 都是一种不同的 failure condition。F 是 HDFS，H 是 Hadoop，Z 是 Zookeeper，C 是 Cassandra，B 是 HBase。最左侧的（白色）bar 是 baseline no-failure case。向右看，下一个是 crash，后面的 bars 则是单个 degraded 但没有 crashed 的 hardware 所对应的 results（越靠右表示越 slower）。在大多数（但并非全部）cases 中，degraded hardware 对 performance 的影响远大于 failed hardware。注意，这些 graphs 全都采用 log scale；向上一个 increment 就意味着 performance 有 10x 的 difference！

有意思的是，failed disk 可能使某些 operations speed up。这是因为某些 operations 在 replica fails 时会有更少的 replication overhead。没有更多的 overhead 让我觉得有点奇怪，因为 system 既要找到 replacement replica，又要 replicate data，不过我又懂什么呢？

话说回来，为什么 slow node 会比 dead node 糟糕那么多？作者们 define 了三种 failure modes，并解释了各自的 causes。其一是 operation limplock，即某个 operation 因为其某个 subpart 是 slow 而变得 slow（例如，disk read 因为 disk 是 degraded 而变得 slow）；其二是 node limplock，即某个 node 即使执行看似 unrelated operations 也会 slow（例如，从 RAM 进行的 read 因为 disk 是 degraded 而变得 slow）；其三是 cluster limplock，即整个 cluster 都变得 slow（例如，单个 degraded disk 使整个 1000 machine cluster 变得 slow）。

这些情况是怎么发生的？

#### Operation Limplock（操作跛锁）

这一种最简单。如果你尝试从 disk 进行 read，而你的 disk 是 slow，那么你的 disk read 就会是 slow。在现实中，当 operations 存在 single point of failure，且 monitoring 被设计为处理 total failure 而不是 degraded performance 时，我们就会看到这种情况。例如，对某个 region 的 HBase access 要经过负责该 region 的 server。data 在 HDFS 上是 replicated 的，但如果拥有这些 data 的 node 正在 limping，这就帮不上忙。说到 HDFS，它的 timeout 是 60s，而且 reads 以 64K chunks 进行，这意味着你的 reads 可以 slow down 到接近 1K/s，HDFS 才会 fail over 到 healthy node。

#### Node Limplock（节点跛锁）

怎么会出现（例如）slow disk 导致 memory reads 也变得 slow 的情况呢？再看 HDFS，它使用 thread pool。如果每个 thread 都忙于 very slowly completing 一次 disk read，那么 memory reads 就会 block，直到某个 thread 变得 free。

这不只是在使用 limited thread pools 或其他 bounded abstractions 时才会出现的问题——现实是，machines 拥有 finite resources，而 unbounded abstractions 如果没有经过精心设计来避免这种可能性，就会碰到 machine limits。例如，Zookeeper 维护着 operations 的 queue，而 slow follower 可能导致 leader 的 queue exhaust physical memory。

#### Cluster Limplock（集群跛锁）

如果整个 cluster 依赖单个 primary，而这个 primary 正在 limping，那么整个 cluster 很容易变得 unhealthy。Cascading failures 也可能造成这种情况——第一张 graph 中，cluster 从每小时 completing 172 jobs 降至每小时 1 job，那实际上是 Hadoop 上的一个 Facebook workload。这里让我惊讶的是，Hadoop 本应是 tail tolerant 的——个别 slow tasks 本不应对整个 job 的 completion 产生很大影响。那么发生了什么？Unhealthy nodes 会 infect healthy nodes，最终 lock up 整个 cluster。

![一个 unhealthy node 会 infect 整个 cluster](https://danluu.com/images/limpware/cascade.webp)

Hadoop 的 tail tolerance 来自这样一种做法：当 results 到达得 slowly 时，启动 speculative computation。具体来说，就是当 stragglers 相比其他 results 到达得 unusually slowly 时。当 reduce node 正在 limping 时，这种做法运行良好（subgraph H2）；但当 [map node](http://static.googleusercontent.com/media/research.google.com/en//archive/mapreduce-osdi04.pdf) 出现 limps 时（subgraph H1），它可能 slow down 同一 job 中的所有 reducers，从而使 Hadoop 的 tail-tolerance mechanisms 失效。

![单个 bad map node 实际上会 deadlocks hadoop](https://danluu.com/images/limpware/hadoop_deadlock.png)

要理解原因，我们得看看 [Hadoop 的 speculation algorithm](https://www.usenix.org/legacy/event/osdi08/tech/full_papers/zaharia/zaharia_html/index.html)。每个 job 都有一个 progress score，它是介于 0 和 1 之间的 number（inclusive）。对于 map，这个 score 是已 read 的 input data 的 fraction。对于 reduce，三个 phases（从 mappers 进行 copying data、sorting 和 reducing）各占 score 的 1/3。如果某个 task 已经 run 了至少一分钟，并且其 progress score less than 所属 category 的 average minus 0.2，就会 run 一个 speculative job。

在 case H2 中，NIC 正在 limping，因此 map phase 会 completes normally，因为 results 最终会被 written 到 local disk。但当 reduce nodes 尝试从 limping map node 进行 fetch data 时，它们全都会 stall，拉低该 category 的 average score，从而阻止 speculative jobs 被 run。从整体来看，每个 Hadoop node 能容纳的 map 和 reduce tasks 数量是 limited 的。如果这些位置全被 limping tasks 占满，整个 node 就会 lock up。由于 Hadoop 并没有被设计为避免 cascading failures，这最终会导致整个 cluster lock up。

有一点让我觉得很有意思：这一模一样的 failures 的 cause，早已[在最初的 MapReduce paper 中被 described](http://research.google.com/archive/mapreduce.html)，那篇 paper 发表于 2004。他们甚至明确指出 slow disk 和 network 是 stragglers 的 causes，这促使他们提出了 speculative execution algorithm。然而，他们并没有提供 algorithm 的细节。作为 MapReduce 的 open source clone，Hadoop 也曾尝试避免同样的问题。Hadoop 最初 released 于 2008。五年后，在我们正在读的这篇 paper 发表时，它用于 straggler detection 的 built-in mechanism 不仅未能防止多种类型的 stragglers，也未能防止 stragglers 实际上 deadlocking 整个 cluster。

### 结论（Conclusion）

我不打算详细介绍每个 system 在 testing 中的表现。那篇 paper 已经对此作了相当详尽的说明，如果你好奇，我建议读一读。总的来说，Cassandra 表现相当好，而 HDFS、Hadoop 和 HBase 则不然。

Cassandra 似乎表现良好，有两个原因。首先，[2009 年的这个 patch](https://issues.apache.org/jira/browse/CASSANDRA-488) prevents queue overflows，使其无法 infecting healthy nodes，从而 prevents 一种主要的 failure mode；这种 failure mode 会在其他 systems 中 causes cluster-wide failures。其次，所采用的 architecture（[SEDA](http://www.eecs.harvard.edu/~mdw/proj/seda/)）会 decouples 不同 types 的 operations，使 good operations 即使在某些 operations 正在 limping 时，也能继续 execute。

读完这篇 paper 后，我最想问的是：这类 failures 多久发生一次，是如何发生的，以及合理的 metrics/reporting 难道不应该无论如何都能 catch 这类情况吗？

关于第一个问题的答案，其中许多作者还合写了另一篇 paper，考察了 [Cassandra、Flume、HDFS 和 ZooKeeper 中的 3000 次 failures](http://ucare.cs.uchicago.edu/pdf/socc14-cbs.pdf)，并确定了哪些 failures 是 hardware related，以及具体的 hardware failure 是什么。

![](https://danluu.com/images/limpware/hardware_failure_causes.webp)

14 起 degraded performance，对比 410 起其他 hardware failures。在他们的 sample 中，前者占 failures 的 3%；虽然少见，却还没有少到可以让我们忽略这个问题。

如果我们不能忽略这类 errors，那么怎样才能在它们进入 production 之前 catch 它们呢？这篇 paper 使用了 [Emulab testbed](http://www.emulab.net/)，确实很酷。遗憾的是，Emulab 页面上写着：“Emulab 是一项公共设施，向全球大多数研究人员免费开放。如果你不确定自己是否符合使用资格，请参阅我们的政策文档，或向我们咨询。如果你认为自己符合资格，可以申请启动一个新 project。”这可以理解，但也意味着，对我们大多数人来说，它可能并不是一个很好的 solution。

绝大多数 limping hardware 都是由 network 或 disk slowness 引起的。为什么不能用 Jepsen 的某个 modified version，或类似的东西，来 simulate disk 或 network slowness 呢？一个 naive implementation 远远达不到 Emulab 的 precision，但既然我们讨论的是 order of magnitude slowdowns，那么存在 10%（甚至 2x）的 variance，对于 testing systems 针对 degraded hardware 的 robustness 应该也可以接受。可以设想出不少实现方式。例如，要在 linux 上 simulate 一个 slow network，可以尝试[通过 qdisc](http://linux-ip.net/articles/Traffic-Control-HOWTO/) 来 throttling，或[通过 ptrace 来 hooking syscalls](https://github.com/majek/fluxcapacitor)，等等。对于 slow CPU，可以通过 cgroups 和 cpu.shares 来 rate-limit，或者直接将 process 进行 map 到 UC memory（如果这样有点太 slow，也许可以用 WT 或 WC）；对于 disk 和其他 failure modes，也可以依此类推。

这样就剩下我最后一个问题了：即使 systems 并不特别关注这类 failures，难道它们不应该已经能够 catch 这些 failures 吗？正如上文所见，存在 cripplingly slow hardware 的 systems 足够少，因此我们完全可以将它们视为 dead，而不会 significantly impacting 我们的 total compute resources。而且，存在 crippled hardware 的 systems 也可以相当直接地被 detected。此外，multi-tenant systems 无论如何都必须[对自身的 performance 进行 continuous monitoring，以获得 good utilization](https://danluu.com/new-cpu-features/#partitioning)。

那么，我们为什么还要关心如何 designing 对 limping hardware 具有 robust 特性的 systems 呢？答案的一部分是 defense in depth。当然，我们应该有 monitoring，但我们也应该有在 monitoring fails 时仍然 robust 的 systems，因为 monitoring 不可避免地会 fails。答案的另一部分是，让 systems 对 limping hardware 更加 tolerant，也会让它们对 multi-tenant environment 中其他 workloads 带来的 interference 更加 tolerant。最后这一点是一个带有一定推测性的 empirical question——也许 designing 并不特别 robust 于同一 machine 上 competing work 所带来的 interference 的 systems，同时使用 [better partitioning](https://danluu.com/intel-cat/) 来 avoid interference，会更 efficient。

感谢 Leah Hanson、Hari Angepat、Laura Lindzey、Julia Evans 和 James M. Lee 提供意见并参与讨论。

## 原文

Every once in awhile, you hear a story like “there was a case of a 1-Gbps NIC card on a machine that suddenly was transmitting only at 1 Kbps, which then caused a chain reaction upstream in such a way that the performance of the entire workload of a 100-node cluster was crawling at a snail's pace, effectively making the system unavailable for all practical purposes”. The stories are interesting and the postmortems are fun to read, but it's not really clear how vulnerable systems are to this kind of failure or how prevalent these failures are.

The situation reminds me of distributed systems failures before [Jepsen](https://aphyr.com/tags/jepsen). There are lots of anecdotal horror stories, but a common response to those is “works for me”, even when talking about systems that are now known to be fantastically broken. A handful of companies that are really serious about correctness have good tests and metrics, but they mostly don't talk about them publicly, and the general public has no easy way of figuring out if the systems they're running are sound.

Thanh Do et al. have tried to look at this systematically -- [what's the effect of hardware that's been crippled but not killed](http://ucare.cs.uchicago.edu/pdf/socc13-limplock.pdf), and [how often does this happen in practice](http://ucare.cs.uchicago.edu/pdf/socc14-cbs.pdf)? It turns out that a lot of commonly used systems aren't robust against against “limping” hardware, but that the incidence of these types of failures are rare (at least until you have unreasonably large scale).

The effect of a single slow node can be [quite dramatic](http://pages.cs.wisc.edu/~thanhdo/pdf/talk-socc-limplock.pdf):

![The effect of a single slow NIC on an entire cluster](https://danluu.com/images/limpware/fb_slow_nic.webp)

The job completion rate slowed down from 172 jobs per hour to 1 job per hour, effectively killing the entire cluster. Facebook has mechanisms to deal with dead machines, but they apparently didn't have any way to deal with slow machines at the time.

When Do et al. looked at widely used open source software (HDFS, Hadoop, ZooKeeper, Cassandra, and HBase), they found similar problems.

![](https://danluu.com/images/limpware/limpware.webp)

Each subgraph is a different failure condition. F is HDFS, H is Hadoop, Z is Zookeeper, C is Cassandra, and B is HBase. The leftmost (white) bar is the baseline no-failure case. Going to the right, the next is a crash, and the subsequent bars are results for a single degraded but not crashed hardware (further right means slower). In most (but not all) cases, having degraded hardware affected performance a lot more than having failed hardware. Note that these graphs are all log scale; going up one increment is a 10x difference in performance!

Curiously, a failed disk can cause some operations to speed up. That's because there are operations that have less replication overhead if a replica fails. It seems a bit weird to me that there isn't more overhead, because the system has to both find a replacement replica and replicate data, but what do I know?

Anyway, why is a slow node so much worse than a dead node? The authors define three failure modes and explain what causes each one. There's operation limplock, when an operation is slow because some subpart of the operation is slow (e.g., a disk read is slow because the disk is degraded), node limplock, when a node is slow even for seemingly unrelated operations (e.g, a read from RAM is slow because a disk is degraded), and cluster limplock, where the entire cluster is slow (e.g., a single degraded disk makes an entire 1000 machine cluster slow).

How do these happen?

#### Operation Limplock

This one is the simplest. If you try to read from disk, and your disk is slow, your disk read will be slow. In the real world, we'll see this when operations have a single point of failure, and when monitoring is designed to handle total failure and not degraded performance. For example, an HBase access to a region goes through the server responsible for that region. The data is replicated on HDFS, but this doesn't help you if the node that owns the data is limping. Speaking of HDFS, it has a timeout is 60s and reads are in 64K chunks, which means your reads can slow down to almost 1K/s before HDFS will fail over to a healthy node.

#### Node Limplock

How can it be the case that (for example) a slow disk causes memory reads to be slow? Looking at HDFS again, it uses a thread pool. If every thread is busy very slowly completing a disk read, memory reads will block until a thread gets free.

This isn't only an issue when using limited thread pools or other bounded abstractions -- the reality is that machines have finite resources, and unbounded abstractions will run into machine limits if they aren't carefully designed to avoid the possibility. For example, Zookeeper keeps queue of operations, and a slow follower can cause the leader's queue to exhaust physical memory.

#### Cluster Limplock

An entire cluster can easily become unhealthy if it relies on a single primary and the primary is limping. Cascading failures can also cause this -- the first graph, where a cluster goes from completing 172 jobs an hour to 1 job an hour is actually a Facebook workload on Hadoop. The thing that's surprising to me here is that Hadoop is supposed to be tail tolerant -- individual slow tasks aren't supposed to have a large impact on the completion of the entire job. So what happened? Unhealthy nodes infect healthy nodes and eventually lock up the whole cluster.

![An unhealthy node infects an entire cluster](https://danluu.com/images/limpware/cascade.webp)

Hadoop's tail tolerance comes from kicking off speculative computation when results are coming in slowly. In particular, when stragglers come in unusually slowly compared to other results. This works fine when a reduce node is limping (subgraph H2), but when a [map node](http://static.googleusercontent.com/media/research.google.com/en//archive/mapreduce-osdi04.pdf) limps (subgraph H1), it can slow down all reducers in the same job, which defeats Hadoop's tail-tolerance mechanisms.

![A single bad map node effectively deadlocks hadoop](https://danluu.com/images/limpware/hadoop_deadlock.png)

To see why, we have to look at [Hadoop's speculation algorithm](https://www.usenix.org/legacy/event/osdi08/tech/full_papers/zaharia/zaharia_html/index.html). Each job has a progress score which is a number between 0 and 1 (inclusive). For a map, the score is the fraction of input data read. For a reduce, each of three phases (copying data from mappers, sorting, and reducing) gets 1/3 of the score. A speculative job will get run if a task has run for at least one minute and has a progress score that's less than the average for its category minus 0.2.

In case H2, the NIC is limping, so the map phase completes normally since results end up written to local disk. But when reduce nodes try to fetch data from the limping map node, they all stall, pulling down the average score for the category, which prevents speculative jobs from being run. Looking at the big picture, each Hadoop node has a limited number of map and reduce tasks. If those fill up with limping tasks, the entire node will lock up. Since Hadoop isn't designed to avoid cascading failures, this eventually causes the entire cluster to lock up.

One thing I find interesting is that this exact cause of failures was [described in the original MapReduce paper](http://research.google.com/archive/mapreduce.html), published in 2004. They even explicitly called out slow disk and network as causes of stragglers, which motivated their speculative execution algorithm. However, they didn't provide the details of the algorithm. The open source clone of MapReduce, Hadoop, attempted to avoid the same problem. Hadoop was initially released in 2008. Five years later, when the paper we're reading was published, its built-in mechanism for straggler detection not only failed to prevent multiple types of stragglers, it also failed to prevent stragglers from effectively deadlocking the entire cluster.

### Conclusion

I'm not going to go into details of how each system fared under testing. That's detailed quite nicely in the paper, which I recommend reading the paper if you're curious. To summarize, Cassandra does quite well, whereas HDFS, Hadoop, and HBase don't.

Cassandra seems to do well for two reasons. First, [this patch from 2009](https://issues.apache.org/jira/browse/CASSANDRA-488) prevents queue overflows from infecting healthy nodes, which prevents a major failure mode that causes cluster-wide failures in other systems. Second, the architecture used ([SEDA](http://www.eecs.harvard.edu/~mdw/proj/seda/)) decouples different types of operations, which lets good operations continue to execute even when some operations are limping.

My big questions after reading this paper are, how often do these kinds of failures happen, how, and shouldn't reasonable metrics/reporting catch this sort of thing anyway?

For the answer to the first question, many of the same authors also have a paper where they looked at [3000 failures in Cassandra, Flume, HDFS, and ZooKeeper](http://ucare.cs.uchicago.edu/pdf/socc14-cbs.pdf) and determined which failures were hardware related and what the hardware failure was.

![](https://danluu.com/images/limpware/hardware_failure_causes.webp)

14 cases of degraded performance vs. 410 other hardware failures. In their sample, that's 3% of failures; rare, but not so rare that we can ignore the issue.

If we can't ignore these kinds of errors, how can we catch them before they go into production? The paper uses the [Emulab testbed](http://www.emulab.net/), which is really cool. Unfortunately, the Emulab page reads “Emulab is a public facility, available without charge to most researchers worldwide. If you are unsure if you qualify for use, please see our policies document, or ask us. If you think you qualify, you can apply to start a new project.”. That's understandable, but that means it's probably not a great solution for most of us.

The vast majority of limping hardware is due to network or disk slowness. Why couldn't a modified version of Jepsen, or something like it, simulate disk or network slowness? A naive implementation wouldn't get anywhere near the precision of Emulab, but since we're talking about order of magnitude slowdowns, having 10% (or even 2x) variance should be ok for testing the robustness of systems against degraded hardware. There are a number of ways you could imagine that working. For example, to simulate a slow network on linux, you could try throttling [via qdisc](http://linux-ip.net/articles/Traffic-Control-HOWTO/), [hooking syscalls via ptrace](https://github.com/majek/fluxcapacitor), etc. For a slow CPU, you can rate-limit via cgroups and cpu.shares, or just map the process to UC memory (or maybe WT or WC if that's a bit too slow), and so on and so forth for disk and other failure modes.

That leaves my last question, shouldn't systems already catch these sorts of failures even if they're not concerned about them in particular? As we saw above, systems with cripplingly slow hardware are rare enough that we can just treat them as dead without significantly impacting our total compute resources. And systems with crippled hardware can be detected pretty straightforwardly. Moreover, multi-tenant systems have to do [continuous monitoring of their own performance to get good utilization](https://danluu.com/new-cpu-features/#partitioning) anyway.

So why should we care about designing systems that are robust against limping hardware? One part of the answer is defense in depth. Of course we should have monitoring, but we should also have systems that are robust when our monitoring fails, as it inevitably will. Another part of the answer is that by making systems more tolerant to limping hardware, we'll also make them more tolerant to interference from other workloads in a multi-tenant environment. That last bit is a somewhat speculative empirical question -- it's possible that it's more efficient to design systems that aren't particularly robust against interference from competing work on the same machine, while using [better partitioning](https://danluu.com/intel-cat/) to avoid interference.
