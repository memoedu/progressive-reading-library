# CPU 后门｜CPU backdoors

---

## 正文

人们普遍认为，任何 software 都可能因 backdoor 而被 compromised。著名的例子包括 [Sony/BMG installer](http://en.wikipedia.org/wiki/Sony_BMG_copy_protection_rootkit_scandal)，它有 built-in backdoor，让 Sony 能阻止 users copying CD，而这也让 malicious third-parties 能够 take over 任何 installed 了该 software 的 machine；[Samsung Galaxy](http://redmine.replicant.us/projects/replicant/wiki/SamsungGalaxyBackdoor)，它有一个 backdoor，允许 modem access device 的 filesystem，这也让任何 running [fake base station 的人都能 access device 上的 files](https://www.youtube.com/watch?v=RXqQioV_bpo)；[Lotus Notes](http://www.cypherspace.org/adam/hacks/lotus-nsa-key.html)，它有一个 backdoor，使 encryption 能被 defeated；以及 [Lenovo laptops](https://forums.lenovo.com/t5/Lenovo-P-Y-and-Z-series/Lenovo-Pre-instaling-adware-spam-Superfish-powerd-by/td-p/1726839)，它们为了 push ads，将所有 web traffic 都 pushed 经过一个 proxy（包括 HTTPS，通过一个 trusted root certificate），使任何拥有正确 key 的人（该 key 被 distributed 在每台 laptop 上）都能 intercept HTTPS traffic。

尽管已经在 [FPGAs](http://www.cl.cam.ac.uk/~sps32/sec_news.html#Assurance) 和 [networking gear](https://github.com/elvanderb/TCP-32764) 中发现了 backdoors，但每当有人提出 CPU backdoors 的可能性时，仍然经常有人声称这是 [impossible](https://news.ycombinator.com/item?id=6147767) 的。我不会声称 CPU backdoors 确实存在，但我会说，只要你拥有合适的 access，implementation 就很容易。

假设你想制作一个 backdoor。你会怎么做？这包含三个部分：一个 backdoored CPU 能做什么，如何 accessed 这个 backdoor，以及 install 这个 backdoor 需要哪种 compromise？

先从第一项开始，backdoor 要做什么？可能性有很多。最简单的是允许 privilege escalation：让 CPU [transition from ring3 to ring0 or SMM](http://en.wikipedia.org/wiki/Protection_ring)，赋予 running process 以 kernel-level privileges。由于执行此操作的是 CPU，因此这可以 punch through hardware 和 software virtualization。你还可以做很多更 subtler 或更 invasive 的事情，但 privilege escalation 已经足够 simple，也足够 powerful，所以我不打算讨论其他选项。

既然你已经知道想让 backdoor 做什么，那么应该如何让它 triggered？理想情况下，它应当是在寻找 backdoors 时，没有人会偶然遇到、甚至无法通过 brute force 遇到的东西。即使有这一限制，可能的 triggers 的 state space 仍然是 huge 的。

我们来看一个特定的 instruction，`fyl2x`[1](https://danluu.com/cpu-backdoors/#fn:I)。在 normal operation 下，它以两个 floating point registers 作为 input，让你有 `2*80=160` bits 可以用来 hide 一个 trigger。如果你根据一对特定的 values 来 trigger backdoor，那么它大概不会被 random discovery。如果你真的担心有人偶然发现这个 backdoor，或者对疑似 backdoor 进行 brute forcing，你可以 check 不止那两个 normal input registers（毕竟，你拥有对 CPU 的 control）。

这个 trigger 很不错，也很 simple，但缺点是 hitting 这个 trigger 很可能需要 executing native code，因为你不太可能让 chrome 或 Firefox emit 一个 `fyl2x` instruction。你可以尝试绕过这个问题，改为根据一个你很容易让 JavaScript engine emit 的 instruction 来 triggering（比如 `fadd`）。这样做的问题在于，如果你 patch 一个 add instruction，并给它添加一些 checks，它就会变得 noticeably slower（不过，如果你能 edit hardware，你应该能在没有 overhead 的情况下做到）。通过 patching 一个 [rep string](http://www.csc.depauw.edu/~bhoward/asmtut/asmtut7.html) instruction，并做些操作来 set up 合适的“key”，然后进行 block copy，或者也许使用 `idiv`，或许就能制作出难以 detect、却能通过 JavaScript triggerable 的东西。另一种办法是，如果你已经设法拿到一份 design，你大概可以想出一种方法，利用 debug logic triggers[2](https://danluu.com/cpu-backdoors/#fn:D) 或 performance counters，在某段 arbitrary JavaScript 被 run 时 set off 一个 backdoor。

好了，现在你有了一个 backdoor。你要如何 insert 这个 backdoor？在 software 中，你会 edit source 或 [binary](https://danluu.com/edit-binary/)。在 hardware 中，如果你拥有对 source 的 access，你就可以像在 software 中一样轻松地 edit 它。hardware 中相当于 recompiling source 的操作，也就是 creating physical chips，有着极高的 fixed costs；如果你想把自己的 changes 放进 source，你就需要要么 compromise design[3](https://danluu.com/cpu-backdoors/#fn:A)，在所有东西被送去 manufactured 之前 insert 你的 edits，要么 compromise manufacturing process，在最后一刻偷偷加入你的 edits[4](https://danluu.com/cpu-backdoors/#fn:E)。

如果这听起来太难，你可以尝试 compromising patch mechanism。大多数现代 CPUs 都有一个 built-in patch mechanism，以便事后进行 bug fixes。你正在使用的 CPU 很可能已经被 patched，可能从第一天起就是如此，也可能是作为 firmware update 的一部分。你的 CPU 的 patch mechanism 的细节是严加保守的秘密。CPU 很可能有一个 etched 到其中的 public key，而且它只会 accept 由正确的 private key signed 的 patch。

这真的正在发生吗？我不知道。这有可能正在发生吗？绝对有可能。概率有多大？嗯，主要挑战是 non-technical 的，所以我不是适合回答这个问题的人。如果一定要猜，我会说没有，哪怕仅仅是因为 [subverting 其他 equipment 很容易](https://github.com/elvanderb/TCP-32764)。

我还没有讨论如何制作这样的 backdoor：即使有人能够 access 你曾用来 trigger backdoor 的 software，它也依然难以 detect。那更难，但一旦 chips 开始配有 built-in [TPMs](http://en.wikipedia.org/wiki/Trusted_Platform_Module)，应该就有可能做到。

[AMD 的 K7 和 K8 的 microcode patch mechanisms 曾遭到 compromised](http://www.realworldtech.com/forum/?threadid=35566&curpostid=35566)，使得本文提到的那类 attacks 成为可能。原来，AMD 既没有 encrypt updates，也没有用 checksum 来 validate 它们，因此你可以轻易 modify updates，直到得到一个能按你的意愿行事的 update。

[这里有一个为演示而 created 的 backdoor 的 example](http://es.slideshare.net/ortegaalfredo/deep-submicronbackdoorsortegasyscan2014slides)，出自 Alfredo Ortega。

对于没有 hardware 背景的读者，[这个介绍如何用 VHDL 来 implement CPU 的演讲很不错，其中还有一节介绍如何 implement backdoor](http://media.ccc.de/browse/congress/2013/30C3_-_5443_-_en_-_saal_g_-_201312281830_-_introduction_to_processor_design_-_byterazor.html#video)。

能否通过提供 bad random results 来 backdoor RDRAND？可以。我在本文初稿中提过这一点，但后来删掉了，因为我的印象是，人们并不信任 RDRAND，而且会将 results 与其他 sources of entropy 进行 mix。这并不会让 backdoor 变得 useless，但会显著 reduces 它的 value。

能否 store 和 dump AES-NI keys？要在无人察觉的情况下将 flash memory 偷偷放到 chip 上，大概是 infeasible 的，但现代 chips 有 logic analyzer facilities，可以让你 store 和 dump data。不过，对这些 facilities 的 access 要通过某种 secret mechanism，而且甚至连如何获得能让你 reverse engineer 其 operation 的 binaries 都不清楚。这与 K8 reverse engineering 形成了鲜明对比；后者之所以可行，是因为 microcode patches 会被 included 在 firmware updates 中。

可以 check instruction prefixes 来寻找 trigger。x86 允许你在 instructions 上放置 redundant（而且 contradictory）的 instruction prefixes。哪些 prefixes 会被 used 是 well defined 的，因此你可以随意 add prefixes，而不会引发问题（最多达到 prefix length limit）。这种做法的问题是：使用 microcode patch 时，大概很难在不 sacrificing performance 的情况下做到这一点；prefixes 的数量有限，加上 length limit，意味着如果你不跨多个 instructions 来 track state，那么你的 effective key size 就会 relatively small；此外，你只能用 native code 来 generate 这个 trigger。

据大家所知，这一切都还只是 speculative，没有人见过真正的 CPU backdoor 在 in the wild 被 used。

    microcoded instruction 与 implemented in hardware 的 instruction 之间的 distinction，本身也有些 arbitrary。CPUs 有它们 implement 的 instruction set，你可以将其视为 public API。在 Internally，它们可以 execute 不同的 instruction set，你可以将其视为 private API。

    在现代 Intel chips 上，会 turn into 四个（或更少）uops（private API calls）的 instructions，由 decoder 直接 translated into uops。会 result in 更多 uops（从五个到几百个，甚至可能几千个）的 Instructions，则通过 microcode engine 来 decoded，该 engine 从 CPU 上的小型 ROM 或 RAM 中 reads uops。为什么是四个而不是五个？这是一些 tradeoffs 的结果，而不是什么 fundamental truth。相关 terminology 并未 standardized，但我认识的人会说，如果一个 instruction 的 decode 由 microcode engine 来 handled，那么它就是“microcoded”；如果它的 decode 由 standard decoder 来 handled，那么它就是“implemented in hardware”。microcode engine 有点像一个独立的 CPU，因为它必须能够处理这类事情：从并非 architecturally visible 的 temporary registers 中 reading 和 writing；对于需要的不只是几个 registers 的 scratch space 的 instructions，从 internal RAM 中 reading 和 writing；以及会 change microcode engine 所 fetches 和 decodes 的 microcode 的 conditional microcode branches，等等。

    Implementation details 各不相同（而且往往是 secret）。不过，无论 implementation 如何，你都可以将 microcode engine 理解为这样的东西：当 CPU starts up 时，它将 microcode loads 到 RAM 中，然后从该 RAM 中 fetches 和 decodes microcoded instructions。通过 microcode patch 来 changing 在 boot 时 loaded 的内容，就很容易 modify 哪些 microcode 会被 executed。

    为了在 debugging 时获得更快的 turnaround，Intel 也有一种 mechanism，让它们能够强制 non-microcoded instructions 从 microcode RAM 中 execute，以便通过 microcode patch 对其进行 patched——这种情况至少是 plausible 的，甚至很可能如此。但即使并非如此，compromising microcode patch mechanism 并 modifying 单个 microcoded instruction，也应该 sufficient to install 一个 backdoor。

    当你查看一个 [chip 的 cross-section](http://www.intel.com/content/dam/www/public/us/en/documents/presentation/silicon-technology-leadership-presentation.pdf) 时，会看到 silicon gates 位于底部，forming 诸如 [nand gates](http://www.nand2tetris.org/) 之类的 logical primitives；上方则有一系列 metal layers（标为 M1 至 M8），forming 用于 connect 不同 gates 的 wires。manufacturing process 的一个 cartoon model 是：chips 从底部向上逐 layer built，每次一 layer，每个 layer 都通过 depositing 某种 material，再使用 mask 将其一部分 etching 掉来 created，这一 process 类似于 [lithographic printing](http://en.wikipedia.org/wiki/Lithography)。并非 cartoon 的版本涉及大量 complexity——[Todd Fernendez 估计，create “M1” 以下的 layers 大约需要 500 个 steps](https://www.youtube.com/watch?v=NGFhc8R_uO4)。此外，所需的 precision 水平非常高，以至于用于 etch 的 light 对 equipment 造成的 wear 足以使其 wears out。你平时大概不会想到，light 穿过 lenses 会使它们 wearing out，但在 make 一个 transistor 所需的数百个 steps 中，每个 step 都要求如此高的 precision，这就成了严重问题。如果这让你感到意外，那么你并不是唯一一个。90 年代的一份 [ITRS roadmap](http://www.itrs.net/) 曾 predicted，到 2016 年，我们将采用 9nm process（越 smaller 越好），达到接近 30GHz（越 higher 越好），而 chips 的 consuming 将接近 300 watts。实际情况却是，5 GHz 已被认为相当 fast，而除 Intel 之外的任何厂商，如果到 2016 年初能在 14nm process 上实现 high-yield production，就已经很幸运了。Making chips 比任何人原先猜想的都更难。

    现代 chip 有如此多的 layers，以至于从头到尾 make 一个需要大约三个月。这使 bugs 成了非常糟糕的消息，因为如果一个 bug fix 需要 change 某个底部 layer，就需要三个月来 manufacture。为了 reduce bug fixes 的 turnaround time，通常会在 silicon 各处 scatter unused logic gates，以便通过 edit 靠近顶部的几个 layers 来完成小型 bug fixes。由于 chips 是通过 manufacturing line process 来 made 的，因此在任何时刻，都有一批批部分完成的 chips。如果你只需要 edit 顶部的某个 metal layer，就可以将该 edit apply 到部分完成的 chip 上，从而将 turnaround time 从几个月 cutting 到几周。

    由于 chips 的 designed 方式允许轻松 edits，因此，在 chip 被 manufactured 之前能够 access 其 design 的人（例如 manufacturer），可以通过 relatively small edits 做出 major changes。我怀疑，如果你向任何大型 CPU company 的人提出这个看法，他们都会告诉你，不可能在他们毫无察觉的情况下做到，因为这会在 characterization 中，或在他们尝试 find speed paths 等类似工作时被 caught。希望如此，但[实际的 hardware devices 已经带着 backdoors shipped](http://www.cl.cam.ac.uk/~sps32/sec_news.html#Assurance)，而要么没有人注意到，要么他们就是共谋。

## 原文

It's generally accepted that any piece of software could be compromised with a backdoor. Prominent examples include the [Sony/BMG installer](http://en.wikipedia.org/wiki/Sony_BMG_copy_protection_rootkit_scandal), which had a backdoor built-in to allow Sony to keep users from copying the CD, which also allowed malicious third-parties to take over any machine with the software installed; the [Samsung Galaxy](http://redmine.replicant.us/projects/replicant/wiki/SamsungGalaxyBackdoor), which has a backdoor that allowed the modem to access the device's filesystem, which also allows anyone running [a fake base station to access files on the device](https://www.youtube.com/watch?v=RXqQioV_bpo); [Lotus Notes](http://www.cypherspace.org/adam/hacks/lotus-nsa-key.html), which had a backdoor which allowed encryption to be defeated; and [Lenovo laptops](https://forums.lenovo.com/t5/Lenovo-P-Y-and-Z-series/Lenovo-Pre-instaling-adware-spam-Superfish-powerd-by/td-p/1726839), which pushed all web traffic through a proxy (including HTTPS, via a trusted root certificate) in order to push ads, which allowed anyone with the correct key (which was distributed on every laptop) to intercept HTTPS traffic.

Despite sightings of backdoors in [FPGAs](http://www.cl.cam.ac.uk/~sps32/sec_news.html#Assurance) and [networking gear](https://github.com/elvanderb/TCP-32764), whenever someone brings up the possibility of CPU backdoors, it's still common for people to claim that it's [impossible](https://news.ycombinator.com/item?id=6147767). I'm not going to claim that CPU backdoors exist, but I will claim that the implementation is easy, if you've got the right access.

Let's say you wanted to make a backdoor. How would you do it? There are three parts to this: what could a backdoored CPU do, how could the backdoor be accessed, and what kind of compromise would be required to install the backdoor?

Starting with the first item, what does the backdoor do? There are a lot of possibilities. The simplest is to allow privilege escalation: make the CPU to [transition from ring3 to ring0 or SMM](http://en.wikipedia.org/wiki/Protection_ring), giving the running process kernel-level privileges. Since it's the CPU that's doing it, this can punch through both hardware and software virtualization. There are a lot of subtler or more invasive things you could do, but privilege escalation is both simple enough and powerful enough that I'm not going to discuss the other options.

Now that you know what you want the backdoor to do, how should it get triggered? Ideally, it will be something that no one will run across by accident, or even by brute force, while looking for backdoors. Even with that limitation, the state space of possible triggers is huge.

Let's look at a particular instruction, `fyl2x`[1](https://danluu.com/cpu-backdoors/#fn:I). Under normal operation, it takes two floating point registers as input, giving you `2*80=160` bits to hide a trigger in. If you trigger the backdoor off of a specific pair of values, that's probably safe against random discovery. If you're really worried about someone stumbling across the backdoor by accident, or brute forcing a suspected backdoor, you can check more than the two normal input registers (after all, you've got control of the CPU).

This trigger is nice and simple, but the downside is that hitting the trigger probably requires executing native code since you're unlikely to get chrome or Firefox to emit an `fyl2x` instruction. You could try to work around that by triggering off an instruction you can easily get a JavaScript engine to emit (like an `fadd`). The problem with that is that if you patch an add instruction and add some checks to it, it will become noticeably slower (although, if you can edit the hardware, you should be able to do it with no overhead). It might be possible to create something hard to detect that's triggerable through JavaScript by patching a [rep string](http://www.csc.depauw.edu/~bhoward/asmtut/asmtut7.html) instruction and doing some stuff to set up the appropriate “key” followed by a block copy, or maybe `idiv`. Alternately, if you've managed to get a copy of the design, you can probably figure out a way to use debug logic triggers[2](https://danluu.com/cpu-backdoors/#fn:D) or performance counters to set off a backdoor when some arbitrary JavaScript gets run.

Alright, now you've got a backdoor. How do you insert the backdoor? In software, you'd either edit the source or the [binary](https://danluu.com/edit-binary/). In hardware, if you have access to the source, you can edit it as easily as you can in software. The hardware equivalent of recompiling the source, creating physical chips, has tremendously high fixed costs; if you're trying to get your changes into the source, you'll want to either compromise the design[3](https://danluu.com/cpu-backdoors/#fn:A) and insert your edits before everything is sent off to get manufactured, or compromise the manufacturing process and sneak in your edits at the last second[4](https://danluu.com/cpu-backdoors/#fn:E).

If that sounds too hard, you could try compromising the patch mechanism. Most modern CPUs come with a built-in patch mechanism to allow bug fixes after the fact. It's likely that the CPU you're using has been patched, possibly from day one, and possibly as part of a firmware update. The details of the patch mechanism for your CPU are a closely guarded secret. It's likely that the CPU has a public key etched into it, and that it will only accept a patch that's been signed by the right private key.

Is this actually happening? I have no idea. Could it be happening? Absolutely. What are the odds? Well, the primary challenge is non-technical, so I'm not the right person to ask about that. If I had to guess, I'd say no, if for no other reason than the [ease of subverting other equipment](https://github.com/elvanderb/TCP-32764).

I haven't discussed how to make a backdoor that's hard to detect even if someone has access to software you've used to trigger a backdoor. That's harder, but it should be possible once chips start coming with built-in [TPMs](http://en.wikipedia.org/wiki/Trusted_Platform_Module).

#### Updates

See [this twitter thread](https://twitter.com/danluu/status/562962211782815746) for much more discussion, some of which is summarized below.

I'm not going to provide individual attributions because there are too many comments, but here's a summary of comments from @hackerfantastic, Arrigo Triulzi, David Kanter, @solardiz, @4Dgifts, Alfredo Ortega, Marsh Ray, and Russ Cox. Mistakes are my own, of course.

[AMD's K7 and K8 had their microcode patch mechanisms compromised](http://www.realworldtech.com/forum/?threadid=35566&curpostid=35566), allowing for the sort of attacks mentioned in this post. Turns out, AMD didn't encrypt updates or validate them with a checksum, which lets you easily modify updates until you get one that does what you want.

[Here's an example of a backdoor that was created for demonstration purposes](http://es.slideshare.net/ortegaalfredo/deep-submicronbackdoorsortegasyscan2014slides), by Alfredo Ortega.

For folks without a hardware background, [this talk on how to implement a CPU in VHDL is nice, and it has a section on how to implement a backdoor](http://media.ccc.de/browse/congress/2013/30C3_-_5443_-_en_-_saal_g_-_201312281830_-_introduction_to_processor_design_-_byterazor.html#video).

Is it possible to backdoor RDRAND by providing bad random results? Yes. I mentioned that in my first draft of this post, but I got rid of it since my impression was that people don't trust RDRAND and mix the results other sources of entropy. That doesn't make a backdoor useless, but it significantly reduces the value.

Would it be possible to store and dump AES-NI keys? It's probably infeasible to sneak flash memory onto a chip without anyone noticing, but modern chips have logic analyzer facilities that let you store and dump data. However, access to those is through some secret mechanism and it's not clear how you'd even get access to binaries that would let you reverse engineer their operation. That's in stark contrast to the K8 reverse engineering, which was possible because microcode patches get included in firmware updates.

It would be possible to check instruction prefixes for the trigger. x86 lets you put redundant (and contradictory) instruction prefixes on instructions. Which prefixes get used are well defined, so you can add as many prefixes as you want without causing problems (up to the prefix length limit). The issues with this are that it's probably hard to do without sacrificing performance with a microcode patch, the limited number of prefixes and the length limit mean that your effective key size is relatively small if you don't track state across multiple instructions, and that you can only generate the trigger with native code.

As far as anyone knows, this is all speculative, and no one has seen an actual CPU backdoor being used in the wild.

1.  This choice of instruction is somewhat, but not completely, arbitrary. You'll probably want an instruction that's both slow and microcoded, to make it easy to patch with a microcode patch without causing a huge performance hit. The rest of this footnote is about what it means for an instruction to be microcoded. It's quite long and not in the critical path of this post, so you might want to skip it.

    The distinction between a microcoded instruction and one that's implemented in hardware is, itself, somewhat arbitrary. CPUs have an instruction set they implement, which you can think of as a public API. Internally, they can execute a different instruction set, which you can think of as a private API.

    On modern Intel chips, instructions that turn into four (or fewer) uops (private API calls) are translated into uops directly by the decoder. Instructions that result in more uops (anywhere from five to hundreds or possibly thousands) are decoded via a microcode engine that reads uops out of a small ROM or RAM on the CPU. Why four and not five? That's a result of some tradeoffs, not some fundamental truth. The terminology for this isn't standardized, but the folks I know would say that an instruction is “microcoded” if its decode is handled by the microcode engine and that it's “implemented in hardware” if its decode is handled by the standard decoder. The microcode engine is sort of its own CPU, since it has to be able to handle things like reading and writing from temporary registers that aren't architecturally visible, reading and writing from internal RAM for instructions that need more than just a few registers of scratch space, conditional microcode branches that change which microcode the microcode engine fetches and decodes, etc.

    Implementation details vary (and tend to be secret). But whatever the implementation, you can think of the microcode engine as something that loads a RAM with microcode when the CPU starts up, which then fetches and decodes microcoded instructions out of that RAM. It's easy to modify what microcode gets executed by changing what gets loaded on boot via a microcode patch.

    For quicker turnaround while debugging, it's somewhere between plausible and likely that Intel also has a mechanism that lets them force non-microcoded instructions to execute out of the microcode RAM in order to allow them to be patched with a microcode patch. But even if that's not the case, compromising the microcode patch mechanism and modifying a single microcoded instruction should be sufficient to install a backdoor.

    It turns out that editing chips before manufacturing is fully complete is relatively easy, by design. To explain why, we'll have to look at how chips are made.

    ![Cross section of Intel chip, 22nm process](https://danluu.com/images/cpu-backdoors/intel_22nm.webp)

    When you look at a [cross-section of a chip](http://www.intel.com/content/dam/www/public/us/en/documents/presentation/silicon-technology-leadership-presentation.pdf), you see that silicon gates are at the bottom, forming logical primitives like [nand gates](http://www.nand2tetris.org/), with a series of metal layers above (labeled M1 through M8), forming wires that connect different gates. A cartoon model of the manufacturing process is that chips are built from the bottom up, one layer a time, where each layer is created by depositing some material and then etching part of it away using a mask, in a process that's analogous to [lithographic printing](http://en.wikipedia.org/wiki/Lithography). The non-cartoon version involves a lot of complexity -- [Todd Fernendez estimates that it takes about 500 steps to create the layers below “M1”](https://www.youtube.com/watch?v=NGFhc8R_uO4). Additionally, the level of precision needed is high enough that the light used to etch causes enough wear in the equipment that it wears out. You probably don't normally think about lenses wearing out due to light passing through them, but at the level of precision required for each of the hundreds of steps required to make a transistor, it's a serious problem. If that sounds surprising to you, you're not alone. An [ITRS roadmap](http://www.itrs.net/) from the 90s predicted that by 2016, we'd be at almost 30GHz (higher is better) on a 9nm process (smaller is better), with chips consuming almost 300 watts. Instead, 5 GHz is considered pretty fast, and anyone who isn't Intel will be lucky to get high-yield production on a 14nm process by the start of 2016. Making chips is harder than anyone guessed it would be.

    A modern chip has enough layers that it takes about three months to make one, from start to finish. This makes bugs very bad news since a bug fix that requires a change to one of the bottom layers takes three months to manufacture. In order to reduce the turnaround time on bug fixes, it's typical to scatter unused logic gates around the silicon, to allow small bug fixes to be done with an edit to a few layers that are near the top. Since chips are made in a manufacturing line process, at any point in time, there are batches of partially complete chips. If you only need to edit one of the top metal layers, you can apply the edit to a partially finished chip, cutting the turnaround time down from months to weeks.

    Since chips are designed to allow easy edits, someone with access to the design before the chip is manufactured (such as the manufacturer) can make major changes with relatively small edits. I suspect that if you were to make this comment to anyone at a major CPU company, they'd tell you it's impossible to do this without them noticing because it would get caught in characterization or when they were trying to find speed paths or something similar. One would hope, but [actual hardware devices have shipped with backdoors](http://www.cl.cam.ac.uk/~sps32/sec_news.html#Assurance), and either no one noticed, or they were complicit.
