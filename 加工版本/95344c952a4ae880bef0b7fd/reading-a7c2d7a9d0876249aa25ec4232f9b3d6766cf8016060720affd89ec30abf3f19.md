# 我们在2015年见识了一些非常严重的英特尔 CPU 缺陷，未来还应预期会出现更多｜We saw some really bad Intel CPU bugs in 2015 and we should expect to see more in the future

---

## 正文

2015 年对 Intel 来说是相当不错的一年。他们的 quarterly earnings reports 每个季度都 exceeded expectations。他们仍然是重要的 server market 中唯一的选择，而这个 market 仍在 grow exponentially；从两家最大的 cloud vendors 的 earnings reports 中，我们可以看到，AWS 和 Azure 分别 grew by 80% 和 100%。这种 growth 实际上已经 offset 了 desktop market 持续 decline 给 Intel 带来的 damage。有一阵子，看起来 [cloud vendors 或许能够通过将它们的 computation moving 到 FPGAs 上来 avoid Intel tax](https://danluu.com/new-cpu-features/#update)，但 Intel 买下了两家主要的 FPGA vendors 之一，再加上他们的 fab advantage，他们似乎已经占据有利位置，能够像一直以来 dominating high-end server CPU market 那样 dominate high-end FPGA market。此外，他们因 anti-competitive practices 而受到的 fine 最终为 $1.45B，远少于他们从 anti-competitive practices 中获得的 benefit[1](https://danluu.com/cpu-bugs/#fn:S)。

不过，在 engineering/bugs 方面，情况就没那么好了。我们已经见到了一些相当 serious 的 CPU bugs，而且看来，我们应该预期今后还会有更多。我平时并不追踪 Intel bugs，除非它们 serious 到让我认识的人因为 potential impact 而急忙部署 patch，但即便如此，仅在今年最后一个季度，我就听说了两个 severe bugs。首先是 [Ben Serebrin 和 Jan Beulic 发现的 bug](http://xenbits.xen.org/xsa/advisory-156.html)，它允许 guest VM 以一种会导致 CPU 在 microcode infinite loop 中 hang 的方式 fault，从而允许任何 VM 对它的 host 进行 DoS。

主要的 cloud vendors 相当幸运，这个 bug 是由一名 Google engineer 发现的，而且 Google 决定在 publicly disclosing 之前，先向它的 competitors 分享对这个 bug 的了解。Black hats 花费大量时间，试图 take down 主要的 services。那些花时间 attacking 我所供职的公司的人，他们的执着和聪明才智确实让我印象深刻。如果我们在 infrastructure 深处有一小段在 [DPC](https://en.wikipedia.org/wiki/Deferred_Procedure_Call) 上 running 的 code，因为某种 hash collision 而 vulnerable to slowdown，就会有人发现并 exploit 它，即使要经过一长串隐晦的事件才能使之发生。如果这个 CPU microcode hang 是被这些 black hats 中的某个人发现的，那么大多数 cloud hosted services 都会在最不方便的时候遭遇重大灾难[2](https://danluu.com/cpu-bugs/#fn:C)。

Serebrin/Beulic bug 被发现后不久，一群人发现，running [prime95](http://www.mersenne.org/download/)——一种常用于 benchmarking 和 burn-in 的 tool——会导致[他们的整个 system lock up](http://mersenneforum.org/showthread.php?t=20714)。[Intel 对此的回应是](https://communities.intel.com/thread/96157?start=15&tstart=0)：

> Intel 已经 identified 一个可能 affects 6th Gen Intel® Core™ family of products 的 issue。这个 issue 只会在某些 complex workload conditions 下 occurs，例如 running Prime95 这样的 applications 时可能遇到的 conditions。在这些情况下，processor 可能 hang 或 cause unpredictable system behavior。

这几乎没有透露实际发生了什么。如果你查看他们的 errata list，就会发现这很典型，只不过他们通常连用于 trigger bug 的 application 名称都不会提。例如，[目前的一份 errata lists](http://www.intel.com/content/dam/www/public/us/en/documents/specification-updates/4th-gen-core-family-desktop-specification-update.pdf) 中就有这样的 entries：

-   某些 AVX Instructions 的 Combinations 可能 Cause Unpredictable System Behavior
-   本应 Result in #DF 的 AVX Gather Instruction 可能 Cause Unexpected System Behavior
-   Processor 在 High Activity 的 Periods 期间可能 Experience 一次 Spurious LLC-Related Machine Check
-   Page Fault 可能 Report Incorrect Fault Information

正如我们已经看到的，“unexpected system behavior”可能意味着我们彻底完蛋了。Machine checks 也好不到哪里去——它们会导致 Windows blue screen 和 Linux kernel panic。page fault 中的 incorrect address 可能甚至比单纯的 crash 更糟，而如果你仔细翻查这份 list，还能找到许多其他听起来很吓人的 bugs。

而且别忘了，Intel errata list 中有如下 disclaimer：

> Errata 会在 product 的整个 lifecycle 内保留于 specification update 中，或一直保留到某个特定 stepping 不再 commercially available 为止。在这些情况下，从 specification update 中 removed 的 errata 会被 archived，并可应要求提供。

一旦他们停止 manufacturing 某个 stepping（hardware 中相当于 point release 的东西），他们就保留 remove errata 的权利，而除非你对 Intel 足够重要，否则你就无法查明自己的旧 stepping 有哪些 errata。

总之，回到 2015 年。我们在最后一个季度已经见到了 Intel CPUs 中至少两个 serious bugs[3](https://danluu.com/cpu-bugs/#fn:A)，而且几乎可以肯定，还有更多 bugs 潜伏着。以前我在一家 produced Intel compatible CPUs 的公司工作时，我们对 Intel CPUs 做了相当多的 testing 和 characterization；作为一个刚毕业、此前一直认为 CPUs 基本上都能正常工作的人，我们能找到那么多 bugs，让我十分惊讶。尽管我从未从事 characterization 和 competitive analysis 方面的工作，但仅仅在日常工作过程中，四处探查、verify 那些我觉得 non-obvious 的事情时，我自己仍然发现过多个 Intel CPU bugs。事实证明，那些对我而言 non-obvious 的事情，有时对 Intel engineers 而言也同样 non-obvious。随着更多 services move 到 cloud，以及 system hang 和 reset vulnerabilities 的 impact 增加，我们会看到更多 black hats 投入时间 finding CPU bugs。当人们意识到 finding 这些 bugs 远比看起来容易时，我们应该预期会见到更多这样的 bugs。曾经，一个 CPU family 每年可能只有一个 bug，serious bugs 每隔几年才会出现一次，甚至十年才出现一次，但那个时代已经过去了。部分原因在于，“unpredictable system behavior”已经从一种恼人的 class of bugs——迫使你 restart 自己的 computation——变成了一种 attack vector，让任何拥有 AWS account 的人都可以 attack random cloud-hosted services；但更主要的原因是，CPUs [已经变得更加 complex，使它们更难被有效地 test](https://danluu.com/new-cpu-features/) 和 [audit](https://danluu.com/cpu-backdoors/)，而 Intel 似乎还在削减 validation effort。讽刺的是，我们有本应在 security 方面帮助我们的 hardware virtualization，但 virtualization 如此 complicated[4](https://danluu.com/cpu-bugs/#fn:V)，以至于 hardware virtualization implementation 很可能 expose 原本不会存在的“unpredictable system behavior”bugs。这并不是说已经毫无希望——原则上，可以 design CPUs，使一个 core 上的 hang bug 不会 crash 整个 system。只是在每个 level 都做到这一点，需要相当多的工作（cache directories、uncore 等都必须被 modified，才能在某个 core 处于 hung 状态时 operate，OS schedulers 也一样）。没有人做过这项工作，因为它以前似乎并不重要。

你经常会听到从事 software 的人说，这些事情无关紧要，因为它们（有时）可以被 patched。但是，许多 devices 永远不会被 patched，这意味着 hardware security bugs 会让一些 devices 在整个 lifetime 内都处于 vulnerable 状态。而且，即使你不在乎 consumers，serious bugs 对 CPU vendors 来说也非常糟糕。我曾经供职的一家公司有一次让一个 bug escape validation，直到我们 shipped 之后才被发现。此后，一家 OEM 大约五年都不愿意跟我们打交道，而其他继续与我们合作的 OEMs 不得不用我们的 microcode patch 重新 re-qualify 它们的 parts，并且特意让我们知道这样做有多 expensive。Intel 的分量足够重，OEMs 不可能因为一个 bug 就直接离开他们，但他们的 political capital 并非无限，每个 serious bug 都会消耗 political capital，即使它可以被 patched。

这并不是说我们应该努力达到 zero bugs。development speed 和 bug rate 之间总会存在 trade off，而 optimal point 很可能并不是 zero bugs。但我们现在经常见到具有 security implications 的 severe bugs，这大大改变了 tradeoff。对于 [FDIV bug](https://en.wikipedia.org/wiki/Pentium_FDIV_bug) 这样的事情，你可以论证说，任何一个不 run numerical analysis code 的特定 user，在 statistically 意义上都不太可能受到 impacted，但 security bugs 不一样。Attackers 不会 run random code，所以你不能只是说，某个 condition 不太可能 occur。

### 更新

写完这篇文章后，一位自称曾是 Intel 员工的人说：“即使你有 privileged access，你也根本不了解情况”，而 reddit 上一位使用化名的评论者[发表了这条评论](https://www.reddit.com/r/programming/comments/41k3yx/we_saw_some_really_bad_intel_cpu_bugs_in_2015_and/cz2zwag)：

> 作为一个直到 mid-2014 左右还在 Intel 的 SOCs Validation 团队工作的人，我可以告诉你，是的，你将会看到比过去从 post-FDIV-bug 时代直到最近更多的 Intel CPU bugs。
> 
> 为什么？
> 
> 让我交代一下背景：那是 2013 年末。Intel 因为在 mobile CPU 之战中输给 ARM 而焦急万分。所有 validation 团队都参加了会议。负责 Validation 的头头大意说：“我们需要加快速度。Intel 的 Validation 所花的时间远比竞争对手长。我们需要尽一切可能减少这些时间……我们不能永远活在 90 年代初 FDIV bug 的阴影下，我们需要向前走。竞争对手的行动比我们快得多”——我是在转述。在场的许多 engineers 都还记得 20 年前的 FDIV bug，以及随后给 Intel 带来的问题。我们当中许多人都很震惊，一位身居高位的人竟然会暗示我们需要在 validation 上偷工减料——当然，他并没有明确这么说，但隐含的信息就是如此。对于当时在场的许多人来说，2013 年末的那次会议标志着 Intel 的一次巨变。而且看起来不会是好的变化。我们当中有些人选择了趁情况还好时离开。作为一个直到 mid-2014 左右还在 Intel 的 SOCs Validation 团队工作的人，我可以告诉你，是的，你将会看到比过去从 post-FDIV-bug 时代直到最近更多的 Intel CPU bugs。

我还没能从另一位我个人认识的消息来源那里证实这件事，不过另一位匿名评论者说：“我在 2013 年中离开了 INTC。之前做的是 validation。这……与我的经历相比是准确的。”另一位我认识的匿名人士没有听过那次讲话，但发现大约就在那时，“velocity”成了流行词，管理层花了大量时间讨论 Intel 如何需要更多“velocity”才能与 ARM 竞争。这似乎印证了那种态度，即使未能证实那次讲话本身。

我还听 formal methods 领域的人说，大约在第一条评论提到的那段时间，formal verification 人员出现了大规模离职。我听到的一种说法是，人们离开是因为担心被裁掉。有人告诉我，当时正在酝酿提前退休方案，大家强烈怀疑会有裁员。我听到的另一种说法是，由于 Intel 专注于与 ARM 的 mobile 之战，情况变得十分古怪，人们想在局面进一步恶化之前离开。但很难说这意味着什么，因为 Intel 一直有大量人员流向 Apple，原因是 Apple 提供更好的薪酬待遇，并承诺不会那么运转失调。

我还收到了一些关于 bugs 的匿名消息。一位从事 HPC 工作的人告诉我，当他们在选购 Haswell parts 时，有人私下透露，greater than 12 cores 的 variants 会出现 drastically reduced performance。他们尝试搭建了 12-core 和 16-core systems，发现对于各种各样的 workloads，12-core systems 都有 noticeably better performance。那不是更好的 per-core performance——而是更好的 absolute performance。Adding 4 more cores 竟然 reduced 了 parallel workloads 的 performance！single-socket 和 two-socket benchmarks 都是如此。

还有[一个在 idle/low-activity 期间发生神秘 hang、而 Intel 似乎尚未弄清楚的 bug](http://www.tomshardware.com/forum/id-2830772/skylake-build-randomly-freezing-crashing.html)。

然后还有[这个 Broadwell bug，如果不 disable low-power states，它就会 hangs Linux](https://bugzilla.kernel.org/show_bug.cgi?id=103351)。

当然，Intel 不是唯一有 bugs 的公司——这个 [Robert Swiecki 发现的 AMD bug](https://lists.debian.org/debian-security/2016/03/msg00084.html) 不仅允许 VM 去 crash 它的 host，还允许 VM 去 take over 这个 host。

我怀疑自己甚至还没听说过最近所有的 bugs 和有关 verification/validation 的消息。欢迎把其他 reports 发给我。

### 更多更新

不少人注意到了 [storage devices 中的 unusual failure rates](https://forum.synology.com/enu/viewtopic.php?f=7&t=119727&start=60)，switches 中也有这种情况。这[似乎与一个 Intel Atom bug 有关](https://www.servethehome.com/intel-atom-c2000-series-bug-quiet/)。我觉得这很有意思，因为 Atom 是一种 relatively simple chip，因此也是一种 relatively simple、易于 verify 的 chip。first-gen Atom released 时，Intel 的人似乎很自豪，因为只需很少几次 chip 的 internal spins 就能 ship 一个 working production chip，而这得益于 chip 的 simplicity。如今的 Atoms 更 complicated，但并没有 complicated 到_那种_程度。

Intel Skylake 和 Kaby Lake 有[一个 hyperthreading bug，严重到 Debian 建议 users 通过 disable hyperthreading 来避免这个 bug](https://lists.debian.org/debian-devel/2017/06/msg00308.html)，它可能“cause spurious errors，例如 application and system misbehavior、data corruption 和 data loss”。

AMD 那边可能也有[一个与最近任何 Intel CPU bug 一样 serious 的 bug](https://community.amd.com/message/2796982)。如果你读一下链接中的 thread，就会看到一位 AMD 代表要求大家 disable SMT、OPCache Control，并 changing LLC settings，以便可能 mitigate 或 narrow down 一个 serious crashing bug。在[另一个 thread](https://forums.gentoo.org/viewtopic-t-1061546-postdays-0-postorder-asc-start-150.html) 中，你可以看到有人 reporting 一个带有“u-op cache crc mismatch”的 #MC exception。

尽管 AMD 在 forum 中回应说这些只是 isolated issues，[phoronix 还是通过 running 一个由 compiling 多个 open source programs 构成的 stress test，成功 reproduce crashes](http://www.phoronix.com/scan.php?page=article&item=ryzen-segv-continues)。他们报告说，在一小时的 attempted compilation 中，他们得到了 53 segfaults。

一些 FreeBSD 人员也注意到了看似 unrelated crashes，并且能够通过在 high address 处 running code、随后 firing an interrupt 来得到 reproduction。[这可能 result in 一个 hang 或一个 crash](https://svnweb.freebsd.org/base?view=revision&revision=321899)。之所以这看起来与最早 reported 的 Ryzen issues 无关，是因为即使 SMT disabled，这个问题仍然 easily reproducible。

Matt Dillon 发现了一个由 DragonflyBSD triggered 的 AMD bug，并[commited 了一个很小的 patch 来 fix 它](http://gitweb.dragonflybsd.org/dragonfly.git/commitdiff/b48dd28447fc8ef62fbc963accd301557fd9ac20)：

> Ryzen 中有一个 bug，与 kernel iretq'ing 到 user address space 末端附近的 high user %rip address（user stack 的 top）有关。这是针对该 issue 的 temporary workaround。
> 
> sigtramp 原来的 %rip 是 0x00007fffffffffe0。将它 Moving it down 到 fa0 还不 sufficient。将它 Moving it down 到 f00 后，bug 从几乎立即出现变成需要几小时才能 reproduce。将它 Moving it down 到 be0 后，需要一天才能 reproduce。将它 Moving it down 到 0x00007ffffffffba0（这次 commit）后，成功 survived 了 overnight test。

### [Meltdown / spectre](https://meltdownattack.com/) 更新

这是一类有意思的 attack，它利用 speculative execution 加上 side channel attacks，将 privileged information leak 到 user processes 中。看来，这些 attacks 中至少有一些可以通过 browser 中的 javascript 来完成。

关于前几次更新中谈到的 Intel 最近对 validation 的态度，[另一位自称是 Intel 前员工的人也支持上述说法](https://news.ycombinator.com/item?id=16059635)：

> 作为一名前 Intel 员工，这与我的经历非常吻合。我并不在 validation 部门工作（实际上，我是随 Altera 一起加入的），但 velocity 绝对是个流行词，而 senior management 面对 complex challenges 的方式完全就是惊慌失措。schedules 的 Slips 完全不被容忍——因此，validation 中的 problems 就成了关乎存亡的威胁，你的 project 很容易就会被砍掉。另外，由于公司规模庞大，quality 和 completeness 被“acheived”的方式极其官僚化，很少能体现真正的 engineering fundamentals。

### 2024 更新

距离我写下这篇文章已经快十年了，serious CPU bugs 仍然不断出现。比如，最近这个就是由 [RAD tools](https://www.radgametools.com/oodleintel.htm) 发现的：

> Intel Processor Instability 导致 Oodle Decompression Failures
> 
> 我们认为，这是一个 hardware problem，主要 affects Intel 13900K 和 14900K processors，也可能 affects 13700、14700 及其他相关 processors，但可能性较小。这些 processors 中只有一小部分会 exhibit 这种 behavior。这个 problem 似乎是由 BIOS settings 与这些 processors 的 high clock rates 和 power usage 共同造成的，导致 heavy load 下的 system instability 和 unpredictable behavior……任何在许多 threads 上 heavily use processor 的 programs 都可能 cause crashes 或 unpredictable behavior。RealBench、CineBench、Prime95、Handbrake、Visual Studio 等都已经出现过 crashes。这个 problem 也可能表现为 GPU error message，例如 spurious "out of video memory" errors，尽管它实际上是由 CPU 造成的。

有人可以争辩说，这是一个 configuration bug，但从一个普通 user 的角度来看，他们观察到的只是自己的 CPU 正在 causing crashes。而且，现实地说，Intel 知道自己的 CPUs 正在被 shipping 到采用这些 settings 的 systems 中。对此的 mitigation 涉及 changing 下列 settings 之类的操作：""SVID behavior" → "Intel fail safe", "Long duration power limit" → 如果 set 得更高，则 reduce 到 125W（ARK 上的 "Processor Base Power"）", "Short duration power limit" → 如果 set 得更高，则 reduce 到 253W（适用于 13900/14900 CPUs，其他 CPUs 有其他 limits！ARK 上的 "Maximum Turbo Power"）"，等等。

如果他们希望自己的 CPUs 不因这个 issue 而 crash，他们本可以、也本应该 enforced 这些 settings 以及另外一些 settings。但他们却把这件事留给了 BIOS settings，于是就有了眼下的局面。

过去，Intel 对 verification、validation 和 testing 的重视程度远高于 AMD，我们也在他们的产出中看到了这一点。曾经有一段时间，当许多 enthusiast sites 对 AMD 热情高涨时（在 K7 时代），Google 停止使用 AMD，基本上禁止采购 AMD CPUs，因为它们实在太 buggy，造成了太多 hard-to-debug problems。但随着时间推移，Intel 分配给 verification/validation/test 的相对投入水平已经下降，而在真正 serious bugs 的 rate 上，Intel 似乎已经几乎赶上、甚至可能已经赶上了 AMD。考虑到 Intel 当前的 market position，以及来自 AMD、ARM 和 Nvidia 的巨大压力，Intel 似乎不太可能在可预见的未来扭转这一局面。过去，Nvidia 一直比 AMD 或 Intel 显著更 buggier，因此，Intel 距离成为最 buggy 的主要 chip manufacturer，仍然有相当大的空间。考虑到 Nvidia 是 Intel 面临的最大威胁之一，再看看 Intel 过去如何应对其他当时更 buggier 的 manufacturers 带来的威胁，我们似乎应该预期，未来十年 bad bugs 的 rate 还会更高。

就这个具体的 bug 而言，出于多种原因，CPU manufacturer 承受着巨大的压力，要更像一家“快速行动，打破常规”的 software company 那样运作，而不是像传统、保守的 CPU manufacturer 那样运作。当你 manufacture 一个 CPU 时，它最终能 run 多 fast 带有一定的 random 性，除了 testing 它之外，没有可靠的办法判断它能 run 多 fast，因此 CPU companies 会在 CPU 上 run 一组 tests，看看它能达到多 fast。这个 test time 实际上相当昂贵，因此，人们做了大量工作，试图找到尽可能小的一组 tests，同时又能 correctly determine CPU 可以 operate 得多 fast。这里一个简单的削减成本的办法，就是少 run 一些 tests，即使较小的一组 tests 并不能 fully guarantee CPU 可以按其出售时标称的 speed 来 operate。

另一个影响因素是，以 nominally faster 的名义出售的 CPUs 可以卖得更贵，因此，也存在着将 CPUs 尽可能推近其 limits 的压力。要看出这里的 margin 总体上已经 decreased，一种办法就是看看 CPUs 有多 overclockable。人们往往只要 run 几个 tests，例如 prime95、stresstest 等，而自己的 part 没有 crash，就会对自己的 overclocked CPU 感到满意；但这远不足以 determine CPU 是否真的可以 run user 可能交给它的一切。不过，如果你真的尝试认真 test 一个 CPU（在 Intel 的竞争对手那里工作时，我们经常这样做），就会发现，Intel 和其他 CPU companies 在其宣称的 CPUs 能有多 fast 与它们实际能有多 fast 之间，确实已经逼近了 limit，这有时会导致售出的 CPUs 已经被推到了其 capabilities 之外。

关于 overclocking，正如 RAD 的 Fabian Giesen 所指出的，

> 这些东西并未得到认可，如果你尝试对它进行 RMA，它会被算作 overclocking，但它却被当作 platform 的一项主要 feature 来销售，而 review sites 在 test 时也会将它开启。

Daniel Gibson 回复说

> 嗯，在我的 mainboard（ASUS ROG Strix B550-A Gaming——显然是 gaming hardware，不过处于中等价位）上，我必须 explicitly enable XMP/EXPO profile，DDR4-RAM 才能以 full speed 来 run——也就是 DDR4-3200，这是 CPU（Ryzen 5950X）officially supported 的。否则，它好像是以 DDR4-2400 speed 来 ran 的？还是 2133？我忘了，至少要显著更低

对此，Fabian 指出

> 没错。有趣的是：开启 EXPO 从技术上讲会使你的 warranty 失效……真棒；CPU 和 RAM 都将它列为 supported，但官方却并不 supported。
> 
> 如果愿意用这么犀利的措辞，有人也许会称之为敲诈。

Intel 过去不会以官方的方式非官方地 support 这类事情。而且，更一般地说，过去 CPU manufacturers 只要能够避免，就非常不愿意 ship 那些在按预期使用时存在不可忽略的 crashes 和 data corruption 风险的 parts，但这类 bugs 却越来越多。有些最终变得广为人知，就像这次一样，因为有人发表了关于它们的 report，例如上面的 RAD report。还有一些则由大型公司悄悄 reported 给 CPU manufacturer，通常还伴随着某种 NDA agreement：大型公司获得 replacement CPUs，而 Intel 或其他 manufacturer 则悄悄 ships 针对该 issue 的 firmware fixes。而且，肯定还有一些根本没有真正被 caught，除非你把偶尔发生的 data corruption 或 crash 也算作被 caught。

## 原文

2015 was a pretty good year for Intel. Their quarterly earnings reports exceeded expectations every quarter. They continue to be the only game in town for the serious server market, which continues to grow exponentially; from the earnings reports of the two largest cloud vendors, we can see that AWS and Azure grew by 80% and 100%, respectively. That growth has effectively offset the damage Intel has seen from the continued decline of the desktop market. For a while, it looked like [cloud vendors might be able to avoid the Intel tax by moving their computation onto FPGAs](https://danluu.com/new-cpu-features/#update), but Intel bought one of the two serious FPGA vendors and, combined with their fab advantage, they look well positioned to dominate the high-end FPGA market the same way they've been dominating the high-end server CPU market. Also, their fine for anti-competitive practices turned out to be $1.45B, much less than the benefit they gained from their anti-competitive practices[1](https://danluu.com/cpu-bugs/#fn:S).

Things haven't looked so great on the engineering/bugs side of things, though. We've seen a number of fairly serious CPU bugs and it looks like we should expect more in the future. I don't keep track of Intel bugs unless they're so serious that people I know are scrambling to get a patch in because of the potential impact, and I still heard about two severe bugs this year in the last quarter of the year alone. First, there was the [bug found by Ben Serebrin and Jan Beulic](http://xenbits.xen.org/xsa/advisory-156.html), which allowed a guest VM to fault in a way that would cause the CPU to hang in a microcode infinite loop, allowing any VM to DoS its host.

Major cloud vendors were quite lucky that this bug was found by a Google engineer, and that Google decided to share its knowledge of the bug with its competitors before publicly disclosing. Black hats spend a lot of time trying to take down major services. I'm actually really impressed by both the persistence and the cleverness of the people who spend their time attacking the companies I work for. If, buried deep in our infrastructure, we have a bit of code running at [DPC](https://en.wikipedia.org/wiki/Deferred_Procedure_Call) that's vulnerable to slowdown because of some kind of hash collision, someone will find and exploit that, even if it takes a long and obscure sequence of events to make it happen. If this CPU microcode hang had been found by one of these black hats, there would have been major carnage for most cloud hosted services at the most inconvenient possible time[2](https://danluu.com/cpu-bugs/#fn:C).

Shortly after the Serebrin/Beulic bug was found, a group of people found that running [prime95](http://www.mersenne.org/download/), a commonly used tool for benchmarking and burn-in, causes [their entire system to lock up](http://mersenneforum.org/showthread.php?t=20714). [Intel's response to this was](https://communities.intel.com/thread/96157?start=15&tstart=0):

> Intel has identified an issue that potentially affects the 6th Gen Intel® Core™ family of products. This issue only occurs under certain complex workload conditions, like those that may be encountered when running applications like Prime95. In those cases, the processor may hang or cause unpredictable system behavior.

which reveals almost nothing about what's actually going on. If you look at their errata list, you'll find that this is typical, except that they normally won't even name the application that was used to trigger the bug. For example, [one of the current errata lists](http://www.intel.com/content/dam/www/public/us/en/documents/specification-updates/4th-gen-core-family-desktop-specification-update.pdf) has entries like

-   Certain Combinations of AVX Instructions May Cause Unpredictable System Behavior
-   AVX Gather Instruction That Should Result in #DF May Cause Unexpected System Behavior
-   Processor May Experience a Spurious LLC-Related Machine Check During Periods of High Activity
-   Page Fault May Report Incorrect Fault Information

As we've seen, “unexpected system behavior” can mean that we're completely screwed. Machine checks aren't great either -- they cause Windows to blue screen and Linux to kernel panic. An incorrect address on a page fault is potentially even worse than a mere crash, and if you dig through the list you can find a lot of other scary sounding bugs.

And keep in mind that the Intel errata list has the following disclaimer:

> Errata remain in the specification update throughout the product's lifecycle, or until a particular stepping is no longer commercially available. Under these circumstances, errata removed from the specification update are archived and available upon request.

Once they stop manufacturing a stepping (the hardware equivalent of a point release), they reserve the right to remove the errata and you won't be able to find out what errata your older stepping has unless you're important enough to Intel.

Anyway, back to 2015. We've seen at least two serious bugs in Intel CPUs in the last quarter[3](https://danluu.com/cpu-bugs/#fn:A), and it's almost certain there are more bugs lurking. Back when I worked at a company that produced Intel compatible CPUs, we did a fair amount of testing and characterization of Intel CPUs; as someone fresh out of school who'd previously assumed that CPUs basically worked, I was surprised by how many bugs we were able to find. Even though I never worked on the characterization and competitive analysis side of things, I still personally found multiple Intel CPU bugs just in the normal course of doing my job, poking around to verify things that seemed non-obvious to me. Turns out things that seem non-obvious to me are sometimes also non-obvious to Intel engineers. As more services move to the cloud and the impact of system hang and reset vulnerabilities increases, we'll see more black hats investing time in finding CPU bugs. We should expect to see a lot more of these when people realize that it's much easier than it seems to find these bugs. There was a time when a CPU family might only have one bug per year, with serious bugs happening once every few years, or even once a decade, but we've moved past that. In part, that's because "unpredictable system behavior" have moved from being an annoying class of bugs that forces you to restart your computation to an attack vector that lets anyone with an AWS account attack random cloud-hosted services, but it's mostly because CPUs [have gotten more complex, making them more difficult to test](https://danluu.com/new-cpu-features/) and [audit](https://danluu.com/cpu-backdoors/) effectively, while Intel appears to be cutting back on validation effort. Ironically, we have hardware virtualization that's supposed to help us with security, but the virtualization is so complicated[4](https://danluu.com/cpu-bugs/#fn:V) that the hardware virtualization implementation is likely to expose "unpredictable system behavior" bugs that wouldn't otherwise have existed. This isn't to say it's hopeless -- it's possible, in principle, to design CPUs such that a hang bug on one core doesn't crash the entire system. It's just that it's a fair amount of work to do that at every level (cache directories, the uncore, etc., would have to be modified to operate when a core is hung, as well as OS schedulers). No one's done the work because it hasn't previously seemed important.

You'll often hear software folks say that these things don't matter because they can (sometimes) be patched. But, many devices will never get patched, which means that hardware security bugs will leave some devices vulnerable for their entire lifetime. And even if you don't care about consumers, serious bugs are very bad for CPU vendors. At a company I worked for, we once had a bug escape validation and get found after we shipped. One OEM wouldn't talk to us for something like five years after that, and other OEMs that continued working with us had to re-qualify their parts with our microcode patch and they made sure to let us know how expensive that was. Intel has enough weight that OEMs can't just walk away from them after a bug, but they don't have unlimited political capital and every serious bug uses up political capital, even if it can be patched.

This isn't to say that we should try to get to zero bugs. There's always going to be a trade off between development speed and and bug rate and the optimal point probably isn't zero bugs. But we're now regularly seeing severe bugs with security implications, which changes the tradeoff a lot. With something like the [FDIV bug](https://en.wikipedia.org/wiki/Pentium_FDIV_bug) you can argue that it's statistically unlikely that any particular user who doesn't run numerical analysis code will be impacted, but security bugs are different. Attackers don't run random code, so you can't just say that it's unlikely that some condition will occur.

### 2024 update

We're approaching a decade since I wrote this post and the serious CPU bugs keep coming. For example, this recent one was found by [RAD tools](https://www.radgametools.com/oodleintel.htm):

> Intel Processor Instability Causing Oodle Decompression Failures
> 
> We believe that this is a hardware problem which affects primarily Intel 13900K and 14900K processors, less likely 13700, 14700 and other related processors as well. Only a small fraction of those processors will exhibit this behavior. The problem seems to be caused by a combination of BIOS settings and the high clock rates and power usage of these processors, leading to system instability and unpredictable behavior under heavy load ... Any programs which heavily use the processor on many threads may cause crashes or unpredictable behavior. There have been crashes seen in RealBench, CineBench, Prime95, Handbrake, Visual Studio, and more. This problem can also show up as a GPU error message, such as spurious "out of video memory" errors, even though it is caused by the CPU.

One can argue that this is a configuration bug, but from the standpoint of a typical user, all what they observe is that their CPU is causing crashes. And, realistically, Intel knows that their CPUs are shipping into systems with these settings. The mitigation for this involves doing things like changing the following settings ""SVID behavior" → "Intel fail safe", "Long duration power limit" → reduce to 125W if set higher ("Processor Base Power" on ARK)", "Short duration power limit" → reduce to 253W if set higher (for 13900/14900 CPUs, other CPUs have other limits! "Maximum Turbo Power" on ARK)", etc.

If they wanted their CPUs to not crash due to this issue, they could have and should have enforced these settings as well as some others. Instead, they left this up to the BIOS settings, and here we are.

Historically, Intel was much more serious about verification, validation, and testing than AMD and we saw this in their output. At one point, when a lot of enthusiast sites were excited about AMD (in the K7 days), Google stopped using AMD and basically banned purchases of AMD CPUs because they were so buggy and had caused so many hard-to-debug problems. But, over time, the relative level of verification/validation/test effort Intel allocates has gone down and Intel seems to have nearly caught or maybe caught AMD in their rate of really serious bugs. Considering Intel's current market position, with very heavy pressure from AMD, ARM, and Nvidia, it seems unlikely that Intel will turn this around in the foreseeable future. Nvidia, historically, has been significantly buggier than AMD or Intel, so Intel still has quite a bit of room to run to become the most buggy major chip manufacturer. Considering that Nvidia is one of the biggest threats to Intel and how Intel responded to threats from other, then-buggier, manufacturers, it seems like we should expect an even higher rate of bad bugs in the coming decade.

On the specific bug, there's tremendous pressure to operate more like a "move fast and break things" software company than a traditional, conservative, CPU manufacturer for multiple reasons. When you make a manufacture a CPU, how fast it will run ends up being somewhat random and there's no reliable way to tell how fast it will run other than testing it, so CPU companies run a set of tests on the CPU to see how fast it will go. This test time is actually fairly expensive, so there's a lot of work done to try to find the smallest set of tests possible that will correctly determine how fast the CPU can operate. One easy way to cut costs here is to just run fewer tests even if the smaller set of tests doesn't fully guarantee that the CPU can operate at the speed it's sold at.

Another factor influencing this is that CPUs that are sold as nominally faster can sell for more, so there's also pressure to push the CPUs as close to their limits as possible. One way we can see that the margin here has, in general, decreased, is by looking at how overclockable CPUs are. People are often happy with their overclocked CPU if they run a few tests, like prime95, stresstest, etc., and their part doesn't crash, but this isn't nearly enough to determine if the CPU can really run everything a user could throw at it, but if you really try to seriously test a CPU (working at an Intel competitor, we would do this regularly), Intel and other CPU companies have really pushed the limit of how fast they claim their CPUs are relative to how fast they actually are, which sometimes results in CPUs that are sold that have been pushed beyond their capabilities.

On overclocking, as Fabian Giesen of RAD notes,

> This stuff is not sanctioned and will count as overclocking if you try to RMA it but it's sold as a major feature of the platform and review sites test with it on.

Daniel Gibson replied with

> hmm on my mainboard (ASUS ROG Strix B550-A Gaming -clearly gaming hardware, but middle price range) I had to explicitly enable the XMP/EXPO profile for the DDR4-RAM to run at full speed - which is DDR4-3200, officially supported by the CPU (Ryzen 5950X). Otherwise it ran at DDR4-2400 speed, I think? Or was it 2133? I forgot, at least significantly lower

To which Fabian noted

> Correct. Fun fact: turning on EXPO technically voids your warranty ... t's great; both the CPU and the RAM list it as supported but it's officially not.
> 
> One might call it a racket, if one were inclined to such incisive language.

Intel didn't used to officially unofficially support this kind of thing. And, more generally, historically, CPU manufacturers were very hesitant to ship parts that had a non-negligible risk of crashes and data corruption when used as intended if they could avoid them, but more and more of these bugs keep happening. Some end up becoming quite public, like this, due to someone publishing a report about them like the RAD report above. And some get quietly reported to the CPU manufacturer by a huge company, often with some kind of NDA agreement, where the big company gets replacement CPUs and Intel or another manufacturer quietly ships firmware fixes to the issue. And it surely must be the case that some of these aren't really caught at all, unless you count the occasional data corruption or crash as being caught.

We now have decades of evidence that the theory that long sentences will deter crime is either empirically false or that the effect is very small; turns out that people who impulse commit crimes don't deeply study sentencing guidelines before they commit crimes. Ironically, for white-collar corporate crimes where Becker's theory might more plausibly hold, Becker's theory isn't applied. [\[return\]](https://danluu.com/cpu-bugs/#fnref:S)

In the time that it takes a sophisticated attacker to find a hole in Azure that will cause an hour of disruption across 1% of VMs, that same attacker could probably completely take down ten unicorns for a much longer period of time.
