# 缓存：LRU 与随机替换｜Caches: LRU v. random

---

## 正文

很久以前，我的 [computer architecture professor](http://pages.cs.wisc.edu/~sohi/) 提到，对 caches 使用 random eviction policy 其实并不那么糟糕。random eviction 并不糟糕，这一点可能令人惊讶——如果你的 cache fills up，而你不得不移除某些内容，那么选择 [least recently used (LRU)](http://www.mathcs.emory.edu/~cheung/Courses/355/Syllabus/9-virtual-mem/LRU-replace.html) 是一个显而易见的选择，因为如果你最近 used 过某项内容，你就更有可能再次 use 它。如果你有一个 tight loop，只要这个 loop fits in cache，LRU 就会表现得完美无缺，但如果这个 loop 不 fit，它就会每次都 cause a miss。当 loop 变得过大时，random eviction policy 会 degrades gracefully。

在实践中，对于 real workloads，random 往往比其他 algorithms 表现更差。但如果我们取 two random choices (2-random)，然后只在这两个 choices 之间使用 LRU，会怎样呢？

下面是我们使用类似 Sandy Bridge 的 cache 对 SPEC CPU[1](https://danluu.com/2choices-eviction/#fn:1) 得到的 relative miss rates（[8-way associative](https://danluu.com/3c-conflict/)，L1、L2 和 L3 caches 的大小分别为 64k、256k 和 2MB）。这些是 ratios（algorithm miss rate : random miss rate）；越 lower 越好。每个 cache 在 cache 的所有 levels 都使用相同的 policy。

| Policy | L1 (64k) | L2 (256k) | L3 (2MB) |
| --- | --- | --- | --- |
| 2-random | 0.91 | 0.93 | 0.95 |
| FIFO | 0.96 | 0.97 | 1.02 |
| LRU | 0.90 | 0.90 | 0.97 |
| random | 1.00 | 1.00 | 1.00 |

Random 和 FIFO 都 strictly worse than LRU 或 2-random。LRU 和 2-random 的表现相当接近，对于较小的 caches，LRU 略胜 2-random；对于较大的 caches，2-random 略胜 LRU。

为了看看某个单独的 benchmark 中是否出现了什么异常，我们可以查看每个 sub-benchmark 的 raw results。下面，每个 benchmark 的 L1、L2 和 L3 miss rates 都 plotted 在同一个 column 中：

![类似 Sandy Bridge 的 cache 的 Cache miss rates](https://danluu.com/images/2choices-eviction/sandy-bridge-miss.webp)

正如我们可能预期的那样，当 miss rates 为 high 时，LRU 比 2-random 表现更差，而当 miss rates 为 low 时，表现更好。

目前尚不清楚，2-random 在 L3 cache miss rates 上胜过 LRU，是因为它在 caches 较大时表现更好，还是因为这是 hierarchical cache 中的 third level。由于一个在 L1 或 L2 中被 actively used 的 cache line 在 L3 中并不会被 touched，因此 L3 中可能发生 eviction（这会迫使 L1 和 L2 都发生 eviction），因为在 L3 看来，那个 line 最近并没有被 used。这使得 LRU 是否是 L3 cache 的良好 eviction policy 变得不那么显而易见。

为了区分这些 effects，让我们看看各种 sizes[2](https://danluu.com/2choices-eviction/#fn:2) 下 non-hierarchical (single level) 与 hierarchical caches 的 relative miss rates。对于 hierarchical cache，L1 和 L2 的 sizes 与上面一样，分别是 64k 和 256k，只有 L3 cache size varies。下面，我们给出了各个 policy 表现的 ratios[3](https://danluu.com/2choices-eviction/#fn:G) 的 geometric means（涵盖所有 SPEC sub-benchmarks，与 random eviction 相比）。这个 metric 的一个潜在缺点是，如果某些 miss rates 非常 low，它们可能会 dominate 这个 mean，因为 small fluctuations 会对 ratio 产生很大影响，不过我们可以查看 results 的 distribution，看看是否确实如此。

![cache sizes 在 64K 与 16M 之间时的 Cache miss ratios](https://danluu.com/images/2choices-eviction/sweep-sizes-mean-ratios.webp)

![cache sizes 在 512K 与 16M 之间时的 L3 cache miss ratios](https://danluu.com/images/2choices-eviction/sweep-sizes-mean-ratios-l3.webp)

在 hierarchical 情况下，没有列出低于 512k 的 Sizes，这是因为 L2 为 256k——我们在这里使用的是 inclusive L3 cache，因此让 L3 小于 L2 实在没有什么意义。高于 16M 的 Sizes 被省略了，因为当 cache 变得过大时，cache miss rates 会 converge，这就没什么意思了。

看看 single cache 的情况，似乎对于较小的 caches，LRU 比 2-random 表现稍好（越 lower 的 miss ratio 越好）；随着 cache 变大，2-random 则略胜 LRU。hierarchical 情况也类似，只是我们实际上没有考察 LRU 更优的那些较小 cache sizes。

Comparing 这两种情况，results 虽然不同，但又足够相似，因此看起来我们最初的 results 并不只是考察 hierarchical cache 的 last level 所产生的 artifact。

下面，我们将查看整个 distribution，以便判断 ratios 的 mean 是否被极小的 results 所 skewed。

![cache sizes 在 512K 与 16M 之间时的 L3 cache miss ratios](https://danluu.com/images/2choices-eviction/sweep-sizes-miss.webp)

![cache sizes 在 512K 与 16M 之间时的 L3 cache miss ratios](https://danluu.com/images/2choices-eviction/sweep-sizes-miss-l3.webp)

看起来，对于某个特定的 cache size（graph 中的一个 column），randomized algorithms 在 miss rates relatively high 时表现更好，而在 miss rates relatively low 时表现更差，因此，如果说有什么影响的话，那么只看 geometric mean 反而对它们不利——如果我们取 arithmetic mean，result 就会被较大的 results 所 dominated，而在这些情况下，2 random choices 和普通的 random 表现相对不错[4](https://danluu.com/2choices-eviction/#fn:C)。

从我们看到的 mean ratios 来说，2-random 对于 large caches 看起来不错；而从我们看到的 results 的 distribution 来说，这是在 mean ratio metric 对 2-random 不利的情况下取得的，这使它对于 large caches 显得相当出色。

然而，implement pseudo-LRU policies 很常见，因为 LRU 可能过于 expensive，以至于无法实际使用。由于 2-random requires 至少与 LRU 一样多的 information，让我们看看使用 pseudo 2-random（approximately 80% accurate）和 pseudo 3-random（一个 two-level tournament，其中每个 level 都 approximately 80% accurate）时会发生什么。

由于 random 和 FIFO 显然不是好的 replacement policies，我会在接下来的 graphs 中省略它们。另外，由于 single cache 和 multi-level cache 情况下的 results 相似，我们只看更贴近实际的 multi-level cache 情况下的 results 就可以了。

![cache sizes 在 512K 与 16M 之间时的 L3 cache miss ratios](https://danluu.com/images/2choices-eviction/sweep-sizes-mean-ratios-l3-pseudo.webp)

由于 pseudo 2-random 在 20% 的情况下表现得像 random，在 80% 的情况下表现得像 2-random，我们可能预期它的表现会落在 2-random 和 random 之间，实际情况正是如此。尝试 improve pseudo 2-random 的一个简单调整，就是试试 pseudo 3-random（evict 3 random choices 中的 least recently used）。虽然它仍然不及真正的 2-random，但已经相当接近，而且对于大于 1M 的 caches，它仍然优于 LRU（以及 pseudo LRU）。

我们尚未探索的一个重要 variable 是 set associativity。为了看看在不同 cache sizes 下 LRU 与 2-random 的比较情况，让我们看看 LRU:2-random miss ratio（higher/red 表示 LRU 更好，lower/green 表示 2-random 更好）。

![cache sizes 在 64K 与 16M 之间、associativities 在与 64 之间时的 Cache miss ratios](https://danluu.com/images/2choices-eviction/sweep-sizes-assocs-mean-ratios.webp)

On average，increasing associativity 会 increases 两种 policies 之间的 difference。与之前一样，LRU 对 small caches 更好，2-random 对 large caches 更好。没有展示为 1 和 2 的 Associativities，因为对于这两种 algorithms，它们的表现应该是 identical 的。

仍有我们尚未尝试的、呈 combinatorial explosion 的 possibilities。一件可以做的事，是在不同 cache levels 尝试不同 eviction policies（L1 和 L2 使用 LRU，L3 使用 2-random，似乎很有前景）。另一件可以做的事，是针对不同 types 的 caches 尝试这种方法。我碰巧选择 CPU caches，是因为 simulators 和 benchmark traces 很容易找到，但在如今这个“给它加个 cache”的世界里，还有很多其他地方可以 applied 2-random[5](https://danluu.com/2choices-eviction/#fn:H)。

对于各位 comp arch 同行，根据这些 data，我怀疑 2-random 赶不上 DIP 这样的 adaptive policies（虽然也可能赶得上——它的表现处于相近范围，但它是在不同 workload 上、使用不同 simulator 进行 characterized 的，所以还不能 100% 确定）。然而，可以 implemented 一种 pseudo 2-random policy，它使用的 resources 几乎不比 pseudo-LRU policies 多，因此与 DIP 相比非常 cheap。另外，我们可以看到，pseudo 3-random 明显优于 pseudo 2-random，这表明对于这个 k，k-random 很可能是对 2-random 的 improvement。某种 k-random policy 也许会是对 DIP 的 improvement。

我们已经看到这样做有效，但最初为什么会有人想到这样做呢？Mitzenmacher、Richa 和 Sitaraman 撰写的 [The Power of Two Random Choices: A Survey of Techniques and Results](http://www.eecs.harvard.edu/~michaelm/postscripts/handbook2001.pdf) 对此有很好的解释。其 mathematical intuition 是，如果我们（randomly）将 n balls throw 进 n bins，那么任何 bin 中的 balls 的 maximum number 都是 `O(log n / log log n)`，且 with high probability，这几乎就是 `O(log n)`。但如果我们不是 choosing randomly，而是 choose k random bins 中的 least loaded，那么 maximum 就是 `O(log log n / log k)`，且 with high probability，也就是说，即使只有 two random choices，它也基本上是 `O(log log n)`，而每个额外的 choice 只会将 load reduces 一个 constant factor。

事实证明，这有各种各样的 applications；[load balancing](http://brooker.co.za/blog/2012/01/17/two-random.html) 和 hash distribution 之类的事情天然适合 balls and bins model。还有许多 applications 与 balls and bins model 的 analogous 关系并不明显，例如 [circuit routing](http://citeseerx.ist.psu.edu/showciting?cid=1042246) 和 [Erdős–Rényi](http://www.math.cmu.edu/math/mathcolloquium.php?SeminarSelect=522) graphs。

## 原文

Once upon a time, my [computer architecture professor](http://pages.cs.wisc.edu/~sohi/) mentioned that using a random eviction policy for caches really isn't so bad. That random eviction isn't bad can be surprising — if your cache fills up and you have to get rid of something, choosing the [least recently used (LRU)](http://www.mathcs.emory.edu/~cheung/Courses/355/Syllabus/9-virtual-mem/LRU-replace.html) is an obvious choice, since you're more likely to use something if you've used it recently. If you have a tight loop, LRU is going to be perfect as long as the loop fits in cache, but it's going to cause a miss every time if the loop doesn't fit. A random eviction policy degrades gracefully as the loop gets too big.

In practice, on real workloads, random tends to do worse than other algorithms. But what if we take two random choices (2-random) and just use LRU between those two choices?

Here are the relative miss rates we get for SPEC CPU[1](https://danluu.com/2choices-eviction/#fn:1) with a Sandy Bridge-like cache ([8-way associative](https://danluu.com/3c-conflict/), 64k, 256k, and 2MB L1, L2, and L3 caches, respectively). These are ratios (algorithm miss rate : random miss rate); lower is better. Each cache uses the same policy at all levels of the cache.

| Policy | L1 (64k) | L2 (256k) | L3 (2MB) |
| --- | --- | --- | --- |
| 2-random | 0.91 | 0.93 | 0.95 |
| FIFO | 0.96 | 0.97 | 1.02 |
| LRU | 0.90 | 0.90 | 0.97 |
| random | 1.00 | 1.00 | 1.00 |

Random and FIFO are both strictly worse than either LRU or 2-random. LRU and 2-random are pretty close, with LRU edging out 2-random for the smaller caches and 2-random edging out LRU for the larger caches.

To see if anything odd is going on in any individual benchmark, we can look at the raw results on each sub-benchmark. The L1, L2, and L3 miss rates are all plotted in the same column for each benchmark, below:

![Cache miss rates for Sandy Bridge-like cache](https://danluu.com/images/2choices-eviction/sandy-bridge-miss.webp)

As we might expect, LRU does worse than 2-random when the miss rates are high, and better when the miss rates are low.

At this point, it's not clear if 2-random is beating LRU in L3 cache miss rates because it does better when the caches are large or because it does better because it's the third level in a hierarchical cache. Since a cache line that's being actively used in L1 or L2 isn't touched in L3, an eviction can happen from the L3 (which forces an eviction of both the L1 and L2) since, as far as the L3 is concerned, that line hasn't been used recently. This makes it less obvious that LRU is a good eviction policy for L3 cache.

To separate out the effects, let's look at the relative miss rates for a non-hierarchical (single level) vs. hierarchical caches at various sizes[2](https://danluu.com/2choices-eviction/#fn:2). For the hierarchical cache, the L1 and L2 sizes are as above, 64k and 256k, and only the L3 cache size varies. Below, we've got the geometric means of the ratios[3](https://danluu.com/2choices-eviction/#fn:G) of how each policy does (over all SPEC sub-benchmarks, compared to random eviction). A possible downside to this metric is that if we have some very low miss rates, those could dominate the mean since small fluctuations will have a large effect on the ratio, but we can look the distribution of results to see if that's the case.

![Cache miss ratios for cache sizes between 64K and 16M](https://danluu.com/images/2choices-eviction/sweep-sizes-mean-ratios.webp)

![L3 cache miss ratios for cache sizes between 512K and 16M](https://danluu.com/images/2choices-eviction/sweep-sizes-mean-ratios-l3.webp)

Sizes below 512k are missing for the hierarchical case because of the 256k L2 — we're using an inclusive L3 cache here, so it doesn't really make sense to have an L3 that's smaller than the L2. Sizes above 16M are omitted because cache miss rates converge when the cache gets too big, which is uninteresting.

Looking at the single cache case, it seems that LRU works a bit better than 2-random for smaller caches (lower miss ratio is better), 2-random edges out LRU as the cache gets bigger. The story is similar in the hierarchical case, except that we don't really look at the smaller cache sizes where LRU is superior.

Comparing the two cases, the results are different, but similar enough that it looks our original results weren't only an artifact of looking at the last level of a hierarchical cache.

Below, we'll look at the entire distribution so we can see if the mean of the ratios is being skewed by tiny results.

![L3 cache miss ratios for cache sizes between 512K and 16M](https://danluu.com/images/2choices-eviction/sweep-sizes-miss.webp)

![L3 cache miss ratios for cache sizes between 512K and 16M](https://danluu.com/images/2choices-eviction/sweep-sizes-miss-l3.webp)

It looks like, for a particular cache size (one column of the graph), the randomized algorithms do better when miss rates are relatively high and worse when miss rates are relatively low, so, if anything, they're disadvantaged when we just look at the geometric mean — if we were to take the arithmetic mean, the result would be dominated by the larger results, where 2 random choices and plain old random do relatively well[4](https://danluu.com/2choices-eviction/#fn:C).

From what we've seen of the mean ratios, 2-random looks fine for large caches, and from what we've seen of the distribution of the results, that's despite 2-random being penalized by the mean ratio metric, which makes it seem pretty good for large caches.

However, it's common to implement pseudo-LRU policies because LRU can be too expensive to be workable. Since 2-random requires having at least as much information as LRU, let's take a look at what happens we use pseudo 2-random (approximately 80% accurate), and pseudo 3-random (a two-level tournament, each level of which is approximately 80% accurate).

Since random and FIFO are clearly not good replacement policies, I'll leave them out of the following graphs. Also, since the results were similar in the single cache as well as multi-level cache case, we can just look at the results from the more realistic multi-level cache case.

![L3 cache miss ratios for cache sizes between 512K and 16M](https://danluu.com/images/2choices-eviction/sweep-sizes-mean-ratios-l3-pseudo.webp)

Since pseudo 2-random acts like random 20% of the time and 2-random 80% of the time, we might expect it to fall somewhere between 2-random and random, which is exactly what happens. A simple tweak to try to improve pseudo 2-random is to try pseudo 3-random (evict the least recently used of 3 random choices). While that's still not quite as good as true 2-random, it's pretty close, and it's still better than LRU (and pseudo LRU) for caches larger than 1M.

The one big variable we haven't explored is the set associativity. To see how LRU compares with 2-random across different cache sizes let's look at the LRU:2-random miss ratio (higher/red means LRU is better, lower/green means 2-random is better).

![Cache miss ratios for cache sizes between 64K and 16M with associativities between and 64](https://danluu.com/images/2choices-eviction/sweep-sizes-assocs-mean-ratios.webp)

On average, increasing associativity increases the difference between the two policies. As before, LRU is better for small caches and 2-random is better for large caches. Associativities of 1 and 2 aren't shown because they should be identical for both algorithms.

There's still a combinatorial explosion of possibilities we haven't tried yet. One thing to do is to try different eviction policies at different cache levels (LRU for L1 and L2 with 2-random for L3 seems promising). Another thing to do is to try this for different types of caches. I happened to choose CPU caches because it's easy to find simulators and benchmark traces, but in today's “put a cache on it” world, there are a lot of other places 2-random can be applied[5](https://danluu.com/2choices-eviction/#fn:H).

For any comp arch folks, from this data, I suspect that 2-random doesn't keep up with adaptive policies like DIP (although it might — it's in the right ballpark, but it was characterized on a different workload using a different simulator, so it's not 100% clear). However, A pseudo 2-random policy can be implemented that barely uses more resources than pseudo-LRU policies, which makes this very cheap compared to DIP. Also, we can see that pseudo 3-random is substantially better than pseudo 2-random, which indicates that k-random is probably an improvement over 2-random for the k. Some k-random policy might be an improvement over DIP.

So we've seen that this works, but why would anyone think to do this in the first place? [The Power of Two Random Choices: A Survey of Techniques and Results by Mitzenmacher, Richa, and Sitaraman](http://www.eecs.harvard.edu/~michaelm/postscripts/handbook2001.pdf) has a great explanation. The mathematical intuition is that if we (randomly) throw n balls into n bins, the maximum number of balls in any bin is `O(log n / log log n)` with high probability, which is pretty much just `O(log n)`. But if (instead of choosing randomly) we choose the least loaded of k random bins, the maximum is `O(log log n / log k)` with high probability, i.e., even with two random choices, it's basically `O(log log n)` and each additional choice only reduces the load by a constant factor.

This turns out to have all sorts of applications; things like [load balancing](http://brooker.co.za/blog/2012/01/17/two-random.html) and hash distribution are natural fits for the balls and bins model. There are also a lot of applications that aren't obviously analogous to the balls and bins model, like [circuit routing](http://citeseerx.ist.psu.edu/showciting?cid=1042246) and [Erdős–Rényi](http://www.math.cmu.edu/math/mathcolloquium.php?SeminarSelect=522) graphs.
