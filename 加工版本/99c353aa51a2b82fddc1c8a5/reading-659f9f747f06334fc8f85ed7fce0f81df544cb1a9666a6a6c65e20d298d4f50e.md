# 单体仓库的优势｜Advantages of monorepos

---

## 正文

下面这段对话，我总是反复遇到：

> **某人**：你听说 Facebook/Google 使用一个 giant monorepo 了吗？卧槽！  
> **我**：是啊！这真的很方便，你不觉得吗？  
> **某人**：这是我听过的最荒谬的事。难道 FB 和 Google 不知道，把你所有的 code 放进 single repo 是个多么糟糕的主意吗？  
> **我**：我想，FB 和 Google 的 engineers 大概很熟悉使用 smaller repos（[Junio Hamano](http://en.wikipedia.org/wiki/Junio_Hamano) 不就在 Google 工作吗？），但他们仍然因为\[这些原因\]而更喜欢 single huge repo。  
> **某人**：哦，那听起来确实挺不错。我还是觉得奇怪，不过我能理解为什么有人会想要这样了。

“\[这些原因\]”说起来相当长，所以我把它写下来，免得一遍又一遍地重复同样的对话。

### 简化的 organization

使用 multiple repos 时，你通常要么让每个 repo 有一个 project，要么让每个 repo 包含一组 related projects，但这迫使你为自己的团队或公司 define 什么才算一个“project”，有时还迫使你出于纯属 overhead 的原因去 split 和 merge repos。例如，因为一个 project 对你的 VCS 来说太大，或者有太多 history，就不得不 split 它，这并不 optimal。

使用 monorepo 时，projects 可以按照你认为最 logically consistent 的任何方式来 organized 和 grouped together，而不只是因为你的 version control system 迫使你以某种特定方式来 organize 这些东西。使用 single repo 还会 reduces 管理 dependencies 所带来的 overhead。

simplified organization 的一个 side effect 是，navigate projects 变得更容易。我用过的 monorepos 基本上让你能够像一切都在 networked file system 上那样 navigate，re-using 在 projects 内部 navigate 时使用的 idiom。Multi repo setups 通常有两个 separate levels 的 navigation -- 一是在 projects 内部使用的 filesystem idiom，另一个则是用于在 projects 之间 navigating 的 meta-level。

那个 side effect 又带来一个 side effect：使用 monorepos 时，往往很容易就能把 dev environment set up 好，以 run builds 和 tests。如果你预期能用相当于 `cd` 的方式在 projects 之间 navigate，你也会预期能执行 `cd; make`。既然这要是不能工作就显得很奇怪，它通常也就能工作，而为了让它工作所必需的 tooling 工作也都会完成[1](https://danluu.com/monorepo/#fn:R)。虽然在 multiple repos 中实现这种便利在技术上是可能的，但它没有那么自然，这意味着所需的工作也就没有那么经常得到完成。

### 简化的 dependencies

这大概不用说，但使用 multiple repos 时，你需要有某种方式来 specifying 和 versioning 它们之间的 dependencies。这听起来应该很直接，但实际上，大多数 solutions 都很繁琐，而且涉及大量 overhead。

使用 monorepo 时，很容易让所有 projects 都有一个 universal version number。由于 atomic cross-project commits 是可能的（尽管在大公司里，出于实际原因，它们往往会 split 成许多部分），repository 可以始终处于 consistent state -- 在 commit #X，所有 project builds 都应该能工作。Dependencies 仍然需要在 build system 中被 specified，但无论那是 make Makefiles 还是 bazel BUILD files，它们都可以像其他所有东西一样被 checked into version control。而且，由于只有一个 version number，Makefiles、BUILD files 或者你选择的其他东西，都不需要 specify version numbers。

### Tooling（工具支持）

navigation 和 dependencies 的 simplification 使 write tools 容易得多。tools 不必既理解 repositories 之间的 relationships，又理解 repositories 内部 files 的 nature，而基本上只需要能够 read files（包括某种 file format，用来 specifies repo 内部 units 之间的 dependencies）。

这听起来像件小事，不过，[看看 Christopher Van Arsdale 的这个例子](https://github.com/chrisvana/repobuild/wiki/Motivation)，就知道 builds 可以变得多么容易：

> [Google 内部的 build system](http://bazel.io/) 让使用 large modular blocks of code 来 build software 变得极其容易。你想要一个 crawler？在这里 Add 几行 lines。你需要一个 RSS parser？再 Add 几行 lines。一个 large distributed, fault tolerant datastore？当然，再 add 几行 lines。这些都是由许多 projects shared、而且易于 integrate 的 building blocks 和 services。……这种 Lego-like development process 在 open source 世界里并不能如此 cleanly 地实现。……由于这种状况（更多的推测），open source 中存在一道 complexity barrier，在过去几年里并没有 changed significantly。这就在 Google 这样的公司里容易获得的东西与一个$$n$$ open sourced project 中容易获得的东西之间造成了差距。

Arsdale 所指的 system 如此方便，以至于在它被 open sourced 之前，[Facebook](https://facebook.github.io/buck/) 和 [Twitter](https://pantsbuild.github.io/) 的前 Google engineers 就为了获得同样的好处，wrote 了各自的 bazel versions。

从理论上说，即使没有 monorepo，也可能 create 一个 build system，让 building 任何东西、使用任何 dependencies 都变得简单，但这需要更多工作，多到我从未见过一个 system 能 seamlessly 地做到这一点。Maven 和 sbt 在某种程度上相当不错，但在 tracking down 和 fixing version dependency issues 上耗费大量时间，并不罕见。rbenv 和 virtualenv 这样的 Systems 试图绕开这个问题，但它们导致 development environments 大量 proliferation。使用一个 HEAD 始终 points to consistent 且 valid version 的 monorepo，就能完全 removes tracking multiple repo versions 的问题[2](https://danluu.com/monorepo/#fn:V)。

Build systems 并不是唯一能从 running on mono repo 中受益的东西。举个例子，static analysis 可以跨越 project boundaries 来 run，而无须任何额外工作。许多其他东西，例如 cross-project integration testing 和 [code search](https://github.com/google/codesearch)，也都得到了极大的 simplified。

### 跨项目变更（Cross-project changes）

有大量 repos 时，进行 cross-repo changes 很痛苦。这通常涉及在各个 repo 之间进行繁琐的 manual coordination，或者使用 hack-y scripts。而且，即使 scripts 能正常工作，也存在 correctly updating cross-repo version dependencies 的 overhead。对数十个 active internal projects 都在使用的 API 进行 Refactoring，可能就要花掉一天中的大半时间。对数千个 active internal projects 都在使用的 API 进行 Refactoring，则毫无希望。

有了 monorepo，你只需在一个 commit 中 [refactor API 及其所有 callers](http://research.google.com/pubs/pub41342.html)。这并不总是 trivial，但比起使用大量 small repos，要容易得多。我见过在数百个 projects 中有数千处 usages 的 APIs 被 refactored；有了 monorepo setup，这件事就容易到谁都不会再三犹豫。

现在，大多数人都认为，使用 CVS、RCS 或 ClearCase 这样的 version control system 很荒谬：其中无法跨 multiple files 进行一次 single atomic commit，迫使人们要么 manually 查看 timestamps 和 commit messages，要么保留 meta information，以 determine 某一组特定的 cross-file changes 是否“真正”是 atomic。SVN、hg、git 等解决了 atomic cross-file changes 的问题；monorepos 则跨 projects 解决了同样的问题。

这不仅对 large-scale API refactorings 有用。David Turner 曾参与 twitter 从许多 repos 向 monorepo 的 migration，他给出了下面这个例子，说明一个 small cross-cutting change，以及不得不为这类 changes 进行 releases 所带来的 overhead：

> 我需要 update \[Project A\]，但为此，我需要同事先 fix 它的一个 dependencies，即 \[Project B\]。而这位同事又需要先 fix \[Project C\]。如果我必须先等 C 进行 release，再等 B，然后才能 fix 并 deploy A，那我可能现在还在等。但因为所有东西都在同一个 repo 中，同事可以先进行他的 change 并 commit，然后我就能立刻进行我的 change。
> 
> 我想，如果所有东西都通过 git versions 来 linked，我也能这样做，但同事仍然得进行两次 commits。而且，人总是忍不住想随便选一个 version，然后让它“stabilize”（也就是说，停滞不前）。如果你只有一个 project，那没什么问题；但当你有一张由存在 interdependencies 的 projects 构成的网时，就不太好了。
> 
> \[反过来说，\] Forcing _dependees_ 去 update，其实也是 monorepo 的另一个好处。

不仅进行 cross-project changes 更容易，tracking 它们也更容易。要跨 multiple repos 做到相当于 `git bisect` 的事情，你必须自觉使用另一个 tool 来 track meta information，而大多数 projects 根本不会这么做。即使做了，你现在也有了两个截然不同的 tools，而原本一个就足够了。

讽刺的是，从某种意义上说，这一好处会随着公司规模扩大而减少。在算不上小的 Twitter，David Turner 从能够 ship cross-project changes 这件事中获益良多。但在 Google 那样规模的公司，large commits 可能大到出于各种原因，将它们 split 成许多 smaller commits 才更合理；这就需要能够有效地将 large conceptually atomic changes split up 为许多 non-atomic commits 的 tooling。

### Mercurial 和 git 很棒；这是真的

针对这些观点，我收到的最常见回应是，从 CVS 或 SVN switching 到 git 或 hg，会极大地提高 productivity。这是真的。但其中很大一部分是因为 git 和 hg 在多个方面更胜一筹（例如，更好的 merging），而不是因为拥有 small repos 本身更好。

事实上，Twitter 一直在 patching git，而 [Facebook 一直在 patching Mercurial](https://code.facebook.com/posts/218678814984400/scaling-mercurial-at-facebook/)，以 support giant monorepos。

### 缺点

当然，使用 monorepo 也有缺点。我不打算讨论它们，因为这些缺点已经得到了广泛讨论。Monorepos 并不 strictly superior to manyrepos。它们也并不 strictly worse。我的意思不是说你一定应该 switch 到 monorepo；我只是说，使用 monorepo 并非完全不合理，Google、Facebook、Twitter、Digital Ocean 和 Etsy 等公司的那些人，可能有充分的理由，宁愿选择 monorepo，也不选择数百、数千乃至数万个 smaller repos。

## 原文

Here's a conversation I keep having:

> **Someone**: Did you hear that Facebook/Google uses a giant monorepo? WTF!  
> **Me**: Yeah! It's really convenient, don't you think?  
> **Someone**: That's THE MOST RIDICULOUS THING I've ever heard. Don't FB and Google know what a terrible idea it is to put all your code in a single repo?  
> **Me**: I think engineers at FB and Google are probably familiar with using smaller repos (doesn't [Junio Hamano](http://en.wikipedia.org/wiki/Junio_Hamano) work at Google?), and they still prefer a single huge repo for \[reasons\].  
> **Someone**: Oh that does sound pretty nice. I still think it's weird but I could see why someone would want that.  

“\[reasons\]” is pretty long, so I'm writing this down in order to avoid repeating the same conversation over and over again.

### Simplified organization

With multiple repos, you typically either have one project per repo, or an umbrella of related projects per repo, but that forces you to define what a “project” is for your particular team or company, and it sometimes forces you to split and merge repos for reasons that are pure overhead. For example, having to split a project because it's too big or has too much history for your VCS is not optimal.

With a monorepo, projects can be organized and grouped together in whatever way you find to be most logically consistent, and not just because your version control system forces you to organize things in a particular way. Using a single repo also reduces overhead from managing dependencies.

A side effect of the simplified organization is that it's easier to navigate projects. The monorepos I've used let you essentially navigate as if everything is on a networked file system, re-using the idiom that's used to navigate within projects. Multi repo setups usually have two separate levels of navigation -- the filesystem idiom that's used inside projects, and then a meta-level for navigating between projects.

A side effect of that side effect is that, with monorepos, it's often the case that it's very easy to get a dev environment set up to run builds and tests. If you expect to be able to navigate between projects with the equivalent of `cd`, you also expect to be able to do `cd; make`. Since it seems weird for that to not work, it usually works, and whatever tooling effort is necessary to make it work gets done[1](https://danluu.com/monorepo/#fn:R). While it's technically possible to get that kind of ease in multiple repos, it's not as natural, which means that the necessary work isn't done as often.

### Simplified dependencies

This probably goes without saying, but with multiple repos, you need to have some way of specifying and versioning dependencies between them. That sounds like it ought to be straightforward, but in practice, most solutions are cumbersome and involve a lot of overhead.

With a monorepo, it's easy to have one universal version number for all projects. Since atomic cross-project commits are possible (though these tend to split into many parts for practical reasons at large companies), the repository can always be in a consistent state -- at commit #X, all project builds should work. Dependencies still need to be specified in the build system, but whether that's a make Makefiles or bazel BUILD files, those can be checked into version control like everything else. And since there's just one version number, the Makefiles or BUILD files or whatever you choose don't need to specify version numbers.

### Tooling

The simplification of navigation and dependencies makes it much easier to write tools. Instead of having tools that must understand relationships between repositories, as well as the nature of files within repositories, tools basically just need to be able to read files (including some file format that specifies dependencies between units within the repo).

This sounds like a trivial thing but, [take this example by Christopher Van Arsdale](https://github.com/chrisvana/repobuild/wiki/Motivation) on how easy builds can become:

> [The build system inside of Google](http://bazel.io/) makes it incredibly easy to build software using large modular blocks of code. You want a crawler? Add a few lines here. You need an RSS parser? Add a few more lines. A large distributed, fault tolerant datastore? Sure, add a few more lines. These are building blocks and services that are shared by many projects, and easy to integrate. … This sort of Lego-like development process does not happen as cleanly in the open source world. … As a result of this state of affairs (more speculation), there is a complexity barrier in open source that has not changed significantly in the last few years. This creates a gap between what is easily obtainable at a company like Google versus a\[n\] open sourced project.

The system that Arsdale is referring to is so convenient that, before it was open sourced, ex-Google engineers at [Facebook](https://facebook.github.io/buck/) and [Twitter](https://pantsbuild.github.io/) wrote their own versions of bazel in order to get the same benefits.

It's theoretically possible to create a build system that makes building anything, with any dependencies, simple without having a monorepo, but it's more effort, enough effort that I've never seen a system that does it seamlessly. Maven and sbt are pretty nice, in a way, but it's not uncommon to lose a lot of time tracking down and fixing version dependency issues. Systems like rbenv and virtualenv try to sidestep the problem, but they result in a proliferation of development environments. Using a monorepo where HEAD always points to a consistent and valid version removes the problem of tracking multiple repo versions entirely[2](https://danluu.com/monorepo/#fn:V).

Build systems aren't the only thing that benefit from running on a mono repo. Just for example, static analysis can run across project boundaries without any extra work. Many other things, like cross-project integration testing and [code search](https://github.com/google/codesearch) are also greatly simplified.

### Cross-project changes

With lots of repos, making cross-repo changes is painful. It typically involves tedious manual coordination across each repo or hack-y scripts. And even if the scripts work, there's the overhead of correctly updating cross-repo version dependencies. Refactoring an API that's used across tens of active internal projects will probably a good chunk of a day. Refactoring an API that's used across thousands of active internal projects is hopeless.

With a monorepo, you just [refactor the API and all of its callers](http://research.google.com/pubs/pub41342.html) in one commit. That's not always trivial, but it's much easier than it would be with lots of small repos. I've seen APIs with thousands of usages across hundreds of projects get refactored and with a monorepo setup it's so easy that it's no one even thinks twice.

Most people now consider it absurd to use a version control system like CVS, RCS, or ClearCase, where it's impossible to do a single atomic commit across multiple files, forcing people to either manually look at timestamps and commit messages or keep meta information around to determine if some particular set of cross-file changes are “really” atomic. SVN, hg, git, etc solve the problem of atomic cross-file changes; monorepos solve the same problem across projects.

This isn't just useful for large-scale API refactorings. David Turner, who worked on twitter's migration from many repos to a monorepo gives this example of a small cross-cutting change and the overhead of having to do releases for those:

> I needed to update \[Project A\], but to do that, I needed my colleague to fix one of its dependencies, \[Project B\]. The colleague, in turn, needed to fix \[Project C\]. If I had had to wait for C to do a release, and then B, before I could fix and deploy A, I might still be waiting. But since everything's in one repo, my colleague could make his change and commit, and then I could immediately make my change.
> 
> I guess I could do that if everything were linked by git versions, but my colleague would still have had to do two commits. And there's always the temptation to just pick a version and "stabilize" (meaning, stagnate). That's fine if you just have one project, but when you have a web of projects with interdependencies, it's not so good.
> 
> \[In the other direction,\] Forcing _dependees_ to update is actually another benefit of a monorepo.

It's not just that making cross-project changes is easier, tracking them is easier, too. To do the equivalent of `git bisect` across multiple repos, you must be disciplined about using another tool to track meta information, and most projects simply don't do that. Even if they do, you now have two really different tools where one would have sufficed.

Ironically, there's a sense in which this benefit decreases as the company gets larger. At Twitter, which isn't exactly small, David Turner got a lot of value out of being able to ship cross-project changes. But at a Google-sized company, large commits can be large enough that it makes sense to split them into many smaller commits for a variety of reasons, which necessitates tooling that can effectively split up large conceptually atomic changes into many non-atomic commits.

### Mercurial and git are awesome; it's true

The most common response I've gotten to these points is that switching to either git or hg from either CVS or SVN is a huge productivity win. That's true. But a lot of that is because git and hg are superior in multiple respects (e.g., better merging), not because having small repos is better per se.

In fact, Twitter has been patching git and [Facebook has been patching Mercurial](https://code.facebook.com/posts/218678814984400/scaling-mercurial-at-facebook/) in order to support giant monorepos.

### Downsides

Of course, there are downsides to using a monorepo. I'm not going to discuss them because the downsides are already widely discussed. Monorepos aren't strictly superior to manyrepos. They're not strictly worse, either. My point isn't that you should definitely switch to a monorepo; it's merely that using a monorepo isn't totally unreasonable, that folks at places like Google, Facebook, Twitter, Digital Ocean, and Etsy might have good reasons for preferring a monorepo over hundreds or thousands or tens of thousands of smaller repos.
