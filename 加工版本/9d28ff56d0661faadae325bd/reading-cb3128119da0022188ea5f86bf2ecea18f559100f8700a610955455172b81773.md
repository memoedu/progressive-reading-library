# 英特尔为何引入缓存分区｜Why Intel added cache partitioning

---

## 正文

[典型的 server utilization 在 10% 到 50% 之间。Google 已经展示了 90% utilization，且_不会 impacting latency SLAs_](http://csl.stanford.edu/~christos/publications/2015.heracles.isca.pdf)。[Xkcd 估计 Google 拥有 2 million machines](https://what-if.xkcd.com/63/)。如果你估计 amortized total cost 为 [$4k per machine per year](http://www.morganclaypool.com/doi/pdf/10.2200/S00516ED2V01Y201306CAC024), that's $每年 8 billion。有了这样的数字，即使小幅 improvements 也会带来很大的 impact，而这可不是小幅 improvement。

如何才能在同样的 hardware 上获得 2x 到 9x 的更好 utilization？这些典型 utilization 数字的 low end，源于 service 有 variable demand，而 machine allocations 是 fixed。假设你有 100 machines 专门用于 Jenkins。当 devs 活跃时，这些 machines 可能非常繁忙，但在凌晨 3 点，它们也可能只有 2% utilization。Dynamic allocation（在不需要这些 machines 时，将它们 switching 到其他 work）可以将典型 latency-sensitive service 的 utilization 提高到 30%-70% range 中的某个水平。要在有 tight SLAs 的各种 latency-sensitive workloads 上做得更好，我们就需要某种办法，在同样的 machines 上 schedule low priority work，同时不 affecting high priority work 的 latency。

这是否可能，并不显而易见。如果 high 和 low priority workloads 都需要 monopolize 某些 shared resources，例如 last-level cache (LLC)、memory bandwidth、disk bandwidth 或 network bandwidth，那我们就没办法了。除了一些 specialized services，很少会 max out disk 或 network。但 caches 和 memory 呢？事实证明，[Ferdman et al.](http://www.industry-academia.org/download/ASPLOS12_Clearing_the_Clouds.pdf) 早在 2012 年就研究过这个问题，并发现，尽管现代 server chips 拥有大得多的 caches，典型 server workloads 并不会因拥有超过 4MB - 6MB 的 LLC 而 benefit。

![](https://danluu.com/images/intel-cat/server_llc.webp)

在这张 graph 中，scale-out workloads 指的是 distributed key-value stores、MapReduce-like computations、web search、web serving 等。SPECint(mcf) 是一种传统的 workstation benchmark。“server” 指的是 SPECweb 和 TPC 这样的老式 server benchmarks。我们可以看到，LLC 从 4MB 增加到 11MB，对典型 datacenter workloads 的 effect 很小，但对这个传统 workstation benchmark 的 effect 却很 significant。

Datacenter workloads 所 operate on 的 data sets 如此 large，以至于通常不可能将 dataset fit 到 single machine 的 RAM 中，更不用说 cache 了，因此更大的 LLC 并不是特别 useful。[Kanev et al. 的 ISCA 2015 paper 对 Google 的 workloads 进行了研究，confirmed 了这个 result](http://www.eecs.harvard.edu/~skanev/papers/isca15wsc.pdf)。他们还表明，memory bandwidth utilization 平均而言相当 low。

![](https://danluu.com/images/intel-cat/low_bandwidth_utilization.webp)

你可能会认为，low bandwidth utilization 是因为 workloads 是 compute bound，而且没有很多 memory accesses。然而，当作者研究 cores 在做什么时，他们发现大量时间都处于 stalled 状态，在等待 cache/memory。

![](https://danluu.com/images/intel-cat/cache_stalls.webp)

每个 row 都是一个 Google workload。在 running 这些典型 workloads 时，cores 有 46% 到 61% 的时间 blocked on cache/memory。奇怪的是，我们既有 low cache hit rates，又有大量时间 stalled on cache/memory，同时还有 low bandwidth utilization。这暗示 workloads 花了大量时间等待 memory accesses，而这些 memory accesses 存在某种 dependencies，导致它们无法被 executed independently。

high-end server chips 的 LLCs 在 12MB 到 30MB 之间，尽管我们只需要 4MB 就能获得 90% 的 performance，而 bandwidth 的 90%-ile utilization 是 31%。这似乎是对 resources 的浪费。我们有大量 resources 处于 idle 状态，或者没有被 used effectively。好消息是，既然 chips 上 shared resources 的 utilization 如此 low，我们应该能够在一台 machine 上 schedule multiple tasks，而不会 degrading performance。

太好了！当我们在一台 machine 上 schedule multiple tasks 时，会发生什么？[Lo et al. 今年在 ISCA 发表的 Heracles paper 非常详细地探讨了这个问题](http://csl.stanford.edu/~christos/publications/2015.heracles.isca.pdf)。Heracles 的目标是，通过在同一台 machine 上 co-locating multiple tasks，获得更好的 machines utilization。

![](https://danluu.com/images/intel-cat/heracles_interference.webp)

上面的 figure 展示了三种具有 strict SLAs 的 latency sensitive (LC) workloads。websearch 是 Google search 中的 query serving service，ml\_cluster 是 real-time text clustering，而 memkeyval 是一个 analogous to memcached 的 key-value store。这些 values 是 latencies 占 SLA 所允许的 maximum 的 percent。columns 表示 service 的 load，rows 表示不同 types 的 interference。LLC、DRAM 和 Network 正如其名称所示；它们是专门设计为仅 compete 那一种 resource 的 custom tasks。HyperThread 意味着 interfering task 是一个 spinloop，在同一个 core 的另一个 hyperthread 中 running（甚至不考虑在同一个 hyperthread 中 running，因为 OS context switches 太 expensive）。CPU power 是一个专门设计为 use 大量 power 并 induce thermal throttling 的 task。Brain 是 deep learning。所有 interference tasks 都在一个具有 low priority 的 container 中 run。

这张 figure 包含很多内容，但我们马上就能看出，当仅使用 container priorities 时，我们想要 schedule 的 best effort (BE) task 无法与任何 LC tasks co-exist -- 所有 `brain` rows 都是红色的，即使在 low utilization（最左边的 columns）下，latency 也远远高于 SLA latency 的 100%.. 同样清楚的是，不同 LC tasks 有不同的 profiles，能够 handle 不同 types 的 interference。例如，websearch 和 ml\_cluster 既不是 network intensive，也不是 compute intensive，因此它们能很好地 handle network 和 power interference。然而，由于 memkeyval 既是 network intensive，又是 compute intensive，它无法 handle network 或 power interference 中的任何一种。这篇 paper 更详细地讨论了你能从 table 的细节中 infer 出什么。我觉得这是这篇 paper 最有趣的部分之一；我打算跳过它，但如果你对这类事情感兴趣，我建议读一读这篇 paper。

作者作出的一个 simplifying assumption 是，这些 types 的 interference 基本上是 independent 的。这意味着，通过 independent mechanisms 将 LC task 与每一种 individual resource 的“过量”使用 isolate 开来，应该就足以 prevent overall interference。也就是说，我们可以为每一种 resource usage set 某个 cap，然后只要保持在每个 cap 以下即可。然而，这个 assumption 并不完全 true -- 例如，作者展示了这张 figure，将 LLC cache size 与 allocated 给 LC task 的 cores 数量 relates 起来。

![](https://danluu.com/images/intel-cat/llc_vs_cores.webp)

vertical axis 表示 LC task 在 allocated 某个特定 LLC 和 cores 数量时，在 violating 其 SLA 之前能够 handle 的 max load。我们可以看到，cache 与 cores 之间可以 trade off，这意味着我们实际上可以在一个 dimension 上超过 resource cap，并通过少用另一种 resource 来 maintain 我们的 SLA。在 general case 下，我们或许也能 trade off 其他 resources。然而，可以 independently 处理每种 resource 的 assumption，将一个 complex optimization problem reduces 成了相对 straightforward 的问题。

现在，让我们看看每一种 shared resource interference，以及 Heracles 如何 allocates resources 来 prevent SLA-violating interference。

#### Core（核心）

将 LC 和 BE tasks 进行 Pinning，使其位于不同的 cores，就足以 prevent same-core context switching interference 和 hyperthreading interference。为此，Heracles 使用了 [cpuset](https://www.kernel.org/doc/Documentation/cgroups/cpusets.txt)。Cpuset 允许你将一个 process（及其 children）limit 为只能在一个 limited set 的 CPUs 上 run。

#### Network（网络）

在 local machines 上，Heracles 使用 [qdisc](https://wiki.archlinux.org/index.php/Advanced_traffic_control) 来 enforce quotas。要进一步了解 cpuset、qdisc 和其他 quota/partitioning mechanisms，[Neil Brown 撰写的这组关于 cgroups 的 LWN 系列文章是很好的起点](https://lwn.net/Articles/604609/)。如今，许多广泛使用的 software 都在使用 Cgroups（Docker、Kubernetes、Mesos 等）；即使你不关心这一特定 application，它们也很可能值得了解。

#### Power（功率）

Heracles 使用 [Intel 的 running average power limit](https://01.org/blogs/tlcounts/2014/running-average-power-limit-%E2%80%93-rapl) 来 estimate power。这是 Sandy Bridge (2009) 及更新的 processors 上的一项 feature，它使用一些 on-chip monitoring hardware 来相当 precisely 地 estimate power usage。[Per-core dynamic voltage and frequency scaling](http://www.cs.binghamton.edu/~millerti/cs680r/papers/DVFS/SystemLevelAnalysis.pdf) 被用于 limit 特定 cores 的 power usage，以免它们 going over budget。

#### Cache（缓存）

前面那些 isolation mechanisms 已经存在一段时间了，但这一项是 Broadwell chips（于 2015 年发布）新增的。这里的问题是，如果 BE task 需要 1MB 的 LLC，而 LC task 需要 4MB 的 LLC，那么来自 BE task 的一次 large allocation 就会在整个 shared LLC 中 scribble，wiping out LC 所需的那 4MB cached data。

Intel 的“[Cache Allocation Technology](http://www.intel.com/content/dam/www/public/us/en/documents/manuals/64-ia-32-architectures-software-developer-vol-3b-part-2-manual.pdf)”（CAT）允许 LLC 对哪些 cores 可以 access cache 的不同 parts 进行 limit。既然我们往往本来就想将 performance sensitive tasks 进行 pin，使其位于 cores 上，这就使我们能够按 per-task basis 来 divide up cache。

![](https://danluu.com/images/intel-cat/CAT_LLC.webp)

Intel 的[2015 年 4 月关于他们所称的 Cache Allocation Technology (CAT) 的 whitepaper](http://www.intel.com/content/dam/www/public/us/en/documents/white-papers/cache-allocation-technology-white-paper.pdf) 中，有一些比较 CAT vs. no-CAT 的 simple benchmarks。在这个 example 中，他们在另一个 application 存在 heavy CPU-to-memory traffic 时，分别在 CAT on 和 off 的情况下，measure respond to PCIe interrupts 的 latency。

| Condition | Min | Max | Avg |
| --- | --- | --- | --- |
| no CAT | 1.66 | 30.91 | 4.53 |
| CAT | 1.22 | 20.98 | 1.62 |

使用 CAT 时，average latency 是不使用 CAT 时 latency 的 36%。Tail latency 并没有 improve 那么多，但也有 substantial improvement。这很有意思，不过对我而言，更有意思的问题是它在 real workloads 上究竟有多 effective；等我们把所有这些 mechanisms 结合起来时，就会看到这一点。

CAT 的另一种用途是 prevent timing attacks，我完全不打算在这里展开讨论，例如[这个 attack，它能够通过 LLC interference 跨 VMs recover RSA keys](https://eprint.iacr.org/2015/898.pdf)。

#### DRAM bandwidth（DRAM 带宽）

Broadwell 及更新的 Intel chips 具有 memory bandwidth monitoring，但没有 control mechanism。为了绕过这一限制，如果 BE task 因使用过多 bandwidth 而 interfering with LC task，Heracles 就会减少 allocated 给 BE task 的 cores 的 number。用于这一目的的 coarse grained monitoring 和 control 在许多方面都是 inefficient 的，paper 中对此有详细说明，不过，尽管存在这些 inefficiencies，这种方法仍然有效。然而，如果有 per-core bandwidth limiting，就能以更少的工作取得更好的 results。

#### 将这些结合起来

这个 graph 展示了 LC websearch 的 effective utilization，其中其他 BE tasks 被 scheduled 时保留了足够的 slack，使 websearch 的 SLA 不会被 violated。

![](https://danluu.com/images/new-cpu-features/google_heracles.webp)

根据我在酒吧里与其他公司的人交谈的情况，这里的 baseline（红色）看起来已经相当不错了：peak times 期间有 80% utilization，另有一个持续 7 小时的 trough，其间 utilization 低于 50%。使用 Heracles 后，_worst case_ 下的 utilization 是 80%，而 average 是 90%。这太惊人了。

请注意，effective utilization 可以 greater than 100%，因为它的 measured 方式是：LC task 在 single machine 上、处于 100% load 时的 throughput，plus BE task 在 single machine 上、处于 100% load 时的 throughput。例如，如果一个 task 需要 100% 的 DRAM bandwidth 和 0% 的 network bandwidth，而另一个 task 的需求恰好相反，那么这两个 tasks 就能在同一 machine 上 co-locate，并达到 200% effective utilization。

在现实中，我们也许“只能”从 Heracles 这样的 system 中获得 90% average utilization。回想我们对 operating cost 的 estimate，即 \$4 billion for a large company, if the company already had a quite-good average utilization of 75%, using [a standard model for datacenter operating costs](http://www.morganclaypool.com/doi/pdf/10.2200/S00516ED2V01Y201306CAC024), we'd expect 15% more throughput per dollar, or \$600 million 的免费 compute。根据我与那些正在成长为大公司的较小公司的交谈（这些公司每年在 compute 上的支出范围为 \$10 million to \$100 million），它们的 utilization 往往在 20% 左右。再次使用相同的 total cost model，它们可以预期 compute per dollar 获得 300% increase，或者说，根据其规模，每年获得 \$30 million to \$300 million 的免费 compute[1](https://danluu.com/intel-cat/#fn:S)。

#### 其他 observations

我们看过的所有 papers 中都有许多有趣的宝藏。我不打算在这里逐一展开，但有几处特别引起了我的注意。

##### ARM / Atom servers（ARM / Atom 服务器）

人们早就知道，datacenter machines 大约有一半时间处于 stalled 状态，等待 memory。此外，server chips 在 real workloads 上能够 execute 的 average number of instructions per clock 相当低。

![](https://danluu.com/images/intel-cat/server_ipc.webp)

上面的 rows（带 horizontal bars）是 Google 内部的 workloads，下面的 rows（带 green dots）是来自 SPEC 的 workstation benchmarks；SPEC 是一个 standard benchmark suite。我们可以看到，Google workloads 的 average 能达到 .5 instructions per clock 就已经很幸运了。我们前面也看到，这些 workloads 会使 cores 至少有一半时间因 memory 而 stalled。

尽管 high-end server chips 大部分时间都在等待 memory，而且 average 大约只有每个 clock cycle 半条 instruction，它们在 real workloads 上的表现仍然远好于 Atom 或 ARM chips（Reddi et al., ToCS 2011）。这听起来有些矛盾 -- 如果 chips 只是在等待 memory，为什么还需要 high-performance chip？一个小小的 ARM chip 同样能够有效地等待。事实上，它甚至可能更擅长等待，因为[更多 cores 在等待意味着它可以使用更多 bandwidth](http://yosefk.com/blog/amdahls-law-in-reverse-the-wimpy-core-advantage.html)。但事实是，servers 也花费大量时间 exploiting instruction-level parallelism，同时 executing 多条 instructions。

![](https://danluu.com/images/intel-cat/server_ilp.webp)

这个 graph 展示了同时处于 busy 状态的 execution units 的数量。几乎三分之一的时间里，都有 3+ execution units 处于 busy 状态。在等待 memory 的漫长 stalls 之间，high-end chips 能够完成更多 computation，并更早开始等待下一次 stall。另一个令人好奇的现象是，server workloads 的 instruction cache miss rates 远高于 traditional workstation workloads。

##### Code and Data Prioritization Technology（代码与数据优先级技术）

![](https://danluu.com/images/intel-cat/icache_miss.webp)

同样，上面的 rows（带有 horizontal bars）是 internal Google workloads，下面的 rows（带有 green dots）则是来自 SPEC 的 workstation benchmarks，SPEC 是一套 standard suite benchmark suite。作者将 instruction misses 的这一 increase 归因于两个 factors。首先，deploy 会 overwhelm instruction caches 的 large binaries（100MB）是很常见的。其次，instructions 必须与大得多的 data streams 争夺 cache 中的 space，这会使大量 instructions 被 evicted。

为了解决这个问题，Intel 推出了他们称为“Code and Data Prioritization Technology”（CDP）的技术。这是 CAT 的一个 extension，它允许 cores 分别 limit instructions 和 data 可以 occupy LLC 的哪些 subsets。由于它针对的是 last-level cache，因此并不直接解决上图所展示的 L2 cache miss rates 问题。不过，一个在 LLC 中 hits 的 L2 cache miss 的 cost 大约是 [Broadwell 上的 26ns，而一个同样 misses LLC、必须访问 main memory 的 L2 miss 则需要 86ns](http://users.atw.hu/instlatx64/GenuineIntel00306D4_Broadwell2_NewMemLat.txt)，这个 difference 相当大。

Kanev et al. 建议再进一步，采用 split icache/dcache hierarchy。这并不算什么激进的想法 -- l1 caches 已经是 split 的了，为什么其他部分不也这样呢？我的猜测是，Intel 和其他主要 chip vendors 已经有 simulation results 表明，这不会 improve performance per dollar，但谁知道呢？也许我们很快就能看到 split L2 caches。

##### SPEC（SPEC 基准测试）

一个更普遍的 observation 是，SPEC 作为 benchmark，如今基本上已经无关紧要了。作为 workstation benchmark，它有些过时了；而作为 servers、office machines、gaming machines、dumb terminals、laptops 和 mobile devices 的 benchmark，它则完全不合适[2](https://danluu.com/intel-cat/#fn:M)。SPEC 所针对的 market 每年都在缩小，而且至少十年来，SPEC 甚至都没有真正 representative 地反映那个 market。然而，在研究 chip 的人当中，它仍然是使用最广泛的 benchmark。

![](https://danluu.com/images/intel-cat/search_query.webp)

这就是 Google 的一个 search query 的样子。一个 query 进来后，会向一组 machines 发出一组 wide fanout 的 RPCs（第一 row）。其中每个 machine 也会进行一组 RPCs（第二 row），它们又会进行更多 RPCs（第三 row）；还有第四 row 没有显示出来，因为 graph 中的内容太多，看起来就像 noise。这是 datacenter 中一种相当常见的 workload，而 SPEC 中没有任何东西与此类似。

这些 papers 中还有许多有趣的小细节，如果你觉得这篇文章中的任何内容有趣，我都推荐你读一读它们。**如果你喜欢这篇文章，你可能也会喜欢 [Dick Sites 关于各种 performance 和 profiling 相关话题的这场演讲](https://www.youtube.com/watch?v=QBu2Ae8-8LM)、[这篇介绍 Intel 新的 CLWB 和 PCOMMIT instructions 的文章](https://danluu.com/clwb-pcommit/)，以及[这篇介绍其他“新”CPU features 的文章](https://danluu.com/new-cpu-features/)**。

## 原文

[Typical server utilization is between 10% and 50%. Google has demonstrated 90% utilization _without impacting latency SLAs_](http://csl.stanford.edu/~christos/publications/2015.heracles.isca.pdf). [Xkcd estimated that Google owns 2 million machines](https://what-if.xkcd.com/63/). If you estimate an amortized total cost of [$4k per machine per year](http://www.morganclaypool.com/doi/pdf/10.2200/S00516ED2V01Y201306CAC024), that's $8 billion per year. With numbers like that, even small improvements have a large impact, and this isn't a small improvement.

How is it possible to get 2x to 9x better utilization on the same hardware? The low end of those typical utilization numbers comes from having a service with variable demand and fixed machine allocations. Say you have 100 machines dedicated to Jenkins. Those machines might be very busy when devs are active, but they might also have 2% utilization at 3am. Dynamic allocation (switching the machines to other work when they're not needed) can get a typical latency-sensitive service up to somewhere in the 30%-70% range. To do better than that across a wide variety of latency-sensitive workloads with tight SLAs, we need some way to schedule low priority work on the same machines, without affecting the latency of the high priority work.

It's not obvious that this is possible. If both high and low priority workloads need to monopolize some shared resources like the last-level cache (LLC), memory bandwidth, disk bandwidth, or network bandwidth, there we're out of luck. With the exception of some specialized services, it's rare to max out disk or network. But what about caches and memory? It turns out that [Ferdman et al.](http://www.industry-academia.org/download/ASPLOS12_Clearing_the_Clouds.pdf) looked at this back in 2012 and found that typical server workloads don't benefit from having more than 4MB - 6MB of LLC, despite modern server chips having much larger caches.

![](https://danluu.com/images/intel-cat/server_llc.webp)

For this graph, scale-out workloads are things like distributed key-value stores, MapReduce-like computations, web search, web serving, etc. SPECint(mcf) is a traditional workstation benchmark. “server” is old school server benchmarks like SPECweb and TPC . We can see that going from 4MB to 11MB of LLC has a small effect on typical datacenter workloads, but a significant effect on this traditional workstation benchmark.

Datacenter workloads operate on such large data sets that it's often impossible to fit the dataset in RAM on a single machine, let alone in cache, making a larger LLC not particularly useful. This was result was confirmed by [Kanev et al.'s ISCA 2015 paper where they looked at workloads at Google](http://www.eecs.harvard.edu/~skanev/papers/isca15wsc.pdf). They also showed that memory bandwidth utilization is, on average, quite low.

![](https://danluu.com/images/intel-cat/low_bandwidth_utilization.webp)

You might think that the low bandwidth utilization is because the workloads are compute bound and don't have many memory accesses. However, when the authors looked at what the cores were doing, they found that a lot of time was spent stalled, waiting for cache/memory.

![](https://danluu.com/images/intel-cat/cache_stalls.webp)

Each row is a Google workload. When running these typical workloads, cores spend somewhere between 46% and 61% of their time blocked on cache/memory. It's curious that we have low cache hit rates, a lot of time stalled on cache/memory, and low bandwidth utilization. This is suggestive of workloads spending a lot of time waiting on memory accesses that have some kind of dependencies that prevent them from being executed independently.

LLCs for high-end server chips are between 12MB and 30MB, even though we only need 4MB to get 90% of the performance, and the 90%-ile utilization of bandwidth is 31%. This seems like a waste of resources. We have a lot of resources sitting idle, or not being used effectively. The good news is that, since we get such low utilization out of the shared resources on our chips, we should be able to schedule multiple tasks on one machine without degrading performance.

Great! What happens when we schedule multiple tasks on one machine? The [Lo et al. Heracles paper at ISCA this year explores this in great detail](http://csl.stanford.edu/~christos/publications/2015.heracles.isca.pdf). The goal of Heracles is to get better utilization on machines by co-locating multiple tasks on the same machine.

![](https://danluu.com/images/intel-cat/heracles_interference.webp)

The figure above shows three latency sensitive (LC) workloads with strict SLAs. websearch is the query serving service in Google search, ml\_cluster is real-time text clustering, and memkeyval is a key-value store analogous to memcached. The values are latencies as a percent of maximum allowed by the SLA. The columns indicate the load on the service, and the rows indicate different types of interference. LLC, DRAM, and Network are exactly what they sound like; custom tasks designed to compete only for that resource. HyperThread means that the interfering task is a spinloop running in the other hyperthread on the same core (running in the same hyperthread isn't even considered since OS context switches are too expensive). CPU power is a task that's designed to use a lot of power and induce thermal throttling. Brain is deep learning. All of the interference tasks are run in a container with low priority.

There's a lot going on in this figure, but we can immediately see that the best effort (BE) task we'd like to schedule can't co-exist with any of the LC tasks when only container priorities are used -- all of the `brain` rows are red, and even at low utilization (the leftmost columns), latency is way above 100% of the SLA latency.. It's also clear that the different LC tasks have different profiles and can handle different types of interference. For example, websearch and ml\_cluster are neither network nor compute intensive, so they can handle network and power interference well. However, since memkeyval is both network and compute intensive, it can't handle either network or power interference. The paper goes into a lot more detail about what you can infer from the details of the table. I find this to be one of the most interesting parts of the paper; I'm going to skip over it, but I recommend reading the paper if you're interested in this kind of thing.

A simplifying assumption the authors make is that these types of interference are basically independent. This means that independent mechanisms that isolate LC task from “too much” of each individual type of resource should be sufficient to prevent overall interference. That is, we can set some cap for each type of resource usage, and just stay below each cap. However, this assumption isn't exactly true -- for example, the authors show this figure that relates the LLC cache size to the number cores allocated to an LC task.

![](https://danluu.com/images/intel-cat/llc_vs_cores.webp)

The vertical axis is the max load the LC task can handle before violating its SLA when allocated some specific LLC and number of cores. We can see that it's possible to trade off cache vs cores, which means that we can actually go above a resource cap in one dimension and maintain our SLA by using less of another resource. In the general case, we might also be able to trade off other resources. However, the assumption that we can deal with each resource independently reduces a complex optimization problem to something that's relatively straightforward.

Now, let's look at each type of shared resource interference and how Heracles allocates resources to prevent SLA-violating interference.

#### Core

Pinning the LC and BE tasks to different cores is sufficient to prevent same-core context switching interference and hyperthreading interference. For this, Heracles used [cpuset](https://www.kernel.org/doc/Documentation/cgroups/cpusets.txt). Cpuset allows you to limit a process (and its children) to only run on a limited set of CPUs.

#### Network

On the local machines, Heracles used [qdisc](https://wiki.archlinux.org/index.php/Advanced_traffic_control) to enforce quotas. For more on cpuset, qdisc, and other quota/partitioning mechanisms [this LWN series on cgroups by Neil Brown is a good place to start](https://lwn.net/Articles/604609/). Cgroups are used by a lot of widely used software now (Docker, Kubernetes, Mesos, etc.); they're probably worth learning about even if you don't care about this particular application.

#### Power

Heracles uses [Intel's running average power limit](https://01.org/blogs/tlcounts/2014/running-average-power-limit-%E2%80%93-rapl) to estimate power. This is a feature on Sandy Bridge (2009) and newer processors that uses some on-chip monitoring hardware to estimate power usage fairly precisely. [Per-core dynamic voltage and frequency scaling](http://www.cs.binghamton.edu/~millerti/cs680r/papers/DVFS/SystemLevelAnalysis.pdf) is used to limit power usage by specific cores to keep them from going over budget.

#### Cache

The previous isolation mechanisms have been around for a while, but this is one is new to Broadwell chips (released in 2015). The problem here is that if the BE task needs 1MB of LLC and the LC task needs 4MB of LLC, a single large allocation from the BE task will scribble all over the LLC, which is shared, wiping out the 4MB of cached data the LC needs.

Intel's “[Cache Allocation Technology](http://www.intel.com/content/dam/www/public/us/en/documents/manuals/64-ia-32-architectures-software-developer-vol-3b-part-2-manual.pdf)” (CAT) allows the LLC to limit which cores can can access different parts of the cache. Since we often want to pin performance sensitive tasks to cores anyway, this allows us to divide up the cache on a per-task basis.

![](https://danluu.com/images/intel-cat/CAT_LLC.webp)

Intel's [April 2015 whitepaper on what they call Cache Allocation Technology (CAT)](http://www.intel.com/content/dam/www/public/us/en/documents/white-papers/cache-allocation-technology-white-paper.pdf) has some simple benchmarks comparing CAT vs. no-CAT. In this example, they measure the latency to respond to PCIe interrupts while another application has heavy CPU-to-memory traffic, with CAT on and off.

| Condition | Min | Max | Avg |
| --- | --- | --- | --- |
| no CAT | 1.66 | 30.91 | 4.53 |
| CAT | 1.22 | 20.98 | 1.62 |

With CAT, average latency is 36% of latency without CAT. Tail latency doesn't improve as much, but there's also a substantial improvement there. That's interesting, but to me the more interesting question is how effective this is on real workloads, which we'll see when we put all of these mechanisms together.

Another use of CAT that I'm not going to discuss at all is to prevent timing attacks, like [this attack, which can recover RSA keys across VMs via LLC interference](https://eprint.iacr.org/2015/898.pdf).

#### DRAM bandwidth

Broadwell and newer Intel chips have memory bandwidth monitoring, but no control mechanism. To work around this, Heracles drops the number of cores allocated to the BE task if it's interfering with the LC task by using too much bandwidth. The coarse grained monitoring and control for this is inefficient in a number of ways that are detailed in the paper, but this still works despite the inefficiencies. However, having per-core bandwidth limiting would give better results with less effort.

#### Putting it all together

This graph shows the effective utilization of LC websearch with other BE tasks scheduled with enough slack that the SLA for websearch isn't violated.

![](https://danluu.com/images/new-cpu-features/google_heracles.webp)

From barroom conversations with folks at other companies, the baseline (in red) here already looks pretty good: 80% utilization during peak times with a 7 hour trough when utilization is below 50%. With Heracles, the _worst case_ utilization is 80%, and the average is 90%. This is amazing.

Note that effective utilization can be greater than 100% since it's measured as throughput for the LC task on a single machine at 100% load plus throughput for the BE task on a single machine at 100% load. For example, if one task needs 100% of the DRAM bandwidth and 0% of the network bandwidth, and the other task needs the opposite, the two tasks would be able to co-locate on the same machine and achieve 200% effective utilization.

In the real world, we might “only” get 90% average utilization out of a system like Heracles. Recalling our operating cost estimate of $4 billion for a large company, if the company already had a quite-good average utilization of 75%, using [a standard model for datacenter operating costs](http://www.morganclaypool.com/doi/pdf/10.2200/S00516ED2V01Y201306CAC024), we'd expect 15% more throughput per dollar, or $600 million in free compute. From talking to smaller companies that are on their way to becoming large (companies that spend in the range of $10 million to $100 million a year on compute), they often have utilization that's in the 20% range. Using the same total cost model again, they'd expect to get a 300% increase in compute per dollar, or $30 million to $300 million a year in free compute, depending on their size[1](https://danluu.com/intel-cat/#fn:S).

#### Other observations

All of the papers we've looked at have a lot of interesting gems. I'm not going to go into all of them here, but there are a few that jumped out at me.

##### ARM / Atom servers

It's been known for a long time that datacenter machines spend approximately half their time stalled, waiting on memory. In addition, the average number of instructions per clock that server chips are able to execute on real workloads is quite low.

![](https://danluu.com/images/intel-cat/server_ipc.webp)

The top rows (with horizontal bars) are internal Google workloads and the bottom rows (with green dots) are workstation benchmarks from SPEC, a standard benchmark suite. We can see that Google workloads are lucky to average .5 instructions per clock. We also previously saw that these workloads cause cores to be stalled on memory at least half the time.

Despite spending most of their time waiting for memory and averaging something like half an instruction per clock cycle, high-end server chips do much better than Atom or ARM chips on real workloads (Reddi et al., ToCS 2011). This sounds a bit paradoxical -- if chips are just waiting on memory, why should you need a high-performance chip? A tiny ARM chip can wait just as effectively. In fact, it might even be better at waiting since having [more cores waiting means it can use more bandwidth](http://yosefk.com/blog/amdahls-law-in-reverse-the-wimpy-core-advantage.html). But it turns out that servers also spend a lot of their time exploiting instruction-level parallelism, executing multiple instructions at the same time.

![](https://danluu.com/images/intel-cat/server_ilp.webp)

This is a graph of how many execution units are busy at the same time. Almost a third of the time is spent with 3+ execution units busy. In between long stalls waiting on memory, high-end chips are able to get more computation done and start waiting for the next stall earlier. Something else that's curious is that server workloads have much higher instruction cache miss rates than traditional workstation workloads.

##### Code and Data Prioritization Technology

![](https://danluu.com/images/intel-cat/icache_miss.webp)

Once again, the top rows (with horizontal bars) are internal Google workloads and the bottom rows (with green dots) are workstation benchmarks from SPEC, a standard suite benchmark suite. The authors attribute this increase in instruction misses to two factors. First, that it's normal to deploy large binaries (100MB) that overwhelm instruction caches. And second, that instructions have to compete with much larger data streams for space in the cache, which causes a lot of instructions to get evicted.

In order to address this problem, Intel introduced what they call “Code and Data Prioritization Technology” (CDP). This is an extension of CAT that allows cores to separately limit which subsets of the LLC instructions and data can occupy. Since it's targeted at the last-level cache, it doesn't directly address the graph above, which shows L2 cache miss rates. However, the cost of an L2 cache miss that hits in the LLC is something like [26ns on Broadwell vs. 86ns for an L2 miss that also misses the LLC and has to go to main memory](http://users.atw.hu/instlatx64/GenuineIntel00306D4_Broadwell2_NewMemLat.txt), which is a substantial difference.

Kanev et al. propose going a step further and having a split icache/dcache hierarchy. This isn't exactly a radical idea -- l1 caches are already split, so why not everything else? My guess is that Intel and other major chip vendors have simulation results showing that this doesn't improve performance per dollar, but who knows? Maybe we'll see split L2 caches soon.

##### SPEC

A more general observation is that SPEC is basically irrelevant as a benchmark now. It's somewhat dated as a workstation benchmark, and simply completely inappropriate as a benchmark for servers, office machines, gaming machines, dumb terminals, laptops, and mobile devices[2](https://danluu.com/intel-cat/#fn:M). The market for which SPEC is designed is getting smaller every year, and SPEC hasn't even been really representative of that market for at least a decade. And yet, among chip folks, it's still the most widely used benchmark around.

![](https://danluu.com/images/intel-cat/search_query.webp)

This is what a search query looks like at Google. A query comes in, a wide fanout set of RPCs are issued to a set of machines (the first row). Each of those machines also does a set of RPCs (the second row), those do more RPCs (the third row), and there's a fourth row that's not shown because the graph has so much going on that it looks like noise. This is one quite normal type of workload for a datacenter, and there's nothing in SPEC that looks like this.

There are a lot more fun tidbits in all of these papers, and I recommend reading them if you thought anything in this post was interesting. **If you liked this post, you'll probably also like [this talk by Dick Sites on various performance and profiling related topics](https://www.youtube.com/watch?v=QBu2Ae8-8LM), [this post on Intel's new CLWB and PCOMMIT instructions](https://danluu.com/clwb-pcommit/), and [this post on other "new" CPU features](https://danluu.com/new-cpu-features/)**.
