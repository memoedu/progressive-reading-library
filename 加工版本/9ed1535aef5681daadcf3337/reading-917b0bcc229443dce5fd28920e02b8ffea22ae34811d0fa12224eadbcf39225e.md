# 命令行选项的增长，1979年至今｜The growth of command line options, 1979-Present

---

## 正文

[我的爱好](https://www.xkcd.com/1795/)：在一个 monitor 上打开 [McIlroy’s UNIX philosophy](https://danluu.com/mcilroy-unix/)，同时在另一个上阅读 manpages。

McIlroy 的第一条 dicta 经常被转述为“做一件事，并把它做好”，这是从“让每个 program 都做好一件事。要完成新的 job，就重新 build，而不是通过添加新的 ‘features’ 来 complicate 旧的 programs”[缩写而来](https://danluu.com/mcilroy-unix/)的。

McIlroy 为这条 dictum 举的 example 是：

> 让外行感到惊讶的是，UNIX compilers 不 produce 任何 listings：printing 可以由一个 separate program 做得更好、更灵活。

如果你在 mac 上打开 `ls` 的 manpage，就会看到它以如下内容开头

```
ls [-ABCFGHLOPRSTUW@abcdefghiklmnopqrstuwx1] [file ...]
```

也就是说，`ls` 的 one-letter flags include 除 `{jvyz}` 之外的每个 lowercase letter、14 个 uppercase letters，再加上 `@` 和 `1`。光是 single-character options 就有 22 + 14 + 2 = 38 个。

在 ubuntu 17 上，如果你阅读 coreutils `ls` 的 manpage，并不会得到一份清晰的 options summary，但你会看到 `ls` 有 58 个 options（包括 `--help` 和 `--version`）。

要看看 `ls` 是否是个异例，还是说 commands 做这么多事情本来就很正常，我们可以看看一些按 frequency of use 进行 sorted 的常见 commands。

这个 table 列出了 v7 Unix (1979)、slackware 3.1 (1996)、ubuntu 12 (2015) 和 ubuntu 17 (2017) 中各个 commands 的 command line options 数量。Cells 中的 options 越多，颜色就越深、越蓝（log scale）；如果没有找到 command，则会 greyed out。

我们可以看到，command line options 的数量随着时间显著增加；越往右，entries 往往越深（更多 options），而没有任何 entries 变浅（更少 options）的情况。

[McIlroy 长期以来一直谴责 commands 的 options 数量、size 和 general functionality 的增加](https://archive.org/details/DougMcIlroy_AncestryOfLinux_DLSLUG)[1](https://danluu.com/cli-complexity/#fn:M)：

> 以前一切都很小，而当我看到 Linux 的 size 时，我就为它感到心痛\[听不清\]。同样的 utilities，以前能装进 eight k\[ilobytes\]，如今却要占 a meg。而 manual page，以前真的能放在一页上，以前真的就是一张 manual _page_，如今却成了一本小册子，里面有一千个 options……我们以前常坐在 UNIX 那间屋子里，说“我们能扔掉什么？为什么会有这个 option？”通常，往往是因为 basic design 存在某种 deficiency——你并没有真正找准 design point。与其添加一个 option，不如弄清楚为什么，究竟是什么迫使你添加那个 option。这种观点，部分是因为当时 hardware 很小才不得不采用的……如今已经丢失，而我们并没有因此过得更好。

讽刺的是，command line options 数量上升的原因之一，正是 McIlroy 的另一条 dictum：“Write programs 来 handle text streams，因为那是一个 universal interface”（其中一个 example 见 `ls`）。

如果传来传去的是 structured data 或 objects，formatting 就可以留给最后的一次 formatting pass。但是，对于 plain text，formatting 和 content 是 intermingled 的；因为 formatting 只能通过 parsing 出 content 来完成，所以 commands 为了方便而添加 formatting options 是很常见的。另一种办法是，user 利用自己对 data 的 structure 的了解，把这些了解 encodes 为传给 `cut`、`awk`、`sed` 等的 arguments，来完成 formatting（同时也利用自己对那些 programs 如何 handle formatting 的了解；不同 programs 的做法不同，而 user 被要求知道，比如，[知道 `cut -f4` 与 `awk '{ print $4 }'` 有什么不同](https://unix.stackexchange.com/a/132322/261842)[2](https://danluu.com/cli-complexity/#fn:T)）。这比向一个 sequence 中最后的 command 传入一两个 arguments 要麻烦得多，而且把 complexity 从 tool 推给了 user。

人们有时会说，他们不想 support structured data，因为要做一个 universal tool，就必须 support 多种 formats，但他们本来就已经必须 support 多种 formats 才能做出 universal tool。有些 standard commands 无法 read 其他 commands 的 output，因为它们使用不同的 formats；`wc -w` 不能正确地 handle Unicode，等等。说“text”是一种 universal format，就像说“binary”是一种 universal format 一样。

我听人说过，对于 command line tools 来说，这种 complexity 实际上没有其他选择，但这样说的人从来没有真正尝试过其他选择，比如 PowerShell。我对 PowerShell 有很多抱怨，但让 structured data 传来传去，以及能够轻松地对 structured data 进行 operate，而不必在脑子里记住 metadata information，以便在 pipeline 中正确的位置把适当的 metadata 传给正确的 command line tools，并不在我的抱怨之列[3](https://danluu.com/cli-complexity/#fn:W)。

当有人说，只要让一切都 handle text，就能让 software 保持 simple 和 compatible 时，他耍的把戏就是假装 text data 没有需要 parsed 的 structure[4](https://danluu.com/cli-complexity/#fn:C)。在某些情况下，我们可以直接把一切视为一条 single space separated line，或者一个带有我们所指定的 row 和 column separators 的 table（[当然，其中有些 behavior 在不同 tools 之间并不 consistent](https://unix.stackexchange.com/a/132322/261842)）。即使这能行得通，也会增添一些麻烦；还有一些情况下，把 data 进行 serializing 为 flat text format 会增加相当大的 complexity，因为 data 的 structure 意味着，简单的 flattening 就需要大量 parsing 工作，才能以有意义的方式 re-ingest 这些 data。

如今 commands 有更多 options 的另一个原因，是人们为原本可以通过拼凑一系列 commands 来实现的 functionality 添加了 convenience flags。这些早在 v7 unix 中就已经存在，当时 `ls` 就有一个用于 reverse sort order 的 option（这本可以通过把 output 传给类似 `tac` 的东西来完成，只要他们当时 written 了 `tac`，而不是添加一个 special-case reverse option）。

随着时间推移，更多 convenience options 被添加进来。例如，选一个最初有 zero options 的 command，`mv` 可以 move _并且_ create 一个 backup（三个 options；其中两个是 specify 一个 backup 的不同方式，一个 takes 一个 argument，另一个 takes zero explicit arguments，并从 `VERSION_CONTROL` environment variable 中 reads 一个 implicit argument；还有一个 option 允许 overriding default backup suffix）。`mv` 如今还有一些 options，可以永不 overwrite，以及仅在 file 是 newer 时才 overwrite。

`mkdir` 是另一个以前没有 options 的 program，除去 SELinux 或 SMACK 的 security 相关内容，以及 help 和 version options，添加的 options 都是 convenience flags：setting 新 directory 的 permissions，以及在 parent directories 不存在时 making 它们。

如果我们看看 `tail`，它最初只有一个 option（`-number`，用来告诉 `tail` 从哪里 start），如今它既添加了 formatting options，也添加了 convenience options。对于 formatting，它有 `-z`，可以让 line delimiter 成为 `null`，而不是 newline。convenience options 的一些 examples 包括：`-f`，用于在有新 changes 时 print；`-s`，用于 set 每次 checking `-f` changes 之间的 sleep interval；`--retry`，用于在 file 不是 accessible 时 retry。

McIlroy 说，添加了所有这些 options 之后，“我们并没有过得更好”，但我的处境确实更好了。我们讨论过的 options 中，有些我从未用过，另一些也只是偶尔使用，但这正是 command line options 的妙处——与 GUI 不同，添加这些 options 不会让 interface 变得杂乱。manpage 可能会变得杂乱，但在 google 和 stackoverflow 的时代，我怀疑很多人本来就只是搜索自己想做之事的解决办法，而不去阅读 manpage。

这并不是说添加 options 没有代价——更多 options 意味着更多 maintenance burden，但这是 maintainers 为了让 users 受益而承担的代价，考虑到 maintainers 与 users 的 ratio，这并不显然是不合理的。这类似于 Gary Bernhardt 的说法：一场演讲练习五十遍是合理的，因为如果有三百名观众，观看演讲所花的时间与练习所花时间的 ratio 仍然只有 1:6。一般来说，对于常用的 command line tools，这个 ratio 还会更加悬殊。

有人可能会认为，所有这些额外的 options 给 users 带来了负担。这不算错，但那个 complexity burden 本来就总会存在，问题只在于这个负担会落在哪里。如果你把一组 command line tools 连同一个 shell 看作构成了一种 language，在这种 language 中，任何人都可以 write 一个新的 method，而如果它流行起来，实际上就会被 added 到 standard library 中，且 standards 由“write programs 来 handle text streams，因为那是一个 universal interface”这样的 dicta 来 defined，那么把它作为整体看待时，这种 language 注定会变成一团 write-only、incoherent 的乱麻。至少，对于那些把比 UNIX-y 风格更多的 functionality 和 options bundle 起来的 tools，users 可以用一组仅仅数量庞大的 tools，来 replace 一组数量极其庞大且极为 inconsistent 的 tools；前者虽然彼此 inconsistent，但可能还具有一些 internal consistency。

McIlroy 暗示，问题在于人们思考得不够深入，老派 UNIX 行家会坐在同一间屋子里，思考得更久、更深入，直到想出一组具有“非同寻常的 simplicity”的 consistent tools。但那种做法永远无法 scale，这套 philosophy 使我们如今身处的混乱成为必然。这不是没有思考得更久或更深入的问题；而是这套 philosophy 无法 scale，除非你有一个相对较小、具有共同文化理解、能够坐在同一间屋子里的团队。

五十年后的今天，我们仍然摆脱不了的许多主要的长期 UNIX anti-features 和 anti-patterns，都来自“我们都应该像身处同一间屋子那样行事”的 design philosophy；如果你想 create 美好、usable、general，并且能够 adapt 到 original designers 未曾想到的问题的 interfaces，这恰好与你所需要的方法相反。例如，人们经常抱怨，现代 shells 和 terminals 缺少一大堆任何 designing 现代 interface 的人都会想要的显而易见的 features。当你与那些秉持现代 principles、written 了新的 shell 和新的 terminal 的人交谈时，比如 Jesse Luehrs，他们会指出，一个主要问题是 UNIX model 没有良好的 seperation of interface and implementation；如果你打算 write 一个 terminal，让它的行为与五十年前 created 的 terminal 一样，这还行得通，但如果你想 build 一个现代 terminal，这就会立刻显现出明显的问题。如果所有人都在同一间屋子里，而且 system 不需要随着 contributors 数量或时间而 scale up，那种 design philosophy 没什么问题，但我们今天生活的世界根本不是这样。

如果任何人都能 write 一个 tool，而主要指导来自“unix philosophy”，那么人们对于“[simplicity](https://twitter.com/hillelogram/status/1174714902151421952)”或“doing one thing”[5](https://danluu.com/cli-complexity/#fn:P) 意味着什么、做事的正确方式是什么，就会有不同看法，而 inconsistency 就会滋生，产生那种在应对 PHP 这样极其 inconsistent 的 language 时会遇到的 complexity。人们嘲笑 PHP 和 javascript 有各种缺陷和古怪的 inconsistencies，但作为一种 language 和一个 standard library，任何常用的 shell 加上广泛使用的 \*nix tools 的集合，整体来看都要糟糕得多；即便在单个 Linux distro 内部，也包含多得多的由 inconsistency 导致的 accidental complexity，而且它不可能有其他结果。如果跨 Linux distros、BSDs、Solaris、AIX 等进行 compare，users 在 switching systems 时必须记在脑中的 accidental complexity，其数量让 PHP 或 javascript 的 incoherence 相形见绌。相比之下，那些最广受嘲笑的 programming languages 都堪称优秀 design 的典范。

说清楚一点，我并不是说，凭借 70 年代已有的知识，我或其他任何人就能做得更好，造出一个当时 practically useful、到今天仍然 elegant 的 system。事后回看，借助后见之明发现问题很容易。我不赞同的是如今 Unix 行家们发表的评论；比如 McIlroy 的评论，暗示我们只是忘记了或不理解 simplicity 的价值，或者 [Ken Thompson 说 C 和任何 language 一样 safe，如果我们不想要 bugs，就应该直接 write bug-free code](https://twitter.com/danluu/status/885214004649615360)。这些评论暗示，我们没什么可从后见之明中学到的；在 70 年代，我们 building systems 的成效已经不逊于今天任何人所能达到的程度；五十年的集体经验、数千万个人年，什么也没教会我们；只要我们回去像最初的 Unix 行家那样 building systems，一切就都会好起来。恕我不能赞同。

### 附录：memory

虽然回应 McIlroy 对 binary size bloat 的抱怨有些超出本文范围，但我想指出，2017 年，我买了一台配备 16GB RAM 的 Chromebook，价格为 \$300. A 1 meg binary might have been a serious problem in 1979, when a standard Apple II had 4KB. An Apple II cost $1298，以 1979 年的美元计，或以 2020 年的美元计为 $4612。你可以买到一台 low end Chromebook，价格不到它的 1/15th，却拥有四百万倍的 memory。当一台便宜超过一个 order of magnitude 的（portable！）machine 拥有四百万倍的 memory 时，抱怨 memory usage 增长了一千倍，似乎有些荒唐。

我偏爱 slimmer software，所以我把自己的 home page optimized 到了两个 packets（如果我的 CDN served high-level brotli，它就会只有一个 packet），但这纯粹是审美偏好，是我为了好玩而做的事。command line tools 的 bottleneck 不是 memory usage，花时间 optimizing 一个只占 one meg 的 tool 的 memory footprint，就像把 homepage 压缩到一个 packet 一样。或许是个有趣的爱好，但不该成为任何人强加给别人的要求。

### table 的 Methodology

Command frequencies 来自 github 上公开的 command history files，不一定能代表你个人的 usage。只保留了“simple” commands，因此排除了 curl、git、gcc（它有 > 1000 个 options）和 wget 等。什么算 simple 是任意决定的。[Shell builtins](https://en.wikipedia.org/wiki/Shell_builtin)，例如 `cd`，没有被纳入。

Repeated options 不会被 counted 为 separate options。例如，`git blame -C`、`git blame -C -C` 和 `git blame -C -C -C` 有不同的 behavior，但它们都会被 counted 为一个 argument，尽管 `-C -C` 实际上是不同于 `-C` 的 argument。

这个 table 将 sub-options counts 为一个 option。例如，`ls` 有以下内容：

> \--format=WORD across -x, commas -m,  horizontal  -x,  long  -l,  single-column  -1,  verbose  -l, vertical -C

尽管有七个 format options，这里仍只把它视为一个 option。

被 explicitly listed 为不做任何事的 Options 仍会被 counted 为 options，例如 `ls -g`，其说明为 `Ignored; for Unix compatibility.`，也被 counted 为一个 option。

同一个 option 的多个 versions 也被视为一个 option。例如，对于 `ls`，`-A` 和 `--almost-all` 被 counted 为一个 option。

如果 manpage 说某个 option 应当存在，但它并不存在，就不 counted 这个 option。例如，v7 `mv` 的 manpage 说：

> BUGS（缺陷）
> 
> 如果 file1 和 file2 位于不同的 file systems，mv 必须 copy 这个 file 并 delete 原来的 file。在这种情况下，owner name 会变为 copying process 的 owner name，与其他 files 的任何 linking relationship 都会 lost。
> 
> Mv 应该像 rm 一样 take **\-f** flag，以便在 target exists 且不是 writable 时 suppress 询问。

`-f` 在 table 中不被 counted 为 flag，因为这个 option 实际上并不存在。

    看待这个问题的另一种方式，是借助 [Conway's law](https://en.wikipedia.org/wiki/Conway's_law)。如果我们有一组由不同的人 built 的 command line tools，而这些人在组织上往往没有联系，那么除非有人能 define 一个 standard 并让人们 adopt 它，否则这些 tools 就会极其 inconsistent。这在 Windows 上实际上做得相对不错，而且不只是在 PowerShell 中。

    对 Microsoft 的一个常见抱怨是，他们造成了大量 API churn，往往出于非技术性的组织原因（例如 Sinofsky 的权力斗争，就像 [https://twitter.com/stevesi/status/733654590034300929](https://twitter.com/stevesi/status/733654590034300929) 处现已删除的 Tweet 的回复中描述的那次）。这是真的。即便如此，从一个 naive user 的角度来看，现成的 Windows software 在 passing non-textual data 方面通常比 \*nix 好得多。这部分源于 Windows 对 non-textual data 的接纳，至少可以追溯到 1999 年的 [COM](https://en.wikipedia.org/wiki/Component_Object_Model)（也可以说能追溯到分别于 1990 年和 1987 年发布的 OLE 和 DDE）。

    例如，如果你从 supports binary formats `A` 和 `B` 的 Foo 中 copy 到 supports formats `B` 和 `C` 的 Bar 中，然后再从 Bar 中 copy 到 supports `C` 和 `D` 的 Baz 中，那么即便 Foo 和 Baz 没有共同 supported formats，这也能 work。

    当你 cut/copy 某些内容时，application 基本上会“告诉”clipboard，它能以哪些 formats provide data。当你 paste 到 application 中时，destination application 可以用任何 available 的 formats 来 request data。如果 data 已经在 clipboard 中，“Windows”就会 provides 它。如果不在，Windows 就会从 source application gets data，然后交给 destination application，并在 Windows 中将一个 copy saved 一段时间。如果你从 Excel 中“cut”，它会告诉“你”，它有数十种 formats 的 data available。这种 system 对 compatibility 相当不错，尽管它显然并不 simple，也不 minimal。

    除了很好地 supporting 许多不同的 formats，而且长期如此，以至于许多 software 都能很好地配合之外，Windows 通常还开箱即有更好的 clipboard support。

    假设你 copy 然后 paste 少量 text。大多数时候，在 Windows 和 Linux 上，这都会如你所料地 work。但现在假设你 copy 一些 text，close 你从中 copied 的 program，然后再 paste 它。许多人的 mental model 是，当他们 copy 时，data 是 stored 在 clipboard 中，而不是在被 copied 的 program 中。在 Windows 上，software 通常会被 written 成符合这种预期的样子（尽管从技术上说，clipboard API 的 users 并不必须这么做）。这在使用 X 的 Linux 上就没那么常见了；对于其中大多数 software，正确的 mental model 是，copying 会 stores 一个指向 data 的 pointer，而 data 仍然 owned by 最初从中 copied data 的 program，这意味着如果 program 被 closed，paste 就不会 work。我曾（非正式地）调查过 programmers，如果他们没有真正为某个 application 做过 copy+paste 相关工作，他们通常会对此感到惊讶。我调查 non-programmers 时，他们往往既觉得这种 behavior 令人困惑，也感到意外。

    让 OS 实际上 own clipboard 的 contents，其缺点是 copy 大量 data 的 cost 很高。假设你 copy 了非常大量的 text，达到许多 gigabytes，或者某个 complex object，然后始终没有 paste 它。你其实并不希望为了让这些 data 可供使用，就将它们从你的 program copy 到 OS 中。Windows 对此也处理得相当合理：当这样做被认为有利时，applications 可以[仅在 request 时 provide data](https://docs.microsoft.com/en-us/openspecs/windows_protocols/ms-rdpeclip/fa309d1b-8034-44bf-b927-adfc753e69c1)。在上面提到的情况下，当有人 closes program 时，program 可以决定是否应该将这些 data push 到 clipboard 中，还是 discard 它们。在这种情况下，许多 software（例如 Excel）会提示是将 data “keep”在 clipboard 中，还是 discard 它们，这相当合理。

    在 Linux 上 support 其中一些做法并非不可能。例如，[ClipboardManager spec](https://freedesktop.org/wiki/ClipboardManager/) 描述了一种 persistence mechanism，而 GNOME applications 一般也算是或多或少地 support 它（尽管[存在一些 bugs](https://bugzilla.gnome.org/show_bug.cgi?id=510204#c8)），但 \*nix 上的情况确实不同于 Windows applications 对良好 clipboard behavior 往往提供的更广泛的 support。

    [\[返回\]](https://danluu.com/cli-complexity/#fnref:W)
4.  这方面的另一个例子是基于 modern compilers 提供的 tools。如果我们回头看看 McIlroy 的 canonical example，即规范的 UNIX compilers 是如此 specialized，以至于 listings 由一个 separate tool 处理，我们就会发现，即使仍然有可用于 listings 的 separate tool，这种情况也已经改变了。一些常用的 Linux compilers 确实有数千个 options，而且能做许多事情。例如，`clang` 如今所做的许多事情之一就是 static analysis。截至本文写作时，[有 79 项 normal static analysis checks 和 44 项 experimental checks](https://clang.llvm.org/docs/analyzer/checkers.html#default-checkers)。如果这些是 separate commands（也许是 individual commands，也许是一个 `static_analysis` command，它们仍然会依赖同一套 underlying compiler infrastructure，并带来相同的 maintenance burden——让这些 static analysis tools operate on plain text，并 reimplement 整套必要的 compiler toolchain，以达到能够进行 static analysis 的程度，其实并不合理。它们可以是 separate commands，而不是被 bundled 到 `clang` 中，但它们仍然会对 compiler 所使用的同一套 machinery 产生 dependency，并且要么给 compiler 带来 maintenance 和 complexity burden（它必须为基于它构建的 tools support non-breaking interfaces），要么它们就会频繁 break。

    “只要让一切都成为 text，就能保持 simple”是一句好听的口号，但实际上，如果你想做真正有用的工作，data 的 textual representation 往往并不是你想要的。

    而具体到 clang，无论你把它做成一个 monolithic command，还是数千个较小的 commands，clang 所做的事情就是比 1979 年存在的任何 compiler，甚至比 1979 年存在的所有 compilers 加起来还要多。说 1979 年的东西更 simpler，说我们这些 modern programmers 已经迷失了方向，都很容易。真正提出一种确实更 simpler、而且真能被 adopted 的 design，就更难了。这样的 design 不可能既 maintain 所有现有的 functionality 和 configurability，又像 1979 年的东西一样 simple。

    [\[返回\]](https://danluu.com/cli-complexity/#fnref:C)
5.  自诞生以来，curl 已经从 supporting 3 个 protocols 发展到 40 个。这是否意味着它做了 40 件事，而将它 split 成 40 个 separate commands 会更“UNIX-y”？这取决于你问谁。如果每个 protocol 都有自己的 command，并由不同的人 created 和 maintained，我们就会陷入与其他 commands 相同的处境。Inconsistent command line options，尽管全都是 text streams 却仍然 inconsistent 的 output formats，等等。这会更接近 McIlroy 所倡导的 simplicity 吗？这取决于你问谁。[\[返回\]](https://danluu.com/cli-complexity/#fnref:P)

## 原文

[My hobby](https://www.xkcd.com/1795/): opening up [McIlroy’s UNIX philosophy](https://danluu.com/mcilroy-unix/) on one monitor while reading manpages on the other.

The first of McIlroy's dicta is often paraphrased as "do one thing and do it well", which is [shortened from](https://danluu.com/mcilroy-unix/) "Make each program do one thing well. To do a new job, build afresh rather than complicate old programs by adding new 'features.'"

McIlroy's example of this dictum is:

> Surprising to outsiders is the fact that UNIX compilers produce no listings: printing can be done better and more flexibly by a separate program.

If you open up a manpage for `ls` on mac, you’ll see that it starts with

```
ls [-ABCFGHLOPRSTUW@abcdefghiklmnopqrstuwx1] [file ...]
```

That is, the one-letter flags to `ls` include every lowercase letter except for `{jvyz}`, 14 uppercase letters, plus `@` and `1`. That’s 22 + 14 + 2 = 38 single-character options alone.

On ubuntu 17, if you read the manpage for coreutils `ls`, you don’t get a nice summary of options, but you’ll see that `ls` has 58 options (including `--help` and `--version`).

To see if `ls` is an aberration or if it's normal to have commands that do this much stuff, we can look at some common commands, sorted by frequency of use.

We can see that the number of command line options has dramatically increased over time; entries tend to get darker going to the right (more options) and there are no cases where entries get lighter (fewer options). 

[McIlroy has long decried the increase in the number of options, size, and general functionality of commands](https://archive.org/details/DougMcIlroy_AncestryOfLinux_DLSLUG)[1](https://danluu.com/cli-complexity/#fn:M):

> Everything was small and my heart sinks for Linux when I see the size \[inaudible\]. The same utilities that used to fit in eight k\[ilobytes\] are a meg now. And the manual page, which used to really fit on, which used to really be a manual _page_, is now a small volume with a thousand options... We used to sit around in the UNIX room saying "what can we throw out? Why is there this option?" It's usually, it's often because there's some deficiency in the basic design — you didn't really hit the right design point. Instead of putting in an option, figure out why, what was forcing you to add that option. This viewpoint, which was imposed partly because there was very small hardware ... has been lost and we're not better off for it.

Ironically, one of the reasons for the rise in the number of command line options is another McIlroy dictum, "Write programs to handle text streams, because that is a universal interface" (see `ls` for one example of this).

If structured data or objects were passed around, formatting could be left to a final formatting pass. But, with plain text, the formatting and the content are intermingled; because formatting can only be done by parsing the content out, it's common for commands to add formatting options for convenience. Alternately, formatting can be done when the user leverages their knowledge of the structure of the data and encodes that knowledge into arguments to `cut`, `awk`, `sed`, etc. (also using their knowledge of how those programs handle formatting; it's different for different programs and the user is expected to, for example, [know how `cut -f4` is different from `awk '{ print $4 }'`](https://unix.stackexchange.com/a/132322/261842)[2](https://danluu.com/cli-complexity/#fn:T)). That's a lot more hassle than passing in one or two arguments to the last command in a sequence and it pushes the complexity from the tool to the user.

People sometimes say that they don't want to support structured data because they'd have to support multiple formats to make a universal tool, but they already have to support multiple formats to make a universal tool. Some standard commands can't read output from other commands because they use different formats, `wc -w` doesn't handle Unicode correctly, etc. Saying that "text" is a universal format is like saying that "binary" is a universal format.

I've heard people say that there isn't really any alternative to this kind of complexity for command line tools, but people who say that have never really tried the alternative, something like PowerShell. I have plenty of complaints about PowerShell, but passing structured data around and easily being able to operate on structured data without having to hold metadata information in my head so that I can pass the appropriate metadata to the right command line tools at that right places the pipeline isn't among my complaints[3](https://danluu.com/cli-complexity/#fn:W).

The sleight of hand that's happening when someone says that we can keep software simple and compatible by making everything handle text is the pretense that text data doesn't have a structure that needs to be parsed[4](https://danluu.com/cli-complexity/#fn:C). In some cases, we can just think of everything as a single space separated line, or maybe a table with some row and column separators that we specify ([with some behavior that isn't consistent across tools, of course](https://unix.stackexchange.com/a/132322/261842)). That adds some hassle when it works, and then there are the cases where serializing data to a flat text format adds considerable complexity since the structure of data means that simple flattening requires significant parsing work to re-ingest the data in a meaningful way.

Another reason commands now have more options is that people have added convenience flags for functionality that could have been done by cobbling together a series of commands. These go all the way back to v7 unix, where `ls` has an option to reverse the sort order (which could have been done by passing the output to something like `tac` had they written `tac` instead of adding a special-case reverse option).

Over time, more convenience options have been added. For example, to pick a command that originally has zero options, `mv` can move _and_ create a backup (three options; two are different ways to specify a backup, one of which takes an argument and the other of which takes zero explicit arguments and reads an implicit argument from the `VERSION_CONTROL` environment variable; one option allows overriding the default backup suffix). `mv` now also has options to never overwrite and to only overwrite if the file is newer.

`mkdir` is another program that used to have no options where, excluding security things for SELinux or SMACK as well as help and version options, the added options are convenience flags: setting the permissions of the new directory and making parent directories if they don't exist.

If we look at `tail`, which originally had one option (`-number`, telling `tail` where to start), it's added both formatting and convenience options For formatting, it has `-z`, which makes the line delimiter `null` instead of a newline. Some examples of convenience options are `-f` to print when there are new changes, `-s` to set the sleep interval between checking for `-f` changes, `--retry` to retry if the file isn't accessible.

McIlroy says "we're not better off" for having added all of these options but I'm better off. I've never used some of the options we've discussed and only rarely use others, but that's the beauty of command line options — unlike with a GUI, adding these options doesn't clutter up the interface. The manpage can get cluttered, but in the age of google and stackoverflow, I suspect many people just search for a solution to what they're trying to do without reading the manpage anyway.

This isn't to say there's no cost to adding options — more options means more maintenance burden, but that's a cost that maintainers pay to benefit users, which isn't obviously unreasonable considering the ratio of maintainers to users. This is analogous to Gary Bernhardt's comment that it's reasonable to practice a talk fifty times since, if there's a three hundred person audience, the ratio of time spent watching to the talk to time spent practicing will still only be 1:6. In general, this ratio will be even more extreme with commonly used command line tools.

Someone might argue that all these extra options create a burden for users. That's not exactly wrong, but that complexity burden was always going to be there, it's just a question of where the burden was going to lie. If you think of the set of command line tools along with a shell as forming a language, a language where anyone can write a new method and it effectively gets added to the standard library if it becomes popular, where standards are defined by dicta like "write programs to handle text streams, because that is a universal interface", the language was always going to turn into a write-only incoherent mess when taken as a whole. At least with tools that bundle up more functionality and options than is UNIX-y users can replace a gigantic set of wildly inconsistent tools with a merely large set of tools that, while inconsistent with each other, may have some internal consistency.

McIlroy implies that the problem is that people didn't think hard enough, the old school UNIX mavens would have sat down in the same room and thought longer and harder until they came up with a set of consistent tools that has "unusual simplicity". But that was never going to scale, the philosophy made the mess we're in inevitable. It's not a matter of not thinking longer or harder; it's a matter of having a philosophy that cannot scale unless you have a relatively small team with a shared cultural understanding, able to to sit down in the same room.

Many of the main long-term UNIX anti-features and anti-patterns that we're still stuck with today, fifty years later, come from the "we should all act like we're in the same room" design philosophy, which is the opposite of the approach you want if you want to create nice, usable, general, interfaces that can adapt to problems that the original designers didn't think of. For example, it's a common complain that modern shells and terminals lack a bunch of obvious features that anyone designing a modern interface would want. When you talk to people who've written a new shell and a new terminal with modern principles in mind, like Jesse Luehrs, they'll note that a major problem is that the UNIX model doesn't have a good seperation of interface and implementation, which works ok if you're going to write a terminal that acts in the same way that a terminal that was created fifty years ago acts, but is immediately and obviously problematic if you want to build a modern terminal. That design philosophy works fine if everyone's in the same room and the system doesn't need to scale up the number of contributors or over time, but that's simply not the world we live in today.

If anyone can write a tool and the main instruction comes from "the unix philosophy", people will have different opinions about what "[simplicity](https://twitter.com/hillelogram/status/1174714902151421952)" or "doing one thing"[5](https://danluu.com/cli-complexity/#fn:P) means, what the right way to do things is, and inconsistency will bloom, resulting in the kind of complexity you get when dealing with a wildly inconsistent language, like PHP. People make fun of PHP and javascript for having all sorts of warts and weird inconsistencies, but as a language and a standard library, any commonly used shell plus the collection of widely used \*nix tools taken together is much worse and contains much more accidental complexity due to inconsistency even within a single Linux distro and there's no other way it could have turned out. If you compare across Linux distros, BSDs, Solaris, AIX, etc., the amount of accidental complexity that users have to hold in their heads when switching systems dwarfs PHP or javascript's incoherence. The most widely mocked programming languages are paragons of great design by comparison.

To be clear, I'm not saying that I or anyone else could have done better with the knowledge available in the 70s in terms of making a system that was practically useful at the time that would be elegant today. It's easy to look back and find issues with the benefit of hindsight. What I disagree with are comments from Unix mavens speaking today; comments like McIlroy's, which imply that we just forgot or don't understand the value of simplicity, or [Ken Thompson saying that C is as safe a language as any and if we don't want bugs we should just write bug-free code](https://twitter.com/danluu/status/885214004649615360). These kinds of comments imply that there's not much to learn from hindsight; in the 70s, we were building systems as effectively as anyone can today; five decades of collective experience, tens of millions of person-years, have taught us nothing; if we just go back to building systems like the original Unix mavens did, all will be well. I respectfully disagree.

### Appendix: memory

Although addressing McIlroy's complaints about binary size bloat is a bit out of scope for this, I will note that, in 2017, I bought a Chromebook that had 16GB of RAM for $300. A 1 meg binary might have been a serious problem in 1979, when a standard Apple II had 4KB. An Apple II cost $1298 in 1979 dollars, or $4612 in 2020 dollars. You can get a low end Chromebook that costs less than 1/15th as much which has four million times more memory. Complaining that memory usage grew by a factor of one thousand when a (portable!) machine that's more than an order of magnitude cheaper has four million times more memory seems a bit ridiculous.

I prefer slimmer software, which is why I optimized my home page down to two packets (it would be a single packet if my CDN served high-level brotli), but that's purely an aesthetic preference, something I do for fun. The bottleneck for command line tools isn't memory usage and spending time optimizing the memory footprint of a tool that takes one meg is like getting a homepage down to a single packet. Perhaps a fun hobby, but not something that anyone should prescribe.

### Methodology for table

Command frequencies were sourced from public command history files on github, not necessarily representative of your personal usage. Only "simple" commands were kept, which ruled out things like curl, git, gcc (which has > 1000 options), and wget. What's considered simple is arbitrary. [Shell builtins](https://en.wikipedia.org/wiki/Shell_builtin), like `cd` weren't included.

Repeated options aren't counted as separate options. For example, `git blame -C`, `git blame -C -C`, and `git blame -C -C -C` have different behavior, but these would all be counted as a single argument even though `-C -C` is effectively a different argument from `-C`.

The table counts sub-options as a single option. For example, `ls` has the following:

> \--format=WORD across -x, commas -m,  horizontal  -x,  long  -l,  single-column  -1,  verbose  -l, vertical -C

Even though there are seven format options, this is considered to be only one option.

Options that are explicitly listed as not doing anything are still counted as options, e.g., `ls -g`, which reads `Ignored; for Unix compatibility.` is counted as an option.

Multiple versions of the same option are also considered to be one option. For example, with `ls`, `-A` and `--almost-all` are counted as a single option.

In cases where the manpage says an option is supposed to exist, but doesn't, the option isn't counted. For example, the v7 `mv` manpage says

> BUGS
> 
> If file1 and file2 lie on different file systems, mv must copy the file and delete the original. In this case the owner name becomes that of the copying process and any linking relationship with other files is lost.
> 
> Mv should take **\-f** flag, like rm, to suppress the question if the target exists and is not writable.

`-f` isn't counted as a flag in the table because the option doesn't actually exist.

The latest year in the table is 2017 because I wrote the first draft for this post in 2017 and didn't get around to cleaning it up until 2020.

    Another way to look at this is through the lens of [Conway's law](https://en.wikipedia.org/wiki/Conway's_law). If we have a set of command line tools that are built by different people, often not organizationally connected, the tools are going to be wildly inconsistent unless someone can define a standard and get people to adopt it. It's true. Even so, from the standpoint of a naive user, off-the-shelf Windows software is generally a lot better at passing non-textual data around than \*nix. One thing this falls out of is Windows's embracing of non-textual data, which goes back at least to [COM](https://en.wikipedia.org/wiki/Component_Object_Model) in 1999 (and arguably OLE and DDE, released in 1990 and 1987, respectively).

    For example, if you copy from Foo, which supports binary formats `A` and `B`, into Bar, which supports formats `B` and `C` and you then copy from Bar into Baz, which supports `C` and `D`, this will work even though Foo and Baz have no commonly supported formats. 

    When you cut/copy something, the application basically "tells" the clipboard what formats it could provide data in. When you paste into the application, the destination application can request the data in any of the formats in which it's available. If the data is already in the clipboard, "Windows" provides it. If it isn't, Windows gets the data from the source application and then gives to the destination application and a copy is saved for some length of time in Windows. If you "cut" from Excel it will tell "you" that it has the data available in many tens of formats. This kind of system is pretty good for compatibility, although it definitely isn't simple or minimal.

    In addition to nicely supporting many different formats and doing so for long enough that a lot of software plays nicely with this, Windows also generally has nicer clipboard support out of the box.

    Let's say you copy and then paste a small amount of text. Most of the time, this will work like you'd expect on both Windows and Linux. But now let's say you copy some text, close the program you copied from, and then paste it. A mental model that a lot of people have is that when they copy, the data is stored in the clipboard, not in the program being copied from. On Windows, software is typically written to conform to this expectation (although, technically, users of the clipboard API don't have to do this). This is less common on Linux with X, where the correct mental model for most software is that copying stores a pointer to the data, which is still owned by the program the data was copied from, which means that paste won't work if the program is closed. When I've (informally) surveyed programmers, they're usually surprised by this if they haven't actually done copy+paste related work for an application. When I've surveyed non-programmers, they tend to find the behavior to be confusing as well as surprising.

    The downside of having the OS effectively own the contents of the clipboard is that it's expensive to copy large amounts of data. Let's say you copy a really large amount of text, many gigabytes, or some complex object and then never paste it. You don't really want to copy that data from your program into the OS so that it can be available. Windows also handles this reasonably: applications can [provide data only on request](https://docs.microsoft.com/en-us/openspecs/windows_protocols/ms-rdpeclip/fa309d1b-8034-44bf-b927-adfc753e69c1) when that's deemed advantageous. In the case mentioned above, when someone closes the program, the program can decide whether or not it should push that data into the clipboard or discard it. In that circumstance, a lot of software (e.g., Excel) will prompt to "keep" the data in the clipboard or discard it, which is pretty reasonable.

    It's not impossible to support some of this on Linux. For example, [the ClipboardManager spec](https://freedesktop.org/wiki/ClipboardManager/) describes a persistence mechanism and GNOME applications generally kind of sort of support it (although [there are some bugs](https://bugzilla.gnome.org/show_bug.cgi?id=510204#c8)) but the situation on \*nix is really different from the more pervasive support Windows applications tend to have for nice clipboard behavior.

4.  Another example of this are tools that are available on top of modern compilers. If we go back and look at McIlroy's canonical example, how proper UNIX compilers are so specialized that listings are a separate tool, we can see that this has changed even if there's still a separate tool you can use for listings. Some commonly used Linux compilers have literally thousands of options and do many things. For example, one of the many things `clang` now does is static analysis. As of this writing, [there are 79 normal static analysis checks and 44 experimental checks](https://clang.llvm.org/docs/analyzer/checkers.html#default-checkers). If these were separate commands (perhaps individual commands or perhaps a `static_analysis` command, they'd still rely on the same underlying compiler infrastructure and impose the same maintenance burden — it's not really reasonable to have these static analysis tools operate on plain text and reimplement the entire compiler toolchain necessary to get the point where they can do static analysis. They could be separate commands instead of bundled into `clang`, but they'd still take a dependency on the same machinery that's used for the compiler and either impose a maintenance and complexity burden on the compiler (which has to support non-breaking interfaces for the tools built on top) or they'd break all the time.

    Just make everything text so that it's simple makes for a nice soundbite, but in reality the textual representation of the data is often not what you want if you want to do actually useful work.

    And on clang in particular, whether you make it a monolithic command or thousands of smaller commands, clang simply does more than any compiler that existed in 1979 or even all compilers that existed in 1979 combined. It's easy to say that things were simpler in 1979 and that us modern programmers have lost our way. It's harder to actually propose a design that's actually much simpler and could really get adopted. It's impossible that such a design could maintain all of the existing functionality and configurability and be as simple as something from 1979.

5.  Since its inception, curl has gone from supporting 3 protocols to 40. Does that mean it does 40 things and it would be more "UNIX-y" to split it up into 40 separate commands? Depends on who you ask. If each protocol were its own command, created and maintained by a different person, we'd be in the same situation we are with other commands. Inconsistent command line options, inconsistent output formats despite it all being text streams, etc. Would that be closer to the simplicity McIlroy advocates for? Depends on who you ask.
