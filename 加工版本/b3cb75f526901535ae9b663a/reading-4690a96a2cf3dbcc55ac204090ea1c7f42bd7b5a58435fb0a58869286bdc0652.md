# 使用 Astra 的测试/验证技术有效性｜Test/verification technique effectiveness with Astra

---

## 正文

当我们考察[agents 在八月使用 test/verification techniques 的效果](https://danluu.com/agentic-testing/)[1](https://danluu.com/astra-testing/#fn:A)时，我们发现，当被要求使用 TDD、QuickCheck、Lean 4 等 technique 或 library 时，GPT-5.6 Sol 的做法通常可以说是对各种 techniques 的拙劣模仿；不指定任何特定 test method（我们将其称为 Default）会 resulted in 许多 worthless unit tests，但这却是表现最好的 conditions 之一，因为要求 agents 以特定方式 test，大多反而会让它们表现得更差。在那次 eval 中，我们向 agents 提供了 Zstd RFC，并要求它们 implement Zstd（对于 Default 以外的所有 conditions，还附加了说明，规定它们应如何 test）。

使用 GPT-6 Astra 重新 running 同一个 eval 后，我们看到了两个重大差异：

1.  Astra 的 capability 已经 increased 到需要更 difficult eval 的程度（在 Zstd implementation eval 上，无论使用何种 technique，几乎每个 condition 在 medium 下几乎每次都能获得 100% correctness）
2.  Agents 似乎能更 effectively 使用 test 和 verification techniques

关于 (1)，我们此前发现，在使用 5.6 Sol 根据 RFC implementing Zstd 时，agents 在 xhigh effort 下平均花费 \$3.50 on medium effort and $5.50，获得 full (holdout) test correctness 的比例分别约为 63% 和 77%。使用 Astra 时，agents 在 medium effort 下花费 $1，就能在超过 99% 的情况下获得 full test correctness。

关于 (2)，举个例子，当我们要求 5.6 Sol 进行 fuzzing 时，它会 generate 许多 worthless random inputs，这些 inputs 大多会 hit 相同的 code paths，而不会 test 任何有意思的东西。使用 6 Astra 时，我们看到，被要求进行 fuzzing 的 agents 会以 structured 方式进行，实际 exercises code paths 并 finds non-trivial bugs，但我们无法判断这是否 improved correctness，因为 Zstd implementation benchmark 已经 saturated。

我们也尝试过向 5.6 Sol 提供 IMAP RFC，但这对 5.6 Sol 来说太难了。使用 6 Astra 再试一次，我们得到了以下 results 的 distribution（y-axis 是所有 tests 都 pass 的 runs 所占的 percent；我们不会向 agents 提供 tests，而这些 points 是每个 condition 的 80 次 runs 的 results）。

Default 再次显得相当不错。有些 conditions 带来了稍好的 correctness，但 cost 也更高。虽然 IMAP RFC 尚未 saturated，但如果也能看到更难 task 上的 results 就好了，因为我的大部分时间都花在 agents 大多数时候无法 one-shot 的 tasks 上。为了 test 这一点，我们将尝试[我们在 comparing programming languages 时考察过的 pandoc eval](https://danluu.com/pl-tokens/)。我想看到更大 evals 上的 results，一个原因是，正如我们[考察 caveman mode 时](https://danluu.com/ai-coding/#caveman-mode)以及考察 languages 时所观察到的，models 在更大 tasks 上的表现往往相当不同。对于 caveman mode，人们所报告的巨大收益缩小或消失了；对于 languages，我们从多个方面看到了这一点，例如，Zstd 的 C 和 C++ implementations 在 memory safety 方面至少还算过得去，而 Pandoc 的 C 和 C++ implementations 则受到 memory safety issues 的困扰。

Pandoc 要难得多，即使 running 多个 turns（平均约 14 个）后，也没有任何 condition 达到 100% correctness，因此我们将考察 passed 的 tests 所占的 fraction，而不是达到 100% 的 runs 所占的 fraction。

由于涉及的 cost，我们只对每个 condition ran 了 25 次。按 MSRP 计算，这花费了约 $90k。

请回想一下，在我们过去针对 languages 和 test/verification techniques 进行的 evals 中，failures 往往是 agents 的 operate 方式所带来的 idiosyncratic results，例如，使用 Clojure 的 agents 默认 writing incorrect byte conversion code，或者使用 Verus 的 agents writing vacuous proofs。这类事情与我听到的人们主张 agents 应该使用某种特定 language 或 test/verification technique 的理由相当不同；那些理由通常是一些听起来不错的解释，说明为什么某种东西理应更好，它们很符合人类的直觉、颇具吸引力，但当我们考察 agents 实际做了什么时，这些解释似乎与现实无关[2](https://danluu.com/astra-testing/#fn:R)。

因为我们在这里“只”进行了价值 $90k 的 evals，所以我们实际上没有足够的信息来解释几乎任何事情为什么会发生。我们可以观察到某些 conditions 比其他 conditions 表现更好，但很难说这意味着什么。因此，我们不应过度解读这些 results，不过，我们确实看到了一些似乎符合预期的现象：我们可能会预期，大多数建议使用的 test techniques 和 libraries 能带来更好的 generalization，进而带来更好的 holdout vs. test scores（查看 visible vs. holdout test scores 时，result 位于 Default line 的左上方），而 TDD 则带来更差的 generalization（位于 Default line 的右下方）。

但是，如果 testing properties 确实能带来更好的 generalization，而像 TDD 这样 resulted in 大量 small tests 的 conditions 会带来较不 general 的 results，那么我们就会预期 built-in condition 相对于 Default 也会有较低的 holdout:visible，但我们看到的并非如此。原因尚不清楚，我认为，如果没有多得多的 runs，我们就无法真正 determine 这一点。

对于实际 results，cost vs. holdout 和 cost vs. visible 中显示的 line，表示根据跨多个 turns 的所有 graph trajectories 的 shape、以 Default 为对象 fitted 的 curves。位于 line 下方 / 右方的情况可以视为更差，而位于上方 / 左方的情况可以视为更好。使用 5.6 Sol 时，很明显，test conditions 通常没有发挥有用的作用，这是多种原因共同造成的：

1.  几乎没有 condition outperformed Default
2.  在其他 evals（此处未详细讨论）上，类似的 prompts 也没有 outperform Default
3.  non-Default conditions 所 produced 的 tests 大多荒唐可笑，没有体现出相应 technique 的价值

在这里，我们看到的情况是，许多不同的 techniques 都得到了比 Default 更好的 result。每个 condition 的 conceptual error bars 都相当宽（比 plots 上显示的 bootstrap intervals 所表明的还要宽），但 outperform Default 的 conditions 数量之多，使得一个或多个 conditions 确实 outperforms Default 成为合理的可能性，即使我们并不知道具体是哪些。此外，某些 conditions 很可能确实 outperform 其他 conditions，但我们实际上没有足够的 data 来判断哪些 conditions 总体上更好。当各式各样的 techniques 几乎全都表现糟糕时，事情反而简单得多。

对于这些 results，我有以下几个问题：

1.  这些 results 在多大程度上可以被 extrapolated 到 running 更多 turns，以使 Pandoc 达到 near-complete correctness 的情况？一般来说，随着 turns 增加，各个 conditions 确实会大致 maintain 各自的 rank order，因此 ranking 可能会保持现状，但这一点尚未经过 tested
2.  这些 results 有多少是由 small sample size（针对每个 condition 而言）造成的？对于 Pandoc eval，我们“只”对每个 condition ran 了 25 次。虽然 running 了许多不同的 turns，但从此前的 experiments 以及使用 agents 的实际经验中，我们知道，在对 generated code 进行 looping 时，存在高度的 path dependence
3.  这些 results 有多少是由 small sample size（针对 minute / trivial variations 而言）造成的？通过 running 几个有些可笑的 evals，我知道，在提出相同要求时，一些 trivial changes（例如改变句子结构、改变大小写等）就可能带来非常不同的 results；目前的 results 有多少源自这类任意因素？
4.  这些 results 有多少是由 small sample size（针对正在 solved 的 problem 而言）造成的？我们考察了一个“Pandoc-sized” problem。如果我们考察 100 个，Pandoc 会有多大的 representative 程度？

如果我真想回答这些问题，我会希望至少 running 这里工作量的 100x，以 running 完整的 matrix。Steve Yegge 曾提到，使用 ~20 个 Claude subscriptions，按 MSRP 计算，每月花费 ~$120k/mo 的 token spend。靠那样的 setup 达到 100x 并不现实，但如果有限地 expanded testing，再加上一些猜测和 extrapolation，做到 2x 到 3x 是有可能的。考虑到这会花费多少时间，以及我有多么缺乏空闲时间，我不知道自己这么做是否真有意义；不过，考虑到[学术界在 studying programming productivity 时研究过些什么](https://danluu.com/empirical-pl/)，也许让一位研究生来做这件事是有意义的，因为它能提供的信息会多于不少被广泛 cited 的 studies。不过，在 industry 中，我不确定除了 AI lab 以外还有谁会做这件事。

话虽如此，只要你记得，我们并不知道这些 results 中的任何一项能在多大程度上 generalize，我还是想指出几件我觉得有趣的事。

1.  Differential testing 促使 agents 以一种比其他 conditions 更能产生良好“understanding”的方式 examine tests 和 invariants
2.  TDD 再次 underperformed，但并非所有促使 agents write 大量 small tests 的 conditions 都 underperformed
3.  ACL2（一种 theorem prover）表现良好（[它在 5.6 Sol Zstd eval 中也表现良好](https://danluu.com/agentic-testing/)）
4.  Property-based testing（不是以此命名的 condition，而是一些强制使用该 technique 的 libraries）终于 resulted in 能实现人们对 PBT 期望的 tests

(1)：我曾尝试通过为 5.6 Sol Zstd eval 匆忙编写的 skill，让 agents 做到这一点；虽然这个 skill 表现尚可，但 agents 基本没有这么做。不过，在 Pandoc eval 中，differential testing 确实促使 agents 仔细 examine boundary conditions，并弄清楚如何 write tests（进而如何 write code），以 correctly implements boundary 的两侧。我没有把握这能 generalize，但看看它是否确实能 generalize，以及还有什么能让 agents systematically 做这类事情，会很有意思。

(2)：虽然 TDD underperforming 完全符合我的预期（请记得，我将 TDD 加入 5.6 Sol eval，就是因为我认为它会 underperform），但其他导致大量 small tests 被 generated 的 conditions 并没有 underperformance，这应该降低我们对那个听起来合理的理由的 confidence，即 writing 许多 small tests 会 underperforms。

(3)：长期以来，我一直觉得，相比其他 verification tools，ACL2 被低估了（相对于围绕它的 academic work 的数量，它在 industry 的某些领域被大量使用，并取得了良好效果）。我对这一看法的 confidence 原本就低，现在依然如此，但它在我迄今做过的 evals 中表现良好。考虑到目前有多少精力被投入到让 agents effectively 使用 Lean 上，我预期 Lean 最终会 outperform ACL2，即使今天是 ACL2 outperforms；不过，ACL2 今天似乎也不是个坏选择。对于使用 Lean 4 进行 verification 或 proofs 的人，我很好奇，相比使用 ACL2，results 会如何。

(4)：太好了（也许吧）。出于上述所有原因，我对于这能 generalizes 的 confidence 很低，但 Proptest 再次表现良好。而且，这次的 testing 比我们在 5.6 Sol Zstd eval 中看到的好得多。我没有这方面的内部消息，但我猜，在 5.6 Sol 和 6 Astra 之间，并没有针对 improving PBT / fuzzing / 等等投入重大努力，这应当来自更好的 generalization 和更高的 capability。如果确实如此（而且这不只是我仅花费 $90k MSRP and not $9M MSRP 所造成的某种 artifact），那么这对未来更好的 testing 是个好兆头，因为我们应该可以期待，即使不特别投入精力去 improve testing capabilities，models 也会变得更擅长 testing。

在我 running 这些 tests 到发布这篇文章之间，一项主张在网上广泛传播：你应该告诉 agents 不要 write tests（依据是 running DeepSWE）。具体说法是：

> 好了，现在可以正式宣布了……\[省略号来自原引文\] AI-written unit tests 和 integration tests 已被 empirically proven 是 unhelpful。你应该告诉你的 agents 停止自行 writing tests

[正如我们先前指出的](https://danluu.com/exercise-7/#30-deepswe-senior-swe-bench)，我认为 DeepSWE 并不 representative 于我所做的工作，因此对我个人而言毫无意义。此外，那次使用的是 Sonnet 5.5 High，因此它通常只在比这里讨论的 problems 容易得多的 problems 上 passed，而且正如这里以及其他近期 evals 中观察到的，哪些 techniques 是 effective 的，往往并不能跨 problem size 或 problem difficulty 进行 generalize。我认为，对于 coding agents 觉得非常容易的 problems，告诉它们不要 test 会 reduces cost，这是合理的（如果有人在意 DeepSWE，那么实际展示出来的就是这一点）。根据那次进行的 test，将其 Generalizing 为“AI-written unit tests 和 integration tests 已被 empirically proven 为 unhelpful”，似乎是不对的，无论这是否对其他 problems 成立，而且这个 claim 似乎也不太可能成立。这个 claim 的依据是要求不写 tests，而这带来了相近的 correctness 和少量 cost savings（on average 为 9%）。在我们这里以及此前的 tests 中，我们发现 correctness 存在 differences，cost 的 difference 也大于 9%，因此，根据 small problems 的 benchmark 上 9% 的 cost difference，就声称“AI-written unit tests 和 integration tests 已被 empirically proven 为 unhelpful”，这样的 claim 似乎不太可能是 correct 的。另一件值得注意的事是，DeepSWE 的 grader 在 testing 方面是 broken 的，因为（除其他 issues 外），[一个 agent 可以 add 一个与 grader 的 secret test name 存在 conflicts 的 test name，随后这就会 cause 一次 failure](https://epoch.ai/benchmarks/deepswe/review)。考虑到这类 issues，adding tests 会受到 inherent 的 penalized，而这种方式并不 representative 于 real-world usage。

你可以说，这个 claim 非常有效，因为夸大其词地声称某件事已被 empirically proven，是一种让内容广泛传播[3](https://danluu.com/astra-testing/#fn:V)或[获得大量 citations](https://danluu.com/empirical-pl/)的好方法，但这不是弄清如何 effectively 使用 coding agents 的好方法。

[在 Nolan Lawson 最近关于 JavaScript framework choice 如何 impacts agents 的文章中](https://nolanlawson.com/2026/10/28/the-ai-cost-of-javascript-frameworks/)，他指出：

> 我在这里的目的，不是为“我是一个 vibe-coder，我应该选择哪个 framework？”编写一个包揽一切的 benchmark。这篇文章的重点是表明，在 AI coding 的时代，仍然可以根据 evidence 而不是 vibes 来作决定。

我在这里也有同样的感受，因为我认为，run 一些 toy evals 并看看 results 是什么，是有价值的。即使有人可以使用一个 AI lab 的资源，我也不认为他们能说 X 或 Y 已被“empirically proven 为 unhelpful \[或 helpful\]”，但我们仍然可以获得某种信息。

根据我们在 testing evals 中看到的情况，如果我想要一个 Rust 的 property-based testing library，我会倾向于试试 proptest；而对于任何我会使用 Lean 的 problem，我也会倾向于试试 ACL2，看看 results 如何 vary，以及我是否能获得更好的 results；此外，也有相当多的信息可以归入某种基于 vibes 的直觉。

正如我在最近 N 篇文章中提到的，我一直试图在 30 分钟内写完其中的每一篇，因为要写的 results 太多，而时间不够，所以我不会[像在 5.6 Sol Zstd eval 中那样，逐一说明每个 condition 下发生了什么](https://danluu.com/agentic-testing/)。这篇文章已经花了我超过 30 分钟，因此我就写到这里，也许我们会在以后的文章中进一步研究 testing 和 verification。

### 附录：为什么 AI labs 不发布更多关于哪些 techniques 是 effective 的 comparisons？

与我们这些无名之辈不同，他们确实拥有 run 相对 comprehensive 的 evals 的资源，而关于什么是 effective 的，普遍缺乏信息。如果人们懂得如何更好地使用 AI，似乎就会带来更多 AI usage。另外，我的经验是，对于 OpenAI 的 models 与 Anthropic 的 models，effective 的 techniques 并不相同。如果其中一家公司发布关于什么对其 models 有效的优质信息，就可能引导人们以对该公司有利的方式与 agents 进行 interacting。

我猜，反对这么做的理由大概是：revenue growth 如此迅速，做其他工作能赚更多钱，而且／或者，人们如何 prompt 的 differences 反正并不真正重要。作为这些 labs 之外的人，前者在我看来是合理的，而后者似乎不可能是真的（因为我反复观察到，行事合理、并没有做明显愚蠢事情的人会得到非常不同的 results，甚至一个人可能无法为某个 problem 获得 working solution，而另一个人却能轻松让事情运作起来）。如果这些 results 是“真实”的，而不是 testing 足够广泛的一组事物所产生的 artifact，那么其 impact 就比仅仅匆匆浏览 graph 时看起来的更大，因为随着我们在 implementing Pandoc 上投入更多 effort/turns/dollars，我们在 correctness 方面会得到 dimishing returns。通过查看 Default fit line 就可以观察到这一点：它的 slope 远低于我们从 (0,0) 到 Default point 进行 fit 一条 straight line 时所得到的 slope；查看 fit line 的 curve 也能观察到这一点。尽管如此，我在实践中观察到的人们如何 prompt 所产生的 impact 的 differences，远大于我们通过增加几个关于如何 test 的词来 variying test techinque 时所看到的 differences。我认为这相当不令人意外（我们并不真的指望存在某些神奇的 testing/verification 词语，能带来 10x improvement），但这类事情使得 run 一个能够探究人们如何 prompt 的 differences 的 eval 变得困难／昂贵。

David R. MacIver 指出：

> 顺便说一句，我在对这个 skill 的 evaluations 中注意到的一件事是，ChatGPT 对 PBT 的热衷程度远不如 Claude。在我目前的 benchmarks 中，Claude 会相当积极地 write property-based tests，而且在 development 过程中似乎会从中受益，但 ChatGPT sol 不会这么做，除非你非常坚持。所以，这里可能存在某种 prompt sensitivity，也可能是 model specific 的。我还完全没有为 ChatGPT 对这个 skill 进行 optimised，所以也有可能是我无意中把它的某些地方搞砸了。顺便说一句，我其实并不知道 Claude 在 PBT 上是否比 ChatGPT _更好_（我真的应该 check 一下）。它只是更主动地去做，但当它们真正 write properties 时，quality 处于大致相同的 level，也是有可能的。

我还没有对 Claude 做过同等广度的 testing。根据 MacIver 的说法，Claude 可能更擅长 property-based testing，也可能并非如此。另外，考虑到他 develops Hegel，而且通常使用 Claude，Hegel 与 Claude 配合时可能比与 Codex 配合时表现更好，如果我们尝试使用 Claude，也可能看到 Hegel 给出更好的 results。所以，这里可能存在某种 prompt sensitivity，也可能是 model specific 的。

虽然 graph 上没有展示，但用于 5.6 Sol Zstd eval 的原始 Hegel skilled，以及 MacIver 在那次 eval 之后对 skill 做了更多 testing 而创建的 updated 版本，两者的表现都不如不使用 skill 的 Hegel。Correctness 相当接近，而两者的 cost 都高得多，其中 updated skill 是两者中更昂贵的。我认为，这个为某些 cases 得到 improved 的 skill，在其他 cases 上却变差了，是件很有意思的事。正如我们在上一篇文章中讨论的，要编写某些种类的 skills（例如 test technique skills），使其跨 models 和 effort levels 都是 effective 的，似乎非常困难。这里我们可以观察到的另一件相关的事是，Skill condition——也就是我根据自己使用 GPT-5.5 和 GPT-5.6 Sol 推动 agentic testing 的经验匆忙编写的一个 skill——在我们的 5.6 Sol eval 中 outperformed，但在这里使用 6 Astra 处理 Pandoc 时却 underperformed。对于使用 6 Astra 在 larger problems 上推动 testing 更有经验的人，大概可以编写一个在那些情况下 outperforms 的 skill，至少对于那些与此人处理过的 problems 在性质上相似的 problems 是如此，但我还没有足够深入地研究 Astra test effectiveness，无法自己编写那个 skill。

说到相关的事，出于各种偶然的原因，我已经习惯了使用 Codex。我用它似乎还不错。但这几乎不能让我知道，自己使用 Claude 会有多 effective。

我觉得这很有意思，也很希望看到更多人把自己观察到的情况写成 case studies。

## 原文

When we looked at [how well agents used test/verification techniques in August](https://danluu.com/agentic-testing/)[1](https://danluu.com/astra-testing/#fn:A), we saw that GPT-5.6 Sol generally did what you might call a caricature of various techniques when asked to use a technique or library such as TDD, QuickCheck, Lean 4, etc.; not specifying any particular test method (which we'll call Default) resulted in many worthless unit tests, which was one of the best performing conditions because asking agents to test in specific ways mostly made them worse. In that eval, we gave agents the Zstd RFC and asked them to implement Zstd (with an addendum for how they should test for all conditions other than Default).

On re-running the same eval with GPT-6 Astra, we see two big differences:

1.  Astra's capability has increased by enough that we need a more difficult eval (on the Zstd implementation eval, almost every condition gets 100% correctness almost every time on medium regardless of technique)
2.  Agents seemed to use test and verification techniques more effectively

On (1), we previously saw that, when implementing Zstd from the RFC with 5.6 Sol, on average, agents spent $3.50 on medium effort and $5.50 on xhigh effort to get full (holdout) test correctness about 63% and 77% of the time, respectively. With Astra, agents cost $1 to get full test correctness over 99% of the time at medium effort.

On (2), an example would be that when we asked 5.6 Sol to do fuzzing, it would generate many worthless random inputs, which would mostly hit the same code paths and not test anything interesting. With 6 Astra, we see agents that are asked to do fuzzing in a structured way that actually exercises code paths and finds non-trivial bugs, but we can't tell if this improved correctness or not because the Zstd implementation benchmark is saturated.

We also tried giving 5.6 Sol the IMAP RFC, but it was too hard for 5.6 Sol. When trying again with 6 Astra, we get the following distribution of results (the y-axis is the percent of runs where all tests pass; agents are not given the tests and the points are the results across 80 runs of each condition).

Default once again looks pretty good. Some conditions result in somewhat better correctness, but also with higher cost. Although the IMAP RFC isn't saturated, it would be nice to also see results on a harder task since most of my time goes to tasks that agents can't one-shot most of the time. To test this, we'll try the [pandoc eval we looked at when comparing programming languages](https://danluu.com/pl-tokens/). A reason I want to see results on larger evals is that, as we observed [when looking at caveman mode](https://danluu.com/ai-coding/#caveman-mode) and as we saw with languages, models often perform fairly differently on larger tasks. With caveman mode, the large wins that people reported became smaller or disappeared and with languages, we saw this in multiple ways, such as C and C++ implementations of Zstd being at least somewhat ok on memory safety, whereas C and C++ implementations of Pandoc were plagued by memory safety issues.

Pandoc is significantly harder, and even after running multiple turns (roughly 14 on average), no condition reached 100% correctness, so we'll look at the fraction of tests passed instead of fraction of runs that got to 100%.

For this, we only ran each condition 25 times due to the cost involved. At MSRP, this cost about $90k.

Recall that, in past evals we ran on languages and test/verification techniques, the failures were often idiosyncratic results of how agents operate, such as agents using Clojure writing incorrect byte conversion code by default or agents using Verus writing vacuous proofs. This kind of thing is quite different from the reasons I've seen people say that agents should use some particular language or test/verification technique, which are generally nice-sounding explanations for why something ought to be better that sound appealing in a very human way but appear to be unrelated to reality when we look at what agents actually did[2](https://danluu.com/astra-testing/#fn:R).

Because we "only" ran $90k worth of evals here, we don't really have enough information to say why almost anything happened. We can observe that some conditions performed better than others, but it's difficult to say what it means. As a result, we shouldn't read too much into this, but we do see some things that seem consistent with what one might expect, in that we might expect most of the test techniques and libraries suggested to give better generalization, which would then give better holdout vs. test scores (result is up and to the left of the Default line when viewing visible vs. holdout test scores), with TDD giving worse generalization (down and to the right of the Default line).

But, if it's true that testing properties gives us better generalization and conditions like TDD that result in a lot of small tests give less general results, we'd expect the built-in condition to also have a low holdout:visible relative to Default and that's not what we saw. Why this is is unclear and I don't think we can really determine this without a lot more runs.

For the actual results, the line shown for cost vs. holdout and cost vs. visible show curves fitted to the shape of all graph trajectories across multiple turns, fit to Default. Things that are below / right of the line can be thought of as worse and above / left can be considered better. With 5.6 Sol, it was clear that the test conditions generally weren't doing useful work for a combination of reasons:

1.  Almost no condition outperformed Default
2.  On other evals (not discussed in detail), similar prompts also did not outperform Default
3.  The tests produced by non-Default conditions were mostly ridiculous and didn't capture the value of the technique

Here, we have a situation where many different techniques have a better result than Default. The conceptual error bars on each condition are quite wide (more so than indicated by the bootstrap intervals shown on the plots), but the number of conditions that outperform Default makes it plausible that one or more conditions truly outperforms Default even if we don't know which ones exactly. Furthermore, some conditions likely truly outperform other conditions, but we don't really have sufficient data to tell which conditions are generally better. It's much simpler when almost everything looks bad across a wide variety of techniques.

Here are some questions I have about the results:

1.  To what extent can these results be extrapolated to running more turns to get to near-complete correctness for Pandoc? In general, conditions do maintain something like their rank order with additional turns, so it's plausible the ranking will continue as-is, but this is untested
2.  How much of the results are due to a small sample size (with respect to each condition)? For the Pandoc eval, we "only" ran each condition 25 times. Many different turns were run, but we know from previous experiments as well as just using agents that there's a high degree of path dependence when looping over generated code
3.  How much of the results are due to a small sample size (with respect to minute / trivial variations)? From having run a few silly evals, I know that it's possible to get very different results when asking for the same thing due to trivial changes (such as changing sentence structure, changing capitalization, etc.); how much of the current results are due to something arbitrary like this?
4.  How much of the results are due to a small sample size (with respect to the problem being solved)? We looked at one "Pandoc-sized" problem. If we looked at 100, how representative would Pandoc be?

If I really wanted to answer these questions, I'd want to run at least 100x what was run here to run the full matrix. Steve Yegge has mentioned using ~20 Claude subscriptions to spend ~$120k/mo of MSRP token spend. Getting to 100x isn't plausible with a setup like that, but 2x to 3x could be done with testing expanded in a limited fashion and some guesswork and extrapolation. I don't know that it really makes sense for me to do that given how much time it would take and how little spare time I have, but considering [what kinds of things academics have looked at when studying programming productivity](https://danluu.com/empirical-pl/), maybe it makes sense for a grad student to do this, since it would be more informative than a number of widely cited studies. But, in industry, I'm not sure who would do this outside of an AI lab.

That being said, if you keep in mind that we don't know how well any of these results generalize, I'll note a few things that I thought were interesting.

1.  Differential testing caused agents to examine tests and invariants in a way that engendered better "understanding" than other conditions
2.  TDD once again underperformed, but not all conditions that caused agents to write a lot of small tests underperformed
3.  ACL2 (a theorem prover) performed well ([it also performed well in the 5.6 Sol Zstd eval](https://danluu.com/agentic-testing/))
4.  Property-based testing (not the named condition, but a number of libraries that force the use of the technique) finally resulted in tests that do what one might hope from PBT

(1): I tried to get agents to do this with the hastily written skill I wrote for the 5.6 Sol Zstd eval; although the skill performed decently, agents basically didn't do this. However, for the Pandoc eval, differential testing did cause agents to closely examine boundary conditions and figure out how to write tests (and therefore how to write code) that correctly implements both sides of the boundary. I'm not confident that this generalize, but it would be interesting to see if it does generalize and what else can get agents to do this kind of thing systematically.

(2): Although TDD underperforming is exactly what I'd expect (recall that I added TDD to the 5.6 Sol eval because I thought it would underperform), the lack of underperformance of other conditions that cause many small tests to get generated should reduce confidence in the plausible sounding reason that writing many small tests underperforms.

(3): I've felt for a long time that ACL2 is underrated relative to other verification tools (it was heavily used to good effect in industry in some areas relative to the amount of academic work on it). I had low confidence in this opinion and continue to have low confidence, but it has performed well in evals I've done so far. Given how much effort is being poured into getting agents to use Lean effectively, I'd expect that Lean will eventually outperform ACL2 even if ACL2 outperforms today, but ACL2 doesn't seem like a bad choice today. For people doing verification or proofs with Lean 4, I'd be curious how the results compare to using ACL2.

(4): Yay (perhaps). For all the reasons I noted above, I have low confidence that this generalizes, but Proptest once again performed well. And, this time, the testing was a lot better than we saw in the 5.6 Sol Zstd eval. I have no inside information on this, but I would guess that there wasn't a major effort on improving PBT / fuzzing / etc. between 5.6 Sol and 6 Astra and that this comes out of better generalization and higher capability. If that's true (and this isn't just some artifact of my only spending $90k MSRP and not $9M MSRP), this bodes well for better testing in the future in that we should expect models to get better at testing without any particular effort to improve testing capabilities.

Between my running these tests and publishing this post, a claim that you should tell agents not to write tests (based on running DeepSWE) went viral. The specific claim was

> ok it's official...\[ellipses from original quote\] AI-written unit tests and integration tests are empirically proven to be unhelpful. you should tell your agents to stop writing tests by themselves

[As we previously noted](https://danluu.com/exercise-7/#30-deepswe-senior-swe-bench), I find DeepSWE unrepresentative of work that I do and therefore meaningless to me personally. Additionally, that was done with Sonnet 5.5 High, so it generally only passed on problems that are much easier than the problems discussed here, and as observed here and in other recent evals, which techniques are effective often doesn't generalize across problem size or problem difficulty. I find it plausible that for problems coding agents find very easy, telling them not to test reduces cost (which is what was actually shown conditional on someone caring about DeepSWE). Generalizing this to "AI-written unit tests and integration tests are empirically proven to be unhelpful" based on the test that was run seems wrong regardless of whether or not this holds for other problems, and it seems unlikely that the claim holds. The claim was based on asking for no tests, which resulted in similar correctness and a small cost savings (9%, on average). In our tests here as well as before, we find differences in correctness as well as a larger than 9% difference in cost, so it seems unlikely that a claim like "AI-written unit tests and integration tests are empirically proven to be unhelpful" based on a 9% difference in cost on a benchmark of small problems is correct. Another thing to note is that DeepSWE's grader is broken with respect to testing because (among other issues), [an agent can add a test name that conflicts with a grader's secret test name, which will then cause a failure](https://epoch.ai/benchmarks/deepswe/review). Given issues like that, adding tests is inherently penalized in a way that isn't representative of real-world usage.

You can argue the claim was highly effective, in that making overstated claims that something is empirically proven is a good way to go viral[3](https://danluu.com/astra-testing/#fn:V) or [get a lot of citations](https://danluu.com/empirical-pl/), but it's not a good way to figure out how to use coding agents effectively.

[In Nolan Lawson's recent post on how JavaScript framework choice impacts agents](https://nolanlawson.com/2026/10/28/the-ai-cost-of-javascript-frameworks/), he noted:

> My goal here is not to write the end-all-be-all benchmark for “I’m a vibe-coder, which framework should I choose?” The point of this post is to demonstrate that it’s possible in the era of AI coding to still make decisions based on evidence rather than vibes.

I feel the same way here, in that I think it's valuable to run some toy evals and see what the results are. Even if someone had the resources of an AI lab available to them, I don't think they could say that X or Y are "empirically proven to be unhelpful \[or helpful\]", but we can still get some kind of information.

From what we've seen in our testing evals, I'd be inclined to try proptest if I wanted a property-based testing library in Rust, and for any problem that I'd use Lean on, I'd be inclined to try ACL2 as well to see how results vary and if I get better results, and there's also a fair amount of information that fits into some kind of vibes-based feel for things.

As I've noted in my N most recent posts, I've been trying to write up each of these in 30 minutes because there are too many results to write up and not enough time, so I'm not going to provide [an accounting of what happened for each condition like I did for the 5.6 Sol Zstd eval](https://danluu.com/agentic-testing/). I'm already over 30 minutes on this post, so I'll stop here and perhaps we'll look more into testing and verification in a future post.

### Appendix: why don't AI labs publish more comparisons on what techniques are effective?

Unlike us randos, they actually have the resources to run relatively comprehensive evals and there's a general lack of information about what's effective. If people understood how to use AI better, it seems like that would result in more AI usage. Also, my experience has been that different techniques are effective with OpenAI's models vs. Anthropic's models. If one of these companies published good information about what works with their models, that could move people towards interacting with agents in a way that's advantageous for them.

I guess the case against this is something like, revenue growth is so rapid that more money can be made by doing other work and/or differences in how people prompt don't really matter anyway. As someone on the outside of these labs, the former seems plausible to me, whereas the latter doesn't seem like it can be true (because I've repeatedly observed reasonable people who aren't doing obviously silly things get very different results, to the point where one person might fail to get a working solution to a problem where another person easily makes things work). To the extent the results are "real" and not an artifact of testing a broad enough set of things, the impact is larger than it might seem from just skimming the graph because, as we put more effort/turns/dollars into implementing Pandoc, we get dimishing returns with respect to correctness. This can be observed by looking at the Default fit line, which has a slope far below what we'd get if we fit a straight line from (0,0) to the Default point, as well as by looking at the curve of the fit line. Despite that, the differences I've observed w.r.t. the impact of how people prompt in practice are much larger than what we see from variying test techinque by adding a few words about how to test. I think this is fairly unsurprising (we dont really expect there to be some magic testing/verification words that give us a 10x improvement), but this kind of thing makes it difficult/expensive to run an eval that gets at differences in how people prompt.
