一、不要凭直觉乱优化代码：代码具体哪里快、哪里慢是极其复杂的问题，尤其在虚拟机环境下，很难猜到运行时优化的具体行为。不要凭直觉乱优化代码，是从编译原理课上学到的最有价值的事情。

二、针对性能关键处优化：CPU 缓存、自动向量化对性能影响非常大，应该针对这些方面优化；非热点代码则应该以可读性为主，这样对维护才是经济的。

三、学前曾凭猜测优化代码：我学编译原理之前，经常猜测编译器的行为，觉得这么写可能会慢、那么写可能会慢，然后自以为是地“优化”代码。

四、热点中的判断未必有分支开销：C# 的 `Sse.isSupported` 是 JIT 时期的常量，因此即使在非常密集的地方用它选择 `f_sse()` 或 `f()`，运行时也几乎没有分支开销，因为判断会被替换成对应硬件架构的函数。“几乎”的限定在于 JIT 之前可能还会执行几次 if。事先不了解这些知识，就可能误以为这种判断是在热点代码中做蠢事，进而用奇怪的方法“优化”，最终适得其反。

五、理解虚拟机优势才能自主判断：“native 编译会比 JIT 编译快”是被反驳的谣言，上述按硬件架构选择函数的代码就是反驳它的例子。只有了解虚拟机技术的优势，才能有自己的判断，不听信这类谣言。

六、基础知识贴近现实编程：编译原理、运行时优化和虚拟机技术这类知识属于编程基础知识，而非应用知识，离现实编程很近，正应该在高校学习。尤其在如今 vibe coding 这么厉害的情况下，人类更应该学会把握编程中的重点、难点，而不是琐碎细节。

## 正文

我学编译原理之前经常会猜编译器的行为，觉得这么写可能会慢、那么写可能会慢，然后自以为是地“优化”代码。实际上具体什么地方快、什么地方慢是个非常非常非常复杂的问题，尤其是在有虚拟机环境下，很难猜到运行时优化的具体行为。不要凭借直觉去乱优化代码就是我从编译原理课上学到的最有价值的事情。CPU 缓存、自动向量化对性能影响非常大，这些才是我应该去针对性优化的地方，而非热点代码其实应该以可读性为主，这样对于维护而言才是经济的。

^pr-e2636d429b80

比如我最近才知道 C# 的 `Sse.isSupported` 是 JIT 时期的常量， 所以我们如果在一些非常密集的地方写 `if Sse.isSupported { f_sse() } else { f() }` 几乎不会在运行时有任何 branching 开销，因为这个判断在运行时会被替换成对应硬件架构的函数。说“几乎”是因为在 JIT 之前可能还会 if 几次。这些事情如果我没有事先的知识，我可能就会认为这是在热点代码干蠢事，然后搞一些奇奇怪怪的方法去“优化”之，最后适得其反。甚至我可能还会听信一些谣言，说什么 native 编译会比 JIT 编译快，这种话你要是信了，上面那代码你就 native 编译去吧。了解虚拟机技术的优势之后，才能有自己的判断。谣言止于智者。

^pr-4f2919872cd5

这类知识正是应该在高校学习的，在我看来属于编程基础知识（而非应用知识），离现实编程是很近的。尤其是现在 vibe coding 这么厉害，人类更应该学会把握编程中的重点、难点，而不是琐碎的细节。
