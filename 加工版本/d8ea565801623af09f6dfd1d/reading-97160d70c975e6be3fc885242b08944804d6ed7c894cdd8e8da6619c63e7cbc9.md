## 正文

从去年 November 起，我就一直在相当频繁地使用 AI，整个过程是种有趣的体验。一个 agent 会做出某种事，要是人做了同样的事，你会立刻开除他。当然，我的反应是表现得好像这棒极了，然后 spin up 一千个 agents，让它们能做更多这样的事。

去年年中，我让 GPT（可能是 5.0 或 5.1）试着 find 一个 bug 的 source。不出所料，这些 code 没有 tests，而且 `git bisect` 也不能 work；这还是一个 UI interaction bug，我甚至都不太有资格为它 write 一个 test，所以我请 Codex 在 dates X 和 Y 之间 bisect，find 那个 introduced 这个 bug 的 commit。Codex 立刻告诉我，那个 offending commit 在这个 date range 之后（这根本不可能 correct）。我告诉 Codex 这不对后，它又有一两次告诉我某个 commit，而那些显然也不是 offending commit。我告诉它那些都不对后，它才告诉我，offending commit 是某个看起来说得通的 commit。当我要求它 prove or disprove 自己的 theory 时，它告诉我，它 wrote 一个 test，并 confirmed 那个 alleged commit 就是 breaking commit。

接着，我要求它在正常的 browser test environment 中，使用完整的 developer end-to-end stack 制作一段 video，展示给我看。它声称自己没有这样做的 permissions（这是谎话），但它可以在 playwright 中使用适当的 test code，制作 commit 前后 repro 的 execution 的 video。这段 video 很有说服力，展示了 feature 在 commit 前 working properly，而在 commit 后 failing to work。我觉得有些不对劲，于是试着在 commit 前后手动 reproducing 这个 issue，结果发现整件事都是捏造的。video 让人以为 Codex 已经 reproduced 那个 bug，但那是一个 artificial browser environment，专门被 designed 来 create 一个 fake repro，而不是真正的 environment。

就像我说的，因为这确实是一次如此美妙的体验——我不是在反讽——我立刻心想：“怎样才能再多来点？”于是开始越来越频繁地使用 agents，直到去年年中至年末，我已经在大量使用 coding agents。

### Testing 的背景

在 testing 方面，LLMs 能发挥很大的杠杆作用。从所需投入来看，达到某个 quality bar 比以往任何时候都容易，但 software 的 quality 却似乎比以往任何时候都低。十年前，我们看过[我在随意选取的一周里遇到的 bugs](https://danluu.com/everything-is-broken/)。那时 bugs 就不少，而我现在遇到的 bugs 更多，但我不认为事情非得如此。

首先，在一个 bug 已经被 shipped 之后，使用 data-driven approach 来 find 和 fix 这个 bug 比以往任何时候都容易。举个例子，在工作中，我试着 creating 一个从 support ticket（chat 或 email）到 pull request（PR）的 pipeline。据我所知，这样 works 得还可以。由于我所在的公司采用 traditional workflow，所有这些 fixes 都会由人 reviewed，而且到目前为止，我们没有发现任何已知的 false positives。

每投入一个 unit of time，也可以进行更 thorough 的 testing。我个人认为，这可以足够 effective，让我相当放心地尝试通过“[software factories](https://factory.strongdm.ai/)” workflow 来 ship 大量 code，因为我见过一种 testing-heavy no-review workflow，它带来的 quality 远高于我见过、甚至听说过的任何 review-reliant workflow。

和所有人一样，我也有源于自身经历的偏见。恰好，我职业生涯的头十年是在一家公司度过的，那里的 test processes 恰好在今天的 LLM environment 中也很适用。[我曾在 Mastodon 上谈到把 fuzzing 作为 default testing methodology](https://mastodon.social/@danluu/116486547257066966)，而[一位怀疑者试了试，立刻 found 一些 bugs](https://mastodon.social/@22@sfba.social/116508702500087643)：

> 所以我又读了一遍那篇博文，当时满脸怀疑，但还真是，Claude fuzzing found 了好几个值得 fixing 的 classes of bugs

我聊过的其他一些人也试着采用类似于我们将在这里讨论的 testing flow，他们全都立刻在自己经手的 software 中 found bugs，其中包括仅仅要求 Codex 或 Claude 去 audit code 中的 bugs、find bugs、“test”、“test more”等不会 surfaced 的 bugs。例如，Dennis Snell 提到，他和队友 Jon Surrell 不仅在他们正在处理的 code 中 found bugs，还以相当少的投入，“在 upstream dependencies 中，包括 HTML specification、big-three browsers 和其他 open-source projects”里 found bugs。

一般来说，当我和 software 从业者谈 testing 时，我的出发点与他们差别大到他们立刻像看外星人一样看着我。因此，我们来谈谈我以前任职的 hardware 公司 Centaur 是怎样 tested 的，这段经历影响了我对工作方式的偏好。我们做过的一些在 software 界曾经或至今仍不合常规的事情包括：

1.  我们 Hired 专职 QA / test engineers，让 testing 成为与 developer 并列的 first-class career path
2.  默认不做 code review
3.  几乎没有 hand-written tests
4.  通过 programmers 有时称为 property based testing、randomized testing、fuzzing 等方式进行 Constant testing，不过我们只把那些叫作 tests（hand-written tests 则叫作“hand tests”）。
5.  有 Large regeression test suite（在 compute farm 上 execute 需要 3 months wall clock）
6.  没有 unit tests

为了让你对总体结构有个概念，我离职时（2013），我们大约有 1000 台 machines，一直在为大约 20 位 logic designers 和 20 位 test engineers generating 和 running tests。这些都是 on prem，machines 占了我们所在大楼的半层。

总体结构是，大概 20% 的 machines 在 running regression tests，80% 在 generating 和 running 新的 tests。用三个月的 regression tests 来 gate commits 太久了，所以还有一个短得多的 tests 列表，run 一遍大约需要 10 minutes 左右，大家会在 committing 前 run。这些 pre-commit tests 会在一个特殊的 setup 上 run，以尽可能快地完成：使用花钱能买到的最快 machines，并进行 overclocked，同时还使用不同的 simulator setup。

新的 failures 一出现就会被 found 和 reported，并有一到两位 engineers 专门 sorting through failures，再对它们 triaging（rejecting false positives、fixing test generator 中导致它们 generate false positives 的 issues，等等）。

就影响程度而言，[除非你把文化单独算作一项](https://danluu.com/culture/)，(1) 大概是我们与典型 software company 之间最大的区别，但也是与这里的读者最不相关的一项，所以我会把这部分讨论放到 footnote[1](https://danluu.com/ai-coding/#fn:T) 里，只在这里简短说一句：testing 和任何其他 skill 一样，花更多时间去做，就会提高 skill；而由于 testing 在大多数大型 tech companies 里不是 first-class career path，software companies 里的人通常不具备某些职业 CPU test engineers 所拥有的那种 testing skills 水平。一个花了 20 years 从事 distributed systems 或 UX 的 engineer，会比一个同样有才华、却只把 5% 的时间用于 distributed systems 或 UX 的 engineer 强得多；同样，一个花了 20 years 从事 testing 的人，也会比一个只把 5% 的时间用于 testing 的人强得多。

(2) 是让我们在 chip company 采用的某些 test practices 适合 AI workflows 的原因之一。我们默认不 review code，因为我们足够信任自己的 test practices，所以一般来说，review 并不能增加多少 reliability。我们每年 shipping 的 significant user-visible bug 少于 1 个；只有当某人觉得某件事特别棘手，希望再找个人帮忙看看时，才按需进行 review[2](https://danluu.com/ai-coding/#fn:R)。有了 AI coding workflows，一个人很容易 generate 超过任何一个人、甚至任何十个人能手动 review 的 code 量。对于 shipping 未经 review 的 code，人们的接受程度各不相同。我个人非常放心地 shipping 未经 human review 的 code，因为我见过这种做法被用于一些 products，而它们在技术上比大多数 software companies 的大多数 software 都更有挑战性。

我常看到有人说：“那 risk 太大了；我们有数百万 users。”但从 empirically 来看，他们所说的 workflow，如果只看 raw count，其人均 ships bugs 的 rate 可能高出一千倍；如果再按 severity 调整，ratio 还会高得多。如果一家主要依靠 review 来 catch bugs 的公司，其 shipping bugs 的 rate 比如说只有我们在 Centaur 时的百分之一，那我就能理解他们的观点。但典型 software company 的情况并非如此，那里的人因为认为 shipping bugs 有 risk，而不愿意摆脱 human review。

(3) 和 (4) 是相辅相成的。我所知道的几乎每一个认真对待 reliability 的 software group（那些 ship reliable databases、distributed databases 等的各种 teams），至少都在朝着同一个方向做，尽管它们的 hand written tests 占比可能更高。依靠自己与 software interacting，并观察 software 看起来是否 work 来进行 testing，被认为不是好主意；出于同样的原因，依靠直接键入一个 test 的 inputs 和 expected outputs 也不是好主意。[如前所述](https://danluu.com/testing/)，手动 write tests 实在很 inefficient。对于任何给定的 reliability 水平，如果你优先采用 randomized test generation，而不是 hand-written tests，就能更快达到。

(5) 源于大量 tests find 了大量 bugs。一般来说，如果一个 test found 了某个后来被我们 fixed 的 bug，我们就会永远把这个 test 保留在 regression test suite 中。事实证明，如果你用好的 tests find 大量 bugs，最终就会得到一个 large test suite。不过，即使先把这点放在一边，单从 test efficiency 的角度来看，software 中那种对每个 PR 都在 CI 里 run 同一组 tests 的 standard setup 也极其 inefficient：想想看，哪一种更可能 find 一个 bug，是一天内 running 同一个 test 一千次，还是在相同的 test time 内 running 一千个不同的 tests？

(6) 同样源于对 test efficiency 的考虑，因为我们的 team 比 competitors 小得多。这也是公司能生存那么久的原因之一。当 Intel 让 AMD 之外的所有 x86 designer 都退出市场时，我们的 operating cost 足够低，使公司一直存续到 2021，随后被 Intel 以 $125M acquired。以公司那么小的 team size，不可能靠 unit tests 获得合理的 test coverage；而 hiring 足够多的人来做 unit tests，很可能意味着公司会提前十年或二十年，走上 Transmeta、Rise、Cyrix、TI、UMC、NEC、VM 等公司的 x86 efforts 的老路。从 efficiency 的角度来看，unit testing 的表现相当差。

总之，我们做了不少大多数 software 从业者会告诉我是坏主意的事（dedicated test engineers、没有 unit tests、没有 code review 等），而我们的 quality 远高于我任职过的任何 software company，也远高于我用过的任何 software。每当我谈起这件事，人们就会说这不适用于 software，因为 CPUs 只有 X 方面的 concerns，而你无法对 Y 做同样的事。刚从 CPU design 转向 software 时，我觉得这或许是对的，但此后，凡是有人说这种 testing methodology 无法奏效的 Y，我都逐一试过，而它对每一种都奏效了，所以我已不再觉得这种说法很可信（而那些 X 通常涉及[对 hardware development 是什么样的 incorrect assumptions](https://www.hillelwayne.com/post/are-we-really-engineers/)）。尽管 hardware 与 software 确实存在 differences，但在我见过的人们以此为由，认为 testing techniques 无法迁移的情况中，他们依赖的都是某种想象出来的 factor；它之所以显得 relevant，只是因为他们对 hardware development 所知甚少。

一个 significant difference 是投入 testing 与 development 的 effort 的 ratio，但 fuzzing 的 fixed costs 相当低，因此无论投入多少 effort，这种做法都是 scalable 的，而且 efficiency gains 依然存在。再加上 test efficiency 的 gains，effort 的 ratio 并没有 software engineers 通常想象的那么大。我们的 test engineers 与 developers 的 ratio 大约是 1:1，另外大概有 10% 的时间处于“freeze”state，其间的目标是 find bugs，而不是 ship new features，因此，对这里的 overhead 作一个 zeroth order estimate，就是我们把 55% 的 effort 用于 testing，45% 用于 development；换句话说，如果我们在 testing 上完全不投入 effort，就能在 development 上投入 2.2x 的 effort。如果你看一家 shipping significant bugs 的速度比我们快许多倍的 software company，宣布进入紧急状态，让大家把 55% 的 effort 用于 testing，我不认为那个 ratio 会改变太多。或许他们能达到原来 ratio 的一半之类，但真正造成 difference 的并不是 effort 的多少。

如今，人们还会说，既然直接让一个 LLM 去 find bugs 就行了，何必费事做 fuzzing？这两种方法我现在都试过不少次了，我的经验是，fuzzing 在 find a bug 的 latency 上通常胜出，而在 finding more bugs 和拥有更低的 false positive rate 方面则占据压倒性优势。LLMs 的 variance 相当高（后面会进一步讨论），所以直接让 Codex 或 Claude 去 find a bug 有时也能胜出，但 on average，胜出的是 fuzzing。

### 关于 testing 的一些细节

尽管我对 LLMs testing 说了很多好话，LLMs 似乎并不擅长 testing。不过，无论你投入多少 testing effort，只要引导得当，LLMs 都能让你比以前更容易地施加 testing effort。

一个极端的例子是，我聊过的所有哪怕稍微在意 quality 或 testing 的人，都觉得 LLMs 默认 generate 的 tests，或者你告诉它们“Write tests”“Write more tests”等之后 generate 的 tests，很差。根据各自的标准，人们对这些 tests 的评价往往介于毫无价值和略有用处之间。

例如，Em Chu（一位 compiler engineer）说：

> 我目前使用的 tests 并不完美，但仍然高于 LLMs 似乎瞄准的标准；我会把那个标准形容为“足够 thorough，能让一个 feature 蒙混通过 human code review”。对于 compiler（相比于例如 UI），我猜普通的 test 更容易 write，但人们通常对 end product 的 correctness 有更高要求，而 LLMs 实在太差了。人类为了 write 出真正能 find bugs 的 tests，会采用 adversarial 的“那么，现在这样做会怎样”或“试试所有东西的 cross-product 吧”这样的 process，而它们在这方面差得令人难受

与此同时，我也见过不少人热情称赞，说只要告诉 LLMs“Write tests”“Write more tests”等，它们在 testing 上就好得惊人。当我探究人们为什么说 LLMs 擅长 testing 时，我发现，觉得 LLMs 擅长 testing 的，是那些原本基本不做任何 testing 的人。嗯，这就说得通了。如果从几乎零 testing effort 变成投入一点点 testing effort，那确实是巨大的进步。

截至 June 2026，指导 LLMs 做 fuzzing / randomized testing，也给我类似的感觉。我试过用一个 LLM 来 generate 一个 fuzzer，而对大多数 projects 来说，[这会在几分钟内找出真实且往往 serious 的 bugs](https://mastodon.social/@danluu/116486547257066966)。然而，当我查看 LLM-created fuzzer 试图 test 什么时，我的反应就和一个在意 quality 的普通 programmer 看到 LLM-created tests 时一样。LLM-generated fuzzer 的 coverage 差得令人费解，遗漏了各种 basic 的东西，而你本会期待一个人类匆忙写出的 fuzzer 都能 cover 它们。根据你是悲观还是乐观的人，你或许会说，这说明了大多数 projects 的 test coverage 是什么状况，或者说，这说明了 fuzzing 有着出人意料的 effectiveness。

从总体上看，如今 SOTA models 所产生的 LLM-generated fuzzers，并不善于“思考”应该如何 varied inputs 才能 elicit bugs。然后，如果你只是简单告诉它 inputs 应该如何 varied，以及要 combine 这些变化，它也不会以合理的方式 combine bug ingredients。你可以给出能够奏效的 instructions，但这在很大程度上依赖 user 提供方向。

如果你把 randomized testing 当作“加分项”，用来多 catch 几个 bugs，或者用来 replace traditional software testing processes，那么你只需告诉一个 LLM，去寻找 code 中的 risky areas，find 可能被 violated 的 invariants，再对它们进行 fuzz。这样还算奏效。在我说服人们尝试一些 randomized testing 时，他们通常会从这里入手，find 不少让他们庆幸找到的 bugs。由于愿意尝试对自己而言新颖的 test techniques 的人本身具有某些特点，这些人往往曾参与公司里一些最 well-tested、最 reliable 的 code 的工作，而他们能在自己相对 well-tested 的 code 中 find bugs。

如果你想用 randomized testing 来确保一个 agentic 的“software factories”workflow 不弄虚作假，那么就需要有办法应对 SOTA models 的 gaps，因为当你每天向一个 project 中 shipping 相当于数百乃至数千个 PRs 的内容时，一切未被 constrained、可以 degrading 的东西都会迅速 degrade。

从总体上看，整个 system 需要某种 feedback，能够 finds gaps，并指示正在对 fuzzer 作出 adjustments 的那个 loop 去 close the gaps。最近，我一直在 testing 一些自己既不了解 domain，也不了解 project 或 code 的东西，因此相当于在摸黑前进，并且知道自己想出来的东西会有很多 gaps（而且，如上所述，LLMs 在这方面很糟糕）。但即使是在我熟悉 domain、对 code 也比较了解的领域，仍然会有一些 gaps，因为人会遗漏东西、会犯错，所以始终需要有某种 feedback 进入 test setup，能够 find gaps，并让你或一个 agent 去 close the gaps。

我一直在尝试各种办法，让 agents 聚集、再聚集，以使 agentic loops 运行得更好；虽然这类做法有所帮助，但我还没找到一种足够好的方式，能创建某种不依赖 outside feedback 的 agentic software quality improvement loop。这种 outside feedback 可以是偶尔的 human input，也可以是 shipping 某些东西（理想情况下只向一小部分用户 shipping，并采用 staged rollout），然后让 system 对 metrics/logs/traces/support tickets/其他什么进行 monitor，将其作为 feedback。我前面提到的从 support ticket 到 PR 的 pipeline，就是这样一种 feedback loop。这个 pipeline 不仅会尝试 generate 一个 PR，还会尝试让 test setup 添加 test coverage，以便 find 那个 bug，并可能 surface 其他 bugs，或者在未来出现 regression 时重新 find 那个 bug。这似乎还算奏效，因为它能 finds real bugs 并 improves test coverage，但我确信仍有很大的改进空间。

与此相关，我一直在想，为什么 LLMs 如此不擅长 writing tests。向周围的人打听了一下后，有人告诉我，这是因为 LLMs 的 capabilities 来自人们 building [RL](https://en.wikipedia.org/wiki/Reinforcement_learning) environments，这些 environments 让 models 能够在 tasks 上 improve，有时是以 generalizable 的方式，有时则不是。他们还告诉我，出售 RL envs 是有市场的，但市场相当小，因为买家并不多，而且你最好认识某个 lab 里负责采购或与采购关系密切的人。如果你就是这样的人，或者能帮我联系这样的人，能否帮个忙，联系我一下（通过 [X](https://x.com/danluu)、[Mastodon](https://mastodon.social/@danluu/)、电子邮件等都很容易联系到我）。我很好奇这件事如何运作，也好奇为 testing、optimization，或这篇文章讨论的 longer horizon tasks 之类的事情出售一个 RL env 有多大可行性，因为在这些方面很容易 observe significant gaps。

回到 testing 的话题，在进行 fuzzing 或任何一种 bug auditing 时，detecting false positives 都是 process 中至关重要的一部分。至少目前，能使用一个比任何公开可用的 model 都更好的 model，也救不了你。前些时候，Dennis Snell 沮丧地告诉我，他花了一整天，在 Anthropic 转发给他雇主的 AI slop 里艰难筛查；这些东西来自他们大肆吹捧的 Mythos model，据说这个 model 太危险，不能向公众 release。Anthropic 显然是在通过提交 Mythos 发现的 security issues，给这家公司帮某种忙，或者是在做某种 EA security improvement，只不过他们懒得建立一个合理的 false positive rejection process，于是只是把一些真实的 vunlnerbilities 和大量 AI slop 一起转发过去 \[September 2026 更新：[另见](https://x.com/danluu/status/2102804723342688744)，[以及](https://www.vulncheck.com/blog/anthropic-glasswing-receipts)，其中也有人报告了同样的情况\]。当时，我使用的 model——如果 Fable 能说明什么的话——看起来在 capability 上比 Mythos 稍逊一些，但我毫不费力就能 generate 源源不断的 bugs（其中一些是 security issues），而且没有已知的 false positives。这似乎表明，在 model 周围建立合理的 setup，至少与拥有最新、最强的 model 同样重要。我不清楚 Anthropic 为什么没有做类似的事，因为做这种事最大的 blockers 对他们并不构成问题（token cost，以及很难使用他们的 models 或 OpenAI 最好的 models 来运行一个良好的 false positive rejection process，因为即使获得了标准的“cyber”approval，最新/最好的 models 也会 rejects create 和 run exploits 的尝试，因此你无法采取那个直截了当的办法：rejecting 那些你无法为之 create an exploit 的东西）。

我一直按各个 project / problem 尝试 custom workflows，并没有一个真正 generic 的 false positive rejection scheme，但有各种做法看起来具有一定的 semi-generalizable 性。如果你不介意花费 tokens，让 independent agents 反复 check 一个声称存在的 bug reproduction (repro)，能大幅降低 false positive rate。几个月前，[我提到过，使用不同的“personas”来进行 reviews，以及 managing agentic loops，都让我取得了不错的效果](https://mastodon.social/@danluu/116514958701771749)，也收到了一些回复，从理论上解释这为什么不会奏效，但在实践中，它似乎相当有效。我的 workflow 经常变化，大概在那次讨论一周后，我开始在其中加入“contrarian”personas，在相同的 wall clock 或 token budget 下，这提升了 performance。

对于任何需要 human reviewed 的内容，都必须有某种 artifact（例如，如果某个 bug 预期会在 UI 中明显显现，就需要一段视频）。即使没有真正明确要求 agent 对它进行 review，仅仅是 producing 这个东西，似乎就能在一定程度上 reduce false positive rate；然后，让 agent 对 artifact 进行 review，又能进一步 reduces false positive rate。要求 agents independently review 这个 artifact（例如，查看 produces 视频的 test code，而不是查看视频本身），也能进一步 reduces false positive rate。总的来说，获得 independent perspectives 似乎对 reducing false positives 很有帮助。在我做过的 experiments 中，按每单位 wall clock time 或每美元来衡量，这不如让 agents 采用不同的 personas / perspective 有效，但仅仅多次提出同一个问题就能 improves results，原因从 LLM variance 一节的 graphs 中应该就能看出来。

我尝试过的几乎所有用于 reduce false positive rate 的办法都奏效了，所以，如果你没有把 workflow scaling up 到需要在意 optimizing costs 的程度，那么，做任何稍微合理一点的事情，似乎都能取得相当不错的效果。

### Caveman mode（穴居人模式）

我不断收到各种 tool 和 workflow 的推荐，但每当深入了解时，我几乎总是找不到足够好的信息，来判断采纳这些推荐是否合理。举个例子，我在工作中已经多次看到有人推荐“[caveman mode](https://github.com/juliusbrussee/caveman)”。据说 Caveman mode 能 reduces token usage 并 speeds up prompt resolution（README 声称 token usage 减少 75%、token usage 减少 65%，以及使用的 tokens 减少 2x，此外还有 3x 的 speed increase）。

我搜索相关信息时（只是在 Google 上搜索 'caveman mode'，不加引号），排名最靠前、又不是指向 caveman mode 的链接的结果，是[这个 reddit thread](https://www.reddit.com/r/ClaudeAI/comments/1si197b/does_caveman_mode_save_tokens_at_the_cost_of/)，其中排名前三的评论里，一条是玩笑，另外两条则极力推荐它：

> 就是极其简短，令人耳目一新……而且大幅 lowered token count，似乎完全没有影响 analytical thinking……不过我没办法对使用前后进行 benchmark。
> 
> 公司里有人正在 testing 它，看起来它确实能 save tokens，而且效果同样好。

其余排名靠前的搜索结果，大多数也都是对 caveman mode 的正面推荐，声称做过某种 eval（虽然读起来像是未经筛选的 LLM text）；而 YouTube 上排名第一的结果，则是[最知名的 programming YouTubers 之一](https://www.youtube.com/watch?v=L29q2LRiMRc)在说：

> 它真的有用；它真的相当好用……不，我没有夸张

在工作中的一个 slack thread 里，大家正在推荐 caveman mode，我问有没有人做过 comparison，并指出 caveman mode 的创建者在有关 caveman mode 的 HN thread 中回复说，这就是个玩笑。有人贴了一篇有关 caveman mode 的 analysis，声称它有显著优势，但那篇 analysis 是一篇 LLM-generated SEO spam article，里面错误百出。我礼貌地指出这一点后，贴出链接的人说：“我只是略读了一下。”

到这时，我决定花点时间 generating 一些 caveman mode benchmarks，每个大约花 15 seconds（现在大家似乎把 benchmarks 叫作 evals，所以我是不是也该把这些叫作 evals？）（[之前在这里有更详细的讨论](https://www.patreon.com/posts/160473058)）。

先从头说起。几个月前出现这番讨论、而我对这东西进行 benchmark 时，我一直在大量使用 GPT-5.5 xhigh，所以，我们先看看 GPT-5.5 xhigh 在第一个 benchmark 上的表现。这是一个简单的 benchmark，我们要求 agent 在 wasm 中 optimize 一些 code。既然这只是我花了 15 seconds 通过 prompting 让 agent generate 的东西，我觉得不值得花大量时间讨论细节，不过有一点值得注意：完全有可能取得远好于这里任何一个 agent 所取得的 results。我预期，由人亲自动手，或者由人明确规定 agent 应该做什么，得到的 results 都会远好于任何一个 AI）。对于 optimization chart，1.0 表示没有 speedup，越高越好（低于 1.0 意味着这次“optimization”反而 slowed things down）。为了让你了解运行 experiments 时是什么样子，你可以点击按钮，以交互方式跟着看，也可以直接播放动画。

我们可以看到，对于第一个 benchmark（在 wasm 中 optimize 一个 non-trivial algorithm），一次 run 之后，caveman 看起来表现不错。我们得到了 1.027 的 speedup，对比 0.987，\$12.10 vs. $23.10，以及 8m51s 对比 14m9s 的 wall clock time（即 agent 花了多长时间）。但我们知道 LLMs 是 stochastic，所以大概应该再 run 一次。第二次 run 之后，我们可以看到 results 出现了很大变化，两者的 average speedup 都是 1.0，但 caveman mode 的数据是 \$12.45 in 8m64s vs. $40.38，用时 17m57s。这是巨大的 cost savings，与 caveman mode 声称的节省幅度相符。逐步讲解动画的每一步有点傻，不过，如果直接跳到最后，我们可以看到，50 runs 之后的 average 对 caveman 有利：speedup 是 1.03 对比 1.01，以及 \$17.97 in 13m46s vs. $24.21，用时 16m52s。这不如我们在两个 points 之后看到的表现，但仍然明显有利于 caveman mode。

### LLM Variance（LLM 的变异性）

最近，每当新的 models 发布时，我都会搜索一下，看看大家怎么评价它们。总的来说，外面有很多相互矛盾的评论。例如，GPT-5.5 发布时，人们给出了各种说法：GPT-5.4 比 5.5 更好，因为它更能 staying on task，而 5.5 会跑偏并 overthinks 这个 problem，使得 5.5 贵得多，也没什么意义；5.5 比 5.4 好太多了，用起来反而更便宜，因为它不那么容易搞砸，也不那么容易陷入 fixing 自己的 issues 的过程；5.5 比 5.4 更便宜，因为它表现得足够好，可以在更低的 effort level 下 run；5.5 “就是能用”，而 5.4 经常 fails，需要手把手指导，等等。往往会有人 run 一个 benchmark，证明自己的说法是对的。

看这些 benchmarks，我们就能为我在 GPT-5.5 发布后不久搜索 reddit 评论时看到的所有这些说法找到支持。在 Optimization 1 中，GPT-5.4 的 results 比 5.5 更好，而且便宜得多。但在 Game AI 中，GPT-5.5 比 5.4 好得多，以至于 5.5 high 的 costs 与 5.4 xhigh 差不多，却有更好的 results，而 5.5 medium 比 high 更便宜，results 还显著更好。只靠这三个 evals，就能为我看到的有关 GPT-5.5 发布时的每一种说法找到支持，因为所有这些说法有时都是对的。而且，这还是我们用相当多的 runs 来 averaging out variance 之后的情况；任何一个理性的人，都不会为了支持自己随手发到网上的一条评论而做这么多 runs。

总的来说，正是因为这类事情，每当我看到一个 summarizes 一组 benchmarks 的 metric 或 graph 时，我就会想：“给我看看 distribution。”models 的 Benchmarks 经常被 reduce 成一个单独、漂亮、整齐的 number，让你看到 X 比 Y 更好，Y 又比 Z 更好。我觉得这些基本上没有意义，因为如果我们看的是 OpenAI 和 Anthropic 最新、最强的东西，我们知道，既有合理的 benchmarks 显示 X 比 Y 更好，也有合理的 benchmarks 显示相反的情况。如果这组 benchmarks 里多几个偏向 Y 而不是 X 的 benchmarks，results 就会 flipped。这样的 summary metric 若要对我有用，就必须满足两个条件：这组 benchmarks 完美反映我所做 tasks 的 distribution 和 weight，而且我只能选择一个 model 来处理所有 tasks。既然这两个条件都不成立，我就不清楚能从这些 benchmarks 中得到什么可据以行动的信息。

如果更详细地看 public benchmarks，情况似乎比上面那个 abstract argument 所呈现的还要糟糕。Results 通常以相当高的 precision 呈现，仿佛那很有意义。例如，在 DeepSWE 上，我们可能会看到（举例来说）GPT-5.5-xhigh 比 Fable 5 medium 好 1%，但 cost 低 19%。然后，如果拿 Opus 4.8 来 compare，也许它比 GPT-5.5 xhigh 差 13%，cost 却高 11%。如果我们想知道这意味着什么，就可以深入查看 data，然后发现有个 benchmark 声称自己有意义，因为它有这么大一组 diverse tasks，但这些全是 run 4 次的 pass/fail tasks，而且大多数 tasks 要么非常简单，最好的 models 都能拿到 4/4（只是由于一些 random noise，有时会随机出现一个 3/4），要么非常难，大多拿到 0/4。于是，真正 determine 这些 SOTA models 的 relative scores 的，只是 tasks 中某个很小的 subset。如果把其中一个换成另一个，两个 scoring 最高的 models 之间的 results 就可能 flipped。如果换掉几个 tasks（总共大约 100 个），就能看到看起来差得多的 Opus 4.8 超过 GPT-5.5。再换几个 tasks，GLM-5.2 就可能领先。

看到这样的事情，我就会想起 Miguel Indurain。我小时候，他的名气大到家喻户晓，即使我不关注 cycling，也听说过他。几年前，我很好奇，为什么 Indurain 之后那些家喻户晓的 cycling 选手，都与 Indurain 属于不同的 archetypes，结果发现，答案是这很任意。出于一些任意的原因，Tour de France 成了世界上最著名的 cycling race，一个连续占据统治地位的人，可能因此出名到连 cycling 圈外的人都知道。又出于另外一些任意的原因，TdF 曾有一段时期的 time trial stages 比现在长得多，这很适合 Indurain 这种 archetype 的人。稍微 tweak 一下 benchmark，Miguel Indurain 就会从一个曾经家喻户晓的人，变成一位历史上伟大的 time trialist，除非关注 cycling，否则几乎没人听说过他。

回到 coding agents 的话题，我不清楚到底谁真的需要关注这些用 summary metrics 呈现 models 表现的 benchmarks。正如我们前面所说，作为 models 的用户，这些 benchmarks 并不能有意义地告诉我应该使用哪个 model。

如果许多其他用户根据这些 benchmarks 来做决定，那么 AI labs 就需要在意自己在这些 benchmarks 上的 results。但即使在 5.5 当家期间，GPT-5.5 在这些 benchmarks 的大多数上都轻松击败了各个 Opus 4.x models，在最好的 publicly available models 是 GPT-5.5 和 Opus 4.6/4.7/4.8 的那段时期，Anthropic 的业务增长仍比 OpenAI 快得多，以至于 OpenAI 一直在给公司提供免费的 tokens，试图说服人们使用 GPT。我所在的公司就是众多拿到数月免费 tokens 的公司之一，而在那段时期，大多数人仍主要使用 Claude 和 Opus。Anthropic 的 revenue trajectory 与这些 benchmarks 是 user choice 的主要 determinants 这一说法不相容，所以我不知道为什么有人真的应该在意这些 summary metrics 显示了什么。

我们刚才看的那组 graphs 显示了不同 tasks 之间有多大的 variance，但从此前那组 graphs 中，我们还看到了同一 model、同一 effort level 在同一 tasks 内部的大量 variance。如果只看少量 individual runs，那么由于 runs 之间的 variance，几乎可以得出任何 conclusion。例如，看看 Optimization 1，对于 GPT-5.5 xhigh，runs 之间的一个 standard deviation 是 0.075（即 7.5% 的 performance increase / decrease）。如果看 tested GPT 中最好和最差者的 average difference，两者分别是 1.055（GPT-5.4 xhigh caveman）和 0.986（GPT 5.4 mini low），这个差距小于 GPT-5.5 xhigh 的 1 standard deviation (SD)。下面是实际的 graphs，而不只是 summary statistics：

对于每个 task，不管最好的 condition 是什么，都很容易得到这样的 result：最好的 condition 实际 scores 比最差的 condition 的某次 result 还差。我和 Max Bittker 聊天时，他说了下面这番话；他经营一家 RL environment 创业公司，因此做过的 benchmarking 比我多得多：

> 是啊——不同 task 之间、不同 run 之间的 noise 水平如此之高，难怪最后的讨论会混乱不堪。很容易犯这样的错误：“哇，$new\_model 太棒了” -> “哎呀，我原来一直都在用旧的 model”，或者“这个新的 harness / prompting 技巧太好用了！”

还有一条评论，这次只能根据记忆大致转述，是 Matt Mullenweg 说的：如果观察那些从事 high variance 活动的人，比如赌徒，会发现他们往往很迷信。你会看到有人穿着自己的幸运袜，或者在坐下玩老虎机之前，先完成一套固定的仪式。使用 caveman mode，或者因为试了一下之后 coding agent 给出了一个好 result，就决定哪个 model 好，与此没有太大区别。

我在 Fable 发布之前做完了上述事情，也写好了这篇文章的初稿，然后 Fable 发布了，所以纯粹出于好奇，我 run 了几个 Fable benchmarks；在那个时候它还没发布，因此我也用 Opus 4.8 做了几次 runs。\[本文后来又在 5.6 发布后进行了编辑，在下面的 graphs 中加入了 5.6 benchmarks\]

就像前面说的，这些都是我每个花大约 15 秒给 agent 打字而创建的小 benchmarks。考虑到 coding agents 能让你 scale processes，你可以用每个只花 15 秒人工时间的方式，创建大量合理的 benchmarks，但这并不是什么经过精心设计、用于批量制作它们的 setup；我只是想得到某种 caveman mode comparison，才做了这些，而当我尝试让 agents 在没有 supervision 的情况下做这件事时，得到的 benchmarks 完全没有价值。稍微花一点时间之后，这些 benchmarks 看起来就足以用来 evaluating caveman mode，并确定它不值得进一步 investigation。如果当时我打算把这些写出来公开发表，我会再花几分钟，从多个方面改进这些 benchmarks，但我认为，用于这里关于 variance 的讨论，它们已经足够好了。我不会过度解读这些 reuslts，不过我确实做了一些 basic checks，例如查看 outlier results，确保 agents 没有 cheating，也没有某种 issue（例如 box 上的 noise）导致异常差的 runtime results；结果 agents 没有 cheating，最慢的 results 在 quiet box 上也确实能够 reproduce，等等。

抛开这番说明，就像 GPT benchmarks 一样，我们能在这些 benchmarks 中看到与网上讨论相呼应的 variance，例如，Fable 在一些 tasks 上很棒，在另一些 tasks 上却没那么好，而相当多的人正在根据自己尝试的一小组事情上的 performance，判断 Fable 的 overall performance。正如前面所说，OpenAI 在 DeepSWE 上比 Anthropic 表现更好（GPT-5.5 =~ Fable 5 > Opus 4.8），而我们也能在 Optimization 1 这个 benchmark 中看到类似的 result。另一个被广泛引用、不断有人转给我的 benchmark 是 Senior SWE-Bench，其中 Anthropic 比 OpenAI 表现更好（Fable 5 > Opus 4.8 > GPT-5.6 Sol），而我们也能在 Game AI benchmark 中看到类似的 result，其中是 Fable 5 > Opus 4.8 > GPT-5.6 Sol > GPT-5.5）。

前面我们讨论过，为什么我不清楚，我或任何一个具体的 agents 用户，究竟能怎样有效利用这些 benchmarks：它们给出一个 ranking，或者一小组 numbers 构成的 tuple，声称能告诉你一个 model 有多好。但即便深入查看某个 benchmark，我仍不清楚，作为用户，我为什么、又该如何根据这些 benchmarks 改变自己的行为。

举个例子，我观察到，Opus 4.8 为了解释事情而编造糟糕 rationalizations 的频率，比 GPT-5.5 高得多。我多次尝试让它们处理同一个 problem（我经常让两者都去 solve 一个我实际遇到的 problem，只是想看看会发生什么）。这些 problems 往往比这里的 benchmark problems 大得多，比如真正的 debugging tasks；或者在构建 game AI 时，不是用一个简单的 prompt 来 produce 一个 AI，而是通过 agentic loop 和/或一系列 instructions，让 agent produce 一个相当强的 AI。我问过几个人，他们在 GPT-5.x 与 Opus 4.6/4.7/4.8 上都观察到了同样的情况，包括那些更喜欢 Claude、主要使用 Claude，而且使用 Opus 的经验比 GPT 更多的人。

另一方面，我见过两个 measure models 在 detecting false information 和/或不 making things up 方面表现如何的 benchmarks，而这两个 benchmarks 都表明，Opus 在这方面远好于 GPT，甚至到了这样的程度：如果这些 benchmarks 展示的确实是人们可能预期它们展示的东西，那么我和其他人的亲身经历似乎就不可能发生。例如，在一个 benchmark 中，直观地阅读其 benchmark presentation，会得到这样的印象：Claude Opus 和 Sonnet 在 detecting false information 方面远好于任何其他 model，而 Opus 4.8 是绝对最好的，95% 的时候都能 detects false information，在 software 中也是 95%。GPTs 在这方面糟糕透顶，rank 低于 Qwen、Grok、Kimi、Minimax、Mimi 和 Nemotron。

这是怎么回事？我不确定。

也许那些 benchmarks 所 measuring 的 making things up 的方面，与我交谈过的人（以及我）在处理真实 programming problems 时遇到的不同；也许这是 small sample size，而我交谈过的人（以及我）只是碰巧在 Opus 身上接连运气不好；又或者，我们在使用 Opus 时“用错了方式”。我怀疑，实际情况是这些 benchmarks 所 measuring 的东西，与 coding 或 debugging 时遇到 incorrect rationalizations 的情况不同，但要对此有任何把握，我就得 run 一些相当昂贵的 experiments。如果你想支持我开展各种 experiments，可以[订阅我的 Patreon](https://www.patreon.com/danluu)，或者，如果你在 AI lab 工作，也可以给我一些免费的 credits，用来 run experiments。

顺便说一句，这里的 Game AI benchmark 中也有类似的情况：Opus 明显好于 GPT，但当我尝试管理创建一个真正强大（superhuman）的 game AI 的过程时，GPT 似乎表现更好，因为 Opus 总是陷入 making things up / rationalizing nonsense 的 failure mode。没有 supervision 时，两者都毫无用处，而且各有自己的 failure modes；但在有人指引时，GPT 只需更少的督促，就能保持方向，继续做可能有效的事情。这在那个小型 Game AI benchmark 中完全没有体现：其中一次 xhigh run 就是一个 single prompt，“只”花费 \$10 左右，而这个小型 benchmark 得出的 result，与我们实际完成这个 task 时看到的恰好相反。

但这里的重点是，即便你找到了 measure 的东西似乎正是你所关心的 benchmarks，那些 benchmarks 最终也往往无法 matching 你在实践中看到的情况。如果你像我一样是个怪人，也许会决定花上大量时间和/或金钱，run 一些 experiments，弄清楚究竟怎么回事；但如果你只是有件工作想完成（也许就是你的本职工作），那这样做就相当不合理了。

顺便说一句，这些 benchmarks 中有些 patterns，常常让人觉得违反直觉。与依据 publicly available benchmarks 讨论哪个 model 更好不同（那种讨论毫无意义），我确实觉得这些 patterns 有些意思，也能提供一些信息。我们上面已经指出，有些 benchmarks 中 GPT-5.4 outperforms 5.5。我们也能看到，更多 effort 既可能让 results 变好，也可能让它们变差。例如，在 Optimization 1 中，GPT-5.6 Luna 随着 effort 增加而变得 monotonically worse，在 Optimization 2 中也总体变差，但在 Game AI 中，它却随着 effort 增加而 monotonically improves。我们还可以看到，对于 GPT-5.6 Sol，在 Optimization 1 和 Game AI 中，max 表现比 xhigh 更差。对于 GPT-5.6 Sol，ultra 在全部三个 benchmarks 中都好于 max，而且在 Optimization 1 和 Game AI 中实际上还比 max 更便宜。即使在同一个 provider 或同一个 model 内，人们直觉上会预期的许多事情（例如更多 effort 带来更好的 results）也并不成立。再加上我们在不同 providers 之间看到的更大 differences，results 就呈现出极高程度的 heterogeneity，使得诸如 X is better than Y 这样的简单陈述通常都是错的，除非 models 之间的 capability 存在非常大的 difference。但如上所述，我们无需 cherry picking，就能轻易找到 Anthropic 的上一代 model outperforms OpenAI 的当代 model 的情况，反过来也一样。

我看到人们拿这些 benchmarks 说事时，它们往往只是被用来支持某个人的迷信观念。例如，在工作中，我见过有人引用 Senior SWE-Bench 的 result，即 Fable 5 > Opus 4.8 > GPT-5.6 Sol，说这符合实际（说这话的人相信 Anthropic 远远领先于 OpenAI）。当然，别人也完全可以同样轻易地引用 DeepSWE，而它展示的是相反的情况。

在这些事情上，所有我信任其判断的人都觉得这些 benchmarks 相当不靠谱，因为对于一个充分使用过这些东西的人来说，认为如今 Anthropic 的上一代 model 总体上好于 OpenAI 的当代 model，或反过来，都实在经不起常识检验。我问过一些我信任、在 AI labs 之外工作的人，他们如何形成对一个 model 好坏的印象；通常，他们只是凭感觉，再收集其他同样凭感觉的人的印象，因为显然，这些 benchmark results 并不能比直接 eyeballing 更好地说明实际情况。

### Benchmarking 与 data analysis（基准测评与数据分析）

没什么特别的原因，我一直喜欢 designing experiments 和 measuring 各种东西。早在我考虑职业之前很久就是如此，直到今天仍然如此。[正如这里讨论的](https://danluu.com/why-benchmark/)，measurement 是这个博客的主要主题之一，也许就是最主要的主题。幸运的是，我得以把这个终身爱好变成职业。更幸运的是，coding agents 似乎让这项技能的相对价值变得更高了[3](https://danluu.com/ai-coding/#fn:C)。

正如我们上面讨论的，testing 是 highly agentic workflows 中的一个 rate-limiting factor，因为当你让 agents 开始做大量事情时，任何没有经过充分 tested 的东西都会被 stochastically degraded。你通过 agents 进行 ship 的东西越多，情况就越糟。如果你所做的一切都像这些 model evals 中的某一个，每个 task 都是 pass/fail task，除了不把 task 做错之外，根本没有办法做得更好，那么你只需确保 tests 足够好，然后让 agents 放手去干，直到 tests pass，一切就都很好。在实践中，对于几乎所有 non-contrived problems，都可能有一个 solution，虽然 passes 一个 strict correctness eval，却仍然在某种 non-strict correctness 意义上有好坏之分。如果你想让 agents 在一个 problem 上放手去干（无论是随意快速的 vibe coding，还是 running autonomous agentic loops），那么现在你就有了一个 benchmarking problem。

如果任由 agents 自行其是，在 self-improving loops 中 running，它们似乎相当不擅长这件事。过去几个月，我一直在尝试各种小办法，取得了一些 improvement（让许多 agents independently 思考，再混入 contrarian agents，经过 multiple iterations 重新聚在一起讨论，等等），但如果没有 human intervention，它们似乎仍然不太行。

一个原因似乎是，agents 真的很不擅长 understanding data 和 doing data analysis。在某种 agentic loop 或 large problem 的背景下做这件事，比做 standalone data analysis 更难；但即使人们只是让一个 agent 做 standalone data analysis，没有大量指导，results 通常也糟糕透顶。因为让 agent 做 data analysis 实在太容易，我见过不少由 agent 主导的 analyses，至少到目前为止，我见到的每一个都完全不靠谱。我自己也做过不少（我认为，人们实在低估了从 LLM 得到完全不靠谱的 output 的价值；稍后再谈），发现的情况也一样。

我说完全不靠谱，指的是诸如此类的事情：找出实际上并无关联的不同 numbers，却不知怎么就从它们的 relationship 中 inferring 出某种深刻结论；从众多 numbers 或 examples 中挑出两个，提出一个与 data 中其他 numbers 相矛盾的 theory；制作展示毫无意义的东西（但往往看起来很漂亮）的 plots，等等。随便举一个具体例子，上一次我查看一个 agent 生成的 analysis 时（写这篇文章时，我瞥了一眼），有人让一个 agent analyze 某个东西的 resource utilization。用的是 max 下的 Opus 4.8（Fable 被 disabled 了，所以这是当时花钱能买到的 Anthropic 最好的东西），agent 判定某个 task consumed 了 514% 的 resources，而在那个场景下，无论如何都不可能 consumed 超过 100% 的 resources。我有一位同事有时会评论这些东西，问些无伤大雅的问题，比如“X 是什么意思？”。通常，他要么得不到回应，要么得到一段看起来像 AI 写的回应，而它与他最初回复的那段内容一样 incorrect。

总之，当我开始使用 agents 做 data analysis 时，大概是 2025 年 11 月，我发现这种 speedup 相当惊人。有些 analyses，粗略来说，原本需要几周，现在只需几小时。

接下来这件我一直在做的事，我甚至有些犹豫要不要描述，因为我已经看到太多完全不靠谱的 data analyses。但我经常做的一件事是 run 一个简单的 agentic loop，让 agent（或 agents）“understand”并 analyze problem，然后由我修正那些需要修正的部分，从 agent 产出的东西中提取一个好的 analysis。我发现，这比做一个“普通的 vibe coded data analysis”带来的 speedup 要大得多。

这个不靠谱的 LLM loop 能带来多大 speedup，取决于 problem；但上一次尝试时，我认为，按照传统的 pre-LLM 方式 analysis 那个 issue，会花掉我好几天。就算两天吧。如果采用一种我一边 multitasking、一边在 LLM 需要督促时推它一把的 workflow，我猜会在一两天里花掉我一到三小时。而使用这种“让 LLM loop，不断 producing 一个我明知会错的 result”的 workflow，在几天里只花了我大约五分钟，就得到了一个可以接受的 result。毫不夸张地说，每次我查看 analysis 中任何此前没有 corrected 过的部分，analysis 都是错的（而且有时我还得多次作出 corrections）；但不知怎么，整个过程仍然比我设法引导 LLM 快得多。

我认为，人们实在低估了从 LLM 得到完全 incorrect results 的价值。只要指引得当，这确实能带来积极的根本性改变，我并不是在说反话。

SOTA models 在 data analysis 上糟糕得令人难以置信，却又能大幅 speed up 人类的 data analysis，这种反差有些奇怪。我有这么一系列关于 benchmarking、evals 和 experimental design 的 exercises（[第 1 部分](https://www.patreon.com/posts/107155602)、[第 2 部分](https://www.patreon.com/posts/109004070)、[第 3 部分](https://www.patreon.com/posts/118646029)、[第 4 部分](https://www.patreon.com/posts/127627543)、[第 5 部分](https://www.patreon.com/posts/149123122)、[第 6 部分](https://www.patreon.com/posts/160473058)）。GPT-o3 发布时，Tyler Cowen 说 o3

> 几乎在所有方面都把人类打得落花流水……如果你不愿称它为 AGI，我并不介意。而且，是的，它并不是样样都对，也有一些办法可以骗过它，通常只需一些（对人类来说）相当简单的问题。但我们别再对眼前发生的事情自欺欺人了。在极其广泛的 topics 和 methods 上，它都把人类打得落花流水。是时候坦率地承认这一点了。

这促使我尝试把这些 exercises 中的 questions 提给 SOTA models。它们的表现通常 underperform 我对一位合格的初级同事的预期，除非你专门调整 question 的措辞，让 models 能够 answer 这些 questions。如果你只是按照现实中向一位合格的人类同事提问的方式来问，它们通常表现不佳。这不只是有人提出 evals homework question 时才会出现的 theoretical problem。只要你让 agent 执行某种 empirical、open ended、longer horizon improvement task，这个问题就会出现。

我见过这个问题出现在各种 real world problems 中，但即使是几乎不具有 real world problems 那种复杂杂乱之处的 contrived problems，也会出现这个问题。我认为 building board game AIs 就是一个不错的例子。这个 problem 比大多数 real-world problems 更容易 evaluate，因为归根结底，你想要的是在一个 well-defined game 中 beat humans 和其他 AIs，而这个 game 有简单的 win/loss/draw result。

如果让 Agents 自行其是，它们其实弄不清该怎么做。公平地说，这个 problem 比网上评论者认为的要难一些。例如，如果你只是 search 关于如何 implement 这些东西的资料，就会看到各种[像这样](https://news.ycombinator.com/item?id=34802039)[或这样](https://news.ycombinator.com/item?id=20034115)的交流：没做过的人会解释为什么这很简单，做过的人则会告诉他们，这比他们想象的更难。大多数 online tutorials 都不太有用，以至于[广受好评的 bullet library 的作者建议 beginners 不要去看](https://github.com/jw1912/bullet/blob/main/docs/1-basics.md)“$$a$$lmost 所有关于 \[a board game AI technique\] 的 article/blogpost/book，只要作者没有自己的强大 \[board game AI\] 作为支撑”。虽然这个 problem 算不上特别难，但其中的 pitfalls 似乎足以绊倒大多数人（以及所有 publicly avialable LLMs）。

我刚开始尝试 implement 一个 board game AI 时（那还是 GPT-5.1 到 5.2 的时候），对 board game AIs 一无所知，于是尝试让 coding agents implement 它们认为可行的方案。现在我对 board game AIs 有了一点了解，可以说 GPT 当时试图建议的每个方向都很糟糕，而且行不通。作为一次 experiment，我最近又试了一遍，当时 GPT-5.5 和 Opus 4.8 是最好的 publicly available models，而它们以完全相同的方式 failed，还提出了许多完全相同的糟糕想法（为了真正确认，我让它们 implement 了那些糟糕想法，结果它们果然如预期般 failed）。Fable 可用之后，我也用 Fable 试了这件事，它同样以完全相同的方式 failed。Fable 在实践中更好，因为经过 15-20 次 corrections 后，它能够在 autonomous loop 中 work effectively，而 Opus 4.8 和 GPT-5.5 做不到。顺便说一句，这又是 public benchmarks 无法 capture 的一类事情的例子。

不过，回到 LLMs 在没有 guidance 的情况下 iterating 这个话题，我认为在某种程度上，这是如今 LLMs 中一个已被相当充分认识到的 gap。巧合的是，就在我尝试用 GPT-5.1 或 5.2 做这件事的前后，[Code Clash](https://codeclash.ai/) eval 被创建了，它也 tests 同样的事情，并得出了同样的 result

> 无法 Iterate：Models 难以在 rounds 之间 improve，并 exhibiting 各种 failure modes。

尽管 agents 极不擅长 setting direction，而我对 board game AIs 一无所知，我还是不知怎么地，用 GPT-5.1/5.2 花了自己大约 5 hours 的时间，拼出了[一个用于 Azul 的 superhuman AI](https://danluu.com/game/tile/)，又在总计投入自己大约 20 hours 的时间后，把它提升到了具有压倒性实力的水平，远远超过当时已有的任何其他 AI（我认为现在依然如此）。Azul world champion、也可能是综合实力世界最强的 player 说：

> 这个 bot 现在相当离谱。肯定看起来比我更强，不过要真正 test 它，我得像玩 turn-based game 那样与它对局。在我这边时间有限的情况下，我毫无胜算 🙂[4](https://danluu.com/ai-coding/#fn:B)。

虽然我很想说这其中有“一个奇招”，但实际上有两个；不过两个也不算多，尤其是它们还能 generalize 到其他种类的 projects。这两个技巧是：

-   查看 data / 准备一些还算合理的 evals
-   进行 Solve problems systematically

这些都不必非常 rigorous。事实上，我会说，这一切全凭感觉在推进（这里用的是 vibe coding 出现之前的词义）。在 data 方面，这个 project 中我采用了自己常用的习惯：对一堆看起来相关的东西进行 plotting，用眼睛观察，再朝着我希望能 improves things 的方向做些微调。一个更 rigorous（也可能更好）的 approach，是从头 run 一堆 experiments，进行添加或移除单个想法的“ablation” runs，等等，从而理解每个 component 做什么、有什么 impact。但我想尽可能少花自己的时间，仅在自己的 laptop 上 training，就得到一个强大的 AI；在这些 constraints 下，以 rigorous 的方式做事似乎代价太高。

我确信，对有 ML experience 的人来说，这一切本来都会很简单，但有一堆细节需要我先 observe，再想办法处理（这正是 agents 目前极不擅长的事情）。例如，在确定该查看哪一组好的 evals 时，就有几件有趣的事。其一，你很容易做出能够 reduce [loss](https://en.wikipedia.org/wiki/Loss_function)、却不 change 对 actual opponents（humans 或其他 bots）的 win rate 的 changes，反过来也一样。其二，如果你试图依据自己的 bot beat 自身 previous versions 的程度来 track improvement，就很容易做出一系列 changes，让 bot beat 自身所有 previous versions，相对于 prior versions 获得表面上 1000 或 2000 的 Elo gain，却在面对 humans 或以不同 style 对局的 bots 时毫无改善。而且，当时并没有可供对局的 superhuman bot，因此你无法仅靠与一众 existing bots 对局就得到合理的 eval。

对人类来说，这些其实不是难题。一个合格的人可以查看其中一个问题，想几分钟，然后提出一个很可能可行的 proposed solution（如果不可行，还可以尝试另一个 solution）。但其中的微妙之处，已经足以让如今的 agents 在没有 supervision 时表现不佳（公平地说，许多或大多数人类也一样——我找到的可供对局的 bots 几乎都相当差，尽管人们似乎在其中许多 bot 上投入了不少时间；唯一 publicly available 的例外，是 [https://github.com/cestpasphoto/alpha-zero-general](https://github.com/cestpasphoto/alpha-zero-general) 中的“PJF98” Azul bot）。曾有一个比 PJF98 bot 更强的 bot，[但它并未普遍开放供人对局，只被用来赢下 BGA 的一个 season（由于使用 bot 属于 cheating，该成绩被作废）](https://www.youtube.com/watch?v=qkzpeXGwE-4)，之后就再也没有出现过。

我提到的另一个技巧，是采用 systematic approach。从总体上说，这是因为当你处理一个具有一定 complexity 的 opaque system 时，每当你看到某个 bug 的 symptom，它很可能就是一个窗口，让你窥见一个或多个你还不知道如何 observe 的其他 bugs。如果你 non-systematically 地关闭这个窗口，却没有 fixing 其他 bugs，那些其他 bugs 仍然存在；你只是再也不知道该如何 find 它们了。

在 building 一个使用 neural net 的 board game AI 时，情况就是如此：这个 net 在做着谁也说不清的事，某种 search function 也在做着谁也说不清的事，而你有时能发现某些具体且明显糟糕的 moves。vibe coding 和/或 agentic loops 通常也是如此，因为 agents 在做着谁也说不清的事，而它们 produce 的那一大堆过度 complex 的 code 会 emit 某种明显糟糕的 behavior，让你有时得以窥见哪里出了问题。

具体到 board games，我看了看已有的其他 Azul AIs。很多人都 built 了 bots，尤其是最近，coding agents 让 build 一个 bot 变得如此容易。对于其中一些，你实际上可以看到那个人是如何尝试引导 bot 的（例如，因为他们把给 Claude 的 instructions 放进了 repo）。据我所知，这些其他 bots 在花费了更多人类时间的情况下却差得多，主要是因为同时存在两个问题：使用了错误的 evals，以及 fixing 的是 problem 的 symptom 而不是 cause。

例如，有一位作者把 Claude instructions 留在了 repo 中，所以你可以看到他们做了什么。在某个时候，他们的 bot 做出了一个非常糟糕的 move，比任何刚学会这个 game 的人会做出的 move 还差。作者 instructed Claude 做一系列 straightforward fixes，以阻止 bot 再做出那个 move，Claude 也确实做到了；但这并没有 fix 由 bot 的 systemic problems 导致的所有其他 bad moves，只是 fixed 了作者能看到的那个非常明显的 bad move symptom。

我的 bot 也有过一个大致 analogous 的 issue：有一阵子，它几乎总是试图 open 在 column 2。我认为一个可能有效的 simple fix，是 tweak 这个 bot，让它少一些 play 在 column 2。我尝试了各种“显而易见”的 fixes，例如 increasing noise 来 increase self play 中的 exploration，等等；但除了直接 reducing column 2 的 value 之外，所有显而易见的 fixes 都没有奏效，而那又存在我们讨论过的另一个问题：并没有真正 solving the problem。在那个具体案例中，一个确实奏效、并让 bot 的 play 更普遍 robust 的更 systematic fix，是在 game 的不同阶段，将 game fork 成具有不同 column permutations 的新 game。这里的思路是，problem 在于，on average，column 2 是最好的 column，因此即使 bot opens 在不同的 column，由于它过去见过的 games，它也会倾向于回到那个 average best column。如果你是 DeepMind，可以往这个 problem 上砸一大笔钱，让 bot play 多得多的 games，并 learn 别的东西。但如果你是在 laptop 上 running，这可能要花上一段时间；而且，如果你试图 tweak 用来引导 bot 远离 column 2 的 weight，你不可能得到一组 reasonably optimal weights 来做这件事。但如果你（例如）有时在接近 endgame 时，将 column 2 permute 到 column 4，bot 就会 learn：如果有一个 nearly filled column 4，那么 complete 它就是 winning move。这会帮助 bot learn，在 game 更早的阶段，如果有一个 partially complete column 4，将它推进到 near completion 是合理的，如此层层递推，直到在 opening 时，bot learns 它应该以合理的 distribution 来 open。

对于像我这样没有 ML/AI background 的人来说，让 bot 达到 superhuman performance，就是解开一系列这样的谜题：既要弄清采用什么恰当的 data view 才能看见 problems，又要 systematically 地 tweaking，以 solve the problem。这与 managing 用于一般 problems 的 agentic loops 没有太大区别。Michael Malis 说过，running 一个“software factories” workflow 感觉像是在玩 Factorio，我能理解他的意思。

### 杂谈

我不确定讨论具体的 workflow 技巧有多少价值，因为这些技巧的 half-life 太短了。在我开始运行更 autonomous 的 loops、还在做更多 human-in-the loop 工作的时候，“我的” agents 经常会做出直接违背 AGENTS.md 或其他 instructions 的事情。我随口向 Yossi Kreinin 提起这件事时，他建议在我的 AGENTS.md 底部加一条说明，要求在 compaction 后重新阅读 instruction。说不定这只是毫无作用的迷信行为，但它似乎把这个问题的发生 rate 从每天几次（同时照看几个 agents，所以可能每几个 agent-days 一次）降到了每一两周一次（可能每 100 agent-days 左右一次）。现在似乎已经不需要这样做了，所以，要么这从一开始就是毫无作用的 placebo，只是我有一阵子运气不好；要么 AI labs 也加入了这项措施。在 LLMs 默认只会 produce code、不会 run 它的时候，[我们在 2024 年 8 月讨论过](https://danluu.com/codenames/#appendix-writing-the-code-for-the-post)一个技巧：只需设置一个 loop 来 runs the code，确保它 works 并且 passes tests。考虑到这个技巧如此显而易见、如此有用，它的有效寿命长得令人意外；不过，大型 AI labs 最终当然也意识到了它有多有用，现在它们都有能做这件事的 tools。

过去几个月里，我用的“技巧”是弄一个大致与 Gas Town 这类东西处于同一领域的东西，但加入各种小措施，尝试让它更 reliable。Claude 的 Dynamic Workflows 似乎把这些技巧中的一半放进了一个易用的 package（我还没用过，因为听说它采用 waterfall model，一个 stage 的事情要等待上一个 stage，不过这个问题要么迟早会被修复，要么会有人发布没有这个 limitation 的东西）；Codex 也宣传了一些尚未发布的 features，看起来目标也是做同样的事情。原则上，goal mode 应该能把另一半技巧中的大部分 package 起来，尽管它目前的效果远没有那么好（除了有时会因为 bug 而 failing，它在 pursuing the goal 方面似乎不如手写的 loop，而且还真的可能偏离方向；Dennis Snell 提到，他让一个自己以为很小的 task 在 goal mode 下运行，后来发现，据 codex 所说，它花掉了本来相当于 $60M in tokens in a few days had his employer not been on an unlimited token deal; on asking again, it then said $200k 的费用）。想必这些东西会改进，而我现在所做的大部分事情，几个月内就会有现成可用的东西？和上面提到的技巧一样，这些事情都太显而易见了，我不知道花很多时间讨论细节有多大价值，不过我会在[后面的 appendix 中放一些简短说明](https://danluu.com/ai-coding/#appendix-agentic-loops-and-writing-this-post)，以备有人好奇。

上面讨论的 meta techniques 对我来说，在各种 projects 上都 generalized 得相当好；只要 agents 还不能仅凭一个 non-trivial problem description，就比我更好地 fully solve the problem，这些技巧似乎就应该能持续有效。等到了那一步，我也就不用操心了，因为我的 economic value 可能已经接近零。

另一个有用的 meta idea，是一个非常显而易见的想法：coding agents 相对于人类的 effectiveness 是高度 non-uniform 的。在讨论 traditional productivity 时，[Fabian Giesen 曾这样评论 velocity improvements 如何改变他的工作方式](https://danluu.com/productivity-velocity/)：

> 当你跨过某些 thresholds 时，就会发生“phase changes”（细节在一定程度上取决于 problem），你的整个工作方式都会改变。……有很多事情，我理论上可以用任何速度去做，但实际上不行，因为随着 iteration time 增加，一开始它会变得令人沮丧，以至于我无法坚持做太久；最后耗时长到它真的会从我的 short-term memory 中消失，于是我必须记笔记或用其他方式整理，否则就根本做不了。当然，如果我能在 interactive UI 中通过拖动 slider 做一个 experiment，并在不到一秒内看到 result，那么这时基本就是“不过脑子”：想试什么就直接试。一旦 iteration times 达到几秒的量级（比如 statically compiled lang 的一个 compile-link cycle），你就不再只是随便尝试，也会花时间思考这次尝试能不能告诉你什么，因为它耗时已经长到让你不愿白白浪费一次 run。一旦 iteration times 达到几分钟或几个小时，你就需要做很多规划，以免浪费 runs；还会有 context switching，因为等待时你会做其他事情；也需要记笔记、做记录。而且在这个层面，犯错的代价更高（因为浪费一次 run 就会浪费更多时间），也更常见（因为你的注意力被分散得很厉害）。再继续 scale 下去，你可能会在一段不可忽略的时间里占用大量 resources，需要获得批准并安排 budget，这本身又需要开会等等。agentic coding 的 velocity improvements 也有类似的情况。人们有时声称 agentic coding 的 [productive 程度提高了 100x 或 1000x](https://www.patreon.com/posts/160473058)。看我自己做的 tasks，很难真正确定一个数字，因为你无法有效地把人类的 workflow 原封不动搬给 agents，所以我做的事情与我原本会做的事情非常不同。比如，看看上面讨论过的那个想法：让 agents 查看每一张 support ticket，把 support issues 转成 PRs。如果我要声称这里存在某种 speedup，那会是一个巨大的数字，轻轻松松超过 1000000x。但我当然不会自己阅读每一张 support ticket，所以这种说法没有意义。更合理的 estimate 方法，是尝试弄清楚什么样的 traditional organizational structure 才能用 classical techniques 产生那么多 bug fixes，然后 estimate 这个 ratio；但这种 estimate 的 error bars 会超过一个 order of magnitude，而且任何正常的 software company 本来也不会这么做，所以这种 comparison 又一次没有意义。这就像一个每年开车 20000 miles 的人说，开车让他通勤节省了 6000 hours，获得了 15x 的 speedup，因为走完同样的距离需要那么久。显然，开车使他能够做原本做不到的事情，但讨论这个 ratio 没有意义。

还有一个例子，你可以声称获得了巨大的 speedup，可能超过 1000000x，但这个数字没有意义：在尝试让 LLM 以 semi-automated 方式 generate a fuzzer 时，我试过让 LLM 查看整个 commit history 和所有 bug fixes，以及历史上每一张可能相关的 support ticket，尝试让 LLM-written fuzzer 能以某种 general 的方式 reproduce the bugs。这样做似乎是有用的，但很难给它的价值标出一个实在的数字。

对我来说，LLMs 的实际价值在于，很多原本太耗时、因而不值得去做的 tasks，现在都能相当轻松地完成。我在一个 footnote 中提到，现在有很多 apps 都可以轻松 build，所以我有时会在一个 custom app 上玩 online board games，它提供的体验比我能在任何主要 board game platforms 上获得的都更好（也比通常为某个 board game 专门做的 app 更好）。

对于那些我主要为满足好奇心而做、但也可能与业务有些关系的事情，我也会做一些以前觉得不太值得花时间的 data analyses。比如，我一直很好奇 user-experienced bugs 与 support tickets 的 ratio。有了 coding agents，我只花了几分钟，就让 agents 列出了 major incidents：我们知道，在这些 incidents 中，每个尝试 access the site 或 use a feature 的 user 都无法 use the feature 或 site；同时，还列出了看起来与每个 incident 相关的 tickets。对这些 data 进行 joining 后，典型的 ratio 是每张 ticket 对应 200 个 impacted users，ratio 经常在 100:1 到 1000:1 之间（而且我确信，如果纳入更多 incidents，还会发现更宽的 range）。顺便说一句，我 pre-registered 的猜测是 100:1 到 1000:1，更倾向于 1000:1，所以我在这里猜得有些偏，因为典型的 200:1 更接近 100:1，而不是 1000:1。

当然，这个 analysis 有很多漏洞。无法确定没有遗漏的 tickets（我确实通过与 bug tracker 中被手动 tagged 为与某个 incident 相关的 tickets 进行独立 cross-checking，检查了 false negatives；主要发现是，agents 能找到的 tickets 比人类找到的多得多，但这并不意味着不存在同时逃过人类和 agents 的 false negatives）。我也 randomly sampled 了几张 tickets，看看关联的 tickets 是否合理，它们看起来是合理的；不过，这只是一次快速的 order-of-magnitude analysis，所以我没有 manually inspect 足够多的 tickets，无法真正 validate 一个 high precision analysis。

对于 less severe issues，这个 ratio 会如何变化，也不清楚。一般来说，less severe issues 的 ratio 应该更高，投入较少的 users 也是如此（比如 sign-up flow 中的典型 user）。我的猜测是，对于许多 less severe issues，我们通常会看到远高于 1000:1 的 ratios；对于许多 subtle issues，这个 ratio 很容易超过 10000:1，甚至超过 100000:1。

这个 analysis 无法让我说出太 precise 的结论，但当有人因为一个 issue 有六张 tickets，就说“只有六个 users 受到了 impacted”时，它确实能用来回应。这通常意味着，有一张 internal bug tracker ticket，有人给它附上了六张 support tickets。使用 agent search 相关 tickets 后，你可能会找到二十五张 tickets；然后，根据 issue severity，你可能会 estimate 出 10000:1 的 ratio，于是“只有六个 users 受到了 impacted”，就可能变成“至少 5000 个 users 受到了 impacted 的可能性极高，而 25000 个 users 受到了 impacted 也说得通，甚至很可能如此”。

如果我原本就熟悉这个 analysis 需要 query 的每个 system，我估计，要得到一个 rough guess 也会花上几个小时，而且猜测还会更粗略。但考虑到我并不熟悉，我猜这本来会花上几天。结果，这只花了我大约 15 分钟。正如 Fabian 所说，这类 speedup，让原本需要几个小时或几天才能完成的 app 或 analysis 变得轻松可做，是一种真正改变工作方式的 phase change；这还没算上那些只需要偶尔 maintenance 的 autonomous loops。

另一个想法——而且我事先并没有料到会这样——是，对于那些对自己想做的事情相对更 expert 的人，LLMs 似乎是更大的 productivity multiplier。我到处寻找相关评论时，当然先看到了一页又一页 LLM generated SEO spam；费劲翻过这些内容后，我看到了不少表达相反观点的评论。基本意思是，现在任何人都能做任何事。虽然这比过去更接近事实，但某个领域的 expertise 变得更有价值，似乎是一个更确切的事实。Max Bittker 有一条评论说，这至少部分是因为 LLMs 很擅长 counterfeiting，但 counterfeits 还没有那么好（暂时？），而 experts 能分辨 counterfeit 和真东西，我觉得这是一个有意思的 framing。

接着[这篇 2015 年关于许多人如何低估 AI 将在多大程度上 displace humans 的文章](https://danluu.com/customer-service/)往下说，在过去一年里，我的 LLM-driven remote customer service interaction 的 median，比我的 human remote customer service interaction 的 median 更好（薪酬优厚的人类客服提供的体验，会好于我经历过的几乎所有 LLM-driven 体验，也许只有一次例外，但公司不想雇用薪酬优厚的人类客服）。那篇 2015 年文章中反驳过的完全相同的论证思路，[在 2022 年 ChatGPT 发布时又被重复了一遍](https://mastodon.social/@danluu/109458271351706514)。这套论证思路如此受欢迎，以至于自 2022 年以来，每年都会成为思想领袖们反复传播的爆款；我看不出这种情况会很快改变，但直到今天，我仍觉得它是错的。

顺便说一句，[正如我们之前讨论过的](https://danluu.com/learn-what/)，成为 effective programmer 的方式有很多，所以我并不是说这里讨论的是最好的做事方式，甚至也不是说它是很好的方式（随着我弄明白新的东西，我也在经常改变自己的 workflow）；不过，这是我一直在尝试的做法，对我而言，它似乎比纯粹的 traditional workflow 更有效。考虑到我的背景和兴趣，我很自然地会对 agentic coding 采取 systematic、evals-driven 的 approach。我也见过有人采用几乎完全相反的 approach，并同样让它对自己奏效：他们几乎不理解正在发生什么，却推进得非常快，一旦找到有价值的东西，就会 recursively 将全部精力投入其中。这不仅不太适合我的背景，我也不觉得它会对我处理过的大多数 problems 真正奏效；我之所以选择这些 problems，就是因为它们似乎比较适合我处理 problems 的方式。毫无疑问，如果把我的 workflow 搬到适合那种相反 workflow 的 problems 上，它也不会很有效。

### 附录：人们各说各话

人们意见不一致时各说各话，这种情况一直存在，但在今天讨论 agentic coding 时，这个问题似乎比讨论许多其他话题时更加突出。

我见过的一些主要原因是：

-   普遍的不相信
-   基于 Workflow 的 reliability 差异
-   一般的 workflow 问题，也就是“skill issue”
-   预期的差异

说到普遍的不相信，我看到有人说 X 是 impossible，没人做 X，任何声称自己在做 X 的人都是骗子；但我认识的人（我信任他们，他们也可信）就在做 X，或者我自己就在做 X。这种情况比我人生中任何其他时候都更多。人们对 AI 有大量的不相信。十一年前，[我们看过，即使 AI 已经在 replace 或 displace humans，人们仍然在说这绝不可能发生](https://danluu.com/customer-service/)；但当时那种 displacement 并不是普通中产阶级人士或 programmer 会认真担忧的事，所以对我可能在“街头”遇到的人来说，它并不像今天这样引人关注。如今，这件事对我遇到的人而言更加“近在眼前”，否认现实的情况也随之猛增。

顺便说一句，我觉得许多人不相信是相当合理的。首先，许多关于 AI 的正面说法都是 incorrect。平均而言，夸张而 incorrect 的说法，比枯燥但 precise 且 correct 的说法更容易引起关注，所以不关注这些事情的人，会看到许多很容易驳斥的 incorrect 说法。更糟的是，发表这些说法的许多人，都与 AI companies 的整体成功有直接的经济利益关系，这让怀疑者很容易认定这些人全是自私自利的骗子。

说到基于 workflow 的 reliability 差异，我的意思是，不同的 workflows 要求不同程度的 reliability，而使用要求更高 reliability 的 workflow 的人，常常会因为 AI 达不到 X reliability 就声称它毫无用处，却忽略了许多有效用途并不要求那种程度的 reliability。举一个极端的例子，有人已经利用 AI 做出了 novel mathematical research，并 solved open problems。假设你每尝试 100 次，AI 就有 1 次 solves 你正在研究的某个 open problem，另外 100 次中的 99 次则 returns 完全不知所云的内容。这似乎很棒。在 math research 中，100 次里有 1 次 Solving 一个重大的 open problem，是相当了不起的 result；即便 100 次里只有 1 次做出合理的 code review，而 100 次里有 99 次 producing 糟糕的 code review，会是糟糕的 result。

举一个不那么极端的例子，在 programming work 中，如果你不 assume agent 是 100% reliable，并 build systems 来处理这一点，那么，相比那些 assume agent 是 reliable、需要某种 human-in-the-loop correction 来处理 agent 不 reliable 的情况的人，你可以 tolerate 低得多的 reliability。我经常看到有人建议说：“不要用 AI 做 X \[因为它不会在 100% 的时候 work\]”，但我知道有人一直在做 X，而且有某种平淡无奇的 system 来处理 X 并非 100% reliable 的情况。无论你是否在与 agents 打交道，这都是 programming 中经常需要做的事，那么为什么不使用同样的 techniques 来处理 agents 不 reliable 的情况呢？

scale 的差异也会让人们各说各话，因为人们在不同 scales 下对 reliability 的要求截然不同。有一条老经验法则说，对于 traditional software systems，scale 每增加一个 order of magnitude，你就需要不同的 architecture。这其实并不准确，但它表达了一个方向上正确的想法：在不同 scales 下，你确实会想要不同的 architectures。使用 agents 时也是如此。

举个例子，我反复看到的一种情况，与前面提到的事情有关：在我做的 tasks 中，即使在 AGENTS.md 里添加明确、严格的 instruction，要求不要做某件事，在同时应付 10 个 agents 时，每一两周仍会 fails 一次，failure rate 大约是每 100 rule-agent-days 一次。这有用吗？如果你在做 human-in-the-loop coding，agents 和 rule 的数量相对较少（比如 10 个 agents、10 条 rules），而 failures 都是 non-catastrophic 的事情，通常会被 human review caught，那么这很管用。如果你在 running 数百或数千个 agents，或者即使只有几个 agents，却在没有 review 或其他 guardrails 的情况下 shipping，而且 failures 可能造成严重问题，那么这就完全不管用。虽然有些 techniques 是 scale invariant，但许多并不是。

另一类 workflow 问题是，有人的 workflow 无法用于 X，于是就因为自己没能做成 X，而断定没有人能做成 X。对于具体哪些做法行不通，我没有想得太多，不过 Max Bittker 有如下评论：

> 我注意到的几个 patterns，排名不分先后：
> 
> 1) 人们有时使用的是 misconfigured environments：他们用着旧 model，开启了一堆 MCPs 或 after-market system prompts，或者 LLM 正试图应付 Windows、某种不常见的 environment 或 IDE。
> 
> 2) 人们有时会使用一个极长、充满 backtracking 的 chat，或者一个极其混乱的 working directory，从而毁掉自己的 context window。
> 
> 3) 通过不精确的语言 Injecting 意外的 requirements，让 LLM 去做比他们原本打算的更难的 task，比如在 building 游戏的 core 之前先 building 一个 matchmaking system
> 
> 4) 如果你对自己想要什么、或者何时才算完成没有明确想法，你可能会 under-specify，然后在合作中不断偏离方向，随着时间推移改变 requirements，却没有朝任何明确的目标前进（许多 AI-psychosis vibe coders 都会这样做）

### 附录：agentic loops 与撰写本文

正如我在本文开头的 alt text 中提到的，多年来我一直很犹豫要不要写 AI，因为我待在 Galapagos Island 这里，与正在发生的事情严重脱节：我没怎么看 social media，也没能好好与 SF 那些真正身处一线的人保持联系。

到了 5 月，我与几位从 SF 来这里参加 PGConf 的人聊天，才相信写点东西或许有意义。尽管他们身处一线，而且似乎很接近人们使用 agents 的最前沿，他们仍然觉得我的 workflow 中有些东西很有意思。不过，正如我说过的，具体 workflow 技巧的 half-life 很短，因此我觉得，详细记录某个确切的 workflow 不会有多大用处；这也是正文更侧重 higher level ideas 的原因。我不确定什么可能真正有用，但我打算试着写点关于我的 workflow 如何演变的内容。如上所述，我觉得我的 workflow 从来没有在哪个时间点真正称得上出色，但它有用，而且似乎总有自然而然的下一步，能让它的 productive 程度再提高一点。

早在石器时代，也就是 Claude 和 Codex 这样的 tools 出现之前，我有时只是 run 一个非常简单的 loop，不断 compiling 这些 code、running 这些 tests，并 re-prompting，直到一切都 passes，[我在 2024 年年中曾在这里提到过](https://danluu.com/codenames/)。当时，我觉得这还没用到值得拿来处理那些我知道自己在做什么的事情，但它让我能在那篇文章里 embed 一个小 web game，并完成其他一些 tasks；否则，这些 tasks 就需要我学习某个领域的知识，而我可能永远都不会对真正掌握那个领域的 expertise 特别感兴趣，比如 building 一个 web app。

有相当长一段时间，当我想完成某个简单 task 时，这类做法还算有点用；但直到经历了本文开头的 bisect/video 故事，又做了一些其他 data analysis，看到它能在多大程度上 speed up 这些 data analysis，我才开始大量使用 agents。顺便说一句，那个 bisect/video 故事源于一项 analysis：我当时想知道，一个 working feature 和/或 bug fix 的 half-life 是多久。巧的是，那项 analysis 与本文中的几个想法有关。首先，结果发现，在 pre-LLM 时期，这个 half-life 相当短；如果我们想提高 velocity（无论是否使用 LLMs），这似乎就支持了应当做更多 testing 的观点。其次，这又是一项耗时很长、以至于我在 pre-LLM 时期不会去做的 analysis。

在 2025 年年中到年末的某个时候，我尝试对一些个人 projects 进行 vibe coding。我使用 Codex，只是因为有人说它的 subscription plans 会给你更多 quota（后来我两种都试过了，这说法似乎准确）。当时，我的目标是在个人 projects 上尽可能少花自己的时间，同时获得想要的 output；但我此前并没有真正做过任何 vibe coding，也完全不知道什么做法会有效，不过很快就明显看出，我采用的是最 naive 的 loop：只是把许多份“如果 X 还没 done，就 implement X，直到 complete；如果 X 已经 done，……”的副本 queue up。我没读过别人都在做什么，而我亲自交流的人通常也没怎么用 AI，因此我完全不知道，“Ralph loop”这个 term 早在 2025 年年中就已经出现了，而且人们正在使用这种做法的各种更省事的 variants；不过，这其实也没有那么麻烦（prompt 写好以后，把它的副本 queue up 大概只需要 5 秒左右）。

而且，回过头看，在把事情引向正确方向这方面，与 Ralph loop 相比，这个 workflow 也不算差。我通常每天会看几次（睡前、醒来时，或许再加上其他几次）；一般来说，每次查看时，事情都不太对劲，我会先查看解释当前情况的 logs/metrics/graphs/等等，再 queue up 一些 commands，把事情往正确方向推一推。由于这些是我每天只花几分钟的个人 projects，我并没有试图 maximize throughput，只是在手头闲置的两台不同 laptops 上各 running 几样东西。如果有更 autonomous 的 loops，可以无限持续下去，而不需要手动补充 queue，那当然更好；但这实际能省下的时间并没有那么多，我想每天还不到 10 分钟。

这样做了一阵子之后，今年早些时候，我开始（有时）尝试 run 更 autonomous 的 loops。再说一次，与人们在任何特定时刻热衷的东西相比，我想这一定有点落后于潮流，但它似乎还算有效。开始这样做以后，我发现，人们推荐的很多 tooling 并不太适合 managing agentic loops，而专门为此 designed 的 tooling 又似乎有点“vibe”味，会出现 reliability 问题。

前一种情况的一个例子是 Conductor：当时它被广泛推荐，但它并不是真正为 support 我想做的许多事情而打造的。例如，Conductor 有 workspace 这个 concept，用来 separate 各种东西。我经常想 invoke 某种或许可以叫作“higher order workspaces”的东西：由一个 agent（或一组 independent agents）decide 应该对一份 items 的 list 做什么，接着把每个 item fed into 另一个 agent（或 independent set of agents）（可能还对 agent concurrency 有某种 limit），然后再如此继续，用某种 graph structure 来 determine 这些 tasks 如何流转，其中包含 reduce-like steps，查看一批 tasks 的 output，如此等等。虽然从技术上说，可以让 Conductor 做到这些，但它并不是真正为此 designed 的；而既然你可以直接让 agents write scripts 来 create 这样的 structure，那么直接使用 custom vibe-coded scripts 似乎简单得多。

像 Gas Town 这样 designed 来使用大量 agents 的 tools，大多似乎面向 less structured workflows，而且往往看起来高度依赖 vibe coded，因此也有些 unreliable，以至于我不确定，为什么要用它们中的某一个，而不是自己拼凑点东西。\[2026-08 更新：[在这篇文章中](https://yegge.ai/essays/the-shape-of-things-to-come/)，Yegge 提到，他从未成功用 Gas Town build 出任何东西，所以看来我对 Gas Town 的印象并没有错\]。我的意思是，正如关于 board games 的那篇长 footnote 所讨论的，如果某样东西在 quality 和 complexity 上没有达到某个门槛，自己做一个 version 是相当容易的。即使你为自己做的东西比那个 product 更 buggier，你仍然可以确保，在你的 workflow 下，它没有会影响你特定 workflow 的 bugs；因此，它甚至不需要达到那个 product 同样的整体 quality 门槛，就能对你更好用。

因此，我最终采用的做法，是为需要 run 一段时间的 tasks 制作 one-off loops。building 某种符合我需求的 orchestrator 大概会带来 efficiency gain，但我觉得，我真正 set up 过的这类 loops 还不够多，不足以让我知道自己想要什么，而且我的需求会随着 problem 的不同而有很大变化。有时，我希望某些 metrics trigger 一个能 fix issues 的 agent 来做 health check；有时，我希望每次 iteration（不管那具体意味着什么）之后，都 automatically invoked 一个 agent 或一组 agents 来检查进展；有时，我希望 agents continuously check 进展。有时，我想要带有某种 multi-level triage 的 graph structure，等等。

因为让 agent set up 你想要的任何 arbitrary structure 都相当容易，我通常会从某种 simple structure 开始，加上一些 basic health checks 和 monitoring，然后定期查看，尝试通过 structural fixes 来解决 issues，让 issue 不再 recur。原则上，这种东西如果 set up 得好，可以无限持续地产出有用的工作；但至少就我 set up 的东西而言，这些 loops 的 productivity 往往会随时间 degrade。即使没有什么严重问题，如果我亲自在键盘前输入 instructions，从各个方面推一推，同时 monitoring 正在发生的事情，这些 loops 的 productive 程度也会高得多。如果我把其中一个放着几天或一周不管，它通常仍会产出 non-zero 数量的有用工作，但远远不如我每天查看时那么多。我尝试过各种 strategies，想让这些 loops 在没有 intervention 的情况下更能保持正轨，也发现了各种有帮助的做法，但我还没有弄明白怎样 replace 我自己（还没有？）。

例如，[在 2026 年 4 月/5 月，我尝试让一批“personas”反复聚到一起，试着代替我推动 loop](https://mastodon.social/@danluu/116514958701771749)。当时，我试图让一个 loop 顺畅 running，它正在处理一些使用 CRDTs 的 code（顺便说一句，我对此一无所知），所以我尝试用类似这样的内容来 diagnosing issues：“使用 independent agents，以 linus torvalds、kyle kingsbury、marc brooker、tptacek、dan luu 以及 4 个 contrarian personas 的身份进行 review。让每个都想很久”，并对此进行多次 iterations（是的，我确实觉得 invoke 自己的名字很傻）。这些 personas 中的每一个，似乎都会以不同的方式让事情保持正轨，例如，“linus torvalds”这个 persona 往往会抵制 loop 的那种“natural”倾向，也就是由于反复添加不必要的 complexity，导致事情失控；“dan luu”这个 persona 会强迫 loop 在 implementing 之前先 measure，有时也会说“我们绝不能 rationalize XYZ”之类的话，抵制某些糟糕的 reasoning。这些都不足以 replace 人类的 observation 和 intervention，但采用这种做法的各种 variations，足以让这些 loops running 得更顺畅，需要的 intervention 也更少。

这种 persona setup 对 architectural design、debugging 等也带来了改善。同样，还没有好到完全不需要人类，但足以让人类少做一些工作。

如果人类了解常见的 failure modes，这一切似乎效果最好。例如，当要求 agents debug 并解释某个 bug 是何时 introduced 的，如果只是 prompted 它们解释，那么即使经过多轮 independent analysis，它们也常常会给出完全 incorrect 的 explanation（大概有 50% 的时候如此）。当要求它们通过实际 executing code 来 confirm 自己的 hypothesis、检查 hypothesis 是否 correct 时，这就消除了大多数 incorrect explanations。仅仅在一个 simple prompt 中加入 forced checking，success rate 就比让 agents 做 independent analyses 并互相 cross-check 更高（把两者结合起来，success rate 似乎还会更高）。

从 agents 中获得价值，很大程度上似乎在于对它们的 failure modes 有所了解，然后 working around 它们。本文前面我们提到，如果人们现在不使用 coding agents，而是在 M 个月后才开始，他们其实并不会被远远甩下，因为他们最多只能落后 M 个月；而由于变化如此之快，他们实际落后的程度很可能远小于此。据我所知，一个主要原因是，使用 agents 所涉及的很多 skill，其实是在 working around 它们的 failures。当然，AI labs 想 fix 这些 failures，这意味着 new releases 的 design 就是要尽可能让这些 skills 过时。这一点可以直接观察到：一年前还很常见的一些 failure modes，现在已经罕见得多了。

顺便说，这也是我个人觉得许多 benchmarks 对我没用的另一个原因。总体而言，benchmarks 已经转向尽量不去“过度解释”，而是模仿一个不太会使用 agents 的 naive user。AI labs 关心这一点是合理的，因为他们想做出一种操作时所需 expertise 尽可能少的 product；但作为 professional programmer，如果有办法绕过 agents 的某种 failure mode，你大概会采用它，而不是表现得像一个 benchmark，因此，即使你做的恰好是某个 benchmark 中的 task，你得到的 result 也会非常不同。

1.  在我工作过的每个地方，我都听过反对配备 test enginers 的说法，有时听到这些话时，test engineers 正在被裁员。这种说法大致是：“最能 test code 的人就是写出它的人；而且，如果 programmers 把 testing 外包给别人，他们就会在 testing 上变懒。”但这只是一个有两面的 trade-off 中的一面。

    总体而言，specialization 会带来 efficiency gains，因为人们会在 specialization 中培养更深的 skills；也会带来 efficiency losses，因为 skills 的分割会造成各种 fragmentation issues。针对 dedicated testers 的同一套论点，也可以用来反对配备 dedicated front-end 和 back-end 人员、mobile engineers 等等；这些说法都成立。但另一面也有成立的论点，而且人们普遍承认，一旦达到一定 scale，[配备理解特定事物的 specialists 所带来的 gains，会 outweigh 配备全是 generalists 的 teams 所带来的 benefits](https://danluu.com/in-house/)，那些 generalists 对每件事都只是勉强过得去。我见过人们花一二十年专门学习 test skills 后，在 testing 上能有多出色，因此我认为 software companies 没有配备具备这些 skills 的人，是错失了机会；但这可以说超出了本文的范围，因为你并不能直接出去 hire 一群在 software 方面具备这种 skillset 的人。要让这样一群人存在，你需要像 hardware companies 那样的文化和晋升阶梯，让 verification engineers 与 logic designers 一样，都是 first-class citizens，拥有相同的 pay scale，以同样的速度晋升到高层级，享有同样的声望等等，然后你还得这样做上二十年。

    这里的 gains 不仅仅是整个职业生涯都在做某件事所积累的直接 expertise。一家公司中存在一个庞大的 community of practice，也意味着人们在公司里成长得更快。我很幸运，[因为恰好坐在一位 distributed tracing 专家旁边，学到了许多 distributed tracing 的知识](https://danluu.com/tracing-analytics/)，几个月里学到的东西，可能相当于我自己摸索几年才能学到的；同样，我也很幸运，因为坐在一群 world class test engineers 中间，学到了许多 testing 的知识。即使在规模超过那家 hardware company 一千倍的 software companies，我也不确定那里是否聚集了那么多有才华、花了 40+ 年专攻 testing 的 test engineers，供我向他们学习（而且即使有，那群人也会离我很远，我根本不会和他们打交道）。

4.  顺便说一句，我很好奇 online board games 将会怎样发展（除了这条脚注的结尾，整条脚注都在谈 board games；如果你对 board games 没兴趣，可以跳到底部）。一个问题是，人们对 cheating 的“需求”很高，而且即使在 LLMs 出现之前，competitive online play 中就已经有相当多的 cheating。如今，做一个能 cheat 的 bot 并没有那么难，而且只会越来越容易。我对和网上随机遇到的陌生人对战没什么兴趣，所以通常不玩 ranked/competitive online board games，但有不少人会玩。如果 cheating 的数量增加，很难看出这种玩法该如何维持。

    我好奇的另一件事是大型 game platforms 的价值。Board Game Arena (BGA) 似乎以相当大的优势成为最大的 platform，Tabletop Simulator (TTS) 排在第二。BGA，呃，客气一点说，你可以说它相当古怪。例如，默认情况下，这个 platform 实际上不允许 players act concurrently。如果你在另一个 player 点击的同时点击任何东西，只要你的点击比他的稍早一点到达 server，就会阻止他执行 action。对于有 simultaneous actions 或 selections 的 games，这会导致人们在其他 players 执行 actions 时，每次被卡住几十秒，无法完成自己的 turns。关于 BGA 的各种问题，我可以写出一篇和本文一样长的文章；不过，只要说，对于一个 players 尝试 act concurrently 就根本无法正常工作的 multiple player online platform，你能想到的其他问题，这个平台也都有。总体而言，TTS 用起来甚至更笨拙。

    因此，对于不需要 complex interface 的 games，implement 一个更好的 user experience 相当容易。Game rules 和 mechanisms 不受 US copyright law 保护，所以，只要不使用他们的 graphics、trademarked logo 等，implement 一个 rules 完全相同的 game 看起来完全合法。我个人并不想尝试构建一个包含 unlicensed games、试图与 BGA 竞争的 platform，但我有时确实想玩一个没有 BGA 那些毛病的 game（或者 BGA 上没有的 game）。视 game 而定，让一个看起来合理的 rules 版本正常工作，花费的个人时间从几秒到几个小时不等。几秒适用于 simple games，基本上一个 simple prompt 就能让 game 正常工作（例如，[这里有一个 rules 与 Scout 相同的 game](https://danluu.com/game/flip-taker/)，我 implement 它是因为朋友们找不到在线玩 Scout 的办法。顺便说，如果你去试，我并不保证这个 game 能正常工作——它 hosted 在某种不太靠谱的 free tier hosting 上，因为如我所说，我并不是想构建什么大型 platform；我和朋友们使用时，它比 BGA 更好用，这就是我追求的（非常低的）quality bar：我们玩的时候不遇到 bugs，而不是它是一个普遍 robust 的 implementation。而且，虽然我的 game implementations 的 runtime performance 与技术上可能做到的水平相比非常差，但习惯了 BGA 的朋友们都说它感觉是 instantaneous，因为他们习惯了 BGA 慢得多的 performance。当人们习惯的 platform 既极慢又极其 buggy 时，vibe code 出一个更好用的东西很容易。

    有些 games 会花更长时间，因为目前的 models 无法 one shot 它们。以我的个人时间而言，Guards of Atlantis 可能是我尝试 implement 过的最耗时的 game。它有很多 rules，因为每张 card 都有一些 custom rules，而且这些 rules 对人类来说似乎格外难理解，这也让它们对 LLMs 而言并不理想。相对而言，我观察到人们无意中把 rules 玩错的 rate，远高于大多数 games；除非一个人在官方 discord 上关注那里的 rules 讨论，或者由这样的人教过，否则我都不确定自己是否见过谁玩对了。鉴于这一点，我觉得期待一个 LLM 能 one-shot 这个 game 并不合理。

    总之，既然只要花一个人几秒到几个小时的时间，就能把一个 board game implement 成比主流 online board game platforms 上更好的形式，我很好奇这些占主导地位的 board game platforms 将会怎样？人们会因为 network effects 而继续使用它们吗？我认识的在线玩 board games 的人不多，但其中相当一部分人觉得 network effects 没多大重要性。例如，看看前面提到的世界 #1 Azul player 的这些话：

    > 最近我在自己的 games 中尝试\[你的 bot\]，玩得非常开心。这个 bot 会找到我绝不会考虑的、非常酷的/creative moves，这帮助我以更开放的心态思考该如何处理 rounds
    > 
    > ...
    > 
    > 如果这些 bots 的 strength 是 ~equal，和它们 playing games 可以相当有趣（我已经几个月没在 bga 上碰过 azul 了）

    看到世界顶尖 player 连续几个月都在和 bots 对战，而不是在 BGA 上玩，很有意思，但我觉得并不意外。如今大型 online platforms 的一个问题是，实际上很难 match up 到 skill 相当的人。player 越强，这个问题就越严重。如前面所说，我不太喜欢和随机遇到的陌生人对战，因此玩得不多；但在 BGA 上玩 competitive ranked games 的人，几乎普遍都会抱怨 ladder 有多磨人。如果你是一个很强的 competitive player，你 match up 到的几乎所有人 Elo 都低得多，于是你就在玩这些无聊的 games，碾压对手，每个 game 只赚一点点 Elo。然后，只要你出现一次 blunder，就会因为一场失利损失大量 Elo。前阵子，我病得几乎什么都做不了，于是尝试在 BGA 上玩一个 game 的 ranked competitive play，打到了世界 #4。在冲到 #4 的整个过程中，我只和排名 top 10 的人玩过两场 games。其他每一场都是对阵明显较弱 player 的、相当无聊的 game。对于 competitive players，既有即将到来的 rampant cheating 问题，也有眼下 ranked competitive play 大多无聊到令人麻木的问题。

I've been using AI fairly heavily since last November and the whole thing is a funny experience. An agent will do something that, if a human did it, you'd immediately fire them. My reaction, of course, is to act as if this is great and spin up a thousand agents so they can do even more of that.

### Testing background

LLMs are highly leveraged when it comes to testing. In terms of the amount of effort it takes, it's easier than ever to hit a particular quality bar and yet, software seems to be lower quality than ever. A decade ago, we looked at [the bugs I ran into in an arbitrary week](https://danluu.com/everything-is-broken/). There were quite a few bugs then and I run into more bugs now, but I don't think this has to be the case.

For one thing, after a bug has been shipped, it's easier than it's ever been to use a data-driven approach to find and fix the bug. Just for example, at work, I tried creating a pipeline that goes from support ticket (chat or email) to pull request (PR). As far as I can tell, this works ok. Since I work for a company that has a traditional workflow, all of these fixes get reviewed by a human and, so far, we've had no known false positives.

Per unit of time invested, it's also possible to do more thorough testing. Personally, I think this can be effective enough that I'm fairly comfortable trying to ship a large volume of code via a "[software factories](https://factory.strongdm.ai/)" workflow because I've seen a testing-heavy no-review workflow that results in much higher quality than any review-reliant workflow I've seen or even heard of.

Like everybody, I have biases that fall out of my experiences. It just so happens that I spent the first decade of my career at a company whose test processes happen to work well in today's LLM environment. [I talked about fuzzing as a default testing methodology on Mastodon](https://mastodon.social/@danluu/116486547257066966), and [a skeptic tried it out and immediately found some bugs](https://mastodon.social/@22@sfba.social/116508702500087643):

> so I reread the blog post and was very "dubious face" but no yeah, Claude fuzzing found several classes of bugs that are worth fixing

A number of other folks I've talked to have also tried adopting something like the testing flow we'll discuss here and they've all immediately found bugs in the software they work on, including bugs that don't get surfaced by just asking Codex or Claude to audit the code for bugs, find bugs, "test", "test more", etc. For example, Dennis Snell mentioned that he and a teammate, Jon Surrell, not only found bugs in the code they're working on, but also "in upstream dependencies, including the HTML specification, big-three browsers, and other open-source projects" with fairly low effort.

In general, when I talk to software folks about testing, I'm coming from such a different place that they immediately look at me like I'm an alien, so let's talk about how we tested at this hardware company I worked for, Centaur, which informs my biases about how I like to work. Some of the things that we did that were or are unorthodox in the software world are:

1.  Hired dedicated QA / test engineers, with testing being a first-class career path on par with being a developer
2.  No code review by default
3.  Virtually no hand-written tests
4.  Constant testing via what programmers sometimes called property based testing, randomized testing, fuzzing, etc., although we just called those tests (hand-written tests were called "hand tests").
5.  Large regeression test suite (3 months wall clock to execute on compute farm)
6.  No unit tests

Just to give you an idea of the general structure, when I left (in 2013), we had about 1000 machines generating and running tests at all times for roughly 20 logic designers and 20 test engineers. This was on prem and the machines took up half a floor of the building we were in.

The general structure was that we had maybe 20% of machines running regression tests, and 80% generating and running new tests. Three months of regression tests is too much to gate commits on, so there was a much shorter list of tests that took maybe 10 minutes or so to run that people would run before committing. Those pre-commit tests would run on a special setup to run as quickly as possible, with overclocked machines that were the fastest machines money could buy, as well as a different simulator setup.

New failures would get found and reported as they happened and one to two engineers had a job of sorting through failures and triaging them (rejecting false positives, fixing issues in the test generator that caused them to generate false positives, etc.).

In terms of the magnitude of the impact, [unless you count culture as a separate item](https://danluu.com/culture/), (1) was probably the biggest difference between us and a typical software company, but also the most irrelevant for readers here, so I'll relegate the discussion to a footnote[1](https://danluu.com/ai-coding/#fn:T), except for this brief comment that testing is like any other skill; spending more time doing it improves skill and, since testing isn't a first-class career path at most major tech companies, people generally don't have the same level of testing skills at software companies as you see in some career CPU test engineers. In the same way that an engineer who who spends 20 years working on distributed systems or UX is going to be much better at it than an equally talented engineer who spends 5% of their time on distributed systems or UX, someone who spends 20 years working on testing is going to be much better at it than somebody who spends 5% of their time on testing.

(2) is one of the things that makes some of the test practices we used at the chip company suited to AI workflows. We didn't review code by default because we trusted our test practices enough that review didn't, in general, add much reliability. We were shipping fewer than 1 significant user-visible bug per year, and review was done on an as-needed basis when someone wanted an extra set of eyes on something they thought was particularly tricky[2](https://danluu.com/ai-coding/#fn:R). With AI coding workflows, it's easy for one person to generate more code than any human or even any ten humans can review by hand. People have different levels of comfort with shipping code without review. Personally, I'm very comfortable shipping code without human review because I've seen it done on products that are technically more challenging than most software at most software companies.

I often see people say things like, "that's too much risk; we have millions of users" but, empirically, they're talking about a workflow that ships bugs at a rate that's maybe a thousand times higher per capita on raw count, with the ratio being much higher if you adjust for severity. If a company were shipping bugs at, say, a hundredth the rate we were at Centaur while relying primarily on review to catch bugs, then I could see their point, but that's not what's happening at the typical software company where people don't want to move away from human review because of the perceived risk of shipping bugs.

(3) and (4) go hand in hand. Almost every software group I know of that's serious about reliability (various teams that ship reliable databases, distributed databases etc.) are at least directionally doing the same thing, although they might have a larger fraction of hand written tests. For the same reason it's considered a bad idea to rely on testing by interacting with the software yourself and observing whether or not the software appeared to work, it's a bad idea to rely on directly typing out the inputs to a test and the expected outputs. [As previously discussed](https://danluu.com/testing/), it's just really inefficient to write tests by hand. For any given level of reliability, you'll get there more quickly if you prefer randomized test generation over hand-written tests.

(5) fell out of having a lot of tests find a lot of bugs. In general, if a test found a bug that we later fixed, we'd keep the test in our regression test suite forever. It turns out, if you find a lot of bugs with good tests, you'll end up with a large test suite. But putting that aside and just looking at it from a test efficiency standpoint, the standard setup in software of having the same set of tests run in CI for each PR is extraordinarily inefficient if you think about the what's more likely to find a bug, running the same test a thousand times in a day or, in the same amount of test time, running a thousand different tests.

(6) came out of test efficiency concerns as well, in that we had a much smaller team than our competitors. That was a reason the company managed to survive for so long. While Intel was putting every x86 designer out of business other than AMD, our operating cost was low enough that the company survived until 2021, at which point it was acquired by Intel for $125M. With the company's tiny team size, it wouldn't have been possible to get reasonable test coverage with unit tests and hiring enough to do unit tests probably would've meant the company would've gone the way of the x86 efforts of Transmeta, Rise, Cyrix, TI, UMC, NEC, VM, etc., a decade or two sooner. From an efficiency standpoint, unit testing does pretty poorly.

To sum it up, we did quite a few things that most software people tell me are bad ideas (dedicated test engineers, no unit tests, no code review, etc.) and we had much higher quality than any software company I've worked for or any software I've used. Whenever I talk about this, people will say that this doesn't apply to software because CPUs only have X concerns and you can't do the same thing with Y. When I first switched from CPU design to software I thought that might be true, but I've since tried this testing methodology with every kind of Y that someone has mentioned this can't work for and it's worked for every single one, so I no longer find this very plausible (and the Xs generally involved [incorrect assumptions of what hardware development is like](https://www.hillelwayne.com/post/are-we-really-engineers/)). While there are real differences between hardware and software, when I’ve seen people lean on that as a reason that testing techniques don’t carry over, it’s been the case that the person is relying on some imagined factor that only seems relevant because the person doesn’t know much about hardware development.

One significant difference was the ratio of effort that went into testing vs. development, but the fixed costs of fuzzing are fairly low, so this is scalable to any level of effort and the efficiency gains are still there. And, due to the gains in test efficiency, the ratio of effort wasn't as large as software engineers generally imagine. We had about a 1:1 ratio of test engineers to developers and then spent maybe 10% of our time in a "freeze" state, where the goal was to find bugs and not ship new features, so a zeroth order estimate for the overhead here is that we spent 55% of our effort on testing and 45% on development, or we could've put 2.2x the effort into development if we spent zero effort on testing. If you look at a software company that's shipping significant bugs many times faster than we did and you declare an emergency and get people to spend 55% of their effort on testing, I don't think the ratio changes too much. Maybe they get to half the previous ratio or something, but the level of effort isn't really what's making the difference.

Nowadays, another thing people will say is, why bother with fuzzing when you can just ask an LLM to find bugs? I've tried doing both quite a few times now and my experience has been that fuzzing generally wins on latency to find a bug, and it dominates on finding more bugs and having a lower false positive rate. LLMs have fairly high variance (more on this later), so just asking Codex or Claude to find a bug can sometimes win but, on average, fuzzing has won.

### Some details on testing

Despite the very positive things I've said about LLMs testing, LLMs seem pretty bad at testing. However, for any level of testing effort, LLMs let you apply testing effort a lot more easily than before if steered properly.

An extreme example of this is that everybody I've talked to who cares about quality or testing at all finds the tests LLMs generate by default, or if you tell them "Write tests", "Write more tests", etc., to be poor. People tend to rate the tests as somewhere between worthless and marginally useful, depending on their standards.

For example, Em Chu (a compiler engineer) says:

> The existing tests I'm working with aren't perfect, but are still above the bar LLMs seem to aim for, which I would describe as "thorough enough to smuggle a feature through human code review." For a compiler (compared to e.g. UI), where I'm guessing it's easier to write the average test, but a higher bar of correctness is generally expected of the end product, LLMs just suck. They are painfully bad at the adversarial "now, what if I do this" or "let's try the cross-product of everything" process humans use to write tests that actually find bugs

At the same time, I've seen a number of folks rave at how amazingly good LLMs are at testing when you tell them "Write tests", "Write more tests", etc. When I've looked into why people say LLMs are great at testing, what I've found is that people who did essentially no testing at all find LLMs to be great at testing. Well, that makes sense. If you go from basically zero testing effort to a tiny bit of testing effort, that's a huge win.

As of June 2026, directing LLMs to do fuzzing / randomized testing feels similar. I've tried using an LLM to generate a fuzzer and, for most projects, [this will turn up real and often serious bugs within minutes](https://mastodon.social/@danluu/116486547257066966). However, on looking at what the LLM-created fuzzer is trying to test, I have the same reaction as a normal programmer who cares about quality looking at LLM-created tests. The coverage of the LLM-generated fuzzer is curiously bad and misses all kinds of basic things you'd expect a hastily human-written fuzzer to cover. Depending on whether you're a glass half empty or a glass half full person, you might say that this says something about the test coverage of most projects, or that it says something about the unreasonable effectiveness of fuzzing.

At a high level, LLM-generated fuzzers from SOTA models today don't do a good job of "thinking about" how inputs should be varied to elicit bugs. Then, if you naively tell it about how inputs should be varied and to combine these, it will also not combine bug ingredients in a reasonable way. It's possible to give instructions that will work well, but this heavily relies on the user to provide direction.

If you're using randomized testing as "extra credit", to catch a few more bugs, or to replace traditional software testing processes, you can just tell an LLM to look for risky areas of the code and find invariants that might be violated and fuzz them. This works ok. When I've convinced people to try some randomized testing, they usually start here and find quite a few bugs they're happy to have found. Due to the nature of who's interested in trying out novel-to-them test techniques, this is often from people who've worked on some of the most well-tested and reliable code at the company and they can find bugs in their own relatively well-tested code.

If you want to use randomized testing to keep an agentic "software factories" workflow honest, then you need to have a way to deal with gaps in SOTA models because, when you're shipping the equivalent of hundreds or thousands of PRs a day into a project, everything that's not constrained from degrading will rapidly degrade.

At a high level, the entire system needs some kind of feedback that finds gaps and instructs whatever loop is making adjustments to the fuzzer to close the gaps. Recently, I've been testing things where I don't understand the domain and don't understand the project or the code, so I've been flying relatively blind and know that there will be a lot of gaps in what I come up with (and, as noted above, LLMs are terrible at this). But even in areas where I'm familiar with the domain and understand the code relatively well, there will still be some gaps because humans miss things and make mistakes, so there always needs to be some kind of feedback into the test setup that can find gaps and allow you or an agent to close the gaps.

I've been playing with various ways to have agents convene and reconvene to get agentic loops running better and, while that kind of thing helps, I haven't figured out a way to do do this well enough to create some kind agentic software quality improvement loop that doesn't rely on outside feedback, whether that's occasional human input, or shipping something (ideally only fractionally and with staged rollout) and then having the system monitor metrics/logs/traces/support tickets/whatever to use that as feedback. The support ticket to PR pipeline I mentioned above is one such feedback loop. The pipeline not only tries to generate a PR, it also tries to get the test setup to add test coverage that will find the bug and possibly surface other bugs, or will re-find the bug if there's a future regression. This seems to work ok-ish, in that it finds real bugs and improves test coverage, but I'm sure there's a lot of room for improvement.

Relatedly, I've been wondering why LLMs are so bad at writing tests. On asking around a bit, I'm told that this is because the capabilities that LLMs have come out of people building [RL](https://en.wikipedia.org/wiki/Reinforcement_learning) environments which allow models to improve at tasks, sometimes in a generalizable way and sometimes not. I'm also told that there's a market for selling RL envs, but it's fairly thin because there aren't all that many buyers for them, and you really want to know someone at a lab who's a buyer or close to it. If you are such a person or can connect me with such a person, could you do me a favor and reach out to me (I'm fairly easily reachable on [X](https://x.com/danluu), [Mastodon](https://mastodon.social/@danluu/), email, etc.). I'm curious about how this works and how plausible it is to sell an RL env for something like testing, optimization, or the longer horizon tasks discussed in this post, where it's easy to observe significant gaps.

Back on the topic of testing, when fuzzing or doing any kind of bug auditing, detecting false positives is a critical part of the process. At least for now, having access to a model that's better than anything you can publicly use won't save you. A while back, Dennis Snell told me, frustratedly, that he spent the day wading through AI slop forwarded to his employer by Anthropic that came from their vaunted Mythos model that's too dangerous to release from the public. Anthropic was apparently doing the company some kind of favor or maybe doing some kind of EA security improvement by submitting security issues from Mythos, except that they didn't bother with having a reasonable false positive rejection process so they were just forwarding some real vunlnerbilities with a lot of AI slop \[September 2026 update: [see also](https://x.com/danluu/status/2102804723342688744), [and](https://www.vulncheck.com/blog/anthropic-glasswing-receipts), where people report the same thing\]. At the time, I was using a model that, if Fable is any indication, appears to be moderately less capable than Mythos, but I had no problem generating an endless stream of bugs (some of which were security issues) with no known false positives, which seems to indicate that having a reasonable setup around the model is a least as important as having the latest and greatest model. It's not clear why Anthropic wouldn't have done something like this beacuse the biggest blockers for something like this are irrelevant to them (token cost, and that it's difficult to get a good false positive rejection process running with their models or OpenAI's best models because even with standard "cyber" approval the newest/best models rejects attempts to create and run exploits, so you can't do the straightforward thing of rejecting things for which you can't create an exploit).

I've been trying custom workflows on a per-project / per-problem basis and don't exactly have a generic false positive rejection scheme, but there are various things that seem to be semi-generalizable. If you don't mind spending tokens, having independent agents repeatedly check an alleged bug reproduction (repro) substantially cuts the false positive rate. A couple months ago, [I mentioned that I had good luck using different "personas" for reviews as well as for managing agentic loops](https://mastodon.social/@danluu/116514958701771749) and I got some responses with theoretical reasons this doesn't work well but, in practice, it seems to work fairly well. My workflow changes regularly and maybe a week after that discussion I started adding "contrarian" personas to the mix, which improved performance given the same wall clock or token budget.

For anything human reviewed, having some kind of artifact (e.g., a video if it's a bug that's expected to be apparent in the UI) is necessary. Without really explicitly trying to have the agent review this, just producing this at all seems to reduce the false positive rate somewhat, and then having the agent review the artifact reduces the false positive rate further. Asking agents to independently review the artifact (e.g., looking at the test code that produces the video vs. looking at the video itself) also reduces the false positive rate further. In general, getting independent perspectives seems to help a lot with reducing false positives. In the experiments I've run, this has been less effective than having agents with different personas / perspective per wall clock time or per dollar, but just asking the same question multiple times improves results, for reasons that should be obvious from the graphs in the LLM variance section.

Pretty much everything I've tried to reduce false positive rate has worked, so if you're not scaling up a workflow to the point where optimizing the costs matters, doing anything remotely reasonable seems to work fairly well.

### Caveman mode

I keep getting various tool and workflow recommendations and, when I look into it, I can almost never find good information on whether or not it makes sense to adopt the recommendation. Just for example, I've seen "[caveman mode](https://github.com/juliusbrussee/caveman)" recommended multiple times at work. Caveman mode allegedly reduces token usage and speeds up prompt resolution (the README claims 75% reduction in token usage, 65% reduction token usage, and 2x fewer tokens used, as well as a 3x speed increase).

Searching for information (just googling 'caveman mode', no quotes, the top hit that wasn't a link to caveman mode was [this reddit thread](https://www.reddit.com/r/ClaudeAI/comments/1si197b/does_caveman_mode_save_tokens_at_the_cost_of/) where, of the three top comments, one is joke and the other two highly recommend it:

> Just extreme brevity in a refreshing way... and dramatically lowered token count without any seeming impact on the analytical thinking... but i have no way to benchmark before and after.
> 
> Someone at work is testing it and it seems to actually save tokens AND work just as well.

Most of the rest of the top hits were also positive recommendations for caveman mode that purported to do some kind of eval (although they read like unfiltered LLM text) and the top hit on YouTube was one of the [the biggest programming YouTubers](https://www.youtube.com/watch?v=L29q2LRiMRc) saying

> it actually works; it actually works quite well ... no, I'm not exaggerating

In a slack thread at work where people were recommending caveman mode, I asked if anyone had done a comparison, noting that the creator of caveman mode responded to the HN thread about caveman mode by saying it's a joke. Someone linked to an analysis of caveman mode that claims a significant win, but the analysis was an LLM-generated SEO spam article with numerous errors. When I politely pointed this out, the person who posted the link said "I only skimmed it".

At that point, I decided to spend about 15 seconds apiece generating some caveman mode benchmarks (it seems like people call benchmarks evals now, so I should call these evals?) ([previously discussed in more detail here](https://www.patreon.com/posts/160473058)).

To start with, I'd been using a lot of GPT-5.5 xhigh when this discussion came up a couple months ago and I benchmarked this thing, so let's look at how this looks for GPT-5.5 xhigh on the first benchmark, a simple benchmark where we ask the agent to optimize some code in wasm. Since this is something I spent 15 seconds prompting an agent to generate, I don't think it's worth spending a ton of time discussing the details, but one thing to note is that it's possible to do much better than any of the results an agent achieved here. I would expect a human doing this by hand or a human who's being prescriptive about what the agent should to do to get much better results than any of the AIs). For the optimization chart, 1.0 is no speedup and higher is better (below 1.0 means the "optimization" slowed things down). To give you an idea of what this looked like when running the experiments, you can click the buttons to follow along interactively or just play an animation.

We can see that, for the first benchmark (optimize a non-trivial algorithm in wasm), after one run, caveman is looking good. We get 1.027 speedup vs. 0.987, $12.10 vs. $23.10, and a wall clock time (of how long the agent took) of 8m51s vs. 14m9s. But we know that LLMs are stochastic, so we should probably run again. After a second run, we can see a big change in the results, with an average of 1.0 speedup for both, but caveman mode coming in at $12.45 in 8m64s vs. $40.38 in 17m57s. That's a huge cost savings that's in line with the claimed savings from caveman mode. It's a bit silly to narrate each step of the animation, but if we skip to the end, we can see that the average after 50 runs is in favor of caveman, with 1.03 vs. 1.01 speedup, and $17.97 in 13m46s vs. $24.21 in 16m52s. That's not as good as what we saw after two points, but that's still solidly in favor of caveman mode.

I asked GPT-5.5 xhigh to do classical and Bayesian statistics on this and it produced a script that says that, for the Optimization 1 benchmark, the p-values for caveman having better speedup, cost, and wall clock time, are 0.1, 0.005, and 0.001, respectively. With Bayesian stats, we have P(caveman better) 0.958, 0.999, and 1.000, respectively. We can look at the plots for the other two benchmarks I spent 15 seconds on as well. Optimization 2 is another "optimize this code in wasm" benchmark, and Game AI is a task where the agent is asked to implement a board game AI for the game Lost Cities with a deadline of 10ms per move.

The results with these benchmarks look mixed. ### LLM Variance

Recently, when new models have been released, I've done a search to see what people are saying about them. In general, there are a lot of contradictory comments out there. For example, when GPT-5.5 was released people said, variously, GPT-5.4 is better than 5.5 because it's better at staying on task while 5.5 wanders off and overthinks the problem, making 5.5 much more expensive and pointless; 5.5 is so much better than 5.4 that it's cheaper to use because it doesn't mess up and then get stuck fixing its own issues as much; 5.5 is cheaper than 5.4 because it works so well you can run at a lower effort level; 5.5 "just works" while 5.4 often fails and needs handholding, etc. Often, someone will run a benchmark and show that their statement is true.

Looking at these benchmarks, we can see support for all of these statements that I saw on reddit when searching for comments on GPT-5.5 shortly after release. In Optimization 1, GPT-5.4 has better results than 5.5 and is much cheaper. But in Game AI, GPT-5.5 is substantially better than 5.4, so much so that 5.5 high costs about as much as 5.4 xhigh, but with better results, and 5.5 medium is cheaper than high with significantly better results. With just these three evals, you can find support for every statement I saw people making about GPT-5.5 on release because all of the statements are sometimes true. And that's when we're averaging out variance with quite a few more runs than any reasonable person is going to make to support some comment they're throwing out on the internet.

In general, this kind of thing is why, when I see a metric or graph that summarizes a set of benchmarks, I think, "show me the distribution". Benchmarks of models often reduce to a single, nice, neat number, where you see that X is better than Y, which is better than Z. I find these to be basically meaningless, in that, if we're looking at the latest and greatest from OpenAI and Anthropic, we know there are reasonable benchmarks where X is better than Y and vice versa. If the set of benchmarks had a few more benchmarks that favored Y instead of X, the results would be flipped. For some kind of summary metric like that to be useful to me, it would have to be the case that the set of benchmarks perfectly mirrors the distribution and weight of tasks I do and that I can only choose a single model to use for all tasks. Since neither of those is true, it’s not clear what actionable information I can take away from these benchmarks.

If we look at public benchmarks in more detail, the situation seems worse than it appears from the abstract argument above. Results are generally presented in fairly high precision, as if that's meaningful. For example, on DeepSWE, we might see that (for example) GPT-5.5-xhigh is 1% better than Fable 5 medium, but at 19% lower cost. And then if we compare to Opus 4.8 maybe it's 13% worse than GPT-5.5 xhigh at 11% higher cost. If we want to know what this means, we can dig into the data and see that we have some benchmark that claims to be meaningful because it has this big set of diverse tasks, but they're all pass/fail tasks that get run 4 times and most tasks are either very easy and get 4/4 with the best models (except, due to some random noise, you sometimes see a random 3/4) or are very hard and mostly get 0/4. Then there's some small subset of tasks that actually determine the relative scores of these SOTA models. If you change out one of these for a different one, the results between the two highest scoring models can get flipped. If you change a few tasks (out of about 100), then you can see the apparently much worse Opus 4.8 move ahead of GPT-5.5. Change a few more tasks and GLM-5.2 can pull ahead.

When I see things like this, it reminds me of Miguel Indurain, who was enough of a household name when I was a kid that I'd heard of him even though I don't follow cycling. A few years ago, I was curious why household names in cycling since Indurain are all different archetypes from Indurain and it turns out the answer is that it's arbitrary. For arbitrary reasons, the Tour de France has become the most famous cycling race in the world and someone who has a dominant streak can become famous enough that they become known outside of cycling circles. For other arbitrary reasons, there was a period of time where the TdF had much longer time trial stages than it does now, which suits someone of Indurain's archetype. You tweak the benchmark a bit and Miguel Indurain goes from being a once household name to an all-time great time trialist that pretty much nobody has heard of unless they follow cycling.

Back on the topic of coding agents, it's not clear who really needs to pay attention to these benchmarks that present summary metrics of how models are doing. As we noted above, as a user of models, these benchmarks don't meaningfully tell me which model I should use.

If many other users based their decisions on these benchmarks, then AI labs would need to care about their results on these benchmarks. But even though GPT-5.5 has been handily beating the various Opus 4.x models during 5.5's tenure on most of these benchmarks, Anthropic's business grew much faster than OpenAI's during the time period that the best publicly available models were GPT-5.5 and Opus 4.6/4.7/4.8, so much so that OpenAI has been giving companies free tokens to try to convince people to use GPT. My company was one of many to get months of free tokens and, during that time period, most people still primarily used Claude and Opus. Anthropic's revenue trajectory is incompatible with these benchmarks being major determinants of user choice, so I don't know why anyone should really care what these summary metrics show.

The last set of graphs we looked at shows how much variance we see across tasks, but from the prior set of graphs, we also saw a lot of variance within tasks with the same model and effort level. If we look at a small number of individual runs, then pretty much any conclusion is possible due to the variance between runs. Just for example if we look at Optimization 1, for GPT-5.5 xhigh, one standard deviation between runs is 0.075 (i.e., 7.5% performance increase / decrease). If we look at the average difference between the best and worst tested GPT, that's 1.055 (GPT-5.4 xhigh caveman) and 0.986 (GPT 5.4 mini low), which is less than 1 standard deviation (SD) across GPT-5.5 xhigh. For the actual graphs and not just summary statistics, we have:

For every task, whatever the best condition is, it's easy to get a result where the best condition actually scores worse than a result from the worst condition. When I was chatting to Max Bittker, who's done a lot more benchmarking than I have because he runs an RL environment startup said:

> Yeah - the level of noise from task to task and run to run is so high that it's no wonder the discourse ends up confused. Easy to make mistakes like "Wow, $new\_model is amazing" -> "Oops, I was still using the old model the whole time", or "this new harness / prompting trick works great!"
>

Another comment, this time loosely paraphrased because this is from memory, was that Matt Mullenweg said that, if you look at people who undertake high variance activities, like gamblers, they're often superstitious. You'll see somebody wear their lucky socks or have a specific routine they do before they sit down to play the slots. Using caveman mode or deciding which model is good because a coding agent coughed up a good result after trying it is not so different.

I did the above and wrote the draft of this post before Fable was released, and then Fable was released, so just out of curiosity, I ran a few Fable benchmarks, at which point it was unreleased, so I also did a few runs with Opus 4.8. \[This post was then edited after the 5.6 release to add 5.6 benchmarks to the graphs below\]

Like I mentioned above, these are little benchmarks I created by typing to an agent for about 15 seconds a piece. With how coding agents let you scale processes, you could create a very large number of reasonable benchmarks in 15 seconds of a human time a piece, but this isn't some carefully designed setup for stamping out a bunch of these; it's just something I did because I wanted to get some kind of caveman mode comparison, and when I tried to have agents do this with no supervision, the benchmarks were completely worthless. With a little bit of time spent, the benchmarks seemed good enough for the purposes of evaluating caveman mode and determining that it's not worth further investigation. If I was planning on writing this up publicly, I would've spent a few more minutes making these benchmarks better in multiple ways, but I think they're good enough for the purposes of this variance discussion. I wouldn't read too much into the reuslts, but I did do a few basic checks such as looking at outlier results to make sure agents weren't cheating or there wasn't some issue (such as noise on the box) causing unusually poor runtime results, and the agents weren't cheating and the slowest results did reproduce on a quiet box, etc.

And, that disclaimer aside, just like with the GPT benchmarks, we can see variance in these benchmarks that reflects the discussion that's happening online, e.g., Fable is great at some tasks and not so great at other tasks, and quite a few people are making claims about Fable's overall performance based on the performance on some small set of things they tried. As we noted above, OpenAI does better than Anthropic at DeepSWE (GPT-5.5 =~ Fable 5 > Opus 4.8), and we can see a benchmark where we get an analogous result in Optimization 1. The other widely cited benchmark people keep passing me is Senior SWE-Bench, where Anthropic does better than OpenAI (Fable 5 > Opus 4.8 > GPT-5.6 Sol) and we can see an analogous result in the Game AI benchmark, where we have Fable 5 > Opus 4.8 > GPT-5.6 Sol > GPT-5.5).

Above, we discussed why it's not clear how I or any particular user of agents can usefully use these benchmarks that produce a ranking or a small tuple of numbers that allegedly tell you how good a model is. But even when drilling down into a benchmark, it's still not clear to me why, as a user, how I should change my behavior as a result of the benchmarks.

Just for example, something I've observed is that Opus 4.8 makes up bad rationalizations to explain things much more often than GPT-5.5. I've tried having them approach the same problem a number of times (I'll often ask both to solve a real problem I'm running into just to see what happens). These are often much larger problems than these benchmark problems, things like real debugging tasks or, in the case of building a game AI, instead of a simple prompt to produce an AI, an agentic loop and/or a series of instructions to get the agent to produce a fairly strong AI. I've asked a small handful of people and they've all observed the same thing with GPT-5.x vs. Opus 4.6/4.7/4.8, including people who prefer Claude and primarily use Claude and are more experienced with Opus than with GPT.

On the flip side, I've seen two benchmarks that measure how good models are at detecting false information and/or not making things up and those benchmarks both show that Opus is much better than GPT at this, to the point where, if the benchmarks show what one might expect them to show, the experiences I and other people have had seem impossible. For example, in one benchmark, a naive reading of the benchmark presentation is that Claude Opus and Sonnet are much better at detecting false information than any other model and Opus 4.8 is the absolute best and detects false information 95% of the time, including 95% of the time in software. The GPTs are terrible at this and rank below Qwen, Grok, Kimi, Minimax, Mimi, and Nemotron.

What's going on here? I'm not sure.

Maybe those benchmarks are measuring a different aspect of making things up than what the people I've talked to (and I) run into while working on real programming problems, or maybe this is a small sample size and the people I've talked to (and I) have just randomly gotten bad rolls of the dice from Opus, or maybe we're "holding it wrong" when it comes to using Opus. I suspect what's happening is that the benchmarks are measuring something different from what happens when you encounter incorrect rationalizations while coding or debugging, but to have any confidence in this I'd have to run some experiments that will be fairly expensive. If you want to support my doing experiments in general, you can [subscribe to my Patreon](https://www.patreon.com/danluu) or, if you're at an AI lab, give me some free credits to run experiments with.

BTW, there's something analogous in the Game AI benchmark here, where Opus is substantially better than GPT, but when I tried to have to manage the process of creating an actually strong (superhuman) game AI, GPT seemed to do better because Opus kept falling into making things up / rationalizing nonsense failure mode. With no supervision, both were worthless and had their own failure modes, but when directed, GPT took less prodding to stay on track and keep doing things that could work. This is not reflected at all in the small Game AI benchmark where an xhigh run is a single prompt that "only" costs on the order of $10 and the small benchmark turns up the oppposite result as we see in doing the real version of the task.

But, the point here is that, even when you find benchmarks that measure something that seems to be the exact thing you care about, those benchmarks often don't end up matching what you see in practice. If you're a weirdo like me maybe you'll decide to spend a bunch of time and/or money running some experiments to figure out what's going on but, if you have some job you want to get done (maybe for your actual job), that's a fairly unreasonable thing to do.

BTW, there are some patterns in the benchmarks that people often find counterintuitive. Unlike a discussion of which model is better based on publicly available benchmarks (which is pointless), I do find this somewhat interesting and informative. We already noted above that there are benchmarks where GPT-5.4 outperforms 5.5. It's also the case that we can see that, more effort can make results better or worse. For example, in Optimization 1, GPT-5.6 Luna gets monotonically worse with more effort and it generally gets worse in Optimization 2, but it monotonically improves with more effort for Game AI. We can also see that max fares worse than xhigh for GPT-5.6 Sol in Optimization 1 and Game AI. With GPT-5.6 Sol, ultra is better than max for all three benchmarks and actually cheaper than max for Optimization 1 and Game AI. Even within one provider or one model, a lot of things people would intuitively expect (such as better results from more effort) aren't true. When you add in the larger differences we see across different providers, there's a very high degree of heterogeneity in results that makes simple statements such as X is better than Y generally wrong except in cases where there's a very large difference in capability bewteen models. But as noted above, We can easily find, without cherry picking, cases where Anthropic's last-generation model outperforms OpenAI's current generation model and vice versa.

When I've seen people throw these benchmarks around, they're often just used to back up someone's superstitious beliefs, e.g., at work, I saw someone cite Senior SWE-Bench's result that Fable 5 > Opus 4.8 > GPT-5.6 Sol, saying this is realistic (from someone who believes Anthropic is way ahead of OpenAI). Of course someone could just as easily cite DeepSWE, which shows the opposite.

Everyone whose judgment I trust on these things find these benchmarks to be fairly bogus because the idea that, today, Anthropic's last-generation model is, overall, better than OpenAI's current generation model or vice versa doesn't really pass the sniff test for someone who's used these things a decent amount. When I've asked people I trust outside of AI labs how they form an impression of how good a model is, it's generally just going on vibes and collecting impressions from other people who are going on vibes because it's obvious the benchmark results don't give you a better idea of what's going on than you get from just eyeballing things.

### Benchmarking and data analysis

For no particular reason, I've always liked designing experiments and measuring things. This was true long before I ever thought about careers and it's still true today. [As discussed here](https://danluu.com/why-benchmark/), measurement is one of the primary themes of this blog, maybe the primary theme. Lucky for me, this lifelong hobby has been something I've been able to make a career out of. And even luckier, this skill seems to have been made relatively more valuable by coding agents[3](https://danluu.com/ai-coding/#fn:C).

As we discussed above, testing is a rate-limiting factor in highly agentic workflows because when you let agents start doing a lot of things, anything that's not well tested gets stochastically degraded. The more you ship with agents, the worse this gets. If everything you do is like one of these model evals where every task is a pass/fail task and there's no way to really do better than simply not getting the task wrong, then you can make sure your tests are good enough and let agents go to town until tests pass and everything will be great. In practice, for almost all non-contrived problems, it's possible to have a solution that passes a strict correctness eval but is still better or worse in some kind of non-strict correctness sense. If you want to let agents go wild on a problem (whether this is fast and loose vibe coding or running autonomous agentic loops), now you have a benchmarking problem.

When left to their own devices, running in self-improving loops, agents seem fairly bad at this. There are various little things I've been doing for a few months that get some improvement here (having lots of agents think about things independently and reconvene over multiple iterations with a mix of contrarian agents, etc.), but they still don't seem great at this without human intervention.

One reason for this seems to be that agents are really bad at understanding data and doing data analysis. Doing this in the context of some kind of agentic loop or large problem is harder than doing a standalone data analysis, but when people just have an agent do a standalone data analysis, the results are generally terrible without a lot of guidance. Because it's so easy to have an agent do data analysis, I've seen quite a few agent led analyses and, at least so far, every one that I've seen is completely bogus. I've also done a fair number myself (I think people really underrate the value of getting completely bogus output from an LLM; more on this shortly) and found the same thing.

When I say complete bogus, I mean things like finding different numbers that aren't really related and somehow inferring something deep about their relationship, picking two numbers or examples out of many and coming up with a theory that contradicts other numbers in the data, making plots that show something meaningless (but often look pretty), etc. For a random concrete example, the last time I looked at an analysis produced by an agent (I glanced at this as I was writing this), someone had asked an agent to analyze the resource utilization of something. This was Opus 4.8 on max (Fable was disabled, so this was the best thing money could buy from Anthropic at the time) agent determined that 514% of the resources were being consumed by some task where it was impossible that more than 100% of the resources could possibly be consumed in any way. I have a colleague who sometimes comments on these things and will ask innocuous questions like "what does X mean?". Generally, he either gets no response or what appears to be some kind of AI-written response that's as incorrect as the first thing he replied to.

Anyway, when I started using agents for data analysis, maybe in November 2025, I found the speedup to be pretty incredible. There are analyses that, roughly speaking, would've taken weeks that instead take hours.

I hesitate to even describe this next thing I've been doing because of how many completely bogus data analyses I'm already seeing, but something I've been doing a lot of, which I find to be a much larger speedup than doing a "normal vibe coded data analysis" is to run a simple agentic loop where the agent (or agents) "understand" and analyze the problem and then fix up the parts that need to be fixed for me to extract a good analysis from what the agent has produced.

How much this bogus LLM loop speeds things up depends on the problem, but the last time I tried it, I think a traditional pre-LLM analysis of the issue would've taken me some number of days. Let's say two days. With a workflow where I'm multitasking and poking the LLM when it needs poking, my guess is that it would've taken one to three hours of my time over the course of a day or two. With this "have the LLM loop on producing a result I know will be wrong" workflow, it took about five minutes of my time over the course of a few days to get an acceptable result. Literally every time I looked at any part of the analysis I hadn't previously corrected, the analysis was wrong (and, in some cases, I had to issue multiple corrections) but, somehow, the whole thing still moved a lot faster than if I tried to steer the LLM.

I think people are really underestimating the value of getting completely incorrect results out of an LLM. This is, non-ironically, a game changer in a positive way, when directed correctly.

There's something a bit odd about how incredibly bad SOTA models are at data analysis and how much they speed up human data analysis. I have this series of exercises in benchmarking, evals, and experimental design ([part 1](https://www.patreon.com/posts/107155602), [part 2](https://www.patreon.com/posts/109004070), [part 3](https://www.patreon.com/posts/118646029), [part 4](https://www.patreon.com/posts/127627543), [part 5](https://www.patreon.com/posts/149123122), [part 6](https://www.patreon.com/posts/160473058)). When GPT-o3 was released, Tyler Cowen said that o3

> wipes the floor with the humans, pretty much across the board ... I don’t mind if you don’t want to call it AGI. And no it doesn’t get everything right, and there are some ways to trick it, typically with quite simple (for humans) questions. But let’s not fool ourselves about what is going on here. On a vast array of topics and methods, it wipes the floor with the humans. It is time to just fess up and admit that.

This prompted me to try asking the questions from these exercises to SOTA models. They generally underperform what I'd expect from a reasonable junior colleague unless you specifically word the question so that models can answer the questions. If you just ask the question the way you'd ask the question to a reasonable human colleague in real life, they generally don't do well. This isn't just a theoretical problem that comes up when someone asks an evals homework question. This issue comes up any time you ask an agent to do some kind of empirical, open ended, longer horizon improvement task.

I've seen this issue come up on a wide variety of real world problems, but it even comes up on contrived problems that don't have almost any of the messiness of real world problems. An example of this that I think is a nice problem is building board game AIs. This is a much easier problem to evaluate than most real-world problems because, at the end of the day, you want to beat humans and other AIs on a well-defined game that has a simple win/loss/draw result.

Agents can't really figure out how to do this when left to their own devices. To be fair to AIs, this problem is somewhat harder than internet commenters give it credit for. For example, if you just search for information on how to implement these things, you see all kinds of exchanges [like this](https://news.ycombinator.com/item?id=34802039) [or this](https://news.ycombinator.com/item?id=20034115) where someone who hasn't done it will explain why it's easy and someone who has will tell them it's harder than they think. Most of the online tutorials aren't very useful, to the point that [the author of the well-regarded bullet library suggests that beginners avoid looking at](https://github.com/jw1912/bullet/blob/main/docs/1-basics.md) "\[a\]lmost any article/blogpost/book on \[a board game AI technique\] that isn't backed by the author's strong \[board game AI\]". While the problem isn't exactly hard, it seems to have enough pitfalls to trip up most people (and all publicly avialable LLMs).

When I first started trying to implement a board game AI (this was in the GPT-5.1 to 5.2 days), I didn't know anything about board game AIs and tried having coding agents implement what they thought would work. Now that I know a bit about board game AIs, I can say that every direction GPT tried to suggest was bad and couldn't work. As an experiment, I tried this again recently, when GPT-5.5 and Opus 4.8 were the best publicly available models and they failed in the exact same way and suggested many of the exact same bad ideas (just to really make sure, I let them implement the bad ideas and they failed as expected). When Fable became available, I also tried this with Fable and it also failed in the exact same ways. Fable was better in practice as it was able to work effectively in an autonomous loop after 15-20 corrections, which Opus 4.8 and GPT-5.5 were not. BTW, this is another example of a kind of thing that public benchmarks fail to capture.

But back on the topic of LLMs iterating without guidance, I think, at some level, this is a fairly well understood gap in LLMs today. Coincidentally, around the time I was trying GPT-5.1 or 5.2 at this, the [Code Clash](https://codeclash.ai/) eval was created, which also tests the same thing and found the same result

> Unable to Iterate: Models struggle to improve over rounds, exhibiting a variety of failure modes.

Despite agents being terrible at setting direction and me not knowing anything about board game AIs, I was somehow able to cobble together [a superhuman AI for Azul](https://danluu.com/game/tile/) in about 5 hours of my time with GPT-5.1/5.2 and get it to a crushingly strong level that's well above any other AI that was out there at the time (and I think still out there now) in about 20 hours of my time. The Azul world champion and probably strongest player in the world overall said:

> the bot is quite insane now. def seems stronger than me, though to really test it i would have to play it like a turn-based game. with limited time on my end, i stand no chance 🙂[4](https://danluu.com/ai-coding/#fn:B).

As much as I'd like to be able to say there was "one weird trick", there were really two tricks, but two tricks isn't so bad, especially when they generalize to other kinds of projects as well. The two tricks were:

-   Look at the data / have some reasonable-ish evals
-   Solve problems systematically

None of this has to be very rigorous. In fact, I'd say this was all running on vibes (in the pre-vibe coding sense of the word). For the data side, for this project, I used a common habit for me, plotting a bunch of things that seemed relevant, eyeballing them, and then nudging things in a direction that I would hope improves things. A more rigorous (and possibly better) approach is to run a bunch of experiments from scratch, do "ablation" runs where you add or remove individual ideas, etc., and understand what each component does and what the impact is. But I wanted to get a strong AI while using as little of my time as possible and just training on my laptop and doing things rigorously seemed too expensive given those constraints.

I'm sure all of this would've been trivial for someone with ML experience, but there were a bunch of little things I had to observe and then find ways to deal with (which is something agents are currently terrible at). For example, in terms of figuring out a good set of evals to look at it, there are a few funny things. One is that you can easily make changes that reduce [loss](https://en.wikipedia.org/wiki/Loss_function) but don't change the win rate against actual opponents (humans or other bots) and vice versa. Another is that, if you try to track improvement in terms of how well your bot beats previous versions of itself, it's very easy to make a series of changes that allows the bot to beat all previous versions of itself and have an apparent Elo gain of 1000 or 2000 against prior versions that isn't any better against humans or bots that play in a different style. And, at the time, there was no superhuman bot that was available to play against, so you couldn't get a reasonable eval by just playing against a field of existing bots.

For a human, these aren't really hard problems. A reasonable human can look at one of these issues, think for a few minutes, and come up with a proposed solution that will probably work (and when it doesn't work, they can try another solution). But there's enough subtlety that agents don't do well at this today without supervision (to be fair to coding agents, many or most humans don't either—almost all of the bots I found to play against were fairly bad, despite people seeming to have spent a decent amount of time on a lot of them, with the one publicly available exception being the "PJF98" Azul bot in [https://github.com/cestpasphoto/alpha-zero-general](https://github.com/cestpasphoto/alpha-zero-general)). There was one bot stronger than the PJF98 bot in existence, [but it wasn't made generally available to play against and was just used to win one season on BGA (which was voided because using a bot is cheating)](https://www.youtube.com/watch?v=qkzpeXGwE-4) and then never seen again.

The other trick I mentioned was taking a systematic approach. At a high level, this is because when dealing with an opaque system with some complexity, every time you see a symptom of a bug, there's a good chance this is a window into one or more other bugs that you don't know how to observe. If you non-systematically close the window without fixing the other bugs, those other bugs are still there; you just don't know how to find them anymore.

This is the case when building a board game AI that uses a neural net because you have this net that's doing who-knows-what and some kind of search function that's doing who-knows-what and you can sometimes spot specific obviously bad moves. This is also generally the case with vibe coding and/or agentic loops because you have agents doing who-knows-what and you sometimes get a window into what's going wrong as the giant, overly complex, pile of code the agents produce will emit some kind of obviously bad behavior.

Specifically in the case of board games, I looked at the other Azul AIs that are out there. A lot of people had built bots, especially recently with coding agents making it so easy to build a bot. For some of those, you can actually see how the person tried to nudge the bot (for example, because they included the instructions they gave to Claude in their repo) and, AFAICT, the main reason these other bots were much worse despite more human time spent on the effort was a combination of using the wrong evals and fixing the symptom of a problem and not the cause.

For example, in one case where the author left the Claude instructions in the repo so you can see what they did, at one point, their bot was making a very bad move that's worse than a move that any human would play even if they'd just learned the game. The author instructed Claude to make a series of straightforward fixes that would stop the bot from making that move, which it did, but this didn't fix all of the other bad moves that fall out of the systemic problems the bot has; it just fixed the one very obvious symptom of a bad move that the author could see.

A vaguely analogous issue my bot had is that, at one point, my bot would almost always try to open in column 2. A simple fix that I think would've worked would be to tweak the bot to play in column 2 less often. I tried the various "obvious" fixes like increasing noise to increase exploration in self play, etc., but none of the obvious fixes worked other than directly reducing the value of column 2, but that has this other issue we discussed of not really solving the problem. In that specific case, a more systematic fix that worked and made that bot's play a lot more generally robust was to, at various points in the game, fork the game into a new game with different column permutations. The idea here is, the problem is that, on average, column 2 is the best column, so even if the bot opens in a different column, it will have this tendency to go back to the average best column due to the games it's seen in the past. If you're DeepMind, you can throw a bunch of money at this problem and have the bot play a lot more games and learn something else. But if you're running on a laptop, that could take a while and if you're trying to tweak the weight at which the bot should be nudged away from column 2, there's no way you're going to get a reasonably optimal set of weights to do this with. But if you (for example) sometimes, near the endgame, permute column 2 to column 4, the bot will learn that if you have a nearly filled column 4, it's a winning move to complete it, which will help the bot learn that earlier in the game, if you have a partially complete column 4, it makes sense to advance it to near completion, and so on and so forth, until, in the opening, the bot learns that in the opening, it should then open with a reasonable distribution.

For someone like me with no ML/AI background, getting the bot to superhuman performance was a series of puzzles like this that are a combination of figuring out what the right view of the data is to see problems and then tweaking this systematically to solve the problem. This is not so different from managing agentic loops for general problems. Michael Malis has said that running a "software factories" workflow feels like playing Factorio and I can see what he means by that.

### Misc

I'm not sure how much value there is in talking about specific workflow tips and tricks since the half-life of these is so short. Before I was running more autonomous loops and was doing more human-in-the loop work, "my" agents would often do something that's in direct contradiction of AGENTS.md or other instructions. When I offhandedly mentioned this to Yossi Kreinin, he suggested adding a note at the bottom of my AGENTS.md to re-read instruction after compaction. For all I know, that's a superstitious act that did nothing, but it seemed to reduce the rate of this issue from a few times a day (when juggling a handful of agents at once, so maybe once every few agent-days) to once every week or two (maybe once every 100 agent-days or so). It seems like this isn't necessary anymore, so either this was a placebo that never did anything in the first place and I was just getting unlucky for a while, or the AI labs have added this as well. A trick [we discussed in August 2024](https://danluu.com/codenames/#appendix-writing-the-code-for-the-post), back when LLMs would produce code but not run it by default, was to just have a loop that runs the code to make sure that it works and passes tests. That trick had a surprisingly long useful life considering how obvious and useful the trick was, but of course the big AI labs eventually realized how useful that was and they all have tools that do this now.

For the past few months, the "trick" I've been using is to have something that's vaguely in the same space as something like Gas Town, but with various little things to try to make it more reliable. It seems like Claude's Dynamic Workflows put half of these tricks into an easy to use package (I haven't used it since I'm told that it uses a waterfall model where things from one stage wait on the last one, but either that will be fixed at some point or someone will release something without that limitation) and Codex has some advertised but yet to be released features that seem targeted at doing the same thing. In principle, goal mode should package up most of the other half of the tricks, although it doesn't work nearly as well for now (besides sometimes failing due to a bug, it seems less good at pursuing the goal than a manually written loop, and it can also really get off track; Dennis Snell mentioned letting what he expected to be small task go in goal mode and finding that, according to codex, it spent what would've been $60M in tokens in a few days had his employer not been on an unlimited token deal; on asking again, it then said $200k). Presumably these things will improve and most of what I'm doing now will be available off-the-shelf within a couple of months? Like the tricks mentioned above, these are all things that are so obvious enough I don't know that there's much value in spending a lot of time talking about the details, but I'll put [some brief comments in a later appendix](https://danluu.com/ai-coding/#appendix-agentic-loops-and-writing-this-post) in case anyone is curious.

The meta techniques discussed above have generalized fairly well for me on a variety of projects and they seem like they should be durable as long as agents can't just take a non-trivial problem description and fully solve the problem better than I can, at which point I won't have to worry about it because my economic value may be close to zero.

Another meta idea that's been useful is the very obvious thought that coding agents are highly non-uniform in their effectiveness relative to humans. When discussing about traditional productivity, [Fabian Giesen made this comment on how velocity improvements change how he works](https://danluu.com/productivity-velocity/):

> There are "phase changes" as you cross certain thresholds (details depend on the problem to some extent) where your entire way of working changes. ... ​​There's a lot of things I could in theory do at any speed but in practice cannot, because as iteration time increases it first becomes so frustrating that I can't do it for long and eventually it takes so long that it literally drops out of my short-term memory, so I need to keep notes or otherwise organize it or I can't do it at all. Certainly if I can do an experiment in an interactive UI by dragging on a slider and see the result in a fraction of a second, at that point it's very "no filter", if you want to try something you just do it. Once you're at iteration times in the low seconds (say a compile-link cycle with a statically compiled lang) you don't just try stuff anymore, you also spend time thinking about whether it's gonna tell you anything because it takes long enough that you'd rather not waste a run. Once you get into several-minute or multi-hour iteration times there's a lot of planning to not waste runs, and context switching because you do other stuff while you wait, and note-taking/bookkeeping; also at this level mistakes are both more expensive (because a wasted run wastes more time) and more common (because your attention is so divided). As you scale that up even more you might now take significant resources for a noticeable amount of time and need to get that approved and budgeted, which takes its own meetings etc. There's something analogous about agentic coding velocity improvements. People sometimes make claims about how agentic coding is [100x or 1000x more productive](https://www.patreon.com/posts/160473058). When I look at tasks I do, it's hard to really pin down a number because you can't effectively lift-and-shift a human workflow to agents, so I'm doing something very different from what I would've done in the first place. For example, we look at the idea discussed above of having agents look at every support ticket to convert support issues into PRs. If I were to claim some kind of speedup here, it would be a huge number, easily more than 1000000x. But of course I wouldn't read every support ticket myself, so such a claim is meaningless. A more reasonable way to estimate this would be to try to figure out what kind of traditional organizational structure would generate that many bug fixes using classical techniques and estimate the ratio, but the error bars on an estimate like that will be more than one order of magnitude and it's also not something that would've been done at any normal software company, so the comparison is once again meaningless. It's like someone who drives 20000 miles a year saying they saved 6000 hours and got a 15x speedup on their commute by driving because that's how long it would've taken to walk the same distance. It's clear that the driving enabled them to do things they wouldn't have been able to otherwise do, but there's no point in discussing the ratio.

Another example of a place where you can claim a massive speedup number, possibly more than 1000000x, that's a meaningless number is, when trying to get an LLM to generate a fuzzer in a semi-automated way, I've tried having an LLM look at the entire commit history and all bug fixes, as well as every plausibly related support ticket in history, to try to get the LLM-written fuzzer to be able to reproduce the bugs in some general way. This seems to have been useful to do, but it's hard to put a real number on the value.

For me, the effective value of LLMs is that there are a lot of tasks that would've been too time consuming to reasonably do that can now be done fairly trivially. In a footnote, I mentioned that there are lots of apps you can just trivially build now, so I sometimes play online board games on a custom app that's just a nicer experience than I can get on any of the major board game platforms (which is also nicer than the typical dedicated app for a board game).

In things that I mostly do to satisfy my curiosity, but that can also have some relevance to a business, I'll also do data analyses that didn't really seem worth the time before. For example, I've long been curious about the ratio of user-experienced bugs to support tickets. With coding agents, it took minutes of my time to get agents to produce a list of major incidents where we know that every user that tried to access the site or use a feature couldn't use the feature or site and to get a list of tickets that appeared to be associated with each incident. On joining this data, a typical ratio was 200 impacted users per ticket, with the ratio often being between 100:1 and 1000:1 (and, I'm sure, a wider range would've been found if more incidents were included). FWIW, I pre-registered a guess of 100:1 to 1000:1, leaning more towards the 1000:1, so I was somewhat off here as the typical 200:1 is closer to 100:1 than it is to 1000:1.

Of course, there are a lot of holes in this analysis. There's no way to tell for sure that there aren't missing tickets (I did check for false negatives by independently cross-checking with tickets that were manually tagged in the bug tracker as being associated with an incident and the main thing that turned up was that agents were able to find many more tickets than humans found, but that doesn't mean that that aren't false negatives the eluded both humans and agents). I also randomly sampled a handful of tickets to see if the associated tickets were reasonable and they seemed reasonable, but this was just a quick order-of-magnitude analysis, so I didn't manually inspect as many tickets as would be necessary to really validate a high precision analysis.

It's also not clear how the ratio changes for less severe issues. It should generally be the case that, for less severe issues, the ratio is higher, and also for less invested users (such as the typical user in the sign-up flow). My guess is that, for many less severe issues, we generally see ratios well above 1000:1, with the ratio being easily above 10000:1 or even above 100000:1 for many subtle issues.

This analysis doesn't let me say anything too precise, but it does work as a response to when someone says "only six users were impacted" because an issue had six tickets. That typically means that there's an internal bug tracker ticket for which someone attached six support tickets. On using an agent to search for related tickets, you might find twenty-five tickets and then, looking at the issue severity, you might estimate a ratio of 10000:1, so "only six users were impacted" may turn into "it's overwhelmingly likely that at least 5000 users were impacted and plausible to likely that 25000 users were impacted".

If I was already familiar with every system I'd need to query for this analysis, I suspect getting a rough guess for this would've taken hours and it would've been a rougher guess. But given that I wasn't familiar, I would guess that this would've taken a couple of days. Instead, this took maybe 15 minutes of my time. Like Fabian mentioned, this kind of speedup where an app or analysis that would've taken hours or days can be done is a phase change that really changes how you work, and that's not even including autonomous loops that only need occasional maintenance.

Another thought, and it wasn't obvious to me in advance that this would be the case, is that LLMs seem to be a larger productivity multiplier for people who are relatively more expert at the thing they're trying to do. On looking around for commentary on this, I of course got pages full of LLM generated SEO spam and, after wading through it, I saw quite a few comments indicating the opposite. Basically, that anyone can do anything now. While that's more true than it used to be, it seems to be even more true that expertise in an area has become more valuable. Max Bittker had a comment that this is at least partially because LLMs are good at counterfeiting things, but that counterfeits aren't that good (yet?), and experts can tell the difference between a counterfeit and the real thing, which I thought was an interesting framing.

And following up [on this 2015 post about how many people are underestimating how much AI will displace humans](https://danluu.com/customer-service/), in the past year, my median LLM-driven remote customer service interaction has been better than my median human remote customer service interaction (a well-paid human would provide a better experience than all but maybe one of my LLM-driven experiences, but companies don't want well-paid humans). The exact same line of reasoning that was rebutted in that post 2015 [was repeated in 2022 on the release of ChatGPT](https://mastodon.social/@danluu/109458271351706514). The line of reasoning is so popular that it's been a repeat thought leader viral hit every year since 2022 and I don't see that changing any time soon, but it still seems wrong to me today.

By the way, [as we previously discussed](https://danluu.com/learn-what/), there are lots of ways to be an effective programmer, so I'm not saying what's discussed here is the best way to do things or even a very good way (I'm changing my workflow regularly as I figure out new things) but this is what I've been trying that seems to work better than a purely traditional workflow for me. Just given my background and interests, it's natural for me to take a systematic, evals-driven, approach to agentic coding. I've seen people use what is pretty much the opposite approach and make it work for them as well, where they move very quickly without almost any understanding of what's happening and, when they strike gold, they recursively put all of their effort into that. Not only is that not a great fit for my background, I don't think it would really work well for most of the problems I've worked on, which I select because they seem like a reasonable fit for how I approach problems. No doubt my workflow, ported to the problems the opposite kind of workflow is suited to, would also not work very well.

### Appendix: people talking past each other

It's always been the case that people talk past each other when they disagree, but this seems to be more of an issue when talking about agentic coding today than it has been for a lot of other topics.

Some of the major reasons I've seen for this are:

-   General incredulity
-   Workflow-based reliability differences
-   General workflow issues, i.e., "skill issue"
-   Differences in expectations

On general incredulity, moreso than at any other time in my life, I see people saying that X is impossible, nobody does X, and anyone who claims that they're doing X is a liar, when I know people (who I trust and are credible) doing X or I'm doing X. There's a lot of incredulity out there about AI. Eleven years ago, [we looked at how people were saying AI can't possibly replace or displace humans even as it was already happening](https://danluu.com/customer-service/), but the kind of displacement there wasn't a serious fear for a typical middle-class person or programmer, so it wasn't as salient for folks I might run into "on the street" as it is today. Now that this is more "in your face" for people I'm running into, the amount of denying reality has shot up.

BTW, I find it quite reasonable that a lot of people are incredulous. For one thing, a lot of the positive claims about AI are incorrect. On average, wild, incorrect, claims get more traction than boringly precise and correct claims, so someone who isn't following this stuff is going to see a lot of incorrect claims that are easy to dismiss. It doesn't help that a lot of the people making these claims have a direct financial interest in the general success of AI companies, which makes it easy for skeptics to conclude that these people are all self-interested liars.

On workflow-based reliability differences, what I mean is that different workflows demand different levels of reliability and people who use a workflow that demands a higher level of reliability will often claim AI is useless because it can't do X reliability, missing that there are many effective uses that don't require that level of reliability. To take an extreme example, some people have done novel mathematical research and solved open problems using AI. Let's say, hypothetically, AI solves some open problem you're working on 1 out of every 100 times you try it and returns completely gibberish 99 out of 100 times. That seems great. Solving a serious open problem in math research 1 in 100 times is a pretty awesome result, even if doing a reasonable code review 1 in 100 times and producing a bad code review 99 out of 100 times would be a bad result.

For a less extreme example, for programming work, if you don't assume that the agent is 100% reliable and build systems to handle this, you can tolerate a much lower level of reliability than somebody who assumes the agent is reliable and needs some kind of human-in-the-loop correction to deal with cases where the agent isn't reliable. I regularly see people give advice saying, "don't use AI for X \[because it won't work 100% of the time\]" where I know someone who does X all the time and have some boring system for handling X not being 100% reliable. This is something you commonly have to do in programming regardless of whether or not you're dealing with agents, so why not use the same techniques you'd use to handle agents being unreliable?

Differences in scale also cause people to talk past each other as people have very different reliability demands at different scales. There's an old rule of thumb that, for traditional software systems, for every order of magnitude increase in scale, you need a different architecture. That's not really true, but it gets at this directionally correct idea that you really want different architectures at different scales. This is also true for using agents.

Just for example, one that I've seen come up repeatedly related to the earlier note that, on tasks that I do, adding a clear, strict, instruction in AGENTS.md to not do something fails once every week or two when juggling 10 agents, a failure rate of something like one per 100 rule-agent-days. Does this work? If you're doing human-in-the-loop coding with a relatively small number of agents and rule (say, 10 agents, 10 rules) with failures being non-catastrophic things that are usually caught by human review, this works fine. If you're running hundreds or thousands of agents or if you're shipping without review or other guardrails even with only a few agents and failures can cause serious problems, this doesn't work at all. While some techniques are scale invariant, many aren't.

Another kind of workflow issue is when people have a workflow that can't work for X and then conclude that nobody can do X because they weren't able to do X. I haven't thought too much about the specifics of what doesn't work, but Max Bittker had the following comments:

> A few patterns I've noticed, not in order:
> 
> 1) People sometimes have misconfigured environments: They're on an old model, they have a bunch of MCPs or after-market system prompts turned on, or the LLM is trying to deal with Windows or some unusual environment or IDE.
> 
> 2) People sometimes trash their context window by using a single super long chat with lots of backtracking or single super-messy working directory.
> 
> 3) Injecting accidental requirements via imprecise language, sending the LLM off on a harder task than they intended like building a matchmaking system before the core of the game
> 
> 4) If you don't have a strong idea what you want or when you're done, you might under-specify and then collaboratively drift and change requirements over time and going nowhere in particular (many AI-psychosis vibe coders do this)

### Appendix: agentic loops and writing this post

As I noted in the alt text at the start of this post, I was very hesitant to write about AI for years because I'm up here in Galapagos Island, highly disconnected from what's happening because I haven't been reading social media much and I've also been doing a bad job at keeping in touch with folks who are really in the thick of it in SF.

I was convinced that it might make sense to write something in May, when I chatted with a couple folks from SF who were in town for PGConf. Even though they are in the thick of it and seem to be close to the cutting edge of what people are doing with agents, there were still things from my workflow that they thought were interesting. But, like I said, the half-life of particular workflow tips and tricks is short enough that I didn't think it would be useful to write up detailed notes on an exact workflow, which is why the main post has focused more on higher level ideas. I'm not sure what might actually be useful, but I'm going to try writing up something about the evolution of my workflow. As noted above, I don't think there was any point in time where my workflow was great, exactly, but it was useful and there always seemed to be a natural next step to make it a bit more productive.

Back in the stone ages, before tools like Claude and Codex, I would sometimes just run a very simple loop that would just keep compiling the code and running the tests and re-prompting until everything passes, [which I mentioned here in mid-2024](https://danluu.com/codenames/). At the time, I didn't find this useful enough to use for anything where I knew what I was doing, but it enabled me to embed a little web game into that post and do other tasks that would've required me to learn something about an area where having actual expertise will probably never be particularly interesting to me, such as building a web app.

That kind of thing was mildly useful for quite a while when I wanted to accomplish some simple task, but I didn't start using agents much until running into the bisect/video story at the top of this post, and doing some other data analysis and seeing how much it could speed up data analysis. BTW, the bisect/video story came out of an analysis where I was wondering what the half-life of a working feature and/or bug fix is. Coincidentally, that analysis is linked to a couple of ideas in the post. First, the half-life turned out to be fairly short pre-LLM, which seemed like a point in favor of more testing if we wanted to turn the dial up on velocity (with or without LLMs). And, second, this is yet another analysis that would've taken long enough that I wouldn't have done it pre-LLM.

At some point mid-late 2025, I tried vibe coding some personal projects. I used Codex just because people said it gives you more quota on the subscription plans (I've since tried both and that seems to be accurate). At that point, my goal was to use as little of my time as possible on personal projects while getting the output I wanted, but I hadn't really done any vibe coding before and didn't have any idea what would work, but it quickly became apparent that I did the most naive possible loop, where I would just queue up a bunch of copies of "if X isn't done, implement X until complete; if X is done, ...". I wasn't reading anything about what other people were doing and the people I was personally talking to generally weren't using AI much, so I had no idea that the term "Ralph loop" had been coined in mid-2025 and people were doing various, less cumbersome, variants of this, although this wasn't really all that cumbersome (maybe 5 seconds or so to queue up the copies of the prompt once they're written).

And, in retrospect, this workflow wasn't so bad in terms of steering things in the right direction compared to a Ralph loop. I'd usually look at this a handful of times every day (right before bed, on waking up, maybe a couple other times) and, in general, every time I looked, things would not quite be right and I'd queue up some commands to nudge things in the right direction after looking at the logs/metrics/graphs/etc. that explained what was going on. Since this was for personal projects I was spending a small number of minutes a day on, I wasn't trying to maximize throughput and was just running a few things on each of two different laptops I have lying around. It would've been better to have more autonomous loops that can keep going indefinitely without refilling the queue by hand, but the actual time savings from that isn't really all that much, I think less than 10 minutes per day.

After doing that for a while, I started (sometimes) trying to run more autonomous loops earlier this year. Once again, I think this must've been somewhat behind the curve compared to whatever people are excited about at any given time, but it seemed to work ok. On starting to do that, I found that a lot of the tooling people were recommending wasn't really a great fit for managing agentic loops and the tooling that was designed for it seemed a bit "vibe"-y and would have reliability issues.

An example of the first thing is that Conductor was widely recommended at the time and it wasn't really made to support a lot of things I'd want to do. For example, Conductor has the concept of a workspace to separate things. I often want to invoke what one might call "higher order workspaces", where an agent (or a set of independent agents) decide what should be done with a list of items, after which each item should be fed into another agent (or independent set of agents) (possibly with some limit on agent concurrency), after which, etc., with some kind of graph structure determine how tasks move around, where there are reduce-like steps that look at the output from a bunch of tasks, and so on and so forth.. While it's technically possible to make Conductor do this, it wasn't really designed for it and, given that you can just tell agents to write scripts to create a structure like this, it seemed a lot simpler to just use custom vibe-coded scripts.

The kinds of tools that were designed for use of a lot of agents, like Gas Town, mostly seemed to be for less structured workflows, and they often seemed highly vibe coded and somewhat unreliable as a result, to the point that I wasn't sure why I would want to use one of them and not just cobble together something myself. \[2026-08 update: [in this post](https://yegge.ai/essays/the-shape-of-things-to-come/), Yegge notes that he never succeeded at using Gas Town to build anything, so it seems that my impression of Gas Town wasn't wrong\]. What I mean there is, per the discussion in the long footnote about board games, if something doesn't meet a certain bar for quality and complexity, it's fairly easy to just make a version of it yourself. Even if the thing you make for yourself is buggier than the product, you can make sure that, given your workflow, it doesn't have bugs that impact your particular workflow, so you don't even have to meet the same overall quality bar as the product does for it to be better for you.

As a result, what I've ended up doing is making one-off loops for tasks that need to run for a while. There's probably an efficiency gain from building some kind of orchestrator that fits what I want, but I don't think I've really set up enough of these loops to know what I want, and what I want varies a lot depending on the problem. Sometimes I want to have certain metrics trigger a health check by an agent that can fix issues and sometimes I want an agent or set of agents to automatically be invoked after each iteration (whatever that means) to check on progress and sometimes I want agents to continuously check on progress. Sometimes I want a graph structure with some kind of multi-level triage, etc.

Because it's fairly easy to have an agent set up whatever arbitrary structure you want, I'll generally start with some kind of simple structure with some basic health checks and monitoring and then I'll check in on it periodically and try to make structural fixes to address issues so that the issue doesn't recur. In principle, something like this that's well set up could produce useful work indefinitely but, at least for what I've set up, these loops tend to degrade in productivity over time. Even if nothing is badly wrong, the loops are a lot more productive if I'm actively at the keyboard typing instructions to nudge things in various ways, while monitoring what's happening. If I leave one of these alone for a few days or a week, it will usually still be producing a non-zero amount of useful work, but not nearly as much as if I'd check in daily. I've tried various strategies to try to keep these loops more on track without intervention and I've found various things that can help, but I haven't figured out how to replace myself (yet?).

For example, [in April/May 2026, I tried having a bunch of "personas" convene and reconvene to try to nudge the loop instead of doing it myself](https://mastodon.social/@danluu/116514958701771749). At the time, I was trying to get a loop running smoothly that was doing some work on some code that uses CRDTs (which I know nothing about, BTW), so I tried diagnosing issues with something like "use independent agents to review as linus torvalds, kyle kingsbury, marc brooker, tptacek, dan luu, and 4 contrarian personas. have each think for a long time", with multiple iterations of this (yes, I do find it quite silly to invoke my own name). Each of these personas seemed to keep things on track in a different way, e.g., the "linus torvalds" persona would tend to push back against the loop's "natural" tendency to have things spiral out of control due by repeatedly adding unnecessary complexity, the "dan luu" persona would force the loop to measure things before implementing and also sometimes say things like "we must not rationalize XYZ" and push back on some bad reasoning. None of this was enough to replace human observation and intervention, but doing variations of this was enough to keep these loops running more smoothly, with less intervention required.

This kind of persona setup also improved things for architectural design, debugging, etc. Again, not so much that you wouldn't want a human at all, but enough that the human can do a bit less work.

All of this seems to work best if the human understands the common failure modes. For example, when asked to debug and explain when a bug was introduced, if just prompted to explain, even with multiple independent rounds of analysis, the agents would often come back with a completely incorrect explanation (maybe 50% of the time or so). When asked to confirm their hypothesis by actually executing code to check if the hypothesis is correct, that removed most incorrect explanations. Just adding forced checking to a simple prompt has a better success rate than having agents do independent analyses and cross-check each other (doing both together seems to have an even higher success rate).

A lot of getting value out of agents seems to be having some kind of understanding of their failure modes and then working around them. Earlier in the post, we noted that people aren't really going to be left behind if they're not using coding agents now and get started in M months because they can be at most M months behind, but will likely be much less behind than that because of how quickly things are changing. A major reason for this is, AFAICT, a lot of the skill involved in using agents is working around their failures. Of course AI labs want to fix these failures, which means new releases are designed to obsolete these skills as much as possible. This is possible to observe directly, in some failure modes that were quite common a year ago are now much rarer.

BTW, this is another reason I don't find a lot of benchmarks useful for me personally. In general, benchmarks have moved to trying not to "over explain" and instead act like a naive user who isn't very good at using agents. This is a reasonable thing for AI labs to care about because they want to make a product that needs as little expertise as possible to operate but, as a professional programmer, if there's way to work around some failure mode of agents, you're probably going to use it instead of acting like you're a benchmark, and you therefore get a very different result even if you're doing the exact task from some benchmark.

The argument against having test enginers that I've heard everywhere I've worked, sometimes as test engineers were being laid off, goes something like "the people who can test the code best are the people who wrote it; also, programmers will get lazy about testing if they outsource testing to somebody else", but that's only one side of a trade-off that has two sides.

You can state the same case made against having dedicated testers about having dedicated front-end and back-end folks, mobile engineers, etc.; it's all true. But there's also a true argument on the other side and it's generally acknowledged that, once you hit a certain scale, [the gains from having specialists who understand specific things outweigh the benefits of having teams full of generalists](https://danluu.com/in-house/) who are only kinda ok at each thing. From having seen how good people can get at testing if they spend a decade or two specializing in learning test skills, I think software companies are missing out by not having people with these skills, but this is arguably out of scope for this post since it's not like you can go out and hire a bunch of people with that skillset with respect to software. To even have that population exist, you'd need a culture and ladders like hardware companies have, where verification engineers are first-class citizens, just like logic designers, where they're on the same pay scale, get promoted to high levels at the same rate, have the same amount of prestige, etc., and then you'd have to do that for twenty years.

    The gains here are not just the direct expertise gained from spending a career doing something. The existence of a large community of practice at a company also means that people level up faster at the company. In the same way that I was lucky [to learn a lot about distributed tracing because I happened to sit next to an expert in distributed tracing](https://danluu.com/tracing-analytics/) and I probably learned as much in a few months from that as I would've if I spent years figuring it out on my own, I was lucky to learn a lot about testing because I sat in a cluster of world class test engineers. Even at software companies that were over one-thousand times the size of that hardware company, I'm not sure that they had a cluster of that many talented test engineers who'd spent 40+ years specializing in testing for me to learn from (and if they did, that group would be so far from me that I'd never interact with them anyway).

Just as an aside, I wonder what's going to happen with online board games (except for the end of this footnote, this entire footnote is about board games, and you might want to skip to the bottom if you have no interest in board games). One issue is that there's high "demand" for cheating and there was quite a bit of cheating in competitive online play even before LLMs. Today, it's not all that hard to make a bot that can cheat and it's only going to get easier. I'm not really interested in playing against random strangers online, so I don't generally play ranked/competitive online board games, but quite a few people do. It's hard to see how this survives if the amount of cheating increases.

    Another thing I wonder about is the value of the big game platforms. Board Game Arena (BGA) seems like the biggest platform by a fairly large margin, with Tabletop Simulator (TTS) being second. BGA is, uhhh, you might call it fairly quirky if you're being generous. For example, by default, the platform doesn't really allow players to act concurrently. If you click on anything at the same time another player clicks, it prevents them from doing an action if your click manages to get through to the server slightly before theirs. For games with simultaneous actions or selections, this can cause people to get stalled out of their turns for tens of seconds at a time as other players do their actions. I could write a post the length of this entire post on various issues with BGA, but suffice to say that the other issues you might expect of a multiple player online platform that fundamentally doesn't work if players attempt to act concurrently are problems on the platform. On average, TTS is even clunkier to use.

    As a result of this, it's fairly easy to implement a nicer user experience for games that don't need a complex interface. Game rules and mechanisms don't fall under US copyright law, so it appears completely legal to implement a game with the exact same rules as long as you don't use their graphics, trademarked logo, etc. I don't personally want to try to build a platform with unlicensed games that tries to compete with BGA, but I do sometimes want to play a game without the quirks that BGA has (or that isn't available on BGA). Depending on the game, it's taken between seconds of my time and a small number of hours to get what seems like a reasonable version of the rules working. Seconds is for simple games where the game basically just works from a simple prompt (for example, [here's a game with the same rules as Scout](https://danluu.com/game/flip-taker/), which I implemented because my friends couldn't find a way to play Scout online. BTW, I don't promise the game will work at all if you try it—it's hosted on some kind of janky free tier hosting because, as I mentioned, I'm not trying to build some kind of big platform and this works better than BGA when me and my friends use it, which is the (very low) quality bar I'm shooting for, which is that we don't run into bugs while playing, not that it's a generally robust implementation. And although the runtime performance of my game implementations is very poor compared to what's technically possible, my friends who are used to BGA all comment on how it feels instantaneous because they're used to the much slower performance of BGA. When the platform people are used to is both extremely slow and extremely buggy, it's easy to vibe code something nicer.

    Some games will take longer because current models can't one shot them. In terms of my time, Guards of Atlantis is probably the most time consuming game I've tried to implement. It has a lot of rules because each card has some custom rules and the rules seem unusually difficult for humans to understand, which also makes them non-ideal for LLMs. Relatively speaking, I've observed a much higher rate of people accidentally playing rules incorrectly than I do for most games and I'm not sure that I've seen anyone play correctly unless they're on the official discord and follow rules discussions there or were taught by such a person. Given that, I don't think it would be reasonable to expect an LLM to one-shot the game.

    Anyway, given that it takes between seconds and a few hours of someone's time to implement a board game in a nicer form than on the dominant online board game platforms, I wonder what's going to happen to the dominant board game platforms? Will people keep them because of network effects? A decent fraction of the few people I know who play board games online find network effects to be of little import. For example, see these quotes from the aforementioned #1 Azul player in the world:

    > \[I\]'ve been having a blast experimenting with \[your bot\] during my games recently. the bot finds really cool/creative moves that i would never consider, which helps me become more open-minded to how i approach rounds
    > 
    > ...
    > 
    > playing games against these bots can be quite fun (i havent touched azul on bga in months) if they are of ~equal strength

    It was interesting but I think not surprising to see the top player in the world playing against bots instead of on BGA, for months. One thing with the big online platforms today is that it's actually fairly hard to match up with someone of comparable skill. The stronger a player is, the worse this problem is. Like I said above, I don't really enjoy playing against random strangers, so I don't do it much, but a nearly universal complaint from folks who play competitive ranked games on BGA is what a grind the ladder is. If you're a strong competitive player, almost everyone you match up with is much lower Elo, so you're playing these boring games where you stomp the other player to gain a tiny bit of Elo per game. And then if you make a blunder, you lose a ton of Elo for a single loss. A while ago, I was too sick to do much of anything, so I tried ranked competitive play for a game on BGA and got up to #4 in the world. During the entire climb to get to #4, I played two games against someone ranked in the top 10. Every other game was a fairly boring game against a significantly weaker player. For competitive players, there's the impending problem of rampant cheating, and the existing problem that ranked competitive play is mostly mind-numbingly boring.

    For non-competitive play, BGA is less problematic, but I happen to have been teaching somebody how to play a game as I wrote this footnote and they ran into three different bugs as I was writing this footnote. And, unless you're playing one of the most popular games, there's often a long wait for a game (and even for the most popular games, you're in for a wait during off hours). It's not clear to me why people should be playing on these platforms other than inertia. Maybe inertia is enough of a reason and these platforms will continue to be the place people play, but for someone like me who mostly just plays with local friends when playing online, there isn't really any reason not to use a less buggy and better performing app someone vibe coded over their lunch break.

    This same kind of reasoning seems like it should apply to a lot of other kinds of apps. For example, [here's Josh Bleecher Snyder talking about coding up a shopping list app as he was shopping](https://commaok.xyz/ai/just-in-time-software/). In theory, if software worked, you'd want to use the highly-polished well-tested version that some company has created, but [software mostly doesn't work](https://danluu.com/nothing-works/) and there are a lot of apps where it's fairly easy to whip up a better version than what most people are using today. Of course, there are still many cases where that's not practical, but I still find it amazing how much software I use somewhat regularly can be re-made in a nicer way fairly easily.
