## 核心洞察

一、优化应服务于目的而非手段：Google Prequal 论文的核心在于标题：Load balance、DP balance、Expert balance 都是方式而非目的。优化应服务于最上层指标，如 hit ratio、毛利、TTFT 等。若沿错误 goal 优化会陷入局部最优，需重新定义 loss function。论文将目标从打平 CPU 利用率改为把请求送到有余力的机器，避免过载。
[[#^pr-952e5b9f3df7|正文跳转]]

二、测量应深入一层：核心观点是永远比你以为够了的层次再深入测量一层。常见错误包括信任数字（测量代码可能有 bug）、猜测而非测量（应客观展示数据）、确认偏误（潜意识希望优化有效）。原则包括花时间、用直觉提问而非回答、在下一层抓 profile。深挖根因培养的嗅觉是 infra 程序员最重要的经验。
[[#^pr-a2dcc79a7a55|正文跳转]]

三、反馈延迟决定流量塑形激进程度：Google 2025 论文将负载均衡建模为最小化平均请求延迟，拆分为网络延迟和服务延迟。最小队列 baseline 的状态过时导致振荡，因此采用缓慢切量（如 delta 1%）避免过载。直觉是反馈越慢，越不能激烈塑形；极致反馈可带来极致塑形。对 LLM 节点上下线稳定性有实际意义。
[[#^pr-cb81f69ee7e7|正文跳转]]

四、建模问题比直接优化更重要：对于路由、并行策略收益等大话题，应建模问题（如 tp dp pp ep、bs、ctx length、硬件），虽然不一定准，但逼迫想明白问题再前进。数学建模是漂亮且能产生观点的，方法可能 naive 但建模本身有价值。
[[#^pr-94f708e1d3a9|正文跳转]]

五、抽象需服务于目的而非隐藏复杂度：抽象有两种：一种只是隐藏复杂度，看不见等于不复杂；另一种是真抽象，规定什么能做，服务于目的。复杂度只是转移形式，是否更优雅是主观问题。模块职责、接口、语义需反复踩坑重构，没有捷径。
[[#^pr-6f53ac8d599d|正文跳转]]

六、Infra 需自建 DevOps 与 Harness：多数公司没有专职 DevOps 工程师，infra 需自担。DevOps 优化交付速度、频率、可靠性，让研发流程流水线化。沉淀 harness（如 bench、测试、profile 工具）避免重复劳动，提高效率。好的 DevOps 让人更专注开发研究。
[[#^pr-0a7ff5520043|正文跳转]]

七、先跑起来再追求完美：在 LLM serving 开源竞争下，先跑起来更重要，有流量用户后续迭代顺利。提前思考优化 ROI 低，应快速验证 idea。Pegaflow 和 Openinfer 最初都是 toy project，完美需要时间。用真实数据驱动架构决策，先有能卖的饼。
[[#^pr-f76806444bf0|正文跳转]]

八、Infra 核心使命是降本增效：公司招聘 infra 人才本质为降本增效，如一个亿服务优化 10% 成本省一千万，花 500w 招 team 稳赚。但越往后投入人力更大收益更小，人力成本超过收益时公司会裁员，如 database 公司离职潮。infra 程序员需时刻转型，思考下一个优化点。
[[#^pr-147e8dafe362|正文跳转]]

九、只打高 ROI 的球：Ted Williams 将 strike zone 分为 77 格，只挥击甜区球，纪律性放掉烂球。类比 infra 工作，应只做 ROI 最高的优化，而非什么都做。善弈者谋势，不善弈者谋子。

## 正文

今天突然有所感想，谈一谈我认为的好的 infra taste，或者说怎么把 Infra 做好。想到什么写什么，纯手写，非 LLM 生成。

### 向上看：第一性原理，你的目的是什么？

Google 有一篇论文叫《Load is not what you should balance: Introducing Prequal》，我觉得高光就在于标题。大家常说 Load balance，包括 DP balance、Expert balance，这些是“方式”，而不是“目的”，优化是服务于目的。为什么要优化 hit ratio，更高的毛利？更稳定的 TTFT？对于服务来说最上层的指标是什么。

^pr-952e5b9f3df7

DP balance， Expert balance 都服务于一个指标，TPOT 的改善。

那篇论文的 baseline 是按一个 dynamic WRR 去均衡 CPU 利用率，但问题在 CPU 可能是 VM 的，利用率不等于真实性能。所以论文换成了 requests in flight + latency，核心目标也从“尽可能打平机器的 CPU 利用率”，变成了“把请求送到还有余力的机器上”，尽可能避免“过载”的发生。

如果我们沿着错误的 goal 优化，最后会陷入“局部最优解”，我们需要跳出来，重新定义 loss function，当我们优化时，loss function 到底是什么？

> 不识庐山真面目，只因身在此山中

当然这篇 paper 是 2023 年的，2025 他们又发了一篇，又是一个 taste，后文提。

### 向下看： Always measure one level deeper

说点暴论：如果没有读过这篇，我觉得不是一个合格的 infra 选手。

最早是上学期间吧，看陈硕大佬的某个回答或者博客推荐的，特意拜读了一下，是一篇对我影响非常深刻的随笔。

核心观点就是一个 **永远要比你以为够了的层次再深入测量一层。**

^pr-a2dcc79a7a55

文章中列了一些常见的错误：

1. Trusting the numbers，测量本身也是代码，也可能有 bug
2. Guessing instead of measuring，infra 工程师说话要客观，而非认为、觉得。Talk is cheap, show me your data
3. Confirmation bias：潜意识里，profile 站在对自己有利的角度，我们有时候不希望自己的优化被证明无用，人的潜意识是有一些利己的。

一些有用的原则：

1. Allow lots of time：要花时间。
2. Use your intuition to ask questions, not to answer them. 直觉是用来生成可能性的，而非证明可能性的。
3. Always measure one level deeper：能否在下一个层级抓一个 profile 出来

很多时候，所谓的“证据”“原因”都是“可能”，而非客观证据，真正有价值的洞察来自于下一层。很多时候选择停下，一方面可能因为认知不足，比如我不懂 GPU arch，我没法深入 SM 内部、NVLink 内部，给出一些更有价值的分析；有时候是因为懒，因为惯性，给一个大差不差的原因也能交差，认知的懒惰性。

因为不少人 profile 或者分析问题，也比如 LLM 吧，经常会停在某个中间层，认为这就是原因，不再深入，但其实如果再深一层，再多一些实验，经常会得到不一样的结论。而这些主动向下获得的经验，就是一个 infra 程序员最重要的 taste 和经验。深挖过这些问题根因的，虽然深挖不一定百分百保证原因翻案，但经历过，培养出的嗅觉，会在未来帮助他更快判定问题。

虽然有点王婆卖瓜，但是我的上一篇文章，green context 我觉得就是很好的这个例子。其实实验本身我和 cc 可能一起迭代了二十多个，在不同硬件、不同负载、不同 nsys、ncu flag，虽然写到文章里的可能只有若干几个。大部分实验可能没什么用，但是“实验没用”本身也是一种经验。

### predict before you move

学会建模问题。话题回到 Google 后续的 2025 的那篇论文，标题叫《Load Balancing with Network Latencies via Distributed Gradient Descent》。论文把问题建模了：请求从不同地方来，回到不同地方去，处理有时候也并非一个串行的过程，目标是最小化平均请求延迟，又把延迟拆分为网络延迟和服务延迟。

对比的 baseline 是最小队列，请求给队列数量最小的。但问题在于这个“状态”是过时的，可能是几秒前的，因为路由器和 server 只能通过一定的时间频次通信（在 LLM 里，也许 RDMA 能给一个很新鲜的值，这也是一个思考）。

他认为的 bad taste 就来自于观测的延后性。如果某个人突然很空，请求一股脑打过去，就爆炸了，又一起切换到其他节点，其他节点也开始爆。这其实对于 LLM 来说也是有实际问题的，节点的上下线会造成系统极大的不稳定性，尤其现在需要做 cache aware 和负载混合的调度。

所以论文认为 delayed feedback 导致振荡。

所以论文的做法是：缓慢切量。比如现在 ABC 各自 3 分之一的流量，A 开始观测到“退化”，就开始下调 A 的流量，可能 delta 1% 慢慢过渡给 BC。

直觉就是：**反馈越慢，别激烈进行流量塑形。** 反过来说，极致的反馈，也可以带来极致的流量塑形。这是向上看的一部分。

^pr-cb81f69ee7e7

方法可能 naive，但论文的数学建模是比较漂亮的，虽然我读着有一点晕。但论文里提出的观点也是从他的建模里来的，有机会专门认真读完！

总的来说，我们需要建模问题，我们需要数学。对于一些比较大的话题，比如这样的路由，比如不同并行策略收益的建模，tp dp pp ep、bs、ctx length、选用硬件。建模好问题，虽然不一定准，但这会逼迫自身想想明白问题再前进。

^pr-94f708e1d3a9

### 学会抽象

这里其实很主观。就像之前说的，一种抽象只是隐藏了复杂度，看不见等于不复杂；而另一种是真抽象，规定了什么能做，服务于一个目的。这个问题在于，这是一个主观的问题，抽象需要一定的背景理解，复杂度并没有完全丢失，只是从一种形式转移成了另一种形式，问题在于这个过程真的更能使得“代码更优雅”吗？是一个偏主观的问题。

^pr-6f53ac8d599d

模块的职责是什么，接口是什么，语义是什么，抽象是什么，接口是什么。需要反复踩坑，重构，没有捷径可走。

### 工欲善其事：做自己的 dev ops，做自己的 Harness

> DevOps 是一组实践，用来自动化软件开发团队和 IT 运维团队之间的流程，让他们能更快、更可靠地 build、test、release 软件；目标是缩短软件开发生命周期，同时提高可靠性，并持续交付功能、修复和更新。

在我呆过的几家公司，从创业公司到大厂，其实都是没有这个职责的工程师的。所以 infra 自身要承担起这部分工作。dev ops 的优化支持我们的交付速度、交付频率、交付可靠性，让研发流程本身成为某种流水线。比如如何快速 bench 一个 LLM serving 的 kv cache 在实际 serving 形状下的性能（openinfer 里有一个 vllm bench, multi turn 的 skill），如何测试，测试覆盖面（写更多的 IT、e2e），更方便的测试 `cargo test xx`，跑完所有测试，怎么 profile，怎么 bench（怎么刷 l2）。如果我们不沉淀自己的 harness，重复在这些事情上花费重复的时间，是一个很低效的事情。好的 dev ops，能让我们更加专注于开发、研究本身。

^pr-0a7ff5520043

### Make it work first

在去年年初，我也是一个有点代码洁癖的人的，总是时不时追求代码和架构上的“绝对正确”，而且这样的思考不高效（怎么思考也是一个话题，比如第二大脑那样，原子笔记什么的）。去年在 LLM serving infra 开源抢地盘的负载下，先跑起来更重要，有流量，有用户，后续的迭代只会顺利。再到年末我看到一些 Rust 的工作，我突然大彻大悟，像是开窍了，也许是年末 LLM 增长了一波能力。一些提前思考、提前优化其实是很低效的，ROI 很低的。Idea is cheap，我们要快速验证各种 idea 的可行性。

^pr-f76806444bf0

无论 pegaflow 还是 openinfer，最初都只是一个 vibe 出来的 toy project，到现在 pegaflow 绝对算是生产 ready 的 kv cache，“完美”是需要时间的。虽然 Openinfer 还有一定距离，但我在持续迭代，它总会到的。

先有能卖的饼，学会画大饼，项目才有走下去的可能。同时在迭代过程中，根据实际的运行、测试、profile 得出来的数据，结论可能让项目 idea 更快验证。用真实数据驱动架构决策。

包括 Pegaflow 早期我一直想做 layer first，结果到现在发现没什么用，layer first 理想很美好，但现实很残酷，也是一个痛苦的教训。

### Infra的核心使命：降本增效

这更多是站在一个 high level 去思考自己的工作边界、能力提升，低头前行的时候，也需要看看前方的路况。

我们需要经常思考 infra 公司的运作，他们是如何赚钱的。比如推理吧，中国、海外都有很多推理工程师岗位，但他们服务的目的不同，公司赚钱的方式不同。公司为什么招聘 infra 人才，本质是为了降本增效。一个亿的服务，优化 10% 的成本，省一千万，那我花 500w 招个 team，稳赚不赔。优化完呢？下一个优化点？越往前走，投入人力更大，换取的收益更小，总有一天，人力成本超过收益，对于公司只能选择让一部分离开，这也是最近听说很多 database 公司离职潮的一个原因吧我想。也许对于 infra 程序员，如果只做技术，意味着必须时刻跟着时代潮流转型。

^pr-147e8dafe362

所以我们需要思考，对于这个赛道，下一个最能优化的地方在哪里。我想这也是当年我选择离开数据库的一个原因，再向前走一步，实在太难。

这也是我现在投入大量空闲时间做 openinfer 的原因，未雨绸缪。

有个棒球手叫 Ted Williams，他在《The Science of Hitting》里把 strike zone 切成 77 个棒球大小的格子，每格标好打那个位置的预期打击率——核心主张是：**只挥击进入“甜区”（happy zone）的球，哪怕两好球的压力下，也不为打不好的球出棒。** 纪律性地放掉烂球，只在高期望值的格子上发力。不是哪个球都打，是只打 ROI 最高的那格。

^pr-7fc116093136

**善弈者谋势，不善弈者谋子**
