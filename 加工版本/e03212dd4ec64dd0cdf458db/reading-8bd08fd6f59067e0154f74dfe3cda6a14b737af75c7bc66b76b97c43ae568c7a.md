# 编辑二进制文件｜Editing binaries

---

## 正文

Editing binaries 是一种每年都会派上几次用场的技巧。你并不经常需要这样做，但需要时就没有别的办法。当我提起 patching binaries 时，得到的反应只有两种：震惊不已，或者毫无反应。据我所知，这是因为大多数人对世界的理解属于以下两种 models 之一：

> 1.  存在 source code。Compilers 对 source code 做一些事情，使其成为 runnable。如果你 change 这些 source code，就会发生不同的事情。
>     
> 2.  存在 processor。这个 processor takes 一些 bits 并 decodes 它们，让事情发生。如果你 change 这些 bits，就会发生不同的事情。
>     

如果你持第一种看法，那么拿出 hex editor 来 modify 一个 program 就是疯子的行为。如果你持第二种看法，editing binaries 就是世界上最自然的事。为什么不直接 edit 这个 binary 呢？这往往是得到所需结果的最简单办法。

例如，如果你使用 [non-Intel non-AMD x86 processor](http://forum.osdev.org/viewtopic.php?f=1&t=26351)，就会经常被迫这样做。它们并不 checking [CPUID feature flags，而是由 programs 来 check 这些 CPUID family、model 和 stepping](http://www.sandpile.org/x86/cpuid.htm)，以 determine features，这会导致 non-standard CPUs 上的 incorrect behavior。有时你必须做一次 edit，才能让 program 使用最新的 SSE instructions；有时你必须做一次 edit，才能让 program 得以 run。你可以尝试 filing a bug，但[直接 edit 你的 binaries 要容易得多](https://code.google.com/p/nativeclient/issues/detail?id=2508)。

即使你是在 mainstream Intel CPU 上 running，当你遇到 [closed sourced software 中的 bugs](http://blogs.msdn.com/b/oldnewthing/archive/2012/11/13/10367904.aspx?Redirected=true) 时，这些技巧也很有用。此外，还有紧急情况。

前几天，我一位在中型初创公司做 DevOps 的朋友，向我讲起他们有一次对外 released 了一个 internal alpha build，导致 auto-update mechanism 将所有人原本 working 的 binary 都 replace 成了一个 buggy experimental version。他们只花了一分钟就弄清楚了发生的事情。Updates 会在几天内逐渐 roll out 给所有 users，这意味着那个糟糕的 version 当时仅传播到了全部 users 的 `1 / (60*24*2) = 0.03%`。但他们无法将旧 version push 到 auto-updater 中，因为 client 只 accepts 来自 higher numbered versions 的 updates。他们不得不走完整个 build 和 release process（耗时一小时），仅仅是为了 release 一个与上次良好 version 完全 identical 的 version。如果当时有人想到 edit 这个 binary 来 increment 其 version number，他们就能在一分钟而非一小时内 pushed out 一个良好的 update，从而使问题不至于传播到超过 `0.06%` 的 users，而不是向 `2%` 的 users 发送一个 broken update[1](https://danluu.com/edit-binary/#fn:E)。

这远没有听起来那么难。我们来试一个 example。如果你打算经常做这类事情，你可能会想使用像 [IDA](https://hex-rays.com/products/ida/support/download_freeware.shtml)[2](https://danluu.com/edit-binary/#fn:D) 这样的真正的 disassembler。不过，如果只是偶尔需要这样做，简单的 tools 也够用。我碰巧正在使用一台不用来做 development 的 Mac，所以我准备使用 [lldb](http://lldb.llvm.org/) 进行 disassembly，并使用 [HexFiend](http://ridiculousfish.com/hexfiend/) 来 edit 这个 example。Gdb、otool 和 objdump 也很适合用来做 quick and dirty disassembly。

这里有一个 toy code snippet，`wat-arg.c`，它应该很容易进行 binary edit：

```c
#include <stdio.h>

int main(int argc, char **argv) {
  if (argc > 1) {
    printf("got an arg\n");
  } else {
    printf("no args\n");
  }
}
```

如果我们 compile 它，然后针对这个 binary launch lldb，再 step into main，就能看到以下 machine code：

```
$ lldb wat-arg
(lldb) breakpoint set -n main
Breakpoint 1: where = original`main, address = 0x0000000100000ee0
(lldb) run
(lldb) disas -b -p -c 20
;  address       hex opcode            disassembly
-> 0x100000ee0:  55                    pushq  %rbp
   0x100000ee1:  48 89 e5              movq   %rsp, %rbp
   0x100000ee4:  48 83 ec 20           subq   $32, %rsp
   0x100000ee8:  c7 45 fc 00 00 00 00  movl   $0, -4(%rbp)
   0x100000eef:  89 7d f8              movl   %edi, -8(%rbp)
   0x100000ef2:  48 89 75 f0           movq   %rsi, -16(%rbp)
   0x100000ef6:  81 7d f8 01 00 00 00  cmpl   $1, -8(%rbp)
   0x100000efd:  0f 8e 16 00 00 00     jle    0x100000f19               ; main + 57
   0x100000f03:  48 8d 3d 4c 00 00 00  leaq   76(%rip), %rdi            ; "got an arg\n"
   0x100000f0a:  b0 00                 movb   $0, %al
   0x100000f0c:  e8 23 00 00 00        callq  0x100000f34               ; symbol stub for: printf
   0x100000f11:  89 45 ec              movl   %eax, -20(%rbp)
   0x100000f14:  e9 11 00 00 00        jmpq   0x100000f2a               ; main + 74
   0x100000f19:  48 8d 3d 42 00 00 00  leaq   66(%rip), %rdi            ; "no args\n"
   0x100000f20:  b0 00                 movb   $0, %al
   0x100000f22:  e8 0d 00 00 00        callq  0x100000f34               ; symbol stub for: printf
```

正如预期，我们 load 一个 value，用 `cmpl $1, -8(%rbp)` 将它 compare 至 1，然后根据 compare 的结果决定 jump 的方向，进而 print `got an arg` 或 `no args`。

```
$ ./wat-arg
no args
$ ./wat-arg 1
got an arg
```

如果我们打开 hex editor，并将 `81 7d f8 01 00 00 00; cmpl 1, -8(%rbp)` change 为 `81 7d f8 06 00 00 00; cmpl 6, -8(%rbp)`，应该就会使 program check 6 args，而不是 1

![将 cmpl Replace 为 cmpl 6](https://danluu.com/images/edit-binary/edit-binary.webp)

```
$ ./wat-arg
no args
$ ./wat-arg 1
no args
$ ./wat-arg 1 2
no args
$ ./wat-arg 1 2 3 4 5 6 7 8
got an arg
```

很简单！如果你再多做几次，很快就会养成 patching in `90`[3](https://danluu.com/edit-binary/#fn:1)，以便用 NOPs 来 overwrite 东西的习惯。例如，如果我们将 `0f 8e 16 00 00 00; jle` 和 `e9 11 00 00 00; jmpq` replace 为 `90`，就会得到以下结果：

```
   0x100000ee1:  48 89 e5              movq   %rsp, %rbp
   0x100000ee4:  48 83 ec 20           subq   $32, %rsp
   0x100000ee8:  c7 45 fc 00 00 00 00  movl   $0, -4(%rbp)
   0x100000eef:  89 7d f8              movl   %edi, -8(%rbp)
   0x100000ef2:  48 89 75 f0           movq   %rsi, -16(%rbp)
   0x100000ef6:  81 7d f8 01 00 00 00  cmpl   $1, -8(%rbp)
   0x100000efd:  90                    nop
   0x100000efe:  90                    nop
   0x100000eff:  90                    nop
   0x100000f00:  90                    nop
   0x100000f01:  90                    nop
   0x100000f02:  90                    nop
   0x100000f03:  48 8d 3d 4c 00 00 00  leaq   76(%rip), %rdi            ; "got an arg\n"
   0x100000f0a:  b0 00                 movb   $0, %al
   0x100000f0c:  e8 23 00 00 00        callq  0x100000f34               ; symbol stub for: printf
   0x100000f11:  89 45 ec              movl   %eax, -20(%rbp)
   0x100000f14:  90                    nop
   0x100000f15:  90                    nop
   0x100000f16:  90                    nop
   0x100000f17:  90                    nop
   0x100000f18:  90                    nop
   0x100000f19:  48 8d 3d 42 00 00 00  leaq   66(%rip), %rdi            ; "no args\n"
   0x100000f20:  b0 00                 movb   $0, %al
   0x100000f22:  e8 0d 00 00 00        callq  0x100000f34               ; symbol stub for: printf
```

注意，由于我们用 single byte instructions 来 replaced 了几个 multi-byte instructions，program 现在有了更多的 total instructions。

```
$ ./wat-arg
got an arg
no args
```

其他常见技巧包括 patching in `cc` 来 redirect 到 interrupt handler，使用 `db` 来 cause 一个 debug breakpoint，以及知道该 change 哪个 bit，才能 flip 一个 compare 或 jump 的 polarity，等等。这些内容在 [Intel architecture manuals](http://www.intel.com/content/www/us/en/processors/architectures-software-developer-manuals.html) 中都有详细说明，但学习它们最简单的办法，是逐个练习，形成肌肉记忆。

玩得开心！

## 原文

Editing binaries is a trick that comes in handy a few times a year. You don't often need to, but when you do, there's no alternative. When I mention patching binaries, I get one of two reactions: complete shock or no reaction at all. As far as I can tell, this is because most people have one of these two models of the world:

> 1.  There exists source code. Compilers do something to source code to make it runnable. If you change the source code, different things happen.
>     
> 2.  There exists a processor. The processor takes some bits and decodes them to make things happen. If you change the bits, different things happen.
>     

If you have the first view, breaking out a hex editor to modify a program is the action of a deranged lunatic. If you have the second view, editing binaries is the most natural thing in the world. Why wouldn't you just edit the binary? It's often the easiest way to get what you need.

For instance, you're forced to do this all the time if you use a [non-Intel non-AMD x86 processor](http://forum.osdev.org/viewtopic.php?f=1&t=26351). Instead of checking [CPUID feature flags, programs will check the CPUID family, model, and stepping](http://www.sandpile.org/x86/cpuid.htm) to determine features, which results in incorrect behavior on non-standard CPUs. Sometimes you have to do an edit to get the program to use the latest SSE instructions and sometimes you have to do an edit to get the program to run at all. You can try filing a bug, but it's much [easier to just edit your binaries](https://code.google.com/p/nativeclient/issues/detail?id=2508).

Even if you're running on a mainstream Intel CPU, these tricks are useful when you run into [bugs in closed sourced software](http://blogs.msdn.com/b/oldnewthing/archive/2012/11/13/10367904.aspx?Redirected=true). And then there are emergencies.

The other day, a DevOps friend of mine at a mid-sized startup told me about the time they released an internal alpha build externally, which caused their auto-update mechanism to replace everyone's working binary with a buggy experimental version. It only took a minute to figure out what happened. Updates gradually roll out to all users over a couple days, which meant that the bad version had only spread to `1 / (60*24*2) = 0.03%` of all users. But they couldn't push the old version into the auto-updater because the client only accepts updates from higher numbered versions. They had to go through the entire build and release process (an hour long endeavor) just to release a version that was identical to their last good version. If it had occurred to anyone to edit the binary to increment the version number, they could have pushed out a good update in a minute instead of an hour, which would have kept the issue from spreading to more than `0.06%` of their users, instead of sending `2%` of their users a broken update[1](https://danluu.com/edit-binary/#fn:E).

This isn't nearly as hard as it sounds. Let's try an example. If you're going to do this sort of thing regularly, you probably want to use a real disassembler like [IDA](https://hex-rays.com/products/ida/support/download_freeware.shtml)[2](https://danluu.com/edit-binary/#fn:D). But, you can get by with simple tools if you only need to do this every once in a while. I happen to be on a Mac that I don't use for development, so I'm going to use [lldb](http://lldb.llvm.org/) for disassembly and [HexFiend](http://ridiculousfish.com/hexfiend/) to edit this example. Gdb, otool, and objdump also work fine for quick and dirty disassembly.

Here's a toy code snippet, `wat-arg.c`, that should be easy to binary edit:

```c
#include <stdio.h>

int main(int argc, char **argv) {
  if (argc > 1) {
    printf("got an arg\n");
  } else {
    printf("no args\n");
  }
}
```

If we compile this and then launch lldb on the binary and step into main, we can see the following machine code:

```
$ lldb wat-arg
(lldb) breakpoint set -n main
Breakpoint 1: where = original`main, address = 0x0000000100000ee0
(lldb) run
(lldb) disas -b -p -c 20
;  address       hex opcode            disassembly
-> 0x100000ee0:  55                    pushq  %rbp
   0x100000ee1:  48 89 e5              movq   %rsp, %rbp
   0x100000ee4:  48 83 ec 20           subq   $32, %rsp
   0x100000ee8:  c7 45 fc 00 00 00 00  movl   $0, -4(%rbp)
   0x100000eef:  89 7d f8              movl   %edi, -8(%rbp)
   0x100000ef2:  48 89 75 f0           movq   %rsi, -16(%rbp)
   0x100000ef6:  81 7d f8 01 00 00 00  cmpl   $1, -8(%rbp)
   0x100000efd:  0f 8e 16 00 00 00     jle    0x100000f19               ; main + 57
   0x100000f03:  48 8d 3d 4c 00 00 00  leaq   76(%rip), %rdi            ; "got an arg\n"
   0x100000f0a:  b0 00                 movb   $0, %al
   0x100000f0c:  e8 23 00 00 00        callq  0x100000f34               ; symbol stub for: printf
   0x100000f11:  89 45 ec              movl   %eax, -20(%rbp)
   0x100000f14:  e9 11 00 00 00        jmpq   0x100000f2a               ; main + 74
   0x100000f19:  48 8d 3d 42 00 00 00  leaq   66(%rip), %rdi            ; "no args\n"
   0x100000f20:  b0 00                 movb   $0, %al
   0x100000f22:  e8 0d 00 00 00        callq  0x100000f34               ; symbol stub for: printf
```

As expected, we load a value, compare it to 1 with `cmpl $1, -8(%rbp)`, and then print `got an arg` or `no args` depending on which way we jump as a result of the compare.

```
$ ./wat-arg
no args
$ ./wat-arg 1
got an arg
```

If we open up a hex editor and change `81 7d f8 01 00 00 00; cmpl 1, -8(%rbp)` to `81 7d f8 06 00 00 00; cmpl 6, -8(%rbp)`, that should cause the program to check for 6 args instead of 1

![Replace cmpl with cmpl 6](https://danluu.com/images/edit-binary/edit-binary.webp)

```
$ ./wat-arg
no args
$ ./wat-arg 1
no args
$ ./wat-arg 1 2
no args
$ ./wat-arg 1 2 3 4 5 6 7 8
got an arg
```

Simple! If you do this a bit more, you'll soon get in the habit of patching in `90`[3](https://danluu.com/edit-binary/#fn:1) to overwrite things with NOPs. For example, if we replace `0f 8e 16 00 00 00; jle` and `e9 11 00 00 00; jmpq` with `90`, we get the following:

```
   0x100000ee1:  48 89 e5              movq   %rsp, %rbp
   0x100000ee4:  48 83 ec 20           subq   $32, %rsp
   0x100000ee8:  c7 45 fc 00 00 00 00  movl   $0, -4(%rbp)
   0x100000eef:  89 7d f8              movl   %edi, -8(%rbp)
   0x100000ef2:  48 89 75 f0           movq   %rsi, -16(%rbp)
   0x100000ef6:  81 7d f8 01 00 00 00  cmpl   $1, -8(%rbp)
   0x100000efd:  90                    nop
   0x100000efe:  90                    nop
   0x100000eff:  90                    nop
   0x100000f00:  90                    nop
   0x100000f01:  90                    nop
   0x100000f02:  90                    nop
   0x100000f03:  48 8d 3d 4c 00 00 00  leaq   76(%rip), %rdi            ; "got an arg\n"
   0x100000f0a:  b0 00                 movb   $0, %al
   0x100000f0c:  e8 23 00 00 00        callq  0x100000f34               ; symbol stub for: printf
   0x100000f11:  89 45 ec              movl   %eax, -20(%rbp)
   0x100000f14:  90                    nop
   0x100000f15:  90                    nop
   0x100000f16:  90                    nop
   0x100000f17:  90                    nop
   0x100000f18:  90                    nop
   0x100000f19:  48 8d 3d 42 00 00 00  leaq   66(%rip), %rdi            ; "no args\n"
   0x100000f20:  b0 00                 movb   $0, %al
   0x100000f22:  e8 0d 00 00 00        callq  0x100000f34               ; symbol stub for: printf
```

Note that since we replaced a couple of multi-byte instructions with single byte instructions, the program now has more total instructions.

```
$ ./wat-arg
got an arg
no args
```

Other common tricks include patching in `cc` to redirect to an interrupt handler, `db` to cause a debug breakpoint, knowing which bit to change to flip the polarity of a compare or jump, etc. These things are all detailed in the [Intel architecture manuals](http://www.intel.com/content/www/us/en/processors/architectures-software-developer-manuals.html), but the easiest way to learn these is to develop the muscle memory for them one at a time.

Have fun!
