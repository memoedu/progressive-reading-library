## 正文

关于构建在神经网络上的个人维基的提议：所有编辑都被记录并用于实时微调一个神经网络助手。

> 现有的个人维基或个人知识管理工具（例如 Roam、Obsidian、org-mode）对强大的语言和代码生成神经网络（如 GPT-4 这样的 LLM）的利用非常有限，仅限于一些小的改进，如建议相关链接或提供编辑建议。
> 
> 这与其说是由于神经网络能力的缺乏，不如说是由于将它们集成到文档系统中的困难，这些系统都是在 LLM 出现之前很久就设计好的范式。如果 [Vannevar Bush⁠](https://en.wikipedia.org/wiki/Memex) 或 [Douglas Engelbart⁠](https://en.wikipedia.org/wiki/Douglas_Engelbart) 从头设计一个“神经维基”作为“思考工具”，并把 GPT-4 级别的 LLM 视为理所当然，那会是什么样子？
> 
> 它可能不会像现有工具那样，采用超文本方法，即一组相互引用的独立节点，并以文本文件形式进行版本控制。简单的基于文本文件的方法，比如复制整个文档，很快就会遇到性能限制或虽小但不可忽视的错误率。
> 
> 更自然的方法是从深度学习扩展范式中汲取灵感，将“一切视为序列预测任务”：在这种以 LLM 为中心的维基范式（**Nenex**）中，维基将不是以文件/节点为中心，而是以_编辑_为中心。
> 
> 不是被那些为简单性而优化并对其通用聊天机器人模型心怀嫉妒的云提供商所束缚，而是记录所有操作来训练_一个本地 LLM_ 以模仿_你_，并在采取行动和批准/不批准执行预测行动之间交替使用系统。随着数据的积累，LLM 不仅学习工具使用或通用文本预测，还学习预测_你的_文本，包括你独特的引用、偏好，甚至个性/价值观。
> 
> 维基不是表示为一组带有隐式历史的静态文件，而是更像修订控制系统或函数式编程风格，作为主日志中的编辑历史；LLM 只需学习预测日志中的下一个操作（使用 [“动态评估”⁠](https://gwern.net/doc/ai/nn/rnn/2010-mikolov.pdf#page=2) 微调以实现可扩展性）。
> 
> 所有用户编辑、引用添加、拼写检查或新词汇添加、摘要、更新过时页面等，都只是 LLM 需要实时学习预测的更多操作。它可以灵活地使用 [嵌入⁠](https://en.wikipedia.org/wiki/Word_embedding) 和检索、简单的外部工具（如下载研究论文），并通过 API 操作。Nenex 的 LLM 可以通过在 Nenex 日志上训练新模型来轻松升级，额外训练所有相关信息（私有或公共），并纳入用户的任意反馈。
> 
> 一个 Nenex 将交互式地适应用户的写作风格、知识、现有语料库，并启用其他系统无法提供的语义功能，例如在个人维基中搜索需要更新的页面，考虑到其他页面的更新。

[A](https://gwern.net/dropcap#kanzlei)截至 2023 年 9 月，LLM 已经彻底改变了我的代码编写，但我不得不承认，它们还没有彻底改变我的自然语言写作——作为我 Gwern.net 工作的一部分，我已经以一些适度的方式集成了 LLM，比如处理烦人的格式任务（例如，将 LaTeX 数学表达式转换为 HTML+[Unicode⁠](https://en.wikipedia.org/wiki/Unicode)）或进行注释的向量搜索（正如你在大多数 Gwern.net 弹出窗口中看到的 `similars` 标签）。有时我可以把一篇文章输入 GPT-4 或 Claude-2，得到一些好的建议。

并不令人印象深刻。如果 LLM 所能做的只是实现我可以用聊天格式表达而不会太麻烦的简短代码需求，而其他一切都得我来做，那么我能从 LLM 中得到的东西实在有限。

## [背景：无生命的语料库](https://gwern.net/nenex#background-lifeless-corpuses "链接到章节：§ '背景：无生命的语料库'")

> …写作与绘画共享一个奇特的特征。绘画的产物站在那里，仿佛它们是活的，但如果有人问它们什么，它们却保持最庄严的沉默。文字也是如此。你会以为它们说话时好像有所理解，但如果你想了解更多而质疑所说的话，它却永远只表示同一件事……它总是需要其父亲的支持；独自一人时，它既不能自卫，也不能自我支持。
> 
> “苏格拉底”，[柏拉图《斐德罗篇》⁠](https://en.wikipedia.org/wiki/Phaedrus_\(dialogue\))

与编程相比，我发现写作令人沮丧的一点是它是多么_惰性_。写作不_做_任何事，当一个人写作时，文字只是累积。那些文字中表达的思想会相互链接并构建，但写作过程本身保持不变：无论一个人写了多少百万字，每次，他都面对同样的空白页和闪烁的文本光标。无论一个人多少次将笔记整理成文章，或扩展大纲，或运行拼写检查，下一次都需要同样多的工作，即使是最花哨的文本编辑器，如[Emacs⁠](https://en.wikipedia.org/wiki/Emacs)或[Scrivener⁠](https://en.wikipedia.org/wiki/Scrivener_\(software\))，也提供不了多少帮助。（部分原因是许多功能——尤其是键绑定——的好处小于学习、配置和记住如何使用它们所需的努力。）

其他格式也是如此，比如期刊。无论一份期刊多么著名和有影响力，它只与其最新一期一样好，而作为组织和语料库的期刊，其价值惊人地低。例如，像《时代》或《生活》或《新闻周刊》这样的杂志，由于互联网而在一夜之间变得几乎一文不值，而那些品牌名下发表的东西只是原来震撼世界的巨人的苍白影子。无论有多少杰出的作家为之奉献一生，无论他们的报道多么广泛，无论他们的档案（被恰如其分地称为[“停尸房”⁠](https://en.wikipedia.org/wiki/Morgue_file)）多么庞大——它们都以极低的价格被出售。写作本身、编辑、技术设备、印刷机、文化——现在都一文不值。（这些剩余价值中的大部分反映了其摄影档案对Getty Images等图片库巨头的知识产权许可价值。）没有什么比昨天的新闻更无用的了。

然而，为什么是这样？为什么几十年写作积累的智慧不是更有用？

像写作这样的智力工作，为什么如此缺乏‘基础设施’或‘资本’，以至于人们不能‘把一个新实习生插入《时代》’而他们突然成为更好的记者？为什么《时代》的精神，一个世纪报道的场所精神，不能附身于一个实习生，赋予他们广博的知识和新闻编辑室的所有秘密，以及诸如知道在哪里挖掘尸体或如何解读说谎的政治家给你的隐藏线索等技能？

嗯，显然，因为所有这些要么锁在另一个人的头脑中（那个人可能早已不在），要么它惰性地、隐藏地坐在一堆死树中。无论那个语料库变得多大，无论其中埋藏着什么宝藏，它仍然什么都不做，永远不会为自己说话，我们也没有工具让它悬浮起来。⁠[⁠1⁠](https://gwern.net/nenex#fn1)

我想要的是 _让我的死语料库活起来，让它能学习、思考并写作_。

## [征寻：真正的写作助手](https://gwern.net/nenex#wanted-real-writing-assistants "链接到章节：§ '征寻：真正的写作助手'")

LLM 很方便，但也就那样了，它们的能力有限。我很失望，自己竟然很少使用如此强大的技术：这些是装在盒子里的脑子，几乎能替我把文章写完！肯定有比这些更有用的写作 LLM 工具——就像写代码那样，GPT-4 已经迅速成为我快速编写或审查代码不可或缺的工具。⁠[⁠2⁠](https://gwern.net/nenex#fn2) 但似乎没有任何写作工具走得更远。⁠[⁠3⁠](https://gwern.net/nenex#fn3) 当然，像 Roam、Obsidian、org-mode/Logseq 等流行的写作工具，似乎并没有在深度融合 LLM 方面取得太大进展。⁠[⁠4⁠](https://gwern.net/nenex#fn4)

并不是说标准的思维工具体验中没有很多可以用 LLM 改进的地方。例如，标签管理是一个长期存在的痛点：给页面或 URL 添加标签、拆分过于庞大的标签、给新的子标签命名……这些都是极其繁琐的杂务，导致用户放弃使用标签，但 [⁠用 LLM 嵌入+提示词完全可以自动化⁠](https://gwern.net/design#future-tag-features)。给短页面命名和加标题很麻烦，这从一开始就阻碍了创建它们。把一篇长文章拆分成有用的标题层级，并不是在床上用笔记本电脑时最有趣的事。或者考虑为所有这些写好的修订/补丁摘要——烦人！⁠[⁠5⁠](https://gwern.net/nenex#fn5)

## [写作助手的局限](https://gwern.net/nenex#writing-assistant-limitations "链接到章节：§ '写作助手的局限'")

> “金妮！”韦斯莱先生惊愕地说，“我什么都没教你吗？我一直跟你说的什么？永远不要相信任何能独立思考的东西，除非你看清它把脑子放在哪里！”
> 
> _《哈利·波特与密室》_，J. K. 罗琳

但很容易看到LLM深度集成的障碍。第一个问题是：你究竟如何将文本_输入_LLM，让它对其做任何处理？你马上会遇到一个问题：大多数LLM使用只能接受少量文本（一篇文章的一小部分），而且只是暂时的——一旦该请求完成，这些文本就会被遗忘。这意味着LLM对你个人wiki的其余部分一无所知，更不用说更大、可能非常有用的文本数据集了。（例如，LLM个人助理将受益于研究你的所有电子邮件和聊天记录，以及你读过的每篇论文或网页的文本。）你也不能更新LLM：如果你能编制一份LLM助理犯的每个错误的列表（比如将新名称或词汇术语标记为拼写错误），并将其反馈回去，那就太好了；但你也不能这样做，因为如果你把错误和更正列表放入LLM输入，它放不下。而且你可以忘记诸如将你的打字实时流式传输给LLM以教它你如何思考和修改文本之类的想法。

将内容放入LLM是一个如此大的障碍，以至于大多数用途都围绕着如何将大型文本语料库切分成不太容易出错的小块，以便输入一小部分文本并获得有用的东西，然后可以盲目地将其插回语料库。（而且由于这些不可能那么有用，它们必须非常便宜，人们可能根本不会费心去使用它们。）

我们还有安全问题：我们的LLM助理太容易被变成一个[困惑的代理人⁠](https://en.wikipedia.org/wiki/Confused_deputy)，执行来自攻击者通过提示注入的命令，而不是我们自己的命令，因为它们往往_看起来_一样，而且我们的LLM助理对我们了解不多——如果“我们”命令它删除我们所有的文件，它怎么知道那不是我们永远不会做的事情？它只是被训练成“乐于助人”，而没有关于对_谁_有帮助的具体细节。

## [动态评估](https://gwern.net/nenex#dynamic-evaluation "链接到章节：§ '动态评估'")

> 移动的手指写字；写完后，
> 
> 便继续前行：你的虔诚或才智
> 
> 都无法诱它回来取消半行，
> 
> 你的眼泪也洗不去一个字。
> 
> 爱德华·菲茨杰拉德（第51首，《鲁拜集》）

LLM最大的问题是注意力机制的处理瓶颈，限制了它灵活地从任何类型的语料库中学习的能力。

我们_可以_等待更好的[注意力与记忆机制⁠](https://gwern.net/doc/ai/nn/transformer/attention/index)。这是一个热门的研究领域，截至2023年9月，像Claude-2这样的公开模型已经能够消化多达数十万个token。也许这正是神经维基所等待的？或者是对检索的进一步调整？

但大的上下文窗口仍然极其昂贵，注意力机制似乎经常失效或导致虚构，而且一个处理数十万token的Transformer如果每输出一个token都必须重新处理整个输入，很可能天生就慢。而我们想要的是数百万或数千万的token，并且尽可能少用花哨的架构工程——一个真正的LLM极致主义者希望用数据而非代码来编程神经网络（而且是利用已有的数据）。

如果我们回顾深度学习历史中那个已被遗忘的RNN时代，会发现上下文窗口之外还有一种替代方案。如果我们放弃通常未言明的假设，即必须使用无状态的API调用（除了提示词外无法个性化），那么微调的想法就变得显而易见。由于神经网络模型过度参数化，并在权重中存储了大量记忆的事实，它们可以轻松容纳用户可能写的任何内容或他们的参考数据库——毕竟，它们在训练期间通常见过数十亿或数万亿的token，再多几百万又何妨？大型神经网络越来越样本高效，从比小模型更少的数据点中学习更多，常常在记忆的同时还能泛化；事实上，它们有时只需一次接触就能记住文本。而且微调不必是一次性的，也不必局限于在用户睡觉时离线批量运行。

当[RNN⁠](https://en.wikipedia.org/wiki/Recurrent_neural_network)用户希望在新文本语料上获得最佳性能时，他们会怎么做？他们使用[**动态评估**⁠](https://arxiv.org/abs/1308.0850)（[Transformer版本⁠](https://arxiv.org/abs/1904.08378)，[w⁠](https://arxiv.org/abs/2310.10638#facebook)/[检索⁠](https://arxiv.org/abs/2305.18466)）⁠[⁠6⁠](https://gwern.net/nenex#fn6)：本质上，就是在每个时间步对到达的每个输入进行微调（使用普通的[‘在线’⁠](https://en.wikipedia.org/wiki/Online_machine_learning)[SGD⁠](https://en.wikipedia.org/wiki/Stochastic_gradient_descent)）⁠[⁠7⁠](https://gwern.net/nenex#fn7)。（例如，一个字符级RNN可能预测下一个字符，接收实际的下一个字符，执行一次[反向传播⁠](https://en.wikipedia.org/wiki/Backpropagation)步骤，然后通过将当前隐藏状态输入到权重更新后的RNN中来预测再下一个字符。）这让模型能够从最新数据中学习，比仅仅在上下文窗口中进行上下文/元学习更深刻，因为权重可以在多个时间步中反复变化，基于先前的权重更新进行构建，并将知识永久编码到权重中。语言模型可以记住训练中仅见过几次甚至一次的样本，但仍然受益[于多个epoch的训练⁠](https://arxiv.org/abs/2305.16264#huggingface)，所以我们可以鱼与熊掌兼得：拥有既聪明又会记忆的模型——事实上，我们可以刻意训练模型记忆大量事实作为长期记忆，例如相关文档的唯一[ID⁠](https://arxiv.org/abs/2206.02743#microsoft)。（关于这一范式的更多背景，请参阅我的[⁠AUNN提案⁠](https://gwern.net/aunn#memorization)，它将记忆数据的范式发挥到了极致。）

使用冻结模型处理大规模时变新数据集所面临的挑战。

动态评估特别擅长将模型更新到相当不同的数据分布，处理重复或罕见/新颖（或两者兼有）的标记，且成本为常数因子（必要时可舍弃），原则上能够无限改进。它可能帮助小模型超越（冻结的）大模型或昂贵的大上下文窗口（参见 [Rannen-Triki 等人 2024⁠](https://arxiv.org/abs/2403.01518#deepmind)）。

这使得动态评估比向量检索等其他技术更适合高度个性化的长篇写作，因为在这种场景中，人们可能会引入许多新概念、术语（例如“Nenex”）或参考文献，而预训练模型可能不知道这些，并且它们也可能不在上下文窗口内（因为之前的实例位于不同的文件中，或者在当前文件中距离焦点太远，无论之前还是之后）：一旦使用，它就被注入到模型的权重中，未预测文本越令人惊讶或新颖，更新就越大。起初，当文本仍适合上下文窗口且 Transformer 能进行上下文学习时，动态评估不会有太大帮助，因为它仍在“预热”，但随着它看到更多文本，它会逐渐改进，而健忘的 Transformer 则不能；少样本提示在示例足够多时可以[赶上微调⁠](https://arxiv.org/abs/2404.11018#google)，但可能需要数千个示例，并消耗甚至数百万个标记的上下文窗口，代价和延迟惊人；而批量微调的 Transformer 可能具有竞争力，但只能在间隔很大的时间点上——太晚而无法帮助用户撰写当前的文章。

这将是实现个人写作助手的自然方式：微调在大量使用中摊销后并不昂贵⁠[⁠8⁠](https://gwern.net/nenex#fn8)，用户打字速度不快（以每秒标记数计），因此一个好的 Transformer 可以在动态评估的同时跟上（甚至可以在[同一小批量上重复训练⁠](https://arxiv.org/abs/1806.07353)或返回进行多个周期），并且 Transformer 将能够在大型语料库上显著更好地预测。

我们还可以从个性化中获得独特的性能优势，比如_定制分词_。使用以英语为中心的 LLM 的用户可能不会注意到这一点，但 BPE 标记字典需要覆盖每种可能的语言和源代码等模态，这会使字典膨胀到数十万或数百万个唯一标记以试图压缩它们，从而产生显著的性能损失。但万事通却样样稀松，为什么一个可能只用中文写作且不编程的用户需要为所有这些其他领域付出性能代价呢？如果用户可以将 BPE 专门用于其个人语料库（类似于 [Brotli⁠](https://en.wikipedia.org/wiki/Brotli) 等压缩工具），他们可能会在标记压缩方面获得显著改进（也许 10-20%？）；并且他们的 BPE 字典大小可以通过超参数搜索或已知的标记缩放定律根据语料库大小进行缩放。这将需要重新训练 LLM 以处理词汇量的潜在巨大变化，因为许多罕见或外来标记突然被重新用于用户经常说的内容，但这并不是一个重大的技术挑战，因为动态评估可以处理领域偏移，并且可以通过配对“翻译”等技巧来学习新的分词（即强制将所有新标记分词为它们各自的字节标记等价物，以教会 LLM 等价关系）。

^pr-3f380fed325d

朴素的方法是在文本编辑器中预测用户的写作，并提供一些制表符补全辅助。这没问题，但我们可以做得更好。如果它能预测用户的下一个打字动作，为什么不预测用户的下一个动作呢？不仅仅是退格键来纠正拼写错误，而是_所有_动作：拼写检查、编写提交消息、切换文本缓冲区……很像 AI 代理，[文本编辑器想要所有可能的上下文⁠](http://www.catb.org/esr/writings/taoup/html/ch13s03.html#id2967765)，以便能够处理影响用户的所有文本；它不想成为一个狭窄的工具。

（我们这里的目标不是“超级智能”，而是“超级知识”。）

## [性能](https://gwern.net/nenex#performance "链接到章节：§ '性能'")

因为用户平均打字速度较慢，如果LLM足够快，能在合理时间内提供补全，那么它很可能也能被动态评估；如果不能，那么可以开始进行更重的优化。

例如，可以并行运行模型：在一个地方训练模型，同时在另一个地方运行模型（不一定相同）。像[LoRA⁠](https://arxiv.org/abs/2106.09685#microsoft)这样的轻量级微调方法可能会有帮助，尽管不是万能药，因为重点不是将模型硬连接到预先存在的能力上，利用大多数任务的线性与低维性，而是让模型记住关于用户的_一切_，理想情况下是他们写过或读过的所有内容，以及来自电子邮件或日历等来源的所有可用数据，这些是大量需要记忆的详细事实，无法容纳在几KB（甚至几MB）的“轻量级适配器”中——因此，例如LoRA在英语指令微调中效果很好，但轻量级微调方法不能[泛化⁠](https://arxiv.org/abs/2410.21228)或[良好扩展⁠](https://arxiv.org/abs/2402.17193#deepmind)，而要[完全用另一种语言⁠](https://arxiv.org/abs/2304.08109)进行则需要真正的微调。仅采样的模型可以使用[量化⁠](https://gwern.net/doc/ai/nn/sparsity/low-precision/index)等重度性能优化（这可以快速完成）。

Transformer模型在这种并行设置中天生具有延迟容忍性，因为它们的大上下文窗口为训练提供了缓冲；模型不需要每秒都更新才能工作，因为最新的用户行为仍会在上下文窗口中。只要上下文窗口不“溢出”，上下文学习就可以替代动态性。

即使溢出，用户可能也很难立即注意到衰减——他们需要调用那些独特依赖于上下文窗口（用户行为不断用相关文本重新填充）与已经动态评估并不断从训练过程同步过来的模型之间间隙中不可预测文本的行为。

而且训练模型落后的越多，它就越有机会利用 _n_ > 1 个小批量从串行训练切换到并行批量训练，并跨越式地追赶到当前，然后与采样模型进行一次大的同步。（如果 GPU 显存允许采样但不允许任何训练，那么交替训练实例可以放在 CPU 上，那里可能有足够的内存来缓慢训练。）

如果用户放慢速度，那么问题就会自行解决。

## [不可变性](https://gwern.net/nenex#immutability "链接到章节：§ '不可变性'")

我们可以通过从简单地记录键入的单词退一步，转而记录所有操作来实现这一点。核心对象不再是磁盘上的静态文本文件，而是一系列操作。每个文本文件都是由用户执行的一系列操作构建的：插入其他文件、删除单词、拼写检查、键入、运行内置函数来执行诸如排序行之类的操作……每个操作都可以被记录，LLM 可以被动态训练以预测下一个操作。⁠[⁠9⁠](https://gwern.net/nenex#fn9)

这种方法特别适合 Lisp 方法，因为像 Emacs 这样的 Lisp 系统可以轻松地将所有已执行的用户操作序列化为文本 [S-表达式⁠](https://en.wikipedia.org/wiki/S-expression)，然后调用 LLM 生成新的 S-表达式，并解释 _那个_ 以实现用户能做的任何事情。⁠[⁠10⁠](https://gwern.net/nenex#fn10)

## [模仿学习](https://gwern.net/nenex#imitation-learning "链接到章节：§ '模仿学习'")

这为“文本编辑器”提供了一种新范式。Emacs 是“一切都是缓冲区或 Lisp 函数”，vi 是“一切都是击键”，而对于神经助手来说，“一切都是用户模仿”。所有用户操作和状态转换都存储为序列，并由 LLM 预测。

LLM 现在是一个模仿学习的深度 [强化学习⁠](https://en.wikipedia.org/wiki/Reinforcement_learning) 智能体，类似于 [Decision Transformer⁠](https://sites.google.com/berkeley.edu/decision-transformer) 如 [Gato⁠](https://arxiv.org/abs/2205.06175#deepmind) 或 [Toolformer⁠](https://arxiv.org/abs/2302.04761#facebook)。它既是操作系统 _又_ 是用户：它被训练来预测用户在文本编辑器“环境”中的操作，以达到良好状态（如高质量的文章）。

而且由于它受到用户的监督，其错误会立即得到纠正，从而形成类似 [DAgger⁠](https://arxiv.org/abs/1011.0686) 的自举：如果神经网络在特定方式上频繁出错，它会收到关于该类错误的反馈并修复它。这是因为如果预测不太有效，用户的后续操作会纠正它：他们要么撤销并重试直到得到正确结果，要么将错误响应编辑为正确响应（这可能是一种普遍的习惯用法，也许绑定到特定的 `should-have-been` 函数来编辑任何可编辑的内容），要么手动执行正确操作。这些方法中的每一种都会在不同程度上修复模型，并且理想情况下，不仅会修复该特定实例或类似错误，还会通过学习用户+语料库的联合函数逐步改善模型的整体响应。

由于模型被动态评估，这些修复会 _立即_ 发生，这些改进会 _持久_——它们不会简单地消失在上下文窗口之外（或消失在某个遥远的云数据库中，也许有一天会改进明年可能部署的模型）。

用户写得或做得越多，模型就越能学会模仿，用户从“做”转变为“批准”，并且可以委托给神经网络的事情就越多。这种模仿用户的目标也有助于解决关于破坏或泄露的安全问题。⁠[⁠11⁠](https://gwern.net/nenex#fn11)

## [热启动](https://gwern.net/nenex#warm-starting "链接到章节：§ '热启动'")

LLM 可以通过演示来学会做很多事情，用户只需通过“手工编辑”功能即可创建新功能。但如果 Nenex 是一块 _白板_，用户必须为他们可能想要的每个功能都实际这样做，那将是繁重的（尽管“从零开始引导你自己独特的知识库/维基/编辑器”可能是一个有趣的练习）。

因此，Nenex 的 LLM 将在一个公开的“演示语料库”上进行预训练，该语料库是一个日志，其中包含了所有标准功能的演示。用户可以贡献额外的演示来“修补”问题。⁠[⁠12⁠](https://gwern.net/nenex#fn12)

## [实现功能](https://gwern.net/nenex#implementing-features "链接到章节：§ '实现功能'")

在这种范式下，我们现在可以通过将许多“思维工具”目标表达为格式适当的日志项，然后使用 LLM 根据当前日志和/或提示来预测操作，从而实现这些目标。

^pr-b5b7c61e67c0

1.  **文本补全** 保持原样，只是现在包装在某种 `insert-text` 包装器中。

    建议的文本补全通过某种 GUI 或 TUI 界面呈现给用户，例如灰色文本或列在侧边栏中。（一个用于所有 LLM“评论”的侧边栏，类似于流媒体网站如何在视频旁边或下方实现聊天窗格，将是 GUI 的明显首版。）

    如果用户忽略了呈现的补全并继续书写，这会以通常的方式自动纠正 LLM：那些补全毕竟不是很可能，本就不应被预测；反之，如果用户确实接受了某个补全，也是如此。无需做任何特殊处理，只需记录通常的文本插入即可。

    -   _复制/粘贴_：剪切/复制/粘贴，无论是简单熟悉的形式，还是文本编辑器支持的更强大形式（如 Emacs 的 kill-ring 和寄存器），都是打字之后最常见的任务。在大多数情况下，几次击键就足以指定一切，而让 LLM 参与并无帮助。

        在更复杂的情况下，比如用户可能大量使用寄存器来存储多个不同的复制文本片段，并在不同时间粘贴它们，强大的文本补全可以提供相同的功能：用户“剪切”几个文本片段（无需显式决定寄存器存储），在日志中创建离散的原子文本节，然后输入第一个或两个单词，并接受 LLM 对其余部分的制表符补全。这避免了命名、记忆和指定各个寄存器的认知开销。

    -   _缩写/模板_：另一个常见的文本编辑器高级用户功能是各种“文本扩展”：输入一个缩写可能会扩展为完整的拼写单词或短语，或者一个 ID 可能会扩展为某种模板，如格式信函。这些通常被 LLM 进行的普通文本补全所涵盖，只要它能足够字面地访问历史记录，尤其是如果用户养成了在输入机械文本之前先输入 ID 或关键字的习惯。

    -   _自动链接_：高度超链接文本的最大麻烦之一就是简单地添加相关链接。自动链接是一个令人烦恼的问题，过去的自动化方法不够智能，无法在不花费大量精力的情况下使其工作，但手动操作既太容易又太难。每个链接都需要回忆和查找，给容易出错的记忆带来压力。像 [英语维基百科⁠](https://en.wikipedia.org/wiki/English_Wikipedia) 这样的网站可以依靠编辑者使用专门的链接添加工具，但个人 wiki 不行。这也不像设置正则表达式/URL 对那么简单，因为那样常常会误触发（或无法触发），即使所有文本命中都有效，也会导致过度链接——通常，人们只想链接第一个实例，嗯，除非第一个实例在文本中距离较远或读者可能没有注意到，在这种情况下，也许人们还想链接一些后面的实例，这取决于上下文……

        然而，LLM 可以轻松记住用户曾经写过的完整超链接集，并且可以轻松理解微妙的上下文规则，如“通常只链接第一个”。而链接预测只是文本预测的一个子集。

2.  **拼写检查**通过用户运行拼写检查或直接编辑错误单词的日志自动学习。

    与补全类似，拼写检查会自我修正。如果用户拒绝更正，则该操作会被记录，模型会学习预测该拒绝及其无效性，并应保留和预测该单词。

3.  **摘要/抽象**：大多数LLM可以被提示为一篇文章撰写摘要。

    如果情况并非如此或需要自定义摘要，则可以通过日志条目训练抽象能力，这些日志条目包含现有文章、移除摘要、添加摘要提示前缀和摘要后缀。

4.  **分节**：为一篇文章创建一组良好的层级标题可能很繁琐。

    这可能无法通过提示实现，但可以像摘要一样进行训练：通过定义分节提示、从现有文章中移除章节并将其作为答案附加来构建训练示例。

    这会以通常的方式在线学习：例如，用户运行 sectionize 函数，注意到某个章节标题不好，修复它，现在日志中就有了一个新示例：‘这里是一个不好的标题，用户将其纠正为好的标题’，而‘好标题’的概念下次会得到改进。

5.  **导航**操作：在不同文件（或 Emacs 术语中的‘缓冲区’）之间切换是另一种需要记录和预测的操作。

    让 LLM 在文本编辑器中自主切换缓冲区不一定有用，但它_可以_预测要切换到的‘默认’缓冲区。鉴于当前时刻之前的上下文（LLM 知道这些，因为它被动态评估，并且可以在其上下文窗口中看到最新的日志条目），所需的缓冲区通常是显而易见的——用户已反复切换到它，或者存在定期的缓冲区切换循环，或者某个缓冲区包含与当前段落相关的文本。

    随着 LLM 变得更好，用户可以简单地点击一个简短易用的键绑定来‘执行我的意图’。

6.  **变更控制**：在给定用户示例的情况下，选择编辑并将其总结为补丁可以自动化。

    用户可以将一组编辑指定为一个‘补丁’，编写摘要，并将其作为条目‘提交’到日志中。编辑可能采用差异（diff）的形式，或者它们可能只是指定一个日志条目范围，例如前 1000 个日志条目加上摘要‘记录了今天的自行车之旅’。

    然后这就变得可提示了。

7.  **任意知识**都可以被添加到日志中，包裹在一个空操作命令里。

    例如，如果我们希望教会LLM有用的参考文献，我们可以发出某种`download-paper https://arxiv.org/abs/2023.1234`命令，该命令将下载论文的全文并将其插入日志中。LLM将在论文文本上进行训练，学习所有相关内容，并且现在将理解我们对“如Smith等人2023年所示，需要20个GPU才能frobnicate一个doodad”的引用，并且可能会指出Smith实际上说的是“10个GPU”。

    或者我们可以添加电子邮件、聊天记录、网页片段或键盘日志。这些输入不一定有直接用途，但关于作者的知识越多越好。

    （由于该模型是私有的，并在本地为用户定制，假设不使用API，这不会带来隐私风险——想必作者在发表自己的文章之前会_阅读_它们，并会看到任何意外泄露，比如泄露他们的地址！我们还可以注意到，对远程模型进行微调是一种强大的混淆形式，这对于担心训练数据语料库的传票和法律发现的公司来说尤其重要；如果你微调模型并丢弃数据，模型就像人类员工一样，保留了能力/知识，但必须被明确“询问”才能提取任何信息……)

    -   _接入更好的模型_：一个特别值得强调的“任意知识”来源是_更大、更好的模型_。

        当我谈论使用 Nenex 本地模型与使用远程 SaaS API 模型（尤其是昂贵的前沿 LLM）时，这并不是严格的非此即彼：我们可以同时使用 _两者_！没有理由说我们的本地模型不能学会在不确定时调用大型模型寻求帮助。

^pr-780c8d29579c

        让我们称之为顾问模型。你可以简单地将最后 _n_ 百万个令牌的上下文转储到另一个模型中，获取输出（这将非常智能，但受限于缺乏个性化），并将其放入本地模型的日志中使用，然后进行训练。

        你这样做得越多，就越能将顾问的相关知识‘蒸馏’到本地模型中，同时本地模型也越能学会何时适合调用顾问。

8.  **学习检索：**

    模仿学习方法的一个优点是，神经网络可以学习近似任意复杂过程的输出，例如更大的神经网络、人类或自动化工具。

    一个值得近似的有用例子是向量搜索。向量搜索往往不够灵活，因为嵌入是为通用目的生成的，并且存在博而不精的问题。

    然而，Nenex LLM 可以学习定制化的检索。它记住了相关作品的 URL，并能在响应查询时建议这些链接；随着相关链接被插入到文章中，这变成了更多的反馈。

    它甚至可以学习模仿 _实际_ 检索数据库的响应！当检索查询被执行并记录结果时，那就是训练数据。这可以与检索后过滤相结合：“查找与 `(retrieve 'https://arxiv.org/abs/2023.1234')` 相关的 Transformer 论文”，其中检索以正常的向量搜索方式进行，然后 LLM 过滤掉非 Transformer 论文，并返回最终匹配的 URL1–_n_。这变成了一个日志条目（“查找 Transformer 论文…” → URL1–_n_），在某个时刻，用户可以直接询问类似“`https://arxiv.org/abs/2023.1234` 的 Transformer 内容是什么？”这样的查询，而它就知道。

    除了本身有用之外，这种嵌入模仿可以帮助向神经网络灌输更通用的知识，更好地组织其对检索材料的理解。

9.  **过时页面**：随着你编辑和时间流逝，不可避免地会出现“漂移”，这是自然语言中相当于[⁠比特腐烂⁠](https://gwern.net/holy-war#bitrot)的现象。你能在 Nenex 中解决这个问题吗？当然可以。

    你只需取用神经网络（它已经记住了你的 wiki），并在每个上下文窗口的文本上运行它（可能结合相似文本范围的检索），提示为“这段文字中是否有任何过时或不正确的信息？如果有，生成一个修复它的编辑”，每次它预测出一个编辑时，就向用户展示上下文和编辑；如果用户接受，它立即生效，无论如何，它都会被添加到日志中，模型会在此基础上进行微调，并重新启动全站更新。

^pr-60dd2d0109ce

    每次它进行编辑或用户拒绝编辑时，它都会学习，整个网站会迅速更新任何过时的段落。用户不可能每次更新内容或一周过去后都阅读整个网站……但模型可以！

    你可以想象对此的许多优化。嵌入定义了一个图，因此每当用户编辑一段文本时，这个迭代更新过程就可以从被编辑的文本开始，进行广度优先遍历，根据用户刚刚写的内容寻找需要更新的文本。（例如，你有一堆记录某个软件工具的页面，你打开编辑器写下“版本1.0现在可以处理JSON”，然后所有提到“JSON”的段落都会被模型检查，模型会说“显然这个写着‘该工具不处理JSON’的页面现在已经过时了，让我们询问用户是否要编辑`[−not ]`。”）

10.  **评论/批评**⁠[⁠13⁠](https://gwern.net/nenex#fn13)：提示可以激发模型中的不同角色来提出写作建议。

     由于LLM的全部能力可用，我们可以从任何角度请求写作建议和批评。用户可以将一组提示打包成单个命令，如`M-x criticize-paragraph`。角色可以由用户指定，但也可以提示模型检索或生成要使用的列表。

     批评功能可以由Nenex智能地运行，仅当它看到段落完成且用户继续到下一段时：如果这是一个内容丰富的段落，那么值得写批评，但如果是一个简短的段落，比如修辞性陈述，则可以跳过。这将在用户使用它时自然发生。

     -   _头脑风暴_：既然我们已经为GPU付费，我们不妨做更多的后台任务。评论/批评的一个例子是尝试头脑风暴新想法；人们可以做一些事情，比如[“白日梦循环”⁠](https://gwern.net/ai-daydreaming)，并检索语料库的随机片段以尝试生成新颖的输出，并将最有希望的传递给用户进行评估。

## 原文

Proposal for a personal wiki built on neural nets: all edits are logged & used to finetune a NN assistant in realtime.

> Ex­ist­ing per­sonal wikis or per­sonal knowl­edge man­age­ment tools (eg. Roam, Ob­sid­ian, org-mode) make highly lim­ited use of the wave of pow­er­ful lan­guage & code-generating neural net­works (LLMs like GPT-4), lim­ited to minor im­prove­ments such as sug­gest­ing rel­e­vant links or of­fer­ing copy­edit­ing sug­ges­tions.
> 
> This is due less to a lack of neural net­work ca­pa­bil­i­ties than the dif­fi­culty of in­te­grat­ing them into doc­u­ment sys­tems all de­signed in par­a­digms long pre­dat­ing LLMs. If [Van­nevar Bush⁠](https://en.wikipedia.org/wiki/Memex) or [Dou­glas En­gel­bart⁠](https://en.wikipedia.org/wiki/Douglas_Engelbart) were de­sign­ing a ‘neural wiki’ from the ground up to be a ‘tool for thought’, tak­ing GPT-4-level LLMs for granted, what would that _look like_?
> 
> It would prob­a­bly not look like ex­ist­ing tools, which take a hy­per­text ap­proach of a col­lec­tion of in­de­pen­dent nodes ref­er­enc­ing each other and version-controlled as text files. Sim­ple text-file-based ap­proaches like copy­ing in en­tire doc­u­ments quickly run into per­for­mance lim­its or small but non-trivial error rates.
> 
> A more nat­ural ap­proach would be to draw in­spi­ra­tion from DL scal­ing par­a­digms in treat­ing ‘every­thing as a se­quence pre­dic­tion task’: in this LLM-centric wiki par­a­digm (**Nenex**), the wiki would not be file/node-centric but _edit_\-centric.
> 
> In­stead of being hob­bled by cloud providers op­ti­miz­ing for sim­plic­ity & jeal­ous of their gener­i­cized chat­bot mod­els, you log all ac­tions to train _a local LLM_ to im­i­tate _you_, and use the sys­tem al­ter­nat­ing be­tween tak­ing ac­tions and ap­prov­ing/dis­ap­prov­ing ex­e­cu­tion of pre­dicted ac­tions. As data ac­cu­mu­lates, the LLM learns not sim­ply tool usage or generic text pre­dic­tion, but pre­dic­tion of _your_ text, with your unique ref­er­ences, pref­er­ences, and even per­son­al­ity/val­ues.
> 
> The wiki is rep­re­sented not as a set of sta­tic files with im­plicit his­tory, but in more of a revision-control sys­tem or func­tional pro­gram­ming style as a his­tory of edits in a mas­ter log; the LLM sim­ply learns to pre­dict the next ac­tion in the log (using [‘dy­namic eval­u­a­tion’⁠](https://gwern.net/doc/ai/nn/rnn/2010-mikolov.pdf#page=2) fine­tun­ing for scal­a­bil­ity).
> 
> All user edits, ref­er­ence ad­di­tions, spellchecks or new vo­cab­u­lary ad­di­tion, sum­ma­riza­tion, up­dates of now-outdated pages etc., are just more ac­tions for the LLM to learn to pre­dict on the fly. It can flex­i­bly use [em­bed­dings⁠](https://en.wikipedia.org/wiki/Word_embedding) & re­trieval, sim­ple ex­ter­nal tools (such as down­load­ing re­search pa­pers), & op­er­ate over an API. A Nenex’s LLM can be eas­ily up­graded by train­ing new mod­els on the Nenex log, ad­di­tion­ally trained on all rel­e­vant in­for­ma­tion (pri­vate or pub­lic), and in­cor­po­rate ar­bi­trary feed­back from the user.
> 
> A Nenex would in­ter­ac­tively tai­lor it­self to a user’s writ­ing style, knowl­edge, ex­ist­ing cor­pus, and en­able se­man­tic fea­tures un­avail­able in other sys­tems, such as search­ing a per­sonal wiki for pages that need up­dat­ing given up­dates to other pages.

[A](https://gwern.net/dropcap#kanzlei)s of September 2023, LLMs have revolutionized my code writing, but I would have to admit that they have not revolutionized my natural-language writing—as part of my Gwern.net work, I’ve integrated LLMs in a few modest ways like handling annoying formatting tasks (eg. converting LaTeX math expressions to HTML+[Unicode⁠](https://en.wikipedia.org/wiki/Unicode)) or for doing vector search of annotations (as you can see in most Gwern.net popups as the `similars` tab). And sometimes I can pop an essay into GPT-4 or Claude-2 and get some good suggestions.

Not impressive. There is just not that much I can get out of an LLM if all it can do is implement short code requirements I can express in a chat format without too much friction, and I have to do everything else for it.

## [Background: Lifeless Corpuses](https://gwern.net/nenex#background-lifeless-corpuses "Link to section: § 'Background: Lifeless Corpuses'")

> …Writing shares a strange feature with painting. The offsprings of painting stand there as if they are alive, but if anyone asks them anything, they remain most solemnly silent. The same is true of written words. You’d think they were speaking as if they had understanding, but if you question anything that has been said because you want to learn more, it continues to signify just that same thing forever…it always needs its father’s support; alone. it can neither defend itself nor come to its own support.
> 
> “Socrates”, [Plato’s _Phaedrus_⁠](https://en.wikipedia.org/wiki/Phaedrus_\(dialogue\))

Something I find depressing about writing, as compared to programming, is how _inert_ it is. Writing does not _do_ anything and when one writes, the words simply accumulate. The ideas expressed in those writings will link & build on each other, but the writing process itself remains unaffected: no matter how many millions of words one has written, each time, one confronts the same empty page and blinking text cursor. No matter how many times one corrals notes into an essay or expands an outline or runs spellcheck, it takes the same amount of work the next time, and even the fanciest text editor like [Emacs⁠](https://en.wikipedia.org/wiki/Emacs) or [Scrivener⁠](https://en.wikipedia.org/wiki/Scrivener_\(software\)) offers little help. (In part because the benefit of many features—especially keybindings—is less than the effort it would take to learn & configure & remember how to use them.)

And this is true for other formats, like periodicals. No matter how famous and influential a periodical is, it is only as good as its latest issue, and the periodical as an organization & corpus, has shockingly little value. For example, magazines like _Time_ or _Life_ or _Newsweek_ became nearly worthless overnight thanks to the Internet, and what gets published under those brand names are but pale shadows of the original globe-shaking colossi. It doesn’t matter how many extraordinary writers dedicated their lives to them or how vast their reportage was or or how large their archives (tellingly called [“morgues”⁠](https://en.wikipedia.org/wiki/Morgue_file)) are—they have all sold for a song. The writing itself, the editors, the technical equipment, the printing presses, the culture—all now worthless. (Much of that residual value reflected the IP copyright licensing value of their photographic archives to stock photography giants like Getty Images.) Nothing is more useless than yesterday’s news.

And yet, why is it? Why isn’t the accumulated wisdom of decades of writing more useful?

What is it about such intellectual work like writing that there is so little ‘infrastructure’ or ‘capital’ such that one could ‘plug a new intern into _Time_’ and they suddenly become a far better journalist? Why couldn’t the spirit of _Time_, the genius loci of a century of reporting, possess an intern, imbuing them with vast knowledge & all the secrets of the newsroom and skills like knowing where to dig up dead bodies or how to read the hidden clues a lying politician is giving you?

Well, obviously, because all of that is either locked in another human’s head (who is probably long gone), or it’s sitting inert and hidden in a mountain of dead trees. No matter how large that corpus gets, no matter what treasures are buried within, it still does nothing and it will never speak for itself, and we have no tools to levitate it with.⁠[⁠1⁠](https://gwern.net/nenex#fn1)

What I want is to _animate my dead corpus so it can learn & think & write_.

## [Wanted: Real Writing Assistants](https://gwern.net/nenex#wanted-real-writing-assistants "Link to section: § 'Wanted: Real Writing Assistants'")

LLMs are convenient, as far as they go, but that is not far. I’m disappointed how little use I’ve made of such astonishingly powerful technology: these are brains in boxes that could almost write my essays for me! There have to be more useful writing LLM tools than these—like there is in writing code, where GPT-4 has rapidly become indispensable for quickly writing or reviewing my code.⁠[⁠2⁠](https://gwern.net/nenex#fn2) But it doesn’t seem like there’s any writing tools which have gone much further.⁠[⁠3⁠](https://gwern.net/nenex#fn3) Certainly, popular writing tools like Roam, Obsidian, org-mode/Logseq etc. do not seem to have made much progress incorporating LLMs in any profound way.⁠[⁠4⁠](https://gwern.net/nenex#fn4)

It’s not like there aren’t plenty of things about the standard tool-for-thought experience which couldn’t be improved by LLMs. For example, tag management is a perennial pain point: adding tags to pages or URLs, splitting up overgrown tags, naming the new sub-tags… All extremely tedious chores which cause users to abandon tagging, but also [⁠straightforwardly automatable⁠](https://gwern.net/design#future-tag-features) using LLM embeddings+prompts. Naming & titling short pages is a hassle that discourages creating them in the first place. Breaking up a long essay into a useful hierarchy of section headers is not the most fun one could have on one’s laptop in bed. Or consider writing good revision/patch summaries for all that—annoying!⁠[⁠5⁠](https://gwern.net/nenex#fn5)

## [Writing Assistant Limitations](https://gwern.net/nenex#writing-assistant-limitations "Link to section: § 'Writing Assistant Limitations'")

> “Ginny!” said Mr. Weasley, flabbergasted. “Haven’t I taught you anything? What have I always told you? Never trust anything that can think for itself if you can’t see where it keeps its brain?”
> 
> _Harry Potter and the Chamber of Secrets_, J. K. Rowling

But it’s easy to see barriers to a deep integration of LLMs. The first question is: how do you even get your text _into_ an LLM for it to do anything with it? You immediately run into the problem that most LLM use can accept a small amount of text (a small fraction of an essay), and only temporarily—that text will be forgotten as soon as that request finishes. This means that an LLM is ignorant of the rest of your personal wiki, never mind even larger feasible text datasets that would be highly useful. (For example, an LLM personal assistant would benefit from studying all your emails & chats, and the text of every paper or web page you’ve read.) You also can’t update the LLM: it would be great if you could compile a list of every error your LLM assistant made (like flagging a new name or vocabulary term as a spelling error), and feed that back in; but you can’t do that either, because if you put the list of errors & corrections into the LLM input, it wouldn’t fit. And you can forget about ideas like feeding a livestream of your typing to the LLM to teach it how you think & revise text.

Putting stuff into LLMs is such a barrier that most uses revolve around figuring out how to dice up a large text corpus in a way which isn’t too error-prone to feed in a small morsel of text and get back something useful that can then be blindly inserted back into the corpus. (And because these can’t be all that useful, they must be extremely cheap, and one may not bother with them at all.)

We also have security issues: our LLM assistant is too easily turned into a [confused deputy⁠](https://en.wikipedia.org/wiki/Confused_deputy), executing orders that come from attackers via prompt injection, rather than our own commands, because they tend to _look_ the same, and our LLM assistant just doesn’t know that much about us—if “we” command it to delete all our files, how should it know that that’s not something we’d ever do? It was simply trained to be ‘helpful’, without any particular details about helpful to _whom_.

## [Dynamic Evaluation](https://gwern.net/nenex#dynamic-evaluation "Link to section: § 'Dynamic Evaluation'")

> The Moving Finger writes; and, having writ,
> 
> Moves on: nor all thy Piety nor Wit
> 
> Shall lure it back to cancel half a Line,
> 
> Nor all thy Tears wash out a Word of it.
> 
> Edward FitzGerald (#51, _Rubáiyát of Omar Khayyám_)

The biggest problem with LLMs is the processing bottleneck of attention limiting its ability to flexibly learn from any kind of corpus.

We _could_ wait for better [attention & memory mechanisms⁠](https://gwern.net/doc/ai/nn/transformer/attention/index). It’s a hot area of research, and publicly-accessible models like Claude-2 can, as of September 2023, digest up to hundreds of thousands of tokens. Perhaps that is what neural wikis are waiting for? Or some further tweaks to retrieval?

But large context windows are still extremely expensive, the attention seems to routinely fail or result on confabulations and it seems likely that a Transformer over hundreds of thousands of tokens will be inherently slow if it must reprocess the entire input for every token output. And we want millions or tens of millions of tokens, with as little fancy architecture engineering as possible—a real LLM maximalist wants to program NNs using not code, but data (and pre-existing data at that).

There is an alternative to context windows, if we look back in DL history to the now-forgotten age of RNNs. If we drop the usual unstated assumption that one _must_ use stateless API calls which cannot be personalized beyond the prompt, the idea of finetuning becomes an obvious one. As NN models are so vastly overparameterized and store vast amounts of memorized facts in their weights, they can easily accommodate anything that a user might write, or their reference database—after all, they generally saw billions or trillions of tokens during training, so what’s a few million more? Large NNs are increasingly sample-efficient, learning more from fewer data points than smaller models, often memorizing while still generalizing; in fact, they can sometimes memorize text after only one exposure. And finetuning doesn’t need to be one-and-done, or limited to running offline in a batch process overnight while the user sleeps.

When [RNN⁠](https://en.wikipedia.org/wiki/Recurrent_neural_network) users wanted the best performance possible on a new corpus of text, what did they do? They used [**dynamic evaluation**⁠](https://arxiv.org/abs/1308.0850) ([Transformer version⁠](https://arxiv.org/abs/1904.08378), [w⁠](https://arxiv.org/abs/2310.10638#facebook)/[retrieval⁠](https://arxiv.org/abs/2305.18466))⁠[⁠6⁠](https://gwern.net/nenex#fn6): essentially, just finetuning the model (using ordinary [‘online’⁠](https://en.wikipedia.org/wiki/Online_machine_learning) [SGD⁠](https://en.wikipedia.org/wiki/Stochastic_gradient_descent)) each timestep on each input as it arrived.⁠[⁠7⁠](https://gwern.net/nenex#fn7) (For example, a char-RNN might predict the next character, receive the actual next character, do a [backprop⁠](https://en.wikipedia.org/wiki/Backpropagation) step, and predict the next character after that by feeding the current hidden state into the newly-weight-updated RNN.) This lets the model learn from the latest data, in a more profound way than simply being in a context window & doing in-context/meta-learning, because the weights can change repeatedly over many timesteps, building on prior weight updates, and permanently encoding knowledge into its weights. Language models can memorize samples seen only a few times during training, or even once, but still benefit [from training for multiple epochs⁠](https://arxiv.org/abs/2305.16264#huggingface), so we can have our cake and eat it too: have smart models which memorize—indeed, we can deliberately train models to memorize large sets of facts to serve as a long-term memory, such as the unique [IDs of relevant documents⁠](https://arxiv.org/abs/2206.02743#microsoft). (For more background on this paradigm, see my [⁠AUNN proposal⁠](https://gwern.net/aunn#memorization) which takes the memorizing-data paradigm to its limit.)

![A humorous critique of complicated solutions to LLMs having limited context windows which are widely used in industry and proposed by researchers, in the format of the ‘mental gymnastics’ meme, contrasting the simplicity of dynamic evaluation of models on new data vs the vast menagerie of ad hoc solutions, ranging from complicated search techniques to exotic bleeding-edge hardware optimizations to complicated model retraining procedures working around the limitations of fixed large models.](https://gwern.net/doc/ai/nn/dynamic-evaluation/2023-12-31-gwern-mentalgymnasticsmeme-dynamicevaluationvsalternativeapproaches.jpg "A humorous critique of complicated solutions to LLMs having limited context windows which are widely used in industry and proposed by researchers, in the format of the 'mental gymnastics' meme, contrasting the simplicity of dynamic evaluation of models on new data vs the vast menagerie of ad hoc solutions, ranging from complicated search techniques to exotic bleeding-edge hardware optimizations to complicated model retraining procedures working around the limitations of fixed large models.")

Challenges in using a frozen model with large new time-varying datasets.

Dynamic evaluation is particularly good at updating a model to a rather different data distribution, handling repeated or rare/novel (or both) tokens, at a constant factor cost (which can be dropped as necessary), while in principal being able to improve indefinitely. It may be able to help small models surpass (frozen) large models or large expensive context windows (see [Rannen-Triki et al 2024⁠](https://arxiv.org/abs/2403.01518#deepmind)).

This makes dynamic evaluation much more suitable than other techniques like vector retrieval for highly-personalized long-form writing, where one might introduce many new concepts, terms (eg. ‘Nenex’), or references, which a pretrained model might not know and which might not be in the context window either (because the previous instances were in a different file, or just too far away in the current file either before or after the focus): as soon as it is used, it is infused into the model’s weights, and the more surprising or novel the unpredicted text is, the larger the update. At the beginning, when text still fits into the context window & the Transformer can learn in-context, dynamic evaluation won’t help too much because it is still ‘warming up’, but it will gradually improve the more text it sees, while an amnesiac Transformer cannot; few-shot prompting can, with enough examples, [catch up to finetuning⁠](https://arxiv.org/abs/2404.11018#google), but may require thousands of examples and use up a context window of even millions of tokens at staggering expense & latency; and a batch-finetuned Transformer may be competitive, but it will be so only at greatly staggered intervals—too late to assist the user in writing their current essay.

This would be a natural way to implement a personal writing assistant: finetuning is not that expensive when amortized over heavy use⁠[⁠8⁠](https://gwern.net/nenex#fn8), a user doesn’t type fast in terms of tokens per second, so a good Transformer can keep up while being dynamically evaluated (and even train on the [same minibatch repeatedly⁠](https://arxiv.org/abs/1806.07353) or go back to do multiple epochs), and the Transformer will be able to predict substantially better over large corpuses.

We can also get unique performance benefits from personalization, like _customized tokenization_. Users of English-centric LLMs may not notice this, but there is a substantial performance penalty to BPE token dictionaries needing to cover every possible language and modalities like source code, which bloats dictionaries out to hundreds of thousands or millions of unique tokens to try to compress them all. But a jack of all trades is the master of none, and why does a user, who may write exclusively in, say, Chinese and do no programming, need to pay the performance penalty of all these other domains? If a user could specialize the BPE to their personal corpus (similar to compression utilities like [Brotli⁠](https://en.wikipedia.org/wiki/Brotli)), they could probably get a noticeable improvement in token compression (maybe 10–20%?); and the size of their BPE dictionary can be scaled to their corpus size using hyperparameter search or known token scaling laws. This would require retraining the LLM to handle the potentially large change in vocabulary, as many rare or foreign tokens suddenly get reused for things the user often says, but this is not a major technical challenge as dynamic evaluation can handle domain shift and the new tokenization can be learned by tricks like paired ‘translations’ (ie. forcibly tokenizing all the new tokens into their individual byte token equivalents to teach the LLM the equivalence).

The naive approach would be to just predict one’s writing inside the text editor, with some tab-completion assistance. That’s fine, but we can do better. If it can predict the user’s next typed word action, why not predict the user’s next action, period? Not just Backspace to correct a typo, but _all_ actions: spellcheck, writing commit messages, switching text buffers… Much like AI agents, [a text editor wants all possible context⁠](http://www.catb.org/esr/writings/taoup/html/ch13s03.html#id2967765), to be able to operate on all text that affects a user; it does not want to be a narrow tool.

(Our goal here is not ‘superintelligence’, but ‘superknowledge’.)

## [Performance](https://gwern.net/nenex#performance "Link to section: § 'Performance'")

Because users type slowly on average, if the LLM is fast enough to provide completions in a reasonable timeframe at all, then it can probably be dynamically evaluated as well; if it is not, then one can begin optimizing more heavily.

For example, one could run models in parallel: train a model one place while running a model (not necessarily identical) elsewhere. Lightweight finetuning methods like [LoRA⁠](https://arxiv.org/abs/2106.09685#microsoft) may be helpful, although not a panacea, because the point is not to hardwire the model to a pre-existing capability, exploiting the linearity & low-dimensionality of most tasks, but to have the model memorize _everything_ about the user, ideally everything they’ve ever written or read, and all data available from sources like emails or calendars, which is a large amount of detailed brute facts that must be memorized & will not fit in a ‘lightweight adaptor’ of a few kilobytes (or even megabytes)—so eg. LoRA works fine for instruction-tuning in English, but lightweight finetuning methods do not [generalize⁠](https://arxiv.org/abs/2410.21228) or [scale well⁠](https://arxiv.org/abs/2402.17193#deepmind), and to do it in [a different language altogether⁠](https://arxiv.org/abs/2304.08109) requires true finetuning. The sampling-only model could use heavy performance optimizations like [quantization⁠](https://gwern.net/doc/ai/nn/sparsity/low-precision/index) (which can be done quickly).

Transformer models are inherently latency-tolerant in this sort of parallel setup, because their large context window provides a buffer for training; the model does not need to be up-to-the-second to work, because the most recent user behavior will still be in the context window. The in-context learning can substitute for dynamicism as long as the context window doesn’t ‘overflow’.

Even if it overflows, it will probably be hard for the user to notice the decay immediately—they would need to be invoking behavior uniquely dependent on unpredictable text in the gap between the context window (which the user’s actions are constantly repopulating with relevant text) and the already-dynamically-evaluated model constantly being synced over from the training process.

And the further behind the training model becomes, the more opportunity it has to use _n_ > 1 minibatches to switch from serial training to parallel batch training, and leapfrog to the present, and do one big sync with the sampling model. (And if GPU VRAM permits sampling but not any training, then the alternate training instance can be located on CPU, where there may be enough RAM to slowly train.)

If the user slows down, then the problem will solve itself.

## [Immutability](https://gwern.net/nenex#immutability "Link to section: § 'Immutability'")

We can do this by stepping back from simply recording typed words, to recording all actions. The central object is no longer a static text file sitting on disk, but a sequence of actions. Every text file is built up by a sequence of actions taken by the user: inserting other files, deleting words, spellchecking, typing, running built-in functions to do things like sort lines… Each action can be logged, and the LLM dynamically trained to predict the next action.⁠[⁠9⁠](https://gwern.net/nenex#fn9)

This would work particularly well with a Lisp approach, as Lisp systems like Emacs can easily serialize all executed user actions to textual [S-expressions⁠](https://en.wikipedia.org/wiki/S-expression), and then call the LLM to generate a new S-expression, and interpret _that_ to achieve anything that the user could do.⁠[⁠10⁠](https://gwern.net/nenex#fn10)

## [Imitation Learning](https://gwern.net/nenex#imitation-learning "Link to section: § 'Imitation Learning'")

This gives a new paradigm for a ‘text editor’. Where Emacs is “everything is a buffer or Lisp function”, and vi is “everything is a keystroke”, for a neural assistant, “everything is user imitation”. All user actions and state transitions are stored as a sequence, and predicted by the LLM.

The LLM is now an imitation learning deep [reinforcement learning⁠](https://en.wikipedia.org/wiki/Reinforcement_learning) agent, similar to a [Decision Transformer⁠](https://sites.google.com/berkeley.edu/decision-transformer) like [Gato⁠](https://arxiv.org/abs/2205.06175#deepmind) or [Toolformer⁠](https://arxiv.org/abs/2302.04761#facebook). It is both the operating system _and_ the user: it is training to predict the user’s actions in the text editor ‘environment’ to achieve good states (like a high-quality essay).

And because it is supervised by the user, its errors are corrected immediately, leading to a [DAgger⁠](https://arxiv.org/abs/1011.0686)\-like bootstrap: if the NN errors frequently in a particular way, it gets feedback on that class of errors and fixes it. This is because if a prediction doesn’t quite work, the user’s subsequent actions correct it: they either undo it and try again until they get the right thing, edit the wrong response into a right response (this can be a pervasive idiom, perhaps bound to a specific `should-have-been` function to edit anything that can be edited), or do the right thing manually. Each of these fixes the model to varying degrees, and ideally, will fix not just that specific instance or similar errors, but gradually improve the model’s responses as a whole by learning the joint function of user+corpus.

Because the model is being dynamically evaluated, these fixes happen _immediately_ and these improvements _stick_—they do not simply disappear out the context window (or disappear into some distant cloud database to perhaps someday improve a model which may be deployed next year).

The more the user writes or does, the more the model learns to imitate it and the user switches from ‘doing’ to ‘approving’, and the more can be delegated to the NN. This goal of imitating the user also helps resolve security concerns about destruction or exfiltration.⁠[⁠11⁠](https://gwern.net/nenex#fn11)

## [Warm-Starting](https://gwern.net/nenex#warm-starting "Link to section: § 'Warm-Starting'")

The LLM can be taught by demonstration to do many things, and new features created by the user simply by ‘hand-editing’ the feature. But it would be burdensome for the user if a Nenex came as a _tabula rasa_ where they had to actually do so for every feature they might want (as interesting an exercise as ‘bootstrapping your own unique knowledge-base/wiki/editor from scratch’ might be).

So a Nenex’s LLM would come pretrained on a public ‘demo corpus’, a log which ran through demonstrations of all standard functionality. Users could contribute back additional demonstrations to ‘patch’ problems.⁠[⁠12⁠](https://gwern.net/nenex#fn12)

## [Implementing Features](https://gwern.net/nenex#implementing-features "Link to section: § 'Implementing Features'")

With this paradigm, we can now accomplish many ‘tools for thought’ goals, by expressing them as appropriately-formatted log items and then using the LLM to predict actions conditional on the current log and/or prompts.

1.  **Text completion** remains as before, simply now wrapped in some sort of `insert-text` wrapper.

    The suggested text completion is presented to the user through some sort of GUI or TUI interface, like grayed-out text or listed in a side pane. (A side pane for all the LLM ‘commentary’, akin to how streaming websites implement chat in a pane next to or below the streamed video, would be the obvious first stab at a GUI.)

    If the user ignores the presented completions and continues writing, this automatically corrects the LLM in the usual way: those completions were not likely after all, and should not have been predicted; and vice-versa if the user _does_ accept a completion. Nothing special need be done, merely the usual text-insertion recorded.

    -   _Copying/pasting_: cut/copy/paste, in the simple familiar form and the more powerful forms supported by text editors (like Emacs’s kill-ring and registers), are the most common tasks after typing. In most cases, a few keystrokes is enough to specify everything, and involving an LLM would not help.

        In more complex cases, of the sort that one might make heavy use of registers to store multiple different copied pieces of text while pasting them at various times, powerful text completion can provide the same functionality: the user ‘cuts’ several pieces of text (without any explicit decision about register storage), creating discrete atomic sections of text in the log, and then types the first word or two, and accepts a tab-completion of the rest of it from the LLM. This avoids the cognitive overhead of naming and remembering and specifying individual registers.

    -   _Abbreviations/templates_: another common text editor power user feature is various sorts of ‘text expansion’: typing an acronym might expand out into the full spelled-out word or phrase, or an ID might expand out to some template like a form letter. These are generally subsumed by an LLM doing ordinary text-completion with sufficiently literal access to history, especially if the user made a habit of typing an ID or keyword first before the rote text.

    -   _Auto-Links_: one of the greatest hassles of densely hyperlinked text is simply adding relevant links. Auto-linking is one of the annoying problems where past automated methods aren’t quite smart enough to make it work without a lot of effort, but doing it manually is both too easy & too hard. Each link has to be recalled & looked up, stressing fallible memory. A website like [English Wikipedia⁠](https://en.wikipedia.org/wiki/English_Wikipedia) can count on editors using specialized link-adding tools, but not a personal wiki. It is also not as simple as setting up regexp/URL pairs, as that will often misfire (or fail to fire), and even when all the text hits are valid, result in over-linking as well—usually, one only wants the _first_ instance linked, well, unless the first instance is distant in the text or a reader might not have noticed it, in which case maybe one wants some later instances as well, depending on the context…

        However, an LLM can easily memorize the full set of hyperlinks a user ever writes, and it can easily understand subtle contextual rules like ‘link the first one only—usually’. And link prediction is simply a subset of text prediction.

2.  **Spellcheck** is automatically learned by logs of the user running spellcheck or simply editing erroneous words.

    Like completions, spellcheck fixes itself. If the user rejects corrections, then that is logged and the model learns to predict the rejection and that it was not useful, and the word in question should be preserved & predicted.

3.  **Summarization/abstraction**: most LLMs can be prompted to write abstracts for an essay.

    Should this not be the case or customized abstracts desired, abstraction can be trained by log entries which take the existing essays, the abstract removed, an abstraction prompt prefixed, and the abstract suffixed.

4.  **Sectionizing**: creating a good set of hierarchical headers for an essay can be tedious.

    This may not be promptable, but can be trained like summarization: construct the training examples by defining a sectionizing prompt, strip the sections from existing essays, and append them as the answer.

    This learns online in the usual way: eg. the user runs the sectionize function, notes that one section header is bad, fixes it, and now there’s a new example in the log of ‘here is a bad header that the user corrected to a good header’, and the concept of ‘good header’ improves for next time.

5.  **Navigation** actions: switching between different files (or ‘buffers’ in Emacs terminology) is another action to be logged and predicted.

    It would not necessarily be useful to let the LLM autonomously switch buffers in the text editor, but it _can_ predict a ‘default’ buffer to switch to. Given the context up to the present instant (which the LLM knows, because it is being dynamically evaluated & can see the latest log entries in its context window), the desired buffer is usually obvious—the user has switched to it repeatedly, or there is a regular cycle of buffer switches, or one buffer contains text relevant to the current paragraph.

    As the LLM gets good, the user can simply tap a short easy keybinding to ‘do what I mean’.

6.  **Change control**: selecting edits and summarizing them as a patch can be automated given user examples.

    A user can designate a set of edits as a ‘patch’, write a summary, and ‘commit’ it to the log as an entry. The edits might take the form of a diff, or they might simply specify a range of log entries, like the previous 1000 log entries combined with the summary “wrote up today’s bike trip”.

    Then this becomes promptable.

7.  **Arbitrary knowledge** can be added into the log, wrapped in a null-op command.

    For example, if we wish to teach the LLM about useful references, we could issue some sort of `download-paper https://arxiv.org/abs/2023.1234` command, which would download the fulltext of the paper and insert that into the log. The LLM will train on the paper text, learning all about it, and will now understand our reference to “as Smith et al 2023 shows, it takes 20 GPUs to frobnicate a doodad”, and perhaps will point out that Smith actually said “10 GPUs”.

    Or we could add in emails, or chats, or web page snippets, or keyboard logs. These inputs do not necessarily have direct uses, but the more knowledge about/from the author, the better.

    (As the model is private and customized for the user locally, assuming no API use, this poses no privacy risks—presumably the author is _reading_ their own essays before publishing them and would see any accidental leaks like publishing their address! We can also note that finetuning a remote model is a powerful form of obfuscation, which is a fact of particular interest to companies worried about subpoenas & legal discovery over training data corpuses; if you finetune the model and throw away the data, the model, like a human employee, keeps the capability/knowledge but has to be explicitly ‘questioned’ to extract any information…)

    -   _Plugging in better models_: one source of ‘arbitrary knowledge’ particularly worth highlighting is _bigger, better models_.

        When I talk about using the Nenex local model vs using a remote SaaS API model (especially an expensive frontier LLM), this is not a strict xor: we can use _both_! There is no reason that our local model cannot learn to call, when uncertain, out to a large model for assistance.

        Let’s call that advisor models. You can simply dump the last _n_ million tokens of context into another model(s), get the output (which will be highly intelligent, but limited by lack of personalization), and put that into the local model’s log to use, and then train on.

        The more you do this, the more you ‘distill’ the relevant knowledge from the advisors into the local model, and the more the local model also learns when it would be good to call out to an advisor.

8.  **Learned retrieval:**

    One of the advantages of an imitation-learning approach is that the NN can learn to approximate the output of arbitrarily complicated processes, such as larger NNs or humans or automated tools.

    One example of something useful to approximate is vector search. Vector search tends to be inflexible because the embeddings were generated for generic purposes, and suffer from being a jack-of-all-trades.

    A Nenex LLM, however, can learn customized retrieval. It has memorized the URLs of relevant works, and can suggest them in response to a query; as the relevant links get inserted in essays, this becomes more feedback.

    It can even learn to imitate an _actual_ retrieval database’s responses! When retrieval queries are executed and the results logged, that is training data. This can be combined with post-retrieval filtering: “look up Transformer papers related to `(retrieve 'https://arxiv.org/abs/2023.1234')`”, where the retrieval happens in the normal vector search way, and then the LLM filters out the non-Transformer papers, and returns the final matches URL1–_n_. This turns into a log item of (“look up Transformer papers…” → URL1–_n_), and at some point the user can just ask a query like “what’s the Transformer stuff for `https://arxiv.org/abs/2023.1234`?” and it knows.

    Aside from being useful in its own right, such embedding imitation can help instill more general knowledge into the NN, better organizing its understanding of retrieved material.

9.  **Outdated Pages**: as you edit, and time passes, inevitably there’s ‘drift’, the natural language equivalent of [⁠bitrot⁠](https://gwern.net/holy-war#bitrot). Can you solve this in Nenex? Of course.

    You simply take the NN (which has memorized your wiki), and run it over each context window’s worth of text (perhaps packed with retrieval of similar text ranges), with the prompt “Is there any outdated or incorrect information in this passage? If there is, generate an edit fixing it”, and for each time that it predicts an edit, prompt the user with the context and the edit; if the user accepts it, it happens immediately, and regardless, it is added to the log and the model finetunes on it and restarts the site-wide update.

    Each time it makes an edit or the user rejects an edit, it learns, and the site as a whole quickly updates any outdated passages. The user can’t read the whole site every time he updates something or a week passes… but the model can!

    You can imagine many optimizations to this. An embedding defines a graph, so any time the user edits a piece of text, this iterative update process can kick off at the edited text and do breadth-first traversal looking for text to update based on what the user just wrote. (eg. you have a bunch of pages documenting some software tool and you fire up the editor and write ‘version 1.0 can now handle JSON’ and then all the passages which mention ‘JSON’ get inspected by the model which says ‘well obviously this page which says “the tool does not handle JSON” is now out of date, let’s ask the user for an edit to `[−not ]`.’)

10.  **Commentary/critique**⁠[⁠13⁠](https://gwern.net/nenex#fn13): prompts can elicit different persona in the model to make writing suggestions.

     Since the full power of the LLM is available, we can ask for writing advice & critiques from any angle. A user could package up a set of prompts into a single command, like `M-x criticize-paragraph`. The personas could be specified by the user, but one could just as well prompt the model to retrieve or generate a list to use.

     The criticize function could be intelligently run by Nenex only when it sees a paragraph is finished and the user moved on to the next paragraph: if it’s a meaty paragraph, then it’s worth writing the critique, but if it’s a short paragraph, like a rhetorical statement, then it can be skipped. This would happen naturally as the user makes use of it

     -   _Brainstorming_: Since we have paid for a GPU, we might as well do more background tasks. One example of commentary/critique is trying to brainstorm new ideas; one could do things like a [“day-dreaming loop”⁠](https://gwern.net/ai-daydreaming) and retrieve random fragments of the corpus to attempt to generate novel outputs, and pass the most promising up to the user for evaluation.
