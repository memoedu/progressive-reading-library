# 延迟测量中的一些陷阱｜Some latency measurement pitfalls

---

## 正文

_这是我一两年前在 Twitter 做的一场简短 lightning talk 的 pseudo-transcript（为使其比 100% 忠实的 transcription 更易读，实际措辞有所修改），内容是我们使用 latency metrics 时的陷阱（根据公关要求，实际 service names 已作 anonymized 处理）。自这次 presentation 以来，infra 方面在这个问题上已有显著进展，因此情况比当时介绍的改善了很多，但我认为这些内容仍有意义，因为在与同行公司的人员交谈后，我发现许多人也面临类似问题。_

我们在 Twitter 经常使用 [tail latency](https://research.google/pubs/pub40801/) metrics。最常见的情况是，service owners 想得到自己 services 的 cluster-wide 或 Twitter-wide latency numbers。遗憾的是，由于我们的 latency measurement setup 中一些历史遗留的特殊之处，service owners 通常使用的 numbers 与我们想要 measure 的内容有所不同：

-   不透明且未加监测的延迟：Opaque, uninstrumented, latency
-   缺乏集群范围的聚合能力：Lack of, cluster-wide, aggregation capability
-   分钟级分辨率：Minutely resolution

#### 不透明且未加监测的延迟：Opaque, uninstrumented, latency

当我们查看大多数 services 的 dashboards 时，其中显示并用于 alerting 的 latency metrics 通常来自 service 本身运行所在的 server。一些 services 的 dashboards 是由曾受 invisible latency 困扰的 senior SREs 设置的，这些 dashboards 还会包含来自该 service 的 callers 的 client-observed latency。我想讨论这种 setup 的三个问题。

在这次演讲中，我们可以把一个 client request 看作：在 client "user" code 将 request 传给我们的 RPC layer，即 Finagle([https://twitter.github.io/finagle/](https://twitter.github.io/finagle/)) 之后，到 client user code receive response 之前，会经过下面的 pipeline（按照 Finagle 目前 handles requests 的方式，一旦 request 被交给我们使用的 network library——[netty](https://danluu.com/latency-pitfalls/\(https://netty.io/\)，我们就无法取得某个特定 request 的 timestamps）

`client netty -> client Linux -> network -> server Linux -> server netty -> server "user code" -> server netty -> server Linux -> network -> client Linux -> client netty`

正如我们之前在\[一份 quantifying [CFS bandwidth control throttling](https://www.kernel.org/doc/html/latest/scheduler/sched-bwc.html) 的 impact，以及我们使用 excessively large thread pools 如何 causes throttling 的内部文档\][1](https://danluu.com/latency-pitfalls/#fn:W)中看到的，我们经常在 netty 内部及其下方遇到大量 queuing，其连带影响是导致 services 被 kernel throttled，而这往往造成大量 opaque latency，尤其是在 high load 下，也就是我们最希望 dashboards 显示 correct latency numbers 的时候。。

当我们在 server 处 sample latency 时，我们得到的基本上是来自以下部分的 latency

-   服务器服务的“用户”代码：Server service "user" code

当我们在 client 处 sample latency 时，我们基本上得到以下部分

-   服务器服务的“用户”代码：Server service "user" code
-   服务器端的 netty：Server-side netty
-   服务器端的 Linux 延迟：Server-side Linux latency
-   客户端的 Linux 延迟：Client-side Linux latency
-   客户端的 netty 延迟：Client-side netty latency

这里有两个问题：仅凭 metrics data，我们没有好办法判断 stack 的 opaque parts 中的 latency 来自 client 还是 server。作为 service owner，如果你根据 client latency 设置 alerts，那么即使你的 service 运行顺畅，当 client 上的 netty 或 Linux 中有过多 queuing 导致 client latency rises 时，你也会收到 alerted 通知。

此外，考虑到我们 expose 的内容，那些适合查看的 client latency metrics 给出的是某个 client 与之通信的所有 servers 的 latency，这与我们从 server metrics 中看到的视角十分不同：后者给出 per-server latency numbers，而我们没有好办法跨所有 clients 对 per-server client numbers 进行 aggregate，所以很难判断，例如某个特定 server instance 是否在 netty 中存在 high latency。

下面是几个在 client 与 server 处 measured 的 latency 的 cluster-wide measurements 示例。这些示例经过有意挑选，以展示 client 与 server 之间各种 deltas 的横截面。

![这张 Graph 显示，在 client 与 server 处 measured 的 latency 之间存在 large difference](https://danluu.com/images/latency-pitfalls/service-1.webp)

这是一个 [CDF](https://en.wikipedia.org/wiki/Cumulative_distribution_function)，采用 CDF 的 standard orientation 呈现，percentile 位于 y-axis，value 位于 x-axis，因此向下、向右表示 higher latency，向上、向左表示 lower latency；flatter line 意味着 latency 正在 increasing quickly，而 steeper line 意味着 latency 正在 increasing more slowly。

由于 chart 的两个 axes 都采用 log scale，尽管 lines 看起来相距并不那么远，client 与 server latency 之间的 difference 仍然很大。例如，如果查看 99%-ile latency，我们会看到，在 server 处 measured 时它是 ~16ms，而在 client 处 measured 时是 ~240ms，相差一个 15 的 factor。或者，如果我们查看某个 fixed latency，例如 240ms，并查找对应的 percentile，就会发现它是 client 上的 99%-ile latency，却远高于 server 上的 99.9%-ile latency。

下面的 graphs 具有类似的 properties，不过 client 与 server 之间的 delta 会有所不同。

![这张 Graph 显示，直到 p99.5，client 与 server 处的差异为 moderate，而在 p99.5 以上存在 large difference](https://danluu.com/images/latency-pitfalls/service-2.webp) ![这张 Graph 显示，直到 p74，在 client 与 server 处 measured 的 latency 之间存在 small difference，之后则出现 increasing divergence](https://danluu.com/images/latency-pitfalls/service-3.webp) ![这张 Graph 显示，直到接近 client timeout value，在 client 与 server 处 measured 的 latency 之间存在 moderate difference，而在 timeout value 附近存在 large divergence](https://danluu.com/images/latency-pitfalls/service-4.webp) ![这张 Graph 显示，直到 p999，在 client 与 server 处 measured 的 latency 之间存在 small difference，之后则出现 rapid increasing](https://danluu.com/images/latency-pitfalls/service-5.webp)

我们可以看到，在 client 处 measured 与在 server 处 measured 的 latencies 经常 differ significantly；即使在 lower percentiles 的 delta 很小的情况下，它有时也会在 higher percentiles 变大，因为更多 load 可能导致更多 queueing，从而在 netty 和 kernel 中产生更多 latency。

需要注意的一点是，对于任意特定的 measured server latency value，我们都会看到范围非常宽的 client latency values。例如，这里有一张 `service-5` 的 client 与 server latency 的 zoomed in scatterplot。如果我们 zoom out，就会看到，对于一个 server-measured latency 为 10ms 的 request，其 client-measured latencies 可以高达 500ms。更一般地说，我们看到许多 requests 的 server-measured latency 与 client-measured latency 非常接近，同时也有零星 requests，其 server-measured latency 是对 client-measured latency 非常 inaccurate 的 representation。在几乎所有这些情况下，client-measured latency 更高，原因是 stack 中对我们而言 opaque 的某个部分存在 queuing；而在（非常）少数情况下，client-measured latency 更低，原因是我们的 instrumentation 存在一些问题。在下面的 plot 中，由于我们 track latencies 的方式，我们的 latencies 只有 1ms granularity。下面 plots 中的 points 已经过 +/- 0.4ms 的 randomly jittered 处理，以便更好地看清 plot 上非常 dense 的 points 处的 distribution。

![这张 client 与 server latency 的 Per-request scatterplot 显示，任意特定的 server latency value 都可能与范围非常宽的 client latency values associated](https://danluu.com/images/latency-pitfalls/service-scatter.webp)

虽然可以将 instrumentation 贯通 netty 和 kernel，以便在 Finagle 将 requests 交出后 track request latencies（kernel 甚至提供了 hooks，使这件事还算直接），但在近期内，这项工作可能得不偿失。如果你想了解自己的 service 如何受到 opaque latency 的影响，那么借助 [Zipkin](https://zipkin.io/)，并利用 [Rebecca Isaacs、Jonathan Simms 和 Rahul Iyer 已经完成的工作](https://danluu.com/tracing-analytics/)，就很容易有个大致了解；我就是这样 generated 上面的 plots 的。这些 plots 的 code 已经 checked into \[我们 monorepo 中的一个 path\]，如果你只是想查看另一个 service，可以填入你自己的 service names。

#### 缺乏 cluster-wide aggregation capability

在上面的 examples 中，我们能够得到 cluster-wide latency percentiles，是因为我们使用了 Zipkin 的 data，而它会尝试 sample requests uniformly at random。由于种种原因，service owners 大多依赖 metrics data；这些 data 虽然因为是 unsampled 而更 complete，却无法让我们 compute cluster-wide aggregates，因为我们会按 per-shard 方式 pre-compute fixed aggregations，而且无法从 per-shard aggregates reconstruct 出 cluster-wide aggregate。

从我们各项 services 的 dashboards 来看，最常见的 latency target 是 shard-level 99%-ile latency 的 per-shard average（一些在 request tree 中处于 deep 位置的 services，例如 cache，会使用更靠近 tail 的 numbers）。遗憾的是，对 per-shard tail latency 取 average，违背了 monitoring tail latency 的目的。如果[我们想想为什么要使用 tail latency](https://brooker.co.za/blog/2021/04/19/latency.html)，就会发现，这是因为当我们有 high fanout 和 high depth request trees 时，极小一部分 server responses 的 slowing down 就能 slow down 许多乃至大多数 top-level requests；对 tail latency 取 average 无法体现使用 tail latency 的价值，因为 shard-level tail latencies 的 average 无法体现这样一种 property：一小部分 server responses 的 slow 就能 slow down 许多乃至大多数 requests，同时[也失去了查看 cluster-wide averages 的优势](https://brooker.co.za/blog/2017/12/28/mean.html)，而 cluster-wide averages 是可以从 per-shard averages reconstructed 出来的。

例如，当我们有少数 bad nodes 在 returning 时，这对 average per-shard tail latency 的 impact 很小，尽管 cluster-wide tail latency 会 highly elevated。正如我们在\[一份 quantifying 整个 fleet 中 machine-level issues 的程度及其对 data integrity 和 performance 的 impact 的文档\][2](https://danluu.com/latency-pitfalls/#fn:H)中看到的，我们经常遇到 host-level issues，它们能使一个 node 上的 tail latency 上升 one or more orders of magnitude，有时甚至能使该 node 的 median latency 超过其他 nodes 的 tail latency。由于少数甚至一个这样的 node 就能 determine 一个 cluster 的 tail latency，对所有 nodes 取 average 可能产生误导；例如，如果我们有一个 100 node cluster，其中一个 node 的 tail latency 上升了 10x，这可能使我们的 cluster-wide latencies 的 average increase by a factor of 0.99 + 0.01 \* 10 = 1.09，而 tail latency 的实际 increase 要大得多。

一些 service owners 尝试对 99%-ile 取 percentile，通常是 90%-ile 或 99%-ile，以得到 cluster-wide tail latency 的更好 approximation，但这也行不通，而且一般而言，并不存在能够 reconstruct cluster-level tail latency 的 per-shard percentile，或对 per-shard tail latencies 的其他 aggregation。

下面这些 plots 对比了人们在 dashboards 上用 instance-level metrics data 获取 cluster-wide latency 的各种尝试与一个 service 的实际（sampled）cluster-wide latency；对这个 service 而言，percentile of percentile 的尝试比对较小 services 的此类尝试更 accurate。我们可以看到，correlation 非常 weak，而且存在我们预料中的问题：tail 的 average 受到 outlier shards 的 influenced 程度没有它“应该”受到的那么大，而各种常用 percentiles 在 average 意义上，要么受到的 influenced 不够，要么受到的 influenced 过多，而且它们与实际 latencies 也只是 weakly correlated。由于我们以 minutely granularity 来 track metrics，下面 graphs 中的每个 point 代表一分钟，其中 sampled cluster-wide p999 latency 位于 x-axis，dashboard aggregated metric value 位于 y-axis。由于来自 tracing pipeline 的 individual latency measurements 具有 1ms granularity，points 会被 jittered horizontally +/- 0.3ms，以更好地展示 distribution（vertically 不会应用这种 jitter，因为我们的 metrics pipeline 没有这一 limitation，因此那些 data 的 precision 更高）。

![per-shard p999 的 average 与实际 p999 的 Per-minute scatterplot，显示 per-shard p999 的 average 是非常差的 approximation](https://danluu.com/images/latency-pitfalls/cluster-1.webp) ![per-shard p999 的 p99 与实际 p999 的 Per-minute scatterplot，显示 per-shard p999 的 p99 是较差的 approximation](https://danluu.com/images/latency-pitfalls/cluster-2.webp) ![per-shard p999 的 p999 与实际 p999 的 Per-minute scatterplot，显示 per-shard p999 的 p999 是非常差的 approximation](https://danluu.com/images/latency-pitfalls/cluster-3.webp)

cluster-wide latency 与 per-shard latency 的 aggregations 之间的 correlation 如此 weak，以至于即使你选择了能产生 correct average behavior 的 aggregation，对几乎所有 samples（分钟）而言，其 value 仍然会相当 wrong。考虑到我们的 infra，这里真正可行的 solutions 只有：扩展我们的 tracing pipeline，使其可用于 dashboards 和 alerts；或者向 Finagle 添加 metric histograms，并将这些 data 经由所有环节 plumbing 到 \[dashboard software\] 中，从而获得 proper cluster-level aggregations[3](https://danluu.com/latency-pitfalls/#fn:M)。

虽然对 tail latencies 取 average 很流行，因为这样做很容易，而且人们对此很熟悉（例如，\[已隐去的同行公司名称\] 的 observability 的 TL 曾说，他们不应该费心考虑 averages 以外的任何东西，因为所有人都只想要 averages），但对 shard-level tail latencies 取 average 或其他 aggregation，既不具有人们想要的 properties，也不具有人们预期的 properties。

#### 每分钟的 resolution

另一个 independent issue 是，我们只以 minutely granularity collect metrics，这使我们在 observe infrastructure 中发生的情况时存在缺口。Rezolus 会以 secondly（有些情况下甚至是 sub-secondly）granularity 进行 metrics collection，但由于一些超出本次演讲范围的原因，它通常只用于 system-level metrics（有少数例外）。

我们都见过某些 bursty、sub-minutely event 导致问题的 incidents。让我们来看一个这样的 incident 的 example。在这次 incident 中，一个 service 出现了 elevated latency 和 error rate。查看我们 export 的 standard metrics 没有提供什么有用信息，但查看 sub-minutely metrics 就立即揭示了一条线索：

![sampled requests 的 per-request latency 的 Plot，显示一个 large spike，随后 request rate severely reduced](https://danluu.com/images/latency-pitfalls/minutely-1.webp)

对于一个 cache 的这个特定 shard（以及许多未展示的其他 shards），latency 在 `time 0` 出现了非常大的 increase，随后是 30 seconds 的极低 request rate。这 30 seconds 是因为 `service-6` 的 shards 被 configured 为：如果 `service-6` clients 遇到太多 failed requests，就将它们与之通信的 servers mark 为 dead，持续 30 seconds。这个 decision 是 distributed 的，这也就是为什么发往 `cache-1` 的受影响 shard 的 request rate 不是 zero；`service-6` 的一些 shards 在 elevated latency 期间没有向 `cache-1` 的那个特定 shard send requests，因此它们没有将 `cache-1` 的那个 shard mark 为 dead，并继续 issue requests。

request latency 的 sub-minutely view 非常清楚地显示了什么 mechanism 导致 `service-6` 中出现 elevated error rates 和 latency。

需要注意的一点是，缺乏 sub-minutely visibility 并不是这里唯一的 issue。大量 elevated latency 发生在 latency metric 无法看见的位置，导致 monitoring `cache-1` latencies 不足以 detect 这个 issue。下面，blue points 是 `cache-1` 的一个 single instance 所 reported 的 latency metrics，black line 则是 client observed 到的 measured（sampled）latency[4](https://danluu.com/latency-pitfalls/#fn:O)。Reported p99 latency 是 0.37ms，但实际 p99 latency 是 ~580ms，两者相差超过 three order of magnitude。

![reported metric latency 与来自 trace data 的 latency 的 Plot，显示 metric latency 与 trace latency 之间存在极大的 difference](https://danluu.com/images/latency-pitfalls/minutely-2.webp)

#### 总结（Summary）

虽然我们现有的 latency reporting 和 alerting setup 运作得相当不错，毕竟 site 通常都能正常运作，而且与规模相当的同行公司相比，我们的 reliability 实际上相当好，但这个 setup 确实也让我们付出了一些显著的 costs。

其中一点是，我们经常遇到一些 incidents，如果不使用那些被认为是 specialized、而且大多数人都不用的 tools，就很难看清究竟发生了什么，这增加了 on call 的 toil。另一点是，由于我们对 cluster-wide latencies 的 estimates 存在很大的 margins of error，为了避免 user-visible incidents，我们不得不 provision 大量的 slack，并维持远比我们实际想要达到的 latencies 更为严格的 latency SLOs。这会 increases operating costs，正如我们在\[一份将 per-user operating costs 与那些 serve 类似 kinds 和 levels 的 traffic 的公司进行 comparing 的文档\]中看到的那样。

_如果你喜欢这篇文章，你可能也会想读读关于 **[单个 host 上的 tracing 与 sampling profilers 的比较](https://danluu.com/perf-tracing/)** 的文章_。

#### 附录：open 与 closed loop latency measurements

我们的一些 synthetic benchmarking setups，例如 setup-1，使用 "closed-loop" measurement，也就是实际上先 send 单个 request，等它返回，再 send 另一个 request。其中一些允许一定程度的 parallelism，也就是可以同时有 N 个 request 处于 in flight 状态，但在 realism 方面仍然存在类似的问题。

作为这个问题的一个 toy example，假设我们有一个 service，它在 production 中每 second 恰好 receives 1 个 request，而且这个 service 的 normal response time 是 1/2 second。在 normal behavior 下，如果我们以每 second 1 个的速率 issue requests，就会 observe 到 mean、median 和所有 percentile request times 都是 1/2 second。留给读者一个 exercise：如果这个 service 没有 parallelism，而且在一次 1 minute benchmark run 的中途，有一个 request 耗时 10 seconds，请分别为 closed 与 open loop benchmark setup 的情形 compute mean 和 90%-ile latency；其中，benchmarking setup 在 open loop 情形下以每 second 1 个的速率 issues requests，在 closed loop 情形下也以每 second 1 个的速率进行，但会等待前一个 request 完成。

关于这一点的更多信息，请参阅 [Nitsan Wakart 关于 fixing YCSB benchmark 中这一问题的文章](https://psy-lob-saw.blogspot.com/2015/03/fixing-ycsb-coordinated-omission.html)，或 [Gil Tene 关于这一问题的演讲](https://www.youtube.com/watch?v=9MKY4KypBzg)。

#### 附录：unweighted averages 的使用

在我看过的 dashboards 上，averages 有一个常见问题，它与我们取 tail latencies 的 average 时出现的问题是 independent 的：unweighted average 经常会 underestimates 实际的 latency。

我经常在两种情况下看到 unweighted average：一种是有人通过取跨 datacenters 的 unweighted average 来得到 overall latency，另一种是有人通过取跨 shards 的 average 来得到 cluster-wide latency。这两种做法都有同一个问题，即具有 lower load 的 shards 往往也具有 lower latency。当我们 fail away from 某个 datacenter 时，这一点尤其明显。那些错误地使用跨 datacenters 的 unweighted average 的 Services，常常会显示 decreased latency，尽管实际 served requests 的 latency 却 increased 了。

## 原文

_This is a pseudo-transcript (actual words modified to be more readable than a 100% faithful transcription) of a short lightning talk I did at Twitter a year or two ago, on pitfalls of how we use latency metrics (with the actual service names anonymized per a comms request). Since this presentation, significant progress has been made on this on the infra side, so the situation is much improved over what was presented, but I think this is still relevant since, from talking to folks at peer companies, many folks are facing similar issues._

We frequently use [tail latency](https://research.google/pubs/pub40801/) metrics here at Twitter. Most frequently, service owners want to get cluster-wide or Twitter-wide latency numbers for their services. Unfortunately, the numbers that service owners tend to use differ from what we'd like to measure due some historical quirks in our latency measurement setup:

-   Opaque, uninstrumented, latency
-   Lack of, cluster-wide, aggregation capability
-   Minutely resolution

#### Opaque, uninstrumented, latency

When we look at the dashboards for most services, the latency metrics that are displayed and are used for alerting are usually from the server the service itself is running on. Some services that have dashboards set up by senior SREs who've been burned by invisible latency before will also have the service's client-observed latency from callers of the service. I'd like to discuss three issues with this setup.

For the purposes of this talk, we can view a client request as passing through the following pipeline after client "user" code passes the request to our RPC layer, Finagle([https://twitter.github.io/finagle/](https://twitter.github.io/finagle/)), and before client user code receive the response (the way Finagle currently handles requests, we can't get timestamps for a particular request once the request is handled over to the network library we use, [netty](https://danluu.com/latency-pitfalls/\(https://netty.io/\))

`client netty -> client Linux -> network -> server Linux -> server netty -> server "user code" -> server netty -> server Linux -> network -> client Linux -> client netty`

As we previously saw in \[an internal document quantifying the impact of [CFS bandwidth control throttling](https://www.kernel.org/doc/html/latest/scheduler/sched-bwc.html) and how our use of excessively large thread pools causes throttling\][1](https://danluu.com/latency-pitfalls/#fn:W), we frequently get a lot of queuing in and below netty, which has the knock-off effect of causing services to get throttled by the kernel, which often results in a lot of opaque latency, especially when under high load, when we most want dashboards to show correct latency numbers..

When we sample latency at the server, we basically get latency from

-   Server service "user" code

When we sample latency at the client, we basically get

-   Server service "user" code
-   Server-side netty
-   Server-side Linux latency
-   Client-side Linux latency
-   Client-side netty latency

Two issues with this are that we don't, with metrics data, have a nice way to tell if latency is in the opaque parts of the stack are coming from the client or the server. As a service owner, if you set alerts based on client latency, you'll get alerted when client latency rises because there's too much queuing in netty or Linux on the client even when your service is running smoothly.

Also, the client latency metrics that are reasonable to look at given what we expose give you latency for all servers a client talks to, which is a really different view from what we see on server metrics, which gives us per-server latency numbers and there isn't a good way to aggregate per-server client numbers across all clients, so it's difficult to tell, for example, if a particular instance of a server has high latency in netty.

Below are a handful examples of cluster-wide measurements of latency measured at the client vs. the server. These were deliberately selected to show a cross-section of deltas between the client and the server.

![Graph showing large difference between latency measured at the client vs. at the server](https://danluu.com/images/latency-pitfalls/service-1.webp)

This is a [CDF](https://en.wikipedia.org/wiki/Cumulative_distribution_function), presented with the standard orientation for a CDF, with the percentile is on the y-axis and the value on the x-axis, which makes down and to the right higher latency and up and to the left lower latency, and a flatter line meaning latency is increasing quickly and a steeper line meaning that latency is increasing more slowly.

Because the chart is log scale on both axes, the difference between client and server latency is large even though the lines don't look all that far apart. For example, if we look at 99%-ile latency, we can see that it's ~16ms when measured at the server and ~240ms when measured at the client, a factor of 15 difference. Alternately, if we look at a fixed latency, like 240ms, and look up the percentile, we see that's 99%-ile latency on the client, but well above 99.9%-ile latency on the server.

#### Lack of cluster-wide aggregation capability

In the examples above, we were able to get cluster-wide latency percentiles because we used data from Zipkin, which attempts to sample requests uniformly at random. For a variety of reasons, service owners mostly rely on metrics data which, while more complete because it's unsampled, doesn't let us compute cluster-wide aggregates because we pre-compute fixed aggregations on a per-shard basis and there's no way to reconstruct the cluster-wide aggregate from the per-shard aggregates.

From looking at dashboards of our services, the most common latency target is a per-shard average of shard-level 99%-ile latency (with some services that are deep in the request tree, like cache, using numbers further in the tail). Unfortunately, taking the average of per-shard tail latency defeats the purpose of monitoring tail latency. If [we think about why we want to use tail latency](https://brooker.co.za/blog/2021/04/19/latency.html) because, when we have high fanout and high depth request trees, a very small fraction of server responses slowing down can slow down many or most top-level requests, taking the average of tail latency fails to capture the value of using tail latency since the average of shard-level tail latencies fails to capture the property that a small fraction of server responses being slow can slow down many or most requests while [also missing out on the advantages of looking at cluster-wide averages](https://brooker.co.za/blog/2017/12/28/mean.html), which can be reconstructed from per-shard averages.

For example, when we have a few bad nodes returning , that has a small impact on the average per-shard tail latency even though cluster-wide tail latency will be highly elevated. As we saw in \[a document quantifying the extent of machine-level issues across the fleet as well as the impact on data integrity and performance\][2](https://danluu.com/latency-pitfalls/#fn:H), we frequently have host-level issues that can drive tail latency on a node up by one or more orders of magnitude, which can sometimes drive median latency on the node up past the tail latency on other nodes. Since a few or even one such node can determine the tail latency for a cluster, taking the average across all nodes can be misleading, e.g., if we have a 100 node cluster where tail latency is up by 10x on one node, this might cause our average of cluster-wide latencies to increase by a factor of 0.99 + 0.01 \* 10 = 1.09 when the actual increase in tail latency is much larger.

Some service owners try to get a better approximation of cluster-wide tail latency by taking a percentile of the 99%-ile, often the 90%-ile or the 99%-ile, but this doesn't work either and there is, in general, no per-shard percentile or other aggregation of per-shard tail latencies that can reconstruct the cluster-level tail latency.

Below are plots of the various attempts that people have on dashboards to get cluster-wide latency with instance-level metrics data vs. actual (sampled) cluster-wide latency on a service which makes the percentile of percentile attempts more accurate than for smaller services. We can see the correlation is very weak and has the problem we expect, where the average of the tail isn't influenced by outlier shards as much as it "should be" and the various commonly used percentiles either aren't influenced enough or are influenced too much, on average and are also weakly correlated with the actual latencies. Because we track metrics with minutely granularity, each point in the graphs below represents one minute, with the sampled cluster-wide p999 latency on the x-axis and the dashboard aggregated metric value on the y-axis. Because we have 1ms granularity on individual latency measurements from our tracing pipeline, points are jittered horizontally +/- 0.3ms to give a better idea of the distribution (no such jitter is applied vertically since we don't have this limitation in our metrics pipeline, so that data is higher precision).

![Per-minute scatterplot of average of per-shard p999 vs. actual p999, showing that average of per-shard p999 is a very poor approximation](https://danluu.com/images/latency-pitfalls/cluster-1.webp) ![Per-minute scatterplot of p99 of per-shard p999 vs. actual p999, showing that p99 of per-shard p999 is a poor approximation](https://danluu.com/images/latency-pitfalls/cluster-2.webp) ![Per-minute scatterplot of p999 of per-shard p999 vs. actual p999, showing that p999 of per-shard p999 is a very poor approximation](https://danluu.com/images/latency-pitfalls/cluster-3.webp)

The correlation between cluster-wide latency and aggregations of per-shard latency is weak enough that even if you pick the aggregation that results in the correct average behavior, the value will still be quite wrong for almost all samples (minutes). Given our infra, the only solutions that can really work here are extending our tracing pipeline for use on dashboards and with alerts or adding metric histograms to Finagle and plumbing that data up through everything and the into \[dashboard software\] so that we can get proper cluster-level aggregations[3](https://danluu.com/latency-pitfalls/#fn:M).

While it's popular to take the average of tail latencies because it's easy and people are familiar with it (e.g., the TL of observability at \[redacted peer company name\] has said that they shouldn't bother with anything other than averages because everyone just wants averages), taking the average or another aggregation of shard-level tail latencies has neither the properties people want nor the properties people expect.

#### Minutely resolution

Another, independent, issue that's a gap in our ability to observe what's going on with our infrastructure is that we only collect metrics at a minutely granularity. Rezolus does metrics collection on a secondly (and in some cases, even sub-secondly) granularity, but for reasons that are beyond the scope of this talk, it's generally only used for system-level metrics (with a few exceptions).

We've all seen incidents where some bursty, sub-minutely event, is the cause of a problem. Let's look at an example of one such incident. In this incident, a service had elevated latency and error rate. Looking at the standard metrics we export wasn't informative, but looking at sub-minutely metrics immediately reveals a clue:

![Plot of per-request latency for sampled requests, showing large spike followed by severely reduced request rate](https://danluu.com/images/latency-pitfalls/minutely-1.webp)

For this particular shard of a cache (and many others, not shown), there's a very large increase in latency at `time 0`, followed by 30 seconds of very low request rate. The 30 seconds is because shards of `service-6` were configured to mark servers they talk to as dead for 30 seconds if `service-6` clients encounter too many failed requests. This decision is distributed, which is why the request rate to the impacted shard of `cache-1` isn't zero; some shards of `service-6` didn't send requests to that particular shard of `cache-1` during during the period of elevated latency, so they didn't mark that shard of `cache-1` as dead and continued to issue requests.

A sub-minutely view of request latency made it very obvious what mechanism caused elevated error rates and latency in `service-6`.

One thing to note is that the lack of sub-minutely visibility wasn't the only issue here. Much of the elevated latency was in places that are invisible to the latency metric, resulting in monitoring `cache-1` latencies insufficient to detect the issue. Below, the reported latency metrics for a single instance of `cache-1` are the blue points and the measured (sampled) latency the client observed is the black line[4](https://danluu.com/latency-pitfalls/#fn:O). Reported p99 latency is 0.37ms, but actual p99 latency is ~580ms, an over three order of magnitude difference.

![Plot of reported metric latency vs. latency from trace data, showing extremely large difference between metric latency and trace latency](https://danluu.com/images/latency-pitfalls/minutely-2.webp)

#### Summary

Although our existing setup for reporting and alerting on latency works pretty decently, in that the site generally works and our reliability is actually quite good compared to peer companies in our size class, we do pay some significant costs as a result of our setup.

One is that we often have incidents where it's difficult to see what's going on without using tools that are considered specialized that most people don't use, adding to the toil of being on call. Another is that, due to large margins of error in our estimates of cluster-wide latencies, we have to have to provision a very large amount of slack and keep latency SLOs that are much stricter than the actual latencies we want to achieve to avoid user-visible incidents. This increases operating costs as we've seen in \[a document comparing per-user operating costs to companies that serve similar kinds of and levels of traffic\].

#### Appendix: open vs. closed loop latency measurements

Some of our synthetic benchmarking setups, such as setup-1, use "closed-loop" measurement, where they effectively send a single request, wait for it to come back, and then send another request. Some of these allow for a degree of parallelism, where N request can be in flight at once but that still has similar problems in terms of realism.

For a toy example of the problem, let's say that we have a service that, in production, receives exactly 1 request every second and that the service has a normal response time of 1/2 second. Under normal behavior, if we issue requests at 1 per second, we'll observe that the mean, median, and all percentile request times are 1/2 second. As an exercise for the reader, compute the mean and 90%-ile latency if the service has no parallelism and one request takes 10 seconds in the middle of a 1 minute benchmark run for a closed vs. open loop benchmark setup where the benchmarking setup issues requests at 1 per second for the open loop case, and 1 per second but waits for the previous request to finish in the closed loop case.

For more info on this, see [Nitsan Wakart's write-up on fixing this issue in the YCSB benchmark](https://psy-lob-saw.blogspot.com/2015/03/fixing-ycsb-coordinated-omission.html) or [Gil Tene's presentation on this issue](https://www.youtube.com/watch?v=9MKY4KypBzg).

#### Appendix: use of unweighted averages

An common issue with averages on dashboards that I've looked at that's independent of the issues that come up when we take the average of tail latencies is that an unweighted average frequently underestimates the actual latency.

Two places I commonly see an unweighted average are when someone gets an overall latency by taking an unweighted average across datacenters and when someone gets a cluster-wide latency by taking an average across shards. Both of these have the same issue, that shards that have lower load tend to have lower latency. This is especially pronounced when we fail away from a datacenter. Services that incorrectly use an unweighted average across datacenters will often show decreased latency even though actually served requests have increased latency.
