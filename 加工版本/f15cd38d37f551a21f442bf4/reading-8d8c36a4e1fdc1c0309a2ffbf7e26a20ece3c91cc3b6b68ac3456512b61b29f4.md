# 智能体运用测试／验证技术的能力如何？｜How well do agents use test/verification techniques?

---

## 正文

[我们此前指出，虽然让 coding agents 使用 effective test techniques 来达到某个 quality bar 比以往任何时候都更容易，但 software quality 似乎正在变差](https://danluu.com/ai-coding/)，这表明 developers 正在使用的 defaults 可能并不太管用。在这里，我们 test：仅仅 instructions agents 使用特定 techniques 或 libraries，是否会 improve implementation correctness，以此作为一种 test，看看当指导者并没有 testing 方面的 expertise，只是可能听说过应该 apply 某些 techniques 或使用某些 libraries 时，agents 能有多 effective。

我们将 re-use [这篇 agentic programming language effectiveness 比较中讨论过的 Zstd implementation eval](https://danluu.com/pl-tokens/)，不过这次改为 compare 不同的 testing techniques 和 testing libraries：给 agents 一个 implement Zstd 的 prompt，并附上不同的补充内容，例如“使用 test-driven development”“使用 Lean 4”“使用 QuickCheck”“使用 property-based testing”等。我还 ran 了一些其他 evals，例如针对 IMAP RFC 的 evals，文中也会简要讨论。

所有 implementations 都使用 Rust。tested 的 26 个 prompt conditions 是 ACL2、Alloy、“Audit 并 fuzz risky areas”、“先 Audit”、Creusot、Default（没有额外 instructions）、Differential testing、Fuzzing、Hegel、Insta、Judgement（要求 agents 使用最佳 technique）、Kani、Lean 4、“不要犯错”、Metamorphic testing、Mutation testing、Property-based testing、Proptest、QuickCheck、rstest、Rust built-in test framework、SMT solvers（Z3、cvc5 和 Yices 均可用）、Spin、TDD、TLA+ 和 Verus。另外还 tested 了 4 个 skills：搭配[官方 Hegel skill](https://github.com/hegeldev/hegel-skill/blob/ef36dc6b26a6dc0fdfdab5476b1affff37552ef0/skills/hegel/SKILL.md) 的 Hegel、[ECC Rust test skill](https://github.com/affaan-m/ECC/blob/e04ea0b9cc8248686edf5ac751cadff550e162b8/skills/rust-testing/)（ECC 是一个拥有 250k GitHub stars 和 38k forks 的 skills 集合）、[Trail of Bits property test skill](https://github.com/trailofbits/skills/blob/d3323cefbcf645678b8dc481de204b02ad3d02dc/plugins/property-based-testing/skills/property-based-testing/SKILL.md)，以及我写的一个 test skill（我是个守旧的人，使用 prompts 而不是 skills，对于如何写出好的 skill 完全没有感觉）。除了我自己的 skill，其余 skills 之所以被选中，是因为让 codex 寻找相关 skills 时，它找到的最靠前的就是这些。

### Predictions（预测）

我对各个 conditions 的表现 pre-registered 了一些猜测：

-   TDD 将会 underperform（55% confidence）
    -   我实际上就是因为认为 TDD 会 underperform，才特意加入了它
    -   我对此的 confidence 较低，因为我不知道 agents 在被 instructions 做 TDD 时会做什么；也许 agents 不会做 TDD，而会做某种不会 underperform 的事情（也可能是我对 TDD underperformance 的判断错了）
-   Formal methods 不会 overperform（52% confidence）
    -   我的想法是，虽然 formal methods 是 effective 且有用的（如今比以往任何时候都更是如此），但好的 test methods 也同样 effective 且有用；对于 simple problems，如果使用者的 competence 水平相近，formal methods 不应该 outperform
    -   与上面类似，而且程度更甚，我对此的 confidence 较低，因为我不知道 agents 在收到任何 instructions 时会做什么，而且在 agentic coding 方面，formal methods 比 effective test techniques 得到了更多炒作，因此完全有可能 labs 已经使用带有 synthetic data 的 RL environments 来 trained agents，让它们在 formal methods 上非常 effective，却没有 trained agents 使其 effective 地使用好的 test techniques（我原本以为后者更容易做到，但由于 effective test techniques 相对不时髦，所以没有人去做）
-   Make no mistakes 不会 outperform 没有 instructions 的情况（95% confidence）
    -   这就是个玩笑，而且很多人都试过。如果真管用，大家肯定早就注意到了吧？
-   ECC test skill（拥有 250k stars 和 38k forks）不会 outperform（65% confidence）
    -   它有点大，而且没有任何我认为会有用的信息。它 instructs agents 使用 TDD；如果它真的让 agents 使用了 TDD，我预计这会让事情变得更糟（而且它比 TDD condition 更具指令性，也许更可能成功，虽然说不定这反而会降低成功的可能性）；其余信息似乎没有用，却有一些 cost
    -   我所有的 skill predictions 都是 low confidence，因为我平时不太使用 skills，也不知道如何真正 evaluate 它们。我的思考方式是：“如果我把这些文字作为 prompt 传进去，让它待在 LLM 的 context window 里，会有多 effective？”
-   Hegel 的 skill 不会 outperform（65% confidence）
    -   它非常大（SKILL.md 加上链接的 Rust reference 超过 20k tokens），读起来更像 tutorial，而不是 agent instructions
-   Trail of Bits test skill 不会 outperform（55% confidence）
    -   它包含一些看起来可能有用的信息，但它也相当大

### 总体 results

下面有一张非常凌乱的 graph，展示了 tested conditions 的 results（使用 GPT-5.6 Sol 的 codex，efforts 为 medium 和 xhigh）。查看 data 时，相比大多数人，我往往更喜欢密集得多、凌乱得多的 graphs，[例如这里的第一张 graph](https://danluu.com/android-updates/)。由于大多数人觉得这类 graphs 凌乱到无法阅读，所以向别人展示信息时，我通常会把信息拆成一系列 graphs，每张展示较少的信息。由于下文会讨论的原因，我这次不打算这样做，而是直接展示这张极其凌乱的 graph：x axis 是 cost，y axis 是 passed 100%（hidden）tests 的 runs 所占的 fraction，取每个 condition 和 effort 的 80 次 runs 的 average（鼠标悬停在各项上会显示 bootstrap covariance、[50% uncertainty](https://statmodeling.stat.columbia.edu/2016/11/05/why-i-prefer-50-to-95-intervals/)，并且尝试为相似的内容使用相近的 colors，例如 formal methods 偏蓝，property-based testing 偏绿，等等）：

我们可以看到，没有什么真正大幅 outperforms。不过，Default（没有额外 instructions）的表现远高于 average。看 xhigh，平均而言，与 fuzzing 和 PBT 相关的 conditions 比 formal methods 稍好，而 medium 的情况则复杂得多。codex 推荐我们尝试的 testing 相关 skills 都 underperformed，不过我们快速定制的 skill 表现尚可（一个主要区别是，我们的 skill 旨在让它们偏离 default behavior，转向更 productive 的 behaviors，而其他 skills 看起来更像 tutorials）。正如预测的那样，TDD 表现不佳（一个 skill 也建议 agents 使用 TDD，而在 agents 尝试遵循该 instruction 的 cases 中，这个 skill 的表现也很差）。

如果真正看看 agents 做了什么，很快就会发现，总体上 agents 并不知道如何很好地使用这些 tools 或 techniques。[正如我们在这里指出的](https://danluu.com/ai-coding/)，也正如我聊过的所有人都指出的，agents 非常不擅长 testing，似乎不明白如何“by default”合理地 test。例如，[Gary Bernhardt 有这样一条评论](https://x.com/garybernhardt/status/2067002665427775613)：

> AI agents 对 testing 的做法，大致如下：
> 
> 1.  拿来某个 15 年前反对 mocks、却从未真正使用过 mocks 的人凭空想象的 pathological cases。对 excessive mocking 的天真幻想。
>     
> 2.  把这些 pathologies 作为你的 testing strategy 的支柱。
>     

事实证明，如果要求 agents 使用某个 test technique 或 test library，这种做法并不会像你希望的那样发生很大变化。我们会更详细地看看各个 cases 中发生了什么，但从 high level 来看，对于 test techniques，agents 往往要么仍然只是 write 它们通常会 write 的 tests，不过把它们放进另一类 test technique 的 framework 中；要么只是 superficially 使用某个 technique，却没有真正做那些能发挥该 technique 价值的事情。大多数时候，当某个 technique 被点名时，它们做的就是 Gary 描述的事情，只不过针对的是那个 technique（例如，对于 formal methods，它们大多 proved 无关的 properties；而对于 property-based testing，agents 会严重依赖完全 random inputs，大量 hit invalid/rejection cases，或者找一个 trivial property 来 check，再针对这个 trivial property run low-value random cases）。IMAP RFC 上的 results（我对每个 condition 尝试了 40 次 runs）或其他随意选取的 RFCs 上的 results（我尝试了少量单独的 runs）没有实质性差别。总体而言，不管 problem 是什么类型，无论是像 Zstd 这样的某种 bit manipulation problem、像 IMAP[1](https://danluu.com/agentic-testing/#fn:I) 这样的 protocol，还是其他任何东西，agents 都没有 effective 地使用 formal methods、test libraries 或 techniques。

在 xhigh 上，agents 通常能让自己写的 tests pass，但它们写的 tests 很差（例如，它们会向一个使用 four bitstreams 的 feature 的 test 提交 four identical bitstreams，从而漏掉任何因它们 transposed bitstreams 而发生的 bug）。[而且，正如我们此前在讨论 languages 时对 Zstd eval 指出的](https://danluu.com/pl-tokens/#appendix-medium-in-a-loop-vs-ultra)，在 naive loop 中以较低 effort level running，会得到更差的 results（agents 会更多地做这类事情，并在更低的 correctness 上停滞）。

我很好奇，为什么 AI labs 还没有创建 RL envs，让 agents 学会如何好好 test，因为 software 无法合理 working 似乎是影响 coding agent adoption 的重要问题，而且这似乎也是适合 RL 的事情。[正如我们此前看到的，agents 已经相当擅长 bounded runtime optimization problems](https://danluu.com/no-slow/)，这很合理，因为这恰好就是可以廉价创建大量 RL envs 来进行 train 的那类事情。也许这属于那种实际尝试时才发现比看起来更难的事情，但为 effective testing 和 test techniques 创建 RL envs，似乎属于同一类 problem。也许 limiting factor 只是关于 [effective test techniques](https://danluu.com/testing/) 的知识并不普及，所以没人想到尝试，大家反而让 agents inefficiently test（例如，做 standard unit testing）[2](https://danluu.com/agentic-testing/#fn:U)；又或者，由于某种原因，这个 problem 比 runtime optimization 难以封装得多？如果 agents 变得足够强，通常无需 testing 或 verification 就能 write correct code，那么这个问题可能很快就不再重要了；但至少对于从最初出现到现在（2026 年 9 月）公开可用的 agents 的状态而言，如果 agents 无需 testing expert 指导就对如何 test 有所了解，似乎本可以大幅提高 agentic coding effectiveness。

下面我们将按 correctness 从最差到最好排列，看看 agents 在每个 condition 下是怎么做的，但我提醒大家，不要从这个 ordering 得出任何强烈的 conclusions。

这里的许多 failures 似乎类似于我们研究 [programming language 对 token usage 和 correctness 的影响](https://danluu.com/pl-tokens/)时看到的 failures，因为这些 failures 往往是 idiosyncratic 的。例如，对于 programming languages，我们看到 agents 在 Clojure 中弄错 byte conversion 的 semantics 的比例相当高，但在 Java 中却并非如此，尽管 agents “应该”（而且可能也算是）知道，使用 `unchecked-byte` 而不是 `byte` 来 converting，就可以得到 Java byte conversion semantics。

尽管人们对于为什么某些 languages 比其他 languages 更适合 agents 有各种含糊的 high-level 解释，但当我们看看 agents 实际做了什么，以及 failure modes 是什么时，我听过的那些关于某人偏爱的 language 为什么适合 agentic coding 的解释，无论说的是 Elixir、Ocaml 还是 J，实际上没有一个成立（关于 Rust 的 memory safety 的评论除外，[这些评论在我们尝试的 multi-language pandoc eval 中，通过比较 agent-written C、C++ 和 Rust 之间的 memory safety issues 得到了 validated](https://danluu.com/pl-tokens/#appendix-more-details-on-zstd)）。相反，我们看到的是一堆原因不明的 idiosyncratic failures[3](https://danluu.com/agentic-testing/#fn:P)。对于 languages，因为我们能观察到 language popularity 与 performance（既包括 lower cost，也包括 higher correctness）之间存在 moderate correlation，所以一个看似合理的猜测是，更 popular 的 languages 有更多 training data（可能是 synthetic data，而不只是 human-written code）。这里没有 clear pattern，除了这样一点：当 agents 所拥有的只是某个 library 或 technique 的名字时，它们大多无法有效地 applying test 或 verification techniques（我们稍后会讨论什么做法更有效）。如果你不想阅读每个 condition 中发生的事情，[点击这里跳到最后一项](https://danluu.com/agentic-testing/#skill)。

### Verus（关于 Verus）

[Verus](https://github.com/verus-lang/verus) uses 一个 SMT solver 和各种 reasoning 来 prove：code matches specifications。

尽管 Verus 能够 prove：code matches specifications，但 agents 并没有这样做。相反，它们针对与 Zstd 有关的各种 abstract properties 做了 proofs。我自己没有用过 Verus 这样的 tool，所以我无法评价 expert 乃至 beginner user 通常会怎么做，但读过 tutorial 后，我觉得有点奇怪：agents 并未尝试用 Verus 来 verify 任何实际的 code，而只是用它做 abstract reasoning，因为它的设计似乎就是为了让人能轻松地 prove 实际 code 的 properties。

此外，如果我们看看那些被 proved 的 properties，会发现通常只有很少的 properties 被 proved，而且那些被 proved 的 properties 并不有趣。例如，agents 会 prove 这样的东西：“给定一个 valid cursor/index/distance，得到的 operation remains in bounds”，prove 这一点并不坏，但它实际上并不是 bugs 的来源。另外，agents 经常会写出 vacuous proofs，实际上就是 `A => A`。一个这种形式的实际 Verus proof 如下：

```
  requires                                                                                                                                                                                         
      0 < a <= window,                                                                           
      0 < b <= window,
      0 < c <= window,
  ensures
      0 < c <= window,
      0 < a <= window,
      0 < b <= window,
```

在 agents 确实 proved 了某些东西的情况下，它们通常 proved 的是相对 simple 的东西，并且避开了对那些可能有 bug 的部分的 properties 进行 proving（例如，agents 经常未能为 encode 和 decode 正确地 reverse bitstream order，并且会写出无法 detect 这一点的 tests，因为这些 tests 是 palindromic；也许这里某种关于 reversal 的 proof 能让 agents 换一种方式“思考”这件事）。

当只提供 Verus 和 Verus docs 时，agents 似乎并没有从 Verus 中获得价值。

如果我们看看结果，aggregate xhigh Verus results 还不错（correctness 比 average 略低，但便宜得多）。medium results 的 cost 处于 average，而 correct runs 的 percentage 最低，correct tests 的 average number 也最低。因为 agents 没有真正从 Verus 中获得价值，它们实际为 correctness 所做的主要只是 traditional tests（带有 unit tests 的 built-in Rust `#[test]` functions）。从 medium 到 xhigh，agents 在 traditional testing 上花费了多得多的 effort，而在使用 Verus 上只多花了一点 effort，这使 xhigh 的结果还算可以。

看看实际的 tests，对于使用 Verus 的 agents 表现差得多的两个 features 之一（[four stream jump table](https://github.com/facebook/zstd/blob/dev/doc/zstd_compression_format.md)），Verus agents 在 160 个 cases 中有 89 个为它写了 test，巧合的是，这个数字与 Default agents 完全相同，但 Verus agents 写出糟糕 tests 的可能性高得多。它们更容易在 tests 中 encode incorrect results，也更容易做出 easy to pass、却无法很好地 cover space 的 tests，例如让所有 four streams 都 identical。我说 failures 是 idiosyncratic，指的就是这种事情。Verus 本身并没有什么必然会让人在不使用 Verus 时写出糟糕 tests 的东西，而且一般来说，我们不会预期一个用过 Verus 的人会写出糟糕的 unit tests，就像我们不会预期一个使用 Clojure 的人会犯更多 byte conversion mistakes 一样，但这里不知为什么就是发生了（也可能是巧合）。

我不知道 AI labs 内部的人是否能获得更好的信息，了解这些事情为什么会发生，但我们这些外部的人通常很难判断这样的事情为什么会发生（即使我们对 language 问题形成了一个 plausible hypothesis，也需要 running 许多 languages 的许多 samples，而我们看过的研究同一问题的 papers 并未观察到 language popularity / agentic effectiveness correlation，因为它们要么考察的 languages 太少，无法对如此 weak correlation 进行 reason，要么考察的 problems 太小、太 trivial）。

### Alloy（关于 Alloy）

Alloy 经常被称为 bounded model checker。对于 Alloy 6，这也许不完全准确，因为它引入了一些额外的 features，但这远远超出了我的专业范围。我的理解是，使用 Alloy 时，你通常会 prove 你的 model 的 properties（而不是 proving 你的 code 能正常工作）。

Alloy 的 correctness score 倒数第 2，而且不同寻常的是，它在 medium 和 xhigh 上的 score 普遍都很差。尽管这里没有展示（因为似乎没提供什么额外信息），但总体而言，max 与 xhigh 的 results 是 highly correlated，而它们与 medium results 差异很大。

正如我们在 Verus 中看到的，使用 Alloy 的 agents 基本上依靠 standard Rust `#[test]` 来保障 correctness，而对 Alloy 大多只是在瞎折腾。再一次，糟糕地使用 formal tool 并没有帮助提高 correctness。

个别使用 Alloy 的 cases 差一点就找到了 issue 或 risk，但即便如此，这样的 cases 也只有少数。在一个 case 中，Alloy 找到了一个 counterexample，随后促使 agent 在 implement Rust version 时加入了针对 potential bug 的 mitigation。不幸的是，这个 counterexample 依赖于一个实际上不可能发生的 8-bit overflow，因为实际 implementation 使用的是 64-bit `usize`，而在给定 inputs 下不可能出现 overflow，所以它只是让 code 更 complex，却没有 preventing 任何实际的 bug。

在另一个 case 中，Alloy specification 是 incorrect 的，一个相关 test failed。test failed 后，agent fixed 了 Alloy specification。如果 specification 原本是 correct 的，也许 agent 就会写出 correct code，而不会出现这个 failure。有些 cases 可能发生了这种事情的好版本，但不清楚是否真的 prevented 了某个 potential bug。

Alloy agents 确实对一些比 Verus agents 所处理的东西更贴近 Zstd algorithm 的东西进行了 model（Verus agents 主要 checked arithmetic 之类的东西），但这仍然是错误的 modeling。

### Differential testing（差分测试）

Differential testing 是一种 technique：你把相同的 inputs 提供给多个 implementations，然后 compare results 来 find issues。原则上，这似乎是值得让 LLMs 尝试的合理做法，因为我们经常在不同次尝试中得到不同的 results，而且[正如我们在这里指出的](https://danluu.com/pl-tokens/#appendix-medium-in-a-loop-vs-ultra)，让 agent 在一个 implementation 上进行更多 iterate（它可能只是整个东西的一部分，甚至可能只是一个 function 的一部分），效果往往不如让 agent 从头重新开始。

但这给我们带来了倒数第三的 results。在这种情况下，我们在 xhigh 上的 results 略高于 average，在 medium 上的 results 则远低于 average。没有一个 agents 创建两个完整的 implementations 来 compare。在 160 次 runs 中，135 次做了某种你或许可以称为 differential testing 的事情，但和我们见过的其他 conditions 一样，这些通常都是 trivial 的，实际上毫无用处。而在 differential testing 本可能 caught a bug 的情况下，agents 并没有以 independent 的方式 implementing，而只是把同样的事情做了两遍，并在两个 versions 中 encoded 了相同的 bug。

我有时会告诉 agents independently 做事，并让它们以 separate contexts 启动，但在 differential 中，这并没有得到有效落实，agents 通常只会把同样的东西写两遍。

### Hegel Skill（Hegel 技能）

讨论官方 Hegel skill 如何改变 Hegel behavior 是合理的，但按照 correctness 从差到好的顺序，Hegel Skill 出现在 Hegel 上方，因为它的 correctness result 更差。关于这个 skill 的讨论，请参见下面的 Hegel 部分。

### Lean 4（Lean 4）

Lean 4 或许可以被描述为[一种 interactive theorem prover](https://en.wikipedia.org/wiki/Proof_assistant)。

虽然我没有为 Lean pre-register 一个猜测，但如果我曾 pre-registered 关于哪些 formal tools 会表现良好的猜测，我会把 Lean 列入我预期表现良好的名单，因为它相对热门、时髦，因此似乎比较有可能由于 RL envs 中的 synthetic data 而拥有良好的 performance。

Lean agents 确实做了 prove properties，但和 Verus condition 一样，agents 主要做的是 arithmetic proofs，并没有触及 bug-prone 或 risk surface areas。

和其他 formal conditions 一样，Lean agents 严重依赖 standard Rust tests。与目前为止的 formal conditions 一样，为无关紧要的东西做几个 proofs，并没有帮助提高 correctness。

### QuickCheck（QuickCheck）

QuickCheck 是[一种 property-based testing library](https://en.wikipedia.org/wiki/Property_testing)，在很长一段时间里，它可能都是最知名的此类 library，尽管如今这个头衔可能属于 Hypothesis。

遗憾的是，agents 使用 property-based testing 的 effectiveness，与使用我们目前见过的 formal tools 时差不多。在使用 QuickCheck 时，agents 主要编写非常简单的“smoke tests”，并没有 check 多少东西。它们还使用 random inputs，而这些 inputs 在 fully randomized 时，非常不适合 testing 像 Zstd 这样的东西（因为它们只会进入少数几个 failure/rejection code paths 之一）。

此外，被 checked 的 properties 相对很少。虽然所有 agents 都使用了 QuickCheck，但在 160 次 runs 中，有 63 次只 checked 了单个 property。agents 再次主要依赖 traditional testing，尽管从技术上说，它们确实使用了 QuickCheck。不知为什么，agents 实际上编写的 traditional tests 比 Default condition 或大多数其他 conditions 下更多，但进行的 test-fix iterations 更少（这使得这个 condition 的 cost 低于 average）。

### TDD（测试驱动开发）

TDD 在这里以及在 IMAP RFC eval 中都 underperformed。

TDD prompt 似乎导致 agent behavior 发生了很大变化。Agents 生成的 tests 数量是原来的两倍，并采用了更加 iterative 的 test-code-test-code-etc. workflow，尽管 TDD 倡导者可能会说，agents 实际上并没有使用 TDD。agents 进行某种 fine-grained iterative TDD 的情况只有少数几次。

总体而言，agents 在开始时编写了更多 tests；例如，在 160 个 cases 中，有 67 个 cases 的 agents 在进行实质性的（non-stub）implementation 之前，就已经有一个或多个 failing tests，而 Default condition 则是 160 个中有 0 个。

从宽泛的 test classes 来看，TDD 的每一种 tests 都更多。small、trivial tests 更多，integration 和 end-to-end tests 也更多。任何明显的 high-level 解释，比如“agents 做了太多或太少的 X”，似乎都不符合 data。如果我们查看具体的 failures，以及 tests 如何漏掉它们，就能观察到 TDD condition 中有不少这样的情况。例如，当存在四个 Huffman streams 时，Zstd 会使用一种叫作 jump table 的东西。

尽管 TDD agents 编写了更多 cover general case 的 tests，但它们更有可能 fail 针对此项的 eval test。不知为什么，TDD agents 更有可能编写不 cover hard cases 的 tests（例如，让全部四个 streams 都 identical，而且还让它们变得 trivial，就像我们在 Verus 中见到的那样）。这又是一个让我好奇 AI labs 内部的人拥有什么样的可见性的例子，因为从外部看，并不清楚为什么用 TDD 对 agents 进行 priming，会让它们编写更差的 tests 和更差的 implementations。

如果我们只能依据 TDD 和少数几个 test conditions 来判断，那么一个 hypothesis 可能是，TDD'd code 往往看起来有许多不太好的 small tests，因此，也许用 TDD 对 agents 进行 priming，会导致它们编写更多这类 ineffective tests。但目前不清楚，为什么我们会在 Verus 上看到相同的 pattern。也许可以在一个 open model 上 re-running 这个 experiment，并在某个层面 inspecting model 内部实际发生的事情；如果 Verus（或其他）behavior 存在共同原因，我们或许就能判断这对于 TDD 是否成立？

其中两个 skills 也让 agents 采用了更加 iterative 的方式，也许是基于更频繁地 executing 会带来更好 results 的理论，而这两个 skills 也都 underperformed。总体而言，在所有 conditions 中，agents 都能在 xhigh 和 max 上让自己编写的 tests pass（这里没有展示 max，但它的 correctness 略好于 xhigh，cost 则明显更好）。以更加 iterative 的方式让自己的 tests pass，往往会使 agents 编写更多 incorrect tests，从而 enforce incorrect behavior。

关于 TDD 为什么可能导致更差的 tests，Yossi Kreinin 有这样的想法：

> 姑且说说我的看法，我认为，如果你在 code 之前编写 tests，就更难 test 那些更难的 cases，因为你对哪些东西会难了解得更少；而且，即使你进行 random testing——我认为“tdd”与它并没有关联——你也更不可能把 distribution 引向 bugs 所在的方向。如果你编写过 code，或者至少能看看它，你就会知道哪些东西看起来是 trivially correct，哪些东西可能 work，也可能不 work，因为并不容易理解它在做什么。换句话说，tdd 会把你引向 black box testing，而对于 complicated machinery，在我看来，它的 effectiveness 不如 white box testing；我相当确定，人是这样的，但对 agents 就没那么确定了

我关于 TDD 会 underperform 的猜测是正确的吗？严格按 result 来说，答案是肯定的。至于我的 reasoning（没有以书面形式明确 pre-registered，但我确实知道自己当时在想什么），我认为还不清楚。我的想法大致是，正如我们[最近](https://danluu.com/benchpocalypse/)[讨论过的](https://danluu.com/ai-coding/)，在[各种 contexts](https://danluu.com/pl-tokens/) 中，让 agents 真正做出接近正确的事情，而不只是 overfit，是通过 agents 实现良好 performance 或 correctness 的关键部分。如果讨论的是 methodology 本身，而不是这条 instruction 如何改变 agent behavior，那么 TDD 看起来很容易导致 overfitting。

Agents 确实编写了更差的 tests，有时还采用了相对昂贵且 ineffective 的 iterative workflow，但我不知道，我所预期的人类使用 TDD、然后指挥 agents implement 时出现的 failure mode，是否真是这里的问题，而那个问题正是我的直觉来源。我会认为，这里的 reasoning 也许接近正确方向，也许并不接近；我认为，要判断这一点，还需要更多 evals 和调查，而且我猜 additional data 的 result 会表明，我原来的 reasoning 是错的。

### Spin（模型检查器）

Spin 是一个 model checker。

现在我们进入了 results 与 average 相差不大的范围。Spin 在 medium 和 xhigh 上都比 average 略差，cost 则低于 average。正如我们在其他 formal tools 上看到的，Spin 的使用总体上是 ineffective。具体到这里，使用 Spin 来 model 某一 class 的 behavior，与 covering 该 behavior 的 hidden tests 是 passing 还是 failing 之间没有 correlation。Spin 的使用是 superficial，而且并不 productive。

### Hegel（基于属性的测试库）

Hegel 是一个基于 [Hypothesis](https://github.com/hypothesisWorks/hypothesis/) 的 property-based testing library。

正如我们到现在可能已经预料到的，agents 并没有 effectively use Hegel。即使它们使用了，也只是 superficially 使用，而且通常是在 heavily relying on ordinary testing 之后才使用。由于反复说 agents 并没有真正有意义地做这件事会显得重复，我会把这些 sections 写得简短一些，只突出特别值得玩味的地方。

agents 实际使用的 workflow 通常是

1.  阅读 RFC 和 API/contract
2.  对 Zstd 进行 Implement
3.  对 normal tests 进行 Run
4.  阅读 Hegel docs
5.  使用 Hegel 来 write 1-4 个 simple property-based tests
6.  继续使用 normal built-in Rust tests

如上所述，Hegel skill 并没有 improve correctness。Correctness 更差了（不过差距很小，可能只是 random）。更引人注目的是，cost 高了很多（medium 上高了 26%，xhigh 上高了 41%），其原因看起来具有 causal 关系。

这个 skill 导致 agents generate 更多 tests。新增的 tests 主要是检查 malformed inputs 不会 cause a panic，以及 round-trip tests。对于所有 property-based 和 fuzzing conditions，agents 本来就倾向于过量做前者，所以在那里投入额外 effort 并没有用。后者似乎并不是一个 inherently bad idea（我甚至经常明确指示 agents create round-trip tests，而且它们似乎对于 check specific properties 很有用），但 agents 并没有在任何最 bug-prone 的 areas 这样做。没有额外 instruction 时，agents 倾向于为那些本来就很可能是 correct 的 relatively trivial properties 创建 round-trip tests。

至于 cost，它有多个原因。一个原因是这个 skill 相当大（skill 有 34k characters，而且还会 loads 一个 45k 的 Rust-specific reference，最终超过 20k tokens）。这些内容在 run 开始时被 loaded，并在后续许多 actions 中被 re-read。这使 medium 的 dollar cost 平均额外增加了 16%，xhigh 则增加了 18%（按 raw tokens 计算，medium 平均增加了 900k，xhigh 增加了 1.8M；虽然这些内容的 cache hit rate 非常高，在 initial read 之后达到 99.85%，但 re-read 次数足够多，因此仍占 total cost 的相当一部分）。

另一个 multiplicative cost（这个 multiplier 已包含在前面的数字中）来自 skill 还规定了一组 structured operations，导致更多工作被完成。这些工作并没有 increase correctness，因此只是 increased cost，而没有相应的收益。

需要注意的一点是，这个 skill 在 160 个 cases 中“只”被使用了 157 次。正如使用 LLMs 时通常会发生的，actions 和 results 是 random。如果你有一个可用的 skill，并认为 agent 应该将它用于某个 task，它可能会使用，也可能不会，取决于一些对 AI labs 之外的人来说似乎不透明的因素。

### ToB skill（ToB 技能）

这里，160 次 runs 中只有 108 次实际打开并阅读了[这个 skill](https://github.com/trailofbits/skills/blob/d3323cefbcf645678b8dc481de204b02ad3d02dc/plugins/property-based-testing/skills/property-based-testing/SKILL.md)。这个 skill 建议在 Rust 中使用 proptest，但它又提出，add a dependency 需要批准，而这些都是 single-turn autonomous runs，所以这件事并没有做。

与此前看到的其他 property test cases 一样，property testing 很 rudimentary，而且并没有以有帮助的方式进行。

### Rstest（测试库）

Rstest 是一个 [fixture-based](https://en.wikipedia.org/wiki/Test_fixture#Software) test library。

Agents 实际上并没有使用 rstest。它们 technically 确实使用了，但基本上只是在 rstest 里面 wrote standard unit tests，没有按预期使用 rstest，使 rstest 失去了意义。虽然在某个 high level 上，对于此前看到的 techniques 也可以说是如此，但 agents 至少还在 superficially 使用其中一些其他 techniques（例如用 Hegel writing 一些 low-value property tests）；而这里，agents 没有使用让 Rstest 成为 Rstest 的东西（对于 property-based testing libraries，类似的 behavior 就是只用它们 wrote non-property-based unit tests）。

### Rust test（Rust 测试）

这里指的是 standard Rust built-in test framework，agents 在 Default condition 下使用它，在其他 conditions 下也非常 heavily relied on 它。

明确要求 agents 使用 built-in test framework，带来了更多 tests（medium 上是通常数量的两倍，xhigh 上多了 25%），但这并没有带来更好的 correctness。当 agents 出错时，往往是因为它们没有 test significant behavior，或者 implemented incorrect test behavior。Adding 更多 tests 并没有实质性地 increase risky behaviors 的 coverage，也没有 reduce 那些带有 encoded incorrect behavior 的 tests 的 runs 所占的 fraction。

Yossi Kreinin 补充道：

> 我认为，fixed input/output 这种 testing 方式会同样助长 machines 和 humans 的这种做法。如果你 generate inputs，那么就需要有 code 来将 output 分为 correct 或 incorrect；虽然这个 code 本身可能是 buggy，但比起 running code 后就假定其 output 是正确答案，它至少更容易促使你思考 correct 意味着什么，以及如何判断某个东西是否 correct。使用 fixed outputs 时，你很可能只是 encode code 的 output，然后说服自己它是合理的

### Creusot（形式化验证工具）

Creusot 与 Verus 处在相同的领域。

正如我们在其他 formal conditions 下看到的，Creusot 并没有被 effectively 使用。

### Mutation testing（变异测试）

[Mutation testing](https://en.wikipedia.org/wiki/Mutation_testing) 涉及 modifying code，以确定 tests 有多 effective，然后 adding tests 来获得良好的 coverage。虽然 mutation testing 是一个 standard programming term，但 agents 通常并没有真正做 mutation testing，而是做 normal testing，外加少量并不真正属于 mutation testing 的 mutating 操作；这类似于 TDD instruction 改变了 behavior，却没有让 agents 做 TDD。

有几个 cases 确实发生了 mutation testing，但量很少，而且这样的情况很罕见。

### Judgement（判断）

这个 condition 要求 agents 根据自己的 judgement，酌情 adaptively use testing methods。鉴于我们到目前为止看到的情况，毫不意外，agents 大多使用了 standard Rust unit tests。少数 agents 做了一些 limited fuzzing。Agents 可以使用其他 test 和 formal libraries，但没有使用它们。

### Fuzzing（模糊测试）

Fuzzing 涉及以某种方式 randomizing test inputs。

Agents 非常依赖于送入 random bytes，而这大多导致走过相同的 code paths（invalid input）。Agents 也尝试送入 valid inputs 的 random variations，而这大多也只是 repeatedly exercised input rejection paths。

在 agents 偶尔 generated random structured inputs 时（160 个 cases 中有 10 个），有一半时候发现了真正的 bugs，其中一些是 non-trivial cases。在 160 个 cases 中有 5 个能稍微 effectively 使用 fuzzing，算不上好，但这已经是我们到目前为止看到的对某种 technique 较为 effective 的使用之一。这似乎也表明，可以通过 training 让 agents 把这件事做得更好，也可以在不改变 training 的情况下，引导它们做得更好。从某种意义上说，它们确实知道该怎么做；只是通常在没有受到推动时，它们并不会真正去做。

### Insta（快照测试库）

Insta 是一个用于 snapshot testing（有时称为 golden testing）的 library，在这种 testing 中，你将 results 与 correct results 的一个“snapshot”或“golden file”进行 compare。一般而言，snapshot 通常是某种 serialized data，例如，它可以是某个 data structure 的 JSON object、CLI output 的 log，等等。

正如你可能预料到的，snapshot testing 几乎没有被使用，agents 大多依赖 traditional tests。Agents 确实使用了 Insta，但往往只是在 Insta 中编写普通的 unit tests。

### SMT（可满足性模理论）

Agents 被要求使用一个 [SMT solver](https://en.wikipedia.org/wiki/Satisfiability_modulo_theories)，并且已经 installed Z3、cvc5 和 Yices。

Agents 大多把 SMT solver 当作一种草稿纸，用于 compute 诸如 FSE state ranges、header arithmetic 等内容。即使 agents modeled 某些东西，它们通常也不会 model 能够避免某个常见 mistake 的正确对象。

例如，有一个 computation 本应是 `byte1 + (byte2 << 8) + 0x7F00`。许多 agents 却 implemented `byte1 + (byte2 << 8) | 0x7F00`。Agents 使用 SMT solvers 来 prove 与这个 computation 有关的 properties，但随后仍然写出了错误的 code，使得使用 SMT 看起来并不比 Default（无指令）更好。

### TLA+（行为建模语言与工具）

TLA+ 是用于 modeling behaviors 的一种 language 和 tool。

现在我们进入了 results 高于 average 的这一组（但仍然差于 Default），不过，如上所述，我不会太认真地看待实际 ordering。虽然这不一定是 significant 的，但 TLA+ 在 medium 上的 score 确实略高于 average，在 xhigh 上则高出更多。

159/160 个 agents 创建了某种 TLA+ model，通常是 Zstd 的 state-machine model。就具体的 coverage 而言，30 个 modeled Huffman/FSE/entropy（这些 areas 经常有 bugs）。与其他 formal cases 一样，TLA+ modeling 发生在流程中相对较晚的阶段（在大量 standard tests 和 implementation 之后）。Agents 有时会发现并 fixed TLA+ model 中的 errors，但我没有发现任何一个 TLA+ issue 导致 Rust code 发生实际 change 的例子。

尽管确实出现了一些看起来像样的 TLA+ modelling，但如果这 improved correctness，其作用也很小，难以观察到。总体而言，进行了更 sophisticated TLA+ modeling 的 runs，并没有更好的 correctness。

### Metamorphic testing（蜕变测试）

在 metamorphic testing 中，我们 check related inputs 是否 produce 具有 expected relationship 的 outputs。例如，对于 sort function，你可以 check：changing unequal inputs 的 order 不会 change outputs 的 order；或者对于 addition，向某个 input adding a value 会向 output adds the value modulo overflow。

正如我们在其他 conditions 中看到的，Metamorphic testing 在 correctness 方面并没有发挥很大作用。一些确实 reasonable 的 properties 得到了 checked（例如，在 frame boundary 处 inserting a skippable frame 不应 change output，legal block repartitioning 不应 change outputs，等等），但这些没有触及 agents 相对经常出错的 areas，因此 checking 这些 properties 并没有帮助。总体而言，agents 似乎很喜欢那个老笑话：

> 一名警察看见一个醉汉在路灯下找东西，便问他丢了什么。他说自己丢了钥匙，于是两人一起在路灯下寻找。几分钟后，警察问他是否确定是在这里丢的，醉汉回答说不是，是在公园里丢的。警察问他为什么在这里找，醉汉回答：“这里有光。”

奇怪的是，在 xhigh 上使用 metamorphic testing 的情况比 medium 上更少。

### ECC（技能集合）

[ECC Rust test skill](https://github.com/affaan-m/ECC/blob/e04ea0b9cc8248686edf5ac751cadff550e162b8/skills/rust-testing/SKILL.md) 表现尚可，但主要是因为这个 skill 的大部分内容都被忽略了。Agents 通常会打开并阅读这个 skill（153/160 个读过它），这似乎使它们 generate 更多 tests。不仅 agents 在这个 condition 下 generated 更多 tests，而且如果我们考察 agents 何时阅读 skill（较早、较晚，还是从未阅读），会发现 added tests 的数量呈现出一个 exposure-based gradient。

尽管 ECC 的 score 几乎与 Default 一样好，但根据 agents 在更多接触这个 skill 时的表现，我猜这属于 random 情况。Agent 越早查看 skill，其 behavior 受到的影响就越大，correctness result 也越差。

从 raw score 来看，ECC 似乎表现尚可，因为没有阅读 skill 的 7 个 agents 表现异常出色，得到了 100% correct result，而较晚查看 ECC、几乎没有受到影响的另外 9 个 agents 也表现很好，达到了 100% correctness。这也解释了 ECC 的一个不寻常 result：medium 的 score 与 xhigh 相同（在这些 agents 没有真正查看 skill 的 runs 中，除一个之外，其余都发生在 medium 上）。诚然，skill 何时被 invoked、是否被 invoked，可能存在某种 bias，但整体 pattern 表明 ECC 并不 effective，除非你认为 ECC 是一种能改善 results 的幸运符，只不过只有在这个 skill 没有真正被使用时才有效，而这种情况更容易发生在较低的 effort levels 上。

当然，agents 不应受到它们没有查看过的 skill 的影响，我们应当根据 skill 被使用的 cases 来 score。如果我们考察 skill 实际影响了 agents 的 cases，ECC 的 scores 低于 average（介于 Rust built-in framework 和 Creusot 之间），其 failure mode 与 Rust built-in framework 非常相似：存在大量 small 且没有 meaningful 内容的 tests。这个 skill 告诉 agents 使用 red-green TDD。Agent behavior 可能不是 TDD practitioner 所谓的 TDD，但 agents 确实会在 implementing functionality 之前编写一个 small test，从而产生大量 tests。如上所述，这不是 agents 进行 develop 的 effective 方式，因此 result 比没有 instruction、没有 skill 时更差。

顺便说一句，[正如我们试用 Caveman mode 时提到的](https://danluu.com/ai-coding/#caveman-mode)，这里有相当大的 variance，人们经常因为少数几次小规模 runs 而误以为某个 skill 有用。这一次，我们对一个 skill 尝试了 160 次 runs，数量已经相当大，超过任何理性的人会做的次数。然而，从表面上看，如果我们只看 score，ECC 似乎还不错。

我们需要多得多的 runs，才能 average out 使用 LLM 时固有的 noise。我们可以像这里一样，[检查 results，稍微动用一下我们人类的脑子](https://danluu.com/brain-off/)，但在人们讨论公开的 LLM benchmarks 时，无论是关于 skills 还是其他东西，我都很少看到有人这么做（我确实尝试过让 LLMs analyze results，但和往常一样，即使用了当前公开的 SOTA models，analysis 依然很差，而且充满了基本的 reasoning errors）。相反，我大多看到人们四处传播 top-line number，即便它由于一些无聊的 statistical 原因而没有 meaningful 意义，或者更糟，[benchmark 存在致命缺陷，就像我们在 Senior SWE-Bench 中看到的那样](https://danluu.com/exercise-7/)。

### Default（默认条件）

Default 没有给 agent 任何 test 或 verification instructions。

根据我们目前看到的情况，Default 的 scored above average 并不令人意外。当被要求使用特定 libraries 或特定 test techniques 时，Agents 通常做了一些没有用的事。不告诉 agents 去做那些会让它们做无用功的事，比告诉它们去做这些事表现更好，这是合乎道理的。

### Audit（审查）

Audit 要求 agents 在 implementation 之后 audit code。152/160 个 agents 确实这样做了，151 个 agents 声称发现了 issue，并随后因为 audit 而做了 change。Agents 通常选择了合理的 areas 来 audit，但通常没有使用 fresh context 进行 independent audit（我经常会要求 agents 这样做），而且往往只是在 audit 中再次犯下它们之前已经犯过的同一个 mistake。

42 个使用了 independent agent，但这些 runs 实际上 scored worse（这可能不是 causal，agents 可能是因为处于更糟糕或更困难的局面，才决定另行启动 independent audit）。Audit 最终在 xhigh 上取得了最好的 correctness，但在 medium 上的 correctness 却 below average，而且所有这些 auditing 都大幅增加了 cost，尤其是在 xhigh 上。On average，Audit 的表现与 Default 大致相当，尚不清楚它是否真的在 xhigh 上更好、在 medium 上更差。这是有可能的，但我认为我们没有足够的 evidence 来判断。

Em Chu 有如下评论：

> 这里的 results 与我的经验是一致的。目前我的大多数 tokens 都花在 Auditing code 上，因为我觉得这很有用。不过，我总会给出这两条 instructions：
> 
> -   不要 spawn subagents；自己 read 并 understand code/diff
> -   不要 execute 任何 code
> 
> 因为我发现，如果让 LLM 做这两件事中的任何一件，它都会明显变笨（当然，我并没有 measured……）。它 by default 真的不会 read code 或对 code 进行 reason，即便我做的 change 从来都没有大到会 exceed 它的 context window。
> 
> 我通常还会加上一些废话，比如“要 adversarial”“考虑 features 的 all possible combinations”“考虑整个 input space”，但我更不确定这些到底有没有帮助。

试试这个会很有意思，但正如我在最近的文章中提到的，我正尝试在文章里少讲一些细节，所以这也许会成为另一篇文章的话题。

### Audit 并 fuzz risky areas

对于 Zstd，当这条 instruction 被遵循时，它会让 agents 高度关注 [FSE](https://github.com/cyan4973/finitestateentropy)、[Huffman](https://en.wikipedia.org/wiki/Huffman_coding)、bit readers 和 state。总体而言，这些都是 agents 经常漏掉 issues 的 areas，所以 agents 认为这些 areas 是 risky，这个判断是正确的。作为 fuzzing 目标的这些 areas，比单纯的 Fuzzing condition 所选的更好。

在 medium effort 下，agents 大多忽略了这条 instruction，没有去做，但在 xhigh 下，它们确实遵循了 instructions。虽然这个 condition 的表现并不差，但它似乎也没有比不给 instructions 更好。

观察 agents 实际做了什么时，一个 issue 是，agents 往往只是 generated 一堆 random inputs，这些 inputs 通常是 invalid，也不会 test 任何 interesting condition。

当 human tester generates randomized tests 时，通常会尝试有针对性地进行 randomization，以 generates “interesting” inputs，而 agents 没能做到这一点。Agents 对 outputs 的 check 也不太有效，在许多情况下，只寻找 crashes。Fuzzing 经常被认为只检查 crashes，而不检查 properties，所以这也许并不太令人意外，但如果一个人是在 testing Zstd implementation，这大概不是他想要的。

### Make no mistakes（不要犯错）

虽然严格说来，这个 condition 的 scored higher than Default，但 behavior 似乎没有有意义的差异，而且 scores 非常接近；我猜这是 random variation 造成的。在我观察 results 的每一个 level 上，它们都与 Default 的 random draws 无法区分。

### Kani（工具名称）

Kani 是一个 Rust [model checking](https://en.wikipedia.org/wiki/Model_checking) library。

就“确实在将会 execute 的 code 上使用 formal method”而言，Kani 有最好的 coverage，因为 Kani 确实被用在了 Zstd code 上。不过，这只是偶尔发生，大多数 use 都是 superficial。

有一个 case，真正的 Kani use caught 一个 non-trivial bug，促使 Rust code 发生了 change。160 次中只有 1 次并不惊人，但它确实表明，agents 有时能误打误撞地合理使用 Kani（我猜这意味着，如果在 RL env 中使用它，models 可以学会如何更有效地使用 Kani）。

Kani 的 cost 明显高于其他 conditions。这似乎是因为反复读取 Kani output 很昂贵，从而导致很高的 input token cost。

### ACL2（工具名称）

ACL2 是一个 theorem prover。这里的 result 有一点需要注意：在许多 cases 中，ACL2 OOM'd（192 GiB limit）。OOM results 没有被 counted，这以某种不透明的方式使 results 产生了 biases。

虽然 ACL2 的 scored higher than Default，但如果这是 causal 且 significant 的，我会觉得意外。正如我们在几乎所有其他 formal methods 中看到的，ACL2 大多被用来 prove 一些不会显著影响 correctness 的东西，所以尚不清楚这为什么会 improve correctness。

在有许多不同 conditions 的情况下，除非其他 conditions 的 performance 已经 severely degraded，否则我们不会预期 Default 或看起来 equivalent 的 Make no mistakes 会排在最前面。

### Proptest（库名称）

Proptest 是一个 property-based testing library。

正如我们在其他 randomized testing 中看到的，大多数 tests 都不太 interesting，而过度依赖 randomness 导致了 poor coverage。

尽管 property-based testing 的使用总体上很差，proptest 的 shrinking（finding 一个会 causes test failure 的 simpler input）有时确实提供了一些 value，这比我们在其他大多数 cases 中看到的几乎没有 value 要好。

### Property-based testing（基于属性的测试）

与其他 technique-based approaches 一样，agents 有一个装好了所有 options 的 container。每个 agent 都选择使用 proptest，所以这实际上变成了第 2 个 proptest condition。

与 proptest condition 一样，tests 大多不太好，但它们有时确实 find bugs，shrinking 似乎也带来了一些收获。

我觉得稍微有点意思的是，这个第二个“意外产生的”proptest arm 也和 proptest 一样，scored well above average。

### Skill（技能）

这里，Skill 指的是我为了 test 使用一个 simple skill 的效果而写的 skill（而不是我让一个 agent 寻找相关 testing skills 时找到的那些 large/complex skills）。

也许我应该使用 skills，但我通常不这样做，而是依靠 prompting，看看发生了什么，然后再做更多 prompting。因此，我对于怎样才算一个好的 skill 没有什么直觉，因为我没有这方面的实践，不过 Max Bittker 建议说，用一个尝试 encode 我脑中有关 testing 的一些信息的 test skill，看看结果会很有意思。看到结果后，他的反应是“我早就告诉过你了”。

我没有为此写下 pre-registered guess，不过我心里的猜测是，这不会有很好的效果。[从我在 2015 年尝试向人们传达这些内容的经历来看](https://danluu.com/testing/)——我会说那次尝试基本上失败了——我不觉得自己擅长用文字明确说明一个人应该怎样 test。我曾坐下来向人们演示该怎么做，这通常让他们从此彻底改变了做法，并让他们成为 [way above average](https://danluu.com/p95-skill/) 的 bug finders，但[通过演示向别人传达某件事，与通过写下操作方法来传达它，是不同的（而且更容易的）技能](https://danluu.com/hardware-unforgiving/)。

这次的 skill 是：

-   在 implementing 之前，思考可能存在 subtle bugs 的 areas；对于每一个，说明可能的 mistakes 和合理的 alternative interpretations，然后想出一个 results 会 differ 的 check（优先选择 boundary 两侧的 asymmetric / boundary examples）
-   在 implementing 之后，对于 high risk areas，在没有 production code 的 context 的情况下 independently re-derive result，并进行 compare（fresh context，不要 re-use helper functions）
-   在可行时，使用 property-based testing 或 randomized inputs，尝试 explore space，尽量减少在 no-panic 或 no-crash randomization 上花费的精力
-   在 randomizing 时，偏向于会 explore 有意思的 state 和 code paths 的 inputs（不要只是 naively randomize 那些全都会落入相同 error paths 的 inputs）；这可能需要 structured random inputs
-   如果你对细节不确定，就使用 independent reasoning 来 check 什么是 correct（fresh context，不要 re-use helper functions）

它得到了最高的 score，但没有按预期发挥作用。它几乎从未真正做到 fresh context 那件事，所以把这一条放进去没有什么意义，而且我们不知道，这究竟是一种有效的做法，需要 refined 以迫使 agents 更频繁地这样做，还是应该 removed（虽然从技术上说，它有可能恰好以 optimal frequency 发生，但我对此非常怀疑）。

我们在“Audit and fuzz risky”中提到，agents 似乎知道如何 identify risky areas。这里也是如此，但这并不一定意味着 agents 做了正确的事。例如，agents 将 Zstd 中 encoding 与 decoding 时 bitstreams 被 reversed 识别为 risky，但 agents 在 exercised 这一点的 tests 上并没有表现得更好。如果看具体的例子，在 medium run #35 中，一个 agent 将这一点识别为 risky，做了 independent derivations 和一次 audit，但仍然失败了。它有一个相关的 test，但 input 是 palindromic，所以 reversing order 会得到相同的 result，使得一个把这一点弄反了的 failing implementation 也能通过。

另一个问题——如果可以这么称呼的话——是所有 fuzzing / property-based testing 都是“手工”完成的。考虑到 agents 使用 proptest 似乎还可以，而且 proptest 有一些可以借助的有用 machinery，只需 instructing agents 使用 proptest，大概就能轻易 improved 这个 skill。那些旨在 minimize 生成大量无用的“too random” tests 这一 standard failure mode 的 instructions，在方向上起到了作用，更大比例的 agents 生成了多少有些意义的 tests，但这些 tests 仍然不如我预期一个人会写出的 tests（或者一个有主动人工指导的 agent 会写出的 tests）。如果不对此进行 iterating，我不确定什么 generic guidance 会比较好（而不是花几分钟看看 Zstd 的 structure，再给出 Zstd-specific guidance；后一种做法是我在其他问题上用得比较成功的一类方法）。

作为一个有待 iterate 的 skill 的 first draft，我不觉得它很糟糕，但也不觉得它真的已经可以使用了。如果用更多 examples 来尝试它，以确保没有对 RFC-like problems、bit-manipulation-intensive problems 等产生 overfitting，我能想象一个 improved version 会有效；不过，由于我通常不制作 skills，也从未尝试过 iterate 一个 skill，它没能体现我或另一个人在真正 driving 一个 agent 时会做的事。

因为我习惯了 prompting，然后查看 result（不一定是 code，但至少会看 agents 说自己做了什么、某种关于发生了什么的 agentic summary，以及某些 experimental work 的部分实际 results），再据此 re-prompting，所以我不习惯一开始就把信息全部放进去；这与根据收到的信息作出反应是相当不同的问题。从之前的 fuzzing 工作中，我见过 agents 经常陷入的 failure modes，而这个 skill 的目的就是 prevent 那些 failure modes；但即使只是偶尔回来查看一下，也比完全在一开始就处理好更容易，而一开始给出的 instructions 不足以阻止那些 standard failure modes，尽管确实在一定程度上 mitigate 了它们。

如前所述，我没有尝试以一种美观、易读的方式 break down data。我没有这样做，是因为一旦我们看看 agents 实际做了什么，就会发现它们大多相当 ineffective，而我不觉得比较“把 Verus 用得很差的 agents”和“把 QuickCheck 用得很差的 agents”表现如何特别有意思。我觉得稍微有点意思的一点是，当被要求 identify 那些 risky 或容易出现 subtle bugs 的 areas 时，agents 能够做到。

但总体而言，无论建议使用哪种 library 或 technique，agents 都没能用好该 technique。如[之前所讨论的](https://danluu.com/ai-coding/)，只是要求 agents 去“test”，或者反复要求它们做更多 test，会导致 poor testing。事实证明，要求它们使用 test techniques（其中一些是我亲自发现 highly effective 的）也会导致 poor testing。我匆忙写出的那个粗糙 skill 看起来可能会稍微改善情况，但要真正有用，需要投入的不止是我花在上面的 2 分钟。Yossi Kreinin 评论说，software testing 的现状糟糕透顶，因此，如果 agents 可以说是退回到它们的 training 所教的做法，我们就应该预期会得到 poor results，而这正是我们所看到的。

不知为什么，agents 使用 proptest 似乎稍微更好一些，尽管 testing 的水平远低于我的预期：一个水平尚可、读过 proptest manual、并在如何 test 方面得到一些指导的人，应该能做得更好。我很好奇，得到更多指导的 agents 使用 proptest 是否会比使用其他 libraries 更 effective，但这是另一篇文章的话题了，因为我一直在尝试半小时写完一篇文章，而这里已经接近 9000 词，超出了半小时内尝试打出来的合理篇幅。

### 如何让 agents 写出好的 tests？

我的经验是，如果你引导 agents 建立合理的 test 和 triage structure，那么让 agents 在不需要大量监督的情况下 effectively 往里面添加内容，效果还算可以。由于我的背景（偏见），我倾向于依赖的 testing 是某种形式的 randomized testing / fuzzing / property-based testing。

我和 Jamie Brandon 聊过这件事，他在 snapshot testing 上也有同样的发现。他提到，在一个 project 中，当他要求 agents（使用各种 models）进行 snapshot testing 时，它们会说自己正在做，然后实际上却根本不做（它们会写一个 unit test，然后说自己写了一个 snapshot test）。在另一个 project 中，他成功让它们写出了带有 mocked IO 的合理的 end-to-end tests，但这是在把 tests 移到一个单独的 crate，并在 AGENTS.md 中加入 instructions，要求把 tests 保留在这个 crate 中、不要 modify public interface 之后才做到的。

至少到目前为止，我比 Jamie 更依赖让 agents 编写 test code（我通常会在 CLI 中打字与 agents 交流；至少目前，他比我更喜欢手写 code），但只要建立了某种合理的 structure，具体怎么做似乎并不重要。

[与我们之前看过的这个 problem 类似](https://danluu.com/ai-coding/)，似乎只要做得稍微合理一点，就会有效。如果你像我们在 Zstd 或 IMAP evals 中那样，与一个 agent “交谈”，给它一些简单的 instructions，它就会把工作做得很差。但如果你看看它做了什么，再多打几句话，往往就能很快让它做得不错（至少我在其他 problems 上的经验是这样）。我从未尝试理解 models 为什么能起作用；对于为什么似乎只要做得稍微合理一点通常就有效，我凭空想出的、很可能完全错误的猜测是：在 model 内部的某个地方，存在某种关于如何做这些事情的理解。这不是 default，甚至离 default 还远到仅仅说出要使用什么 technique 都不起作用，但如果 model 得到了充分的 primed，关于如何做这些事情的知识就确实会被付诸实践。

我很好奇，这能否被 effectively 封装成 skills，或者 AI labs 是否会开始 training models，让它们更擅长 testing 或 formal methods；又或者，它们正在做的那些并不直接改进这些能力的事情，是否仍会间接带来足够的改进，使 agents 无需太多监督或 structure 就能写出像样的 tests。

### Prediction accuracy（预测准确性）

-   TDD 会 underperforms（55% confidence）
    -   True（正确）
-   Formal methods 不会 outperform（52% confidence）
    -   True，但不是因为我预期的原因。Agents 完全没能 effectively 使用它们，所以当然不可能 outperform
-   Make no mistakes 不会 outperform 不给 instructions 的情况（95% confidence）
    -   True；它 outperformed 大多数 conditions，因为 no-op 比让 agents 去做 ineffective 的事情更好
-   ECC skill 不会 outperform
    -   True；我觉得，如果我更多地使用 skills，就会对此有更高的 confidence，因为大部分 skill text 看起来都不会起什么作用，而那些看起来会起作用的 text 又显得适得其反
-   Hegel skill 不会 outperform
    -   True；这也是一个如果我更多地使用 skills 就会有更高 confidence 的例子，因为它确实因我猜测的原因而效果不佳；只是我当时对自己的这个感觉没有什么 confidence
-   ToB skill 不会 outperform
    -   True（正确）

以下是我没有登记的猜测，但看到结果时我感到惊讶，因此可以判断自己曾隐约持有这些猜测：

-   Lean 在 formal methods 中会表现得相对较好
    -   False（错误）
-   我的 skill 会表现平庸甚至很差
    -   False，尽管 Max Bittker 正确猜到了会发生什么，提前告诉了我，还指出了一个与实际情况一致的原因；当别人指出某件事将会发生的原因，而你不相信，最后它却恰恰因为对方指出的原因发生了，这种感觉实在挺傻的

### Skills（技能）

我曾不时觉得自己的 workflow 很差、过时、ineffective，因为我听说别人在做某些事情，而我一直懒得尝试。对于 skills，我有这种感觉已经有一阵子了，因为我其实不怎么使用 skills。我反而保留了一个很大的 scratchpad，里面有些内容我偶尔会 copy+paste 进去当作 prompts；这感觉有点像通过 commenting out blocks of code 来保存它们，而不是使用 version control。

但后来，[我看了 Thorsten Ball 的这场演讲](https://thorstenball.com/talks/how-i-prompt/)，他在其中提到自己并不十分依赖 skills；我也与几位看起来很擅长使用 LLMs、却同样不怎么使用 skills 的人聊过，这让我开始怀疑，自己是不是其实并没有错过多少东西。

然后我做了这个 experiment。当时我的感觉是，我看过的那些 skills 不会有帮助，而且很可能反而会有害；由于我对 skills 一无所知，所以 confidence 很低。这些 skills 的表现基本符合我的预期，所以看来，仅仅通过观察 agents 如何回应各种事情、再做一堆小 experiments 而形成的直觉，用在 skills 上也还算站得住脚。我还看了其他一些据说能改善 testing 的 skills，没有把它们纳入这个 experiment；它们看起来也会有与我们 tested 的 skills 相同的 failure modes。

我还针对其他一些由公司提供、用于支持其 product 的“官方”skills 做了两个 experiments（这里不讨论细节，也许改天会再写一篇 10k 词的文章）。其中一个来自一家大型 AI lab，另一个来自一家估值几十亿美元的“小”公司，但在这两种情况下，skills 都让结果变得更差，就像我们在这里看到的一样。有趣的是，在这些 experiments 之后，我反而比以前更看好个人使用的 skills，因为这些 failure modes 似乎是 predictable 的，因此无需大量代价高昂的 experimentation 就能修复。要创建一个公开发布、真正优秀、能在不同 models 和 harnesses 等环境中都有良好表现的 skill，似乎可能很难（claude 和 codex 似乎“想要”不同风格的 prompting，所以 skills 当然也应如此）；但如果只是为了个人使用，解决那些导致许多 skills 比不用 skill 还差的问题，似乎完全做得到？

### 关于 skill writing 的一些粗浅想法

我对 skills 的了解还不足以说该如何写出好的 skill，但我们在这篇文章里看过的所有 skills（除了我花一两分钟写的那个），以及另外两个 experiments 中的 skills，似乎都写得像给人看的 tutorial instructions，也就是说，skill 的目标似乎是解释该如何做某件事。作为一个总共只写过一个 skill 的人，我的粗浅想法是：在与一个应该已经对这个主题有所了解的 model 合作时，我猜这并不是 optimal 的做法（这里和另外几个 experiments 都是这种情况）。model 本来就会有某种 default behavior distribution，所以我觉得更自然的做法是给出能 modify 那种 behavior 的陈述，而不是写出一套让人或不了解相关知识的 agent 从零开始就能做出这种 behavior 的 instructions。

一个明显的问题是，不同的 harnesses、models 和 effort levels 会产生不同的 default behaviors，但往 prompt 或 skill 里塞进一大堆文字，并不会真正改变这一点；那只是用更长的方式让 agent 偏离它的 default，其中很多文字还可能造成某种无意的推动。正如我们在这里看到的，大量文字直接被忽略了（当然，哪些内容在什么时候被忽略，取决于 harness、model 和 effort）。例如，对于 ECC skill，即使它被读过，其中大多数 instructions 也被忽略了；而且，尽管 TDD instructions 确实产生了影响（让 results 变得更差），但即使要求进行 TDD 的 instructions 写得很清楚，它们仍然没有真正被遵循。

由于哪种 prompting 是 effective 的，在不同 model releases 和 effort levels 之间会发生相当大的变化，对于像“把 testing code 做好”这样的一般性事情，我并不清楚这些 skills 要如何在这么多 models 和 efforts 上发挥作用。仅仅从 GPT-5.5 换到 GPT-5.6，就大幅改变了我的工作方式，因为不少在 GPT-5.5 上相当可靠的做法，要么不再奏效，要么变得远不如以前可靠（尽管整体而言，capability 水平似乎更高了）。就像我不会用当初 prompted GPT-5.5 的方式来 prompt GPT-5.6 一样，我想我也不会想用相同的 skills。

我不确定除了 AI lab 里的人以外，还有谁真的会费心对 skills 运行 evals，看看对于每种 model 和 effort level，什么才是 effective 的，然后创建一组按 model 和 effort 加以区分的 skills；而且，我也不指望 AI labs 会有针对竞争对手的 harnesses 和 models 进行 optimized 的 skills。因此，对于 generic 的“testing”skills 这类东西，我也说不准（如上所述，我看过但没有在这里 test 的不少 testing skills，看起来会有与我们 tested 的现有 skills 完全相同的 failure modes），但我可以想象，自己会有几个适用于自身 use cases 的 skills，配合我通常选用的特定 harness/model/efforts。

单就 testing 而言，虽然某些 models 在某些 effort levels 下会掉进一些特定的陷阱，而我想引导它们避开，但我其实并没有一套想交给 agents 的 generic test workflow，可以独立于被 tested 的东西、我希望它达到的 quality 水平，以及我希望它在哪些 dimensions 上具备 quality。因此，我想我不会需要一个 generic test skill，列出一组通常应该让 agents 执行的 testing steps。我做的许多 task 也有类似情况：我希望它们以 task-specific 的方式完成，而不是以 generic 的方式完成。我能想象某种 skill 会先向我提问，再向 agents 输出正确的 instructions，但考虑到 models 改进得如此之快，如果只是做给自己用，我不觉得花时间不断 tweaking 这样的 skill，直到它有用为止，有什么意义。如果我在开发一个 agentic product，并且希望有更多人使用它，那可能就是另一回事了；但我试过的 skills 都有与我们在这里 tested 的 skills 相同的 failure modes，所以，做出一个最终并不那么 effective 的 skill，似乎相当容易。

我能想象 skills 对某些事情普遍有用，比如教 agents 如何 execute workflows，或如何与 APIs/interfaces 进行 interact，例如 [Sawyer Hood 那个帮助 agents drive a web browser 的 skill](https://github.com/SawyerHood/dev-browser)。由于我还没试过那个 skill，我并不是在为它背书，但通读之后，它看起来属于那种能很好地发挥作用的东西，在我试图让 agent drive a web browser 时，能帮我省掉很多麻烦。不过，如果你去读实际的 skill（以及 scripts），会发现它的风格与我们在这里试过的 testing skills 很不一样。

### 附录：agent 的蠢事

我让一个 agent 为一项 analysis 做个简单的 lookup，结果它 exec'd 了一个 perl process，跑了 2 小时 20 分钟，直到我把它 killed 才停下来（我真的需要有个东西能 automatically catches 这种情况，因为这相当常见）。

一个 subagent 用 perl 对一个相对较小的 file（44kB，1364 lines）做 regex search，但这个 expression 在 PCRE 下是 degenerate 的，导致了 combinatorially large 的工作量。我试着用[我们在这里尝试花几分钟 building 的 FRE regex engine](https://danluu.com/benchpocalypse/) 来 re-running，结果它在 0.7s 内完成了 matching（Rust regex 是 0.6s）。

agents 自己去做事时，你永远不知道会发生什么，但至少有些办法本可以防止这件事。首先，这个 agent 本可以避免 invoking 会产生这种 combinatorial explosion 的 regex engine；看起来没有什么充分理由不为此使用更 safer 的 regex engine（例如采用 default settings 的 ripgrep）。其次，这个 agent 本可以 issued 它原本想 emit 的 regex；它实际 emit 的 regex 会 returns 一个大得毫无用处的 capture，而且即使 succeeds，也不会做到预期的事。第三，subagent（或 harness）可以在 subagent 完成后 automatically kill 这种东西。当然，并不是 subagent runs 的所有东西都应该这样处理，但 agents 经常留下这种 runaway processes 不管（在这个例子中，launch 这个 process 的 subagent 似乎在 30s 后就停下了，却让这个 process 一直 running，尽管这样的 search 原本是为了 returned 一个供 subagent 使用的 result，而如果 subagent 已经完成，这个 result 也就毫无价值了）。

我其实有一个 process，会到处清理 agents 留下的东西（本身会 leak memory 的 agents、consume space 的 temporary build artifacts 等），但它没有寻找 runaway perl processes。这又是一项需要加上的内容，但遇到这个问题的肯定不止我一个人。我想，我可以把自己处理这件事的那个傻乎乎的 tool 给 open source，但等主要的 harnesses fix 了这个问题，它就应该过时了；所以，即使我把它 open source，似乎也没有什么充分理由让任何人一开始就来用我的东西，因为 AI labs 大概不用太久就会 fix 这类问题。

## 原文

[We previously noted that, while it's easier than ever to hit a particular quality bar by having coding agents use effective test techniques, software quality seems to be getting worse](https://danluu.com/ai-coding/), indicating that whatever defaults developers are using may not work very well. Here, we test if simple instructions to agents to use particular techniques or libraries improve implementation correctness, as a kind of test to see how effective agents are when guided by someone with no expertise in testing who's maybe heard that you should apply certain techniques or use certain libraries.

We'll re-use [the Zstd implementation eval discussed in this comparison of agentic programming language effectiveness](https://danluu.com/pl-tokens/) and, instead, compare different testing techniques and testing libraries when agents are given a prompt to implement Zstd with different addendums, such as "Use test-driven development", "Use Lean 4", "Use QuickCheck", "Use property-based testing", etc. I also ran some other evals, such as on the IMAP RFC, which are briefly discussed.

All implementations were in Rust. The 26 prompt conditions tested were ACL2, Alloy, "Audit and fuzz risky areas", "Audit first", Creusot, Default (no additional instructions), Differential testing, Fuzzing, Hegel, Insta, Judgement (agents asked to use the best technique), Kani, Lean 4, "Make no mistakes", Metamorphic testing, Mutation testing, Property-based testing, Proptest, QuickCheck, rstest, Rust built-in test framework, SMT solvers (with Z3, cvc5, and Yices, all available), Spin, TDD, TLA+, and Verus. Additional, 4 skills were tested: Hegel with [the official Hegel skill](https://github.com/hegeldev/hegel-skill/blob/ef36dc6b26a6dc0fdfdab5476b1affff37552ef0/skills/hegel/SKILL.md), the [ECC Rust test skill](https://github.com/affaan-m/ECC/blob/e04ea0b9cc8248686edf5ac751cadff550e162b8/skills/rust-testing/) (ECC is a collection of skills with 250k GitHub stars and 38k forks), the [Trail of Bits property test skill](https://github.com/trailofbits/skills/blob/d3323cefbcf645678b8dc481de204b02ad3d02dc/plugins/property-based-testing/skills/property-based-testing/SKILL.md), and a test skill I wrote (I'm a luddite who uses prompts instead of skills and have no feel for how to write a good skill). Other than my skill, the skills were chosen because those were the top skills codex turned up when asked to find relevant skills.

### Predictions

I pre-registered some guesses on how conditions will do:

-   TDD will underperform (55% confidence)
    -   I actually added TDD specifically because I thought it would underperform
    -   My confidence is low here because I don't know what agents will do when instructed to do TDD; perhaps agents won't do TDD and will do something that doesn't underperform (or perhaps I'm wrong about TDD underperformance)
-   Formal methods will not overperform (52% confidence)
    -   My thought here is that while formal methods are effective and useful (more so now than ever), good test methods are also effective and useful and, on simple problems, formal methods shouldn't outperform if used at a similar level of competence
    -   As with the above, but even more so, my confidence is low here because I don't know what agents will do when instructed to do anything, and formal methods have been more hyped than effective test techniques for agentic coding, so it's entirely plausible that labs have trained agents with RL environments with synthetic data which trains them to be very effective with formal methods without having trained agents to be effective with good test techniques (which I would expect to be easier to do, but not done because of how relatively untrendy effective test techniques are)
-   Make no mistakes will not outperform no instructions (95% confidence)
    -   It's a joke, and one that a lot of people have tried. If it worked, surely people would've noticed?
-   The ECC test skill (with 250k stars and 38k forks) will not outperform (65% confidence)
    -   It's somewhat big and doesn't have any information I'd expect to be useful. It instructs agents to use TDD; to the extent that it gets agents to use TDD, I'd expect this to make things worse (and it's more directive than the TDD condition and perhaps more likely to succeed, although for all I know that makes it less likely to succeed); the rest of the information doesn't seem useful and has some cost
    -   All of my skill predictions are low confidence because I don't tend to use skills and don't know how to really evaluate them. I'm thinking of this like, "how effective would it be if I passed the text in as a prompt and had this thing floating around in the LLM's context window?"
-   Hegel's skill will not outperform (65% confidence)
    -   It's very big (the SKILL.md plus the linked Rust reference are over 20k tokens) and reads more like a tutorial than agent instructions
-   The Trail of Bits test skill will not outperform (55% confidence)
    -   It has what looks like it might be useful information, but it's also fairly big

### Overall results

Below, we have a very messy graph which shows the results for the conditions tested (codex with GPT-5.6 Sol, with medium and xhigh efforts). When looking at data, I tend to prefer much denser and messier graphs than most people, [such as the first graph here](https://danluu.com/android-updates/). Because most people find these kinds of graphs unreadably messy, I tend to split information out into a series of graphs, each of which shows less information, when presenting information to others. For reasons discussed elow, I'm not going to do this here and am just going to present this extremely messy graph where we have cost on the x axis and the fraction of runs that passed 100% of the (hidden) tests on the y axis, average of 80 runs from each condition and effort (mousing over items shows bootstrap covariance, [50% uncertainty](https://statmodeling.stat.columbia.edu/2016/11/05/why-i-prefer-50-to-95-intervals/), and there's some attempt at making like things similar colors, e.g., blue-ish for formal methods, green-ish for property-based testing, etc.):

One thing we can see is that nothing really wildly outperforms. However, Default (no additional instructions) does well above average. Looking at xhigh, on average, the fuzzing and PBT-related conditions did a little better than formal methods on average, with the situation being a lot more mixed at medium. The testing-related skills codex recommended we try underperformed, although our quick custom skill did ok (a major difference is that our skill is designed to nudge away from their default behavior towards more productive behaviors whereas the other skills seem more like tutorials). TDD didn't do well, as predicted (one skill also suggested that agents used TDD, and that skill also fared poorly in the cases where agents attempted to follow the instruction).

If we actually look at what agents did, it quickly becomes apparent that, in general, agents don't know how to use these tools or techniques very well. [As we noted here](https://danluu.com/ai-coding/), and as everybody I've talked to has also noted, agents are really bad at testing and don't seem to understand how to test reasonably "by default". For example, [here's a comment by Gary Bernhardt](https://x.com/garybernhardt/status/2067002665427775613):

> AI agents' approach to testing, more or less:
> 
> 1.  Take the pathological cases dreamed up by someone objecting to mocks 15 years ago, without ever having actually used mocks. Naive dreams of excessive mocking.
>     
> 2.  Make those pathologies the backbone of your testing strategy.
>     

It turns out, if you ask agents to use a particular test technique or test library, this approach doesn't change as much as you'd hope. We'll look at what happened in cases in more detail, but at a high level, with test techniques, agents tend to either just write the tests they would normally write, but inside a framework for a different type of test technique, or they'll use a technique superficially but not really do the things that get the value out of the technique. For the most part, when a technique was named, they did what Gary described, but with respect to that technique (for example, for formal methods, they mostly proved irrelevant properties and with property-based testing, agents would lean heavily on totally random inputs and heavily hit invalid/rejection cases or find a trivial property to check and run low-value random cases against the trivial property). Results weren't materially different on the IMAP RFC (where I tried 40 runs of each condition) or other random RFCs (where I tried a few individual runs). In general, regardless of the type of problem, whether it's some kind of bit manipulation problem like Zstd, a protocol like IMAP[1](https://danluu.com/agentic-testing/#fn:I), or anything else, agents did not use formal methods or test libraries or techniques in an effective way.

On xhigh, agents were generally able to get the tests they wrote to pass, but they wrote poor tests (e.g., they'd submit four identical bitstreams into a test of a feature that uses four bitstreams and miss any bug that would occur because they transposed bitstreams). [And as we noted previously on the Zstd eval with respect to languages](https://danluu.com/pl-tokens/#appendix-medium-in-a-loop-vs-ultra), running at a lower effort level in a naive loop gets worse results (agents do even more of this and stall out with lower correctness).

I'm curious why AI labs haven't created RL envs to get agents to learn how to test well since software not working reasonably seems important for coding agent adoption and it also seems like the kind of thing that's amenable to RL. [As we previously saw, agents have gotten quite good at bounded runtime optimization problems](https://danluu.com/no-slow/), which makes sense because that's exactly the kind of thing you cheaply create a ton of RL envs to train on. Maybe this is one of those things that's harder than it seems when you try it, but creating RL envs for effective testing and test techniques seems like it's in the same class of problem. Perhaps the limiting factor is just that knowledge of [effective test techniques](https://danluu.com/testing/) isn't very widespread, so no one's thought to try it and people are getting agents to test inefficiently (for example, by doing standard unit testing)[2](https://danluu.com/agentic-testing/#fn:U), or maybe this problem is much harder to package up than runtime optimization for some reason? It's possible this will be a moot point soon if agents get so good that they can generally write correct code without testing or verification, but at least for the state of publicly available agents from inception until now (September 2026), it seems like agents having some idea how to test without being guided by a testing expert would've substantially increased agentic coding effectiveness.

Below we'll look at how agents did things for each condition, ordered from worst correctness to best, but I would caution anyone against drawing any kind of strong conclusions from the ordering.

A lot of the failures here seem analogous to the failures we saw when we looked at [the impact of programming language on token usage and correctness](https://danluu.com/pl-tokens/), in that the failures are often idiosyncratic. For example, with programming languages, we saw that agents had a fairly high rate of getting the semantics of byte conversion incorrect in Clojure but not Java, even though agents "should" (and probably sort of do) know that they can get Java byte conversion semantics by converting with `unchecked-byte` instead of `byte`.

Although people have all sorts of hand wave-y high-level explanations for why some languages are better for agents than others, when we look at what agents actually do and what the failure modes are, none of the explanations I've heard for why someone's pet language is suited for agentic coding, whether it's Elixir or Ocaml or J, are actually true (with the exception of comments about Rust's memory safety, [which were validated in the multi-language pandoc eval we tried by comparison memory safety issues between agent-written C, C++, and Rust](https://danluu.com/pl-tokens/#appendix-more-details-on-zstd)). Instead, we see a bunch of idiosyncratic failures that happen for unclear reasons[3](https://danluu.com/agentic-testing/#fn:P). With languages, because we can observe a moderate correlation between language popularity and performance (both lower cost and higher correctness), it seems reasonable to guess that the reason is because there was more training data (possibly synthetic data and not just human-written code) for more popular languages. Here, there isn't a clear pattern, other than that agents are mostly not very effective at applying test or verification techniques when all they have is the name of a library or technique (we'll discuss what works better afterwards). If you don't want to read about what happened in each condition, [click here to skip to the last item](https://danluu.com/agentic-testing/#skill).

### Verus

[Verus](https://github.com/verus-lang/verus) uses an SMT solver and various types of reasoning to prove that the code matches specifications.

Although Verus can prove that code matches specifications, agents didn't do that. Instead, they made proofs about various abstract properties relating to Zstd. I've not used a tool like Verus myself, so I can't speak to what an expert or even a beginner user would normally do, but from reading the tutorial, I find it a bit odd that agents didn't attempt to use Verus to verify any of the actual code and only used it to do abstract reasoning, as it seems designed to make it easy to prove properties about the actual code.

Additionally, if we look at the properties proved, there were generally few properties proved and the properties that were proved were uninteresting. For example, agents would prove things like "given a valid cursor/index/distance, the resulting operation remains in bounds", which isn't bad to prove, but wasn't really a source of bugs. Also, agents would frequently write vacuous proofs that were effectively `A => A`. An actual Verus proof of this form was:

```
  requires                                                                                                                                                                                         
      0 < a <= window,                                                                           
      0 < b <= window,
      0 < c <= window,
  ensures
      0 < c <= window,
      0 < a <= window,
      0 < b <= window,
```

In cases where agents actually proved something, they generally proved something relatively simple and avoided proving properties about the parts that were likely to have a bug (for example, agents often failed to reverse the bitstream order for encode and decode and would write tests that failed to detect this because the tests were palindromic; perhaps some kind of proof of reversal here might get agents to "think" about this in a different way).

It doesn't seem that agents were getting value out of Verus when just provided with Verus and the Verus docs.

If we look at the result, the aggregate xhigh Verus results are fine (slightly lower correctness than average, but much cheaper). The medium results had average cost and the lowest percentage of correct runs as well as the lowest average number of correct tests. Because agents didn't really get value out of Verus, what they actually did for correctness was mostly just traditional tests (built-in Rust `#[test]` functions with unit tests). When going from medium to xhigh, agents spend much more effort on traditional testing and only a bit more effort on using Verus, which allowed the xhigh result to be ok.

Looking at the actual tests, for one of the two features which agents using Verus did much worse on (the [four stream jump table](https://github.com/facebook/zstd/blob/dev/doc/zstd_compression_format.md)), Verus agents wrote a test for this in 89 out of 160 cases, coincidentally the exact same number as Default agents, but Verus agents were much more likely to write bad tests. They were more likely to encode incorrect results in the tests as well as make easy to pass tests that don't cover the space well, such as making all four streams identical. This kind of thing is what I meant when I said that the failures were idiosyncratic. There's nothing about Verus that necessarily makes one write poor tests when not using Verus and we wouldn't, in general, expect a human who's used Verus to write bad unit tests, in the same way that we wouldn't expect a human using Clojure to make more byte conversion mistakes, but this happened here for whatever reason (possibly a coincidence).

I don't know if folks inside AI labs can get access to better information on why things happened, but here on the outside it's generally quite difficult to tell why something like this happened (even when we formed a plausible hypothesis for the language issue, it required running many samples of many languages, and papers we looked at which studied the same thing didn't observe the language popularity / agentic effectiveness correlation because they either looked at too few languages to be able to reason about such a weak correlation or they looked at problems that were too small and too trivial).

### Alloy

Alloy is often called a bounded model checker. This is maybe not quite right with Alloy 6 since that introduces some extra features, but this is way outside of my area of expertise. My understanding is that, with Alloy, you normally prove properties about your model (as opposed to proving that your code works).

Alloy got the 2nd worst correctness score and, unusually, scored generally poorly on both medium and xhigh. Although it isn't shown (because it doesn't seem to add anything), in general, results were highly correlated between max and xhigh, which were quite different from medium results.

As we saw with Verus, agents using Alloy pretty much relied on standard Rust `#[test]` for correctness and mostly faffed about with Alloy. Once again, using a formal tool poorly did not help with correctness.

There were individual cases of Alloy use that were close to finding an issue or risk, but even then, only a small number. In one case, Alloy found a counterexample which then caused the agent to implement the Rust version with a mitigation for the potential bug. Unfortunately, the counterexample relied on an 8-bit overflow that couldn't happen in practice because the actual implementation used 64-bit `usize` with no possibility of overflow given the inputs, so it just made the code more complex without preventing an actual bug.

In another case, the Alloy specification was incorrect and a related test failed. After the test failed, the agent fixed the Alloy specification. Had the specification been correct, perhaps the agent would've written the correct code without the failure. There were some cases where it's possible the good version of this happened, but it's not clear if an actual potential bug was prevented.

Alloy agents did model things that were more closely related to the Zstd algorithm than Verus agents (which mostly checked things like arithmetic), but it was still the wrong modeling.

### Differential testing

Differential testing is a technique where you give the same inputs to multiple implementations and then compare results to find issues. In principle, this seems like a reasonable thing to try with LLMs as we often get different results from different rolls of the dice, and [as we noted here](https://danluu.com/pl-tokens/#appendix-medium-in-a-loop-vs-ultra), having an agent iterate more on an implementation (which might be only part of the entire thing, perhaps even only part of a function) often works worse than having the agent restart from scratch.

But this gave us the third worst results. In this case, we had slightly above average results on xhigh and far below average results on medium. None of the agents created two full implementations to compare. Out of 160 runs, 135 did something you might call differential testing, but like the other conditions we've seen, these were generally trivial and effectively useless. And, in the cases where differential testing might've caught a bug, instead of implementing things in independent ways, agents just did the same thing twice and encoded the same bug in both versions.

I sometimes tell agents to do things independently and get them to launch with separate contexts, but this was not done effectively for differential and agents would generally just write the same thing twice.

### Hegel Skill

It makes sense to discuss how the official Hegel skill changes Hegel behavior, but in reverse correctness order, Hegel Skill appears above Hegel because the result was worse on correctness. See the Hegel section below for discussion of this skill.

### Lean 4

Lean 4 can maybe be described as [an interactive theorem prover](https://en.wikipedia.org/wiki/Proof_assistant).

Although I didn't pre-register a guess about Lean, if I had pre-registered guesses on which formal tools would do well, I would've put Lean on the list of things I'd expect to do well because it's relatively hot/trendy and therefore seems relatively likely to have good performance due to synthetic data from RL envs.

The Lean agents did prove properties, like the Verus condition, agents mostly did arithmetic proofs that didn't hit the bug-prone or risk surface areas.

Like the other formal conditions, Lean agents relied heavily on standard Rust tests. As with the formal conditions so far, doing a few proofs of things that don't matter didn't help with correctness.

### QuickCheck

QuickCheck is [a property-based testing library](https://en.wikipedia.org/wiki/Property_testing), probably the best known such library for a long time, although Hypothesis might currently hold that crown.

Unfortunately, agents were about as effective at using property-based testing as they were at using the formal tools we've seen so far. When using QuickCheck, agents mostly wrote very simple "smoke tests" that didn't check much. They also used random inputs, which, when fully randomized, are pretty poor for testing something like Zstd (because they just go down one of a few failure/rejection code paths).

Also, relatively few properties were checked. Although all agents used QuickCheck, 63 out of the 160 runs only checked a single property. Agents once again mostly relied on traditional testing, although they technically did use QuickCheck. For whatever reason, agents actually wrote more traditional tests than under the Default condition or most other conditions, but did fewer test-fix iterations (which resulted in this condition coming in with below average cost).

### TDD

TDD underperformed here as well as in the IMAP RFC eval.

The TDD prompt seemed to cause large changes to agent behavior. Agents produced twice as many tests, and worked in a much more iterative test-code-test-code-etc. workflow, although a TDD advocate would probably say that agents didn't actually use TDD. There were only a few instances of agents doing some kind of fine-grained iterative TDD.

Overall, agents wrote more tests up front; for example, agents had one or more failing tests in 67 of 160 cases before doing substantial (non-stub) implementation, vs. 0 of 160 for the Default condition.

For broad test classes, TDD had more tests of every kind. There were more small, trivial tests and there were also more integration and end-to-end tests. Any kind of obvious high-level "agents did too much or too little of X" doesn't seem to fit the data. If we look at specific failures and how they were missed by tests, we can observe that the TDD condition had a number of these. For example, Zstd uses something called a jump table when there are four Huffman streams.

TDD agents were more likely to fail the eval test for this although they wrote more tests that cover the general case. For whatever reason, TDD agents were more likely to write tests that don't cover hard cases (e.g., making all four streams identical and then also making them trivial, like we saw with Verus). This is another case where I'd be curious what kind of visibility people at AI labs have since it's not obvious from the outside why priming agents with TDD made them write worse tests and worse implementations.

If we only had TDD and a few test conditions to go on, a hypothesis might be that TDD'd code often seems to have a lot of small tests that aren't very good, so maybe priming agents with TDD causes them to write more of these sorts of ineffective tests. But it's not clear why we should see the same pattern with Verus. Maybe we could tell whether or not this is true for TDD if there's a shared reason for the Verus (or other) behavior by re-running the experiment on an open model and inspecting what's actually going on inside the model at some level?

Two of the skills also caused agents to run in a more iterative approach, perhaps on the theory that executing more frequently would give better results, and both of those skills also underperformed. In general, across all conditions, agents were able to get the tests they wrote to pass on xhigh and max (not shown, but max had slightly better correctness than xhigh at substantially better cost). Getting their own tests to pass more iteratively tended to get agents to write more incorrect tests that would enforce incorrect behavior.

Yossi Kreinin had this thought for why TDD might result in worse tests:

> fwiw, I think if you write the tests before the code, it's harder to test the harder cases since you know less about what is going to be hard, and even if you do random testing which I don't think "tdd" is associated with, you are less likely to steer the distribution in the direction where the bugs are. if you wrote the code or at least can look at it, you know what seems trivially correct and what might or might not work since it's not easy to understand what it does. in other words, tdd steers you towards black box testing which for complicated machinery seems to me to be less effective than white box testing; pretty sure this is how it works with people, less sure about agents

Was my guess that TDD would underperform correct? Strictly on the result, the answer is yes. On my reasoning (not explicitly pre-registered in writing, but I do know what I was thinking), I think it's not clear. My thinking was something like, as we've [recently](https://danluu.com/benchpocalypse/) [discussed](https://danluu.com/ai-coding/) in [a variety of contexts](https://danluu.com/pl-tokens/), getting agents to actually do something like the right thing and not just overfit is a key part of achieving good performance or correctness with agents. Speaking to the methodology in general and not how this instruction changed agent behavior, TDD seems primed to cause overfitting.

Agents did write worse tests and sometimes used a relatively expensive and ineffective iterative workflow, but I don't know that the failure mode I'd expect from a human using TDD and then directing agents to implement was the real problem here, and that problem was where my intuition came from. I would rate the reasoning here as perhaps and perhaps not in the right vicinity; I think more evals and investigation would be necessary to decide this and I would guess that the result of additional data would be that my original reasoning is wrong.

### Spin

Spin is a model checker.

Now we're getting into the range where results weren't far from average. Spin did moderately worse than average on both medium and xhigh, at below average cost. As we saw with the other formal tools, usage of Spin was generally ineffective. In this case specifically, using Spin to model a certain class of behavior had no correlation to passing or failing the hidden tests covering that behavior. Usage of Spin was superficial and not productive.

### Hegel

Hegel is a property-based testing library based on [Hypothesis](https://github.com/hypothesisWorks/hypothesis/).

As we might expect by now, agents didn't use Hegel effectively. To the extent they used it, they used it superficially, and they generally used it after heavily relying on ordinary testing. Since just saying that agents didn't really meaningfully do the thing is repetitive, I'll make these sections short and only highlight particular curiosities.

The actual workflow agents used was generally

1.  Read the RFC and API/contract
2.  Implement Zstd
3.  Run normal tests
4.  Read Hegel docs
5.  Use Hegel to write 1-4 simple property-based tests
6.  Continue using normal built-in Rust tests

As noted above, the Hegel skill didn't improve correctness. Correctness was worse (though it was close enough that this could've been random). What was more striking was that cost was much higher (26% higher on medium and 41% on xhigh), for reasons which seem causal.

The skill caused agents to generate more tests. The additional tests were mostly checks that malformed inputs don't cause a panic and round-trip tests. The former is something that agents were already inclined to do an excessive amount of for all of the property-based and fuzzing conditions, so additional effort there wasn't useful. The latter doesn't seem like an inherently bad idea (I even often explicitly instruct agents to create round-trip tests and they seem to be useful to check specific properties), but it wasn't done in any of the most bug-prone areas. Without additional instruction, agents were inclined to create round-trip tests for relatively trivial properties that were already likely to be correct.

As for the cost, there are multiple reasons for the cost. One is that the skill is fairly large (34k characters for the skill, which also loads a 45k Rust-specific reference, which ends up being more than 20k tokens). This was loaded at the start of the run and was re-read on many subsequent actions. This resulted in an average additional dollar cost of 16% for medium and 18% for xhigh (by raw tokens, the average increase was 900k on medium and 1.8M on xhigh; although the cache hit rate on these was very high, 99.85% after the initial read, they were re-read enough that this was still a substantial fraction of total cost).

A multiplicative cost (this multiplier is included in the previous numbers) is that the skill also specified a structured set of operations that cause a lot more work to get done. This work didn't increase correctness, so this increased cost without a concomitant benefit.

One thing to note is that the skill was "only" used in 157 out of 160 cases. As is generally the case when using LLMs, the actions and results are random. If you have a skill available that you think an agent should use for a particular task, it may or may not use it depending on factors that seem opaque to people outside of AI labs.

### ToB skill

In this case, only 108 out of 160 runs actually opened [the skill](https://github.com/trailofbits/skills/blob/d3323cefbcf645678b8dc481de204b02ad3d02dc/plugins/property-based-testing/skills/property-based-testing/SKILL.md) to read it. The skill suggests using proptest in Rust, but the skill suggests approval is required to add a dependency and these were all single-turn autonomous runs, so this wasn't done.

As with the other property test cases seen so far, property testing was rudimentary and not done in a helpful way.

### Rstest

Rstest is a [fixture-based](https://en.wikipedia.org/wiki/Test_fixture#Software) test library.

Agents effectively didn't use rstest. They technically did use it, but they pretty much just wrote standard unit tests inside rstest and didn't use rstest as intended, defeating the purpose of rstest. While this is arguably true at some high level for techniques seen so far, agents were at least superficially using some of the other techniques (such as writing some low-value property tests with Hegel), but here agents didn't use the thing that makes Rstest Rstest (the analogous behavior for the property-based testing libraries would be if they just wrote non-property-based unit tests with them).

### Rust test

This is referring to the standard Rust built-in test framework that agents used in the Default condition and also very heavily relied on in the other conditions.

Explicitly asking agents to use the built-in test framework resulted in more tests (double normal on medium, 25% more on xhigh), but this didn't result in better correctness. When agents got things wrong, it was often because they didn't test significant behavior or implemented incorrect test behavior. Adding more tests didn't materially increase coverage of risky behaviors or reduce the fraction of runs with tests that encoded incorrect behavior.

Yossi Kreinin added:

> i think the fixed input/output style of testing encourages this in machines and humans alike. if you generate inputs you need to then have code that classifies output as correct or incorrect, and while this code itself might be buggy, it at least makes you think about what correct means and how to tell if something is correct more easily than running the code and assuming its output is the right answer. with fixed outputs you are quite likely to just encode the output of the code and convince yourself that it makes sense

### Creusot

Creusot sits in the same space as Verus.

As we've seen with the other formal conditions, Creusot was not used effectively.

### Mutation testing

[Mutation testing](https://en.wikipedia.org/wiki/Mutation_testing) involves modifying the code to determine how effective tests are and then adding tests to get good coverage. Although mutation testing is a standard programming term, agents generally didn't actually do mutation testing and instead did normal testing with some small amount of mutating things in a way that isn't really mutation testing, similar to how the TDD instruction modified behavior but didn't get agents to do TDD.

There were a few cases where mutation testing occurred, but only a small amount, and that was rare.

### Judgement

This condition asked agents to adaptively use testing methods as appropriate based on their judgement. Given what we've seen so far, unsurprisingly, agents mostly used standard Rust unit tests. A few agents did some limited fuzzing. Agents had access to other test and formal libraries but didn't use them.

### Fuzzing

Fuzzing involves randomizing test inputs in some way.

Agents relied heavily on sending random bytes in, which mostly resulted in going down the same code paths (invalid input). Agents also tried sending in random variations of valid inputs, which mostly also just repeatedly exercised input rejection paths.

On the rare occasion that agents generated random structured inputs (10 out of 160 cases), this found real bugs half the time, some of which were non-trivial cases. Using fuzzing a bit effectively in 5 out of 160 cases isn't exactly good, but this was one of the more effective uses of a technique that we've seen so far. This also seems to indicate that agents could be trained to do this better and also that that can be directed to do this better without changes in training. They do, in some sense, know how to do this; they just don't normally actually do it without being pushed into doing it.

### Insta

Insta is a library for snapshot testing (sometimes called golden testing), where you compare results to a "snapshot" or "golden file" of correct results. Speaking generally, a snapshot is usually some kind of serialized data, e.g., it could be a JSON object of a data structure, a log of CLI output, etc.

As you might expect, snapshot testing was barely used and agents mostly relied on traditional tests. Agents did use Insta, but would often just write normal unit tests in Insta.

### SMT

Agents were instructed to use an [SMT solver](https://en.wikipedia.org/wiki/Satisfiability_modulo_theories), with Z3, cvc5, and Yices installed.

Agents mostly used the SMT solver as a kind of scratchpad to compute things like FSE state ranges, header arithmetic, etc. Even when agents modeled something, they would generally not model the right thing to avoid a common mistake.

For example, there's a computation that should've been `byte1 + (byte2 << 8) + 0x7F00`. Many agents implemented `byte1 + (byte2 << 8) | 0x7F00` instead. Agents used SMT solvers to prove properties relating to this computation, but then still wrote the wrong code, making SMT use seemingly no better than Default (no instructions).

### TLA+

TLA+ is a language and tool for modeling behaviors.

We're into the set of above average results (but still worse than Default) but, as noted above, I wouldn't take the actual ordering too seriously. Though this isn't necessarily significant, TLA+ did score a bit above average on medium and more above average on xhigh.

159/160 agents created some kind of TLA+ model, generally a state-machine model of Zstd. For particular coverage, 30 modeled Huffman/FSE/entropy (areas that often had bugs). As with the other formal cases, TLA+ modeling happened relatively late in the flow (after a lot of standard tests and implementation). Agents sometimes found and fixed errors in the TLA+ model, but I didn't find an instance of a TLA+ issue resulting in an actual change in the Rust code.

Although there was some real looking TLA+ modelling happening, if this improved correctness, it did so in a small way that was difficult to observe. In general, runs that had more sophisticated TLA+ modeling did not have better correctness.

### Metamorphic testing

With metamorphic testing, we check that related inputs produce outputs with the expected relationship. For example, you could check that, for a sort function, changing the order of unequal inputs doesn't change the order of the outputs, or for addition, adding a value to an input adds the value to the output modulo overflow.

As we've seen for the other conditions, Metamorphic testing wasn't done very usefully with respect to correctness. Some actually reasonable properties were checked (e.g., inserting a skippable frame at a frame boundary shouldn't change the output, legal block repartitioning shouldn't change outputs, etc.), but these didn't hit the areas that agents got wrong relatively frequently so checking these properties didn't help. In general, agents seemed to be fans of the old joke:

> A policeman sees a drunk man searching for something under a streetlight and asks what the drunk has lost. He says he lost his keys and they both look under the streetlight together. After a few minutes the policeman asks if he is sure he lost them here, and the drunk replies, no, and that he lost them in the park. The policeman asks why he is searching here, and the drunk replies, "this is where the light is".

Curiously, metamorphic testing was used less on xhigh than on medium.

### ECC

The [ECC Rust test skill](https://github.com/affaan-m/ECC/blob/e04ea0b9cc8248686edf5ac751cadff550e162b8/skills/rust-testing/SKILL.md) did ok, but mostly because large parts of the skill were ignored. Agents generally opened and read the skill (153/160 read it) and this seemed to cause them to generate more tests. Not only did agents generate more tests in this condition, if we look at when agents read the skill (earlier vs. lateer vs. never), there's an exposure-based gradient in how many tests were added.

Although ECC scored almost as well as Default, based on how agents did when more exposed to the skill, I would guess that this is random. The earlier an agent looked at the skill, the more its behavior was impacted and the worse the correctness result.

ECC seemed to do ok in terms of raw score because the 7 agents that didn't read the skill did unusually well and got a 100% correct result, and then the 9 agents that looked at ECC late and were only barely influenced also did well and had 100% correctness. This also explains the unusual ECC result that medium had the same score as xhigh (all but one of these runs where agents didn't really look at the skill happened on medium). While it's true that there may be some kind bias in when the skill gets invoked or not, the overall pattern would indicate that ECC is not effective unless you think ECC acts as a good luck charm that improves results, but only when the skill isn't really used, which is more likely to happen at lower effort levels.

Of course, agents shouldn't be influenced by a skill they didn't look at and we should score this based on the cases where the skill was used. If we look at the cases where the skill actually influenced agents, ECC scores below average (between Rust built-in framework and Creusot), with a very similar failure mode to Rust built-in framework of having a large number of small and not meaningful tests. The skill tells agents to use red-green TDD. The agent behavior probably isn't what a TDD practitioner would call TDD, but agents do write a small test before implementing functionality, which results in a large number of tests. As noted above, this isn't an effective way for agents to develop, so the result is worse than no instruction and no skill.

BTW, [as we noted when we tried out Caveman mode](https://danluu.com/ai-coding/#caveman-mode), there's quite a bit of variance and people are often misled into thinking a skill is useful by a few small runs. In this case, we tried 160 runs of a skill, a fairly large number, more than any reasonable person would do. And yet, superficially, if we just look at the score, ECC seems ok.

We would need a much larger number of runs to average out the noise inherent when using an LLM. We can do what we did here, and [inspect the results and use our human brains a little bit](https://danluu.com/brain-off/), but I rarely see this done when people are talking about public LLM benchmarks, whether it's for skills or anything else (I did try having LLMs analyze the results but, as usual, even with current public SOTA models, the analysis was poor and full of basic reasoning errors). Instead, I mostly see people pass around the top-line number, even when it's not meaningful for boring statistical reasons or, worse yet, [the benchmark is fatally flawed, as we saw with Senior SWE-Bench](https://danluu.com/exercise-7/).

### Default

Default gave the agent no test or verification instructions.

Given what we've seen so far, it's not surprising that Default scored above average. Agents generally did things that were not useful when asked to use particular libraries or use particular test techniques. It stands to reason that not telling agents to do things that will make them do useless work does better than telling them to do things that will make them do useless work.

### Audit

Audit asked agents to audit the code after implementation. 152/160 agents actually did this and 151 agents claimed find an issue and then made a change as a result of the audit. Agents generally picked reasonable areas to audit, but usually didn't do an independent audit with a fresh context (which I will often ask agents to do) and often just made the same mistake in the audit that they had already made.

42 used an independent agent, but these runs actually scored worse (it's possible this isn't causal and agents decided to spin off an independent audit because they were in a worse or harder situation). Audit ended up with the best correctness on xhigh, but below average correctness on medium, and all of this auditing substantially increased cost, especially on xhigh. On average, Audit did about as well as Default and it's not clear if it's really better on xhigh and worse on medium. That would be plausible, but I don't think we have enough evidence to tell.

Em Chu had the following comment:

> The results here are consistent with my experience. Auditing code is where most of my tokens go at the moment because I find it quite useful. I always give the two instructions though:
> 
> -   Don't spawn subagents; read and understand the code/diff yourself
> -   Don't execute any of the code
> 
> because I find the LLM to be significantly dumber if you let it do either of those (though of course I haven't measured...). It really doesn't read or reason about code by default, even if I'm never making a change big enough to exceed its context window.
> 
> I also usually include some BS like "be adversarial" "consider all possible combinations of features" "consider the entire input space" but I'm less sure that helps at all.

It would be interesting to try that, but as I've noted in my recent posts, I'm trying to go into less detail in posts, so maybe that will be a topic for another post.

### Audit and fuzz risky areas

For Zstd, when this instruction was followed, it caused agents to focus heavily on [FSE](https://github.com/cyan4973/finitestateentropy), [Huffman](https://en.wikipedia.org/wiki/Huffman_coding), bit readers, and state. These were areas where, in general, agents often missed issues, so agents were correct to think that these areas were risky. The areas that were targeted for fuzzing were better choices than the plain Fuzzing condition.

On medium effort, agents mostly ignored the instruction and didn't do it, but they did follow instructions on xhigh. While this condition didn't perform poorly, it didn't seem to do better than no instructions.

When looking at what agents actually did, one issue was that agents often just generated a bunch of random inputs which were generally invalid and wouldn't test any interesting condition.

When a human tester generates randomized tests, they'll generally try to target the randomization in a way that generates "interesting" inputs and agents failed to do that. Agents also didn't check outputs very effectively and, in many cases, only looked for crashes. Fuzzing is often associated with only checking for crashes and not checking for properties, so this is maybe not too surprising, but it's probably not what a human would want if they were testing a Zstd implementation.

### Make no mistakes

Although this technically scored higher than Default, behavior didn't seem to be meaningfully different and the scores are quite close; I would guess that this is due to random variation. At every level at which I looked at the results, they were indistinguishable from random draws of Default.

### Kani

Kani is a Rust [model checking](https://en.wikipedia.org/wiki/Model_checking) library.

In terms of "actually using a formal method on the code that will execute", Kani had the best coverage in that Kani was actually used on the Zstd code. However, that only happened occasionally and most use was superficial.

There was one case where real Kani use caught a non-trivial bug that caused Rust code to change. 1 out of 160 isn't amazing, but it does indicate that agents can stumble into using Kani reasonably sometimes (which, I would guess, means that, if used in an RL env, models could learn how to use Kani more effectively).

Kani had noticeably higher cost than other conditions. This seemed to be because reading Kani output repeatedly was expensive, which resulted in a high input token cost.

### ACL2

ACL2 is a theorem prover. One thing to note about the result here is that, in many cases, ACL2 OOM'd (192 GiB limit). OOM results weren't counted, which biases the results in some opaque way.

Although ACL2 scored higher than Default, I think it would be surprising if this was causal and significant. As we saw with almost all of the other formal methods, ACL2 was mostly used to prove things that didn't significantly impact correctness, so it's not clear why this would improve correctness.

With many different conditions, we wouldn't expect Default or the seemingly equivalent Make no mistakes to be at the top unless other conditions had severely degraded performance.

### Proptest

Proptest is a property-based testing library.

Just as we saw with the other randomized testing, most tests weren't very interesting, and a too-heavy reliance on randomness caused poor coverage.

Despite generally poor use of property-based testing, proptest's shrinking (finding a simpler input that causes a test failure) did sometimes provide some value, which is better than the little to no value we saw in most other cases.

### Property-based testing

As with the other technique-based approaches, agents had a container with all options installed. Every agent chose to use proptest, so this effectively became a 2nd proptest condition.

As with the proptest condition, tests were mostly not very good but they did sometimes find bugs and shrinking seemed to generate some wins.

I find it mildly interesting that this second "accidental" proptest arm also scored well above average, just like proptest.

### Skill

Here, Skill refers to the skill I wrote to test having a simple skill (as opposed to the large/complex skills that were what I found when I asked an agent to find relevant testing skills).

Maybe I should use skills, but I generally don't and instead rely on prompting and seeing what happened and then prompting some more. As a result, I have no intuition for what makes a good skill since I don't have any practice at it, but Max Bittker suggested that it would be interesting to see the result with a test skill that attempts to encode some information I have in my head about testing. On seeing the result of this, he had an "I told you so" reaction.

I didn't write a pre-registered guess about this, but the guess in my head was that this wouldn't work well. [From my attempt at conveying this to humans in 2015](https://danluu.com/testing/), which I would say pretty much failed, I don't think I'm good at explicitly laying out how someone should test in writing. I've sat down with people and showed them what to do, which has generally converted them for life and turned them into [way above average](https://danluu.com/p95-skill/) bug finders, but [being able to convey something by showing someone is a different (and easier) skill than conveying it by writing down how to do it](https://danluu.com/hardware-unforgiving/).

In this case, the skill was:

-   Think about areas likely to have subtle bugs before implementing; for each, state likely mistakes and plausible alternative interpretations, then come up with a check where the results differ (prefer asymmetric / boundary examples on both sides of the boundary)
-   After implementing, for high risk areas, independently re-derive the result without context on production code and compare (fresh context, do not re-use helper functions)
-   When feasible, use property-based testing or randomized inputs to try to explore the space, minimizing effort on no-panic or no-crash randomization
-   When randomizing, lean towards inputs that will explore interesting state and code paths (don't just naively randomize inputs that all fall into the same error paths); this may require structured random inputs
-   If you're unsure about details, use independent reasoning to check what's correct (fresh context, do not re-use helper functions)

This got the highest score, but didn't work as intended. It didn't really do the fresh context thing almost ever, so it was pointless to have that in there and we don't know if that's something that's effective that needs to be refined to force agents to do it more frequently or if it's something that should be removed (while it's technically possible it's happening at the optimal frequency, I highly doubt it).

We noted in "Audit and fuzz risky" that agents seemed to know how to identify risky areas. This was true here as well, but this didn't necessarily mean that agents did the right thing. For example, agents identified bitstreams being reversed for encoding vs. decoding in Zstd as being risky, but agents didn't do better on tests that exercised this. If we look at specific examples, for medium run #35, an agent identified this as risky, did independent derivations and an audit, but still failed. It had a relevant test, but the input was palindromic, so reversing the order gave the same result, allowing for a failing implementation that had this backwards.

Another issue, if we can call it that, is that all of the fuzzing / property-based testing was done "by hand". Given that agents seem ok at using proptest and that proptest has some useful machinery to lean on, this skill could probably trivially be improved by instructing agents to use proptest. The instructions to agents that were intended to minimize the standard failure mode of generating many useless "too random" tests directionally worked and a larger fraction of agents generated somewhat meaningful tests, but the tests were still worse than I'd expect a human to write (or an agent with active human guidance). Without iterating on this, I'm not sure what generic guidance would be good (as opposed to spending a few minutes looking at the structure of Zstd and giving Zstd-specific guidance, which is one kind of thing that's worked well for me on other problems).

As a first draft for a skill to iterate on, I don't think this is horrible, but I don't think it's really ready to use either. I could see an improved version of this working if it were tried with many more examples to make sure there isn't overfitting to RFC-like problems, bit-manipulation-intensive problems, etc., but, since I don't normally make skills and haven't ever tried to iterate on one, this fails to capture what I or another human would do if really driving an agent.

Since I'm used to prompting and then looking at the result (not necessarily the code, but at least what agents say they did and some kind of agentic summary of what happened, and parts of actual results for some kinds of experimental work) and then re-prompting based on that, I'm not used to front-loading information, which is a fairly different problem than reacting to information. From previous fuzzing work, I've seen failure modes that agents often fall into and the skill was intended to prevent those failure modes, but it's easier to do this if you check back in even occasionally than to do it fully up front, and the up front instructions weren't sufficient to stop the standard failure modes, though they did mitigate them somewhat.

As we noted above, I didn't try to break down the data in a nice, easy to look at way. I didn't do that because, once we look at what agents actually did, it seems like they were mostly pretty ineffective and I don't think it's particularly interesting to see how well "agents using Verus badly" do compared to "agents using QuickCheck badly". One thing that I find a bit interesting is that, when asked to identify areas that are risky or prone to subtle bugs, agents were able to do that.

But, in general, regardless of the library or technique suggested, agents failed to use the technique. As [previously discussed](https://danluu.com/ai-coding/), just asking agents to "test" or repeatedly asking them to test more results in poor testing. It turns out that asking them to use test techniques (some of which I've personally found to be highly effective) also results in poor testing. The quick and dirty skill I wrote seems like it could improve things a bit, but would need more than the 2 minutes I spent on it to be actually useful. Yossi Kreinin made the comment that the state of software testing is atrocious, therefore we should expect poor results if agents fall back to their training, so to speak, which is what we saw.

For whatever reason, agents seemed to be somewhat better at using proptest, although the level of testing was well below what I'd expect out of a reasonable human who's read the proptest manual and is given some direction on how to test. I'd be curious if agents that are given more direction are more effective with proptest than with other libraries, but that's a topic for another post as I've been trying to get posts out in half an hour and we're approaching 9000 words here, which is beyond a reasonable amount to try to type in half an hour.

### How do you get agents to write good tests?

My experience has been, if you guide agents to set up a reasonable test and triage structure, getting agents to add to that effectively without a huge amount of supervision works ok-ish. Because of my background (bias), the kind of testing I tend to lean on is some form of randomized testing / fuzzing / property-based testing.

I talked to Jamie Brandon about this, and he's found the same with snapshot testing. He mentioned that, on one project, when he asked agents (using a variety of models) to do snapshot testing, they would say that they were doing it and then just wouldn't do it (they would write a unit test and then say they wrote a snapshot test). On a different project, he was able to get them to write reasonable end-to-end tests with mocked IO, but only after moving the tests into a separate crate and putting instructions in AGENTS.md to keep tests in the crate and not modify the public interface.

At least to date, I've been leaning more heavily on getting agents to write the test code than Jamie (my tendency has been to type to agents in a CLI; at least for now, he favors writing code by hand a lot more than I do), but it doesn't seem to matter how you do it as long as you set up some kind of reasonable structure.

[Similar to this earlier problem we looked at](https://danluu.com/ai-coding/), it seems like doing anything remotely reasonable works. If you "talk to" an agent and give it light instructions like we did for the Zstd or IMAP evals, the agent will do poor work. But if you look at what it does and type a few more sentences, you can often get it to a good place pretty quickly (or that's what my experience has been on other problems, anyway). Without having ever attempted to understand what makes models work, my made up and probably completely wrong guess for why it seems like doing something remotely reasonable generally works is that, somewhere inside the model is some kind of understanding how to do this stuff. It's not the default, and it's not even near enough to the default that naming what technique to use works, but if the model is sufficiently primed, the knowledge for how to do this stuff will actually get put into practice.

I'd be curious if this can be effectively packaged up into skills, or if AI labs are going to start training models to get better at testing or formal methods, or if whatever they're doing that doesn't directly improve those things will still improve those indirectly enough that agents will write decent tests without much supervision or structure.

### Skills

At various times, I've felt like I have a bad/antiquated/ineffective workflow because I hear people are doing something and I've been too lazy to try it out. I've felt this way about skills for a while since I don't really use skills. Instead, I keep a large scratchpad of things that I sometimes copy+paste in as prompts, which sort of feels like the equivalent of commenting out blocks of code to save them instead of using version control.

But then [I saw this talk by Thorsten Ball](https://thorstenball.com/talks/how-i-prompt/), where he mentions he doesn't rely heavily on skills, and I talked to a couple people who seem relatively effective with LLMs who also don't really use skills, and it made me wonder if I'm not missing out on much.

Then I tried this experiment, where my feeling was that the skills I looked at weren't going to help and are probably actually going to hurt, with low confidence since I don't know anything about skills. The skills did pretty much what I thought they would do, so it turns out the intuition I have from just seeing how agents respond to things and running a bunch of little experiments seems to hold up ok for skills. I also looked at a number of other skills that allegedly improve testing which I didn't include in this experiment that looked like they would have the same failure modes as the skills we tested.

I also ran two experiments (details not discussed here, perhaps in another 10k word post another time) on some other skills that are "official" skills that companies have to support their product. One is from a big AI lab and the other is from a "small" few billion dollar company, but in both cases, the skills made results worse, just like we saw here. Funnily enough, after these experiments, I'm actually more bullish on skills for personal use than I was before since the failure modes seem predictable and therefore fixable without a huge amount of costly experimentation. Creating a publicly released skill that's intended to be really good, work well across different models and harnesses, etc., seems like it might be hard (claude and codex seem to "want" different styles of prompting, so of course that should be true for skills as well), but just addressing the issues that cause a lot of skills to be worse than no skill for personal use seems quite doable?

### Naive thoughts on skill writing

I don't know enough about skills to say how to write a good skill, but with all the skills we looked at in this post (except for the one I wrote in a minute or two) and the skills from these other two experiments, the skills seemed written like they're human tutorial instructions, in that the goal of the skill seems to be to explain how to do something. My naive thought as someone who's written all of one skill is, I'd guess that this isn't optimal when working with a model that should already have some knowledge of the topic (which was the case here and in the other experiments as well). The model is already going to have some kind of default behavior distribution, so I feel like the more natural thing to do is to give statements that will modify that behavior, not write instructions that would allow a human or non-knowledgeable agent to do the behavior at all.

One obvious problem is that we get different default behaviors from different harnesses, models, and effort levels, but throwing a bunch of text into a prompt or a skill doesn't actually change this; that's just a longer way to push the agent away from its default, with a lot of text that may do some kind of unintentonal pushing. As we saw here, much of the text just gets ignored (and what gets ignored and when is of course harness, model, and effort dependent). For example, for the ECC skill, even when it was read, had most instructions ignored, and although the TDD instructions were influential (which made results worse), the instructions to do TDD were still not really followed despite them being laid out clearly.

Since what kind of prompting is effective changes enough between model releases and effort levels, for something general like "testing code well", it's not clear to me how these skills are supposed to work across so many models and efforts. Just going from GPT-5.5 to GPT-5.6 changed how I worked substantially because a number of things that worked fairly reliably with GPT-5.5 either stopped working or became much less reliable (even though, overall, the level of capability seems higher). In the same way that I don't prompt GPT-5.6 the same way I prompted GPT-5.5, I don't think I'd want to use the same skills.

I'm not sure who, other than someone at an AI lab, would actually go through the trouble of running evals on skills to see what's effective for each model and effort level and then create a portfolio of skills that are differentiated by model and effort, and I wouldn't expect AI labs to have skills that are optimized for their competitors' harnesses and models, so I don't know about things like generic "testing" skills (as noted above, quite a few testing skills that I looked at but didn't test here looked like they would have the exact same failure modes as the pre-existing skills we tested), but I could see having a few skills that work for my own use cases with the specific harness/model/efforts that I tend to reach for.

Just thinking about testing, while there are particular pitfalls that certain models fall into at certain effort levels that I want to nudge them away from, there isn't really a generic test workflow that I want to give agents that's independent of the thing being tested and the level of quality I want from the thing and the dimensions in which I want quality, so I don't think I'd want a generic test skill that lays out a set of testing steps that agents should, in general, do. Something like this goes for a lot of task that I do, which I want done in task-specific way and not a generic way. I could imagine some kind of skill that asks me questions and then emits the correct instructions to agents, but given how fast models are improving, if I'm making something for personal use, I don't think it makes sense to spend time tweaking a skill like that until it's useful. If I was working on an agentic product and wanted more people to use it, that might be a different story, but the skills I've tried have had the same failure modes as the skills we tested here, so it seems fairly easy to make a skill that turns out to not be that effective.

I could see skills being generically useful for things like teaching agents how to execute workflows or how to interact with APIs/interfaces, such as [Sawyer Hood's skill that helps agents drive a web browser](https://github.com/SawyerHood/dev-browser). Since I haven't tried that skill, I'm not endorsing it, but from reading through it, it seems like the kind of thing that would work well and save me a lot of hassle when I'm trying to get an agent to drive a web browser. However, if you read the actual skill (and scripts), it has a very different style than the testing skills we tried here.

### Appendix: agent silliness

After asking an agent to do a simple lookup of something for an analysis, it exec'd a perl process that ran for 2 hours and 20 minutes before I killed it (I really need to have something that automatically catches things like this, because it's fairly common).

A subagent used perl to do a regex search over a relatively small file (44kB, 1364 lines), but the expression was degenerate with PCRE and did a combinatorially large amount of work. I tried re-running this with [the FRE regex engine we tried building in a few minutes here](https://danluu.com/benchpocalypse/) and it finished matching in 0.7s (Rust regex was 0.6s).

You never know what's going to happen when agents are off doing things, but there are at least was this could've been prevented. First, the agent could've avoided invoking a regex engine that can give you a combinatorial explosion like this; there doesn't appear to be a strong reason not to use a safer regex engine for this (such as ripgrep at default settings). Second, the agent could've issued the regex it was trying to emit; the actual regex it did emit returns a uselessly large capture and doesn't do what's intended when it succeeds. Third, the subagent (or the harness) could automatically kill things like this after the subagent finishes. Of course this shouldn't happen for everything a subagent runs, but agents often leave runaway processes like this lying around (in this case, it appears the subagent that launched this stopped after 30s but left this process running indefintely even though a search like this is intended to returned a result that's used by the subagent, which has no value if the subagent has finished).

I actually have a process that goes around cleaning up after things agents leave lying around (agents that, themselves, leak memory, temporary build artifacts that consume space, etc.), but it wasn't looking for runaway perl processes. That's another one to add, but surely I'm not the only person who's run into this problem. I guess I could open source my silly tool for this, but it should become obsolete once the major harnesses fix this, so there doesn't seem to be any good reason for anyone to even pick up my thing in the first place were I to open source it since the AI labs are probably going to fix this kind of thing in not too long.
