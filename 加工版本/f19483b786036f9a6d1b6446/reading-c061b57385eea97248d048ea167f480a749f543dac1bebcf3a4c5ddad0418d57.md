一、弃用 Skills 者多未认真使用：回答认为，当前弃用 Skills 的用户中，很多并未在自己的项目中认真使用过 SKILL，因此其弃用决策缺乏实践基础。这一判断暗示，对 Skills 的评价应基于实际项目使用经验，而非泛泛而谈。

三、LLM 涌现现象与上下文焦虑：回答指出，小费提示类 Skills 之所以有效，是因为 LLM 在海量语料中建立了积极情感语料对完成任务的正向增益，这是一种涌现现象。类似现象还有接近 Context Limit 边界时的上下文焦虑。这些经验对旧模型有效，但未必适用于新模型，因此相关 Skills 可弃。

## 弃用 Skills 者的真实情况

/goal 筛出了一堆没怎么认真用过 SKILL 在自己项目里的人罢了。

^pr-9e4d894ddd0a

## 可弃的 Skills：与项目无关的通用约束

能弃的是类似 Superpower、Grill me、Ralph Loop、Frontend Design 这一类确实本身就是和你的项目没什么关系的 SKILL，虽然 Superpower/Grill me 这种更多的是为了防止人蠢了或者懒了而做的强制设计先行。这些 SKILL 有点像以前那种小费提示，告诉模型我会给你小费，对应 Benchmark 就真的会刷高，效果也确实会更好，这也是 LLM 涌现的一种神奇的现象，它竟然在海量语料中建立了积极情感语料对完成任务的正向增益，类似的现象其实还有接近 Context Limit 边界时的上下文焦虑，以前大家知道这些缺陷，当然能建个通用 SKILL 来约束，但这些经验不一定对新的模型是必要的。这些能弃，是因为基座模型本身能力成长了，它们本身也就不需要多说就会自动去做，例如 Frontend Design 这种其实就是规范下不要产出 AI Slops 的前端，基座模型能力增长了，你不故意说那些规范，它写出来的前端 Slops 也会少很多。

^pr-8c161d9b3d0e

## 不可弃的 Skills：与项目环境强绑定的 Harness 层

不能弃的，是那种和你的项目环境和流程 SKILL 强绑定的，你说它是 Harness 层也可以，虽然比较花哨，但我们就暂且这样说吧。例如你的项目的 DevOps 是企业的 GitLab 还是什么，针对你的系统有个类似标准的个性化或者平台相关的部署流程、针对你的后端排查有一些积累下来的排查错误的脚本、常用的 SQL+整理查询，针对你的项目的专用模块化经验。这些东西的特点是，你把它们删了，模型是不可能在预训练过程中知道你当前项目或者既有经验的提炼之后的做法的；你把它们删了，模型要么重新造一次轮子（SKILL），要么每次都从头从代码源分析来整理和梳理方法，这些 SKILL 的特点是有时候代码都不一定是唯一真相；你把它们删了，Agent 根本从代码推测不出来你们的标准部署流程要过几次 Review，哪些部分的测试是不能动的，线上能不能直接合并，排查着重关注的到底是召回还是是显存占用、还是是后端的某个 API 的指标。有人会问这个积累在 CLAUDE.md 或者 AGENTS.md 里不就行了吗，那就丢了 SKILL 本身防上下文爆炸的渐进式披露，按需加载的好处。
