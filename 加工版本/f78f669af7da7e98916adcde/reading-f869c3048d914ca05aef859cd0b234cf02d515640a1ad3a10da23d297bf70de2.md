# 反对本质复杂性与偶然复杂性｜Against essential and accidental complexity

---

## 正文

在 1986 年的经典文章 [No Silver Bullet](http://worrydream.com/refs/Brooks-NoSilverBullet.pdf) 中，Fred Brooks 主张，在某种意义上，能够为 improve programmer productivity 做的事情并没有那么多。他的推理思路是，programming tasks 包含一个 essential/conceptual[1](https://danluu.com/essential-complexity/#fn:C) complexity 的 core，而任何潜在的 technology advances（例如 languages 或 tooling）从根本上都无法对其进行 attack。随后，他使用一个 [Ahmdahl's law](https://en.wikipedia.org/wiki/Amdahl%27s_law) argument，表示由于 complexity 的 1/X 是 essential，因此通过 technological improvements 获得超过 a factor of X 的 improvement 永远是不可能的。

在文章接近结尾时，Brooks 声称，programming 中至少 1/2（大部分）的 complexity 是 essential，这就将所有 technological programming innovations 合计所剩的 potential improvement 限制在至多 a factor of 2[2](https://danluu.com/essential-complexity/#fn:T)：

> 所有针对 software process 的 accidents 的 technological attacks，从根本上都受到 productivity equation 的 limited：
> 
> Time of task = Sum over i { Frequency\_i Time\_i }
> 
> 如果正如我所相信的，task 的 conceptual components 现在占用了大部分时间，那么，无论对那些仅仅是 concepts 的 expression 的 task components 开展多少 activity，都无法带来 large productivity gains。

Brooks 为 programmer productivity 能够 improve 多少提出了一个 bound。但在实践中，要正确地陈述这个 bound，就必须能够设想出一些 problems：由于使用当前 technologies 来 solving 这些 problem 所涉及的 friction 太多，没有人会合理地尝试 solve 它们。

如果无法预测未来，就不可能 estimate 这一点。如果我们知道未来，也许会发现，programmers 能够 productively use 的 computational power 或 storage 存在某种 practical limit，从而为 programmer 可用的 resources 设定 bound；但要得到 accidental complexity 数量的 bound，仍然需要正确地 reason：programmers 将如何能够 use 比今天可用的 resources 多出无数倍的 resources。这实在太难，我们不妨称之为不可能。

而且，对于每一种可能存在的 tool class，都必须有效地预见所有可能的 innovations。Brooks 对此采取的策略，是考察已有的 tools categories，然后逐一表示，它们会是 ineffective，或者虽然 effective，却已经没有进一步发展的余地。这种看法是错的，不仅因为它低估了那些尚不存在、[尚未 effective](https://danluu.com/butler-lampson-1999/)，或他并不熟悉的 tools classes 所能带来的 gains（例如，他否定了 formal methods，却甚至没有想到要提及 fuzzers、不对 code 进行 fully formally verify 的 static analysis tools、valgrind 这样的 tools，等等），还因为 Brooks 认为，每一种曾经出现 major improvement 的 tool class 都已经没有进一步发展的余地，而事实证明，没有任何一种是如此。例如，Brooks 认为 programming languages 基本上已经发展完毕，而那恰恰是在 "scripting languages" 兴起之前，也是在 GC languages 占据绝大多数 programming 之前[3](https://danluu.com/essential-complexity/#fn:L)。尽管你偶尔会听到这样的说法，但不会有多少人因为 modern languages 带来的 gains 不可能比使用 modern language 超过 2x，就自愿用 C 来 write 一个 webapp。

Brooks 否定的另一个领域是 AI，他说：“用于 speech recognition 的 techniques，似乎与用于 image recognition 的那些没有多少共同之处，而两者又都与 expert systems 中使用的那些不同。”但当然，这在今天已经不再成立——neural nets 对 image recognition 和 speech recognition 都是 highly effective。它们作为 programming tool 是否会 highly effective，尚有待确定，但 Brooks 反对 AI 的 argument 的一个关键支点已经被 invalidated，而且认为经过 greatly improved 的 GPT-2 能够给 programmers 带来 significant productivity gains，也并非牵强。当然，指望 Brooks 能够预见 neural nets 会对 speech 和 image recognition 都变得 effective，并不合理；但这恰恰说明，Brooks 否定 AI 以及 computer science 的所有其他 field 的一切未来 advance，同样不合理。

Brooks 也 underestimates practices 以及使这些 practices 成为可能的 tooling 带来的 gains。仅举一个例子，看看老一辈 programming 大师所提倡的观点，我们能看到 [Ken Thompson 主张 language safety 是 useless](https://twitter.com/danluu/status/885214004649615360)，而 bugs 的发生是因为人们 write fragile code，如果不想有 bugs，就不该这么做；还有 [Jamie Zawinski 主张，在期限紧迫时，automated testing 是浪费时间，而且不进行 testing、“第一次就把它做对，确实有很多可取之处”](https://mastodon.social/@danluu/110213164472670607)。Brooks 承认 testing 的重要性，但他提到的唯一可能的 testing improvement，是能够让初学者更容易进行 testing 的 expert systems。如果你考察具有一定 large scale 的 modern software projects 的 complexity，就会发现，它们远远超出了 80 年代所见的任何 software project。如果你认真想一想，使用老式 correctness practices 来处理这些 projects 意味着什么，我认为，对于一个 typical team 而言，从那类 practices 到 modern practices 的 speedup 是 infinite，因为如果给大多数使用那些 practices 的 teams 一个许多大公司都曾 independently solved 的 problem，例如 produce 一个具有某种明确 SLO 的 distributed database，它们根本无法 produce 一个 working product。有人可能会质疑 infinite speedup 这个 claim，但任何在认真对待 correctness 的 complex project 上工作过的人，都用过[能够带来 massive development speedups 的 tools 和 techniques](https://danluu.com/testing/)，相比 80 年代的 practices，轻易就能超过 2x。Brooks 似乎没有想到这种可能性，因为看起来，他认为 testing 所涉及的 essential complexity 使重大的 testing improvements 不可能实现。

另一个 basic tooling/practice example 是 version control。具有 multi-file commits、branches，以及只要 devs 不碰相同 lines 通常就能正常工作的 automatic merging 等功能的 version control system，是相当近代的发明。[在 90 年代，Microsoft 处于 software development 的最前沿，但直到 Win2k 之后，他们才终于获得一个既 supported 所需 repo size（Win2k development 需要 30M LOC）、又 supported branches 的 version control system](https://danluu.com/microsoft-culture/)。当时，Branches 是通过直接 copying 整个 source tree，再尝试 manually merge source tree 的 copies 来 simulated 的。change source tree 需要特别批准，而且由于 manual merging 的痛苦，整个 Win2k team（5000 人，包括 1400 devs 和 1700 testers）即使在顺利的一天，也只能 merge 100 changes（不顺利时，如果 build team 因为花时间 fixing build breaks 而停滞，就是 0）。这已经是在 Brooks 写作的十年之后，而更好的 version control tooling、test tooling 和 practices、使 testing 更快的 machine speedups 等，仍然轻易就能带来 an order of magnitude 的 speedup。请注意，Brooks 不仅没有意识到 version control 和 test tooling 日后会带来 massive productivity gains，还声称 hardware speedups 不会使 developers 显著地 more productive，尽管 hardware speed 被指出是 Win2k development velocity 的一个 major limiting factor。Brooks 无法想象有人会 building 一个像 Win2k 那样 complex、能够真正 utilize 更快 hardware 的 project。当然，使用 Brooks 那个时代的 tools 和 practices，build 一个像 Win2k 那样 complex 的 project 在实践中是不可能的，但 tools 和 practices 的进步如此之快，仅仅十年之后就能做到了，尽管由于那些“石器时代”的 tools 和 practices，其 development velocity 与我们今天习惯的相比仍如慢动作一般。

再从上面挑一个 sub-part 来看，Brooks 没有把 CI/CD 列为潜在的 productivity improvement，因为 Brooks 甚至无法想象，竟然可能拥有能够使 modern build practices 成为可能的 tools。在 1995 年的文字中，Brooks 提到，Microsoft 的某个人告诉他，他们每晚都会 build。对此，Brooks 表示，要实现每天 building（至少）一次，可能需要太多工作，并指出 Bell Northern Research 每周 builds 一次，是相当合理的。Brooks 写下这些话后不久，Google 成立了，而 Google 的 engineers 甚至无法想象接受 Microsoft 那样的 setup，更不用说每周 building 一次了。他们不得不 build 大量 custom software，才能让 Google 那种 scale 的 monorepo 采用今天会被视为 modern practices 的做法，但他们做到了。我曾经工作过的一家成立于 1995 年的 startup，也 built out 了自己的 CI infra，使持续 merging 和从 HEAD 进行 building 成为可能，因为任何着眼于还能做什么，而不是认为能做的事都已经做完了的人，都会这么做。对于 large projects，仅仅拥有 CI/CD 并 maintaining a clean build，相比每周 building，就应该轻易带来 2x productivity improvement，超过 Brooks 所声称的一半 complexity 是 essential 时所允许的幅度。值得庆幸的是，Google、我工作过的那家 startup，以及许多其他地方的 engineers，并不相信不可能获得 2x improvement，而是真的 built 了能够带来 massive productivity improvements 的 tools。

在某种意义上，考察 No Silver Bullet，与[我们考察 Unix 时，发现 Unix 行家说我们应该像他们在 70 年代那样 write software](https://danluu.com/cli-complexity/#maven)，并且说[他们发明的 languages 已经达到了任何 language 所能达到的 safe 程度](https://twitter.com/danluu/status/885214004649615360)，十分相似。早在 computers 被发明之前很久，长辈就一直在告诉下一代，他们已经做完了一切能做的事，下一代不可能取得更多成就。在 computer 时代，我们也在 programming 之外见过无数类似的预测，比如 Cliff Stoll 如今声名狼藉的预测：internet 不会改变任何事情：

> 有远见的人看到的未来，是 telecommuting workers、interactive libraries 和 multimedia classrooms。他们谈论 electronic town meetings 和 virtual communities。Commerce 和 business 将从办公室和商场转向 networks 和 modems。而 digital networks 的自由将使政府更加民主。
> 
> 胡说八道。我们的 computer 专家难道一点常识都没有吗？事实是，没有任何 online database 会取代你每天读的报纸……electronic publishing 又怎么样呢？试试读一本 disc 上的书吧。充其量，那也是一件令人不快的苦差事：笨重 computer 发出的令人近视的微光，取代了书本亲切的纸页。而且你还不能把那台 laptop 拎到海滩上。然而，MIT Media Lab 主任 Nicholas Negroponte 预测，我们很快就会直接通过 Intenet 购买书籍和报纸。呃，当然了。……然后还有 cyberbusiness。有人向我们保证，instant catalog shopping 即将到来——只需 point and click，就能买到超值商品。我们将通过 network 订机票、预订餐厅并洽谈 sales contracts。商店将被淘汰。那么，为什么我家附近的商场一个下午做的生意，比整个 Internet 一个月处理的还多呢？

只要稍做一点 search and replace，就会发现，Stoll 说的与 Brooks 是同一回事。当然，technologies 在过去改变过事物，但我无法想象新的 technologies 会如何改变事物，所以它们就是不会。

即使不了解 programming 的任何具体细节，我们也能看出，这类论证在历史上并未站住脚，并且可以相当有把握地认为，长辈们这次其实也不正确。

Brooks 在不再亲自从事相关工作后，仍然写了很长一段时间关于 software 的文章，但他在 1964 年进入学术界之后，却懒得跟进 industry 中发生的事情。这一点从我们看过的 1986 年那篇文章中就已经很明显了，而如果你看看他 2010 年的书《Design of Design》，就会更加明显：他在其中依赖的仍然是[他在更早的文章和书中依赖过的那些例子](https://www.patreon.com/posts/46629220)，而新材料的大部分则来自他建造的一所房子。我们已经看到，[试图把自己的 knowledge generalize 到 civil engineering 的 programmers，通常会说出一些愚蠢的话，任何 2nd 年的 civil engineering 学生都能看出这些话是 false 的](https://danluu.com/cocktail-ideas/)；事实证明，试图从 house building techniques 中获取关于 software engineering design techniques 的深刻见解，也好不到哪里去。但由于 Brooks 没有跟进 industry，他能拿出来的也就是这些了。虽然确实存在超越时代和行业的恒久见解，但 Brooks 提出了一些非常具体的建议，例如像 [cocktail party](https://danluu.com/cocktail-ideas/) surgical teams 那样运作 software teams。这些建议来自对如何改进 Brooks 在 50 年代于 IBM 见到的 development practices 的思考。然而，事实证明，industry 早已远远超越 IBM 在 1950 年代的 software practices，而那些相较于 IBM 在 1950 年代的做法有所改进的想法，在 70 年后并没有特别大的用处。

回到本文的主要话题，借助事后之明，审视他关于 accidental complexity 的具体说法，我们可以看到，Brooks 在 1986 年声称我们基本上已经获取了 high-level languages 所能提供的全部 productivity gains，这与一个 assembly language programmer 在 1955 年说出同样的话，认为 assembly 已经和任何 language 所能达到的水平一样好[4](https://danluu.com/essential-complexity/#fn:A)，并没有太大区别；而他关于其他 categories 的说法也类似。这些说法主要表明的，是缺乏想象力。当 Brooks 提到 conceptual complexity 时，他指的是使用 Brooks 在 1986 年熟悉的 conceptual building blocks 所带来的 complexity（针对那些 Brooks 会认为属于 programming problems 的 problems）。任何人都没有理由认为 Brooks 在 1986 年对 programming 的认识是 fundamental 的，就像他们没有理由认为一个 1955 年的 assembly programmer 的思维方式是 fundamental 的一样。人们常常嘲笑那句未经证实的“640k 对任何人来说都应该足够了”，但 Brooks 声称，在所有可能带来 productivity improvement 的 categories 中，我们已经完成了大部分能够完成的事情，这与那句话如出一辙，而且还不是杜撰的！

如果我们着眼于未来，complexity 中可能属于 accidental 的 fraction 实际上是 unbounded 的。有人可能会说，如果我们着眼于当下，这些 terms 就并非毫无意义。不过，虽然这会因 domain 而异，但我个人从未处理过一个不是完全由 accidental complexity 所 dominated 的 non-trivial problem，因此，在我处理过的任何值得讨论的 problem 上，essential complexity 这个 concept 都没有意义。

### 附录：具体的 problems

让我们看看，对于我最近在工作中做的几件事，这个关于 essential complexity 的说法是否成立：

-   从一批 hosts 进行 scp，以 read 和 download logs，然后 parse 这些 logs，以了解一个 problem 的 scope
-   针对某些 classes 的 software，从我雇主拥有的每个 software 的每个 instance 中 Query 两年的 metrics data，然后 generate 各种 plots，让我能够弄清楚我对我们的 software 正在做什么、如何使用 computer resources 的一些疑问

#### Logs（日​​志）

如果把这个 task 拆开，我们会得到

-   把 logs 从几十万台 machines scp 到一台 local box
    -   为此 used 了一个 Python script，以获得 parallelism，以及比 pssh/parallel-scp 所能提供的更 robust 的 error handling
    -   write 这个 script 花了 ~1 minute
-   在 logs download 时做其他工作
-   parse 已 downloaded 的 logs（几 TB）
    -   为此 used 了一个 Rust script，write 花了几分钟（这里出于 performance 原因，used 的是 Rust 而不是 Python——如果我不想把这个 task 分派给 multiple machines，那么仅仅用 idiomatic Python opening 这些 logs 并 scanning 每个 line，就已经比我希望的更慢了）

在 1986 年，我或许会使用 telnet 或 ftp，而不是 scp。Modern scripting languages 当时还不存在（perl 是在 1987 年 created 的，而有些人认为第一个称得上 modern 的 version，即 perl5，是在 1994 年 released 的），因此，writing 能够以 parallelism 和“足够好”的 error handling 完成这件事的 code，所花的时间会比今天多出不止一个 order of magnitude。事实上，我认为，仅仅在 managing 一个 connection pool 的同时获得还算过得去的 error handling，就很容易比我完成这整个 task 所花的时间多出一个 order of magnitude（不包括在 background 中 downloading logs 所花的时间）。

接下来就是 parsing 这些 logs。拿“1 TB”这样的 absolute number 来比较并不公平，所以我们就把它称为“多到足以让我们关心 performance”（我们会在 metrics 的例子中更详细地讨论 scale）。如今，我们可以选择各种 high-performance languages，用它们很容易 write 出 fast、safe 的 code，并利用 libraries 的力量（例如一个 regexp library[5](https://danluu.com/essential-complexity/#fn:B)），轻松地 write 一个 quick and dirty script 来 parse 和 classify logs，把工作分派给我电脑上的所有 cores（我认为 Zig 也会让这件事变得容易，但我 used 的是 Rust，因为我的 team 已经有了足够多的 Rust programmers）。

在 1986 年，不会有可比的 language，但更重要的是，我无法轻而易举地 find、download 和 compile 合适的 libraries，而必须手动 write 所有 parsing code，把一个只需几分钟的 task 变成一个能在一小时内完成就算幸运的 task。此外，如果我不知道如何使用这个 library，或者不知道自己可以使用一个 library，我可以很容易地在 StackOverflow 上找到该如何 solve 这个 problem，这会大幅 reduce accidental complexity。不用说，在 1986 年，并没有什么真正相当于通过 Googling 查找 StackOverflow solutions 的东西。

而且，即使到了今天，这个相当 standard 的 programmer devops/SRE task，在相比 1986 年类似的 task 获得至少一个 order of magnitude 的 speedup 之后，仍然几乎全是 accidental complexity。

如果这些 data 被 exported 到我们的 metrics stack 中，或者我们的 centralized logging 的工作方式稍有不同，那么整个 task 都会是 trivial 的。而如果这两点都不成立，但 log format 更 uniform，那么在拿到 logs 后，我就不必 write 任何 code；[rg](https://github.com/BurntSushi/ripgrep) 或 [ag](https://github.com/ggreer/the_silver_searcher) 就足够了。如果我试着看看自己在这个 task 的 essential conceptual core 上花了多少时间，这个时间少得难以估计。

#### 查询 metrics（Query metrics）

我们其实只需要一个 counter-example，但我认为，看看一个更 complex 的 task，了解 Brooks 的 argument 在更 involved 的 task 中如何 scales，会很有说明作用。如果你想跳过这个冗长的 example，[点击这里跳到下一节](https://danluu.com/essential-complexity/#summary)。

我们可以把我的 metrics querying task 看作由以下 sub-tasks 组成：

-   Write 一组 [Presto SQL](https://en.wikipedia.org/wiki/Presto_\(SQL_query_engine\)) queries，每个 query 实际上都从一个 data set 中 scan 大约 100 TB 的 data；如果我没有 [maintain 只 contain relevant 的 data subset 的 tables](https://danluu.com/metrics-analytics/)，这个 data set 的 data 就会达到大约 100 PB
    -   write 第一个 query 可能需要 30 seconds，queries 需要几分钟才能 finish，使用大约 1 CPU-year 的 CPU time
-   Write 一些 ggplot code，来 plot 我好奇的各种 properties
    -   不确定这花了多长时间；比 queries 完成所花的时间短，因此没有增加这个 task 的总时间

这些 tasks 中的第一个，如今完成起来快了如此多的 orders of magnitude，以至于即使允许误差达到一两个 orders of magnitude，我都无法冒险猜测如今究竟快了多少。不过，让我们把第一个 task 拆成 component parts，了解一下这个 task 在哪些方面变得更容易了。

把 100 PB 这样的 absolute numbers 搬到 1986 年是不公平的，但仅仅是拥有一个 pipeline，能够 collects 和 persists comprehensive data，类似于我在一家 consumer software company 所查看的 data（关于我们 software 的 resource usage 和 efficiency 的各种 data），这样的想法在 1986 年就会被认为荒谬。这里，我们看到了用 accidental essential complexity 的 concept 为 productivity improvements 提供 upper bound 的一个致命缺陷：accidental complexity 太多的 tasks，甚至根本不会被认为是可能的。Brooks 所看到的 accidental complexity 有多少，其 limit 实际上是他想象力的 limit，而不是什么 fundamental 的东西。

Brooks 明确否认 increased computational power 能够 improve productivity（“嗯，一个人能有效地 use 多少 MIPS 呢？”，后面还会详谈），但 storage 和 CPU power（更不用说 network speed 和 RAM）所带来的 accidental complexity 如此巨大，以至于它们 bounded 了 Brooks 能够想到的 problems 的 space。

在这个 example 中，假设我们在 1986 年设法有了足够的 storage，能够 keep 我们想要 query 的 data。接下来就是 marshall 大约相当于 1 CPU-year 的 resources，并让 query 在几分钟内 complete。和 storage problem 一样，这在 1986 年也会是荒谬的[6](https://danluu.com/essential-complexity/#fn:F)，所以我们又遇到了第二块 non-essential complexity，它如此巨大，以至于会让一个 1986 年的人根本想不到这个 problem。

接下来是 writing 这个 query。如果我当时是在为 Cray-2 writing，并且想要 productive，我大概会用 Cray 的 Fortran 77 dialect 来 written 这些 queries。我能在每个 query 不到 300 seconds 的时间内做到吗？绝无可能；即使用 Scala/Scalding，我也远远做不到，而我认为即使用 Python/PySpark，也会很勉强。我认为，这是我们看到的 gain 最小的方面，但这里仍然远远超过一个 order of magnitude。

把 data processed 之后，我们必须 generate plots。即使使用今天的 technology，我认为不用 ggplot，也会让我在 productivity 上付出至少 2x 的代价。我试过每一个号称 equivalent 的主要 plotting library（无论哪种 language），而我试过的每个 library，要么在 rendering 我认为在 ggplot 中属于 basic 的 plots 时存在多个 show-stopping bugs，要么太 low-level，以至于我被迫 manually 做一些在 ggplot 中本来 trivial 的事情，损失超过 2x 的 productivity。在 2020 年，仅仅一个 library 的存在，就已经在这一步为我节省了 2x。如果回到 1986 年，在 [the grammar of graphics](https://amzn.to/3r9Mvzw) 这个 concept 及任何合理的 implementation 出现之前，即便假设有某种神奇的 workstation hardware，能够在合理的时间内完成我所做的 plotting operations，我也不可能不在 plotting 上多花至少两个 orders of magnitude 的时间（我的 machine 在 rendering 这些 plots 时慢得令人难受；Cray-2 根本不可能在任何称得上合理的 timeframe 内完成 rendering）。

从 1986 年到今天，这个 problem 的 accidental complexity reduction 达到了如此多的 orders of magnitude，我甚至无法 estimate；然而，这个 problem 中 accidental complexity 的 fraction 仍然如此之大，以至于又一次很难猜测 complexity 中有多大的 fraction 是 essential。要把我能想到的所有 accidental complexity 全部写下来，至少需要 20k 字，不过，为了让你稍微体会一下这种 complexity，我来写几件事。

-   SQL；它属于那种表面上 simple，[但实际上 extremely complex](https://scattered-thoughts.net/writing/select-wat-from-sql/) 的东西
    -   还有 Presto SQL
-   Arbitrary Presto limits，其中一些来自 Presto，另一些来自我们 operate Presto 的具体方式以及我们使用的 version
    -   有一个 internal Presto data structure assert fail，会在我以某种特定方式同时 use `numeric_histogram` 和 `cross join unnest` 时被 triggered。因为 write 一个 bug-exposing query、等它 fail、然后再 re-write，是在浪费时间，所以我脑中有一个 heuristic，用来猜测任何同时 uses 这两个 constructs 的 query 是否会 hit 这个 bug，并 apply 它，避免不得不 write 两个 queries。如果这个 heuristic applies，我就会改为 write 一个更 verbose、execute 更慢的 query，而不是那个更 straightforward 的 query
    -   我们按 date 来 partition data，但当我 join tables 时，Presto 会把这一点丢掉，导致我 join 横跨很长一段时间的 data 时产生非常 large、因而 expensive 的 joins，尽管原则上这可以是一系列 cheap joins；如果 join 大到足以让我的 query blow up，我就会 write 一个本质上是小型 query compiler 的东西，来 execute 逐日的 queries，然后按需要 post-process data，而不是 writing 那个 naive query
        -   在许多情况下，query 中的某种 optimization 能让 query 变得 feasible，而不必把 query 按天拆开（例如，如果我想把 host-level metrics data 与包含某个 host 属于哪个 cluster 的 table 进行 join，那么对跨越多年的 data 而言，这是一个非常 slow 的 join；但我也知道哪些 kinds 的 hosts 位于哪些 clusters，这在某些情况下让我能够根据其中的 core count 和 total memory 等，从 host-level metrics data 中 filter hosts out，从而让这个 join 的较大 input 变得足够 small，使 query 不必 manually partitioning 就能 succeed）
    -   我们有一个“fast”但 memory limits “low”的 Presto cluster，还有一个“slow”但 memory limits “high”的 cluster，所以我会在脑中 estimate 一个 query 需要多少 per-node memory，以便将它 schedule 到合适的 cluster
    -   等等。
-   出于 performance 原因，我应该何时在 Presto 中 compute CDF 或 histogram，而不是留到最后让 ggplot 来 compute
-   为了让 ggplot 能够 handle data，我是否需要 downsample data，如果需要，要 downsample 多少，以及这可能如何 impact analyses
-   各种 Arbitrary ggplot 事项
    -   在 scatterplot 中放入大约多少 points 后，我就应该停止使用 `size = [number]`，转而使用 single-pixel plotting，因为把 points plotting 成 circles 太 slow 了
    -   points 的 minimum allowable opacity 是多少
    -   如果因为这个 limit，我超过了 scatterplot 中能够看出 gradient 的 maximum density，那么我需要把 image 做到多 large，才能适当地 reduce density（我何时会这样做而不是使用 heatmap，值得另写一篇文章）
    -   等等。
-   以上全都是关于我用来 write 和 examine queries 的 tools，但还有所有 data issues 的 mental model；为了 generate valid result，writing query 时必须考虑这些 issues，其中包括 clock skew、Linux accounting bugs、我们 metrics pipeline 的 issues、underlying data sources 中的 problems 所导致的 data issues，等等。
-   等等。

对于 Presto 和 ggplot，我脑中都隐含地记着一百多件事，才能让我的 queries 和 plots work；我选择使用它们，是因为在我所知道且能够使用的 tools 中，它们的 overhead 最低。如果有人让我说出，我必须 deal with 的 complexity 中有多少 percentage 是 essential，我会说，它低得根本没法 estimate。对于某些 queries，可以说它是 zero——我的工作之所以 necessary，只是因为某个 arbitrary quirk，没有这个 quirk，就没有任何工作需要做。但即使在某种 query 看起来 necessary 的情况下，我也认为，很难相信 essential complexity 会超过我必须 deal with 的 complexity 的 1%。

再来看 Brooks 对 computer performance 的看法：尽管我在 2020 年仍然要 deal with hardware performance 的 limitations 所造成的 complexity，并且今天仍然非常想要 faster computers，但 Brooks 在 1986 年就断言，faster hardware 基本上不会 improving developer productivity：

> individual workstation 的 power 和 memory capacity 必然且迅速的 increase，可以为 software art 带来哪些 gains？嗯，一个人能有效地 use 多少 MIPS 呢？今天的 speeds 已经 fully supported 了 programs 和 documents 的 composition 和 editing。Compiling 倒是可以再 boost 一下，但 machine speed 提高一个 factor of 10，肯定就会 . . .

但这至少在两个层面上是错的。首先，如果我能用上 faster computers，我的大量 accidental complexity 就会消失（如果 computers 足够 powerful，我就不需要 Presto 这样的 complex tools；我直接在 local computer 上 run 一个 query 就行了）。我们现在的 computers 已经快得多，但 faster computers 能让许多 involved engineering tasks 变得 trivial，这一点仍然成立。正如 James Hague 指出的，在 80 年代中期，[writing 一个 spellchecker 因为 performance constraints 而是一个严肃的 engineering problem](https://prog21.dadgum.com/29.html)。

其次，（仅举一例）ggplot 之所以存在，只是因为 computers 如此 fast。从事 performance 工作的人经常抱怨：如果把 tool X 所做的 fundamental operations 与今天 hardware 的 speed 相比较，就会发现它存在两个到十个 orders of magnitude 的 inefficiency[7](https://danluu.com/essential-complexity/#fn:O)。但有多大 fraction 的 programmers，能够 realize 一台 modern multi-socket machine 的 potential performance 的哪怕 one half 呢？我猜不到千分之一，而且我会说，肯定不到百分之一。并且，performance knowledge 并不 independent of 其他 knowledge——在 controlling for age 和 experience 后，它与非“systems” domains 的 knowledge 是 negatively correlated，因为花时间学习那些为了 realize 一台 computer 一半 potential 所必需的深奥 accidental complexity，就意味着没有把这些时间花在学习“directly” applicable domain knowledge 上。看看那些需要大量 domain knowledge 的 software（例如 ggplot），或者 large 到需要一个 large team 来 implement 的 software（例如 IntelliJ[8](https://danluu.com/essential-complexity/#fn:V)），如果 machines 慢上多个 orders of magnitude，而 writing usable software 又要求榨出 machine 的大部分 performance，那么其中绝大多数都不会存在。幸运的是，hardware 已经快得多，让绝大多数 developers 能够忽略 performance-related accidental complexity，转而专注于今天要做到 productive 所必需的其他所有 accidental complexity。

Faster computers 既能 reduce tool users 遇到的 accidental complexity 的量，也能 reduce tool creators 需要处理的 accidental complexity 的量，从而让更 productive 的 tools 得以出现。

### 2022 更新

很多人说这篇文章是错的，因为 Brooks 显然是在说 X，而 Brooks 并不是我在这篇文章中引用的那些话的意思。但对于 Brooks 真正的意思，人们给出了各种不同的 Xs，因此，综合来看，这些 counterarguments 是 self-refuting 的，因为他们认为 Brooks“显然”表达的是某一个具体意思，但如果真有那么明显，人们就不会对 Brooks 的意思有那么多不同的理解。

当然，对于 Brooks 这篇如同 Rorschach test 一般的文章，这种情况不可避免，因为它陈述了各种不同且 contradictory 的事情。

2.  奇怪的是，他在同一篇文章中还声称，在十年之内，任何 individual improvement 都不能 yield 10x improvement。虽然严格说来，这并不 contradict 他的 Ahmdal's law argument 加上“most”（即至少一半）的 complexity 是 essential/conceptual 这一 claim，但不清楚他为什么还要加上这一 claim。

3.  这里我们看到的另一个问题，是 Brooks 坚持在 categories 之间划出 bright-line distinctions。Essential vs. accidental complexity。solutions 的“Types”，比如 languages 与“build vs. buy”等等。

    Brooks 承认，“build vs. buy”是 attack essential complexity 的一条途径。也许他会同意，buying 一个 regexp package 会 reduce essential complexity，因为对于 simple tasks，这能让我不必把所有与 writing a parser 相关的 concepts 都记在脑子里。但如果我不是 buying regexes，而是使用一种将它们 bundled into standard library、或者以其他方式随 language distributed 的 language，又会怎样？又或者，如果我不必 write 自己的 concurrency primitives，而是它们已经 bundled into language，又会怎样？再进一步说，[一整个 HTTP server](https://golang.org/pkg/net/http/) 又如何？一个人可以“buy”的 library（如今在很多情况下是免费的）中的东西，与 bundled into language 的 library 中的东西之间，并没有 bright-line distinction，因此，language 提供的 gains 与可以“bought”的 gains 之间，也不可能存在 bright-line distinction。但如果这里不存在 bright-line distinction，那么就不可能一边说其中一个能 reduce essential complexity、另一个不能，一边又在 essential 和 accidental complexity 之间维持 bright-line distinction（在对 Brooks 的回应中，Harel 曾 argued，不存在 clear distinction，而 Brooks 的回应则是说，事实上确实存在 bright-line distinction，尽管他没有提供新的 argument）。

    Brooks 反复坚持这些 false distinctions，意味着文章中的 reasoning 并不是 composable 的。正如我们已经在另一条脚注中看到的，如果你把文章某一部分的 reasoning 拿出来，与文章另一部分的 reasoning 一起 apply，就很容易产生荒谬的 outcomes，有时甚至会出现直接的 contradictions。

## 原文

In the classic 1986 essay, [No Silver Bullet](http://worrydream.com/refs/Brooks-NoSilverBullet.pdf), Fred Brooks argued that there is, in some sense, not that much that can be done to improve programmer productivity. His line of reasoning is that programming tasks contain a core of essential/conceptual[1](https://danluu.com/essential-complexity/#fn:C) complexity that's fundamentally not amenable to attack by any potential advances in technology (such as languages or tooling). He then uses an [Ahmdahl's law](https://en.wikipedia.org/wiki/Amdahl%27s_law) argument, saying that because 1/X of complexity is essential, it's impossible to ever get more than a factor of X improvement via technological improvements.

Towards the end of the essay, Brooks claims that at least 1/2 (most) of complexity in programming is essential, bounding the potential improvement remaining for all technological programming innovations combined to, at most, a factor of 2[2](https://danluu.com/essential-complexity/#fn:T):

> All of the technological attacks on the accidents of the software process are fundamentally limited by the productivity equation:
> 
> Time of task = Sum over i { Frequency\_i Time\_i }
> 
> If, as I believe, the conceptual components of the task are now taking most of the time, then no amount of activity on the task components that are merely the expression of the concepts can give large productivity gains.

Brooks states a bound on how much programmer productivity can improve. But, in practice, to state this bound correctly, one would have to be able to conceive of problems that no one would reasonably attempt to solve due to the amount of friction involved in solving the problem with current technologies.

Without being able to predict the future, this is impossible to estimate. If we knew the future, it might turn out that there's some practical limit on how much computational power or storage programmers can productively use, bounding the resources available to a programmer, but getting a bound on the amount of accidental complexity would still require one to correctly reason about how programmers are going to be able to use zillions times more resources than are available today, which is so difficult we might as well call it impossible.

Moreover, for each class of tool that could exist, one would have to effectively anticipate all possible innovations. Brooks' strategy for this was to look at existing categories of tools and state, for each, that they would be ineffective or that they were effective but played out. This was wrong not only because it underestimated gains from classes of tools that didn't exist yet, [weren't yet effective](https://danluu.com/butler-lampson-1999/), or he wasn't familiar with (e.g., he writes off formal methods, but it doesn't even occur to him to mention fuzzers, static analysis tools that don't fully formally verify code, tools like valgrind, etc.) but also because Brooks thought that every class of tool where there was major improvement was played out and it turns out that none of them were. For example, Brooks wrote off programming languages as basically done, just before the rise of "scripting languages" as well as just before GC languages took over the vast majority of programming[3](https://danluu.com/essential-complexity/#fn:L). Although you will occasionally hear statements like this, not many people will volunteer to write a webapp in C because gains from modern languages can't be more than 2x over using a modern language.

Another one Brooks writes off is AI, saying "The techniques used for speech recognition seem to have little in common with those used for image recognition, and both are different from those used in expert systems". But, of course this is no longer true now — neural nets are highly effective for both image recognition and speech recognition. Whether or not they'll be highly effective as a programming tool is to be determined, but a lynchpin of Brooks's argument against AI has been invalidated and it's not a stretch to think that a greatly improved GPT-2 could give significant productivity gains to programmers. Of course, it's not reasonable to expect that Brooks could've foreseen neural nets becoming effective for both speech and image recognition, but that's exactly what makes it unreasonable for Brooks to write off all future advance in AI as well as every other field of computer science.

Brooks also underestimates gains from practices and tooling that enables practices. Just for example, looking at what old school programming gurus advocated, we have [Ken Thompson arguing that language safety is useless](https://twitter.com/danluu/status/885214004649615360) and that bugs happen because people write fragile code, which they should not do if they don't want to have bugs and [Jamie Zawinski arguing that, when on a tight deadline, automated testing is a waste of time and "there’s a lot to be said for just getting it right the first time" without testing](https://mastodon.social/@danluu/110213164472670607). Brooks acknowledges the importance of testing, but the only possible improvement to testing that he mentions are expert systems that could make testing easier for beginners. If you look at the complexity of moderately large scale modern software projects, they're well beyond any software project that had been seen in the 80s. If you really think about what it would mean to approach these projects using old school correctness practices, I think the speedup from those sorts of practices to modern practices is infinite for a typical team since most teams using those practices would fail to produce a working product at all if presented with a problem that many big companies have independently solved, e.g., produce a distributed database with some stated SLO. Someone could dispute the infinite speedup claim, but anyone who's worked on a complex project that's serious about correctness will have used [tools and techniques that result in massive development speedups](https://danluu.com/testing/), easily more than 2x compared to 80s practices, a possibility that didn't seem to occur to Brooks as it appears that Brooks thought that serious testing improvements were not possible due to the essential complexity involved in testing.

Another basic tooling/practice example would be version control. A version control system that multi-file commits, branches, automatic merging that generally works as long as devs don't touch the same lines, etc., is a fairly modern invention. [During the 90s, Microsoft was at the cutting edge of software development and they didn't manage to get a version control system that supported the repo size they needed (30M LOC for Win2k development) and supported branches until after Win2k](https://danluu.com/microsoft-culture/). Branches were simulated by simply copying the entire source tree and then manually attempting to merge copies of the source tree. Special approval was required to change the source tree and, due to the pain of manual merging, the entire Win2k team (5000 people, including 1400 devs and 1700 testers) could only merge 100 changes per day on a good day (0 on a bad day when the build team got stalled due to time spent fixing build breaks). This was a decade after Brooks was writing and there was still easily an order of magnitude speedup available from better version control tooling, test tooling and practices, machine speedups allowing faster testing, etc. Note that, in addition to not realizing that version control and test tooling would later result in massive productivity gains, Brooks claimed that hardware speedups wouldn't make developers significantly more productive even though hardware speed was noted to be a major limiting factor in Win2k development velocity. Brooks couldn't conceive of anyone building a project as complex as Win2k, which could really utilize faster hardware. Of course, using the tools and practices of Brooks's time, it was practically impossible to build as project as complex as Win2k, but tools and practices advanced so quickly that it was possible only a decade later even if development velocity moved in slow motion compared to what we're used to today due to "stone age" tools and practices.

To pick another sub-part of the above, Brooks didn't list CI/CD as a potential productivity improvement because Brooks couldn't even imagine ever having tools that could possibly enable modern build practices. Writing in 1995, Brooks mentions that someone from Microsoft told him that they build nightly. To that, Brooks says that it may be too much work to enable building (at least) once a day, noting that Bell Northern Research, quite reasonably, builds weekly. Shortly after Brooks wrote that, Google was founded and engineers at Google couldn't even imagine settling for a setup like Microsoft had, let alone building once a week. They had to build a lot of custom software to get a monorepo of Google's scale on to what would be considered modern practices today, but they were able to do it. A startup that I worked for that was founded in 1995 also built out its own CI infra that allowed for constant merging and building from HEAD because that's what anyone who was looking at what could be done instead of thinking that everything that could be done has been done would do. For large projects, just having CI/CD alone and maintaining a clean build over building weekly should easily be a 2x productivity improvement, large than would be possible if Brooks's claim that half of complexity was essential would allow for. It's good that engineers at Google, the startup I worked for, as well as many other places didn't believe that it wasn't possible to get a 2x improvement and actually built tools that enabled massive productivity improvements.

In some sense, looking at No Silver Bullet is quite similar to when [we looked at Unix and found the Unix mavens saying that we should write software like they did in the 70s](https://danluu.com/cli-complexity/#maven) and that [the languages they invented are as safe as any language can be](https://twitter.com/danluu/status/885214004649615360). Long before computers were invented, elders have been telling the next generation that they've done everything that there is to be done and that the next generation won't be able to achieve more. In the computer age, we've seen countless similar predictions outside of programming as well, such as Cliff Stoll's now-infamous prediction that the internet wouldn't chagne anything:

> Visionaries see a future of telecommuting workers, interactive libraries and multimedia classrooms. They speak of electronic town meetings and virtual communities. Commerce and business will shift from offices and malls to networks and modems. And the freedom of digital networks will make government more democratic.
> 
> Baloney. Do our computer pundits lack all common sense? The truth is no online database will replace your daily newspaper ... How about electronic publishing? Try reading a book on disc. At best, it's an unpleasant chore: the myopic glow of a clunky computer replaces the friendly pages of a book. And you can't tote that laptop to the beach. Yet Nicholas Negroponte, director of the MIT Media Lab, predicts that we'll soon buy books and newspapers straight over the Intenet. Uh, sure. ... Then there's cyberbusiness. We're promised instant catalog shopping—just point and click for great deals. We'll order airline tickets over the network, make restaurant reservations and negotiate sales contracts. Stores will become obselete. So how come my local mall does more business in an afternoon than the entire Internet handles in a month?

If you do a little search and replace, Stoll is saying the same thing Brooks did. Sure, technologies changed things in the past, but I can't imagine how new technologies would change things, so they simply won't.

Even without knowing any specifics about programming, we would be able to see that these kinds of arguments have not historically help up and have decent confidence that the elders are not, in fact, correct this time.

Brooks kept writing about software for quite a while after he was a practitioner, but didn't bother to keep up with what was happening in industry after moving into Academia in 1964, which is already obvious from the 1986 essay we looked at, but even more obvious if you look at his 2010 book, Design of Design, where he relies on [the same examples he relied on in earlier essays and books](https://www.patreon.com/posts/46629220), where the bulk of his new material comes from a house that he built. We've seen that [programmers who try to generalize their knowledge to civil engineering generally make silly statements that any 2nd year civil engineering student can observe are false](https://danluu.com/cocktail-ideas/), and it turns out that trying to glean deep insights about software engineering design techniques from house building techniques doesn't work any better, but since Brooks didn't keep up with the industry, that's what he had to offer. While there are timeless insights that transcend era and industry, Brooks has very specific suggestions, e.g., running software teams like [cocktail party](https://danluu.com/cocktail-ideas/) surgical teams, which come from thinking about how one could improve on the development practices Brooks saw at IBM in the 50s. But it turns out the industry has moved well beyond IBM's 1950s software practices and ideas that are improvements over what IBM did in the 1950s aren't particularly useful 70 years later.

Going back to the main topic of this post and looking at the specifics of what he talks about with respect to accidental complexity with the benefit of hindsight, we can see that Brooks' 1986 claim that we've basically captured all the productivity gains high-level languages can provide isn't too different from an assembly language programmer saying the same thing in 1955, thinking that assembly is as good as any language can be[4](https://danluu.com/essential-complexity/#fn:A) and that his claims about other categories are similar. The main thing these claims demonstrate are a lack of imagination. When Brooks referred to conceptual complexity, he was referring to complexity of using the conceptual building blocks that Brooks was familiar with in 1986 (on problems that Brooks would've thought of as programming problems). There's no reason anyone should think that Brooks' 1986 conception of programming is fundamental any more than they should think that how an assembly programmer from 1955 thought was fundamental. People often make fun of the apocryphal "640k should be enough for anybody" quote, but Brooks saying that, across all categories of potential productivity improvement, we've done most of what's possible to do, is analogous and not apocryphal!

If we look at the future, the fraction of complexity that might be accidental is effectively unbounded. One might argue that, if we look at the present, these terms wouldn't be meaningless. But, while this will vary by domain, I've personally never worked on a non-trivial problem that isn't completely dominated by accidental complexity, making the concept of essential complexity meaningless on any problem I've worked on that's worth discussing.

### Appendix: concrete problems

Let's see how this essential complexity claim holds for a couple of things I did recently at work:

-   scp from a bunch of hosts to read and download logs, and then parse the logs to understand the scope of a problem
-   Query two years of metrics data from every instance of every piece of software my employer has, for some classes of software and then generate a variety of plots that let me understand some questions I have about what our software is doing and how it's using computer resources

#### Logs

If we break this task down, we have

-   scp logs from a few hundred thousand machines to a local box
    -   used a Python script for this to get parallelism with more robust error handling than you'd get out of pssh/parallel-scp
    -   ~1 minute to write the script
-   do other work while logs download
-   parse downloaded logs (a few TB)
    -   used a Rust script for this, a few minutes to write (used Rust instead of Python for performance reasons here — just opening the logs and scanning each line with idiomatic Python was already slower than I'd want if I didn't want to farm the task out to multiple machines)

In 1986, perhaps I would have used telnet or ftp instead of scp. Modern scripting languages didn't exist yet (perl was created in 1987 and perl5, the first version that some argue is modern, was released in 1994), so writing code that would do this with parallelism and "good enough" error handling would have taken more than an order of magnitude more time than it takes today. In fact, I think just getting semi-decent error handling while managing a connection pool could have easily taken an order of magnitude longer than this entire task took me (not including time spent downloading logs in the background).

Next up would be parsing the logs. It's not fair to compare an absolute number like "1 TB", so let's just call this "enough that we care about performance" (we'll talk about scale in more detail in the metrics example). Today, we have our choice of high-performance languages where it's easy to write, fast, safe code and harness the power of libraries (e.g., a regexp library[5](https://danluu.com/essential-complexity/#fn:B)) that make it easy to write a quick and dirty script to parse and classify logs, farming out the work to all of the cores on my computer (I think Zig would've also made this easy, but I used Rust because my team has a critical mass of Rust programmers).

In 1986, there would have been no comparable language, but more importantly, I wouldn't have been able to trivially find, download, and compile the appropriate libraries and would've had to write all of the parsing code by hand, turning a task that took a few minutes into a task that I'd be lucky to get done in an hour. Also, if I didn't know how to use the library or that I could use a library, I could easily find out how I should solve the problem on StackOverflow, which would massively reduce accidental complexity. Needless to say, there was no real equivalent to Googling for StackOverflow solutions in 1986.

Moreover, even today, this task, a pretty standard programmer devops/SRE task, after at least an order of magnitude speedup over the analogous task in 1986, is still nearly entirely accidental complexity.

If the data were exported into our metrics stack or if our centralized logging worked a bit differently, the entire task would be trivial. And if neither of those were true, but the log format were more uniform, I wouldn't have had to write any code after getting the logs; [rg](https://github.com/BurntSushi/ripgrep) or [ag](https://github.com/ggreer/the_silver_searcher) would have been sufficient. If I look for how much time I spent on the essential conceptual core of the task, it's so small that it's hard to estimate.

#### Query metrics

We really only need one counter-example, but I think it's illustrative to look at a more complex task to see how Brooks' argument scales for a more involved task. If you'd like to skip this lengthy example, [click here to skip to the next section](https://danluu.com/essential-complexity/#summary).

We can view my metrics querying task as being made up of the following sub-tasks:

-   Write a set of [Presto SQL](https://en.wikipedia.org/wiki/Presto_\(SQL_query_engine\)) queries that effectively scan on the order of 100 TB of data each, from a data set that would be on the order of 100 PB of data if I didn't [maintain tables that only contain a subset of data that's relevant](https://danluu.com/metrics-analytics/)
    -   Maybe 30 seconds to write the first query and a few minutes for queries to finish, using on the order of 1 CPU-year of CPU time
-   Write some ggplot code to plot the various properties that I'm curious about
    -   Not sure how long this took; less time than the queries took to complete, so this didn't add to the total time of this task

The first of these tasks is so many orders of magnitude quicker to accomplish today that I'm not even able to hazard a guess to as to how much quicker it is today within one or two orders of magnitude, but let's break down the first task into component parts to get some idea about the ways in which the task has gotten easier.

It's not fair to port absolute numbers like 100 PB into 1986, but just the idea of having a pipeline that collects and persists comprehensive data analogous to the data I was looking at for a consumer software company (various data on the resource usage and efficiency of our software) would have been considered absurd in 1986. Here we see one fatal flaw in the concept of accidental essential complexity providing an upper bound on productivity improvements: tasks with too much accidental complexity wouldn't have even been considered possible. The limit on how much accidental complexity Brooks sees is really a limit of his imagination, not something fundamental.

Brooks explicitly dismisses increased computational power as something that will not improve productivity ("Well, how many MIPS can one use fruitfully?", more on this later), but both storage and CPU power (not to mention network speed and RAM) were sources of accidental complexity so large that they bounded the space of problems Brooks was able to conceive of.

In this example, let's say that we somehow had enough storage to keep the data we want to query in 1986. The next part would be to marshall on the order of 1 CPU-year worth of resources and have the query complete in minutes. As with the storage problem, this would have also been absurd in 1986[6](https://danluu.com/essential-complexity/#fn:F), so we've run into a second piece of non-essential complexity so large that it would stop a person from 1986 from thinking of this problem at all.

Next up would be writing the query. If I were writing for the Cray-2 and wanted to be productive, I probably would have written the queries in Cray's dialect of Fortran 77. Could I do that in less than 300 seconds per query? Not a chance; I couldn't even come close with Scala/Scalding and I think it would be a near thing even with Python/PySpark. This is the aspect where I think we see the smallest gain and we're still well above one order of magnitude here.

After we have the data processed, we have to generate the plots. Even with today's technology, I think not using ggplot would cost me at least 2x in terms of productivity. I've tried every major plotting library that's supposedly equivalent (in any language) and every library I've tried either has multiple show-stopping bugs rendering plots that I consider to be basic in ggplot or is so low-level that I lose more than 2x productivity by being forced to do stuff manually that would be trivial in ggplot. In 2020, the existence of a single library already saves me 2x on this one step. If we go back to 1986, before the concept of [the grammar of graphics](https://amzn.to/3r9Mvzw) and any reasonable implementation, there's no way that I wouldn't lose at least two orders of magnitude of time on plotting even assuming some magical workstation hardware that was capable of doing the plotting operations I do in a reasonable amount of time (my machine is painfully slow at rendering the plots; a Cray-2 would not be able to do the rendering in anything resembling a reasonable timeframe).

The number of orders of magnitude of accidental complexity reduction for this problem from 1986 to today is so large I can't even estimate it and yet this problem still contains such a large fraction of accidental complexity that it's once again difficult to even guess at what fraction of complexity is essential. To write it all down all of the accidental complexity I can think of would require at least 20k words, but just to provide a bit of the flavor of the complexity, let me write down a few things.

-   SQL; this is one of those things that's superficially simple [but actually extremely complex](https://scattered-thoughts.net/writing/select-wat-from-sql/)
    -   Also, Presto SQL
-   Arbitrary Presto limits, some of which are from Presto and some of which are from the specific ways we operate Presto and the version we're using
    -   There's an internal Presto data structure assert fail that gets triggered when I use both `numeric_histogram` and `cross join unnest` in a particular way. Because it's a waste of time to write the bug-exposing query, wait for it to fail, and then re-write it, I have a mental heuristic I use to guess, for any query that uses both constructs, whether or not I'll hit the bug and I apply it to avoid having to write two queries. If the heuristic applies, I'll instead write a more verbose query that's slower to execute instead of the more straightforward query
    -   We partition data by date, but Presto throws this away when I join tables, resulting in very large and therefore expensive joins when I join data across a long period of time even though, in principle, this could be a series of cheap joins; if the join is large enough to cause my query to blow up, I'll write what's essentially a little query compiler to execute day-by-day queries and then post-process the data as necessary instead of writing the naive query
        -   There are a bunch of cases where some kind of optimization in the query will make the query feasible without having to break the query across days (e.g., if I want to join host-level metrics data with the table that contains what cluster a host is in, that's a very slow join across years of data, but I also know what kinds of hosts are in which clusters, which, in some cases, lets me filter hosts out of the host-level metrics data that's in there, like core count and total memory, which can make the larger input to this join small enough that the query can succeed without manually partitioning the query)
    -   We have a Presto cluster that's "fast" but has "low" memory limits a cluster that's "slow" but has "high" memory limits, so I mentally estimate how much per-node memory a query will need so that I can schedule it to the right cluster
    -   etc.
-   When, for performance reasons, I should compute the CDF or histogram in Presto vs. leaving it to the end for ggplot to compute
-   How much I need to downsample the data, if at all, for ggplot to be able to handle it, and how that may impact analyses
-   Arbitrary ggplot stuff
    -   roughly how many points I need to put in a scatterplot before I should stop using `size = [number]` and should switch to single-pixel plotting because plotting points as circles is too slow
    -   what the minimum allowable opacity for points is
    -   If I exceed the maximum density where you can see a gradient in a scatterplot due to this limit, how large I need to make the image to reduce the density appropriately (when I would do this instead of using a heatmap deserves its own post)
    -   etc.
-   All of the above is about tools that I use to write and examine queries, but there's also the mental model of all of the data issues that must be taken into account when writing the query in order to generate a valid result, which includes things like clock skew, Linux accounting bugs, issues with our metrics pipeline, issues with data due to problems in the underlying data sources, etc.
-   etc.

For each of Presto and ggplot I implicitly hold over a hundred things in my head to be able to get my queries and plots to work and I choose to use these because these are the lowest overhead tools that I know of that are available to me. If someone asked me to name the percentage of complexity I had to deal with that was essential, I'd say that it was so low that there's no way to even estimate it. For some queries, it's arguably zero — my work was necessary only because of some arbitrary quirk and there would be no work to do without the quirk. But even in cases where some kind of query seems necessary, I think it's unbelievable that essential complexity could have been more than 1% of the complexity I had to deal with.

Revisiting Brooks on computer performance, even though I deal with complexity due to the limitations of hardware performance in 2020 and would love to have faster computers today, Brooks wrote off faster hardware as pretty much not improving developer productivity in 1986:

> What gains are to be expected for the software art from the certain and rapid increase in the power and memory capacity of the individual workstation? Well, how many MIPS can one use fruitfully? The composition and editing of programs and documents is fully supported by today’s speeds. Compiling could stand a boost, but a factor of 10 in machine speed would surely . . .

But this is wrong on at least two levels. First, if I had access to faster computers, a huge amount of my accidental complexity would go away (if computers were powerful enough, I wouldn't need complex tools like Presto; I could just run a query on my local computer). We have much faster computers now, but it's still true that having faster computers would make many involved engineering tasks trivial. As James Hague notes, in the mid-80s, [writing a spellchecker was a serious engineering problem due to performance constraints](https://prog21.dadgum.com/29.html).

Second, (just for example) ggplot only exists because computers are so fast. A common complaint from people who work on performance is that tool X has somewhere between two and ten orders of magnitude of inefficiency when you look at the fundamental operations it does vs. the speed of hardware today[7](https://danluu.com/essential-complexity/#fn:O). But what fraction of programmers can realize even one half of the potential performance of a modern multi-socket machine? I would guess fewer than one in a thousand and I would say certainly fewer than one in a hundred. And performance knowledge isn't independent of other knowledge — controlling for age and experience, it's negatively correlated with knowledge of non-"systems" domains since time spent learning about the esoteric accidental complexity necessary to realize half of the potential of a computer is time spent not learning about "directly" applicable domain knowledge. When we look software that requires a significant amount of domain knowledge (e.g., ggplot) or that's large enough that it requires a large team to implement (e.g., IntelliJ[8](https://danluu.com/essential-complexity/#fn:V)), the vast majority of it wouldn't exist if machines were orders of magnitude slower and writing usable software required wringing most of the performance out of the machine. Luckily for us, hardware has gotten much faster, allowing the vast majority of developers to ignore performance-related accidental complexity and instead focus on all of the other accidental complexity necessary to be productive today.

Faster computers both reduce the amount of accidental complexity tool users run into as well as the amount of accidental complexity that tool creators need to deal with, allowing more productive tools to come into existence.

### 2022 Update

A lot of people have said that this post is wrong because Brooks was obviously saying X and Brooks did not mean the things I quoted in this post. But people state all sorts of different Xs for what Brooks really meant so, in aggregate, these counterarguments are self-refuting because they think that Brooks "obviously" meant one specific thing but, if it were so obvious, people wouldn't have so many different ideas of what Brooks meant.

This is, of course, inevitable when it comes to a Rorschach test essay like Brooks's essay, which states a wide variety of different and contradictory things.

2.  Curiously, he also claims, in the same essay, that no individual improvement can yield a 10x improvement within one decade. While this technically doesn't contradict his Ahmdal's law argument plus the claim that "most" (i.e., at least half) of complexity is essential/conceptual, it's unclear why he would include this claim as well.

    When Brooks revisited his essay in 1995 in No Silver Bullet Refired, he claimed that he was correct by using the weakest form of the three claims he made in 1986, that within one decade, no single improvement would result in an order of magnitude improvement. However, he did then re-state the strongest form of the claim he made in 1986 and made it again in 1995, saying that this time, no set of technological improvements could improve productivity more than 2x, for real:

    > It is my opinion, and that is all, that the accidental or representational part of the work is now down to about half or less of the total. Since this fraction is a question of fact, its value could in principle be settled by measurement. Failing that, my estimate of it can be corrected by better informed and more current estimates. Significantly, no one who has written publicly or privately has asserted that the accidental part is as large as 9/10.

    By the way, I find it interesting that he says that no one disputed this 9/10ths figure. Per the body of this post, I would put it at far above 9/10th for my day-to-day work and, if I were to try to solve the same problems in 1986, the fraction would have been so high that people wouldn't have even conceived of the problem. As a side effect of having worked in hardware for a decade, I've also done work that's not too different from what some people faced in 1986 (microcode, assembly & C written for DOS) and I would put that work as easily above 9/10th as well.

    Another part of his follow-up that I find interesting is that he quotes Harel's "Biting the Silver Bullet" from 1992, which, among other things, argues that that decade deadline for an order of magnitude improvement is arbitrary. Brooks' response to this is

    > There are other reasons for the decade limit: the claims made for candidate bullets all have had a certain immediacy about them . . . We will surely make substantial progress over the next 40 years; an order of magnitude over 40 years is hardly magical.

    But by Brooks' own words when he revisits the argument in 1995, if 9/10th of complexity is essential, it would be impossible to get more than an order of magnitude improvement from reducing it, with no caveat on the timespan:

    > "NSB" argues, indisputably, that if the accidental part of the work is less than 9/10 of the total, shrinking it to zero (which would take magic) will not give an order of magnitude productivity improvement.

    Both his original essay and the 1995 follow-up are charismatically written and contain a sort of local logic, where each piece of the essay sounds somewhat reasonable if you don't think about it too hard and you forget everything else the essay says. As with the original, a pedant could argue that this is technically not incoherent — after all, Brooks could be saying:

    -   at most 9/10th of complexity is accidental (if we ignore the later 1/2 claim, which is the kind of suspension of memory/disbelief one must do to read the essay)
    -   it would not be surprising for us to eliminate 100% of accidental complexity after 40 years

    While this is technically consistent (again, if we ignore the part that's inconsistent) and is a set of claims one could make, this would imply that 40 years from 1986, i.e., in 2026, it wouldn't be implausible for there to be literally zero room for any sort of productivity improvement from tooling, languages, or any other potential source of improvement. But this is absurd. If we look at other sections of Brooks' essay and combine their reasoning, we see other inconsistencies and absurdities.

    [\[return\]](https://danluu.com/essential-complexity/#fnref:T)
3.  Another issue that we see here is Brooks' insistence on bright-line distinctions between categories. Essential vs. accidental complexity. "Types" of solutions, such as languages vs. "build vs. buy", etc.

    Brooks admits that "build vs. buy" is one avenue of attack on essential complexity. Perhaps he would agree that buying a regexp package would reduce the essential complexity since that would allow me to avoid keeping all of the concepts associated with writing a parser in my head for simple tasks. But what if, instead of buying regexes, I used a language where they're bundled into the standard library or is otherwise distributed with the language? Or what if, instead of having to write my own concurrency primitives, those are bundled into the language? Or for that matter, what about [an entire HTTP server](https://golang.org/pkg/net/http/)? There is no bright-line distinction between what's in a library one can "buy" (for free in many cases nowadays) and one that's bundled into the language, so there cannot be a bright-line distinction between what gains a language provides and what gains can be "bought". But if there's no bright-line distinction here, then it's not possible to say that one of these can reduce essential complexity and the other can't and maintain a bright-line distinction between essential and accidental complexity (in a response to Brooks, Harel argued against there being a clear distinction in a response, and Brooks' response was to say that there there is, in fact, a bright-line distinction, although he provided no new argument).

    Brooks' repeated insistence on these false distinctions means that the reasoning in the essay isn't composable. As we've already seen in another footnote, if you take reasoning from one part of the essay and apply it alongside reasoning from another part of the essay, it's easy to create absurd outcomes and sometimes outright contradictions.

    I suspect this is one reason discussions about essential vs. accidental complexity are so muddled. It's not just that [Brooks is being vague and handwave-y](https://twitter.com/hillelogram/status/1211433465956196352), he's actually not self-consistent, so there isn't and cannot be a coherent takeaway. Michael Feathers has noted [that people are generally not able to correct identify essential complexity](https://twitter.com/mfeathers/status/1259295515532865543); as he says, [One person’s essential complexity is another person’s accidental complexity.](https://twitter.com/mfeathers/status/1256995176959971329). This is exactly what we should expect from the essay, since people who have different parts of it in mind will end up with incompatible views.

    This is also a problem when criticizing Brooks. Inevitably, someone will say that what Brooks really meant was something completely different. And that will be true. But Brooks will have meant something completely different while also having meant the things he said that I mention. In defense of the view I'm presenting in the body of the text here, it's a coherent view that one could have had in 1986. Many of Brooks' statements don't make sense even when considered as standalone statements, let alone when cross-referenced with the rest of his essay. For example, the statement that no single development will result in an order of magnitude improvement in the next decade. This statement is meaningless as Brooks does not define and no one can definitively say what a "single improvement" is. And, as mentioned above, Brooks' essay reads quite oddly and basically does not make sense if that's what he's trying to claim. Another issue with most other readings of Brooks is that those are positions that are also meaningless even if Brooks had done the work to make them well defined. Why does it matter if one single improvement or two result in an order of magnitude improvement. If it's two improvements, we'll use them both.
