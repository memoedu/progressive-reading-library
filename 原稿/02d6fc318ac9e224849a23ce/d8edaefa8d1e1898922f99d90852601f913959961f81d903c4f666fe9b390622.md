## 引言

很多人第一次把 AI 用到论文写作里，是从网页版 ChatGPT 开始的：把 Overleaf 里的一段文字复制出来，粘贴到对话框里，让它润色、翻译、解释公式，然后再把结果粘贴回论文。

这种方式当然有用。临时问一个概念、改一小段英文、翻译摘要、解释一个公式，它都很方便。但如果你正在写一篇真正的数学、统计或数值分析论文，只靠这种复制粘贴式对话，很快会遇到瓶颈。

原因很简单：论文不是一个孤立文本框，而是一个项目。

一个常见的 LaTeX 论文项目里，可能有 `main.tex`、多个章节文件、`references.bib`、图片、表格、宏定义和自定义命令。网页版 ChatGPT 通常只能看到你粘贴给它的那一小段内容。它不知道你的章节如何组织，不知道前文符号怎么定义，也不能直接检查多个文件之间的引用关系。

更麻烦的是，大改之后你很难追踪它到底改了哪里。它给出的结果也许看起来顺，但是否改动了不该改的 citation key、是否引入了不一致的术语、是否破坏了原来的 LaTeX 结构，最后仍然要你自己一点点检查。

所以本文想介绍的不是“怎么让 AI 替你写论文”，而是一种更适合科研写作的线性工作流：

-   Overleaf 负责编译和预览；
-   Git 负责同步、版本管理和回退；
-   VS Code 作为本地项目入口；
-   Codex 负责本地 Agent 辅助修改。

这个工作流的核心矛盾是：我们不想在本地配置 LaTeX 编译环境，但又希望 AI 能直接读取和修改论文项目，同时还要保留 Overleaf 的在线编译和预览能力。

解决办法就是：在 Overleaf 和 Codex 之间加上一层 Git。

![](https://pica.zhimg.com/v2-1face26a5bf396f9e97aff04222b858e_1440w.jpg)

网页版 ChatGPT 与 Agent 工作流对比图

这里需要说明：现在的 Overleaf 里 Git 集成属于 Premium 功能，免费版默认不能使用。如果你的 Overleaf 中包含了Git集成，就可以很方便的使用这个工作流

还需要先说清楚：Codex 这类 Agent 可以读取项目、修改文件、总结变更，但它不能替代作者判断。数学论证是否成立、符号是否合适、表述是否过度，最终仍然由作者负责。AI 在这里是辅助修改工具，不是科研判断的替代品。

## 第 0 部分：准备账号和模型

开始搭建工作流之前，先明确一件事：本文默认使用 Codex 辅助修改本地论文项目。不同平台、不同客户端、不同模型对 Agent 能力的支持并不完全相同，所以账号和模型会影响实际体验。

如果你希望尽量顺利地复现本文的 Codex + Git + Overleaf 工作流，ChatGPT Plus 是更直接的选择。Plus目前最划算的订阅方法是土区apple账号，Pro目前最划算的是美区账号。这里不建议使用来源不明的共享账号。论文项目里可能包含未发表内容、作者信息、实验数据、私有路径和项目链接，账号来源不可靠会带来额外风险。

如果预算有限，也可以考虑 DeepSeek V4 Pro 这类替代方案。它更适合做中文内容整理、普通代码辅助和轻量文本修改。DeepSeek现在有着极低的价格、极高的缓存命中率，不用省吃俭用，站起来蹬也没事。

后文默认读者使用 Windows、VS Code、Git、Overleaf Git 功能、Codex 和 ChatGPT Plus。如果你的系统或客户端不同，整体思想仍然可以参考，但具体入口和界面可能会有差异。

## 第一部分：先看整体架构

在真正开始敲命令之前，先不要急着操作。这套工作流可以先记成一句话：

Overleaf 负责编译和预览，Git 负责同步和版本管理，VS Code 是本地项目入口，Codex 负责在本地辅助修改论文文件。

完整闭环如下：

1.  论文项目最初放在 Overleaf 上。
2.  使用 `git clone` 或 `git pull` 把 Overleaf 项目同步到本地。
3.  用 VS Code 打开本地 Git 仓库。
4.  让 Codex 阅读和修改本地 LaTeX 文件。
5.  使用 `git diff` 检查 Codex 到底改了什么。
6.  确认修改没有问题后，使用 `git add` 和 `git commit` 记录这次修改。
7.  使用 `git push` 把本地提交推送回 Overleaf。
8.  回到 Overleaf 在线编译和预览 PDF。

![](https://pic1.zhimg.com/v2-a21d320dfe76b76ac1e1f6e518a35472_1440w.jpg)

这套流程的重点不是多用几个工具，而是让每一步都有清楚的责任。

Overleaf 仍然是论文编译和预览的平台。本文不要求你在本地配置 LaTeX，也不要求你先解决 TeX Live、宏包、字体和编译链问题。Overleaf 负责在线编译、PDF 预览、最终排版检查，以及必要时和导师或合作者协作。

Git 的作用也不复杂：同步项目、记录修改、方便回退。对新手来说，先不要急着学复杂分支。这里先只使用最简单的线性流程。Git 负责把 Overleaf 项目同步到本地，记录每一轮修改，让你知道 Codex 改了哪些文件，并把本地修改推送回 Overleaf。

VS Code 是本地项目入口。你用它打开从 Overleaf 同步下来的论文仓库，查看 `main.tex`、章节文件、图片文件夹和参考文献文件，也可以通过 Source Control 面板查看哪些文件发生了变化。

Codex 则负责 Agent 辅助修改。它可以阅读 `main.tex`，理解文章如何组织章节，找到某一节对应的 `.tex` 文件，并按你的要求修改指定段落。它也适合做术语统一、局部重写、章节草稿生成和 LaTeX 报错修复。

但是，Codex 不应该被当成“自动写论文机器”。你要给它明确边界：只修改哪个文件、只改哪一节、保持哪些符号、不要改 citation key、不要新增没有来源的参考文献、修改后总结改动。Codex 负责执行修改，作者负责判断和验收。

这一部分先记住几个命令的角色即可。

`git clone` 的作用是第一次把 Overleaf 项目下载到本地，通常只在搭建项目时做一次。

`git pull` 的作用是把 Overleaf 远程仓库中的最新修改同步到本地，确保本地项目是最新版本。每一轮本地修改前，都建议先执行这一步。

`git diff` 的作用是查看本地文件发生了哪些逐行变化。它是检查 Codex 修改内容的核心步骤，不能省。

`git add` 的作用是把确认无误的修改加入下一次提交。可以理解为：这些修改我检查过了，准备记录下来。

`git commit` 的作用是记录一次清晰的本地版本。提交信息应该写清楚这次做了什么，例如 `git commit -m "write section 3"`，不要写成 `update`、`final` 或 `111` 这种以后看不懂的 message。

`git push` 的作用是把本地提交推送回 Overleaf。推送完成后，你就可以回到 Overleaf 在线编译和预览。

后文会把这些命令放进完整写作流程里逐条展开。这里可以先试试看git的基本操作，不要急着学习复杂 Git 分支，也不要一开始就配置本地 LaTeX 编译环境。先把最简单的闭环跑通：

1.  从 Overleaf 同步到本地；
2.  用 VS Code 打开项目；
3.  让 Codex 修改指定文件；
4.  用 `git diff` 检查修改；
5.  提交并推送回 Overleaf；
6.  在 Overleaf 编译和预览。

这就是本文后面要详细展开的核心工作流。它的目标不是让你变成 Git 高手，也不是让 AI 替你写论文，而是在不本地配置 LaTeX 编译环境的前提下，建立一个更稳定、更可检查的 Agent 辅助论文写作流程。

## 第二部分：环境搭建

这一部分解决正式写作前的准备问题：本地项目放在哪里，怎样从 Overleaf 下载项目，怎样用 VS Code 打开，怎样准备 `.gitignore` 和 `AGENTS.md`。

### 1\. 创建清晰的科研项目目录

建议不要把所有科研材料都放在桌面或下载文件夹里。桌面适合临时文件，不适合长期维护论文、报告和代码。一个清晰的总目录，可以让后面的 Git、Codex 和 VS Code 都更好工作。

对于单篇论文，可以使用：

-   `paper-name/`

-   `main.tex`
-   `references.bib`
-   `AGENTS.md`
-   `.gitignore`
-   `sections/`

-   `sections/introduction.tex`
-   `sections/method.tex`
-   `sections/numerical.tex`
-   `sections/conclusion.tex`

-   `figures/`
-   `tables/`

这里的 `main.tex` 通常是主文件，`references.bib` 是参考文献文件，`sections/` 存放各章节，`figures/` 和 `tables/` 存放图表材料。

### 2\. 从 Overleaf 获取 Git 地址

Overleaf 项目可以通过 Git 同步到本地。第一次使用时，需要从 Overleaf 页面中找到项目的 Git 地址。

一般步骤是：（这里是USTC latex的面板）

1.  打开你的 Overleaf 项目。
2.  左上角菜单中有 Git 或同步相关入口。
3.  复制项目提供的 Git 地址。
4.  回到本地，选择一个合适的论文目录。
5.  使用 `git clone` 下载项目。

![](https://pic2.zhimg.com/v2-edeb27a6ffee79223c1d8d6e8873518b_1440w.jpg)

`git clone <你的 Overleaf Git 地址>` 的作用是第一次把远程 Overleaf 项目完整下载到本地，形成一个本地 Git 仓库。这个命令通常只需要在项目初始化时执行一次。这时候可能需要生成一次性git密钥。

这里最重要的提醒是：不要在截图、文章或聊天记录中暴露真实 Git 地址。Overleaf Git 地址通常包含私有 token 或项目信息，一旦泄露，就可能暴露你的项目访问入口。

### 3\. 用 VS Code 打开本地项目

项目下载到本地后，用 VS Code 打开这个文件夹。

操作步骤很简单：

1.  打开 VS Code。
2.  选择 `File -> Open Folder`。
3.  打开刚刚下载下来的论文文件夹。
4.  确认左侧资源管理器中能看到 `main.tex`、`references.bib`、`sections/`、`figures/` 等文件。

VS Code 的作用是提供一个本地项目入口。你可以在这里看文件结构、检查修改、使用 Git 插件，也可以让 Codex 在当前项目里工作。

### 4\. 创建 `.gitignore`

`.gitignore` 用来告诉 Git 哪些文件不需要纳入版本管理。

LaTeX 编译会产生很多辅助文件，例如 `.aux`、`.log`、`.out`。这些文件通常不需要提交到 Git，也不需要同步回 Overleaf。

可以先写成这样：

```text
# LaTeX auxiliary files
*.aux
*.log
*.out
*.toc
*.synctex.gz
*.fls
*.fdb_latexmk
*.bbl
*.blg

# System files
.DS_Store
Thumbs.db

# Local editor settings
.vscode/
```

如果项目中有大型实验结果或临时数据，也可以根据实际情况忽略：

```text
*.mat
*.csv
*.rds
*.RData
```

但要注意：论文必须用到的小型图片、重要表格源文件、必须同步到 Overleaf 的材料，不要误加入 `.gitignore`。

### 5\. 创建 `AGENTS.md`

`AGENTS.md` 是给 Codex 的项目说明书。它可以告诉 Agent：这个项目是什么、默认语言是什么、哪些文件可以改、哪些行为不允许。

一个论文项目里的 `AGENTS.md` 可以写清楚：

-   默认用中文回复；
-   保持已有 LaTeX 风格；
-   大规模修改前先给计划；
-   不随意改 citation key；
-   不新增没有来源的参考文献；
-   不在本地编译，除非用户明确要求；
-   修改完成后总结变更。

`AGENTS.md` 的价值在于让 Agent 工作流更稳定。你不需要每次都重新解释所有规则，Codex 进入项目后会先读取这些说明。

### 6\. 推荐安装的 VS Code 插件

建议安装：

-   Git Graph；
-   GitLens；
-   LaTeX Workshop；
-   Codex 插件。

这里非常推荐Git Graph，可以直观看到 commit 历史。GitLens 可以帮助查看文件修改记录。LaTeX Workshop 适合查看 LaTeX 项目结构。Codex 插件用于在本地项目中使用 Agent 辅助修改。

## 第三部分：科研写作工作流

这是全文最重要的一部分。为了避免风险，不推荐一开始就使用功能分支。分支是 Git 的最重要的功能，熟悉 Git 后可以使用；但刚开始时，目标应该是把最简单的线性流程跑通。

新手阶段建议一直在 `main` 分支工作，保持线性历史。一轮完整修改可以概括为：

1.  `git pull`
2.  使用 Codex 的 Plan mode 确认修改方案
3.  Codex 修改文件
4.  `git diff`
5.  `git add .`
6.  `git commit -m "write section 3"`
7.  `git push`
8.  回到 Overleaf 编译和预览

下面逐步说明。

### 1\. 修改前先执行 `git pull`

`git pull` 的作用是把 Overleaf 远程仓库中的最新修改同步到本地，确保本地项目是最新版本。

这一步应该放在每一轮本地修改之前。尤其是你刚刚在 Overleaf 网页端改过内容，或者合作者可能更新过项目时，先 `git pull` 可以减少后面出现版本冲突的概率。

可以把它理解成：开始让 Codex 改论文之前，先把 Overleaf 上的最新版本拿回来。

### 2\. 先用 Plan mode 确认修改方案

不要一上来就让 Codex 直接改 `.tex` 文件。更稳妥的方式是先进入 Plan mode，让 Codex 阅读项目结构、理解 `main.tex` 如何组织章节，并给出修改方案。

Plan mode 适合处理这些问题：

-   要改哪个文件；
-   这次只改哪一节；
-   是否需要先统一符号；
-   是否会影响 citation key；
-   哪些内容需要用户补充；
-   哪些地方不应该让 AI 自己发挥。

例如你要写 Section 3，可以先在 Plan mode 里让 Codex 判断：Section 3 对应哪个 `.tex` 文件，应该分成哪些小节，哪些符号要和前文一致，哪些地方需要你提供数学细节。确认方案后，再切回执行修改的模式，让 Codex 只改指定文件和指定范围。

这样做的目的不是增加流程，而是把“讨论方案”和“实际改文件”分开。论文写作里最怕的是还没想清楚结构，就让 Agent 大范围改动。

### 3\. 让 Codex 修改指定文件

方案确认后，再让 Codex 修改文件。这里一定要说清楚修改范围。

例如：只修改 `sections/method.tex` 中的 Section 3，不要修改其他章节；保持现有 LaTeX 风格；不要改动 citation key；不要新增没有来源的参考文献；修改完成后总结改了哪些地方。

范围越清楚，修改越可控。不要只写“帮我完善论文第三节”，因为这类要求太宽，容易导致 Agent 顺手改动无关内容。

### 4\. 用 `git diff` 检查修改

Codex 修改完成后，不要直接接受。先执行 `git diff`。

`git diff` 的作用是显示当前工作区相对上一次 commit 的变化。你可以看到哪些行被删除、哪些行被新增、哪些地方被重写。这里可以直接再Vscode中查看修改

![](https://pic3.zhimg.com/v2-ad4e7dcd93a0e493d445e10a2d499dfa_1440w.jpg)

点击changes就可以查看修改

重点检查：

-   是否改了不该改的文件；
-   是否删除了重要内容；
-   公式是否正确；
-   citation key 是否仍然存在；
-   是否引入了无法编译的 LaTeX 命令；
-   文字是否符合论文风格。

这一步是整个工作流里最重要的安全阀。AI 修改不是问题，不检查 AI 修改才是问题。

### 5\. 用 `git add .` 暂存确认后的修改

确认修改无误后，执行 `git add .`。

![](https://pic1.zhimg.com/v2-3b7a584354adcb0beeb40112ea94ea80_1440w.jpg)

`git add .` 的作用是把当前目录下的修改加入暂存区，也就是告诉 Git：这些修改我已经检查过，准备进入下一次版本记录。

如果 `git diff` 里发现 Codex 改了不该改的文件，不要急着执行 `git add .`。先让 Codex 按你的要求修正，或者手动处理后再暂存。

需要说明一点，Codex一般可以识别根目录下的.git，可以直接在Codex中提交

![](https://pic4.zhimg.com/v2-33efd13f347711c1557223a15e63d329_1440w.jpg)

但如果不是根目录下的git仓库，Codex一般无法识别，需要手动提交。

### 6\. 用 `git commit` 记录这次修改

暂存完成后，执行 `git commit -m "write section 3"`。

`git commit -m "write section 3"` 的作用是创建一次本地提交，并用 `write section 3` 作为提交说明。

commit message 应该简洁清楚。推荐：

-   `git commit -m "write section 3"`：表示写了第三节；
-   `git commit -m "revise introduction"`：表示修改了引言；
-   `git commit -m "fix latex error"`：表示修复了 LaTeX 错误；
-   `git commit -m "update references"`：表示更新了参考文献。

不推荐：

-   `git commit -m "update"`：太模糊，不知道更新了什么；
-   `git commit -m "final"`：论文通常不会真的 final；
-   `git commit -m "111"`：没有任何信息；
-   `git commit -m "修改"`：过于笼统。

### 7\. 用 `git push` 推送回 Overleaf

提交完成后，执行 `git push`。

`git push` 的作用是把本地 commit 推送到 Overleaf 远程仓库。推送成功后，回到 Overleaf 刷新项目，就能看到本地 Codex 修改后的版本。

然后在 Overleaf 中：

1.  编译项目；
2.  检查 PDF；
3.  检查公式编号、引用、图表和参考文献；
4.  如果编译失败，把报错信息复制给 Codex。

### 8\. 把闭环跑稳定

一轮完整修改最终就是：

1.  `git pull`：把 Overleaf 最新版本同步到本地。
2.  Plan mode：先确认修改方案，不直接改文件。
3.  Codex 修改文件。
4.  `git diff`：检查 Codex 修改了什么。
5.  `git add .`：把确认后的修改加入暂存区。
6.  `git commit -m "write section 3"`：记录一次清晰提交。
7.  `git push`：推送回 Overleaf。
8.  Overleaf 编译和预览。

这一部分只讲一个核心问题：不要同时在本地和 Overleaf 网页端编辑同一个项目。

很多 Git 冲突不是因为 Git 本身难，而是因为同一轮写作里，本地和 Overleaf 两边都在改。比如你在本地让 Codex 修改 `main.tex`，同时又在 Overleaf 网页端修改同一个 `main.tex`。这时本地版本和远程版本都会前进。

等你执行 `git push` 时，Git 会发现 Overleaf 上已经有了你本地没有的修改。这里的 `git push` 是把本地 commit 推送到远程 Overleaf 项目的命令；当远程已经先变化时，它可能会被拒绝。

如果你接着执行 `git pull`，Git 需要把远程 Overleaf 的修改同步到本地。如果两边改了同一文件的同一部分，就可能出现 merge conflict。

### 1\. 正确习惯：同一轮只在一边改

每一轮写作前，先决定这一轮在哪里改。

如果这一轮用 Codex 本地修改，就不要在 Overleaf 网页端编辑。推荐顺序是：

1.  先停止在 Overleaf 网页端编辑；
2.  执行 `git pull`，把 Overleaf 最新版本同步到本地；
3.  使用 Plan mode 确认修改方案；
4.  让 Codex 修改指定文件；
5.  执行 `git diff` 检查本地改动；
6.  执行 `git add .` 暂存确认后的修改；
7.  执行 `git commit -m "clear commit message"` 记录一次本地提交；
8.  执行 `git push` 把本地提交推送回 Overleaf；
9.  回到 Overleaf 编译和预览。

如果这一轮在 Overleaf 网页端修改，就不要同时在本地让 Codex 修改。Overleaf 修改完成后，回到本地执行 `git pull`，确认本地已经同步最新内容，再继续使用 Codex。

核心原则很简单：同一轮不要两边同时编辑。

### 2\. 如何识别推送被拒绝

如果远程 Overleaf 上有本地没有的修改，你执行 `git push` 时可能会看到类似提示：

```text
Updates were rejected because the remote contains work that you do not have locally.
```

这通常说明 Overleaf 远程仓库里有本地没有的修改。也就是说，远程版本已经先于本地发生变化，Git 不允许你直接把本地提交推上去覆盖远程变化。

如果拉取时产生冲突，你可能看到类似提示：

```text
CONFLICT (content): Merge conflict in main.tex
```

这说明本地和 Overleaf 修改了同一个文件中 Git 无法自动合并的位置，需要你手动判断应该保留哪一边。

### 3\. 冲突标记是什么意思

打开冲突文件后，你可能会看到类似内容：

![](https://pic1.zhimg.com/v2-7a5e288e04b95a8ae93198181c62fcee_1440w.jpg)

`<<<<<<< HEAD`

本地版本

`=======`

远程 Overleaf 版本

`>>>>>>> origin/main`

这里的含义是：

-   `HEAD` 是本地当前版本；
-   `origin/main` 是 Overleaf 远程版本；
-   `=======` 上下分别是两边的不同内容；
-   解决冲突后必须删除这些冲突标记。

你需要阅读上下文，判断保留本地版本、远程版本，还是把两边内容手动合并成一个正确版本。不要把这些冲突标记留在 `.tex` 文件里，它们不是 LaTeX 正文，残留后很可能导致 Overleaf 编译失败。

### 4\. 在 VS Code 中解决冲突

VS Code 通常会在冲突处提供几个按钮：

-   Accept Current Change：保留本地当前版本；
-   Accept Incoming Change：保留远程 Overleaf 版本；
-   Accept Both Changes：两边都保留。

这些按钮只是辅助选择，最终仍然要你阅读上下文，确认论文内容是正确的。尤其是数学论文，不要只按按钮不读内容。一个符号、一个假设、一个编号被误保留，后面可能会引出更多问题。

解决后要检查文件中是否还残留 `<<<<<<<`、`=======`、`>>>>>>>` 这些标记。确认冲突已经解决后，执行：

```text
git add main.tex
```

`git add main.tex` 的作用是告诉 Git：`main.tex` 的冲突已经解决，可以进入下一次提交。

然后执行：

```text
git commit -m "resolve merge conflict"
```

`git commit -m "resolve merge conflict"` 的作用是记录一次冲突解决提交，提交说明是 `resolve merge conflict`。

最后执行 `git push`，把解决后的版本推送回 Overleaf，这时候可以看到 Git Graph 中会显示两个分支已经融合了

![](https://pic3.zhimg.com/v2-0482357a1f652ce3eed096b1c2d200f6_1440w.jpg)

### 5\. 不要对 Overleaf 使用强制推送

遇到冲突时，不要对 Overleaf 使用强制推送，Overleaf 也不支持 -force 提交。

强制推送的含义是用本地历史覆盖远程历史。对新手来说，这很危险，因为它可能让 Overleaf 上已有的修改从历史中消失。Overleaf 通常也不适合这种强制覆盖式操作。

正确做法是先 `git pull` 同步远程修改，解决冲突，再正常 `git push`。

这也是本文一直强调线性工作流的原因：不要两边同时编辑，每轮开始前先同步，每轮结束后及时提交和推送。

## 结语

本文推荐的不是复杂 Git 技巧，而是一套适合新手的线性科研写作流程。

最终命令闭环是：

1.  `git pull`
2.  Plan mode 确认修改方案
3.  Codex 修改文件
4.  `git diff`
5.  `git add .`
6.  `git commit -m "clear commit message"`
7.  `git push`
8.  Overleaf 编译和预览

每一步的作用都很明确：

`git pull` 用来把 Overleaf 远程仓库中的最新修改同步到本地。

Plan mode 用来在真正改文件前确认修改范围、章节结构和注意事项。

Codex 负责在本地修改指定文件。

`git diff` 用来检查 Codex 修改了哪些内容。

`git add .` 用来把确认后的修改加入暂存区。

`git commit -m "clear commit message"` 用来创建一次清晰的本地提交。

`git push` 用来把本地提交推送回 Overleaf。

Overleaf 负责最后的在线编译、PDF 预览和排版检查。

这套流程里的三个核心工具分工很清楚：

-   Overleaf 负责编译；
-   Git 负责版本；
-   Codex 负责修改。

真正重要的是先建立一个稳定习惯：每一次 AI 修改都能看到差异，每一次接受修改都能留下记录，每一次写完都能推送回 Overleaf 编译检查。

根据观察，学界对 AI 以及 Agent 工作流的接受速度，明显落后于工业界；数学界尤其如此。很多工业界已经很自然使用的项目级 AI 辅助方式，在科研写作里还停留在“复制一段文字到网页对话框里问一问”的阶段。

这并不是说科研写作应该被 AI 接管。恰恰相反，数学和科研工作更需要作者保持判断力：定义是否准确、证明是否成立、假设是否合理、引用是否恰当，这些都不能交给模型替你决定。

但这不妨碍我们把 Agent 当成更好的工作工具。让它帮你阅读项目结构、修改指定文件、统一术语、检查局部 LaTeX 问题，再用 Git 把每次修改记录下来。这些事情不神秘，也不应该只停留在计算机界和工业界。

希望这篇文章能让更多数学系和科研写作者开始尝试 Agent 工作流，让 AI 辅助真正进入论文项目本身，而不是停留在复制粘贴式问答里。这样至少可以减少重复劳动，把更多时间留给真正需要作者判断的部分。
