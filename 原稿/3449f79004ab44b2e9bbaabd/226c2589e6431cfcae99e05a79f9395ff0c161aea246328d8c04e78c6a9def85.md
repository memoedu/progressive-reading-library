先说下什么是大模型。

所有人都会告诉你大模型的下面是 transformer，也会和你说结构长啥样，其实都不关键。本质是大模型是通过一大堆文本数据训练出的预测下一个 token 的黑盒。即：给定文本作为上文，这个黑盒会吐出一个合理的下文，一次只吐一个 token。

那么怎么让它吐出一个完整的句子呢？那就是把新吐出的 token 和之前的上文结合，变成新的上文，再喂给模型。这样往复，直到模型吐出一个 <EOS> token，代表 end of sentence，说明这一轮交互结束，就不用再喂上一个 token 了。

这个是心智模型，实际大模型在运行的时候是一个有状态的黑箱，你不需要每次都把上文给他。相当于他每次蹦一个词出来，你把这个新词给他，然后蹦下一个。关于你喂过的上文，实际上在模型中以一个高维度的参数矩阵的方式作为状态存在，每次喂了新词之后，这个状态就会更新。

再真实一点，模型运行时会分 encode 阶段和 decode 阶段，比上述模型要复杂一些，大致原理是模型可以一次性接收数个 token 进行 encode，譬如给定初始 prompt，或者一轮对话结束后给它后续指令，模型就会进入 encode 阶段，因为此时下一个 token 是给定 prompt 中的，不需要被生成，因此 encode 效率会比 decode 高的多（这也是为什么输入 token 定价上比输出 token 便宜的原因）。而当所有的输入 token 都被 encode 完后，模型就会进入 decode 阶段，这个阶段才是上面说的循环往复（术语叫自回归，auto regressive）。

无论是 encode 还是 decode 阶段，模型总是会看到一个时序上连贯的 token 序列，我们称这个序列为 context。而模型的 context 长度，指的就是从第一个 token 不断连续喂或者往复喂，模型能吃下的总长度。

有了这个认知，我们来看什么是 tool call。

如果模型只能回答问题和对话，那么能力是很有限的，因为它无法采取行动。直到有一天大家发现，模型能力足够强，可以输出一些命令，然后由程序自动执行，再把结果提取出来回复给大模型。这个过程就是 tool call。

具体做法就是在 prompt 中告诉大模型，有哪些 tool 可以使用，应该输出什么样格式的内容去完成 tool 的调用，最基本的 tool 包括 read/write/search 本地的文件，也可以有 web search 或者使用 bash 命令行去执行指令。tool call 格式都是 json，模型输出 json 格式的调用，指定调用哪个 tool，用什么样的参数，然后等执行和结果。

而这个负责提供 tool、处理 tool call 命令，完成执行和给结果的框架，就是 claude code/codex/xxxclaw/pi/hermes 等等一大堆项目，就是 harness，就是 agent framework，甚至可以说就是 agent 本身（记住，LLM 只是大脑）。

当 agent framework 拿到模型一轮的输出后，如果发现是一个合法的 tool call，就会执行并把结果作为新的输入，继续喂给模型，直到模型决定不再需要 tool call，直接输出结果——甚至输出结果也可以作为一个 tool call，由 framework 决定如何 present 给用户。

大模型本身无法读你本地的文件，也不会改你的代码文件，它只会吐出 tool call 让 framework 去读写文件，从而表现得像一个 agent 一样，可以写代码。

MCP 可以理解成一种可以被动态注入的 tool，在启动 agent 时或者运行过程中，注入 MCP 所代表的 tool call，给 LLM 更多的能力。MCP 本质上是一个 API server，用户是 LLM 而已。打个比方，如果各种 SaaS 是 MCP 的话，人就是 LLM，电脑就是 harness，如果你可以想象有一个人被关在一个监狱里，通过电脑来操作各种 SaaS 来创办一个公司的话，你大概就知道 LLM 是怎么改变世界的了。

除了 MCP，agent 所运行的真实环境也可以为 agent 所用，譬如跑在 linux 上的 agent 就可以运行 bash 命令，运行在 macos 上的 agent 就可以操作 chrome browser （通过譬如 opencli 这类优秀工具），本质都是 tool call。

之所以 tool call 有效，有几个层面的因素：

1.  大模型在通用语料上完成训练之后，可以在 tool call 的场景上构建专门的语料进行微调，使得模型更会进行 tool call，对什么时候应该用什么工具产生智能
2.  tool call 大幅扩展了模型的能力边界，使得模型在 agent framework 的包装下，变成像人一样可以做出动作，产生影响
3.  tool call 也允许模型在运行过程中获取丰富的模型外信息，无论是 web search 的结果，还是本地 skills 或者 kb 文档，会帮助模型 make informed decision

一个很显然的趋势是，给人类开发的工具，都会为 agent 重新开发一次。agent 也会不断自己发明新的工具，这个飞轮已经转起来了。

再看 compaction。这是另一个相当本质的技术，上文提到过 LLM 能接受的上下文长度是有限的，这是模型结构导致的必然限制，LLM 本身不能无限地喂 token，这个能喂的最大 token 量就是 context 长度限制。早期 128K 时我们觉得捉襟见肘，现在大部分主流模型都拓展到 1M 了，这背后是无数的工程优化和研究改进。即便如此，1M 的 context 对于一个需要 long running 的 agent 来说，还是会出现不够的情况。

怎么做呢？很简单，就是在 context 快超的时候，让 LLM 对于 context 做一个摘要，把重要内容输出一遍（这个过程本身也要占据 context，因此需要保留一定 context 余量开始 compaction），然后把输出的内容作为新的 context，喂到一个从头来过的 LLM 状态里（注意不一定是 0 token 开始，harness 会注入一些初始 prompt），这个过程就叫做 compaction。

我们会观察到一些特性：

1.  compaction 比较慢，因为需要输出一堆 token，并且还要 encode 一遍到新的 LLM state 里
2.  compaction 本身也有可能使得 context 超标
3.  compaction 一定损失了信息
4.  新启动的 LLM 的部分 context 被 compaction 结果占据，而不是从 0 开始

如果真要把 agent 当做人来看待，long running 是必须要实现的，而 compaction 就充当了底层最核心的对有限 context 的 walk around，基本原理是简单的，但是想要做好还是有大量细节需要考虑，一个最简单的问题是：怎么权衡 compaction 的时机，这个问题展开来聊可以写一篇新文章了，更不用说如何评估 compaction 的有效性了。
