进程同步是分时操作系统中的一个很重要的问题。由于分时操作系统会不断地打断当前的进程，使得许多我们认为的理所当然的处理结果出现各种各样的问题，其中对于共享资源的访问与修改就是一个很大的问题。

因此，我们需要使用「进程同步」来让分时操作系统处理共享资源时满足同样的处理和访问顺序。

# 临界区问题

临界区代表存在对共享变量进行访问或修改的代码段。我们使用`critical_section`代表临界区代码。除了临界区代码外剩余的部分被称为`remainder_section`。

如何让进程正常访问临界区资源被称为临界区问题。

临界区问题应该满足的条件：

1. 互斥访问：只有一个进程可以在临界区中。
2. 空闲让进：如果没有其他进程在临界区内，则一个想进入临界区的进程应当可以进入。
3. 有限等待：不能无限等待。

---

# 临界区问题的解决方案

## Peterson方法

Perterson方法是不需要硬件协助的同步方法，也就是软同步，使用Peterson方法同步两个进程的实例代码如下所示：

`进程i`

```c
void process_i() {
	flag[i] = true;
    turn = j;
    while (flag[j] && turn == j);
    critical_section;
    flag[j] = false;
    remainder_section;
}
```

`进程j`

```c
void process_j() {
	flag[j] = true;
    turn = i;
    while (flag[i] && turn == i);
    critical_section;
    flag[i] = false;
    remainder_section;
}
```

Peterson方法的优缺点：

优点：

- 当CPU严格顺序执行指令时，正确（这种CPU不多了）
- 不需要特殊硬件指令的支持
- 可用于内核或者用户进程

缺点：

- 证明正确性较复杂
- 如果CPU跳着执行指令会有问题
- Peterson方法本质还是忙等，对CPU的有效利用率较低

> Peterson方法至今都没有主流计算机采用过这个方法来做进程同步，可以说是只存在于论文上的方法



## 硬件同步（锁）

基本所有硬件同步的方法都是基于锁来完成的，写过多进程或多线程同步的同学应该非常熟悉了。也就是如下的这个写法范式：

```c
acquire_lock();		// 拿锁
critical_section;
release_lock();		// 释放锁
remainder_section;
```

那么如何实现锁呢？

### 方法一：关中断

临界区问题出现的原因之一就是当前进程的时间片用完了，在中断后被打断了。那么我们直接在进程进入临界区之前把中断关闭了不就行了？因此，基于「关中断」的进程同步范式如下：

```c
asm{"cli"};
critical_section;
asm{"sti"};
remainder_section;
```

但是这么做有两个主要问题：

- 开关中断是特权指令，只能被内核使用，用户程序下无法使用。
- 开关中断只能针对当前被调度的CPU，如果是多核CPU，关中断的方法就失效了（就算是单核CPU，如果存在能够访问内存的外设，同样存在风险，不过这就不在讨论范围之内了）

---

### 方法二：读和写的原子指令

临界区问题出现的根本原因就是当前时间片用完，被打断了，那么除了关中断让进程不被打断还有别的方法来让当前进程不被打断吗？很遗憾，如果没有特定的CPU指令支持，很难做到。

因此，我们需要CPU提供一条指令来满足同步的需求，那么要提供什么指令呢？我们不难观察到，出错的临界区代码都是在读和写的过程中被打断了，因此，我们需要CPU提供一个读写不被打断的指令。

实现目标的函数主要有两种：

- 测试内存并设置值（test_and_set，简称TS）
- 对换两个内存单元的内容（swap）

> 上面两条都是CPU指令，CPU指令是不可能被打断的，是原子性的

#### TS

TS的伪代码如下：

```c
bool TS(bool *target) {
    bool rv = *target;
    *target = true;
    return rv;
}
```

有了TS指令后，我们就可以做一把自旋锁，由于对中间变量的读写是不可打断的，因此，这把自旋锁可以达到目标要求。代码如下：

```c
bool lock = false;		// 多进程间共享的变量

while (TS(&lock));
critical_section;
lock = false;
remainder_section;
```

这么做，我们就通过TS完成了进程同步。

#### swap

swap就是一条交换两个变量值的CPU指令，通过它也能间接实现进程同步：

```c
bool lock = false;		// 多进程间共享的变量

bool key = true;		// 进程内局部变量
while (key) swap(&lock, &key);
critical_section;
lock = false;
remainder_section;
```

**这种方法在xv6的自旋锁的实现中被使用**，在xv6中，用于交换两个变量的汇编指令为`xchg`。

---

### 方法三：信号量（PV操作）

信号量的思想很直观，进入临界区的进程拿到信号量（剩余资源），其他的进程看到信号量的值如果小于0，那么就去睡觉（block），这些进程此时不会被调度，而且也不会使用CPU。

为了完成上述的过程，需要一个整数变量s，被称为信号量，初始值非负（代表初始情况下临界区资源的总量）。

还需要两个**原子操作**：

- wait(s)：执行`s--`，如果`s<0`，那么将进程加入队列（这个队列记录了哪些进程在睡觉），并让进程进入阻塞状态（睡觉）；否则直接返回。
- signal(s)：执行`s++`，如果`s<=0`，那么从队列里找一个进程将它的状态设为就绪（唤醒）；否则直接返回。

伪代码如下，首先，需要定义信号量的数据结构：

```c
struct semaphore {
	int value;
    struct process *list;
};
```

然后，实现`wait`：

```c
void wait(semaphore *s) {
    s->value --;
    if (s->value < 0) {
        add process to s->list;
        block();
    }
}
```

实现`signal`：

```c
void signal(semaphore *s) {
    s->value ++;
    if (s->value <= 0) {
        remove a process p from s->list;
        wakeup(p);
    }
}
```

# 经典进程同步问题

## 生产者消费者问题

这个模型在实际开发中用得非常多，生产者负责生产资源，消费者负责消费资源，它们之间通过一个共享的缓冲区来交互。缓冲区包括：

- n个位置，用数组buffer代表缓冲区。
- in：当前生产者放置产品的位置。
- out：当前消费者消费产品的位置。

对于生产者来说，剩余资源是共享缓冲区剩余的大小；对于消费者来说，剩余资源代表共享共享缓冲区内部的生产资源数量。因此不难写成如下的伪代码来模拟生产者和消费者的代码。

首先是共享的信号量：

```c
semaphore empty = n, full = 0;
```

生产者进程核心代码：

```c
void producer() {
    while (true) {
        produce_an_item;
        wait(empty);
        buffer[in] = item;
        in = (in + 1) % n;
        signal(full);
    }
}
```

消费者进程的核心代码：

```c
void consumer() {
    while (true) {
        wait(full);
        item = buffer[out];
        out = (out + 1) % n;
        signal(empty);
        consume_an_item;
    }
}
```



## 读者写者问题

读者写者问题也是非常经典且在数据库系统，飞机票预定等诸多场景都会用到的模型。这个模型中存在读者进程和写者进程，它们需要满足如下约束：

- 写者：可以读，也可以写
- 读者：只能读，不能写
- 多个读者可以同时读
- 写者修改数据时，其他写者和读者不可访问数据
- 读者读数据时，其他写者不可修改数据

读者写者没有完美的解决方案，有关问题需要视具体情况而定，下面给出一种可行的解决思路：

首先是共享变量：

```c
semaphore wmutex = 1, rmutex = 1;
int readcount = 0;
```

然后是写者进程：

```c
void writer() {
    while (true) {
        wait(wmutex);
        write_something;
        signal(wmutex);
    }
}
```

读者如下：

```c
void reader() {
    while (true) {
        wait(rmutex);
        if (readcount == 0)
            wait(wmutex);
        readcount ++;
        signal(rmutex);
        read_something;
        wait(rmutex);
        readcount --;
        if (readcount == 0)
            signal(wmutex);
        signal(rmutex);
    }
}
```

不过这个写法有一个小问题，如果有持续不断的读者进入，那么写者就会长时间等待，在很多场景下这是不行的，一种方法就是给读者设定一个值，只允许最多连续的n的读者优先于写者。



## 哲学家进餐

哲学家进餐是进程同步中非常经典的一个问题，它讲了这么一件事情：

- 有五个哲学家和五只筷子，哲学家只有两种状态中：吃或者思考
- 当他吃饭时，需要拿起 两根筷子，但一次只能拿一只
- 吃完后放回筷子，继续思考
- 哲学家之间不允许抢筷子

如果把每个哲学家当作一个进程，那么请设计一个算法来让每个哲学家吃到饭。

一个非常常见的错误如下，即让每个哲学家尝试去拿左手的筷子和右手的筷子：

```c
semephore chopstick[5] = {1, 1, 1, 1, 1};
void process(int i) {
    while (true) {
        wait(chopstick[i]);
        wait(chopstick[(i + 1) % 5]);
        eat;
        signal(chopstick[(i + 1) % 5]);
        signal(chopstick[i]);
    }
}
```

请注意，`wait(chopstick[i]);`和`wait(chopstick[(i + 1) % 5]);`加在一起可不是原子操作，上述的写法可能导致死锁。

一种可行的解法为，通过一个额外的互斥信号量`mutex=1`来让两个`wait`变成原子操作。

还有一种比较巧妙的做法：坐在奇数位置的哲学家，先去拿左手的筷子，再去拿右手的筷子。



## Barriers

Barriers代表等待阻塞，在多人游戏等场景下经常使用。它的意思是，若有N个进程调用了`barrier`，那么只有当最后一个进程执行到`barrier`时，这N个进程才能继续执行。

> 这很像打多人在线游戏，所有玩家需要等待最后一个玩家准备好了，游戏才能进行

一种可行的实现如下：

```c
semaphore mutex = 1, waiter = 0;
int pos = -1;    // 指向当前的进程索引
int n = 3; // 代表我们可以同步三个进程
// 上述全部共享

void barrier() {
    wait(mutex);
    pos ++;
    signal(mutex);
    
    // 按位置堵住
    if (pos + 1 < n) {
        wait(waiter);
    } 
    
    // 释放，使得前面的n - 1个进程可以退出wait
    signal(waiter);
}
```
