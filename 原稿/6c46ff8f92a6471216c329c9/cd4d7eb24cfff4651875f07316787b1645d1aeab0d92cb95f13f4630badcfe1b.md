**Test-driven development (测试驱动的开发）是现在个人觉得 the single most important 方法论。**

一提到测试，大家可能就会想到各种 test case。就比如说像 LeetCode 里面一样，有一些regular case 和一些 corner case，然后会有一些去测 scalability 和 runtime 的 stress test 等等。

这个是传统算法意义上的测试。可能仅仅只是测试的 10%

本篇文章分为两部分：

1\. 第一部分介绍 SRE 意义上的测试

2\. 第二部分介绍输出本身就是非确定性的 Machine Learning sense 的测试。

* * *

**第一部分**

真的做过比较大一点的项目的朋友，都一定会重视 SRE（Site Reliability Engineering）相关的概念。除了代码本身在一个局部的 module 里对于正确的 input 能否输出正确的结果，中大型的服务往往还会涉及到各种异步、各种并发、各种竞争、各种数据库、各种服务掉线、各种物理 bug，以及各种网络超时，各种版本不匹配，各种内存泄露，各种worker冻结，各种外部dependency service（比如proxy，browser farm，llm）error，以及各种error propagation.

在传统意义上去写这些测试，其实开销会很大。因为这往往需要通过 simulation（模拟）来还原现实的场景配置，它们已经不仅仅是一个 single program（单个程序）自身的问题了，而是存在着非常多的外部变量。

一个 program 是 deterministic 的，完全确定性的。

但当你有一堆的用户，并发数随着时段不稳定、外部依赖服务不稳定、硬件规模大有硬件 bug 的可能性，整个的问题就变成了一个不可控的系统，有非常多的 uncertainty 和 extrinsic variables. 这个时候就已经不仅仅是测试一个算法、测试 module（模块）那样子的测试了，而是需要系统测试，也就是 SRE 的心智模式。

所以，一般一个个人亲测非常好用的方式，就是除了写这种 correctness（输出正确性）的 test case 外，一定要去写这种 simulation test case，在一定程度上拟合出一批外部变量的 configuration 搭配，然后在不同的搭配下去压力测试整个系统的 robustness.

基于这些 simulation test cases 让模型去做各种 SRE 措施（比如 reporting、error discovery、watchdog、冗余备份等），会比起让模型在没有测试、纯凭经验、没有实际场景融入的情况下直接愣写防护措施，要来得稳健得多。

* * *

**第二部分**

如果读者朋友有机器学习的经验，就会天然地质疑：很多时候，只有这种 computable、可以被 finite state machine 直接解释的 symbolic program，才可以去 run test case。

但是神经网络这种 distributed representation，它天然的输出就是 fuzzy的、gradual 的、连贯的、probabilistic 的。不能够非黑即白地去说运行的结果是对的还是错的，你只能说它的各种 metrics（比如说 accuracy、F1、precision、perplexity 等各种 performance metrics 指标）在这个数据集上究竟是高还是低，来测量这个神经网络本身的能力好坏。

现在很多时候，各种 RAG、各种问答、各种分类任务、各种 routing、各种信息抽取，已经变成了很多服务、很多系统的天然一部分，这大概是是跟十年前最不一样的地方。

于是乎，instead of 让这些神经网络或者机器学习模型去做很多数据点，然后去一个一个人力 review，个人的一个经验是，不如事先准备一个小规模的 benchmark（一般大概 30 个数据点可能就够了）。

现在的时代红利就是，你甚至不用自己去标这些数据点、自己去制定一套 annotation protocol，然后让网页版或者干脆让 Claude Code 自己给标了就行。如果遇到特别艰难的，可以自己去手标一组，然后再让这个模型去 in-context learning。

实测：标音频、标视频、标 3D 模型、标点云、标文本、标图片都好用。现在模型就是很强。

很多时候，如果真的在做业务，需求是特别特别长尾分布的。我们基本上没有办法把现成的东西拿来开箱即用，都得去进行客制化。

这里面用到的 Prompt Engineering，往往需要去现场即调即用；而那些小的 Classifier 或小的 Model，则需要现用、现训练、现优化。

所以，这个时候并没有以前积累下来的现成数据集可以用，但我们又需要比较科学地测定这些 Performance 究竟怎么样，这样才能比较严谨、不凭空想象（unwishful）地进行 A/B test。

所以往往我的一个个人经验就是，会去做一个小规模的 benchmark。

这里边有一个特别好用的 trick：虽然可能没有特别好的现成标签，但是 Hugging Face 上很多数据集还是可以拿过来作为 raw input，然后去进行一番魔改（或者说进行一番重标注）。

然后就可以在这个小规模 benchmark 上去进行各种 feature engineering、各种调优、各种 prompt engineering 的迭代，以及各种 harness 的迭代。

而且我们可以有一个非常 definite、非常明确的数字，来看到并且量化这些变化。

这里边插一个另外的小技巧，就是可以刻意造一些特别 tricky、特别 sneaky 的 corner case（括号：即使是对于 Neural Network 也是有这样一说的），参见以前 Neural Network Robustness 的研究。一般来说的话，准备 10 个这样的 sneaky corner case，能够让我们的模型把这些 hard case 都给做对了，这个 performance 也就基本差不多了可以依赖了。

这里有一个坑，就是一定要跟大模型说好，禁止用特别 hard-coded、rule-based 的方式去为了刷这 10 个 sneaky cases 的分数而刷。

它应该去把这些 test cases 当作 unknown 来对待（treat these test cases as unknown），这样子才算比较好。

* * *

最后补一句推论：如果真的想让模型去进行 auto research，进行这种一个模型自己连续工作好几天、完全脱手的 long horizon execution，其实个人的经验是：一次性准备 10 个以上的 benchmarks for each important modules （仅define 输入输出，怎么实现用什么 base model 都不管，让大模型自己迭代），这样能够广域测试各种各样的中间指标，让整个 system 的可靠度大大提升。

当然，事先准备好这些 case 当然会比较麻烦，而且设计这种东西本身的时长和成本就已经非常 high cost 了。不过大概做到这样才不算 wishful coding 吧。
