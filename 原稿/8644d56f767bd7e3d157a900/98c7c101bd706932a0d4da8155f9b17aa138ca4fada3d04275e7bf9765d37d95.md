## 运营是个很大很混沌的垃圾山概念，基本什么创业力的杂活累活儿脏活儿都能归到运营。曾经有很长一段时间有很大理解困难。

但现在看来，运营最重要的 sense 是：**在一个有固定资本支出的 workflow / pipeline 建成系统、每个环节的 input-output 都 stable 以后，持续不断的 investment & constant inputs。**

就比如说，一个生产系统，可能有这样一套 pipeline：

从 external input $x_1$ 开始，经过第一个 component $f_1$，产生若干 intermediate outcomes，然后分别进入 $f_2$、$f_3$、$f_4$ 等不同的 branch。不同的 branch 可能是异步的，有些可以 parallel execution，有些则有 dependency，需要等待前一个环节的产物。最后，不同 branch 的产物又汇集到下游的 $f_5$，形成最终的 outcome。

这是一个有复杂时间线的过程，而且每一个 component 都吃不同的 input。

每个 component 可能吃的是之前环节 / component 的产物，也可能是外部 externally 注入的外部产物。整个系统的运行，不只是将一个 input 丢进去，然后等着一个 output 出来，而是要持续地向不同的 component 提供相应的 inputs，保证整个 pipeline 能够不断运转。

举个实际例子，比如 AI 视频内容生产（比如红果短剧）。

我们可能有一个 pipeline：首先有人负责选题、构思、写 prompt，之后进入图像生成，再到视频生成、refinement、插帧、超分辨率、剪辑、人工 QC，最后发布到 TikTok 、红果或者其他平台。

这里面每一个环节都是一个 component，都有自己的 input、output、cost 和 execution time。

比如图像生成的产物，是视频生成环节的 input；视频生成的结果，又成为后续 refinement 的 input。与此同时，可能还有一些 branch 在 parallel processing，比如音频生成、字幕、视频 metadata 的整理等。这些 branch 未必需要互相等待，但在最终视频发布之前，又必须汇集起来。

而且其中还会有很多 external injections。比如突然来了一个客户的新需求，需要修改 prompt；或者某个视频没通过人工 QC，需要重新生成；或者平台对视频规格提出了新的要求，需要在后处理环节临时增加一个 component。

这些 input 并不是在 pipeline 最初就一次性确定好的，而是可能在运行过程中，不断从外部注入到系统中的。

而且，**components are engineered, not conceptual**。

所以会有各种困难、bug，需要维修。有的环节 / component 干脆就是 human labor，这就需要 HR 了。

比如说，GPU 可能会 OOM，生成任务可能会失败，某个模型更新以后可能不兼容原来的 pipeline，某个负责 QC 的人可能今天不在岗，或者某个 branch 的 processing speed 太慢，导致后续所有环节都在等待。

这些问题并不是 conceptually 把 pipeline 画出来就解决了的。

一个 component 即使从逻辑上说完全合理，在工程上也可能经常失败。一个 workflow 即使每个 component 单独运行都没有问题，组合起来以后，也可能出现排队、资源竞争、依赖阻塞等问题。

这就意味着，**当这个 pipeline 被设计出来以后，它本身还需要持续不断的投入、维护、调度和协调，才能真正稳定地产生 outputs。**

* * *

甚至在一个系统已经高度自动化以后，Operation 也不会因此消失。因为自动化本身只是把一部分 human labor 转移成了 engineered components。组件虽然不再需要人工逐个执行，但仍然需要有人保证 external inputs 的供应、维护组件的运行、处理异常，以及检查最后的 outputs 是否满足要求。

相比之下，R&D 的职能逻辑是很不同的。

首先，你有一个或多个目标产物 $z_1, z_2, z_3, \ldots$，或者对目标产物有 constraints $C_1, C_2, C_3, \ldots$。

然后，你去设计出一个 workflow / pipeline / system，去 satisfy 这些 constraints，达成目标产物的形式。

比如还是拿 AI 视频生产来讲，我们最初可能只有一个目标：能够稳定地生产出某种质量、某种时长、某种分辨率的视频，同时保证成本足够低、生产速度足够快。

但究竟要采用什么模型、需要几个 GPU、要不要分成多个 generation stages、如何处理人物一致性、要不要进行 refinement、哪些环节可以 parallel execution、哪些需要人工介入，这些其实都没有确定。

这时候我们做的就是 R&D。

我们需要不断实验不同的技术方案，找到满足这些 constraints 的 pipeline。

而且，因为每一个 component $f_1, f_2, \ldots, f_n$ 都有 cost，有投入产出比，因此还要进一步优化每个 $f$ 的 cost，甚至是砍掉 / 合并掉某些 component。

比如原本一个视频需要经过三个生成环节，但后来发现其中一个环节可以由另外两个环节替代，或者某个 model 的更新使得整个 workflow 可以缩短一半，那我们就可以重新设计这套 pipeline。

甚至有时候，优化并不是发生在某个 component 内部，而是直接改变整个系统的 topology，比如把原本 sequential 的两个 branch 改成 parallel，或者改变 intermediate outcomes 的形式，从而避免某些重复计算。

这些都是 R&D 的 work，是很不同的。

再比如餐饮业。

一个连锁餐饮品牌在开设新门店之前，需要研发菜品、确定菜单、设计厨房动线、测试出餐工艺、确定供应链，以及评估每个环节的成本。这些是系统设计的问题。

但当门店开起来以后，每天需要采购食材、安排员工排班、处理订单、保证出餐速度、维护设备、处理库存和损耗。这些事情已经不再主要是设计一个新系统，而是在已有的系统中，持续投入 resources，保证其稳定运行。

甚至每天的采购量、到店客流、外卖订单量，都是不断变化的 external inputs。厨房、备料、收银、配送等不同环节也存在复杂的时间和 dependency 关系。

一旦某个环节出现 bottleneck，整个系统的 throughput 就可能下降。

这和前面 AI 视频生产的例子，本质上是很类似的。

当然，R&D 和 Operation 并不是完全分离的。Operation 过程中发现的问题，也可能反过来成为新的 R&D objectives。比如某个 component 经常出 bug，或者某个环节的人力成本过高，就可能需要重新设计 pipeline。

但两者所关注的问题还是不同。

**R&D 关注的是：为了实现某个目标产物，应该设计出一套什么样的系统，以及如何优化这套系统的结构、性能和成本。**

**Operation 关注的是：在这套系统已经建成以后，如何持续提供 inputs、分配 resources、协调不同 components，并处理各种实际运行问题，从而保证系统能够长期、稳定地产生 outputs。**

前者主要是设计和优化生产系统，后者主要是让生产系统持续运转。

而 business model 又是另一个层面的问题：这个系统生产出来的 outputs 究竟给谁创造了什么价值，谁会为此付钱，以及收入如何覆盖整个系统的成本。

所以，business model、R&D 和 Operation 虽然彼此相关，但并不是一回事。

一个 business model 即使 conceptually 很有吸引力，如果没有一套可行的 pipeline，可能根本生产不出需要的产物。而一套工程上非常先进的 pipeline，即使 R&D 做得很好，如果没有持续的 inputs、维护和协调，也不一定能形成稳定的生产能力。

同样，即使整个 pipeline 能够稳定生产 outputs，也不意味着它一定有一个好的 business model。

这三个层面的问题，还是需要分开考虑的。
