## 传统拓扑结构的局限性

大型数据中心的网络结构多采用树型结构来将 N 台独立的服务器组网，从而允许分布式并行计算（比如 MapReduce），集群虚拟化（Slurm 集群）等诸多 M2M Communication 操作。比如做深度学习常常需要使用多卡集群进行训练，N 台 GPU 服务器组网底层就需要如此实现。

> 不清楚 MapReduce 是什么的朋友可以出门左拐，重修《高性能计算理论》了

传统的数据中心为单根拓扑结构或者多根拓扑结构，如下图

但是传统单根多跟拓扑结构有以下的缺点：

- 成本高，底层服务器的所有负载最终都在根节点上，这要求根节点选购极其昂贵的高带宽高性能路由器。
- 由于不同的服务器的最近公共祖先节点大概率会在根节点上，导致根节点需要负责实现底层的大部分 MapReduce 和 数据拷贝 操作，导致性能问题。这种问题被我们称为 bottleneck

## Fat-Tree 的定义

Fat-Tree 一共分为三层：核心层、汇聚层和接入层。对于一个 $k$ 元 Fat-Tree 而言：

- 每台交换机都有 $k$ 个端口，即出入度和为 $k$
- 核心层有 $k^2 / 4$ 台交换机
- 一共有 $k$ 个 pod，每个 pod 有 $k$ 台交换机组成，其中汇聚层和接入层各占一半。
- 接入层的每台交换机最多直连 $k / 2$ 台服务器，不难算出， $k$ 元 Fat-Tree 最多可容纳 $k^3 / 4$ 台服务器。
- 任意两个 pod 之间存在 $k$ 条路劲。

## Fat-Tree 路由表算法

受限于篇幅，我暂时不从理论层面证明为什么 Fat-Tree 可以解决之前传统拓扑结构的两个问题，相信读者从上面的图中也能形成感性的认知。这里简单讲讲当你使用 Fat-Tree 组网后，你要如何基于根节点的 IP 从分配底层服务器的 IP。

### 基本结构

Fat-Tree 中采用 A段 保留段作为内容 IP 的前缀，为了方便，说明，我们把这个A段IP记作 `10.x.y.z`。并且我放出下图，方便读者理解。

<div align=center>
<img src="https://pic1.zhimg.com/80/v2-2b202fb0c85bb397b7da27eae87e3251_1440w.png?source=d16d100b" style="width: 70%;"/>
</div>


这里还需要澄清几个概念，最底层的服务器，每一台在局域网内的表示我们都称为 host，host 等价于说它们在局域网内的 IP 地址；最底层的每 $k / 2$ 台服务器和一个交换机相连，这 $k / 2$ 个 host 和直连的交换机被我们称为一个子网（subnet）。

假设目前的 Fat-Tree 是 $k$ 元的，那么 `10.x.y.z` 中的 `x` 取值范围为 `0-k`。其中 $x\in [0, k)$ 时，代表当前 IP 在描述第 $x$ 个 pod 内部的交换机。$x=k$ 时，表示当前 IP 在描述 Core 层的交换机。如上图所示。

在一个 pod 内，`y` 代表交换机的编号，比如在 4 元 Fat-Tree 的 0 号 pod 内，四个交互机从左到右，从下到上编号分别为0，1，2，3，所以它们的IP分别为：

- 0 号：`10.0.0.1`
- 1 号：`10.0.1.1`
- 2 号：`10.0.2.1`
- 3 号：`10.0.3.1`

<div align=center>
<img src="https://picx.zhimg.com/80/v2-54a6eca020379036a9605178f50d93ef_1440w.png" style="width: 40%;"/>
</div>


最后一位是 1，阁下可以理解为是特意这么设计的，没什么特殊含义。

如果一个 host 向另一个 host 发送了报文，这两个 host 在同一个 pod 内，但是在不同的子网内。那么此时各个交换机的路由表如何进行配置的呢？

我先讲一下比较抽象的规则，然后再配合一个具体的例子来讲解。Fat-Tree 中，所有的交互机都采用完全一直的路由表，该路由表由前缀路由表和后缀路由表组成。IP 为 `10.2.2.1` 的交换机的路由表如下。

前缀路由表：

| 前缀匹配规则                | 对应的物理端口   |
| --------------------------- | ---------------- |
| `10.<pod>.<交换机 id>.0/24` | 0                |
| `10.<pod>.<交换机 id>.0/24` | 1                |
| `0.0.0.0/0`                 | <查询后缀路由表> |

后缀路由表：


| 后缀匹配规则 | 对应的物理端口 |
| ------------ | -------------- |
| `0.0.0.2/8`  | 2              |
| `0.0.0.3/8`  | 3              |

简单解释一下交换机中的前缀匹配和后缀匹配。

- 在上面的前缀路由表中，比如 `10.2.0.0/24` 代表只匹配前24个位置的前缀，匹配上就算。
- 后缀匹配中的 `0.0.0.2/8` 代表只匹配后8个位置的后缀，匹配上就算。
- 前缀匹配中还有一个 `0.0.0.0/0` ，这个就类似于编程语言中的 `else`，所有匹配都失效就走这个。

### Fat-Tree Routing Algorithm

具体而言，每一个交换机的路由表的具体规则由下方的伪代码给出：

<div align=center>
<img src="https://picx.zhimg.com/80/v2-6cc86165a0b2600eb8e5d6744ff9c095_1440w.png" style="width: 60%;"/>
</div>


如果阁下看上面的伪代码看着不舒服，不妨看看我写的 python 伪代码：

```python
# 为 switch_ip 交换机的前缀路由表添加规则
def add_prefix(switch_ip, prefix_rule, port):
    pass

# 为 switch_ip 交换机的后缀路由表添加规则
def add_suffix(switch_ip, suffix_rule, port):
    pass

for x in range(0, k):				# x 代表 pod 编号 
    for z in range(k // 2, k): 		# z 代表交换机编号
    	# 添加 pod 内部交换机的路由映射表
        for i in range(0, k // 2):	# i 代表子网编号
            add_prefix(f'10.{x}.{z}.1', f'10.{x}.{i}.0/24', i)
        
        # 增加默认路由
        add_prefix(f'10.{x}.{z}.1', '0.0.0.0/0', 0)
        
        # 如果是汇聚层，则添加映射到核心层交换机的路由表
        # 如果是接入层，则添加映射到子网 host 的路由表
        for i in range(2, k // 2 + 2):
            add_suffix(f'10.{x}.{z}.1', f'0.0.0.{i}/8', (i - 2 + z) % (k // 2) + k // 2)
```

通过上面的算法，我们会发现一个非常有趣的事实：**同一个 pod 内的不同交换机的前缀路由表完全相同**，后缀路由表虽然不同，但是它们在 `+1` 算子构成的模 `k // 2`  置换群中是共轭的。



### 一个例子

我们接下来讲一个具体的例子，讲完后你就知道为什么所有交换机采用统一路由表就能正常工作了。


比如下图中，IP 为 `10.0.1.2` 的 host 向最左边的 `10.0.0.2` 发送信息。

<div align=center>
<img src="https://pica.zhimg.com/80/v2-3e58bf8f5dbf7005b66da59a6004e567_1440w.png" style="width: 40%;"/>
</div>


数据包会先从 `10.0.1.2` 出发，因为在一个内网中，host 自然知道自己交换机是谁，于是找到 `10.0.1.1`，希望它可以帮忙把数据发给 `10.0.0.2`；根据上述的算法， `10.0.1.1` 属于 0 号 pod 的 1 号交换机，根据算法，它的路由表如下。

前缀路由表：

| 前缀匹配规则  | 对应的物理端口   |
| ------------- | ---------------- |
| `10.0.0.0/24` | 0                |
| `10.0.1.0/24` | 1                |
| `0.0.0.0/0`   | <查询后缀路由表> |

后缀路由表：


| 后缀匹配规则 | 对应的物理端口 |
| ------------ | -------------- |
| `0.0.0.2/8`  | 2              |
| `0.0.0.3/8`  | 3              |

当 `10.0.1.1` 接收到目标为 `10.0.0.2` 的数据包后，使用 `10.0.0.2` 现在前缀表中做匹配，发现匹配到了 `10.0.0.0/24` 规则下的 0 号物理端口，然后 `10.0.1.1` 就把数据包发给 0 号端口连接着的 `10.0.2.1`。

根据之前的结论，我们可以知道 `10.0.2.1` 的前缀路由表和 `10.0.1.1` 的完全相同，`10.0.0.2` 刚好匹配前缀中的 `10.0.0.0/24` 到端口 0，端口 0 连接着 `10.0.0.1`。到 `10.0.0.1` 时，同理，也会走 0 号端口，通往 `10.0.0.2`，从而完成数据传输。

> 你问我为啥上面的0号端口总是能连接到正确的交换机，我会回答你，这是事先设计好的，如果你自己去设计，你会发现端口-交换机的分配法往往是存在且唯一的。

从上面看到，同一个 pod 内的数据传输总是走前缀路由表。

那么什么时候会走后缀路由表呢？很显然就是不匹配到前缀路由表。而前缀路由表的形式为 `10.<pod>.<交换机 id>.0/24`，显然，目标和当前的 pod 不一样，就不会走前缀路由表了。

因此，向互联网或者不同 pod 的 host 进行数据传输就需要使用后缀表了。从这种先走前缀表再走后缀表的形式就能看出 Fat-Tree 的优势，它非常适合做需要使用内网带宽的任务，比如多机并行，分布式文档检索。
