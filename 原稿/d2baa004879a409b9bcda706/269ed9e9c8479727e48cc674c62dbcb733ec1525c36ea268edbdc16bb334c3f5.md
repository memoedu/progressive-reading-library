这个问题我在组里被讨论过不止一次。

* * *

我把这块展开说，因为这是整个判断框架的地基。你得知道prompt的上限在哪里，才能知道什么时候是真的到了上限。

**格式约束**

这是最被忽视的，但影响最大。

很多任务的”效果差”，追根溯源是格式没约束好，下游解析崩了，然后被归结为”模型能力不够”。

约束格式有几种写法，效果差距很大：

最弱的是文字描述：

```
请以JSON格式输出，包含name、time、location三个字段
```

稍强的是给schema：

```
请严格按照以下格式输出，不要添加任何额外字段：
{
  "name": "字符串，人名",
  "time": "字符串或null，时间信息",
  "location": "字符串或null，地点信息"
}
字段不存在时输出null，不要推断，不要补全
```

最强的是直接给示例，让模型看到一个完整的输入输出对，它会直接对齐那个格式，比你用语言描述可靠得多。

如果你用的模型支持JSON mode或者structured output，先开这个，很多格式问题直接消失。

下面煮啵就展开说一下：

**Few-shot示例**

这个东西被低估的程度，超出大多数人的想象。

零样本和三样本之间的性能差距，在很多任务上能有二三十个百分点。原因不复杂：模型在用你给的示例校准它对任务的理解。你以为你在prompt里把任务说清楚了，但你用的语言本身是有歧义的，示例是消除歧义最直接的方式。

几个细节，做和不做效果差很多：

示例要覆盖边界情况，不能只给”教科书案例”。如果你的任务里有”字段不存在”的情况，示例里必须有一个这样的，让模型看到你期望的处理方式是输出null而不是推断一个值出来。

示例的输入分布要接近真实数据。用构造的玩具数据做示例，然后在真实数据上评测，分布偏移会系统性地拉低效果。

数量不是越多越好。我的体感是三到五个精心挑选的示例，比十个凑数的示例效果好。而且示例太多会占用上下文，挤压真正有用的信息。（啊啊啊，希望上下文这个问题今年有大佬可以解决啊，这个真的是很大的一个瓶颈了，前几天和北大的师弟讨论做项目的时候，他说无尽上下文的方向感觉是错误的，不知道有没有大佬给点评价哈哈哈）

**Chain-of-Thought**

对推理类任务，这个东西的效果超出很多人的直觉。

最简单的用法是在prompt末尾加”请一步步思考”，听起来很蠢，但在推理任务上有效，有系统性的论文验证过，不是玄学。

更强的用法是在few-shot示例里带上完整的推理过程，让模型看到你期望的思考链长什么样，然后照着做。

再往上是Self-Consistency：同一个问题采样多次，取多数票。在推理任务上能再涨几个点，代价是推理成本乘以采样次数，生产环境里得算这个账。

还有一个用法很多人没想到：**任务拆解**。不让模型一次做完所有事，而是分成多个步骤，每步的输出作为下一步的输入。实质上是用外部控制流来补偿模型在复杂任务上的推理局限。我在做比较复杂的信息抽取任务的时候，先让模型做”定位”，再做”抽取”，再做”格式化”，分三步走，比一步到位的效果稳定很多。

**System prompt**

很多人的system prompt是”你是一个专业的XX助手”，然后就没了。这个思路太浅。

我感觉system prompt应该干的事：

把任务边界划清楚。明确告诉模型什么该做什么不该做，”如果用户问的问题超出以下范围，直接告知用户，不要尝试推断或者转移话题”。

把领域规则写进去。如果你的任务依赖某些特定的业务规则或者领域定义，在system prompt里写清楚，比让模型自己猜可靠得多。比如”在本系统中，’有效订单’的定义是……”。

约束输出风格和长度。”回答控制在三句话以内”“不要使用markdown格式”“所有专业术语后面加括号解释”——这类约束放在system prompt里，比放在每次的user message里稳定。

* * *

## 知识问题别用微调解，用RAG

这个判断很多人在实操的时候搞混了。

模型表现差，有两种完全不同的原因：一种是推理能力不够，一种是没有相关知识。这两件事的解法截然不同，混淆了就会走弯路。

区分方法很简单：**把你觉得模型缺少的知识直接放进prompt，看模型能不能用这些知识给出正确答案。**

如果放了知识之后模型能答对，说明是知识缺失问题，用RAG。如果放了知识模型还是答错，说明是推理能力的问题，这时候才考虑微调。

RAG的逻辑比微调干净得多：知识放在外部库，检索进来再推理，知识更新直接更新库，不碰模型。而用微调解决知识问题的代价是很高的——知识更新得重新微调，微调进去的知识和模型原有参数之间会有干扰，召回精度天然不如直接检索。

RAG真正的难点不在于”要不要用”，在于”怎么用好”。chunk切分策略、embedding模型选择、rerank怎么做，这些细节都会影响最终效果。检索质量是RAG效果的上限，检索回来的内容不对，后面的生成再好也没用。

* * *

## 失败案例分析，是最关键也最被跳过的一步

很多人做判断的方式是看aggregate指标——准确率70%，不够好，需要微调。

这个结论太粗了，粗到没有指导意义。

你需要把失败的case拉出来，逐条看，搞清楚错误的类型。

**格式错误**：输出的内容对，但格式不对。JSON多了注释，字段名大小写乱，枚举值用了同义词。这类错误几乎一定是prompt没约束好，回去改prompt，别碰微调。

**理解偏差**：模型理解了任务，但对某些概念的定义跟你预期的不一致。比如你要的是金融场景下的情感分析，模型给你做了通用情感判断。这类错误通常是任务定义不清晰，或者示例没有覆盖有歧义的情况，还是prompt问题。

**推理链断裂**：模型在做多步推理的时候，中间某步出了问题，导致最终答案错。这类错误，加CoT通常有帮助，加任务拆解更好。如果CoT之后还是有规律性地在某类推理上出错，再考虑用高质量的推理链数据做SFT。

**知识缺失**：模型根本不知道某个领域知识，不是推理出了问题，是前提知识不在它的参数里。用上面说的方法区分清楚，然后上RAG。

**结构性上限**：任务需要某种模型在结构上不具备的能力。精确计算用工具调用，别指望模型算对。超长上下文里的精确定位，考虑换更大上下文窗口的模型，或者重新设计检索策略。

做一个简单的统计，把失败case按这几类分类，看各类占比。前两类占主体，继续优化prompt；后几类占主体，才到了认真考虑微调的时候。

这个分析做了，你对问题的诊断会清晰很多，不会再凭感觉说”效果不好”。

## 那什么时候SFT是真正需要的

穷尽了prompt、RAG、工具调用之后，SFT真正有价值的场景：

**风格一致性。** 你可以在prompt里描述风格，但模型对风格的理解是模糊的，在大量不同输入下保持一致很难。SFT把风格刻进了输出分布，不再需要每次推理时去”理解”你的风格描述，稳定性会明显提升。

**高频任务的成本优化。** SFT之后可以用更短的prompt得到同等质量的输出，推理成本下降。规模化部署的场景里，这个差异是实实在在的钱。

**私有格式适配。** 需要输出某个非常特殊的格式或者私有协议的时候，prompt约束的上限比你预期的低。SFT把格式和语言模式压进输出分布，生成稳定性比纯prompt约束高一个量级。

**真正的领域能力提升。** 这是最诱人也最容易被高估的场景。有几个前提条件得满足：数据量要够，几百条大概率过拟合，至少得有几千条高质量样本；数据质量得过关，标注有噪声，SFT会忠实地学进去；数据分布不能太窄，不然在训练分布外的泛化能力会损失。（说起来，这里煮啵其实在阿里也后训练过模型，当时数据集真的是很小，哈哈哈，不过公司机密就不说了，只能说，高质量数据真的是很贵的）

还有一个trade-off很多人没认真想：**SFT之后，模型在训练分布内的任务上会更好，但通用能力可能有损失——也就是灾难性遗忘。** 任务场景高度固定，这个trade-off合算；如果你需要模型保持一定泛化能力，要仔细权衡。

## RL和SFT不是一回事

这两个经常被放在一起讨论，但能解决的问题不一样，单独说一下。

SFT是在告诉模型”正确的输出长什么样”，前提是你有高质量的标注数据，你知道什么是好答案。

RL解决的是另一类问题：**你知道什么是好的结果，但你描述不清楚好的过程，或者根本没有足够的好过程数据。**

代码生成是个典型例子。你可以通过跑测试用例自动判断代码对不对，这个反馈信号是天然存在的，不需要人逐行标注代码质量。DeepSeek-R1的核心逻辑之一就是：用可验证任务（数学、代码）的结果反馈做RL，让模型学会更好的推理链。

什么时候RL值得认真考虑：你有可靠的自动化评估指标，而且这个指标确实代表你真正关心的目标。

什么时候RL会出问题：你的评估指标和真实目标之间有偏差，RL会优化到一个你不想要的地方，而且它会优化得很彻底——reward hacking说的就是这件事。

我导对RL有一句话我觉得说得很准：”你的reward function定义了你的模型的天花板和陷阱，两个都在那里，取决于你怎么设计。”

## 给大家一个可以直接用的检查清单

做微调决策之前，过一遍这几个问题：

任务描述足够精确吗？不是”帮我做分类”，是有明确边界、明确定义的任务描述。

格式约束加了吗？给了schema或者示例吗？

Few-shot示例覆盖边界情况了吗？有没有包含负样本和歧义案例？

推理类任务加了CoT吗？有没有考虑任务拆解？

知识相关的失败案例，试过把知识直接放进prompt吗？试过RAG吗？

失败案例按类型分类之后，格式错误和理解偏差占多少比例？

你手上的标注数据有多少条，质量怎么样，分布够不够宽？

如果这几个问题没有都认真回答过，微调决策就是在跳步。

说到这里，我想说一个更底层的东西。

这个判断框架，本质上是在回答一个问题：**你对自己任务的理解够不够深？**

很多人做prompt做得不好，不是因为不会写prompt，是因为他们其实没有把任务想清楚。任务的边界在哪里，正确答案的定义是什么，边界情况怎么处理，这些问题没想清楚，写出来的prompt一定是模糊的，模糊的prompt喂给模型，模型在自由空间里乱跑，然后你得出结论说”模型能力不够”。

这个结论可能是错的。

真正的问题可能是：你自己都没想清楚你要什么。

我在做那个医学抽取任务的时候，改了三版prompt之后效果上来了，但有一个副产品——我对这个任务的理解也深了很多。我知道了哪些字段在什么情况下会缺失，知道了哪些表达方式是同义的，知道了哪些边界情况是真实存在的。

这些理解，是我在写prompt的过程里逼出来的。

如果我一开始就跑去做微调，我会跳过这个过程。我会用一堆我自己都没想清楚的标注数据去训练一个模型，然后不知道为什么它在某些情况下会出错，因为我的标注本身就是含糊的。

**穷尽prompt的过程，不只是在测试模型，也是在逼你把任务想清楚。** 这个副产品，比很多人意识到的更有价值。

* * *

当然，这不是说微调没有价值。微调是有价值的，SFT和RL解决的问题是真实存在的。

但我在组里观察到一个规律：**做微调做得好的人，往往是那些在做微调之前已经把prompt优化到了一个很高水平的人。** 因为他们对任务的理解够深，他们知道微调在补什么，他们的标注数据质量相对高，他们能清楚地定义什么是好的输出。

而那些一遇到效果不好就去做微调的人，通常做出来的结果也不理想。不是因为微调本身有问题，是因为他们跳过了理解任务这一步，然后把这个问题带进了微调流程。

微调放大你对任务的理解，不管这个理解是清晰的还是含糊的。

* * *

最后说一个让我印象比较深的事。

年前的组会，我们在讨论一个项目的优化方向，有人提议做SFT，我导问了一个问题：”你们现在的prompt，迭代了几版？”

回答是三版。

我导没有直接否定，他说：”三版不够。你们去把失败的case拉出来，按类型分类，然后再来跟我说要不要做SFT。”

那个项目后来又迭代了六版prompt，效果从勉强可用到基本满足要求。SFT没做。

我不是说三版一定不够，也不是说九版一定够。这个数字本身不重要。

重要的是那个动作：把失败case拉出来，按类型分类，搞清楚错误从哪里来。

做完这件事之后，你对”要不要微调”这个问题的回答，会比之前清晰很多。

大概率你会发现，还有一版prompt没写好。
