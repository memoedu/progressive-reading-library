最近 Agent 太火了，火到有点喧嚣（自己想了想还是选择了用这个词来形容）。

Claude Code、Codex、各种 coding agent、research agent、workflow agent，好像一下子把软件开发推到了一个新阶段。很多过去需要人手写/查/改的事情，现在确实可以交给 Agent 做，而且效果经常好到让人有点不适应。

自己一直在从事 AI 基础软件研发，也越来越多地在日常工作中使用 Agent，并推动团队同学更多把 Agent 放进真实工作流里。总体感受很明确：这确实是一类生产力跃迁级别的技术。

但越是这样，我越觉得需要认真看清它的边界。

这篇不是技术报告，也不是学术论文，只是一些比较 random 的思考。形式和组织都比较随意，想到哪写到哪。

### 一、“**日抛型软件”的前提是验证成本**

现在有一个很流行的说法：有了 Agent 以后，软件可以变成“日抛型”的。

这个说法有一部分是对的。

过去写一个小工具、内部页面、数据处理脚本、临时 dashboard，成本很高。所以哪怕只是短期需求，大家也常常倾向于在已有系统上凑合扩展。现在 Agent 可以很快生成一套能跑的东西，很多一次性、低风险、低状态依赖的软件，确实可以更像“日抛用品”。

但这里有一个关键边界：

-   日抛不日抛，核心不取决于写代码的成本，而取决于验证成本。

Agent 降低的是“写”的成本，但没有自动消灭“信”的成本。

你怎么确信这个新写的东西是对的？怎么确信它没有破坏上下游？怎么确信它不会污染数据？怎么确信它一个月后还能被理解，半年后还能继续演进？

所以我现在更愿意用这样一个判断标准：

-   如果“重新写一个新东西并验证它”的成本，显著低于“在存量系统上扩展并验证它”的成本，那么它适合日抛。

反过来，如果新写软件的验证成本显著高于改造存量系统的验证成本，那么它就不适合日抛。

一次性脚本、临时数据转换、低风险原型，这些场景里，我可以很放心地让 Agent 大量发挥。因为它们输入输出清楚，失败影响有限，也没有太多长期维护要求。

真正让掌控成本飙升的，是“可维护性”这个维度。

所谓日抛，本质上是在说：**这段代码不需要在可维护性上花太多掌控成本。那你得先确认，它真的不需要。**

### **二、Agent 写代码进生产环境，根本挑战是不确定性**

Agent 生成的代码要进入生产环境，**最大的挑战不是“它能不能写代码”**。

它当然能写代码，而且很多时候写得很快、很像样。

**真正的问题是不确定性。**

**第一层不确定性来自模型本身**。Coding Agent 本质上是一个非确定性工具。prompt 稍微变一点，context 稍微变一点，模型版本变一下，工具返回结果变一下，都可能得到不同结果。

对于一个简单任务，这种不确定性无所谓。**但对于一个多步骤、强依赖、需要长期稳定运行的生产级任务，每一步的小偏差都会向后传递。步骤越多，端到端完全自主跑通的概率就越难保证。**

**第二层不确定性来自 context。**

Agent 看到的不是“真实系统本身”，而是某个窗口里的上下文：代码片段、文档、工具调用结果、测试输出、搜索结果、日志片段。这里任何一个东西都可能不完整、过期、噪声很大，甚至相互矛盾。

**第三层不确定性来自执行环境。**

GPU 浮点计算、并发、缓存、调度策略、随机种子、采样算法，都可能引入微妙差异。对于普通 demo，这些差异不重要；但对于高性能计算、数据库、交易系统、推理引擎、训练框架等关键生产场景，这些差异就可能非常关键了。

**这些不确定性不是简单相加，而是叠加在一起。**

还有一个更隐蔽的问题：**reward hacking。**

举一个 AI 基础软件里很典型的例子：**让 Agent 生成一个“性能超过 baseline 的 kernel”，和让它生成一个“质量达到生产标准、性能超过 baseline、并且没有引入 correctness bug 或其他 shape 上性能回归的 kernel”，是两件完全不同的事情。**

前者是一个容易被 reward game 掉的任务。只要有一个还不错的参考实现作为基础，在某个特定输入、特定 shape、特定 benchmark 上跑得快，看起来就赢了。

后者才是生产真正需要的东西。

**Agent 会非常“聪明”地朝你给的那个不完整 reward 去优化。你验收标准里没写死的东西，它不保证。你没有让它覆盖的场景，它可能不会主动替你守住。你没有表达出来的架构不变量，它可能直接破坏掉。**

这其实不是 Agent 独有的问题。人也会 reward hacking。**只是 Agent 的工作原理让这种 reward hacking 的速度更快、规模更大，也更容易被误认为“智能地解决了问题”。**

**复杂软件开发里，很多关键判断仍然沉淀在资深工程师的经验、组织记忆、系统历史和隐性 tradeoff 里。当前很多团队还没有能力把这些东西完整结构化地表达出来，更不要说让 Agent 自动稳定遵守。这里有更深层次的认知论的原因，佛法里说”言语道破，一说就错“其实也有几分相关的意味。LLM的处理对象是文本，文字是人类智慧表征的结晶物，但并不是所有的人类智力活动都可以轻松地以文字的方式全部记录下来。**

**Agent 不是不聪明，而是我们经常没有把该告诉它的东西告诉全，而告诉全的代价可能超出了我们常规的预期。**

### **三、能 run 的 demo，和能稳定跑的生产系统，是两回事**

最近我已经不止一次听朋友（比较幸运的是，自己所在的公司还没有遇到这样的情况）说起类似情况。

公司高层看到 Agent 很强，于是给执行团队下很硬的目标：**过去正常排期需要几周甚至几个月的软件需求，现在要求用 Agent 在非常短时间内交付。**

甚至有些产品或业务同学，自己用 Agent 攒了一个“看起来能 run 的 demo”，然后拿着这个 demo 去问工程团队：为什么你们不能更快？

这个现象恐怕至少在未来一段时间内会越来越常见。

因为 Agent 让“看起来能跑”的门槛大幅降低了。过去一个非工程背景的人很难做出一个像样 demo；现在只要需求描述够清楚，Agent 可能几个小时就能搞出一个页面、一个 API、一个流程，甚至还能接上 mock data。

但这里最大的误解是：

> 一个能 run 的 demo，和一个能稳定运行的生产系统，不是同一种东西。 一个一个月后就没人敢改的系统，和一个能经得起半年以上迭代演进的系统，也不是同一种东西。

生产系统需要处理权限管理、数据一致性、异常路径、监控告警、日志、扩展性、可部署、可回滚、上下游兼容、长期维护，等等。

**更重要的是，它要被团队理解和接管。**

**一个 demo 可以靠“看起来对”通过验收。生产系统不能。**

而且这里还有一个更反直觉的点：**Agent 让写代码变容易了，但可能让管理一个 repo 变难了。**

当每个人都可以用 Agent 高速产出 PR，PR 数量会激增，CI 会承压，重复代码会加速增殖，review 负担会上升，代码的可理解性和一致性会下降。

写得快带来的下游成本，会转嫁到 repo 治理、CI 稳定性、review 机制和组织协作上。

**demo 阶段感受不到这些成本，因为 demo 没有长期 repo，没有多人协作，没有历史包袱，也没有未来演进。**

但生产系统有。

**所以 Agent 最危险的地方之一，是它让非工程角色更容易低估工程复杂度。以前大家至少知道“我不会写代码，所以这件事可能不简单”。现在 demo 能跑了，就容易产生错觉：既然 Agent 已经做出来了，那工程团队为什么还要排期？**

这个错觉对工程组织的伤害可能远超常规认知。

短期看，交付速度上去了；长期看，系统可能变得越来越脆弱。

### **四、积极拥抱 Agent，和迷信 Agent 是两回事**

我并不反对大力推动 Agent。

相反，我认为任何认真做软件的团队，都应该积极拥抱 Agent 技术。存量系统也应该思考如何变得更 Agent-native：**更清晰的模块边界，更好的测试 harness，更结构化的文档，更明确的 owner，更自动化的验证链路，更适合 Agent 理解和修改的代码组织方式。**

这些都非常非常重要。

**但积极拥抱 Agent，和迷信 Agent 是两件完全不同的事情。**

积极拥抱 Agent 的管理者，会问：

-   哪些任务适合 Agent？
-   哪些任务需要人工 review？
-   哪些系统要先补测试和文档？
-   哪些 repo 边界太乱，Agent 进去只会制造更多复杂度？
-   哪些流程可以通过 harness 改造让 Agent 更可靠？
-   Agent 带来的速度收益，是否超过新增 review 和验证成本？

迷信 Agent 的管理者，会问：

-   为什么别人一天能做出来，你们不行？
-   为什么还要排期？
-   为什么不能让 Agent 直接写？
-   为什么 demo 能跑，生产还要这么久？
-   为什么你们不能更 aggressive？

这两种心态对工程执行团队的影响天差地别。

**前者是在提升系统能力。后者是在把复杂度和风险向下游和未来转嫁。**

尤其当决策层距离技术细节比较远，主要通过二手甚至三手信息形成判断时，这种认知偏差会被放大。外部宣传看到的是“Agent 完成了某个复杂任务”，内部团队面对的是“这个任务如何在我们的系统里稳定运行半年以上”。

中间差了很多层。

如果这种认知偏差再以硬目标的形式压到执行团队头上，而执行团队明知道路上有坑，却没有足够话语权解释坑在哪里，那破坏力会非常大。

### 五、正确使用 Agent：批判性、开放性、工程化

说了这么多，不是要唱反调。

Agent 是一门非常强大的技术，它对生产力的提升毋庸置疑。我只是觉得，在这个热闹的阶段，姿势比热情更重要。

我自己给自己的原则大概有几条。

**第一，批判性地使用 Agent。**

如果一个任务用 Agent 做出来的效果没有预想中好，第一反应不应该是“Agent 不行”，而是去想：

-   是不是 prompt 不好？
-   是不是上下文不够？
-   是不是工具链不合适？
-   是不是测试 harness 太弱？
-   是不是 repo 结构太混乱？
-   是不是现有系统本身就不适合 Agent 修改？
-   是不是可以换更新模型继续 push boundary？

很多时候，**Agent 做不好一件事，本质上暴露的是系统本身不够 agent-friendly。**

比如没有可靠测试，没有清楚模块边界，文档过期，运行环境难复现，reviewer 需要靠隐性知识判断，需求没有可执行验收标准。

这些问题不是 Agent 引入的，但 Agent 会把它们放大。

**第二，把 human-in-the-loop 逐步沉淀成 harness。**

**很多所谓 human-in-the-loop，本质上是“还没有被编码的定制 harness”。**

**人每次介入去纠偏、补上下文、卡验收、定义边界、限制不该改的路径，这些动作里有相当一部分是可以沉淀成规则、脚本、测试、CI gate、review checklist、benchmark harness 的。**

成熟的做法可能不是“人一直盯着 Agent”，而是形成双层结构：

> 定制 harness 控制做什么、不做什么，消除工作流层面的不确定性； 通用 Coding Agent 在这个边界内自由发挥。

这样人的角色也会发生变化。

人不再只是逐行写代码，当然仍然需要保持对代码的敏感度；更重要的是去分解系统复杂度，把它映射成受控流程，为每个模块定义验收标准，搭建迭代闭环，并做系统集成。

**第三，对 Agent 产物保持足够掌控力。**

这种 review 不一定是逐行代码级别。很多时候逐行 review 反而低效。更重要的是知道它改了什么、为什么改、影响面在哪里、验证链路是否覆盖、失败时如何回滚、有没有破坏长期可维护性。

无论中间用了多强的模型，最终为 Agent 产物负责的，仍然是人。

**第四，保持开放，但同样保持批判。**

要及时跟进领域里最新的进展，包括 Anthropic、OpenAI 这些头部公司的经验分享，也包括很多实干派公司的实践。

但也要带着批判的眼光来看待。

厂商展示的通常相对更适合展示能力边界的任务。比如安全修复、代码漏洞、特定场景下的性能benchmark优化、不需要考虑维护性判断标准清晰且更多考虑高智力执行吞吐能力的数学和算法题的求解。这些问题本身就相对适合 AI 处理，因为目标更清晰，反馈更快，Agent高执行吞吐的特点能够有效加速求解过程，验证更直接。

**这不是说这些展示不真实，而是说它们未必等于你的生产系统。**

外界流传的很多惊艳 Agent 成功案例，往往共享一组特别适合 Agent 的性质：范围相对封闭，反馈可迭代，生产约束较弱，长期维护要求不高，或者验证信号足够清楚。

**你不能拿这些案例直接反推：所以我的复杂生产系统也能这么干。**

**同样也不能简单得出Agent技术不适合你当前在工作的复杂生产系统。这两种极端的态度同样有害。**

你的系统可能有历史包袱，有跨团队依赖，有没有文档化的业务规则，有版本兼容性的考虑，有用户状态，有线上事故沉淀下来的内隐知识。

这些东西不会因为模型升级自动消失。

**六、Agent 真正改变的，可能是工程系统的组织方式**

我当前的观点是，Agent 最大的影响不只是“帮人写更多代码”。

它会倒逼工程系统变得更可验证、更模块化、更显性、更自动化。

过去很多系统靠人的长期记忆运行。某个模块为什么这么写，某个测试为什么不能动，某个参数为什么不能改，某个客户场景为什么特殊，可能都在几个资深工程师脑子里。

这种模式本来就脆弱，只是过去没有那么明显。

**Agent 进来以后，这种隐性知识的缺陷会被放大。因为 Agent 不知道那些没有写下来的东西。它只会根据看到的代码、文档、测试反馈、日志和工具返回结果来不知疲倦地行动。**

**所以如果一个团队希望真正用好 Agent，不能只是买工具、升级模型、要求大家更快交付。更关键的是把工程系统本身改造成 Agent 可以理解、可以验证、可以安全修改的形态。**

这包括：

-   更清晰的模块 owner；
-   更明确的接口边界；
-   更可靠的 CI；
-   更好且高效的测试覆盖；
-   更结构化的设计文档；
-   更清楚的验收标准；
-   更少的隐性业务规则；
-   更稳定的开发环境；
-   更可追溯的变更记录。

**这些听起来很传统，甚至有点无聊。**

**但恰恰是这些传统工程基本功，决定了 Agent 能不能从“聪明的 demo 工具”，变成“可靠的生产力基础设施”。**

### **写在最后**

Agent 是一门强大的技术。生产力提升是真实的。

但它终究是一门技术。既然是技术，就一定有适用场景、边界条件、失败模式和成本结构。

**我现在最担心的不是工程师不用 Agent，而是组织在没有理解边界的情况下，把 Agent 当成取消工程纪律、压缩正常排期、绕过验证流程的理由。**

这会很危险。

**更好的方式是把 Agent 当作杠杆，而不是银弹。**

**杠杆可以放大能力，也可以放大错误。系统基础越好，Agent 的收益越大；系统边界越乱，Agent 制造的混乱也越大。验证体系越强，Agent 越能安全加速；验证体系越弱，Agent 越容易把“看起来能跑”包装成“已经完成”。**

所以，在当前这个热闹甚至有些喧嚣的时代，第一性的事情不是追逐每一个新 demo，而是保持独立的工程判断。

回到自己的真实业务场景，持续试，持续改，持续复盘。用 Agent push boundary，但不要假装 boundary 不存在。

不迷信，不抗拒。

热闹是别人的，边界是自己的。
