## 前言：被 🦞 搞红温

小龙虾来越不稳定了，3.31 这个版本更新后，我直接红温了，我用小龙虾构建了一套本地工作流，直接报废了。而且我发现在过去一个月的时间内，我主要使用的全都是kimi和cc，小龙虾我倒没怎么用。这不禁让我思考，我能不能直接把 kimi 和 cc 接到飞书或者是QQ这类聊天软件里面。在这个时候，我突然想到了一个好几个月之前看到的技术叫做ACP。

我们都知道kimi，cc这类AI编程智能体，交互的时候，是通过命令行来实现的。

![](https://pic1.zhimg.com/v2-50474e1c71f59ad3f0c193cd066658ce_r.jpg)

所以如果我们想要直接在飞书这类聊天软件里操作这些AI编程工具，一个直观的想法，就是直接让本地一个进程代替我们去和这样的一个TUI进行交互，但这么做有很大的缺点。首先这种TUI本来就是设计给人进行交互的，它里面会像打字机一样不断打出文字。AI很难判断当前这个TUI什么时候代表当前的交互结束了。虽然对于人来说判断这个很简单。其次就是如果想要与他交互的话，就需要通过IPC的方法进行数据传输。这是一个非常低效的方法。而且也不是很优雅，并且有很多的边界条件很难估及到。

那么有什么方法可以更加优雅地无痛将这些AI编程工具接入到聊天软件里面吗？

经常看锦恢频道的同学这个时候应该能想到了——遇到这类需要标准输入输出的情况，我们第一个要考虑到的就是当前有没有一套标准的协议，支持了这些通用做法的输入与输出。如果有这样一项协议，那么我们就可以将这个协议作为一个桥梁，直接把kimi接入到聊天软件里面。这个协议就被我们称为 ACP 协议。

## 什么是 ACP 协议

ACP，全称 Agent Client Protocol，这是一个用于标准化代码编辑器和编程智能体之间交互的一个通信协议。这么说可能会比较抽象，大家可以想象一个如下场景：我在命令行上使用了不同的编程智能体。比如说Claude Code，比如说Cursor CLI，比如说kimi，我们发现这三个智能体用起来没有任何区别，他们都是一个命令行的TUI界面，大家输入文本，然后这些编程智能体处理完工作内容，并将结果通过文本返回给我们。那么既然他们的交互方式都是完全一致的，那假如我现在想把这样的一个东西放到 Vscode，Zed 的这些代码编辑器里去使用，有什么最快的方法把它接入吗？

![](https://pic4.zhimg.com/v2-30cf86fa0d94b9e56559f94d79a78f81_r.jpg)

这里很容易想到，我们可以设置一个中间层的协议，来标准化这些不同的编程智能体的一个数据结构，并且将它转接到这些 代码编辑器/IDE 里面。这样一套规范了编程智能体要如何的输入输出信息，并和代码编辑器/IDE的终端用户进行端要端的交互。这样的一套协议，便是ACP协议。

### ACP 协议社区生态

ACP 协议目前主要是社区在维护，而主要的几个社区核心贡献者都是 Zed 编辑器的主要开发成员。这是他们的官方网站：[Get started with the Agent Client Protocol.](https://agentclientprotocol.com/)

目前的主项目诞生的结果便是ACP的SDK包。目前支持了javascript跟python两个不同的生态。js 通过下面安装 sdk

```bash
npm install @agentclientprotocol/sdk
```

通过网络搜索，不难发现几乎所有主流的 AI Coding CLI 都支持 ACP 协议：

* cc: <https://github.com/agentclientprotocol/claude-agent-acp>

* kimi CLI: <https://moonshotai.github.io/kimi-cli/en/reference/kimi-acp.html>

* cursor CLI: <https://cursor.com/cn/docs/cli/acp>

* opencode: <https://opencode.ai/docs/acp/>

## 基于 ACP 实现把 kimi cli 接入飞书

### 基本架构

那么在有了 ACP 协议之后，我们想将 kimi 之类的编程智能体接入到飞书里面就非常简单了。通过上面的描述，我们不难想出如下的一套实现架构。

![](https://pica.zhimg.com/v2-445135552a7bf485f34d1d316b17d8ea_r.jpg)

这套架构的好处就是基于统一的 ACP 协议，我们可以自由的将任意支持ACP协议的编程智能体接入。你觉得 kimi 不好用，想换成 Claude Code ？没问题，直接换。你的 Cursor 会员快过期了？没关系，直接换。

并且如果未来越来越多的聊天软件，它支持了ACP协议，那么我们也可以在QQ微信甚至更多的聊天软件里面直接使用到我们的任意编程智能体。当然，这些都是交给社区来做的后话了。只不过因为我们使用这些编程智能体的反馈结果，大概都是一些和代码有关的东西。而目前对于代码渲染最好的聊天软件，就算考虑到海外同类型仍然是飞书，这也是为什么我这篇文章是以拿飞书作为讨论对象的原因。

### 开发提示词

想要实现这样一套架构，如果不考虑corner case的话，实现起来非常简单，打开你的编程智能体，在一个空白的文件夹下输入如下的提示词，就可以让它开始干活了，当然，为了快速搞一个 mvp，我们此处限定只用kimi cli和飞书：

```
我们现在要实现基于 ACP 协议的一个飞书的编程智能体接入程序。
请通过 typescript 来构建当前的项目。通过 dotenv 进行变量管理。
我们通过 ACP 协议构建起和 kimi cli 的标准化通信函数，使用 @agentclientprotocol/sdk 这个库作为 ACP 客户端框架。
kimi cli ACP 协议的支持文档为： https://moonshotai.github.io/kimi-cli/en/reference/kimi-acp.html
使用 @larksuiteoapi/node-sdk 作为和飞书通信的框架，除此之外，ACP 客户端从服务端得到的信息，先需要通过转换层将编程智能体输出的 markdown 转换成可以在飞书里更加漂亮渲染的 lark md，并且以post类型的数据输出卡片信息。
lark md 标准自己搜。
你需要保证编程智能体返回的 markdown 能够在飞书正常的渲染，并同时支持多级标题、有序无序列表、表格、行间代码块和行内代码块并支持对应的语法格量。

默认的 .env 模板为

# 飞书应用配置（必填）
FEISHU_APP_ID=cli_xxxxxxxxxxxxxxxx
FEISHU_APP_SECRET=xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx

# ACP Agent 配置
ACP_DEFAULT_CWD=/Users/yourname/projects
KIMI_PATH=kimi

# 开启后当前项目，需要将编程智能体通过ECP协议返回的thinking和toolcall内容也一并发送到聊天软件里面。
DEBUG=false

# 思考过程和工具调用显示模式: force(不显示), summary(摘要), detailed(详细)
SHOW_THINKING_TOOL=force
```

然后你需要去飞书上配置一下机器人，并且拿到它的 id 和 secret，并将这个 secret 填到上面这个提示词创建的 .env 文件里面。不知道怎么在飞书上配置机器人，并拿到对应的这些登录凭证的，可以看我的这篇文章：<https://kirigaya.cn/blog/article?seq=366>。

### 启动并体验

初始完成之后，AI也会帮你自动的启动这个最小的案例，然后你就可以在非处理直接和机器人对话了。建议一开始先输入一些简单的字符，来确保当前的系统是联通的状态。
