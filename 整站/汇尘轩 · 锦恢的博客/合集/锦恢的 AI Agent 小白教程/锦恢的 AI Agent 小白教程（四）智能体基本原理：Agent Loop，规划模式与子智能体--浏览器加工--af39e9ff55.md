## 4.1 智能体的核心 Agent Loop

在第一章中，我们已经提到了 workflow 与 autonomous agent 的一个基本区别，不熟悉的朋友们可以再去回顾一下温故知新 [锦恢的 AI Agent 小白教程（一）Agent 的基本概念与分类](https://kirigaya.cn/blog/article?seq=351)。

### 4.1.1 为什么要做智能体？

我们想搞智能体的初衷也非常简单，因为大模型虽然非常的智能，但是我们使用它来解决一个非常具体的应用问题的时候，仍然需要通过不断的询问，然后观测大模型的返回结果。然后我们再完成自己的判断。这个过程中其实会有很多很多的重复劳动在里面。

我们把目光回到两三年前，也就是 2023 年的时候，那个时候大家就已经开始尝试使用大模型来辅助进行代码编程了，当我们遇到一个bug，或者是想要创造一个新的UI页面的时候，我们通常是自己来构造上下文，然后再询问大模型这一个部分要怎么写，大模型再返回一个可复制的代码片段。然后我们再将这个代码片段重新的粘贴回我们的项目的编辑器里面。显然，在这个过程中存在大量的重复劳动，而且它也不够自动化。我们往往需要将大模型生成的文本复制并选择性的粘贴到代码的对应片段，然后再重新启动开发服务器，或者根据提示信息来修改其中的一部分语法错误。在这个过程中，实际上我们的生产力并没有被彻底解放出来。所以我们就在思考一个问题，能不能让 AI 更加一步到位的把这些重复的劳动也完全自动化。

![图片](https://kirigaya.cn/api/storage/image/9344ff1c-3be7-4693-b06c-a3f273fb9d2a.webp)

但是对于大模型来说，一问一答的交互模式注定了它无法完成这样的自动化操作。想要完成自动化操作的一个AI系统，它一定得是基于大模型制作的一个复杂系统，拥有操作电脑中各个板块的权限。而这样的复杂系统，其实就是我们现在的智能体，更加规范化的说法是 autonomous agent。

对于 autonomous agent 而言，它最重要的核心就是 agent loop，这是智能体算法的核心，你必须完全理解它的工作机制才能继续理解后续的章节。而在工业界和学术圈，这一套 agent loop 的方法有一个更广为人知的说法，叫做 ReAct (Reasoning + Acting)。

> 在一些国外的开源教程里，agent loop 有时候也会被称为 query loop。

### 4.1.2 智能体的核心 —— ReAct

如果阁下拥有控制论或是强化学习相关的一些基础，那么不难想到，为了让一套系统能够自发地去发现和解决问题，我们自然需要将这套系统本身的状态首尾相连，从而构建成一个循环。让它可以自产自销，循环往复。而在工业界工程师们的尝试下，一些非常容易被大家想到的范式便被验证和凝练了出来，并且最终在业内沉淀出一套规范化的说法，叫做 ReAct。

ReAct（Reasoning + Acting 简称）是非常朴素的一套让大模型能够成为自主执行任务的智能体的一个架构算法，毕竟大模型它只能生成文本，那么要怎么设计才能让基于大模型的一套系统能够自主来进行决策和持续工作，从而能在一些任务上完成闭环呢？

根据上一章的内容，大家不难想到，完全可以让大模型基于一个最初的任务，让它生成工具调用，然后再根据工具调用的结果去做，直到工具调用的列表为空为止。这样一来，我们就可以把流程串通了。 AI 就能在接收到最初的命令后自主完成一系列任务了。

> 如果阁下有控制论或者强化学习的基础，你就会发现这个 loop 就是这两个学科里面的东西。

显然，这样的一个流程是能够基于“当前是不是有工具要用？”来构成一个闭环的，也就是如下图所示：

![](https://pica.zhimg.com/v2-0195daecd1ca7730636bfd1e38c0c99e_r.jpg?source=d16d100b)

当然了，根据不同厂商的实现也会有略微的差异，比如对于 LangGraph 来说，它的做法就是只判断 tool_calls 是否为空，为空时退出循环；OpenAI 则是当 LLM 的  finish_reason  为  stop （正常结束）而非  tool_calls  时终止。

在继续下面的讲解之前，基于整个 agent loop 有一些术语规约了中间环节的一些细节。我觉得有必要来让大家这知晓一下：

* prompt/question: 用户在一开始提出的问题或者是下达的指令。

* thought: 大模型在生成内容或者是生成需要调用的工具前的思维链内容。

* action: 大模型生成的需要调用的工具的执行。一个 action 包含了一个或多个工具调用。

* observation: 工具执行的输出结果。一个 observation 包含了一个或多个工具调用的结果。一个 observation 和一个 action 对应。

* trajectory/trace: 从用户发出 question，智能体会不断进行 thought，执行 action，获得 observation，循环往复，直到 finish 结束。这个过程会形成一条 (question, thought1, action1, observation1, thought2, action2, observation2, …, finish) 的序列，这样一条序列就被称为 trajectory。

* rollout: 采集 trajectory 的这样的一个过程就是 rollout。因为 rollout 比 trajectory 读起来更简单，很多时候，我们也直接拿 rollout 指代 trajectory，比如有些论文会直接写 collect rollouts，工业界很多人交流工作也更喜欢说 “这条 rollout 质量咋这么差”。反正具体情况具体分析吧。

### 4.1.3 题外话：从 LLM RL 到 Agentic RL

上面的这样一个流程，是不是让你感觉很眼熟呢？没错，(question, thought1, action1, observation1, thought2, action2, observation2, …, finish) 这样的 trajectory，完全可以被建模成一个马尔可夫链，甚至如果是有标准答案，可以构造为强化学习的训练范式。

> 没有强化学习基础的朋友，可以去看我6年前写的强化学习教程：<https://zhuanlan.zhihu.com/p/149885358>

用 ReAct 的 agent loop 中产生的 trajectory 构造强化学习的训练框架？这个就是目前业内非常爆火的一个研发方向 —— Agentic RL，也就是在智能体 ReAct 链路的范式下来训练大模型，这样的范式下训练出来的大模型，将能更好的适配 ReAct 这样的 Agent Loop，它所驱动的智能体能够更加完美的完成各种各样实际的工具调用和更加复杂的任务。

毕竟在大模型的设计之初，它就被设计为接收文本，生成回答的一个范式。但我们目前却实希望大模型能够在 ReAct 的 loop 中不断调用工具闭环的完成任务，显然，这个过程和传统大模型的训练框架是不太一致的。因此，针对这样的场景还是需要专门训练的，而 Agentic RL 就是工业界针对于这类训练任务所给出的答案。前沿项目有清华团队 slime，我们团队的 dressage 等等，当然了，更加细节的部分就属于 infra 层面的内容了。我们会在 infra 系列教程的大概第五个章节提到它的细节。而在此处，大家只要对这玩意儿稍微有点了解就行了，知道它大概是属于哪一个层面，为什么要有就可以了。

而最近半年大家讨论的最多的agent，也就是类似于Claude Code，Codex这样的用来写代码的agent了。而它们之所以能够在代码方面变得越来越强，并不是它们的大模型的本质能力有了什么提升，而是这些公司在写代码的这件事情上，利用了上面的这样的一个 agentic rl 的训练范式去采集了程序员在开发工程中的很多 trajectory 来训练了这些模型，使得最终组装成的编程智能体能够更加正确地去执行 agent loop，从而完成编程任务。

### 4.1.4 Agent Harness

那么回到最初我们谈论的发明智能体的动机。我们希望能够把与大模型对话，从而解决某些问题的流程做的更加自动化。比如我们举的例子就是询问大模型获取结果复制粘贴，通过这样的方法来写代码。我们给予智能体系统阅读和编辑文件的权限。那么我们就不再需要手动的去复制文本，粘贴到项目中的代码文件了。智能体自己会根据 ReAct 这样的一个循环，不断的根据输出的结果，去自动的完成指定片段的复制和粘贴，从而将我们重复的劳动给解放出来。

显然，除了终止条件之外，整套 loop 中间仍然有一些细节需要我们讨论，并且也并非只存在一种可行性。而如何在业务场景下来确定 loop 中的每一个细节，这便是 agent harness 工程师需要完成的工作。在今年某些自媒体中，他们也喜欢把这玩意儿称之为 loop engineering。

所以到底什么是 agent harness？也就是在 ReAct 这个层级对工具，架构，任务执行方式，调度策略基于你的实际业务来进行对应的设计、开发和后续的优化。如果我们将大模型的神奇能力比作CPU那一秒上一次运算的强大计算能力。那么 agent harness 其实就类似于操作系统的设计与开发。毕竟，操作系统本身的设计与开发并没有从物理层面来增加 CPU 本身的运作效率，但是它却行之有效的让人类能够更好的驾驭 CPU。

我举个例子，比如说让我们的智能体在执行某一个任务的过程中，顺带让它将一个文档进行观测和总结，是一个很常见的需求。但如果我们直接的让智能体总结文档，它会直接调用相关的工具，来将一整份文档里面的文本载入整个上下文。不少的文档可能都有100多页10万字，那么可能就直接会占据对应大模型40%的上下文，让之前的任务的执行，直接在后续因为上下文爆炸了失败，或者提前进入压缩上下文，降低使用的体验和成功率。那么这个时候一个优秀的 harness/loop engineering 工程师就应该想到，可以通过调试系统提示词来执行对应的 Agentic RL，并使用 subagent 的方法，让对应的大模型驱动的智能体，面对这样的一类任务时，能够直接将任务开在一个子智能体里面，并直接获取最终的结果，从而完成上下文的隔离。让文档总结这一个任务，不会让上下文爆炸。而像这样的 corner case，在整个 agent 的实际业务开发中有很多很多。

所以通过这个例子，你也能看到，在实际的工业场景的开发中，我们发现 agent harness 和 model training 并不是完全解耦合的，它们之间仍然有一些相关的地方。比如我们上面提到的让 AI 尽可能将文档总结这类任务来开成子智能体，这不仅仅需要对系统提示词进行一定的优化，甚至有的时候还需要来对大模型做对应的 Agentic RL 的训练，来让它记住这类任务，尽可能开子智能体。这个其实就和人类在执行一些任务的时候一样，我们只是修改系统提示词的话，它也只是临时的记住一个指令，而进行训练，则是养成对应的肌肉记忆。显然，一个长期迭代的能够成为业务扛把子的智能体，它一定是需要像人一样在睡眠的时间，加固某些记忆，形成一些业务上的肌肉记忆的。所以从长期来看，一个优秀的智能体的开发中，Agentic RL 训练是不可避免的一件事情。锦恢仍然认为，目前的 AI Agent 的架构设计和开发处于一个早期阶段。随着GPU价格的下降和相关范式的成熟。未来的 agent harness 和 model training 的一部分有可能会慢慢的结合在一起。

所以 agent harness 其实是一个很难一次性概括的概念。因此，我们在下文中会基于 coding agent 这样的一个最为典型的 agent 的场景。来讲解一下，在 coding agent 这个场景下，一些已经被工业界认可与践行的 harness 是怎么设计出来的。而熟练掌握 coding agent harness 的设计，能够有助于你在其他的业务场景中做出相仿的设计。

> coding agent，也称编程智能体，顾名思义，专门用来写代码的智能体。claude code，codex，cursor，kimi cli 都属于典型的 coding agent，coding agent 公司也引领了这个时代整个智能体协议、规范、标准、技术方案等等各个方面。想要跟进 agent 技术前沿，最好的方法就是去阅读这些 coding agent 公司的博客，譬如 <https://www.anthropic.com/engineering/>

## 4.2 规划模式 plan mode

### 4.2.1 为啥需要 plan mode

通过前文中的描述，你会发现当前的这样的一个 agent loop 在运行的过程中，实际上它是不断的会将看到的结果、执行的结果、用户的命令，一点一点地装入上下文里面，其实也就是一个 messages 数组里面。随着任务的执行，这个数组会越来越长。

而每一次执行大模型都会将这个数组从头到尾重新读一遍。这个做法在面对简单任务的时候，比如说查询一下万象城的泰式餐馆里面我最喜欢的咖喱饭，今天还有多少库存，自然没有问题。但如果是执行一些稍微复杂一点的任务，在实践中我们发现了一些新出现的问题。

就拿 Agent 最典型的场景写代码来说，假设我们一直让 AI 帮我们写代码，现在有用户反映了当前我们的APP上某一个按钮，它的点下去之后有错误，或者没有反应。那么这个时候我们直接让AI帮我们改代码的话，大概率就是说出如下的一段提示词“有用户反映说圈子页面的按钮点下去之后没有反应了，你帮我解决这个问题。”对于一个有经验的工程师来说，面对这样的一个需求，往往我们会经历如下的几个步骤：

1. 先阅读仓库里源代码，找到用户反映的这个按钮，它所在的代码文件。

2. 根据用户的反馈和上下文修改这个问题。

3. 完成对应的测试，防止发生软件回归问题或者破坏其他共同祖先依赖项的子功能。

4. 提交推送代码。

5. 部署软件。

如果没有 plan 模式，让 agent 单纯只是执行一个非常简单的 agent loop，那么AI有可能就直接根据当前的需求去**盲目**的更改代码了，而不会考虑到一些更加深远和系统性的问题，很有可能它改了某一个细节代码之后，就立刻停止工作了。因为在某个细节问题上，连续工作若干轮的agent loop会改变当前大模型的一个注意力，让它将注意力，从用户的需求变为了当前修改的某个代码细节，从而让大模型想到要做后续步骤的概率变低。

加入了 plan mode 之后，智能体就会通过一些特殊的工具（子智能体那一章节会讲），先完成整个项目的扫描和上下文的分析，并且罗列出一份完整的计划，然后再根据这份计划去执行。从而保证整个执行的过程能够更加的系统和完整，或者说可以更好的对齐用户需求中任务的语义。其实就和我们人一样，当我们想要去超市买个菜的时候，我们往往是凭借本能和记忆，立刻就前往地铁口到最近的超市买菜了。但如果我们要做的事情是前往一个陌生的城市旅游，我们并不会不加思索的立刻开始行动，而是会在小红书上找攻略，然后再看自己未来几天的日期安排，从而给自己的旅行计划做出一个规划：哪一天要去哪个景点，通勤怎么安排，住宿怎么安排。其实这也就是 plan。从人类的角度思考，为什么人需要plan？因为我们的大脑容量有限，我们很难在短时之内迅速处理一个庞大的任务。简单的来说，就是人类的上下文和注意力是有限的。那对于大模型而言，其实也是类似的。所以才需要使用规划模式来对复杂任务进行拆解，从而在有限的上下文中完成尽可能庞大而复杂的任务。

> 从形式上，大家有没有觉得这个过程特别的像大模型的思维链呢？我们当初提出思维链的时候，也是让大模型先思考用户的需求，然后再根据结果回答用户的问题。这种分部的执行非常有助于大模型更好的充分理解上下文，并给出更加对其用户想法的回答。而这种具备思维量的大模型，往往被我们称之为推理模型，比如当年让思维链火起来的 deepseek r1，这个模型在 deepseek 官网上的调用名就叫做 deepseek-reasoner。而 plan 这个模式特别像智能体这一个层面的思维链，所以业内大家也经常将这样的一个步骤称之为 Agent reasoning 或者 Agent Inference。

下面就简单讲讲在主流大模型厂商中，规划模式的一个工程实现。

### 4.2.2 EnterPlan 和 ExitPlan

那么从 harness 层面，要如何实现 plan 呢？业内主流的实现方法为，提供一对工具 `EnterPlan` 和 `ExitPlan`，当然，这也是 Agent 的内置工具。如果当前用户在外部开启了 plan 模式，那么 100% 会在 agent loop 的第一轮中就调用 `EnterPlan` 进行规划模式，该模式下，agent 的所有写操作属性的内置工具和 MCP 会被全部禁用，它会通过只读工具去捕获更多的上下文，从而在执行任务前考虑到更多的细节。

当AI觉得当前的规划已经完成之后，它通常会生成一份规划报告来让用户进行审核，那么智能体系会通过使用 `ExitPlan` 工具来退出规划，从而提交这份规划的审核报告给用户，让用户定夺是否要批准这份报告，或是给予一些额外的提示和上下文。

这里的细节实现在业界又分为两派，一派主张直接通过工具生成一份文档模式的“规划书”和配套的 TODO 列表，另一派则主张生成一张 DAG（有向无环图），每一个节点都会派遣一个子智能体去执行，主节点的智能体则负责统筹与调度。本文主要讲的是前面那一派，如果你能理解前面那一派的做法，后面那一派的做法其实理解和实现起来也非常容易。

### 4.2.3 AskUser

为了降低智能体的幻觉，最好的方法就是给智能体提供更多的有效上下文。而提供有效上下文的方法，目前主要有两种，一种就是让AI通过只读工具去阅读文档源代码或者是网络上搜集到的可信信息；第二种就是询问用户了，也就是 `AskUser` 这个内置工具，上游的大模型会在后训练的时候，被训练的更加积极主动的调用这个工具，向用户询问信息，从而避免因不知道某个信息产生幻觉，最终将任务搞砸。

比如说下图就是我在使用某家 coding agent 来开发一个用来进行线上业务的某个 AI 功能评测平台时，这个 agent 通过 `AskUser` 工具向我提出的4个问题。通过这4个问题，它能更加精准的知道我的“描述足够精准”的真实诉求。比如说后台管理系统的AI评测里面上传的图片应该存储到哪一个 COS 的 bucket 里面。这会关乎到当前的存储代码是否有效，是否能够在线上也仍然被访问到，是否能够不增加当前维护的额外风险等等。而如果AI不问这个问题，他就可能会因为幻觉发作而随机用某一个 bucket，导致我们后续的图片上传都失败。

![图片](https://kirigaya.cn/api/storage/image/d1e5875b-9ae6-423e-9881-7591b9663765.webp)

而 `AskUser` 这个工具是众多的agent的厂商的agent在 `EnterPlan` 调用后下经常会调用的一个工具。

### 4.2.4 Explorer

而针对于 coding agent 这个场景，获取上下文的一个相当关键的方法手段就是阅读项目的源代码。而很多大型项目的代码非常非常大。比如说我有个哥们儿最近就在根据他们的业务场景去修改虚幻4引擎的源代码。这个源代码可能就有几百万行。那么AI一读几百万行的源代码，在规划模式下就直接将上下文给撑爆炸了，并会极其严重地影响其他部分的注意力权重。为了避免这样的一个问题，在 coding 场景下的规划模式下，有一种特化工具，用来阅读源代码，那就是 explorer。

explorer 的本质就是一个被严格规定了工具权限的子智能体。和正常进入规划模式的主智能体一样，explorer它只具备基本的文件阅读能力，它不具备任何的编辑修改的能力。除此之外，explorer它可以搜索网络，但是被禁止派生新的子智能体。

以 kimi cli 的实现为例，explorer 它的system prompt核心就两句话：

* **"You are a codebase exploration specialist"** — 定位自己是代码库探索专家

* **"You do NOT have access to file editing tools"** — 明确禁止写操作

它基本的操作权限如下

| 维度 | Explorer 拥有 | Explorer 被禁止 |
| :--- | :--- | :--- |
| 文件操作 | `ReadFile`, `Glob`, `Grep` | `WriteFile`, `StrReplaceFile` |
| Shell | 只读命令 (`ls`, `git log`, `find`) | 任何创建/修改命令 |
| 网络 | `SearchWeb`, `FetchURL` | — |
| 递归 | — | `Agent`（禁止创建子agent） |

虽然 explorer 专为阅读和寻找代码片段及其 reference 而生，但想法是共通的，稍加改造也能应用到某个其他场景的 agent 的规划模式中。请善加利用，我的朋友。

### 4.2.5 TODO

在很多成熟的coding agent中，相信大家在执行规划模式时都会看到agent会在当前的工作区域下面固定创建一个 TODO 列表。比如下图是我在使用 kimi 解决一个软件的bug时，它创建的 TODO。

![图片](https://kirigaya.cn/api/storage/image/6432461e-2e71-4ad7-9f3b-5dd9f9e3e304.webp)

而创建和编辑这样的一个 TODO 列表，也是目前的 coding agent 的一个内置工具。而这样的一个工具，它的目的就是为了防止当前的agent在超长任务执行中发生偏移。比如说我们让智能体帮我们创建一个网站，那么目的是完成这个网站的创建和验收。但在创建网站的过程中，智能体可能会因为当前的电脑版本或是一些客观环境的问题，在某几个依赖的安装上，从持续的失败，从而钻牛角尖将当前的任务目标从验收创建网站变成了解决这个依赖，并在完成依赖解决之后立刻停止工作。

这是大模型的注意力稀疏问题导致的。因为随着消息的变长，原本用来指导大模型完成任务的这个具体任务的消息片段，它的注意力会慢慢的变少。而排在消息最末尾和最开头的信息永远会被给更多的注意力。而最末尾的信息也就是AI在持续解决的这个依赖项问题。所以智能体在任务执行的过程中，就会逐渐的将原本的目标偏移到解决当前的依赖项。而这个问题一般被我们称之为目标漂移（target shift）。

为了解决智能体在执行程序列任务时的目标漂移问题，社区中提出了很多的方法，而通过社区中工程师们的持续尝试，大家发现在规划模式下给智能体一个 TODO 来让它可以在一开始就将任务目标写到 TODO 里面，并且在任务执行的过程中能够来持续的查询这个 TODO 的内容，可以很好解决目标漂移的问题。而早期的智能体并不支持to do，所以社区中又涌现了很多的skill。

而目前主流的 coding agent 都已经在智能体的内置工具表和前端 AI 编辑器的渲染组里面支持了，并且对这项能力也进行了一定的 agentic rl 的特化训练。

如果大家在构建自己垂直领域和业务的智能体时，也发现了业务中的错误，能够归结为目标漂移，那么不妨尝试往其中加入 TODO 这个内置工具来解决这个问题。

## 4.4 子智能体 subagent

通过前面的文章，大概大家应该对规划模式和对应的细节有了一个大概的认识，也应该能够认识到 harness 工程师大概是做一件什么样的事情。没错，从总结凝练编程智能体实际业务场景的技术问题的本质，再到这些 coding agent 的内置工具的开发，这些都是 harness 工程师需要负责的工作。

而在刚才的叙述中，子智能体这一个名词被我们提到了很多遍。在这一个章节中，我们就将详细的聊一聊子智能体它的一个设计初衷和一些细节。

工业界大家对于子智能体在智能体系统中的提出最初的原因莫衷一是，但在锦恢的记忆中，大家谈子智能体最初的一个缘由是从强化学习领域的多智能体 marl 泛化出来的一个想法。社区中对于子智能体的一个架构设计，也有很多很多的讨论，比如，关于中心化和去中心化的设计。这些讨论，其实我认为大部分是没有意义的。所以我也不想在文章中详细的讲这些东西，我只讲目前的 coding agent 里面常见的一个子智能体，它是如何在系统中被设计和排布的。

### 4.4.1 子智能体提出的场景

子智能体非常显而易见的需求，其实是来自于这样一个场景：智能体在执行某些任务的过程中，有些任务其实本身是可被拆分的，但这些任务仍然线性的被添加到了智能体的上下文里面，从而造成了大量上下文的浪费。而实际上这些操作本身是可以被拆分出主任务单独的执行的，不仅可以有更好的鲁棒性，而且能够隔离出上下文，防止上下文被挤压。

我们可以举一个例子，那就是让智能体开发一个对应主题的网站。如下图所示。

![图片](https://kirigaya.cn/api/storage/image/63fe35db-b951-4e36-8206-f98e1b71c266.webp)

正常情况下，大模型驱动的智能体会正常的安装依赖环境，并且逐步的实现对应的代码，最终完成网站的创建。这个过程中有可能在某些环节上，智能体会产生很多的 rollout。比如说安装很多依赖，并且这些依赖可能和本地的一些组件会有冲突。智能体可能会花很多很多时间去解决这样一个问题。而这些问题的解决本身可能会占据了30%左右的上下文，而在很多复杂任务的执行中，上下文是非常珍贵的。因为大模型因为智能体会持续的根据上下文去做出各种各样的决策，直到上下文被占满为止。这个时候很多智能体虽然会对上下文进行一次压缩，但是这个压缩本身其实会丢失很多宝贵的信息。所以，有效的管理上下文仍然是一件非常重要的事情。

而针对这样的一个操作，由于安装依赖项这个过程，其实它和我们完成这样一个网站创建的业务是正交的。也就是说我们完全可以将安装依赖的过程单独抽离到一个新的智能体去完成。而主智能体只需要和只需要派发给这个新的智能体安装依赖项的任务，并且最终只要看到这个依赖项是否被安装成功就行了。至于中间的过程，其实我们不关心，我们的主智能体也不关心，只要能保证这个依赖被安装成功就行了。所以我们就可以将安装依赖项这样一个与主业务正交的步骤完全移动到一个新的子智能体里面。如同上图的右图所示。而移动完成之后，在主智能体这边原本可能要通过几十步才能完成的依赖安装变成了派生一个子智能体，并且在一定时间内获取它的输出这样的一个过程。那么整体的上下文就有可能会从30%降低到1%、2%这样一个很小的数字。

这就是子智能体设计的一个最基本的初衷，那就是隔离上下文。而隔离上下文的原因有很多，我们上面提到的将正交的业务执行移交到子智能体，从而节省主智能体的上下文，这只是目的之一。还有一些别的目的。而这些目的无论如何，都离不开大模型本身的一些缺点。那就是上下文窗口有限和注意力有限的问题。这些其实在我们过往的章节中都已经提到了。不过在这里我们再次声明一下：

* 上下文窗口有限：大模型的上下文是有限的，并不能往里面塞入无限的文本或者是数据。

* 注意力有限：由于transformer本身的架构，大模型倾向于将更多的注意力移动到整个message数组的开头和结尾。随着任务的执行，中间发生过的一些操作大模型会逐渐“淡忘”。

除此之外，使用子智能体还有一个好处，那就是主智能体可以更加方便地来完成任务编排了。在我们的第一章节中提到了workflow这个概念。

> 第一章节指引：<https://kirigaya.cn/blog/article?seq=351>

![](https://pic1.zhimg.com/80/v2-17b8440b0a32b1df06a36fe954ccd4eb_1440w.png)

比如这样一个用来爬取 github 流行项目的一个 workflow。如果大模型本身已经做了相关的训练，那么主智能体在规划模式下完全可以生成这样的一个编排任务，并且为每一个节点派生子智能体来完成执行，从而全自动的完成一个workflow的创建和执行。

所以从趋势来看，autonomous agent 可以在最终完成一小部分 workflow 的取代。这两者并非是完全独立的。

### 4.4.2 子智能体工程实现

在工程实践中，我们通常并不会从头实现一个子智能体的类，而是在正常的智能体类实现的时候，就考虑到派生子智体的情况。当我们需要真正实例化一个子智能体的时候，只需要对正常的智能体内施加额外的初始化参数即可。

以 kimi-cli 为例，它的用于进行主智能体和子智能体派生的配置如下所示。

| 参数 | 类型 | 默认值 | 说明 |
| :--- | :--- | :--- | :--- |
| `description` | string | 必填 | 任务简短描述（3-5词） |
| `prompt` | string | 必填 | 任务详细描述 |
| `subagent_type` | string | `"coder"` | 内置子agent类型：`coder`/`explore`/`plan` |
| `model` | string \ | null | null | 可选模型覆盖，优先级：此参数 > 类型默认模型 > 父agent当前模型 |
| `resume` | string \ | null | null | 恢复已有实例的 agent_id |
| `run_in_background` | bool | false | 是否后台运行 |
| `timeout` | int \ | null | null | 超时秒数（30-3600），前台默认无超时，后台默认15分钟 |

只需要指定一下上面的各个参数，就能实例化出一个对应的智能体。根据`subagent_type`的不同，派生出的智能体能够使用的工具也不一样。比如 plan 就是我们之前提到的规划模式，在客户端上，如果你将当前的开发代码模式转成了 plan 模式，那么当前默认派生出的智能体就会是 plan，否则就是 coder。

而正如前文所言，plan 模式下的智能体系是不具备任何编辑文件的能力的，它只具备一些只读能力和 TODO 等等利用进行长任务规划的能力。

`subagent_type`为 explore 时，就代表这个子智能体是一个 explorer，和 coder 相比，explorer 只具备读取文件和网络搜索等利于聚合代码上下文的能力，不具备编辑文件，派生智能体的能力。

从技术角度来说，如何进行沙盒隔离，子智能体生命周期的定义和管理，执行过程的恢复和持久化是构建子智能体较为困难的技术点。不过这些技术就过于琐碎了，本文就不再赘述了。

### 4.4.3 编程智能体的使用技巧：主动使用子智能体分解任务

下面这部分原本是想在氛围编程系列中讲的，但是此处关联性比较大，所以顺带讲一下。那就是当大家了解到子智能体的一个基本原理和它解决的问题场景之后，就应该能想到，当我们使用编程智能体在处理一些可被并行化分解的任务时，我们就应该想到能够主动的让AI使用子智能体去做这件事情，而不是直接让AI顺序的去做这件事。

我举个例子，比如说当大家使用 codex 来帮我们的代码项目生成部分的美术资产的时候。基本的一个提示词可能是下面的这样一段话：

```
请帮我从 foods 表中找到所有封面还没有填写图片链接的记录，并且基于这些记录本身的 description 字段来帮我使用 image2 绘制对应的图片，并上传到静态存储后，完成 food 表的落库。
```

假设这张表里面还没有完成图片链接填写的记录有100条。那么 codex 就有可能会顺序的去一张一张的执行上述的这样一个流程。而随着上下文的逐步增大，原本的这样的一个命令，它的注意力会慢慢缩小。很有可能codex生成到第10张图片完成落库之后就停止工作了。但我们想要的一个效果是这样的一句话施加下去之后，codex 能够持之以恒的去执行任务，直到100张图片全都完成生成，并且落库。具体的执行时间我们并不在意，我们只在意这个过程必须全自动完成。这样我们才能去干别的事情，而不用关心此处的进度。

显然，我们重新看一下这个任务。很显然，这个任务里面需要执行的100条记录，它们彼此之间都是相互独立的，这100个任务是完全正交的，它们完全可以并行的执行。所以我们可以考虑把这100条记录分配给若干个子智能体。然后再让我们当前的主智能体去管理这些子智能体，从而全自动的完成这个可能会消耗很长时间的任务。

所以当我们理解了子智能体的基本原理之后，我们就可以对上面的提示词做出如下的修改：

```
请帮我从 foods 表中找到所有封面还没有填写图片链接的记录，并且基于这些记录本身的 description 字段来帮我使用 image2 绘制对应的图片，并上传到静态存储后，完成 food 表的落库。
你需要将处理这些记录的任务分配给若干个子智能体，每一个子智能体最多处理 5 个记录。
```

有了这样的提示词之后，在获取了当前记录条目之后，当前的主智能体就会调用 subagent 方法来派生出若干个子智能体完成任务。在codex里面，你能在当前面板的右侧区域看到目前开启的所有子智能体，并且通过点击它们来查看每一个子智能体内部的完成情况。

![图片](https://kirigaya.cn/api/storage/image/f1cc9f30-9830-4966-ad95-50827c23dfd6.webp)

在 qoder，vscode 等等 AI Editor 里面，也有类似的前端面板方便查看。大家不妨去试一试玩一玩，来更加有效的将自己的工作内容自动化。
