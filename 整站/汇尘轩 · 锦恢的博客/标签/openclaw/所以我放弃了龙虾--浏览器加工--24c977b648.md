## AI 时代的“人月神话”

喜欢写软件和做产品的朋友，一定听过“人月神话”这个经典的软件工程学难题。这个难题指的是，软件开发并不可以靠多加人来线性的提升工程的推进速度。在很多情况下，同样一个工程软件项目，你让参与的人变多，反而可能会让整体的软件开发效率变低，甚至在某一个节点引发崩溃问题。

### 历史上最著名的人月神话事件 —— IBM软件危机。

要说人月神话，那就不得不谈这个名词的起源和它最著名的那场历史事件——IBM软件危机。

上世纪60年代，IBM 为统一其混乱的计算机产品线，启动了史无前例的 System/360 计划，并试图开发一套通用操作系统 OS/360。起初他们相信，可以通过增加工程师人数来压缩开发周期，但随着项目推进，人员规模迅速膨胀，沟通成本、培训成本与系统复杂度同步失控。

最终结果是：人越多，进度越慢；系统越做越大，问题越积越多。项目被迫延期、超支，并经历多次重构与功能削减才勉强完成。

这场危机过后，该项目的项目经理 Fred Brooks 并就开始进行了事后的复盘，并且最终写出了那本计算机界非常知名的书——**《The Mythical Man-Month》**，翻译成中文就是《人月神话》。

在这本书中，Brooks 跨时代地提出了多个至今仍适用的原则：

* 人月不可交换（9个女人不能1个月生出孩子）

* 软件复杂性是本质问题

* 没有银弹（No Silver Bullet）

人月神话这本书至今仍在深刻的影响着软件工程本身，无数不信邪的组织也在上面栽了一次又一次的跟头。

### 小龙虾的 PR 泥潭 —— 人月神话的幽灵

而如今的小龙虾项目也遇到了 “人月神话”，只是非常有意思的是，这一次故事的主角从人变成AI。

我们点开小龙虾的项目主页，不难看到它的 issue 和 pr 都已经完全超出了 github 预设的最大值。这里简单对非程序员背景的朋友解释一下什么是 pr，我们都知道开源软件是由社区组织的，网络的上大家就像给一个文章写评论一样，为这个项目贡献自己的代码，从而让一个项目变得越来越丰富和庞大。而为一个项目贡献自己代码的方式，就是通过提交 pr 来实现。

显然，一个项目的 pr 越多，后面这个项目越受欢迎。因为大家都想要贡献自己的代码。

![图片](https://kirigaya.cn/api/storage/image/5ec1ff4a-f56d-40b6-b52d-6f6f46558441.webp)

作为项目的发起人和作者，我们肯定是非常乐意看到有其他人为我们的项目贡献代码的这不仅仅是为我们分担了一部分的开发压力，也是社区对于项目的一种认可。

说的更加通俗易懂一点。假设我们将一个开源项目看成是一个公司的项目，就好像我们刚才提到的 IBM 的 360 项目一样。那么这个项目的作者和所有提交 pr 的贡献者都可以看成是这个项目的一个员工。那么自然而然的，人月神话这个现象在开源社区的这种协作模式下仍然存在。

小龙虾的平均项目贡献频率可以达到1个小时50个 pr。也就是说一个小时会有50个员工向你提交他们的工作结果，而你需要对这些工作结果进行一一的校验与合并，来保证系统仍然可以健康的运行。显然，这对于一个人来说是根本做不到的。

> 甚至你无法完全信任这些社区的成员。因为你无法保证他们的 pr 里面不含有恶意代码和病毒，或者是广告下崽器。在公司里面，大家是拿自己的职位和奖金作为担保来担保自己的工作成果的。但是在开源社区中能做担保的也只有自己的账号名誉了，但是大部分人是没有名誉可言的。全球开源项目中核心中的核心项目 ssh，在去年就被爆出在开源项目的贡献者中正常贡献了好几年代码的人被报出是潜藏的黑客，并往 ssh 新版本中注入了病毒，用来窃取用户的服务器密码。
>
> 正是由于这种问题，所以很多知名开源项目看起来是社区中大家一起做的一个项目，其乐融融，一片盛况。但实际上这个项目的所有贡献者可能都是在一个圈子里，他们拒绝圈外人为他们贡献代码。当然扯远了，这些都是一些补充知识了。

所以基于这样的一个现状，Peter的团队不得不采取了AI校验与AI合并，这边促成了vibe coding有史以来第一次大规模的管理学实验，也就是尝试通过AI的方法来解决人月神话，这里我就不谈各种各样引发人类神话的技术细节了，单从结果而言来看的话，AI管理下的代码交验与合并似乎并没有很好的解决海量贡献代码带来的项目管理混乱的问题，bug仍然层出层出不穷，回归问题时有发生，并且软件本体变得越来越臃肿，启动时间变得越来越长，整个软件的结构风险在不断提升。更不用提AI合并的提交给小龙虾的代码本身也是由各种各样的AI生成的。

所以这不得不让我们重新审视那个困扰了我们若干年的问题——人月神话这个问题，真的能在这个时代得到解决吗？AI真的有能力在没有高级工程师的指导下，不引发回归问题和软件和降低软件本身健壮性的情况下来合并海量代码，并且自动的帮我们更新迭代其中的部分需求吗？

我想小龙虾的这一次管理学实验已经回答了部分答案——人月神话的幽灵仍然飘荡在 vibe coding 时代。

## 龙虾的替代方案

那么说了这么多玄乎的东西，是时候回答一下观众们最感兴趣的话题了——假设龙虾的项目最终烂尾了。那么我们有什么替代方案呢？

有的，朋友，有的。

### 各种各样的虾兵蟹将

其实对于龙虾目前架构的担忧与不满，很早就在开源社区酝酿了。一些人像我一样只会动动嘴皮子，还有一些人则是切实行动起来。交出了自己的一份答卷。这里就给大家按照优先级隆重推荐几个我认为很好的取代方案：

* Astrbot：<https://github.com/astrbotdevs/astrbot> ，经久不凡的老牌 IM 框架机器人，它几乎拥有小龙虾的一切功能，而且有一个图形界面，能够极其友好的来让普通用户也能安装与配置机器人。龙虾爆火之后， astrbot 社区炸就好像直播没来得及顶号被毁号的倒霉蛋一样非常生气。因为大家都知道他做的其实比小龙虾更完善，但是爆火的却不是它，Astrbot 社区将愤怒化为了持续更新的动力。所以如果大家对小龙虾颇有微词，可以尝试用这个项目来满足你们的工作需要。TIP：这个项目对国内的很多聊天软件做的特殊支持，使用体验会更好一点。

* Ironclaw：<https://github.com/nearai/ironclaw> ，用 rust 重写了一遍的龙虾框架，跟 openclaw 功能基本上没有差别，但是作者特化了它的安全性并重做了执行容器，对云服务厂商更加友好。

* Tinyclaw：<https://github.com/warengonzaga/tinyclaw> ，专为树莓派等嵌入设备特制的超轻量化小龙虾，去除了作者认为不该有的一些冗余功能，保持极简性，对定制化要求很高的朋友，可以考虑使用这个项目进行改造。

* LBot：<https://github.com/LSTM-Kirigaya/LBot> ，超级精简的智能体项目，可以直接用于 QQ 的机器人群管理员，并且也可以支持极其灵活的定制。非常适合初学者用来快速了解一个 AI Agent 聊天机器人的基本结构和聊天软件网关层的协议细节，也非常适合需要定制化的一些朋友来进行改造。它本身提供了一个极简案例来告诉大家如何将聊天软件本身的各项基础功能包装成一个MCP。（当然，这是我写的）

### 你需要的未必是小龙虾

在小龙虾刚推出那一会儿，网络上有很多反对的声音，说我本地的kimi或者是 claude code 也能完成完全一样的效果。唯一的差别就是少一个飞书这样的用户友好型的聊天界面。那么有没有方法来直接把 claude code 和 kimi 这样的本地的智能体接入到飞书或者是QQ这样的聊天软件里呢？

有的，朋友，有的。

通过ACP协议，就可以立刻把任意编程智能体接入到任意的聊天软件里面。具体可以看我的这篇博客：[想要在任意聊天软件里面使用 kimi, claude code 这样的编程智能体？ACP 协议一键搞定！](https://kirigaya.cn/blog/article?seq=371)

我现在一部分的工作负载就是通过这套方案实现的。比如我现在让5个智能体帮我干活，结果有一些急事，我需要出去一趟，一个小时之后才能回到家。但是我给Aent派的这些活，他们有可能10分钟之内就解决了。而下一个我需要发送的命令，可能非常非常短，但必须得由我来通过简单的评估之后发送。

这个时候就非常尴尬了，相当于我们浪费了50分钟的时间。这50分钟之内，原本其实可以让AI干更多的事情。

所以我的方案就是通过上面那篇博客的方法，将我本地的一个kimi接入到了我的飞书机器人里面。这样的话，我出门的时候就可以立刻的通过飞书的机器人，直接查看kimi每一个session的工作内容，并且进行额外的提示词输入，让它继续干活。而我每次只要打开手机简单看一看，然后用语音输入，输入几句话就可以完成。大部分时间我可以看看小说听听歌，或者是和我的合作伙伴进行商业会谈。

## 龙虾工程给于我们的经验与教训

其实许多人包括我在内一开始对于龙虾的结构上的缺点，反应是比较集中的。我们认为龙虾它不应该一次性做出这么大一个系统。计算机从发展至今这么多年，一个大优良传统就是做抽象。一个逻辑一旦复杂了，我们就会将它抽象出来再进行发展。而抽象的层与层之间则通过协议和规定的方法来进行连接，门级电路，芯片指令集，语言操作系统，高级编程语言。一路上都是这样不断抽象的。

### AI Agent 的三层抽象

而对于如今的 AI Agent 来说，这种抽象的时候也应该到了。实际上，通过过去若干年的发展，目前的 AI Agent 已经发展出了如下图所示的一个架构。

![图片](https://kirigaya.cn/api/storage/image/4ec401b5-b084-4d65-bb2c-c38348d53354.webp)

整个层面的核心就是中间的这个智能体循环，也被我们称为 Agent Loop（对内部原理感兴趣的朋友可以阅读 [锦恢的 AI Agent 小白教程（一）Agent 的基本概念与分类](https://kirigaya.cn/blog/article?seq=351)），大家好像人类的小脑一样，允许大模型这个大脑进行工具的调度和各种资源的选配。常见的 Claude Code，Kimi CLI，Cursor 这些都算是智能体循环层的产品。

在智能体循环层之上的就是 Harness，这个名词相信大家最近也听的非常多，有不少的自媒体都在发软文说这东西在硅谷爆火了。其实 Harness 也没有那么玄乎了，Harness 的英文是马鞍的意思，意思就是套在「大模型」这个马上的辅助工具。它指的就是 agent 可以使用的各种基础组件。比如说大家耳熟能详的SKILL，MCP，还有各种可以让智能体保持 长期记忆的记忆模块，他们都通通属于这一个层级的内容。随着业内的发展，最新业内的认知，我们将这个层级分为两个大致的板块——Agent Infra 和 Agent CLI。

> 我会在后续的内容中讲解它们的基本定义和可能带来的商业机会。感兴趣的朋友可以关注我的微信公众号「汇尘轩」的「Z 世代智能体」专栏，或者是订阅我的个人网站「汇尘轩」，订阅方法，移步文章末尾。

gateway 层就顾名思义了，这个层定义了 AI Agent 要如何跟我们真人进行交互，gateway 层实现了飞书，那我们就可以在飞书里面和 AI Agent 进行交互

gateway 层实现了微信 QQ，那我们就可以在微信QQ里和这个智能体系统对话，帮我我们解决工作中的问题。

如果我们在智能眼镜或者是智能项链里面实现了对应的gateway层，那我们就可以通过我们的智能眼镜和项链来与智能体系进行对话和工作协作。一个最容易想到也是我正在做的方向，便是把很多常见的 toC 产品通过 gateway 层的方法来接入到AI眼镜里面，从而用户有一个更好的使用体验。比如说你在健身的时候使用健身软件可能会觉得很麻烦。但如果健身软件本身做成了 AI Agent，并且还实现了对应的 gateway 层，那你就可以在带上AI眼镜的过程中间边健身，边让AI给你各种各样的建议，或者是情感陪伴。

### 龙虾的现状

而小龙虾则是一次性的将这三个全部做成了一整个大的系统，这违背了龙虾只想做 gateway 层的初衷。当整个业界其他层还在处于一个发展阶段，并没有成熟解决方案的时候，就贸然的将这三层强行的揉合成一个产品。再加之我们之前讲到的人月神话的问题，整个龙虾项目未来能否稳定的迭代，并且持续跟上业界不断产生了新的技术。我觉得这得打个问号。

而我认为的一个合理的做法，就应该是分层之后的每一层，由社区或者是商业公司自行地进行横向拓宽，来在业内不断形成成熟的解决方案。最终大家才通过层间的衔接，完成整套系统。这样设计在工程上不仅更加利于功能拓展和风险的排查，并且也能带动更多的 AI Agent 领域的就业岗位，让整个行业可以更加可持续的发展和扩大。

### 龙虾的人月神话真的就没有解决方案了吗？

答案肯定是否定的。我相信随着人工智能技术和方法论的不断跟进，过去的软件工程中的很多问题是可以被解决的，或者说是可以在一定程度上被化解的。

随着AI编程技术发展的这几年，其实很多有经验的开发者都能慢慢的注意到一件事。那就是在开发产品的过程中间，实际上我们耗费精力并不在于单纯的敲那一行行代码上。做一件产品最耗时的也最精贵的永远是需求的收集和整理的过程。

我们可以看下面这张图，它代表了软件在迭代过程中发生的几个环节。我们从不同的信息源，有可能是用户的内测群，有可能是市场部门的综合报告，也有可能是其他的地方搜集到了需求。这些需求会经过一步又一步的讨论和否定，最终变成精细化的提示词。投喂给AI来让帮我们实现大量细节上的代码。最终我们再进行验证和回归测试，这是一个 AI Coding 时代目前逐渐兴起的工作流。

![图片](https://kirigaya.cn/api/storage/image/2e26c4e3-faad-4d49-b0de-73f26cd97314.webp)

这套工作流程事实上它也是适用于小龙虾的迭代的，而且从大家向小龙虾贡献的代码出发，我们并不是为了写代码，而向小龙虾贡献的，而是出于对于某一个需求的需要有了这个需求，我们在实现了小龙虾的这一个代码。但问题就在于这个需求实现本身有可能会和现有的需求发生冲突。比如说最典型的就是我们上文最早提到的权限设置的问题。龙虾内部其实是有一套非常完善的 hook 系统，你完全可以利用已有的三层权限模型开源项目结合这个 hook 系统做一套定制化程度提高的权限管理系统，但是现在又有人直接给它增加了一个一刀切的命令权限申请，这就与之前的设计矛盾了，所以在用户使用起来就会感到非常的别扭。并且这套系统它并没有考虑到已经建立起的会话。任何关于这个新的权限的系统文件修改，它都不会影响到老的会话。这导致了新的权限管理方案生效了，但是你改了全局配置文件之后，老的会话并不会因此而发生修改，就导致很多的请求就会发生失败，机器人反复的向你索要权限，但是给了之后很快就失效。

这样的问题在系统扩大之后会越来越多。这是因为AI在写代码的时候，它也只能看到这10%到20%的耗时的部分。它并无法看到左侧最耗时这一部分的内部逻辑关系，就导致修改了一个功能之后，某些老功能也受到了功能影响，甚至直接出现了严重的bug。这并非是技术实现上的问题，而是从需求层面出发，AI它就看不到需求的全局。因此实现了某些小的细节与已有的需求框架出现了冲突而不自知。

并且我们做产品的时候，很少有人会写整个项目全局的需求文件，很多东西都是我们想到什么做什么，而并不会留有一个和项目孪生的需求文档。就算留下很多人的需求文档，其实也并不算是需求文档，而是技术文档。你从这份文档里很难还原出整个项目的商业闭环逻辑和设计功能全景。

所以我认为在AI时代软件工程需要越来越多的将注意力从接口级别的架构慢慢移动到需求工程上来。我觉得需求工程会是一个未来重要的研究方向。如果哪一天我们能做到「需求即提示词」，并且这个过程中还能辅助以各种各样的冲突与风险检查，那么上面的很多问题都可以得到解决。
