## k1. $state 数组的响应变化

在 vue3 中，我们使用这样创建任何一个响应式的数组：

```typescript
const reactiveArray = reactive<any[]>([]);
```

这样外部只要对这个数组进行任何操作，Proxy 都会进行拦截和响应。

在 svelte 中，我们通过 state 来创建响应式数组：

```typescript
let reactiveArray = $state<any[]>([]);
```
并非所有对这个数组的操作都会让 svelte 去响应。根据我的使用经验，只有当数组长度发生变化时，这玩意儿才会响应。

假设你在响应式地通过这个数组去渲染一个视图，你现在只是想要改变其中一个项的属性，然后让DOM发生变化。

```typescript
let reactiveArray = $state<any[]>([
  { name: "kirigaya", avatar: "https://xxx" },
  { name: "peace", avatar: "https://xxx" }
]);
```

如上，假设，你要把第一个项的 name 改成 `kirigaya123`，那么只是  `item.name = "kirigaya123"` 这样是没用的，你必须重新创建一个新的 item，然后：

```typescript
reactiveArray[0] = newItem;
```

这样才能引起一次响应。

## k2. 观测也会引起变化

新版本的 svelte 鼓励用户通过 $effect 来捕获响应式变量发生的句柄。

```typescript
$effect(() => {
  // 页面挂载时进入
  // 位置1

  return () => {
    // 页面销毁时进入
    // 位置2
  }
});
```

svelte 会在编译的时候，会遍历整个 effect 内所有函数调用中涉及到的 rune 变量（比如 state）。只要有其中一个 rune 发生变化，effect 的 「位置1」 那个地方就会被扔进微任务队列中去执行一次。

这意味着什么，这意味着你就算只是 log 打印了一个 rune，当这个 rune 发生改变时，「位置1」 都会被执行一次。这在我们对一些复杂页面和功能进行调试时，会带来一些很麻烦的问题：


```typescript
function render3D() {
  // shaderMode 是来自其他文件的一个 rune
  console.log($shaderMode);
  // 执行一些很消耗性能的操作
}


$effect(() => {
  if ( /* 一些判断 */ ) {
    render3D();
  }
});
```

这个例子中，如果外部修改了 shaderMode 这个 rune 的值，那么 render3D 就会被执行，这在很多场景下是不应该发生的事情。

如果你在调试你的 svelte 代码时，发现一些函数被意外执行了好几次，那就要去看了，大概率是你的 effect scope 内引入了很多 rune，可以把这些 rune 删除，或者外面套一层判断。

## k3. writable 慢一拍

writable 的定义的变量在数值发生改变后，你可以通过 subscribe 方法输入自定义的 callback 来捕获这次变化，但是需要注意的是，当 subscribe 方法的 callback 被触发的时候，value 和原本的 rune 并不一样：

```typescript
let shaderMode = writeable('white');

shaderMode.subscribe(value => {
  // 此时的 value 比 $shaderMode 要新
});
```

新值只能拿 value 传递到后续的调用栈。这件事很重要，它会影响前期的架构设计。

## k4. SSR

这个其实不能算坑吧，但是我想记录一下。svelte 也是可以做 SSR 的，而且非常方便，脚手架可以用 svelte-kit 去搭建，搭建 SSR 后，后端都是以 `+layout.server.ts` 为名的文件，它往往对应同级目录下的 `+layout.svelte` 文件。

比如现在有如下两个文件：

```
+layout.server.ts
+layout.svelte
```

它们的内容如下：

```typescript
// +layout.server.ts
import type { LayoutServerLoad } from './$types';

export const load = (async ({ locals }) => {
    // 根据 session 恢复当前用户状态
    const user = ...

    // return 操作的返回值会注入到同级下的 +layout.svelte 和 +page.svelte 中
    return {
        user: user,
    };
}) satisfies LayoutServerLoad;
```

```typescript
// +layout.svelte
<script lang="ts">
  let { data, children } = $props();	
  onMount(() => {
    console.log("Welcome to Seed3D :D");
    // 获取 SSR 发送的 user
    const user = data.user;
  });
</script>

{@render children()}

```

假设它们对应路由 `/hello`，那么当用户访问 `/hello` 时，先会走 +layout.server.ts，这部分在服务器上执行，执行后的结果会注入到 +layout.svelte 后得到最终的 html 发送给用户。


因此，接触到一个陌生的 svelte 项目时，你需要先确认这是否是 SSR，如果是 SSR，那么部分数据流的溯源你就应该知道它是从顶层的 +layout.server.ts 注入的，然后继续找后端的代码。
