## 攻击类型一：XSS攻击

XSS攻击一般指通过将代码注入文本中，让全栈系统的解释器将这部分文本当作代码解释从而对你的网站进行快乐的破坏的行为，这些“解释器”包括但不限于：

- 浏览器的JavaScript解释器。
- 后端解释器（仅限于使用脚本语言开发的后端，比如php, python, js）
- 数据库解释器（MySQL，Redis）

最常见的行为比如：在评论区文本中写入`<script>alert("鸡汤来咯")</script>`。如果浏览器在渲染这段文本时，处理不当会把这个这段文本作为JS代码执行。

alert还算好的，如果有前端大佬分析出了你的项目结构，可以通过DOM操作对你的网站渲染造成严重的破坏，比如我通过F12查看元素知道了你的网页的根元素id是main，而且你的网站没用做XSS预防，那么我就可以在评论区写入以下代码让你的网站在加载完评论区后变得空无一物：

```js
const mainEl = document.getElementById("main");
document.body.remove(mainEl);
```

这样，每次进入网站，你的网站代码就会自己把自己的根元素销毁。

后端解释器则可以通过猜测代码结构来获取id，session等key来让攻击者的权限提高，不过我用的是静态语言，所以这个问题发生的概率不大。所以建议使用静态强类型的语言构建后端，安全性更高。

数据库解释器可玩性就更高了，我们一般把这种XSS攻击叫做SQL注入，比如你通过分析，猜测某个请求背后的数据库操作是：

```sql
match n where n.name="A" set n.id=%d
```

其中`%d`就是前端向后端传递的参数，假设网站开发者用的是脚本语言做的全栈，且没用做运行时的类型检查，那么我们完全可以把前端向后端传递的参数设置为："1 set n.name=\\"xxxxx\\""。这样，实际上的sql执行变为：

```sql
match n where n.name="A" set n.id=1 set n.name="xxx"
```

当然，对于强类型来说，解包GET或者POST请求时都会进行类型检查，因此，这种攻击方式对于后端是强类型运行时类型检查的框架而言，无效。

当然，还有猜测管理员id来将自己ID改成管理员ID从而获得权限提升的。总之，如果后端没用使用数据库框架，没用将得到的参数格式化为对象，那么可操作的空间就非常大。

## 攻击类型二：频繁请求

这个不必多说了，如果你的好朋友对你的某个比较“昂贵”的操作短时间请求很多次，那么可能导致别的用户的请求被阻塞，甚至导致你的服务器瘫痪或者后端进程直接爆炸。从而你的全栈系统会直接下线。

<div align=center>
<img src="https://i0.hdslb.com/bfs/article/8371943096268c8cedef65a952f51bb16076e854.gif" style="width: 60%;"/>
<p class="img-caption">服务器又寄了</p>
</div>

一般的做法有两种，限制某个remote IP在短时间的请求频率，类似于前端的防抖机制，这个要实现也很简单，比如下面就用go实现了一个适配gin框架的，简单的针对单个IP的限制，让单个IP不能在intervalSeconds秒内发起两次请求：

```go
import (
	"time"
	"github.com/gin-gonic/gin"
)

var ipIntervalLimitPool = make(map[string]int64)
var ipIntervalMaxLength = 100

func LimitIpInterval(c *gin.Context, intervalSeconds int64) bool {
	ip := c.ClientIP()
	lastTp, ok := ipIntervalLimitPool[ip]
	currentTp := time.Now().Unix()
	ipIntervalLimitPool[ip] = currentTp

	if !ok {
		ipIntervalLimitPool[ip] = time.Now().Unix()
		return true
	}
	if currentTp - lastTp <= intervalSeconds {
		return false	
	}
	// 及时清理
	if len(ipIntervalLimitPool) > ipIntervalMaxLength {
		for k := range ipIntervalLimitPool {
			delete(ipIntervalLimitPool, k)
		}
	}

	return true
}
```

### 关于DDos

当然，上面的方法对于DDos都没什么用，因为DDos是让一堆IP不同的服务器向你的服务器发送请求，如何辨别请求IP来自DDos集群一直是一个难题，如果你有钱，可以购买IP高防服务器来缓解潜在的DDos服务器。不过一般而言，只要你的网站没用动到其他人的蛋糕，那么一般情况下，没人会闲着没事去花高价买DDos去打你的服务器。有的话，自认倒霉吧。

## 攻击类型三：抓包+代理请求

对于那些熟悉抓包的同学，他们可能会在作业写完后，打开F12，去找你的网站有哪些请求。比如你的发布评论的请求是什么，然后去猜参数，然后伪装成其他用户发表评论。

简而言之，就是对于涉及到写入数据库的暴露请求，一定要设置权限，比如传入发表言论的人的密码，或者使用session。我一开始就偷懒没有给发表评论功能增加权限，因为我以为peacesheep无法获取其他用户的ID。但是事实上，我在其他的接口中向前端暴露了这个接口，所以只要是在评论区现身的用户，都可以通过那个某个潜在API访问，从而伪装成指定用户发表评论。所以，前往不要只将id或者某个令牌作为向后端发送请求的标志。

>  任何涉及到写入数据库的操作请一定显式或隐式地传入权限参数，比如发布者密码（如果你方便拿到的话），sessionId（隐式）

## 攻击类型四：CSRF攻击

**CSRF(Cross-Site Request Forgery)**攻击，我今天第一次遇到，感觉还挺出乎意料的。

举个例子，假设你现在后端有一个发布评论的API：`/api/publish-comment`，这个请求是GET请求，参数为text。它基于隐式传递的sessionId来进行权限验证。你以为这很安全了，毕竟有sessionId保驾护航了，没错，攻击者确实无法主动发起攻击，来伪造你的身份来发送请求了，但是他们可以让你自己发。

假设你的网站支持基于图床链接发送图片，那么攻击者可以这么写评论：

```html
<img src="/api/publish-comment?text=鸡汤来喽"/>
```

那么，当你登入自己的账号，进入评论区后，浏览器在加载上面这句话时，会通过GET请求去获取img的src图源，此时加上域后的请求变成了发表评论，这就会导致你自己无意识地向后端发送了一条发表评论的请求，而且sessionId也会被传递，因此，这条请求是有效的。每一个进入此页面的用户都会“被动地”发送一条“鸡汤来喽”的评论。

之所以会有这个漏洞是因为攻击者巧妙利用了浏览器本身对于部分资源请求的默认行为，比如img是用GET请求获取src渲染的，a标签的`to="_blank"`跳转也会对src使用GET请求，攻击者就可以凭借对浏览器默认行为的理解，将部分操作注入这些链接中，从而让用户被动地使用自己的刀攻击自己的网站。

想要解决CSRF方法也不少，具体可以参考这篇文章：[什么是CSRF？如何防御CSRF攻击？知了堂告诉你 - 知乎 (zhihu.com)](https://zhuanlan.zhihu.com/p/343515825)。此处提一些我个人的心得：

- 争对浏览器的默认行为，避免使用部分请求。涉及到写入数据库的操作，请避免使用GET请求；使用POST请求时，请把参数写入请求体中。
- 可以在请求中带入一个token来动态表示这个请求是用户手动发送的，比如可以是发送的时间戳，后端接受到请求后，检验当前的时间戳和请求中的时间戳间隔是否小于某个值，如果太大，那么直接拒绝服务。
